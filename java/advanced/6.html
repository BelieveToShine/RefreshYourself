What's retained vs. what's stuck — two different snapshots

"You suspect a memory leak vs. a stuck thread — which diagnostic tool do you reach for, and why?"

Why it matters ▾
📸 Heap Dump
❗ Problem"Memory keeps growing" alone doesn't say which object, or which reference chain, is actually responsible — guessing from code review alone is slow and often wrong.
✅ SolutionA heap dump is a snapshot of every live object and their reference graph — load it in a profiler and sort by retained size to see exactly what's holding memory, and through what chain.
RecallHeap dump = what's retaining memory, and why it's still reachable.
🧵 Thread Dump
❗ Problem"Requests are timing out" doesn't say whether threads are deadlocked, blocked on a lock, or the pool simply ran out of workers — and the heap tells you nothing about any of that.
✅ SolutionA thread dump is a snapshot of every thread's stack trace and state at one instant — it shows exactly where each thread is stuck, and (for a deadlock) the circular lock wait itself.
RecallThread dump = who's stuck, and exactly where in the code.
🔥 Easy interview recall

Memory growing → heap dump

App stuck / unresponsive → thread dump

Think: heap dump = a photo of what's being held. Thread dump = a photo of who's holding things up.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Out of memory" is not one error. java.lang.OutOfMemoryError: Java heap space, GC overhead limit exceeded, Metaspace, and unable to create native thread each point at a different root cause — treating them all as "just increase the heap" misses the ones that aren't actually a heap problem.

🔄 Likely Follow-up

"What's actually different about the Metaspace flavor?" It means class metadata itself ran out of room — usually from loading far more classes than expected (dynamic class generation, a classloader leak from repeatedly reloading the same classes), not from too many regular objects on the heap.

🎯 Say this in the interview — the exact lines to land

"A heap dump is a snapshot of every live object and their reference graph — the tool for finding what's retaining memory in a leak. A thread dump is a snapshot of every thread's stack trace and state — the tool for a deadlock, a stuck thread, or thread-pool exhaustion. And OutOfMemoryError has distinct flavors — heap space, GC overhead limit, Metaspace, unable to create native thread — that each point at a different cause."

  • Memory growing over time → take a heap dump, sort by retained size.
  • App unresponsive / timing out → take a thread dump, look for circular waits.
  • Metaspace OOM → too many loaded classes, not too many objects.
  • GC overhead limit exceeded → the GC is running constantly but barely reclaiming anything.
  • unable to create native thread → the OS is out of threads/memory for the process, not the Java heap itself.
📖 Explanation ▾

A heap dump (triggered manually with jmap/jcmd, or automatically on OOM with -XX:+HeapDumpOnOutOfMemoryError) captures every live object at that instant, plus the references between them. Loaded into a profiler, you can sort by retained size (how much memory would be freed if this object were collected) and walk the reference chain back to a GC root — exactly how you'd actually find the leak described on the previous page, rather than guessing from the source.

A thread dump (jstack, or kill -3 / jcmd Thread.print on the running process) captures every thread's current stack trace and state (RUNNABLE, BLOCKED, WAITING, …) at that instant. For a deadlock specifically, the JVM's own deadlock detector often reports the circular "waiting to lock … which is held by …" chain directly in the dump — no manual tracing needed.

OutOfMemoryError isn't one failure mode. Java heap space means object allocation genuinely has nowhere to go. GC overhead limit exceeded means the collector is running almost continuously while reclaiming almost nothing — a symptom of a heap that's nearly full of live (not garbage) data. Metaspace means class metadata itself — not regular objects — ran out of room, often from a classloader leak that keeps reloading classes no one properly discards. Unable to create native thread means the operating system refused a new OS thread for the process — an OS-level resource limit, not the Java heap at all.

💻 See the code ▾
Shell 
# Take a heap dump from a running JVM (find PID with jps)
jmap -dump:live,format=b,file=heap.hprof <pid>

# Auto-dump on the actual OOM, no guessing about timing
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./heap.hprof -jar app.jar

# Take a thread dump from a running JVM
jstack <pid> > threads.txt

Prefer -XX:+HeapDumpOnOutOfMemoryError in production — a manual jmap taken minutes after the fact may already have missed the state that actually caused the failure.

Text 
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x00..., which is held by "Thread-2"
"Thread-2":
  waiting to lock monitor 0x00..., which is held by "Thread-1"

A thread dump's deadlock detector names the exact circular wait — this is the kind of finding a heap dump simply cannot show.

🧭 Use Cases — recognize these when they happen to you ▾
1 Heap usage trends upward over days, then the app crashes with OutOfMemoryError

A slow, steady climb with full-GC collections not bringing it back down is the classic leak signature — a heap dump, sorted by retained size, is the fastest way to name exactly which object and chain is responsible.

RememberDays-long memory growth → heap dump, not thread dump.
2 All requests suddenly stall at once, CPU usage drops to near zero

Low CPU plus total unresponsiveness points at threads waiting on each other, not threads doing expensive work — a thread dump's built-in deadlock detector will usually name the exact circular lock wait directly.

RememberFrozen + idle CPU → thread dump, look for a deadlock.
3 You see "OutOfMemoryError" in the log and assume the heap is simply too small

A candidate often treats every OutOfMemoryError as "the heap is too small, just increase -Xmx." That's not always true — Metaspace and unable to create native thread flavors point at completely different fixes (classloader leak, OS thread limits), and bumping heap size won't touch either one.

RememberRead the exact OOM flavor before assuming "just raise the heap."
🌍 Real-world example ▾

A service's response times degrade over several hours, then it stops accepting new connections entirely. Pulling a thread dump first shows whether every request-handling thread is blocked waiting on the same lock (a contention issue, not a leak) — if threads look healthy and busy instead, a heap dump is the next step, since the real bottleneck is more likely memory pressure triggering constant GC.
