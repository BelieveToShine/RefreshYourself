Most production incidents are infrastructure, not code

An ALB is returning 5xx errors — what do you actually check?

Why it matters ▾

⚠️ Common Trap

Assuming "the app is broken" means a code bug. A large share of production incidents are actually infrastructure or config — security groups, IAM policies, route tables, health checks — and a quick systematic check catches them faster than diving into a code review first.

🔄 Likely Follow-up

"How would you roll back a production deployment that caused failures?" If a blue-green or deployment-slot setup was already in place, swap back immediately — it's near-instant; otherwise, redeploy the last known-good version, AMI, or container image as fast as possible, and root-cause the actual failure separately.

🎯 Say this in the interview — the exact lines to land

"Most production incidents are infrastructure or config, not code — I'd check security groups, IAM, route tables, and health checks systematically before assuming it's a code bug."

  • 502 vs. 504 → different root causes: 502 is the target's own bad response, 504 is the target being too slow to respond.
  • RDS connection failures → check security groups, RDS status, and connection-pool limits together.
  • S3 AccessDenied → check bucket policy, IAM policy, and Block Public Access together, not just one of them.
  • Lambda timing out → check CloudWatch Logs/X-Ray for where the time is actually going, not just raise the timeout.
  • One AZ failing → check whether the app was actually deployed across multiple AZs to begin with.
📖 Explanation ▾

A production alert rarely says what's actually wrong — "the app is down" or "the app is slow" fits a code bug, a bad config, and a dozen other causes equally well. Running a short, systematic infrastructure check first, before opening the code, resolves most incidents faster than a code review does, because most incidents genuinely are infrastructure or config, not a logic bug.

The instinct is the same across every service: don't stop at "it's failing" — ask which specific thing is failing and why. Some of the most common pairings:

  • High EC2 CPU → CloudWatch metrics and recent deploys — is it real load, or a runaway process?
  • RDS connection failures → security groups, RDS instance status, connection limits/pool exhaustion.
  • Private-subnet instance can't reach the internet → the NAT Gateway and its route table.
  • S3 AccessDenied → bucket policy, IAM policy, AND Block Public Access settings together — not just one.
  • Lambda timing out → CloudWatch Logs/X-Ray for where the time is actually going, and whether the timeout setting itself is too low.
  • Lambda receiving duplicate events → expected under at-least-once delivery — check consumer idempotency, not the trigger.
  • SQS messages reappearing → visibility timeout vs. actual processing time.
  • ALB 5xx errors → target group health checks, and whether it's 502 (bad response) or 504 (too slow) — different root causes.
  • One Availability Zone failing → whether the app was actually deployed across multiple AZs to begin with.
  • A sudden billing spike → Cost Explorer broken down by service/resource, for a runaway resource.
🧭 Use Cases — recognize these when they happen to you ▾
1 Your app suddenly can't connect to RDS, and you assume the database itself is down

In most cases RDS itself is healthy — the real cause is a security group not allowing the app's traffic through to RDS's inbound rule, or the connection pool has exhausted RDS's max-connections limit, not an actual database outage.

RememberRDS "down" → check security groups and connection-pool limits before assuming an outage.
2 S3 returns AccessDenied even though you're sure the IAM policy allows the action

The denial can come from the bucket policy, the IAM policy, or Block Public Access — any one of the three can override the others, so checking only the IAM policy misses the actual cause.

RememberS3 AccessDenied → check bucket policy + IAM policy + Block Public Access together, not just one.
3 A Lambda function keeps timing out, and the instinct is to just raise the timeout setting

Raising the timeout just delays the same failure — CloudWatch Logs and X-Ray show where the time is actually going (a slow downstream call, a cold start, throttling), which is what actually needs fixing.

RememberLambda timeout → trace where the time is going first, don't just raise the timeout.
🌍 Real-world example

An ALB suddenly starts returning 502s right after a deploy. The targets are actually healthy and serving real traffic just fine — but the deploy broke the app's own health-check endpoint, so the ALB keeps marking targets unhealthy and cycling them out of rotation. The fix only shows up once someone checks which health check is failing and why, not just confirms that one is failing.
