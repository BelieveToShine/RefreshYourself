watch vs. watchEffect — naming the source, or just reading it

"What's the difference between watch and watchEffect?"

Why it matters ▾
🎯 watch
❗ ProblemReacting to a change often needs to know what it changed FROM, not just that it changed — a user ID switching from 1 to 2 might need the old user's data cleaned up specifically.
✅ Solutionwatch(source, callback) names exactly what to watch and hands the callback both the old and new value, so "what changed from what" is always answerable.
Recallwatch = named source, gives you (newVal, oldVal).
🪄 watchEffect
❗ ProblemAn effect that reads from 3-4 reactive values means writing a watch with an awkward combined source just to react to any of them changing.
✅ SolutionwatchEffect(fn) runs immediately and auto-tracks whatever reactive values it reads inside itself, re-running whenever any of them change — no source to declare at all.
RecallwatchEffect = runs itself, figures out its own dependencies by reading them.
🔥 Easy interview recall

watch → named source, gets old + new value

watchEffect → auto-tracks whatever it reads, no old value

Think: watch asks "did THIS change?" watchEffect asks "did anything I touched change?"

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

watchEffect cannot give you the previous value — structurally, not just by convention. If "what changed from what" matters, watch is the only option; reaching for watchEffect here means rebuilding the old value yourself with a separate variable.

🔄 Likely Follow-up

"Does watchEffect run on initial setup?" Yes — immediately once, then again on every dependency change. watch only runs on change by default, unless given { immediate: true }.

🎯 Say this in the interview — the exact lines to land

"watch(source, callback) explicitly names what to watch and gives me both the old and new value. watchEffect(fn) runs immediately and automatically tracks whatever reactive values it reads inside itself, re-running on any of their changes — no explicit source, no access to the old value."

  • watch → named source, gives (newVal, oldVal).
  • watchEffect → auto-tracked dependencies, runs immediately too.
  • Need the old value → only watch can give it to you.
  • Reading 3+ reactive sources together → watchEffect avoids an awkward combined source.
📖 Explanation ▾

watch takes an explicit source — a ref, a reactive property getter, or an array of them — and a callback that only runs when that specific source changes. The callback receives both the new and old value, which is exactly why watch exists whenever "what changed from what" is the actual question.

watchEffect takes just a function and runs it right away. Vue tracks every reactive value the function reads DURING that run, and re-runs the whole function again whenever any of those tracked values change — there's no list of dependencies to write by hand, Vue discovers them by watching what you actually touch.

Because watchEffect re-runs the whole function rather than diffing a value, it has nothing to compare against — there's no "old" version of the function's own prior run to hand you. That's a structural fact, not a missing option.

💻 See the code ▾
Vue 
import { watch, ref } from 'vue'

const userId = ref(1)

watch(userId, (newId, oldId) => {
  console.log(`changed from ${oldId} to ${newId}`)   // ✅ both values
})

Only watch can tell you what it used to be.

Vue 
import { watchEffect } from 'vue'

watchEffect(() => {
  console.log(userId.value, page.value)   // ✅ both auto-tracked, no source list
})                                         // runs once immediately too

Reading userId.value and page.value inside the function is what registers them — no array to maintain.

🧭 Use Cases — recognize these when they happen to you ▾
1 Cleaning up the PREVIOUS item before loading the new one

Switching a live subscription (a chat room, a websocket channel) needs the old id to tear down cleanly before the new one opens — only watch hands you that old value directly.

RememberTeardown the old, set up the new → watch, for the old value.
2 Syncing a derived DOM effect (document title, scroll position) to several reactive values

watchEffect(() => document.title = `${title} (${count})`) auto-tracks both title and count just by reading them — no array of sources to keep in sync with the function body.

RememberEffect reads multiple values → watchEffect skips the combined-source dance.
🌍 Real-world example ▾

A search page re-fetching results every time the query or the selected filter changes. watchEffect reading both query.value and filter.value inside one fetch function reacts to either changing, without manually listing both as a combined watch source.
