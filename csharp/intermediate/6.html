Equals() and GetHashCode() — a contract that breaks silently if you get it wrong

"Why must GetHashCode() be overridden whenever Equals() is?"

Why it matters ▾
🟰 Equals()
❗ ProblemA hash-based collection lets more than one object land in the same bucket on purpose — a collision — so something still has to tell which of those candidates is the real match.
✅ SolutionEquals() is that check — the collection calls it against every object already in the bucket instead of scanning the whole collection.
RecallEquals() finds the real match — only after GetHashCode() has already picked the bucket.
#️⃣ GetHashCode()
❗ ProblemA Dictionary/HashSet computes an object's bucket exactly once, at insert time — if that value ever changed afterward, no future lookup would check the bucket the object is actually sitting in.
✅ SolutionGetHashCode() must return the same value for anything Equals() calls equal, and it's only safe to base it on fields that stay fixed after insertion.
RecallGetHashCode() picks the bucket once, at insert — build it only from fields that never change.
🔥 Easy interview recall

Equal objects = "must always produce equal hash codes."

Think: Equals → same hash, guaranteed. Same hash → not guaranteed equal — collisions are fine.

⚠️ Common Trap

GetHashCode() isn't a one-time calculation you can forget about. If it reads a mutable field and that field changes after insertion, the Dictionary/HashSet computes a new bucket on every future lookup while the object stays put in the old one — permanently unreachable, with no exception thrown.

🔄 Likely Follow-up

"If you already override Equals(object), why also implement IEquatable<T>?" IEquatable<T> gives a strongly-typed Equals(T) that skips the cast and boxing check the object override needs — you still keep the object override for callers that only have an object reference.

🎯 Say this in the interview — the exact lines to land

"Equals() and GetHashCode() are one contract: if two objects are equal, they must return the same hash code, or hash-based collections like Dictionary and HashSet will silently fail to find them."

  • Equal objects must return equal hash codes — that direction of the rule is non-negotiable.
  • Equal hash codes don't mean the objects are equal — collisions are expected and already handled.
  • Base GetHashCode() only on immutable fields — a mutable one can strand the object in a stale bucket.
  • A record (or a readonly struct) keeps both methods built from the same fields automatically, so they can't drift apart.
📖 Explanation ▾

Hash-based collections (Dictionary<TKey,TValue>, HashSet<T>) never scan every entry to find a match — they call GetHashCode() once to pick a bucket, then only run Equals() against whatever already lives in that bucket. That's the entire reason the contract exists: if two objects Equals() considers the same land in different buckets because their hash codes disagree, the collection never even looks in the right place to compare them.

The relationship only has to hold in one direction. Equal objects must produce equal hashes — but two unequal objects sharing a hash is completely normal; that's a collision, and every hash-based collection already falls back to Equals() inside a bucket to sort collisions out. The real bug isn't collisions — it's an object whose hash silently changes after the fact.

That's what makes a mutable hash field dangerous. A Dictionary/HashSet computes an object's bucket exactly once, at insert time, and never revisits it. Mutate a field GetHashCode() depends on afterward, and every future lookup recomputes a different bucket — the object is still physically sitting in the old one, just permanently invisible to Contains(), indexers, and removal alike.

💻 See the code ▾
C# 
public override bool Equals(object? obj) =>
    obj is Point p && X == p.X && Y == p.Y;

public override int GetHashCode() =>
    HashCode.Combine(X, Y);   // ✅ same fields Equals() uses

Both methods are built from the exact same fields — that's the whole contract in one line.

C# 
var set = new HashSet<Order>();
var o = new Order { Status = "Open" };
set.Add(o);                // hashed while Status = "Open"

o.Status = "Closed";         // ❌ mutates a field GetHashCode() reads
set.Contains(o);           // ❌ false — looks in the wrong bucket now

Same reference, same object — but the set can no longer find it. No exception, just a wrong answer.

C# 
public sealed record Order(string Status);
// ✅ compiler-generated Equals()/GetHashCode(), always in sync

A record (or a readonly struct) removes the mutable field entirely — nothing left to drift.

🧭 Use Cases — recognize these when they happen to you ▾
1 You use an immutable key — like a record — in a Dictionary or HashSet

Equals() and GetHashCode() stay built from the same fields for the whole lifetime of the key, so the hash computed at insert time still matches on every later lookup — Contains(), indexers, and removal all keep finding it exactly as expected. This is the #1 scenario you'll actually run into.

RememberImmutable key, matching Equals/GetHashCode → lookups just work.
2 You override Equals() to compare by value, but never touch GetHashCode()

Left at its default, GetHashCode() is based on the object's own identity, not the fields Equals() now compares — so two objects Equals() considers the same can still hash differently, and the collection never even looks in the same bucket to compare them.

RememberOverride one without the other → the contract breaks, silently.
3 You mutate a field GetHashCode() reads after the object is already inserted

The Dictionary/HashSet already computed this object's bucket once, at insert time, and never revisits it. From this point on, every lookup checks the new (wrong) bucket while the object itself is still sitting, unmoved, in the old one — no exception is thrown, the entry just silently can't be found. A great interview trap — candidates often assume a missing entry would at least throw.

RememberMutate a hashed field after insertion → object goes missing, no exception.
🌍 Real-world example ▾

You cache open orders in a Dictionary<Order, Summary> keyed by the order object itself. Later, some other code updates that order's Status field in place. From then on, dict.TryGetValue(thatSameOrder, ...) returns false — the entry never disappeared, the dictionary is just checking a bucket the object no longer hashes to. The fix isn't a smarter lookup; it's never hashing on a field that can change after insertion.
