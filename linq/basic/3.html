Where(...).First() vs. First(predicate) — same result, so why pick one?

"list.Where(x => ...).First() vs. list.First(x => ...) — do they behave the same, and does it matter which you write?"

Why it matters ▾
🔍 Where(...).First() vs. First(predicate)
❗ ProblemIt looks like Where(...).First() must build a filtered list first, then grab the first entry — and so it looks slower than First(predicate), which seems to go straight to the answer.
✅ SolutionWhere is lazily evaluated — it streams one element at a time, never building an intermediate list. Both forms stop scanning at the exact same first match; the real reason to prefer First(predicate) is that one call states the intent directly.
RecallBoth forms stream and stop at the same element — First(predicate) wins on clarity, not speed.
🔥 Easy interview recall

Where(...).First() and First(predicate) stop at the same element — both are lazy, neither builds a filtered list first.

Think: pick First(predicate) for clarity, not speed — over IEnumerable<T> there's nothing measurable to win.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming Where(...).First() silently builds a full filtered list before First() runs. It does not — Where is lazy and streams one element at a time, so both forms short-circuit at the exact same point.

🔄 Likely Follow-up

"Does that still hold for an IQueryable over EF Core?" Yes, in effect — both forms translate to equivalent SQL (a WHERE clause plus a row-limiting construct). Neither reliably produces cheaper SQL than the other, so don't treat this as a performance decision there either.

🎯 Say this in the interview — the exact lines to land

"Where(...).First() and First(predicate) return the same element and scan the same way — Where streams lazily, so both stop at the first match without building an intermediate list. I'd reach for First(predicate) for clarity, not because it's faster."

  • Where(...).First() → same short-circuit — Where streams one element at a time.
  • First(predicate) → clearer intent, one call instead of two.
  • Over IQueryable → both forms translate to equivalent SQL — neither is reliably faster.
📖 Explanation ▾

Over IEnumerable<T>, Where doesn't run eagerly. It returns a deferred pipeline that yields one element at a time as something else pulls from it — First() pulls exactly until it gets one match, then stops. No intermediate filtered list ever gets built, so Where(...).First() and First(predicate) walk the same elements and stop at the same one.

What actually differs is what the call says. First(predicate) reads as a single intent — "give me the first match" — while Where(...).First() reads as two steps even though it runs as one streamed pass. Prefer First(predicate) when the predicate is the only thing between you and the answer; keep Where explicit when something else needs to sit in the chain first (sorting, projecting, another filter).

💻 See the code ▾
C# 
var firstBig = numbers
    .Where(x => x > 5)
    .First();   // streams, stops at the first match — no intermediate list

Two operators, one streamed pass — Where never materializes anything.

C# 
var firstBig = numbers.First(x => x > 5);  // ✅ same element, one call

Same result, same scan order — just stated as one direct intent.

🧭 Use Cases — recognize these when they happen to you ▾
1 A single condition, nothing else in the chain

When the filter is the only thing standing between you and the answer, First(predicate) is the idiomatic, direct way to write it. This is the #1 case you'll actually reach for it.

RememberOne condition, nothing else → First(predicate).
2 Other operators sit between the filter and the result (e.g. a sort)

First(predicate) can only express a single trailing filter — it can't fold in a sort or a second filter. The moment anything else needs to sit in the chain, Where has to stay explicit, with First() just ending the pipeline.

RememberExtra operators in between → keep Where explicit.
3 You benchmark the two forms expecting a clear winner

Both forms funnel through the same lazy enumeration (or, over IQueryable, the same provider translation). A microbenchmark comparing them is likely to show noise-level differences, not a real winner — treat this as a style choice, not a performance one.

RememberNo measurable winner → pick by clarity, not a benchmark.
🌍 Real-world example ▾

It's like asking for "the first email from Sam" two ways — filtering your inbox down to Sam's messages and taking the top one, or scanning with "first email from Sam" as a single instruction. You look at messages in the exact same order either way; only the phrasing of the request differs.
