LINQ — when does the query actually run?

"When does a LINQ query actually run?"

Why it matters ▾
⏳ Deferred execution
❗ ProblemAssuming Where/Select already filtered the data lets the same query silently rebuild and re-run against the whole source on every single enumeration — inside a loop, that turns one cheap check into a repeated full scan on every iteration.
✅ SolutionDeferred operators (Where, Select, OrderBy, GroupBy) just wrap the source in a plan that remembers how to filter — nothing touches the source until something actually enumerates it, and each enumeration walks it fresh.
RecallDeferred = builds a plan now, runs it later, every time it's enumerated.
▶️ Immediate execution
❗ ProblemA deferred query re-runs on every enumeration, so on its own it can never serve as a stable, fixed snapshot — anything that needs a result set that won't shift under it later needs more than Where/Select alone.
✅ Solution.ToList(), .ToArray(), and .Count() force that walk to happen right away and hand back a real, fixed collection — call one once, right where a stable snapshot is actually needed.
RecallImmediate = runs the moment the call executes, and freezes the result.
🔥 Easy interview recall

Where / Select → builds the query, nothing runs

foreach / .ToList() → runs it, right now

Think: a LINQ query is a recipe, not a meal — nothing happens until something actually enumerates it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

var query = list.Where(...) does not run the filter. query only holds a recipe for later — the filter runs fresh every time something enumerates it, which is exactly why the same query variable can hand back different results the second time.

🔄 Likely Follow-up

"What breaks if the same deferred query is enumerated twice while its source changed in between?" Nothing breaks technically — each enumeration re-runs the query against the source's current state, so the two results can legitimately differ; that's expected behavior, not a bug.

🎯 Say this in the interview — the exact lines to land

"A LINQ query built with Where or Select is deferred — it doesn't run when it's written. It only executes when something enumerates it, like a foreach or .ToList(). Because of that, the same query variable can produce different results each time it's enumerated, if the source changed in between."

  • Where / Select → builds the query, doesn't touch the source yet.
  • foreach / .ToList() / .Count() → triggers execution, right then.
  • Same query, enumerated twice, source changed between → two different results — expected, not a bug.
  • Query re-built inside a loop → materialize once with .ToList() before the loop starts.
📖 Explanation ▾

Deferred LINQ operators — Where, Select, OrderBy — don't touch the source when that line runs. They just wrap it in a small object that remembers how to filter or project, once something actually asks for the items.

That's why var query = list.Where(...) is really a plan, not a result set. Every enumeration — a foreach, a .ToList(), even a second one on the exact same variable — walks the source again, live, right then. If the list changed in between, the second walk sees the new list.

.ToList(), .ToArray(), and .Count() are immediate — they force that walk to happen right there and hand back a real, fixed collection. Call one of those once, right where a stable snapshot is actually needed, and everything built on top of the result reads from that snapshot, not the live source.

💻 See the code ▾
C# 
var query = list.Where(p => p.InStock);   // builds the query — nothing runs yet
Console.WriteLine("query created");        // ✅ prints immediately — the filter hasn't touched an item

Assigning a LINQ query to a variable doesn't run it — query is a plan, not a result.

C# 
var results1 = query.ToList();   // 1st enumeration — filter runs NOW
list.Add(new Product { InStock = true });
var results2 = query.ToList();   // 2nd enumeration — runs AGAIN, sees the new item

Same query variable, same line of code — but each .ToList() re-runs the filter against whatever the source looks like at that exact moment.

C# 
foreach (var _ in Enumerable.Range(0, 1000))
{
    var expensive = data.Where(SlowCheck);  // ❌ rebuilt AND re-run every iteration
}

var expensive = data.Where(SlowCheck).ToList();  // ✅ materialized once, before the loop
foreach (var _ in Enumerable.Range(0, 1000))
{
    // reuse `expensive` here — no re-filtering
}

Pulling .ToList() out of the loop, once, is the fix — the query stops re-running the expensive filter on every pass.

🧭 Use Cases — recognize these when they happen to you ▾
1 You store a LINQ query in a variable and treat it like it's already the filtered results

Nothing has touched the source yet — query is only a plan. The filter doesn't run until something actually enumerates it, like a foreach or a .ToList() later in the method.

RememberAssigning a query ≠ running it — only enumeration runs it.
2 You build a LINQ query fresh inside a loop that runs many times

It's easy to assume a query only really "runs" once, the way a normal method call would — but a deferred query re-executes in full on every enumeration, loop iteration included. Rebuilding it inside a 1,000-iteration loop reruns the filter 1,000 times, turning a cheap check into a full O(n × iterations) scan.

RememberQuery inside a loop → pull .ToList() out before the loop runs.
3 You need to hand a stable, fixed result set off to something else

.ToList() forces the walk to happen right there and hands back a real, fixed collection — pass that along instead of the raw query, and whatever receives it reads from that frozen snapshot, not the live, still-changing source.

RememberNeed a stable result → materialize once with .ToList()/.ToArray().
🌍 Real-world example ▾

A report job builds a LINQ query once, then calls it inside a loop that runs a thousand times, expecting the filter to have already happened. It hasn't — every iteration re-walks the whole source and reapplies the filter, turning a cheap O(n) operation into an O(n × iterations) one. The fix is one line: pull .ToList() out of the loop and materialize the query once, before it starts.
