Your app is slow on Azure — what do you check, and in what order?

What performance improvements would you make to a slow application running on Azure?

Why it matters ▾
📊 Measure First
❗ ProblemScaling up, adding a cache, or moving to a bigger SKU is a guess if you don't actually know whether the slow part is a database call, an external dependency, CPU, or memory — and guessing wrong wastes both time and money.
✅ SolutionApplication Insights and Azure Monitor show the real end-to-end breakdown — which dependency call is slow, which endpoint is the problem, and whether it's CPU, memory, or something downstream — before you spend effort fixing the wrong thing.
RecallMeasure with Application Insights/Azure Monitor before you touch anything else.
⚙️ Right-Size & Autoscale
❗ ProblemA fixed App Service plan, VM size, or AKS node pool sized by guesswork either sits over-provisioned most of the time, or falls over the moment real traffic exceeds what was guessed.
✅ SolutionMatch the plan/VM/node pool size to the load you actually measured, then add autoscale rules tied to real metrics like CPU or queue length so capacity tracks real demand instead of sitting at a fixed number.
RecallSize for the load you measured, then let autoscale rules handle the rest.
⚡ Cache Above the Database
❗ ProblemRead-heavy, rarely-changing data hitting the database on every request keeps re-running the same expensive query for the same answer, over and over.
✅ SolutionAzure Cache for Redis sits in front of the database and serves that same answer from memory, removing the repeat load entirely for anything cacheable.
RecallRedis in front of read-heavy data → the database stops seeing the repeat traffic.
🌍 Push Content to the Edge
❗ ProblemA user far from the app's primary region pays for that physical distance on every request, even for content that never actually changes.
✅ SolutionAzure CDN or Azure Front Door caches static and cacheable content at edge locations closer to users, so distant users stop paying the full round-trip to the primary region.
RecallFar-from-region latency → serve it from the edge instead.
🗄️ Database-Level Tuning
❗ ProblemThe app's own code can be fine and the app still feels slow if the database tier is undersized for the real workload, or queries are missing the indexes they need.
✅ SolutionRight-size the service tier/compute to the actual workload, add read replicas or geo-replication to offload read traffic, and apply the same indexing/query fundamentals as any SQL database.
RecallA slow database isn't always the app's fault — check tier size, replicas, and indexes too.
📬 Decouple With a Queue
❗ ProblemA traffic spike that has to be processed synchronously forces the backend to scale instantly to match it, which is expensive and still risks falling behind.
✅ SolutionService Bus or Storage Queues absorb the spike and let backend processing catch up asynchronously, so the system doesn't need to scale synchronously to match every burst.
RecallA queue turns "scale instantly or fall behind" into "catch up when ready."
🔥 Easy interview recall

📊 Measure → App Insights/Monitor finds the real bottleneck

⚙️ Right-size & autoscale → match compute to real load

⚡ Cache → Redis removes repeat database load

🌍 Edge → CDN/Front Door cuts latency for distant users

Think: profile first — whichever lever actually matches the measured bottleneck is the right one, not whichever is easiest to reach for.

⚠️ Common Trap

Scaling up or out without measuring first is the common mistake. If the real bottleneck is a slow dependency call or a missing index, throwing more compute at it doesn't fix anything — it just costs more while the app is still slow.

🔄 Likely Follow-up

"Say Application Insights points at the database — what's the actual fix?" Right-size the tier to the real workload, add read replicas for read-heavy traffic, and apply standard indexing/query tuning — the same database fundamentals as any SQL database, not an Azure-specific trick.

🎯 Say this in the interview — the exact lines to land

"I'd start with Application Insights and Azure Monitor to find the actual bottleneck, then right-size and autoscale compute to match real load, add Azure Cache for Redis in front of the database, and use a CDN or Front Door for users far from the primary region — database tuning and a queue come in for data-heavy or bursty-traffic cases specifically."

  • Application Insights/Azure Monitor → use first, always — find the real bottleneck before changing anything.
  • Right-size & autoscale → use when compute is the bottleneck or load varies over time.
  • Azure Cache for Redis → use when the same read-heavy data is hit repeatedly.
  • CDN/Front Door → use when users far from the primary region feel the latency.
  • Database tuning (tier, replicas, indexes) → use when the database itself is the measured bottleneck.
  • Service Bus/queue → use when bursty traffic needs to be absorbed instead of scaled synchronously.
📖 Explanation ▾

Measuring first is what turns "make it faster" from a guess into a plan. Application Insights and Azure Monitor show exactly where time is actually going — a slow dependency call, a specific slow endpoint, or real CPU/memory pressure — so the next step targets the real bottleneck instead of whichever fix sounds most obvious.

Once the bottleneck is known, the fix is usually one of: compute (right-size the plan/VM/node pool, then autoscale against real metrics instead of a fixed size), caching (Azure Cache for Redis removes repeat load from the database for anything read-heavy and rarely changing), the edge (Azure CDN or Azure Front Door serves cacheable content closer to distant users), or the database itself (the right tier, read replicas/geo-replication for read traffic, and ordinary indexing/query tuning — the same fundamentals that apply to any SQL database).

A traffic spike is a different shape of problem than steady slowness: instead of scaling synchronously to match every burst, a queue (Service Bus or Storage Queues) absorbs the spike and lets backend processing catch up asynchronously. And for Azure Functions specifically, cold starts on the Consumption plan can matter for latency-sensitive scenarios — a Premium or Flex Consumption plan trades extra cost for pre-warmed instances, but it's a narrower, Functions-specific case next to the levers above.

💻 See the code ▾
C# 
var cached = await cache.GetStringAsync(key);   // ✅ try Redis first
if (cached != null)
    return JsonSerializer.Deserialize<Product>(cached);

var product = await db.Products.FindAsync(id);  // ❌ only on a cache miss
await cache.SetStringAsync(key, JsonSerializer.Serialize(product),
    new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10) });
return product;

Cache-aside with Redis: read from the cache first, only hit the database on a miss, and refill the cache with a short expiry.

CLI 
az monitor autoscale create \
  --resource-group myRG --resource myAppServicePlan \
  --resource-type Microsoft.Web/serverfarms \
  --min-count 2 --max-count 10 --count 2   // ✅ ties capacity to real demand

az monitor autoscale rule create \
  --resource-group myRG --autoscale-name myAppServicePlan \
  --condition "CpuPercentage > 70 avg 10m" --scale out 1

An autoscale rule tied to a real metric (here, average CPU) instead of leaving the plan at a fixed, guessed size.

🧭 Use Cases — recognize these when they happen to you ▾
1 An App Service instance is maxed out on CPU during a traffic spike

Before just scaling the plan up, check Application Insights for the actual cause — a dependency call waiting on a slow database, or genuine CPU-bound work. If it's the database, scaling the App Service plan alone won't fix it.

RememberMaxed-out CPU still needs a diagnosis before a bigger plan is the answer.
2 Users far from the primary region report slow page loads

This is a distance problem, not a compute problem — scaling the app up won't shorten the physical round trip. Azure CDN or Azure Front Door caches the cacheable content at an edge location close to that user instead.

RememberDistance problem → edge/CDN fix, not a bigger App Service plan.
3 The database's CPU is pegged and queries feel slow even though the app server has headroom

The app server having headroom rules out compute as the bottleneck — the database itself is the lever here. Check the service tier against the real workload, consider a read replica for read-heavy traffic, and look for missing indexes on the queries actually running.

RememberApp server headroom + slow queries → look at the database, not the app.
🌍 Real-world scenario ▾

A checkout endpoint slows down during a flash sale. Application Insights shows most of the time is inside a dependency call to the database, not app-server CPU — so the first fix isn't a bigger App Service plan, it's the database: right-size the tier for the new load and confirm the hot queries are actually indexed.

Separately, the product-catalog pages being read far more than they're written are moved behind Azure Cache for Redis, which takes that repeat read traffic off the database entirely. And because the order-placement burst itself is spiky rather than sustained, order processing is handed to a Service Bus queue — orders are accepted immediately and processed as capacity allows, instead of needing the checkout path to scale synchronously to match the sale's peak.
