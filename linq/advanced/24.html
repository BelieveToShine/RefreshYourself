Deduping by two fields — which of these four actually fits?

"Given a list of orders that needs deduplicating by a business rule — say, one order per (CustomerId, OrderDate) combination — which of these four approaches would you reach for?"

Why it matters ▾
🧹 Four Ways to De-dup, One Right Fit
❗ ProblemAll four options can deduplicate the same list of orders by (CustomerId, OrderDate) — reaching for whichever one you remember first can mean writing a whole comparer class for a one-off rule, or losing information (like duplicate counts) you'll need two lines later.
✅ SolutionMatch the tool to what else the task needs: DistinctBy for a clean single derived key, GroupBy when you also need to know how many duplicates existed, a named comparer class when the same rule gets reused across several operators, and plain Distinct with an inline comparer only for a true one-off.
RecallPick by what you need besides the dedup — a count, reuse, or just a one-off key.
🔥 Easy interview recall

DistinctBy(key) → cleanest for one derived key

GroupBy().Select(First) → keeps the count per group

Named comparer class → reused across several operators

Think: DistinctBy is the one-liner. GroupBy is the one that remembers how many. A named comparer is the one worth writing once and reusing.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Distinct() can take a key selector like DistinctBy." Plain Distinct() only compares whole elements (or a full custom IEqualityComparer<T>) — it has no key-selector overload; that convenience belongs to DistinctBy specifically.

🔄 Likely Follow-up

"Which of these runs fastest?" All four are roughly the same O(n) hashing-based approach under the hood — the real difference isn't speed, it's what information survives the dedup (a count, in GroupBy's case) and how much boilerplate it costs to express a multi-field rule.

🎯 Say this in the interview — the exact lines to land

"For a one-off multi-field key I'd reach for DistinctBy — it's the cleanest one-liner since .NET 6. I'd only drop to GroupBy if I also needed the duplicate count per group, and only write a named IEqualityComparer<T> class if that same equality rule needs to be reused across more than one LINQ operator in the codebase."

  • DistinctBy(key) → the cleanest one-liner for a single derived key, no class needed.
  • GroupBy().Select(g => g.First()) → use when you also need the per-group count, not just the first item.
  • Named comparer class → worth it when reused across Distinct/GroupBy/Join/set operators.
  • Plain Distinct() → needs a comparer class for anything beyond whole-element equality.
📖 Explanation ▾

Distinct() only ever compares whole elements using Equals/GetHashCode, or a custom IEqualityComparer<T> passed in — it has no built-in way to say "equal by just these two fields." Expressing the (CustomerId, OrderDate) rule through Distinct() means writing a small class whose whole job is that one comparison.

DistinctBy (.NET 6+) removes that ceremony entirely — a key selector like o => (o.CustomerId, o.OrderDate) says the same rule in one line, using a tuple as the key, with no comparer class in sight. It's the right default for a single derived key with no other requirements.

GroupBy earns its place specifically when the dedup needs to know how many duplicates existed — grouping keeps the full group around, so g.Count() is available alongside g.First(), something neither Distinct() nor DistinctBy can answer after the fact, since both have already thrown the extra rows away by the time they return. A named comparer class is worth the extra file specifically when that same equality rule needs to be reused across Distinct, GroupBy, Join, or a set operator elsewhere in the codebase — one definition instead of restating the rule as an inline lambda every time.

💻 See the code ▾
C# 
var deduped = orders.DistinctBy(o => (o.CustomerId, o.OrderDate));
// ✅ one line, tuple key, no comparer class

The cleanest option for a single derived key — this is the first thing to reach for.

C# 
var grouped = orders
    .GroupBy(o => (o.CustomerId, o.OrderDate))
    .Select(g => new { First = g.First(), DuplicateCount = g.Count() });
// ✅ keeps the duplicate count — Distinct/DistinctBy can't answer this

Reach for GroupBy only when the count itself matters, not just the first match.

C# 
class OrderKeyComparer : IEqualityComparer<Order>
{
    public bool Equals(Order a, Order b) =>
        a.CustomerId == b.CustomerId && a.OrderDate == b.OrderDate;
    public int GetHashCode(Order o) => HashCode.Combine(o.CustomerId, o.OrderDate);
}
// ✅ reusable across Distinct(), GroupBy(), Join(), and the set operators

Worth writing once this rule is needed by more than one operator in the codebase.

🧭 Use Cases — recognize these when they happen to you ▾
1 A one-off report just needs one order per customer/date combination, nothing else

This is the #1 scenario in practice: a single derived key, used once. DistinctBy says exactly that in one line, with no comparer class to maintain for a rule that's only used here.

RememberSingle key, used once → DistinctBy, no class needed.
2 The business also wants to flag customers who placed more than one order on the same date

The moment "how many duplicates" becomes part of the requirement, Distinct/DistinctBy can't answer it — they've already discarded the extra rows. GroupBy keeps the whole group around specifically so g.Count() is still there to check.

RememberNeed the duplicate count → GroupBy, not Distinct/DistinctBy.
3 The same (CustomerId, OrderDate) equality rule is needed for Distinct, a Join, and a set-difference check elsewhere in the same service

Restating the same inline lambda key in three different places is a maintenance risk — if the business rule changes, all three call sites have to be found and updated together. A single named IEqualityComparer<T> class fixes that: one definition, reused everywhere the rule applies.

RememberSame rule, multiple operators → a named comparer class pays for itself.
🌍 Real-world example ▾

A nightly reconciliation job needs to collapse duplicate order rows down to one per customer/date, and separately report how many duplicates it found for an audit log. DistinctBy alone can't answer "how many" — it's already discarded the extras by the time it returns. GroupBy(o => (o.CustomerId, o.OrderDate)) followed by Select(g => new { First = g.First(), Count = g.Count() }) keeps both answers in one pass.
