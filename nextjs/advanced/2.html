revalidateTag vs. revalidatePath vs. router.refresh() — which cache do they actually touch?

"What's the difference between revalidateTag, revalidatePath, and router.refresh()?"

Why it matters ▾
🏷️ revalidateTag
❗ ProblemThe same data (e.g. "posts") is fetched by several different pages — invalidating each page one by one after an edit is easy to forget one of.
✅ SolutionrevalidateTag('posts') invalidates every cached fetch() tagged 'posts', wherever it was used, in one call.
RecallrevalidateTag = invalidate by data, across every page that used it.
🛣️ revalidatePath
❗ ProblemOne specific route's rendered output is stale and you know exactly which URL — tagging every fetch on that page is more setup than the situation needs.
✅ SolutionrevalidatePath('/blog/post-1') clears the Full Route Cache for that one path directly.
RecallrevalidatePath = invalidate by URL, one specific route.
💻 router.refresh()
❗ ProblemAfter a client-side action, the user needs the current route's data re-fetched — but a full page reload would blow away scroll position and unrelated form state.
✅ Solutionrouter.refresh() re-fetches the current route from the client and updates the Router Cache, with no full reload.
Recallrouter.refresh() = client-side refresh of the Router Cache only.
🔥 Easy interview recall

revalidateTag → by data, every page using that tag

revalidatePath → by URL, one route's Full Route Cache

router.refresh() → client-only, Router Cache, no reload

Think: the first two run on the server and bust server caches. router.refresh() never leaves the browser.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

router.refresh() does not bust the server caches. It only re-fetches and updates the client-side Router Cache — the server's Data Cache and Full Route Cache still need revalidateTag/revalidatePath to actually clear.

🔄 Likely Follow-up

"Why would you tag a fetch call instead of just using revalidatePath?" Tags let you invalidate data used across multiple different routes in one call — revalidatePath only targets one specific path's own cache entry.

🎯 Say this in the interview — the exact lines to land

"revalidateTag invalidates every cached fetch tagged with that string, wherever it's used; revalidatePath invalidates the Full Route Cache for one specific path; router.refresh() is client-side only — it re-fetches the current route and updates the Router Cache, without a full reload."

  • revalidateTag('x') → targets data, fans out to every page that tagged a fetch with it.
  • revalidatePath('/x') → targets one route's Full Route Cache, nothing else.
  • router.refresh() → client-only, never touches the server cache, preserves scroll/state.
  • After a mutation → call revalidateTag/Path from the Server Action, not from the client.
📖 Explanation ▾

revalidateTag and revalidatePath both run server-side and both clear real server cache entries, but they key on different things: a tag is attached to individual fetch() calls via {next:{tags:[...]}} and can span any number of routes, while a path targets the Full Route Cache for exactly one URL (optionally including its layout). Calling either one is typically done from inside a Server Action, right after the mutation that made the old data wrong.

router.refresh() is a different kind of tool entirely — it's a client-side API that asks the current route to re-render with fresh data, without throwing away client state like scroll position or inputs in components that didn't change. It updates the Router Cache for the route you're currently on; it has no way to reach into the server's Data Cache or Full Route Cache at all.

In practice the two layers cooperate: a Server Action calls revalidateTag/revalidatePath to fix the server-side truth, and the client often follows up with router.refresh() (or Next.js triggers it automatically after a Server Action completes) so the current view picks up the now-fresh data immediately.

💻 See the code ▾
JavaScript 
// app/actions.js
'use server';
import { revalidateTag } from 'next/cache';

export async function updatePost(id, data) {
  await db.posts.update(id, data);
  revalidateTag('posts'); // ✅ hits every page that tagged a fetch 'posts'
}

Every route that fetched 'posts' with next:{'{'}tags:['posts']{'}'} gets invalidated — the Server Action never needs to know which routes those are.

JavaScript 
// client component
'use client';
import { useRouter } from 'next/navigation';

const router = useRouter();
function onRetry() {
  router.refresh(); // ❌ does NOT call revalidateTag/Path for you
}

router.refresh() only re-reads whatever the server caches already say right now — it can't force a server cache that's still fresh to change.

🧭 Use Cases — recognize these when they happen to you ▾
1 The same data feeds several different routes

Reach for revalidateTag whenever more than one route depends on the same underlying data — it's the only one of the three that fans out by data rather than by URL.

RememberShared data, many routes → tag it once, invalidate once.
2 You know the exact single URL that went stale

No tagging needed — revalidatePath is the simpler, direct tool when exactly one route's Full Route Cache is the thing that needs to go.

RememberKnow the exact URL → revalidatePath, no tag plumbing required.
3 You call router.refresh() hoping it busts the server cache too

The server's Data Cache and Full Route Cache are completely unaffected by this call. A common interview trap: assuming "refresh" means "revalidate everywhere."

Rememberrouter.refresh() ≠ server-side invalidation.
🌍 Real-world example ▾

Your service is leaking stale likes-counts on a social feed. The like button's Server Action updates the database and calls revalidateTag('post-likes') — every card on every page that rendered that post picks up the new count on its next fetch. The client that clicked "like" then calls router.refresh() so its own current view updates immediately too, without a full page reload.
