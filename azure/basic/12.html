Application Insights — telemetry you didn't have to write code for

"What is Application Insights, and what does it capture?"

Why it matters ▾
  • Comes up the moment monitoring, observability, or "how would you debug a slow request in production" gets asked.
  • Explains why a slow-page or failing-request question can be answered from a dashboard instead of adding custom timing code and redeploying.
  • A common opener before Azure Monitor, Log Analytics, or alerting come up.
🔥 Easy interview recall

Application Insights = "telemetry that's auto-captured and correlated end-to-end."

Think: requests + dependencies + exceptions — one request ID ties every piece to the same story.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Application Insights is not "just logging." It's structured telemetry with automatic correlation and built-in duration data — plain text log lines don't give you that timing or that end-to-end linkage for free.

🔄 Likely Follow-up

"How does it find slow dependencies without you timing anything?" It auto-instruments outbound calls (database, HTTP, etc.) and records their duration itself, surfaced in the Dependencies view — zero manual timing code needed.

🎯 Say this in the interview — the exact lines to land

"Application Insights auto-captures requests, dependencies, and exceptions, correlated end-to-end — it's the APM layer inside Azure Monitor, and it's structured telemetry, not a substitute for plain text logging."

  • Requests & dependencies → every inbound request and outbound call (DB, HTTP) is timed automatically.
  • Correlated end-to-end → one operation ID ties every segment together, so you can follow one request start to finish.
  • Not the same as logging → structured telemetry with built-in timing, not a plain-text log substitute.
  • Part of Azure Monitor → App Insights is the application-level APM piece of the broader Azure Monitor platform.
📖 Explanation ▾

Application Insights is Azure's application performance monitoring (APM) service, part of the wider Azure Monitor platform. Once wired into an app, it automatically captures requests (every inbound call), dependencies (every outbound call — a database query, an HTTP call to another API, and so on), exceptions, custom events/metrics you emit yourself, and traces. Everything shares a common operation ID, so one request's whole journey — in, through its dependencies, back out — reads as a single correlated timeline instead of scattered, unrelated log lines.

Requests and dependencies are timed through auto-instrumentation — the SDK wraps the request pipeline and outbound calls itself, so duration shows up in the Dependencies view with no manual timing code. Custom events (TrackEvent) and exceptions (TrackException) exist for the things automatic capture can't know on its own — a business event like "OrderPlaced," not a technical failure the SDK already sees.

💻 See the code ▾
C# 
TelemetryClient telemetryClient = new TelemetryClient(configuration);
telemetryClient.TrackEvent("OrderPlaced");   // a custom business event

This custom event shows up in Application Insights alongside the auto-captured requests and dependencies — same timeline, same correlation.

C# 
try
{
    ProcessOrder(order);
}
catch (Exception ex)
{
    telemetryClient.TrackException(ex);   // tied to the request it happened in
}

TrackException correlates the failure to the exact request that triggered it — no separate log line to cross-reference by hand.

🌍 Real-world example ▾

A checkout page feels slow, and nobody knows why. Instead of adding timing code and redeploying, someone opens that request's telemetry in Application Insights and checks its Dependencies view — it shows a single database call eating most of the page's total load time, with zero extra instrumentation written to find it.
