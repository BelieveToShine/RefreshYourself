raise ... from ... isn't just style — it preserves the real cause in __cause__

"How does exception propagation work? What does exception chaining actually preserve, and why does it matter in production?"

Why it matters ▾
  • Tests whether you actually understand control flow under failure, not just where to put a try and a except.
  • Explains a real production bug pattern: a caught-and-hidden exception that masks an outage until users start reporting broken behavior.
  • Sets up the exact distinction interviewers probe for — __cause__ vs. __context__ — and why a bare except: is dangerous.
🔥 Easy interview recall

raise ... from ... = "setting the real cause on purpose."

Think: __cause__ → explicit, you set it. __context__ → automatic, Python sets it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Re-raising without from loses the original error. It doesn't — Python still records it automatically as __context__ — but skipping from leaves the causal relationship implicit and accidental instead of explicit and intentional; use raise ... from None only when the original really is irrelevant noise.

🔄 Likely Follow-up

"When should you use finally vs. just letting an exception propagate?" Use finally for cleanup that must happen regardless of success or failure — closing a file, connection, or lock — never for logic that depends on whether an exception actually happened; that belongs in except or else.

🎯 Say this in the interview — the exact lines to land

"raise ... from ..." sets __cause__ explicitly — that's what keeps a chained traceback from losing the real root cause in production."

  • __cause__ → explicit and intentional: only set when you write raise ... from original.
  • __context__ → automatic and implicit: Python sets it any time a new exception is raised while handling another, even with no from at all.
  • Never catch broadly — a bare except: or except Exception: swallows bugs you never anticipated, and a bare except: can even catch KeyboardInterrupt.
  • finally → always runs, success or failure — the right place for mandatory cleanup, never conditional logic.
📖 Explanation ▾

try wraps the risky code. except catches a matching exception type. else runs only when the try block raised nothing at all. finally always runs — cleanup code that fires whether or not an exception occurred, even if the exception keeps propagating past this block.

Every exception is a subclass of BaseException, the true root of the hierarchy — it also covers SystemExit and KeyboardInterrupt, which you almost never want to catch. Exception is the base for everything you'd normally handle, and custom exceptions should subclass Exception (or a more specific built-in) rather than BaseException directly. Catching bare except Exception, or worse a bare except:, silently swallows bugs you never anticipated and hides real failures — catch only the specific exception type(s) you actually expect and know how to handle.

raise NewError(...) from original sets __cause__ to original — a documented, intentional "this new error was caused by that one." __context__ is different: Python sets it automatically any time a new exception is raised while already handling another, with no from required. Both are real links in the exception object, they just get shown, and set, differently.

💻 See the code ▾
Python 
try:
    connect_to_db()
except ConnectionError as original:
    # ❌ ConnectionError becomes original's __cause__
    raise ServiceError("could not process order") from original

The caller only ever sees ServiceError — but __cause__ keeps the real ConnectionError attached to it, on purpose.

Python 
try:
    process_order(order)
except Exception:
    pass  # ❌ swallows EVERYTHING, even bugs you never expected

A bare except Exception: pass hides real failures instead of handling them — nothing tells you it ever happened.

Python 
try:
    process_order(order)
except (ConnectionError, TimeoutError) as e:
    # ✅ specific, expected, and still visible
    logger.error("order failed: %s", e)
    raise

Catch only what you actually expect and know how to handle — a bug outside that list keeps propagating, exactly as it should.

🌍 Real-world example ▾

A production incident: an ORM's ConnectionError, raised whenever the database was briefly unreachable, was being silently swallowed by a bare except Exception: pass deep in a data-access layer. There was no log, no alert, and no chained traceback — just a quietly returned None. The real database outage stayed invisible until users started reporting missing records, and the on-call engineer had nothing but a symptom to chase, with no cause attached anywhere.
