HTTP Interceptors — every request and response funnels through one place before you ever see it

"How do HTTP interceptors chain together, and how do you stop a refresh-token interceptor from intercepting its own refresh request?"

Why it matters ▾
🔧 Functional
❗ ProblemRequiring a full class (implementing HttpInterceptor, wired through the HTTP_INTERCEPTORS multi-provider) for something as small as "add one header" is real ceremony in a modern standalone app already built around plain provider functions.
✅ SolutionA functional interceptor is just a plain function matching HttpInterceptorFn, registered with withInterceptors([...]) inside provideHttpClient() — no class, calling next(req) to hand off to the next one.
RecallFunctional = plain function + withInterceptors([...]) — no class needed.
🏛️ Class-based
❗ ProblemNot every real app is on the newest style — older, still-supported NgModule-based code was written before HttpInterceptorFn existed, and a candidate who only knows the modern function shape can be caught off guard reading it.
✅ SolutionA class implementing HttpInterceptor does the identical chaining job — intercept(req, next) calling next.handle(req) — registered as a HTTP_INTERCEPTORS multi-provider entry; same order and immutability rules, just the older shape.
RecallClass-based = HttpInterceptor class + HTTP_INTERCEPTORS multi-provider — the older, still-supported shape.
🔥 Easy interview recall

Interceptor = "a checkpoint every HTTP call is forced to pass through."

Think: Outbound → A → B → network Response → B → A → back to you, reversed

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

req.headers.set(...) doesn't work. HttpRequest objects are immutable — any change needs req.clone({...}) to produce a new request, then that clone is passed to next(); mutating the original silently does nothing.

🔄 Likely Follow-up

"If two interceptors both set the same header, whose value wins?" Whichever interceptor runs last in the outbound chain — it receives the already-cloned request from every interceptor before it, so its change is the one that actually reaches the network. Registration order is a real design decision, not an arbitrary list.

🎯 Say this in the interview — the exact lines to land

"An interceptor sits between HttpClient and the network — every request passes through the whole registered chain in order, then the response comes back through that same chain in reverse. I register a functional interceptor with provideHttpClient(withInterceptors([...])), clone the request with req.clone() for any change since requests are immutable, and guard a refresh-token interceptor by checking the request URL so it never tries to refresh its own refresh call."

  • Chain order → outbound follows registration order, response comes back reversed.
  • Requests are immutable → always req.clone({...}) before calling next().
  • Two registration styles → HttpInterceptorFn via withInterceptors(), or a class implementing HttpInterceptor via the HTTP_INTERCEPTORS multi-provider.
  • Refresh-token recursion → skip the interceptor's own logic for the refresh endpoint's URL (or a custom HttpContext token) so it can't call itself forever.
  • Everyday uses → auth headers, logging, global error handling, retry, correlation IDs — one place instead of every call site.
📖 Explanation ▾

An interceptor sits between HttpClient and the actual network call, so it can inspect or change the outgoing request and the incoming response for every call that goes through HttpClient — one place for cross-cutting concerns like auth headers, logging, or error handling, instead of repeating that logic at every .get()/.post() call site.

Chaining works because each interceptor calls next(req) (or next.handle(req) for the older class-based style) to hand control to whichever interceptor is registered right after it. That makes the interceptors registered earlier effectively wrap the ones after them: the request flows through in registration order on the way out, and the response flows back through the same interceptors in the opposite order.

Two registration styles exist today, doing the same job through a different shape. Modern code uses a plain function matching HttpInterceptorFn; older code (still fully supported) uses a class implementing HttpInterceptor.

💻 See the code ▾
TypeScript 
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token();   // read current token
  return next(req.clone({                     // req is immutable — clone it
    setHeaders: { Authorization: `Bearer ${token}` }
  }));
};

Registered once via provideHttpClient(withInterceptors([authInterceptor])) — every HttpClient call gets this header automatically.

TypeScript 
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  if (req.url.includes('/auth/refresh')) {
    return next(req);   // ✅ skip — don't recurse into ourselves
  }
  // ...normal auth-header / 401-handling logic goes here
  return next(req.clone({ /* ... */ }));
};

Without this check, a 401 on the refresh call itself would trigger another refresh attempt — the same interceptor calling itself, forever.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're building a new standalone Angular app and add an interceptor

This is the #1 scenario you'll actually run into: a plain function matching HttpInterceptorFn, registered directly with provideHttpClient(withInterceptors([...])). No class, no NgModule — the function just calls next(req) to hand the request to whatever's registered after it.

RememberNew standalone app → functional interceptor, registered via withInterceptors().
2 You're working in an older NgModule-based codebase that already registers interceptors as classes

Still fully supported: a class implementing HttpInterceptor does the same chaining job through its intercept(req, next) method, calling next.handle(req) instead of next(req), registered as a HTTP_INTERCEPTORS multi-provider entry with useClass.

RememberOlder/NgModule app → class-based interceptor, registered via HTTP_INTERCEPTORS.
3 Your refresh-token interceptor doesn't check the request URL before running its normal logic

Without a check like req.url.includes('/auth/refresh'), a 401 on the refresh call itself gets handled by the same interceptor logic, which tries to refresh again — the same interceptor calling itself, forever.

RememberAlways skip the interceptor's own refresh-token URL, or it loops on itself forever.
🌍 Real-world example ▾

HTTP interceptors are like a mail sorting facility every letter must pass through. One station stamps a return-address label (the auth token) on every outgoing letter, another logs a copy before it leaves, and a third checks incoming mail for a "return to sender" stamp (error handling). The one thing the facility has to get right: it can't sort its own internal "please issue a new stamp" request the same way, or it gets stuck sorting mail to itself forever.
