IComparable vs. IComparer — order inside the type, or passed in

"What's the difference between IComparable and IComparer, and how does List.Sort use them?"

Why it matters ▾
↕️ Sorting your own types
❗ ProblemSort() can order numbers and strings because they already know how to compare themselves — but a plain Person class doesn't, so the sort has no idea whether to use name, age or anything else (and may throw at runtime).
✅ SolutionGive the type a natural order with IComparable<T>.CompareTo, which Sort() uses by default. For any other order — or a type you can't edit — pass an IComparer<T> (or a Comparison<T> lambda) to Sort.
RecallIComparable = the type compares itself; IComparer = someone else decides the order.
🔥 Easy interview recall

IComparable = "I know my own order." IComparer = "here's an order, from outside."

Think: Natural order lives in the type (one only); external order is passed to Sort (as many as you like).

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

List<T>.Sort is not stable. Items that compare as equal can come out in a different order than they went in. If you need equal items to keep their original order, use LINQ OrderBy, which is stable.

🔄 Likely Follow-up

"How do you sort by name, then by age?" In CompareTo (or a comparer), return the name comparison unless it is 0, then fall through to the age comparison — or use LINQ OrderBy(...).ThenBy(...) (see LINQ).

🎯 Say this in the interview — the exact lines to land

"IComparable<T> is the type's own natural order — Sort() uses it by default. IComparer<T> is an external order I pass in, so I can have many orders without touching the type. Sort isn't stable."

  • IComparable<T> → the type compares itself with CompareTo; one natural order.
  • IComparer<T> → an external comparer; many orders, and it works on types you can't edit.
  • CompareTo returns → negative, zero or positive (before, equal, after).
  • Sort(Comparison<T>) or Comparer<T>.Create → a lambda is enough; no class needed.
  • List.Sort → not stable; OrderBy is.
📖 Explanation ▾

List<T>.Sort() with no arguments uses the type's default comparer. For your own class, that default works only if the class implements IComparable<T>. If it doesn't, Sort() throws at runtime — it can't guess your order.

IComparer<T> moves the order outside the type: a small separate object with a Compare(a, b) method. You pass it to Sort, so one type can be sorted by name here and by age there, and it works on classes you don't own. When a full class is overkill, Sort also accepts a Comparison<T> lambda, and Comparer<T>.Create turns a lambda into an IComparer<T>.

Both follow the same contract: return a negative number if the first comes first, zero if they are equal, and a positive number if it comes after. Keep it consistent, or the sort can give odd results.

💻 See the code ▾
C# 
record Person(string Name, int Age) : IComparable<Person>
{
    public int CompareTo(Person? other) =>
        other is null ? 1 : Age.CompareTo(other.Age);   // natural order: by age
}

people.Sort();                                        // uses CompareTo

The type carries its own default order.

C# 
people.Sort(Comparer<Person>.Create(                 // external order: by name
    (a, b) => string.Compare(a.Name, b.Name, StringComparison.Ordinal)));

people.Sort((a, b) => b.Age.CompareTo(a.Age));       // Comparison<T> lambda: oldest first

Same list, different orders — and Person never changed.

🌍 Real-world scenario ▾

A report must list customers by name for one team and by newest order for another. Instead of editing the Customer class for each team, you keep two small comparers and pass the right one to Sort.
