EventBridge routes by what the event actually says

"When would you choose EventBridge instead of SNS/SQS for routing events between services?"

Why it matters ▾
📢 SNS / SQS
❗ ProblemProducers and consumers need to be decoupled without wiring every consumer directly to every producer.
✅ SolutionA producer publishes once and each consumer subscribes to a topic or reads from a queue — simple and reliable for fan-out or point-to-point delivery.
RecallSNS/SQS = subscribe to a topic/queue; filtering is the consumer's job.
📨 EventBridge
❗ ProblemOnce many different event types/sources all need to be routed differently, topic/queue subscription pushes that filtering onto every consumer, and cross-account delivery has to be wired manually per subscription.
✅ SolutionRules match on the event's own content — source, type, fields — centrally, so one bus routes many event types differently, even straight to another account's bus, without consumers re-implementing that filtering.
RecallEventBridge = one bus, rules filter by content, not topic.
🔥 Easy interview recall

EventBridge = "a bus that routes by what's inside the event, not just its topic."

Think: SNS broadcasts to whoever subscribed to a topic; EventBridge reads the event's own fields and lets a rule decide where it goes.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 Don't mix these two — where the filtering logic actually lives
⚠️ Common Trap

"SNS/SQS can route this too, so it doesn't matter which I pick." They can move messages, but SNS/SQS route by topic/queue subscription — routing many different event types/sources by content means every consumer ends up writing its own filtering logic, which is exactly what EventBridge's pattern-matching rules already do for you.

🔄 Likely Follow-up

"How do you route events between services/accounts?" EventBridge rules can target resources in another account (via resource policies) or forward matching events straight to another account's event bus — the producer never needs to know every downstream consumer.

🎯 Say this in the interview — the exact lines to land

"EventBridge routes by content-based pattern matching across many event types and sources — that's the real differentiator from SNS/SQS, which route by topic or queue subscription instead. A rule reads the event's own fields — source, type, detail — and decides where it goes, so consumers don't have to filter it themselves."

  • EventBridge → content-based rules, matched against the event's own fields.
  • SNS/SQS → topic/queue subscription — filtering logic mostly lives on the consumer.
  • Cross-account routing → a rule can target another account's bus directly, no producer-side wiring needed.
  • Reach for EventBridge when there are many event types/sources that need to fan out differently, not a single simple hand-off.
📖 Explanation ▾

EventBridge is an event bus built for event-driven architecture. Producers — AWS services, your own applications, or even third-party SaaS partners — publish events onto a bus. Rules attached to that bus match events against a pattern (by source, event type, or fields inside the event body) and route every matching event to one or more targets: Lambda, SQS, Step Functions, and more.

The distinction that actually matters against SNS/SQS: those route by subscription — a consumer signs up for a topic or reads from a queue, and any filtering beyond that is the consumer's own logic. EventBridge's rules do that content-based filtering centrally, so a single bus can serve many unrelated event types and route each one differently without every consumer re-implementing the same filtering.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your service emits several different event types, and each type needs to land on a different target

This is the #1 scenario you'll actually run into — one EventBridge rule per event type keeps the routing decision in one place, instead of every Lambda having to inspect the event just to decide whether it cares.

RememberMany event types, different targets → one rule per type, not one consumer doing the sorting.
2 You're already on SNS/SQS, and each new event type tempts you to just add another topic or queue

This is exactly the trap — every one of those consumers ends up writing its own filtering logic to figure out whether it cares about a given message, which is the exact routing job EventBridge's content-matching rules already do for you centrally.

RememberMore event types on SNS/SQS → filtering logic spreads into every consumer.
3 One producer just needs to hand events off to one or two known consumers, nothing content-based

This is the simple fan-out/point-to-point case where SNS/SQS's topic or queue subscription is already the right, lighter-weight tool — reaching for EventBridge's rule engine here is more machinery than the job needs.

RememberSimple hand-off, known consumers → SNS/SQS is the right-sized tool, not EventBridge.
🌍 Real-world example ▾

An e-commerce platform routes order.placed, order.shipped, and order.refunded events all through one EventBridge bus, with a separate rule matching each event type to its own downstream Lambda — no consumer has to inspect every event just to decide whether it cares about it.
