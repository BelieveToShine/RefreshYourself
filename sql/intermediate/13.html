#TempTable vs. @TableVar vs. CTE — which one survives a ROLLBACK?

"Temp tables vs. table variables vs. CTEs — when would you actually reach for each?"

Why it matters ▾
  • Checks whether you know these are three genuinely different tools — not three ways to spell the same thing — differing in real storage, indexing, and optimizer statistics.
  • Comes up any time you need to build an intermediate result once and query it more than once, or when a query using a table variable inexplicably gets a slow plan on large data.
  • A very common opener when the conversation turns to refactoring a long stored procedure or diagnosing a bad execution plan.
🔥 Easy interview recall

#TempTable → real table, indexed, real stats

@TableVar → lightweight, but stats are a guess

CTE → not stored at all, one statement only

Think: #TempTable is a real table. @TableVar is a sticky note. A CTE is a name, not a place.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A table variable is always lighter weight, so it's the safe default." On a large intermediate result, its missing or poor optimizer statistics can produce a much worse query plan than a temp table would get — the opposite of the intended optimization.

🔄 Likely Follow-up

"You need to build an intermediate result once, then run three separate queries against it — which would you reach for, and why not a CTE?" A temp table — a CTE only exists for the single statement it's part of, so it can't be reused across three separate statements the way a temp table can.

🎯 Say this in the interview — the exact lines to land

"A temp table is a real, session-scoped table in tempdb — it can be indexed and the optimizer has real statistics on it, so it's the right choice for a larger intermediate result I'll query more than once. A table variable is lighter and scoped to its own batch, but the optimizer historically has little to no real statistics on it, so I only reach for it on small, short-lived data. A CTE isn't materialized at all — it only exists for the one statement it's part of, so it's best for readability, not for reusing the same result across multiple statements."

  • #TempTable → real table, real stats — best for a larger set you'll query more than once.
  • @TableVar → lightweight, batch-scoped — best for small, short-lived results.
  • CTE → not materialized, one statement — best for readability, not reuse.
  • Missing or poor statistics is the real risk with a table variable on large data — not indexing.
  • A table variable's rows → survive a ROLLBACK — sometimes used deliberately for logging even when the surrounding transaction fails.
📖 Explanation ▾

A temp table (#TempTable) is a real, physical table — it just happens to live in tempdb and be scoped to your session instead of a permanent database. Because it's a real table, it can be indexed, altered with normal DDL, and the optimizer keeps real statistics on it, the same as any other table. It also stays visible across multiple batches and statements within the same session, so it's the right tool when you need to build a result once and query it several times.

A table variable (@TableVar) is more lightweight, but that lightness comes with a trade-off: it's scoped strictly to the batch or procedure it's declared in, and older engine versions gave the optimizer little to work with — treating it as a fixed, tiny row-count estimate regardless of how much data it actually held. Modern engine versions have improved this somewhat, but it's still not as reliable as a temp table's statistics on a large set. It also doesn't roll back the same way a temp table's data does — its rows survive a surrounding ROLLBACK, which some code deliberately exploits for logging even when the transaction it's logging fails.

A CTE isn't materialized as a table at all — see CTEs for the full picture. It's scoped to the single statement it's part of and can't be indexed, which makes it great for readability and one-shot use, but the wrong choice the moment you need to reuse the same intermediate result across more than one statement.

💻 See the code ▾
SQL 
CREATE TABLE #Recent (OrderId INT, CustomerId INT, OrderDate DATE);
CREATE INDEX IX_Recent_Customer ON #Recent(CustomerId);  -- ✅ real DDL, a real index

INSERT INTO #Recent
SELECT OrderId, CustomerId, OrderDate FROM Orders WHERE OrderDate > '2024-01-01';

-- Batch 2, later in the same session — #Recent is STILL visible here
SELECT CustomerId, COUNT(*) FROM #Recent GROUP BY CustomerId;

One temp table, indexed once, queried by more than one batch in the same session — a CTE can't do either of those things.

SQL 
DECLARE @Log TABLE (Msg NVARCHAR(100));

BEGIN TRAN;
    INSERT INTO @Log VALUES ('attempted the update');
    UPDATE Accounts SET Balance = Balance - 1000000 WHERE Id = 1; -- fails a check constraint
ROLLBACK;  -- rolls back the UPDATE...

SELECT * FROM @Log;  -- ✅ still has the row — @Log doesn't roll back with the tran

The @Log row survives the ROLLBACK even though the UPDATE it logged didn't — a real, sometimes deliberately exploited behavior, and a genuine surprise if you weren't expecting it.

🌍 Real-world example ▾

A temp table is a whiteboard in a shared conference room — anyone in that same room (any batch, in the same session) can still read it later, and it's sturdy enough to index and organize. A table variable is a sticky note in your own notebook — quick and personal, gone once you close the notebook (the batch ends), and nobody keeps careful records on how many sticky notes you usually write. A CTE isn't a place at all — it's just a name you use once while speaking a single sentence.
