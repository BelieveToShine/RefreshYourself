A Query Goes Into Deadlock

A query that used to run fine is now deadlocking — how do you find out why, and what's the actual fix?

Why it matters ▾
🔒 Diagnosing a Deadlock
❗ ProblemA query that starts deadlocking under load can look like random bad luck, which tempts a guess-and-restart response — or worse, a schema change that doesn't actually address what's causing it.
✅ SolutionThe engine's own deadlock graph shows exactly which two transactions were holding locks the other one needed, and in what order — the real fix is a consistent lock order, short transactions, and the right indexes, not changing the schema.
RecallDeadlock = two transactions, each holding what the other one wants.
🔥 Easy interview recall

Deadlock = "two transactions, each holding what the other one wants."

Think: check the deadlock graph first, then fix the lock order — not the schema.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Deadlocks mean the schema needs denormalizing." Usually not — the real levers are lock order and transaction scope; normalization vs. denormalization affects query complexity and join cost, not lock-ordering deadlocks directly.

🔄 Likely Follow-up

"Why do shorter transactions reduce deadlock risk?" A lock is held for the transaction's full duration — the longer it's held, the larger the window for another transaction to need the same resource and collide. Keeping transactions short shrinks that window.

🎯 Say this in the interview — the exact lines to land

"I'd pull the deadlock graph first — SQL Server's deadlock trace or Extended Events, or InnoDB's status output in MySQL — to see exactly which two transactions were holding locks the other needed, and in what order. The usual root cause is two transactions acquiring the same resources in different orders; the fix is a consistent lock order, short transactions, and the right indexes — not denormalizing the schema."

  • Diagnose first → the deadlock graph/trace shows the actual lock order each transaction took.
  • Root cause → two transactions acquiring the same resources in a different order.
  • Fix: lock order → make every transaction acquire resources in the same sequence.
  • Fix: short transactions → shrinks the window a lock is held, lowering collision odds.
  • Fix: right indexes → a missing index can force a scan that locks far more rows than necessary.
📖 Explanation ▾

Diagnose before fixing anything. The database engine already recorded exactly what happened: SQL Server's deadlock trace/Extended Events, or MySQL's InnoDB status output, show which two transactions were each holding a lock the other one needed, and the order each one acquired its locks in. The overwhelmingly common root cause is the same two resources, locked in a different order by two transactions running at the same time — transaction A locks table1 then table2, transaction B locks table2 then table1, and if their timing lines up, each ends up waiting on the other.

The fix follows directly from the cause: make every transaction that touches both resources acquire them in the same order, so the cycle can't form. Keeping transactions short reduces the odds further, since a lock is held for the whole transaction and a shorter transaction means a smaller window for a collision. A missing index can make this worse too — a full table scan locks far more rows than a precise index seek would, raising the odds that two transactions touch the same row at the same time.

💻 See the code ▾
SQL 
-- Transaction A
BEGIN TRAN;
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountId = 1; -- locks Accounts first
UPDATE Orders   SET Status = 'Paid'          WHERE OrderId = 55;   -- then locks Orders
COMMIT;

-- Transaction B, running at the same time
BEGIN TRAN;
UPDATE Orders   SET Status = 'Paid'          WHERE OrderId = 55;   -- locks Orders first
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountId = 1; -- ❌ wants Accounts, deadlock
COMMIT;

Same two tables, opposite order — this is the classic deadlock shape.

SQL 
-- Fixed: both transactions now lock in the SAME order
BEGIN TRAN;
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountId = 1; -- ✅ Accounts first, always
UPDATE Orders   SET Status = 'Paid'          WHERE OrderId = 55;
COMMIT;

Enforcing one fixed order across every transaction that touches both tables breaks the cycle — no schema change required.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two nightly batch jobs update the same two tables, and they deadlock a few times a week

This is the #1 scenario you'll actually run into — two recurring jobs each touching the same two tables, in opposite order. Fix the order in both jobs and the deadlocks stop entirely.

RememberSame two tables, opposite order, recurring → fix the order in both.
2 Deadlocks started right after a new feature shipped that touches multiple tables per request

A new code path that touches the same tables as existing code, but in a different order, is a very common way for deadlocks to suddenly appear — check the new feature's lock order against the existing one first.

RememberDeadlocks started after a deploy → check the new code's lock order.
3 Someone on the team suggests "let's just denormalize to fix the deadlocks"

Denormalizing changes join cost and query complexity, not lock ordering — it doesn't touch the actual cause, so the same deadlock pattern comes right back under load.

RememberDenormalizing doesn't fix deadlocks → fix lock order and transaction scope instead.
🌍 Real-world example ▾

Scenario: nightly batch jobs updating the Accounts and Orders tables start deadlocking under load. Pulling the deadlock graph shows job A locking Accounts then Orders, while job B locks Orders then Accounts — the classic crossed order. Rewriting both jobs to always touch Accounts first, then Orders, eliminates the deadlocks without touching the schema.
