A method gets flagged in review — extract, don't rewrite

A reviewer flags one of your methods as needing a refactor — what's your actual process?

Why it matters ▾
🔧 Flagged in Review
❗ ProblemA method flagged in review is usually doing too much or nesting too deep — touching it carelessly, or sneaking in an unrelated bug fix in the same change, makes it impossible to tell afterward which edit caused what if something breaks.
✅ SolutionPin down current behavior with tests first, then extract the tangled pieces into small, named methods one independently-verifiable step at a time — structure changes and behavior changes never share a step.
RecallTest first, extract in small steps, structure only — never behavior too.
🔥 Easy interview recall

1. Why → too many responsibilities or too many branches

2. Extract → pull cohesive chunks into named methods/classes

3. Verify → tests before you start, small steps as you go

Think: Why → Extract → Verify — and never fold a behavior change into the same step as the cleanup.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Refactoring is not the same change as fixing a bug you noticed. Mixing "make it cleaner" with "also fix this bug I spotted" in the same change makes it impossible to tell which edit caused what if something breaks, and much harder to review.

🔄 Likely Follow-up

"How do you know when a method has gotten too big, concretely?" There's no single universal number, but common signals: it needs a comment to explain what a section does (that section should be its own named method instead), it mixes multiple levels of abstraction in one method body, or it nests more than ~3-4 levels of conditionals deep.

🎯 Say this in the interview — the exact lines to land

"First I find out why it's flagged — usually too many responsibilities or too much nesting — then I make sure tests pin down the current behavior, and only then do I extract the tangled pieces into small, named methods one independently-verifiable step at a time, never changing behavior and structure in the same step."

  • Why it's flagged → almost always too many responsibilities (SRP) or too much nesting.
  • Before touching it → confirm or add tests that pin down the current behavior.
  • Each extraction → one small, independently-verifiable step, not one big rewrite.
  • Never mix in a behavior change with the structural cleanup — separate changes, separate reviews.
  • Concrete "too big" signal → needs a comment to explain a section, mixes abstraction levels, or nests 3-4+ levels deep.
📖 Explanation ▾

Start by naming why the reviewer flagged it, not by editing right away. Almost every real flag comes down to one of two things: the method is doing too much — a discount rule, a payment call, and an email send all living in one place, each a different team's reason to touch it — or it's just hard to follow, with deep nested if blocks or the same logic copied in two places. Naming the actual cause first keeps the fix targeted instead of a vague "clean this up" pass.

The fix is extraction: pull each cohesive chunk out into its own named method or class, so the original method reads like a short list of steps instead of a wall of logic. A good extracted name — ValidateOrder, CalculateTotal — already tells a reader what that chunk does without them reading its body.

Order matters as much as the extraction itself. Confirm tests exist that lock in the current behavior before moving a single line — those tests are what let you prove "I changed the shape, not the result" afterward. Then refactor in small steps, each one independently verifiable against those same tests, rather than one large rewrite where a single mistake anywhere is hard to isolate.

💻 See the code ▾
C# 
public void ProcessPayment(Order order)
{
    // ❌ validation, pricing, and notification, all tangled in one method
    if (order == null) throw new ArgumentNullException(nameof(order));
    if (order.Items.Count == 0) throw new InvalidOperationException("Empty order");

    decimal total = order.Items.Sum(i => i.Price);
    if (order.CustomerType == "VIP") total *= 0.9m;
    if (order.Items.Count > 10) total *= 0.95m; // ❌ a second discount rule, buried here too

    var message = $"Hi {order.CustomerName}, your order of {total:C} is confirmed.";
    EmailSender.Send(order.Email, message);
}

Three jobs — validation, pricing, notification — with no obvious seams between them, and a second discount rule hiding inside the pricing lines.

C# 
public void ProcessPayment(Order order)
{
    ValidateOrder(order);                 // ✅ step 1, named
    var total = CalculateTotal(order);  // ✅ step 2, named
    SendConfirmation(order, total);       // ✅ step 3, named
}

private void ValidateOrder(Order order)
{
    if (order == null) throw new ArgumentNullException(nameof(order));
    if (order.Items.Count == 0) throw new InvalidOperationException("Empty order");
}

private decimal CalculateTotal(Order order)
{
    decimal total = order.Items.Sum(i => i.Price);
    if (order.CustomerType == "VIP") total *= 0.9m;
    if (order.Items.Count > 10) total *= 0.95m;
    return total;
}

The orchestrating method now reads like a short list of steps — each extracted method is independently named, independently testable, and the two discount rules now live together in one obvious place instead of hiding inline.

🧭 Use Cases — recognize these when they happen to you ▾
1 A reviewer leaves 3 separate comments that all point at the same method

Multiple comments on one method usually share a single root cause — "rename this," "this branch is confusing," and "please add a test" often all trace back to the same too-many-responsibilities problem. This is the #1 way this actually shows up in a real review.

RememberSeveral comments, one method → look for one shared cause.
2 The flagged method has zero tests around it today

No existing tests doesn't mean skip testing — it means write characterization tests against the current behavior first, even ugly ones, so you have something that fails the moment an extraction accidentally changes an outcome.

RememberNo tests yet → write pinning tests before touching structure.
3 Mid-refactor, you spot a real bug that has nothing to do with the cleanup

Finish the structural refactor first and note the bug separately — fixing it in the same change makes it impossible to tell afterward which edit caused what if something breaks, and makes the change much harder to review.

RememberFound a bug while refactoring? Note it — don't fix it in the same diff.
🌍 Real-world example ▾

Scenario: a reviewer leaves one comment — "this method is doing too much, please refactor" — on a 40-line ProcessPayment method that mixes validation, pricing, and notification, with a second discount rule hiding inline.

Working it: confirm (or add) tests around the current behavior first, then extract validation, pricing, and notification into three named private methods called from a short orchestrating method — one extraction at a time, each checked against the same tests before moving to the next, with no unrelated bug fix folded into the same change.
