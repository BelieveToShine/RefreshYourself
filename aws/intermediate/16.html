CDK compiles down to CloudFormation — same engine, friendlier syntax

"CloudFormation vs. Terraform vs. CDK — what's the actual tradeoff?"

Why it matters ▾
  • Checks whether you understand that CDK isn't a competing deployment engine — it's an authoring layer on top of CloudFormation, not a replacement for it.
  • Comes up any time the conversation turns to "how does your team manage infrastructure," especially in a multi-cloud shop.
  • A natural opener before a deeper question about drift, rollback behavior, or secrets handling in a template.
🔥 Easy interview recall

CloudFormation → AWS-native, YAML/JSON

CDK → synthesizes to CloudFormation

Terraform → multi-cloud, its own engine

Think: CDK is a friendlier front door to the same house CloudFormation lives in. Terraform lives in a different house entirely.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

CDK is not a different deployment engine from CloudFormation. It's purely a friendlier authoring layer — it synthesizes to a CloudFormation template and deploys through the exact same CloudFormation stack mechanism underneath, so anything true of a CloudFormation stack (drift detection, automatic rollback) is true of a CDK-deployed one too.

🔄 Likely Follow-up

"What happens when a CloudFormation deployment fails?" By default, CloudFormation automatically rolls back the entire stack to its last known-good state, undoing whatever partial changes had already been applied.

🎯 Say this in the interview — the exact lines to land

"CDK synthesizes to CloudFormation — same engine, just a friendlier authoring layer in a real programming language. Terraform is a genuinely separate, multi-cloud tool with its own engine and its own AWS provider."

  • CloudFormation → use it when you want AWS-native YAML/JSON with no extra tooling, and built-in drift detection.
  • CDK → use it for readable, reusable, testable infrastructure code — still just CloudFormation underneath.
  • Terraform → use it when the team manages more than one cloud and wants one consistent workflow.
  • CloudFormation's default failure behavior is automatic rollback of the whole stack, not a partial, half-applied state.
  • Never hardcode a secret in a template — reference Secrets Manager or Parameter Store instead.
📖 Explanation ▾

CloudFormation is AWS's own declarative infrastructure-as-code service. You describe the resources you want in a YAML or JSON template, and CloudFormation figures out how to create, update, or delete them to match — grouped together as a stack. Because it's AWS-native, it also understands your account's real state well enough to detect drift: a resource someone changed by hand outside the template, diverging from what the template says it should be.

Terraform (from HashiCorp) is a separate tool with its own engine, written in its own language (HCL), that talks to AWS through its own AWS provider — the same provider pattern it uses for every other cloud it supports. That's the real reason a team picks it: one consistent workflow across AWS, another cloud, and other services, instead of learning a different tool per provider.

CDK is neither of those — it's a way to write infrastructure in a real programming language (TypeScript, Python, and others) that gets synthesized into a CloudFormation template before deployment. Same stack, same rollback behavior, same drift detection — CDK just makes the authoring side more expressive and reusable (loops, functions, and real abstractions instead of copy-pasted YAML blocks).

Managing secrets is the same rule everywhere: never write a real secret value into a template. Reference Secrets Manager or Parameter Store instead, so the template only ever holds a pointer to the secret, not the secret itself.

💻 See the code ▾
TypeScript 
new s3.Bucket(this, 'MyBucket', { versioned: true }); // synthesizes to an equivalent CloudFormation resource

This one line becomes a full AWS::S3::Bucket resource block in the generated CloudFormation template — CDK is just writing the same target output for you.

🌍 Real-world example ▾

An AWS-only team maintaining a pile of hand-written CloudFormation YAML switches to CDK for readability and reuse — the same stacks get deployed, nothing about what actually gets created in AWS changes, only how it's authored. A multi-cloud team, meanwhile, keeps everything in Terraform, because one consistent workflow across every cloud they touch is worth more to them than AWS-native tooling.
