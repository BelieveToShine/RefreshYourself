ConcurrentHashMap — per-bin locking, not one lock for the table

"How does ConcurrentHashMap avoid locking the whole table on every write?"

Why it matters ▾
🔒 Per-bin locking
❗ ProblemA single lock around the whole map would force every thread to wait, even when two threads are touching completely different keys — terrible concurrent throughput.
✅ SolutionModern ConcurrentHashMap (Java 8+) synchronizes only the specific bin being modified on a collision, using CAS for simple operations — different bins proceed with zero contention.
RecallConcurrentHashMap = lock the bin, not the table.
⚛️ Atomic compound ops
❗ ProblemChecking whether a key is present and then writing to it as two separate calls is a race under concurrent access — another thread can sneak in between the check and the write.
✅ SolutioncomputeIfAbsent, compute, and merge read-and-conditionally-write a single key atomically, with no external lock needed.
Recallcompute()/merge() = check-and-write, in one atomic step.
🔥 Easy interview recall

ConcurrentHashMap = "lock the one bin that's colliding, never the whole table."

Think: different bins → no lock at all. Same bin, a collision → that one bin gets synchronized, nothing else.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ConcurrentHashMap does not use segment locking anymore. That was the pre-Java-8 design; the modern (Java 8+) implementation locks only the specific bin being modified, using CAS for most operations — never a fixed set of 16 segments.

🔄 Likely Follow-up

"Why not just synchronize the whole map, like Hashtable does?" You could, but then every thread waits for every operation anywhere in the map, even on completely unrelated keys — exactly the throughput problem per-bin locking exists to avoid.

🎯 Say this in the interview — the exact lines to land

"Modern ConcurrentHashMap (Java 8+) locks at the bin level — it synchronizes only the specific bucket being modified on a collision, using CAS for simple operations, so threads touching different bins never contend at all. Compound operations like computeIfAbsent, compute, and merge do a read-and-write on one key atomically, without needing an external lock."

  • Locking granularity → per-bin (bucket), not per-segment, not whole-table.
  • Simple ops (get/put) → CAS-based, lock-free in the common case.
  • A real collision → only that one bin gets synchronized.
  • computeIfAbsent/compute/merge → atomic check-and-write on a single key.
  • Pre-Java-8 segment locking → historical, not the current design.
📖 Explanation ▾

ConcurrentHashMap, like HashMap, stores entries across an array of bins (buckets), each picked by a key's hash. For a simple operation like get or an uncontended put, the implementation uses CAS (compare-and-swap) instructions — no lock is taken at all. Only when two threads genuinely collide on the same bin does that one bin get synchronized, for just long enough to resolve the collision (the historical segment-locking design, which split the table into a fixed set of segments each with their own lock, was replaced entirely as of Java 8).

The atomic compound methods solve a different, equally real problem: computeIfAbsent/compute/ merge let you check a key's current value and write a new one in a single atomic step, scoped to that one key — no separate containsKey-then-put race window, and no need to hold an external lock around the two calls yourself.

💻 See the code ▾
Java 
// ❌ race: another thread can put() between containsKey() and put()
if (!map.containsKey(key)) {
    map.put(key, computeExpensiveValue());
}

Two threads can both pass the containsKey check before either calls put — the expensive computation can run twice, or overwrite a newer value.

Java 
ConcurrentHashMap<String, Value> map = new ConcurrentHashMap<>();
map.computeIfAbsent(key, k -> computeExpensiveValue()); // ✅ atomic, scoped to this key

Only one thread's lambda ever actually runs for a given key — the check and the write happen as one atomic step.

Java 
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge(word, 1, Integer::sum); // ✅ atomic increment-or-insert

A classic word-count update — no manual synchronized block, no lost updates under concurrent calls.

🧭 Use Cases — recognize these when they happen to you ▾
1 A shared in-memory cache, read and written by many request threads

A cache most requests read, and only occasionally write to, is the textbook case — per-bin locking means unrelated keys almost never contend with each other.

RememberMany threads, mostly different keys → ConcurrentHashMap.
2 Counting occurrences of something across many concurrent events

merge() turns "increment this key, or insert 1 if it's new" into one atomic call — no lost updates even with many threads hitting the same key.

RememberConcurrent counters → merge(), not read-then-write.
3 Describing ConcurrentHashMap's internals in an interview

Describing the old segment-locking design as if it's still current is a dated answer that signals stale knowledge. A common interview trap: many engineers learned "16 segments" years ago and never updated the mental model to Java 8's per-bin design.

Remember"Segments" → outdated. Say "per-bin" instead.
🌍 Real-world example ▾

A session-tracking map in a web server is read and written by hundreds of request threads at once, keyed by session ID. Because different sessions almost always land in different bins, ConcurrentHashMap lets those requests proceed with essentially no contention — the rare case where two sessions happen to hash into the same bin only ever blocks those two threads against each other, never the whole table.
