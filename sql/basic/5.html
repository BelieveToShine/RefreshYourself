NULL — why = NULL never matches anything

"How does SQL handle NULL in comparisons, and why does = NULL never match?"

Why it matters ▾
  • The most common reason a WHERE clause silently returns fewer rows than expected — a comparison against NULL that nobody noticed was failing.
  • One of the most-asked "gotcha" questions across every SQL interview, junior through architect.
  • Sets up every later topic that filters or joins on a possibly-missing column.
🔥 Easy interview recall

NULL = "unknown," not "empty."

Think: unknown vs. anything is still unknown — never TRUE, never FALSE. That's exactly why IS NULL exists as its own operator, not a comparison.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

column <> NULL will find all the non-NULL rows. Same problem as = NULL — any comparison against NULL evaluates to UNKNOWN, so it matches nothing, not even the rows you wanted; use IS NOT NULL instead.

🔄 Likely Follow-up

"What does NULL = NULL evaluate to?" UNKNOWN, not TRUE — even though "nothing equals nothing" feels intuitive, SQL treats two unknowns as still unrelatable, which is exactly why IS NULL exists as dedicated syntax instead of relying on =.

🎯 Say this in the interview — the exact lines to land

"SQL treats any comparison against NULL — including NULL = NULL — as UNKNOWN, not TRUE or FALSE, so a plain WHERE clause never matches those rows. IS NULL and IS NOT NULL are dedicated operators built specifically to test for it, not ordinary comparisons."

  • NULL means unknown → not empty, not zero — a distinct, third state.
  • = NULL never matches → the comparison evaluates to UNKNOWN, and WHERE always treats UNKNOWN as no match.
  • <> NULL has the same problem → it doesn't find the non-NULL rows either — it also evaluates to UNKNOWN.
  • Use IS NULL / IS NOT NULL → the only operators built specifically to test for NULL.
📖 Explanation ▾

SQL doesn't use plain true/false logic — it uses three-valued logic: TRUE, FALSE, and UNKNOWN. NULL represents a genuinely unknown value, not an empty string and not zero. Because the value is unknown, SQL can't honestly say whether a comparison against it is true or false — so =, <>, >, and every other comparison operator evaluate to UNKNOWN whenever either side is NULL, even when both sides are NULL.

A WHERE clause only keeps a row when its condition evaluates to TRUE — UNKNOWN is treated the same as FALSE for that purpose, so the row gets dropped either way. That's the whole mechanism behind the trap: the comparison isn't broken or buggy, it's doing exactly what three-valued logic says it should. IS NULL and IS NOT NULL exist as their own dedicated keywords, not comparison operators, precisely because no comparison operator can ever answer "is this unknown thing NULL" with a TRUE or FALSE.

💻 See the code ▾
SQL 
SELECT * FROM Customers
WHERE Email = NULL;   -- ❌ returns 0 rows, even if Email IS NULL for some customers

This returns zero rows — even for customers whose Email really is NULL — because = NULL evaluates to UNKNOWN, not TRUE.

SQL 
SELECT * FROM Customers WHERE Email IS NULL;       -- ✅ finds the NULL rows
SELECT * FROM Customers WHERE Email IS NOT NULL;   -- ✅ finds the non-NULL rows

IS NULL / IS NOT NULL are dedicated operators, not ordinary comparisons — this is the reliable way to test for NULL.

🌍 Real-world example ▾

Imagine asking two strangers whose ages you don't know: "Is your unknown age equal to my unknown age?" You can't honestly say yes or no — neither age is known, so the only honest answer is "I don't know." That's exactly what SQL's UNKNOWN represents: NULL = NULL isn't a confident "yes," it's an honest "can't tell."
