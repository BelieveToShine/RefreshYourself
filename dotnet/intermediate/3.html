Singleton, Scoped, Transient — who actually gets a new instance?

"What's the actual difference between Singleton, Scoped, and Transient service lifetimes?"

Why it matters ▾
  • Almost certainly the single most-asked ASP.NET Core question — often the first check for "have you actually used DI, or just read about it."
  • Comes up every time you register a service in Program.cs, and every time you're debugging why one user's data showed up in another user's response.
  • The follow-up about a Singleton depending on a Scoped service is a favorite way to separate memorized definitions from real experience.
🔥 Easy interview recall

Singleton → one instance, forever

Scoped → one instance, per request

Transient → new instance, every time

Think: Singleton is one, forever. Scoped resets each request. Transient resets every time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A Singleton holding per-request state in a field is not harmless. Because a Singleton is shared by every concurrent request forever, a field like private User _currentUser; leaks one user's data into another user's response under load — the fix is almost always registering the service as Scoped or Transient instead.

🔄 Likely Follow-up

"If Scoped means one instance per HTTP request, what does 'scope' mean in a background service, where there's no request?" There's no automatic scope to hook into — you create one yourself with IServiceScopeFactory.CreateScope(), resolve what you need inside it, then let it get disposed when you're done.

🎯 Say this in the interview — the exact lines to land

"Singleton creates one instance for the whole application and reuses it forever. Scoped creates one instance per scope — in a web app that scope is the HTTP request, so everything resolved during one request shares it, but the next request gets a new one. Transient creates a brand-new instance every single time it's resolved, even more than once inside the same request."

  • Singleton → one instance, whole app, forever.
  • Scoped → one instance per HTTP request, fresh again next request.
  • Transient → brand-new every resolution, even twice in one request.
  • Service leaking state between requests → check whether it's a Singleton holding per-request data first.
  • Scoped or Transient injected into a Singleton's constructor → captive dependency, frozen at startup.
📖 Explanation ▾

Singleton means the container builds the service exactly once — the first time something asks for it — and hands that same object to every consumer from then on, for the rest of the application's lifetime.

Scoped means the container builds one instance per scope, and in a web app the framework creates exactly one scope per incoming HTTP request. Every repository, service, or DbContext resolved while handling that one request shares the same Scoped instance — that's exactly why DbContext is registered Scoped: everything touching the database in one request shares a single unit of work and one set of tracked changes, but the next request starts clean.

Transient means the container never reuses an instance — it builds a fresh one every time something asks for it, even twice within the same method. The thing that catches people out: injecting a Scoped or Transient service into a Singleton's constructor doesn't make it behave normally — the Singleton is only ever built once, so whatever instance it captured at that moment stays frozen there forever, a bug called a captive dependency. ASP.NET Core's container can catch the most obvious case of this at startup — with scope validation enabled (the default in the Development environment), resolving a Scoped service through a Singleton throws instead of silently freezing it.

💻 See the code ▾
C# 
builder.Services.AddSingleton<ISingletonThing, Thing>();
builder.Services.AddScoped<IScopedThing, Thing>();
builder.Services.AddTransient<ITransientThing, Thing>();

Same class, three registrations — the lifetime is a property of the registration, not the class.

C# 
using var scope1 = provider.CreateScope();
var a1 = scope1.ServiceProvider.GetRequiredService<ISingletonThing>();
var b1 = scope1.ServiceProvider.GetRequiredService<IScopedThing>();
var c1 = scope1.ServiceProvider.GetRequiredService<ITransientThing>();
var c2 = scope1.ServiceProvider.GetRequiredService<ITransientThing>();

using var scope2 = provider.CreateScope();
var a2 = scope2.ServiceProvider.GetRequiredService<ISingletonThing>();
var b2 = scope2.ServiceProvider.GetRequiredService<IScopedThing>();

Console.WriteLine(a1 == a2);   // ✅ true — same Singleton, different scopes
Console.WriteLine(b1 == b2);   // ❌ false — Scoped resets per scope
Console.WriteLine(c1 == c2);   // ❌ false — Transient resets every resolve, even inside scope1

Each scope stands in for one HTTP request — this is exactly how ASP.NET Core resolves your services per request.

C# 
builder.Services.AddScoped<IScopedThing, Thing>();
builder.Services.AddSingleton<Broken>();

public class Broken
{
    private readonly IScopedThing _thing;
    public Broken(IScopedThing thing) => _thing = thing;   // 🐛 captured once, frozen forever
}

Broken is a Singleton, so the container builds it once — whatever Scoped instance it grabbed then never gets refreshed.

🌍 Real-world example ▾

Scenario: user A occasionally sees user B's name in the response, under load, only in production. The first thing to check is whether the service on that code path is registered as Singleton — it's the only lifetime that survives across concurrent requests, so it's the only one that can physically hold a field like _currentUser long enough for a second request to see it. The fix is almost always changing the registration to Scoped (or Transient), or moving that value out of instance state entirely.
