v-for and :key — how Vue tells your rows apart

"Why does v-for need a :key, and what goes wrong without one?"

Why it matters ▾
🔑 :key
❗ ProblemWhen a list reorders, gets filtered, or has items inserted, Vue has to figure out which old DOM nodes correspond to which new data — guessing by position alone gets it wrong.
✅ Solution:key gives each rendered node a stable identity, so Vue's diffing algorithm matches old nodes to new ones by that identity, not by slot position.
Recall:key = a stable identity Vue can track across re-renders.
🔥 Easy interview recall

:key = "a stable ID so Vue matches old DOM nodes to new data correctly."

Think: list reorders → a stable :key means each row's data follows it to its new slot — the array index does not.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Using the array index as :key when the list can reorder or be filtered. Vue then matches stale DOM nodes to the wrong items — visibly surfacing as inputs, focus, or local state attached to the wrong row after a reorder.

🔄 Likely Follow-up

"What goes wrong with no key at all?" Vue falls back to an in-place patch strategy that's cheaper to compute but can leave DOM state — a focused input, a mid-flight CSS transition — attached to the wrong item once the list's order or contents change.

🎯 Say this in the interview — the exact lines to land

"v-for renders one element per item, and :key gives each rendered node a stable identity so Vue's diffing algorithm can correctly match old DOM nodes to new ones across reorders, insertions, and deletions — instead of patching purely by position."

  • :key → use a stable, unique ID from the data, like a database ID.
  • Never the array index as :key if the list can reorder or be filtered.
  • No key at all → Vue falls back to patch-by-position, which can misplace local DOM state.
📖 Explanation ▾

v-for="item in list" renders one element per array item. On a re-render, Vue has to decide which existing DOM nodes to reuse, move, or destroy — and :key is the identity it diffs by. With a stable key (an ID that's the same for a given piece of data no matter where it ends up in the array), Vue can tell "this is still the same row, just in a new position" and simply move the existing DOM node instead of rebuilding it.

Using the array index as the key defeats this — the index describes a position, not the item's identity, so after a reorder, index 0 just silently points at whatever item is now first. Vue has no way to tell that happened, so it reuses the old DOM node for index 0 as if nothing changed, carrying over any local state (focus, scroll position, a mid-typed value) that belonged to the previous item.

💻 See the code ▾
Vue 
<li v-for="todo in todos" :key="todo.id">   // ✅ stable — todo.id never changes
  <input v-model="todo.text" />
</li>

The <input>'s typed value and focus correctly follow each todo, even after a reorder.

Vue 
<li v-for="(todo, index) in todos" :key="index">  // ❌ index is position, not identity
  <input v-model="todo.text" />
</li>

After sorting todos, a focused input can end up attached to the wrong todo.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're rendering rows from a database with real IDs

The easy, correct case — the data already has a unique ID, so use it directly. This is the #1 scenario you'll actually hit.

RememberData already has an ID → always use it as :key.
2 You're rendering a short, static list that never reorders or filters

If the list's order and contents genuinely never change at runtime, the index-as-key risk never actually triggers. It's still clearer to use a real value (like the label text) if one's available.

RememberTruly static list → index risk doesn't apply, but a real value is still clearer.
3 You sort or filter a list that uses the index as :key

A sortable or filterable table is exactly where index-as-key breaks — a user mid-typing into row 2's input can suddenly find their text attached to a different row after a sort.

RememberSortable/filterable list + index key → guaranteed to misbehave eventually.
🌍 Real-world example ▾

It's like checking a coat by name tag instead of by coat-rack number. If the racks get rearranged, the name tag still finds the right coat — the rack number would hand someone else's coat to the wrong person.
