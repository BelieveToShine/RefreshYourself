Dependency Inversion — it's the principle, not the injection

What does "depend on abstractions, not concretions" mean, and how is Dependency Inversion different from Dependency Injection?

Why it matters ▾
  • Interviewers use this to separate "I've used a DI container" from actually understanding the design rule underneath it.
  • Comes up whenever you're deciding where an interface should live — shaped by the high-level code that needs it, not by the low-level class implementing it.
  • A common opener right before drilling into ASP.NET Core's built-in container — service lifetimes, AddScoped vs. AddSingleton — that's the next question, not this one.
🔥 Easy interview recall

Dependency Inversion → the principle (depend on abstractions)

Dependency Injection → the technique (wires up which one you get)

Think: DIP says what to depend on. DI is just one way to hand it over.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Dependency Injection is not the same thing as Dependency Inversion. DIP is the design rule — depend on abstractions; DI is just one technique — constructor injection, a container, even passing the interface in by hand — for satisfying that rule at runtime.

🔄 Likely Follow-up

"How does this show up in ASP.NET Core's DI container?" services.AddScoped<IOrderRepository, SqlOrderRepository>() is the container automating the exact constructor wiring you'd otherwise do by hand — the container mechanics themselves (lifetimes, registration) are their own topic in the .NET/ASP.NET Core track.

🎯 Say this in the interview — the exact lines to land

"Dependency Inversion means high-level code depends on an abstraction that it owns, not on a concrete low-level implementation. Dependency Injection is a technique — often a container — that supplies which concrete type satisfies that abstraction at runtime; you can follow DIP without a container, and a container without abstractions doesn't give you DIP."

  • Dependency Inversion → depend on an abstraction, not a concrete class.
  • Dependency Injection → the technique that wires up which concrete type you get.
  • The abstraction is owned by the high-level side — not shaped by the low-level detail.
  • ASP.NET Core's container → automates the manual wiring, it doesn't replace the principle.
📖 Explanation ▾

Dependency Inversion says a high-level class shouldn't name a low-level class directly. An OrderService that writes new SqlOrderRepository() is locked to one concrete database — swap it, or try to test OrderService on its own, and you're stuck. The fix: give OrderService an IOrderRepository abstraction instead, and let SqlOrderRepository implement it. Both sides now point at the interface instead of one pointing straight at the other — that's the "inversion" in the name.

The detail people miss: the abstraction is shaped by OrderService's needs, not by whatever SqlOrderRepository happens to expose. The high-level side owns the interface; the low-level class just has to conform to it.

Dependency Injection is a separate thing: the mechanism that actually decides which concrete type OrderService gets handed at runtime. Passing an IOrderRepository into a constructor by hand is already DI — no container required. A container just automates that same handoff at scale.

💻 See the code ▾
C# 
public class OrderService
{
    private readonly SqlOrderRepository _repository = new SqlOrderRepository();  // ❌ concrete type

    public void PlaceOrder(Order order) => _repository.Save(order);
}

OrderService reaches straight for a concrete class — swap databases and this line has to change.

C# 
public interface IOrderRepository
{
    void Save(Order order);
}

public class SqlOrderRepository : IOrderRepository
{
    public void Save(Order order) { /* ... */ }
}

public class OrderService
{
    private readonly IOrderRepository _repository;

    public OrderService(IOrderRepository repository) => _repository = repository;  // ✅ depends on the abstraction

    public void PlaceOrder(Order order) => _repository.Save(order);
}

No container anywhere here — passing the interface in by hand still satisfies DIP.

C# 
// Program.cs
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();  // container supplies the concrete type

The container automates exactly the constructor call above — the lifetime/registration mechanics are the .NET/ASP.NET Core track's topic, not this one.

🌍 Real-world example ▾

Think of a lamp and a wall outlet. The lamp (high-level) doesn't care whether the electricity behind the outlet comes from a coal plant or a solar farm (low-level) — it only needs the standard outlet shape (the abstraction). Swap the power source and the lamp never changes; that's exactly what IOrderRepository buys OrderService when you swap out SqlOrderRepository for a different database.
