🔥 AI · Advanced · Must Know

A trace is a tree of calls, not a pile of isolated logs

How do you trace an LLM call in production — what has to be captured, and how do you trace a multi-step pipeline like RAG or an agent?

Why it matters ▾
  • Without this, debugging a bad output in production is guesswork — you can't tell what prompt actually produced it, whether it was slow because of the model or something else, or whether a cost spike came from one specific feature or model.
  • This is the observability baseline every production GenAI system needs — before evals, cost dashboards, or drift monitoring can exist, they need this data to exist first.
  • A standard senior/architect question once "we shipped an LLM feature" comes up — the interviewer wants to know you'd have this in place before it hits production, not after.
🔥 Easy interview recall

Every call → log prompt, response, tokens (in/out), latency, cost, model+version

Multi-step pipeline → one parent trace ID, each step a child span

Think: a trace is a tree, not a flat list — every span still belongs to the one request that kicked it off.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Logging each LLM call as its own flat, unrelated line. That tells you *a* call was slow or expensive, but not *which user request* it belonged to or *which other calls* ran alongside it — you lose the ability to say "this one slow retrieval is why this one generation felt slow," because nothing ties them together.

🔄 Likely Follow-up

"Why record the model version, not just the model name?" Providers update models over time under the same name — if quality regresses and the version handling each request wasn't recorded, there's no way to correlate the regression to a model change versus anything else that shifted.

🎯 Say this in the interview — the exact lines to land

"Every LLM call in production gets traced with its exact prompt, response, input/output token counts, latency, cost, and model version. For a multi-step pipeline, each step is its own span, and all the spans for one user request share a single parent trace ID — so the trace is a tree, not a flat pile of isolated logs."

  • Per call → prompt, response, tokens in/out, latency, cost, model + version.
  • Multi-step pipeline → one parent trace ID, each step a child span.
  • Model version → recorded per call, so a quality regression can be tied back to a specific model change.
  • This data feeds the eval/regression pipeline and any cost or drift dashboard — it's the raw material both are built on.
📖 Explanation ▾

Tracing an LLM call means capturing, for every single call, the exact prompt sent, the response received, input and output token counts separately, the latency, the cost, and which model and model version handled it. Without this, a bad output in production is unexplainable after the fact — there's no way to tell what prompt actually produced it, whether a slowdown came from the model or from something else in the request path, or whether a cost spike traces back to one specific feature or one specific model.

A single user request rarely maps to a single LLM call. A RAG pipeline might retrieve, rerank, then generate; an agent might take several tool-calling steps before answering. Each of those steps is its own call and deserves its own logged details — but they also need to stay connected as one logical request. That's what a trace is: one parent trace ID for the whole request, with each individual call recorded as a child span under it. A trace is a tree or chain of calls, not a flat list of calls that happen to have run around the same time.

Recording the model version specifically matters because providers update models over time, sometimes under the same model name. If output quality regresses and the version that handled each request wasn't recorded, there's no way to connect that regression back to a model change instead of chasing the wrong cause. This same tracing data is also what feeds an eval or regression-testing pipeline, and what a cost dashboard or drift-monitoring system gets built on top of — it's the raw log, not a one-off debugging aid.

💻 See the code ▾
Python 
# one call, fully traced
start = time.monotonic()
response = client.chat.completions.create(
    model="your-chat-model",
    messages=[{"role": "user", "content": prompt}],
)
log_span(
    trace_id=trace_id,          # ties this call to the parent request
    prompt=prompt,
    response=response.choices[0].message.content,
    input_tokens=response.usage.prompt_tokens,
    output_tokens=response.usage.completion_tokens,
    latency_ms=(time.monotonic() - start) * 1000,
    model=response.model,        # ✅ exact model + version, not just the name you asked for
)

The same trace_id gets passed into every span for one user request — the retrieve, rerank, and generate calls all log it, which is what turns three separate log lines back into one tree.

🌍 Real-world example ▾

Scenario: a RAG feature's answer quality drops for one specific customer segment, and support asks "why did this answer come back wrong?" With per-call tracing, you can open that exact request's trace, see the retrieve span pulled the wrong chunks, see the generate span was handed those chunks in its prompt, and confirm which model version produced the final response — turning a vague complaint into a specific, provable root cause instead of re-running the pipeline and guessing.
