IEnumerable<T> vs. IQueryable<T> — where does the query actually run?

"What's the practical difference, specifically with EF Core?"

Why it matters ▾
  • Shows up any time EF Core is in the stack — one of the most common "do you actually understand LINQ" questions.
  • Get it wrong in real code and a query that looked fine pulls an entire table into memory instead of filtering it in SQL.
  • Separates someone who's memorized LINQ syntax from someone who knows where each part of the query actually executes.
🔥 Easy interview recall

IQueryable<T> → stays a query, runs in the database

IEnumerable<T> → already objects, runs in .NET memory

Think: IQueryable is a plan the database hasn't run yet. IEnumerable is the results already sitting in memory.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

.ToList() mid-query isn't harmless materialization — call it before your filters run and the whole table gets pulled into memory first, with every later Where filtering .NET objects instead of rows in SQL.

🔄 Likely Follow-up

"So should everything just stay IQueryable<T> as long as possible?" Not always — once the data's already in memory (a List<T>, an array) there's no database left to translate against, so IEnumerable<T> is the only option and the right one; the risk only shows up when a query that's supposed to run in the database quietly stops early.

🎯 Say this in the interview — the exact lines to land

"IQueryable<T> builds an expression tree that EF Core translates into SQL and runs in the database. The moment you switch to IEnumerable<T> — directly, or through a method LINQ-to-SQL can't translate — everything from that point runs in .NET, in memory, against whatever rows have already been pulled back."

  • IQueryable<T> → keep filtering in the database for as long as possible — every Where/Select before materializing becomes part of the SQL.
  • IEnumerable<T> → use once the data's already local — an in-memory list, or logic EF Core genuinely can't translate.
  • .ToList() / .AsEnumerable() → the line where execution moves — everything before it is SQL, everything after is .NET.
  • A repository returning IQueryable<T> → lets the caller keep composing the query, but couples the service layer to EF Core.
📖 Explanation ▾

IQueryable<T> doesn't hold data — it holds a description of a query, built as an expression tree. Nothing runs until something actually enumerates it (a foreach, .ToList(), .First()); only then does EF Core translate that tree into SQL and send it to the database.

IEnumerable<T> makes no such promise — it's just "something you can loop over," and LINQ methods called on it run as ordinary .NET code, item by item, in memory. The moment a query's static type becomes IEnumerable<T> instead of IQueryable<T>, every operator chained after that point compiles against Enumerable, not Queryable — there's no more expression tree left to translate.

Why this bites specifically with EF Core: a method the SQL translator doesn't understand (a custom C# function, some string formatting) silently forces that switch. The query still compiles and still runs — it just quietly stops being one database query and starts being "fetch everything so far, then filter it in .NET."

💻 See the code ▾
C# 
IQueryable<Order> query = db.Orders
    .Where(o => o.Total > 100);      // still just an expression tree — no SQL yet

List<Order> results = query.ToList(); // ✅ NOW it translates to SQL and hits the database

Nothing runs until something enumerates the query — .ToList() is the trigger, not .Where().

C# 
var orders = db.Orders
    .AsEnumerable()                  // ❌ switches to IEnumerable<T> here
    .Where(o => IsSpecialOrder(o)); // runs in .NET, after the WHOLE table is pulled in

Everything after .AsEnumerable() compiles against Enumerable, not Queryable — EF Core already fetched every row by then.

C# 
var orders = db.Orders
    .Where(o => o.Total > 100)  // ✅ stays IQueryable<T> — becomes part of the SQL
    .ToList();                     // ✅ materialize last, once filtering is done

Keep every filter inside the IQueryable<T> chain and materialize (.ToList()) once, at the end.

🌍 Real-world example ▾

Scenario: A report page that used to load instantly starts timing out under load. The code calls .ToList() right after loading the table, then filters and sorts that in-memory list with LINQ. Every one of those filters used to be a WHERE clause — now they're .NET loops over rows that shouldn't have been fetched at all.

Architecture: Should a repository return IQueryable<T> up to the service layer, or always materialize first? Generally materialize at the repository boundary — handing an IQueryable<T> upward lets the service layer keep composing the query, which quietly couples it to EF Core and the database and makes it easy to build an inefficient query far from where it actually runs.
