Semantic Kernel and Microsoft.Extensions.AI — not rival frameworks, one is built on the other

"What's the difference between Semantic Kernel and Microsoft.Extensions.AI, and how do they fit together in a .NET GenAI application?"

Why it matters ▾
  • This is the site's own .NET differentiator — knowing the idiomatic, first-party way to build GenAI features in C# is a real edge over reaching for a Python-first framework.
  • Mixing the two up as competing SDKs instead of layers is a common misunderstanding worth clearing up before it comes up live.
  • A natural "do you know the .NET-native GenAI stack" screening question once a team starts adding AI features to an existing .NET codebase.
🔥 Easy interview recall

Microsoft.Extensions.AI → the phone line — one interface to any provider

Semantic Kernel → the call center built on that line — plugins, planning, memory

Think: Semantic Kernel sits on top of IChatClient — it doesn't replace it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Treating Semantic Kernel and Microsoft.Extensions.AI as two competing SDKs to pick between. They're not alternatives — Microsoft.Extensions.AI is the lower-level, provider-agnostic IChatClient abstraction, and Semantic Kernel is a higher-level orchestration framework that can sit on top of it (or another client) to add plugins, planning, and memory.

🔄 Likely Follow-up

"If Semantic Kernel already gives you plugins and orchestration, why would you ever use IChatClient on its own?" Plenty of features are one plain request/response — a completion, a summary, a classification — with no multi-step planning or tool-calling involved. Reaching for the full orchestration framework there is unnecessary weight when the plain abstraction already does the job.

🎯 Say this in the interview — the exact lines to land

"Microsoft.Extensions.AI gives .NET a provider-agnostic IChatClient abstraction, so application code depends on one interface instead of a specific vendor SDK. Semantic Kernel is a higher-level orchestration framework built on top of that same idea — it adds plugins, planners, and memory — so the two aren't competing choices, they're different layers of the same idiomatic .NET GenAI stack."

  • IChatClient → swap providers without touching app code — or fake it in a unit test.
  • Semantic Kernel plugins → the .NET version of tool/function calling — reusable functions the model can invoke.
  • Semantic Kernel planner → breaks a goal into a sequence of plugin calls automatically.
  • Semantic Kernel memory → stores and retrieves context across a conversation or session.
  • Plain IChatClient → for a single request/response; Semantic Kernel → once orchestration is needed.
📖 Explanation ▾

Microsoft.Extensions.AI provides a unified abstraction — commonly referred to as IChatClient — for talking to different LLM providers from .NET code through one consistent interface. Application code depends on that abstraction, not on any one provider's specific SDK, which is exactly why it's easy to swap providers later, or drop in a fake implementation for a unit test.

Semantic Kernel is a higher-level .NET framework built for orchestrating a whole GenAI application, not just a single call. Its plugins are the .NET equivalent of tool-calling — reusable functions the model can invoke. Its planner breaks a bigger goal into a sequence of those plugin calls, and its memory stores and retrieves context across a conversation or session. Semantic Kernel can sit on top of Microsoft.Extensions.AI's IChatClient — or another client — to add all of that.

It's roughly the same relationship as a generic HTTP client library and a full application framework built on top of HTTP: one is the low-level way to make a call, the other adds routing, structure, and state around it. For a .NET-focused engineer, this pairing matters because it's the idiomatic, first-party way to build GenAI features in a .NET/C# codebase, rather than reaching for a Python-first framework.

💻 See the code ▾
C# 
// Any provider's SDK can be wrapped as an IChatClient
IChatClient client = new AzureOpenAIClient(endpoint, credential)
    .GetChatClient("gpt-4o-mini")
    .AsIChatClient();                                    // ✅ app only sees the interface

ChatResponse response = await client.GetResponseAsync(
    "Summarize this support ticket in one sentence.");

Console.WriteLine(response.Text);

Swap AzureOpenAIClient for any other provider's SDK — the rest of the app only ever calls IChatClient.

C# 
public class TicketPlugin
{
    [KernelFunction, Description("Looks up a support ticket by its ID.")]
    public string GetTicket(string ticketId) => _tickets[ticketId];
}

var builder = Kernel.CreateBuilder();
builder.Services.AddOpenAIChatCompletion("gpt-4o-mini", apiKey);
builder.Plugins.AddFromType<TicketPlugin>();          // ✅ model can now call GetTicket

Kernel kernel = builder.Build();

[KernelFunction] marks a plain C# method as something the model can call — Semantic Kernel's version of tool calling.

🌍 Real-world example ▾

A phone line vs. a call center. Microsoft.Extensions.AI is the phone line — pick up any provider's handset and it still works the same way. Semantic Kernel is the call center built around that line — routing calls, following a script, remembering who called before. Use just the phone line for a simple call, or the whole call center once the conversation needs steps and memory.
