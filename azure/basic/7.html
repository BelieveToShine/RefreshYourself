Key Vault — a locker for secrets, keys & certificates, not config

"What is Key Vault, and what belongs in it?"

Why it matters ▾
🔒 Key Vault
❗ ProblemA connection string or password typed straight into appsettings.json ends up sitting in plain text — and one careless commit puts it in source control for good.
✅ SolutionKey Vault stores that secret (plus encryption keys and certificates) centrally, and the app authenticates with an identity to read it by name at runtime instead of having the value baked into a file.
RecallKey Vault = secrets/keys/certs an app reads by name — never a config file.
🔥 Easy interview recall

Secrets → passwords & connection strings

Keys → encryption keys, can be HSM-backed

Certificates → TLS/SSL certificates

Think: Key Vault is a locker, not a settings file.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Key Vault is just a place to put any app configuration. It's built for secrets, keys, and certificates specifically — it carries request-rate limits that make it a poor fit for general config like feature flags, which is exactly what Azure App Configuration exists for.

🔄 Likely Follow-up

"How does an app actually authenticate to reach Key Vault?" Typically through a Managed Identity, not a stored key — the mechanics of how that works are their own page, deliberately not restated here.

🎯 Say this in the interview — the exact lines to land

"Key Vault holds secrets, keys, and certificates — not general app config. Apps reach in using an identity at runtime, instead of a key or password hardcoded into a config file."

  • Three things only → secrets, encryption keys, and certificates — not settings or feature flags.
  • Not general config → rate limits make it the wrong place for app config; that's Azure App Configuration's job.
  • Managed Identity accesses it → apps authenticate with an identity, never a stored key, at runtime.
  • Never in source control → the real payoff: a secret never sits in appsettings.json or gets committed to git.
📖 Explanation ▾

Key Vault is a managed, secure store for three distinct kinds of material: secrets (connection strings, passwords, API keys), keys (encryption keys, some backed by a hardware security module for extra protection), and certificates. An app reads what it needs from Key Vault at runtime instead of having the value typed into appsettings.json or checked into a source file.

The point isn't just "somewhere else to put it" — it's that the value never has to leave Key Vault's control to be distributed by hand. An app authenticates to Key Vault (usually with a Managed Identity — its own page covers exactly how), asks for a value by name, and gets it back over an authenticated call. Nobody emails a password around or pastes one into a chat to get an app running.

💻 See the code ▾
CLI 
az keyvault secret set --vault-name my-vault --name DbPassword --value "..."

Creates or updates the secret named DbPassword inside my-vault — the app reads it back by name at runtime instead of storing the value itself.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app needs a database password or connection string at startup

This is the #1 scenario you'll actually run into — the exact case the CLI example above creates. The app authenticates in and asks Key Vault for DbPassword by name; the value is never typed into a config file.

RememberConnection string / password → a secret, read by name at runtime.
2 Your app needs to encrypt or decrypt data with a key

This is a key, not a secret — a distinct object type Key Vault stores, some backed by a hardware security module for extra protection. The app calls Key Vault to use the key, the same way it would ask for a secret by name.

RememberNeed to encrypt/decrypt → a key, can be HSM-backed.
3 You're tempted to put feature flags or general app settings in Key Vault too

Key Vault carries request-rate limits that make it a poor fit for general config — feature flags and settings belong in Azure App Configuration instead. A common trap — candidates often assume Key Vault is a generic "settings store" because it's secure, when its real job is narrower than that.

RememberFeature flags / general config → App Configuration, not Key Vault.
🌍 Real-world example ▾

A web app's database connection string lives in Key Vault, not in appsettings.json. The app asks Key Vault for it by name at startup, so the value never gets typed into a config file — and never ends up checked into source control by accident.
