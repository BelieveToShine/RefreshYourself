A million records overnight isn't one chat request, repeated — it's a bounded, queued pipeline

How would you design a pipeline that enriches millions of records with an LLM overnight, and keep it inside a fixed cost and rate budget?

Why it matters ▾
  • Separates candidates who default to "just call the API in a loop" from those who actually think about throughput, cost, and failure recovery at scale — a common senior/ staff system-design probe.
  • Comes up any time a real product needs an LLM to enrich an existing dataset — tagging, summarizing, classifying millions of rows — rather than answering one live user request.
  • Checks whether someone knows how to keep a large job inside a rate-limit and cost budget, and how to make it safely resumable, not just "add more parallel calls."
🔥 Easy interview recall

Bulk job = queue + a bounded worker pool — never one call at a time, never unbounded either.

Think: a toll booth with 3 open lanes — cars queue up, only 3 pass through at once no matter how long the line gets.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming more concurrency is always better. Firing hundreds of parallel LLM calls at once blows through the provider's rate limit and makes the job's cost unpredictable — the fix is a bounded worker pool (a semaphore or a fixed-size pool), not "as parallel as possible."

🔄 Likely Follow-up

"What happens if the job dies halfway through and you rerun it?" Nothing bad — every write is idempotent (behind a unique constraint, or an upsert), so replaying already-completed records just overwrites the same result instead of creating a duplicate.

🎯 Say this in the interview — the exact lines to land

"I'd treat it as an async, queued pipeline, not a live request: push records onto a queue, pull them with a bounded pool of concurrent workers so I respect the provider's rate limit and keep cost predictable, use a batch API if the provider offers one and the results don't need to be ready immediately, and make every write idempotent — behind a unique constraint or an upsert — so a retried or resumed run can never create duplicates."

  • Queue + worker pool → decouples processing from a live request/response call, so many records get handled concurrently instead of one at a time.
  • Batch API → lower cost, results come back later — a natural fit for overnight, non-time-sensitive work if the provider offers one.
  • Bound the concurrency → a semaphore or fixed-size pool caps rate-limit and cost exposure, instead of firing an unbounded flood of parallel calls.
  • Idempotent writes → an upsert or unique constraint means a retried run can't create duplicate records.
📖 Explanation ▾

A nightly job that enriches millions of records doesn't need a real-time answer the way a live chat request does — nobody is staring at a screen waiting on record #40,000. Treating it like a live request anyway, one call at a time, wastes the chance to process it far more efficiently. The better shape is queue-based processing: records go onto a queue, and a pool of workers pulls from that queue and calls the LLM for each one, handling many records concurrently instead of sequentially. This is an async, decoupled pattern — nothing is waiting on a synchronous request/response the whole time.

Some providers also offer a batch API built specifically for large volumes of non-time-sensitive requests, often at a meaningfully lower cost than real-time calls, in exchange for the results coming back later rather than immediately. That trade — cheaper, but not instant — is exactly the shape of a nightly enrichment job, which makes it worth checking for before building a fully custom queue-and-workers setup.

Whichever approach is used, the number of records being processed at once has to stay bounded — a semaphore or a fixed-size worker pool — both to respect the provider's rate limits and to keep the job's total cost and throughput predictable, rather than firing unbounded parallel requests. And because a bulk job can partially fail and need to be retried or resumed, every write should be idempotent — behind a unique constraint, or an upsert — so replaying a run that already got partway through doesn't create duplicate records.

💻 See the code ▾
Python 
semaphore = asyncio.Semaphore(3)  # only 3 calls in flight at once

async def process(record):
    async with semaphore:                  # blocks here until a slot frees
        result = await llm.enrich(record)
        await db.upsert(record.id, result)  # idempotent write

await asyncio.gather(*(process(r) for r in queue))

The semaphore is the bound — a 4th record's process() call simply waits at async with semaphore until a slot frees; it never fires a 4th concurrent LLM call.

SQL (Postgres) 
INSERT INTO enriched_records (record_id, summary)
VALUES (@id, @summary)
ON CONFLICT (record_id) DO UPDATE
SET summary = EXCLUDED.summary;  -- upsert: safe to run twice

Re-running the whole job after a crash just re-applies the same rows — the unique constraint on record_id means no duplicate row is ever created.

🌍 Real-world example ▾

A team needs an LLM to summarize five million support tickets every night before an analytics dashboard refreshes at 6am, without blowing the month's API budget. The answer: push every ticket ID onto a queue, run a small worker pool sized to the account's rate limit pulling from it, use the provider's batch API if the summaries don't need to exist before the very next business day, and upsert each ticket's summary by ticket ID — so if the job crashes at 2am and gets restarted, it just picks up from where it left off without reprocessing, or duplicating, the tickets it already finished.
