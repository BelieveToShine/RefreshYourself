A cold start is the price of a fresh environment

"What is a cold start, and how do you reduce its impact?"

Why it matters ▾
🧊 Provisioned Concurrency
❗ ProblemBursty or scaling traffic keeps launching brand-new Lambda environments, and each one pays the init/download cold-start cost before your handler even runs — you can't guarantee consistent latency this way.
✅ SolutionProvisioned concurrency pre-initializes a set number of environments and keeps them warm ahead of time, so invocations landing on that reserved capacity skip the init phase entirely — you pay for that warm capacity even while it's idle.
RecallProvisioned concurrency = pay for pre-warmed capacity to guarantee latency.
🔒 Reserved Concurrency
❗ ProblemWithout a cap, one Lambda function scaling up could consume the account's whole concurrency limit — starving every other function, or overwhelming a downstream resource that can only handle so many simultaneous connections.
✅ SolutionReserved concurrency sets a hard max — and a guarantee — on how many concurrent executions that one function can have; it says nothing about whether those environments are warm, which is exactly the name mix-up candidates make with provisioned concurrency.
RecallReserved concurrency = a concurrency ceiling/guarantee, not a warmth setting.
🔥 Easy interview recall

Cold start = "the setup tax on a brand-new Lambda environment."

Think: Provisioned concurrency → keeps environments warm. Reserved concurrency → just caps how many can run at once.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 Don't mix these two — the single most valuable distinction on this page
⚠️ Common Trap

Reserved concurrency fixes cold starts. It doesn't — reserved concurrency only caps/guarantees how many concurrent executions a function can have; it says nothing about whether those environments are warm. Only provisioned concurrency pre-initializes environments ahead of time.

🔄 Likely Follow-up

"How does Lambda scale under load?" AWS automatically launches new concurrent execution environments as needed — each handling one invocation at a time — up to the account/function's concurrency limits; that's exactly what triggers a cold start, when new environments are needed faster than they can spin up.

🎯 Say this in the interview — the exact lines to land

"A cold start is the cost of spinning up a fresh execution environment — provisioned concurrency keeps environments warm to avoid it."

  • Provisioned concurrency → pre-warms a set number of environments so that capacity never pays the cold-start cost — you're billed for it even while idle.
  • Reserved concurrency → just caps/guarantees a max number of concurrent executions — unrelated to warmth, easy to confuse with provisioned by name alone.
  • Cold start → happens on the first invocation, or whenever scaling needs a brand-new concurrent instance.
  • Init code → runs once per fresh environment; handler code runs on every single invocation, warm or cold.
📖 Explanation ▾

Lambda is serverless compute — it runs your code in response to a trigger (API Gateway, an S3 event, SQS, EventBridge, and more), scales automatically, and bills per invocation and duration. A cold start is the latency of provisioning a fresh execution environment before your handler can even run: downloading your code, and initializing the runtime plus any of your own init-time code. This happens on the very first invocation, or any time traffic scales up and a brand-new concurrent instance is needed.

Provisioned concurrency fixes this directly — it keeps a specified number of environments pre-initialized and sitting warm, so invocations that land on that reserved capacity skip the init phase entirely. That comes at a cost: you pay for the warm capacity whether or not it's actually being used. Reserved concurrency is a different, unrelated setting — it simply caps (and guarantees) the maximum number of concurrent executions a function can have; it does nothing to keep any environment warm.

💻 See the code ▾
🐍 Python 
import boto3

# INIT CODE — runs ONCE per fresh (cold) environment
s3 = boto3.client("s3")
CONFIG = load_config()  # heavy setup happens here, not per-request

def handler(event, context):
    # HANDLER CODE — runs on EVERY invocation, warm or cold
    bucket = event["bucket"]
    return s3.get_object(Bucket=bucket, Key=CONFIG["key"])

Everything outside handler() runs once per new environment — that's the cost a cold start pays. Everything inside it runs every single call, warm or cold.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your customer-facing API needs consistently fast responses even under bursty traffic

This is the #1 scenario you'll actually reach for provisioned concurrency: it pre-warms a fixed number of environments so invocations landing on that capacity skip init entirely, matching this page's own real-world example.

RememberProvisioned concurrency = pay for warm capacity to guarantee latency.
2 A downstream resource — a database, a rate-limited third-party API — can only handle so many simultaneous connections

Reserved concurrency caps how many concurrent executions that function can ever have, protecting the downstream resource from being overwhelmed — it's a concurrency ceiling, and has nothing to do with keeping anything warm.

RememberReserved concurrency = a hard cap/guarantee on concurrency, not a warmth setting.
3 You set reserved concurrency on a latency-sensitive function, expecting it to also stop cold starts

It won't help — reserved concurrency only caps/guarantees how many executions can run at once; it does nothing to pre-initialize environments. Only provisioned concurrency actually pre-warms.

RememberReserved concurrency ≠ warm. Only provisioned concurrency fixes cold starts.
🌍 Real-world example ▾

A latency-sensitive, customer-facing API uses provisioned concurrency to guarantee consistent response times no matter when a request arrives. An internal batch-processing function, run on a schedule where nobody's waiting on the response, accepts occasional cold starts instead — latency just doesn't matter there, so paying for warm capacity would be wasted money.
