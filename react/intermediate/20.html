Context, Redux or Zustand — who re-renders when one value changes?

"Context, Redux or Zustand — how do you choose for client state?"

Why it matters ▾
🌐 Context
❗ ProblemPassing a value through many levels by props is tedious, but Context re-renders every consumer when it changes.
✅ SolutionUse it for values that rarely change — theme, locale, current user.
RecallContext = delivery, not state management.
🏛️ Redux
❗ ProblemIn a big app with many people, state changes scattered everywhere become hard to trace.
✅ SolutionOne store, changed only by actions through reducers, with devtools to inspect each change.
RecallRedux = one store, strict rules, great tooling.
🐻 Zustand
❗ ProblemContext re-renders too much, and Redux can feel heavy for a small app.
✅ SolutionA small store read with selectors, so a component re-renders only when its slice changes.
RecallZustand = small store, selector subscriptions.
🔥 Easy interview recall

Context → low-frequency values

Redux → big app, strict, traceable

Zustand → small store, selectors

Think: Context re-renders all consumers. Stores re-render only the changed selector. Server data goes in a query cache.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Context is a state management tool." It is only a delivery mechanism — the state still lives in useState or useReducer — and it re-renders every consumer when the value changes. A value that changes often (like typed text) in one big context can cause needless re-renders.

🔄 Likely Follow-up

"Where does data fetched from an API go?" Not in any of these. It is server state, which belongs in a cache like TanStack Query or SWR — see Server State vs. Client State. Stores and context are for client state.

🎯 Say this in the interview — the exact lines to land

"Context delivers a value and re-renders every consumer when it changes, so I use it for low-frequency things like a theme or the current user. For shared client state that changes often, I use a store with selectors — Redux when the app or team needs one traceable store with strict rules and devtools, Zustand when I want something small and quick. I choose by scale and team, not fashion, and server data goes in a query cache instead."

  • Context → low-frequency values: theme, locale, current user.
  • Redux → big app, many people: one store, reducers, devtools.
  • Zustand → small store read with selectors.
  • Context update → all consumers re-render.
  • Selector → re-render only when the selected slice changes (Redux, Zustand).
  • Choose by scale and team, not fashion.
📖 Explanation ▾

Context is a way to deliver a value, not a way to manage state — the state still lives in useState or useReducer. When the provider's value changes, every component that reads that context re-renders, even if it only used part of the value. That is fine for a theme, a locale, or the current user. It gets costly for values that change often.

Redux (written today with Redux Toolkit) keeps one store that changes only through dispatched actions handled by reducers, with devtools to inspect each change. A component reads with a selector and re-renders only when its selected value changes. The price is more structure — which is exactly what a big app with many contributors wants. Zustand is a small store you read with selectors too, with no provider needed and less ceremony.

A sensible order: start with useState / useReducer (see useReducer vs. useState), use context for low-frequency shared values (Context API), and add a store only when state is shared widely and updates often. Data that comes from the server belongs in a query cache instead (Server State vs. Client State). More on the architecture view is in State Management Architecture.

💻 See the code ▾
JSX 
const ThemeContext = createContext('light');

// every component that calls useContext(ThemeContext)
// re-renders whenever this value changes
<ThemeContext.Provider value={theme}>{children}</ThemeContext.Provider>

Context re-renders all consumers of the value — good for rarely-changing things like a theme.

JSX 
const counter = createSlice({
  name: 'counter',
  initialState: { count: 0 },
  reducers: { inc(state) { state.count += 1; } },  // Redux Toolkit allows this syntax
});
const count = useSelector((s) => s.counter.count);  // ✅ re-renders only if count changes

Redux Toolkit uses a helper (Immer) that turns this "change in place" syntax into a new state — plain reducers still must not mutate.

JSX 
const useCounter = create((set) => ({
  count: 0,
  inc: () => set((s) => ({ count: s.count + 1 })),
}));
const count = useCounter((s) => s.count);  // ✅ selector → re-renders only if count changes

Zustand: a small store plus a selector — no provider needed.

🌍 Real-world example ▾

Context is a loudspeaker; a selector store is a pager. The loudspeaker announces to every room whether or not they care; the pager only buzzes the people who subscribed to that topic.
