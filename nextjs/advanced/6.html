A Server Component doesn't send HTML — it sends a serialized tree

"What actually gets sent across the Server-to-Client Component boundary, and why can't you pass a function prop?"

Why it matters ▾
📦 The RSC payload
❗ ProblemAssuming a Server Component just "sends HTML" or "sends JSON" leads straight to confusion about why a function, a class instance, or a Date can't simply be passed as a prop into a Client Component.
✅ SolutionA Server Component produces a special serialized format — the RSC payload — describing the rendered tree; only genuinely serializable values can cross into a Client Component.
RecallRSC payload = a serialized tree description, not HTML, not plain JSON.
🔥 Easy interview recall

RSC payload = "a serialized description of the tree, not the rendered output."

Think: only strings, numbers, plain objects/arrays (and a few special cases like Promises) can cross into a Client Component — a function can't.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

You can't pass a function (an event handler, a DB client instance) as a prop from a Server Component into a Client Component. It isn't serializable across the RSC boundary — it errors or silently fails depending on what's attempted.

🔄 Likely Follow-up

"How does a Server Action get around the 'functions can't cross the boundary' rule, then?" It isn't really passed as a live function reference — the framework replaces it with a special reference that, when invoked client-side, triggers a real network call back to the server-side function by its registered ID.

🎯 Say this in the interview — the exact lines to land

"A Server Component produces an RSC payload — a serialized description of the rendered tree, not HTML and not plain JSON — which React uses on the client to reconcile and hydrate. Only serializable values cross that boundary into a Client Component; functions and class instances generally can't."

  • RSC payload → a serialized tree description, not HTML, not JSON.
  • Can cross as props → strings, numbers, plain objects/arrays, some Promises.
  • Can't cross → functions, class instances, raw Dates without explicit handling.
  • Server Actions → a reference, not a closure — invoking it makes a real network call.
📖 Explanation ▾

When a Server Component renders, React doesn't hand the client a finished HTML string the way traditional server-rendered HTML works, and it isn't plain JSON either — it's a special serialized format describing the component tree: which elements exist, their props, and where a Client Component boundary begins. The client-side React runtime reads that payload to reconcile the tree and hydrate the interactive parts.

Because the payload has to be serialized, only values with a real serialized representation can cross from a Server Component into a Client Component as props — strings, numbers, booleans, plain objects and arrays, and a few React-specific special cases like Promises (used for streaming data into a Client Component). Functions, class instances, and raw Dates don't have a general serialized form, so passing one directly either throws or produces unexpected behavior.

Server Actions look like an exception but aren't really one: the framework doesn't serialize the function body at all. It replaces the function with a reference tied to a registered server-side ID, and calling that reference from the client triggers an actual network request back to the real function on the server — the "function" the client holds is a remote-call stub, not a closure.

💻 See the code ▾
JavaScript 
// Server Component
function Page() {
  const onClick = () => console.log('hi');
  return <ClientButton onClick={onClick} />; // ❌ can't serialize a function
}

A plain closure has no serialized form — this throws at render time, not silently.

JavaScript 
// Server Component
'use server';
async function deletePost(id) { /* runs on the server */ }

function Page() {
  return <ClientButton onClick={deletePost} />; // ✅ a Server Action, not a closure
}

This "function" is actually a reference — calling it client-side makes a real network call back to deletePost on the server.

🧭 Use Cases — recognize these when they happen to you ▾
1 Passing plain data down into an interactive Client Component

Strings, numbers, and plain objects/arrays cross the boundary with no special handling — this is the normal, common case.

RememberPlain data props → always fine across the RSC boundary.
2 Passing a database client or an event handler straight down

A DB client instance or a plain closure has no serialized form. A common interview trap: assuming "it's just JavaScript" means anything can be passed as a prop.

RememberNot every JS value can cross the RSC boundary — only serializable ones.
3 Wiring a mutation button to run server logic

A Server Action passed as a prop is really a reference to a registered server function — invoking it client-side makes a real request, it doesn't run any code locally.

RememberServer Action prop → a remote-call stub, not a live function.
🌍 Real-world example ▾

A Server Component fetches a post from the database and renders a Client Component "like" button. The post's title and ID (plain data) pass through fine. If that Server Component also tried to hand the button a direct reference to its database connection "to save a round trip," it would fail — the connection object isn't serializable. The correct pattern is a Server Action: a small server-side function the button invokes by reference, which runs the real database write back on the server.
