Dependency Injection — every injector in the tree gets its own chance to answer first

How does hierarchical dependency injection actually work, and what happens when a provider is declared at the component level?

Why it matters ▾
🌳 Root
❗ ProblemIf every part of an app-wide singleton (logging, auth state, a shared cart) had to be created and wired up separately in each component, they'd never reliably stay in sync with each other.
✅ SolutionprovidedIn: 'root' registers a service once with the app's root injector, so every part of the tree resolves the same token to that exact one instance by default.
RecallRoot = one shared instance, app-wide, until something re-provides the token lower down.
🧩 Component
❗ ProblemSometimes one part of the UI genuinely needs a different implementation of a shared service (e.g. a dark theme just for an admin panel) — sharing root's single instance would leak that override onto the whole app.
✅ SolutionDeclaring the same token in a component's own providers array creates a new instance scoped to just that component and its descendants, shadowing root without touching root's instance anywhere else.
RecallComponent providers = its own instance for that subtree, shadows root.
🛣️ Route
❗ ProblemFeature-scoped state (like an in-progress checkout wizard) shouldn't outlive the feature — keeping it in a root or component instance risks it lingering or leaking into unrelated screens after the user navigates away.
✅ SolutionA route's own providers config spins up an injector scoped to that route and its children, which is destroyed the moment the user leaves — a fresh instance is created next time the route activates.
RecallRoute providers = feature-scoped, destroyed on leaving, fresh on return.
🔥 Easy interview recall

providedIn: 'root' → one instance, app-wide

component providers → its own instance, shadows root

Think: Angular walks UP the tree from the request, never down — the closest provider it finds wins, even over root's.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

providedIn: 'root' does not guarantee one instance forever. Providing that same service again inside any component's own providers array silently creates a separate instance for that subtree — state that looks "randomly reset" is almost always a re-provided token, not a bug in the service itself.

🔄 Likely Follow-up

"If a route provides a service and the user navigates away then back, does the same instance survive?" No — a route-level injector, and everything it provides, is destroyed when leaving that route, and a brand-new injector with a fresh instance is created the next time the route activates again — exactly why route-level providers suit temporary, feature-scoped state, not anything that needs to persist across navigations.

🎯 Say this in the interview — the exact lines to land

"Angular's injectors form a tree that mirrors the component tree — a request for a dependency starts at the requester's own injector and walks up through its parents until it finds a provider, and the first one found, closest to the requester, wins. A provider declared in a component's own providers array creates a new instance scoped to that component and its descendants, completely shadowing whatever the root injector would otherwise supply for that same token."

  • providedIn: 'root' → one shared instance, app-wide by default.
  • Component-level providers → its own instance, shadows root for that subtree.
  • Same service provided at several components → separate, independent instances, never sharing state.
  • Route-level providers → destroyed on navigating away, a fresh instance next time the route activates.
  • multi: true on the same token → returns an array of every registered value, like HTTP_INTERCEPTORS.
📖 Explanation ▾

Angular's dependency injection isn't one flat container — every component can have its own injector, and together they form a tree that mirrors the component tree, with a single root injector at the top holding everything registered with providedIn: 'root'. When a component asks for a dependency, Angular starts at that component's own injector and walks up toward the root, stopping at the first provider it finds — closest to the requester wins, so a component-level provider for a token completely shadows whatever root would have supplied, for that entire subtree.

The same closest-wins rule extends past components. A route's own providers array spins up a fresh injector scoped to that route and its children — useful for state that should live only as long as a feature is active, then get thrown away on navigating elsewhere. InjectionToken<T> exists because a TypeScript interface has no identity at runtime — it gives a plain config object or interface-shaped value a real, unique key to be injected by, resolved with useValue for a fixed object or useFactory when the value has to be computed from something read first, like an environment flag or another injected service.

Providers registered with multi: true for the same token don't override each other — injecting the token returns an array of every value registered for it, which is exactly how Angular's own HTTP_INTERCEPTORS works. The same resolution mechanism is also what makes testing easy: TestBed.configureTestingModule can provide a mock for a token inside just that one test, without touching the real service class at all.

💻 See the code ▾
TypeScript 
@Component({
  selector: 'app-admin-panel',
  providers: [
    { provide: ThemeService, useClass: DarkThemeService } // this subtree gets DarkThemeService
  ]
})
export class AdminPanelComponent {}

Every child inside AdminPanelComponent now resolves ThemeService to DarkThemeService — root's own instance is never reached for this subtree.

TypeScript 
providers: [
  { provide: VALIDATORS, useValue: customValidator, multi: true } // adds to the list, doesn't replace it
]

Injecting VALIDATORS now returns an array of every value registered this way — the same pattern HTTP_INTERCEPTORS uses.

🧭 Use Cases — recognize these when they happen to you ▾
1 A service marked providedIn: 'root' somehow holds different state in different parts of the app

Somewhere down the tree, a component (or route) re-provided that exact same token in its own providers array. That subtree's lookup now stops there and never reaches root, so it silently gets a completely separate instance. This is the single most common cause of "my singleton isn't behaving like a singleton" — and the near-guaranteed follow-up once you explain the basic idea.

Remember"root" means one instance only until something re-provides that same token lower in the tree.
2 One part of the UI needs a different implementation of a shared service, without touching the rest of the app

Declaring { provide: ThemeService, useClass: DarkThemeService } inside just that one component's own providers array creates a new instance scoped to it and its descendants — everywhere else in the app keeps resolving to root's original ThemeService, completely untouched.

RememberComponent-level providers = an intentional, scoped override — not a bug.
3 A feature stores its in-progress state in a route-provided service, and the user navigates away then back

Leaving the route destroys its injector, and everything it provided along with it. Navigating back creates a brand-new injector with a fresh instance — none of the previous progress survives, by design, which is exactly why route-level providers suit temporary, feature-scoped state and nothing that needs to persist across navigations.

RememberRoute providers = feature-scoped and disposable, never for state that must outlive the route.
🌍 Real-world example ▾

Asking a question inside a large company. Hierarchical DI is like asking your own team lead first — if they don't have a specific answer or policy, the question goes up to the department head, then eventually to company-wide policy at the top. If your own team lead HAS set a team-specific policy that overrides the company-wide one, your team follows theirs, not head office's, for as long as you're on that team.
