⭐ LINQ · Advanced · Should Know

One winner per department — OrderByDescending().First(), or MaxBy()?

"Write a query that returns the highest-paid employee in each department."

Why it matters ▾
🏆 Top-Per-Group
❗ Problem"Highest-paid per department" needs a sort-and-pick-the-top step applied inside every group, not across the whole list — a plain OrderByDescending(Salary).First() on the full employee list only finds the single highest-paid person company-wide, not one per department.
✅ SolutionGroupBy(e => e.Department) first, so the sort-and-pick runs once per group: either .Select(g => g.OrderByDescending(e => e.Salary).First()), or the shorter .Select(g => g.MaxBy(e => e.Salary)) available from .NET 6 onward.
RecallGroup first, then pick the top — per group, not across the whole list.
🔥 Easy interview recall

GroupBy(Dept).Select(g => g.OrderByDescending(Salary).First()) → works everywhere

GroupBy(Dept).Select(g => g.MaxBy(Salary)) → .NET 6+, shorter

Think: group first, then pick the top of each group — MaxBy is just a shorter way to say OrderByDescending().First() once you're inside a group.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"OrderByDescending(Salary).First() on the whole list finds the top earner per department." Without GroupBy first, that finds exactly one employee company-wide — the highest-paid person overall, not one per department.

🔄 Likely Follow-up

"What if two employees in the same department tie on salary?" Both OrderByDescending().First() and MaxBy() return exactly one of the tied employees — which one is unspecified unless a secondary sort key (like employee ID) breaks the tie deterministically.

🎯 Say this in the interview — the exact lines to land

"I'd group by department first, then pick the top salary inside each group — either g.OrderByDescending(e => e.Salary).First(), which works on any .NET version, or the shorter g.MaxBy(e => e.Salary) from .NET 6 onward."

  • GroupBy(Department) → required first — otherwise you get one winner company-wide, not per department.
  • MaxBy(Salary) → more readable, .NET 6+, one call instead of two.
  • OrderByDescending().First() → works on any version, slightly more verbose.
  • Both → return one arbitrary employee on a salary tie, unless a secondary key is added.
📖 Explanation ▾

The shape of this problem is "top N within each group," not "top N overall" — which means GroupBy has to run before any sorting or picking happens. Each group produced by GroupBy(e => e.Department) is itself a small sequence of just that department's employees, and the sort-and-pick step runs separately inside each one.

OrderByDescending(e => e.Salary).First() sorts the whole group by salary descending and takes the first result — correct on every .NET version, and the same general pattern used in Inner Join vs. Left Outer Join's GroupJoin-based scenarios. MaxBy(e => e.Salary) (.NET 6+) does the identical job in one call — it finds the element with the maximum key without a full sort, which also reads more directly as "the maximum," not "sort, then take the first."

Neither approach guarantees which employee wins a tie. If two employees in the same department share the exact same salary, both methods return one of them — which one is an implementation detail, not a documented contract. A secondary sort key (e.g. .ThenBy(e => e.Id) before .First()) is the fix if a deterministic tie-break actually matters.

💻 See the code ▾
C# 
var topPerDept = employees
    .GroupBy(e => e.Department)
    .Select(g => g.OrderByDescending(e => e.Salary).First());
// ✅ works on every .NET version

Sorts each group, then takes the first — correct, slightly more to type.

C# 
var topPerDept = employees
    .GroupBy(e => e.Department)
    .Select(g => g.MaxBy(e => e.Salary));
// ✅ .NET 6+ — one call, reads as "the maximum," not "sort then take first"

MaxBy is the more readable default once .NET 6+ is available.

🧭 Use Cases — recognize these when they happen to you ▾
1 The codebase already targets .NET 6 or later, and readability is the priority

This is the default choice on a modern codebase: MaxBy says exactly what's happening in one call, with no intermediate "sort the whole group" step to read past.

Remember.NET 6+ and no other requirement → MaxBy is the cleaner default.
2 The codebase still targets an older .NET version, or needs a deterministic tie-break

OrderByDescending().First() still works everywhere and is the natural place to add a .ThenBy(e => e.Id) secondary key, which MaxBy has no equivalent slot for.

RememberPre-.NET 6, or need a tie-break → OrderByDescending().First() with a ThenBy.
3 A report shows only one employee total instead of one per department

This is the exact Common Trap surfacing as a bug: skipping GroupBy and sorting the full employee list finds exactly one person — the company's single highest earner — not one winner per department.

RememberOnly one row came back instead of N → check whether GroupBy ran before the sort.
🌍 Real-world example ▾

HR wants a one-page report: the top earner in every department, refreshed nightly. employees.GroupBy(e => e.Department).Select(g => g.MaxBy(e => e.Salary)) produces exactly that list in a single readable statement — one row per department, no manual looping, and no risk of accidentally sorting the whole company into a single winner.
