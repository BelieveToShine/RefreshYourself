🔥 Java · Advanced · Must Know

volatile makes a value visible — it doesn't make count++ atomic

"Does marking a counter volatile make count++ thread-safe?"

Why it matters ▾
👁️ volatile
❗ ProblemWithout any visibility guarantee, one thread's write to a shared field might never become visible to another thread reading it — the JMM allows caching/reordering that can hide the write indefinitely.
✅ Solutionvolatile guarantees every read sees the latest write, and prevents certain reorderings around it — but it only makes each individual read or write visible, not a sequence of them.
Recallvolatile = every read sees the latest write. Nothing more.
🔒 synchronized
❗ ProblemA compound operation — read, modify, then write, like count++ — needs to run as one indivisible step, or two threads can both read the same value before either writes back, losing an update.
✅ Solutionsynchronized gives both visibility and mutual exclusion: only one thread executes the guarded block at a time, so the whole read-modify-write sequence completes as one atomic step.
Recallsynchronized = visibility AND atomicity, at the cost of locking.
⚛️ Atomic classes
❗ ProblemLocking around a simple counter increment works, but pays for a full lock acquire/release on every single operation, even under light contention.
✅ SolutionAtomicInteger/AtomicLong provide the same compound-operation atomicity using a lock-free CAS (compare-and-swap) hardware instruction — often faster than synchronized for simple counter-style state.
RecallAtomic classes = lock-free atomicity via CAS.
🔥 Easy interview recall

volatile → visibility only, not atomicity

synchronized → visibility + atomicity, with locking

AtomicInteger → atomicity, lock-free (CAS)

Think: count++ on a plain volatile int is still two steps — read, then write — and another thread can slip in between them.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

volatile int count; count++; is not thread-safe. The increment is read-then-write, two separate operations — volatile only protects the visibility of each individual read/write, not the atomicity of the sequence between them.

🔄 Likely Follow-up

"If AtomicInteger is often faster than synchronized, why not just use it everywhere?" Atomic classes only make a single, simple compound operation atomic — they can't guard a whole multi-step critical section (like transferring between two balances) the way synchronized or a Lock can, and CAS also degrades under very high contention since failed attempts just retry.

🎯 Say this in the interview — the exact lines to land

"volatile only guarantees visibility — every read sees the latest write — it does not make a compound operation like count++ atomic, since that's a separate read-then-write. synchronized adds mutual exclusion so the whole sequence is one atomic step, and Atomic classes give that same atomicity lock-free via CAS."

  • volatile → visibility only, never atomicity for compound ops.
  • count++ on a volatile int → still two separate steps — not thread-safe.
  • synchronized → visibility + atomicity, real locking cost.
  • AtomicInteger/AtomicLong → lock-free atomicity via CAS, often faster for simple counters.
  • Need a whole multi-step section atomic → synchronized/Lock, not a single Atomic class.
📖 Explanation ▾

volatile solves exactly one problem: making sure a read of a field always sees the most recent write to it, from any thread, and preventing the compiler/CPU from reordering certain operations around it. That's a real, useful guarantee — but it's a guarantee about individual reads and writes, not about a sequence of them. count++ is actually three steps under the hood (read the current value, add one, write the new value back) — volatile makes each of those three visible correctly, but says nothing about whether another thread can act in between them.

synchronized closes that gap by adding mutual exclusion: while one thread is inside the guarded block, no other thread can enter it, so the whole read-modify-write sequence happens as a single atomic step from every other thread's point of view — at the cost of actually acquiring a lock. Atomic classes get the same end result — the whole compound operation behaves as one indivisible step — without a lock at all: internally, incrementAndGet() reads the current value, computes the new one, and uses a CAS (compare-and-swap) instruction to write it back only if nothing else changed it first, retrying automatically if it did.

💻 See the code ▾
Java 
private volatile int count = 0;

void increment() {
    count++;   // ❌ read-then-write — NOT atomic, even though volatile
}

Two threads can both read the same value before either writes back — one increment is silently lost.

Java 
private int count = 0;

synchronized void increment() {
    count++;   // ✅ whole read-modify-write runs as one atomic step
}

Only one thread executes this block at a time, so the read and the write can never be split by another thread.

Java 
private final AtomicInteger count = new AtomicInteger(0);

void increment() {
    count.incrementAndGet(); // ✅ atomic, lock-free (CAS)
}

incrementAndGet() is one atomic operation — no lock, and no two threads can ever interleave inside it.

🧭 Use Cases — recognize these when they happen to you ▾
1 A shared volatile counter is incremented directly (count++) from multiple threads

Under real concurrent load, this silently undercounts — some increments get lost to the exact interleaving the main diagram shows. A common interview trap: assuming volatile alone was enough because the field "looked" synchronized.

Remembervolatile + compound op → lost updates under load.
2 A simple shutdown flag, read by a worker but never incremented

A plain write followed by a plain read — no read-modify-write involved — is exactly what volatile is for: it's correct and sufficient on its own here, no locking needed.

RememberSingle write, single read → volatile alone is correct.
3 A transfer must debit one balance and credit another, together

A single AtomicLong can only make one field's operation atomic — debiting one balance and crediting another needs both changes to happen as one step together, which only synchronized or a Lock around both can guarantee.

RememberTwo fields, one step → lock the whole section, not one Atomic field.
🌍 Real-world example ▾

Under load, a request counter implemented as private volatile long requests; requests++; undercounts significantly compared to real traffic. Switching to AtomicLong (or guarding the increment with synchronized) fixes it — the lost updates were coming from the increment being two unsynchronized steps, not from volatile failing to do its visibility job.
