"It looks good" isn't evaluation — how do you prove a prompt change didn't break anything?

How would you evaluate an LLM feature before shipping a prompt change?

Why it matters ▾
🧪 Eval Set & Regression Testing
❗ ProblemA prompt or model change that fixes one complaint can quietly make other cases worse, and with no fixed set of cases run before and after the change, nobody notices until a user hits the regression in production.
✅ SolutionBuild an eval set — common, edge, and known-hard cases, including past regressions, each with a known answer or rubric — and run every candidate change against it, comparing the new scores to the previous version's baseline before shipping.
RecallEval set = automated regression tests for prompts — run every change against the same fixed cases, compare to baseline, block on any regression.
🔥 Easy interview recall

Eval set → a fixed, representative set of real cases, not a vibe check

Regression testing → run every change against it, compare to baseline, before shipping

Think: an eval set is automated regression tests — for prompts, instead of code.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Treating "I tried a few examples and it looked good" as evaluation. A handful of cases you happened to try isn't a representative eval set, and it won't catch a regression in the one case you didn't think to check.

🔄 Likely Follow-up

"What's the difference between offline and online evaluation?" Offline evaluation runs the fixed eval set before shipping; online evaluation monitors real production traffic and feedback signals after shipping — the eval set alone can't catch everything a live user population actually does.

🎯 Say this in the interview — the exact lines to land

"I'd build a representative eval set — common cases, edge cases, and past regressions — each with a known correct answer or a clear rubric, run any prompt or model change against it before shipping, and compare the new scores to the previous version's baseline to catch a regression before a user does."

  • Eval set → sampled from real, representative usage, not just cases the developer happened to think of.
  • Regression cases → past problems get added to the set, so future changes are checked against them automatically.
  • Faithfulness / groundedness → does the answer stay consistent with the retrieved context, with no unsupported claims added.
  • Context precision → of the chunks retrieved, how many were actually relevant Context recall → of the relevant chunks that exist, how many retrieval actually found
  • Offline vs. online → the eval set catches regressions before shipping; production monitoring catches what real users do that the eval set never anticipated.
📖 Explanation ▾

An eval set is a curated collection of realistic input cases — the common ones, the edge cases, and the ones already known to be hard — each paired with either a known correct answer or a clear rubric for judging the response. It's built by sampling real, representative usage, not just cases a developer happened to think of, and it deliberately includes past problem cases (regression cases) so a future change gets checked against them automatically, instead of relying on someone remembering to re-test by hand.

For a RAG feature specifically, a good eval set scores more than "did it answer." Faithfulness (or groundedness) checks whether the generated answer actually stays consistent with what the retrieved context said, without adding claims the context doesn't support. Answer relevancy checks whether the answer actually addresses the question that was asked. Context precision and context recall score retrieval itself — precision is how many of the retrieved chunks were actually relevant, recall is how many of the truly relevant chunks that exist were actually found.

Before shipping any prompt or model change, run it against the eval set and compare the new scores to the previous version's — that's what catches a change that fixes the one case it was targeting while silently making another case worse. This offline check still isn't the whole picture: online evaluation — monitoring real production traffic and feedback signals after shipping — is what catches what a live user population actually does that the eval set never anticipated.

💻 See the code ▾
Eval case 
{
  "id": "case_014",
  "category": "regression",  // common | edge | known-hard | regression
  "input": "What's the refund window for a damaged item?",
  "expected": "Rubric: cites the 30-day damaged-item policy, no invented dates"
}

Each case is a realistic input plus either the exact right answer or a rubric — this is what makes "looks good" testable instead of a feeling.

Regression gate 
new_score = run_eval(new_version, eval_set)
baseline_score = run_eval(previous_version, eval_set)

for case in eval_set:
    if new_score[case] < baseline_score[case]:
        block_release(case)   # regressed — was passing, now isn't

This is the actual gate: not "did the new version score well overall," but "did any individual case get worse compared to before."

🧭 Use Cases — recognize these when they happen to you ▾
1 You're about to ship a prompt or model change that fixes a real complaint

This is the #1 scenario you'll actually run into — the exact regression-gate flow in the diagram above. Run the candidate change against the eval set, including its regression cases, and compare the new scores to the previous version's baseline before shipping.

RememberOffline evaluation = the eval set run before shipping, comparing new scores to baseline.
2 The change already shipped, and you want to know what real users are hitting

The eval set only tests the cases someone already thought to include. Online evaluation — monitoring real production traffic and feedback signals after shipping — is what catches what a live user population actually does that the eval set never anticipated.

RememberOnline evaluation = production monitoring after shipping; the eval set alone can't catch everything.
3 You tried a handful of examples by hand, they looked fine, and you called it "evaluated"

A few cases you happened to try isn't a representative eval set — it won't catch a regression in the one case you didn't think to check, which is exactly what lets a change pass a casual look while quietly breaking something else.

Remember"I tried a few examples" is not evaluation — only a fixed, representative eval set with regression cases counts.
🌍 Real-world example ▾

Your team wants to change the system prompt to fix a customer complaint about a curt tone. Before shipping, how do you know it doesn't break the three refund-policy cases that used to pass? Run the new prompt against the eval set — including those three regression cases — and compare the new scores against baseline. If any of them drop below their previous score, block the release even though the tone complaint case now passes.
