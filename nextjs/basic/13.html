Server Components vs. Client Components — who ships JavaScript, and who doesn't?

"What's the default component type in the App Router, and when do you actually need a Client Component?"

Why it matters ▾
🧩 Server vs. Client Components
❗ ProblemSending every component's JavaScript to the browser — even the parts that never change after the page loads — means more bytes to download and more work before anything is interactive.
✅ SolutionEvery component is a Server Component by default — zero client JS, direct backend access. Only the components that genuinely need interactivity opt in with 'use client'.
RecallDefault = server, zero JS. Opt in only where you need interactivity.
🔥 Easy interview recall

Server Component → default, zero client JS

Client Component → opt-in, still renders on the server once

Think: 'use client' doesn't mean browser-only — it means "allowed to hydrate and use state."

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Marking a component 'use client' "just to be safe." That opts it — and everything it imports — out of the Server Component benefits (zero client JS, direct backend access) for no reason if it never actually needs interactivity.

🔄 Likely Follow-up

"Can a Server Component render a Client Component, and vice versa?" A Server Component can import and render a Client Component (common — a small interactive island inside a static page). A Client Component cannot import a Server Component directly — it can only receive one passed in as a prop/children from a Server Component ancestor.

🎯 Say this in the interview — the exact lines to land

"In the App Router, every component is a Server Component by default — it renders on the server only, can access the database or filesystem directly, and ships zero of its own JavaScript. A Client Component, marked 'use client', is needed for interactivity or React state/effects — it still renders once on the server for the initial HTML, then hydrates."

  • Default → Server Component, zero client JS, direct backend access.
  • 'use client' → needed for state, effects, browser APIs, not "browser-only."
  • Client Component → still server-rendered once, then hydrates.
📖 Explanation ▾

In the App Router, every component is a Server Component unless you say otherwise. It renders entirely on the server — it can read a database, touch the filesystem, use secrets directly — and the browser never receives its JavaScript, only the HTML it produced.

A Client Component — any file (or anything it imports) under a 'use client' boundary — is what you reach for when a piece of UI genuinely needs useState, useEffect, an event handler, or a browser-only API. It still does an initial server render for its HTML, exactly like a Server Component does — the difference is it then also ships its JavaScript and hydrates in the browser, so it can keep responding to interaction afterward.

The practical effect: a page can be almost entirely zero-JS Server Components, with small interactive "islands" of Client Components dropped in only where something genuinely needs to react to the user.

Server ComponentClient Component
Default?✅ yes❌ opt-in only
Ships its own JS?❌ never✅ yes
Can use state/effects?❌ no✅ yes
Direct DB/filesystem access?✅ yes❌ no
Renders on the server at all?✅ yes, only✅ yes, once — then hydrates
💻 See the code ▾
JSX 
// ProductList.jsx — no directive, Server Component by default
export default async function ProductList() {
  const products = await db.product.findMany();  // ✅ direct DB access
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

No 'use client' at the top → this ships zero JavaScript to the browser.

JSX 
'use client';  // LikeButton.jsx — the small interactive island

export default function LikeButton() {
  const [liked, setLiked] = useState(false);  // ✅ state needs the client
  return <button onClick={() => setLiked(!liked)}>{liked ? '❤️' : '🤍'}</button>;
}

This is the one component on the page that actually needed interactivity — and the only one that ships JS.

🧭 Use Cases — recognize these when they happen to you ▾
1 A page is mostly static content pulled straight from a database

A product listing or blog post body doesn't need to react to anything in the browser — leave it as a Server Component and it never costs a single byte of JS. This is the #1 scenario you'll actually run into.

RememberNo interactivity needed → leave it as a Server Component.
2 One small widget needs a click handler or local state

Carve out just that one widget as a Client Component and keep everything around it — the page shell, the rest of the content — as Server Components. Small, deliberate islands beat marking the whole page client-side.

RememberInteractive widget → its own small Client Component, not the whole page.
3 A Client Component tries to import a Server Component directly

A Client Component can only receive a Server Component as something already-rendered, passed in as children/a prop from a Server Component ancestor — it can never import one directly and render it itself.

RememberClient → Server import direction doesn't exist; only pass Server Components in as children.
🌍 Real-world example ▾

A news article page is mostly a printed page — except the "like" button. The headline, body, and images don't need to do anything once they're on screen (Server Components, zero JS). The one interactive control — the heart you can tap — is the single Client Component island that actually needs to run in the browser.
