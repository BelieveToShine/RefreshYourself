OnDelete — delete the parent, and what happens to the children?

"What happens to child rows when you delete the parent?"

Why it matters ▾
🗑️ Delete behaviour
❗ ProblemDelete a parent row that other rows point to and those child rows are left orphaned — or the database refuses the delete with a foreign-key error.
✅ SolutionEvery relationship has a delete behaviour, set with OnDelete, that says whether the children are deleted, get their key set to null, or block the delete.
RecallRequired FK → Cascade by default. Optional FK → ClientSetNull.
🔥 Easy interview recall

Required FK → Cascade — children deleted too

Optional FK → ClientSetNull — FK nulled, no database cascade

Restrict → blocked while children exist

Think: Delete parent → children are deleted, nulled, or blocking.The OnDelete setting picks which.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Deleting a parent always deletes its children" is only the default for a required relationship. An optional one (nullable FK) defaults to ClientSetNull: EF Core nulls the key on children it has loaded, but the database does not cascade — so a child it never loaded can make the delete fail.

🔄 Likely Follow-up

"How do you stop a parent being deleted while it still has children?" Configure OnDelete(DeleteBehavior.Restrict) — the database then rejects the delete (SaveChanges() throws) while any child row exists.

🎯 Say this in the interview — the exact lines to land

"By convention a required relationship cascades — deleting the parent deletes its children — while an optional one defaults to ClientSetNull, which nulls the foreign key on tracked children. I can override either with OnDelete: Cascade, SetNull, Restrict or NoAction."

  • Required FK → Cascade by default, children deleted with the parent.
  • Optional FK → ClientSetNull, only tracked children get a null key.
  • SetNull → the database nulls the key, so the FK must be nullable.
  • Restrict → delete is blocked while children exist — the safe choice for important data.
📖 Explanation ▾

When you delete a parent row, every child row that points at it through a foreign key needs a plan. The delete behaviour is that plan: delete the children, null their key, or refuse the delete. You set it per relationship with OnDelete(...).

The default depends on whether the foreign key is required. A required relationship (non-nullable FK) defaults to Cascade. An optional one (nullable FK) defaults to ClientSetNull: EF Core sets the key to null on children it is tracking, but the database foreign key does not cascade, so a child EF Core never loaded can still make the database reject the delete.

SetNull hands that job to the database, and needs a nullable FK. Restrict and NoAction leave the children alone and let the database reject the delete while any exist — the safe choice when deleting a parent should be deliberate. 💻 See the code ▾
C# 
modelBuilder.Entity<Order>()
    .HasMany(o => o.Lines)
    .WithOne(l => l.Order)
    .HasForeignKey(l => l.OrderId)
    .OnDelete(DeleteBehavior.Restrict);   // ✅ blocks deleting an Order that has lines

OnDelete is configured on the relationship — pick the behaviour you want, don't rely on the default by accident.

C# 
var order = await db.Orders.FindAsync(id);
db.Orders.Remove(order);
await db.SaveChangesAsync();   // required FK + default Cascade: its OrderLines are deleted too

With the default on a required relationship, one Remove takes the children with it.

🌍 Real-world example ▾

Deleting a customer who has orders. With cascade, one click silently wipes their whole order history. Teams usually set Restrict on that relationship (delete refused) and keep Cascade only for true parts-of-a-whole, like an order and its lines.
