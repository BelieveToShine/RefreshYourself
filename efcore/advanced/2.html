Include() two collections, and rows multiply — not add

What is query splitting, and what problem does it solve?

Why it matters ▾
🔗 Default (JOIN)
❗ ProblemInclude()ing two or more collection navigations onto the same parent forces the database to join both into one query — every row in the first collection pairs with every row in the second, so 5 related rows and 4 related rows come back as 20 duplicated parent rows, not 9.
✅ SolutionFor a single collection Include(), or only reference Include()s, this default one-query JOIN is exactly right — one round trip, one atomic snapshot, and nothing to multiply against.
RecallDefault (JOIN) = one query, correct for one collection, multiplies rows once a second collection joins in.
🧩 AsSplitQuery()
❗ ProblemOnce a second collection Include() joins in, the single JOINed query's cartesian product (20 rows instead of 9) is silently wrong and only gets worse as either collection grows.
✅ SolutionIt issues one separate query per collection Include() (2, here) instead of one join, so each collection comes back correctly shaped — 5 rows plus 4 rows — at the cost of an extra round trip per split collection and no longer reading from one atomic snapshot.
RecallAsSplitQuery() = one query per collection, correct row counts, more round trips, no atomic snapshot.
🔥 Easy interview recall

Two collection Include()s, no split → one JOIN, rows multiply

AsSplitQuery() → one query per collection, rows stay correct

Think: 5 related rows × 4 related rows = 20 duplicated parent rows, not 5 + 4 = 9.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

AsSplitQuery() is not a "turn it on everywhere" setting. It only fixes the cartesian blowup from multiple collection Include()s on the same query — a query with just one collection Include() has no cartesian product to begin with, so splitting it changes nothing.

🔄 Likely Follow-up

"You Include() two collection navigations on the same query without AsSplitQuery() — one has 5 related rows, the other has 4. How many total rows come back from that single JOINed query?" 5 × 4 = 20 duplicated parent rows — the cartesian product of the two collections, not 5 + 4 = 9.

🎯 Say this in the interview — the exact lines to land

"Include()ing two or more collection navigations on the same query produces one SQL statement with multiple JOINs, and joining two one-to-many collections onto the same parent multiplies the rows — 5 related rows in one collection and 4 in another comes back as 20 duplicated parent rows, not 9. AsSplitQuery() fixes it by issuing one separate, correctly-shaped query per collection instead."

  • Two+ collection Include()s, no split → rows multiply: 5 × 4 = 20, not 9.
  • AsSplitQuery() → one query per collection, correctly shaped, no duplicates.
  • Only one collection Include() → no cartesian problem exists, splitting gains nothing.
  • Trade-off → more round trips, no single atomic snapshot across the separate queries.
📖 Explanation ▾

A single collection Include() generates one clean JOIN — each related row is just an extra row, no duplication. The moment a second collection joins onto the same parent, the database can't keep the two collections independent: every row from the first collection gets paired with every row from the second, so the parent row itself is duplicated once per pairing. That's a cartesian product, not a sum — 5 rows and 4 rows don't add to 9, they multiply to 20.

AsSplitQuery() sidesteps this by not joining the collections at all. EF Core issues one query for the parent plus the first collection, then a separate query for the parent plus the second collection, and stitches the results back together in memory — each query is correctly shaped on its own, so nothing multiplies. The cost is an extra round trip per split collection.

The two approaches aren't interchangeable, though: a single JOINed query reads every row from one atomic snapshot of the database. Split queries are separate round trips, so if a concurrent write changes the underlying rows between them, the combined result could theoretically mix data from two slightly different moments — rare under normal load, but a real trade-off the single-query approach doesn't have.

💻 See the code ▾
C# 
Order order = context.Orders
    .Include(o => o.Items)   // collection — 5 rows
    .Include(o => o.Notes)   // collection — 4 rows
    .First(o => o.Id == 42);
// ❌ one query, one JOIN — returns 5 × 4 = 20 duplicated rows

Both Include()s are collections, joined onto the same parent — the database has no way to keep them independent.

C# 
Order order = context.Orders
    .Include(o => o.Items)
    .Include(o => o.Notes)
    .AsSplitQuery()          // ✅ one query per collection
    .First(o => o.Id == 42);

EF Core now issues 2 separate queries — Items loads its own 5 rows, Notes loads its own 4 — nothing multiplies.

C# 
Order order = context.Orders
    .Include(o => o.Items)   // only one collection — nothing to multiply against
    .First(o => o.Id == 42);
// AsSplitQuery() here would just add a round trip for nothing

One collection Include() has no cartesian product to begin with — AsSplitQuery() only matters once a second collection Include() joins in.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your query only Include()s one collection navigation

One collection has nothing to join against — the default single JOIN query is already correctly shaped, so there's no cartesian product and no reason to reach for AsSplitQuery() here.

RememberOne collection Include() → default JOIN is already correct.
2 You Include() two or more collections without AsSplitQuery()

Every row in the first collection pairs with every row in the second inside one JOINed query, so the parent row duplicates once per pairing — 5 related rows and 4 related rows come back as 20 duplicated rows, not 9. The query still compiles and runs with no error, which is exactly why candidates who assume a second Include() just adds a second set of rows get caught out by this.

Remember2+ collection Include()s, no split → rows multiply (5 × 4 = 20, not 9).
3 You Include() two or more collections and add AsSplitQuery()

EF Core issues one separate query per collection Include() (2, here) instead of one join, so each collection comes back correctly shaped — 5 rows plus 4 rows, no duplicates — at the cost of an extra round trip and no longer reading from one atomic snapshot.

RememberAsSplitQuery() → correct row counts, more round trips, no atomic snapshot.
🌍 Real-world example ▾

A reporting page pulls one order with its line items and its audit notes, and Include()s both. It works fine in dev with a handful of rows each, then a support ticket comes in about a large order — hundreds of line items, dozens of notes — and the same query now returns tens of thousands of rows and the page times out. That's the cartesian product hiding inside a perfectly normal-looking two-Include() query — the fix is AsSplitQuery(), so each collection loads through its own correctly-shaped query instead of one exploding JOIN.
