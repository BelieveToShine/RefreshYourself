Checked vs. Unchecked Exceptions — compiler-enforced, or not

"What's the real difference between checked and unchecked exceptions, and when should you use each?"

Why it matters ▾
✅ Checked
❗ ProblemSome failures — a missing file, a network call failing — are completely expected in normal operation. If nothing forces a caller to even acknowledge the possibility, it's easy to ship code that silently ignores a failure it could have actually recovered from.
✅ SolutionChecked exceptions (Exception minus RuntimeException) force the compiler to make the caller either catch them or declare them in throws — the possibility of failure becomes part of the method's visible contract.
Recallchecked = compiler makes you deal with it.
⚡ Unchecked
❗ ProblemRequiring every caller to catch or declare every possible programming bug — a null reference, an invalid argument — at every call site would bury real logic errors under boilerplate try/catch blocks nobody can meaningfully recover from anyway.
✅ SolutionUnchecked exceptions (RuntimeException and Error) need no declaration at all — they signal a bug the caller shouldn't be forced to handle at every call site, just fixed in the code that caused it.
Recallunchecked = compiler doesn't ask, it's usually a bug.
🔥 Easy interview recall

Checked → caught or declared, compiler-enforced

Unchecked → no declaration needed, usually a bug

Think: Checked = a recoverable condition. Unchecked = a programming mistake.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Unchecked doesn't mean "don't catch it." It only means the compiler won't force you to — a well-designed program still catches specific runtime exceptions it can actually do something about; it just isn't required to.

🔄 Likely Follow-up

"Why does Java even have checked exceptions when C#, Kotlin, and Python don't?" It's a deliberate design choice to force recoverable failures into a method's visible contract — modern guidance leans more unchecked because checked exceptions can pollute signatures and get swallowed by lazy catch blocks, but that compiler-enforced visibility is unique to Java's checked exceptions.

🎯 Say this in the interview — the exact lines to land

"Checked exceptions — Exception minus RuntimeException — must be caught or declared in throws; it's compiler-enforced. Unchecked exceptions — RuntimeException and Error — need no declaration and are typically programming bugs, not recoverable conditions."

  • Checked → compiler-enforced, must catch or declare.
  • Unchecked → no declaration needed, usually a bug.
  • Use checked for conditions a caller can recover from.
  • Use unchecked for programming errors the caller shouldn't be forced to handle everywhere.
📖 Explanation ▾

Every exception in Java is a subclass of Throwable, which splits into two branches: Error and Exception. Error covers serious, usually unrecoverable JVM-level failures (OutOfMemoryError, StackOverflowError) — unchecked, because a caller generally can't do anything meaningful about them anyway. Exception splits again: RuntimeException and everything beneath it is unchecked; everything else under Exception is checked.

"Checked" is purely a compiler behavior, not a severity label — the compiler refuses to compile a method that might throw a checked exception unless that method either catches it or lists it in its own throws clause, forcing the possibility of failure to be visible at every level of the call chain.

The real-world guidance most teams converge on: reach for a checked exception when a well-written caller can reasonably be expected to recover (retry a failed network call, prompt for a different file path); reach for an unchecked exception when the failure is a programming bug (a null argument, an invalid index) that the caller should fix in the code, not handle at runtime.

💻 See the code ▾
Java 
void readConfig(String path) throws IOException {  // ✅ declared
    Files.readAllLines(Path.of(path));
}

IOException is checked — the compiler won't compile this without declaring or catching it.

Java 
void setAge(int age) {   // no throws needed
    if (age < 0) throw new IllegalArgumentException("age");  // ✅ compiles fine
}

IllegalArgumentException is unchecked — no declaration required at all.

Java 
class InsufficientFundsException extends Exception {  // custom checked
    InsufficientFundsException(String msg) { super(msg); }
}

Extending Exception (not RuntimeException) makes it checked — callers must handle it.

🧭 Use Cases — recognize these when they happen to you ▾
1 Reading a file or calling an external API that can genuinely fail

This is the #1 scenario you'll actually run into. A missing file or a dropped connection is an expected possibility, not a bug — checked forces every caller up the chain to actually decide how to handle it.

RememberA real, recoverable failure mode → checked.
2 Validating a method argument before using it

A negative age is a caller bug, not an expected runtime condition. Forcing every caller of setAge() to declare or catch this would just add boilerplate around something that should simply get fixed in the calling code.

RememberA bug in the calling code → unchecked.
3 You catch Exception broadly just to avoid declaring several checked types

Catching the broad Exception type to dodge declaring several checked exceptions also silently swallows unrelated unchecked bugs the same block never meant to catch — catch the specific checked types instead.

RememberCatching broadly to avoid declaring → hides real bugs, not just the expected one.
🌍 Real-world example ▾

A checked-exception-throwing call sits deep inside a stream's lambda, and the code won't compile because a functional interface like Function can't declare a checked exception. The common fix is wrapping the checked exception in an unchecked one (a custom RuntimeException subclass) right at that point — a well-known, real friction point between Java's checked exceptions and its functional-interface design.
