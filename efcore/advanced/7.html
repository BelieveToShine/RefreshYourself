EnableRetryOnFailure — retry the whole unit, not one command

"How do you handle transient database failures in EF Core?"

Why it matters ▾
🔁 Connection Resiliency
❗ ProblemCloud databases sometimes drop a connection or time out for a moment. Without retries, a failure that would have cleared in a second becomes a failed request.
✅ SolutionTurn on EnableRetryOnFailure() so transient errors are retried automatically — and wrap your own transactions in an execution strategy so the whole unit can be repeated.
RecallRetry transient errors → EnableRetryOnFailure(); own transaction → strategy.ExecuteAsync; the unit may run twice.
🔥 Easy interview recall

Resiliency = "retry the whole unit when the failure is transient."

Think: EnableRetryOnFailure() → turns retries on Your own transaction → wrap it in CreateExecutionStrategy().ExecuteAsync Retried unit → may run twice, so keep it safe to repeat

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"I turned on EnableRetryOnFailure() and my manual BeginTransaction code still works." It throws an InvalidOperationException — the strategy cannot replay a transaction it does not control. Wrap the whole unit in strategy.ExecuteAsync.

🔄 Likely Follow-up

"What if the commit actually succeeded, but the connection dropped before you heard back?" The strategy may run the unit again, so it has to be safe to repeat — make it idempotent, or check whether the first attempt already worked before doing it again.

🎯 Say this in the interview — the exact lines to land

"I enable EnableRetryOnFailure on the database provider, so transient errors like a brief connection drop are retried with a delay. A plain SaveChanges is retried automatically. If I need my own transaction, I wrap the whole unit in an execution strategy's ExecuteAsync and make sure running it twice is safe."

  • EnableRetryOnFailure() → retries transient errors only — not every error.
  • Plain SaveChanges() → retried automatically as one unit.
  • Own transaction → wrap it in strategy.ExecuteAsync.
  • The unit may run twice → keep it idempotent; no emails or outside calls inside.
📖 Explanation ▾

A transient failure is one that is likely to go away if you simply try again — a dropped connection, a short timeout, a brief failover. EnableRetryOnFailure() installs a retrying execution strategy for your provider: when a command fails with a known transient error, it waits and tries again, waiting longer each time, up to limits you can configure. Each provider decides which errors count as transient.

A retry has to replay everything that belongs together. A plain SaveChanges() already runs as one unit, so it retries safely on its own. But if you start a transaction yourself, the strategy cannot know which statements to repeat, so BeginTransaction throws once retries are on. The fix is to hand the whole unit — begin, work, commit — to CreateExecutionStrategy().ExecuteAsync(...), and rebuild any state inside it, because it may be run more than once.

That last point is the real risk: if a commit succeeded but the confirmation was lost, the unit can run again. Keep what is inside idempotent — safe to repeat — and keep side effects such as sending an email outside it.

💻 See the code ▾
C# 
services.AddDbContext<AppDb>(o => o.UseSqlServer(connectionString,
    sql => sql.EnableRetryOnFailure()));      // ✅ transient errors are retried

One line on the provider options turns retries on.

C# 
await using var tx = await db.Database.BeginTransactionAsync();
// ❌ throws InvalidOperationException once retry-on-failure is enabled

A transaction you start yourself sits outside the strategy, so EF Core refuses it.

C# 
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync();   // ✅ inside the retry unit
    db.Orders.Add(order);
    await db.SaveChangesAsync();
    await tx.CommitAsync();                                           // may run again — keep it repeat-safe
});

The strategy owns the whole begin-to-commit block, so a retry repeats all of it.

🌍 Real-world example ▾

An API on a cloud database sees occasional one-second connection drops during maintenance or throttling. With retries enabled, most requests quietly succeed on the second attempt; a transfer that uses its own transaction goes through ExecuteAsync and checks it cannot be applied twice.
