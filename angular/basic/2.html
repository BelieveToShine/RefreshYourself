🔥 Must Know

@Component — the piece everything else in Angular attaches to

"What is an Angular component, and what does @Component actually do?"

Why it matters ▾
  • Every Angular app is just a tree of components — if you can't explain what one is, you can't explain anything built on top of it.
  • Interviewers use it to check you know a decorator is metadata, not logic — an easy early trip-up.
  • "Component vs. service — what belongs where?" is a favorite follow-up that separates people who've shipped real apps from people who've only read the docs.
🔥 Easy interview recall

Component = "a class + a template, wired together by @Component."

Think: @Input → value flows down. @Output → event flows up.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

@Input/@Output are not automatically two-way. Each one only moves in a single direction — @Input parent→child, @Output child→parent — genuine two-way binding ([(ngModel)], or a signal-based model() today) is a separate feature built on top of these two one-way primitives, not a third, unrelated one.

🔄 Likely Follow-up

"Can a component talk to a sibling component directly?" Not directly — Angular has no built-in sibling-to-sibling channel. The standard pattern is bubbling the event up to a shared parent via @Output, then having the parent pass data back down to the other sibling via @Input (or lifting the shared state into a service both siblings inject).

🎯 Say this in the interview — the exact lines to land

"A component pairs a class with a template, and @Component is the decorator that turns that plain class into something Angular can render — it declares the selector, the template, and the styles as metadata, not logic."

  • @Component is declarative metadata — selector, template, styles — read by the compiler, not executable logic.
  • @Input() → a value flows parent to child through property binding.
  • @Output() + EventEmitter → the child emits an event, the parent listens through event binding.
  • A reusable component takes configuration in via @Input, sends events out via @Output — it never reaches outside itself for data it should have been given.
  • Component owns UI state and interaction; a service owns logic/data that isn't tied to one screen — a component making its own HTTP calls is a common code smell.
📖 Explanation ▾

@Component is a decorator — it attaches metadata to a plain TypeScript class so Angular's compiler recognizes it and knows how to instantiate and render it. The decorator itself carries no logic; it's configuration the framework reads. At minimum that metadata is a selector (the custom tag it matches, e.g. app-user-card) and a view, given as an inline template string or an external templateUrl — purely an organizational choice, most real components use a separate file for readability and tooling. Modern standalone components also declare standalone: true and an imports array listing whatever the template needs.

@Input() and @Output() are the two channels a component exposes to the outside. A parent binds a value onto the child with property binding ([value]="x") and the child receives it as a decorated property. Going the other way, the child declares an @Output() backed by an EventEmitter, calls .emit(payload) when something happens, and the parent listens with event binding ((someEvent)="handle($event)"). EventEmitter is how a child shouts upward without knowing who, if anyone, is listening.

Bigger UI is built by nesting smaller components inside each other's templates — the same idea as function composition, applied to a screen. A component stays reusable as long as it makes no hard-coded assumptions about its parent: configuration comes in through @Input, events go out through @Output, and it never reaches outside itself for data it should have been given instead.

💻 See the code ▾
TypeScript 
export class ItemComponent {
  @Input() label!: string;                          // value comes in from the parent
  @Output() selected = new EventEmitter<string>();  // event goes out to the parent

  onClick() {
    this.selected.emit(this.label);                 // ✅ shouts upward, doesn't know who's listening
  }
}

The child only ever declares its own inputs and outputs — it never reaches out to find its parent.

HTML 
<app-item
  [label]="name"
  (selected)="onSelect($event)">
</app-item>

[label] sends a value down; (selected) listens for the event coming back up.

🌍 Real-world example ▾

A component is like a custom-built widget on a control panel. You feed it a setting from outside — an @Input, like someone else setting a dial position — and it reports back when something happens — an @Output, like a light that turns on when the widget is pressed. The widget itself doesn't know or care who's watching.
