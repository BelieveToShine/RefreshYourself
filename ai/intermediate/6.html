Tool calling — the model asks, but who actually pulls the trigger?

"How does function/tool calling actually work? How do you guard a tool that has a real side effect?"

Why it matters ▾
  • Tests the single most common misconception about tools/agents — that the model itself runs the function. It never does.
  • Comes up any time you're asked to design a chatbot, agent, or MCP-style integration that needs to act on real systems.
  • The guard question — "what if the model calls a real tool with the wrong arguments?" — is a very common production-risk follow-up.
🔥 Easy interview recall

Tool calling = "the model asks, your code does."

Think: model → returns a request (tool name + arguments) your code → actually runs it model → gets the result back, then answers or calls another tool

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The model does not call the function. It only returns a structured request naming the tool and arguments — your own code is what decides whether, and how, to actually run it.

🔄 Likely Follow-up

"How do you guard a tool that sends an email or deletes data?" Add an explicit guard before it executes — require human confirmation, restrict what the tool is allowed to do, or validate the model's proposed arguments — never run a side-effecting call on blind trust.

🎯 Say this in the interview — the exact lines to land

"Tool calling is a loop: you describe the available tools to the model with a schema, the model returns a structured request naming the tool and its arguments — it never executes anything itself — your own code runs the real function and feeds the result back, and the model continues from there, repeating for multi-step tasks."

  • Model requests, your code executes — never the other way around.
  • Give every tool a clear schema → name, description, parameter types so the model picks the right tool and fills its arguments correctly.
  • Design for idempotency where possible, and feed tool errors back to the model so it can react — for example, retry differently.
  • Side-effecting tool (email, payment, delete) → always add a guard — human confirmation, a restricted scope, or argument validation before it executes.
  • Never execute blindly → the model can propose an incorrect, or even adversarially manipulated, call — that's a real production risk, not a hypothetical.
📖 Explanation ▾

Tool calling works as a loop, and the model never crosses the execution boundary at any point in it. You describe the available tools to the model up front — a name, a description, and a schema for the parameters. Given a user request, the model decides a tool is needed and returns a structured request naming which tool to call and with what arguments; it does not call it itself. Your own code receives that request and actually executes the real function or API call, then feeds the tool's result back to the model as another message. The model uses that result to continue — answering the user, or requesting another tool — and this request → execute → feed-back cycle can repeat several times for a genuinely multi-step task.

Good tool design starts with the schema: a clear, unambiguous name, description, and parameter types are what let the model pick the right tool and fill in its arguments correctly — a vague schema produces vague, wrong calls. Where possible, design a tool to be idempotent, so calling it twice with the same arguments is safe. Handle errors from the tool gracefully and feed them back to the model rather than failing silently, so it can react — for example, retrying with different arguments.

Any tool with a real side effect — sending an email, making a payment, deleting data — needs an explicit guard before it runs. The model can propose an incorrect call, or even an adversarially-manipulated one, so blindly executing whatever it returns is a real production risk, not an edge case. Requiring human confirmation, restricting what the tool is allowed to do, or validating the model's proposed arguments before the real call runs are all ways to close that gap.

💻 See the code ▾
JSON 
{
  // this is ALL the model ever sees — never your real implementation
  "name": "send_email",
  "description": "Sends an email to one recipient.",
  "parameters": {
    "to": "string (email address)",
    "subject": "string",
    "body": "string"
  }
}

A clear schema is what lets the model pick the right tool and fill in valid arguments.

Python 
# 1) model returns a REQUEST — it does not run anything
response = model.chat(messages, tools=[send_email_schema])
tool_call = response.tool_calls[0]   # name + arguments only

# 2) YOUR code decides whether to actually run it
if is_side_effecting(tool_call):
    if not user_confirms(tool_call):      # ✅ the guard
        result = "cancelled by user"
    else:
        result = run_tool(tool_call)     # the real side effect
else:
    result = run_tool(tool_call)

# 3) feed the result back so the model can continue
messages.append(tool_result_message(tool_call, result))
next_response = model.chat(messages, tools=[send_email_schema])

The guard sits entirely in your own code — the model only ever sees the schema and whatever result you choose to send back.

🌍 Real-world example ▾

An agent has a refund_payment tool wired to a real payment API. Never let the model's proposed amount and account execute directly — validate them against the actual order record on the server, and require an explicit confirmation step for any refund over a small threshold, before the real call runs.
