🔥 JavaScript · Advanced · Must Know

Same goal, opposite clocks — debounce waits for silence, throttle never stops ticking

"Can you implement debounce and throttle from scratch, and explain when you'd reach for each one?"

Why it matters ▾
  • One of the most common live-coding exercises in a front-end interview — you're expected to write working code on the spot, not just describe the idea.
  • Both show up constantly in production: a search-as-you-type box, a resize handler, an infinite-scroll listener, a "save" button someone can double-click by accident.
  • Mixing them up is a real bug, not just a vocabulary slip — using throttle where you needed debounce fires a search request on every keystroke instead of waiting for the user to stop typing.
🔥 Easy interview recall

Debounce = "wait for quiet." Throttle = "at most once per tick."

Think: debounce keeps pushing a deadline back until you stop calling it; throttle never moves its clock — it just ignores calls that land between ticks.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Throttle is not "debounce but faster." Throttle still fires repeatedly, at a fixed pace, WHILE calls keep coming — it never waits for silence the way debounce does.

🔄 Likely Follow-up

"What's the difference between leading and trailing execution?" Leading fires immediately on the first call, then ignores the rest until the window ends; trailing waits and fires at the end of the window instead. Most simple implementations are trailing-only — supporting both in one function takes extra bookkeeping.

🎯 Say this in the interview — the exact lines to land

"Debounce delays execution until the calls stop — every new call cancels the pending timer and starts a fresh one. Throttle executes at a fixed rate no matter how many calls come in, ignoring extra calls until the interval passes."

  • Debounce → search-as-you-type, resize-end, save-on-idle — wait for the user to stop.
  • Throttle → scroll tracking, drag/mousemove, rate-limiting a button — stay responsive but capped.
  • Debounce implementation: clearTimeout the pending call, then setTimeout a new one.
  • Throttle implementation: track a "can run now" flag or last-run timestamp, ignore calls until the interval passes.
  • Trailing is the naive default — leading fires on the first call instead of the last.
📖 Explanation ▾

Debounce is a delay that keeps getting pushed back. Every time the debounced function is called, it cancels whatever timer is still pending and starts a brand new one. The wrapped function only actually runs once the calls stop coming in for the full delay — one call, one execution, always at the end of the burst.

Throttle is a fixed-rate limiter instead of a delay. It runs the function immediately (or on the next tick), then locks itself for a set interval — any call that lands inside that locked window is simply dropped. It doesn't care whether calls are still coming in; it just refuses to run again until its own clock says the interval is up.

💻 See the code ▾
JS 
// trailing debounce — waits for calls to STOP for `delay` ms
function debounce(fn, delay) {
  let timerId = null;
  return function(...args) {
    clearTimeout(timerId);           // cancel the pending run — resets the wait
    timerId = setTimeout(() => {
      fn.apply(this, args);   // only the LAST call in the burst survives
    }, delay);
  };
}

const onType = debounce(searchApi, 300);
input.addEventListener("input", onType);  // fires 300ms after typing stops

Every call clears the previous timer before starting a new one — only a call followed by delay ms of silence ever actually runs fn.

JS 
// leading throttle — runs immediately, then ignores calls for `limit` ms
function throttle(fn, limit) {
  let canRun = true;
  return function(...args) {
    if (!canRun) return;    // still inside the locked window — drop this call
    canRun = false;
    fn.apply(this, args);
    setTimeout(() => { canRun = true; }, limit);  // unlock after the interval
  };
}

const onScroll = throttle(updatePosition, 200);
window.addEventListener("scroll", onScroll);  // runs at most every 200ms

The canRun flag is the whole trick — calls that arrive while it's false are simply dropped, not queued or delayed.

🌍 Real-world example ▾

Debounce is an elevator door: every time someone new walks up, it resets the "closing" timer — it only actually closes once no one's arrived for a few seconds. Throttle is a security camera taking a photo every 5 seconds: people can walk past constantly, but it only ever captures on its own fixed schedule, not one per person.
