fetch() — a 404 doesn't make the Promise reject

"If fetch() gets back a 404 or 500 from the server, does the returned Promise reject or resolve?"

Why it matters ▾
  • Nearly every real app talks to a server through fetch, and getting this exact behavior wrong is why apps silently show broken or empty UI on a 404 instead of an error message.
  • Comes up whenever an interviewer wants to check you actually understand what "reject" means for a Promise, not just that you can write await fetch(...).
  • AbortController and timeout handling are near-guaranteed follow-ups once basic fetch usage is confirmed.
🔥 Easy interview recall

fetch() → returns a Promise, same as any other async call

HTTP error (404/500) → Promise still resolves — check response.ok

Network failure (DNS/offline) → Promise rejects — the only real reject case

response.json() → its own Promise — needs a second await

Think: fetch() builds on the Promise you already know — nothing new about the mechanism "Did the request fail" and "did the server say no" are two different questions

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

fetch() does not reject on a 404 or 500. It only rejects on a true network-level failure (DNS, offline, CORS) — an HTTP error still resolves normally with response.ok === false, so checking response.ok yourself is required, not optional.

🔄 Likely Follow-up

"fetch() has no timeout option — how would you cancel a request that's taking too long?" Create an AbortController, pass controller.signal into fetch's options, and call controller.abort() from a setTimeout — the in-flight fetch then rejects with an AbortError.

🎯 Say this in the interview — the exact lines to land

"fetch() returns a Promise like any other async call, but it only rejects on a genuine network failure — a 404 or 500 still resolves normally, so I always check response.ok myself before trusting the response. Parsing the body is a second async step, since response.json() returns its own Promise. Since fetch has no built-in timeout, I pair it with AbortController and setTimeout to cancel a request that's taking too long."

  • fetch() → only rejects on network failure, never on an HTTP error status.
  • response.ok === false on 4xx/5xx → still a resolved Promise — check it yourself.
  • response.json() → returns its own Promise — needs a second await.
  • No built-in timeout → AbortController + setTimeout is the standard pattern.
  • controller.abort() → rejects the in-flight fetch with an AbortError.
📖 Explanation ▾

fetch(url) returns a Promise — the exact same kind covered on the Promises and async/await pages, nothing new about the mechanism itself. What's different is when that Promise settles: it resolves as soon as the server sends back a response, whatever the status code is. A 200, a 404, and a 500 all resolve that same Promise; only a genuine network-level failure — a DNS lookup fails, the connection drops, a CORS block — makes it reject.

The response carries the status in response.status and a convenience boolean, response.ok (true for 200–299). The body isn't parsed yet at that point — calling response.json() (or .text(), .blob()) starts its own asynchronous read and returns its own Promise, so it needs a second await. Headers work the same way on both sides: pass a plain object under the headers option to send them, and read them back off response.headers, which is its own iterable object with get()/has() — not a plain {} you index into.

fetch() has no built-in timeout or cancel button on its own. AbortController fills both gaps: create one, pass its .signal into fetch's options, and call .abort() whenever you want to stop the request — the in-flight fetch then rejects with an AbortError. Pairing that with setTimeout is the standard way to build a timeout, since fetch alone never gives up on its own. Building retry logic on top of this, or handling a fast typist firing overlapping search requests, is a step further — see Production Scenarios for that.

💻 See the code ▾
JavaScript 
const res = await fetch('/api/user/9999'); // 404 — Promise still resolves!

console.log(res.ok);      // false
console.log(res.status);  // 404

if (!res.ok) {
  throw new Error(`Request failed: ${res.status}`); // ❌ you throw it — fetch never did
}

const data = await res.json(); // second await — json() is its own Promise

fetch() resolved completely normally here — nothing ever reached a .catch() or a try/catch on its own, because a 404 isn't a network failure.

JavaScript 
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 5000); // 5s timeout

try {
  const res = await fetch(url, { signal: controller.signal });
  clearTimeout(timer);           // ✅ finished in time — cancel the timer
} catch (err) {
  if (err.name === 'AbortError') {
    console.log('Request timed out or was cancelled');
  }
}

fetch has no built-in timeout — pairing AbortController with setTimeout is the standard way to build one.

JavaScript 
const res = await fetch(url, {
  headers: { 'Authorization': `Bearer ${token}`, 'Content-Type': 'application/json' }
});

console.log(res.headers.get('content-type')); // read one header

for (const [key, value] of res.headers) { // iterate every response header
  console.log(key, value);
}

Headers is its own object with get()/has()/entries() — not a plain {} you can index into directly.

🌍 Real-world example ▾

A dashboard loading a chart calls a REST endpoint with fetch(), checks response.ok before touching the body, and wraps the call in the AbortController + setTimeout pattern so a slow backend can't hang the UI forever. Building retry logic on top of that, or handling a fast typist firing overlapping search requests, is a step further — that's covered under Production Scenarios, not repeated here.
