Azure SQL — how much of SQL Server did it actually keep?

"What is Azure SQL, and how does it relate to on-prem SQL Server?"

Why it matters ▾
🗄️ Azure SQL vs. on-prem SQL Server
❗ ProblemThe moment a database migration to Azure comes up, picking the wrong option — like Azure SQL Database for an app that leans on SQL Agent jobs, cross-database queries, or linked servers — means losing those instance-level features and rewriting the app instead of just moving it.
✅ SolutionAzure actually offers three points on one spectrum — SQL Server on a VM, Managed Instance, Azure SQL Database — each trading how much Microsoft manages for how much of the on-prem SQL Server surface it keeps, so picking the right one up front avoids that rewrite.
RecallThree points, one spectrum — the more Microsoft manages, the less on-prem SQL Server surface you keep.
🔥 Easy interview recall

SQL Server on a VM → full control, you manage it

Managed Instance → near-100% compatible, managed

Azure SQL Database → most managed, narrower surface

Think: the more Microsoft manages for you, the less of classic SQL Server you keep.

⚠️ Common Trap

Azure SQL Database is not a drop-in replacement for every on-prem SQL Server feature. Some instance-level features — cross-database queries, classic SQL Agent jobs, linked servers — differ or aren't available, and need Managed Instance (or a VM) instead.

🔄 Likely Follow-up

"When would you pick Managed Instance over Azure SQL Database?" When migrating an existing on-prem app that depends on instance-level features — SQL Agent jobs, cross-database queries, linked servers — with minimal code change.

🎯 Say this in the interview — the exact lines to land

"Azure SQL Database is PaaS SQL Server. Managed Instance is for near-full compatibility, built for lift-and-shift migrations. A SQL Server VM is full IaaS — complete control, but I manage the instance myself."

  • Azure SQL Database → everyday default for new, cloud-native apps — least ops overhead.
  • Managed Instance → use when migrating an existing app that needs SQL Agent jobs, linked servers, or cross-database queries.
  • SQL Server on a VM → use only for full OS/instance-level control Azure's managed options don't offer.
  • Migration-effort tradeoff → the more Microsoft manages, the less you touch — but also the fewer instance-level features you keep.
📖 Explanation ▾

Azure SQL Database is Microsoft's fully managed, PaaS evolution of the SQL Server engine — mostly compatible with on-prem T-SQL, but Microsoft owns patching, backups, and high availability, and the surface exposed to you is narrower than a full SQL Server instance.

Azure SQL Managed Instance targets near-100% compatibility with on-prem SQL Server at the instance level, specifically so an existing app can move with minimal rewrite — it keeps things Azure SQL Database doesn't, like SQL Agent jobs, cross-database queries, and linked servers.

SQL Server on an Azure VM is a separate, third option — genuinely IaaS, running full SQL Server yourself on a VM you patch and manage. It's distinct from both "Azure SQL" offerings, not a variant of either one.

The tcp:...database.windows.net,1433 shape is the same whether you're pointed at Azure SQL Database or Managed Instance — only the server name and a few options change.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're building a new, cloud-native app with no legacy database dependencies

There's no SQL Agent job or linked server to preserve, so the fully managed option is the least-ops path — Microsoft handles patching, backups, and HA, and the narrower surface never gets in the way. This is the everyday default choice.

RememberNew app, no legacy baggage → Azure SQL Database.
2 Your on-prem app already depends on SQL Agent jobs, cross-database queries, or linked servers

Moving straight to Azure SQL Database would mean rewriting all of that scheduling and cross-database logic. Managed Instance keeps those instance-level features working close to as-is, so the migration stays a lift-and-shift instead of a rewrite.

RememberInstance-level features to preserve → Managed Instance.
3 You need OS- or instance-level control that even Managed Instance doesn't expose

This is genuinely IaaS — you own the VM, the OS, and the SQL Server instance yourself, trading Microsoft's management for full control. It's a separate, third option, not a variant of either Azure SQL offering.

RememberFull OS/instance control needed → SQL Server on a VM, not either managed option.
🌍 Real-world example ▾

A team is migrating a 10-year-old on-prem app that leans on SQL Agent jobs for nightly batch processing. Moving straight to Azure SQL Database would mean rewriting all of that scheduling logic. Picking Managed Instance instead keeps the SQL Agent jobs working close to as-is, so the migration stays close to a lift-and-shift instead of a rewrite.
