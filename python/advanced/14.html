Separating business logic from infrastructure is what lets you swap a database or add a queue without rewriting your rules

How would you structure a large Python application, separating business logic from infrastructure?

Why it matters ▾
  • Tests whether you can design for testability and long-term change, not just make code run — anyone can write a script that works once.
  • A natural follow-up once a candidate says "I'd write clean code" — the interviewer wants the actual structural mechanism, not a general promise.
  • A common opener before a scenario question about swapping a database or adding a message queue under load.
🔥 Easy interview recall

Structure = "business rules depend on abstractions; infrastructure plugs in at the edges."

Think: a Protocol sits in the middle — Postgres or SQS is just whatever is plugged into it today.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Business logic calling a specific database client or ORM model directly everywhere is not "keeping it simple." It forces every test to spin up a real database, turns swapping infrastructure into a sprawling rewrite, and buries the actual business rule underneath infrastructure calls.

🔄 Likely Follow-up

"How do you manage configuration and secrets differently?" Configuration (timeouts, feature flags, environment name) can reasonably live in environment variables or config files checked into deploy tooling; secrets (API keys, database passwords, tokens) need a dedicated secrets manager — or at minimum injected via environment variables that are never committed to source control — and must never appear in logs.

🎯 Say this in the interview — the exact lines to land

"Business logic should depend on abstractions, not concrete infrastructure — that's what makes swapping a database or adding a queue tractable instead of a rewrite."

  • Dependency injection → depends on a Protocol or interface, never a concrete DB client — the real implementation is handed in from outside.
  • Configuration → environment variables or config files per environment — timeouts, feature flags, environment name.
  • Secrets need a genuinely different, more careful path — a dedicated secrets manager, or env vars never committed, and never logged.
  • Centralized logging and a deliberate error strategy → which layer catches what — expected failures vs. genuine bugs.
  • Testing, packaging, and observability → covered on their own pages — this page is the structural decisions that make those easier.
📖 Explanation ▾

Business logic is the actual rules and decisions an application makes. Infrastructure is how those rules get carried out — how data is stored, how requests arrive, which specific database, queue, or cache technology is behind it. Separating the two, usually through clear module/package boundaries and dependency injection, means the core rules can be tested and reasoned about without spinning up a real database or network call, and an infrastructure change doesn't ripple through the rules. The mechanism is a business-logic function or class that depends on an abstraction — an interface or Protocol — instead of importing a concrete database client directly.

Configuration and secrets need genuinely different handling, not the same bucket:

ConfigurationSecrets
Examplestimeouts, feature flags, environment nameAPI keys, database passwords, tokens

The rest of a maintainable structure is consistent, centralized logging instead of scattered print calls, and a deliberate error-handling strategy — deciding which layer catches what, and which errors are expected and handled versus genuinely unexpected bugs. Testing, packaging/deployment, and observability each get their own depth elsewhere on this site — this page is about the structural decisions that make all of those easier, not those topics themselves.

💻 See the code ▾
Python 
# ❌ business logic imports a concrete DB client directly
import psycopg2

def get_active_user(user_id):
    conn = psycopg2.connect(DSN)  # a specific client, baked in
    cur = conn.cursor()
    cur.execute("SELECT * FROM users WHERE id=%s AND active=true", (user_id,))
    return cur.fetchone()

Testing this rule needs a real Postgres connection, and swapping databases means rewriting every function shaped like this one.

Python 
# ✅ business logic depends on a Protocol, not a concrete client
from typing import Protocol

class UserRepository(Protocol):
    def get_user(self, user_id: int) -> dict | None: ...

def get_active_user(user_id: int, repo: UserRepository) -> dict | None:
    user = repo.get_user(user_id)  # only knows the Protocol's shape
    return user if user and user["active"] else None

A Postgres, Mongo, or in-memory fake repository can be handed in as repo without touching this function at all.

🌍 Real-world example ▾

A team migrated from a synchronous ORM to an async database driver in weeks, not months, specifically because their business logic had never directly imported the ORM's model classes — every database access went through a thin repository abstraction. Swapping what sat behind that one abstraction was a contained, mechanical change instead of a rewrite touching every business rule in the codebase.
