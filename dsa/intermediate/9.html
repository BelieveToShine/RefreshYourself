Prefix Sum & Difference Array — O(n) once, O(1) forever

"How do you answer many range-sum queries on the same array without recomputing each one from scratch?"

Why it matters ▾
  • A common early warm-up — interviewers use it to see if you reach for O(1) precomputation instead of just restating a loop.
  • The building block behind rolling totals in dashboards, "sum of sales this week" style queries, and area-sum problems on grids.
  • The natural follow-up (does the array change between queries?) is a favorite way to separate memorized syntax from real understanding of the trade-off.
🔥 Easy interview recall

Prefix Sum → cheap range queries on a fixed array

Difference Array → cheap range updates, read once at the end

Think: Prefix Sum answers "what's the sum?" fast. Difference Array answers "add to a range" fast — mirror images of the same trick.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Summing the range from scratch inside the query loop isn't "fine for now." The moment there are many range-sum queries on the same array, that's the exact signal to precompute a prefix sum once instead of re-scanning the range every time.

🔄 Likely Follow-up

"What if the array itself gets updated between range-sum queries?" A plain prefix sum needs a full O(n) rebuild after every update, which defeats the point — that mixed read/write case is what a Fenwick Tree (Binary Indexed Tree) or Segment Tree is for, both supporting range queries and point updates in O(log n) each.

🎯 Say this in the interview — the exact lines to land

"Prefix sum precomputes running totals once, so any range sum after that is one subtraction — O(1) per query. A difference array is the reverse trick: it turns many range updates into O(1) point writes, then a single prefix-sum pass rebuilds the final array."

  • Prefix Sum → O(n) once, O(1) per range query after that.
  • Difference Array → O(1) per range update, reconstruct with one prefix-sum pass.
  • Range sum formula → P[j] − P[i−1], careful with the i = 0 case.
  • Array mutates between queries? → Fenwick Tree / Segment Tree, not a plain prefix sum.
📖 Explanation ▾

A prefix sum array stores the running total up to each index: P[i] = A[0] + A[1] + ... + A[i]. Once that's built — a single O(n) pass — the sum of any range [i, j] in the original array is just P[j] − P[i−1] (or plain P[j] when i is 0). What used to cost O(n) per query, every single time, now costs one subtraction.

A difference array flips the idea around for the opposite problem: many range updates instead of many range queries. Store D[i] = A[i] − A[i−1], and adding a value v to every element from i to j becomes two point writes — D[i] += v and D[j+1] −= v — no matter how wide the range is. Read the real array back at the end by taking the prefix sum of D. The two are exact inverses of each other: one turns a running total back into values, the other turns values into the deltas between them.

The same trick extends to a grid. A 2D prefix-sum table holds the sum of every rectangle from the top-left corner to each cell, built once with inclusion–exclusion (add the two overlapping rectangles above and to the left, subtract the double-counted corner). After that, any rectangular sub-region's sum is four lookups and simple arithmetic — still O(1).

💻 See the code ▾
C# 
int[] A = { 2, 4, 1, 5, 3 };
int[] P = new int[A.Length];
P[0] = A[0];
for (int i = 1; i < A.Length; i++)
    P[i] = P[i - 1] + A[i];      // ✅ O(n), built once

int RangeSum(int i, int j) =>
    i == 0 ? P[j] : P[j] - P[i - 1];   // ✅ O(1) per query

Build P once — every RangeSum call after that is one subtraction, however many queries follow.

C# 
int n = 5;
int[] D = new int[n + 1];   // one extra slot for the closing write

void AddRange(int i, int j, int v)
{
    D[i] += v;        // ✅ O(1) — starts the range
    D[j + 1] -= v;    // ✅ O(1) — cancels it right after
}

AddRange(1, 3, 3);      // add 3 to indices 1..3

int[] result = new int[n];
result[0] = D[0];
for (int k = 1; k < n; k++)
    result[k] = result[k - 1] + D[k];   // ✅ prefix-sum D → final array

Any number of AddRange calls still cost O(1) each — the O(n) prefix-sum pass only happens once, at the very end.

🌍 Real-world example ▾

An interviewer asks for the sum of a range, then another, then another — many times over the same array. Building the prefix sum once and answering each with one subtraction turns an O(n)-per-query slog into O(1) per query. Flip side: if instead they ask you to add a value to a whole range, over and over, before reading the final totals once — that's the moment to reach for a difference array instead, so each update stays O(1) too.
