Not every lookup problem is a map — let the access pattern pick the collection

"Design a high-throughput lookup service with frequent reads, updates, and duplicate values. Which collection do you actually reach for?"

Why it matters ▾
🗂️ The Access Pattern Decides
❗ Problem"High-throughput lookup service" sounds like it just needs a bigger, faster HashMap — but a plain HashMap under real concurrent reads and writes corrupts or throws under load, and "duplicate values" can quietly mean the data isn't even a keyed lookup at all.
✅ SolutionName the actual access pattern first — concurrent read/write at scale, read-heavy with rare updates, or a stream of items rather than a keyed lookup — and the right collection (ConcurrentHashMap, an immutable map behind a volatile reference, or a concurrent queue) falls out of that, not out of habit.
RecallName the access pattern first — the collection is the answer to that, not the starting point.
🔥 Easy interview recall

HashMap → single-threaded only

ConcurrentHashMap → concurrent read + write

immutable map + volatile → read-heavy, rare updates

concurrent queue → a stream, not a keyed lookup

Think: ask "what's the real access pattern" before reaching for a type — "duplicate values" is often the tell that it's not a map problem at all.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Duplicate values" means I need a Map<K, List<V>>. Often it actually means the data isn't a keyed lookup at all — it's a stream of events or work items to process, which is a concurrent queue problem, not a map problem forced into one.

🔄 Likely Follow-up

"Why not just synchronize a plain HashMap instead of using ConcurrentHashMap?" A synchronized HashMap serializes every reader and writer behind one lock, so throughput collapses under real concurrent load; ConcurrentHashMap's per-bin locking lets unrelated keys be read and written at the same time, which is the whole reason it exists.

🎯 Say this in the interview — the exact lines to land

"I'd start from the actual access pattern — a plain HashMap is only safe single-threaded, ConcurrentHashMap is the default for real concurrent reads and writes, an immutable map swapped through a volatile reference is best when reads vastly outnumber updates, and if 'duplicate values' really means a stream of work items, that's a concurrent queue, not a map at all."

  • HashMap → fine only single-threaded or externally synchronized — a bottleneck under real load.
  • ConcurrentHashMap → default correct choice for concurrent read+write at scale, via per-bin locking.
  • Immutable map + volatile → zero-synchronization reads when data is read-heavy and rarely updated.
  • Concurrent queue → the right shape when it's really a stream of items, not a keyed lookup.
📖 Explanation ▾

A plain HashMap is genuinely fine when the service really is single-threaded, or every access already goes through external synchronization — but under real concurrent load without that protection, it can corrupt its internal structure or throw during iteration, and wrapping it in a single lock just turns every reader and writer into a queue behind one gate. ConcurrentHashMap is the default correct choice at scale specifically because it doesn't need that single gate: Java 8+ uses per-bin locking (with per-bin treeification once a bin gets crowded), so unrelated keys can be read and written concurrently without contending with each other.

When the data is read far more often than it's written — a feature-flag set, a routing table, a config snapshot — an immutable map behind a volatile reference beats even ConcurrentHashMap for reads: a reader just dereferences the current volatile reference and reads a map that can never change underneath it, with zero synchronization cost per read. An update builds a brand-new immutable map and swaps the reference atomically — more expensive per update, but updates here are rare by assumption, so that cost is the right one to pay.

"Duplicate values" is the detail worth pausing on: if it actually describes a flow of events or work items arriving over time — not a value you look up by key — forcing that into a Map<K, List<V>> is solving the wrong problem. A ConcurrentLinkedQueue, or a BlockingQueue when producers need to be slowed down when consumers fall behind (backpressure), is the shape that actually matches a stream of items — recognizing that distinction is exactly what separates a candidate reciting "use ConcurrentHashMap" from one who checked the access pattern first.

💻 See the code ▾
Java 
Map<String, Session> sessions = new ConcurrentHashMap<>();
sessions.computeIfAbsent(id, k -> loadSession(k)); // ✅ per-key atomic, high concurrent throughput

Unrelated session keys can be read and written at the same time — ConcurrentHashMap never serializes the whole map behind one lock.

Java 
private volatile Map<String, Flag> flags = Map.copyOf(loadFlags());

void reload() {
    flags = Map.copyOf(loadFlags()); // ✅ build new, swap the reference atomically
}

Readers just dereference flags — zero synchronization per read, because the map they see can never be mutated underneath them.

🧭 Use Cases — recognize these when they happen to you ▾
1 A cache or session store is read and written by many threads at once

This is the #1 scenario you'll actually run into: real concurrent read and write traffic hitting the same keyed store. ConcurrentHashMap is the default here precisely because its per-bin locking lets unrelated keys proceed without contending with each other, unlike a synchronized HashMap serialized behind one lock.

RememberConcurrent read + write at scale → ConcurrentHashMap, not a synchronized HashMap.
2 Config or routing data is read constantly but only reloaded occasionally

When updates are rare and reads vastly dominate, an immutable map rebuilt in full and swapped through a volatile reference beats ConcurrentHashMap for pure read throughput — readers never pay any synchronization cost at all, because the map they see can never change underneath them.

RememberRare updates, heavy reads → rebuild immutable, swap the volatile reference.
3 "Duplicate values" turns out to mean a stream of incoming events, not a keyed lookup

A candidate who forces this into a Map<K, List<V>> has solved the wrong problem — there's no key being looked up, just items arriving and needing processing. A concurrent queue (ConcurrentLinkedQueue, or a BlockingQueue when producers need to slow down for consumers) is the shape that actually fits.

RememberA stream of items to process is a queue problem, not a map problem.
🌍 Real-world example ▾

A session store is hit by thousands of concurrent requests per second, almost evenly split between reads and writes. ConcurrentHashMap is the right default here: its per-bin locking lets unrelated sessions be read and written at the same time, which is exactly the throughput profile this workload needs.
