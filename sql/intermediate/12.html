Recursive CTEs — one query that walks a hierarchy it can't see the bottom of

"What is a recursive CTE, and what does it let you do that a non-recursive query structurally can't?"

Why it matters ▾
  • The natural follow-up right after a plain CTE question — "can a CTE reference itself?" comes up often.
  • The standard tool for hierarchical data: an org chart, a category tree, a bill-of-materials — anything with an unknown number of levels.
  • A common way in to "find every report under a manager, however deep the chart goes."
🔥 Easy interview recall

Recursive CTE = "a query that keeps joining back to its own result until nothing new comes back."

Think: 👑 CEO → 🧑‍💼 direct reports → 👤 their reports → … repeats until a round returns nothing new.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Recursive CTEs are inherently slow or exotic." For genuinely hierarchical data they're the standard, correct tool — the real risk is a cyclical relationship in the data causing infinite recursion, not the technique itself.

🔄 Likely Follow-up

"How would you find all employees reporting up to a given manager, at any depth, without knowing how many levels deep the org chart goes?" Exactly what a recursive CTE is for — anchor = the manager's row, the recursive member joins ManagerId back to the growing result set, repeating until no new reports are found.

🎯 Say this in the interview — the exact lines to land

"A recursive CTE has two parts combined with UNION ALL: an anchor member that's a normal SELECT picking the starting rows, and a recursive member that joins back to the CTE's own name, re-running until it returns no new rows. It's the standard way to walk hierarchical data — an org chart, a category tree — without knowing how many levels deep it goes. The real risk isn't performance, it's forgetting to guard against a cycle in the data."

  • Anchor member → the starting rows — a plain SELECT, no self-reference.
  • Recursive member → joins back to the CTE itself, combined with UNION ALL.
  • Reach for it → for hierarchical data — org chart, category tree, bill-of-materials.
  • Cycle risk → guard the data, not just the engine's MAXRECURSION cutoff.
📖 Explanation ▾

Building on the plain CTE — a recursive CTE adds one capability a non-recursive query structurally can't have: it can reference its own result set mid-query. It's built from two parts combined with UNION ALL: the anchor member is an ordinary SELECT that establishes the starting rows (no self-reference at all), and the recursive member is a SELECT that joins back to the CTE's own name, joined against the base table. The engine runs the recursive member again and again, each time against only the rows the previous round added, until a round returns zero new rows — that's the stopping condition, not a fixed number of levels.

Because recursion keeps executing until no new rows appear, a genuine cycle in the underlying data (A reports to B, B reports to A) would recurse forever. Most engines have a built-in safety cutoff — T-SQL's MAXRECURSION, default 100 — but that's a blunt backstop that just fails loudly once the limit is hit. It doesn't make the query correct. For real correctness, the query itself should guard against a cycle directly, for example by tracking a depth or a visited-path column and stopping once it exceeds a sane bound.

💻 See the code ▾
SQL 
WITH OrgChart AS (
    -- anchor: the top of the hierarchy (no manager)
    SELECT Id, ManagerId, Name, 0 AS Depth
    FROM Employees
    WHERE ManagerId IS NULL
    UNION ALL
    -- recursive: joins back to OrgChart itself, one level deeper
    SELECT e.Id, e.ManagerId, e.Name, o.Depth + 1
    FROM Employees e
    JOIN OrgChart o ON e.ManagerId = o.Id
)
SELECT * FROM OrgChart ORDER BY Depth;  -- ✅ every level, in one query

The recursive member only ever looks one join deeper than the last round — Depth just labels which round produced each row.

SQL 
WITH OrgChart AS (
    SELECT Id, ManagerId, Name, 0 AS Depth
    FROM Employees
    WHERE ManagerId IS NULL
    UNION ALL
    SELECT e.Id, e.ManagerId, e.Name, o.Depth + 1
    FROM Employees e
    JOIN OrgChart o ON e.ManagerId = o.Id
    WHERE o.Depth < 50  -- ✅ guards against a real cycle in the data
)
SELECT * FROM OrgChart
OPTION (MAXRECURSION 100);  -- engine's own backstop, not a substitute

MAXRECURSION is T-SQL's built-in safety cutoff — useful, but the WHERE o.Depth < 50 guard is what actually protects against a genuine cycle (A reports to B, B reports to A) instead of just failing loudly at round 100.

🌍 Real-world example ▾

It's like asking "who's their manager?" over and over, automatically, instead of asking it by hand at every level. You ask it once, the answer feeds the next "who's their manager?", and it keeps going on its own until someone answers "nobody" — at which point it stops, because there's nothing new left to ask.
