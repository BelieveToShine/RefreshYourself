What Is React — a library that lets you describe UI, not command it

"What is React, and what problem does it actually solve?"

Why it matters ▾
🔧 Imperative
❗ ProblemData keeps changing, and the real DOM has to be kept in sync with it — someone has to find the right element and update it, by hand, every single time.
✅ SolutionYou write each DOM step yourself — find it, change it, toggle it — which works, but a forgotten step lets the DOM silently drift from your data.
RecallImperative = you write every update step yourself, by hand.
⚛️ Declarative (React)
❗ ProblemHand-writing every DOM step for every update is repetitive, and one missed step leaves the DOM out of sync with no warning.
✅ SolutionYou describe what the UI should look like for the current state, and React's virtual-DOM diff works out the minimal real DOM changes needed — that whole class of forgotten-step bug doesn't exist.
RecallDeclarative = you describe the result, React figures out the DOM steps.
🔥 Easy interview recall

React = "describe what the UI should look like, not how to update it step by step."

Think: declarative (what) vs. imperative (how) — React is declarative.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"React manipulates the DOM directly, and that's why it's fast." The real advantage is batching updates and touching the DOM only where something actually changed, via a virtual-DOM diff — not a blanket "always faster than the DOM" guarantee; carefully hand-tuned direct DOM code can still beat it in a narrow case.

🔄 Likely Follow-up

"Is React a framework or a library?" A library — it only handles the view layer. Routing, global state management, and other concerns are separate tools you choose and assemble yourself, unlike an all-in-one framework that makes those decisions for you.

🎯 Say this in the interview — the exact lines to land

"React is a JavaScript library for building UI out of reusable components — it only owns the view layer. You describe what the UI should look like for a given state, and React works out how to update the real DOM to match, using an internal virtual DOM to compute the minimal set of changes needed."

  • Library, not a framework — routing and state management are separate choices you assemble yourself.
  • Declarative → you say what the UI should look like, React figures out how to get there.
  • Virtual DOM → an internal representation React diffs to find the minimal real DOM change.
  • Not "always faster" → the real win is batched, consistent updates, not a universal speed guarantee.
📖 Explanation ▾

React is a JavaScript library, not a framework — it only handles the view/UI layer. Building UI out of reusable components is its whole job; routing, global state management, and everything else are separate libraries you pick and wire together yourself.

The problem it solves is keeping the DOM in sync with data that keeps changing. Instead of you writing the steps to update the page by hand, you describe what the UI should look like for the current state, and React figures out how to make the real DOM match — using an internal representation, the virtual DOM, to work out the smallest set of real DOM changes actually needed.

💻 See the code ▾
JSX 
function Greeting({ name }) {
  return <h1>Hello, {name}</h1>;  // describes WHAT to show
}

This describes what to render for this data — nothing here reaches into the DOM directly.

JavaScript 
// vanilla JS — the "how" React replaces
const el = document.getElementById("greeting");  // find it
el.textContent = "Hello, " + name;                 // change it, by hand

This is the manual, step-by-step work a virtual-DOM diff does for you automatically.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're updating a page with plain JavaScript or jQuery, one step at a time

This is the imperative style — you write every DOM step yourself in your own code. It works, but skip a step and the UI silently drifts from your data.

RememberManual DOM steps in your own code → that's imperative, not React's model.
2 You're writing a React component that returns JSX for the current state

This is the declarative style — you state what the UI should look like for this data, and React works out how to get there via a virtual-DOM diff. This is the #1 mental model you'll actually use every day in React.

RememberJSX describing the UI → declarative, React handles the how.
3 An interviewer asks why React is fast, and you're tempted to say "it manipulates the DOM directly"

React doesn't touch the DOM directly for every change — the real advantage is batching updates and touching the DOM only where something actually changed, via the virtual-DOM diff, not a blanket "always faster than the DOM" guarantee.

RememberNot "always faster" — the real win is batched, minimal DOM updates.
🌍 Real-world example ▾

Telling a taxi driver "take me to the airport" is declarative — you state the destination and the driver works out the turns. Giving turn-by-turn directions yourself is imperative — you're doing the driver's job for them. JSX works the same way: you state the UI you want for this data, and React works out the actual DOM turns to get there.
