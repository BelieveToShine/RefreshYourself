String vs. StringBuilder vs. StringBuffer — which one secretly rebuilds the whole string?

"What's the difference between String, StringBuilder, and StringBuffer?"

Why it matters ▾
📌 String
❗ ProblemBuilding up text with + inside a loop looks harmless, but each one allocates a brand-new String object — a 10,000-iteration loop quietly creates 10,000 throwaway objects.
✅ SolutionString is immutable on purpose — every "modification" (+, concat, replace) has to return a new object, which is exactly why it's safe to share and cache, but wasteful to rebuild repeatedly.
RecallString = immutable — every change is a new object.
🧵 StringBuilder
❗ ProblemRepeated concatenation in a hot loop needs one buffer that grows, not thousands of discarded objects piling up along the way.
✅ SolutionStringBuilder holds one mutable character buffer — append() grows it in place instead of allocating a new object on every call.
RecallStringBuilder = one mutable buffer, built for loops.
🔒 StringBuffer
❗ ProblemSharing that same builder across multiple threads risks two threads appending at the same time and corrupting the result.
✅ SolutionStringBuffer is the identical mutable API, but every method is synchronized — only one thread can modify it at a time, at a real throughput cost.
RecallStringBuffer = StringBuilder + synchronized, slower on purpose.
🔥 Easy interview recall

String → new object every time

StringBuilder → mutable, fast, not thread-safe

StringBuffer → mutable, thread-safe, slower

Think: String rebuilds. StringBuilder grows in place. StringBuffer grows in place, safely shared.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

StringBuilder is not "the thread-safe version" of StringBuffer. It's the other way round — StringBuffer came first; StringBuilder (Java 5) is the newer, unsynchronized one, added because most code never needed that locking.

🔄 Likely Follow-up

"If StringBuilder isn't thread-safe, how do you build a string safely across threads?" Prefer confining a StringBuilder to one thread when you can (build it locally inside each task) — reach for StringBuffer only when the same instance genuinely has to be mutated by more than one thread.

🎯 Say this in the interview — the exact lines to land

"String is immutable, so every modification creates a new object. StringBuilder is a mutable buffer for efficient repeated changes, but isn't thread-safe. StringBuffer is the same mutable API with every method synchronized, which costs throughput."

  • String → use for fixed or rarely-changed text, safe to share and cache.
  • StringBuilder → default choice for building strings in a loop, single-threaded.
  • StringBuffer → use only when one instance is genuinely shared across threads.
📖 Explanation ▾

String can't be changed after it's created — "modifying" it (+, concat, replace) always hands back a new object, leaving the old one for the garbage collector to reclaim.

StringBuilder keeps one resizable character buffer and mutates it directly — append(), insert(), and delete() all operate on the same object, so building a long string in a loop does one growing allocation instead of thousands of throwaway ones.

StringBuffer is the same API as StringBuilder, method for method, except every method is synchronized — safe to call from multiple threads on the same instance, at the cost of acquiring a lock on every single call.

💻 See the code ▾
Java 
String s = "";
for (int i = 0; i < 3; i++) {
    s += i;             // ❌ a new String object every iteration
}

Three iterations, three throwaway String objects — only the last one survives.

Java 
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 3; i++) {
    sb.append(i);        // ✅ same buffer, grown in place
}
String result = sb.toString();

One object the whole time — append() never allocates a new String.

Java 
StringBuffer buf = new StringBuffer();
buf.append("Hi");       // 🔒 synchronized — safe if another thread appends too

Identical API to StringBuilder — the only difference is the synchronized lock on every call.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're building a large string in a single-threaded loop

A report, a CSV row, a log line assembled from many pieces — this is the everyday case StringBuilder exists for. This is the #1 scenario you'll actually run into.

RememberLoop building text, one thread → StringBuilder.
2 You're reusing a fixed piece of text everywhere

A status code, a config key, a map key — text that doesn't change needs none of a builder's machinery. String is simpler, and its immutability is exactly what makes it safe to cache and share.

RememberFixed text, reused everywhere → plain String.
3 You reach for StringBuffer "just to be safe" in ordinary code

If the code never leaves one thread, every synchronized call on a StringBuffer acquires and releases a lock that nothing is ever contending for — pure overhead, no actual safety gained over StringBuilder.

RememberNo real multi-thread sharing → the synchronization is wasted cost.
🌍 Real-world example ▾

String is a printed photo; StringBuilder is a document you keep editing. To change a printed photo you have to print a brand-new one — you can't edit the paper itself, same as String. Editing a document in place, over and over, is StringBuilder. StringBuffer is that same document, except the keyboard locks so only one person can type into it at a time.
