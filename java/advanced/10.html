synchronized vs. Lock — automatic safety, or explicit control?

"When would you reach for an explicit Lock instead of the synchronized keyword?"

Why it matters ▾
🔒 synchronized
❗ ProblemAny code that mutates shared state from multiple threads needs mutual exclusion — and manually acquiring/releasing a lock around every exit path, including exceptions, is easy to get wrong.
✅ Solutionsynchronized acquires an intrinsic monitor lock automatically, and releases it automatically when the block exits — even via an exception — so there's no unlock to forget.
Recallsynchronized = automatic lock, automatic release, no manual bookkeeping.
🔑 Lock
❗ Problemsynchronized has no timeout, no way to abandon an attempt that's taking too long, no interruptibility, and no fairness policy — real constraints once contention gets serious.
✅ Solutionjava.util.concurrent.locks.Lock is an explicit API: lock()/unlock() yourself, always inside a finally — in exchange for tryLock() with a timeout, interruptible locking, and fairness options synchronized can't offer.
RecallLock = you manage it, but you get timeout, interruptibility and fairness.
🔥 Easy interview recall

synchronized → automatic acquire/release

Lock → explicit lock()/unlock(), more control

Think: synchronized never forgets to unlock. Lock can time out, get interrupted, or wait fairly — if you remember the finally.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling lock() without an immediate try/finally is not "mostly safe." If any code between lock() and unlock() throws, the lock is never released — unlike synchronized, there's no compiler or runtime safety net to save you.

🔄 Likely Follow-up

"Can two threads using Lock ever deadlock the same way synchronized can?" Yes — Lock doesn't remove deadlock risk, it only adds tools (tryLock() with a timeout, interruptible acquisition) that can help avoid or break one. Acquiring the same two locks in inconsistent order across threads deadlocks whether they're synchronized blocks or explicit Locks.

🎯 Say this in the interview — the exact lines to land

"synchronized acquires and releases an intrinsic lock automatically, even across an exception, which is simplest for the common case. I'd reach for an explicit Lock like ReentrantLock when I need tryLock() with a timeout, interruptible locking, or a fairness policy that synchronized simply doesn't expose."

  • synchronized → automatic acquire and release, even on exception.
  • Lock → explicit lock()/unlock(), always inside a finally.
  • tryLock(timeout) / interruptible / fairness → only Lock offers these.
  • Forgetting unlock() in a finally → leaks the lock permanently — no safety net like synchronized has.
  • Deadlock risk → exists with both — Lock just gives more tools to manage it.
📖 Explanation ▾

synchronized acquires Java's built-in intrinsic monitor lock — every object already has one — and the JVM itself guarantees the lock is released when the block or method exits, whether that's a normal return or an exception propagating out. That guarantee is exactly why it's the right default: there's no code path where a mistake leaves the lock held forever.

Lock, most commonly ReentrantLock, trades that automatic safety for real capabilities synchronized doesn't have: tryLock() (optionally with a timeout) lets a thread give up instead of blocking forever, lockInterruptibly() lets a blocked thread respond to an interrupt, and the constructor's fairness flag can make waiting threads get served roughly in arrival order instead of whichever one the JVM happens to wake first. None of that is free — the code has to call unlock() itself, and the standard safe pattern is always lock() immediately followed by a try block with unlock() in its finally.

💻 See the code ▾
Java 
public synchronized void deposit(int amount) {
    balance += amount;  // ✅ lock released automatically, even if this threw
}

No finally anywhere — the JVM itself guarantees the monitor is released on the way out, success or failure.

Java 
private final Lock lock = new ReentrantLock();

public void deposit(int amount) {
    lock.lock();
    try {
        balance += amount;
    } finally {
        lock.unlock();     // ✅ must be here — releases even on an exception above
    }
}

The finally is doing the job synchronized does for free — skip it, and a thrown exception leaks the lock forever.

Java 
if (lock.tryLock(200, TimeUnit.MILLISECONDS)) { // ✅ give up instead of blocking forever
    try {
        balance += amount;
    } finally {
        lock.unlock();
    }
} else {
    // couldn't get it in time — back off, retry, or fail fast
}

synchronized has no equivalent to this — a thread blocked on an intrinsic lock waits indefinitely, with no way to give up.

🧭 Use Cases — recognize these when they happen to you ▾
1 A simple shared counter or cache, guarded only briefly

For a brief critical section — bump a counter, update a cached value — synchronized is enough, and simpler: no finally to remember, no extra fields to manage.

RememberShort, simple critical section → synchronized by default.
2 A high-contention resource where a thread shouldn't wait forever

Under heavy contention, a thread blocking indefinitely on synchronized can pile up and stall a whole request path. Lock.tryLock(timeout) lets it give up and back off (or fail fast) instead.

RememberCan't afford to wait forever → tryLock with a timeout.
3 unlock() is missing from a finally

An exception between lock() and a missing finally unlock leaves the lock held forever — every other thread waiting on it blocks permanently. A common interview trap: assuming a Lock behaves like synchronized and cleans up after itself.

RememberNo finally unlock() → a permanent leak, not a slow path.
🌍 Real-world example ▾

Your service's threads occasionally get stuck forever on the same lock, and a thread dump shows one thread holding it and never letting go. That's almost always a Lock.lock() call without an immediate try/finally, where an exception skipped the unlock() — leaking the lock permanently. A synchronized block can't leak this way, since it unlocks automatically no matter how it exits.
