Service Bus — decoupling "send it" from "process it"

"What is Service Bus, and what's it for?"

Why it matters ▾
  • Comes up any time an interview touches asynchronous or decoupled service-to-service communication.
  • Explains a real production pattern: a slow or temporarily-down worker doesn't take the front-end down with it.
  • A common opener before comparing Service Bus to Event Hubs or Queue Storage.
🔥 Easy interview recall

Queue → one consumer processes it

Topic/Subscription → many subscribers each get a copy

Think: the sender never waits on the receiver — Service Bus holds the message safely in between.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Service Bus is not for firehose telemetry. Streaming millions of sensor or click events through it is Event Hubs' job — Service Bus is optimized for reliable, ordered business-message delivery, not massive raw event throughput.

🔄 Likely Follow-up

"What happens to a message that keeps failing processing?" After it hits its max delivery count, Service Bus moves it to the dead-letter sub-queue instead of retrying forever.

🎯 Say this in the interview — the exact lines to land

"Service Bus decouples sending a message from processing it, reliably — the sender drops a message on a queue or topic and moves on, and a separate consumer picks it up whenever it's ready, with at-least-once delivery guaranteed."

  • Dead-lettering → the safety net: a message that keeps failing gets pulled aside after max delivery count instead of looping forever.
  • Queue → point-to-point, one consumer per message.
  • Topic/Subscription → pub/sub, every subscription gets its own copy.
  • Not for firehose events → that's Event Hubs' job; Service Bus optimizes for reliable delivery, not raw throughput.
📖 Explanation ▾

Service Bus is Azure's enterprise message broker — a durable middle layer that sits between apps and services so the sender doesn't have to wait for, or even know about, whoever eventually handles the message. It supports two delivery shapes: a queue for point-to-point work (one consumer per message) and a topic with subscriptions for publish/subscribe (every subscription gets its own copy of the message).

It guarantees at-least-once delivery — a message is never silently dropped, though a consumer can occasionally see the same message twice if it crashes right after processing but before confirming completion. Ordering, sessions (grouping related messages so they're handled in sequence), and transactions (batching several send/receive operations atomically) all build on that same durable queue.

💻 See the code ▾
C# 
ServiceBusClient client = new ServiceBusClient(connectionString);
ServiceBusSender sender = client.CreateSender("orders-queue");   // point-to-point queue

await sender.SendMessageAsync(new ServiceBusMessage("order-placed"));
// Checkout API returns immediately — a worker reads this later

The checkout API's job ends at SendMessageAsync — it never waits for the order to actually be processed.

🌍 Real-world example ▾

An order-processing system pushes new orders onto a Service Bus queue so the checkout API can respond to the customer instantly, while a separate worker processes each order reliably — even if that worker is temporarily down, the orders just wait safely in the queue until it's back.
