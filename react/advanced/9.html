Beyond one app — where React's model stops and the host starts

"How much of React's own mental model carries over to React Native, and what's fundamentally different?"

Why it matters ▾
  • Micro-frontend, monorepo, and React Native questions come up as soon as a team scales past one app — they check for real multi-app experience, not just React syntax.
  • Confusing "same React model" with "same environment" is a fast tell that someone's React Native exposure is shallow.
  • A common opener before an interviewer digs into how you'd structure a large, multi-team React codebase.
🔥 Easy interview recall

Components, props, state, and Hooks carry over to React Native almost entirely — there's just no DOM at all, a different host environment underneath.

Think: React Native tests whether you know what's core to React versus what's actually DOM-specific.

⚠️ Common Trap

"React Native is basically just React with different CSS" is not right. Components, props, state, and Hooks carry over almost entirely, but there is no DOM at all in React Native — it renders to native platform views through a completely different host environment, with no CSS at all (a JS-based styling API instead) and different navigation primitives entirely, not just a CSS syntax difference.

🔄 Likely Follow-up

"Monorepo vs. polyrepo for a large React codebase — what's the actual trade-off?" A monorepo buys shared tooling and versioning plus atomic cross-package changes — one PR updating a shared component and every consumer together, in the same commit; the cost is build/CI complexity at scale, which needs smart caching and incremental builds to stay fast as the repository grows.

🎯 Say this in the interview — the exact lines to land

"React's core model — components, props, state, Hooks — carries over almost entirely to React Native, but there's no DOM at all there: it renders to native platform views through a different host, with a different styling model and different navigation primitives."

  • Micro-frontends → Module Federation, build-time package composition, or iframes/Web Components as a last resort for stronger isolation.
  • Monorepo → shared tooling and atomic cross-package changes, at the cost of build/CI complexity that needs smart caching.
  • React Native → no DOM at all — same core model, a completely different host environment underneath.
  • Web Components interop → matters when the architecture genuinely needs that boundary — a design-system component inside a non-React host, or the reverse.
  • i18n → more a library/pattern choice than something React itself goes deep on — locale-aware routing, where strings live, formatting dates, numbers, and currency.
📖 Explanation ▾

A micro-frontend architecture composes multiple independently-deployed apps — each potentially its own React app, or a different framework entirely — into one experience. Three real approaches show up in practice: Module Federation loads remote bundles at runtime, build-time package composition publishes each app as a package and composes them at build time, and iframes or Web Components sit as a last resort for stronger isolation, at the cost of integration flexibility.

Composedat runtime — remotes load into the shellat build time — each app is a published packageat runtime, through a strong isolation boundary
Isolationshared runtime, weaker isolationshared build, weaker isolationstrong — a separate document/element boundary
Integration flexibilityhighhighlower — the trade-off for that isolation

A monorepo — one repository holding many packages — buys shared tooling and versioning, plus atomic cross-package changes: one PR can update a shared component and every consumer together, in the same commit. The cost is build and CI complexity as the repo grows, which needs smart caching and incremental builds to stay fast, not just more compute thrown at it.

Web Components interop matters when an architecture genuinely needs that boundary — embedding a design-system component into a non-React host app, or the reverse. Structuring for i18n is more a library and pattern-choice question than something React itself goes deep on: it touches locale-aware routing and URLs, where translated strings actually live, and formatting dates, numbers, and currency per locale.

🌍 Real-world example ▾

A stage actor's core craft — timing, delivery, presence — carries over almost entirely to film acting. But the actual medium is completely different: no live audience, a camera instead, and editing reshaping the performance afterward. The craft transfers; the environment it operates in doesn't — the same way React's model carries into React Native, but the DOM doesn't.
