application/problem+json — one error shape every client can parse

What should an API error response look like?

Why it matters ▾
📄 ProblemDetails
❗ ProblemEvery endpoint invents its own error JSON ({ "error": "…" }, { "message": "…" }, an HTML page, a stack trace), so every client writes custom parsing and may see internals.
✅ SolutionRFC 7807 defines one standard body — type, title, status, detail, instance — sent as application/problem+json, so errors look the same everywhere.
RecallProblemDetails = one standard shape for every API error.
🔥 Easy interview recall

type + title → what kind of problem

status + detail → this response, this case

Think: Exception → handler → problem+json Bad input → ValidationProblemDetails with an errors map

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Put ex.Message in detail so the client knows what went wrong." Exception text can carry connection strings, SQL and file paths — detail is for safe, human-readable text about this case, and the real exception belongs in the log.

🔄 Likely Follow-up

"How is a validation failure different from other problem details?" It's a ValidationProblemDetails — the same fields plus an errors dictionary (field name → messages), usually status 400; a [ApiController] returns it automatically when model validation fails.

🎯 Say this in the interview — the exact lines to land

"I return errors as RFC 7807 problem details — application/problem+json with type, title, status, detail and instance — so every client parses one shape. In ASP.NET Core I enable it with AddProblemDetails, turn unexpected exceptions into it in an IExceptionHandler, and validation failures come back as ValidationProblemDetails with an errors map. The body never contains stack traces or internals."

  • Standard fields → type, title, status, detail, instance.
  • application/problem+json → the media type that says "this is an error body".
  • AddProblemDetails + IExceptionHandler → one place turns exceptions into problem bodies.
  • ValidationProblemDetails → adds an errors map per field, status 400.
  • detail is safe text → never a stack trace or ex.Message.
📖 Explanation ▾

ProblemDetails is the .NET class for the standard error body in RFC 7807 (now updated by RFC 9457, same shape). The client reads the status, then the same few fields — no guessing which custom JSON this endpoint uses. It's sent with the media type application/problem+json, so a client can tell "this is an error body" from the header alone.

FieldWhat it saysChanges per occurrence?
typea URI naming the kind of problemno — same for the same kind
titleshort human summary of that kindno
statusthe HTTP status codeno
detailwhat went wrong in this caseyes
instancea URI for this occurrenceyes

In ASP.NET Core, AddProblemDetails() turns on the writer, and an IExceptionHandler (.NET 8+) catches unexpected exceptions in one place and answers with a generic 500 problem. With [ApiController], an invalid model already returns a ValidationProblemDetails, and bare error results like NotFound() are wrapped in a problem body too. For the exception middleware itself, see Global Exception Handling.

💻 See the code ▾
C# 
builder.Services.AddProblemDetails();                        // ✅ enables the writer
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
var app = builder.Build();
app.UseExceptionHandler();                                    // ✅ unhandled exceptions → handler

Three lines wire it up — the handler decides what the client sees.

C# 
public class GlobalExceptionHandler(IProblemDetailsService problems) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext ctx, Exception ex, CancellationToken ct)
    {
        // log ex here — it never goes in the body
        ctx.Response.StatusCode = 500;
        return await problems.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = ctx,
            ProblemDetails = new ProblemDetails { Status = 500, Title = "Something went wrong" }   // ✅ generic
        });
    }
}

The body is generic on purpose — the stack trace stays in the log, not in detail.

C# 
return Problem(
    title: "Item is out of stock",
    detail: "Only 2 of 5 requested units are left.",
    statusCode: 409);   // ✅ problem+json, status 409

Inside a controller, Problem(...) builds the same body for an expected business error.

JSON 
{
  "type": "https://example.com/problems/out-of-stock",
  "title": "Item is out of stock",
  "status": 409,
  "detail": "Only 2 of 5 requested units are left.",
  "instance": "/orders/123"
}

What the client receives — five predictable fields (a validation failure adds an errors map).

🧭 Use Cases — recognize these when they happen to you ▾
1 A client posts a request body that fails validation

With [ApiController], the framework returns a ValidationProblemDetails on its own — the standard fields plus an errors dictionary keyed by field name, so a UI can show each message beside its input.

RememberInvalid model → 400 + errors map.
2 An unexpected exception escapes in production

One IExceptionHandler catches it, logs the real exception, and returns a generic 500 problem — every endpoint fails in the same shape without its own try/catch.

RememberLog the exception, send a generic problem.
3 A team copies ex.Message into detail

Exception text can name a table, a server or a file path. The standard shape doesn't fix that — what you put in detail is still your job. A classic review catch.

Rememberdetail is for safe text only.
🌍 Real-world example ▾

A mobile app calls five endpoints written by three teams, and each returns errors differently — the app needs three parsers. Agreeing on application/problem+json lets it read status and title the same way everywhere and show errors next to form fields.
