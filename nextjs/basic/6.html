<Link> vs. <a> — instant navigation, or a full reload?

"Why use <Link> instead of a plain <a> tag for internal navigation?"

Why it matters ▾
🔗 <Link>
❗ ProblemA full page reload on every internal click throws away client-side state and feels noticeably slower than it needs to.
✅ Solutionnext/link's <Link> performs client-side navigation — no full reload, client state outside what's unmounting is preserved — and automatically prefetches the linked route's content when it scrolls into view in production.
RecallLink = client-side nav + auto-prefetch, feels instant.
🌐 <a>
❗ ProblemSometimes a genuine full browser navigation is the right outcome — e.g. leaving the app entirely — and client-side routing isn't the tool for that.
✅ SolutionA plain <a href> triggers a full browser page load every time — correct for leaving the app, but a real regression if used for in-app navigation just because it's simpler to write.
Recalla = full page load every time, no matter the destination.
🔥 Easy interview recall

<Link> → client-side, prefetches

<a> → full reload, every time

Think: <Link> stays inside the app. <a> leaves it — that's exactly when you actually want it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Using a plain <a> for in-app navigation "because it's simpler." It loses client-side routing's speed and discards all client-side state on every navigation — a real regression from what the App Router is built to do.

🔄 Likely Follow-up

"When would a plain <a> actually be the right choice in a Next.js app?" Linking to an external site, or to a route genuinely outside the app's own routing (a different domain/subdomain) — <Link> is specifically for internal navigation.

🎯 Say this in the interview — the exact lines to land

"<Link> from next/link navigates client-side — no full reload — and prefetches the linked route in advance, so the transition feels instant. A plain <a href> always triggers a full browser page load, which is only the right choice for a destination genuinely outside the app."

  • <Link> → client-side navigation, auto-prefetches in production.
  • <a> → full reload every time, right only for external destinations.
  • Internal route → always <Link>, never a plain <a>.
📖 Explanation ▾

<Link> intercepts the click and hands navigation to Next.js's own client-side router instead of the browser. The new route's content is already fetched ahead of time — in production, as soon as the link scrolls into view — so the swap feels instant and nothing outside the changing part of the page gets torn down.

<a> is the browser's own, unmodified navigation — it asks the browser to throw away the current page entirely and load a brand-new one. That's exactly the right behavior for leaving the app; it's the wrong one for staying inside it.

Full page reload?❌ no✅ yes, always
Prefetches ahead of time?✅ yes (production)❌ no
Preserves client state?✅ yes, outside what unmounts❌ no, all lost

💻 See the code ▾
JavaScript 
import Link from "next/link";

<Link href="/about">About</Link>   // ✅ client-side, prefetched

Internal route → always <Link>, never a plain <a>.

JavaScript 
<a href="https://example.com">Visit example.com</a>   // ✅ leaving the app — plain <a> is correct here

External destination → a plain <a> is the right tool, not a regression.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your site's main nav menu links between its own pages

This is the #1 scenario you'll actually run into: every item in a nav bar that points somewhere inside the same app is a job for <Link>, no exceptions.

RememberNav menu linking your own pages → Link, every item.
2 A footer link out to a different company's site or your GitHub repo

You're leaving the app entirely, so there's nothing for client-side routing to do — a plain <a> (often with target="_blank") is the genuinely correct choice here.

RememberLeaving the app → plain a, not a workaround.
3 A dropdown item was written as a plain <a> "to keep it simple" and now feels slow

Swapping it for <Link href="/settings"> fixes it immediately — the "feels slow" complaint is almost always a plain <a> hiding on an internal route.

RememberInternal link feels slow → check for a plain a tag first.
🌍 Real-world example ▾

Walking to another room vs. leaving the building. Moving between rooms in the same building (<Link>) doesn't require going back outside and through security again. Actually leaving the building (<a>) does — and that's the right process specifically because you're going somewhere else entirely.
