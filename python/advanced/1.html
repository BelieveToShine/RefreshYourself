Classes are objects too — that's what makes "everything is an object" a mechanism, not a slogan

What does "classes are objects too" actually mean? What is __dict__? What is attribute lookup, mechanically?

Why it matters ▾
🏛️ Class is an object
❗ ProblemIf a class were only compile-time syntax, you could not pass it around, inspect it, or build one at runtime.
✅ SolutionA class is a real object — an instance of type by default — so type(MyClass) is type.
RecallA class is an instance of type.
🔎 Attribute lookup
❗ ProblemWithout a known order, it is unclear whether obj.attr finds an instance value or a class value of the same name.
✅ SolutionPython checks the instance __dict__ first, then the class __dict__ and up the MRO, so instance attributes shadow class ones.

🔥 Easy interview recall

A class → an instance of type

obj.attr → instance __dict__ first, then class __dict__

Think: type(MyClass) is type — a class is data too, not some exception to "everything is an object."

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming attribute lookup only ever checks the instance. Methods and class-level attributes live in the class's __dict__ (and up its MRO), not the instance's — that's exactly why you can call a method that never shows up when you print instance.__dict__.

🔄 Likely Follow-up

"How are classes actually created?" The class statement runs its body to build a namespace dict, then calls the metaclass (type by default) with the class's name, its bases, and that namespace — the exact same mechanism type(name, bases, namespace) uses to build a class directly, at runtime.

🎯 Say this in the interview — the exact lines to land

"A class is itself an instance of type — and attribute lookup falls through from the instance's __dict__ to the class's (and its MRO's) when the instance doesn't have it."

  • type(MyClass) → is type, the default metaclass — a class is an object too, not a special exception.
  • obj.attr → checks instance __dict__ first, then falls through to the class's __dict__ (and its MRO).
  • Methods live in the class's __dict__, never the instance's — that's why they're found on the fallthrough, not the first check.
  • This per-instance __dict__ is why __slots__ saves memory — it skips creating that dict entirely (see the Memory Management page).
  • type(name, bases, namespace) → builds a class dynamically, at runtime — the same mechanism the class statement itself calls under the hood.
📖 Explanation ▾

In Python, a class is itself an instance of a metaclass — by default, type. That's why type(MyClass) evaluates to type: the class object was built by calling type, exactly the way calling MyClass() builds an instance by calling the class. Because a class is a real object, it can be passed around, inspected, stored in a variable, or built dynamically at runtime — it's not a special compile-time-only construct.

Most instances carry their own __dict__, a plain dict holding just that instance's own attributes. A class has its own separate __dict__ too, holding its methods and class-level attributes. obj.attr resolves, roughly in order, by checking the instance's __dict__ first, then falling through to the class's __dict__ (and up the MRO chain for anything inherited). That order is exactly why an instance attribute shadows a class attribute of the same name, and why a method — which lives in the class's __dict__, never the instance's — is still found: it's picked up on that second step.

This same per-instance __dict__ is also the reason __slots__ (its own page) can save real memory: declaring __slots__ tells Python to skip creating that dict altogether and use fixed slots instead.

💻 See the code ▾
Python 
class Dog:
    def bark(self):
        return "Woof"

d = Dog()
d.name = "Rex"  # sets an instance attribute

print(d.__dict__)       # {'name': 'Rex'} — no 'bark' here
print(type(Dog))       # <class 'type'> — Dog is an instance of type

bark never shows up in d.__dict__ because it isn't an instance attribute — it lives in Dog.__dict__, found on the fallthrough step, not the first one.

Python 
# building the SAME class, but with type() directly instead of "class"
def bark(self):
    return "Woof"

Dog2 = type("Dog2", (), {"bark": bark})  # name, bases, namespace
print(Dog2().bark())  # "Woof" — built at runtime, no "class" keyword at all

type(name, bases, namespace) is the exact mechanism the class statement calls under the hood — calling it directly builds a class dynamically, with no class keyword involved.

🌍 Real-world example ▾

A plugin system that reads a config file listing plugin names and behaviors, then calls type(name, bases, namespace) directly to build one class per plugin at startup — no class statement written per plugin, because the set of plugins isn't known until the config is read. This only works because a class really is just an object that type can construct on demand, the same as any other object.
