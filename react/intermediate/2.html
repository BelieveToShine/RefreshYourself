useLayoutEffect — the one that blocks paint on purpose

"What's the timing difference between useEffect and useLayoutEffect, and when do you actually need the layout one?"

Why it matters ▾
  • A tooltip, dropdown, or popover that visibly "jumps" into place on first render is almost always a symptom of measuring the DOM in the wrong hook.
  • Comes up whenever you need to read a rendered element's size/position and adjust it before the user sees the wrong frame.
  • The "why does my effect fire twice" question is one of the most common early-React confusions, and interviewers use it to check you know it's a deliberate dev-only check, not a bug.
🔥 Easy interview recall

useEffect → after paint, async

useLayoutEffect → before paint, sync

Think: reach for useLayoutEffect only to measure or adjust the DOM before the user sees it — a flicker you can see is exactly the case it exists for.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

useLayoutEffect is not just a different name for useEffect. They run at genuinely different times relative to the browser's paint — useEffect is asynchronous and fires after paint, while useLayoutEffect is synchronous and fires before paint, which can visibly block rendering if overused, so it's reserved for measure-then-adjust cases that would otherwise flicker.

🔄 Likely Follow-up

"Why does my effect fire twice in development?" React 18+'s StrictMode deliberately double-invokes effects (mount → cleanup → mount) in development only, to help surface effects that aren't cleaning up after themselves properly — it doesn't happen in a production build.

🎯 Say this in the interview — the exact lines to land

"useEffect runs asynchronously, after the browser has already painted, so it's the safe default. useLayoutEffect runs synchronously, before paint — I only reach for it when I need to measure or adjust the DOM before the user ever sees the unadjusted frame."

  • useEffect → after paint, async, the default choice for most side effects.
  • useLayoutEffect → before paint, sync, only for measure-then-adjust DOM work that would otherwise flicker.
  • useInsertionEffect → runs even earlier, for CSS-in-JS library authors injecting styles — rarely used directly.
  • StrictMode → double-invokes effects in dev only (mount → cleanup → mount) to catch missing cleanup.
📖 Explanation ▾

useEffect is scheduled to run after React has committed the update and the browser has already painted it to the screen. That's why it's asynchronous relative to painting — it never delays what the user sees, which is exactly why it's the right default for data fetching, subscriptions, and most side effects.

useLayoutEffect runs at the same point in the commit but before the browser paints — synchronously, blocking that paint until it finishes. Reach for it specifically when you need to read something about the just-rendered DOM (its size, its position) and adjust it — like repositioning a tooltip based on its own rendered height — so the user only ever sees the corrected frame, never a flash of the wrong one. A third, rarer variant, useInsertionEffect, runs even earlier than useLayoutEffect; it exists specifically for CSS-in-JS library authors to inject styles before layout is read, and an application author almost never calls it directly.

Separately, React 18+'s StrictMode (development builds only) deliberately runs every effect's mount → cleanup → mount sequence twice, so a missing or broken cleanup function shows up immediately instead of silently leaking later. This doubling never happens in a production build — seeing it in dev is expected, not a bug.

💻 See the code ▾
JSX 
function Tooltip({ targetRef }) {
  const tipRef = useRef(null);
  const [top, setTop] = useState(0);

  useLayoutEffect(() => {
    // Runs BEFORE the browser paints this frame
    const { height } = tipRef.current.getBoundingClientRect();
    const targetTop = targetRef.current.getBoundingClientRect().top;
    setTop(targetTop - height);   // ✅ corrected before anything is shown
  }, [targetRef]);

  return <div ref={tipRef} style={{ position: "absolute", top }}>Tip</div>;
}

The tooltip's position is measured and fixed before the browser ever paints the wrong spot — no flicker.

JSX 
useEffect(() => {
  // Same math, wrong hook — this runs AFTER the browser already painted
  const { height } = tipRef.current.getBoundingClientRect();
  setTop(targetTop - height);
  // ❌ the user already saw one wrong-position frame before this fires
}, [targetRef]);

Identical logic, just in useEffect — the DOM read/adjust happens one frame too late to avoid the flicker.

🌍 Real-world example ▾

Adjusting a picture frame before opening the curtains, versus after. useLayoutEffect is straightening the frame while the curtains — the browser's paint — are still closed, so the audience never sees it crooked. useEffect only straightens it after the curtains are already open and people are looking — it still ends up straight, but everyone caught the crooked moment first.
