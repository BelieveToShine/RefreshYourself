One SaaS app, many tenants — path or subdomain?

"How would you structure routes for a SaaS app serving many different customer tenants?"

Why it matters ▾
🧵 Path-Based [tenant]/dashboard
❗ ProblemHard-coding tenant-specific logic scattered across many individual route files doesn't scale, and the team still needs a straightforward way to test a specific tenant locally.
✅ SolutionA dynamic top-level segment ([tenant]/dashboard) reads the tenant straight from the URL path — simple to set up and test locally, with no DNS or certificate work needed.
RecallPath-based tenancy = tenant in the URL path, simplest to stand up.
🌐 Subdomain-Based tenant.example.com
❗ ProblemA path-based URL doesn't give each customer what feels like their own real address, and some SaaS products want a genuine per-tenant domain.
✅ SolutionMiddleware resolves the subdomain (or a custom domain via a stored domain→tenant mapping) and rewrites internally to a shared route structure, passing the tenant down through a header or cookie — needs DNS and wildcard-certificate infrastructure.
RecallSubdomain tenancy feels native per customer, at the cost of DNS/certificate infrastructure.
🔥 Easy interview recall

Path-based → simplest, test locally, no DNS

Subdomain-based → native per-tenant, needs DNS/certs

Think: resolve the tenant once in Middleware, pass it down consistently — never scatter tenant logic across individual route files.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Hard-coding tenant-specific logic scattered across many individual route files. The scalable approach resolves the tenant once in Middleware and passes it down consistently through a header or cookie — not a fresh "which tenant is this" check copied into every route.

🔄 Likely Follow-up

"How would custom domains per tenant, not just subdomains, change this?" Middleware would need to map the incoming domain to a tenant ID — typically via a lookup against a stored domain→tenant mapping — then proceed the same way as the subdomain approach from there.

🎯 Say this in the interview — the exact lines to land

"I'd resolve the tenant in one place — either a dynamic [tenant] URL segment or Middleware reading the subdomain — and pass it down consistently from there, rather than scattering tenant checks across individual route files. Path-based is simpler to set up and test locally; subdomain-based feels more native per customer but needs DNS and wildcard-certificate infrastructure."

  • Path-based [tenant]/dashboard → simplest to set up and test locally, no DNS needed.
  • Subdomain-based tenant.example.com → resolved in Middleware, needs DNS/wildcard certificates.
  • Route Groups → separate a shared marketing/auth layout from the tenant dashboard layout cleanly.
  • Resolve the tenant → once, in Middleware — never scattered across individual routes.
📖 Explanation ▾

The path-based approach is the plainest: a dynamic top-level segment like [tenant] captures the tenant identifier directly from the URL, and every route underneath it reads that same params.tenant value — no extra infrastructure, and any tenant can be tested locally just by changing the URL.

The subdomain-based approach moves tenant resolution into Middleware, which runs before the route itself: it reads the incoming hostname, figures out which tenant that subdomain belongs to, and rewrites the request internally to the same shared route structure — passing the resolved tenant down through a header or cookie so the actual page/route code doesn't need to know whether it arrived via subdomain or path. This needs real DNS wildcard setup (*.example.com) and a matching wildcard certificate, which path-based tenancy never has to deal with.

Either way, Route Groups (a folder in parentheses, like (marketing)) let a shared public layout — a marketing site, a login page — sit cleanly alongside the tenant-specific dashboard layout, without either one leaking into the other's folder structure.

💻 See the code ▾
JSX 
// app/[tenant]/dashboard/page.js
export default function Dashboard({ params }) {
  const { tenant } = params; // ✅ "acme" — straight from the URL path
  return <p>Dashboard for {tenant}</p>;
}

No Middleware needed — the tenant is just a normal dynamic route param.

JS 
// middleware.js
export function middleware(request) {
  const host = request.headers.get('host') || '';
  const tenant = host.split('.')[0]; // ✅ "acme" from acme.example.com

  const url = request.nextUrl.clone();
  url.pathname = `/${tenant}${url.pathname}`; // ✅ rewrite to the shared route structure
  return NextResponse.rewrite(url);
}

The rewrite happens internally — the URL the browser shows stays acme.example.com, but the app serves it through the same shared [tenant] route underneath.

🌍 Real-world example ▾

A B2B SaaS product is adding its first few customers and needs to decide on a route structure before onboarding scales past a handful of tenants. Starting with a path-based [tenant]/dashboard segment ships fastest and needs no DNS infrastructure; if customers later expect their own subdomain, Middleware can be added to resolve and rewrite without changing the underlying shared route structure at all.
