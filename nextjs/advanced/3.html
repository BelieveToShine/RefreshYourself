Same fetch(url), opposite default — depending on which Next.js you're on

"What changed about fetch() caching defaults in Next.js 15?"

Why it matters ▾
🔀 The default flipped
❗ ProblemA developer who learned Next.js on 14 writes a bare fetch(url) expecting it to be cached — in 15 that same line is fresh on every request, and the "bug" is actually the new default working as designed.
✅ SolutionNext.js 14 cached fetch() by default; starting in Next.js 15, you opt in explicitly with {'{'}cache:'force-cache'{'}'} or a revalidate value — an unconfigured fetch is fresh.
Recall14 = cached unless you opt out. 15 = fresh unless you opt in.
🔥 Easy interview recall

Next.js 14 → bare fetch() is cached by default

Next.js 15 → bare fetch() is fresh by default

Think: same line of code, opposite behavior — always name the version when you claim a Next.js caching default.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Next.js fetch() is cached by default" is not always true. That's only accurate for Next.js 14 and earlier — this exact default flipped in Next.js 15, so any caching claim needs the version attached.

🔄 Likely Follow-up

"Why did the Next.js team make this change?" To reduce a real class of production bugs where developers were unexpectedly seeing stale data because they didn't realize caching was on by default — explicit opt-in is more predictable, even if slightly more verbose to configure.

🎯 Say this in the interview — the exact lines to land

"In Next.js 14, fetch() requests were cached by default unless you opted out. Starting in Next.js 15, that flipped — fetch() is not cached by default, and you opt in explicitly with cache:'force-cache' or a revalidate value."

  • Next.js 14 → cached by default, opt out explicitly.
  • Next.js 15 → fresh by default, opt in explicitly.
  • Any caching claim → name the version, this default is version-specific.
  • Reason for the change → fewer surprise-stale-data bugs in production.
📖 Explanation ▾

In Next.js 14 and earlier, a plain fetch(url) inside a Server Component behaved like {'{'}cache:'force-cache'{'}'} unless you told it otherwise — the framework assumed you wanted the result reused across requests, and developers had to actively add {'{'}cache:'no-store'{'}'} or a short revalidate to get fresh data.

Starting in Next.js 15, that default reversed: an unconfigured fetch() is treated as effectively no-store — always fresh, every request. Getting the old caching behavior back now means adding {'{'}cache:'force-cache'{'}'} or a revalidate number explicitly. Nothing about the fetch() call's syntax changed — only what the framework assumes when you don't say anything.

This is exactly the kind of fact that ages badly if memorized without its version attached — the correct statement always names which Next.js major version it describes.

💻 See the code ▾
JavaScript 
// Next.js 14 — cached by default
const res = await fetch('https://api.example.com/posts');
// ✅ same as { cache: 'force-cache' } — no new request until revalidated

On 14, this exact line keeps serving the same result until a revalidate window passes or you clear it — nothing in the call says so explicitly.

JavaScript 
// Next.js 15 — NOT cached by default
const res = await fetch('https://api.example.com/posts');
// ⚠️ fresh every request — identical code, opposite behavior

// to get 14's old caching back on 15, opt in explicitly:
const cached = await fetch('https://api.example.com/posts', {
  cache: 'force-cache', // ✅ explicit opt-in
});

The same bare call that was cached on 14 is fresh on 15 — the fix is an explicit cache option, not a different API.

🧭 Use Cases — recognize these when they happen to you ▾
1 A project just upgraded from Next.js 14 to 15 and data looks "too fresh"

This is the default change, not a bug — every previously-cached fetch() now hits the network/database every time unless it's explicitly opted back into caching.

RememberUpgrade to 15 → re-add cache:'force-cache' anywhere you still want caching.
2 You're writing fresh Next.js 15 code and want the old caching behavior back

Add {'{'}cache:'force-cache'{'}'} or a revalidate number to any fetch() you actually want cached — on 15 it's always an explicit choice now.

RememberOn 15, caching is a choice you write down, not a default you inherit.
🌍 Real-world example ▾

A team upgrades a dashboard from Next.js 14 to 15 and a code review flags a sudden spike in database calls. Nothing in the code changed — every bare fetch() that silently relied on 14's cached-by-default behavior is now fresh on every request. The fix is to go through those calls and add explicit {'{'}cache:'force-cache'{'}'} or a revalidate value wherever the old caching behavior was actually wanted.
