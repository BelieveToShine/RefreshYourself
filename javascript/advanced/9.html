Web Workers — copied, not shared

"What is a Web Worker, and how does it communicate with the main thread?"

Why it matters ▾
  • It's the actual mechanism for keeping heavy computation from freezing the UI — not a library trick, a real separate thread the browser gives you.
  • Useful to know whenever an interview touches performance, large data processing, or "the page feels stuck while I'm working."
  • A natural follow-up after any question about the main thread staying free to render.
🔥 Easy interview recall

Web Worker → a separate thread, no DOM access

Talk to it → only via postMessage

Data sent → copied, not shared

Think: a worker is a separate island — the only way anything reaches it is a message in a bottle, and what arrives is a copy, never the original.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

postMessage does not pass the object by reference like a normal function call would. The data is copied through the structured clone algorithm — the worker gets its own independent object, so mutating it on either side never affects the other.

🔄 Likely Follow-up

"Is copying large data expensive — is there a way around it?" Yes — certain types like ArrayBuffer can be marked as transferable. Instead of copying, ownership moves to the worker and the main thread's reference becomes unusable, which avoids the copy cost entirely for large binary data.

🎯 Say this in the interview — the exact lines to land

"A Web Worker runs JavaScript on a completely separate thread with no access to the DOM, so it's used to offload genuinely CPU-heavy work off the main thread. It only talks to the main thread through postMessage, and the data sent isn't shared — it's copied via the structured clone algorithm, so each side has its own independent object. Transferable objects like ArrayBuffer are the exception: ownership moves instead of copying, so large data doesn't need to be duplicated."

  • Worker → separate thread, no DOM, its own global scope.
  • Why use one → offload heavy synchronous work so the main thread stays free to render and respond to input.
  • postMessage → the only communication channel — asynchronous, no shared memory.
  • Structured clone → data is copied, never passed by reference — unlike a normal function call with the same object.
  • Transferable objects → ownership moves instead of copying — the sender's reference becomes unusable afterward.
📖 Explanation ▾

A Web Worker runs JavaScript on a completely separate thread from the page's main thread. It has no access to the DOM and no access to most main-thread-only APIs — it gets its own global scope instead of the window's. That isolation is the whole point: it exists so genuinely CPU-heavy synchronous work — a heavy computation, parsing a large chunk of data — can run without blocking the thread that has to keep rendering and responding to clicks and keystrokes. This is the same "main thread must stay free" idea behind Performance & Rendering, applied by moving the heavy work off that thread entirely instead of just chunking it.

The main thread and a worker only ever talk through postMessage — asynchronous message passing, not shared memory. Here's the part that's easy to get wrong: a normal function call passes an object by reference — the callee gets the same object, and a mutation on one side is visible on the other. postMessage does not do this. The data is run through the structured clone algorithm, which produces a completely independent copy on the receiving side. Mutate the copy in the worker, and the main thread's original object is untouched, and vice versa.

The one deliberate exception is a transferable object, like an ArrayBuffer. Instead of cloning it, ownership is transferred — the worker becomes the new owner, and the sending side's reference is neutered (accessing it afterward throws or reads as empty). That's how large binary data can cross into a worker without paying the cost of copying it.

💻 See the code ▾
JavaScript 
// main.js
const worker = new Worker("worker.js");
const data = { count: 1000000 };

worker.postMessage(data); // data is CLONED, not shared
data.count = 1; // worker's copy is unaffected

worker.onmessage = (e) => {
  console.log(e.data); // result copied back from the worker
};

Changing data after sending it never changes what the worker received — it already has its own independent copy.

JavaScript 
// Transferring an ArrayBuffer instead of copying it
const buffer = new ArrayBuffer(8 * 1024 * 1024);
worker.postMessage(buffer, [buffer]); // ✅ ownership moves to the worker

console.log(buffer.byteLength); // 0 — this side's reference is now unusable

The second argument's array lists which objects to transfer instead of clone — after this call, buffer belongs to the worker alone.

🌍 Real-world example ▾

Think of it like mailing a photocopy of a document to another office, not the original. They can mark up their copy however they want — your original on your desk stays exactly as it was. If it's an important original you don't need anymore, you can instead hand it over for real (a transfer) — but then it's genuinely gone from your desk, not just copied.
