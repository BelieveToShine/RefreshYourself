dotnet run to your first line of code — what actually happens in between?

"Walk me through what happens from dotnet run to your first line of code executing."

Why it matters ▾
  • A classic opening question — it separates "I can run an app" from "I understand the hosting model underneath it."
  • Comes up the moment you're debugging a startup crash, containerizing an app, or configuring ports and HTTPS.
  • Tests whether you conflate two different things: your app and the HTTP server underneath it.
🔥 Easy interview recall

Startup = "build the host, then hand it to Kestrel."

Think: dotnet run → builder wires config, DI, logging app.Run() → starts the host, then Kestrel starts listening

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Kestrel alone is not "ready to face the internet." It technically can accept connections directly, but the near-universal real-world setup fronts it with a reverse proxy — the separate Kestrel & Reverse Proxies page covers why in depth.

🔄 Likely Follow-up

"What happens if something throws during startup, before Kestrel even starts listening?" The host fails to start — you get a startup exception in the console or logs, and no request is ever served. That's different from a runtime exception during a request, which exception-handling middleware can still catch.

🎯 Say this in the interview — the exact lines to land

"dotnet run loads and JITs Program.cs. WebApplication.CreateBuilder(args) wires up configuration, dependency injection, and logging before anything runs. app.Run() then starts the Generic Host, which starts Kestrel listening — Kestrel is the HTTP server my app sits on top of, not the app itself."

  • WebApplicationBuilder → config, DI, logging wired before a single request exists.
  • app.Run() → starts the Generic Host — the thing that keeps the process alive.
  • Kestrel → the embedded HTTP server, not the app — it turns raw bytes into an HttpContext.
  • In production, Kestrel is almost always fronted by a reverse proxy, not exposed directly.
📖 Explanation ▾

Running dotnet run (or launching the published exe) starts the CLR, which loads and JITs your code, then calls into Program.cs. The first real step is WebApplication.CreateBuilder(args) — it builds a WebApplicationBuilder already carrying default configuration sources, a logging setup, and an empty dependency injection container. Everything you add after that — builder.Services.Add... for services, app.Use... for middleware — is registration, not execution; none of it runs a single request yet.

app.Run() is what actually starts things: it hands control to the Generic Host, the IHost abstraction ASP.NET Core shares with plain console worker services. The Generic Host is what gives an app configuration, DI, logging, and lifetime management wired the same consistent way, whether it's a web app or a background worker — nobody has to reinvent that wiring per project type.

Starting the host is also what starts Kestrel listening on its configured ports. Kestrel is the actual HTTP server embedded inside your app — it parses raw HTTP and produces the HttpContext your code works with — it is not "the app," it's the network layer the app sits on top of. Once a request lands, the host moves through a small set of named lifetime stages — Started, then eventually Stopping, then Stopped — for the life of the process; hooking application code into those specific moments is its own separate topic.

💻 See the code ▾
C# 
var builder = WebApplication.CreateBuilder(args);   // config, DI, logging wired here

builder.Services.AddControllers();                       // register services — not running yet

var app = builder.Build();
app.UseHttpsRedirection();                                // register middleware — still not running
app.MapControllers();

app.Run();   // ✅ starts the Generic Host → Kestrel starts listening

Everything before app.Run() only configures the app — nothing is listening for a request yet.

C# 
var connString = builder.Configuration.GetConnectionString("Default")
    ?? throw new InvalidOperationException("Missing connection string");  // 🐛 thrown while still configuring

var app = builder.Build();   // ❌ never reached if the line above throws
app.Run();                    // Kestrel never even starts listening

A startup exception stops the host before Kestrel ever listens — a request-time exception is a completely different failure, and middleware can catch that one.

🌍 Real-world example ▾

Your container exits immediately after every deploy, before a single request could ever reach it. That's almost always a startup-time failure — a bad connection string, a DI registration that can't resolve — thrown somewhere before app.Run() gets a chance to start Kestrel. Check the startup logs first; nothing in a controller has run yet, so the bug can't be there.
