SignalR vs. WebSockets vs. SSE — is SignalR just WebSockets?

"How would you push real-time updates to browsers from ASP.NET Core?"

Why it matters ▾
🧠 SignalR
❗ ProblemHand-rolling real-time means writing transports, reconnects and group handling yourself.
✅ SolutionSignalR gives hubs, groups and transport fallback out of the box.
RecallSignalR = the real-time toolkit.
🔌 WebSockets
❗ ProblemPlain HTTP request/response can't push, and polling wastes calls and adds delay.
✅ SolutionA WebSocket is one long-lived two-way connection — but it is only the pipe; messaging on top is yours.
RecallWebSockets = the raw two-way pipe.
📡 SSE
❗ ProblemOften you only need server-to-client updates, like a feed or a progress bar.
✅ SolutionServer-Sent Events stream text one way over plain HTTP, and the browser's EventSource reconnects on its own.
RecallSSE = a simple one-way stream.
🔥 Easy interview recall

Push options: SignalR toolkit, WebSockets raw pipe, SSE one-way.

Think: SignalR → two-way, hubs and groups, falls back if needed WebSockets → two-way pipe, you build everything on top SSE → server to client only, simplest

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"SignalR is just WebSockets." It uses WebSockets when it can, but negotiates down to Server-Sent Events or long polling when it can't — and adds hubs, groups and reconnection support on top.

🔄 Likely Follow-up

"What changes when you run two instances?" A client is connected to one server, so a message sent from the other server wouldn't reach it. A backplane — for example Redis — or Azure SignalR Service shares messages across servers.

🎯 Say this in the interview — the exact lines to land

"For a rich two-way feature I'd use SignalR: it uses WebSockets when it can, falls back to Server-Sent Events or long polling, and gives me hubs and groups. If I only need one-way updates, SSE is enough, and for an occasional refresh plain polling is fine. With more than one server I need a backplane such as Redis, or Azure SignalR Service."

  • SignalR → WebSockets first, then SSE, then long polling.
  • A hub → groups and targeted sends, not just broadcast.
  • Raw WebSockets → you build messaging, reconnects and groups yourself.
  • SSE → server to client only — text over plain HTTP.
  • Many servers → you need a backplane to share messages.
📖 Explanation ▾

Pick the simplest tool that fits. Polling asks "anything new?" on a timer — simple, but wasteful and delayed. SSE is a one-way text stream from server to browser. WebSockets give a two-way connection but only a pipe. SignalR sits on top and adds the application layer.

In SignalR you write a Hub class; clients call its methods and the server calls client methods back. Clients.Group(name) targets a group, and connections are added to groups with Groups.AddToGroupAsync. Each client negotiates a transport — WebSockets if both sides support it, otherwise Server-Sent Events, then long polling. Because it runs on ASP.NET Core's pipeline, middleware such as authentication applies to the connection too.

Connections are tied to the server that accepted them. With several instances, a message sent on server A won't reach a client connected to server B unless the servers share messages through a backplane (Redis) or you use Azure SignalR Service. Hosting details such as sticky sessions are worth checking in the current docs. For the Web API side of async and security, see Async APIs & API Security.

💻 See the code ▾
C# 
builder.Services.AddSignalR();

var app = builder.Build();
app.MapHub<ChatHub>("/chat");   // clients connect here

public class ChatHub : Hub
{
    public Task Join(string room) =>
        Groups.AddToGroupAsync(Context.ConnectionId, room);   // put this connection in a group

    public Task Send(string room, string text) =>
        Clients.Group(room).SendAsync("Received", text);      // ✅ only that group hears it
}

A hub gives groups and targeted sends — none of this exists on a bare WebSocket.

C# 
builder.Services.AddSignalR()
    .AddStackExchangeRedis("localhost:6379");   // ✅ servers share messages through Redis

With more than one server, add a backplane so every instance reaches every client.

🌍 Real-world example ▾

A delivery tracker. "Out for delivery" going to one customer's browser is a one-way feed, so SSE would do. A support chat with typing indicators needs two-way groups, so SignalR. A page that refreshes a report once a minute can simply poll.
