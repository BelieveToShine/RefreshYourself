🔥 Next.js · Basic · Must Know

CSR, SSR, SSG, ISR — four answers to one question: when does the HTML get built?

"What are the four main rendering strategies in Next.js, at a plain-language level?"

Why it matters ▾
🧩 CSR / SSR
❗ ProblemSome pages are unique per visitor (a dashboard, a logged-in account page) — there's no single HTML you could build in advance and hand to everyone.
✅ SolutionCSR builds the page in the browser with JS; SSR builds full HTML on the server, fresh, for every single request — both compute the real page on demand, not ahead of time.
RecallCSR/SSR = built fresh, every time someone asks.
📦 SSG / ISR
❗ ProblemRebuilding the exact same HTML from scratch for every visitor, when the content doesn't actually change per-request, wastes server work and is slower than it needs to be.
✅ SolutionSSG builds the HTML once, at build time, and reuses it for everyone. ISR does the same, but automatically refreshes that cached HTML in the background after a set time.
RecallSSG/ISR = built once (or periodically), served instantly from cache.
🔥 Easy interview recall

CSR → blank shell, JS fills it in

SSR → full HTML, every request

SSG → built once, reused for all

ISR → cached, refreshed periodically

Think: this is picked per-route (even per-fetch-call) — not one setting for the whole app.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Treating CSR/SSR/SSG/ISR as one app-wide choice. In the App Router, the rendering strategy is effectively chosen per-route — even per-fetch-call, based on caching/revalidation options — not one global setting for the whole app.

🔄 Likely Follow-up

"Which one should you default to?" Static (SSG/ISR) wherever the content doesn't need to be unique per-request — it's the fastest and cheapest; reach for SSR only when the response genuinely must reflect the current request, like personalized or authenticated content.

🎯 Say this in the interview — the exact lines to land

"CSR renders in the browser with JS after a mostly-empty shell loads. SSR renders full HTML on the server for every request. SSG renders HTML once at build time and reuses it. ISR is SSG that also regenerates in the background after a set time, without a full rebuild."

  • CSR → blank shell first, content fills in after JS runs.
  • SSR → fresh full HTML, computed on every single request.
  • SSG/ISR → built ahead of time, served instantly from cache.
  • Default choice → static wherever possible; SSR only when the response must be request-specific.
📖 Explanation ▾

CSR (Client-Side Rendering) ships a mostly-empty HTML shell, and JavaScript builds the actual page once it downloads and runs in the browser — the real content is the last thing to appear, not the first.

SSR (Server-Side Rendering) renders the full HTML on the server for every incoming request — always fresh, always current, but always paying the cost of rendering again, every time.

SSG (Static Site Generation) renders the HTML exactly once, at build time, and every visitor gets that same pre-built file. ISR (Incremental Static Regeneration) is the same idea with one addition: after a set time window, Next.js regenerates that static HTML in the background — visitors keep getting the fast cached version while the refresh happens, no full rebuild required.

None of these is a single app-wide setting. In the App Router, the choice is effectively made per route, and even per fetch call, through caching and revalidation options — a single page can mix a statically-rendered shell with one dynamically-fetched section.

💻 See the code ▾
JSX 
// SSG — default: fetch with no extra options is cached indefinitely
const res = await fetch('https://api.example.com/posts');

No revalidation option → Next.js treats this as static, built once.

JSX 
// ISR — regenerate this data in the background every 60 seconds
const res = await fetch('https://api.example.com/posts', {
  next: { revalidate: 60 },  // ✅ cached, refreshed on a timer
});

revalidate is what turns plain SSG into ISR — same cache, now with a refresh timer.

JSX 
// SSR — this request's own cookies make it request-specific
const res = await fetch('https://api.example.com/me', { cache: 'no-store' });  // ✅ fresh every time

cache: 'no-store' opts that one fetch out of caching entirely — rendered fresh per request.

🧭 Use Cases — recognize these when they happen to you ▾
1 A marketing page or blog post that reads the same for everyone

Nothing on this page depends on who's looking at it — build it once and serve the exact same file to everyone. This is the #1 scenario you'll actually run into.

RememberSame for everyone → SSG, the cheapest option.
2 A product catalog that changes occasionally, not per-visitor

Still the same for every visitor at any given moment, but stale after a while — ISR keeps serving the fast cached version while quietly refreshing it on a timer.

RememberSame for everyone, but goes stale → ISR.
3 A logged-in account page showing the current user's own data

Statically caching a page that shows one user's private data would serve that same cached HTML to the next visitor too — this has to be SSR (or client-fetched), rendered fresh per request, never cached statically.

RememberPer-user private data → SSR, never SSG/ISR.
🌍 Real-world example ▾

Think of a restaurant's menu board versus a made-to-order receipt. SSG/ISR is the printed menu board — made once (or reprinted occasionally), the same for every customer who walks in. SSR is the receipt — printed fresh, specific to this one order, every single time.
