Bicep vs. ARM vs. Terraform — same engine, or a different one?

"What's the actual tradeoff between Bicep, ARM templates, and Terraform?"

Why it matters ▾
  • Checks whether you know Bicep isn't a separate deployment engine — it's Azure's newer authoring syntax that still goes through the exact same Resource Manager pipeline as ARM JSON.
  • Comes up any time a team is choosing, or migrating, its Infrastructure-as-Code tooling for Azure.
  • A common opener before deeper IaC questions — state management, modules, or CI/CD pipeline design.
🔥 Easy interview recall

Bicep → compiles to ARM JSON, same engine

ARM JSON → Azure's native, verbose format

Terraform → a genuinely separate, multi-cloud tool

Think: Bicep and ARM are one engine wearing a friendlier syntax. Terraform is a different tool that talks to Azure through its own provider.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Bicep is a different engine from ARM." It isn't — Bicep is purely a friendlier authoring syntax that compiles straight down to the exact same ARM JSON and deploys through the exact same Resource Manager pipeline underneath.

🔄 Likely Follow-up

"Why would a team choose Terraform over Bicep if they're Azure-only?" Usually a state-management or module-ecosystem preference, or wanting one consistent tool across on-prem/other providers even for an Azure-heavy shop — not because Terraform can do something to Azure that Bicep fundamentally can't.

🎯 Say this in the interview — the exact lines to land

"Bicep compiles to ARM JSON — same engine, friendlier syntax. Terraform is a genuinely separate, multi-cloud tool that manages Azure through its own provider."

  • Bicep → compiles to ARM JSON before anything ever deploys — not a separate engine.
  • ARM JSON → Azure's original native format — still what Resource Manager actually executes.
  • Terraform → a genuinely separate, multi-cloud tool (HCL, HashiCorp) with its own Azure provider.
  • Terraform still wins for an Azure-only shop for state-management or tooling-consistency reasons — never because it can do something Bicep can't.
📖 Explanation ▾

ARM templates are Azure's original, native Infrastructure-as-Code format — verbose JSON, understood directly by Azure Resource Manager with no translation step. Bicep is Microsoft's current recommended Azure-native choice: a cleaner, purpose-built DSL that compiles down to that same ARM JSON before deployment. Same engine, same Resource Manager pipeline underneath — Bicep just makes the authoring experience far more readable.

Terraform is a different kind of tool entirely — a multi-cloud IaC tool from HashiCorp, written in HCL, that manages Azure through its own azurerm provider rather than handing Azure a template Resource Manager reads natively. It's the natural pick when a team already manages other clouds or services with Terraform and wants one consistent tool, not because it does anything to Azure that Bicep structurally can't.

💻 See the code ▾
Bicep 
resource storage 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'mystg'
  location: 'eastus'
  sku: {
    name: 'Standard_LRS' // ✅ same fields ARM JSON needs, far less punctuation
  }
}

This compiles down to an equivalent, much longer ARM JSON template — same resource, same deployment, same Resource Manager underneath.

🌍 Real-world example ▾

An Azure-only team rewrites its old ARM JSON templates into Bicep purely for readability — nobody on the team, and nothing about what actually gets deployed, changes. A multi-cloud team managing Azure alongside other providers keeps everything in Terraform instead, so the whole platform stays on one consistent workflow rather than splitting tooling per cloud.
