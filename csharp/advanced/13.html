Under GC pressure — what do you actually check first?

"A hot path is under GC pressure — what would you check first?"

Why it matters ▾
📦 Boxing
❗ ProblemA value type added to a List<object> (or passed as object, or through a non-generic interface) gets copied onto the heap on every call — in a hot loop that's a fresh heap allocation every single iteration.
✅ SolutionKeep it strongly typed — a generic List<T> or generic method holds the value in place, so no box (and no matching unbox) ever happens.
RecallBoxing = value type crossing into object → heap allocation.
🔗 LINQ allocations
❗ ProblemA Where/Select query re-run inside an outer loop allocates a fresh iterator — plus a closure class, if the lambda reads an outer variable — every single outer iteration, even though the query looks like it's "just filtering."
✅ SolutionMaterialize the query once outside the loop (.ToList() before the loop starts) so the iterator and closure get built once, not once per outer iteration.
RecallLINQ inside a loop = a hidden iterator + closure, every pass.
✂️ String +=
❗ ProblemStrings are immutable, so += inside a loop can't grow the existing string — it discards the old one and allocates a brand-new string on every iteration.
✅ SolutionStringBuilder mutates one internal buffer instead, so the same loop produces one allocation total, not one per line.
RecallString += in a loop = a new string every pass; StringBuilder fixes it.
🎯 Closures
❗ ProblemA closure captures its whole enclosing scope, not just the variable it actually uses — so an unrelated local sitting nearby gets kept alive for as long as the closure itself is alive.
✅ SolutionCapture only what the closure needs, or hoist the unrelated state out of the closure's scope, so nothing extra outlives the loop by accident.
RecallClosures keep everything nearby alive, not just what they use.
🔥 Easy interview recall

📦 Boxing → value type copied onto the heap

🔗 LINQ → hidden iterator & closure allocations

✂️ String += → a new string every loop iteration

🎯 Closures → capturing more state than they need

Think: whichever one is generating the most short-lived objects is the answer — check them in that order.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling GC.Collect() is not a fix. It doesn't remove whatever is generating the garbage — it just forces an extra, expensive full collection on top of the real problem, which is still allocating.

🔄 Likely Follow-up

"Which of these is usually the actual culprit?" Boxing and LINQ-in-a-hot-loop show up most often in real codebases — string concatenation is easy to catch in review, and forgotten closure captures are the one people miss.

🎯 Say this in the interview — the exact lines to land

"Under GC pressure I'd check four things: boxing of value types, LINQ allocations from iterators and closures, string concatenation in a loop instead of StringBuilder, and closures capturing more state than they need."

  • Boxing → value type crossing into object/an interface allocates on the heap every time.
  • LINQ → iterators and closures allocate even when a query looks free.
  • String += in a loop → a new string every iteration; reach for StringBuilder instead.
  • Closures → capturing more than they need keeps extra objects alive longer than necessary.
📖 Explanation ▾

Boxing copies a value type onto the heap the moment it's assigned into a reference-typed slot — object, a non-generic collection, or an interface. Each box is its own heap allocation, so doing it inside a hot loop turns a cheap value-type operation into a steady stream of garbage.

LINQ methods like Where and Select return iterator objects, and any lambda that reads a local variable compiles to a hidden closure class — both are heap allocations, even though the query reads like it's "just filtering." A closure that captures more than it needs keeps that extra state alive for as long as the closure itself is alive.

Strings are immutable, so += inside a loop doesn't grow the existing string — it discards it and allocates a brand-new one every iteration. StringBuilder mutates one internal buffer instead, so the same loop stops generating garbage entirely.

💻 See the code ▾
C# 
List<object> items = new();
items.Add(42);              // ❌ int boxed onto the heap
int sum = 0;
foreach (var item in items)
    sum += (int)item;        // ❌ unboxed again, every iteration

A generic List<int> keeps the value on the stack — no box, no unbox.

C# 
foreach (var order in orders)
{
    var big = orders.Where(o => o.Total > threshold)  // ❌ new iterator + closure, every outer loop
                        .ToList();
}

Move the LINQ query outside the loop — it should run once, not once per outer iteration.

C# 
string log = "";
foreach (var line in lines)
    log += line;              // ❌ a brand-new string every iteration

StringBuilder sb = new();
foreach (var line in lines)
    sb.Append(line);          // ✅ one buffer, mutated in place

Same result, one allocation instead of one per line.

C# 
for (int i = 0; i < 10; i++)
{
    var fullContext = LoadFullContext();   // ❌ captured but never used below
    handlers.Add(() => Console.WriteLine(i));  // closure keeps fullContext alive too
}

A closure keeps everything in its enclosing scope alive, not just the variable it uses — capture only what's needed.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're reviewing a PR and spot a List<object> or an object parameter holding value types

This is the cheapest place to catch boxing — before it ever runs. Ask for a generic type (List<T>, a generic method) instead of object, and the box never happens in the first place.

RememberCatching boxing in review is cheaper than catching it in a profiler later.
2 An allocation snapshot (dotnet-trace, dotMemory) comes back dominated by <>c__DisplayClass instances

That compiler-generated name means a LINQ query or a closure inside a hot loop is allocating — go find the lambda that's re-running (or re-capturing) on every outer iteration, and pull it out.

Remember<>c__DisplayClass flooding a snapshot points straight at LINQ or a closure.
3 A teammate suggests calling GC.Collect() to fix a slow endpoint

Nothing that was generating garbage stopped — it just paid for one extra, expensive full collection on top of the real problem. Redirect back to the four boxes above and a profiler, not another GC.Collect() call.

RememberGC.Collect() clears the symptom for a moment, never the cause.
🌍 Real-world scenario ▾

Your API's p99 latency spikes under load, and a profiler shows heavy time inside Gen0/Gen1 garbage collections. Boxing, LINQ, and closures are all silent — none of them throw or log anything — so the fix starts with the profiler, not a code read.

Take an allocation snapshot (dotnet-trace, dotMemory, or the equivalent) and look at what type is being allocated the most. A flood of System.Object boxes points at boxing. A flood of compiler-generated <>c__DisplayClass instances points at LINQ or a closure. A flood of System.String concentrated inside one loop points at concatenation. Whichever type dominates the snapshot tells you exactly which of the four boxes above to open first — you don't need to guess.
