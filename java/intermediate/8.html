Fail-Fast vs. Fail-Safe Iteration — throws on a structural change, or tolerates it

"Why does modifying a list while iterating over it sometimes throw an exception and sometimes not?"

Why it matters ▾
⚡ Fail-Fast
❗ ProblemIterating over an ArrayList or HashMap while another part of the code structurally changes it (adds/removes) could silently skip elements, revisit one twice, or throw an unrelated-looking exception deep inside the collection's internals.
✅ SolutionA fail-fast iterator tracks a modification counter and throws ConcurrentModificationException the instant it detects the backing collection changed structurally by anything other than its own remove() — the bug surfaces loudly and immediately instead of corrupting data silently.
Recallfail-fast = detects the change → throws immediately.
🧵 Fail-Safe (Weakly Consistent)
❗ ProblemIn a genuinely concurrent system — many threads reading a shared map while others add or remove entries — a fail-fast collection would throw constantly from completely normal, expected concurrent use, not from an actual bug.
✅ SolutionConcurrentHashMap and CopyOnWriteArrayList iterate over a stable snapshot or otherwise tolerate concurrent structural changes and never throw — the trade-off is the iteration may miss or include an update made during the pass.
Recallfail-safe = tolerates the change → keeps going, no throw.
🔥 Easy interview recall

Fail-Fast → throws immediately

Fail-Safe → never throws

Think: ArrayList/HashMap are fail-fast. ConcurrentHashMap/CopyOnWriteArrayList are fail-safe.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

list.remove(x) inside a for-each over that same list is not safe. It's the single most common way to trigger ConcurrentModificationException — fix it with the iterator's own remove(), or Java 8's Collection.removeIf().

🔄 Likely Follow-up

"What if you actually need to remove elements while iterating?" Use the iterator's own remove(), call Collection.removeIf(), or iterate over a copy (new ArrayList<>(list)) if the original list still needs to be usable mid-loop.

🎯 Say this in the interview — the exact lines to land

"Fail-fast iterators like ArrayList and HashMap's default views track a modification count and throw ConcurrentModificationException the moment they detect a structural change made outside the iterator itself. Fail-safe, weakly-consistent iterators like ConcurrentHashMap and CopyOnWriteArrayList never throw — they iterate a stable snapshot or tolerate concurrent changes instead."

  • Fail-fast → throws ConcurrentModificationException on any unexpected structural change.
  • Fail-safe → never throws, may miss or include a concurrent update.
  • list.remove(x) in a for-each → the classic trigger; fix with iterator.remove() or removeIf().
  • "Weakly consistent" → a deliberate trade-off for concurrency, not a bug.
📖 Explanation ▾

A fail-fast iterator (the default on ArrayList, HashMap, and most of the "classic" collections) keeps a private counter of how many times the backing collection has been structurally changed. Every call to next() checks that counter against the value it started with — if anything other than the iterator's own remove()/add() touched the collection in between, it throws ConcurrentModificationException right there, like a smoke alarm going off the instant it detects smoke rather than waiting for the fire.

A fail-safe (also called weakly consistent) iterator takes a different approach entirely — CopyOnWriteArrayList iterates over a frozen copy of the array taken when the iterator was created, and ConcurrentHashMap's iterators are built to tolerate concurrent bucket changes without ever needing to stop and check a counter. Neither one throws, but neither one guarantees the iteration reflects every single change made while it was running.

This isn't a quality difference — it's a deliberate design trade-off for each collection's intended use. A single-threaded ArrayList has no reason to tolerate concurrent changes, so failing loudly and immediately is the safer default; a genuinely concurrent collection has every reason to avoid throwing from completely normal concurrent access.

💻 See the code ▾
Java 
List<String> names = new ArrayList<>(List.of("Sam", "Max", "Ann"));
for (String n : names) {
    if (n.equals("Max")) names.remove(n);  // ❌ throws CME
}

A direct remove() on the collection mid-loop changes the modification count the iterator is still checking against.

Java 
Iterator<String> it = names.iterator();
while (it.hasNext()) {
    if (it.next().equals("Max")) it.remove();  // ✅ safe
}

The iterator's own remove() updates its tracked count too — no mismatch, no exception.

Java 
names.removeIf(n -> n.equals("Max"));   // ✅ safe, Java 8+

removeIf() is the modern one-liner — no explicit iterator needed at all.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're removing matching elements from a List in a loop

This is the #1 scenario you'll actually run into. The fix is never "catch the exception" — switch to the iterator's own remove() or Collection.removeIf(), both of which keep the modification count consistent.

RememberRemoving inside a for-each → reach for removeIf(), not list.remove().
2 Multiple threads read a shared cache while others update it

A plain HashMap here would throw constantly under normal concurrent traffic. A ConcurrentHashMap is built for exactly this access pattern — readers never see an exception, only a possibly-slightly-stale view.

RememberReal concurrent read/write → ConcurrentHashMap, not a plain HashMap.
3 You assume "fail-safe" means the iteration sees every update live

"Fail-safe" only promises no exception — it never promises the iteration reflects every change made while it was running. Code that depends on seeing every single concurrent update needs real synchronization, not just a tolerant iterator.

RememberNo exception ≠ fully up to date — weakly consistent means exactly that.
🌍 Real-world example ▾

A background job intermittently crashes with ConcurrentModificationException while reading a shared List that another thread occasionally trims. The fail-fast exception is working exactly as designed here — the real fix is switching the shared list to a CopyOnWriteArrayList (reads stay lock-free and never throw) or adding real synchronization, not catching and ignoring the exception.
