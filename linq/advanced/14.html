IAsyncEnumerable<T> vs. IEnumerable<T> — awaiting between elements as they stream in

"What does IAsyncEnumerable<T> actually add over IEnumerable<T>?"

Why it matters ▾
📦 IEnumerable<T>
❗ ProblemA foreach over a huge result set that's already been pulled into a List<T> has to wait for literally every row to arrive before processing even the first one.
✅ SolutionThat's completely fine, and simpler, when the result set is small enough that fully materializing it is cheap — true for most everyday queries.
RecallIEnumerable<T> = wait for everything, then iterate.
🌊 IAsyncEnumerable<T>
❗ ProblemA large or slow-arriving result set means the caller sits idle until the very last row shows up, even though the first row might have been ready to process long before.
✅ Solutionawait foreach over an IAsyncEnumerable<T> — exactly what EF Core's AsAsyncEnumerable() returns — awaits between elements as they stream in, so processing can start on row 1 without waiting for row 100,000.
RecallIAsyncEnumerable<T> = await between each row, as it streams in.
🔥 Easy interview recall

IEnumerable<T> → wait for everything, then iterate

IAsyncEnumerable<T> → await between each element

Think: IEnumerable is a finished box handed to you all at once. IAsyncEnumerable is a conveyor belt you can start working from immediately.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

await foreach over an IAsyncEnumerable<T> is not one database round trip per element. It's still a single query and a single open stream — await just lets the consumer wait for the next row the stream hasn't delivered yet, instead of blocking until the whole result set has arrived.

🔄 Likely Follow-up

"Is IAsyncEnumerable<T> just IEnumerable<T> with async sprinkled on?" No — MoveNext() on IEnumerable<T> is synchronous, so it assumes the next element is already available. MoveNextAsync() on IAsyncEnumerable<T> returns a Task, because producing the next element might itself take time worth awaiting — a genuinely different contract, not the same one with a keyword added.

🎯 Say this in the interview — the exact lines to land

"IAsyncEnumerable<T> lets await foreach await between elements as they stream in, instead of blocking until the entire sequence has materialized first — this is exactly what EF Core's AsAsyncEnumerable() returns."

  • IEnumerable<T> → wait for the whole sequence, then iterate.
  • IAsyncEnumerable<T> → await between each element, as it arrives.
  • Still one query, one stream → not one round trip per element.
  • Reach for it when → the result set is large enough that starting early actually matters.
📖 Explanation ▾

IEnumerable<T>'s iteration contract — MoveNext(), Current — is entirely synchronous. By the time a typical EF Core query reaches a foreach (usually after a ToList() or ToListAsync()), every row has already arrived; the interface itself has no way to say "the next element isn't ready yet, come back to me."

IAsyncEnumerable<T> replaces that with MoveNextAsync(), which returns a Task<bool> — a real place for the runtime to say "not yet" and let the caller await. await foreach is the matching syntax: it awaits each MoveNextAsync() call, so a row that hasn't streamed in yet just means an awaited pause right there, not a blocked thread and not a wait for the rest of the result set.

EF Core's AsAsyncEnumerable() is the bridge between the two worlds — it turns a normal IQueryable<T> query into an IAsyncEnumerable<T> that streams rows as the database delivers them, instead of requiring a terminal operator that waits for all of them.

💻 See the code ▾
C# 
List<Order> orders = await context.Orders.ToListAsync(); // waits for ALL rows

foreach (var order in orders)        // starts only now
    Process(order);

Nothing in the loop runs until every single row has already arrived and been placed in orders.

C# 
IAsyncEnumerable<Order> stream = context.Orders.AsAsyncEnumerable();

await foreach (var order in stream) // ✅ processes each row as it streams in
    Process(order);

Process(order) runs on row 1 as soon as it arrives — it never waits for the rows behind it.

🧭 Use Cases — recognize these when they happen to you ▾
1 A normal, modestly sized result set

Most queries return small enough result sets that materializing everything first costs nothing meaningful — the simpler IEnumerable<T>/ToListAsync() path is the right default here.

RememberSmall result set → ToListAsync() is simpler, and that's fine.
2 A large export or report where starting work early actually matters

This is exactly the case IAsyncEnumerable<T> was built for — a result set large enough that waiting for all of it before doing anything would be a real, visible delay (and a real memory cost).

RememberLarge result set, early processing matters → IAsyncEnumerable.
3 Assuming await foreach means one query per row

The await inside await foreach is waiting on the already-open stream's next delivery, not opening a new database call per row — the query count doesn't change from using it.

Rememberawait foreach → still one query, awaited one row at a time.
🌍 Real-world example ▾

A nightly export job streams a million rows out to a CSV file. Materializing all million rows first with ToListAsync() before writing anything means a large memory spike and no output at all until the entire query finishes. Switching to await foreach over context.Rows.AsAsyncEnumerable() lets it write each row to the file as it arrives, holding roughly constant memory for the whole job instead of one huge spike at the start.
