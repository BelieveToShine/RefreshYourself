ref, out, in — who must initialize, who writes back?

Why it matters ▾
🔄 ref
❗ ProblemNormally C# passes a copy — a method like AddOne can't actually change the caller's n, because it's only working on its own copy of the value.
✅ Solutionref hands over the real variable instead (it must already have a value going in), so AddOne(ref n) changes n itself — the caller sees 6, not 5, after the call.
Recallref = must init before calling, method can read + write it.
📤 out
❗ ProblemA method like TryDivide needs to hand back both whether it succeeded and the actual quotient — returning just one value forces a wrapper type just to carry the second result.
✅ Solutionout doesn't need a value going in, but the compiler forces every path through the method to assign it before returning — the same shape int.TryParse relies on.
Recallout = no init needed going in, but must be written on every path out.
👀 in
❗ ProblemPrintTotal only needs to read price, but passing it normally still copies the whole value in — wasted work if it were a large struct instead of a decimal.
✅ Solutionin passes the real variable in but blocks any write — price++ inside PrintTotal is a compile error — so it's safe to skip the copy purely for performance.
Recallin = read-only, purely for performance — no copy, no writes allowed.
🔥 Easy interview recall

ref → read + write

out → must write before returning

in → read-only

Think: int.TryParse(s, out int n) → the classic out use case

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

out doesn't mean optional. The method must assign it on every path before returning — miss one branch and it's a compile error, not a runtime bug.

🎯 Say this in the interview — the exact lines to land

"All three hand over the real variable instead of a copy. ref needs a value going in and can change it. out can start empty but must be written before returning. in is read-only, purely for performance."

  • out is how methods return more than one value without a wrapper type.
📖 Explanation ▾

Normally, C# passes a copy — the method gets its own version, and changes inside it never reach the caller. ref, out, and in all skip that copy and hand over the real variable instead — they just disagree on what the method may do with it.

ref needs a value going in and allows changing it. out doesn't care what's there going in, but the compiler forces the method to assign it before it returns — perfect for "give me a second result" (like int.TryParse). in only reads — the compiler blocks any write, which makes it useful purely for performance: skip copying a big struct without risking it gets changed underneath you.

refoutin
Must have a value going in?✅ yes❌ no✅ yes

💻 See the code ▾
C# 
void AddOne(ref int x) => x++;
int n = 5;
AddOne(ref n);   // ✅ n is now 6 — the real variable changed

ref needs a value going in, and the method can change it in place.

C# 
bool TryDivide(int a, int b, out int result)
{
    if (b == 0) { return false; }   // ❌ result not assigned on this path
    result = a / b;
    return true;
}

Every path through the method must assign out before it returns — the compiler checks this, every branch.

C# 
void PrintTotal(in decimal price)
{
    Console.WriteLine(price);
    price++;   // ❌ compile error — in is read-only
}

in skips the copy purely for performance — the compiler blocks any write, so nothing can change underneath the caller.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need a method to hand back a second result — like whether it worked, and what it computed

TryDivide doesn't need result to have a value going in, but the compiler checks every path through the method and refuses to compile until each one assigns it — the same shape int.TryParse and the other Try* methods use to hand back an extra result with no wrapper type. This is the #1 scenario you'll actually run into.

Rememberout → no wrapper type, just an extra result the method must write.
2 You need a method to change the caller's own variable, not just read it

AddOne(ref n) isn't handed a copy of n — it's handed the real variable, so x++ inside the method changes the exact same n the caller declared. Miss the ref keyword on either side and you're back to a harmless copy that changes nothing.

Rememberref → the caller's own variable can come back changed.
3 You're passing something into a method that only ever reads it, and copying it would be wasted work

PrintTotal(in decimal price) skips copying price in, but the compiler still protects the caller — price++ inside the method is a compile error, not a runtime surprise. This only pays off for something expensive to copy, like a large struct.

Rememberin → skips the copy, but the compiler blocks every write.
🌍 Real-world example ▾

Handing someone your actual notebook. ref hands over your notebook already written in — they can read it and add to it. out hands over a blank notebook — they're required to write something in it before giving it back. in hands over your notebook with a "look, don't write" rule.
