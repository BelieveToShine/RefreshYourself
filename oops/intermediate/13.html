Decorator — add behavior by wrapping, not subclassing

What is the Decorator pattern, and how does it differ from inheritance?

Why it matters ▾
🎁 Decorator
❗ ProblemYou need logging, caching, or both around OrderService. Subclassing means a new class for every combination (LoggingOrderService, CachingOrderService, LoggingCachingOrderService…).
✅ SolutionEach extra behavior is its own small wrapper that implements the same interface. Stack any wrappers you want at runtime, no new subclass per combination.
RecallDecorator = same interface, wraps another one, adds one behavior.
🔥 Easy interview recall

Decorator → wraps an object with the same interface

Inheritance → fixed at compile time, one class per combo

Think: Decorator is gift wrap: each layer adds something, and the thing inside is still the same gift.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Order of wrapping doesn't matter." It does. With logging on the outside, every call is logged, even cache hits. With logging inside the cache, cache hits are never logged.

🔄 Likely Follow-up

"Why not just use inheritance?" Inheritance picks behavior when you write the class and needs a subclass per combination. A decorator picks it at runtime and combines freely.

🎯 Say this in the interview — the exact lines to land

"A decorator implements the same interface as the object it wraps, holds that object, and adds behavior before or after forwarding the call. You can stack decorators at runtime — that is how it avoids a subclass for every combination."

  • Decorator → same interface, wraps another instance, adds one concern.
  • Versus inheritance → combine at runtime, no subclass explosion.
  • Stacking → each layer does one job (logging, caching, retry).
  • Pitfall → wrapping order changes behavior.
📖 Explanation ▾

A decorator is a class that implements an interface and also holds another object of that same interface. It forwards each call to the inner object and adds its own bit — logging before, caching around, retry after. The caller cannot tell it is talking to a wrapper.

Because every layer has the same interface, you can stack them in any order: new Logging(new Caching(new OrderService())). Compare inheritance: to get every combination you would write a class per combination, decided at compile time.

You have seen this in .NET already. A BufferedStream wraps another Stream and adds buffering — and is itself a Stream. ASP.NET Core middleware has a similar wrap-the-next-step shape, though it is a pipeline rather than a textbook decorator.

💻 See the code ▾
C# 
public interface IOrderService { Order Get(int id); }

public class LoggingOrderService : IOrderService
{
    private readonly IOrderService _inner;
    public LoggingOrderService(IOrderService inner) => _inner = inner;   // ✅ wraps the same interface

    public Order Get(int id)
    {
        Console.WriteLine($"Get {id}");   // extra behavior
        return _inner.Get(id);            // ✅ forward to the real one
    }
}

The wrapper is an IOrderService and has an IOrderService — that pair is the whole pattern.

C# 
IOrderService svc =
    new LoggingOrderService(
        new CachingOrderService(
            new OrderService()));   // ✅ stack at runtime

Reorder the layers and the behavior changes — logging outside the cache sees every call.

🌍 Real-world example ▾

You want to add caching to a slow repository without touching its code. Wrap it in a CachingRepository that implements the same interface. Callers keep using the interface, and removing the cache later is one line in the setup.
