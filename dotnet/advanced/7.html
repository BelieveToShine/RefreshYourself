Stop asking, start listening — real-time order status updates

"Like a food-delivery app — how do status updates (order placed → dispatched → delivered) reach the user's phone in real time?"

Why it matters ▾
📦 Real-Time Status Updates
❗ ProblemPolling repeatedly asks "any update?" — wasting requests and adding a delay between the moment the status actually changes and the moment the user sees it.
✅ SolutionOpen one persistent connection (WebSockets, or SignalR which builds on it with automatic fallback) so the server can push an update the instant the status actually changes.
RecallPush the moment it changes — don't make the client keep asking.
🔥 Easy interview recall

Polling → client keeps asking, wastes requests

SignalR / WebSockets → server pushes the instant it changes

Think: pull wastes round trips. push delivers the moment it happens.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Opening a connection and never explicitly closing it. Leaked connections pile up server-side resources — close it on an explicit "done" signal or a timeout, and have the server detect and clean up dead connections with a heartbeat or ping.

🔄 Likely Follow-up

"How would the server know a specific update belongs to a specific user's order?" The connection is put into a group keyed by that order's ID (or the user's ID) when it's opened. The server only pushes to connections subscribed to that one group — it never broadcasts to everyone.

🎯 Say this in the interview — the exact lines to land

"I'd avoid polling — it wastes requests and adds delay. I'd open one persistent connection, SignalR in ASP.NET Core, which builds on WebSockets with automatic fallback, and have the server push each status change the instant it happens. I'd key each connection into a group by order ID so updates only reach the right client, and make sure connections are closed explicitly when done, with a server-side heartbeat to clean up dead ones."

  • Polling → wastes requests and adds delay — the client keeps asking.
  • SignalR / WebSockets → server pushes the instant it changes, over one open connection.
  • Groups → key the connection to the order or user ID so updates reach only the right client.
  • Cleanup → close explicitly when done; a server heartbeat detects dead connections.
  • Fallback → SignalR falls back automatically when WebSockets aren't available.
📖 Explanation ▾

Polling means the client repeatedly asks "any update?" on a timer. It works, but every request is mostly wasted when nothing changed, and there's always a gap between the real status change and the next poll that happens to catch it.

The real-time mechanism is a persistent connection — a WebSocket, or SignalR, which builds on WebSockets and automatically falls back to other transports when they aren't available. The client opens it once and keeps it open; the server pushes a message down that same connection the instant the order's status actually changes, instead of waiting to be asked. (Full comparison of SignalR vs. plain WebSockets vs. Server-Sent Events is on SignalR vs. WebSockets vs. SSE.)

The server needs to know which open connections care about which order — it puts each connection into a group keyed by the order ID (or the signed-in user's ID) when the connection opens, and only pushes an update to the group for that order. Either side can end the connection: the client closes it once "delivered" arrives or the user navigates away, and the server should detect connections that silently died (a network drop) with a periodic heartbeat, so it isn't holding resources for a client that's already gone.

💻 See the code ▾
C# 
public class OrderStatusHub : Hub
{
    // client calls this once, right after it knows which order to watch
    public Task WatchOrder(string orderId)
        => Groups.AddToGroupAsync(Context.ConnectionId, $"order:{orderId}");
}

// elsewhere, when the order's status actually changes:
await hubContext.Clients.Group($"order:{orderId}")
    .SendAsync("StatusChanged", "Dispatched");

Only connections in that order's group receive the push — not every connected client.

JavaScript 
const connection = new signalR.HubConnectionBuilder()
    .withUrl("/orderStatusHub")
    .build();

await connection.start();                       // one connection, opened once
await connection.invoke("WatchOrder", orderId);

connection.on("StatusChanged", status => {
    if (status === "Delivered") connection.stop();  // ✅ close when done
});

The client never polls — it just reacts to pushes, and closes the connection itself once the order is delivered.

🧭 Use Cases — recognize these when they happen to you ▾
1 One customer tracking their own order's status on a tracking page

The connection joins a group keyed to that one order's ID. Each status push goes only to whoever is watching that order — not to every connected customer.

RememberOne order → one group → pushes reach only that customer.
2 A staff dashboard watches every order in a region at once

The same group mechanism scales to many-to-many — a dashboard connection joins a broader group (a region or a warehouse) and gets every status push for orders in it.

RememberGroups scale from "one order" to "every order in a region."
3 A customer closes the browser tab without the app ever calling "stop"

The server never got an explicit close. Without a heartbeat to notice the connection went silent, it keeps holding resources for a client that's already gone.

RememberNo explicit close → rely on a server heartbeat to clean up dead connections.
🌍 Real-world example ▾

A food-delivery app shows an order moving from "placed" to "dispatched" to "delivered." The phone app opens a SignalR connection once and joins the group for that order. As the kitchen and the driver's app update the order's status, the server pushes each change straight down that same connection — the customer's screen updates within a second, and the phone never once asks "is it ready yet?"
