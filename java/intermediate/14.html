Functional interfaces — one abstract method, three ways to write it

"What makes an interface 'functional,' and what's actually happening when you write a lambda?"

Why it matters ▾
🧩 Functional Interfaces
❗ ProblemPassing a small piece of behavior — a comparison rule, a click handler, a one-line calculation — used to mean writing a whole anonymous class with a method signature and braces, just to carry one real line of logic.
✅ SolutionAn interface with exactly one abstract method is "functional," so a lambda or a method reference can stand in as a compact instance of it — same compiled result, far less code to type and read.
Recallfunctional interface = one abstract method → a lambda IS that method, written shorter.
🔥 Easy interview recall

Functional interface = "exactly one abstract method to implement."

Think: Runnable → just run(). An anonymous class, a lambda, and a method reference are three ways to supply that one method — the compiler treats all three the same.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A lambda is not a special kind of object. It's just shorthand for an instance that implements the interface's one abstract method — if the target interface has more than one abstract method (not counting default/static ones), the code simply won't compile as a lambda at all.

🔄 Likely Follow-up

"Why bother with @FunctionalInterface if the compiler can already tell?" It's a safety net, not a requirement — without it, someone could later add a second abstract method to the interface and silently break every lambda using it; @FunctionalInterface makes the compiler reject that change immediately instead of failing somewhere else.

🎯 Say this in the interview — the exact lines to land

"A functional interface has exactly one abstract method — a lambda or a method reference is just compact syntax for an instance that implements that one method. java.util.function already supplies the common shapes, like Function<T,R> and Predicate<T>, so most code never needs to declare its own."

  • @FunctionalInterface → optional compiler enforcement, not what makes it functional.
  • Lambda / method reference → same compiled target as an anonymous class, just shorter.
  • Function<T,R>, Predicate<T>, Supplier<T>, Consumer<T> → the built-in shapes, cover most needs.
📖 Explanation ▾

An interface is functional when it declares exactly one abstract method — default and static methods don't count, since they already have bodies and don't need to be supplied by whoever implements the interface. @FunctionalInterface is an optional annotation that makes the compiler enforce this rule and reject the interface if a second abstract method ever gets added — it doesn't make the interface functional on its own, it just locks in a guarantee.

A lambda expression is compact syntax for an instance of a functional interface: the compiler already knows which single method the target interface needs, so x -> x * 2 only has to supply the body — no class name, no method name, no explicit parameter types if they can be inferred. A method reference (String::toUpperCase) goes one step further when an existing method already does exactly what's needed, pointing at it directly instead of wrapping it in a new lambda.

The java.util.function package ships the handful of shapes that cover almost every case, so most code never has to declare a new functional interface at all: Function<T,R> takes one argument and returns a result, Predicate<T> takes one and returns a boolean, Supplier<T> takes nothing and returns a value, Consumer<T> takes one and returns nothing, and BiFunction<T,U,R> takes two arguments and returns a result.

💻 See the code ▾
Java 
@FunctionalInterface
interface Calculator {
    int apply(int a, int b);   // the one abstract method
}

Calculator add = (a, b) -> a + b;   // ✅ lambda implements apply()

The lambda's parameters and return type come from apply — nothing is written twice.

Java 
Function<String, Integer> len1 = s -> s.length();   // lambda
Function<String, Integer> len2 = String::length;   // ✅ same thing, as a method reference

A method reference is only possible because length() already matches the shape Function needs.

🧭 Use Cases — recognize these when they happen to you ▾
1 Sorting a list with a custom rule

This is the #1 scenario you'll actually run into. list.sort((a, b) -> a.getAge() - b.getAge()) supplies Comparator's one abstract method, compare, with no separate class needed.

RememberA custom sort rule → a lambda implementing compare, nothing more.
2 Forwarding straight to an existing method

When the lambda's body is nothing but "call this one existing method," a method reference says the same thing more directly — no new parameter names to invent.

RememberLambda just forwards to one method → reach for a method reference instead.
3 You add a second abstract method to an existing functional interface

Every existing lambda targeting that interface instantly stops compiling, because a lambda can no longer tell which method it's supposed to implement. @FunctionalInterface catches this the moment it's typed, at the interface itself, instead of scattering the error across every call site later.

RememberMark it @FunctionalInterface so a second method is a compile error, not a surprise.
🌍 Real-world example ▾

A button's click handler used to be a 5-line anonymous ActionListener class. With a functional interface, it's button.addActionListener(e -> save()) — one line, same registered instance, nothing else changed about how Java calls it back.
