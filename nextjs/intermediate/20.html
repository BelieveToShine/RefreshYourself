Same Next.js app, two hosts — what do you actually lose self-hosting?

"Does a self-hosted Next.js app lose any core features compared to deploying on Vercel?"

Why it matters ▾
🚀 Vercel
❗ ProblemWiring up ISR invalidation, Edge Middleware regions, and an image CDN by hand is real infrastructure work most teams would rather not own.
✅ SolutionVercel — Next.js's creator — auto-detects every Next.js feature with zero config, because the platform and the framework are built by the same team.
RecallVercel = same team as the framework, zero config.
🐳 Self-Hosting
❗ ProblemSome teams need to run outside Vercel entirely — compliance, cost, existing infrastructure — but worry core App Router features simply won't work anywhere else.
✅ SolutionA Docker container or output: 'standalone' runs every core framework feature on any Node.js-capable host — only some Vercel-specific infrastructure optimizations need replicating.
RecallSelf-host = same core features, you own the infrastructure layer.
🔥 Easy interview recall

Vercel → zero-config, same team as the framework

Self-host → same core features, you own the infra

Think: Framework features travel with the code. Only Vercel's own infrastructure optimizations stay behind.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming a self-hosted app loses ISR, Server Actions, or the App Router entirely. It doesn't — those are framework features that run on any Node.js-capable host; what's genuinely Vercel-specific is some infrastructure-level optimization, not the core rendering features.

🔄 Likely Follow-up

"What does output: 'standalone' actually produce?" A minimal, self-contained server bundle with only the exact dependencies needed to run — ideal for a small Docker image, instead of shipping the entire node_modules tree.

🎯 Say this in the interview — the exact lines to land

"A self-hosted Next.js app keeps every core framework feature — ISR, Server Actions, the App Router — because those run on Node.js itself, not on Vercel's infrastructure. What you lose is Vercel-specific platform optimization, like their own global edge caching and image CDN, which you'd need to replicate yourself."

  • Vercel → zero-config, auto-detects every feature.
  • Self-host → same core features, you own the infra layer.
  • output: 'standalone' → minimal server bundle, built for Docker.
  • What's actually lost → Vercel's own edge/image infra, not framework behavior.
📖 Explanation ▾

Vercel built Next.js, so deploying there means every feature — ISR revalidation, Edge Middleware, automatic image optimization — is wired up with no extra configuration, because the platform already knows exactly how the framework expects to run.

Self-hosting — via next start on a normal Node.js server, output: 'standalone' for a minimal bundle, or a Docker container — runs every one of those same core framework features, because they're implemented in the framework itself, not in Vercel's infrastructure. What doesn't come along automatically is Vercel's own platform-level optimization: their global edge network, their managed image CDN. Those either need an equivalent built by hand, or are simply left out.

💻 See the code ▾
JS 
// next.config.js
module.exports = {
  output: 'standalone',  // ✅ produces a minimal, self-contained server bundle
};

The resulting .next/standalone folder is exactly what a small Docker image needs — no full node_modules.

Dockerfile 
FROM node:20-alpine
COPY .next/standalone ./  # ✅ just the minimal server, same ISR/Server Actions intact
CMD ["node", "server.js"]

Still the same Next.js server — nothing about rendering changed, only where it runs.

🧭 Use Cases — recognize these when they happen to you ▾
1 A small team wants to ship without owning any infrastructure

This is the most common case — Vercel auto-detects every feature with no setup, which is exactly the point for a small team that doesn't want to manage servers.

RememberNo infra appetite at all → Vercel is the default answer.
2 Compliance or existing infrastructure requires running on your own servers

An on-prem or regulated environment can still run the full App Router feature set — output: 'standalone' produces a minimal server that drops into any Node-capable host.

RememberMust run on your own infra → standalone output, not a feature downgrade.
3 A team avoids ISR or Server Actions because "those are Vercel-only features"

ISR and Server Actions are implemented inside Next.js itself — they run the same way self-hosted as they do on Vercel. Avoiding them over this assumption gives up real functionality for no actual reason.

RememberCore features aren't Vercel-exclusive — don't design around that myth.
🌍 Real-world example ▾

A company with a strict data-residency requirement can't deploy to Vercel's infrastructure at all. They build the app with output: 'standalone', ship it in a Docker container on their own Kubernetes cluster, and ISR, Server Actions, and the App Router all keep working exactly as before — only the image CDN and edge caching need their own equivalent, built on top of their existing infrastructure.
