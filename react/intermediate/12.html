Finding a slow render before guessing how to fix it

"How do you actually identify and diagnose unnecessary re-renders in a React app?"

Why it matters ▾
  • Interviewers use this to catch candidates who reach straight for useMemo/useCallback instead of measuring first.
  • Real day-to-day skill — reading a flamegraph before touching a single line of code.
  • A common opener for anyone who's shipped a React app that got slow under real data.
🔥 Easy interview recall

"Profile first" — the React DevTools Profiler shows what rendered, how long, and why — then fix what it actually shows.

Think: guessing at memo before measuring is itself the trap.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for useMemo/useCallback everywhere is not the first move. That's guessing without measuring — the actual cause could just as easily be a bundle-size issue, an expensive computation, or too many components mounting at once; the DevTools Profiler (what rendered, how long, and why) is the real first step, and the fix should target whatever it actually shows, not memoization by default.

🔄 Likely Follow-up

"What's virtualization, and when do you reach for it?" Rendering only the list items currently visible in the viewport (plus a small buffer), instead of the whole list at once — reach for it specifically when a list is large enough (thousands of rows) that rendering every item simultaneously is itself the actual bottleneck.

🎯 Say this in the interview — the exact lines to land

"I'd start with the React DevTools Profiler to see what rendered, how long it took, and why — then fix whatever it actually shows: React.memo for unnecessary re-renders with unchanged props, virtualization for a huge list, or code splitting to cut down what has to load and parse before anything even runs."

  • React.memo → use when a component re-renders with unchanged props.
  • Virtualization → use for a large list — render only the rows on screen.
  • Code splitting / lazy loading → fixes bundle size, a separate dimension from render performance.
  • Reducing unnecessary state updates → fewer triggers means fewer re-renders to begin with.
  • Over-memoizing → has its own cost — comparing dependencies on every render isn't free.
📖 Explanation ▾

The React DevTools Profiler is the actual starting point for any "the app feels slow" investigation. Instead of guessing which component is the problem, it records a run of the app and produces a flamegraph: for every component that rendered, it shows how long that render took, and — the most useful part — why it rendered at all. That "why" is what turns "something's slow" into "this specific component, for this specific reason."

Only once the Profiler has pointed at the real bottleneck does a specific fix make sense. A component re-rendering on unchanged props gets React.memo. A huge list gets virtualization — rendering only the rows currently on screen instead of every row at once. A slow first load is usually a bundle-size problem instead — how much JavaScript has to download and parse before anything shows — and that's what code splitting and lazy loading fix directly; it's a genuinely separate concern from render performance, not the same fix wearing a different name. Sometimes the real fix is simpler still: reduce the state updates that don't actually need to trigger a re-render in the first place.

Memoization itself isn't free, either — comparing dependencies on every render has a real, if usually small, cost. Wrapping everything in useMemo/useCallback "just in case" can make a component very slightly slower rather than faster, which is one more reason to measure before reaching for it.

💻 See the code ▾
JSX 
function ProfiledList() {
  return (
    <Profiler id="List" onRender={(id, phase, actualDuration) => {
      console.log(id, actualDuration);  // ms spent rendering, per commit
    }}>
      <List />
    </Profiler>
  );
}

Programmatic access to the same "what rendered, how long" data the DevTools Profiler panel already shows visually.

🌍 Real-world example ▾

A doctor runs diagnostic tests before prescribing treatment — they don't just guess at a remedy and hope it happens to match the actual problem. Profiling first, then fixing what it actually shows, is the same discipline applied to a slow React app instead of a patient.
