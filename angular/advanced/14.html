⭐ Should Know

Dozens of services, no single source of truth for anything — now what?

"State is scattered across dozens of services with unclear ownership — how would you actually redesign it?"

Why it matters ▾
  • This is the architecture-level version of the "when do you need NgRx" question — interviewers use it to see whether you'd redesign a real mess, not just recite the vocabulary.
  • Comes up whenever a growing app's services have quietly turned into a dumping ground for anything that "needs to be shared."
  • The classic wrong move is reaching for NgRx as the fix before anyone has actually sorted out what kind of mess it is.
🔥 Easy interview recall

UI state → stays local to the component

Server state → resource()/services, consistent caching

Truly shared state → consolidate — a few services, maybe NgRx

Think: "state is scattered everywhere" almost always means state was never sorted in the first place — sort first, then pick the tool.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

NgRx is not the default fix for "our state feels messy." A lot of real messy-state problems are just UI state wrongly promoted into a shared service, or server state fetched with no consistent caching pattern — NgRx doesn't solve either of those on its own, it just adds its own structure on top of an unsorted problem.

🔄 Likely Follow-up

"If most state turns out to be UI or simple server state, does that mean NgRx was never actually needed?" Not necessarily never — it means NgRx's real justification is whatever's left after honest categorization: genuinely complex, deeply cross-cutting state with many interacting pieces, which in a large, mature app can still be real. The point isn't "NgRx is unnecessary" — it's don't reach for it before the categorization work tells you how much of the problem it would actually need to solve.

🎯 Say this in the interview — the exact lines to land

"I'd start by categorizing what's actually there — server state, local UI state, and genuinely shared cross-feature state — because most 'scattered state' problems come from those three being mixed together with no boundary. Then I'd give server state a consistent fetching pattern, move UI state back into the components that own it, and only consolidate — into a few services, or NgRx if the coordination need is genuinely large — whatever's left that's truly cross-cutting."

  • Redesign order → categorize before choosing a tool — server, UI, and shared state have different natural homes.
  • UI state → keep it local, never promoted to a shared service just because it's convenient.
  • Server state → a consistent pattern — Signals/services, or resource()/httpResource() for the fetch itself.
  • Introduce NgRx → only once informal sharing is genuinely hard to trace, not as a default reaction to "this feels messy."
  • Signals + services are enough → whenever categorization leaves little that's genuinely complex — most apparent chaos resolves right there.
📖 Explanation ▾

Before redesigning anything, separate what's actually there. Server state is data fetched from an API — inherently async, with its own staleness and caching concerns. UI state is local and synchronous — is a dropdown open, what's in a draft form — and belongs to one component instance. Genuinely shared state is the small set that's truly cross-feature: the logged-in user, a shopping cart, global settings. Most "state is everywhere" complaints are really these three getting mixed together inside the same handful of services, with no boundary between them.

Once sorted, most of the mess resolves on its own. Server state gets a consistent pattern — a small number of Signal-backed stores, or resource()/httpResource() calls, with clear points where data gets refetched — instead of every feature hand-rolling its own loading/error flags. UI state moves back into the component that actually owns it; it was never supposed to live in a shared service in the first place. What's left after that pass — the state that's genuinely cross-cutting — gets consolidated deliberately into a few clearly-named services, or NgRx only if that remaining slice is large and hard to trace on its own.

💻 See the code ▾
TypeScript 
export class SidebarComponent {
  // ❌ was in a shared service for no reason
  // ✅ local to the component that actually needs it
  isMenuOpen = signal(false);
}

A dropdown's open/closed flag is view state — moving it into a shared service doesn't make it more "correct," it just makes it harder to find.

TypeScript 
@Injectable({ providedIn: 'root' })  // one shared instance
export class UserStore {
  readonly user = httpResource(() => '/api/me');  // ✅ loading/error/value, built in
}

No hand-rolled isLoading/error flags to keep in sync — httpResource() gives every consumer the same consistent shape for free, instead of each feature inventing its own.

🌍 Real-world example ▾

An application has grown to 40+ injectable services over two years, many holding a mix of UI flags, cached API responses, and cross-feature settings with no consistent pattern — new engineers can't tell which service actually owns a given piece of state. A redesign audit categorizes each service's state: about half turns out to be UI state that gets moved back into the components that actually use it; a third is server state consolidated into a small number of resource()-based stores with consistent caching; the remaining genuinely cross-cutting state — session, feature flags, cart — is consolidated into 3-4 clearly-named, well-documented services. No NgRx gets introduced at all: even after consolidation, what's left still isn't complex enough to justify it.
