Entra ID app registrations — who is the app claiming to be?

"What is Microsoft Entra ID, and what does an app registration actually represent — the OAuth2/OIDC basics an interviewer expects at this level?"

Why it matters ▾
🔓 OAuth2
❗ ProblemBefore an app can call an API on someone's behalf, something has to say exactly what that app is allowed to do — without handing over the user's actual password.
✅ SolutionOAuth2 issues an access token that answers exactly that: what this app is allowed to call, nothing about who's using it.
RecallOAuth2 = access token → what the app can do.
🪪 OIDC
❗ ProblemAn access token alone never actually confirms who the signed-in human behind the request is — a real gap once the app itself needs to know who's logged in.
✅ SolutionOIDC is built directly on top of OAuth2 and adds an ID token whose only job is proving that identity, so the app never has to see the user's password to sign them in.
RecallOIDC = ID token on top of OAuth2 → who the user is.
🔥 Easy interview recall

Entra ID → the directory — users, groups, apps

App Registration → the app's own identity

OAuth2 → authorization — what you can do

OIDC → authentication — who you are

Think: OIDC rides on top of OAuth2 — one proves identity, the other grants access.

⚠️ Common Trap

An App Registration and an Enterprise Application aren't the same object. The App Registration is the app's own identity (its Client ID, secret, or certificate); the Enterprise Application is that same app being used inside one specific tenant — a distinction that matters most for multi-tenant apps, which get one App Registration but a separate Enterprise Application object in every tenant that installs them.

🔄 Likely Follow-up

"What's the difference between OAuth2 and OIDC in one sentence?" OAuth2 grants a token for authorization — what the app is allowed to access; OIDC adds an ID token on top of that, specifically to prove who the signed-in user is.

🎯 Say this in the interview — the exact lines to land

"An app registration is the app's own identity — OAuth2 authorizes, OIDC authenticates. Entra ID is the directory that holds users, groups, and every app's registered identity."

  • Client ID & secret/cert → how the app proves its own identity when it asks Entra ID for tokens.
  • OAuth2 → authorization — issues an access token for what the app can call.
  • OIDC → authentication — adds an ID token proving who the user is, built on OAuth2.
  • Entra ID → the directory itself, holding users, groups, and app registrations.
📖 Explanation ▾

Entra ID (formerly Azure AD) is Microsoft's cloud identity and directory service — it manages users, groups, and application identities for a tenant. When an app needs to sign users in or call an API on their behalf, it needs its own identity in that directory too. Registering the app creates exactly that: a Client ID, plus a client secret or certificate, so the app can prove who it is when it asks Entra ID for tokens.

OAuth2 and OIDC answer two different questions, and OIDC is built directly on top of OAuth2 rather than replacing it. OAuth2 issues an access token that says what the app is allowed to call. OIDC layers an ID token on top of that, proving who the signed-in user actually is.

💻 See the code ▾
HTTP 
GET https://login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize
  ?client_id=xxxx-xxxx          -- which App Registration is asking
  &response_type=code           -- use the authorization-code flow
  &redirect_uri=https://app/cb  -- where Entra ID sends the user back
  &scope=openid%20profile       -- "openid" = also want an ID token (OIDC)
  &state=xyz123                 -- anti-forgery value, checked on return

Entra ID sends back a short-lived authorization code, not the tokens themselves — the app then trades that code (plus its Client ID/secret) for the real access token and ID token in a second, server-to-server call.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app just needs to know who signed in

This is authentication — OIDC's whole job. The app redirects the user to Entra ID and gets back an ID token proving who they are, without ever seeing their password.

RememberSigning in → OIDC's ID token.
2 Your app needs to call an API on the signed-in user's behalf

This is authorization — OAuth2's whole job. The access token says exactly what the app is allowed to call; it says nothing at all about who the user actually is.

RememberCalling an API → OAuth2's access token.
3 You open the Azure portal and see both "App Registrations" and "Enterprise Applications"

Candidates often assume these are two views of the same thing. They aren't — the App Registration is the app's own identity, while the Enterprise Application is that same app being used inside one specific tenant. A common interview trap.

RememberApp Registration = the app's identity. Enterprise Application = its use inside a tenant.
🌍 Real-world example ▾

A web app registers itself in Entra ID once, up front. From then on, whenever a user opens the app, it redirects them to Microsoft's own login page instead of handling passwords itself, and gets back tokens proving who the user is and what the app is allowed to access — the app never sees the user's actual credentials.
