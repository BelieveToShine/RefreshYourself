<Teleport> — same component, different address in the DOM

"What problem does <Teleport> solve?"

Why it matters ▾
🌀 Teleport
❗ ProblemA modal, tooltip, or toast nested deep inside a component with overflow:hidden or a low z-index context can get visually clipped or buried, no matter how high its own z-index is set.
✅ Solution<Teleport to="body"> moves its slot content's rendered DOM to a different part of the actual page (e.g. document.body) while keeping it logically part of the same component in Vue's component tree.
RecallTeleport moves where it renders, not who it belongs to.
🔥 Easy interview recall

<Teleport> = "keep the logic here, move only where it renders."

Think: Modal declared inside App → DOM output physically moves to <body> → props/events still flow through App.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming <Teleport> also moves the component out of Vue's reactivity and parent-child relationship. It only relocates the rendered DOM nodes — props, events, and the component hierarchy (for devtools and lifecycle purposes) stay exactly where they're logically declared.

🔄 Likely Follow-up

"Why not just always render modals at the body level directly in the template structure?" That would mean threading the modal's props and state all the way up through every intermediate component manually — Teleport lets the modal stay co-located with the component logic that needs it, while only its DOM output moves.

🎯 Say this in the interview — the exact lines to land

"<Teleport to="body"> moves its slot content's rendered DOM to a different part of the page while keeping it logically part of the same component — it solves z-index and overflow-clipping problems for things like modals, tooltips, and toasts."

  • Moves → only the rendered DOM nodes, not the component's identity.
  • Props/events/hierarchy → stay exactly where declared logically.
  • Classic use → modals, tooltips, toasts escaping a clipped parent.
  • Alternative (threading props up manually) → much messier than Teleport.
📖 Explanation ▾

<Teleport> is a built-in Vue component that takes a to target — a CSS selector string like "body" or a real DOM element — and renders its default slot's content there instead of in its own position in the template. Vue still fully tracks that content as belonging to the component that declared it; only the actual rendered DOM nodes move.

This matters specifically for CSS containment problems. A parent with overflow:hidden or its own stacking context can visually clip or bury a child no matter how that child's own z-index is set, because the browser evaluates those rules based on where a node actually sits in the DOM tree — teleporting the node out from under that parent sidesteps the containment entirely, without having to restructure the component tree to do it.

💻 See the code ▾
Vue 
<!-- Modal.vue, nested deep inside App -->
<template>
  <Teleport to="body">              <!-- ✅ DOM output moves to <body> -->
    <div class="modal-overlay">
      <slot />
    </div>
  </Teleport>
</template>

The parent's overflow:hidden or low z-index no longer clips it.

Vue 
<!-- parent still passes props/events normally -->
<Modal :open="isOpen" @close="isOpen = false" />   <!-- ✅ unaffected by Teleport -->

Props and events still flow through the logical parent — only the DOM output moved.

🧭 Use Cases — recognize these when they happen to you ▾
1 A modal nested inside a card with overflow:hidden

No amount of raising the modal's own z-index fixes this — the card's overflow:hidden clips anything inside it regardless. Teleporting the modal's DOM out from under the card removes the containment entirely.

RememberRaising z-index doesn't help against a clipping ancestor — Teleport does.
2 A global toast notification triggered from deep inside a nested form

The toast's logic naturally lives next to the form field that triggers it, but its DOM needs to render above everything else on the page — Teleport keeps the code co-located while still rendering it at the top level.

RememberKeep the trigger logic local, let Teleport handle where it actually paints.
🌍 Real-world example ▾

A "Delete account" confirmation dialog, triggered from deep inside a settings form that sits inside a scrollable card. Without <Teleport>, the dialog would be clipped by the card's scroll container; with it, the dialog's DOM renders at <body> level while its open/close state still lives naturally next to the button that triggers it.
