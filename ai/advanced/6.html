OWASP Top 10 for LLMs — how many can you name cold?

"What security risks does the OWASP Top 10 for LLM Applications cover — can you name a few?"

Why it matters ▾
  • A standard security-awareness question for a senior/staff/architect AI role — the bar is naming several categories with one line each, not reciting the official list verbatim.
  • Each category maps to a real production failure mode: a leaked system prompt, an agent that deleted something it should never have touched, a model quietly trained on poisoned data.
  • Prompt Injection is broad enough to deserve its own deep dive on its own — this page treats it as one line inside the fuller checklist, not a full re-explanation.
🔥 Easy interview recall

Input-side → attacker controls what goes IN

Output & trust → risk in what comes OUT, or what you assume is true

Agency & infra → how much power it has, what it's built from

Think: three buckets — in, out, and how much power / what it runs on.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Treating this list as "prompt injection, restated ten ways." Overreliance, training data poisoning, supply chain risk, and model theft have nothing to do with a crafted prompt at all — this is a checklist of genuinely distinct risk categories, not one problem repeated.

🔄 Likely Follow-up

"How would you actually defend against Excessive Agency?" Give the agent only the permissions the task needs — read-only where read-only is enough — and require a human-approval step before anything side-effecting, like a delete, a send, or a payment. Same least-privilege idea applied to an agent instead of a user account.

🎯 Say this in the interview — the exact lines to land

"OWASP publishes a Top 10 list of security risks specific to building with LLMs — categories like prompt injection, insecure output handling, training data poisoning, excessive agency, and supply chain vulnerabilities — and since the exact wording and ranking gets revised between versions, I think about them in three buckets: what goes in, what comes out, and how much power the system has or what it's built on."

  • Input-side → Prompt Injection & Jailbreaks, Training Data Poisoning — the attacker controls what goes in.
  • Output & trust → Insecure Output Handling, Sensitive Information Disclosure, Overreliance — the risk is in what comes out, or what you assume is true.
  • Agency & infrastructure → Excessive Agency, Insecure Plugin/Tool Design, Model Denial of Service, Supply Chain Vulnerabilities, Model Theft — how much power the system has, and what it's built from.
  • The list gets revised between versions — say "categories such as," never claim a fixed, permanent #1–#10 ranking.
  • Being able to name five or six cold, one line each, is the actual bar most interviews set — not reciting the full list verbatim.
📖 Explanation ▾

OWASP — the same group behind the classic web-app Top 10 — publishes a Top 10 list specifically for LLM applications, covering security risks that are new or reshaped by putting a language model into a system. It's a living document: category names, exact wording, and the ranking order have all been revised between versions. The useful interview skill is naming several well-established categories with a one-line description each, not memorizing an exact numbered list.

Input-side risks are about an attacker controlling what the model reads: Prompt Injection (broad enough for its own deep dive, not repeated here) and Training Data Poisoning, where the training or fine-tuning data itself is the attack surface. Output & trust risks are about what the model produces or reveals: Insecure Output Handling (acting on a model's output without validating it first — rendering it as raw HTML, for example), Sensitive Information Disclosure, and Overreliance (trusting an answer as correct without appropriate verification, especially for a consequential decision).

Agency & infrastructure risks are about how much power the system has and what it's built from: Excessive Agency (an agent given more permission than the task needs — least privilege, applied to an agent), Insecure Plugin/Tool Design (a callable tool with no guardrails on what it's allowed to do), Model Denial of Service (an attacker running up cost or degrading availability), Supply Chain Vulnerabilities (a third-party model, plugin, or training data with unknown provenance), and Model Theft (a proprietary model's weights, or a functionally-equivalent copy of its behavior, getting extracted).

💻 See the code ▾
JavaScript 
const answer = await llm.chat(userQuestion);
resultDiv.innerHTML = answer;  // ❌ trusts model output completely

If the response contains a <script> tag — from an injection, or the model just imitating markup it saw — it executes on the page. This is Insecure Output Handling: acting on model output as if it were already safe.

JavaScript 
const answer = await llm.chat(userQuestion);
const safe = sanitizeHtml(answer);  // ✅ never trust it, validate first
resultDiv.innerHTML = safe;

Same idea applies beyond HTML — output that gets eval()'d, run as a shell command, or dropped into a SQL string needs the same treatment: validate or sanitize before acting on it, every time.

🌍 Real-world example ▾

An internal coding-assistant agent gets a single generic "run any shell command" tool so it can help debug — that's Excessive Agency. The task only ever needed to read log files, never delete one or push a commit, so the fix is scoping the tool down to exactly what's needed (read-only where read-only is enough) instead of handing the model a blank check.
