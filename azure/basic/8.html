Managed Identity — the credential that was never actually stored anywhere

"What is Managed Identity, and what problem does it solve?"

Why it matters ▾
🪪 Managed Identity
❗ ProblemA password or connection string sitting in appsettings.json is exposed the instant that file leaks or gets committed — and someone still has to rotate it by hand whenever it changes.
✅ SolutionAzure creates and manages an Entra ID identity for the resource itself, so DefaultAzureCredential authenticates it automatically — no credential is ever stored in config, and none has to be rotated.
RecallManaged Identity = no credential to leak, none to rotate.
🔥 Easy interview recall

Managed Identity = "the resource's own login, with no password to store."

Think: System-assigned → lives and dies with the resource User-assigned → its own standalone identity, shared across resources

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Managed Identity is not for logging in end users. It's a resource (App Service, VM, Function, …) authenticating to other Azure services — a person signing in is a different problem, handled by Entra ID app registrations and OAuth2/OIDC instead.

🔄 Likely Follow-up

"System-assigned vs. user-assigned — when does it matter?" System-assigned is simpler but doesn't survive the resource being deleted or redeployed cleanly; user-assigned persists independently and can be shared by multiple resources that need the same permissions.

🎯 Say this in the interview — the exact lines to land

"Managed Identity means a resource authenticates to Azure with no credential to store or rotate — Azure creates and manages an Entra ID identity for the resource itself, and the target service just checks that identity instead of a password."

  • System-assigned → tied 1:1 to the resource's own lifecycle, deleted when it is.
  • User-assigned → a standalone identity that can be shared across multiple resources.
  • Not for end users → authenticates a resource to Azure, never a person logging in.
  • Real pattern → DefaultAzureCredential picks it up automatically — no client secret in code.
📖 Explanation ▾

Managed Identity is an Entra ID identity that Azure automatically creates and manages for a resource — App Service, a VM, a Function, and several others all support it. That identity lets the resource authenticate to other Azure services (Key Vault, Storage, SQL) without any credential ever being stored in code or config — Azure handles issuing and rotating the underlying token behind the scenes.

There are two kinds. A system-assigned identity is created and deleted together with the one resource it belongs to — simplest to set up, but it doesn't outlive that resource. A user-assigned identity is its own standalone Azure resource, created independently and then attached to one or more resources that need the same access.

System-assignedUser-assigned
Lifecycletied to the one resourceindependent — created and managed on its own
Shared across resources?no — one identity, one resourceyes — attach to many resources

💻 See the code ▾
C# 
// ❌ Secret sitting right in config — anyone who reads this file has it
var connectionString = "Server=...;Password=P@ss123!;";

A leaked appsettings.json or a repo commit exposes this password directly — nothing else has to go wrong first.

C# 
// ✅ No credential anywhere — Managed Identity handles the login
var credential = new DefaultAzureCredential();
var client = new SecretClient(vaultUri, credential);
var secret = await client.GetSecretAsync("DbPassword");

DefaultAzureCredential automatically picks up the resource's own Managed Identity when running in Azure — no client ID, secret, or certificate anywhere in this code.

🧭 Use Cases — recognize these when they happen to you ▾
1 A single App Service needs to read one secret from Key Vault

One resource, one identity, created and deleted together with it — the simplest setup and the one you'll reach for first. This is the #1 scenario you'll actually run into.

RememberOne resource, own identity → system-assigned.
2 Several resources all need the same downstream access

One standalone identity, created independently and attached to however many resources need the same permissions — it persists on its own, so it survives any one of those resources being redeployed or deleted.

RememberMany resources, same access → user-assigned.
3 Trying to use Managed Identity to log in an end user

Managed Identity authenticates the resource itself to Azure — never a person signing in. A real end-user login still needs an Entra ID app registration with OAuth2/OIDC; candidates often assume Managed Identity covers this too, and it doesn't.

RememberManaged Identity = resource auth only, never end-user login.
🌍 Real-world example ▾

An App Service reads its database password from Key Vault at startup, using its own system-assigned Managed Identity to authenticate the request — zero secrets in appsettings.json, and nothing to rotate by hand when the password changes.
