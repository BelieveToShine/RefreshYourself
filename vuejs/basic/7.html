v-model — one directive, two one-way bindings underneath

"What does v-model actually do under the hood?"

Why it matters ▾
🔄 v-model
❗ ProblemKeeping a form input's displayed value and your reactive data in sync by hand means writing both a :value binding and a change listener, every single field.
✅ Solutionv-model is shorthand for binding a value and listening for its change event in one directive, so both directions stay in sync automatically.
Recallv-model = :value + @input, written as one directive.
🔥 Easy interview recall

v-model = "shorthand for :value plus @input, bundled into one directive."

Think: two one-way bindings, not one magic bidirectional wire.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Treating v-model as "automatic two-way binding on anything." Out of the box it only works on native form elements — using it on a custom component requires that component to explicitly implement the matching prop+emit contract.

🔄 Likely Follow-up

"What do the .lazy, .number, and .trim modifiers do?" .lazy syncs on the change event instead of input (e.g. on blur). .number casts the input's string value to a Number. .trim automatically strips leading/trailing whitespace.

🎯 Say this in the interview — the exact lines to land

"v-model is shorthand for binding a value and listening for its change event in one directive. On a text input, it expands to :value="x" plus @input="x = $event.target.value" — syncing the reactive data and the form element's displayed value in both directions."

  • v-model → two one-way bindings, not one bidirectional one.
  • Works out of the box on native form elements only.
  • On a custom component → needs its own prop+emit contract to support v-model.
📖 Explanation ▾

v-model is compiler sugar over two separate things happening at once: a :value binding that pushes the reactive data's current value into the element, and an @input listener that pushes the element's value back into the data every time the user types. Neither direction is "two-way" on its own — together, they create the effect of two-way sync.

The exact event it listens to and the property it reads differ slightly by element type — a checkbox syncs on change and reads checked, a text input syncs on input and reads value — but the underlying pattern is always the same pair: bind in, listen out.

On a custom component, there's no native value/input pair to hook into automatically, so v-model there relies on the component accepting a modelValue prop and emitting an update:modelValue event — the component has to opt in.

💻 See the code ▾
Vue 
<input v-model="name" />

<!-- ⬇ exactly equivalent to ⬇ -->

<input
  :value="name"
  @input="name = $event.target.value"  // ✅ what v-model expands to
/>

Same two bindings, just written out by hand instead of using the shorthand.

Vue 
<input v-model.lazy="name" />    // syncs on change, not every keystroke
<input v-model.number="age" />   // value cast to Number
<input v-model.trim="name" />    // strips leading/trailing whitespace

Modifiers chain onto v-model the same way they chain onto v-on.

🧭 Use Cases — recognize these when they happen to you ▾
1 A simple text field, like a search box or a name input

The everyday case — type, and the reactive variable updates on every keystroke. This is the #1 scenario you'll actually use.

RememberPlain text input → v-model, no modifier needed.
2 A numeric field, like an age or quantity input

Without .number, qty would end up as the string "3" instead of the number 3 — the modifier casts it for you.

RememberNeed a real number, not a string → .number modifier.
3 You put v-model on a custom component without any setup

A custom component has no native value/input pair for Vue to hook into — it has to accept modelValue as a prop and emit update:modelValue itself before v-model works on it.

RememberCustom component → needs its own modelValue prop + emit contract.
🌍 Real-world example ▾

It's like a thermostat display and the actual temperature setting. The display shows the current setting (data → screen), and turning the dial updates the setting (screen → data) — two separate wires doing their own job, which together just look like one synced device.
