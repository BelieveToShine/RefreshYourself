Security — what did the browser just do on your behalf?

"What are the main web/browser security risks you need to defend against — XSS, CSRF, clickjacking, a loose CORS policy — and how does each one actually work?"

Why it matters ▾
  • Senior front-end interviews probe security specifically because a framework can't stop a raw innerHTML call or a missing CSRF token for you — that's still on the developer.
  • Every one of these is a real, shippable bug, not academic trivia — one unsanitized merge or one unescaped string is enough to open the door.
  • A strong answer reasons about the actual attack mechanism first; naming the acronym without explaining how it works reads as memorized, not understood.
🔥 Easy interview recall

XSS → attacker's script runs inside your page

CSRF → browser sends a request using your cookies, without asking

Clickjacking → your click lands on something you can't see

Think: XSS puts code in the page. CSRF spends your login behind your back. Clickjacking hides the real button under a fake one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

httpOnly cookies are not CSRF protection. httpOnly only stops JavaScript — and therefore XSS — from reading the cookie; the browser still attaches it automatically to a forged cross-site request, so CSRF needs its own defense (a token, or a SameSite cookie).

🔄 Likely Follow-up

"If you already set a strict CSP, do you still need to sanitize input?" Yes — CSP is a defense-in-depth backstop for whatever slips through, not a substitute for it; a CSP that allows 'unsafe-inline', or a page that still writes unsanitized input straight into innerHTML, is still exploitable no matter how the header is configured.

🎯 Say this in the interview — the exact lines to land

"Most of these come down to the browser doing something on the user's behalf that the user never intended: XSS gets the browser to run an attacker's script inside your page, CSRF gets it to fire a request using the user's own cookies, and clickjacking gets a real click to land on a hidden target. The fixes match the mechanism — never write unsanitized input into the DOM, tie state-changing requests to a token the attacker can't produce, and set the right headers (CSP, frame-ancestors, a properly scoped CORS policy) so the browser refuses to cooperate in the first place."

  • DOM-based XSS → unsanitized input into innerHTML lets the browser execute it as script; use textContent or a sanitizer when the content isn't meant to be HTML.
  • CSRF → the browser auto-attaches your cookies to a forged request; pair a CSRF token or SameSite cookie with an httpOnly token, since httpOnly alone doesn't stop CSRF.
  • Same-origin policy blocks cross-origin reads by default → CORS headers are the server's own opt-in for specific origins, not a free-for-all.
  • CSP → a response header that whitelists where scripts/styles can load from — a backstop layer, not a substitute for sanitizing input.
  • Clickjacking → an invisible framed page sits over the real one so your click lands on the attacker's button; block framing with response headers.
  • Prototype pollution → an unsanitized merge reaching a user-controlled __proto__ key corrupts Object.prototype for the whole app — reject dangerous keys before merging.
📖 Explanation ▾

Almost every one of these threats is a variation on the same idea: the browser trusts something it shouldn't, and does the attacker's work for it — runs a script, sends a request, or lets a page get framed. Interviewers rarely want a definitions list; they want to see you reason about the actual mechanism, not just recite the acronym.

By default, the browser's same-origin policy stops a script running on one origin from reading a response from a different origin — a restriction the browser enforces on its own, no server involved. CORS is the server's own explicit opt-in on top of that: response headers like Access-Control-Allow-Origin tell the browser which other origins are allowed to actually read the response. Configure it too loosely — a wildcard origin combined with credentials — and the same door the same-origin policy was closing gets quietly reopened.

Prototype pollution stops being trivia about the [[Prototype]] chain the moment user-controlled input reaches an object-merge or Object.assign call unsanitized — an attacker sends a __proto__ key, and every object in the app can inherit whatever they injected. Token storage carries the same "who can actually reach it" question as any cookie-vs-storage trade-off: a token sitting in localStorage is readable by any script running on the page, including an attacker's, so a sensitive token is safer in an httpOnly cookie — JavaScript, and therefore XSS, simply can't read it.

💻 See the code ▾
JavaScript 
const comment = getUserInput(); // e.g. "<img src=x onerror=alert(1)>"

// ❌ DOM-based XSS — the browser parses this as real HTML/JS
el.innerHTML = comment;

// ✅ Always rendered as literal text, never parsed
el.textContent = comment;

Same string, two different APIs — innerHTML hands it to the parser, textContent never does.

JavaScript 
// Server set: Set-Cookie: session=abc123; SameSite=Strict; HttpOnly

// ❌ An attacker's page can still trigger this — the browser attaches
// the cookie automatically, no matter which site the request came from
fetch("https://bank.com/transfer", { method: "POST", credentials: "include" });

// ✅ Require a token the attacker's page can't read or forge
fetch("https://bank.com/transfer", {
  method: "POST",
  credentials: "include",
  headers: { "X-CSRF-Token": csrfToken } // from a same-origin cookie/meta tag
});

SameSite=Strict stops the cookie being sent cross-site at all; the CSRF token is a second, independent lock on top of it.

JavaScript 
// ❌ Unsanitized merge — a request body of {"__proto__":{"isAdmin":true}}
// pollutes Object.prototype for every object in the app
function merge(target, src) {
  for (const key in src) target[key] = src[key];
  return target;
}

// ✅ Reject the dangerous keys before they ever get assigned
const UNSAFE_KEYS = ["__proto__", "constructor", "prototype"];
function safeMerge(target, src) {
  for (const key in src) {
    if (UNSAFE_KEYS.includes(key)) continue; // 🐛 blocked
    target[key] = src[key];
  }
  return target;
}

The attack needs nothing exotic — just a normal-looking merge function and one attacker-chosen key it never checked for.

🌍 Real-world example ▾

Your app fetches a "settings" object from a public API and merges it straight into a shared config object used everywhere in the app. If that merge doesn't reject __proto__-style keys, a malicious response (or a compromised third-party endpoint) can pollute Object.prototype once and quietly change how every plain object in the app behaves from that point on — the fix is checking the key allow-list before the merge, not after something breaks in production.
