Edge Runtime vs. Node.js Runtime — a trade-off, not a winner

"What's the difference between the Edge Runtime and the Node.js Runtime, and why does Middleware default to one specifically?"

Why it matters ▾
⚡ Edge Runtime
❗ ProblemMiddleware runs on every request, so a slow cold-start or a request routed to a distant region adds latency to literally everything.
✅ SolutionThe Edge Runtime is a lightweight, fast-starting JS runtime (V8 isolates, similar to Cloudflare Workers) that runs geographically close to the user — at the cost of a restricted API surface.
RecallEdge = fast and close, but a narrower set of APIs.
🟢 Node.js Runtime
❗ ProblemSome code genuinely needs full Node.js — native modules, certain database drivers, the filesystem — none of which the Edge Runtime can run.
✅ SolutionThe Node.js Runtime is the full, familiar Node environment — every npm package and Node API works — at the cost of slower cold-starts and standard server-region deployment.
RecallNode.js = full API access, but slower to cold-start.
🔥 Easy interview recall

Edge Runtime → fast, close, restricted API surface

Node.js Runtime → full API, slower cold start

Think: Middleware runs on every request, so it defaults to the Edge Runtime — speed matters more there than full Node API access.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Middleware doesn't have full Node.js APIs just because "it's all JavaScript." It runs on the Edge Runtime by default, so Node-specific modules like fs or certain database drivers fail there, even though the exact same code works fine in a regular Route Handler on the Node.js runtime.

🔄 Likely Follow-up

"How do you choose which runtime a specific Route Handler uses?" export const runtime = 'edge' (or 'nodejs', the default for most routes) at the top of the route file — an explicit per-route opt-in.

🎯 Say this in the interview — the exact lines to land

"The Edge Runtime is a lightweight, fast-starting JS runtime that runs close to the user but only supports a restricted API surface. The Node.js Runtime is the full Node environment — every npm package works — at the cost of slower cold-starts. Middleware defaults to Edge because it runs on every request and speed there matters most."

  • Edge Runtime → fast, globally distributed, restricted APIs.
  • Node.js Runtime → full API access, standard regions, slower cold start.
  • Middleware → defaults to Edge — runs on every single request.
  • Per-route choice → export const runtime = 'edge' | 'nodejs'.
📖 Explanation ▾

The Edge Runtime is built on V8 isolates — the same lightweight execution model used by Cloudflare Workers — rather than a full Node.js process. That's what makes it start almost instantly and lets it run in many geographic regions close to the request, but it also means there's no Node filesystem, no native binary modules, and only a subset of Node's built-in APIs are available.

The Node.js Runtime is the ordinary, full Node.js environment — anything that runs in plain Node runs here, including native modules and filesystem access. The trade-off is the opposite one: a Node.js process is heavier to start and is deployed at standard server regions rather than at the same fine-grained edge locations.

Middleware runs on literally every request that matches its config, so Next.js defaults it to the Edge Runtime — the startup-speed and geographic-distribution benefits apply to every single request, and most Middleware logic (auth checks, redirects, header rewriting) doesn't need full Node APIs anyway. Individual Route Handlers default to the Node.js Runtime but can opt into Edge per-route when their own logic fits Edge's narrower surface.

💻 See the code ▾
JavaScript 
// middleware.js — runs on the Edge Runtime by default
import fs from 'fs'; // ❌ fails — fs isn't available on Edge

export function middleware(request) {
  return NextResponse.next();
}

The exact same import fs from 'fs' works fine in a Route Handler on the Node.js runtime — it's the Edge Runtime's restricted surface that blocks it here.

JavaScript 
// app/api/report/route.js
export const runtime = 'nodejs'; // ✅ explicit — full Node.js API access

export async function GET() {
  const fs = await import('fs'); // ✅ works here
  ...
}

Opting a Route Handler explicitly into 'nodejs' (or 'edge') is a one-line, per-route decision.

🧭 Use Cases — recognize these when they happen to you ▾
1 Middleware doing an auth check or header rewrite on every request

Simple logic that doesn't need Node-specific APIs is exactly what the Edge Runtime's speed is for — this is the common case Middleware is built around.

RememberSimple, every-request logic → Edge's speed pays off.
2 Middleware trying to use a native database driver

A driver that relies on native Node bindings has no Edge equivalent. A common interview trap: assuming Middleware can run anything because "it's just JavaScript."

RememberNative Node dependency in Middleware → move that logic to a Node.js Route Handler instead.
3 A Route Handler that genuinely needs full Node.js

Set export const runtime = 'nodejs' on that specific route — most Route Handlers already default to it, so this is often just confirming the default rather than changing anything.

RememberNeed full Node APIs → opt that one route into 'nodejs' explicitly.
🌍 Real-world example ▾

A global app's Middleware checks an auth cookie and redirects unauthenticated users on every request. Running that check on the Edge Runtime means a user in Singapore and a user in Ireland both get a near-instant response from a nearby location, with no Node.js cold-start tax. If that same app later adds a Route Handler that generates a PDF using a native Node library, that one route explicitly opts into runtime = 'nodejs' — the two runtimes coexist in the same app, chosen per route by what each one actually needs.
