Retry, breaker, timeout — one pipeline on the outgoing call

"How do you implement retry, circuit breaker and timeout on outgoing calls in .NET?"

Why it matters ▾
🛡️ Resilience pipeline
❗ ProblemOne slow or failing service you call makes your own API hang too, and hand-written retry loops scattered around the code often make that outage worse.
✅ SolutionAttach one resilience pipeline (retry with backoff and jitter, circuit breaker, timeouts) to the HttpClient, so every call through it is protected the same way.
RecallConfigure resilience once on the client, not around every call.
🔥 Easy interview recall

Retry → transient errors only, backoff + jitter

Circuit breaker → stop calling a sick service

Timeout → never wait forever

Hedging → second try, idempotent calls only

Think: Timeout sets the patience. Retry tries again. Breaker knows when to stop trying.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A retry can run a non-idempotent call twice. Retrying a POST that charges a card may charge it twice — only retry calls that are safe to repeat (or send an idempotency key), and check what your handler's defaults do for unsafe methods.

🔄 Likely Follow-up

"Do you wrap each call site in a retry?" No — configure the pipeline once on the named or typed HttpClient (via IHttpClientFactory), so every call through that client gets the same protection and nobody can forget it.

🎯 Say this in the interview — the exact lines to land

"I'd attach a resilience pipeline to the HttpClient — with Microsoft.Extensions.Http.Resilience, which is built on Polly v8 — using retry with backoff and jitter for transient errors, a circuit breaker, and timeouts, and I'd only retry calls that are safe to repeat."

  • Retry → backoff plus jitter, transient errors only.
  • Circuit breaker → stops calls to a service that keeps failing.
  • Timeout → a limit on every attempt, plus an overall limit.
  • Hedging → a second parallel try for slow, idempotent calls.
  • Where → once on the HttpClient, not at each call site.
📖 Explanation ▾

The ideas are the ones on Retry vs. Resilience; this page is about where they live in .NET. Polly is the resilience library, and v8 organises it as a pipeline of strategies (retry, circuit breaker, timeout, hedging, and more). Microsoft.Extensions.Http.Resilience builds on it and plugs a pipeline straight into an HttpClient.

The quick route is the standard resilience handler: one call on the client builder gives you a ready-made stack of rate limiting, an overall timeout, retry, a circuit breaker, and a per-attempt timeout. There is also a hedging handler for slow idempotent calls. Check the current docs for the exact defaults and option names before you quote numbers. When you need something custom, build your own pipeline with Polly directly.

Three habits make it safe. Configure once on the client, not around each call. Mind the order — the first strategy added is the outermost, so retry wraps the timeout and each try gets its own time limit. And retry only what is safe to repeat: reads and idempotent writes, not a bare POST.

💻 See the code ▾
C# 
builder.Services.AddHttpClient<RatesClient>(c =>
        c.BaseAddress = new Uri("https://rates.example"))
    .AddStandardResilienceHandler();   // ✅ retry + breaker + timeouts, once

One line on the client builder protects every call that RatesClient makes (package Microsoft.Extensions.Http.Resilience).

C# 
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromSeconds(1),
        BackoffType = DelayBackoffType.Exponential, // waits grow each try
        UseJitter = true                            // ✅ spreads retries out
    })
    .AddTimeout(TimeSpan.FromSeconds(10))          // inside retry = per attempt
    .Build();

await pipeline.ExecuteAsync(async token => { await CallAsync(token); }, ct);

The same ideas built by hand with Polly v8 (package Polly.Core) — check the current docs for the exact option names in your version.

🌍 Real-world example ▾

Your checkout API calls a shipping-rates service that sometimes answers slowly or drops a request. With the pipeline on that client, a blip is retried with growing waits, a real outage trips the breaker so you fail fast instead of piling up waiting requests, and no single call can hang longer than its timeout. The checkout code itself just makes one normal call.
