Peering doesn't chain — that's why Transit Gateway exists

"VPC Peering vs. Transit Gateway — when would you use each?"

Why it matters ▾
  • Tests whether you know peering's 1:1 limit before reaching for a bigger network pattern.
  • Comes up any time a design question involves connecting many VPCs, or on-prem networks via VPN/Direct Connect.
  • A common opener right before a hybrid-connectivity or private-access (VPC endpoints) follow-up.
🔥 Easy interview recall

VPC Peering → 1:1, doesn't chain

Transit Gateway → one hub, many spokes

Think: Peering is a direct line between exactly two. Transit Gateway is a hub everyone plugs into.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"If A peers with B, and B peers with C, then A can reach C." Not true — VPC peering is strictly point-to-point; each peering connection is its own 1:1 relationship, with zero transitivity no matter how many hops it looks like on paper.

🔄 Likely Follow-up

"Gateway endpoint vs. interface endpoint?" Gateway endpoints are free, route-table-based, and only support S3/DynamoDB; interface endpoints use PrivateLink (an ENI with a private IP) and support most other AWS services, at a per-hour + per-GB cost.

🎯 Say this in the interview — the exact lines to land

"Peering is a direct, 1:1 connection between two VPCs and it doesn't chain — if I need many VPCs, or on-prem networks, all talking to each other, I reach for Transit Gateway instead, so every VPC gets one spoke into a central hub rather than a connection to every other VPC."

  • VPC Peering → 1:1, non-transitive — A↔B and B↔C doesn't give you A↔C.
  • Transit Gateway → hub-and-spoke — one attachment per VPC (and per VPN/Direct Connect), not a connection per pair.
  • Gateway endpoint → free, route-table-based — S3 and DynamoDB only.
  • Interface endpoint → PrivateLink ENI — most other AWS services, billed per hour + per GB.
📖 Explanation ▾

VPC Peering is a private, direct network connection between exactly two VPCs' address ranges, carried over AWS's own backbone instead of the public internet. It's strictly 1:1: if VPC A peers with VPC B, and VPC B separately peers with VPC C, A still cannot reach C through B — each peering connection only ever knows about the two VPCs it directly joins.

Transit Gateway is a regional hub that many VPCs — and on-prem networks over VPN or Direct Connect — attach to once. Traffic between any two attached networks routes through that one hub, so connecting N VPCs takes N attachments instead of a connection for every pair.

Connection shape1:1, point-to-pointhub-and-spoke, one attachment per VPC
Transitive?no — A↔B and B↔C doesn't give A↔Cyes — anything attached to the hub can reach anything else attached to it
Scales to many VPCs?gets unmanageable fast (N(N-1)/2 connections)linear — N attachments for N VPCs
On-prem networks?not directly — peering is VPC-to-VPC onlyyes — VPN and Direct Connect can attach to the same hub

A related but different tool: VPC endpoints let resources inside a VPC reach AWS services privately, without going over the internet or through a NAT Gateway. Gateway endpoints are free and route-table based, but only support S3 and DynamoDB. Interface endpoints are powered by PrivateLink — an actual network interface (ENI) with a private IP inside your VPC — and cover most other AWS services, at an hourly plus per-GB cost.

🌍 Real-world example ▾

A company with 15 VPCs wants every team's VPC able to reach every other team's VPC. A full peering mesh would need 105 separate connections (15×14/2) — unmanageable to maintain. They replace it with one Transit Gateway and 15 simple attachments, one per VPC, and get the same connectivity with a fraction of the operational overhead.
