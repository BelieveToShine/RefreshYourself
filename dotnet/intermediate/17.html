Moq fakes the dependency — WebApplicationFactory fakes nothing

"How would you unit test a controller that depends on a repository, and how is that different from integration-testing the whole API?"

Why it matters ▾
  • Builds directly on Unit Testing Fundamentals — this is where "fake every dependency" actually turns into working test code.
  • "How do you test a controller without a real database" is one of the most common practical follow-ups after any DI or testing question.
  • WebApplicationFactory comes up whenever a team argues about how much of the real pipeline a test should exercise.
🔥 Easy interview recall

Moq → fakes an interface — controls what it returns, can verify it was called

Test a controller → new it up directly, pass mocks through the constructor

WebApplicationFactory → boots the real app in memory — only infrastructure gets swapped

Think: mocking replaces one dependency; WebApplicationFactory runs everything else for real.

🧠 Visual Mental Model — understand it in 5 seconds

Once the controller itself is isolated, a different question shows up: how much of the real ASP.NET Core pipeline should a test actually exercise?

⚠️ Common Trap

Mocking a repository inside a WebApplicationFactory test doesn't make it a unit test. The real middleware, routing, and filters are all still running — it's an integration test with one faked piece, and that's exactly the point of using it.

🔄 Likely Follow-up

"What does Verify() actually check that Assert can't?" Assert checks the return value; mock.Verify() checks that a specific method was actually called, with specific arguments — useful when the method under test returns void or the point is confirming a side effect happened.

🎯 Say this in the interview — the exact lines to land

"I'd mock the repository interface with Moq, construct the controller directly with the mock passed in, and assert on the returned action result — that's a fast, isolated unit test. If I need to confirm the whole pipeline behaves correctly — routing, middleware, filters — I'd use WebApplicationFactory to boot the real app in memory and only swap the database registration for a fake."

  • Moq → fakes one interface — set up return values, verify calls happened.
  • Testing a controller → new it directly — no container needed, just constructor injection.
  • WebApplicationFactory → boots the real pipeline — an integration test, not a unit test.
  • Swap only the boundary → real middleware, fake infrastructure — that's the whole point of using it.
📖 Explanation ▾

Moq creates a fake implementation of an interface at runtime. mock.Setup(...) tells it what to return when a specific method is called; mock.Object is the fake instance itself, passed to the class under test exactly like the real dependency would be. This only works because the controller depends on the interface, never the concrete class — the same constructor injection idea from The Built-in DI Container.

Testing the controller itself needs no DI container at all: new OrdersController(mock.Object) constructs it directly, call the action method, and assert on the returned IActionResult. Fast, deterministic, no ASP.NET Core pipeline involved.

WebApplicationFactory<TEntryPoint> answers a different question — does the request actually work end to end through the real pipeline? It boots the real app in memory, including real middleware, routing, and filters; the test only overrides service registrations it genuinely can't run for real (a database, an external API), then sends requests through a real HttpClient.

💻 See the code ▾
C# 
[Fact]
public void Get_ReturnsNotFound_WhenOrderMissing()
{
    var mockRepo = new Mock<IOrderRepository>();
    mockRepo.Setup(r => r.Find(42)).Returns(null);   // no real DB involved

    var controller = new OrdersController(mockRepo.Object);   // ✅ constructed directly, no container

    var result = controller.Get(42);

    Assert.IsType<NotFoundResult>(result);
    mockRepo.Verify(r => r.Find(42), Times.Once);   // confirms it was actually called
}

Verify checks the call happened — Assert alone can't see that.

C# 
public class OrdersApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public OrdersApiTests(WebApplicationFactory<Program> factory)
    {
        // real pipeline boots — only swap the DB registration
        _client = factory.WithWebHostBuilder(b => b.ConfigureServices(services =>
            services.AddScoped<IOrderRepository, FakeOrderRepository>()))
            .CreateClient();
    }

    [Fact]
    public async Task Get_Returns200()
    {
        var response = await _client.GetAsync("/api/orders/42");   // ✅ real routing, real middleware
        response.EnsureSuccessStatusCode();
    }
}

Routing, middleware, and filters all run for real — only IOrderRepository was swapped.

🌍 Real-world example ▾

A code review flags "this test still hits SQLite, so it's not a real unit test." That's correct — swapping a real database for a lighter one still runs real database code, so it's an integration test wearing a unit test's clothes. Either mock the repository interface for a genuine unit test, or keep it as-is and just call it what it is.
