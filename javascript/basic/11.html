Error Handling — the catch that doesn't catch everything

"How do try/catch/finally, throw, and custom error classes work in JavaScript — and what happens when an error is never caught?"

Why it matters ▾
  • Assuming a try/catch protects code that actually runs later, in a callback or a Promise, is one of the most common production bugs in real JavaScript apps.
  • Custom error classes that extend the built-in Error come up constantly in code review and API-design interview questions.
  • A near-guaranteed follow-up once async code comes up: "how do you handle a rejected Promise?"
🔥 Easy interview recall

try → runs the risky code

catch(err) → runs only if try throws

finally → always runs, error or not

throw → hands the error to the nearest catch, or up the stack

Think: try/catch only sees a throw that happens inside that same synchronous call — a throw inside a later callback or a rejected Promise needs its own catch.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Wrapping code in try/catch does not protect a callback that runs later. By the time a setTimeout callback fires, the surrounding try block has already finished and left the call stack, so an error thrown inside it is never caught — the same is true for a rejected Promise, which needs its own .catch() (or a try/catch around an await) instead.

🔄 Likely Follow-up

"So can async code ever use try/catch?" Yes, around an await — await pauses that function until the Promise settles, so a rejection there behaves like a synchronous throw; a plain .then() callback or an un-awaited Promise still needs its own .catch() (full depth on the Promises and async/await pages).

🎯 Say this in the interview — the exact lines to land

"try runs the risky code, catch(err) only runs if it throws, and finally always runs regardless. throw hands an error to the nearest catch, or it bubbles up the call stack uncaught. A rejected Promise or an error inside a callback needs its own catch — a synchronous try/catch around the call that started it won't see it."

  • finally → always runs, error or not — even if try or catch returns early.
  • throw → convention is to throw an Error object, not a plain string — it carries a message and a stack trace.
  • Custom errors → extend the built-in Error class — gives you a named type you can check with instanceof.
  • Uncaught error → bubbles up the call stack until something catches it, or it crashes at the top.
  • Async errors → need their own catch mechanism — a rejected Promise doesn't reach a surrounding synchronous try/catch.
📖 Explanation ▾

try/catch/finally is one block with three jobs: try runs the code that might fail, catch(err) only runs if something inside try throws, and finally runs no matter what happened — error, no error, or even a return inside try or catch. That's what makes finally the right place for cleanup (closing a connection, hiding a loading spinner) that has to happen either way.

throw can technically raise any value, but the real convention is to throw an Error object (or a subclass of it) because it automatically carries a .message and a stack trace. A custom error is a class that extends Error, calls super(message) so the base class still sets up the message and stack, and usually sets this.name to its own class name — that's what lets calling code check err instanceof ValidationError instead of parsing a message string.

If nothing inside a function catches a thrown error, JavaScript pops that function off the call stack and looks for a catch in whatever called it — that's propagation. If it reaches all the way to the top with no catch anywhere, the error is uncaught: it crashes a Node process, or fires the browser's global error handler.

That propagation is a synchronous mechanism — it only walks the call stack that's live right now. A rejected Promise doesn't throw onto that stack at all; it settles as "rejected" and needs a .catch() (or a try/catch around an await) to be handled, or an unhandledrejection event fires instead. The full mechanics of Promises and async/await belong to their own pages later in this track — the point here is just that async errors are a genuinely different mechanism, not the same one running later.

💻 See the code ▾
JavaScript 
function readConfig() {
  try {
    return JSON.parse(rawConfig);   // might throw on bad JSON
  } catch (err) {
    console.error("Bad config:", err.message);
    return {};                       // fallback
  } finally {
    console.log("readConfig finished"); // ✅ runs either way, even after a return
  }
}

finally logs on every path — success, caught error, doesn't matter — because it always runs.

JavaScript 
class ValidationError extends Error {
  constructor(message) {
    super(message);           // sets up .message and the stack trace
    this.name = "ValidationError";
  }
}

throw new ValidationError("email is required");
// catch (err) { if (err instanceof ValidationError) ... }

Extending Error gives calling code a real type to check with instanceof, not just a message to string-match.

JavaScript 
// ❌ this try/catch never sees the error — it already returned by then
try {
  setTimeout(() => { throw new Error("boom"); }, 0);
} catch (err) {
  console.log("caught:", err.message); // never runs
}

// ✅ the catch has to live inside the callback itself
setTimeout(() => {
  try { throw new Error("boom"); }
  catch (err) { console.log("caught:", err.message); }
}, 0);

By the time the timer fires, the outer try already finished — there's nothing left for it to catch.

JavaScript 
fetchUser(id)
  .then(user => render(user))
  .catch(err => console.error("fetch failed:", err)); // a rejection's own catch

// last-resort safety net — logs any Promise rejection nobody caught
window.addEventListener("unhandledrejection", event => {
  console.error("Unhandled rejection:", event.reason);
});

A synchronous try/catch around this call would never see the rejection — .catch() is the mechanism built for it (full depth: Promises, later in this track).

🌍 Real-world example ▾

A payment endpoint wraps the whole request handler in try/catch, yet the server still crashes. The crash is coming from a webhook callback fired later by a timer, not from the request itself — the outer try/catch was never in scope by the time that callback ran. The fix is to catch inside the callback (or await it so a normal try/catch applies), and add a top-level unhandledrejection/uncaughtException handler as a last-resort safety net, not a substitute for handling the error where it actually happens.
