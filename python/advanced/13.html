Unpickling untrusted data is arbitrary code execution — pickle was never designed to be a safe wire format

JSON vs. pickle — and why is unpickling untrusted data dangerous?

Why it matters ▾
  • This is a real security question, not a syntax question — a wrong answer here signals a genuine gap, not just an unfamiliar keyword.
  • It explains why multiprocessing "just works" passing Python objects between processes, and exactly where that same mechanism turns dangerous.
  • Common follow-up the moment a candidate says "pickle is just a faster JSON" — that sentence alone is usually enough for an interviewer to dig here.
🔥 Easy interview recall

JSON → safe anywhere, restricted format

pickle → trusted-only, can run code

Think: JSON is text, safe from strangers. pickle is binary, safe only between friends.

⚠️ Common Trap

pickle is not just a faster, binary JSON. Unpickling can be made to execute arbitrary code embedded in the stream — it's trusted-only, never a drop-in replacement for parsing data from outside your own processes.

🔄 Likely Follow-up

"When is pickle actually the right choice?" For trusted, internal-only serialization between processes you fully control — exactly what multiprocessing uses it for under the hood — never for data coming from outside your trust boundary.

🎯 Say this in the interview — the exact lines to land

"Unpickling untrusted data is arbitrary code execution, not a theoretical risk — JSON is the safe choice across any trust boundary, pickle only between my own trusted processes."

  • This is exactly the mechanism multiprocessing relies on internally — pickle passing objects between processes I already control.
  • json.loads() can only ever produce restricted, safe data — strings, numbers, booleans, null, lists, objects.
  • pickle.loads() on untrusted input is a genuine remote-code-execution vector, not a style preference.
  • Use JSON for any API or unauthenticated input; use pickle only for my own trusted inter-process communication.
  • Serialization always costs CPU time, and for binary formats potentially size — worth measuring on a high-throughput path.
📖 Explanation ▾

JSON is a text-based, language-agnostic format restricted to a small set of shapes — strings, numbers, booleans, null, arrays, and objects. A conforming parser can't be tricked into running code, because there's no instruction in the format for "call this" — only data. That's exactly why it's the right default for anything crossing a trust boundary, even though it can't represent an arbitrary Python object without your own conversion code.

pickle is Python's own binary serialization format. It can represent almost any Python object directly, including instances of your own classes — but the format itself supports embedding instructions to call arbitrary callables while it's being loaded back. A maliciously crafted pickle stream can use that to run whatever code the attacker wants, the moment pickle.loads() executes — this is a genuine remote-code-execution vulnerability, not a theoretical footnote.

The dividing line isn't "which format is better" — it's whose data it is. API serialization talks to any client, so it has to be JSON (or another schema-validated format). Internal object serialization only ever moves between your own trusted processes — pickle is fine there, and it's literally how multiprocessing hands objects between worker processes under the hood.

💻 See the code ▾
Python 
import pickle

def handle_upload(file_bytes):
    data = pickle.loads(file_bytes)   # ❌ arbitrary code execution risk
    return data

The moment loads() runs on a crafted stream, it can call whatever function the attacker embedded — before this function ever inspects data.

Python 
import json

def handle_upload(file_bytes):
    data = json.loads(file_bytes)     # ✅ safe — restricted data only
    return data

Same trust boundary, same shape of code — json.loads() can only ever produce strings, numbers, booleans, null, lists, or dicts. Never a function call.

🌍 Real-world example ▾

This is a well-documented, recurring class of real vulnerability, not a hypothetical: an application caches computed results to disk as pickle files, then loads them back with pickle.load() on a later request. If an attacker can influence what ends up in that cache — a crafted upload treated as a "cache file," a poisoned queue message — their bytes get decoded straight into a call to an arbitrary function the moment the server loads the cache back. This exact pattern, deserializing an untrusted cache or session file with pickle, is exactly why security guidance calls out unpickling untrusted data by name.
