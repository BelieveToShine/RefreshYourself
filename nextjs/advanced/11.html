Securing Server Actions — hidden isn't the same as safe

"Why isn't 'it's only called from authenticated pages' enough to secure a Server Action?"

Why it matters ▾
🔐 Server Action security
❗ ProblemA Server Action compiles down to a real, callable HTTP endpoint (identified by a generated action ID) — assuming "the UI only shows this to authorized users" makes it safe leaves the actual endpoint open to anyone who can construct the request.
✅ SolutionTreat every Server Action like a public API endpoint: re-verify the caller's authentication/authorization inside the action itself, validate and sanitize inputs, and don't expose logic as an action that doesn't need to be callable at all.
RecallServer Action = a real endpoint wearing a function's clothes.
🔥 Easy interview recall

Server Action = "a real HTTP endpoint that looks like a function call."

Think: hiding a door's location isn't the same as locking it — check who's allowed in, every time, from inside the room.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"This Server Action is never imported into public-facing client code, so it's safe" is wrong. Safety from casual discovery isn't the same as being inaccessible — its endpoint exists and is callable by anyone who knows or finds its action ID, same threat model as an unauthenticated REST endpoint.

🔄 Likely Follow-up

"What's a concrete example of a Server Action vulnerability?" A deleteUser(id) action that trusts the id argument and deletes without re-checking that the caller is actually authorized to delete that specific user — exactly the broken-access-control bug a traditional API endpoint would also have if it skipped the same check.

🎯 Say this in the interview — the exact lines to land

"A Server Action compiles to a real, callable HTTP endpoint identified by a generated action ID — I treat it with the same security discipline as any public API: re-verify auth inside the action itself, validate every input, and never rely on the UI only showing it to the right people."

  • Server Action → a real, independently callable endpoint, not a hidden function.
  • UI restriction → controls visibility, not access.
  • Correct check → re-verify auth/authorization inside the action itself, every call.
  • deleteUser(id) example → check the CALLER is allowed to delete THAT id, not just that they're logged in.
📖 Explanation ▾

A Server Action looks like a normal function call from the client component that invokes it, but under the hood it's compiled into a real POST endpoint, reachable by its own generated action ID. The framework doesn't keep that endpoint private to the page that defines it — anything that can send the right request can call it.

That means the usual API-security checklist applies in full: re-check authentication and authorization inside the action (never assume the caller already passed a gate elsewhere), validate and sanitize every argument the same way you would for a REST body, and don't turn something into a Server Action at all if it doesn't genuinely need to be called from the client.

The failure mode to watch for is specifically broken access control — a check that verifies the caller is logged in, but not that they're allowed to act on the specific resource (user ID, record ID) they passed in.

💻 See the code ▾
JSX 
"use server";

// ❌ trusts the caller — no re-check inside the action itself
export async function deleteUser(id) {
  await db.user.delete({ where: { id } }); // anyone who can call this, can run this
}

"Only the admin page renders the button that calls this" is a UI fact — it says nothing about who can actually send this request.

JSX 
"use server";

// ✅ re-verifies the caller, and that THEY can act on THIS id
export async function deleteUser(id) {
  const session = await getSession();
  if (!session?.isAdmin) throw new Error("Unauthorized");
  await db.user.delete({ where: { id } });
}

The check moved inside the action — now it's enforced no matter how the request arrives.

🌍 Real-world example ▾

A code review flags a Server Action with the comment "this is fine, it's only called from the internal admin dashboard." That comment describes the UI, not the endpoint — the actual question to ask is whether the action itself re-checks who's calling before it acts, because the dashboard being the only caller in your own code doesn't stop a different caller from reaching the same endpoint directly.
