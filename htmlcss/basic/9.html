Invisible isn't the same as gone — display:none vs. visibility:hidden vs. opacity:0

"What's the difference between display: none, visibility: hidden, and opacity: 0?"

Why it matters ▾
🚫 display:none
❗ ProblemAn inactive tab panel or a collapsed accordion section needs to be fully out of the page — if it only looked hidden, its layout space, click target, and tab stop would all still be sitting there for no reason.
✅ Solutiondisplay:none removes the box from the render tree entirely — no layout space, no click, no focus, no screen-reader announcement, exactly as if the element were never in the markup.
Recalldisplay:none = the box is gone completely, not just invisible.
👻 visibility:hidden
❗ ProblemHiding one placeholder row with display:none would collapse its space and shift every other row around it — not what a "blank this row but keep the layout" case needs.
✅ Solutionvisibility:hidden keeps the box's layout space reserved and skips it for paint, click, focus, and screen readers — but a descendant can still opt back in with its own visibility:visible.
Recallvisibility:hidden = space stays reserved, box disappears from view and focus.
🎭 opacity:0
❗ ProblemA fade transition needs the element to still fully exist while it animates — but that same "still there" trait is exactly why opacity:0 is the option most people wrongly assume is fully hidden.
✅ Solutionopacity:0 only changes what Paint draws — the box stays in layout, stays in the tab order, and stays clickable, unless it's separately disabled.
Recallopacity:0 = invisible to the eye, still fully interactive.
🔥 Easy interview recall

display:none → gone — no box at all

visibility:hidden → invisible, box still there

opacity:0 → invisible, box still active

Think: display:none = no box. visibility:hidden = box, no paint. opacity:0 = box, paint, just transparent — and still clickable.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

opacity: 0 does not make an element inert. It still occupies its layout space and stays clickable and focusable unless it's separately disabled — only display: none actually removes it from interaction.

🔄 Likely Follow-up

"If visibility: hidden hides a whole section, can one element inside it still show up?" Yes — a descendant can set its own visibility: visible and reappear even while its hidden ancestor stays invisible; display: none allows no such override, since nothing inside a box that was never rendered can render either.

🎯 Say this in the interview — the exact lines to land

"display: none removes the element from the render tree entirely — no space, no click, no focus, no screen reader. visibility: hidden keeps its layout space but hides it from view and assistive tech, though a nested child can override it back to visible. opacity: 0 keeps the element fully in layout and fully interactive — it's invisible to the eye, but not necessarily to a click, a tab press, or a screen reader."

  • display:none → use it when the element shouldn't exist right now — collapsed panels, tabs that aren't active.
  • visibility:hidden → use it when the space must stay reserved — hiding one cell without shifting the rest of the layout.
  • opacity:0 → the one that still works — fine for fade transitions, risky if used to "hide" something from keyboard or screen-reader users.
  • Only display:none skips Layout and Paint both — visibility:hidden and opacity:0 both still run Layout, they just change what Paint does with it.
📖 Explanation ▾

display controls how an element generates its box and lays out next to its neighbors. block stacks full-width, top to bottom. inline flows inside a line of text with no forced line break around it. inline-block flows inline but still accepts a width/height and normal box-model padding, like a block would. flex and grid turn the element into a container that arranges its own children along one axis or a two-dimensional grid — the real mechanics of each are their own pages (Flexbox, CSS Grid). display: none is the odd one out: it doesn't just style the box differently, it removes the box from the render tree completely, as if the element were never in the markup.

The three "invisible" options only look the same to the eye. display: none deletes the box — no space reserved, and because there's no box, nothing inside it can be clicked, tabbed to, announced, or even reappear later on its own. visibility: hidden keeps the box exactly where it was, still taking up its layout space, but skips painting it and skips it for focus and assistive tech — unlike display: none, a descendant can set its own visibility: visible and pop back into view even while its hidden ancestor stays invisible. opacity: 0 keeps the box, keeps it in the tab order, and keeps it clickable — it only changes how the pixels are painted, so anything that doesn't depend on pixels still behaves as if the element were fully visible.

These map onto the browser's real rendering stages: display: none skips Layout and Paint both, while visibility: hidden and opacity: 0 still run Layout and only change what happens in Paint — see Browser Rendering for the full pipeline.

💻 See the code ▾
CSS 
.card { display: block; }        /* full-width box, stacks */
.icon { display: inline-block; } /* inline flow, but has a real box */
.badge { display: none; }        /* removed from layout entirely */

block stacks, inline-block flows but keeps a box, none removes the box completely.

CSS 
.a { display: none; }       /* ❌ space, ❌ click, ❌ focus, ❌ reader */
.b { visibility: hidden; }  /* ✅ space, ❌ click, ❌ focus, ❌ reader */
.c { opacity: 0; }          /* ✅ space, ✅ click, ✅ focus, ⚠️ reader */

Same visual result — invisible — three very different runtime behaviors underneath.

CSS 
.panel { visibility: hidden; }
.panel .badge { visibility: visible; } /* ✅ reappears anyway */

Only visibility supports this override — display: none has no box left to un-hide.

🧭 Use Cases — recognize these when they happen to you ▾
1 You collapse an accordion section or switch away from an inactive tab

The panel needs to behave as if it isn't on the page at all — no reserved space, no lingering click target, no tab stop waiting for an accidental Tab press to land on. display:none is built for exactly this: it deletes the box from the render tree, so nothing about it is left behind.

RememberToggling a whole section away → display:none, not just hiding its look.
2 You need to blank one placeholder row without shifting anything else

Removing the row's box entirely with display:none would collapse its space and shift every row below it up. visibility:hidden keeps the row's layout position exactly where it was — it just stops painting it and skips it for focus and screen readers.

RememberNeed the space to stay reserved? visibility:hidden, not display:none.
3 You fade an element out with opacity:0 and assume it's now fully hidden

opacity:0 only changes what Paint draws — the box is still fully in layout, still in the tab order, and still clickable underneath whatever visually replaced it. Assuming "invisible" automatically means "inert" is exactly the trap here.

Rememberopacity:0 fades the pixels, not the interactivity — disable it separately if you need that too.
🌍 Real-world example ▾

Picture a form's error message. display: none is tearing the sentence off the page — the layout reflows as if it were never printed. visibility: hidden is printing it in invisible ink on the same line — the space stays reserved, nothing shifts. opacity: 0 is printing it in white ink on white paper — the words are still fully there, and someone can still tap exactly where they are and trigger whatever's underneath.
