Scenario: Diagnosing a Production Memory Leak

"Heap usage grows continuously in production, eventually causing OutOfMemoryError. Walk through how you'd investigate it."

Why it matters ▾
📈 Growing Heap
❗ Problem"The heap just grows until it crashes" is a symptom, not a diagnosis — restarting the service papers over the real bug, and the same growing object type will come back and bring the next instance down too.
✅ SolutionTake heap dumps, compare them over time to see which object type's retained size keeps growing (not just what's large right now), then trace that type's retaining reference chain back to a GC root — usually a static collection, a registered listener, or an unbounded cache.
RecallCompare dumps over time to find what's GROWING, then trace the retaining chain back to its root.
🔥 Easy interview recall

A leak in Java isn't "unreferenced garbage" — it's an object that's still reachable but no longer needed. Find what's growing across snapshots, then trace it back to its GC root.

Think: a static collection, a listener that was never unregistered, or a cache with no eviction policy.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A single heap dump is enough to find a leak. One snapshot only shows what's large right now — a legitimately big cache looks identical to a leaking one in a single dump; only comparing retained size across multiple dumps over time reveals what's actually still growing.

🔄 Likely Follow-up

"What are the classic causes you'd check first?" A static collection nothing ever removes from, listeners or callbacks registered but never unregistered, and an unbounded in-memory cache with no eviction policy — all three keep an object reachable from a GC root long after it's actually needed.

🎯 Say this in the interview — the exact lines to land

"I'd take heap dumps over time and compare retained size per object type to find what's actually growing, not just what's large — then trace that type's retaining reference chain back to a GC root, which is usually a static collection, an unregistered listener, or an unbounded cache."

  • One dump → only shows size right now, not growth — compare several over time.
  • Retained size growing → trace the reference chain back to its GC root.
  • Classic suspects → static collections, un-unregistered listeners, unbounded caches.
  • A histogram/dominator-tree view → the fastest way to see which type is dominating retained memory.
📖 Explanation ▾

A memory leak in a garbage-collected language sounds like a contradiction, but it isn't one: the garbage collector only reclaims objects that are unreachable from a GC root (a thread's stack, a static field, a JNI reference, and a few other roots). An object a program no longer logically needs, but still holds a reference to somewhere along that chain, stays reachable forever — the GC is working correctly; the program is just still holding the door open.

The practical investigation starts with a heap dump (triggerable via jmap, a JFR recording, or an APM tool's built-in capture) and a tool that can browse it — a histogram view ranks object types by instance count and retained size, and a dominator-tree view shows exactly which object is keeping a whole subtree of memory alive. Taking this snapshot once tells you what's big right now; taking it two or three times, spaced out while the problem is actively happening, tells you what's actually growing — the distinction that separates a real leak from an intentionally large cache.

Once a growing type is identified, the dump's retaining-reference view traces backward from an instance to whatever root is keeping it alive. In practice this is almost always one of three shapes: a static field holding a collection that only ever grows, an observer/listener pattern where a subscriber registers itself but is never removed, or a cache implemented as a plain map with no size limit or expiry.

💻 See the code ▾
Java 
public class EntryCache {
    private static final Map<String, CacheEntry> CACHE = new HashMap<>();

    public void put(String key, CacheEntry entry) {
        CACHE.put(key, entry); // ❌ never evicted — this IS the GC root
    }
}

A static field lives for the whole life of the classloader — every entry ever put in CACHE stays reachable forever.

A bounded, expiring cache (a proven library, not a hand-rolled map) guarantees retained size has a ceiling.

🧭 Use Cases — recognize these when they happen to you ▾
1 Heap usage climbs steadily over days and only a restart brings it back down

This is the #1 scenario you'll actually run into: a slow, steady climb that a restart resets, pointing at a genuine leak rather than a one-off spike. Taking dumps a few hours apart and comparing retained size per type is the fastest way to confirm it and name the type that's actually growing.

RememberA climb that only a restart fixes is the signature of a real leak, not a transient spike.
2 The dominator-tree view shows a single static field retaining most of the heap

A dominator tree answers "if this one object were freed, what else would go with it" — when one static field dominates a huge share of retained heap, that field is almost certainly the leak's actual GC root, not just a large but legitimate structure.

RememberA dominator tree names the one object actually responsible for a whole retained subtree.
3 A listener-based component is garbage collected, but memory still doesn't drop

Candidates often assume removing the last visible reference to a component is enough — but if that component registered itself with an event publisher or listener list and never unregistered, the publisher still holds a live reference, and the whole component (plus everything it references) stays reachable.

RememberAn unregistered listener keeps its whole owning object reachable from the publisher.
🌍 Real-world example ▾

A service's heap grows by roughly 2% an hour until it hits OutOfMemoryError every few days. Three heap dumps taken a day apart show the same CacheEntry type's retained size tripling, and the retaining-reference view traces every instance back to one static Map that was meant to be a short-lived request cache but never had an eviction policy added.
