Slow Time-to-First-Byte — the network, or a route you didn't mean to make dynamic?

"A route's Time-to-First-Byte is much slower than expected — how do you narrow down the cause?"

Why it matters ▾
🐢 Slow Time-to-First-Byte
❗ ProblemA slow Time-to-First-Byte looks like a network or infrastructure issue, but in Next.js it's very often self-inflicted — a route that reads cookies() or headers() unnecessarily gets forced into full dynamic rendering, paying the full render cost on every single request instead of serving a cached response.
✅ SolutionCheck the build output's route listing for which routes are static vs. dynamic, push the rendering strategy toward static/ISR wherever the content doesn't genuinely need to be request-unique, and isolate any slow fetch/database call behind its own Suspense boundary so it streams instead of blocking the whole response.
RecallAn unexpectedly dynamic route is one of the most common self-inflicted TTFB causes.
🔥 Easy interview recall

Slow TTFB in Next.js = check for an unexpectedly dynamic route first, before blaming the network.

Think: cookies()/headers() called where they didn't need to be is the #1 self-inflicted cause.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming a slow TTFB is always a network or infrastructure issue. In Next.js specifically, an unexpectedly dynamic route — one reading cookies() or headers() when it didn't need to — is one of the most common self-inflicted causes, and it has nothing to do with the network at all.

🔄 Likely Follow-up

"How would you confirm a route is unexpectedly dynamic?" Check the build output's route listing — Next.js reports at build time which routes are static and which are dynamic — a route you expected to be static showing up as dynamic is the first clue.

🎯 Say this in the interview — the exact lines to land

"I'd first check whether the route itself is unexpectedly dynamic — a stray cookies() or headers() call forcing full render cost on every request is the most common self-inflicted cause — then profile any specific fetch or database call inside the render path, and consider pushing the route toward static or ISR, or streaming the slow part behind its own Suspense boundary."

  • Route genuinely dynamic (SSR) → pays full render cost every single request.
  • Unexpected dynamic opt-out → a stray cookies()/headers() call forcing it, check the build output's route list.
  • A slow fetch/database call → profile it directly, then isolate it behind its own Suspense boundary.
  • Content that doesn't need to be request-unique → push it toward static/ISR instead of SSR.
📖 Explanation ▾

A route rendered dynamically — on-demand, server-side, no caching — pays its full rendering cost on every single request, including any data fetching that happens along the way. That cost shows up directly as Time-to-First-Byte, because the browser can't get its first byte of HTML until the server has finished rendering the whole response.

Next.js opts a route into dynamic rendering automatically the moment code in its render path calls something like cookies() or headers() — even if the result of that call isn't actually used to change what's rendered. This is easy to miss: a shared layout or a helper function reading a cookie "just in case" can silently force every route that uses it into dynamic rendering, with no obvious error anywhere.

Once a route is confirmed dynamic for a real reason, the next lever is where the slow part sits. A <Suspense> boundary around just the slow fetch lets the rest of the page's markup reach the browser immediately, streaming the slow piece in afterward — the response starts a lot sooner even though the slow work still has to finish eventually.

💻 See the code ▾
JSX 
import { cookies } from 'next/headers';

export default async function Page() {
  const theme = cookies().get('theme'); // ❌ opts the WHOLE route into dynamic rendering
  return <Article />; // even though theme is never used below
}

The route is now dynamic for every visitor, even though nothing about the rendered output actually depends on the cookie.

JSX 
export default function Page() {
  return (
    <>
      <Article />                          // ✅ served static/ISR, instantly
      <Suspense fallback={<Spinner />}>
        <SlowRecommendations />            // ✅ streams in after, doesn't block TTFB
      </Suspense>
    </>
  );
}

The fast majority of the page reaches the browser immediately — only the genuinely slow piece is isolated and streamed.

🌍 Real-world example ▾

A marketing page's TTFB climbs from under 100ms to over a second after a routine refactor, with no infrastructure changes. Checking the build output's route listing shows the page flipped from static to dynamic — a shared layout started calling headers() to read a locale, forcing every route using that layout into dynamic rendering on every request.
