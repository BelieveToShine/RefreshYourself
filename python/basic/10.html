A circular import isn't a Python bug — it's two modules needing each other before either finishes loading

"What actually happens during an import? How do you avoid a circular import?"

Why it matters ▾
  • Every real codebase is split into modules and packages — knowing what import actually does explains why some code runs twice, or not at all, and when.
  • Circular imports are a genuine, common bug that shows up as a project grows past a single file — interviewers use it to check for real understanding, not memorized syntax.
  • if __name__ == "__main__": shows up in almost every runnable Python file, and interviewers use it to separate "copied the boilerplate" from "actually knows why it's there."
🔥 Easy interview recall

Circular import = "two modules stuck needing each other before either one finishes loading."

Think: import runs a file's top-level code exactly once and caches it in sys.modules — load it out of order, and the trap springs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reordering the import lines "fixes" a circular import. It only works by accident, for whichever import order happens to run first — add a new entry point and the exact same two modules break again; the real fix is restructuring which module owns the shared code, not shuffling import statements.

🔄 Likely Follow-up

"Why does if __name__ == '__main__': matter for testability?" It lets a file be both an importable module — reusable and testable without triggering side effects — and a runnable script, without the import itself ever firing the script's main logic.

🎯 Say this in the interview — the exact lines to land

"A circular import breaks because of load order, not because Python forbids it — whichever module loads first hits the other mid-load, so the fix is restructuring dependencies, not reordering imports."

  • import runs once → Python executes a module's top-level code a single time and caches the finished module in sys.modules.
  • Circular import → A and B import each other at the top level; whoever loads first hits the other before it's finished defining its names.
  • Fix by restructuring → move the import inside a function, or pull the shared code into a third module both sides import instead.
  • __name__ == "__main__" → true only when the file is run directly, letting one file be both an importable module and a runnable script.
📖 Explanation ▾

A module is a single .py file. A package is a directory of modules, usually marked with an __init__.py so import treats it as one unit (modern Python also allows a package with no __init__.py at all, called a namespace package). import x runs module x's top-level code exactly once, caches the finished module object in sys.modules, and binds the name x; from x import y does the same load but binds just y directly.

__name__ is only the string "__main__" when a file is run directly — not when it's imported. That's why if __name__ == "__main__": is the standard guard for code that should only run as a script's entry point, never just because something else imported the file.

A circular import happens when module A imports module B at the top level, and B imports A at its own top level. Whichever one starts loading first runs into the other mid-load — before all of its names exist yet — and hits an ImportError or AttributeError partway through.

Inside a package, from mypackage.sub import thing (absolute) resolves from the top of sys.path, while from .sub import thing (relative) resolves from the current package instead — either style works with any of the three fixes above.

🌍 Real-world example ▾

A new feature module imports from two existing modules that happen to import each other. It works — but only because of the accidental order the app's entry point happens to load things in. Add a second entry point that imports the same two modules in a different order, and the exact same code now throws an ImportError on startup — a classic real circular-import incident, and the fix is the same either way: stop the two modules from needing each other directly.
