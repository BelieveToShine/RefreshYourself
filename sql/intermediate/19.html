Duplicate rows — find them with GROUP BY, delete them with ROW_NUMBER

"How do you find duplicate rows, and delete all but one?"

Why it matters ▾
🔎 Find
❗ ProblemDuplicates hide among thousands of rows.
✅ SolutionGROUP BY the columns that should be unique and keep groups with HAVING COUNT(*) > 1.
RecallFind = GROUP BY + HAVING COUNT(*) > 1.
🗑️ Delete
❗ ProblemDeleting by value would remove every copy, including the one to keep.
✅ SolutionROW_NUMBER() numbers the copies in each group, and you delete the ones numbered above 1.
RecallDelete = number the copies, remove rn > 1.
🛡️ Prevent
❗ ProblemThe same clean-up comes back next month.
✅ SolutionA UNIQUE constraint makes the database reject new duplicates.
RecallPrevent = UNIQUE constraint.
🔥 Easy interview recall

Find → GROUP BY + HAVING COUNT(*) > 1

Delete → ROW_NUMBER(), remove rn > 1

Prevent → a UNIQUE constraint

Think: number the copies 1, 2, 3 — keep number 1, delete the rest.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"SELECT DISTINCT removes the duplicates." It only hides them in the result — the duplicate rows are still in the table, so you need a DELETE.

🔄 Likely Follow-up

"The rows are completely identical, so there is no Id to tell them apart. Can you still delete the extras?" Yes — number the rows with ROW_NUMBER() partitioned by every column and delete through the CTE; which copy survives is arbitrary, and SQL Server lets you delete through a CTE built on a single table.

🎯 Say this in the interview — the exact lines to land

"To find duplicates I GROUP BY the columns that should be unique and keep groups with HAVING COUNT(*) > 1. To delete all but one, I number the copies with ROW_NUMBER() partitioned by those columns in a CTE and delete the rows numbered above 1. Then I add a UNIQUE constraint so they cannot return."

  • Find → GROUP BY the key columns, HAVING COUNT(*) > 1.
  • Delete → ROW_NUMBER() OVER (PARTITION BY …) in a CTE, then DELETE WHERE rn > 1.
  • ORDER BY inside OVER → decides which copy survives, for example the lowest Id.
  • DISTINCT → hides duplicates in a result; it does not remove them.
  • Prevent → a UNIQUE constraint or unique index.
📖 Explanation ▾

Finding is plain aggregation. Group by the columns that define "the same row", count each group, and use HAVING — not WHERE, because the count only exists after grouping. Any group with a count above 1 is a set of duplicates.

Deleting needs a way to single out the extras. ROW_NUMBER() numbers each copy inside its group, so number 1 is the keeper and every higher number is a spare. In SQL Server you can run DELETE straight against a CTE over one table, which removes the matching rows from the base table. Run the same CTE with a SELECT first to preview what would go, and add a UNIQUE constraint afterwards.

💻 See the code ▾
T-SQL 
SELECT Email, COUNT(*) AS Copies
FROM Users
GROUP BY Email
HAVING COUNT(*) > 1;   -- ✅ one row per duplicated email

Find: only groups with more than one row survive the HAVING.

T-SQL 
WITH Numbered AS (
    SELECT Id,
           ROW_NUMBER() OVER (PARTITION BY Email ORDER BY Id) AS rn   -- 1 = the copy to keep
    FROM Users
)
DELETE FROM Numbered WHERE rn > 1;   -- removes every extra copy, keeps the lowest Id

Delete through the CTE removes the rows from Users. Swap in SELECT * first to preview.

T-SQL 
ALTER TABLE Users ADD CONSTRAINT UQ_Users_Email UNIQUE (Email);   -- ✅ new duplicates are rejected

Add the constraint only after the clean-up, or it fails on the existing duplicates.

🌍 Real-world example ▾

Two copies of the same person on a guest list: group the names, spot the ones that appear twice, number them 1 and 2, and cross out every number 2.
