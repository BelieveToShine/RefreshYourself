External sort — bigger than RAM doesn't mean impossible

"How would you sort or process a dataset that's too large to fit into memory?"

Why it matters ▾
  • Senior/architect interviews reach for exactly this scenario — a file bigger than RAM — to check whether you know disk-based algorithms exist at all, not just in-memory ones.
  • A natural follow-up once a candidate has explained an in-memory sort — "fine, now it doesn't fit."
  • A bridge into distributed processing: the same split-then-combine shape scales from one disk to many machines.
🔥 Easy interview recall

Split → memory-sized chunks

Sort each → in RAM, write to disk

Merge → k-way, one small heap

Think: external sort is merge sort stretched across disk instead of RAM.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just re-read from disk inside a loop" is not the fix. Repeatedly re-reading the whole file from disk for every comparison multiplies disk reads instead of controlling them — the actual goal is reading each piece of data from disk roughly once, since disk I/O, not CPU, is the dominant cost here.

🔄 Likely Follow-up

"You need to sort a 100GB file on a machine with 8GB of RAM — walk me through your approach." Split the file into chunks small enough to sort in RAM, sort each one and write it back to disk, then k-way merge every sorted chunk using a small heap that holds just the current front element of each chunk — pulling a chunk's next element only once its current front has actually been consumed.

🎯 Say this in the interview — the exact lines to land

"External sort splits an oversized dataset into chunks that fit in RAM, sorts each chunk in memory, writes it back to disk, then merges every sorted chunk with a k-way merge — a small heap holding just the current front element of each chunk. Merge sort is the natural fit, because 'sort pieces, then merge' maps directly onto disk-resident chunks, which quicksort's in-place partitioning doesn't."

  • Split → chunks that fit in RAM, sorted one at a time.
  • Sort each chunk → in-memory merge sort, then written back to disk.
  • Merge → k-way merge with a small heap, one front element per chunk.
  • Doesn't fit at all → the OS's own virtual-memory paging kicks in, usually far slower than a deliberately chunked algorithm.
  • Beyond one machine → the same split → process → combine shape extends to multiple machines working in parallel.
📖 Explanation ▾

Every in-memory sort — including the ones on the Basic tier's Sorting page — quietly assumes the whole dataset can sit in RAM at once. Once the dataset is bigger than available memory, that assumption breaks: the algorithm has to be redesigned around moving small chunks between disk and memory on purpose, instead of loading everything in one shot.

External sort is the classic answer: split the oversized dataset into chunks small enough to fit in memory individually, sort each chunk with a normal in-memory sort, write each sorted chunk back to disk, then merge all the sorted chunks with a k-way merge — the same technique from the Basic tier's Heaps / Priority Queues page, just reading each chunk's next value from its file on disk instead of from an in-memory list. Merge sort fits this naturally because its whole structure is "sort independent pieces, then merge them" — that maps directly onto "sort what fits in memory, then merge across disk-resident pieces." Quicksort's in-place partitioning doesn't decompose the same way, so it isn't the natural fit here.

Processing data in fixed-size batches — read N records, process them, move on — is the same bounded-memory idea as the Streaming / Large-Dataset Problems page, aimed at a different situation: there, data keeps arriving over time; here, the data is finite but simply too large to hold all at once. Left unmanaged, the OS can fall back to virtual-memory paging — swapping pieces between RAM and disk on its own schedule — which is usually much slower than a deliberately chunked algorithm, since the OS has no idea what the algorithm is actually going to touch next and can end up thrashing the same data in and out. When even one machine's disk and memory together aren't enough, the same split-then-combine shape extends across multiple machines, each handling its own chunk in parallel before results are combined — the same shape MapReduce-style systems are built around, though coordinating multiple machines is its own subject, outside what DSA covers.

💻 See the code ▾
C# 
const int ChunkSize = 500_000; // however many records fit safely in RAM
var chunkFiles = new List<string>();
var batch = new List<int>(ChunkSize);

foreach (var record in ReadRecords(hugeFile))
{
    batch.Add(record);
    if (batch.Count == ChunkSize)
    {
        batch.Sort();                          // ✅ normal in-memory sort (merge sort)
        chunkFiles.Add(WriteChunkToDisk(batch));
        batch.Clear();                         // free the memory for the next chunk
    }
}
if (batch.Count > 0) { batch.Sort(); chunkFiles.Add(WriteChunkToDisk(batch)); }

Peak memory stays bounded at ChunkSize records — no matter how huge the original file actually is.

C# 
var readers = chunkFiles.Select(f => new StreamReader(f)).ToArray();
var heap = new PriorityQueue<int, int>();

for (int i = 0; i < readers.Length; i++)
    heap.Enqueue(i, int.Parse(readers[i].ReadLine())); // one front value per chunk

while (heap.Count > 0)
{
    int chunk = heap.Dequeue();                // ✅ smallest front, across ALL chunks
    string? next = readers[chunk].ReadLine();
    if (next != null) heap.Enqueue(chunk, int.Parse(next)); // pull that chunk's NEXT value only now
}

Only one line per chunk ever sits in memory at a time — the heap holds each chunk's front value, never the whole chunk.

🌍 Real-world example ▾

Picture sorting a warehouse of paper files using only one small desk. You can't spread everything out at once, so you sort one desk-sized stack at a time, stack each sorted pile back on a shelf, then walk the shelves picking whichever pile's next paper comes first — until every paper's been picked up, in order.

Scaling further: when even one machine's disk isn't enough — or the job simply needs to finish faster than one machine can manage — the same split-process-combine shape spreads across multiple machines, each sorting or processing its own chunk in parallel before the results are combined. That's the same shape systems like MapReduce are built around; coordinating multiple machines is a distributed-systems topic in its own right, not something this DSA track teaches in depth.
