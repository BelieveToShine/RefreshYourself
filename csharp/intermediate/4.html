Operator overloading — making + mean something for your own type

"What's a realistic case for overloading an operator?"

Why it matters ▾
  • Comes up the moment a domain type — money, vectors, coordinates — needs to be added, compared, or sorted like a built-in number.
  • A realistic way to introduce a real bug: overloading == and forgetting to keep Equals()/GetHashCode() in sync with it.
  • Interviewers use it to check you know operators are just specially named methods, not compiler magic.
🔥 Easy interview recall

Operator overloading = "teaching + (or -, ==, …) to run your own code for your own type."

Think: m1 + m2 only works because you wrote operator + yourself — overload == and you must keep Equals()/GetHashCode() in step, or collections start lying.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Overloading == without also overriding Equals() and GetHashCode(). == now says two Money values are equal, but hash-based collections still group by the old, untouched GetHashCode() — a Dictionary or HashSet can silently fail to find an entry that == calls equal.

🔄 Likely Follow-up

"Should you overload comparison operators like < and > too?" Only when the type has one genuine, unambiguous ordering — Money comparing Amount is fine, but forcing < onto a type with no natural order just confuses callers who assume the operator means the obvious thing.

🎯 Say this in the interview — the exact lines to land

"Operator overloading lets a type define what +, -, ==, and similar operators mean for it — a Money type defining + as adding two amounts. It only makes sense when the operator has one obvious, natural meaning, and overloading == always has to come with matching Equals() and GetHashCode() overrides, or equality checks and hash-based collections start disagreeing."

  • operator + → define it once, then m1 + m2 reads like normal math everywhere.
  • Only overload when there's one obvious meaning — Money, vectors, complex numbers, not arbitrary business types.
  • Overload == → also override Equals() and GetHashCode(), every time.
  • Skip that, and Dictionary/HashSet lookups silently disagree with what == just told you.
📖 Explanation ▾

An overloaded operator is just a specially named public static method. When the compiler sees m1 + m2 and both sides are Money, it rewrites that expression into a call to Money.operator +(m1, m2) — there's no separate "operator syntax" happening at runtime, only at compile time, when the call is decided. The method almost always returns a brand-new instance rather than mutating either operand, the same way int + int never changes either number.

== and .Equals() are supposed to answer the exact same question — "are these the same value?" Hash-based collections like Dictionary and HashSet trust GetHashCode() to sort items into buckets before they ever call Equals() or == to confirm a match. Overload == alone and that trust breaks silently — the compiler even warns about it (CS0660/CS0661), but still lets the code build.

💻 See the code ▾
C# 
public class Money
{
    public decimal Amount { get; }
    public Money(decimal amount) => Amount = amount;

    public static Money operator +(Money a, Money b)
        => new Money(a.Amount + b.Amount);
}

Money total = new Money(30) + new Money(20);  // ✅ Amount = 50 — plain math, no .Add() needed

operator + is a specially named static method — the compiler calls it every time it sees + between two Money values.

C# 
public static bool operator ==(Money a, Money b) => a.Amount == b.Amount;
public static bool operator !=(Money a, Money b) => !(a == b);
// ⚠️ CS0660/CS0661 — compiler warns, but still compiles

Equals() and GetHashCode() weren't touched — Money now has two different, disagreeing ideas of equality.

C# 
var seen = new HashSet<Money>();
seen.Add(new Money(30));
seen.Contains(new Money(30));   // ❌ false — GetHashCode() still checks object identity

HashSet checks GetHashCode() before it ever calls ==, so the overloaded == never even runs here.

🌍 Real-world example ▾

Your billing service adds up line-item Money values all over the codebase. Writing money1.Add(money2) everywhere is legal, but operator + lets that arithmetic read exactly the way a finance person would write it on paper — total = subtotal + tax + shipping — as long as Equals() and GetHashCode() stay honest wherever == gets overloaded too.
