forwardRef & useImperativeHandle — exposing an API, not the whole node

"How would you let a parent call a method on a child component — like focusing an input inside a custom wrapper?"

Why it matters ▾
  • Function components don't accept ref as an ordinary prop — a parent that tries to put one on a custom component gets undefined without this.
  • Comes up any time a design-system component (a custom <Input>, <Modal>) needs to expose one imperative action — focus(), open() — without handing over its entire internals.
  • Interviewers use it to check you know the difference between forwarding a ref and deliberately narrowing what it exposes.
🔥 Easy interview recall

forwardRef → lets the ref reach the child at all

useImperativeHandle → decides what that ref actually sees

Think: forwardRef opens the door; useImperativeHandle decides what's on the other side of it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for useImperativeHandle as a default way to talk to a child is a design smell, not a normal pattern. It bypasses React's usual data flow (props down, callbacks up) and couples the parent directly to the child's internal API — reserve it for the rare case that's genuinely imperative by nature (focus, scroll, play/pause), not as a substitute for passing props.

🔄 Likely Follow-up

"Do you still need forwardRef in React 19?" Not always — React 19 lets a function component receive ref as a plain prop without wrapping it in forwardRef at all. forwardRef still matters for code that has to support 18 or earlier, and useImperativeHandle still matters either way whenever the exposed API needs to be narrower than the raw node.

🎯 Say this in the interview — the exact lines to land

"forwardRef lets a ref reach a function component at all, since function components don't accept ref as an ordinary prop. useImperativeHandle, called inside that forwarded component, decides exactly what the parent's ref sees — usually a small, deliberate set of methods, not the raw DOM node."

  • forwardRef → lets the ref through — without it, a ref on a function component is undefined.
  • useImperativeHandle → narrows what's exposed — a chosen handle, not the whole element.
  • Overuse → a design smell — it skips props/callbacks, keep it rare and deliberate.
  • React 19 → ref can be a plain prop — forwardRef isn't always required anymore, but the narrowing idea still is.
📖 Explanation ▾

forwardRef exists because a function component's own props object never contains ref — React strips it out before the component ever sees it, the same way it strips out key. Wrapping a component in forwardRef((props, ref) => ...) gives that component a second, explicit parameter carrying whatever ref the parent attached, so it can be handed off to a real DOM node (or to useImperativeHandle) instead of silently going nowhere.

useImperativeHandle(ref, () => ({...})) is the piece that decides what the parent actually receives once the ref does arrive. Without it, forwarding a ref straight onto a <input> hands the parent the entire native DOM element — every property and method it has, whether or not that was ever the intent. useImperativeHandle replaces that with whatever small, custom object the second argument returns, so the parent's ref.current becomes exactly the narrow API the child author chose to expose — { focus, clear }, say — and nothing else.

The two exist together on purpose: forwardRef is the plumbing that lets a ref travel at all, useImperativeHandle is the decision about what it's allowed to touch once it gets there. Most components never need either — this is specifically for the case where a parent genuinely needs to *do* something imperative to a child (focus it, scroll it into view, play/pause it) that props alone can't express.

💻 See the code ▾
JSX 
const FancyInput = forwardRef((props, ref) => {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus() { inputRef.current.focus(); },   // only this
    clear() { inputRef.current.value = ''; }
  }));

  return <input ref={inputRef} {...props} />;
});

// parent: ref.current.focus() works — ref.current.value does not

The parent's ref only ever sees focus and clear — never the raw input element underneath.

🌍 Real-world example ▾

A hotel front desk, not a master key. A guest can ask the front desk to open their own room, request a wake-up call, or ask for extra towels — a handful of specific, allowed actions. They don't get handed a master key to the whole building. useImperativeHandle is the front desk: it decides exactly which requests get honored, instead of handing over unrestricted access to everything behind it.
