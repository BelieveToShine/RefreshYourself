A cache should degrade performance when it fails, not break the app

"What should actually be cached, and what happens when the cache fails?"

Why it matters ▾
🗂️ Redis
❗ ProblemA flat key-value cache alone can't back a leaderboard (needs sorted sets), a durable session store (needs persistence), or a live pub/sub channel — those need real data structures and durability, not just fast lookups.
✅ SolutionRedis adds richer data structures (lists, sets, hashes, sorted sets), optional disk-backed persistence, replication for HA, and pub/sub — everything a flat cache can't offer.
RecallRedis = structures + persistence + replication + pub/sub, at the cost of being mostly single-threaded.
⚡ Memcached
❗ ProblemReaching for Redis's structures, persistence, and replication when a workload never needs any of them just adds operational complexity for no benefit.
✅ SolutionMemcached deliberately skips all of that — plain key-value strings/blobs only, multi-threaded, no persistence, no replication — the simplest, fastest flat cache and nothing else.
RecallMemcached = simple, multi-threaded, flat cache only — pick it when Redis's extras would go unused.
🔥 Easy interview recall

Cache-aside = "check the cache first, fall through to the real source on a miss."

Think: if Redis goes down, the app should just get slower, hitting the real database directly — never go down with it.

🧠 Redis vs. Memcached — what actually decides which one
⚠️ Common Trap

"If Redis goes down, the app goes down." That's an architecture risk, not a caching decision — a cache is meant to be a performance optimization, and the app has to be built to tolerate a cache miss or outage gracefully, falling back to the real source instead of erroring out.

🔄 Likely Follow-up

"Redis vs. Memcached — the real deciding factor?" Need replication, persistence, pub/sub, or richer data structures → Redis. Need the simplest possible flat cache with multi-threaded performance and nothing else → Memcached.

🎯 Say this in the interview — the exact lines to land

"Cache-aside plus a graceful fallback to the real source is the pattern — losing the cache should degrade performance, not break the app."

  • Redis → richer data structures, persistence, replication/HA, pub/sub — pick it when you need more than a flat key-value cache.
  • Memcached → simple, pure cache, multi-threaded — pick it when you just need the fastest, simplest flat cache and nothing else.
  • Cache-aside → app checks the cache first; on a miss it reads the real source and populates the cache.
  • Cache invalidation → deciding when cached data is stale is the genuinely hard part, not the caching itself.
📖 Explanation ▾

ElastiCache is AWS's managed in-memory caching service, running either Redis or Memcached. Both hold data in memory for very fast reads, but they solve slightly different problems. Redis supports richer data structures (lists, sets, hashes, sorted sets), on-disk persistence, replication for high availability, and pub/sub messaging. Memcached is deliberately simpler — a pure key-value cache, multi-threaded, with no persistence and no replication.

The most common pattern is cache-aside: the app checks the cache first; on a hit it returns immediately; on a miss it reads the real source (usually a database) and writes the result into the cache before returning it. The genuinely hard part isn't the cache-aside logic itself — it's cache invalidation, deciding when cached data has gone stale and needs to be refreshed or removed.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app needs a leaderboard, a durable session store, or a live pub/sub channel — not just a flat cache

A leaderboard needs sorted sets, a session store needs durability, and a pub/sub channel needs pub/sub — none of which a plain flat cache has. This is the scenario Redis's extra features actually exist for.

RememberNeed structures, durability, or pub/sub → Redis.
2 You just need the fastest, simplest flat cache in front of a database — nothing else

Nothing here needs structures, persistence, or replication — Memcached's simpler, multi-threaded design is the leaner pick, and Redis's extra capabilities would just go unused.

RememberSimplest flat cache, nothing else → Memcached.
3 A cache node fails, and the cluster needs to keep serving without customers noticing

Redis supports replication for HA, so a failed node fails over to a replica and the cluster keeps serving. Memcached has no replication at all — a node failure there just means those cached entries are gone, with no automatic failover.

RememberNeed failover → Redis; Memcached has none.
🌍 Real-world example ▾

A product catalog page reads from an ElastiCache Redis cluster first. When that Redis cluster fails an upgrade and goes briefly unavailable, the app transparently falls back to querying RDS directly — staying correct, just slower, instead of throwing errors at every visitor.
