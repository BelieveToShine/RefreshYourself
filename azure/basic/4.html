Storage Account — one account, four very different jobs

"What is an Azure Storage Account, and what are the main things you'd store in one?"

Why it matters ▾
🖼️ Blob
❗ ProblemPhotos, backups, and logs don't fit into rows or columns.
✅ SolutionBlob stores each file as a flat named object.
RecallBlob = unstructured files, stored flat by name.
🔑 Table
❗ ProblemA full table scan is too slow for lookups.
✅ SolutionTable indexes NoSQL rows by key for instant reads.
RecallTable = NoSQL rows, fast lookup by key.
✉️ Queue
❗ ProblemOne slow service shouldn't block every other component.
✅ SolutionQueue holds messages until a consumer is ready.
RecallQueue = messages that decouple app components.
🗂️ File
❗ ProblemSeparate VMs need one shared drive, not local disks.
✅ SolutionFile exposes an SMB share many machines can mount.
RecallFile = SMB share, mountable like a network drive.
🔥 Easy interview recall

Blob → files (images, backups, logs)

Table → NoSQL key-value rows

Queue → messages between services

File → SMB shared file system

Think: one Storage Account is like one office building with four separate departments inside it.

⚠️ Common Trap

A Blob "container" is not a Docker container. It's just a folder-like grouping inside a Storage Account for organizing blobs — same word, completely unrelated to a Docker/OCI container that packages and runs an application.

🔄 Likely Follow-up

"What are blob access tiers?" Hot, Cool, and Archive — a tradeoff between storage cost and retrieval cost/latency: the cheaper the tier is to store in, the more it costs (and the longer it takes) to read the data back.

🎯 Say this in the interview — the exact lines to land

"One Storage Account, four services: Blob, Table, Queue, File — each one built for a different shape of data, all reachable under the same account."

  • Blob → unstructured files — images, backups, logs — organized into containers.
  • Table → NoSQL key-value rows, fast lookups by key.
  • Queue → lightweight messaging between app components or background jobs.
  • File → SMB file shares, mountable like a network drive.
  • Access → account key, SAS token, or Entra ID/RBAC — never hardcode the key.
📖 Explanation ▾

A Storage Account is a namespace — one account, one set of endpoints — that can hold four distinct storage services: Blob (unstructured objects/files), Table (a NoSQL key-value store), Queue (simple messaging), and File (SMB file shares). They share the account and its billing, but each one has its own data model and its own way of being read and written.

Blobs don't sit loose in the account — every blob lives inside a container, which is just a flat grouping used to organize and scope access to blobs, nothing more. Whatever the service, access always comes down to one of three things: the account's own access key (full control, so it's treated like a secret), a SAS token (a scoped, time-limited permission slip), or Microsoft Entra ID identity with RBAC roles assigned (the preferred approach for apps, since nothing secret has to be stored at all).

💻 See the code ▾
Azure CLI 
az storage blob upload \
  --account-name mystg \          -- the Storage Account
  --container-name images \       -- the blob container
  --name pic.jpg \                -- the blob's name once uploaded
  --file ./pic.jpg

One blob (pic.jpg) uploaded into one container (images) inside one Storage Account (mystg) — the same account could just as easily hold a Queue or Table alongside it.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to store and serve user-uploaded files, like photos or PDFs

Each upload becomes one blob inside a container — flat, addressed directly by name, with no real folder structure underneath. This is the default choice the moment the data is a file rather than rows.

RememberPhotos, backups, logs → Blob, organized in containers.
2 You need to look up one specific record instantly, without scanning everything

Table storage keys every row by PartitionKey and RowKey — give both and the read is a near-instant point lookup; leave the key out and it scans the whole partition instead.

RememberTable = fast by key, slow without one.
3 Two parts of your app need to talk without one waiting on the other

A producer drops a message in the queue; a consumer picks it up, and the message stays invisible until it's explicitly deleted — or it reappears if the consumer never finishes.

RememberQueue = decouples producer and consumer, safely.
🌍 Real-world example ▾

An app stores every uploaded user photo as a blob, drops a message in a queue whenever a background job needs to run (like generating a thumbnail), and keeps session metadata in table storage for quick lookups — three completely different data shapes, all living under one Storage Account.
