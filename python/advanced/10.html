Blocking code inside async def doesn't just slow down its own task — it freezes every other task on the event loop too

Blocking (synchronous, CPU-bound or blocking-I/O) code is called directly inside an async def function with no await around it — what happens to every other task on the event loop while it runs?

Why it matters ▾
  • A single blocking call inside one handler silently stalls every other concurrent request on that same worker — a real, recurring production incident category, not a rare edge case.
  • Checks whether you understand asyncio is single-threaded cooperative concurrency, not automatic parallelism — a common gap for anyone who assumes async def alone makes the code inside it non-blocking.
  • A near-guaranteed follow-up right after any basic asyncio question — it separates someone who's used async/await syntax from someone who actually understands what it's protecting.
🔥 Easy interview recall

Async = "one thread, many waiting tasks, cooperative switching only at await."

Think: await → hands control back to the loop no await + a real blocking call → the WHOLE loop freezes, not just that task

🧠 Visual Mental Model — understand it in 5 seconds
🔮 Predict the Output
Python 
import asyncio, time

async def handler(name):
    print(f"{name} starting")
    time.sleep(3)          # ❌ blocking call, no await!
    print(f"{name} done")

async def main():
    await asyncio.gather(handler("A"), handler("B"), handler("C"))

asyncio.run(main())

What happens to every other task on the event loop while handler("A") runs its time.sleep(3)?

Answer: Calling a genuinely blocking function — time.sleep(3), or a synchronous blocking network/DB call — directly inside an async def handler, with no await, freezes the entire event loop for that duration. Every other task that was supposed to be running concurrently on that same loop is completely stalled too, because nothing yields control back to it. It isn't "this one handler gets slow" — it's "every concurrent handler on this loop gets slow." B and C won't even print "starting" until A's blocking sleep finishes.

⚠️ Common Trap

async def alone does not make the code inside it non-blocking. It only means the function CAN be paused at an await — calling real blocking code with none inside it blocks the whole event loop just as badly as it would in synchronous code, arguably worse, since it now stalls every other task that was relying on that same loop staying responsive.

🔄 Likely Follow-up

"How do you call synchronous code from async code without blocking the loop?" Run it in a separate thread — await asyncio.to_thread(...) in modern Python, or loop.run_in_executor(...) — so the blocking call happens off the event-loop thread, and await the result instead of calling it directly inline.

🎯 Say this in the interview — the exact lines to land

"async def doesn't make code inside it non-blocking — blocking code with no await inside it freezes the ENTIRE event loop, not just that one task."

  • Blocking with no await → stalls every other task on that loop, not just the caller.
  • asyncio.to_thread() / run_in_executor() → the fix — runs genuinely blocking code off the event-loop thread.
  • Task → actually schedules a coroutine to run concurrently Future → just a placeholder for a result not yet available
  • asyncio is best for many I/O-bound waits, not CPU-bound work — that's multiprocessing's job.
📖 Explanation ▾

Asynchronous code can pause at defined points — an await — to let other work run while it's waiting, instead of blocking the whole program until that one thing finishes. The event loop is the single-threaded scheduler that makes this possible: it runs many coroutines cooperatively, switching between them only at their await points, never in the middle of a line of code. A function defined with async def is a coroutine function — calling it doesn't run its body immediately, it returns a coroutine object that still has to be awaited or scheduled before anything inside it actually executes.

A Future is a low-level placeholder for a result that doesn't exist yet. A Task wraps a coroutine and actually schedules it to run on the event loop, tracking its eventual result — asyncio.create_task(...) is what you reach for to run a coroutine concurrently alongside others, instead of one at a time.

💻 See the code ▾
Python 
import asyncio, time

async def handler(name):
    print(f"{name} starting")      # all three should print this immediately
    time.sleep(3)                    # ❌ blocks the whole loop, not just this task
    print(f"{name} done")

async def main():
    await asyncio.gather(handler("A"), handler("B"), handler("C"))

B and C never even print "starting" until A's time.sleep(3) returns — nothing here ever hands control back to the loop.

Python 
async def handler(name):
    print(f"{name} starting")
    await asyncio.sleep(3)              # ✅ hands control back to the loop
    print(f"{name} done")

Now A, B, and C all start immediately and finish around the same ~3 seconds — await asyncio.sleep() yields control instead of holding it.

Python 
def blocking_call():
    time.sleep(3)                      # a real synchronous, blocking function

async def handler(name):
    print(f"{name} starting")
    await asyncio.to_thread(blocking_call)  # ✅ runs off the event-loop thread
    print(f"{name} done")

asyncio.to_thread() (or loop.run_in_executor()) is the fix when the blocking call itself can't be rewritten as async — it moves the block off the event-loop thread so await can return control while it runs.

🌍 Real-world example ▾

A production incident: one async endpoint accidentally called a synchronous, blocking database driver call with no await around it. Every other concurrent request being served by that same worker's event loop stalled for the exact duration of each of those calls — not just the one request that triggered it — because nothing on that path ever yielded control back to the loop. The fix was swapping the blocking driver call for an async-native one, and wrapping any call that genuinely couldn't be replaced in asyncio.to_thread(...) instead.
