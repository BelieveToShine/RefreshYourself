Scenario: flattening customers and orders with SelectMany

"You have a list of customers, each with a nested list of orders — flatten it into one flat list of orders. How?"

Why it matters ▾
🧺 Nested → flat
❗ ProblemEach customer already holds its own list of orders, but a report, total, or export almost always needs "every order," not "every customer's list of orders" — a nested shape that doesn't compose with the rest of a LINQ pipeline.
✅ Solutioncustomers.SelectMany(c => c.Orders) flattens every customer's orders into one single flat sequence in one call — and the result-selector overload lets you shape each row with fields from both the customer and the order at the same time.
RecallSelectMany = project each customer to their orders, then flatten all of it into one list.
🔥 Easy interview recall

SelectMany(c => c.Orders) → just the orders, flat

SelectMany(c => c.Orders, (c,o) => ...) → orders shaped with customer fields

Think: Select would give you a list of lists. SelectMany flattens that one level down to a single list.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A customer with no orders yet isn't automatically safe. If c.Orders can be null instead of an empty list, SelectMany(c => c.Orders) throws a NullReferenceException on that customer — guard with c.Orders ?? Enumerable.Empty<Order>() or ensure the collection is always initialized.

🔄 Likely Follow-up

"How would you get the total order value per customer, in the same flat shape?" customers.SelectMany(c => c.Orders, (c, o) => new { c.Name, o.Total }) — the result-selector overload projects each flattened row with fields from both levels at once, instead of flattening first and joining the customer back in separately.

🎯 Say this in the interview — the exact lines to land

"I'd call customers.SelectMany(c => c.Orders) — it projects each customer to their orders and flattens the result into one sequence in a single step. If I need fields from the customer alongside each order, I'd use the result-selector overload: SelectMany(c => c.Orders, (c, o) => new { c.Name, o.Total })."

  • Plain flatten → SelectMany(c => c.Orders), just the orders.
  • Need both levels' fields → the result-selector overload shapes both in one call.
  • Select instead of SelectMany → gives a list of lists, not a flat one.
  • A customer with no orders → make sure the collection is empty, never null.
📖 Explanation ▾

Each customer already owns its own Orders collection, so customers.Select(c => c.Orders) produces a sequence of order-collections — one per customer, still nested exactly the way the source data is. SelectMany does the same per-customer projection, then flattens every one of those inner sequences down into a single, flat result — the whole reason it exists over plain Select.

The realistic version of this task rarely wants just the orders — a report usually needs to know which customer each order belonged to as well. The result-selector overload, SelectMany(c => c.Orders, (c, o) => ...), gives you both the outer element (c) and the inner element (o) together at projection time, so the shaped result can combine fields from both without a separate join step afterward.

A nested foreach would get the same data, but it's imperative and doesn't compose with the rest of a LINQ pipeline — no chaining a Where or OrderBy onto a loop. SelectMany keeps the whole operation inside one expression that composes like any other LINQ query.

💻 See the code ▾
C# 
// Just the orders, flattened into one sequence
var allOrders = customers.SelectMany(c => c.Orders);
// ✅ IEnumerable<Order> — no nested structure left

Equivalent query syntax: from c in customers from o in c.Orders select o — same flattening, written as two from clauses.

C# 
// Realistic version — shaped with fields from BOTH levels
var report = customers.SelectMany(
    c => c.Orders,
    (c, o) => new { c.Name, o.Total }); // ✅ customer + order fields, one row per order

The result-selector overload hands you both c and o at once — no separate join needed to bring the customer's name back in.

C# 
// Guard against a customer whose Orders collection is null
var safeOrders = customers.SelectMany(c => c.Orders ?? Enumerable.Empty<Order>());
// ✅ a customer with no orders just contributes zero rows, no exception

Without the ?? guard, a single customer with a null Orders property throws for the whole query, not just that one customer.

🧭 Use Cases — recognize these when they happen to you ▾
1 You just need "every order," regardless of which customer it belongs to

This is the simplest and most common case — a total order count, a sum of all order totals, or any calculation that doesn't care which customer an order came from. The plain form is all you need.

RememberJust need the orders → the plain SelectMany(c => c.Orders) form.
2 A report needs each order's total next to the customer's name

This is the realistic version of the task: the result-selector overload hands you the customer and the order together at projection time, so the shaped row carries fields from both without a separate join afterward.

RememberNeed fields from both levels → the (c, o) => ... result-selector overload.
3 A brand-new customer record has no orders yet, and Orders was never initialized

A single customer with a null Orders property throws a NullReferenceException for the entire query, not just that one customer — because SelectMany tries to enumerate null as if it were a sequence. A common interview trap: assuming an empty-looking customer record is automatically safe to flatten.

RememberOrders could be null → guard with ?? Enumerable.Empty<Order>().
🌍 Real-world example ▾

A nightly finance job needs a single flat table of every order across every customer, with the customer's name attached to each row. customers.SelectMany(c => c.Orders, (c, o) => new { c.Name, o.Total }) produces exactly that shape in one step — no intermediate list of lists, no separate join back to the customer.
