Model binding internals — who wins the source race, and which framework catches the result?

"How does model binding actually decide where to pull a value from, and when would you reach for MVC vs. a pure Web API vs. Razor Pages?"

Why it matters ▾
  • A silent wrong value in a bound parameter is almost always the binder picking a different source than the one you expected — knowing the priority order is how you debug that fast.
  • The custom-binder question checks whether you understand why the default binder exists at all, not just that [FromBody]/[FromQuery] are things.
  • Picking MVC vs. Web API vs. Razor Pages for a new feature is a common system-design follow-up — especially for anyone who's only ever worked in one of the three.
🔥 Easy interview recall

Route values → 1st, straight from the URL path

Query string → 2nd, after the ?

Form body → 3rd, only on a POST form

Think: MVC → full pages Web API → JSON only Razor Pages → simple CRUD, no controller

⚠️ Common Trap

You don't have to pick just one for the whole app. MVC controllers, Web API controllers, and Razor Pages can all live in the same ASP.NET Core project side by side — they plug into the same underlying endpoint routing, so mixing them per feature is normal, not a compromise.

🎯 Say this in the interview — the exact lines to land

"The default binder checks route values first, then the query string, then the request form body — headers and services are bound explicitly with [FromHeader] and [FromServices] instead of joining that priority chain. I'd reach for MVC when I need full server-rendered views, a Web API controller for a JSON-only REST API, and Razor Pages for a simple, mostly-CRUD page-per-feature app — and a real project can mix all three."

  • Binder priority → route values win first, then query string, then form body.
  • Custom binder → needed for app-specific parsing, e.g. a comma-separated ?ids=1,2,3 into a List<int>.
  • MVC → use for full HTML pages with shared layouts and navigation.
  • Web API ([ApiController]) → use for a JSON-only REST API consumed by a SPA, mobile app, or another service.
  • Razor Pages → use for simple, page-per-feature CRUD — no separate controller needed.
📖 Explanation ▾

Route values are checked first — anything captured by the route template (like {id}) wins on a name match before anything else is even looked at. The query string is checked next, then the request form body for a traditional POST form submission. [FromHeader] and [FromServices] sit outside this chase entirely — they bind explicitly by attribute, never by search order. For a complex or nested type, the binder repeats this same source search recursively, property by property. (Model Binding & Validation covers how triggering and validation actually work — this page picks up from there, on where the bound value comes from.)

The default binder only knows how to match one value to one property by name — it can't apply logic on top of that. A query string like ?ids=1,2,3 won't bind to a List<int> on its own, and a value object like Money or EmailAddress can't be parsed from a single string with its own validation baked in. That's what IModelBinder is for: implement it, then register it with [ModelBinder(BinderType = ...)] on the parameter (or a binder provider for something reusable), and the framework calls it instead of the default just for that one parameter.

MVC, Web API, and Razor Pages aren't three separate frameworks — they're three shapes built on the same endpoint routing, and the right one depends on what the endpoint actually needs to produce.

💻 See the code ▾
C# 
public class IntListBinder : IModelBinder
{
    public Task BindModelAsync(ModelBindingContext ctx)
    {
        var raw = ctx.ValueProvider
            .GetValue(ctx.ModelName).FirstValue; // "1,2,3"
        if (raw is null) return Task.CompletedTask;

        // ✅ the default binder can't split one value into a list
        var ids = raw.Split(',').Select(int.Parse).ToList();
        ctx.Result = ModelBindingResult.Success(ids);
        return Task.CompletedTask;
    }
}

The default binder expects one value per key — ?ids=1,2,3 would otherwise bind an empty List<int>.

C# 
[HttpGet("products")]
public IActionResult GetByIds(
    [ModelBinder(BinderType = typeof(IntListBinder))] List<int> ids)
{
    // GET /products?ids=1,2,3 → ids = [1, 2, 3]
    return Ok(_products.Where(p => ids.Contains(p.Id)));
}

[ModelBinder(BinderType = ...)] overrides the default binder for just this one parameter — every other parameter still binds normally.

C# 
// MVC — returns a rendered view
public class OrdersController : Controller
{
    public IActionResult Index() => View(_orders.All());
}

// Web API — JSON only, no views
[ApiController]
public class OrdersApiController : ControllerBase
{
    [HttpGet] public IActionResult Get() => Ok(_orders.All());
}

// Razor Pages — page + its own code-behind, no separate controller
public class IndexModel : PageModel
{
    public void OnGet() => Orders = _orders.All();
}

Same underlying endpoint routing, three different shapes — pick by what the endpoint needs to produce.

🌍 Real-world example ▾

An MVC app that used to feel fine is timing out under real production load. Profile it first (see the follow-up above) — once you know roughly where the time is going, these are the usual suspects:

  • DbContext / query patterns — N+1 queries, or a read-only query missing AsNoTracking().
  • Service lifetime misuse — an expensive dependency built fresh every request instead of cached at a longer lifetime.
  • Sync-over-async blocking — .Result or .Wait() on a Task, which can exhaust the thread pool.
  • View-rendering overhead — an unusually large or complex Razor view, less often the real cause.
