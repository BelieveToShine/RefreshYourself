CSS Variables — the one "variable" still alive after the browser has already rendered the page

"What is a CSS custom property (a CSS variable), and how is it actually different from a variable in a preprocessor like Sass?"

Why it matters ▾
  • Light/dark theme switching is one of the most common practical CSS interview asks, and custom properties are the standard, framework-free way to do it without duplicating every color rule.
  • It's the detail that separates "knows Sass variables" from "understands the platform" — a CSS variable lives in the browser at runtime, so JavaScript can read and change it without any build step.
  • Component libraries and design systems lean on this daily — a component's own local variables let it stay themeable without leaking its internals into the rest of the page.
🔥 Easy interview recall

CSS variable = "a named value (--name) that lives in the browser at runtime — change it, and every var() using it updates instantly, no rebuild."

Think: Sass $var → compiled away before the browser ever sees it --name → still there, live, in the actual rendered page

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A CSS variable isn't just "Sass, but built into the browser." A Sass variable is erased at compile time, before any CSS ships — a CSS custom property is still there in the live page, which is exactly what lets JavaScript read or change it after the page has already loaded.

🔄 Likely Follow-up

"What happens if var(--name) is used but --name was never defined, and there's no fallback?" The property becomes invalid at that point, so the browser treats it as unset — the property falls back to its own inherited or initial value instead of breaking the page. That's exactly the case var(--name, fallback) exists to avoid.

🎯 Say this in the interview — the exact lines to land

"A custom property is defined with --name: value and read with var(--name); it inherits down the DOM like any other CSS value, but unlike a Sass or Less variable it's still live in the browser after the page loads — JavaScript can read or change it with element.style.setProperty(), and every rule using it repaints immediately. That's what makes runtime theme switching possible without rewriting every rule that uses those colors."

  • --spacing: 1rem on :root → inherits everywhere — no need to redeclare it lower in the tree.
  • var(--name, fallback) → a safe default for when the variable is missing or invalid.
  • Live at runtime — setProperty() updates every consumer instantly, unlike a compiled Sass variable.
  • Theme switching → toggle the values, not the rules — a [data-theme="dark"] selector swaps a whole palette in one place.
  • A component can declare its own --card-padding scoped to just itself, separate from the global theme variables.
📖 Explanation ▾

A custom property is any property name starting with two dashes — --spacing, --brand-color — set with --name: value and read anywhere with var(--name). Because it's just a regular CSS value, it inherits down the DOM the same way color does (see the inheritance page) — set once on :root, it reaches every descendant unless something re-declares it lower down.

var(--name, fallback) takes a second argument used only if --name isn't defined (or is invalid) at that point — a safety net so one missing variable doesn't quietly break a whole rule.

The part that actually surprises people coming from Sass or Less: those preprocessor variables are compiled away before any CSS reaches the browser, so nothing about them exists once the page is running. A custom property is never compiled away — it's a real, live value the browser holds onto, which is why element.style.setProperty('--name', value) works: the browser re-renders with the new value right away, no rebuild step involved. That's the mechanic behind theme switching — define a palette as custom properties on :root (or under a [data-theme="dark"] selector), and switching themes becomes toggling which set of values is active, not rewriting every rule that uses them. A component can also define its own local variable, like .card { --card-padding: 1rem; }, which only affects that component's own scope — separate from the site-wide theme variables.

💻 See the code ▾
CSS 
:root {
  --spacing: 1rem;         /* global, set once */
}
.card {
  padding: var(--spacing);   /* reads the global value */
  --card-gap: 0.5rem;     /* local — only .card can see this one */
}

--spacing is a global variable; --card-gap is scoped to .card alone — same syntax, different reach.

CSS 
.btn {
  padding: var(--btn-padding, 0.5rem 1rem); /* used only if --btn-padding is unset */
}

No --btn-padding defined anywhere? .btn still gets a sensible padding instead of nothing.

CSS 
:root                  { --bg: #ffffff; --text: #111827; }
[data-theme="dark"]    { --bg: #111827; --text: #f9fafb; } /* one override point */
body { background: var(--bg); color: var(--text); }

Toggling data-theme on <html> swaps every rule that reads --bg/--text at once — nothing else on the page needs to change.

JS 
document.documentElement.style.setProperty('--spacing', '2rem');
// every var(--spacing) on the page repaints right away — no reload, no rebuild

This line alone is the whole difference from Sass — a Sass variable can never be touched by running JavaScript, because it no longer exists by the time the page runs.

🌍 Real-world example ▾

Scenario: the product wants a light/dark theme toggle, and duplicating every color rule per theme isn't maintainable. Answer: define the palette once as custom properties on :root, override just those properties under [data-theme="dark"], and toggle one attribute — every rule already using var() repaints with the new palette, with zero per-rule duplication.
