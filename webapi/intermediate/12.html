async/await isn't an async API — and JWT isn't security

What makes an API genuinely "async" beyond using async/await, and what should an API guard against beyond authentication?

Why it matters ▾
  • Interviewers use the async question to check you know the difference between "non-blocking code" and a genuinely async API contract — a lot of candidates conflate the two.
  • Comes up any time a feature involves a report, export, bulk import, or anything that can outlast a normal request timeout.
  • The security half is a near-automatic follow-up the moment you say "we use JWT" — it's how an interviewer checks whether you stop at authentication or actually think about the whole request.
🔥 Easy interview recall

async/await → same request, thread just freed

202 + polling → new request, work decoupled

Think: Async API = 202 now, answer later Secure API = auth + input, output, limits, transport, scope, secrets

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"We have JWT auth" does not mean "our API is secure." Authentication only proves who's calling — it says nothing about malformed input, leaked data in a response or error, or whether that caller is allowed to do what it's asking; most real API incidents come from an authenticated caller with too much reach, not an anonymous attacker.

🔄 Likely Follow-up

"For the long-running pattern, what should the initial 202 response actually contain?" A Location header pointing at the status-polling URL — the same convention 201 Created uses — so the client doesn't have to construct that URL itself.

🎯 Say this in the interview — the exact lines to land

"async/await just means the thread isn't blocked while it waits — the client is still in one continuous HTTP call. A genuinely async API returns 202 Accepted immediately with a status URL, and the client polls or gets a callback once the work is actually done. And authentication only proves who's calling — a secure API also validates input, encodes output, rate-limits, enforces HTTPS, applies least privilege, and never leaks secrets in errors or logs."

  • async/await → frees the thread, not the client — still one round trip.
  • 202 Accepted → work happens out-of-band, client polls a Location URL.
  • Input validation → reject bad data before business logic sees it.
  • Output encoding, rate limiting, HTTPS → guard the rest of the request lifecycle, not just identity.
  • Least privilege & secret hygiene → an authenticated caller can still be the incident.
📖 Explanation ▾

async/await is a threading detail, not an API contract. It stops the server thread from sitting idle while it waits on I/O — a database call, another service — but the HTTP request the client made is still exactly one round trip. The client's connection stays open the whole time, waiting for that same response.

A genuinely async API changes the contract itself: for work that can run long (a report, a bulk import), the initial call returns almost instantly with 202 Accepted, and the real work continues somewhere else entirely — a queue, a background worker. The client finds out it's done by polling a status endpoint or receiving a webhook, not by waiting on the original connection.

async/await202 + polling
Client's HTTP callone call, waits for the full resultone fast call, result comes later
What's actually freedthe server thread onlythe whole client connection
Best fornormal request/response workreports, bulk imports, long jobs
How the client learns "done"the same response, when it returnspolling a status URL, or a webhook

Authentication is a single, narrow question: who is this? Everything past that answer is a separate concern. An unvalidated input can carry an injection attack straight past a valid token. An unencoded response can hand a consuming client something it wasn't meant to render. And a caller that's genuinely who they say they are can still be over-scoped — the fix for that is authorization narrow enough that a valid token only unlocks what that caller specifically needs, plus never letting a stack trace or log line hand out a connection string or key by accident.

💻 See the code ▾
C# 
[HttpGet("orders/{id}")]
public async Task<IActionResult> GetOrder(int id)
{
    var order = await _db.Orders.FindAsync(id);  // thread freed while it waits
    return Ok(order);
    // ❌ still ONE HTTP call — client waits for this to finish
}

await here only frees the thread — the client's single request is still open the whole time.

C# 
[HttpPost("reports")]
public IActionResult StartReport([FromBody] ReportRequest req)
{
    var jobId = _jobs.Enqueue(req);    // ✅ real work runs out-of-band
    return Accepted($"/reports/{jobId}/status", new { jobId });
    // ✅ 202 + Location — client polls this URL, doesn't wait here
}

The controller returns in milliseconds — the report itself might take minutes, running somewhere else entirely.

C# 
[Authorize]
[HttpPost("search")]
public IActionResult Search(string term)
{
    var sql = $"SELECT * FROM Products WHERE Name = '{term}'";
    return Ok(_db.RunRaw(sql));
    // ❌ authenticated caller, zero input validation → SQL injection
}

[Authorize] only checked identity — nothing here checked what the caller actually sent.

C# 
catch (Exception ex)
{
    _logger.LogError(ex, "Order create failed");   // ✅ full detail, internal only
    return Problem("Something went wrong.");     // ✅ generic, nothing to leak
    // ❌ returning ex.ToString() to the client can hand out a connection string
}

A secure API's error responses stay generic — the real detail goes to the log, never the client.

🌍 Real-world example ▾

An "export annual report" endpoint starts timing out under load because the export itself takes three minutes, and the request lifecycle only allows thirty seconds. The fix isn't a bigger timeout — it's changing the contract: the endpoint returns 202 Accepted with a job id immediately, a background worker builds the report, and the client polls /reports/{id}/status until it flips to done. Separately, a security review on the same API finds a valid, authenticated service account that can call every endpoint in the system — the incident isn't a broken login, it's a token with far more reach than the one job it was issued for. See Rate Limiting for the abuse-control piece, and Authorization Policies & Claims for narrowing what an authenticated caller can actually do.
