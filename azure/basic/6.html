Cosmos DB — why the same RU/s can feel fast or throttled

"What is Cosmos DB, and what makes it different from a relational database — partition key design and RU/s as the throughput/cost model?"

Why it matters ▾
  • Comes up any time NoSQL vs. relational storage is discussed in an Azure data-tier design question.
  • Explains a real production issue: getting throttled (429 responses) even though plenty of RU/s is provisioned overall.
  • A common opener before a deeper Cosmos DB conversation about modeling, indexing, or consistency levels.
🔥 Easy interview recall

RU/s → the throughput budget, billed per request

Partition key → decides who actually gets to spend it

Think: a high-cardinality key spreads traffic across lanes. A low-cardinality key jams one lane and leaves the rest empty — same RU/s, still throttled.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Just add more RU/s and throttling goes away. Not if the partition key is low-cardinality (e.g. a fixed type field with only a few distinct values) — nearly all the data lands on the same one or two physical partitions, so that hot partition throttles no matter how much RU/s the whole container has provisioned.

🔄 Likely Follow-up

"What makes a good partition key?" A high-cardinality value that's also evenly accessed and matches your most common query pattern — e.g. customerId for a per-customer access pattern.

🎯 Say this in the interview — the exact lines to land

"RU/s is the throughput budget; the partition key decides whether you can actually use it evenly. Every read, write, and query costs a measurable number of RUs, and a poorly chosen key crowds data into a few hot partitions that throttle no matter how much RU/s is provisioned overall."

  • RU/s → the throughput/cost model — every operation has a measurable RU cost.
  • Low-cardinality key → avoid it — a fixed field with only a few values crowds data into a few hot partitions.
  • Good key → high-cardinality, evenly accessed, matches your main query pattern (e.g. customerId).
  • Distribution, not just budget → provisioned RU/s only helps if it's actually reachable evenly across partitions.
📖 Explanation ▾

Cosmos DB is Azure's globally-distributed, multi-model NoSQL database. Instead of billing by CPU time or by the hour, every read, write, and query costs a measurable number of Request Units (RUs), and a container is provisioned with a throughput budget expressed as RU/s. That budget is physically split across every partition the container's data lives on — it isn't one shared pool an application can draw from anywhere.

The partition key is the field Cosmos DB uses to decide which physical partition a document is stored on. A key with many distinct, evenly-hit values spreads documents — and the requests that hit them — across all the partitions, so the provisioned RU/s actually gets used. A key with only a few distinct values crowds most documents onto the same one or two partitions; those specific partitions throttle even though the container's total RU/s looks generous on paper.

💻 See the code ▾
JSON 
{
  "id": "a1b2c3",
  "customerId": "cust-4471",   // ← partition key
  "total": 82.50
}

Every document with customerId: "cust-4471" lands on the same physical partition — that customer's order history is a fast, single-partition read.

🌍 Real-world example ▾

An e-commerce app partitions its orders container by customerId, so every order a given customer ever placed lands on the same physical partition. Looking up "this customer's order history" stays a fast, single-partition query no matter how large the whole container grows.
