Observer — one Subject changes, every Observer finds out

"What is the Observer pattern, and how does it show up in C# itself?"

🧩 Also see the OOP-angle page: Observer Pattern
Why it matters ▾
📡 Observer
❗ ProblemWhen one object's state changes, other parts of the system need to find out — but if the Subject has to call each dependent by its concrete type, it must know about every one of them in advance, and adding a new dependent means editing the Subject's own code.
✅ SolutionObserver gives the Subject a shared Observer interface to loop through instead — it keeps a list, calls Attach/Detach/Notify (or exposes a C# event), and never needs to know the concrete type of anything subscribed to it.
RecallObserver = one Subject notifies many Observers through a shared interface, no direct reference needed.
🔥 Easy interview recall

Observer = "one Subject, many Observers, notified automatically."

Think: Subject → holds the list, fires Notify() Observer → implements Update(), reacts C# event → this exact pattern, built into the language

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Forgetting to unsubscribe (-=) causes a memory leak. The Subject's event delegate holds a reference to every subscribed Observer, so an Observer that should have gone out of scope stays alive as long as the Subject does.

🔄 Likely Follow-up

"Should I always use a C# event instead of a hand-rolled Observer interface?" In most C# code, yes — event is the idiomatic version of this pattern. Reach for Reactive Extensions' IObservable<T>/IObserver<T> instead when you need composable, stream-like push notifications (filtering, combining, throttling multiple sources).

🎯 Say this in the interview — the exact lines to land

"Observer defines a one-to-many dependency: when the Subject's state changes, every registered Observer is notified through a shared interface, without the Subject knowing their concrete types. In C#, the event keyword is a language-level implementation of exactly this pattern — += subscribes, invoking the event notifies, and I always make sure to -= so the Subject doesn't keep the Observer alive."

  • Subject → holds the list, calls Notify(), never knows concrete Observer types.
  • Observer → implements Update() and reacts when notified.
  • C# event → += subscribes, invoking it notifies — Observer built into the language.
  • IObservable<T> → the more explicit, composable version, for push-style streams.
  • Trap to avoid → always -= to unsubscribe, or the Subject keeps the Observer alive.
📖 Explanation ▾

Observer splits a system into a Subject (the thing that changes) and an Observer (something that reacts). The ConcreteSubject holds the real state and a list of subscribers; Attach/Detach add and remove entries from that list, and Notify loops through it calling each one's update method. Every ConcreteObserver implements the same small Observer interface, so the Subject only ever talks to the interface — it never needs to know PriceDisplay from PriceLogger.

C#'s event keyword is this exact pattern, built into the language: the Subject exposes public event Action<decimal>? PriceChanged instead of a hand-written list, and +=/-= stand in for Attach/Detach. Reactive Extensions' IObservable<T>/ IObserver<T> is an even more explicit, GoF-shaped version of the same idea, with the added ability to compose multiple streams together.

💻 See the code ▾
C# 
public class StockTicker
{
    public event Action<decimal>? PriceChanged;   // the "many observers" hook

    public void SetPrice(decimal price) =>
        PriceChanged?.Invoke(price);                         // ✅ notifies every subscriber
}

var ticker = new StockTicker();
ticker.PriceChanged += price => Console.WriteLine($"New price: {price:C}"); // ✅ subscribe

The Subject exposes an event instead of a hand-written list — subscribing is just +=, and notifying is just invoking it.

C# 
public class PriceDisplay : IDisposable
{
    private readonly StockTicker _ticker;

    public PriceDisplay(StockTicker ticker)
    {
        _ticker = ticker;
        _ticker.PriceChanged += OnPriceChanged;    // ✅ subscribe in the constructor
    }

    private void OnPriceChanged(decimal price) => Console.WriteLine(price);

    public void Dispose() =>
        _ticker.PriceChanged -= OnPriceChanged;    // ✅ unsubscribe — without this, PriceDisplay leaks
}

Without the Dispose unsubscribe, _ticker keeps a live reference to PriceDisplay forever, even after nothing else needs it.

🧭 Use Cases — recognize these when they happen to you ▾
1 Several parts of your app must react when one value changes

A price changes, and a display, a logger and an alert all need to know. The ticker just invokes its event, and every subscriber added with += reacts. The ticker never names their types, so adding a fourth one means no edit to the ticker. This is the #1 scenario you'll actually run into.

RememberOne event fired → every subscriber reacts.
2 A short-lived view subscribes to a long-lived ticker and is then thrown away

Many people assume an Observer disappears once nothing else uses it. But the ticker's event holds a reference to every subscriber, so the old view stays alive for as long as the ticker does. Unsubscribe with -=, for example in Dispose.

RememberEvery += needs a matching -=.
3 You need to filter, combine or throttle updates from several sources

A plain event is the right tool for simple notifications. When you need composable, stream-like push updates, such as filtering, combining or throttling several sources, reach for IObservable<T> and IObserver<T> instead — the operators for filtering, combining and throttling come from the Reactive Extensions package (System.Reactive).

RememberSimple notify → event. Stream tricks → IObservable.
🌍 Real-world example ▾

A magazine subscription. The publisher doesn't know who you are individually — it keeps a mailing list and sends the new issue to everyone on it. A YouTube channel's subscribers work the same way: the channel notifies everyone on its list when a new video goes up, without caring who any of them are.
