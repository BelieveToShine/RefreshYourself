The best mock is the one you didn't need to write — mock only what you don't control

"pytest, fixtures, mocking — what should you mock, and what should you NOT mock?"

Why it matters ▾
🧪 Unit vs integration
❗ ProblemTesting everything together makes a failure hard to pin on one piece of logic.
✅ SolutionA unit test checks one small piece in isolation, fast and with no real I/O; an integration test checks several pieces working together.
RecallUnit = one piece. Integration = pieces together.
🔧 Fixture
❗ ProblemCopy-pasting the same setup — a database connection, a temp file — into every test is repetitive and easy to get wrong.
✅ SolutionA @pytest.fixture is reusable setup/teardown that pytest injects into any test naming it as a parameter.
RecallFixture = reusable setup for tests.
🎭 Mock vs stub
❗ ProblemReal network calls, databases or payment gateways make a test slow, flaky or costly.
✅ SolutionA Mock replaces the dependency with a fake that returns canned values and can verify calls with assert_called_with(...); a stub only returns canned data.
RecallMock the edges, never your own logic.
🔥 Easy interview recall

External calls → mock them — you don't control them

Your own logic → never mock — that's the thing being tested

Think: mock the edges of the system, never its core.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A green test suite doesn't mean the code works. Mocking your own business logic — or over-mocking so heavily the test only checks that a mock got called — lets the test pass even when the real logic is completely broken, which is worse than no test at all because it creates false confidence.

🔄 Likely Follow-up

"How do you test that a function correctly raises an exception?" with pytest.raises(ExpectedError): risky_call() — the block asserts that exception type is raised inside it, failing the test if the call doesn't raise it.

🎯 Say this in the interview — the exact lines to land

"Mock external dependencies you don't control — never mock the business logic you're actually trying to verify."

  • pytest → plain assert plus test_* discovery — no special assertion classes needed.
  • @pytest.fixture → reusable setup/teardown, injected into a test just by naming it as a parameter.
  • Mock only the boundary — database, network, email, payment, the clock/randomness — never your own logic under test.
  • pytest.raises(...) → asserts an exception is raised inside the with block.
  • Over-mocking → a green suite that tests nothing real.
📖 Explanation ▾

A unit test checks one small piece of logic in isolation — fast, no real I/O. An integration test checks multiple pieces working together, often with real or realistic dependencies. pytest discovers tests by finding def test_* functions and lets you write plain assert statements instead of a special assertion API. A @pytest.fixture is reusable setup/teardown — a DB connection, a temp file, test data — that pytest injects into any test function that simply names it as a parameter.

Mocking (unittest.mock) replaces a real dependency with a fake stand-in that records how it was called and returns canned values. A Mock is a general, flexible fake that can also verify behavior — mock.assert_called_with(...) — which a plain stub can't do; a stub just hands back canned data with no check on how it was used. Mock the things you don't control and that are slow, flaky, or costly in a test — network calls, a real database, sending email, payment gateways, the current time or randomness. Never mock your own business logic — that defeats the point of testing it — and don't over-mock so heavily that a test just proves its own mocks were called, instead of proving real behavior.

Testing async code needs a plugin like pytest-asyncio so pytest can run an async def test_* function inside an event loop instead of just returning an un-awaited coroutine. Testing that something raises the right exception uses pytest.raises(SomeError) as a context manager around the call expected to fail.

💻 See the code ▾
Python 
import pytest

@pytest.fixture
def db_connection():
    conn = create_test_connection()   # ✅ setup
    yield conn
    conn.close()                      # ✅ teardown, runs even if the test fails

def test_saves_order(db_connection):
    order = save_order(db_connection, sku="A1")
    assert order.id is not None

pytest matches the fixture by parameter name — db_connection is set up before the test and torn down right after, whether the test passes or not.

Python 
from unittest.mock import patch

@patch("orders.payment_client.charge")
def test_checkout_calls_payment_once(mock_charge):
    mock_charge.return_value = {"status": "ok"}
    checkout(cart_total=42.00)
    mock_charge.assert_called_once_with(42.00)  # ✅ verifies the call, not just a fake return

patch swaps the real payment_client.charge for a Mock, only for this test — assert_called_once_with proves checkout actually called it correctly, something a plain stub could never check.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your code calls a payment API or sends an email

A real call is slow, flaky, or costs money. patch replaces it with a Mock for that one test, and assert_called_once_with proves the code called it correctly.

RememberMock the edges, not the core.
2 Many of your tests need the same database setup

A @pytest.fixture holds the setup once. pytest passes it to any test that names it as a parameter, and the code after yield cleans up even if the test fails.

RememberFixture = reusable setup.
3 You are tempted to mock your own pricing function to speed up tests

A common trap — the test then only checks that the mock was called. A real bug in the pricing formula would still pass, which gives false confidence.

RememberNever mock the logic under test.
🌍 Real-world example ▾

A team mocked their own pricing-calculation function "to make the tests run faster," since it did some file lookups. The tests kept passing because they were really just checking that the mock had been called — so when a later refactor introduced a real bug in the pricing formula, it shipped straight to production without a single test catching it. Mocking the exact logic under test made the whole suite blind to the one bug it existed to catch.
