Attributes — metadata that only matters once something reads it

"What is an attribute, and how does reflection actually read one at runtime?"

Why it matters ▾
🏷️ Attributes
❗ ProblemWithout a way to attach metadata directly to the exact type, member, or parameter it describes, a framework would have to track "which property renames to what JSON key" or "which property is required" some other way — a separate config file or naming convention that lives apart from the code and silently drifts out of sync as the code changes.
✅ SolutionAn attribute lets that metadata sit right on the member it describes, compiled straight into the assembly — any code that cares (JsonSerializer, a validator, ASP.NET's routing) queries for it later via reflection and acts only on what it finds, no separate config file to keep in sync.
RecallAttribute = metadata glued to the code it describes; reflection is the only thing that ever reads it.
🔥 Easy interview recall

Attribute = "a label on code that does nothing by itself — only reflection gives it any effect."

Think: [JsonPropertyName("full_name")] sits inert until JsonSerializer uses reflection to go looking for exactly that attribute.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An attribute isn't executable code — applying [Required] or [JsonPropertyName] does nothing on its own. It only has any effect once some other code (a validator, a serializer) uses reflection to specifically look for that attribute type on that member — skip that step, and the attribute might as well not be there.

🔄 Likely Follow-up

"How would you write your own attribute and make something act on it?" Define a class inheriting from Attribute to hold the data, decorate the target with it, then write separate code that calls reflection — GetCustomAttribute<T>() or similar — to find it and act; the attribute class itself never does anything, the behavior lives entirely in whoever reads it.

🎯 Say this in the interview — the exact lines to land

"An attribute is declarative metadata attached to a type, member, or parameter — it compiles into the assembly's metadata but runs no code by itself. Something has to deliberately use reflection — GetCustomAttribute<T>() or similar — to query for that specific attribute on that member and act on what it finds; skip that step, and the attribute might as well not exist."

  • Attribute → pure metadata, compiled in, never executed on its own.
  • Reflection → the only thing that gives an attribute any effect, by querying for it explicitly.
  • Custom attribute → inherit from Attribute, hold data only — the behavior lives in whoever reads it.
  • Hot-path cost → attributes are cheap to declare; the reflection call that reads them is the part worth watching.
📖 Explanation ▾

An attribute compiles into the assembly's metadata table, attached to whichever type, member, or parameter it decorates. Nothing about applying it triggers any code — the compiler just records "this member carries this piece of data," the same way it records a method's name or a field's type. That's why an attribute with no reader is functionally identical to no attribute at all.

Reflection is the only bridge between that stored metadata and actual behavior. Code that cares — System.Text.Json, a validation library, ASP.NET's routing — asks a member for its attributes by type (GetCustomAttribute<JsonPropertyNameAttribute>()), and only then decides what to do with whatever it finds. A custom attribute follows the same split: the attribute class just holds data (inheriting from Attribute), and a separate piece of reflection code supplies the behavior.

💻 See the code ▾
C# 
public class Person
{
    [JsonPropertyName("full_name")]     // compiles into metadata — does nothing by itself
    public string Name { get; set; }
}

Applying the attribute is a compile-time-only step — no code runs, nothing has read it yet.

C# 
PropertyInfo prop = typeof(Person).GetProperty("Name");
var attr = prop.GetCustomAttribute<JsonPropertyNameAttribute>();
if (attr != null)
    Console.WriteLine(attr.Name);   // ✅ "full_name" — only printed because we went looking

Reflection is what turns the stored metadata into something a program can actually act on.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your model property needs a different name in the JSON than in C#

This is the #1 scenario you'll actually run into: [JsonPropertyName] sits on the property as pure metadata, and JsonSerializer only renames the JSON key because it specifically goes looking for that exact attribute via reflection while it's serializing — nothing renames anything up front.

RememberSame attribute, same object — JsonSerializer only acts because it deliberately looked.
2 A property on your model must never be left empty

[Required] works the same way from a different consumer: the attribute itself does no checking at all — a validator walks the model's properties, uses reflection to find any validation attribute like this one attached to them, and only then decides the value is invalid.

Remember[Required] doesn't validate anything — the validator that reads it does.
3 You want your own custom label to trigger behavior when reflection finds it

Once you write your own attribute, you own both halves: the attribute class (inheriting from Attribute) only ever holds data, and a completely separate piece of your own code has to call reflection deliberately to find it on a member and decide what to do — skip writing that reader, and the attribute sits there just as inert as any built-in one would.

RememberWrite the attribute AND the reader — one holds data, the other supplies the behavior.
🌍 Real-world example ▾

[JsonPropertyName] is a sticky note taped to a box in a warehouse. The note means nothing until someone doing inventory decides to read sticky notes and act on what they say — a box with an unread note sits there exactly as if it had no note at all. System.Text.Json is the one who reads it, and only for the boxes it's told to check.
