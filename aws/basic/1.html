AWS Fundamentals — where does AWS's responsibility actually end?

"What is AWS, and what does the shared responsibility model actually split between you and AWS?"

Why it matters ▾
  • Nearly always the very first AWS conceptual question asked, before any specific service comes up.
  • Explains a real operational split: why an EC2 fleet needs its own patching schedule but an RDS database never does.
  • Sets up the exact line interviewers probe on: how much of that split shifts as a service gets more managed.
🔥 Easy interview recall

AWS → secures "of the cloud"

You → secure "in the cloud"

Think: the more managed a service is, the more of that line AWS takes over.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

AWS patches your EC2 instance's guest OS. It doesn't — that's squarely the customer's job under the shared responsibility model; AWS is only responsible for the underlying host and hypervisor, never the guest OS running on top of it.

🔄 Likely Follow-up

"How does the split change for a fully managed service like Lambda?" AWS takes on more — it manages the OS and runtime entirely, so the customer's responsibility narrows down to just their code and IAM permissions.

🎯 Say this in the interview — the exact lines to land

"AWS follows a shared responsibility model: AWS secures everything 'of the cloud' — the physical data centers, the hypervisor, and the network — while I'm responsible for everything 'in the cloud,' like my guest OS, my application, and my data. Exactly where that line sits moves depending on how managed the service is — I own more on EC2, AWS owns more on a fully managed service like Lambda."

  • IaaS → you own OS, runtime, app (e.g. EC2).
  • PaaS → AWS owns OS + platform patching too (e.g. RDS, Elastic Beanstalk).
  • SaaS → AWS/vendor owns everything underneath — you just use the product.
  • EC2 vs. Lambda → EC2 leaves you the OS to patch; Lambda leaves you only code + IAM permissions.
📖 Explanation ▾

AWS is a cloud platform: compute, storage, network, and database capacity rented on demand instead of bought as physical hardware, billed for only what actually gets used. How much of the stack you're handed to manage yourself depends on which delivery model a service uses — IaaS, PaaS, or SaaS.

The Shared Responsibility Model states the same idea as a rule: AWS is always responsible for "of the cloud" — the physical data centers, the hypervisor, the global network — no matter which service is picked. Everything above that line is "in the cloud," and it's the customer's job, whether that's a full guest OS on EC2 or just application code on a serverless service.

🌍 Real-world example ▾

A team running a fleet of EC2 instances has to patch the guest OS on a schedule — that's squarely on their side of the line. The same team's RDS database never gets a similar OS-patching task on the calendar at all, because AWS already owns that layer for a managed database.
