🔥 AWS · Intermediate · Must Know

SCPs never grant anything — they only set a ceiling

"How do you set up cross-account access, and how do Service Control Policies differ from a regular IAM policy?"

Why it matters ▾
🔑 Regular IAM policy
❗ ProblemAn IAM user, group, or role starts with zero permissions, and an SCP's Allow statements can't fix that — an SCP with nothing but Allows still grants nothing.
✅ SolutionA regular IAM policy attached directly to that user, group, or role is what actually grants or denies access — it's the only layer here that can hand out a permission, not just cap one.
RecallRegular IAM policy = the only layer that actually grants access.
🚧 Service Control Policy (SCP)
❗ ProblemA regular IAM policy only ever governs its own account, so nothing stops one account in an OU from launching resources outside the regions leadership approved.
✅ SolutionAn SCP attaches at the Organization/OU level and sets a ceiling every account underneath must obey — a Deny in it blocks the whole account no matter what any local IAM Allow says.
RecallSCP = an Org/OU-level ceiling — it can restrict but never grant.
🔥 Easy interview recall

SCP = "a ceiling that only restricts — it can never grant a permission."

Think: an SCP Deny always wins, no matter what any local IAM Allow says underneath it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"An SCP can grant permissions, just like a regular IAM policy." It can't — an SCP only restricts, setting a ceiling that nothing inside the account can ever exceed, no matter what any local IAM Allow says.

🔄 Likely Follow-up

"Secrets Manager vs. Parameter Store — when would you use each?" Secrets Manager costs more but adds built-in automatic rotation (e.g. for RDS credentials) and finer-grained access policies; Parameter Store is cheaper and fine for static config or secrets that don't need automatic rotation.

🎯 Say this in the interview — the exact lines to land

"SCPs only restrict, they never grant — they set the ceiling every IAM policy in the account operates under. For cross-account access, I'd create a role in the target account that trusts the source account's principal, and use STS AssumeRole to get temporary credentials instead of sharing a user or long-lived keys."

  • SCP → ceiling only, never a grant — a Deny anywhere in it always wins.
  • Cross-account role → a trust policy in the target account lets another account's principal assume it via STS AssumeRole.
  • AWS Organizations → groups accounts so SCPs can apply at the Org/OU level, not just one account.
  • KMS → manages the encryption keys behind most of this — S3, EBS, Secrets Manager, and RDS all lean on it.
  • Secrets Manager vs. Parameter Store → rotation vs. cost: Secrets Manager auto-rotates (e.g. RDS), Parameter Store is cheaper for static config.
📖 Explanation ▾

A cross-account IAM role is a role created in Account B whose trust policy names Account A (or a specific principal in it) as trusted. A principal in Account A calls sts:AssumeRole, gets back temporary credentials scoped to that role's permissions, and never needs a user or standing credentials of its own inside Account B. AWS Organizations groups multiple accounts under one management structure, which is what makes it possible to apply a policy once and have it reach every account underneath.

A Service Control Policy (SCP) attaches at the Organization or OU level and sets the maximum permissions any identity in that account can ever have. It doesn't grant anything on its own — an SCP with nothing but Allow statements still grants nothing; only a local IAM policy grants access, and only within whatever an SCP hasn't already ruled out. A Deny in an SCP is absolute: it makes an action impossible for every identity in that account, including one with a local IAM policy that explicitly allows it.

KMS manages the encryption keys behind most AWS storage and secrets services. Secrets Manager stores and rotates secrets, with built-in automatic rotation support for RDS credentials. Parameter Store (part of Systems Manager) stores configuration and secrets more cheaply, but without Secrets Manager's automatic rotation — a fine trade-off for static values that don't need to change on a schedule.

💻 See the code ▾
CLI 
aws sts assume-role \
  --role-arn arn:aws:iam::ACCOUNT_B:role/CrossAccountRole \
  --role-session-name demo

This is called from Account A. It only works because Account B's role already trusts Account A in its trust policy — no user or key in Account B is involved.

🧭 Use Cases — recognize these when they happen to you ▾
1 Account A needs to read an S3 bucket that lives in Account B, without a new IAM user in Account B

This is the #1 scenario you'll actually run into. Account B's role already trusts Account A in its trust policy, so Account A calls sts:AssumeRole and gets back temporary credentials scoped to that role — no standing user or key in Account B ever exists.

RememberCross-account access → a trust policy plus AssumeRole, never a shared user.
2 You write an SCP that only contains Allow statements, expecting it to hand out extra permissions org-wide

Nothing changes. An SCP never grants — an Allow inside one does nothing on its own, so every identity in the account is still exactly as permissioned as its own local IAM policies say, no more.

RememberSCP Allow ≠ access — only a local IAM policy actually grants.
3 Your RDS database credentials need to rotate on a schedule, but a handful of config values don't

The RDS credentials go in Secrets Manager, which has built-in automatic rotation for them; the static config values go in the cheaper Parameter Store, since they never need to change on a schedule.

RememberNeeds rotation → Secrets Manager; static and cheap → Parameter Store.
🌍 Real-world example ▾

A company's SCP blocks every account in its "sandbox" OU from ever launching a resource outside two approved regions — regardless of what any individual account's own IAM policies allow, because the SCP's ceiling simply doesn't include the other regions.
