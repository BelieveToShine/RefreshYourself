volatile — visibility, not atomicity

"What does volatile actually guarantee?"

Why it matters ▾
🔓 volatile
❗ ProblemWithout it, the compiler and CPU can cache a shared field per thread or reorder instructions around it, so one thread's write may never become visible to another thread reading it in a loop.
✅ Solutionvolatile turns off that caching and reordering for the field, so every thread always reads the latest value — visibility only, not atomicity, so x++ can still race.
Recallvolatile = visibility only, never atomicity.
⚡ Interlocked
❗ Problemcounter++ is still three separate steps — read, add, write — so two threads can interleave them and lose an update, yet wrapping just that one increment in a full lock pays a real blocking cost it doesn't need.
✅ SolutionInterlocked makes one operation — an increment, decrement, or compare-and-swap — a single atomic CPU instruction, so it's safe with no blocking at all.
RecallInterlocked = one atomic op, no blocking, no lock needed.
🔥 Easy interview recall

volatile → visibility only, never atomicity

lock → full exclusion, real blocking cost

Interlocked → one atomic op, never blocks

Think: volatile just tells the truth about the value. lock makes everyone else wait. Interlocked does one thing instantly.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Marking a counter volatile does not make counter++ thread-safe. volatile only stops a stale cached read — the increment is still a separate read, add, and write, and two threads can interleave those three steps and lose an update.

🔄 Likely Follow-up

"If Interlocked is lock-free, why not use it everywhere instead of lock?" Because it only makes one operation atomic — the moment two or more values need to change together as a single unit, only lock can group them.

🎯 Say this in the interview — the exact lines to land

"volatile only guarantees visibility — reads and writes aren't cached or reordered across threads, but a multi-step operation like x++ is still not atomic. lock gives full mutual exclusion so more than one step can run as a single unit, at the cost of real blocking. Interlocked makes one specific operation — an increment or a compare-and-swap — atomic without blocking at all."

  • volatile → visibility flag only — never reach for it to make an operation atomic.
  • lock → use when multiple steps must happen together as one atomic unit.
  • Interlocked → use for a single increment/decrement/compare-exchange, no blocking needed.
  • x++ on a volatile int → still a race — read, add, and write are three separate steps.
📖 Explanation ▾

volatile only turns off two tricks the compiler and CPU normally use — caching a value in a register per thread, and reordering instructions around it. That keeps every thread reading the current value, but it never groups multiple steps together: counter++ is still read, then add, then write — three separate chances for another thread to interleave.

lock is the only one of the three that lets more than one statement run as a single, uninterruptible unit. That extra safety costs a real block — a thread that can't acquire the lock actually waits, which is more overhead than the other two ever pay.

Interlocked sits in between: one specific operation — an increment, a decrement, a compare-and-swap — happens as a single CPU instruction, atomically, with no thread ever blocked. The trade is scope: it only ever protects that one operation, never a sequence of them.

💻 See the code ▾
C# 
private volatile bool _stopRequested;

void Worker()
{
    while (!_stopRequested)   // ✅ always sees the latest value — never a stale cached read
        DoWork();
}

void RequestStop() => _stopRequested = true;

volatile is enough here — only one value is ever read, no read-modify-write sequence.

C# 
private volatile int _counter;

void Increment() => _counter++;   // ❌ read, add, write — three steps, still a race

volatile does not make this atomic — two threads can read the same value before either one writes back.

C# 
private readonly object _gate = new();
private int _total;

void Add(int amount)
{
    lock (_gate)              // ✅ only one thread inside at a time
    {
        _total += amount;     // multiple steps, still safe as a single unit
    }
}

lock is the only one of the three that can protect more than one statement together.

C# 
private int _counter;

void Increment() => Interlocked.Increment(ref _counter);   // ✅ atomic — no lock needed

One CPU instruction does the read, add, and write together — no blocking, no lock object.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your worker thread needs to see a stop signal set from another thread, right away

This is exactly the case volatile was built for — one value, one thread writing it, other threads only ever reading it, no math involved. Marking the field volatile guarantees the worker's loop never gets stuck on a stale cached value.

RememberOne flag, no math → volatile is enough.
2 You need to bump a shared counter and nothing else

A single counter with no other logic attached is exactly what Interlocked.Increment/Decrement was built for — one atomic CPU instruction does the read, add, and write together, with no thread ever blocked waiting on a lock.

RememberOne counter, one op → reach for Interlocked before lock.
3 Two or more values need to change together, as a single unit

Neither volatile nor Interlocked can group more than one statement into a single atomic step — only lock makes a whole block run as an uninterruptible unit, at the cost of a real blocking wait.

Remember2+ steps together → only lock groups them.
🌍 Real-world example ▾

Three everyday scenes for the same three tools. A whiteboard status word ("OPEN"/"CLOSED") is a volatile read — anyone glancing at it just needs the current word, no turn-taking required. A bank teller window is lock — only one customer is served at a time, and everyone else genuinely waits their turn. A turnstile that clicks up by exactly one each time someone passes through is Interlocked — one atomic click, no queue, no waiting room.
