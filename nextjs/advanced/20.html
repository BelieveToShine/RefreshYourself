95% static, one live widget — does the whole page really need to go dynamic?

"A product page is 95% static content with one small personalized widget — how would you architect that?"

Why it matters ▾
🧩 Client-Side Island
❗ ProblemMaking the whole page dynamic just to serve one small personalized widget throws away the static/ISR performance benefit for the 95% of content that didn't need it.
✅ SolutionKeep the page itself static/ISR, and fetch just that one small piece client-side, inside its own small Client Component — no experimental feature needed, and it works today.
RecallStatic shell + a small client-side-fetched widget = the simplest option, available right now.
🧪 Partial Prerendering (PPR)
❗ ProblemA client-side-fetched widget still means that one piece isn't server-rendered at all, which matters when the dynamic content itself is SEO-sensitive.
✅ SolutionPartial Prerendering lets the static shell serve instantly while only that one dynamic "hole" streams in server-side — but it depends on an explicitly experimental feature as of this track's research.
RecallPPR keeps everything server-rendered, at the cost of an experimental feature flag.
🔥 Easy interview recall

Client-side island → simple, no flags, ship today

PPR → fully server-rendered, still experimental

Think: default to the client-side island unless the team has already adopted PPR.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Making the whole page dynamic just because one small piece needs fresh data. That throws away the static/ISR performance benefit for the 95% of content that never needed to be request-unique in the first place.

🔄 Likely Follow-up

"Which option would you actually recommend to a team not yet using PPR?" The static page plus a small client-side-fetched widget — it needs no experimental feature flag and is straightforward to reason about and test.

🎯 Say this in the interview — the exact lines to land

"I'd keep the page itself static or ISR and fetch the small personalized piece client-side in its own Client Component — that needs no experimental feature and works today. If the team already has Partial Prerendering adopted, that dynamic piece could instead be a server-rendered PPR hole, which matters more when that content is SEO-sensitive."

  • 95% static content → keep it static/ISR, don't make the whole page dynamic for one widget.
  • Client-side island → simplest default, no experimental flag, works today.
  • Partial Prerendering → fully server-rendered, but an experimental feature as of this track's research.
  • SEO-sensitive dynamic content → that's the case PPR is actually worth the experimental flag for.
📖 Explanation ▾

A client-side island keeps the page's own render strategy completely untouched — static or ISR, served instantly from cache — and the small personalized piece is just an ordinary client-side data fetch happening inside a 'use client' component, the same way any client-rendered widget would work. Nothing about the page's own caching changes.

Partial Prerendering takes a different approach: it prerenders a static "shell" for the whole page, but leaves an explicit hole wherever dynamic content is needed, and streams that hole in from the server once it's ready — so the dynamic piece is still genuinely server-rendered, not just fetched after the fact in the browser. That matters for content that needs to be indexed or seen correctly by something that doesn't execute client-side JavaScript.

The trade-off is adoption cost, not capability: a client-side island ships with zero extra setup, while PPR needs the experimental feature enabled and a little more care around which parts of a route are genuinely static versus genuinely dynamic.

💻 See the code ▾
JSX 
// page.js — stays static/ISR, no change needed here
export default function ProductPage() {
  return (
    <>
      <ProductDetails />      // ✅ static, served from cache
      <RecentlyViewed />      // ✅ small Client Component, fetches on its own
    </>
  );
}

Only RecentlyViewed needs to be a Client Component — the rest of the page keeps its existing static/ISR behavior unchanged.

JSX 
// Only once PPR is already adopted for the project
export const experimental_ppr = true; // marks this route as a PPR candidate

export default function ProductPage() {
  return (
    <>
      <ProductDetails />                      // ✅ part of the static shell
      <Suspense fallback={<Spinner />}>
        <RecentlyViewed />                    // ✅ the dynamic "hole," streamed server-side
      </Suspense>
    </>
  );
}

The <Suspense> boundary is what marks the dynamic piece as a hole in the otherwise-static shell.

🌍 Real-world example ▾

A product page needs a "recently viewed" strip that's different per visitor, but the rest of the page — description, images, specs — is identical for everyone. Keeping the page static/ISR and fetching the strip client-side in its own small Client Component ships today with no extra setup; reaching for Partial Prerendering only makes sense once the team has already adopted it and that personalized content genuinely needs to be server-rendered.
