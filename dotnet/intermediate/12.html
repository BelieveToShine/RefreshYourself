appsettings.json vs. env vars vs. secrets — who actually wins?

Where does ASP.NET Core configuration actually come from, and what's the override order?

Why it matters ▾
🔢 Configuration Precedence
❗ ProblemThe exact same setting can exist in appsettings.json, a per-environment override file, User Secrets, environment variables, and command-line arguments all at once — with no obvious way to tell which value the app will actually use.
✅ SolutionASP.NET Core loads those sources in one fixed order — appsettings.json lowest, command-line arguments highest — and a later source only overrides an earlier one on a shared key.
RecallLayers stacked in a fixed order — the last one loaded wins on a shared key.
🔥 Easy interview recall

Config sources = "layers stacked on top — the last one loaded wins."

Think: appsettings.json loads first, command-line loads last — whoever loads last wins on a shared key.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

appsettings.{Environment}.json does not replace appsettings.json. It only overrides the specific keys it defines — any key that's only in the base file still applies, layered underneath it.

🔄 Likely Follow-up

"What's the difference between IOptions<T>, IOptionsSnapshot<T>, and IOptionsMonitor<T>?" IOptions<T> is read once and cached for the app's whole lifetime; IOptionsSnapshot<T> re-reads config per scope or request; IOptionsMonitor<T> can actively notify you through a callback when config changes.

🎯 Say this in the interview — the exact lines to land

"ASP.NET Core layers configuration from several sources — appsettings.json, then the environment-specific JSON file, then User Secrets in Development, then environment variables, then command-line arguments — and a later source overrides an earlier one only on a shared key. Instead of reading IConfiguration by string key everywhere, I bind a section to a strongly-typed class and inject IOptions<T>, so the config shape is checked at compile time and easy to test."

  • appsettings.json → base defaults, loaded first.
  • Command-line args → highest priority, win over everything.
  • User Secrets → Development only, keeps secrets out of source control.
  • IOptions<T> → compile-time safety, instead of string-keyed lookups.
📖 Explanation ▾

WebApplication.CreateBuilder wires up every one of these sources the moment the app starts, in a fixed order — each later source is added on top of the ones before it, and only overrides a key if it actually sets that key. This is why the same compiled code can run in local dev, a test environment, and a production container without a single code change: the override just happens through whichever files and variables are present at that point.

Reading configuration with _configuration["Some:Nested:Key"] everywhere works, but every lookup is a plain string — a typo compiles fine and just returns null at runtime. Binding a section to a plain class with services.Configure<MyOptions>(config.GetSection("MySection")) and injecting IOptions<T> instead gives the same values with compile-time checking, and makes tests simple — construct a real MyOptions object, no need to fake IConfiguration itself.

💻 See the code ▾
C# 
// appsettings.json
{ "Greeting": { "Message": "Hello from appsettings.json" } }

var app = builder.Build();
var message = app.Configuration["Greeting:Message"];
Console.WriteLine(message);   // "Hello from appsettings.json"

One key, read the same way every time — no code cares which file it came from.

C# 
// PowerShell — same key, double underscore for nesting
$env:Greeting__Message = "Hello from the environment"

Console.WriteLine(message);   // "Hello from the environment" — env var wins

The exact same line of code now prints a different value — the override happened outside the app, not inside it.

C# 
public class GreetingOptions
{
    public string Message { get; set; } = "";
}

builder.Services.Configure<GreetingOptions>(
    builder.Configuration.GetSection("Greeting"));

// wherever it's needed
public GreetingService(IOptions<GreetingOptions> options)
{
    var message = options.Value.Message;   // typed, no string key
}

IOptions<T> reads the exact same layered config — just through a typed class instead of a string key.

🧭 Use Cases — recognize these when they happen to you ▾
1 You run the app locally with nothing else set

No env vars, no user secrets, no command-line flags in play — the base file is the only layer that exists, so whatever it says is exactly what the app uses. This is the #1 case you'll actually run into during day-to-day local dev.

RememberOne source present → nothing to override, base file wins by default.
2 You deploy the same build to a container and set an environment variable

ConnectionStrings__Default set as an environment variable in the orchestrator loads after appsettings.json, so it overrides the local connection string on that shared key — the same compiled code now points at the real production database.

RememberEnv var loads later than the base file → it wins on a shared key.
3 You need a one-off override right at launch, even over an env var that's already set

A command-line argument passed at launch (e.g. --Greeting:Message="temp override") loads last of all five sources, so it overrides that key no matter what an environment variable, User Secrets, or any JSON file already set it to.

RememberCommand-line loads last → it always wins on a shared key.
🌍 Real-world example ▾

Your connection string is "Server=localhost" in appsettings.json for local development. Deploy the same build to a container and set ConnectionStrings__Default as an environment variable in the orchestrator — the app connects to the real database in production, and not one line of C# had to change to make that happen.
