REST — an architectural style, not a protocol

"What is REST, and what constraints actually make an API RESTful?"

Why it matters ▾
  • Almost every Web API interview opens here — and most candidates only know the buzzword.
  • Comes up again the moment someone calls a JSON-over-HTTP API "RESTful" without meeting the actual constraints.
  • Sets up nearly every other Web API question — versioning, idempotency, and caching all lean on these constraints.
🔥 Easy interview recall

REST = "a set of constraints for building predictable, scalable APIs — not a protocol."

Think: stateless → no session stored on the server resource-based → nouns, not actions (/orders/42) uniform interface → same fixed HTTP verbs, every resource

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An API isn't "RESTful" just because it uses HTTP verbs and returns JSON. A truly RESTful API is stateless and resource-oriented — one that needs session affinity or exposes RPC-style action endpoints like /doSomething is HTTP-based, not genuinely REST.

🔄 Likely Follow-up

"Is GraphQL RESTful?" No — GraphQL deliberately breaks the resource-per-URI constraint, exposing one endpoint with a query language instead. It's a different style solving different problems, not a violation of REST so much as an alternative to it.

🎯 Say this in the interview — the exact lines to land

"REST is an architectural style, not a strict protocol — a set of constraints that together make an API predictable and scalable. The core ones are being stateless, separating client from server, treating resources as nouns identified by URIs, and manipulating them through a small, uniform set of HTTP methods. An API that just speaks HTTP and JSON isn't automatically RESTful — it also has to be stateless and resource-oriented."

  • Stateless → every request carries everything the server needs; no session stored between calls.
  • Resource-based → URIs are nouns (/orders/42), not RPC-style actions (/getOrder?id=42).
  • Uniform interface → a small fixed set of HTTP verbs manipulates every resource the same way.
  • HATEOAS → the textbook constraint that's least often actually implemented in real APIs.
📖 Explanation ▾

REST (Representational State Transfer) is a style, not a standard someone can validate a response against. It names a handful of constraints that, followed together, keep an API predictable: stateless (the server holds no client session between requests), client-server separation (the two evolve independently), a uniform interface (a fixed small set of methods acting on resources identified by URIs), and resource orientation (nouns, not verbs, in the URL).

Two more constraints round out the textbook definition but show up far less in practice: cacheable responses (a response can say whether it's safe to reuse) and a layered system (proxies or gateways can sit transparently in the chain). The least commonly implemented of all is HATEOAS — hypermedia links inside a response pointing to related actions. Textbook says yes; real-world APIs rarely bother.

None of this makes an API "RESTful" just for riding on HTTP. The dividing line is whether it's genuinely stateless and resource-oriented, or whether it's quietly RPC underneath a JSON-over-HTTP skin.

RPC-style over HTTPGenuine REST
URL shape/getOrder?id=42 — an action/orders/42 — a resource
State between calls❌ often needs a session✅ none — every request is self-contained
What the verb meanswhatever the endpoint name saysthe same fixed meaning everywhere (GET reads, DELETE removes…)
Scaling across serversharder — session has to be found or sharedeasier — any server instance can handle any request
💻 See the code ▾
C# 
[HttpGet("getOrder")]
public IActionResult GetOrder(int id)
{
    // ❌ the action lives in the URL — RPC-style, not REST
    var order = _db.Orders.Find(id);
    return Ok(order);
}

Works fine over HTTP — but /getOrder?id=42 names an action, not a resource.

C# 
[HttpGet("orders/{id}")]
public IActionResult GetOrder(int id)
{
    // ✅ the URI names a resource — GET supplies the action
    var order = _db.Orders.Find(id);
    return order is null ? NotFound() : Ok(order);
}

Same logic, resource-based URI: /orders/42 is a noun — the HTTP verb is the action.

C# 
[HttpGet("orders/{id}")]
public IActionResult GetOrder(int id, [FromHeader] string authorization)
{
    // ✅ everything needed travels WITH this request — no Session[...] lookup
    if (!_auth.Validate(authorization)) return Unauthorized();
    var order = _db.Orders.Find(id);
    return order is null ? NotFound() : Ok(order);
}

Stateless: the token rides in the request itself, so any server instance can handle the call.

🌍 Real-world example ▾

REST is a restaurant menu. Every dish (resource) has a name and a number, and one small fixed set of actions — order, modify, cancel — works the same way for any dish on the menu. An RPC-style API is closer to a private phone line to the kitchen for every request ("makeMeAPizza," "cancelMyPizza") — it works, but every action needs its own custom line.
