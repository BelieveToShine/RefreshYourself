Same bug, different page — which technique do you actually reach for?

"A page takes 5 seconds to load, a modal leaks memory, a search box shows a stale result, and a list has 10,000 rows — walk me through how you'd actually fix each one."

Why it matters ▾
  • This is the question that separates a senior/architect interview from a junior one — not "what is a closure," but "given a real symptom, which of the techniques you already know do you reach for, and why."
  • Every scenario below routes back to a page already on this track — the skill being tested is diagnosis and routing, not remembering one more definition.
  • A near-guaranteed opener or closer in any senior/staff JavaScript interview — "tell me about a production bug you fixed" is really this page's questions, asked one at a time.
🔥 Easy interview recall

Slow to interactive → profile, don't guess

Memory grows on open/close → something's still referenced

Stale response wins → track the latest request, not just "a" request

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Debouncing the input is not the fix for the race condition. Debounce only cuts down how many requests get fired — it doesn't stop a slow, older request from resolving after a faster, newer one; you still need to track the latest request id (or AbortController) and discard any response that isn't from it.

🔄 Likely Follow-up

"What if you can't easily attach a request id to the response?" Use AbortController instead — abort every in-flight request the moment a new one fires; an aborted request's promise rejects and never reaches the "update the UI" step at all, so there's nothing stale left to accidentally render.

🎯 Say this in the interview — the exact lines to land

"Every one of these routes back to a technique I already know: profile for long tasks and check the bundle for the slow page, suspect a leftover event listener or detached DOM node for the memory leak, use a concurrency-limited promise pool to cap 5 APIs at 3 at once, track the latest request id or AbortController plus debounce for the stale search result, abort in-flight requests on navigate-away, delegate one listener instead of 10,000, and lean on clean module boundaries so teams don't step on each other's code."

  • Page slow to interactive → profile for long tasks, check bundle size/code-splitting, watch for layout thrashing (Performance & Rendering).
  • Memory grows every modal open/close → a forgotten listener or detached DOM node not cleaned up on close (Memory & Garbage Collection).
  • 5 APIs, only 3 concurrent → a concurrency-limited promise pool, not Promise.all on everything (Advanced Async Concurrency).
  • Stale search result → track the latest request id/AbortController and discard anything older (Fetch/HTTP/AbortController); debounce the keystrokes too (Debounce vs. Throttle). Navigated away mid-request → abort the in-flight request so it doesn't finish into nothing.
  • 10,000 list items → one delegated listener on the container, never 10,000 handlers (Event Delegation).
  • Structuring for independent teams → module boundaries and exports are the contract; avoid shared mutable globals (Modules).
📖 Explanation ▾

A page that takes 5 seconds to become interactive is a profiling question, not a guessing game: open the performance profiler and look for long tasks blocking the main thread, check whether the JavaScript bundle is too big to parse and execute before anything can respond (code-splitting fixes this), and check for layout thrashing — repeatedly reading a layout property right after writing one, forcing the browser to recalculate layout over and over. That's the reasoning Performance & Rendering exists to teach in depth.

Memory that grows every time a modal opens and closes means something from that modal is still reachable after it should be gone — most often an event listener registered when the modal opened but never removed when it closed, or a detached DOM node (removed from the page but still referenced from JavaScript, e.g. by a closure or a stored variable) that the garbage collector can't reclaim. This is exactly the reachability idea from "Memory & Garbage Collection" (advanced, topic 5) — a leak is never "JavaScript broke," it's always something still holding a reference.

Running 5 API calls with only 3 allowed concurrently is the concurrency-limit / promise-pool pattern from "Advanced Async Concurrency" (advanced, topic 2) — kick off the first 3, and each time one finishes, start the next queued one, until all 5 have run and at no point more than 3 are in flight.

A fast typist's search box showing an old response after a newer one is a genuine race condition, not just "add a debounce." Debouncing (from "Debounce vs. Throttle," advanced topic 4) reduces how many requests get fired at all, which helps, but it doesn't guarantee the requests that do fire resolve in the order they were sent — a slow response to an earlier keystroke can still land after a fast response to a later one. The real fix is tracking which request is the latest one (a simple counter, or an AbortController per request — see fetch() / AbortController) and, when a response comes back, checking whether it's still the latest before using it — if it isn't, discard it. The same AbortController also answers the cancellation scenario: if a user navigates away while a request is still in flight, abort it — otherwise the request finishes into a component that no longer exists, wasting the network round trip and risking an update on something that's already gone.

10,000 list items don't need 10,000 click handlers. Attaching one costs memory per item and adds real setup time; Event Delegation attaches a single listener to the shared container and reads event.target to work out which row was actually clicked — one listener no matter how many rows exist now or get added later.

Structuring a large app so different teams can work independently is a module-boundary question, not a tooling question. Modules give each team's code a well-defined set of exports — its public contract — so other teams depend on that contract, not on internal implementation details; avoiding shared mutable global state is what keeps one team's change from silently breaking another team's code.

💻 See the code ▾
JS 
// Concurrency-limit pool: 5 tasks, only 3 running at once
async function runWithLimit(tasks, limit) {
  const results = [];
  let next = 0;
  async function worker() {
    while (next < tasks.length) {
      const i = next++;                 // claim the next task
      results[i] = await tasks[i]();     // run it, then loop for another
    }
  }
  const workers = Array.from({ length: limit }, worker); // 3 workers
  await Promise.all(workers);
  return results;
}

3 workers pull from the same queue — never more than 3 requests in flight, all 5 still run.

JS 
// Search box: discard a response that isn't the latest request
let latestId = 0;

async function onSearchInput(query) {
  const id = ++latestId;               // this keystroke's own id
  const res = await fetch(`/search?q=${query}`);
  const data = await res.json();
  if (id !== latestId) return;     // ❌ a newer request fired since — discard
  renderResults(data);                    // ✅ still the latest — safe to show
}

Whichever response arrives, only the one matching the current latestId ever reaches the screen — order of arrival stops mattering.

🌍 Real-world example ▾

An interviewer says "our checkout page feels sluggish, and support tickets mention the cart total sometimes shows the wrong number after quick edits — where do you start?" Two separate scenarios in one report: the sluggishness is a Performance & Rendering investigation (profile, check the bundle, check for layout thrashing), and the wrong total is very likely a race condition — an old "recalculate total" request resolving after a newer one. The signal being graded is naming both causes correctly and pointing at the specific technique for each, rather than one vague "let me look into performance" answer.
