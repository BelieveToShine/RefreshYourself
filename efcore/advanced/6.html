Connection management — borrowed and returned, never held for life

What does connection management look like with EF Core — does it open one connection per query, per DbContext, or something else?

Why it matters ▾
🏊 Connection Pooling
❗ ProblemIf every "open" paid for a brand-new physical network handshake, opening and closing a connection before and after every single operation would be far too slow to use by default.
✅ SolutionThe ADO.NET provider owns its own connection pool — on by default for essentially every mainstream provider — so "open" is really just a cheap checkout of an already-established physical connection, and "close" just returns it.
RecallConnection pooling = the physical connection, reused, on by default, matters always.
🧩 DbContext Pooling
❗ ProblemAt very high request throughput, constructing and allocating a brand-new DbContext object per request adds real, measurable overhead — separate from anything the connection pool already handles.
✅ SolutionAddDbContextPool, EF Core's own DI registration, opts into reusing the DbContext object itself by resetting its internal state between uses — avoiding that construction/allocation cost.
RecallDbContext pooling = the C# object, reused, opt-in, matters at high throughput.
🔥 Easy interview recall

EF Core → opens, then closes — every operation

"Closed" → returned to the pool, not torn down

DbContext pooling → reuses the object, a separate pool

Think: a DbContext borrows a connection like a library book — checked out, used, returned — never kept on permanent loan.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 A separate layer — object reuse, not connection reuse
⚠️ Common Trap

A DbContext does not hold one open connection for its whole lifetime. By default it opens a connection right before running a command and closes it right after — "closed" just returns it to the ADO.NET connection pool, it doesn't tear down the physical connection.

🔄 Likely Follow-up

"If EF Core opens and closes a connection per operation like you just described, doesn't that mean paying for a brand new physical connection every single time — isn't that slow?" No — "closing" returns the connection to the ADO.NET connection pool rather than tearing it down, so a later "open" is a cheap pool checkout, not a real network handshake, as long as connection pooling is enabled at the provider level, which it is by default for essentially every mainstream provider.

🎯 Say this in the interview — the exact lines to land

"EF Core doesn't hold one connection open for a DbContext's whole lifetime — it opens a connection right before it needs to run a command and closes it right after, unless you're inside an explicit transaction. 'Closing' returns the connection to the ADO.NET provider's own connection pool, so a later open is a cheap checkout, not a new handshake. DbContext pooling is a separate, additional optimization — it reuses the DbContext object itself to cut allocation cost, which is a different layer entirely from the connection pool underneath it."

  • Default lifecycle → open right before, close right after each operation.
  • "Closed" → returned to the ADO.NET pool, not physically torn down.
  • Explicit transaction / OpenConnection() → connection stays open across operations until you close it.
  • AddDbContextPool → reuses the DbContext object itself, a separate pool from the connection pool.
  • Two pools, two different costs → object allocation vs. physical network connection — don't conflate them.
📖 Explanation ▾

By default, a DbContext opens its connection lazily, right before it actually needs to run a command, and closes it again right after that command finishes. It does this per operation, not once for the DbContext's whole life — the only exceptions are when code is inside an explicit transaction, or has explicitly called context.Database.OpenConnection() itself, both of which keep the connection open across multiple operations on purpose.

Connection pooling itself isn't EF Core's job — it's handled below EF Core, by the ADO.NET provider (SQL Client's own pool, for example). So "open right before, close right after" is really just borrowing and returning an already established physical connection each time, not paying for a brand-new network handshake on every single operation.

DbContext pooling (AddDbContextPool in DI registration) is a completely separate, additional optimization layered on top. It reuses the DbContext object itself — not the underlying connection — by resetting its internal state between uses, which reduces object construction/allocation overhead. That only matters at very high request throughput; it says nothing about how connections are opened or closed.

💻 See the code ▾
C# 
using var context = new AppDbContext(options);

var first = await context.Orders.FindAsync(1);
// connection opened just for this query, then closed (returned to the pool)

var second = await context.Orders.FindAsync(2);
// ✅ opened and closed again — a cheap pool checkout each time, not a new handshake

Two separate queries on the same DbContext — the connection is opened and closed independently for each one.

C# 
using var tx = await context.Database.BeginTransactionAsync();
// ❗ the connection now stays open across every operation inside this transaction

await context.Orders.AddAsync(order);
await context.SaveChangesAsync();
await context.Database.ExecuteSqlRawAsync("UPDATE Stock ...");

await tx.CommitAsync(); // only now does the connection close again

An explicit transaction is the one common case where the connection genuinely stays open across multiple operations, not just one.

C# 
services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString)); // pools the DbContext OBJECT
// a different pool from the one above — connection pooling still happens separately, in ADO.NET

AddDbContextPool reuses DbContext instances across requests — it has nothing to do with how the underlying connection is opened or closed.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two separate queries run back-to-back on the same DbContext

Each query opens the connection right before it runs and closes it right after — "closed" just returns it to the ADO.NET pool, so the second query's open is a cheap pool checkout, not a new handshake.

RememberSame DbContext, two queries → two independent opens/closes, both cheap.
2 Your code wraps several operations in an explicit transaction

Once BeginTransactionAsync() runs, the connection stays open across every operation inside that transaction, and only closes again after Commit — this is the one common exception to "open right before, close right after."

RememberExplicit transaction → connection stays open until commit, not per operation.
3 Profiling under high request throughput shows CPU going into allocation, not database waits

The bottleneck here is DbContext construction, not the physical connection — switching to AddDbContextPool reuses the DbContext object itself, a separate pool from the connection pool underneath it.

RememberAllocation-bound, not connection-bound → reach for AddDbContextPool, not pool size.
🌍 Real-world example ▾

A high-throughput API is under load, and profiling shows the CPU time going into object allocation and GC pressure, not into waiting on the database. Bumping the ADO.NET connection pool's max size won't help here — the connections were never the bottleneck. Switching the DbContext registration to AddDbContextPool is the fix: it reuses the DbContext objects themselves across requests, cutting the allocation cost that was actually showing up in the profile — a separate lever from anything connection-pool related.
