One small change in the base class — and a class three levels down breaks

What goes wrong with deep inheritance hierarchies, and what does the fragile base class problem actually look like?

Why it matters ▾
  • A real production bug pattern: someone makes a "safe" change to a widely-used base class, and a subclass three levels down starts failing for reasons its own author can't see.
  • Interviewers use this to check whether you understand depending on a base class's full implementation, not just its public contract — not just whether you know the phrase "favor composition."
  • A natural senior/architect follow-up once a candidate mentions the four pillars — this is where "I know inheritance" turns into "I know when inheritance bites back."
🔥 Easy interview recall

Deep hierarchy → a base change ripples down, breaks a subclass nobody warned

Composition → swap the held behavior, nothing above it breaks

Think: inheritance shares a whole implementation. composition shares only a contract.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Favor composition over inheritance" means never use inheritance. It doesn't — reach for composition especially as a hierarchy gets deep or the is-a claim feels even slightly forced; a genuinely stable, shallow is-a relationship is still simpler left as inheritance.

🔄 Likely Follow-up

"Is there a depth of inheritance hierarchy where you'd say 'this is a smell, stop'?" There's no hard universal number, but more than 2-3 levels deep in application code — outside framework or library base classes — is a common practical warning sign worth naming.

🎯 Say this in the interview — the exact lines to land

"Deep inheritance creates the fragile base class problem — a subclass ends up depending on the base's full implementation, not just its public contract, so a change that looks safe inside the base can silently break a subclass several levels down. Composition avoids that by having a class hold a behavior object instead of inheriting one, at the honest cost of more indirection and delegation code — it isn't a free win, just a better trade-off as hierarchies get deep."

  • Fragile base class → a base change breaks a subclass that depended on internal behavior, not just the public contract.
  • Penguin : Bird forcing Fly() onto every subclass is a real design smell — arguably an LSP violation too.
  • The fix → hold an interchangeable behavior object instead of inheriting a capability that doesn't fit every subtype.
  • Honest trade-off → composition adds indirection and boilerplate delegation code — inheritance is still simpler when it genuinely fits.
  • Practical smell → more than 2-3 levels deep in application code is a common warning sign, not a hard rule.
📖 Explanation ▾

As a hierarchy gets taller — D : C : B : A — every level ends up quietly depending on more than A's public contract; it depends on exactly how A is implemented today. That's the fragile base class problem: a maintainer adds a call from one of A's own methods to another of its methods — a change that looks completely safe from inside A — and it silently breaks D, three levels down, because D had overridden that now-newly-called method expecting it only to run in a different context. It's like renovating the ground floor of a building and only then finding out someone three floors up built their apartment assuming the ground floor would never change — the base class author usually can't see the breakage coming, because they don't know every subclass's assumptions.

A classic worked case: a Bird base class with a Fly() method. It looks like a clean is-a relationship until Fly() gets called polymorphically somewhere and a Penguin : Bird can't actually fly — forcing an awkward override that throws or does nothing. That's a real design smell, and arguably a Liskov Substitution Principle violation too (see that page for the substitutability rule itself — this page isn't re-teaching it). Composition sidesteps the problem: instead of Penguin : Bird, give bird-like things a held IMovementBehavior — a Penguin composes a SwimBehavior, an Eagle composes a FlyBehavior, and no subtype is forced to inherit a capability that doesn't apply to it.

None of this makes composition a free upgrade. Calling through a held reference is more indirection than getting behavior automatically from a base class, and it usually means writing explicit delegation code to forward calls to the composed object. When the is-a relationship is genuinely stable and shallow, inheritance is still the simpler, more honest model.

💻 See the code ▾
C# 
class Base
{
    public virtual void Save()
    {
        Validate();          // ⚠️ added later — looked safe inside Base
        // ...write to storage...
    }

    protected virtual void Validate() { }
}

class AuditedRecord : Base
{
    protected override void Validate()
        => throw new InvalidOperationException();
        // written assuming Validate() is only ever called explicitly, never from Save()
}

The call to Validate() inside Save() is new — and looks completely safe from inside Base. But AuditedRecord overrode Validate() assuming a different context, so every Save() call now throws — the fragile base class problem, live.

C# 
class Bird
{
    public virtual void Fly() => Console.WriteLine("Flying");
}

class Penguin : Bird   // ❌ Penguin IS a Bird, but can't fly
{
    public override void Fly()
        => throw new NotSupportedException(); // or a silent no-op — both are a smell
}

Anything that calls Fly() polymorphically on a Bird now risks a runtime exception the moment it happens to hold a Penguin — the inheritance forced a capability that doesn't apply.

C# 
interface IMovementBehavior { void Move(); }

class SwimBehavior : IMovementBehavior
{
    public void Move() => Console.WriteLine("Swimming");
}

class Penguin
{
    private readonly IMovementBehavior _movement = new SwimBehavior();

    public void Move() => _movement.Move(); // ✅ delegates — never claims to fly
}

Penguin holds whichever IMovementBehavior genuinely applies — an Eagle would hold a FlyBehavior instead — so no subtype is ever forced into a capability it doesn't have.

🌍 Real-world example ▾

Scenario: a codebase has a Bird base class with Fly(), and a new Penguin type needs adding later, by a team that didn't design the original hierarchy. Should Penguin inherit from Bird? No — a penguin genuinely can't fly, so inheriting forces an awkward override that throws or no-ops, and anything calling Fly() polymorphically breaks the moment it holds a Penguin. The fix: give bird-like things a held IMovementBehavior instead, so Penguin composes a SwimBehavior and never inherits a capability it doesn't have.
