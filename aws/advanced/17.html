A slow app on AWS — where do you actually start?

"What performance improvements would you make to a slow application running on AWS?"

Why it matters ▾
📊 Measure first
❗ ProblemGuessing which layer is slow (compute? a dependency? the database?) wastes effort on the wrong fix and can make the bill bigger without making anything faster.
✅ SolutionCloudWatch metrics (CPU, memory, queue depth, a specific slow dependency) show the real bottleneck before you spend any effort on it.
RecallMeasure before you tune — CloudWatch tells you which box to open.
⚙️ Right-size compute
❗ ProblemAn instance sized for the busiest day of the year sits mostly idle the rest of the time, and an instance sized too small just falls over the moment real traffic arrives.
✅ SolutionMatch the EC2 instance type / Auto Scaling Group size to the load you actually observe, and scale on real metrics instead of a fixed, over-provisioned size.
RecallRight-sizing + auto-scaling = capacity that follows real load, not a guess.
🧊 Cache above the DB
❗ ProblemRead-heavy, rarely-changing data (a product catalog, a session lookup) hits the database on every single request, even though the answer barely ever changes.
✅ SolutionElastiCache (Redis/Memcached) sits in front of the database and absorbs those repeat reads entirely.
RecallCache the reads that barely ever change — the database never sees them again.
🌍 Push to the edge
❗ ProblemA user far from your primary region pays the full round-trip latency to reach it, on every request, even for content that never changes per-user.
✅ SolutionCloudFront caches static/cacheable content geographically closer to the user; Route 53 latency-based routing sends the rest of the traffic to whichever region answers fastest.
RecallCloudFront + latency-based routing = distance stops being the bottleneck.
🗄️ Tune the database
❗ ProblemEvery read going to one primary database caps throughput, and a DynamoDB table with a poorly chosen partition key can have one "hot" partition doing all the work while the rest sit idle.
✅ SolutionRead replicas (or Aurora specifically) offload read traffic from the primary; for DynamoDB, a partition key that spreads access evenly avoids hot partitions — see DynamoDB Data Modeling.
RecallA hot partition is a key-design problem, not a capacity problem.
📬 Decouple with a queue
❗ ProblemA sudden burst of traffic forces the backend to process everything synchronously, right now, or requests start failing.
✅ SolutionSQS/SNS absorb the spike and let backend processing catch up asynchronously, instead of needing to scale instantly to match every burst.
RecallA queue turns a traffic spike into a backlog, not an outage.
💽 Storage performance
❗ ProblemThe wrong EBS volume type for the workload caps disk throughput/IOPS, and a large upload from far away is slowed by the same long network path everything else takes.
✅ SolutionPick an EBS type that matches the workload (general-purpose vs. a higher-IOPS type for a database-like access pattern), and use S3 Transfer Acceleration for large, geographically distant uploads.
RecallStorage has its own bottleneck — it isn't only a compute/database question.
❄️ Lambda cold starts
❗ ProblemA synchronous, latency-sensitive Lambda call can hit a cold start — initializing a fresh execution environment — right when a user is waiting on the response.
✅ SolutionProvisioned concurrency keeps instances pre-warmed, trading extra cost for consistently low latency — a narrower fix than the levers above, worth it only for the synchronous, latency-sensitive case.
RecallCold starts only matter for synchronous, latency-sensitive Lambda calls.
🔥 Easy interview recall

📊 Measure → CloudWatch before you touch anything

⚙️ Scale → right-size EC2/ASG to real load

🧊 Cache → ElastiCache in front of the database

🌍 Edge → CloudFront + Route 53 latency routing

🗄️ Database → read replicas/Aurora, fix hot partition keys

📬 Queue → SQS/SNS absorb bursts

Think: CloudWatch tells you which of the levers above actually matters — never start by guessing.

⚠️ Common Trap

Scaling up before measuring is the trap. A bigger EC2 instance or more read replicas can't fix a slow downstream dependency, a missing cache, or a hot DynamoDB partition key — check CloudWatch first, or you can pay more and still be just as slow.

🔄 Likely Follow-up

"So would you just cache everything?" No — cache only read-heavy, rarely-changing data; caching data that changes on every request adds staleness risk for little benefit, and a hot DynamoDB partition key still needs a redesign, not just a cache in front of it.

📖 Explanation ▾

Performance work on AWS starts the same way every time: look at CloudWatch before changing anything. CPU, memory, queue depth, and dependency latency metrics tell you which layer is actually slow — compute, cache, database, network, or storage — so effort goes where it actually helps instead of on a guess.

Once the bottleneck is known, the fix is usually one of a short list of standard levers: right-size and auto-scale compute so capacity tracks real load; cache read-heavy, rarely-changing data above the database with ElastiCache; push cacheable content to the edge with CloudFront, paired with Route 53 latency-based routing for users far from the primary region; offload database reads with read replicas (or Aurora specifically), and for DynamoDB, design the partition key so load spreads evenly instead of piling onto one hot partition; and decouple bursty work with SQS/SNS so backend processing can catch up asynchronously instead of scaling instantly to match every spike.

Storage has its own bottleneck, separate from compute and database: the EBS volume type has to match the workload's throughput/IOPS needs, and a large, geographically distant upload benefits from S3 Transfer Acceleration. Lambda is a narrower case — cold starts (the time to initialize a fresh execution environment) only matter for synchronous, latency-sensitive calls, and provisioned concurrency trades extra cost for pre-warmed instances when that latency genuinely matters.

💻 See the code ▾
AWS CLI 
# Scale out automatically once average CPU crosses 70%
aws application-autoscaling put-scaling-policy \
  --policy-name cpu-target-70 \
  --scaling-target-identifier service/my-cluster/my-service \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration file://policy.json

A target-tracking policy adjusts capacity to real CPU load — no manual resizing after the fact.

Pseudocode 
cached = cache.get(key)
if cached is not None:
    return cached          // ✅ cache hit — never touches the database

data = db.query(key)
cache.set(key, data, ttl=300)
return data                // cache miss — populate for next time

The cache-aside pattern: check ElastiCache before the database, and only fall through on a miss.

🧭 Use Cases — recognize these when they happen to you ▾
1 An EC2-based service is maxed out during a sudden traffic spike

Before scaling anything up, look at CloudWatch — if CPU is actually low and a downstream dependency is slow instead, a bigger instance or more instances won't help at all.

RememberA traffic spike doesn't automatically mean "add compute" — confirm compute is the bottleneck first.
2 A DynamoDB table has one very hot partition key while the others sit idle

More provisioned capacity doesn't spread the load across partitions — it just raises the ceiling on the same one hot partition. The real fix is a partition key that distributes access evenly across items.

RememberA hot partition key is a key-design problem, not a capacity problem.
3 Users far from your primary AWS region report slow page loads

The round trip to a single distant region is the actual cost here, not compute. CloudFront caches static/cacheable content near the user, and Route 53 latency-based routing sends dynamic traffic to whichever region answers fastest.

RememberDistance is a network problem — solve it at the edge, not with a bigger server.
🌍 Real-world example ▾

Your checkout API's p95 latency doubles during a flash sale. The direct answer: check CloudWatch first — CPU, memory, DB connection count, and queue depth — to see which layer is actually struggling. If it's compute, right-size/auto-scale. If it's the database, add a read replica or cache the hot reads in ElastiCache. If it's a burst of write traffic the backend can't keep up with synchronously, put SQS in front of it. The metric tells you which lever to pull — you don't need to guess.
