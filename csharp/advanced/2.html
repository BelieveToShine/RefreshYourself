lock — what's actually happening under the hood

"What does lock actually do under the hood?"

Why it matters ▾
  • A lost update is one of the most common real production bugs — a counter, balance, or cache that's silently wrong under load, with no exception pointing at it.
  • Interviewers ask this specifically to test whether you know lock is just Monitor.Enter/Monitor.Exit under a try/finally, not magic.
  • Shows up the moment two requests touch the same in-memory state at once — a shared dictionary, a counter, a cache.
🔥 Easy interview recall

lock = "syntactic sugar for Monitor.Enter / Monitor.Exit, wrapped in a try/finally."

Think: Two threads, no lock → lost update Same two threads, with lock → one waits its turn

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

lock(this) makes the whole object thread-safe. It only blocks other code that locks the exact same reference — since this is public, unrelated code elsewhere can lock on it too, creating contention (or deadlocks) that have nothing to do with the field you meant to protect; lock on a private, dedicated object instead.

🔄 Likely Follow-up

"Can the same thread take the same lock twice?" Yes — Monitor is reentrant. A thread that already holds the lock can enter another lock block on the same object without blocking itself, as long as it exits the same number of times it entered.

🎯 Say this in the interview — the exact lines to land

"lock is syntactic sugar for Monitor.Enter and Monitor.Exit wrapped in a try/finally — it gives one thread exclusive access to a block of code at a time, so a shared race condition can't leave changes half-applied."

  • lock → compiles to Monitor.Enter / Monitor.Exit in a try/finally.
  • A race condition = two threads read-modify-write shared state without coordination.
  • Never lock on this/typeof(X) — use a private, dedicated lock object.
  • A hot shared cache → reach for ReaderWriterLockSlim, not one lock around everything.
  • Monitor is reentrant — the same thread can safely re-enter its own lock.
📖 Explanation ▾

lock (obj) { ... } is the compiler doing the boring part for you: it emits Monitor.Enter(obj) before the block and Monitor.Exit(obj) in a finally after it, so the lock is released even if the block throws. Nothing about it is special-cased by the runtime beyond that — it's a fixed expansion, every time.

Exclusive means exactly one thread is inside the block at a time. Any other thread that calls Monitor.Enter on the *same* object simply parks there until the first thread calls Monitor.Exit — it's not busy spinning, it's asleep until woken.

A race condition is what happens without that: two clerks both glance at "12 tickets left," both write down 11, and one sale vanishes — not because either clerk made a mistake, but because neither knew the other had looked at the same number at the same moment.

💻 See the code ▾
C# 
int counter = 0;
void Increment() {
    for (int i = 0; i < 100000; i++)
        counter++;              // ❌ read-modify-write, not atomic
}

Parallel.Invoke(Increment, Increment);
Console.WriteLine(counter);     // ❌ almost never 200000

counter++ is really three steps — read, add one, write back — and two threads can interleave between them.

C# 
readonly object _gate = new();
int counter = 0;
void Increment() {
    for (int i = 0; i < 100000; i++)
        lock (_gate) { counter++; }   // ✅ one thread inside at a time
}

Parallel.Invoke(Increment, Increment);
Console.WriteLine(counter);               // ✅ always 200000

lock (_gate) forces the second thread to wait until the first thread's block finishes.

C# 
lock (_gate) {
    counter++;
}

// is (roughly) syntactic sugar for:
Monitor.Enter(_gate);
try {
    counter++;
} finally {
    Monitor.Exit(_gate);          // ✅ still runs even if an exception is thrown
}

The try/finally is the important part — it guarantees Monitor.Exit runs even if the block throws.

🌍 Real-world example ▾

A single-occupancy bathroom door lock. One person turns the latch, everyone else outside just waits — there's no line-cutting and no two people getting in at once. That's all lock is: a latch on a block of code.

Architecture: You have a shared, in-memory cache that's read constantly and written only occasionally, across many threads — how would you structure the locking so reads don't serialize behind each other? A single lock around the whole cache would force every read to queue up behind every other read, not just behind writes. Reach for a ReaderWriterLockSlim (or a concurrent collection built for this exact shape) instead, so any number of readers can proceed together and only a writer needs exclusive access.
