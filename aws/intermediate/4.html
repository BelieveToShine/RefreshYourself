GuardDuty finds threats; Inspector finds weaknesses

"How would you detect compromised credentials in an AWS account?"

Why it matters ▾
  • Checks whether you know AWS security tooling is layered, not one service doing everything — each tool answers a different question.
  • Comes up any time the conversation turns to "how would you know if you'd been breached" or incident response.
  • A natural follow-up after an IAM or security-architecture question, since detection is the next layer up from access control.

GuardDuty → active threats, right now

Inspector → known weaknesses, waiting to be found

Think: GuardDuty watches behavior. Inspector audits your stuff. Both feed Security Hub.

⚠️ Common Trap

GuardDuty and Inspector are not the same thing. GuardDuty watches for suspicious behavior happening right now (an unusual API call, odd network traffic); Inspector scans your own resources for known vulnerabilities that could be exploited later — one is about active threats, the other is about weaknesses sitting there waiting to be found.

🔄 Likely Follow-up

"CloudTrail vs. CloudWatch?" CloudTrail is the API audit log — who did what, and when. CloudWatch is metrics, logs, and performance monitoring — genuinely different jobs, though GuardDuty actually reads CloudTrail as one of its own detection inputs.

🎯 Say this in the interview — the exact lines to land

"GuardDuty detects active threats and anomalies in real time; Inspector finds vulnerabilities in your resources before they can be exploited — different jobs, and both feed into Security Hub for one unified view."

  • GuardDuty → watches CloudTrail, VPC Flow Logs, and DNS logs for suspicious behavior.
  • Inspector → scans EC2, container images, and Lambda for known CVEs.
  • Macie → scans S3 for exposed sensitive data like PII.
  • Security Hub → aggregates every finding into one dashboard with a security score.
  • WAF → filters app-layer traffic (SQLi/XSS); Shield → DDoS protection, Standard is free/automatic, Advanced is paid with more mitigation and support.
📖 Explanation ▾

GuardDuty is continuous, ML- and threat-intel-driven threat detection. It doesn't scan anything itself — it reads signals that already exist (CloudTrail management/data events, VPC Flow Logs, DNS query logs) and flags patterns that look wrong: API calls from a country your account never operates in, or an EC2 instance suddenly querying a known crypto-mining domain. It's about behavior, observed as it happens.

Inspector is the opposite direction: it doesn't watch behavior at all, it inventories your own resources — EC2 instances, container images, Lambda functions — and checks them against known vulnerability databases (CVEs). It's not reacting to something that just happened; it's telling you what's already sitting there, unpatched, before anyone exploits it. That's the whole distinction the recall line is pointing at: GuardDuty answers "is something bad happening," Inspector answers "what could go wrong if someone tried."

The rest of the landscape fills in around those three: Security Hub aggregates findings from all of them (plus partner/third-party tools) into one dashboard with a security score. CloudTrail is the underlying API audit log; AWS Config tracks how resource configuration drifts from what you intended over time. WAF filters HTTP traffic at the application layer against rules like SQL injection and XSS; Shield is DDoS protection — Standard is automatic and free for every AWS customer, Advanced is a paid tier with stronger mitigation and direct support during an attack.

🌍 Real-world example ▾

An EC2 instance suddenly starts making API calls from a geographic location the team never operates in. GuardDuty flags it as an anomaly, and a wired-up automated response (EventBridge triggering a Lambda) revokes that instance's credentials before whoever's behind it can do any real damage — the kind of catch Inspector, which only looks at known vulnerabilities, was never going to make on its own.
