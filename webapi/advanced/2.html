Retry vs. Resilience — trying again isn't staying up

What's the difference between just retrying on failure and genuine resilience — circuit breaking, timeouts, and fallback?

Why it matters ▾
  • A retry storm is a real production incident pattern — every caller retrying instantly against a struggling dependency can turn a brief hiccup into a full outage.
  • Interviewers ask this to check whether "retry 3 times" is the whole answer, or whether you reach for timeouts, circuit breakers, and fallback too.
  • A common opener before the interviewer pushes into how retry and idempotency have to be designed together, not independently.
🔥 Easy interview recall

Retry alone → hammers a struggling service harder

+ backoff & jitter → spreads retries out

+ circuit breaker & fallback → stops calling, degrades gracefully

Think: Retry is one tool. Resilience is retry + timeout + circuit breaker + fallback, working together.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"I added a retry loop, so it's resilient" is the trap. A bare retry with no backoff or circuit breaker is exactly the mechanism that turns a transient blip into a cascading outage — every caller independently hammers the same struggling dependency at the same time.

🔄 Likely Follow-up

"How do retry and idempotency relate?" Retrying a non-idempotent call — a POST with no idempotency key — risks the exact duplicate-creation problem Idempotency covers; resilience and idempotency have to be designed together, not independently, for a retry to be genuinely safe.

🎯 Say this in the interview — the exact lines to land

"Retry alone just hammers a struggling dependency harder — real resilience layers a timeout, exponential backoff with jitter, a circuit breaker that fails fast once a dependency is clearly down, and a fallback that degrades gracefully instead of failing the whole request."

  • Timeout → every outbound call gets one — detect failure fast, don't discover it through exhausted threads.
  • Retry → exponential backoff + jitter, never a tight instant loop.
  • Circuit breaker → fails fast once a dependency is clearly down, protecting both sides.
  • Fallback → degrade gracefully — cached data, a default, a reduced feature set — instead of nothing.
  • Retry + idempotency → must be designed together, or a retried POST risks creating duplicates.
📖 Explanation ▾

A bare retry loop is necessary but incomplete on its own. Retrying immediately against a struggling dependency doesn't help it recover — it adds load at the exact moment the dependency can least afford it, and every failed caller does this independently, at the same time. Exponential backoff waits progressively longer between attempts; jitter randomizes that wait slightly so many clients don't retry in the same synchronized wave.

A timeout has to exist on every outbound call — with no timeout, a slow dependency can hold a thread or connection open indefinitely, and the failure shows up as resource exhaustion instead of a clear, fast error. A circuit breaker goes further: after enough consecutive failures to one dependency, it opens and stops sending requests entirely for a cooldown period. That protects the dependency (no more added load while it's down) and the caller (no more threads spent on calls very likely to fail).

A fallback is what makes the difference visible to the end user. When the primary call fails, or the circuit is open, returning cached data, a sensible default, or a reduced feature set beats propagating the failure with nothing. None of these four mechanisms replaces the others — retry without a circuit breaker can still turn into a storm, and a circuit breaker with no fallback just fails fast with nothing to show for it.

💻 See the code ▾
C# 
public async Task<Order> GetOrderAsync(int id)
{
    for (int attempt = 0; attempt < 3; attempt++)
    {
        try { return await _client.GetOrderAsync(id); }
        catch (HttpRequestException) { } // ❌ no wait, no backoff — fires instantly
    }
    throw new OrderUnavailableException(id);
}

The trap in code form: three attempts fire back-to-back. If the dependency is struggling, this adds load at the exact moment it can least afford it.

C# 
var rnd = new Random();
for (int attempt = 0; attempt < 3; attempt++)
{
    using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(2)); // ✅ explicit timeout
    try { return await _client.GetOrderAsync(id, cts.Token); }
    catch (Exception) when (attempt < 2)
    {
        var delay = TimeSpan.FromMilliseconds(200 * Math.Pow(2, attempt)); // exponential backoff
        var jitter = TimeSpan.FromMilliseconds(rnd.Next(0, 100));          // spreads retries apart
        await Task.Delay(delay + jitter);
    }
}

Each retry waits longer than the last, plus a small random jitter — that is what stops many callers from retrying in the exact same instant.

C# 
public async Task<Order> GetOrderAsync(int id)
{
    if (_breaker.IsOpen)                  // ❌ dependency is known-bad right now
        return Order.CachedOrDefault(id); // ✅ fallback — fail fast, degrade gracefully

    try
    {
        var order = await _client.GetOrderAsync(id);
        _breaker.RecordSuccess();
        return order;
    }
    catch (Exception)
    {
        _breaker.RecordFailure();               // opens after N consecutive failures
        return Order.CachedOrDefault(id);
    }
}

When the breaker is open, the call never even goes out — the fallback returns something usable instead of waiting around to fail again.

🌍 Real-world example ▾

Your payment service starts timing out under load, and every one of its 40 callers is retrying 3 times with no backoff. Within a minute the dependency is worse off than before the first failure, and now you're paged for a second, bigger outage caused by the "fix" that was supposed to help. Add jittered exponential backoff immediately to stop the stampede, put a circuit breaker in front of that specific dependency so callers stop trying once it's clearly down, and give every caller a fallback — a cached last-known price, a queued-for-later response — so the failure never reaches the end user while the dependency recovers.
