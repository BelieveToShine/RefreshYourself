Angular routing — what actually happens the instant you hit refresh

"What happens when a user hits refresh on a deep client-side route, and what has to be configured server-side for it to work?"

Why it matters ▾
🧩 Route Parameter
❗ ProblemWithout a way to bake the resource's own identity into the path itself, showing user 1 vs. user 42 would need two entirely separate route configs, and no single URL could point at "this exact resource."
✅ SolutionA route parameter like :id in users/:id makes that identity part of the path itself — one route config matches every id, and the actual value is read off ActivatedRoute via params/paramMap.
RecallRoute parameter = lives in the path, answers "which resource."
🎛️ Query Parameter
❗ ProblemWithout a way to carry optional display state — like a sort order — separately from the path, changing how a list looks would look like navigating to a completely different resource.
✅ SolutionA query parameter like ?sort=name is appended after the path as separate, optional state — read off ActivatedRoute via queryParams/queryParamMap — without changing which resource is being requested.
RecallQuery parameter = appended after the path, answers "how to display/filter it."
🔥 Easy interview recall

Clicking a link → client-side, the router swaps components, nothing leaves the browser

Hitting refresh → real HTTP request for that exact path, straight to the server

Think: refresh = "ask the server for page 42," not "flip to page 42" — the server has to know what that ask even means.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The refresh 404 is not an Angular bug and can't be fixed "in Angular." The router never even loads on that request — the fix is a server-side fallback rule that serves index.html for unknown paths, before Angular's router gets a chance to run again.

🔄 Likely Follow-up

"So can a route guard be trusted for anything?" Yes, for UX — cleanly stopping an unauthenticated user from seeing a page's UI and redirecting them to login — but never as the real security boundary; a guard is bypassable by calling the API directly, so the backend must enforce authorization on its own.

"On refresh, the browser makes a real HTTP request for that exact URL — if the server has no fallback rule to serve index.html for unknown paths, it 404s before Angular's router ever loads. That's a server-config fix, not something Angular's router controls."

  • Child routes render inside the parent's own <router-outlet> — a shared shell/layout.
  • Wildcard route ** always goes last — routes match in order, top to bottom.
  • loadComponent/loadChildren → lazy-load code only when navigated to, cutting initial bundle size.
  • A route guard controls navigation only — never a substitute for server-side authorization.
📖 Explanation ▾

Angular's router (@angular/router) maps URL paths to components — a route is just a config object pairing a path string with a component (or, in the modern standalone style, a loadComponent). This is what makes the app feel like it has multiple pages while staying one single-page application: swapping the component doesn't reload the page.

A route parameter like :id in users/:id is part of the path itself and answers "which resource?" — a query parameter like ?sort=name is appended after the path and typically represents optional state that doesn't change which resource, just how it's shown. Both are read off ActivatedRoute, just through different properties.

Route parameterQuery parameter
Syntax:id in the path?sort=name
Answerswhich resourceoptional filter/display state
Read viaparams / paramMapqueryParams / queryParamMap

The rest of the config shape follows the same "one small rule at a time" pattern: child routes nest under a parent's children array and render inside that parent's own <router-outlet>; a redirect (redirectTo) sends one URL straight to another, most often as the default landing route; the wildcard (path: '**') catches anything unmatched and must sit last, since routes are checked top to bottom. A guard runs before a route activates and can allow, block, or redirect the navigation — but it's a client-side gate, not a security wall. Lazy loading defers a route's code until it's actually visited; loadComponent lazy-loads one standalone component, loadChildren lazy-loads a whole feature's route set as one chunk. A resolver fetches data before the route activates, so the component renders with its data already there.

💻 See the code ▾
TypeScript 
const routes: Routes = [
  { path: 'users/:id', component: UserDetailComponent },  // :id → route param
  { path: '', redirectTo: '/home', pathMatch: 'full' },   // default landing redirect
  { path: '**', component: NotFoundComponent }             // catch-all — must stay LAST
];

Routes match top to bottom — the wildcard has to be the last entry or it would swallow everything above it.

TypeScript 
{
  path: 'settings',
  loadComponent: () => import('./settings.component')
    .then(m => m.SettingsComponent)     // ✅ downloaded only when visited
}

Compare to component: SettingsComponent (an eager import) — that ships in the initial bundle whether the user ever visits /settings or not.

🧭 Use Cases — recognize these when they happen to you ▾
1 You link to /users/42 and the component needs to know exactly which user that is

The :id in users/:id is a route parameter — it's part of the path itself, so this one route config matches /users/42, /users/7, or any other id. The exact value is read off ActivatedRoute via params or paramMap.

RememberRoute parameter = lives in the path, answers "which resource."
2 You want the same list to also support sorting, without it looking like a totally different page

?sort=price is a query parameter — appended after the path as optional state that doesn't change which resource is being requested, just how it's shown. It's read off ActivatedRoute via queryParams or queryParamMap, separately from any route parameter.

RememberQuery parameter = appended after the path, answers "how to display/filter it."
3 You hit refresh on a deep route in production and get a 404, and assume Angular is broken

This is the refresh problem: the browser makes a real HTTP request for that exact path, and if the server has no fallback rule serving index.html for unknown paths, it 404s before Angular's router ever gets a turn to run. Nothing in the route config causes or fixes this — it's a server-side setting.

RememberA refresh 404 is a missing server fallback, never something the Angular router itself can fix.
🌍 Real-world example ▾

Client-side routing is like flipping through pages of a book someone already handed you — fast, no new book needed. Hitting refresh is like asking the librarian (the server) for that exact page number, fresh. If the librarian doesn't know "page 42 of this book" means "hand them the whole book and let them flip to it themselves," they'll just tell you no such page exists.
