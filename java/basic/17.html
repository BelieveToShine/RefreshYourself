this vs. super — which object, whose version?

"What do this and super actually refer to?"

Why it matters ▾
👉 this
❗ ProblemA constructor parameter and a field often share the same name (name), and inside a method you sometimes need to be explicit that you mean this object's own member, not a local variable.
✅ Solutionthis always refers to the current instance — the object the method is running on — so this.name = name; unambiguously assigns the field from the parameter.
Recallthis = the current object, right here.
⬆️ super
❗ ProblemA subclass overrides a method but still wants to run the parent's original version too, or needs to reach a field the subclass itself shadows with one of the same name.
✅ Solutionsuper explicitly reaches the parent class's version of a member or constructor — bypassing the subclass's own override or shadowed field.
Recallsuper = the parent's version, explicitly.
🔥 Easy interview recall

this → my own layer

super → the parent's layer

Think: same field name, two different boxes inside one object — this opens the front box, super reaches behind it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

super is not "the parent object." There's only ever one real object in memory — super is a way of accessing that same object's inherited members, not a reference to some separate parent instance.

🔄 Likely Follow-up

"Can you call super.method() from anywhere, or only inside an override?" From anywhere in the subclass — but it's overwhelmingly used inside an override, specifically to run the parent's original behavior in addition to the subclass's own.

🎯 Say this in the interview — the exact lines to land

"this refers to the current instance — the object the code is running on. super refers to the parent class's version of a member or constructor, used to call an overridden method's original implementation or reach a field the subclass shadows."

  • this(...)/super(...) → constructor calls, must be the first statement.
  • this.field → disambiguates from a same-named parameter.
  • super.method() → runs the parent's original, even inside an override.
📖 Explanation ▾

this is simply "the object this code is currently running on." It's most useful when a name is ambiguous — a constructor parameter shadowing a field of the same name — so this.balance = balance; clearly means "the field, from the parameter."

super doesn't point at a different object — there's only one object — it's a way of reaching the parent class's version of something that the subclass has overridden (a method) or shadowed (a field). super.makeSound() inside an override runs the parent's original logic; super.fieldName reaches a field the subclass re-declared with the same name, which is legal but rarely a good idea on its own.

💻 See the code ▾
☕ Java 
class Account {
    double balance;
    Account(double balance) {
        this.balance = balance;   // ✅ this.balance = the field, balance = the parameter
    }
}

Without this, balance = balance; would just assign the parameter to itself.

☕ Java 
class Animal {
    void makeSound() { System.out.println("generic sound"); }
}
class Dog extends Animal {
    @Override
    void makeSound() {
        super.makeSound();          // ✅ runs Animal's original first
        System.out.println("bark");
    }
}

super.makeSound() runs the parent's logic — the override still adds its own on top.

🧭 Use Cases — recognize these when they happen to you ▾
1 A constructor parameter has the exact same name as the field it sets

This is the single most common reason this shows up at all — without it, name = name; would just reassign the parameter to itself, leaving the field untouched. The #1 scenario you'll actually write.

RememberSame name as a parameter → this.field disambiguates.
2 An override needs to extend the parent's behavior, not replace it

Calling super.save() first, then adding the subclass's own extra logic, is the standard pattern for "run the base behavior, then add to it" without duplicating the parent's code.

RememberExtend, don't duplicate → call super.method() then add more.
3 You assume super gives you a separate parent object to work with

There is exactly one object in memory. super just picks which version of an inherited member you mean — it never allocates or references a separate parent instance.

Remembersuper ≠ a separate parent object — one object, inherited members.
🌍 Real-world example ▾

A family business with the same job title at two levels. "This manager" is whoever is currently on duty at this branch. "The founder's version" of that same job — how the role was originally done — is still there underneath, reachable on purpose, even after the current manager changed how the job is done day to day.
