DTO — what you hand out, not what you store

"What is a DTO, and why shouldn't you just return your entity directly from an API?"

Why it matters ▾
  • A near-universal API interview opener — it separates candidates who've only used a framework's defaults from ones who've shipped a real contract.
  • Comes up the moment a database column changes and a client app breaks, or a password hash quietly shows up in a JSON response.
  • Sets up the harder follow-up: who maps entity to DTO, and where that mapping should live.
🔥 Easy interview recall

Entity → what's stored

DTO → what's exposed

Think: a DTO is the contract you deliberately design. An Entity is just whatever the database happens to have.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding [JsonIgnore] to the sensitive entity fields is not the same as using a DTO. It's opt-out — every new sensitive field must remember its own [JsonIgnore], or it leaks by default; a DTO is opt-in by construction, so a new entity field is safe until someone deliberately adds it to the DTO.

🔄 Likely Follow-up

"Doesn't a DTO mean writing and maintaining a lot of near-duplicate classes?" Yes — tools like AutoMapper or Mapster exist specifically to cut that boilerplate. But the DTO's existence as an explicit, separate contract is the actual point, not how the mapping gets written; see DTO vs. Entity Mapping for whose job that mapping is.

🎯 Say this in the interview — the exact lines to land

"A DTO is a plain object shaped for exactly what the API contract needs to expose — not the database entity, not the domain model. Returning the entity directly risks leaking internal fields, couples every schema change to the API, and can't reshape or combine data the way a real response often needs to."

  • DTO → opt-in, explicit contract — you only get what you deliberately add.
  • Return the entity instead → over-exposure risk — a new sensitive column leaks by default.
  • Entity as the response → couples schema to API — every DB change becomes a breaking change.
  • A DTO can also → combine or reshape fields the entity's own shape can't.
📖 Explanation ▾

A DTO (Data Transfer Object) is a plain object shaped for whatever crosses the wire — nothing more. It isn't your database entity and it isn't your domain model; it's a shape you control independently of both, built for the consumer's convenience rather than the storage layer's.

Returning the entity directly has three real costs. Over-exposure: an entity often carries fields — a password hash, an internal flag, an audit column — that should never leave the server, and every new field added to the table is a new chance to forget to hide it. Coupling: if the response literally is the entity, a database migration becomes an API-breaking change. Shape mismatch: a response often needs to combine two entities or rename a field for the client — work the entity's own shape was never designed to do.

💻 See the code ▾
C# 
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
    public string PasswordHash { get; set; }  // never meant to leave the server
}

[HttpGet("{id}")]
public User Get(int id) => _db.Users.Find(id);
// ❌ returns PasswordHash to every caller — nothing stops the leak

The entity becomes the response — every field rides along, sensitive ones included.

C# 
public class UserDto
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }   // that's it — PasswordHash isn't declared here
}

[HttpGet("{id}")]
public UserDto Get(int id)
{
    var user = _db.Users.Find(id);
    return new UserDto { Id = user.Id, Name = user.Name, Email = user.Email };
}   // ✅ PasswordHash has no way to end up in the response

The DTO only declares the safe fields — there's nowhere for the leak to happen.

C# 
public class User
{
    public string PasswordHash { get; set; }
    [JsonIgnore]
    public bool IsInternalTestAccount { get; set; }
    public DateTime LastPasswordResetAt { get; set; }  // added later, no one remembered [JsonIgnore]
}
// ❌ LastPasswordResetAt now leaks — [JsonIgnore] only protects the fields someone remembered to tag

[JsonIgnore] is opt-out — a DTO's missing property list is opt-in, by construction.

🌍 Real-world example ▾

A resume is a DTO. Your personnel file is the entity. A resume is a curated document built for one audience — an employer — with exactly the fields that matter to them. Your personnel file has the SSN, the salary history, the disciplinary notes; you'd never hand the whole file to an interviewer just because copying the resume out of it felt like extra work.
