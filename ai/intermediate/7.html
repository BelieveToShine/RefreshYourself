When does an "agent" actually need the loop — and when is a fixed chain enough?

"What's the difference between an agent's ReAct loop and a fixed pipeline, and when would you reach for each?"

Why it matters ▾
  • Tests whether you reach for the simplest tool that fits, instead of building an agent by default — a real, common over-engineering judgment call.
  • Framed as an architecture question ("would you use an agent here, or just a pipeline?"), not a plain "what is ReAct" definition ask.
  • Separates candidates who can reason about cost, latency, and predictability tradeoffs from ones who just know the buzzword.
🔥 Easy interview recall

ReAct = "Reason → Act → Observe, repeat — until the model itself decides it's done."

Think: Fixed chain → the developer decides the sequence, once, up front Agent loop → the model decides the next step, every cycle, based on what it just observed

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for a full agent loop "just in case" is the actual mistake, not the loop itself. If the real sequence of steps is already known and doesn't vary per request, a fixed chain is simpler, cheaper, and easier to test — the extra reasoning and tool-call cycles an agent spends deciding something you already know are pure overhead.

🔄 Likely Follow-up

"What stops an agent loop from running forever?" Guardrails: a stopping condition — a maximum number of iterations, or a check that real progress is actually being made — plus retries for any step that fails, so a confused agent doesn't just keep cycling.

🎯 Say this in the interview — the exact lines to land

"ReAct is Reason → Act → Observe, repeated until the model decides it has enough to answer — the model decides what happens next each cycle, not the developer. I'd reach for an agent only when the right sequence of steps genuinely can't be known in advance; if the workflow is fixed and doesn't vary per request, a hard-coded chain is more predictable, easier to test, and cheaper."

  • Agent loop → use when the next step depends on what you find, e.g. look something up, then decide what to look up next.
  • Fixed chain → use when the workflow is well-known and the same for every request.
  • A full agent loop for a workflow that never varies → over-engineering — more latency, more cost, less predictable behavior, for no real benefit.
  • Any multi-step loop → needs guardrails — max iterations or a progress check, plus retries for failed steps.
📖 Explanation ▾

The ReAct pattern is the classic agent loop: the model reasons about what to do next, takes an action — typically a tool call — then observes the result. It reasons fresh about that new information on the next cycle, and repeats, until it decides it has enough to give a final answer. A fixed chain looks similar on the surface — it's also a series of steps — but the sequence itself is hard-coded by the developer ahead of time: always retrieve, then always summarize, then always format, no matter what any step actually returns.

DimensionAgent Loop (ReAct)Fixed Chain
Who decides the next stepThe model, fresh every cycleThe developer, in advance
Best whenThe right sequence can't be known ahead of timeThe workflow is well-known and doesn't vary per request
Cost & latencyHigher — extra reasoning/tool-call cyclesLower — nothing extra to decide
PredictabilityLower — harder to test every path it might takeHigher — easy to test and debug
Risk if misusedCan loop forever without a stopping guardMisses a case the hard-coded steps didn't anticipate

Any loop that runs more than one step needs guardrails: retries for a step that fails, and a stopping condition — a maximum number of iterations, or a check that real progress is being made — so a confused agent doesn't just keep cycling with nothing to show for it.

💻 See the code ▾
Python 
while not done:
    thought = reason(state)          # what should I do next?
    action = decide_action(thought)  # e.g. call a tool
    result = act(action)             # take the action
    state = observe(result)          # fold the result into state
    done = is_enough(state)          # the model decides when to stop
answer = generate_final_answer(state)

Every line of this loop is decided by the model at runtime, cycle by cycle — nothing here is hard-coded.

Python 
docs = retrieve(query)      # always retrieve first
summary = summarize(docs)   # always summarize next
answer = format(summary)    # always format last

The sequence itself is hard-coded — no step here decides what runs next.

🌍 Real-world example ▾

A support bot that checks account status, and only if that's ambiguous, decides to also look up billing history before answering — that's a genuine agent case, because the second lookup only happens depending on what the first one finds. A bot that always fetches order status and always formats the same reply, in the same order, for every ticket, doesn't need that — a fixed chain does the same job for less cost and fewer surprises.
