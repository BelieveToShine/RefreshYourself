SaveChangesInterceptor — stamp every save in one place

"How would you add audit fields (CreatedAt/ModifiedBy) automatically?"

Why it matters ▾
🧾 Interceptors & Audit Trails
❗ ProblemSetting CreatedAt and ModifiedBy by hand in every method gets forgotten, and one missed spot leaves a hole in your audit data.
✅ SolutionHook into SaveChanges() once. An interceptor sees every changed entity just before it is written and stamps it — nothing to remember at the call site.
RecallOne hook before every save → stamp the changed entities. Bulk ExecuteUpdate skips it.
🔥 Easy interview recall

Audit trail = "stamp the entities just before they are saved."

Think: SaveChangesInterceptor → a reusable hook on every save ChangeTracker.Entries() → the entities that are about to change ExecuteUpdate / raw SQL → bypass it, stamp by hand

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The interceptor sees every write to the database." Only writes that go through SaveChanges(). ExecuteUpdate, ExecuteDelete and raw SQL skip the change tracker, so no audit stamp is added unless you set it yourself.

🔄 Likely Follow-up

"How would you also keep the old values?" Each tracked entry exposes its original and current values, so the same hook can compare them and write audit rows. A database feature such as temporal tables is another route.

🎯 Say this in the interview — the exact lines to land

"I add a SaveChangesInterceptor that loops over ChangeTracker.Entries() and, for added or modified entities, sets CreatedAt, UpdatedAt and the current user. I register it once on the context options. Bulk ExecuteUpdate and ExecuteDelete skip the change tracker, so for those I set the audit values by hand."

  • SaveChangesInterceptor → one reusable hook on every save.
  • Entries<IAuditable>() → find the changed entities by an interface.
  • Overriding SaveChanges → simpler, but tied to one context.
  • ExecuteUpdate / raw SQL → no stamp unless you add it.
  • Current user → comes from an injected service, not a static.
📖 Explanation ▾

The change tracker already knows which entities are Added or Modified when you call SaveChanges(). A SaveChangesInterceptor is a class EF Core calls just before it writes — you override SavingChanges (and SavingChangesAsync for async callers), loop over ChangeTracker.Entries(), and set the audit fields. You register it once with AddInterceptors(...), and the call sites never think about it.

The older alternative is to override SaveChanges and SaveChangesAsync inside your DbContext. It works, but the logic lives inside that one context class. An interceptor is a separate, reusable class — easier to share and to give services like "who is the current user".

The blind spot is bulk work. ExecuteUpdate and ExecuteDelete send SQL straight to the database without tracking entities, so neither approach sees them.

💻 See the code ▾
C# 
public class AuditInterceptor : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        foreach (var e in eventData.Context!.ChangeTracker.Entries<IAuditable>())
        {
            if (e.State == EntityState.Added)    e.Entity.CreatedAt = DateTime.UtcNow;   // ✅ new rows
            if (e.State == EntityState.Modified) e.Entity.UpdatedAt = DateTime.UtcNow;   // ✅ changed rows
        }
        return base.SavingChangesAsync(eventData, result, cancellationToken);
    }
}

One class stamps every added or modified entity right before it is written (override the sync SavingChanges too if anyone calls SaveChanges()).

C# 
optionsBuilder
    .UseSqlServer(connectionString)
    .AddInterceptors(new AuditInterceptor());   // ✅ registered once

Register it on the context options — no call site changes.

C# 
await db.Orders
    .Where(o => o.Status == "Old")
    .ExecuteUpdateAsync(s => s
        .SetProperty(o => o.Status, "Archived")
        .SetProperty(o => o.UpdatedAt, DateTime.UtcNow));   // ✅ stamped by hand — no interceptor runs here

Bulk updates bypass the change tracker, so set the audit column in the update itself.

🌍 Real-world example ▾

Compliance asks "who last changed this order, and when?" The interceptor answers it for every normal save. The one gap: a nightly cleanup job that uses ExecuteUpdate changes rows without touching UpdatedAt — unless the job sets it explicitly.
