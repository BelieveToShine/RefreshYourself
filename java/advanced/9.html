Thread, Runnable, Callable — which one is the task, and which one actually runs it?

"Why is implementing Runnable usually preferred over extending Thread directly?"

Why it matters ▾
🧵 Thread
❗ ProblemSomething has to actually be the real, OS-backed unit of execution a program can start() — without one, there's no thread for any task to run on.
✅ SolutionThread is that execution unit itself. You can extend it directly, but doing so burns your only superclass slot and welds the task to the mechanism that runs it.
RecallThread = the actual thing that runs, not just a description of work.
🏃 Runnable
❗ ProblemExtending Thread for every task means that class can never extend anything else, and ties a reusable task to one specific way of running it.
✅ SolutionRunnable is a functional interface — just run(), no return value, can't throw a checked exception — describing the work, separate from how it executes. Implement it and hand it to a Thread or an ExecutorService.
RecallRunnable = the task description, pluggable into any execution mechanism.
📞 Callable<V>
❗ ProblemA background task that needs to hand back a result — or report failure via a checked exception — has no way to do either through run(), which returns nothing and can't throw checked exceptions.
✅ SolutionCallable<V> is the same idea as Runnable, but call() returns a value and can throw a checked exception. Submit it to an ExecutorService to get back a Future<V>.
RecallCallable = Runnable that can return a result and throw.
🔥 Easy interview recall

Thread → is the execution unit

Runnable → is the task, no return value

Callable → is the task, returns a value

Think: Thread runs it. Runnable describes it. Callable describes it and hands back an answer.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling .run() directly does not start a new thread. It just runs that code synchronously on the calling thread — only Thread.start() (or handing the task to an executor) actually begins concurrent execution.

🔄 Likely Follow-up

"If Runnable can't return a value, how do you get a result back from a background task on an ExecutorService?" Submit a Callable<V> instead — ExecutorService.submit(Callable<V>) returns a Future<V> you can call get() on, which blocks until the result (or thrown exception) is available.

🎯 Say this in the interview — the exact lines to land

"Thread is the actual unit of execution you start(); Runnable and Callable are task descriptions you hand to it. Runnable has no return value and can't throw a checked exception; Callable<V> returns a value and can — which is why it's used with an ExecutorService to get a Future<V> back."

  • Thread → the real execution unit, started via start().
  • Runnable → a task description, no return value, no checked exception.
  • Callable<V> → a task that returns V and can throw checked exceptions.
  • Prefer Runnable over extending Thread → keeps your one superclass slot free and separates task from mechanism.
  • Calling .run() directly → does not start a new thread — only start() (or an executor) does.
📖 Explanation ▾

A Thread is a real, OS-backed unit of execution — the only thing in this trio that start() can actually act on. Extending Thread directly is legal, but it's a poor default: Java only allows one superclass, so a class that extends Thread can never extend anything else, and the task is now permanently welded to "runs on its own dedicated thread" — it can't be handed to a shared thread pool instead.

Runnable and Callable<V> both solve that by describing what to run as a plain, pluggable object, leaving how it runs to whatever mechanism receives it — a Thread, or (more commonly in real code) an ExecutorService. The only real difference between the two is what happens when the work finishes: Runnable.run() returns nothing and can only throw an unchecked exception, while Callable<V>.call() returns a V and is allowed to throw a checked one — which is exactly why Callable is the one used when a caller needs the result, retrieved later through the Future<V> an executor hands back.

💻 See the code ▾
Java 
Runnable task = () -> System.out.println("running");

// Option A — hand it to a Thread
new Thread(task).start();

// Option B — hand it to a shared pool instead
ExecutorService pool = Executors.newFixedThreadPool(4);
pool.execute(task); // ✅ same task, no return value expected

The exact same Runnable works with either execution mechanism — the task never knew or cared how it would be run.

Java 
Callable<Integer> task = () -> {
    if (dataIsMissing()) throw new IOException("no data"); // ✅ checked exception allowed
    return computeResult();            // ✅ returns a value
};

Future<Integer> future = pool.submit(task);
int result = future.get(); // blocks until the result (or thrown exception) is ready

Callable is the one to reach for the moment the caller needs an answer back, not just confirmation the work ran.

Java 
Runnable task = () -> doWork();

task.run();         // ❌ runs on THIS thread — no concurrency at all
new Thread(task).start(); // ✅ this is what actually starts a new thread

run() is just a normal method call — nothing about calling it schedules anything on another thread.

🧭 Use Cases — recognize these when they happen to you ▾
1 A fire-and-forget background task that needs no result

For work where nobody needs to wait on a result — a log line, a cache warm-up — a plain Runnable handed to Thread or executor.execute() is simplest and carries no unused machinery.

RememberNo result needed → Runnable is the right-sized tool.
2 A background computation that must hand back a result, or might fail

Fetching a value, parsing a file, calling another service — anything where the caller eventually needs the answer (or the exception) uses Callable<V> submitted via executor.submit(), read back through Future<V>.get().

RememberNeed the answer back → Callable, not Runnable.
3 Someone calls task.run() directly, expecting concurrency

Calling .run() instead of .start() (or submitting to an executor) runs the code synchronously, right there — nothing about it is concurrent, and the calling thread blocks until it finishes.

Rememberrun() executes it. start() is what makes it concurrent.
🌍 Real-world example ▾

Runnable is a recipe card — it just describes what to cook, with no return value. Thread is the cook who can actually start cooking. Callable is a recipe card that promises to hand you back a finished dish you can collect later, instead of just confirming someone cooked something.
