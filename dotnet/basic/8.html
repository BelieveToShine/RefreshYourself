ILogger<T> — log once in code, let config decide what is kept and where it goes

"How does logging work in ASP.NET Core, and what is structured logging?"

Why it matters ▾
📝 ILogger<T>
❗ ProblemIf code wrote straight to a file or the console, changing where logs go would mean editing every call.
✅ SolutionInject ILogger<T> through DI; the registered providers decide the destination.
RecallOne call, many possible destinations.
🎚️ Levels
❗ ProblemDebug chatter is noisy and costly in production, yet needed while investigating.
✅ SolutionEvery message has a level, and appsettings.json sets the minimum per category — no code change.
RecallLevel + config = what gets kept.
🧩 Message templates
❗ ProblemBuilding the text with string interpolation bakes the values in, so they cannot be searched as fields later.
✅ SolutionA template like "Order {OrderId} shipped" keeps OrderId as a named property a provider can store.
RecallTemplate + args = structured.
🔥 Easy interview recall

ILogger<T> → injected, called like any service

Level → filtered per category in appsettings

{Template} → structured, never interpolated

Provider → decides where it lands

Think: The code says what happened. The config says what is kept and where it goes.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Using string interpolation in a log call. _logger.LogInformation($"Order {id} shipped") builds the whole string up front, even if that level is switched off, and the order id is now just text. Pass a template and the values as arguments instead.

🔄 Likely Follow-up

"How do you use Serilog instead of the built-in logging?" Serilog plugs in as a logging provider (builder.Host.UseSerilog(...)), so code keeps calling ILogger<T> and nothing in it changes. Serilog adds its own sinks and structured-data features.

🎯 Say this in the interview — the exact lines to land

"I inject ILogger<T> from DI and log with message templates, not interpolated strings, so the values stay as named properties. Each message has a level, and appsettings sets the minimum per category, so I can turn Debug on without a code change. Providers — console, a file, Application Insights, or Serilog — decide where it lands."

  • ILogger<T> → injected like any service — T becomes the category, usually the class name.
  • Levels → Trace, Debug, Information, Warning, Error, Critical — filtered by Logging:LogLevel.
  • Templates → named placeholders plus arguments — never $"..." inside a log call.
  • Providers → decide the destination — console, file, Application Insights, or Serilog as a replacement.
📖 Explanation ▾

ILogger<T> comes from the same DI container as any other service. T gives the log its category (normally the class name), which is what you filter on. A new web app starts with a few built-in providers already registered, including the console.

Levels run from Trace up to Critical. In appsettings.json, Logging:LogLevel sets a minimum per category, such as Default at Information and Microsoft.AspNetCore at Warning; the most specific matching category wins. Different environments can override it with their own appsettings file.

Structured logging means the message is a template with named placeholders, and the arguments are matched by position. A provider that understands structure (Application Insights, Serilog sinks) stores OrderId as a real field, so you can later ask for every entry about order 42 instead of searching sentences. See also: The Built-in DI Container, Configuration Sources, and the 500-errors-in-production scenario where logs are the first clue.

💻 See the code ▾
C# 
public class OrderService
{
    private readonly ILogger<OrderService> _logger;   // injected like any service

    public OrderService(ILogger<OrderService> logger) => _logger = logger;

    public void Ship(int orderId)
    {
        _logger.LogInformation("Order {OrderId} shipped", orderId);   // ✅ structured
        // _logger.LogInformation($"Order {orderId} shipped");        // ❌ values baked into text
    }
}

The template stays constant; only the argument changes, so every "shipped" entry groups together.

appsettings.json 
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}

Change a level here and the same code logs more or less — no recompile.

🌍 Real-world example ▾

A form with labelled boxes, not a free-text diary. A structured log is an incident form with fields for order id, user, and amount, so later you can ask "show me every entry for order 42" instead of reading sentences one by one.
