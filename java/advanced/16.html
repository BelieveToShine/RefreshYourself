thenApply() vs. thenCompose() vs. thenCombine() — transform, flatten, or join two

"When would thenCompose() be the right choice instead of thenApply()?"

Why it matters ▾
🔁 thenApply()
❗ ProblemSometimes you just need to transform a result with a plain function — reaching for the wrong combinator here adds needless async nesting.
✅ SolutionthenApply(fn) applies a plain T → R function directly on the result, for when fn doesn't itself return a CompletableFuture.
RecallthenApply = map, for a CompletableFuture.
📎 thenCompose()
❗ ProblemChaining another async step with thenApply produces a nested CompletableFuture<CompletableFuture<R>> — awkward, and easy to get wrong.
✅ SolutionthenCompose(fn) is for chaining another async step (fn returns CompletableFuture<R>) — it flattens the result instead of nesting it, the direct analogue of flatMap.
RecallthenCompose = flatMap, for a CompletableFuture.
🤝 thenCombine()
❗ ProblemTwo independent async calls both need to finish before you can produce one combined result — neither thenApply nor thenCompose operates on two separate futures at once.
✅ SolutionthenCombine(other, fn) joins the results of two independent CompletableFutures once both complete.
RecallthenCombine = join two independent futures into one.
🔥 Easy interview recall

thenApply → transform with a plain function

thenCompose → flatten a nested async step

thenCombine → join two independent futures

Think: thenApply(fn) → fn returns a value thenCompose(fn) → fn returns a CompletableFuture thenCombine(other, fn) → fn takes two results

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

thenApply is not for chaining another async call. Passing a function that itself returns a CompletableFuture to thenApply produces a nested CompletableFuture<CompletableFuture<R>> — exactly the case thenCompose exists to flatten.

🔄 Likely Follow-up

"What if you need to combine three futures, not two?" thenCombine only joins two at a time — chain it pairwise, or use CompletableFuture.allOf(...) and read each one's already-completed result once all of them finish.

🎯 Say this in the interview — the exact lines to land

"thenApply transforms a result with a plain function. thenCompose chains another async step and flattens the result instead of nesting it. thenCombine joins the results of two independent CompletableFutures once both finish."

  • thenApply(fn) → fn returns a plain value, no flattening needed.
  • thenCompose(fn) → fn returns a CompletableFuture, flattens instead of nesting.
  • thenCombine(other, fn) → joins two independent futures once both complete.
  • Mixing up thenApply/thenCompose → produces a nested CompletableFuture<CompletableFuture<R>>.
  • Need 3+ combined? → chain thenCombine pairwise, or use allOf().
📖 Explanation ▾

All three are stage-building methods on CompletableFuture — the difference is entirely in what the callback function returns and how many futures are involved. thenApply expects a plain value back, so it just wraps that value in the next stage. thenCompose expects another CompletableFuture back, so it has to unwrap ("flatten") that nested future into the chain's own single level instead of leaving it double-wrapped.

thenCombine solves a different shaped problem entirely — not "what happens after this one future," but "once these two independent futures are both done, do something with both results together." It doesn't care whether either input future depends on the other; they can (and usually do) run fully concurrently.

💻 See the code ▾
Java 
CompletableFuture<Double> priceWithTax =
    CompletableFuture.supplyAsync(() -> getPrice())
        .thenApply(price -> price * 1.08); // ✅ plain T → R

The lambda returns a plain double, not a CompletableFuture — exactly what thenApply expects.

Java 
CompletableFuture<Orders> orders =
    CompletableFuture.supplyAsync(() -> fetchUser(id))
        .thenCompose(user -> fetchOrdersAsync(user)); // ✅ flattened, not nested

fetchOrdersAsync already returns a CompletableFuture<Orders> — thenCompose keeps the chain at one level instead of nesting it.

Java 
CompletableFuture<Double> price = CompletableFuture.supplyAsync(() -> getPrice());
CompletableFuture<Integer> stock = CompletableFuture.supplyAsync(() -> getStock());

price.thenCombine(stock, (p, s) -> p * s); // ✅ joins two independent futures

price and stock run concurrently — neither waits on the other — and the combining function only runs once both are done.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to apply a plain calculation to an async result

A tax/fee calculation on a price, a formatting step on a fetched string — any plain, non-async function on an already-async result is exactly what thenApply is for.

RememberPlain calculation on a result → thenApply.
2 The next step is itself another async call that depends on this one's result

fetchOrdersAsync returns its own CompletableFuture — thenCompose keeps the whole chain flat instead of producing a future-of-a-future.

RememberNext step is itself async → thenCompose.
3 A function that returns a CompletableFuture gets passed to thenApply by mistake

This compiles, but every caller now has to unwrap a nested future to reach the real value. A common interview trap: treating thenApply/thenCompose as interchangeable — they aren't, once the callback itself is async.

Rememberfn returns a CompletableFuture → thenCompose, never thenApply.
🌍 Real-world example ▾

A product page needs a price (from a pricing service) and a stock count (from an inventory service) — two calls, neither depending on the other. Firing both as separate CompletableFutures and joining them with thenCombine lets both run concurrently and composes the final answer the moment the slower of the two finishes, instead of needlessly waiting on them one after another.
