async void — an exception nobody can catch

"Why should you avoid async void, and when is it actually acceptable?"

Why it matters ▾
💥 async void
❗ ProblemAn async void method hands the caller nothing to wait on or catch from — no Task — so the caller can't await it, can't know when it finishes, and can't put a try/catch around it. If it throws, the exception is raised on the SynchronizationContext instead and can take the whole process down.
✅ SolutionReturn Task (or Task<T>) from every async method. The exception is stored inside the Task and comes back out at the caller's await. Keep async void only where the signature forces void — event handlers.
Recallasync void = fire-and-forget with no safety net; async Task = the caller can await and catch.
🔥 Easy interview recall

async void = "fire and forget — and the exception has nowhere to go."

Think: Task carries the exception back to the caller; void loses it. Use void only for event handlers.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A try/catch around a call to an async void method does not catch what it throws. The method returns to you at its first await, long before the exception happens — so by then your catch block is already gone.

🔄 Likely Follow-up

"So how do you handle exceptions in an async event handler?" Put a try/catch inside the handler itself and keep the body small — call an async Task method and await it there. See Events vs. Delegates for why handlers must return void.

🎯 Say this in the interview — the exact lines to land

"async void can't be awaited and its exceptions can't be caught by the caller — they go to the SynchronizationContext and can crash the process. I return Task everywhere and use async void only for event handlers."

  • async void → can't be awaited, so the caller can't know when it finishes.
  • Exceptions → escape to the SynchronizationContext instead of reaching the caller's catch.
  • Return Task → the exception is stored in the Task and surfaces at await.
  • Acceptable use → event handlers, because the delegate type requires void — and catch inside them.
  • Tests and callers → an async Task method can be awaited; an async void one can't.
📖 Explanation ▾

An async method that returns Task hands the caller a handle to the work. If the method throws, the compiler-generated code catches the exception and stores it in that Task. The caller's await reads it back and re-throws it right there, so a normal try/catch works.

An async void method has no such handle. The caller gets control back at the first await and has nothing to wait on. If the method throws later, the exception is posted to the SynchronizationContext that was current when it started. In a UI app that is the UI thread, and an unhandled exception there typically crashes the app. Without a context it is raised on a thread-pool thread, which can end the process the same way.

So why does async void exist at all? Event handlers. The delegate type (for example EventHandler) returns void, so a handler that needs to await has to be async void. That is the one accepted case — and the fix is to catch inside the handler.

💻 See the code ▾
C# 
async void SaveBad()                       // ❌ caller can't await or catch
{
    await Task.Delay(10);
    throw new InvalidOperationException("boom");
}

async Task SaveAsync()                      // ✅ exception stored in the Task
{
    await Task.Delay(10);
    throw new InvalidOperationException("boom");
}

try { await SaveAsync(); }                  // ✅ caught here
catch (InvalidOperationException) { /* handle */ }

With SaveBad() the same try/catch would never fire — the exception escapes to the context.

C# 
button.Click += async (sender, e) =>      // ✅ acceptable: event handler must be void
{
    try { await SaveAsync(); }
    catch (Exception ex) { ShowError(ex); }
};

Catch inside the handler — nobody above it can.

🌍 Real-world scenario ▾

A desktop app crashes with no obvious cause after a "Save" click: the click handler called an async void helper that threw on a network error, and nothing could catch it. Changing the helper to return Task and awaiting it inside one try/catch in the handler turned the crash into a normal error message.
