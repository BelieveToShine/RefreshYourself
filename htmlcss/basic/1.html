HTML Fundamentals — the browser never renders your HTML, it renders the DOM built from it

"What is HTML, and what actually happens to that markup inside the browser before anything shows up on screen?"

Why it matters ▾
  • Every later HTML/CSS/JS answer assumes you already know the browser works with the DOM, not your raw markup — CSS attaches to DOM nodes and JavaScript reads and changes them, never the text file itself.
  • Almost always the literal opening question in a front-end interview, often folded into "walk me through what happens when a browser loads a page."
  • Saying "HTML is the language browsers use to show pages" and stopping there skips the actual mechanic an interviewer is probing for — how that text turns into a tree in memory.
🔥 Easy interview recall

Element → a tag + its content (<p>Hi</p>)

Attribute → extra info inside the tag (class="hi")

DOM → the tree the parser builds from your HTML

Think: HTML is the text file you write. DOM is what the browser actually works with — CSS and JavaScript both talk to the DOM, never to the raw text.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Invalid HTML doesn't make the browser stop. HTML parsers follow defined error-recovery rules and still build a DOM from broken markup — the real risk is an unexpected tree, not a crashed page.

🔄 Likely Follow-up

"So why bother writing valid HTML if the browser fixes it anyway?" Because the parser's recovery rules don't always guess the structure you meant — a misplaced or unclosed tag can silently produce a different DOM tree than you expect, and CSS/JavaScript relying on that structure breaks along with it.

🎯 Say this in the interview — the exact lines to land

"HTML is the markup language that structures content into elements. The browser's parser reads that markup and builds the DOM — an in-memory tree of nodes — and the DOM, not the text file, is what CSS and JavaScript actually work with. HTML5 added real semantic elements and native form/media support, cutting down on plugin-heavy workarounds, and the parser is deliberately forgiving — invalid markup still produces a DOM, just not necessarily the one you intended."

  • Element vs. attribute → an element is the tag plus its content; an attribute is extra information sitting inside the opening tag.
  • Block vs. inline → block elements take the full width and start a new line; inline elements flow inside the surrounding text.
  • HTML → DOM → the parser turns raw markup into the DOM tree; that tree is what the browser actually renders, not the text file.
  • HTML5 vs. earlier HTML → real semantic tags (<header>, <nav>, <article>) plus native form/media elements, reducing the need for plugins.
  • Forgiving parser → invalid HTML still builds a DOM through defined error-recovery rules — it just might not be the tree you meant.
📖 Explanation ▾

HTML (HyperText Markup Language) structures content into elements — an opening tag, the content, and a closing tag, like <p>Hello</p>. An attribute lives inside the opening tag and adds extra information about that element, like href on an <a> or class on a <div> — an element is the thing itself, an attribute just describes it further. HTML5 is the current standard; compared to earlier HTML it added real semantic elements (<header>, <nav>, <article>, <footer>) and native support for things like video, audio, and richer forms that used to lean on browser plugins.

Every HTML element renders as either block or inline by default — the browser's own default stylesheet decides which.

BlockInline
WidthTakes the full width availableOnly as wide as its own content
Line behaviorStarts on its own new lineFlows inside the surrounding line of text
Examples<div>, <p>, <header><span>, <a>, <strong>

The DOM (Document Object Model) is the tree of nodes the browser actually works with — built by the HTML parser reading your markup tag by tag and creating a node for each element, nested the way the tags were nested. This is the step that turns a flat text file into something CSS can select and JavaScript can walk and change. The parser is famously forgiving: the HTML specification defines exact error-recovery rules for broken markup (an unclosed tag, a misplaced element), so a browser doesn't just refuse to show the page — it still produces a DOM, following those rules, which is why "invalid" HTML usually still renders something. That DOM is also only half the picture — CSS parses into its own tree (the CSSOM), and the two combine into what actually gets painted on screen, covered in full later in the Advanced track.

💻 See the code ▾
HTML 
<a <!-- attribute --> href="/about" class="nav-link">About</a> <!-- element -->

The element is the whole <a>...</a> — tag plus content. href and class are attributes, extra facts about that one element.

HTML 
<div>Block: full width, own line</div>
<span>Inline: flows in the text</span>

<div> pushes onto its own line by default; <span> sits inline, right next to whatever text surrounds it.

HTML 
<p>Unclosed paragraph
<div>Next block</div> <!-- ✅ parser auto-closes the <p> first -->

No closing </p>, no crash — the parser's error-recovery rules close it automatically before starting the <div>.

🌍 Real-world example ▾

Think of HTML like a recipe card, and the DOM like the chef's mise en place. The chef (the browser) reads your card once and turns it into organized bowls of prepped ingredients — that's the DOM. Every later step, seasoning (CSS) or plating (JavaScript), works off those bowls, never off the card itself, which is why what's actually on screen can differ from what you typed if the card was messy.
