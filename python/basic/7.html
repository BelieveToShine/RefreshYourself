🔥 Python · Basic · Must Know

A closure remembers the variable, not the value it happened to hold when the closure was created

"What is LEGB? What is a closure? Why does a closure capturing a loop variable famously surprise people?"

Why it matters ▾
  • Closures power decorators, callbacks, and every "return a function that remembers something" pattern — LEGB is the exact rule Python uses to find any name at all.
  • One of Python's most famous interview traps — a wrong answer here is a fast tell that someone hasn't actually hit it in real code.
  • Explains a real bug: a list of callbacks or event handlers built inside a loop that all end up reacting to the same "last" item.
🔥 Easy interview recall

Local → this function's own names

Enclosing → outer function's names

Global → module-level names

Built-in → Python itself (len, print, …)

Think: a closure carries its Enclosing scope with it — but it carries the variable itself, not a snapshot of its value.

🧠 Visual Mental Model — understand it in 5 seconds
🔮 Predict the Output
Python 
funcs = []
for i in range(3):
    funcs.append(lambda: i)

print([f() for f in funcs])

What does this print, and why does this surprise people?

Answer: [2, 2, 2] — not [0, 1, 2]. Every lambda closes over the SAME variable i, not the value it held when that lambda was created. By the time any of them is actually called, the loop has already finished and i is 2 for all three.

⚠️ Common Trap

A closure does not snapshot the loop variable's value. It captures the variable itself, evaluated only when the closure is actually called — which is usually well after the loop has already finished.

🔄 Likely Follow-up

"How do you actually resolve a variable name at runtime?" Python checks Local scope first, then any Enclosing function scope, then Global (module) scope, then Built-in — the LEGB chain, stopping at the first scope where the name is found.

🎯 Say this in the interview — the exact lines to land

"A closure captures the variable, not a snapshot of its value — that's exactly why the classic loop-lambda trap happens. Python resolves any name by checking Local, then Enclosing, then Global, then Built-in scope, in that order."

  • LEGB → Local → Enclosing → Global → Built-in, the exact order Python searches for a name.
  • global → lets a function assign to a module-level name.
  • nonlocal → lets a nested function assign to an enclosing (non-global) function's variable.
  • The fix → default-argument capture lambda i=i: i binds i's current value at each iteration, or use a helper function that takes i as a parameter.
📖 Explanation ▾

Python resolves every name using the LEGB rule: Local (this function's own names) → Enclosing (any outer function's names) → Global (the module's top-level names) → Built-in (Python's own names like len or print). By default a function can only read a name from an enclosing or global scope, not assign to it — global tells a function "assign to the module-level name instead of creating a local one," and nonlocal does the same thing one level up, for an enclosing function's variable.

A closure is an inner function that keeps access to its enclosing function's variables even after that outer function has already returned. The part that surprises people: a closure captures the variable itself — a live reference into the enclosing scope's cell — not a frozen copy of whatever value it held the moment the closure was created. The value is only looked up when the closure actually runs, which can be long after the variable has already changed.

💻 See the code ▾
Python 
funcs = []
for i in range(3):
    funcs.append(lambda: i)   # ❌ every lambda shares the same i

print([f() for f in funcs])

"What does this print?" [2, 2, 2] — every lambda shares the exact same enclosing-scope cell for i; none of them captured a private copy of the value.

Python 
funcs = []
for i in range(3):
    funcs.append(lambda i=i: i)   # ✅ default binds i's value NOW

print([f() for f in funcs])

The fix: giving i as a default argument (lambda i=i: i) evaluates and binds i's current value right when the lambda is created, as a brand-new parameter — later calls no longer look back at the loop's shared i at all.

🌍 Real-world example ▾

This bites people building a list of UI callbacks or event handlers inside a loop — one button per item, say — and watching every single handler react to the last item instead of its own, because every closure was reading the same shared loop variable by the time a click actually happened.
