Higher-order, pure, curried — buzzwords, or things you're already writing?

"What do terms like higher-order function, pure function, composition, currying, and memoization actually mean — and when would you genuinely reach for each one in real code?"

Why it matters ▾
🔗 Composition
❗ ProblemOne giant function that does every transformation end-to-end is hard to test on its own or reuse in a different order.
✅ SolutionChain small pure functions so each one's output becomes the very next one's only input — pipe reads that chain left to right, compose right to left.
RecallComposition = one function's output → the next one's input, chained.
🧬 Currying
❗ ProblemA generic multi-argument function can't be specialized gradually one known value at a time — you either supply every argument or none.
✅ SolutionBreak it into a chain of one-argument calls, supplying exactly one argument each time until every argument has arrived.
RecallCurrying = one argument per call, chained, until all arrive.
🧩 Partial Application
❗ ProblemSometimes you just want to pre-configure a function with a fixed value now — a logger with a fixed prefix — without being forced into currying's one-argument-per-call chain.
✅ SolutionLock in some arguments right now and hand back a function that still takes the rest together, in a single call.
RecallPartial application = some args fixed now, the rest arrive together.
🗄️ Memoization
❗ ProblemRe-running the same expensive pure calculation for the same input, over and over, wastes time recomputing an answer that will never change.
✅ SolutionCache the return value keyed by its input, so a repeat call with the same input returns the cached result instantly — safe only because the function is pure.
RecallMemoization = same input again → cached result, only safe on pure functions.
🔥 Easy interview recall

Higher-order function → takes or returns a function

Pure function → same input, same output, no side effects

Composition → one function's output becomes the next one's input

Currying → one argument per call, until all are supplied

Think: if a function is pure, you can compose it, memoize it, or run it in any order — none of that is safe once there's a side effect.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Currying is not partial application. Currying always breaks a function down into a chain of one-argument calls; partial application just fixes some arguments now and still hands you a function that takes the rest together in one call.

🔄 Likely Follow-up

"So does compose() run left-to-right like pipe()?" No — compose runs right-to-left (the last function listed runs first), while pipe runs left-to-right. Same idea, opposite reading order, which is exactly why a codebase should pick one and stay consistent.

🎯 Say this in the interview — the exact lines to land

"A higher-order function takes or returns a function; a pure function always gives the same output for the same input with no side effects. Composition chains pure functions so one's output feeds the next's input, currying breaks a multi-argument function into one-argument calls, and memoization caches a pure function's result so it isn't recomputed for the same input."

  • Higher-order function → use when behavior itself needs to be passed around — a callback, a comparator, a middleware.
  • Pure function → no mutation, no shared state — the safest thing to test, reuse, or run in any order.
  • Composition → use to build one pipeline out of small, single-purpose functions instead of one long function.
  • Currying / partial application → use to pre-configure a function — a logger with a fixed prefix, a validator with a fixed rule set.
  • Memoization → only safe on a pure function — cache by input, skip the recompute, never cache something with a side effect.
📖 Explanation ▾

A higher-order function is just a function that takes another function as an argument, returns one, or both — map, filter, and reduce all qualify, and so does anything that wraps a callback. A pure function is one where the output depends only on its arguments — no reading or writing anything outside itself, no side effect like mutating an array, touching the DOM, or hitting a network call. Immutability is what makes purity practical: instead of changing a value in place, a pure function returns a new one, so nothing else holding the old value gets surprised.

Composition is chaining pure functions so each one's output becomes the next one's input — pipe reads that chain left to right; compose reads the same list right to left. Currying turns a function that takes several arguments into a chain of functions that each take exactly one, one call at a time, until every argument has arrived. Partial application is the more relaxed cousin: it locks in some arguments right now and returns a function that still takes the rest together, in a single call — not necessarily one at a time.

Memoization caches a function's return value keyed by its input, so a repeat call with the same input skips the work and returns the cached answer instantly. It only works safely on a pure function — caching something that also has a side effect (like sending an email) would silently skip that side effect on every repeat call, not just the expensive computation.

💻 See the code ▾
JavaScript 
// ❌ impure — mutates the array the caller passed in
function addItem(cart, item) {
  cart.push(item);           // side effect: caller's array changes too
  return cart;
}

// ✅ pure — same inputs always produce a new array, nothing mutated
function addItemPure(cart, item) {
  return [...cart, item];   // a new array, original untouched
}

addItem mutates the caller's array — a side effect; addItemPure always returns a new array, so the same input never surprises anyone holding the old one.

JavaScript 
function withLogging(fn) {            // higher-order: takes a function
  return (...args) => {              // higher-order: returns a function
    console.log('calling', fn.name, args);
    return fn(...args);
  };
}

const loggedAdd = withLogging((a, b) => a + b);
loggedAdd(2, 3);  // logs the call, then returns 5

withLogging both accepts a function and returns one — that's the whole definition of higher-order, nothing more exotic than that.

JavaScript 
const pipe = (...fns) => x => fns.reduce((acc, fn) => fn(acc), x);

const double = x => x * 2;
const increment = x => x + 1;
const square = x => x * x;

pipe(double, increment, square)(3);  // ((3*2)+1)^2 = 49

pipe runs left to right — double first, square last; compose(double, increment, square) would run the same list right to left instead.

JavaScript 
const curriedAdd = a => b => c => a + b + c;
curriedAdd(1)(2)(3);            // 6 — one argument per call

const add = (a, b, c) => a + b + c;
const addFive = add.bind(null, 5);  // partial application — fixes "a"
addFive(2, 3);                    // 10 — the rest arrive together

curriedAdd only ever takes one argument per call; bind fixes one argument up front and still accepts the rest together — the real difference between currying and partial application.

JavaScript 
function memoize(fn) {
  const cache = new Map();
  return (...args) => {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);  // ✅ skip the recompute
    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

Only safe because fn is pure — the same arguments always mean the same result, so caching by arguments never returns a stale answer.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're chaining several small transformations into one pipeline (parse → validate → format)

This is the #1 scenario you'll actually run into: each function only handles one transformation, and pipe wires them together so one step's output becomes the very next step's only input — exactly the pipe(double, increment, square)(3) chain in the diagram above, just with your own steps swapped in.

RememberChained transformations, output feeding the next input → composition.
2 You derive a specific function from a generic one, and aren't sure whether you're currying it or partially applying it

add(a, b, c) is one generic function, but "derive a version of it" can mean two different things. Currying always breaks it into a chain of one-argument calls (curriedAdd(1)(2)(3)); partial application fixes some arguments now and hands back a function that still takes the rest together in one call (addFive(2, 3)).

RememberOne arg at a time, chained → currying. Some args fixed, rest together → partial application.
3 The same expensive pure calculation keeps getting called with the same input, over and over

memoize() wraps the function with a cache keyed by its arguments, so a repeat call with the same input returns the cached answer immediately instead of recomputing it. This is only safe because the wrapped function is pure — caching something with a side effect would silently skip that side effect on every repeat call.

RememberSame input again → return the cached result, safe only on pure functions.
🌍 Real-world example ▾

A list of cards re-renders every child even though nothing visually changed. Many UI frameworks decide whether to re-render by checking if a prop's reference changed (===) — a helper that mutates the array in place keeps the same reference, so that check misses the real change. Swapping it for a pure version that returns a new array (immutability) fixes the wasted re-renders without touching any rendering code.
