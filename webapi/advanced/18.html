Something's broken and you don't know what yet — do you have a repeatable method?

"Something's wrong in production and you don't yet know what — what's your overall approach, not just for one specific bug?"

Why it matters ▾
🧭 A General Troubleshooting Method
❗ ProblemWithout a repeatable framework, an unfamiliar incident turns into ad hoc guessing — jumping straight to "restart it" can mask the real cause and lets the same class of failure happen again.
✅ SolutionWork the same six steps every time regardless of the specific bug: scope impact, check recent changes, check the golden signals, test the lowest-risk hypothesis first, fix it, then write it up so it doesn't recur.
RecallSame method every incident — scope, recent changes, golden signals, cheapest test first, write it up.
🔥 Easy interview recall

Production troubleshooting = "scope it, check what changed, read the signals, test cheap before risky."

Think: Scope → how many users, which endpoints, since when Recent changes → most incidents correlate with something that just changed Golden signals → latency, traffic, errors, saturation Cheapest test first → read logs before restarting anything

⚠️ Common Trap

"Restart the service" as a first move is not troubleshooting. It can mask the actual cause by wiping in-memory diagnostic state, and it often just delays the same failure recurring since the underlying cause was never found.

🔄 Likely Follow-up

"What's the very first thing to check when an incident starts?" What changed recently — a deploy, config, or dependency version bump — since the large majority of production incidents correlate with something that changed shortly before, not a random pre-existing bug suddenly manifesting.

🎯 Say this in the interview — the exact lines to land

"I use the same framework regardless of the specific bug: first confirm and scope the impact — how many users, which endpoints, since when — before touching anything. Then check recent changes, since most incidents correlate with a deploy, config, or dependency change. Then read the golden signals — latency, traffic, errors, saturation — to narrow down which layer is struggling. I test the least risky hypothesis first, like reading logs, before a risky one like restarting or rolling back. Once it's stable, I write a blameless root-cause summary so the same class of issue doesn't recur."

  • Scope first → impact, endpoints, timing, before touching anything.
  • Recent changes → a deploy, config, or dependency bump is the most likely culprit.
  • Golden signals → latency, traffic, errors, saturation narrow down the layer.
  • Cheapest test first → read data before a risky action like a restart or rollback.
  • Blameless postmortem → closes the loop so the same incident class doesn't repeat.
📖 Explanation ▾

The value of a general framework is that it doesn't depend on already knowing what's wrong. Step one is confirming and scoping the actual impact — how many users, which endpoints or regions, and since when — before changing anything; a fix attempted before the blast radius is understood can easily make things worse or hide the real signal. Step two is checking recent changes — a deploy, a configuration change, a dependency version bump — because the large majority of production incidents correlate with something that changed shortly before, not a dormant bug that happened to manifest at random.

Step three is the golden signals — latency, traffic, errors, and saturation — which narrow down *which* layer is actually struggling (the API, the database, a downstream dependency) before forming a specific hypothesis. Step four is testing that hypothesis starting with the least risky action available — reading logs and metrics — before a risky one like restarting a service or rolling back a deploy, since a risky action taken on a guess can destroy the evidence needed to actually confirm the cause. Once the system is stable and the cause is confirmed, a blameless postmortem documents what happened and why, so the fix addresses the actual failure mode rather than just this one instance of it.

StepWhat it answers
1. Scope impactHow bad is it, and for whom, before I touch anything?
2. Recent changesWhat changed right before this started?
3. Golden signalsWhich layer — API, DB, downstream — is actually struggling?
4. Cheapest test firstCan I confirm the hypothesis without a risky action?
5. Blameless postmortemHow do we stop this exact class of issue recurring?
💻 See the code ▾
C# 
// Golden signals are usually already there to read — the method is using them in order,
// not reaching for a fix before checking them.
app.MapGet("/health/signals", () => Results.Ok(new
{
    LatencyP99Ms = Metrics.LatencyP99,     // latency
    RequestsPerSecond = Metrics.Rps,       // traffic
    ErrorRatePercent = Metrics.ErrorRate,  // errors
    CpuPercent = Metrics.Cpu               // ✅ saturation — check this before deciding it's "just load"
}));

The four golden signals in one place — reading them is step 3, before any action is taken, not an afterthought once something's already been changed.

🌍 Real-world example ▾

An on-call alert fires for elevated error rates with no obvious cause yet. Scoping first shows it's isolated to one region and about 8% of requests — not a full outage. Checking recent changes shows a config change shipped twenty minutes earlier. The golden signals show errors spiking with no corresponding traffic or latency change, which points at that config rather than load. Reading the new config's diff (cheap, safe) confirms a typo before anyone needs to roll back blind.
