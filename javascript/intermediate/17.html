for await…of — loop over values that haven't arrived yet

"What is for await…of, and when do you use it over awaiting in a loop?"

Why it matters ▾
🔁 for await…of
❗ ProblemData that arrives over time — pages from an API, chunks from a stream — cannot be walked with a plain for…of, and a hand-written loop of await calls spreads the paging logic across the whole function.
✅ SolutionAn async iterable hands out promised values one at a time, and for await…of waits for each before running the body — the paging logic stays inside an async generator.
Recallfor await…of = a loop that waits for each value to arrive.
🔥 Easy interview recall

for…of → values already there

for await…of → values arrive later, one at a time

Promise.all → everything at once

Think: for await waits for each value before asking for the next — sequential, not parallel.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

for await…of does not run things in parallel. Each iteration waits for the previous one before the next value is requested — for independent work you want done together, start it all at once with Promise.all.

🔄 Likely Follow-up

"Can I use for await…of anywhere?" Only inside an async function, or at the top level of a module — it has to be able to pause and wait.

🎯 Say this in the interview — the exact lines to land

"for await…of loops over an async iterable — something like an async generator, whose values arrive over time. It waits for each value before running the loop body, so it is sequential. I use it for paginated APIs and streams, and Promise.all when I want the work to run in parallel."

  • Source → an async iterable: an object with Symbol.asyncIterator, such as an async generator's result.
  • Order → one value at a time; the next is not requested until the body finishes.
  • Producer → async function* can use both await and yield.
  • Early exit → break stops the producer, so later pages are never fetched.
  • Parallel work → use Promise.all instead — a different job.
📖 Explanation ▾

A normal iterator's next() returns { value, done } straight away (see Iterators & Generators). An async iterator's next() returns a promise of that object. for await…of calls it, awaits the promise, runs the body with the value, and repeats until done. The easiest way to build one is an async function*, which can both await and yield.

Over awaiting in a loop? If you already hold the array, for (const x of arr) { await work(x) } is fine. for await…of is for when the source itself is async — you cannot know page 2 until page 1 has arrived. Node's readable streams are async iterable, and if you hand it a plain array of promises it awaits each one in order. A rejected promise is thrown into the loop, so a try/catch around the loop catches it.

It is sequential on purpose. For independent work started together, use Promise.all (see Promises, async / await and Promise Combinators).

💻 See the code ▾
JavaScript 
async function* pages(url) {
  let next = url;
  while (next) {
    const res = await fetch(next);
    const data = await res.json();
    yield data.items;       // hands one page to the loop
    next = data.nextUrl;    // null on the last page
  }
}

async function main() {
  for await (const items of pages("/api/orders")) {
    console.log(items.length);   // pages arrive one at a time
  }
}

The paging logic lives in the generator; the loop just consumes pages as they come.

JavaScript 
// inside an async function
const urls = ["/a", "/b", "/c"];

for (const url of urls) {
  await fetch(url);                                // one at a time: total = A + B + C
}

await Promise.all(urls.map(url => fetch(url)));    // all start now: total = the slowest

Sequential versus parallel — pick based on whether the calls depend on each other.

JavaScript 
try {
  for await (const items of pages("/api/orders")) {
    if (items.length === 0) break;    // break stops the generator: no more fetches
  }
} catch (err) {
  console.error("a page failed:", err);   // a rejected fetch lands here
}

Both a break and an error end the loop cleanly.

🌍 Real-world example ▾

An export screen needed every order from an API that returns 100 per page with a "next" link. An async generator hid the paging, so the screen's code was just for await (const page of orderPages()) — and the Cancel button's break stopped any further requests.
