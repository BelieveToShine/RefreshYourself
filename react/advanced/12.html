JSX escapes by default — dangerouslySetInnerHTML is the door you opened yourself

"Does JSX automatically prevent XSS, and what makes dangerouslySetInnerHTML dangerous?"

Why it matters ▾
  • Interviewers use this to check you know JSX's escaping is real protection, not a reason to stop thinking about XSS entirely.
  • Comes up any time a feature renders user-generated content — a comment box, a rich text editor, a markdown preview.
  • A common opener before follow-ups on token storage, CSRF vs. XSS, and whether a hidden UI element is actually a security boundary.
🔥 Easy interview recall

JSX auto-escapes {value} by default — that's real XSS protection. dangerouslySetInnerHTML deliberately opts out of it.

Think: the danger is in the name — you turned the protection off yourself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Storing an auth token in localStorage is just as safe as an httpOnly cookie — just a different storage spot, same risk. It isn't: localStorage is readable by any JavaScript running on the page, including injected script from an XSS attack, while an httpOnly cookie is invisible to JavaScript entirely and survives the exact attack that would otherwise hand over a localStorage token.

🔄 Likely Follow-up

"Why is hiding a UI element not real authorization?" Hiding a button or link in the UI doesn't stop a request from reaching the underlying API directly — real authorization has to be enforced server-side, on every request; a hidden "Delete" button is a UX nicety for a well-behaved client, not an actual security boundary against a malicious one.

🎯 Say this in the interview — the exact lines to land

"JSX auto-escapes every {value} it renders, which does prevent a common class of XSS — but that protection isn't universal. dangerouslySetInnerHTML deliberately turns escaping off and injects raw HTML directly, so unsanitized user input rendered through it is a real, direct XSS vector."

  • JSX escapes {value} by default — real protection against a common XSS pattern, not a superficial habit.
  • dangerouslySetInnerHTML opts out of that escaping — sanitize any user-generated HTML before ever rendering it that way.
  • Auth token in an httpOnly cookie → invisible to JS, survives XSS Auth token in localStorage → readable by any script, including injected XSS
  • CSRF and XSS are different threats — different mitigations: CSRF tokens/SameSite cookies vs. output escaping and sanitization.
  • Authorization must be enforced server-side, on every request — hiding a UI element is a UX nicety, not a security boundary.
📖 Explanation ▾

When JSX renders a value through {value} interpolation, it converts that value to a plain text node before it ever reaches the DOM — so a comment containing literal <script> characters shows up on screen as those exact characters, never as a tag the browser parses and runs. That's a genuine defense against a common XSS pattern, not just a marketing claim — but it isn't a blanket "React prevents all XSS" guarantee, and it only covers content that actually goes through that default path.

dangerouslySetInnerHTML exists specifically to step outside that path — it injects a raw HTML string directly, exactly the way innerHTML would with no framework involved at all. If the string it's given comes from user input and hasn't been sanitized first (stripping or escaping dangerous tags and attributes), it's a direct XSS vector — React did not make that call any safer, it simply stopped checking.

The same "what can read this" question shows up in how a session is stored: an httpOnly cookie is never exposed to JavaScript, so an XSS payload running on the page can't read it, while anything in localStorage is fair game for that same injected script. XSS and CSRF get mixed up for a similar reason — XSS is malicious script running inside your page, CSRF is a forged request riding a logged-in browser's own cookies, and each needs its own defense rather than one fix covering both. Authorization follows the same logic one level up: a check that only lives in the UI never reaches the server, so it protects nothing a malicious client can't just skip.

💻 See the code ▾
JSX 
<p>{userComment}</p>   // ✅ auto-escaped — safe even if userComment is "<script>evil()</script>"

JSX renders this as a text node — the browser shows the literal characters, it never parses them as a tag.

JSX 
<div dangerouslySetInnerHTML={{ __html: userComment }} />
// ❌ real XSS vector if userComment isn't sanitized first

This injects userComment as raw HTML — if it contains a <script> tag or an event-handler attribute, the browser runs it.

🌍 Real-world example ▾

Picture a translator who reads any note handed to them aloud, as plain words — never as an instruction to actually do something. That's JSX's default escaping: the note's contents get spoken, not acted on, no matter what's written on it. dangerouslySetInnerHTML is telling that same translator "just do exactly whatever this note says, no questions asked" — and that instruction is exactly as risky as the note itself, whatever it happens to contain.
