<Image> vs. <img> — who prevents the layout shift?

"What does the <Image> component actually do that a plain <img> doesn't?"

Why it matters ▾
🖼️ <Image>
❗ ProblemA plain <img> fetches whatever file exists regardless of how large it's actually displayed, and reserves no space before it loads — wasted bandwidth plus a visible jump when it finally appears.
✅ Solution<Image> automatically resizes to the size actually needed per device/viewport, serves modern formats (WebP/AVIF) where supported, lazy-loads below the fold by default, and requires width/height (or fill) upfront specifically to reserve that space before the image loads.
RecallImage = auto-resized, modern format, lazy by default, space reserved upfront.
🖼️ <img>
❗ ProblemNothing forces a declared size or a right-sized file, so it's easy to accidentally ship an oversized image and cause a layout shift the moment it loads.
✅ Solution<img> fetches and renders exactly what you point it at — no resizing, no format negotiation, no automatic lazy-loading, and no required dimensions.
Recallimg = whatever you give it, exactly as given, no protections.
🔥 Easy interview recall

<Image> → optimized, space reserved

<img> → as-is, no protections

Think: <Image> needs width/height up front precisely so the browser can reserve space before the image loads.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Forgetting to specify width/height (or fill). Without known dimensions upfront, the browser can't reserve the right amount of space before the image loads, causing a layout shift — a real Core Web Vitals regression, exactly what the component exists to prevent.

🔄 Likely Follow-up

"Does next/image work with any image URL, including external ones?" External domains must be explicitly allow-listed in next.config.js (images.domains/remotePatterns) — a security measure so the optimization pipeline doesn't proxy arbitrary untrusted URLs by default.

🎯 Say this in the interview — the exact lines to land

"<Image> automatically resizes to the size actually needed per device, serves modern formats like WebP/AVIF where supported, and lazy-loads below the fold by default. It requires width/height — or fill — upfront specifically so the browser can reserve that space before the image loads, preventing a layout shift that a plain <img> doesn't protect against at all."

  • <Image> → auto-resized + modern format, lazy by default.
  • width/height (or fill) → required — reserves space, stops layout shift.
  • External image URLs → must be allow-listed in next.config.js.
📖 Explanation ▾

<Image> wraps a plain <img> with an optimization pipeline — it picks a right-sized version for the actual device, negotiates a modern format when the browser supports one, and skips loading anything below the fold until it's actually about to be seen.

The width/height requirement isn't bureaucracy — it's what lets the browser allocate the exact box the image will occupy before a single byte of the file arrives, so nothing else on the page has to jump out of the way once it loads. fill is the alternative for when the image should stretch to fill a sized parent element instead of declaring its own fixed dimensions.

💻 See the code ▾
JavaScript 
import Image from "next/image";

<Image
  src="/logo.png"
  width={120}       // ✅ space reserved before load
  height={40}
  alt="Logo"
/>

width/height let the browser reserve the exact box upfront — no jump when the real image arrives.

JavaScript 
// next.config.js — required for an external image source
module.exports = {
  images: {
    remotePatterns: [{ hostname: "images.example.com" }],  // ✅ allow-listed
  },
};

Without this, <Image> refuses to optimize a URL from a domain it doesn't recognize.

🧭 Use Cases — recognize these when they happen to you ▾
1 A grid of product thumbnails that needs to load fast on mobile

This is the #1 scenario you'll actually run into: dozens of small images on one page is exactly where auto-resizing and lazy-loading below the fold save the most bandwidth.

RememberMany images on one page → Image's auto-resize/lazy-load pays off most.
2 Rendering a user's avatar that's hosted on a CMS or third-party storage

Before <Image> will optimize it, that hostname has to be added to next.config.js — a step that's easy to forget the first time an external image is added.

RememberExternal image source → allow-list the hostname first.
3 A hero image loads and the text below it visibly jumps down

This is almost always a missing width/height (or fill) on an <Image> — add the real dimensions and the jump disappears because the space is reserved before the file arrives.

RememberPage jumps when an image loads → check for missing width/height first.
🌍 Real-world example ▾

A picture frame bought before the picture arrives. If you measure the wall and hang an empty frame first, the photo slides in later without anything else on the wall needing to move. Skip the frame and the photo's own size decides the gap after the fact — exactly the jump <Image>'s required dimensions are there to avoid.
