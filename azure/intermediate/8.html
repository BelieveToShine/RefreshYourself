Four load-balancing services — it's really just a 2×2

"Front Door vs. Application Gateway vs. Traffic Manager vs. Load Balancer — what's the actual decision tree between the four?"

Why it matters ▾
🖥️ Load Balancer
❗ ProblemRaw TCP/UDP traffic across a set of VMs in one region needs to be spread out fast, without paying for HTTP-level inspection it doesn't need.
✅ SolutionIt works at L4, hashing on IP/port to forward packets straight to a healthy VM — regional only, no WAF, no path routing.
RecallL4, regional — never looks inside the request.
🚪 App Gateway
❗ ProblemHTTP traffic in one region needs path-based routing, SSL termination, and a WAF — none of which Load Balancer can do since it never looks past the IP and port.
✅ SolutionIt reads the request at L7, terminating TLS and routing by URL path with a WAF available — still scoped to one region.
RecallL7, regional — one layer up from Load Balancer.
🧭 Traffic Manager
❗ ProblemCandidates often assume Traffic Manager load-balances HTTP traffic globally, just like Front Door — but it never sees or proxies the actual request.
✅ SolutionIt only answers at the DNS level, pointing the client at the best region, then steps out of the conversation for good.
RecallDNS answer only — global, but never touches the traffic.
🌐 Front Door
❗ ProblemA global app still needs one entry point that actually receives and proxies HTTP requests — with a WAF and caching — not just a DNS pointer to a region.
✅ SolutionIt runs at Microsoft's edge, receiving the request itself, checking cache, running the WAF, and forwarding only a cache miss to origin.
RecallThe one that's both global AND actually proxies.
🔥 Easy interview recall

Load Balancer → L4, regional

App Gateway → L7, regional

Traffic Manager → DNS, global

Front Door → L7 proxy, global

Think: Load Balancer and App Gateway stay inside one region. Traffic Manager and Front Door work globally — but only Front Door ever actually touches the traffic.

⚠️ Common Trap

"Traffic Manager load-balances my HTTP traffic globally, just like Front Door." It doesn't — Traffic Manager only ever returns a DNS answer telling the client which regional endpoint to talk to; it never sees or proxies the actual HTTP request, so it can't do path routing, SSL termination, or run a WAF the way Front Door can.

🔄 Likely Follow-up

"So what's the real 2x2?" Layer crossed with scope: Load Balancer is L4 + regional, Application Gateway is L7 + regional, Traffic Manager is DNS-level + global, and Front Door is L7 proxy + global.

🎯 Say this in the interview — the exact lines to land

"It's a 2x2 of layer — L4 versus L7 — crossed with scope — regional versus global. Load Balancer is L4 and regional, Application Gateway is L7 and regional, Traffic Manager is DNS-based and global, and Front Door is L7 and global. That's the whole decision."

  • Load Balancer → use for raw TCP/UDP traffic across VMs or instances in one region.
  • Application Gateway → use for HTTP routing, SSL termination, and a WAF inside one region.
  • Traffic Manager → never actually proxies traffic — it only returns a DNS answer pointing at the best region.
  • Front Door → the one that's both global AND actually proxies — L7 routing, WAF, and caching at the edge.
📖 Explanation ▾

Azure Load Balancer works at Layer 4 (transport) — it balances raw TCP/UDP traffic across a set of VMs or instances purely by IP and port. It never looks inside the packet, which is what makes it fast, and it's regional — everything it balances lives in the same region.

Application Gateway works at Layer 7 (HTTP/HTTPS) — it understands URLs, paths, and headers, so it can do path-based routing, SSL termination, and run a Web Application Firewall (WAF). It's still regional, just a layer higher than Load Balancer.

Traffic Manager works at the DNS level — a client asks "where do I go?" and it answers with the address of whichever regional endpoint fits the configured routing method (priority, performance, geographic, …). It never sees the request after that; it directs the client, it doesn't proxy anything.

Front Door is Application Gateway's counterpart at global scale — an L7 service running at Microsoft's network edge, with a WAF and caching, that actually receives and proxies the HTTP traffic itself instead of just answering a DNS lookup.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your backend is a handful of VMs in one Azure region, taking raw TCP/UDP connections

Load Balancer is the pick — it hashes on IP and port and forwards packets straight to a healthy VM, all inside one region, with no WAF or path-routing overhead. This is the #1 scenario you'll actually run into for a simple VM-backed service.

RememberOne region, no HTTP awareness needed → Load Balancer.
2 Your HTTP app is still in one region, but now needs TLS termination, a WAF, and different backend pools per URL path

Application Gateway is the pick — it's L7-aware, so it can terminate TLS, run a WAF, and route /api/* and /images/* to different pools, all while staying inside one region.

RememberNeeds a WAF or path routing, but stays in one region → Application Gateway.
3 Your app now spans multiple regions, and it needs one global entry point that also runs a WAF and caches responses at the edge

Front Door is the pick — unlike Traffic Manager, it actually receives and proxies the HTTP request itself at Microsoft's edge, so caching and a WAF are both possible; Traffic Manager could only ever hand back a DNS answer here.

RememberGlobal AND needs a WAF or caching → Front Door, not Traffic Manager.
🌍 Real-world example ▾

A global SaaS app puts Front Door in front of everything for global L7 routing, a WAF, and edge caching. Inside each region, an internal Application Gateway then handles path-based routing to the right backend service — a global edge layer, with a regional routing layer underneath it.
