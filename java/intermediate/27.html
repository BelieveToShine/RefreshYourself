sealed + Pattern-Matching switch — a closed set the compiler can verify

"How do sealed classes and pattern matching for switch work together to let the compiler guarantee every case is handled?"

Why it matters ▾
🔒 sealed
❗ ProblemA switch over a class hierarchy (Shape → Circle, Square, Triangle) can't know if it has truly covered every possible subtype, because any code anywhere could add a new subclass — so the compiler forces a default branch "just in case," even when every known case is covered.
✅ SolutionA sealed class/interface (finalized Java 17, JEP 409) lists every class permitted to extend/implement it — closing the hierarchy, so the compiler actually knows the full set of possible subtypes.
Recallsealed = the exact list of subtypes, decided once, checked forever.
🔀 pattern-matching switch
❗ ProblemBranching on a value's runtime type used to mean a long instanceof-else if chain with manual casts — nothing stopped a developer from simply forgetting a type.
✅ SolutionPattern matching for switch (finalized Java 21, JEP 441, with record patterns JEP 440) lets a switch branch directly on type and destructure a record's components — paired with a sealed hierarchy, the compiler can verify every case is handled with no default needed.
Recallpattern-matching switch + sealed = exhaustiveness the compiler actually checks.
🔥 Easy interview recall

sealed → closed set of allowed subtypes

switch pattern matching → branches on type, destructures records

together → no default needed, compiler-verified

Think: sealed (Java 17) tells the compiler the full list. switch pattern matching (Java 21) uses that list to prove nothing's missing.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Sealing a hierarchy doesn't make a switch exhaustive by itself. If a sealed interface has 3 permitted subtypes but the switch only has cases for 2 of them, the compiler still requires a default (or reports an error) — exhaustiveness comes from the switch actually covering every permitted type, not from sealing alone.

🔄 Likely Follow-up

"What happens if someone adds a 4th permitted subtype later?" Every exhaustive switch over that sealed type across the codebase fails to compile until a case is added for the new subtype — a missed case becomes a compile error, not a runtime surprise.

🎯 Say this in the interview — the exact lines to land

"sealed restricts a class or interface to an explicitly listed set of permitted subtypes, finalized in Java 17, so the compiler has full closed-world knowledge of the hierarchy. Pattern matching for switch, finalized in Java 21 with record patterns, lets a switch branch on type and destructure records directly — combined with a sealed hierarchy, the compiler can verify every case is covered with no default needed."

  • sealed → closed, explicit list of permitted subtypes (Java 17, JEP 409).
  • pattern matching for switch → branches on type, destructures records (Java 21, JEP 441/440).
  • switch expression → returns a value via -> arrows, no break-per-case (Java 14+).
  • sealed + exhaustive switch → a missing case is a compile error, not a runtime bug.
📖 Explanation ▾

A sealed type names every class allowed to extend or implement it via permits (or lets the compiler infer the list from classes in the same file). That's the piece that was missing before: without it, any hierarchy is open-ended, so the compiler can never be sure it has seen every subtype, and a switch is forced to carry a defensive default branch.

Pattern matching for switch lets a case test a value's actual type (case Circle c ->) and, for a record, pull its components straight out (case Circle(var r) ->) without a manual cast. A switch expression (Java 14+) returns a value directly from each -> arm instead of requiring a break per case. Put a sealed hierarchy and an exhaustive pattern-matching switch expression together, and the compiler can prove — not just hope — that every possible shape of input is handled.

💻 See the code ▾
Java 
sealed interface Shape
    permits Circle, Square, Triangle {}  // ✅ Java 17 — the full list

record Circle(double radius) implements Shape {}
record Square(double side) implements Shape {}
record Triangle(double base, double height) implements Shape {}

No 4th subtype can exist anywhere without being listed here.

Java 
double area = switch (shape) {               // ✅ Java 21 — pattern matching
    case Circle(double r) -> Math.PI * r * r;
    case Square(double s) -> s * s;
    case Triangle(double b, double h) -> 0.5 * b * h;
    // no default — compiler already knows these 3 are ALL of Shape
};

Record patterns destructure directly — no manual cast or getter calls.

🧭 Use Cases — recognize these when they happen to you ▾
1 Modeling a fixed result type instead of exceptions

A sealed PaymentResult with exactly three permitted records — Success, Failure, Pending — lets calling code switch over the outcome with the compiler guaranteeing every case is handled, instead of relying on exceptions or null checks.

RememberA fixed set of outcomes → model it as a sealed hierarchy.
2 Parsing an expression tree with record patterns

Evaluating an AST node (Add, Mul, Const) with record patterns pulls each component straight into a local variable in the case itself — no manual casting or getter calls needed to get at the node's fields.

RememberRecord patterns destructure in the case line itself.
3 Assuming sealed means "can't be extended at all"

sealed restricts who may extend a type, not whether anyone can — the listed permitted subtypes still genuinely extend it. Only final blocks extension entirely; a sealed type's permitted subtypes are real subclasses, not a contradiction.

Remembersealed restricts who extends it, not whether it can be extended.
🌍 Real-world example ▾

An API client's result type is modeled as sealed interface ApiResult permits Success, NotFound, ServerError. Every place in the codebase that handles an API call switches over the result — and the day someone adds a new RateLimited case, every one of those switches fails to compile until it's updated, instead of silently falling through a forgotten default in production.
