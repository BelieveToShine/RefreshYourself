MVC — three roles, and the one job the Controller must never do

"What are Model, View, and Controller, and how do they work together end-to-end?"

Why it matters ▾
  • Almost always the opening question in an ASP.NET Core interview — the doorway to everything else.
  • Explains why a typical project has separate Models, Views, and Controllers folders instead of one giant file.
  • Every later MVC question — filters, model binding, view components — assumes you already have this straight.
🔥 Easy interview recall

Model → data, plain object

View → renders HTML from data

Controller → orchestrates, picks the View

Think: Model → the "what" View → the "shown" Controller → the "who decides" — never the business logic

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Putting business logic inside the Controller action. The Controller should stay thin — validation rules and calculations belong in a service layer, not in the action method itself.

🔄 Likely Follow-up

"Where should validation actually live — the Controller, the Model, or somewhere else?" Simple format checks (required, length, range) can sit on the ViewModel as data annotations; real business-rule validation belongs in a service or domain layer, never in the Controller action.

🎯 Say this in the interview — the exact lines to land

"Model is the data, View is the Razor template that renders it, and Controller orchestrates — it receives the request, asks for data, and decides which View to show. It never contains business logic itself."

  • Model → the data, often a database entity or DTO the Controller fetches.
  • View → the Razor template that renders HTML from whatever it's handed — nothing more.
  • Controller → orchestration only — routes the request, calls services, picks the View.
  • Need both a Controller and a ViewModel because a raw domain Model shouldn't reach the View — it couples the page to your database schema.
📖 Explanation ▾

Model is just a plain object holding data — often a database entity or a DTO. It doesn't know or care that a View exists; it's just data, sometimes with a little behavior of its own.

View is the Razor template. It takes whatever data it's handed and turns it into HTML — it doesn't fetch anything and doesn't decide what to show, it only renders.

Controller is where the request actually lands. The router matches an incoming URL to a controller and action method; that action calls a service or repository for data, then returns a View result along with the data to render. The Controller's job stops at orchestration — deciding what happens and what to show, never how a business rule is calculated.

Because a View shouldn't render a Model straight from the database — that ties the page to your schema and can leak fields — most real actions build a ViewModel first: a plain object shaped for exactly what one View needs.

💻 See the code ▾
C# 
public class Product          // this is the Model
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal CostPrice { get; set; }  // should the View ever see this?
}

Model is just data — it has no idea a View even exists.

C# 
public class ProductController : Controller
{
    private readonly IProductService _products;   // a service, not logic here

    public IActionResult Details(int id)
    {
        var product = _products.GetById(id);   // ask, don't calculate
        return View(product);                  // ✅ pick the View, hand it data
    }
}

The action fetches data and picks a View — it never computes the business rule itself.

C# 
public class ProductViewModel       // shaped for one View
{
    public string Name { get; set; }
    public decimal DisplayPrice { get; set; }
    // CostPrice left out on purpose — the View never needs it
}

ViewModel reshapes the Model for one View — leaving out fields the page shouldn't see.

🌍 Real-world example ▾

Think of a restaurant. The waiter (Controller) takes your order and tells the kitchen — they never cook. The kitchen (Model) makes the actual food. The plating (View) is how it's presented when it reaches your table. Swap the plating and the food is unchanged; swap the food and the same plate now serves the wrong thing.
