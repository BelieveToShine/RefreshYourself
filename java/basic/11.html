Overloading vs. overriding — which one does the compiler decide, and which one waits for runtime?

"What's the difference between method overloading and overriding, and when is each resolved?"

Why it matters ▾
🧩 Overloading
❗ ProblemThe same logical operation (say, "add") often needs to accept different combinations of argument types — forcing a different method name for each combination is ugly and hard to discover.
✅ SolutionOverloading lets several methods share one name with different parameter lists — the compiler picks which one to call based on the declared argument types, at compile time.
RecallOverloading = same name, different parameters, compiler decides.
🔁 Overriding
❗ ProblemCode written against a general type (Shape) needs to run each concrete subtype's own specific behavior (Circle's own draw()) without the caller knowing which subtype it actually has.
✅ SolutionOverriding lets a subclass redefine a parent's method with the identical signature — the JVM looks up which version to run based on the object's actual type, at runtime.
RecallOverriding = same signature, subclass's own version, runtime decides.
🔥 Easy interview recall

Overloading → compile time, declared argument types

Overriding → runtime, the object's actual type

Think: Overloading picks a method before the program even runs. Overriding picks it while the program is running.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming an overload is chosen by the object's runtime type. Overload resolution uses the declared reference type at compile time — passing a Dog through a parameter typed as Animal still resolves overloads against Animal, even though the object at runtime is really a Dog.

🔄 Likely Follow-up

"Can a method be both overloaded and overridden at once?" Yes — a subclass can override one specific overload (matching that exact signature) while the other overloads on the same name are inherited unchanged; overloading and overriding operate independently, on different signatures.

🎯 Say this in the interview — the exact lines to land

"Overloading is same method name, different parameter list, resolved at compile time from the declared argument types. Overriding is a subclass redefining a parent's method with the identical signature, resolved at runtime from the object's actual type via virtual dispatch."

  • Overloading → compiler picks the method, based on declared parameter types.
  • Overriding → JVM picks the method, based on the real object's type.
  • Overload resolution → uses the declared reference type, never the runtime type.
📖 Explanation ▾

Overloading is a compile-time decision: the compiler looks at the declared types of the arguments at the call site and picks the single best-matching method among all the same-named candidates — this is sometimes called static or early binding, because it's fully settled before the program ever runs.

Overriding is a runtime decision: a subclass declares a method with the exact same name, parameter types, and return type (compatible covariant return allowed) as a parent's method, and the JVM uses the object's actual type — not the variable's declared type — to decide which version actually runs. This is virtual method dispatch, the mechanism behind runtime polymorphism.

💻 See the code ▾
Java 
void print(String s) { ... }
void print(int n) { ... }

print("hi");   // ✅ compiler picks print(String) — settled before runtime

Two methods, same name — the compiler matches the call to one based on the argument's declared type.

Java 
class Shape { void draw() { System.out.println("shape"); } }
class Circle extends Shape {
    @Override
    void draw() { System.out.println("circle"); }   // ✅ runs, not Shape's version
}

Shape s = new Circle();
s.draw();   // prints "circle" — the JVM checks the actual object, not the Shape type

The variable is declared Shape, but the overridden method that runs is Circle's — decided at runtime.

🧭 Use Cases — recognize these when they happen to you ▾
1 One operation, several acceptable input shapes

String.valueOf(...), constructors, builder-style APIs — overloading is why the same call-site name can accept ints, doubles, or Strings without inventing a new name for each. This is the #1 everyday reason to overload.

RememberSame action, different input types → overload.
2 Code written against a shared parent type must run each subtype's own version

Looping over a mixed list of shapes and calling shape.draw() on each one runs each element's own overridden version — the caller never needs an if/else chain checking the type.

RememberOne call site, many real behaviors → overriding.
3 You pass a subclass through a superclass-typed overload parameter

Even though the object at runtime is a Dog, overload resolution for feed(a) is fixed at compile time against a's declared type, Animal — it will never pick a feed(Dog) overload this way, no matter the real object underneath.

RememberOverloads look at the declared type, never the runtime type.
🌍 Real-world example ▾

Overloading is picking a form at the front desk based on what you brought with you; overriding is each department handling that form its own way once it arrives. The front desk decision is made the moment you hand over your papers (compile time); which department actually processes it depends on who you really are (runtime).
