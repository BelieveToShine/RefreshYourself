Action, Authorization & Exception Filters — who runs first, and who only shows up when things break

"What's the difference between action, authorization, and exception filters, and what order do they run in?"

Why it matters ▾
  • Interviewers use this to check you know MVC's pipeline isn't just "a filter runs somewhere" — each filter type owns a distinct job and a fixed place in the order.
  • A classic follow-up pits a global filter against a controller-scoped one of the same type — the default resolution order separates memorized syntax from real understanding.
  • Confusing an exception filter with UseExceptionHandler() middleware is one of the most common mix-ups going into a mid-level ASP.NET Core interview.
🔥 Easy interview recall

Authorization → runs first, can block

Action → wraps the action itself

Exception → only on a throw

Think: Authorization gatekeeps. Action wraps. Exception waits.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An exception filter does not catch every unhandled exception in the app. It only catches exceptions thrown inside MVC's own action-invocation pipeline — anything thrown by other middleware, or outside MVC's filter scope, is still the job of pipeline-level middleware like UseExceptionHandler().

🔄 Likely Follow-up

"If a global filter and a controller-specific filter of the same type both apply, which one runs first?" Scope decides the default order — global runs before controller-scoped, which runs before action-scoped, for filters of the same type — though an explicit Order property can override that default.

🎯 Say this in the interview — the exact lines to land

"Authorization filters run first and can short-circuit the request before anything else executes. Action filters wrap the action itself, running code before and after the method body. Exception filters are the odd one out — they only run if the action or an earlier filter throws, acting as MVC's own last-chance handler."

  • Authorization filter → runs first, can short-circuit the whole request.
  • Action filter → wraps the action — runs before and after the method body.
  • Exception filter → only runs when something throws — MVC's own last-chance handler.
  • Global filter → registered once in MvcOptions.Filters, applies to every action in the app.
  • Controller/action-scoped filter → an attribute on one class or method — only that scope is affected.
📖 Explanation ▾

MVC's filter pipeline runs in a fixed sequence, and each filter type owns one specific moment in it, not just a different label. Authorization filters run before anything else in the pipeline gets a chance to execute — including model binding — so they're the cheapest place to reject a caller who was never allowed to reach the action at all.

Action filters wrap the action method itself: OnActionExecuting fires right before the method body runs, and OnActionExecuted fires right after — the same before/after shape already introduced on the Basic filters page, just scoped specifically to the action invocation here.

Exception filters are the one type that doesn't run on every request — they only fire if the action method or an earlier filter in the pipeline throws. That makes them a last-chance handler inside MVC's own filter pipeline, distinct from pipeline-wide middleware like UseExceptionHandler(), which sits outside MVC entirely and catches exceptions no matter which part of the app threw them.

💻 See the code ▾
C# 
public class MustBeOwnerFilter : IAuthorizationFilter
{
    public void OnAuthorization(AuthorizationFilterContext ctx)
    {
        if (!ctx.HttpContext.User.HasClaim("owner", "true"))
            ctx.Result = new ForbidResult();  // ❌ action never runs
    }
}

Setting ctx.Result here short-circuits everything downstream — model binding, action filters, the action itself.

C# 
public class AddHeaderFilter : IActionFilter
{
    public void OnActionExecuting(ActionExecutingContext ctx) { }  // before — nothing to add yet

    public void OnActionExecuted(ActionExecutedContext ctx)
        // ✅ after — the action's result already exists here
        => ctx.HttpContext.Response.Headers["X-Served-By"] = "filter";
}

OnActionExecuted can inspect or modify the result because the action has already run — that ordering is the whole point of the type.

C# 
public class OrderFailedFilter : IExceptionFilter
{
    public void OnException(ExceptionContext ctx)
    {
        ctx.Result = new ObjectResult(new { error = "order failed" }) { StatusCode = 500 };
        ctx.ExceptionHandled = true;  // ✅ only fires if the action above threw
    }
}

This never runs on a normal request — only when the action (or an earlier filter) throws.

C# 
// Program.cs — GLOBAL: applies to every action in the app
builder.Services.AddControllers(options =>
    options.Filters.Add<AddHeaderFilter>());

// Controller — SCOPED: only this one action
[AddHeaderFilter]
public IActionResult Get() => Ok();

Same filter class, two different reach — global runs everywhere, the attribute runs only where it's attached.

🌍 Real-world example ▾

Airport security, not a metal detector. The authorization filter is the ID check at the gate — it turns you away before you're anywhere near the scanner. The action filter is the scan itself, wrapping you as you walk through it, before and after. The exception filter is the incident response team: nobody sees them unless something actually goes wrong at the scanner, and they don't patrol the rest of the airport — only that one checkpoint.
