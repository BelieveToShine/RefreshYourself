IHttpClientFactory — why new HttpClient() per call leaks sockets

"Why not new HttpClient() per request, and what does IHttpClientFactory fix?"

Why it matters ▾
🔌 Socket exhaustion
❗ ProblemCreating and disposing a new HttpClient() per request leaves closed connections lingering, and under load the machine runs out of sockets.
✅ SolutionThe factory reuses pooled handlers, so connections are reused instead of opened for every call.
RecallNew per call = sockets pile up.
🌐 Stale DNS
❗ ProblemA single long-lived client avoids that, but it keeps its connections forever and never notices a DNS change.
✅ SolutionThe factory recycles each handler after a lifetime (two minutes by default), so new connections pick up fresh DNS.
RecallStatic client = stale DNS.
🧩 Central setup
❗ ProblemBase address, headers, and cross-cutting logic copied around every HttpClient usage is easy to get inconsistent.
✅ SolutionNamed or typed clients are configured once at startup, and DelegatingHandlers add shared logic to the outgoing pipeline.
RecallConfigure once, inject anywhere.
🔥 Easy interview recall

new HttpClient() per call → socket exhaustion

static HttpClient → stale DNS

IHttpClientFactory → pools and rotates handlers

Think: The handler is the expensive part, not the HttpClient object. The factory owns the handler, you just use the client.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Thinking using var client = new HttpClient() is the safe, tidy way. Disposing the client does not release its connections right away — they linger in a closed-but-waiting state, so a busy service still runs out of sockets.

🔄 Likely Follow-up

"So why not just keep one static HttpClient?" It avoids the socket pile-up, but the connections live forever and miss DNS changes. The factory rotates handlers for you; a static client can get the same effect with SocketsHttpHandler.PooledConnectionLifetime set.

🎯 Say this in the interview — the exact lines to land

"Creating a new HttpClient for every request exhausts sockets under load, and a single static one never notices DNS changes. IHttpClientFactory pools the underlying handlers, reuses them, and recycles them on a timer, so you get both. I register named or typed clients once at startup and add a DelegatingHandler for cross-cutting logic. Retries and circuit breakers plug in as handlers too."

  • new per call → socket exhaustion — disposing the client does not free connections immediately.
  • Factory → pooled handlers, recycled on a timer — two minutes by default, changeable.
  • Named vs. typed → configured once at startup — a typed client is a class that takes an HttpClient in its constructor.
  • DelegatingHandler → middleware for outgoing calls — logging, auth headers, and retries live here.
📖 Explanation ▾

The problem is the handler underneath HttpClient, which owns the connections. A fresh client per call opens fresh connections, and closed ones linger for a while, so a busy service runs out of sockets. A single static client avoids that, but its connections never recycle, so it can keep talking to an old IP address after DNS changes.

IHttpClientFactory creates lightweight HttpClient objects but manages the expensive handlers itself: it pools them and retires each after a lifetime (two minutes by default, changeable with SetHandlerLifetime). A named client is fetched by a string with CreateClient("name"); a typed client is your own class that receives an HttpClient by constructor injection. A typed client is registered as transient, so avoid injecting it into a singleton: the factory loses control of it and it can miss DNS changes.

AddHttpMessageHandler<T>() adds a DelegatingHandler to the client's outgoing pipeline, a bit like middleware for outbound calls. Resilience (retry, circuit breaker, timeout) attaches the same way but is taught on Retry vs. Resilience. Background: The Built-in DI Container and Service Lifetimes.

💻 See the code ▾
C# 
// ❌ per call: connections pile up under load
using var client = new HttpClient();
var json = await client.GetStringAsync("https://api.example.com/items");

Looks harmless, and works fine in a quick test — the damage only shows under sustained load.

C# 
// named: configure once, ask the factory by name
builder.Services.AddHttpClient("github", c => c.BaseAddress = new Uri("https://api.github.com/"));

// later, with an injected IHttpClientFactory:
var client = factory.CreateClient("github");

The name is just a string, so a typo is a runtime problem — typed clients avoid that.

C# 
builder.Services.AddTransient<LoggingHandler>();
builder.Services.AddHttpClient<GitHubClient>(c =>
    c.BaseAddress = new Uri("https://api.github.com/"))
    .AddHttpMessageHandler<LoggingHandler>();                // outgoing pipeline step

public class GitHubClient
{
    private readonly HttpClient _http;                       // handler managed by the factory
    public GitHubClient(HttpClient http) => _http = http;

    public Task<string> GetRepoAsync(string name) => _http.GetStringAsync($"repos/{name}");
}

public class LoggingHandler : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        Console.WriteLine($"-> {request.Method} {request.RequestUri}");   // before sending
        return await base.SendAsync(request, ct);
    }
}

GitHubClient is a typed client: inject it anywhere, and it never sees how connections are pooled.

🌍 Real-world example ▾

A call centre switchboard. A new HttpClient per call is dialling a fresh phone line for every sentence and leaving it off the hook afterwards; the factory is a switchboard with a pool of lines that are reused and swapped out every few minutes, so the building never runs out of lines.
