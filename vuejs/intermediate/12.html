Custom directives — when a component is the wrong tool

"When would you write a custom directive instead of a component?"

Why it matters ▾
🎛️ Custom Directives
❗ ProblemSome behavior — auto-focusing an input, wiring up a non-Vue tooltip library — is pure imperative DOM manipulation with no template, slots, or props of its own, so wrapping it in a full component feels like overkill.
✅ SolutionA custom directive (app.directive('name', {mounted(el){…}})) hooks straight into an element's lifecycle and runs low-level DOM logic directly on el, outside the usual reactive-template model.
RecallDirective = lifecycle hooks for one raw DOM element, no view of its own.
🔥 Easy interview recall

Custom directive = "raw DOM access tied to an element's lifecycle."

Think: v-focus → mounted(el) → el.focus(), no component needed.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for a custom directive when a component would be the better fit. Directives are for low-level, reusable DOM behavior with no view of their own — once you need markup, slots, or props beyond raw access to one element, it should be a component instead.

🔄 Likely Follow-up

"What hooks does a directive expose?" created, beforeMount, mounted, beforeUpdate, updated, beforeUnmount, unmounted — mirroring the component lifecycle, but scoped to just one raw element.

🎯 Say this in the interview — the exact lines to land

"A custom directive hooks into an element's lifecycle — mounted, updated, unmounted — and runs imperative DOM logic directly on that element, outside the normal reactive-template model."

  • app.directive('focus', {…}) → registers it globally, used as v-focus.
  • Hooks → mirror the component lifecycle, scoped to one element.
  • No template of its own → needs markup/slots? write a component instead.
  • Classic use → auto-focus, tooltips, wiring up non-Vue libraries.
📖 Explanation ▾

A directive is registered with a plain object of lifecycle hooks — mounted(el, binding), updated(el, binding), and so on — and Vue calls the matching hook at the matching moment in that element's lifecycle, handing it the real DOM element (el) directly. binding carries whatever value was passed (v-focus="someValue"), if the directive needs one.

This is deliberately a smaller, lower-level tool than a component. A component gets its own template, props, slots, and emitted events — a directive gets none of that; it only ever gets direct access to one already-existing element and a handful of lifecycle moments to act on it.

💻 See the code ▾
Vue 
// main.js
app.directive('focus', {
  mounted(el) {
    el.focus()             // ✅ runs once, right after mount
  }
})

Registered once globally — used on any element with v-focus.

Vue 
<!-- any template -->
<input v-focus placeholder="Search…" />   <!-- ✅ auto-focused on mount -->

No component, no props — just the element and one line of DOM code.

🧭 Use Cases — recognize these when they happen to you ▾
1 Wiring up a non-Vue tooltip library on a plain element

A jQuery-era or vanilla-JS tooltip library expects a real DOM node to attach to — binding.value carries the tooltip text, and mounted is exactly the moment that node is guaranteed to exist in the document.

RememberBridging to a non-Vue DOM library → a directive, not a component.
2 A "directive" that actually needs its own markup and slots

A directive has no template, props, or slots — if the behavior needs its own markup or needs to render child content, trying to force it into a directive means fighting the tool instead of writing a small component that does the job directly.

RememberNeed slots/markup of your own → that's a component's job, not a directive's.
🌍 Real-world example ▾

A search page where the search box should be focused the instant the page loads. A tiny v-focus directive does exactly that in one line, reused on every form that needs the same behavior — writing a whole wrapper component just to call .focus() once would be solving a one-line problem with a much bigger tool.
