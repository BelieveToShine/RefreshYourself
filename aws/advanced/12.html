Every pushback extends the same design — don't restart from scratch

Design a highly available web application — then: what if AZ-1 fails? What if traffic increases 10x? What if the database becomes the bottleneck?

Why it matters ▾

❗ ProblemA candidate nails the base design, then treats each pushback — AZ-1 failing, 10x traffic, a database bottleneck — as a brand-new problem and starts sketching a different architecture from scratch, which reads as if the first design never actually solved anything.
✅ SolutionTreat every pushback as an extension of the same design already on the board: AZ-1 failing is already covered if the design spans AZs, 10x traffic is answered by scaling the compute tier and caching reads, and a database bottleneck is answered with read replicas, caching, or repartitioning — the one diagram just keeps growing branches.

⚠️ Common Trap

Answering the first design question well, then floundering on the pushback chain. A strong architect answer treats each pushback as an extension of the same design — showing how the architecture actually adapts — not restarting from scratch on a fresh whiteboard each time.

🔄 Likely Follow-up

"What happens if DynamoDB throttles in a serverless-API design?" Check for a hot partition first, then consider on-demand capacity mode or redesigning the partition key — throttling is almost always a partition-key or capacity-mode problem, not "DynamoDB is slow."

🎯 Say this in the interview — the exact lines to land

"Each pushback extends the same design — I show how the architecture adapts, I don't restart from scratch on a new whiteboard."

  • AZ-1 fails → ALB + ASG already span multiple AZs, so traffic just shifts to the healthy ones.
  • 10x traffic → scale the compute tier out, and let caching/CDN absorb the read-heavy load.
  • Database bottleneck → read replicas or caching for reads, repartitioning or a data-model rethink if it's specifically a write bottleneck.
  • Reduce cost → rightsize + Reserved/Savings Plans for the steady baseline, Spot for anything fault-tolerant.
  • Go multi-region → the same active/active vs. active/passive decision, just applied to this design.
  • DynamoDB throttling → check for a hot partition first, not "DynamoDB is slow."
📖 Explanation ▾

A classic AWS architecture-design question starts with something like "design a highly available web application." The expected first answer is almost always the same base shape: Route 53 for DNS, CloudFront + WAF in front for caching and edge protection, an Application Load Balancer distributing traffic, an EC2/ECS compute tier running in an Auto Scaling Group across multiple AZs, and RDS/Aurora as the database, also spanning multiple AZs.

The interview rarely stops there — it turns into a pushback chain: "what if AZ-1 fails?", "what if traffic goes 10x?", "what if the database becomes the bottleneck?" Each one gets answered by extending the exact design already on the whiteboard, not drawing a new one. AZ-1 failing is already covered if the design genuinely spans multiple AZs — the ALB and Auto Scaling Group keep serving from the healthy ones. 10x traffic means scaling the compute tier out and letting CloudFront/caching absorb read-heavy load. A database bottleneck usually means read replicas or a cache (ElastiCache) for read pressure — or, if it's specifically a write bottleneck, rethinking the data model or partitioning instead, since replicas don't help writes.

Two more pushbacks extend the exact same design just as directly. "How would you reduce cost here?" answers with rightsizing the fleet, Reserved Instances or Savings Plans for the steady baseline load, and Spot for anything fault-tolerant that can handle interruption. "How would you make this multi-region?" reuses the same active/active vs. active/passive decision that comes up on any multi-region question, just applied to this specific design.

The same pushback-chain technique applies to the other classic whiteboard prompts too — a serverless API, an event-driven system, a global application — each gets its own chain of follow-ups (throttling, cost, multi-region) answered the same way: extend the design, don't restart it.

🧭 Use Cases — recognize these when they happen to you ▾
1 The interviewer's first pushback lands right after your base design: "what if AZ-1 fails?"

This is the #1 pushback you'll actually get, and it's already answered if the base design genuinely spans multiple AZs — the ALB and Auto Scaling Group just keep serving from the healthy ones, nothing new needs to be drawn.

RememberAZ-1 fails → already covered if the design spans AZs.
2 The interviewer keeps going: "what if traffic goes 10x?", then "what if the database becomes the bottleneck?"

Each pushback extends the exact same design instead of replacing it — scale the compute tier out and let caching/CDN absorb read-heavy traffic; add read replicas or a cache for a read-side database bottleneck, or rethink the data model or partitioning if it's specifically a write bottleneck, since replicas don't help writes.

RememberTraffic and DB pushbacks scale the design, they don't restart it.
3 The same pushback technique shows up on a completely different base design — a serverless API starts throttling

The pushback-chain technique carries over regardless of what's on the whiteboard — but DynamoDB throttling specifically is almost always a hot-partition or capacity-mode problem. A common trap — candidates often assume the service itself is just "slow" instead of checking the partition key first.

RememberThrottling → check the partition key first, not "DynamoDB is slow."
🌍 Real-world example ▾

A candidate's design survives the "AZ-1 fails" pushback cleanly because the base design already spanned 3 AZs from the first sketch — the pushback chain rewards a design that was built defensively from the start, not a scramble of fixes bolted on after the interviewer points out the gap.
