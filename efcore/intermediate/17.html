⭐ EF Core · Intermediate · Should Know

InMemory, SQLite, or a real database — what must your test prove?

"How do you unit-test code that uses EF Core?"

Why it matters ▾
🧪 Testing EF Core Code
❗ ProblemA test that passes against a fake database can still fail in production — constraints, transactions and SQL translation behave differently outside the real engine.
✅ SolutionPick the test database by what you need to prove: InMemory for plain logic, SQLite in-memory for closer relational behaviour, a real database in a container for the most faithful check.
RecallMore faithful = slower: InMemory → SQLite → real DB. Choose by what the test must prove.
🔥 Easy interview recall

Testing EF Core = "a ladder from fast-and-fake to slow-and-real."

Think: InMemory → fastest, but not relational SQLite in-memory → real SQL engine, different dialect Real DB (container) → closest to production

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The InMemory provider is a safe stand-in for the database." It is not a relational database, so things a real engine would enforce or translate — constraints, transactions, real SQL — can behave differently. A test can pass here and fail in production.

🔄 Likely Follow-up

"So should I just mock DbContext or DbSet?" That is brittle: a mocked DbSet runs your LINQ in memory, so it never proves the query translates to SQL. Test the queries against a real provider, and keep the pure business logic apart so it can be tested without a database at all.

🎯 Say this in the interview — the exact lines to land

"I choose the test database by what the test must prove. For plain business logic I keep it away from the database. To check queries and relational behaviour I use SQLite in-memory, or best of all the real database engine in a container. I avoid relying on the InMemory provider because it is not relational."

  • InMemory → fast but not relational — constraints and transactions differ.
  • SQLite in-memory → a real SQL engine, but a different dialect from production.
  • Real DB in a container → most faithful, slowest, same provider as production.
  • Mocking DbSet → never proves the SQL translation.
📖 Explanation ▾

The question is never "which one is best" but what must this test prove. If it only checks plain logic, keep that logic free of DbContext and you need no database. If it checks a query, a constraint or a transaction, the database has to behave like a real one.

The InMemory provider is a simple in-process store, not a relational database — it has no real SQL, ignores transactions, and does not support raw SQL. Microsoft's EF Core docs call using it as a test fake "highly discouraged". SQLite in-memory is a genuine SQL engine, so queries are really translated and run; it is closer, but still a different dialect from SQL Server or PostgreSQL. A real database in a container (for example with Testcontainers) uses the same provider you ship, so it is the most faithful — at the cost of speed and setup.

💻 See the code ▾
C# 
var options = new DbContextOptionsBuilder<AppDb>()
    .UseInMemoryDatabase("test-1")        // fast, but NOT relational
    .Options;

InMemory: quick to set up, but it only mimics a database.

C# 
using var conn = new SqliteConnection("DataSource=:memory:");
conn.Open();                                // ✅ keep it open — closing the connection drops the data

var options = new DbContextOptionsBuilder<AppDb>().UseSqlite(conn).Options;
using var db = new AppDb(options);
db.Database.EnsureCreated();                // builds the schema from the model

SQLite in-memory: a real SQL engine; the database lives only while the connection stays open.

🌍 Real-world example ▾

A test that inserts two users with the same email passes against InMemory. In production the unique index on Email rejects the second one. Run that test on SQLite or the real engine, and the duplicate fails the way it actually will.
