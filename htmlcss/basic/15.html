Script loading — plain, async or defer: who makes the page wait?

"What is the difference between <script>, async and defer?"

Why it matters ▾
⛔ plain <script>
❗ ProblemA script in the middle of the page can freeze page-building until its file is downloaded and run — a slow file holds up everything below it.
✅ SolutionThat is the default on purpose: the script might change the HTML right after it, so the browser stops and waits.
RecallPlain = stop, fetch, run, then carry on.
⚡ async
❗ ProblemA script that depends on nothing (an analytics tag) shouldn't make the page wait for its download.
✅ Solutionasync downloads in parallel and runs the moment it arrives — in any order, pausing the parser only while it runs.
Recallasync = run when ready, no order promised.
⏳ defer
❗ ProblemYour app script needs the whole HTML to exist first, and several scripts must run in the order you wrote them.
✅ Solutiondefer downloads in parallel but waits until parsing is done, then runs the scripts in document order.
Recalldefer = after the page is parsed, in order.
🔥 Easy interview recall

<script> → stops the parser

async → runs as soon as it arrives

defer → runs after parsing, in order

Think: your own app code → defer independent third-party tags → async

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

async is not "a faster defer". async scripts run in whatever order they finish, so two scripts that depend on each other can break — defer keeps document order. Both only work on external scripts (with src).

🔄 Likely Follow-up

"Why not just put the script at the end of <body>?" That also avoids blocking, but the download only starts when the parser reaches the tag. A defer script in the <head> starts downloading straight away and still runs after parsing.

🎯 Say this in the interview — the exact lines to land

"A plain <script> stops the HTML parser while it downloads and runs. async downloads in parallel and runs as soon as it arrives, in no guaranteed order. defer downloads in parallel and runs after parsing finishes, in document order. Module scripts are deferred by default."

  • Plain <script> → blocks the parser while it downloads and runs.
  • async → runs as soon as downloaded, order not guaranteed.
  • defer → runs after parsing, in order, before DOMContentLoaded.
  • type="module" → deferred by default; add async to run it as soon as ready.
  • async and defer need an external file (src) — inline classic scripts ignore them.
📖 Explanation ▾

The browser reads your HTML top to bottom and builds the DOM as it goes (see Browser Rendering). A script is allowed to change that DOM, so by default the parser stops at a plain <script>, waits for the file, runs it, and only then carries on — a slow script delays everything below it.

async and defer both let the download happen in parallel with parsing. They differ in when the script runs. async runs the instant its file arrives, so it can interrupt parsing and the order is not guaranteed. defer waits until parsing is finished, runs in the order written, and finishes before DOMContentLoaded. An async script may run before or after that event.

Rule of thumb: defer for your own code, async for scripts that need nothing else. More page-speed levers are in CSS Performance, and <head> basics are in Document Structure & Metadata.

💻 See the code ▾
HTML 
<script src="a.js"></script>               <!-- ❌ blocks the parser -->
<script async src="ads.js"></script>     <!-- runs when ready, any order -->
<script defer src="app.js"></script>     <!-- runs after parsing, in order -->

Three tags, three behaviours — only the first one stops the parser.

HTML 
<script type="module" src="main.js"></script>
<!-- deferred by default — no defer needed -->

Module scripts behave like defer automatically.

🌍 Real-world example ▾

Think of a kitchen: a plain script means the whole kitchen stops until one delivery is unpacked; async means unpack it the moment it arrives, even mid-prep; defer means unpack all deliveries once prep is done, in the order on the list.
