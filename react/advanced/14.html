🔥 React · Advanced · Must Know

A component that won't stop rendering — find the loop, not just the symptom

"A component keeps rendering indefinitely — how do you diagnose it?"

Why it matters ▾
  • A "the page just freezes" or "the CPU fan spins up" bug report almost always traces back to one specific line in a useEffect dependency array, not a mystery.
  • Interviewers use this to check whether you actually understand referential equality in JavaScript, not just whether you know useEffect takes a dependency array.
  • The same root cause shows up in several disguises — an infinite render loop, an API endpoint getting hammered, and a Context that re-renders the whole app are often the exact same bug wearing different clothes.
🔥 Easy interview recall

A referentially-unstable effect dependency is the #1 cause of a runaway render loop or repeated API calls.

Think: a new object/array/function created every render looks the same but IS a different reference — that's the fuel keeping the loop spinning.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An infinite render loop is always caused by a bug directly visible in the JSX itself. The classic cause actually lives in a useEffect's dependency array — an object, array, or function created fresh every render (even though its contents "look the same") is referentially different each time, so the effect keeps re-running, triggering a state update, causing a re-render, recreating that same "new" dependency again; the bug is in the effect's dependencies, not the JSX markup.

🔄 Likely Follow-up

"An API request fires repeatedly — what would you check first?" The same underlying class of issue as a render loop: a useEffect dependency that's referentially unstable across renders (a fresh object, array, or function each time), or a missing/incorrect dependency array where a single fetch-per-mount was actually intended.

🎯 Say this in the interview — the exact lines to land

"A runaway render loop almost always comes from a useEffect dependency that's referentially unstable — an object, array, or function created fresh every render looks identical but isn't the same reference, so the effect keeps firing, updates state, and triggers another render that recreates the same 'new' dependency again."

  • Referentially-unstable dependency → the #1 cause of a render loop or repeated API calls.
  • Missing/incorrect dependency array → a fetch meant to run once fires on every render instead.
  • Out-of-order responses (a race condition) → guard for "is this still the latest request," or cancel with AbortController.
  • A fresh Context value object every Provider render → memoize it, or every consumer re-renders even when nothing meaningful changed.
📖 Explanation ▾

The reason a referentially-unstable dependency keeps the cycle alive is how React compares a dependency array between renders: it checks reference equality, not "does this look the same." An object or array literal written directly in the component body, or a function defined fresh on every render, is a brand-new value in memory every single time — even if every property inside it is identical to last render's value. React sees "different," re-runs the effect, and if that effect updates state, the component renders again and creates yet another "new" object — the exact same trap, one render later.

A repeated API call firing on every render, instead of once or once per genuine change, is the same class of bug wearing a different symptom: either that same unstable dependency, or a dependency array that's missing a value entirely when a fetch-once-per-mount was actually intended. Out-of-order responses — a real race condition, where a slower earlier request resolves after a faster later one — need a guard that checks whether a response still belongs to the latest request before applying it, or cancellation through AbortController; the Data Fetching page covers this mechanism in depth, it just shows up again here as a real production symptom.

A Context value has the same reference rule underneath it. A value object built fresh on every render of the Provider — even one holding the exact same data — re-renders every single consumer on every Provider render, because Context also compares by reference. Memoizing that value object is what breaks the connection between "the Provider re-rendered" and "every consumer must too."

💻 See the code ▾
JSX 
useEffect(() => {
  fetchData({ id }); // object literal built fresh, every render
}, [{ id }]); // ❌ a NEW object every time — never actually stable

This dependency is never equal to last render's — the effect re-runs on every single render, no matter what id actually is.

JSX 
useEffect(() => {
  fetchData(id); // the primitive value itself
}, [id]); // ✅ stable across renders — only changes when id actually changes

A primitive (string/number) compares by value, not reference — this is what actually breaks the cycle.

🌍 Real-world example ▾

A dashboard component appears to render endlessly, and the browser tab's CPU usage climbs steadily. Check the component's useEffect dependency arrays specifically for an object, array, or function created fresh on every render — that's almost always the actual fuel keeping the loop spinning, not a bug sitting in the JSX itself.
