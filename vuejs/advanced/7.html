Performance tuning — defer what you don't need yet

"What are the main levers for improving a slow Vue app's performance?"

Why it matters ▾
🛣️ Route-level splitting
❗ ProblemBundling every route's JS into one file means visiting one page downloads code for every other page too, upfront.
✅ SolutionDynamic import() on route components means each route's JS only downloads when that route is actually visited.
RecallRoute code → fetched on visit, not before.
🧩 Component-level lazy load
❗ ProblemA heavy component behind a modal or tab still costs bytes on first load, even if the user never opens it.
✅ SolutiondefineAsyncComponent() defers one heavy component's own code until it's actually rendered.
RecallHeavy component → loaded only when it renders.
⚡ Reducing redundant work
❗ ProblemAlready-loaded content can still waste time re-rendering or recomputing things that didn't actually need to change.
✅ Solutionv-memo and computed caching cut unnecessary render and recalculation work for content already on the page.
RecallAlready loaded → cut rework, not download size.
🔥 Easy interview recall

Route-level → import() per route, fetched on visit

Component-level → defineAsyncComponent(), fetched on render

Already loaded → v-memo / computed caching, less rework

Think: defer the download first, then trim the rework.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Lazy-loading the very first route a user lands on backfires. It adds a network round trip to the critical path for zero benefit, since that code was needed immediately anyway.

🔄 Likely Follow-up

"How would you actually measure whether an optimization helped?" Vue Devtools' performance tab for component render timings, plus the browser's Lighthouse/Performance panel for load-time metrics — profile before optimizing, don't guess.

🎯 Say this in the interview — the exact lines to land

"Route-level code splitting — dynamic import() on route components — means each route's JS only downloads when that route is actually visited, shrinking the initial bundle. Component-level lazy loading with defineAsyncComponent() does the same for heavy components behind a modal or tab. v-memo and computed caching reduce unnecessary render and recalculation work for content that's already loaded. I'd profile first, with Vue Devtools or Lighthouse, before deciding what to optimize."

  • Route-level splitting → dynamic import() per route, downloaded only on visit.
  • Component-level lazy loading → defineAsyncComponent() for heavy, rarely-shown components.
  • Already-loaded content → v-memo / computed caching cuts unnecessary rework.
  • Before optimizing → profile with Devtools or Lighthouse, don't guess.
📖 Explanation ▾

Route-level splitting is usually just one line per route in Vue Router: instead of importing a page component directly, you give it a function that imports it — () => import('./ReportsPage.vue'). The bundler turns that into its own chunk, fetched only when the router actually navigates there.

defineAsyncComponent() does the same thing at component scope: pass it a loader function, and it returns a component that resolves lazily the first time it's actually rendered. It also accepts options for a loading component, an error component, and delay/timeout handling, so a slow fetch doesn't leave the user staring at nothing.

Neither of these helps with work that's already on the page — that's what v-memo and computed's own caching are for, trimming unnecessary re-renders and recalculations on content that's already loaded and mounted.

💻 See the code ▾
JavaScript 
const routes = [
  { path: '/reports', component: () => import('./ReportsPage.vue') }  // ✅ own chunk, loaded on visit
]

A user who never visits /reports never downloads its code — the import only fires when the router navigates there.

JavaScript 
const HeavyChart = defineAsyncComponent(() =>
  import('./HeavyChart.vue')
)  // ✅ fetched only when <HeavyChart /> actually renders

A chart library hidden behind a rarely-opened tab never costs anything for users who never open that tab.

🧭 Use Cases — recognize these when they happen to you ▾
1 An admin-only settings page that most users never visit

This is the textbook case — a route most visitors never hit should never be part of their initial download.

RememberRarely-visited route → always worth splitting out.
2 You lazy-load the landing route itself

The code for the very first screen is needed right away — splitting it out just adds a fetch delay before the user sees anything at all.

RememberThe landing route should ship in the initial bundle, not be split out.
3 A heavy charting library sits behind a tab most users never open

Component-level lazy loading is the right tool here — the whole route still loads fast, and the heavy library only arrives if that tab is opened.

RememberOne heavy component, rarely shown → defineAsyncComponent, not route splitting.
🌍 Real-world example ▾

It's like a streaming service that only downloads the next episode when you press play, instead of downloading an entire season before you've watched a single minute. The total data is the same either way — only the timing of when it's paid for changes.
