Accept vs. Content-Type — which one failed: 406 or 415?

How does an API decide between JSON and XML, and what happens on an unsupported Accept?

Why it matters ▾
🤝 Content negotiation
❗ ProblemClients and servers can speak different formats (JSON, XML, CSV), and without an agreed step the server either guesses one or fails in a confusing way.
✅ SolutionThe client names what it wants back (Accept) and what it is sending (Content-Type); the server picks a matching formatter or answers 406 / 415.
RecallAccept = what I want. Content-Type = what I'm sending.
🔥 Easy interview recall

Accept → what I want back (output formatter)

Content-Type → what I'm sending (input formatter)

Think: Content-Type unsupported → 415 Accept unsupported → 406, but only if you turn it on

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"An unsupported Accept returns 406 by default." In ASP.NET Core it quietly falls back to the first formatter that can write the object (JSON by default) and returns 200 — you only get 406 after setting ReturnHttpNotAcceptable = true.

🔄 Likely Follow-up

"How would you add CSV output to an existing endpoint?" Write a custom output formatter (derive from TextOutputFormatter), give it the text/csv media type, and register it in MvcOptions.OutputFormatters — clients then ask for it with Accept: text/csv.

🎯 Say this in the interview — the exact lines to land

"Content negotiation is the client saying which format it wants back with Accept, and which format it's sending with Content-Type. The server picks an output or input formatter to match. JSON is the default in ASP.NET Core; an unsupported Content-Type gets 415, and an unsupported Accept only gets 406 if I enable ReturnHttpNotAcceptable — otherwise it falls back to JSON."

  • Accept → the format the client wants back, picked by an output formatter.
  • Content-Type → the format of the request body, read by an input formatter.
  • 415 vs. 406 → can't read what you sent vs. can't write what you asked for.
  • ReturnHttpNotAcceptable → turns the silent JSON fallback into a real 406.
  • Custom formatter → add a new format (CSV, XML) without touching actions.
📖 Explanation ▾

Two headers, two jobs. Accept goes with a request and says which formats the client can take back, optionally ranked with q values (application/json, application/xml;q=0.8). Content-Type describes the body the client is sending. ASP.NET Core uses input formatters to read a request body and output formatters to write the response; each handles specific media types.

Out of the box, JSON is the main format. Other formats — XML, for example — have to be added (AddXmlSerializerFormatters). When the client's Accept matches nothing, ASP.NET Core still answers with the first formatter that can write the object (JSON by default) unless ReturnHttpNotAcceptable is on. A browser-style Accept: */* is ignored unless RespectBrowserAcceptHeader is set. When the body's Content-Type matches no input formatter, the answer is 415. [Produces] and [Consumes] narrow what one action offers or accepts.

💻 See the code ▾
C# 
builder.Services.AddControllers(o =>
{
    o.ReturnHttpNotAcceptable = true;                // ✅ unsupported Accept → 406, not JSON
    o.OutputFormatters.Add(new CsvOutputFormatter());   // ✅ adds text/csv output
}).AddXmlSerializerFormatters();                       // ✅ adds XML in and out

One place decides which formats the whole API speaks — and whether a miss is a 406.

C# 
[HttpPost]
[Consumes("application/json")]    // ✅ other Content-Type → 415
[Produces("application/json")]    // ✅ this action only offers JSON
public IActionResult Create(OrderDto dto) => Ok(dto);

[Consumes] and [Produces] narrow one action — handy when it must be JSON only.

C# 
public class CsvOutputFormatter : TextOutputFormatter
{
    public CsvOutputFormatter()
    {
        SupportedMediaTypes.Add("text/csv");       // ✅ matches Accept: text/csv
        SupportedEncodings.Add(Encoding.UTF8);
    }
    protected override bool CanWriteType(Type? type) => type == typeof(List<OrderDto>);
    public override Task WriteResponseBodyAsync(OutputFormatterWriteContext ctx, Encoding enc)
        => ctx.HttpContext.Response.WriteAsync(ToCsv((List<OrderDto>)ctx.Object!), enc);   // ToCsv = your helper
}

A custom formatter only says which type and media type it handles, and how to write the body.

🧭 Use Cases — recognize these when they happen to you ▾
1 A partner system needs the same data as XML while the web app uses JSON

Once an XML formatter is added, the partner asks with Accept: application/xml and gets XML, while the web app's Accept: application/json still gets JSON — no second endpoint needed.

RememberDifferent Accept → different body, same action.
2 A client posts an XML body to an endpoint that only has JSON formatters

No input formatter matches the body's Content-Type, so the request is rejected with 415 Unsupported Media Type before the action runs.

RememberUnreadable body → 415.
3 A client asks for Accept: image/png and still gets 200 JSON

That is the default behaviour, not a bug — the server falls back to a formatter it has. If you want a hard 406, switch on ReturnHttpNotAcceptable. A classic interview trap.

RememberA hard 406 is opt-in.
🌍 Real-world example ▾

A reporting partner wants the orders list as CSV while the web app wants JSON — same endpoint, same data. The partner sends Accept: text/csv, the app sends Accept: application/json, and a CSV output formatter registered once serves the first; a client that posts XML to a JSON-only endpoint gets a clear 415.
