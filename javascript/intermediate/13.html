yield — the function that pauses instead of finishing

"What is the difference between an iterator and a generator, and why would you reach for a generator instead of just returning an array?"

Why it matters ▾
  • for...of, spread (...), and destructuring all quietly run on the iterator protocol — knowing it explains why some things are "spreadable" and others aren't.
  • Generators are the real building block behind infinite sequences, custom data-structure traversal, and (historically) async flow-control libraries before async/await existed.
  • A common interview opener: "write a generator that produces an infinite sequence" — it's really testing whether you understand lazy evaluation, not generator syntax.
🔥 Easy interview recall

Generator = "a function that can pause, and resume exactly where it left off."

Think: a normal function runs start-to-finish in one go. A function* can stop at yield, hand a value out, and wait to be asked for the next one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A generator is not just "a fancy way to build an array." An array holds every value up front in memory; a generator computes exactly one value on demand and can represent a sequence that has no end at all — try [...counter()] on an infinite generator and it never finishes, because spread pulls values until the generator says it's done, and this one never will.

🔄 Likely Follow-up

"How does for...of actually know how to loop over a generator?" A generator object implements Symbol.iterator itself (returning itself), and its next() method returns { value, done } — for...of just keeps calling next() until done is true. That's the same iterator protocol every iterable follows.

🎯 Say this in the interview — the exact lines to land

"An iterable is anything with a Symbol.iterator method that returns an iterator — an object with a next() that yields { value, done }. A generator function (function*) is the easy way to build one: each yield pauses the function and hands out one value, and calling next() resumes it right where it left off. That pause-and-resume behavior is lazy evaluation — nothing runs until you actually ask for the next value."

  • Symbol.iterator the method every iterable must have to work with for...of/spread.
  • next() returns { value, done } — the shared shape every iterator protocol call returns.
  • function* / yield pauses execution and hands out one value instead of running to completion.
  • lazy evaluation nothing computes until next() asks for it — that's what makes an infinite sequence possible.
  • generator vs. array one value at a time, on demand, vs. everything held in memory up front.
📖 Explanation ▾

An iterable is any object that knows how to be looped over — arrays, strings, Maps, Sets, and generators all qualify because each one has a Symbol.iterator method. Calling that method produces an iterator: an object with a next() method that returns { value, done } every time it's called, and keeps going until done is true. This is the exact machinery for...of, spread (...arr), and destructuring all run on under the hood.

Writing that iterator object by hand — tracking your own state, returning the right shape every call — is tedious. A function* (generator function) writes it for you: every yield pauses the function, hands the value out, and freezes its local state exactly where it stopped. Calling .next() again resumes from that exact line, not from the top. The generator object itself is both an iterator and an iterable, which is why it drops straight into a for...of loop.

The part worth remembering is lazy evaluation: nothing inside a generator runs until next() actually asks for a value. An array must be fully built before it's returned — every element computed and held in memory up front, with a known, finite length. A generator produces values one at a time, only when asked, so it can represent a sequence that's infinite, or too large to ever hold in memory at once — an endless counter, an infinite stream of IDs, a lazily-read line-by-line file — something no array literal could ever finish building.

💻 See the code ▾
JavaScript 
function* counter() {
  let n = 0;
  while (true) {
    yield n++;              // pauses here, hands out n, then waits
  }
}

const it = counter();
it.next(); // { value: 0, done: false }
it.next(); // { value: 1, done: false }
it.next(); // { value: 2, done: false } — could run forever

An array can't do this — [0, 1, 2, ...] would have to finish computing every element before it's even assigned, and an infinite one never finishes.

JavaScript 
for (const value of counter()) {
  if (value > 3) break;   // ✅ stop pulling whenever you want
  console.log(value);           // 0, 1, 2, 3
}

for...of just keeps calling next() for you until done is true — or until you break, which the array version never needed because it was already fully built.

🌍 Real-world example ▾

Reading a huge log file line by line without loading the whole thing into memory. A generator can read and yield one line at a time, pausing between each — the caller processes a line, asks for the next, and the file never has to exist as one giant in-memory array. That's the same reason Node's streams and many database cursor APIs lean on the same pull-one-at-a-time shape.
