Graph Problem Patterns — spotting the graph hiding in the problem

"How would you recognize that a grid, a multi-start spreading problem, or a puzzle board is really just a graph problem in disguise?"

Why it matters ▾
  • Grid/matrix problems (island counting, mazes, rotting oranges) exist specifically to test whether you reach for BFS/DFS instead of ad-hoc nested loops.
  • Multi-source BFS, 0-1 BFS, and bipartite checks are the layer above plain traversal — this is where "I know graphs" turns into "I know which graph technique fits."
  • A very common opener: "this problem doesn't mention graphs at all" — the interviewer is testing whether you can spot the hidden state-space graph.
🔥 Easy interview recall

Graph Problem Patterns = "if it's states plus legal moves, it's a graph — even when it doesn't look like one."

Think: Grid → cells are nodes, neighbor cells are edges Many starting points → one multi-source BFS, not several single-source ones Only 0/1 edge weights → a deque, not a priority queue Split into 2 non-conflicting groups → 2-color it, check bipartite Directed "seen this before" → check if it's still on the current path

⚠️ Common Trap

Running plain BFS separately from every source and merging the results isn't wrong. It's just far more expensive than pushing every source into one BFS queue up front — that single-pass version is the efficient approach an interviewer is actually checking for.

🔄 Likely Follow-up

"This problem doesn't mention graphs at all — how do I know it's a graph problem?" Whenever there's a set of states or positions and a notion of legal moves between them, that's an implicit graph — a grid, a puzzle board, and a dependency list all qualify, regardless of the problem's surface description.

🎯 Say this in the interview — the exact lines to land

"Most of these aren't new algorithms — they're BFS/DFS applied once you notice the hidden graph: a grid's cells are nodes and neighbors are edges, several starting points become one multi-source BFS, and 0/1-weighted edges let a deque replace a priority queue."

  • Grid → cells are nodes, adjacency is edges, walls just get no edges.
  • Many sources → multi-source BFS, seed the queue with all of them first.
  • Only 0/1 weights → 0-1 BFS with a deque, no priority queue needed.
  • Two non-conflicting groups → bipartite check via 2-coloring.
  • Directed cycle → back edge to a node still on the current path, not just "visited."
  • No graph in sight → model states as nodes, moves as edges.
📖 Explanation ▾

Every one of these patterns starts the same way: you take something that isn't drawn as a graph — a grid, a set of burning cells, a puzzle board — and notice it actually has nodes (the individual states or positions) and edges (the legal moves between them). Once you see that, the entire BFS/DFS toolkit from Basic's Graph Fundamentals applies directly, with no new algorithm to learn.

A grid cell almost always has up to 4 neighbors (up/down/left/right), sometimes 8 if diagonals count — each neighbor is an edge, and a blocked/wall cell is simply a node that never gets an edge into it. Multi-source BFS and 0-1 BFS are still plain BFS underneath: multi-source just seeds the queue with every starting node before the first step runs, and 0-1 BFS swaps the queue for a deque so a free (0-weight) move jumps the line instead of paying for a priority queue it doesn't need.

Bipartite checking and cycle detection both come from the same traversal, read differently: 2-coloring nodes as you BFS/DFS catches a same-color edge as "not bipartite," while cycle detection in a directed graph needs to know whether a revisited node is still on the current path — not just visited at some earlier point — because a directed graph can finish exploring a node down one path with no cycle at all, and later reach it again from a completely unrelated path.

State-space search is the same toolkit applied to a graph that's never drawn anywhere — a puzzle board, or a set of keys collected so far, is a node, and a legal move is an edge. What actually decides whether that search is correct is visited-state modeling: a "state" has to capture every fact that changes which moves are legal next, not just a position. A grid robot that also cares which direction it's facing needs visited[row][col][direction], not visited[row][col] — leave out a real dimension and two genuinely different states collapse into one, silently skipping a valid path. The usual fix is to encode the whole state as one hashable key — a tuple, a small bitmask, a serialized string — and check that key against a set, the same idea as a grid's plain visited[row][col].

💻 See the code ▾
Pseudocode 
queue = []
for each source in sources:
    visited[source] = true
    queue.push(source)              // ✅ every source starts together

while queue not empty:
    cell = queue.pop_front()
    for each neighbor of cell:
        if not visited[neighbor]:
            visited[neighbor] = true
            dist[neighbor] = dist[cell] + 1
            queue.push(neighbor)

Every source enters the queue before the first step runs — one BFS layer expands them all at once, instead of one BFS per source.

Pseudocode 
deque = []
deque.push_front(start)
dist[start] = 0

while deque not empty:
    node = deque.pop_front()
    for each (neighbor, weight) of node:
        newDist = dist[node] + weight
        if newDist < dist[neighbor]:
            dist[neighbor] = newDist
            if weight == 0:
                deque.push_front(neighbor)   // ✅ free — go now
            else:
                deque.push_back(neighbor)    // costs 1 — go later

A 0-weight edge jumps to the front of the deque, a 1-weight edge waits at the back — same result as Dijkstra, no priority queue needed.

🌍 Real-world example ▾

Your interviewer says: "several fires start burning in a grid at the same time — how long until everything has burned?" That's multi-source BFS: push every already-burning cell into the queue before the first step, then let the fire spread outward layer by layer in one pass — not one BFS per fire, compared and merged afterward.
