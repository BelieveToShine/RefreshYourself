Pass-by-value — even when it's an object

"Is Java pass-by-value or pass-by-reference?"

Why it matters ▾
📬 Pass-by-value, always
❗ ProblemIf a method could secretly swap out the caller's own variable for a different object entirely, every method call would be unpredictable — you'd have to read the whole method body to know if your variable still points where you left it.
✅ SolutionJava always copies the argument's value into the parameter. For an object, that value is the reference itself (the address) — so the method can change the object it points to, but reassigning the parameter only ever changes the local copy.
RecallAlways a copy — for objects, a copy of the address, not the object.
🔥 Easy interview recall

Java = "always pass-by-value — even the reference itself gets copied."

Think: d.setX() → changes the shared object, visible outside. d = new Dog() → changes only the local copy, invisible outside.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Java passes objects by reference" is wrong — it only looks right because mutating a shared object through the copied reference looks like reference semantics. The parameter is still a value-copied reference; reassigning it never affects the caller.

🔄 Likely Follow-up

"So why does list.add(x) inside a method show up for the caller too?" Because add mutates the shared List object through the copied reference — the same object, reached two ways. It's not evidence of pass-by-reference; a plain reassignment (list = new ArrayList<>()) would prove the opposite.

🎯 Say this in the interview — the exact lines to land

"Java is always pass-by-value. For an object argument, the value being copied is the reference itself — so a method can mutate the object it points to, but reassigning the parameter inside the method never changes what the caller's variable points to."

  • Mutating through the reference → visible to the caller, same object.
  • Reassigning the parameter → invisible to the caller, local copy only.
  • There is no pass-by-reference in Java, full stop.
📖 Explanation ▾

Every argument in Java is copied into its parameter — no exceptions. For a primitive, that copy is the actual value (5, true). For an object, Java has no way to copy "the object" into a parameter at all — objects always live on the heap and are only ever reached through a reference. So what gets copied is the reference's own value: the address it currently holds.

That single fact explains both halves of the behavior. Calling a method on the parameter (d.setName(...)) follows the copied address to the one shared object on the heap — the caller sees the change, because there's only ever one object. Assigning a brand-new object to the parameter (d = new Dog()) just points the local copy at a different address — the caller's own variable, a completely separate copy, was never touched.

💻 See the code ▾
☕ Java 
static void rename(Dog d) { d.setName("Rex"); }

Dog myDog = new Dog("Fido");
rename(myDog);
System.out.println(myDog.getName());   // ✅ "Rex" — same shared object

The method follows its copy of the address to the one real object — mutation is visible outside.

☕ Java 
static void replace(Dog d) { d = new Dog("Bruno"); }

Dog myDog = new Dog("Fido");
replace(myDog);
System.out.println(myDog.getName());   // ❌ still "Fido" — myDog never moved

Reassigning d only redirects the local copy of the address — myDog is untouched.

🧭 Use Cases — recognize these when they happen to you ▾
1 You pass a List into a method and it calls .add(...) on it

This is the #1 case people point to as "proof" of pass-by-reference — it isn't. The method mutated the one shared List object through its copy of the reference; the caller's own variable still points to that same list.

RememberMutation through a shared object ≠ pass-by-reference.
2 A method tries to "swap" two objects by reassigning both parameters

A classic trick interview question — swap(x, y) can never actually swap the caller's two variables in Java, because the method only ever has its own local copies of the references to reassign.

RememberCan't write a real swap(a, b) in Java — reassignment stays local.
3 You say "Java passes objects by reference" out loud in an interview

Interviewers often ask a quick follow-up ("so can you swap two objects inside a method, then?") specifically to see if that phrase was memorized without being understood — reassignment never crossing back to the caller is the tell.

Remember"Pass by reference" is the #1 wrong phrase to avoid saying here.
🌍 Real-world example ▾

Handing someone a copy of a house address, not the house. They can drive there and repaint the house — the real house changes, and you'll see it too. But if they write a different address on their own copy of the paper, your own paper, and the house it points to, never changes at all.
