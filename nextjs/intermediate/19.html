⭐ Next.js · Intermediate · Should Know

<Script> doesn't just load a script — it decides when

"How does the Script component let you control when a third-party script loads?"

Why it matters ▾
⏱️ next/script
❗ ProblemA heavy third-party script (analytics, ads, a chat widget) loaded with a plain <script> tag competes with the page's own hydration, often hurting how quickly the page actually becomes interactive.
✅ SolutionThe next/script <Script> component's strategy prop controls exactly when the script loads relative to the page's own rendering, instead of loading it immediately and unconditionally.
Recall<Script> = a plain script tag that can wait its turn.
🔥 Easy interview recall

beforeInteractive → before hydration, critical only

afterInteractive → default, soon after interactive

lazyOnload → idle time, lowest priority

worker → off the main thread, experimental

Think: Earliest to latest — beforeInteractive → afterInteractive → lazyOnload, with worker stepping off the main thread entirely.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Loading a heavy third-party script with a plain <script> tag. It blocks or competes with the page's own hydration with no load-timing control, often hurting Core Web Vitals for no functional benefit.

🔄 Likely Follow-up

"Which strategy would a non-critical analytics script typically use?" lazyOnload or afterInteractive — analytics tracking rarely needs to block anything the user is actually trying to do.

🎯 Say this in the interview — the exact lines to land

"next/script's Script component controls exactly when a third-party script loads relative to the page's own hydration, through its strategy prop — beforeInteractive, afterInteractive (the default), lazyOnload, or the experimental worker strategy."

  • beforeInteractive → critical scripts only, rare in practice.
  • afterInteractive → the default, soon after the page is usable.
  • lazyOnload → idle time, for anything genuinely non-urgent.
  • worker → off the main thread entirely, still experimental.
📖 Explanation ▾

A plain HTML <script> tag has no concept of "wait until the page can spare the time" — it loads (and, without async/defer, can block) exactly where it's placed. next/ script's Script component wraps a third-party script with an explicit strategy, so Next.js decides the actual load timing instead of the browser just running it as soon as it's parsed.

beforeInteractive is reserved for scripts that genuinely must exist before any hydration happens — bot detection, some consent managers — because it can delay the page becoming interactive. afterInteractive, the default, loads soon after the page is usable, which covers most analytics and tag-manager scripts. lazyOnload defers loading until the browser is idle, the right choice for anything that genuinely doesn't need to run early.

💻 See the code ▾
JSX 
import Script from 'next/script';

<Script
  src="https://analytics.example.com/tag.js"
  strategy="lazyOnload"  // ✅ waits for idle time — never blocks anything
/>

Non-urgent analytics is the textbook case for lazyOnload.

JSX 
<script src="https://widget.example.com/chat.js"></script>
// ❌ plain tag — competes with hydration, no load-timing control at all

Technically works, but Next.js has no say in when this runs.

🧭 Use Cases — recognize these when they happen to you ▾
1 A tag-manager script (Google Tag Manager, a marketing pixel) needs to load soon, not urgently

This is the most common case — most third-party embeds are fine loading right after the page is usable, which is exactly what the default afterInteractive strategy does.

RememberMost embeds → just leave the default strategy alone.
2 A chat widget or feedback bubble only needs to appear eventually

A chat bubble doesn't need to be ready the instant the page loads — deferring it to idle time with lazyOnload keeps it from competing with anything the visitor actually came for.

RememberNothing depends on it being ready immediately → lazyOnload.
3 You mark a heavy, non-critical script beforeInteractive "just to be safe"

beforeInteractive is meant for scripts that must exist before hydration — a heavy, non-essential script marked this way "to be safe" instead actively delays the page becoming interactive, the opposite of what most third-party scripts need.

RememberbeforeInteractive is for scripts that must run early — not a safety default.
🌍 Real-world example ▾

A marketing team adds a support-chat widget's embed snippet straight from the vendor's docs — a plain <script> tag. Lighthouse's interactivity score drops noticeably; swapping it for <Script src="..." strategy="lazyOnload" /> fixes it without removing any functionality, because the widget never needed to load that early in the first place.
