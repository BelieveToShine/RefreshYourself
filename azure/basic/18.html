Load balancing — the idea before you pick a service for it

"What does load balancing mean at a basic level, before getting into which specific Azure service does it?"

Why it matters ▾
  • Comes up the moment scaling, reliability, or "high availability" is discussed — the natural first question before drilling into which Azure service handles it.
  • Explains a real production behavior: why an app keeps serving traffic without interruption when one instance behind it goes down.
  • Sets up the comparison question that follows right after — which specific Azure service to actually reach for, covered in Intermediate.
🔥 Easy interview recall

Load balancing = "spread the traffic, skip the sick instance."

Think: a health probe checks every instance — fail it, and traffic stops going there until it passes again.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Load balancer" is not one specific Azure service. The right choice genuinely depends on the network layer (L4 vs. L7) and the scope (regional vs. global) — exactly why Azure has more than one service built around this same idea.

🔄 Likely Follow-up

"What's a health probe?" A periodic check the load balancer makes against each backend instance — an instance that fails its probe gets temporarily removed from rotation until it passes again.

🎯 Say this in the interview — the exact lines to land

"Load balancing spreads traffic across multiple backend instances and routes around unhealthy ones using health probes — an instance that fails its probe stops receiving new traffic until it passes again."

  • Spreads traffic → no single instance gets overwhelmed.
  • Health probes → periodic checks that pull a failing instance out of rotation.
  • Layer matters → L4 (transport) vs. L7 (application) change what the balancer can see and route on.
  • Which service? → that choice comes later, in Intermediate — it depends on layer and scope.
📖 Explanation ▾

Load balancing means spreading incoming requests across more than one backend instance, so no single instance gets overloaded while the others sit idle. It also keeps the app available when one instance goes down: the load balancer runs a health probe against every instance, and any instance that fails its probe stops receiving new traffic until it starts passing again.

This is a general networking idea, not one specific product. It can happen at the transport layer (L4 — routes by IP/port, has no idea what's inside the request) or the application layer (L7 — understands HTTP, so it can route by path, header, or hostname). Azure has more than one service built around this same idea, each suited to a different layer and scope (a single region vs. spread across the globe) — comparing those specific services is its own Intermediate-tier topic, deliberately left out here.

🌍 Real-world example ▾

A web app runs behind a load balancer across three instances. One instance crashes — but nothing goes down for users, because the health probe had already stopped sending it traffic before the crash even mattered; the other two keep serving every request without interruption.
