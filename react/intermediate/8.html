Controlled vs. uncontrolled — who actually owns the input's value

"What's the difference between controlled and uncontrolled form inputs?"

Why it matters ▾
🎛️ Controlled
❗ ProblemWithout something owning the input's value as it's typed, React can't react to each keystroke — no live validation, no conditional fields, no showing that value anywhere else on the page.
✅ SolutionA controlled input's value comes from React state and its onChange calls setState on every keystroke, so state is always the single source of truth and can react instantly.
RecallControlled = React state owns it, re-renders every keystroke.
📄 Uncontrolled
❗ ProblemRe-rendering the whole form on every keystroke has a real cost once a form gets large — but not every field actually needs that live reactivity.
✅ SolutionAn uncontrolled input lets the DOM hold its own value the normal browser way — React only reads it once, via a ref, when it actually needs to (e.g. at submit), skipping the per-keystroke render.
RecallUncontrolled = the DOM owns it, React peeks via a ref only when asked.
🔥 Easy interview recall

Controlled → React state owns it, re-renders every keystroke

Uncontrolled → the DOM owns it, React peeks via a ref

Think: Controlled = every keystroke is a React event. Uncontrolled = React checks in only when it asks.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Uncontrolled inputs are not the "outdated" way to build forms. Reading the value only when needed via a ref (e.g. at submit) is a legitimate, often simpler choice for large forms or whenever you don't need to react to every keystroke — it's a trade-off between React-driven reactivity and per-keystroke render cost, not a wrong pattern.

🔄 Likely Follow-up

"How do you prevent unnecessary re-renders in a large controlled form?" Split the form into smaller components so each field's state update only re-renders that field's own subtree, or switch fields that don't need live reactivity to uncontrolled inputs read via a ref only at submit time.

🎯 Say this in the interview — the exact lines to land

"A controlled input's value is driven entirely by React state — every keystroke calls setState, and the value shown comes back from that state. An uncontrolled input lets the DOM hold its own value directly; React only reads it through a ref when it actually needs to, like on submit."

  • Controlled → React state is the single source of truth, re-renders every keystroke.
  • Uncontrolled → the DOM holds the value, use for large forms or when you don't need live reactivity.
  • Fewer re-renders → split into smaller components, or go uncontrolled for fields that don't need live validation.
  • Async submission → needs its own pending/error/success state, same as any async call.
  • Server-side validation errors → surfaced back into the form's own error state once the response comes back.
📖 Explanation ▾

A controlled input's value is driven entirely by React state — the input's value prop always comes back from that state, and its onChange handler calls setState on every keystroke. React re-renders on every character, and the input always shows exactly what state says it should.

An uncontrolled input lets the DOM keep its own value the normal browser way. React doesn't touch it on every keystroke — it only reads the current value when it actually needs to, typically through a ref at submit time, rather than reacting to each character.

Neither is "more correct" — it's a trade-off. Controlled buys you live validation and conditional fields at the cost of a render per keystroke; uncontrolled skips that cost but can't react mid-typing. For a large form, that render cost is reduced by splitting the form into smaller components (so one field's update doesn't re-render the whole form) or by leaving fields that don't need live reactivity uncontrolled. Async submission needs its own pending/error/success state like any async operation, and server-side validation errors get written back into the form's own error-display state once the response arrives.

💻 See the code ▾
JSX 
<input
  value={name}
  onChange={e => setName(e.target.value)}
/>

Every keystroke calls setState — the value shown always comes back from state.

JSX 
const ref = useRef();

<input ref={ref} defaultValue="" />

// later, e.g. on submit:
const value = ref.current.value; // read only on submit

React never sees each keystroke — it reads the DOM's own value once, through the ref.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to validate input live, show/hide fields conditionally, or reflect the typed value elsewhere on the page

This is the #1 reason to reach for controlled: because React state re-renders on every keystroke, you can show an error, disable a submit button, or conditionally render another field the instant the value changes — the value the input shows and the value in state are always the same thing.

RememberLive validation or conditional fields → controlled, so state can react to every keystroke.
2 You have a large form and a field that doesn't need to react to every keystroke, only be read once

Controlled inputs mean React re-renders as the user types in any field, which adds up on a big form. A field that doesn't need live reactivity — read only at submit, say — can go uncontrolled and be read through a ref once, skipping the per-keystroke render entirely.

RememberNo live reactivity needed → uncontrolled skips the per-keystroke render.
3 You assume uncontrolled inputs are just the outdated way to build forms

Uncontrolled isn't a legacy pattern to avoid. Reading the value only when needed via a ref (e.g. at submit) is a legitimate, often simpler choice for large forms or any field that doesn't need to react to every keystroke — a trade-off between React-driven reactivity and per-keystroke render cost, not a wrong pattern.

RememberUncontrolled = a valid trade-off, not an outdated one.
🌍 Real-world example ▾

A controlled input is a live-transcribed conversation — every word is recorded and read back to you in real time, because React state is listening to every keystroke. An uncontrolled input is a private notebook someone only glances at when they specifically ask to see what you wrote, like at submit time.
