?page=3 vs. ?after=<cursor> — the pagination that survives real traffic

"What's the difference between offset-based and cursor-based pagination, and when would you reach for each?"

Why it matters ▾
  • Checks whether you understand pagination past "just add a ?page=" — whether you know when that choice actually hurts once real data volume shows up.
  • Comes up on any endpoint returning more than a screenful of rows — feeds, order queues, admin tables, search results.
  • Sets up the natural follow-up about what a paginated response body should actually return besides the items.
🔥 Easy interview recall

?page=3 → counts rows from the start

?after=<cursor> → anchors to the last item

Think: offset counts. cursor points. Counting drifts when rows change; pointing doesn't.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Offset pagination isn't just "the simpler choice" — it degrades at exactly the scale where pagination starts to matter, re-scanning every discarded row on each request while inserts and deletes shift the count underneath it.

🔄 Likely Follow-up

"What should a paginated response actually include besides the items themselves?" Metadata that tells the client how to get the next page without guessing — a hasNextPage flag and the next cursor (or a total count for offset-based, though total counts get expensive at scale too).

🎯 Say this in the interview — the exact lines to land

"Offset pagination skips a fixed number of rows to reach a page — simple, and it lets you jump straight to any page number, but the database still has to scan and discard every skipped row, and inserts or deletes between requests shift that count, causing skipped or duplicated items. Cursor-based pagination anchors each page to the last item returned and asks for items after it, so it stays stable under concurrent changes and scales better — the trade-off is you lose the ability to jump to an arbitrary page."

  • ?page= → fine for small, mostly-static lists where jumping to page 47 genuinely matters.
  • ?after= → the right default for large, changing data — a feed, a live queue, real traffic.
  • Deep OFFSET → still scans and discards every skipped row — that's the performance cost, not a hypothetical one.
  • Cursor pagination → trades away jump-to-page — next/previous only, anchored to an item, not an index.
📖 Explanation ▾

Offset pagination (?page=3&pageSize=20, or ?offset=40&limit=20) tells the database to skip a fixed number of rows before returning the next batch. It's simple to reason about and lets a client jump directly to any page — but OFFSET 10000 still makes the database walk past those 10,000 rows every single request, so it gets slower the deeper someone pages. Worse, if a row is inserted or deleted while someone is paging, the offset no longer points at the boundary it used to — the same numeric skip now lands on a different row, so items get skipped or shown twice.

Cursor-based pagination (?after=<cursor>) sends back a token pointing at the last item on the current page; the next request asks for whatever comes "after" that item. Because the query becomes "find rows after this specific one" — an indexed lookup — instead of "skip this many rows," it stays fast regardless of how deep the pages go, and it stays correct under concurrent inserts and deletes, since it's anchored to an item's position, not a shifting count.

💻 See the code ▾
C# 
public async Task<IActionResult> GetOrders(int page = 1, int pageSize = 20)
{
    var items = await _db.Orders
        .OrderBy(o => o.Id)
        .Skip((page - 1) * pageSize)   // ❌ still scans & discards every skipped row
        .Take(pageSize)
        .ToListAsync();
    return Ok(items);
}

Skip(10000) makes the database walk past 10,000 rows before it can return anything.

C# 
public async Task<IActionResult> GetOrders(int? after, int pageSize = 20)
{
    var query = _db.Orders.OrderBy(o => o.Id);
    if (after is not null)
        query = query.Where(o => o.Id > after);   // ✅ anchored — no row count to shift
    var items = await query.Take(pageSize).ToListAsync();
    return Ok(items);
}

WHERE Id > after uses the index directly — no skipped rows to scan.

C# 
public class PagedResponse<T>
{
    public List<T> Items { get; set; }
    public int? NextCursor { get; set; }   // null once there's nothing left
    public bool HasNextPage { get; set; }
}

The client never guesses the next URL — the response tells it exactly what to ask for next.

🌍 Real-world example ▾

A catalog endpoint pages fine at page 2, but times out by page two thousand — and support tickets report products appearing twice or vanishing whenever new stock ships mid- scroll. Both symptoms point at offset pagination: a deep OFFSET forces a full scan of every discarded row, and an insert ahead of the current page shifts everything after it. Switching to a cursor (?after=<lastId>) fixes both — it stays anchored to a specific product no matter what gets added or removed around it.
