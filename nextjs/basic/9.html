next/font — self-hosted at build time, so the browser never waits on it

"How does next/font avoid the flash of unstyled text you get with a normal Google Fonts <link> tag?"

Why it matters ▾
🔤 next/font
❗ ProblemA normal Google Fonts <link> tag makes the browser open a whole separate connection to an external CDN before the font can even start downloading — while that's in flight, text either sits invisible or flashes from a fallback font to the real one (FOUT/FOIT), shifting layout.
✅ Solutionnext/font downloads and self-hosts the font files at build time, so they ship from your own server alongside the rest of the page — no external request, no separate round trip, and no client-side JS required to apply it.
Recallnext/font = the font is already yours before the browser ever asks.
🔥 Easy interview recall

next/font = "self-host the font at build time — zero extra network requests."

Think: normal Google Fonts <link> → browser leaves to fetch it. next/font → the font never left home.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Still dropping a <link> tag to Google Fonts' own CDN "for simplicity." That reintroduces the exact external request and possible layout shift next/font exists specifically to remove — once you're on next/font, the manual link tag has no job left to do.

🔄 Likely Follow-up

"Does this work for a custom/local font file too, not just Google Fonts?" Yes — next/font/local handles a self-hosted font file you provide, with the same build-time optimization and the same API shape as next/font/google.

🎯 Say this in the interview — the exact lines to land

"next/font downloads the font file and self-hosts it at build time — even for Google Fonts — so the browser never makes a separate request to an external font CDN. That removes the network round trip and the layout shift that comes with it, with no client-side JavaScript needed to apply it."

  • next/font/google → self-hosts a Google font at build time, no external request.
  • next/font/local → same optimization, same API, for a font file you already have.
  • Zero client JS → the optimization happens at build time, not in the browser.
📖 Explanation ▾

A normal <link href="https://fonts.googleapis.com/...">" tag means the browser has to open a brand-new connection to Google's font servers before it can even start downloading the font — on top of the connection it already opened to load your page. Until that font arrives, the browser either shows invisible text (FOIT) or a fallback font that visibly swaps out once the real one lands (FOUT), and that swap can shift layout if the two fonts don't measure the same.

next/font removes the external request entirely. At build time, it downloads the font files and serves them from your own domain, right alongside your CSS and JS — the browser never has to leave to go get it. Behind the scenes it also sets sensible fallback-font sizing automatically, which is what keeps layout from jumping even before the real font paints.

This is a build-time optimization, not a runtime or client-side one — there's no JavaScript shipped to the browser to make this work. The font is just already there, the same way any other static asset on your own server is.

💻 See the code ▾
JSX 
import { Inter } from 'next/font/google';

const inter = Inter({ subsets: ['latin'] });  // downloaded at build time

export default function RootLayout({ children }) {
  return (
    <html className={inter.className}>
      <body>{children}</body>
    </html>
  );
}

The font is loaded once, at the top of the app — next/font self-hosts it, no external <link> needed anywhere.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're pulling in a Google Font for the whole app

Import the font once in the root layout and apply its generated className to <html> or <body> — every page gets the self-hosted font with zero extra setup. This is the #1 scenario you'll actually run into.

RememberApp-wide font → load once in the root layout.
2 Your design uses a custom font your team already owns

Point next/font/local at your own font file instead of a Google font name. You get the exact same self-hosting and layout-shift protection — it's just reading the file from your project instead of downloading one from Google at build time.

RememberYour own font file → next/font/local, same benefits.
3 A teammate adds Google Fonts' own <link> "just to test"

Adding Google's own CDN link tag back on top of next/font brings back the exact external request and possible flash the API was built to remove — it isn't a harmless extra, it quietly reintroduces the original problem.

RememberAlready on next/font → never add the manual Google Fonts link too.
🌍 Real-world example ▾

Think of it like ordering a book versus already owning it. A normal <link> tag to Google Fonts is ordering the book every time someone visits — there's a wait while it ships. next/font already put a copy on your own shelf at build time, so it's there the instant anyone asks.
