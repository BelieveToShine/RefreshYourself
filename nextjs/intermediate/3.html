One fetch() replaces two separate functions

"How did the App Router replace getStaticProps and getServerSideProps?"

Why it matters ▾
🧭 Pages Router → App Router fetching
❗ ProblemIn the Pages Router, choosing between build-time and per-request data meant choosing between two entirely separate exported functions for the whole page — getStaticProps or getServerSideProps — with no finer-grained option.
✅ SolutionThe App Router removes both functions — a Server Component just fetch()es directly, and the cache option on that specific call decides its freshness, independent of every other fetch on the same page.
RecallTwo named functions → one fetch() with a cache option, decided per call.
🔥 Easy interview recall

getStaticProps → separate function, Pages Router only

getServerSideProps → separate function, Pages Router only

App Router → inline fetch() inside the component

Think: Pages Router picked freshness per page. App Router picks it per fetch call.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

getStaticProps doesn't work inside app/. It's a Pages-Router-only API — the App Router simply never calls it, even if the file exports it, so it silently does nothing instead of erroring.

🔄 Likely Follow-up

"Why did the App Router replace two named functions with one fetch() API?" It turns an all-or-nothing, page-level choice into a per-call choice — finer-grained and composable, so one page can mix a cached fetch with an always-fresh one.

🎯 Say this in the interview — the exact lines to land

"In the Pages Router, getStaticProps and getServerSideProps were separate exported functions that ran before the component and passed data in as props. The App Router removes that split — the Server Component fetches directly, and the cache option on each fetch() call decides its own freshness."

  • getStaticProps → Pages Router only, build-time.
  • getServerSideProps → Pages Router only, per-request.
  • App Router → no separate function — fetch inline, cache option per call.
📖 Explanation ▾

In the Pages Router, Next.js needed to know, for the whole page, whether to render it once at build time or fresh on every request — so it looked for one of two specially-named exported functions, getStaticProps or getServerSideProps, ran whichever one existed before the component itself, and handed the result in as props.

The App Router doesn't have an equivalent function at all. A Server Component's own body is already an async function, so it just calls fetch() directly and awaits the result — the freshness decision moves from "which function did you export" to "what cache option did this fetch call use."

That's a genuine architecture change, not just a rename: a single App Router page can mix a force-cache fetch for rarely-changing data with a no-store fetch for a per-user cart, side by side — something the Pages Router's one-function-per-page model couldn't express at all.

Pages RouterApp Router
Where data fetching livesseparate exported functioninline in the component
Freshness granularitywhole pageper fetch() call
Build-time datagetStaticPropsfetch(..., {cache:'force-cache'})
Per-request datagetServerSidePropsfetch(..., {cache:'no-store'})
💻 See the code ▾
Next.js 
// pages/products.js — Pages Router
export async function getStaticProps() {
  const res = await fetch('https://api.example.com/products');
  return { props: { products: await res.json() } };
}

export default function ProductsPage({ products }) {
  return <ProductList items={products} />;
}

Two separate pieces — the data function, and the component it feeds.

Next.js 
// app/products/page.js — App Router, same outcome
export default async function ProductsPage() {
  const res = await fetch('https://api.example.com/products', {
    cache: 'force-cache'
  });
  const products = await res.json();
  return <ProductList items={products} />;   // ✅ one function, no props handoff
}

The fetch and the render live in the same function — no handoff step.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're migrating a Pages Router page to the App Router

Moving a page with getServerSideProps into app/ means deleting that function and moving its fetch directly into the component with cache: 'no-store' — the per-request freshness carries over, just expressed differently.

RemembergetServerSideProps's job → the fetch call's cache option now.
2 One page needs both cached AND always-fresh data

The Pages Router had no way to say "this page is half-static, half-live" — it was one function for the whole page. The App Router lets two different fetch() calls in the same component each pick their own cache option.

RememberMixed freshness on one page → only possible per-fetch, not per-page.
3 You export getStaticProps from a file inside app/

The App Router doesn't recognize getStaticProps at all — it isn't an error, the export is just never called, which can hide the mistake until someone notices the data never updates the way they expected.

RemembergetStaticProps in app/ → not an error, just dead code.
🌍 Real-world example ▾

A team migrating a large Pages Router site to the App Router, one route at a time. Every route that used to export getStaticProps or getServerSideProps loses that function entirely — the fetch moves inside the component, and whoever did the migration picks the matching cache option so the route keeps the same freshness behavior it had before.
