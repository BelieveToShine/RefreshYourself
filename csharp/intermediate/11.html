init and required — locked after construction, enforced by the compiler

"What does an init-only property allow that a normal setter doesn't?"

Why it matters ▾
  • Shows you understand modern C# immutability, not just get/set from a decade ago.
  • Explains a real compile error (CS9035) a teammate will eventually paste into chat asking "what does this mean?"
  • Comes up the moment a DTO, config object, or record needs to be fully formed before anyone can touch it.
🔥 Easy interview recall

init → settable only during construction

required → compiler forces you to set it

Think: init = write-once. required = must-write.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

required doesn't mean not-null. The compiler only checks that the member was assigned during construction — assigning it null (on a nullable type) or a default value still satisfies required.

🔄 Likely Follow-up

"Can any code inside the class write to an init property, or only the constructor?" Only during construction itself — the constructor body or an object-initializer at the call site. Once the object exists, no method, not even one on the same class, can assign it again.

🎯 Say this in the interview — the exact lines to land

"An init property behaves like a normal setter only while the object is being constructed — an object initializer or the constructor body — then the compiler locks it read-only forever. required doesn't add write access; it forces the caller to actually provide a value, or the code won't compile."

  • init → settable once, then permanently read-only.
  • required → enforced at the call site — miss it and the build fails, nothing runs.
  • required + init together → "must provide it, then can't change it" — the common combo for DTOs and records.
  • required checks presence, not value → a null or default still counts as "provided".
📖 Explanation ▾

init is a setter with a shorter lease than a normal one. Inside an object initializer, or inside the constructor body itself, it works exactly like set. The instant the constructor returns, the compiler simply stops allowing writes — there's no runtime flag being flipped, it's a compile-time rule about where the assignment is allowed to appear.

required is a completely different kind of check: it doesn't touch how the member can be written, only whether it was written. Skip a required member in every constructor call and object initializer, and the code doesn't compile — no NullReferenceException three services downstream, just a build failure at the one place that actually forgot it.

They're independent features that happen to pair naturally: required guarantees a value was supplied, init guarantees nobody can supply a different one later. Put them on the same property and you get "must provide it, then can't change it" — which is exactly the shape most DTOs and records actually want.

💻 See the code ▾
C# 
public class Car
{
    public string Model { get; init; }
}

Car car = new Car { Model = "Tesla" };  // ✅ allowed — still constructing

init behaves like a normal setter until the object finishes constructing.

C# 
car.Model = "Civic";   // ❌ compile error — init is write-once

The same property that accepted a value a moment ago is now permanently locked.

C# 
public class Person
{
    public required int Id { get; init; }
}

Person p1 = new Person();                 // ❌ CS9035 — Id was never set
Person p2 = new Person { Id = 7 };       // ✅ compiles — Id was provided

required turns "don't forget to set this" from a code-review comment into a compiler error.

🌍 Real-world example ▾

Building an object is like filling out a contract before it's notarized. You can only write into the init fields while the ink is still wet — the moment the contract is signed (the constructor returns), the pen is put away for good, even for you. required is the notary who simply won't accept a form with a mandatory field left blank in the first place.
