Single Responsibility Principle — one reason to change, not one method

"What does the Single Responsibility Principle actually mean — and is it about having one method?"

Why it matters ▾
📐 Single Responsibility Principle
❗ ProblemA method that validates input, saves to a database, and sends an email has three separate reasons to change — a validation-rule update, a schema change, and an email-template change would each force an edit to that same code, for reasons that have nothing to do with each other.
✅ SolutionSRP keeps a class to one reason to change — one axis of responsibility — so an unrelated requirement never forces an edit to code that has nothing to do with it, no matter how many methods that class ends up with.
RecallSRP = one reason to change — not one method.
🔥 Easy interview recall

SRP = "one reason to change — not one method."

Think: InvoiceFormatter → 10 methods, one job ProcessOrder() → one method, three jobs

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

One method does not mean one responsibility. A single method that validates input, saves to a database, and sends an email still has three separate reasons to change — that's an SRP violation with a method count of one.

🔄 Likely Follow-up

"How do you actually spot an SRP violation in code review?" Ask: if requirement X changes, does this class need to change? Now ask the same for an unrelated requirement Y — if both answers are yes, the class is doing two jobs.

🎯 Say this in the interview — the exact lines to land

"SRP means one reason to change, not one method. A class can have many methods and still have a single responsibility if every method serves that one job — and it can violate SRP with just one method if that method serves several unrelated reasons to change."

  • Reason to change → one axis of responsibility, one stakeholder who could request a change.
  • Method count is not the measure — ten small methods can serve one job, one method can serve three.
  • Spot a violation by asking: would an unrelated requirement change also force an edit here?
  • InvoiceFormatter → many methods, one job — follows SRP.
  • ProcessOrder() doing validation, storage, and email → one method, three jobs — violates SRP.
📖 Explanation ▾

SRP says a class should have exactly one reason to change — one axis of responsibility, one stakeholder or requirement category that could force an edit. It's not about counting methods or lines; it's about counting who could ask for a change, and why.

A class can have many methods and still one job. InvoiceFormatter might have FormatHeader(), FormatLineItems(), and FormatFooter() — three methods, but every one of them exists for the same reason: formatting an invoice. A formatting-rule change is the only thing that touches this class.

The reverse also holds: a class can have one method and still several jobs. A single method that validates input, saves to a database, and sends an email has three separate reasons to change — a validation-rule update, a schema change, and an email-template change would each force an edit to the same method, for reasons that have nothing to do with each other.

💻 See the code ▾
C# 
public class InvoiceFormatter
{
    public string FormatHeader(Invoice invoice)
        => $"Invoice #{invoice.Id}";             // formatting only

    public string FormatLineItems(Invoice invoice)
        => string.Join("\n", invoice.Items);  // formatting only

    public string FormatFooter(Invoice invoice)
        => $"Total: {invoice.Total:C}";         // formatting only
}

Three methods, one job — every one of them exists to format an invoice. Only a formatting-rule change touches this class.

C# 
public class OrderProcessor
{
    public void ProcessOrder(Order order)
    {
        if (order.Total <= 0)
            throw new InvalidOperationException();   // ❌ validation rule

        _db.Save(order);                                        // ❌ persistence detail
        _mailer.Send(order.CustomerEmail, "Order received"); // ❌ email detail
    }
}

One method, three reasons to change — a validation rule, a database change, and an email template would each force an edit here, for unrelated reasons.

🧭 Use Cases — recognize these when they happen to you ▾
1 A method validates input, saves to a database, and sends an email — all in one place

This is the classic violation shape you'll spot in code review: a validation-rule change, a schema change, and an email-template change would each force an edit to this same method, for reasons that have nothing to do with each other. This is the #1 shape you'll actually run into.

RememberValidation + persistence + notification crammed into one method → three reasons to change, one violation.
2 You're staring at a class with a long method list, unsure if it violates SRP

Counting methods won't tell you. Run the litmus test instead: if requirement X changes, does this class need editing? Now ask the same for an unrelated requirement Y. If both answers are yes, the class is doing two jobs — no matter how many or how few methods got you there.

RememberUnsure? Ask two unrelated "does this force a change" questions, not the method count.
3 A class has several methods, but every one of them does the same kind of work

Like FormatHeader(), FormatLineItems(), and FormatFooter() — three methods, but only a formatting-rule change would ever touch this class. A high method count alone is never proof of an SRP violation.

RememberMany methods, one job → still follows SRP.
🌍 Real-world example ▾

Think of one employee handling reception, payroll, and IT support. One person, one job title — but three unrelated reasons someone might need to retrain them: a new phone system, a new tax rule, or a new ticketing tool. Their method count (the job title) never changed; the reasons to change what they do just kept multiplying.
