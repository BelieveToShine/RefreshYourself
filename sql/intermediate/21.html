MERGE — update if it matches, insert if it doesn't (and the race to watch)

How do you insert-or-update in one statement?

Why it matters ▾
🔀 MERGE / upsert
❗ ProblemThe "check, then insert or update" approach takes extra statements, and two sessions can both decide a row is missing and both try to insert it.
✅ SolutionMERGE joins a source to a target and runs UPDATE for matches and INSERT for non-matches in one statement — but under concurrency it still needs a lock hint such as HOLDLOCK to be safe.
RecallMERGE = match on a key → update if found, insert if not.
🔥 Easy interview recall

MERGE = "match on a key — update if found, insert if not."

Think: WHEN MATCHED → UPDATE WHEN NOT MATCHED → INSERT Concurrent callers → add HOLDLOCK, or use UPDATE-then-INSERT in a transaction

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"One MERGE statement means the upsert is automatically race-free." Without a lock hint such as HOLDLOCK, two sessions can both see "not matched" and both try to insert, so one can fail with a duplicate-key error.

🔄 Likely Follow-up

"So what do you use in production?" Either MERGE with HOLDLOCK on a unique key, or an UPDATE followed by an INSERT when no row was updated, inside a transaction with UPDLOCK, SERIALIZABLE — many teams prefer the second because it is easier to reason about.

🎯 Say this in the interview — the exact lines to land

"MERGE compares a source to a target on a key: WHEN MATCHED runs an update, WHEN NOT MATCHED runs an insert, all in one statement. It is not automatically safe for concurrent callers, so I add a lock hint such as HOLDLOCK — or use UPDATE-then-INSERT in a transaction."

  • WHEN MATCHED → UPDATE; WHEN NOT MATCHED → INSERT.
  • WHEN NOT MATCHED BY SOURCE → delete or update target rows the source no longer has.
  • OUTPUT $action → shows what happened to each row (INSERT, UPDATE or DELETE).
  • Each target row may match only one source row — otherwise an UPDATE or DELETE fails with an error.
  • Concurrent callers → HOLDLOCK on the target, plus a unique index as the safety net.
  • Many teams use UPDATE-then-INSERT in a transaction instead — simpler to reason about.
📖 Explanation ▾

MERGE takes a source (a table, a query, or a VALUES list) and a target, joins them with ON, and runs a different action per case. WHEN MATCHED updates the existing row. WHEN NOT MATCHED inserts a new one. Optionally, WHEN NOT MATCHED BY SOURCE handles target rows that the source no longer has. An OUTPUT clause, with $action, returns what happened to each row. The statement must end with a semicolon.

The catch is concurrency. A MERGE is one statement, but that alone does not stop two sessions racing on the same key: both can find "no match" and both try to insert. The commonly used fix is a HOLDLOCK (serializable) hint on the target, with a unique index on the key so a duplicate becomes an error, never a silent second row.

Because of this — and because Microsoft's own MERGE documentation warns that at scale it "might introduce complicated concurrency issues" and says separate INSERT/UPDATE/DELETE statements can perform better under heavy concurrency (so test it thoroughly) — many teams use plain UPDATE-then-INSERT: update the row, and if @@ROWCOUNT is zero, insert it, all inside a transaction with UPDLOCK, SERIALIZABLE. Neither is wrong; know both. Related: Transaction Control Mechanics and Locking.

💻 See the code ▾
T-SQL 
MERGE dbo.Stock WITH (HOLDLOCK) AS t           -- HOLDLOCK = guard against a concurrent insert
USING (VALUES (1, 50), (5, 20)) AS s (ProductId, Qty)
   ON t.ProductId = s.ProductId
WHEN MATCHED THEN
    UPDATE SET t.Qty = s.Qty                -- ✅ product exists → update
WHEN NOT MATCHED THEN
    INSERT (ProductId, Qty) VALUES (s.ProductId, s.Qty)   -- ✅ new → insert
OUTPUT $action, inserted.ProductId;           -- shows INSERT / UPDATE per row

One statement does both jobs; OUTPUT $action reports which branch each row took.

T-SQL 
BEGIN TRAN;
UPDATE dbo.Stock WITH (UPDLOCK, SERIALIZABLE)
SET Qty = @Qty WHERE ProductId = @Id;    -- locks the key range, even if no row exists

IF @@ROWCOUNT = 0                          -- nothing updated → row is missing
    INSERT dbo.Stock (ProductId, Qty) VALUES (@Id, @Qty);
COMMIT;

The alternative many teams prefer: the hints hold the key range until commit, so a second session cannot slip an insert in between the two statements.

🌍 Real-world example ▾

Scenario: a nightly job loads a supplier price file into a staging table, then one MERGE updates the prices of products you already have and inserts the new ones — and if two imports could ever overlap, the HOLDLOCK hint keeps them from inserting the same product twice.
