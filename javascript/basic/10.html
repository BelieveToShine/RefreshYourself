Modern JavaScript / ES6+ — and the one item on this list that isn't just nicer syntax

"What's new in modern JavaScript (ES6 and later), and when would you reach for a Map or Set instead of a plain object or array?"

Why it matters ▾
🗄️ Map
❗ ProblemA plain object coerces every key to a string (even a number or another object), so two different object keys can silently collide on the exact same property name, and checking the count means Object.keys(obj).length instead of a direct property.
✅ SolutionMap accepts any value as a key without coercing it, keeps insertion order, and reports its size directly with .size — fixing exactly what a plain object gets wrong.
RecallMap = any key type, real .size, no string coercion.
📦 Plain Object
❗ ProblemReaching for new Map() for simple, string-keyed data adds syntax that doesn't buy anything when none of Map's guarantees are actually needed.
✅ SolutionAn object literal stays simpler and JSON-friendly for exactly that shape of data — known string keys, no need for insertion-order or .size guarantees.
RecallPlain object = still right for simple, JSON-shaped, string-keyed data.
🔥 Easy interview recall

${} → template literal, no string concatenation

Map → any key type, keeps order, has .size

Set → unique values only, no duplicates allowed in

WeakMap/WeakSet → weak reference, doesn't block garbage collection

Think: Map/Set = better collections. WeakMap/WeakSet = the same idea, minus the memory leak.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 Don't mix these two — Map vs. plain object as a key-value store
⚠️ Common Trap

A plain object is not a real map. Every key gets coerced to a string (even a number or another object), so two different object keys can silently collide on the exact same property name.

🔄 Likely Follow-up

"So why not just always use Map instead of {}?" Object literals stay simpler and JSON-friendly for plain, string-keyed data — reach for Map specifically when keys aren't strings, insertion order matters, or you need a reliable .size.

🎯 Say this in the interview — the exact lines to land

"Map is a key-value store that accepts any value as a key, keeps insertion order, and reports its size directly with .size — a plain object coerces every key to a string and has none of those guarantees. Set stores only unique values, the way an array can't enforce on its own. WeakMap and WeakSet hold their keys weakly, so an entry doesn't stop that key's object from being garbage collected — that's the entire reason they exist."

  • Map → use when keys aren't strings, or order/size matter.
  • Set → use for guaranteed uniqueness, instead of checking includes() by hand.
  • WeakMap/WeakSet → use to tag an object without leaking memory if it disappears elsewhere.
  • {}/[] → still the right call for plain, JSON-shaped data with known string keys.
📖 Explanation ▾

Template literals (`Hello, ${name}!`) replace string concatenation — backticks let you drop a variable straight into a string with ${}, and even span multiple lines without \n.

The rest of this page's syntax already gets full treatment elsewhere on this track — quick reminders only:

  • Arrow functions — shorter syntax, and this is inherited lexically (see the Functions topic).
  • Destructuring, spread ..., rest ... — unpacking and combining arrays/objects (see the Destructuring / Spread / Rest topic).
  • Default parameters — function greet(name = "there") — the default only kicks in when the argument is undefined.
  • Optional chaining ?. and nullish coalescing ?? — safely read a possibly-missing property, and fall back only on null/undefined (see the Arrays & Objects topic).
  • Modules (import/export) and classes — each gets its own dedicated page later in this track.

The genuinely new capability on this list is a set of four collection types. Map is a key-value store built to fix what a plain object is bad at: object keys always get coerced to a string, and checking the count means Object.keys(obj).length instead of a direct property.

MapPlain Object
Key typeany value — object, function, NaN, …coerced to a string (or Symbol)
Orderinsertion order, guaranteedmostly insertion order, but numeric-looking keys sort first
Size.size propertyObject.keys(obj).length
Iterate directly?✅ yes — built for for...of❌ no — needs Object.entries() first

Set does the same fix for arrays: adding a value that's already present is a no-op, so uniqueness is guaranteed instead of something you check yourself with indexOf()/includes() on every insert.

WeakMap and WeakSet look like Map/Set with one behavioral difference that's the entire point of them: their keys are held weakly — that reference doesn't count when the garbage collector decides whether an object is still reachable. That makes them the right tool for attaching metadata to an object (a DOM node, a class instance) without keeping it alive forever once everything else drops it. The trade-off: keys must be objects (no strings or numbers), and neither is iterable — you can't list what's inside one, by design.

💻 See the code ▾
JavaScript 
const name = "Al";
// template literal — no + concatenation
`Hello, ${name}!`;

// default param + arrow function
const greet = (who = "there") => `Hi, ${who}`;

const user = { profile: { age: 30 } };
// optional chaining + nullish fallback
user.profile?.age ?? "unknown";

Arrow functions, destructuring, and spread/rest each already have their own page — this is just the quick shape of the newer syntax.

JavaScript 
const m = new Map();
m.set(userObj, "admin");      // any value can be a key
m.size;                          // ✅ 1 — no Object.keys() needed

const o = {};
o[userObj] = "admin";          // ❌ key coerced to "[object Object]"

A plain object silently stringifies userObj into the same text key for every object — Map keeps each one distinct.

JavaScript 
const ids = new Set([1, 2, 2, 3]);
ids.add(2);   // no-op — 2 is already in the set
ids.size;    // ✅ 3

Set enforces uniqueness for you — no manual includes() check needed.

JavaScript 
const cache = new WeakMap();

function tag(el) {
  cache.set(el, { seen: Date.now() });
}
// once nothing else references "el", its cache entry
// ✅ is eligible for garbage collection too — no manual cleanup

A regular Map would keep el alive forever just by holding it as a key; WeakMap lets it be collected normally.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to guarantee no duplicate values in a growing list

Adding a value that's already in a Set is a no-op — .size doesn't change. Uniqueness is guaranteed automatically, instead of writing your own includes() check before every insert.

RememberDuplicate add to a Set → silently ignored, size unchanged.
2 You're tagging a DOM element or class instance that may be removed later

A regular Map would keep el alive forever just by holding it as a key. WeakMap's reference is weak, so once nothing else points to el, both it and its cache entry become eligible for garbage collection — no manual cleanup needed.

RememberTagging something removable → WeakMap, not Map, so it can still be collected.
3 You store two different objects as keys on a plain object literal, expecting each to stay separate

Every plain-object key gets coerced to a string, so two different object keys silently collide on the exact same "[object Object]" property — whichever is written last simply overwrites the other. A common trap — candidates often assume each object key stays distinct on its own.

RememberNeed real object keys → Map, not {} — object keys always get stringified.
🌍 Real-world example ▾

A plain object is like a filing cabinet where every label gets typed in the same handwriting — two different folders can end up filed under the exact same-looking label. A Map is a cabinet where you pin the actual folder itself as the label, so nothing collides.

Scenario: a UI layer attaches state to DOM elements as they're created and removed dynamically. Storing that state in a plain object or a regular Map keeps every element alive in memory forever, even long after it's removed from the page — a WeakMap keyed on the element lets the browser reclaim the element and its state together, the moment nothing else references it.
