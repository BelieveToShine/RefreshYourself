Standard vs. Express — long and exact, or short and cheap

"Step Functions Standard vs. Express — and how do you handle retries, errors and long waits?"

Why it matters ▾
🐢 Standard
❗ ProblemA workflow that waits on a person or a slow job for hours or days can't live inside one Lambda function — the function would time out and lose its place.
✅ SolutionStandard workflows can run for up to one year, wait without running your code, run each step exactly once (unless you add Retry), and keep a visible history of every execution.
RecallStandard = long-running, exactly-once, history kept.
⚡ Express
❗ ProblemA stream of short events — thousands a second — gets slow and expensive if every one is tracked as a long-lived, billed-per-step execution.
✅ SolutionExpress workflows are built for short, high-volume runs (up to 5 minutes), billed by executions and duration — but an async run can repeat a step, so steps must be safe to run twice.
RecallExpress = short, high-volume, cheap — make steps idempotent.
🛟 Retry & Catch
❗ ProblemOne flaky call or hard failure halfway through a multi-step flow either kills the whole run or leaves things half-done.
✅ SolutionRetry re-runs a failing step with backoff. Catch sends the flow to a fallback or compensation state once retries run out — so earlier steps can be undone (the saga idea).
RecallRetry = try again. Catch = go somewhere else.
🔥 Easy interview recall

Standard → long (up to one year), exactly-once, history kept

Express → short, high-volume, cheap

Retry → try the same step again

Catch → run a different state when retries are used up

Think: Standard is the careful workflow with a paper trail. Express is the fast, cheap one for floods of short jobs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Express is just the cheaper Standard — use it everywhere." It isn't a drop-in swap: Express runs are short, and an async run can execute a step more than once. A non-idempotent step like "charge the card" can fire twice unless you design for it — so critical, long or human-in-the-loop flows belong on Standard.

🔄 Likely Follow-up

"How do you wait days for a human approval?" Use a Standard workflow: a Wait state for a fixed time, or pause the step on a task token (.waitForTaskToken, which Express does not support) until something calls back with that token. Nothing of yours runs while it waits.

🎯 Say this in the interview — the exact lines to land

"Standard is for long-running, exactly-once workflows with a full history; Express is for short, high-volume runs that can repeat a step, so steps must be idempotent. For errors I put a Retry with backoff on flaky steps and a Catch that routes to a compensation state, so a half-finished flow gets undone instead of left broken."

  • Standard → long-running, exactly-once — history kept, billed per state transition, up to one year, history kept 90 days.
  • Express → short, high-volume — async runs are at-least-once, so make steps idempotent.
  • Retry → same step again — interval, max attempts, backoff rate.
  • Catch → a different state — where the saga's compensation (refund, release) goes.
  • Wait / task token → long waits — no code of yours runs while the flow is paused.
📖 Explanation ▾

Step Functions runs a state machine: a set of steps, written in a JSON language (Amazon States Language), that the service walks through for you. The main state types are Task (do work — call a Lambda or an AWS service), Choice (branch on a condition), Parallel (run branches at the same time), Map (loop over a list) and Wait (pause for a time or until a date).

Standard vs. Express is a choice you make when you create the state machine, and it changes the guarantees, not just the speed. Standard is exactly-once; Express is at-least-once when started asynchronously and at-most-once when started synchronously.

StandardExpress
Run lengthlong — up to one yearshort — up to 5 minutes
Execution guaranteeeach step runs exactly onceasync: at-least-once (a step can repeat); sync: at-most-once
Historykept and viewable per execution (90 days)sent to CloudWatch Logs if you turn it on
Pricing basisper state transitionper execution, plus duration and memory
Best fororchestration, human approval, long waitshigh-volume event processing

Errors: put a Retry on a step to re-run it with an interval, a maximum number of attempts and a backoff rate. Add a Catch to route the flow to another state once retries are used up — that state is where a saga's compensation lives (refund the card, release the stock). Long waits: use a Wait state for a fixed time, or pause on a task token until something calls back — in a Standard workflow, nothing of yours runs while it waits.

💻 See the code ▾
JSON 
{
  "StartAt": "ChargeCard",
  "States": {
    "ChargeCard": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "charge-card", "Payload.$": "$" },
      "Next": "ShipOrder"
    },
    "ShipOrder": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "ship-order", "Payload.$": "$" },
      "Retry": [
        {
          "ErrorEquals": ["States.Timeout", "Lambda.ServiceException"],
          "IntervalSeconds": 2,
          "MaxAttempts": 3,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        { "ErrorEquals": ["States.ALL"], "Next": "RefundCard" }
      ],
      "End": true
    },
    "RefundCard": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "refund-card", "Payload.$": "$" },
      "End": true
    }
  }
}

Retry runs first: up to 3 more tries, waiting longer each time. Only when those are used up does Catch send the flow to RefundCard, which undoes the charge.

🌍 Real-world example ▾

An order flow charges the card, then ships; if shipping still fails after three retries, Catch jumps to a refund state. It runs as Standard because a human may step in and a run can last days — but a separate pipeline cleaning thousands of short events a second would run as Express.
