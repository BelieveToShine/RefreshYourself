🔥 React · Advanced · Must Know

It got slower after a feature shipped — where do you actually look?

"A React application became noticeably slower after adding a feature — how would you investigate?"

Why it matters ▾
  • Interviewers use this to see whether you actually investigate — Profiler, bundle, network — instead of jumping straight to "add more memoization."
  • Comes up any time a team ships a feature and users, or monitoring, report the app feels slower right after.
  • A common Advanced-tier opener for performance-focused rounds, especially at senior/staff level.
🔥 Easy interview recall

"Profile first — the cause is just as likely a bundle-size regression as a rendering issue. Don't optimize the part that isn't actually the bottleneck."

Think: measure before you fix — guessing wastes effort and can add risk for nothing.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"If the app feels slow, the fix is almost always more memoization." Reach for the DevTools Profiler first — the real cause is just as likely a bundle-size regression, an expensive computation running on every render, or too many components mounting at once; memoization only helps the one class of problem it's actually built for — skipping unnecessary re-renders of otherwise-cheap work — not every kind of slowdown.

🔄 Likely Follow-up

"How do caching and a CDN affect React performance, beyond the JS bundle itself?" A CDN moves static assets (JS/CSS/images) physically closer to the user, cutting network latency; proper cache headers mean a returning visitor doesn't re-download unchanged bundles at all — both matter alongside, not instead of, runtime rendering performance itself.

🎯 Say this in the interview — the exact lines to land

"I'd start with the React DevTools Profiler to see what's actually rendering and why, then check whether the new feature added a heavy dependency to the bundle or introduced a caching/network regression — measure first, and don't optimize a part of the app that isn't actually the bottleneck."

  • Profiler first → what rendered, how long, and why — never a guess.
  • Bundle regression → check if the new feature added a heavy dependency, just as likely as a render issue.
  • Large tables/lists & thousands of components → virtualization — only render what's visible.
  • Memory leaks → an effect's subscription/timer/listener with no cleanup, still holding references after the component is gone.
  • Core Web Vitals → code splitting, image optimization, less render-blocking work — bigger than React's own rendering.
  • Caching & a CDN → assets closer to the user, fewer re-downloads — helps beyond the JS bundle itself.
📖 Explanation ▾

Start with the React DevTools Profiler — record a render and look at what actually rendered, how long it took, and why — rather than guessing at a fix. A bundle-size regression is just as likely a cause as a rendering problem: a new feature can quietly pull in a heavy dependency, so it's worth checking what the feature actually added to the bundle before assuming the slowdown is a React rendering issue at all.

Once rendering is the confirmed cause, the fix depends on the shape of the problem. Large tables or lists, or thousands of components mounted at once, call for virtualization — rendering only the rows currently visible — or restructuring so everything isn't mounted simultaneously. A slow memory leak, on the other hand, usually traces back to a subscription, timer, or event listener set up inside an effect without proper cleanup — it keeps holding references long after the component that created it is gone.

Core Web Vitals — the real user-experience metrics for load speed, interactivity, and visual stability — are broader than React's own rendering: code splitting, image optimization, and reducing render-blocking work all matter here too. Caching and a CDN help beyond the JS bundle itself, moving static assets physically closer to the user and skipping re-downloads for a returning visitor. None of this is worth doing, though, until measurement actually points at it — optimizing a part of the app that isn't the real bottleneck is wasted effort that can add complexity and risk for no real benefit.

JSX 
// This is an investigation, not a syntax fix — start here:
// 1. React DevTools → Profiler tab → record a render, see what re-rendered and why
// 2. Check the bundle — did this feature pull in a new, heavy dependency?

No single line of code fixes this — the Profiler tells you which of the causes above is actually the real one before you change anything.

🌍 Real-world scenario ▾

A React app that used to feel snappy became noticeably slower right after a new feature shipped. Check the bundle first for a new heavy dependency, profile with React DevTools to see what's actually rendering and why, and check network/caching for a regression — in roughly that order, measuring before guessing at a fix.
