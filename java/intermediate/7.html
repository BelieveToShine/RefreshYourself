Iterator vs. ListIterator — forward-only, or both directions plus edits

"What can ListIterator do that a plain Iterator can't?"

Why it matters ▾
➡️ Iterator
❗ ProblemRemoving an element while looping over a collection directly (list.remove(x) inside a for-each) throws ConcurrentModificationException — the collection changed underneath the loop.
✅ SolutionAn Iterator is the universal, forward-only interface every collection exposes, and its own remove() is the one edit that's always safe mid-traversal.
RecallIterator = forward only, remove() is the only edit.
↔️ ListIterator
❗ ProblemSometimes removing isn't enough — you need to replace the current element, insert a new one mid-scan, or walk back the way you came, and a plain Iterator can't do any of that.
✅ SolutionListIterator, available only on Lists, adds backward traversal plus set() and add() at the cursor, and index-position queries.
RecallListIterator = both directions, plus set()/add().
🔥 Easy interview recall

Iterator → forward only + remove()

ListIterator → both directions + set()/add()/index

Think: every collection gives you an Iterator. Only a List gives you a ListIterator — because only a List has positions to walk back through.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A plain Iterator cannot go backwards. Backward traversal, set(), add(), and index-position queries exist only on ListIterator — and only for Lists, since those operations all depend on having a position to go back to.

🔄 Likely Follow-up

"Why is ListIterator only available on List, not Set or Map?" Backward traversal and index queries only make sense for something with a defined position — a Set has no index, and a Map's entries aren't position-addressable, so only List exposes a ListIterator.

🎯 Say this in the interview — the exact lines to land

"Iterator is the universal, forward-only interface with remove(). ListIterator, available only on Lists, adds backward traversal, set() to replace the last element returned, add() to insert mid-traversal, and index-position queries."

  • Iterator → forward only, remove() is its only edit.
  • ListIterator → adds backward traversal too.
  • set() → replace the last element returned, in place.
  • add() → insert a new element at the cursor, mid-traversal.
📖 Explanation ▾

Iterator is every collection's basic traversal contract — hasNext(), next(), and remove(). It only ever moves forward, and remove() is the only structural change it's allowed to make, which is exactly why it's safe where a direct list.remove(x) mid-loop isn't — the iterator's own bookkeeping stays in sync with the change it just made.

ListIterator extends that contract for Lists specifically, because a List has something a Set or Map doesn't: a defined position for every element. That position is what makes hasPrevious()/previous() meaningful, lets set() know exactly which element to overwrite, and lets add() know exactly where to splice a new one in.

Both are still fail-fast on anything that changes the list from outside the iterator itself — only the iterator's own remove()/set()/add() calls are safe mid-traversal; calling the list's own remove()/add() directly still throws ConcurrentModificationException.

💻 See the code ▾
☕ Java 
Iterator<String> it = names.iterator();
while (it.hasNext()) {
    if (it.next().equals("B")) {
        it.remove();              // ✅ safe — the iterator's own remove()
    }
}

Direct names.remove("B") inside this same loop would throw ConcurrentModificationException.

☕ Java 
ListIterator<String> it = names.listIterator();
while (it.hasNext()) {
    if (it.next().equals("B")) {
        it.set("B2");              // ✅ replaces "B" in place
        it.add("B3");              // ✅ inserts right after the cursor
    }
}
while (it.hasPrevious()) it.previous(); // ✅ walk back to the start

Three things a plain Iterator simply has no method for.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to remove items safely while looping over any collection

Any collection — not just a List — gives you an Iterator, and its remove() is the one edit guaranteed safe while you're mid-traversal.

RememberRemoving while scanning → use the Iterator's own remove().
2 You need to replace or insert items while scanning a List, or walk backward

Only ListIterator exposes set()/add() and backward traversal — reach for it the moment a scan needs to do more than just read and occasionally remove.

RememberReplace, insert, or backtrack → reach for ListIterator.
3 You call list.set(i, x) directly while iterating with a plain Iterator

Calling the backing list's own add()/remove() directly during a fail-fast iteration still throws ConcurrentModificationException — only the iterator's own set()/add()/remove() (via ListIterator or Iterator) are safe mid-traversal.

RememberEdit through the iterator itself, never the backing list directly.
🌍 Real-world example ▾

A plain Iterator is a one-way museum tour guide — you can skip an exhibit (remove()) but never backtrack or rearrange. A ListIterator is a guide who'll also swap a painting (set()) or hang a new one on the spot (add()), and walk you back the way you came.
