1,000 requests, same instant — is async alone enough?

"1,000 requests hit your API at the exact same time — how do you make sure it holds up?"

Why it matters ▾
🚦 Handling a Concurrent Burst
❗ ProblemA thousand requests arriving at once can exhaust the thread pool if the API blocks, or simply overwhelm a downstream database/service even if the API itself never blocks a single thread.
✅ SolutionLayer the defenses: async I/O so threads aren't tied up, a bounded concurrency gate protecting the downstream resource, horizontal scaling for a compute bottleneck, and a queue in front of genuinely slow work.
RecallAsync stops thread exhaustion. It doesn't stop the database from being overwhelmed — that's a different layer's job.
🔥 Easy interview recall

Handling a burst = "async threads, bounded downstream, scale or queue the rest."

Think: Async → no thread tied up waiting Concurrency gate → protects the DB/service behind it Scale out → when the bottleneck is compute Queue it → when the caller doesn't need the answer right now

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just make it async" alone doesn't solve a concurrency burst. Async prevents thread exhaustion, but a downstream database or third-party API can still be overwhelmed by 1,000 simultaneous calls — concurrency limiting and horizontal scaling solve a different bottleneck than async does.

🔄 Likely Follow-up

"How would you decide between scaling out and queuing the work?" If the work must complete synchronously for the caller (a real-time answer is expected), scale out; if the result can arrive later (a report, a batch job), queue it and return an acknowledgment immediately.

🎯 Say this in the interview — the exact lines to land

"I wouldn't rely on one fix — I'd layer several. The API should be async all the way down so no thread sits blocked waiting on I/O. Downstream resources get a connection pool and a bounded concurrency limit so a burst fails fast or queues instead of taking the database down. If the bottleneck is compute, I'd scale out horizontally behind a load balancer. If the work is genuinely slow and doesn't need an instant answer, I'd put a queue in front of it so the HTTP request returns fast and the work happens asynchronously."

  • Async all the way down → non-blocking I/O, no thread tied up per request.
  • Bounded concurrency → a semaphore/bulkhead protects the DB from the burst itself.
  • Scale out → horizontally, when the bottleneck is compute, not the downstream call.
  • Queue genuinely slow work → return an acknowledgment fast, process it after.
  • Decide by urgency → needs an answer now = scale; can wait = queue.
📖 Explanation ▾

Four defenses sit at different layers, and a burst of 1,000 requests usually needs more than one of them. Async I/O keeps the API's own thread pool free — a thread that's awaiting a database call or an HTTP response goes back to the pool instead of sitting blocked, so the API itself doesn't run out of threads to accept new requests. That's necessary, but it says nothing about whether the database can survive 1,000 simultaneous queries — a connection pool has a limit, and a third-party API has its own rate limit regardless of how async your own code is.

That's what a bounded concurrency gate (a semaphore, or a resilience library's bulkhead policy) is for — it caps how many calls to that downstream resource are in flight at once, so the burst either queues briefly behind the limit or fails fast with a clear error, instead of the downstream resource falling over for everyone. If the actual bottleneck is CPU/compute rather than a downstream resource, scaling out behind a load balancer is the right lever — more instances sharing the same burst. And if the work genuinely doesn't need to finish before responding (building a report, sending a batch of emails), putting a queue in front of it turns a slow synchronous request into a fast "accepted" response plus background processing.

💻 See the code ▾
C# 
private static readonly SemaphoreSlim _gate = new(20); // max 20 in flight

public async Task<Report> BuildReportAsync(int id, CancellationToken ct)
{
    await _gate.WaitAsync(ct); // ✅ queues here if 20 calls are already running
    try
    {
        return await _db.RunReportAsync(id, ct); // the DB never sees more than 20 at once
    }
    finally
    {
        _gate.Release(); // ✅ always release, even if the call throws
    }
}

The API's own threads stay async throughout; the semaphore is what actually protects the database from the burst, independent of how async the code is.

🌍 Real-world example ▾

A marketing email triggers 1,000 users to open a report page within a minute of each other. The API is fully async, so the thread pool never runs dry — but the report query is expensive, and 1,000 simultaneous queries would still take the database down. A bounded concurrency gate lets only a handful run at once; the rest wait briefly in a short, visible queue instead of the database falling over for every user at the same time.
