LINQ-to-Objects vs. LINQ-to-Entities — same syntax, completely different execution

"Same Where/Select syntax — why does it behave completely differently over a List<T> than over a DbSet<T>?"

Why it matters ▾
📋 LINQ-to-Objects
❗ ProblemYou need standard collection operations — filter, project, sort — over data already sitting in memory, with zero translation overhead.
✅ SolutionLINQ-to-Objects runs real, compiled C# delegates (Func<T>) directly against the in-memory IEnumerable<T> — your lambda executes exactly as written, as normal C#.
RecallLINQ-to-Objects = your lambda runs as real C#, in memory.
🗄️ LINQ-to-Entities
❗ ProblemThe data doesn't exist in memory yet — it's rows in a database, and pulling the whole table over just to filter it in C# would be wasteful, or impossible at scale.
✅ SolutionLINQ-to-Entities (EF Core's IQueryable<T> provider) never runs your lambda as C# — it translates the expression tree into SQL and sends that to the database, which does the filtering itself.
RecallLINQ-to-Entities = your lambda becomes SQL; it never runs as C#.
🔥 Easy interview recall

LINQ-to-Objects → runs as real, compiled C#

LINQ-to-Entities → becomes SQL, runs on the database

Think: IEnumerable<T> runs your code. IQueryable<T> translates it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The lambda inside a LINQ-to-Entities query is never executed as C#. It's only ever read as an expression tree and converted into SQL — call a method the translator doesn't recognize, and it's not "slow," it fails to translate at all (see Advanced #7).

🔄 Likely Follow-up

"So could I write Where(u => SomeComplexMethod(u)) against a DbSet<T>?" Only if the provider's translator can map that method into SQL — for an arbitrary custom method, it generally can't, so the line throws a translation exception rather than silently running the method on the server.

🎯 Say this in the interview — the exact lines to land

"LINQ-to-Objects runs your lambda as real, compiled C# directly against data already in memory. LINQ-to-Entities never executes your lambda at all — it reads it as an expression tree and translates it into SQL that runs on the database instead."

  • IEnumerable<T> + Func<T> → your C# code actually runs, line by line.
  • IQueryable<T> + Expression<Func<T>> → your C# code is read as data, then converted to SQL.
  • Filtering a List<T> → LINQ-to-Objects, always in-memory.
  • Filtering a DbSet<T> → LINQ-to-Entities, translated and run on the database.
  • An unsupported method inside a DbSet<T> query → fails to translate — it never "falls back" to running your C# method on the server.
📖 Explanation ▾

The type you're querying decides which world you're in — not the method names. List<T>, arrays, and anything typed IEnumerable<T> go through LINQ-to-Objects: Where/Select/OrderBy are extension methods taking Func<T,...>, so the compiler emits a normal compiled delegate, and the LINQ-to-Objects implementation calls it directly, element by element, in memory.

A DbSet<T> (and anything typed IQueryable<T>) goes through LINQ-to-Entities instead: the same-looking Where/Select/ OrderBy are different extension methods, defined to take Expression<Func<T,...>>, so the compiler builds an expression tree instead of a delegate. EF Core's provider walks that tree and emits SQL — the C# lambda body itself never executes.

This is also why mixing the two matters: once you call AsEnumerable() (see Advanced #6) partway through a DbSet<T> query, everything after that point switches from LINQ-to-Entities back to LINQ-to-Objects, running as real C# again.

💻 See the code ▾
C# 
List<User> users = GetCachedUsers();
var adults = users.Where(u => u.Age > 30).ToList();  // ✅ runs as compiled C#, right here

LINQ-to-Objects — the lambda is a real delegate, called for each element in memory.

C# 
DbSet<User> users = context.Users;
var adults = users.Where(u => u.Age > 30).ToList();  // lambda never runs as C# —
// EF Core reads the tree and builds: SELECT * FROM Users WHERE Age > 30

LINQ-to-Entities — the identical-looking lambda becomes translated SQL instead.

🧭 Use Cases — recognize these when they happen to you ▾
1 Filtering an in-memory List<Order> already loaded earlier

LINQ-to-Objects runs instantly as C#, no translation step and no round trip — the data is already where it needs to be.

RememberAlready in memory → LINQ-to-Objects, runs now.
2 Filtering context.Orders directly

LINQ-to-Entities turns this into part of the generated SQL — the database does the filtering, not your process.

RememberDbSet<T> → LINQ-to-Entities, becomes SQL.
3 Calling .ToList() right after context.Orders, then chaining another .Where()

The second .Where() now runs against an in-memory List<Order>, not the database — it's quietly LINQ-to-Objects, easy to miss that the switch already happened.

RememberChain a method after ToList() → you've already left LINQ-to-Entities.
🌍 Real-world example ▾

A code-review flag that's easy to miss: a method accepts a generic IEnumerable<Order> parameter, and someone passes it a DbSet<Order> directly. It compiles — IQueryable<T> implements IEnumerable<T> — but any further LINQ calls inside that method now resolve against the IEnumerable<T> extension methods, running as LINQ-to-Objects after the entire table has quietly been pulled down first.
