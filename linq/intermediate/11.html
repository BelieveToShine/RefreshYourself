Append/Prepend vs. Collection Modification — a new sequence, never a mutation

"What do Append and Prepend actually do to the original sequence?"

Why it matters ▾
➕ Append / Prepend
❗ ProblemAdding one extra element to the end or start of a sequence feels like it should just mutate the sequence in place, the way List<T>.Add() does — but a LINQ query result isn't a list, and mutating it isn't how any LINQ operator works.
✅ SolutionAppend and Prepend return a brand-new sequence with the extra element added, leaving the original source completely untouched — the exact same immutability contract every other LINQ operator already follows.
RecallAppend/Prepend = new sequence out, original never touched.
🔥 Easy interview recall

Append/Prepend = "a new sequence with one extra element — the original is never touched."

Think: Same rule as every other LINQ operator — Where doesn't delete from the source, Append doesn't add to it either.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Append/Prepend never mutate the original collection. Assuming they add in place is wrong — the original reference still points at the unchanged original sequence afterward; you have to capture the returned sequence to see the extra element at all.

🔄 Likely Follow-up

"If the source is deferred (not yet materialized), does Append also stay deferred?" Yes — Append/Prepend are themselves deferred, just like Where/Select; the extra element isn't actually produced until something enumerates the resulting sequence.

🎯 Say this in the interview — the exact lines to land

"Append and Prepend both return a brand-new sequence with the extra element added — the original source sequence is completely untouched, the same immutability contract every other LINQ operator follows."

  • Append/Prepend → return a new sequence, never mutate.
  • Original reference → still points at the unchanged source afterward.
  • Same contract as Where/Select → every LINQ operator produces, never mutates.
  • Both operators → are themselves deferred, same as the rest of the pipeline.
📖 Explanation ▾

Append and Prepend add one element to the end or the start of a sequence respectively — but like every other LINQ operator, what they hand back is a new sequence, not a change to the one you called them on. The source variable keeps pointing at exactly what it pointed at before the call; only the new variable you assign the result to sees the extra element.

This is the same immutability contract Where, Select, and OrderBy already follow — none of them touch the source, they all build and return something new. Append/Prepend aren't a special case; they just happen to be the two operators where "surely this just adds to the list" feels intuitive, because `List<T>.Add()` really does mutate in place and the names look similar.

Like most LINQ-to-Objects operators, both are deferred: calling Append on an `IEnumerable<T>` doesn't immediately build a bigger in-memory sequence, it wraps the source in an iterator that yields the original elements and then the new one, only when something actually enumerates it.

💻 See the code ▾
C# 
IEnumerable<int> source = new[] { 1, 2, 3 };

var result = source.Append(4);

Console.WriteLine(source.Count());   // ✅ 3 — source is untouched
Console.WriteLine(result.Count());   // ✅ 4 — result is the new sequence

source and result are two different sequences after the call.

C# 
var headers = new[] { "Id", "Name" };

var withLabel = headers.Prepend("Row #");
// ✅ "Row #", "Id", "Name" — a new sequence, headers itself still has 2 items

Prepend works the same way, just adding at the front instead.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to add a header row to a sequence just before exporting it

Exporting a CSV from a query result without a dedicated header row in the data — Prepend("Id,Name,Total") builds the header-plus-data sequence without touching or copying the underlying query result itself.

RememberOne extra row, no mutation needed → Prepend/Append.
2 You need a sentinel/terminator value added only for one specific consumer

A shared sequence is used by multiple consumers, but only one needs a trailing "end of batch" marker — Append adds it for just that one caller without affecting the sequence every other caller sees.

RememberShared source, one-off addition → immutability means other callers are never affected.
3 You call Append and expect the original list to now have the extra item

Calling list.Append(x); as a statement, without capturing the return value, silently does nothing useful — the new sequence is created and then immediately discarded, and list itself never changes.

RememberForgetting to assign the result → the extra element quietly vanishes.
🌍 Real-world example ▾

A search-results pipeline needs a "no results found" placeholder appended only when the underlying query comes back empty, without ever touching the cached query result other pages of the app also read from. Append fits exactly: it hands back a new sequence for this one caller, and the cached original stays exactly as every other reader of it expects.
