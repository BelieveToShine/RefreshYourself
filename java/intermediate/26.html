Annotations — metadata the compiler drops, or code reads at runtime?

"What's the relationship between an annotation and reflection?"

Why it matters ▾
🏷️ Annotations + Reflection
❗ ProblemA framework (Spring's DI container, a JPA ORM, JUnit) needs to know things about your classes — which field to inject, which column a property maps to, which method is a test — without you writing that wiring logic by hand for every class.
✅ SolutionAn annotation attaches that metadata directly on the code; reflection (java.lang.reflect) lets the framework read it and inspect/invoke classes, methods, and fields at runtime, deciding behavior the compiler never sees.
RecallAnnotation = metadata. Reflection = how a framework reads it and acts, at runtime.
🔥 Easy interview recall

Annotation + Reflection = "metadata on code, read and acted on at runtime."

Think: @Override → compiler only, then discarded. @Entity → a framework reads it via reflection to decide what to do.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An annotation has no behavior of its own. Writing @Transactional on a method does nothing by itself — it's inert metadata until something (a reflection-based framework, an annotation processor) actually reads it and acts; without a reader, the annotation is just a label nobody looked at.

🔄 Likely Follow-up

"Is reading annotations via reflection expensive?" Yes, noticeably more than a direct method call — reflective lookups and invocations carry real overhead, which is exactly why frameworks cache that lookup once instead of repeating it; the performance trade-off itself is a deeper, Advanced-tier topic — this page is just the mechanism.

🎯 Say this in the interview — the exact lines to land

"An annotation attaches metadata to code with no behavior of its own — some are only read by the compiler, like @Override and @Deprecated, while others are preserved into the compiled class and read at runtime through reflection, which is how frameworks like dependency injection containers and ORMs decide behavior the compiler never sees."

  • Annotation → inert metadata, does nothing by itself.
  • Compiler-only annotations → @Override, @Deprecated, checked then discarded.
  • Runtime-retained annotations → read via java.lang.reflect, the mechanism behind DI/ORM "magic."
  • Reflection → bypasses normal compile-time checks, inspects and invokes dynamically.
📖 Explanation ▾

Every annotation declares its own @Retention policy, and that policy is what decides whether reflection can ever see it. RetentionPolicy.SOURCE annotations (like a lint hint) don't even survive compilation. CLASS is kept in the .class file but not loaded into the running JVM's reflective view. Only RUNTIME-retained annotations — like Spring's @Autowired or JPA's @Entity — are the ones a framework can actually read back with Class.isAnnotationPresent() or getAnnotation().

Reflection is the java.lang.reflect API that lets code inspect a class's structure and invoke its members dynamically, bypassing the normal compile-time type checking a direct call would go through. A dependency injection container walks a class's fields looking for @Autowired, then uses reflection to set each matching field — logic the compiler had no part in and never sees directly.

💻 See the code ▾
Java 
@Retention(RetentionPolicy.RUNTIME)  // kept for reflection to find
@Target(ElementType.METHOD)
interface LogExecutionTime {}

class OrderService {
    @LogExecutionTime
    void placeOrder() { /* ... */ }
}

The annotation by itself does nothing — placing it changes nothing at runtime yet.

Java 
for (Method m : OrderService.class.getDeclaredMethods()) {
    if (m.isAnnotationPresent(LogExecutionTime.class)) {
        wrapWithTiming(m);  // ✅ reflection is what actually does something
    }
}

This loop, reading the annotation via reflection, is the code that gives it meaning.

🧭 Use Cases — recognize these when they happen to you ▾
1 Overriding a method and marking it @Override

@Override has SOURCE retention — the compiler checks the method actually overrides a superclass method, then the annotation is gone; no runtime code ever sees it, and none needs to.

Remember@Override never reaches reflection — it's compiler-only.
2 A DI container injecting a field marked @Autowired

A DI container scans a class's fields via reflection, finds @Autowired, and sets the field to a matching bean — behavior entirely decided at runtime, driven by metadata the compiler never interpreted.

RememberMost framework "magic" is reflection reading a runtime annotation.
3 Writing a custom annotation and expecting it to "just work"

Defining a brand-new annotation and sprinkling it on methods does nothing on its own — without a reflection-based reader (your own code, or a framework) looking for it, the annotation is inert metadata forever.

RememberAn annotation with no reader is just a comment with extra syntax.
🌍 Real-world example ▾

An annotation is like a sticky note on a form. The compiler glances at some notes and throws them away once it's satisfied — @Override works this way. Other notes are stapled permanently to the form, and a clerk (a framework, reading via reflection) looks at them later to decide what to do with the form. The note itself never does anything — it only matters the moment someone actually reads it.
