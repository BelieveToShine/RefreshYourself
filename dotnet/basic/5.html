Filters — hooks around an action, not around the whole request

"What are filters in ASP.NET Core MVC, and how are they different from middleware?"

Why it matters ▾
🪝 Filters
❗ ProblemWithout a shared hook point, the same before/after logic would be pasted into every action method by hand.
✅ SolutionFilters are hooks that wrap action execution — before it, after it, or around an exception — so that logic lives in one place.
RecallFilters = hooks around an action.
🔥 Easy interview recall

Authorization filter → runs first, can stop the request

Action filter → before and after the action method

Exception filter → handles a throw from the action

Think: Filters wrap one action, inside MVC. Middleware wraps the whole request.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming filters see every request, or that CORS is one of them. Filters only wrap MVC actions, so static files and other non-MVC requests never reach one. CORS is middleware plus a browser rule, covered on its own page: CORS in Web API.

🔄 Likely Follow-up

"What's the difference between a filter and middleware?" Middleware wraps the whole request, before MVC has even picked an action. A filter runs inside MVC, around one action, and can see action details like its arguments and result. MVC-Specific Filters goes deeper.

🎯 Say this in the interview — the exact lines to land

"Filters are hooks that run around an action — before it, after it, or when it throws. There are authorization, resource, action, exception, and result filters, and they only run for MVC endpoints, unlike middleware which wraps every request. HTTPS redirection and logging aren't filters, and CORS has its own page."

  • Filters → hooks around one action — one place for logic you would otherwise paste into every method.
  • Types → authorization, resource, action, exception, result — authorization runs first.
  • vs. middleware → filters live inside MVC — middleware also covers non-MVC requests.
  • Not filters → CORS, HTTPS, logging — see CORS, HTTPS & HSTS, and Logging.
📖 Explanation ▾

Filters are the umbrella name for a hook that runs at a specific point around action execution. Instead of repeating the same before/after code in every action, you write it once as a filter and attach it to an action, a controller, or all actions.

There are five kinds: authorization, resource, action, exception, and result filters. Authorization filters run first and can short-circuit the request; action filters run before and after the action method; exception filters handle an unhandled exception from the action. The full order and the differences are on MVC-Specific Filters.

Filters are not middleware. Middleware wraps the whole pipeline and only knows about HttpContext; filters run inside MVC and can see what MVC knows about the action. This page used to bundle three other topics, which now have their own pages: CORS, HTTPS Redirection & HSTS, and Logging.

💻 See the code ▾
C# 
public class LogActionFilter : IActionFilter
{
    public void OnActionExecuting(ActionExecutingContext ctx)
        // runs BEFORE the action
        => Console.WriteLine("before");

    public void OnActionExecuted(ActionExecutedContext ctx)
        // runs AFTER the action
        => Console.WriteLine("after");
}

IActionFilter is one filter type among several — authorization and exception filters have their own interfaces with the same idea.

C# 
builder.Services.AddControllers(o => o.Filters.Add<LogActionFilter>());   // ✅ every action

Registered globally here; you can also attach a filter to a single controller or action with an attribute.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need logic that also covers static files and non-MVC endpoints

A static file never reaches an MVC action, so no filter runs for it. Logic that has to cover every request belongs in middleware; filters are for code tied to controller actions.

RememberMust cover every request → middleware, not a filter.
2 You keep pasting the same "log before / log after" line into every action method

One IActionFilter applied where it's needed runs its OnActionExecuting/OnActionExecuted hooks around any action it's attached to — the same before/after logic, written once, instead of copied into Action A, Action B, and every action after that.

RememberRepeated before/after code → that's a filter, not a copy-paste.
🌍 Real-world example ▾

Checkpoints on one street vs. gates on the whole road. Filters are the checkpoints at one building's door — they only matter for visitors going into that building (an action) — while middleware is the series of gates every vehicle on the road passes, whichever building it is headed for.
