ref() vs. reactive() — one wraps a box, the other wraps the object itself

"What's the difference between ref() and reactive()?"

Why it matters ▾
📦 ref()
❗ ProblemA plain number or string has no way to notify Vue when it changes — reassigning let count = 5 is invisible to the framework.
✅ Solutionref() wraps any value — primitive or object — in a small object with a .value property, so reassigning .value is exactly what Vue tracks.
Recallref() = a box; reassign .value, Vue sees it.
🧱 reactive()
❗ ProblemWriting .value everywhere for an object with many fields (a form, a settings object) is noisy when each field is naturally accessed by name.
✅ Solutionreactive() wraps an object directly in a Proxy — its properties are tracked with no wrapper, but only objects/arrays work, and reassigning the whole variable breaks reactivity.
Recallreactive() = the object itself, Proxy-wrapped — no .value, no primitives.
🔥 Easy interview recall

ref() → any value, needs .value

reactive() → objects only, no .value

Think: ref is a labeled box you reassign. reactive is the object itself, watched directly.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Destructuring a reactive() object's properties into plain variables. They lose their reactive connection instantly — you've copied out a plain value, not a live reference.

🔄 Likely Follow-up

"Why does the template auto-unwrap .value but script code doesn't?" The template compiler automatically unwraps top-level refs for convenience; raw script code has no such compiler magic, so .value is always required there.

🎯 Say this in the interview — the exact lines to land

"ref() wraps any value in an object with a .value property, and reassigning .value is tracked. reactive() wraps an object directly in a Proxy — no .value needed, but it only works on objects and arrays, and reassigning the whole variable breaks reactivity."

  • ref() → works on any value, always needs .value in script code.
  • reactive() → objects and arrays only, properties accessed directly.
  • Destructuring a reactive() object breaks reactivity on those copied-out values.
  • Templates auto-unwrap top-level refs — script code never does.
📖 Explanation ▾

ref() solves a basic problem: a plain number or string can't notify anything when it changes, because reassignment just points a variable at a new value. Wrapping it in an object — { value: 0 } — gives Vue something stable to watch; reading or writing .value is what Vue actually tracks.

reactive() skips the wrapper for objects: it returns a Proxy around the object itself, so property access (state.count) is already being watched with no extra syntax. That convenience is also its limit — a Proxy can only wrap an object, so reactive() can't be used on a primitive like a number or string at all.

Both share the same failure mode: reassigning the whole variable — count = ref(5), or state = reactive({...}) — replaces the tracked box/Proxy with a brand-new one, severing the connection the rest of the component still has to the old one. The fix either way is the same: mutate what's inside, never swap the container itself.

💻 See the code ▾
Vue 
const count = ref(0);
count.value++;              // ✅ tracked
console.log(count.value);   // 1 — always .value in script

ref() works the same way whether the wrapped value is a number, a string, or an object.

Vue 
const state = reactive({ count: 0 });
state.count++;               // ✅ tracked — no .value
const { count } = state;   // ❌ count is now a plain, disconnected number

Destructuring copies the value out at that instant — further changes to state.count never touch the local count variable.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're tracking a single primitive value — a count, a flag, a string

A single flag, count, or string has no properties to wrap in a Proxy — ref() is the only one of the two that even works here. This is the #1 scenario you'll actually run into.

RememberA single primitive → ref(), reactive() can't wrap it.
2 You're modeling a multi-field object — a form, settings, filters

A form object with several fields reads more naturally as form.name, form.email with reactive() than as form.value.name with ref() — though both would technically work.

RememberMulti-field object → reactive() reads more naturally, no .value noise.
3 You pull fields out of a reactive object to pass them around

The destructured count is a snapshot, not a live connection — later changes to state.count never update it. Vue's own toRefs() exists specifically to destructure a reactive object while keeping each field reactive.

RememberNeed to destructure safely → toRefs(), not plain destructuring.
🌍 Real-world example ▾

Think of a labeled parcel locker vs. an open shelf. ref() is the locker — you always go through its door (.value) to see what's inside, even if you swap the item. reactive() is the open shelf — you reach straight for an item by name, but you can't put a locker's door on the shelf itself; it only holds objects.
