JWT isn't security — a valid token can still ask for someone else's data

Your API has JWT auth — is it secure? What else do you guard against?

Why it matters ▾
🎯 Object-level check
❗ ProblemA logged-in user changes /orders/41 to /orders/42 and reads someone else's order — the token is valid, so authentication passes.
✅ SolutionThe API checks, on every object it loads, that this caller is allowed to touch this object (BOLA / IDOR protection).
RecallValid token ≠ allowed on this object.
🧱 Guard the rest
❗ ProblemJunk or hostile input, over-sized responses, request floods, plain-HTTP traffic and secrets in error messages all get past a valid token.
✅ SolutionValidate input, return only needed fields, rate-limit, force HTTPS, keep tokens least-privilege, and send generic errors.
RecallAuth = who. The rest = what, how much, how safe.
🕵️ 404 vs. 403
❗ ProblemAnswering 403 for "exists but not yours" tells an attacker which ids are real.
✅ SolutionReturn 404 when existence itself is sensitive; use 403 when the resource is publicly known and just restricted.
Recall404 hides it. 403 admits it.
🔥 Easy interview recall

Authentication → who is calling

Object check → is it theirs?

Think: Valid token + someone else's id → BOLA, stopped at the object check Hide that it exists → 404 · admit it → 403

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The token is valid, so the request is fine." A valid token only proves who is calling — the API must still check that this caller may touch this specific object, and skipping that is exactly how BOLA / IDOR happens.

🔄 Likely Follow-up

"If an object exists but isn't the caller's, is it 403 or 404?" Depends on whether its existence is itself secret — 404 hides it (other users' orders, other tenants), 403 is fine when the resource is publicly known and just restricted. Pick one rule per resource type and apply it everywhere, since mixed answers leak the difference.

🎯 Say this in the interview — the exact lines to land

"Authentication only tells me who is calling. I also check that this caller may touch this specific object — that's BOLA, the most common API flaw — then validate input, return only the fields needed, rate-limit, enforce HTTPS, keep tokens least-privilege, and never leak internals in errors. When an object isn't theirs, I return 404 if its existence is sensitive and 403 if it isn't."

  • Object-level check → verify every id against the caller, not just the token.
  • Changing the id in the URL → must never reach someone else's data (BOLA / IDOR).
  • Validate input, return a DTO → reject bad data in, send only needed fields out.
  • Rate limit, HTTPS, least privilege → guard the rest of the request, keep secrets out of errors.
  • 404 hides, 403 admits → pick one rule and stay consistent.
📖 Explanation ▾

Authentication answers one question: who is calling? It says nothing about which objects that caller may touch. The most common API flaw lives exactly there — BOLA (broken object-level authorization, also called IDOR). The caller is logged in, changes 42 to 43 in the URL, and the API returns someone else's record because it only checked the token. OWASP's API Security Top 10 lists it first. The fix is an ownership check on every object load, not a bigger login. Going async doesn't change any of this — see Async APIs.

Around that check sit the other guards, each stopping a different thing: validate input so bad data never reaches business logic, return a response DTO instead of the raw entity so extra fields don't leak, rate-limit so one caller can't flood you, HTTPS only so nothing travels readable, least privilege so a token unlocks only what that caller needs, and no secrets or stack traces in errors or logs. None replaces another.

404 vs. 403 is the information-leakage choice. If an object exists but isn't the caller's, 403 says "it's there, you can't have it" — an attacker can walk ids and learn which ones exist. Answering 404 for both "missing" and "not yours" hides that. Use 404 where existence is itself sensitive; 403 is fine for publicly known, restricted things like an admin endpoint.

💻 See the code ▾
C# 
[Authorize]
[HttpGet("orders/{id}")]
public async Task<IActionResult> GetOrder(int id)
{
    var order = await _db.Orders.FindAsync(id);
    return order is null ? NotFound() : Ok(order);
    // ❌ any logged-in user can read ANY order id (BOLA)
}

[Authorize] only proved who is calling — nothing checked whose order this is.

C# 
var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);   // from the token
var order = await _db.Orders
    .FirstOrDefaultAsync(o => o.Id == id && o.OwnerId == userId);   // ✅ owner check in the query
return order is null ? NotFound() : Ok(order);   // ✅ missing and not-yours look identical

One query does both jobs: it finds the order and proves it belongs to the caller, so the answer is 404 either way.

C# 
var order = await _db.Orders.FindAsync(id);
if (order is null) return NotFound();
var result = await _auth.AuthorizeAsync(User, order, "OrderOwner");
if (!result.Succeeded) return Forbid();   // 403 — admits the order exists

The resource-based version (IAuthorizationService) answers 403 — fine when existence isn't secret.

🧭 Use Cases — recognize these when they happen to you ▾
1 A logged-in user edits the id in the URL and gets someone else's record

Nothing is wrong with the login — the hole is that the handler never asks whose order 42 is. Put the owner check in the query (or a resource-based policy) so every id is tested against the caller.

RememberCheck the object, not just the token.
2 An endpoint returns the whole database entity, including fields the caller never needed

Returning the raw entity can expose internal ids, flags or other people's data the screen never showed. Map to a response DTO that lists exactly the fields the client should see.

RememberReturn a DTO, not the entity.
3 A forbidden object returns 403 while a missing one returns 404

An attacker can try ids one by one and sort them into "real" and "not real" just from the status code. Where existence is sensitive, give the same answer for missing and not-yours. A classic follow-up when you mention BOLA.

RememberSame answer for "missing" and "not yours" when existence is sensitive.
🌍 Real-world example ▾

A support-ticket API logs customers in fine, yet one customer changes /tickets/1001 to /tickets/1002 and reads another company's ticket. The token was valid — the query just never scoped by tenant. The fix is to filter by the caller's tenant in the query and answer 404 when nothing matches. See JWT & Refresh Tokens for the token side, HTTP Status Codes for 403 vs. 404, Rate Limiting for abuse control, and Authorization Policies & Claims for the policy side.
