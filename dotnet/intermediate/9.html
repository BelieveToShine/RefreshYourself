Razor & Routing — C# wearing an HTML costume

"What is Razor syntax actually doing when it mixes C# and HTML?"

Why it matters ▾
  • Interviewers use this to check you know Razor is a real, compiled view engine — not a simple string-templating trick.
  • Comes up the moment you're debugging a Razor page that throws a compile error "inside HTML," which only makes sense once you know it's really C#.
  • The routing half is a common follow-up: knowing exactly when an MVC action needs its own [Route] versus relying on the shared convention.
🔥 Easy interview recall

Razor = "C# and HTML, compiled into one class."

Think: @ → switches into C# mid-markup [Route] → pinned to one action shared template → many actions, matched by name

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Mixing attribute and conventional routing without a rule isn't harmless. When some actions only work through their own [Route] and others only through the shared convention, the app's real URL surface can't be read from either source alone — pick one as the default and use the other only for genuine exceptions.

🔄 Likely Follow-up

"Can Razor syntax do anything C# in a .cs file can't?" No — it's genuinely just C# with a templating-friendly syntax for mixing in markup. Anything written in Razor could be hand-written as a C# method that builds the same string; Razor just makes it far more readable.

🎯 Say this in the interview — the exact lines to land

"Razor isn't a separate templating language — the .cshtml file is parsed into a real C# class, a RazorPage subclass, at compile time or first use, and running that generated class is what actually produces the HTML. For MVC controllers, attribute routing pins an explicit URL directly on an action, while conventional routing registers one shared template that maps every action without its own attribute route, by name."

  • Razor → compiles to a real C# class, not a bolted-on template engine.
  • @ → switches from markup into C# for expressions and statements.
  • [Route] on an action → explicit URL, independent of the class's name.
  • Conventional route in Program.cs → one shared template, matched by name.
  • Mixing both with no rule → hides the app's real URL surface.
📖 Explanation ▾

Razor is a templating syntax that lets C# live directly inside an HTML file. Think of it less as a translator standing between two languages, and more as one language wearing two hats: everything not preceded by @ is literal text to output as-is, and everything after @ — @Model.Name, @if(...) { }, @foreach(...) { } — is compiled exactly like any other C#.

The mechanics: at compile time (or on first use, for a page compiled on demand), the Razor engine parses the .cshtml file and generates a real class — a RazorPage subclass — whose generated method mixes calls that write literal markup with calls that evaluate your C# expressions and write their results. The page you see is produced by running that generated class, the same as any other compiled code.

Routing is a separate concern that sits on top of this, specific to how an MVC controller gets reached at all. Attribute routing puts [Route] directly on the controller or action, so the URL is explicit and doesn't depend on naming. Conventional routing instead registers one template — typically in Program.cs, {controller=Home}/{action=Index}/{id?} — once, and every action without its own attribute route gets a URL by matching that template's placeholders against the controller/action name.

💻 See the code ▾
C# 
<h1>Hello, @Model.Name</h1>   // @ switches into C#

@if (Model.IsAdmin)
{
    <span>Admin</span>        // markup, back inside the block
}

@foreach (var item in Model.Items)
{
    <li>@item.Title</li>      // @ again, once per iteration
}

Every @ is a doorway into real C# — everything else on the line is HTML being written out as-is.

C# 
[Route("orders/{id}")]
public IActionResult GetById(int id) { ... }
// ✅ this exact URL, no matter what the class is named

Renaming OrdersController never changes this URL — the route is pinned to the action itself.

C# 
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");
// one template feeds every action without its own [Route]

HomeController.Index() and BlogController.List() both get a URL from this one line — matched by name, not by declaration.

🌍 Real-world example ▾

A new ReportsController.Generate() action 404s even though it looks just like every other controller in the app. The app mixes attribute and conventional routing with no consistent rule — most controllers rely on the shared default, but a few older ones were given their own [Route] for reasons nobody documented, and this one needed one too. The fix isn't picking a "correct" style — it's picking one as the app's default and treating the other as a deliberate, documented exception, never an accident.
