Expression Trees — code as data, not code that runs

"What is an expression tree, and how is it different from a compiled delegate?"

Why it matters ▾
  • The exact mechanism that lets db.People.Where(x => x.Age > 18) turn into a SQL WHERE clause instead of loading the whole table.
  • A reliable way to separate "has used LINQ" from "understands how EF Core actually works" in an interview.
  • Comes up any time a generic method needs to inspect the logic it's handed, not just run it — LINQ providers, rules engines, dynamic filters.
🔥 Easy interview recall

Func<T,bool> → compiled code — run it, can't read it

Expression<Func<T,bool>> → a tree — read it, walk it, translate it

Think: Func is a sealed black box you can only run. Expression is a recipe you can read line by line.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Expression<Func<T,bool>> is not just a slower Func<T,bool>. It isn't compiled to runnable code at all — it's a data structure describing the logic, which is exactly what lets EF Core translate it into SQL instead of executing it.

🔄 Likely Follow-up

"Why does EF Core specifically need expression trees instead of accepting a Func<T,bool>?" A compiled Func can only be run, never read — EF Core has to inspect your LINQ predicate's actual logic to translate it into SQL, and only an expression tree exposes that logic for it to walk.

🎯 Say this in the interview — the exact lines to land

"An expression tree is a data structure that represents code as an inspectable tree of nodes, instead of compiling it into code that runs. A compiled delegate like Func<T,bool> can only be invoked — an Expression<Func<T,bool>> can be walked and translated, which is exactly what LINQ providers like EF Core do to turn it into SQL."

  • Func<T,bool> → compiles to IL, runs in memory, can never be inspected.
  • Expression<Func<T,bool>> → compiles to a tree of nodes instead of IL.
  • EF Core walks that tree to generate SQL — something it could never do with a plain Func.
  • Reach for an Expression<T> parameter whenever code must be translated, not just executed — LINQ providers, rules engines, dynamic queries.
📖 Explanation ▾

Write x => x.Age > 18 and assign it to a Func<T,bool>, and the compiler emits ordinary IL — a method you can call and nothing else. Assign that exact same lambda to an Expression<Func<T,bool>> instead, and the compiler builds something completely different: a tree of Expression objects — a BinaryExpression for >, with a MemberExpression for x.Age and a ConstantExpression for 18 as its children.

That tree is just data — properties you can read, children you can walk, no different from any other object graph. A LINQ provider like EF Core walks it, matches each node against its own SQL vocabulary, and produces WHERE Age > 18. A Func<T,bool> never gets this chance, because by the time you hold one, the logic is already gone — flattened into IL with nothing left to read.

💻 See the code ▾
C# 
Func<Person, bool> f = x => x.Age > 18;
bool isAdult = f(person);        // ✅ runs — that's all a Func can do

Expression<Func<Person, bool>> expr = x => x.Age > 18;
var body = (BinaryExpression)expr.Body;
Console.WriteLine(body.NodeType);   // ✅ prints "GreaterThan" — the tree can be read

Same lambda, two assignments — only the Expression version leaves anything behind to inspect.

C# 
IQueryable<Person> q = db.People.Where(x => x.Age > 18);
// ✅ EF Core receives an Expression tree — translates it to WHERE Age > 18 in SQL

IEnumerable<Person> list = people.Where(x => x.Age > 18);
// ⚠️ Here .Where() takes a Func — every row is already loaded and filtered in memory

IQueryable<T>'s Where takes an Expression; IEnumerable<T>'s Where takes a plain Func — the method signature alone decides whether your filter runs in the database or in memory.

C# 
string ToSql(Expression e) => e switch
{
    BinaryExpression b => $"{ToSql(b.Left)} > {ToSql(b.Right)}",  // the ">" node
    MemberExpression m => m.Member.Name,                    // "x.Age" node → "Age"
    ConstantExpression c => c.Value.ToString(),            // "18" node
    _ => throw new NotSupportedException()
};                                       // a tiny sketch of what EF Core does at scale

This is the shape of what EF Core actually does — walk the tree node by node and emit the matching SQL fragment for each one.

🌍 Real-world example ▾

Your repository layer wants one generic filter method. Give it GetFiltered(Expression<Func<T,bool>> predicate) instead of GetFiltered(Func<T,bool> predicate), and EF Core can fold that predicate straight into the SQL query — only the matching rows ever leave the database. Take a plain Func instead, and every row has to be pulled into memory first, because there's nothing left in a Func for EF Core to translate.
