A composable — just a function, or something more?

"What's a composable, and how is it different from a plain utility function?"

Why it matters ▾
🧩 Composables
❗ ProblemReactive, stateful logic — tracking mouse position, a debounced search input, a countdown timer — gets duplicated across every component that needs it, or gets copy-pasted and slowly drifts out of sync.
✅ SolutionA composable is a plain function (conventionally named useX()) that uses ref, computed, watch, and lifecycle hooks internally and returns reactive state plus functions — write the logic once, call it from as many components as you need.
RecallComposable = a function that packages reusable, stateful reactive logic.
🔥 Easy interview recall

Composable = "a function that packages reusable reactive logic."

Think: useMouse() called twice → two separate ref pairs, each its own instance.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Returning a reactive() object directly from a composable, instead of individual refs. A consuming component that destructures it loses reactivity the exact same way a plain reactive object does — return toRefs(state) or individual refs instead.

🔄 Likely Follow-up

"How is this different from a plain utility function?" A composable can hold its own reactive state and tie into lifecycle hooks — registering and cleaning up an event listener in onMounted/onUnmounted, for example — a plain utility function is stateless and has no lifecycle awareness at all.

🎯 Say this in the interview — the exact lines to land

"A composable is a plain function, named useX() by convention, that uses ref, computed, watch, and lifecycle hooks internally and returns reactive state plus functions — it's the Vue 3 way to extract and reuse stateful logic across components."

  • useX() naming → convention, not enforced, but expected everywhere.
  • Holds → its own reactive state, unlike a stateless utility function.
  • Ties into → lifecycle hooks, like onMounted/onUnmounted for cleanup.
  • Return → refs or toRefs(), never a bare reactive() object.
📖 Explanation ▾

A composable is nothing more exotic than a regular JavaScript function — what makes it a composable specifically is that it uses Composition API primitives (ref, computed, watch, onMounted) inside its own body, and returns the pieces a component needs to use. Calling it is exactly like calling any other function; the Composition API primitives it uses internally are what give it reactive superpowers a plain function doesn't have.

Each call creates a completely fresh, independent set of state — useMouse() called from two different components produces two separate ref pairs that never interfere with each other, the same way calling any function twice gives you two separate local variables.

💻 See the code ▾
Vue 
// useMouse.js
export function useMouse() {
  const x = ref(0)
  const y = ref(0)

  function update(e) { x.value = e.pageX; y.value = e.pageY }

  onMounted(() => window.addEventListener('mousemove', update))
  onUnmounted(() => window.removeEventListener('mousemove', update))

  return { x, y }        // ✅ returns refs, safe to destructure
}

The event listener is registered and cleaned up inside the composable itself — every caller gets that for free.

Vue 
<!-- any component -->
<script setup>
import { useMouse } from './useMouse'
const { x, y } = useMouse()   // ✅ independent instance, every time
</script>

Two components importing the same composable still get two separate x/y pairs.

🧭 Use Cases — recognize these when they happen to you ▾
1 The same "loading / error / data" fetch pattern shows up in five different components

Pulling the loading/error/data refs and the fetch function into a useFetch(url) composable means every component that needs it just calls the function — fixing a bug once fixes it everywhere it's used.

RememberSame stateful logic in 2+ places → that's a composable waiting to be extracted.
2 A composable returns reactive(state) directly and callers destructure it

This is exactly the previous page's destructure caveat, now hiding one layer behind a function call — the fix is the same: the composable should return toRefs(state) or individual refs, not the bare reactive object.

RememberA composable's return value gets destructured constantly — never return a bare reactive().
🌍 Real-world example ▾

A dashboard with a dozen widgets, each polling its own API endpoint on an interval. A single usePolling(url, intervalMs) composable handles the setInterval/cleanup and returns the latest data — every widget calls it with its own URL and gets its own independent polling loop, with the setup-and-teardown logic written exactly once.
