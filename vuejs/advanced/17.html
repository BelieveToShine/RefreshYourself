A component re-renders too often — chase the reference, not the values

"A component is re-rendering far more often than you'd expect — how do you track down why?"

Why it matters ▾
🔁 Unexpected Re-Renders
❗ ProblemA component re-renders far more than the data flowing into it seems to justify — the usual culprits are an inline object/array literal created fresh every render, or a watcher with no real dependency boundary, and none of them throw an error to point at.
✅ SolutionUse Vue DevTools' render tracking to confirm which component re-renders and how often, then check whether the "same-looking" dependency that triggered it is actually a brand-new object/array reference each time.
RecallSame values, different reference — that's almost always the actual trigger.
🔥 Easy interview recall

Unexpected re-render = "a dependency that LOOKS the same but is a NEW reference every render."

Think: {a:1} is never === to last render's {a:1}, even though every value inside it matches.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming "same values means same reference." A freshly-created {a: 1} object literal is never === to a previous render's {a: 1}, even though they look identical.

🔄 Likely Follow-up

"What's the actual fix once you've found the inline object literal?" Hoist it into a computed — cached, and only produces a new reference when its own dependencies actually change — or define it once outside the render path entirely if it's truly static.

🎯 Say this in the interview — the exact lines to land

"I'd use Vue DevTools' render tracking to confirm which component is re-rendering and on what, then look for a dependency that looks identical between renders but is actually a new object, array, or inline literal reference each time — an inline prop object, a method called in the template that returns a new array, or a watcher with too wide a dependency boundary are the usual suspects."

  • Vue DevTools render tracking → confirms which component re-renders and how often.
  • Inline object/array literal prop → a new reference every render, even with identical values.
  • Fix → hoist it into a `computed`, or define it once outside the render path.
  • Watcher with no clear dependency boundary → fires on changes wider than it actually needs.
📖 Explanation ▾

Start with Vue DevTools' render tracking (the component inspector panel), which can flag exactly which component re-rendered and, often, which reactive dependency changed to cause it. Once you know the component, the real question is never "did the value change" — it's "did the reference change," because that's what Vue's reactivity and prop-diffing actually compare for objects and arrays.

The classic case: a computed or method called directly inside the template (:config="getConfig()") that builds and returns a new object or array literal on every single call. Even if every property inside it is identical to last render's, it's a brand-new value in memory — the child receiving it as a prop sees a "different" reference and re-renders, with nothing in the values themselves actually having changed.

A prop passed a new inline object literal directly in the parent's template (:config="{a: 1}") is the same bug from the other direction — the parent recreates that literal every time it renders, regardless of whether a ever changes. A watcher with no real dependency boundary — watching a whole object instead of the one field it actually cares about — fires on changes to parts of that object the watcher never needed to react to at all.

💻 See the code ▾
Vue 
<template>
  <Child :config="{ a: 1 }" />  // ❌ a NEW object every single render
</template>

Even though { a: 1 } never changes in value, it's a different reference every time the parent renders — the child re-renders too.

Vue 
<script setup>
import { computed } from 'vue';

const config = computed(() => ({ a: 1 })); // ✅ stable reference, recomputed only if deps change
</script>
<template>
  <Child :config="config" />
</template>

A computed caches its result — the child gets the same object reference across renders until a real dependency actually changes.

🧭 Use Cases — recognize these when they happen to you ▾
1 An inline object/array literal is passed as a prop, directly in the parent's template

The parent rebuilds that literal fresh every render, so the child always receives a "new" prop reference, regardless of whether its contents ever change. This is the #1 scenario you'll actually run into.

RememberInline literal prop → a new reference, every single render.
2 A computed or method called inline in the template returns a new array/object every call

A plain method invoked in the template runs again on every render and builds a brand-new array or object each time — unlike a computed, it has no cache to return a stable reference from.

RememberA template-called method has no cache — every call is a fresh value.
3 A watcher has no real dependency boundary — it watches a whole object instead of one field

Watching an entire reactive object fires the callback for changes to any field on it, not just the one the watcher actually cares about — a candidate might assume "it's watching, so it must be precise," when the boundary is really the whole object.

RememberWatch the specific field, not the whole object, unless you mean to.
🌍 Real-world example ▾

A product-list page feels janky, and a quick check in Vue DevTools shows a card component re-rendering on every scroll event, not just when its own data changes. The parent passes a filter object built inline in the template — hoisting that into a computed gives every card a stable reference again, and the unnecessary re-renders stop.
