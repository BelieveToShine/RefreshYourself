Richardson levels 0–3 — does your API really need HATEOAS?

"What are the Richardson maturity levels, and does your API need HATEOAS?"

Why it matters ▾
🪜 Richardson levels
❗ Problem"Is your API RESTful?" sounds like a yes-or-no question, but APIs range from one URL that takes every call to fully link-driven — so a plain "yes" tells the interviewer nothing.
✅ SolutionThe Richardson model names four steps (one endpoint, resources, proper verbs and codes, hypermedia links), so you can say exactly how far an API goes and why it stops there.
RecallFour levels — most real APIs stop at level 2.
🔥 Easy interview recall

Level 0 → one URL

Level 1 → resources

Level 2 → verbs + status codes

Level 3 → links (HATEOAS)

Think: URL → things → verbs → links. Most APIs stop at the verbs step.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 When links actually help — the response changes with the state
⚠️ Common Trap

"A higher level is a better API." Not automatically — level 3 makes every response bigger and the client more complex, so many APIs deliberately stop at level 2.

🔄 Likely Follow-up

"What does a hypermedia response actually look like?" The data plus a list of links, each with a relation name (rel) and a URL, for the next actions allowed right now — such as the next page, or cancel while an order is still pending.

🎯 Say this in the interview — the exact lines to land

"The Richardson model grades an API in four levels: one endpoint, then resources, then proper verbs and status codes, then hypermedia links. Most real APIs stop at level 2, and I add links only where they genuinely help — like paging, or actions that depend on state."

  • Level 0 → one URL, HTTP used only as a tunnel.
  • Level 1 → a URL per resource.
  • Level 2 → proper verbs and status codes — where most APIs stop.
  • Level 3 → hypermedia (HATEOAS): responses carry links to the next actions.
  • Links pay off for paging and state-dependent actions.
  • Strict REST asks for hypermedia, yet clients usually rely on docs or OpenAPI instead.
📖 Explanation ▾

The Richardson Maturity Model grades how REST-like an HTTP API is, in four steps. Level 0 sends every call to one URL, usually with one verb, so HTTP is only a tunnel. Level 1 gives each resource its own URL. Level 2 uses the verbs and status codes properly — see HTTP Verbs and What Is REST. Level 3 adds hypermedia: each response carries links telling the client what it can do next.

That last step is HATEOAS (hypermedia as the engine of application state). The client doesn't hard-code URLs; it follows the links the server hands back, like a person clicking through a website. REST's original author, Roy Fielding, says real REST needs this — so a level-2 API is what most teams call REST, without meeting the strictest reading.

In practice level 3 is rarely built. Clients are usually written against docs or an OpenAPI file and already know the URLs, links make every response bigger, and there is no single link format everyone uses (HAL, JSON:API and Siren are some of the options). Links do earn their keep in a few places: next and previous links for Pagination, and actions that depend on state — an order shows a cancel link only while it is pending.

💻 See the code ▾
JSON 
{
  "id": 5,
  "status": "Pending",
  "links": [
    { "rel": "self", "href": "/orders/5", "method": "GET" },
    { "rel": "cancel", "href": "/orders/5/cancel", "method": "POST" }
  ]
}

A level-3 response: the data plus the next actions the client may take. Once the order ships, the cancel link simply isn't there.

C# 
public record LinkDto(string Rel, string Href, string Method);
public record OrderDto(int Id, string Status, List<LinkDto> Links);

[HttpGet("{id}", Name = "GetOrder")]
public ActionResult<OrderDto> Get(int id)
{
    var order = _orders.Find(id);
    var links = new List<LinkDto>
    {
        new("self", Url.Link("GetOrder", new { id })!, "GET")
    };

    if (order.Status == "Pending")
        links.Add(new("cancel", Url.Link("CancelOrder", new { id })!, "POST"));

    return new OrderDto(order.Id, order.Status, links);
}

The server decides which links to add, based on the order's state. There is no built-in HATEOAS feature to rely on — you build the links yourself (here with Url.Link) or use a library.

🌍 Real-world example ▾

Level 3 works the way a website does: you don't memorise every page's address, you click the links on the page you're already on.

Scenario: an order API returns a cancel link only while the order is pending. The UI shows a Cancel button only when that link is present, so the "can this be cancelled?" rule lives on the server instead of being copied into every client.
