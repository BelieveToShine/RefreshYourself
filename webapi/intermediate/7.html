Validation attributes aren't just checks — they're the contract

How does model validation define your API's contract, and what does Swagger/OpenAPI actually generate from it?

Why it matters ▾
  • Almost every endpoint that accepts input gets asked about this — validation attributes are the first sign an interviewer checks whether you see the contract, not just the checks.
  • Comes up any time you're integrating with another team or generating a client SDK — knowing what Swagger/OpenAPI actually generates from separates "I clicked around Swagger UI" from "I understand the contract."
  • A common opener follow-up: "walk me through what happens when a request fails validation" — the expected answer is a structured error, not just "it returns 400."
🔥 Easy interview recall

Validation attributes → the contract, declared on the DTO

OpenAPI document → that contract, made machine-readable

Swagger UI / client SDK → both generated from the same document

Think: [Required] on the DTO is the source of truth — everything downstream is just a different view of it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Swagger isn't "just documentation." In a contract-driven workflow the OpenAPI document IS the source of truth other teams and tools build against — letting it drift from the real API (undocumented fields, wrong required/optional flags) breaks generated clients more actively than having no docs at all.

🔄 Likely Follow-up

"If your DTO's attributes define the contract, does business-rule validation — like 'this promo code is expired' — use the same mechanism?" No — data-annotation validation is declarative and structural (is the field present, is it the right shape); a business rule needs a service call and doesn't fit a static attribute, so it's checked separately, usually producing the same kind of structured error response through different code.

🎯 Say this in the interview — the exact lines to land

"Validation attributes on the DTO — [Required], [StringLength], [EmailAddress] — declare the contract right where the shape is defined, and a well-designed API returns a structured error, usually RFC 7807 Problem Details, naming which field failed. Swagger/OpenAPI takes that same contract and generates a machine-readable document, which Swagger UI renders as a browsable page and which tools use to generate typed client SDKs — so nobody hand-writes request or response types by guessing."

  • Validation attributes → the contract, declared on the DTO — a consumer reads the shape, not your controller code.
  • Validation failure → return a structured error, commonly RFC 7807 Problem Details, naming which field — not a bare 400.
  • OpenAPI document → the machine-readable source of truth — every endpoint, parameter, and required/optional flag.
  • Swagger UI and generated client SDKs → both generated from the same document — never hand-written from docs.
  • Letting the doc drift from the real API → breaks generated clients, worse than having no docs.
📖 Explanation ▾

Putting [Required], [StringLength], and [EmailAddress] on a DTO does two jobs at once: it tells the framework what to check, and it tells anyone reading the DTO — a teammate, or the generated Swagger doc — exactly what's required and constrained, without them ever opening your controller. That's the contract angle: the shape of the class already answers "what does this endpoint expect." (For how the pipeline actually triggers that check — ModelState.IsValid, [ApiController]'s auto-400 — see Model Binding & Validation on the .NET track; this page stays on what it means to the consumer.)

A bare 400 tells a consumer something failed, not what or why. A well-designed API returns a structured error response — commonly the RFC 7807 "Problem Details" format — naming which field failed and the reason, so a client can show the right message without guessing or parsing a string.

An OpenAPI document is a JSON or YAML file describing the entire API contract: every endpoint, its parameters, request/response shapes, and — thanks to those same validation attributes — which fields are required or constrained. Swagger UI renders that document as a browsable page; other tools read the same document to generate a typed client SDK, so a consumer never hand-writes request or response types by guessing from prose docs.

💻 See the code ▾
C# 
public class CreateUserDto
{
    [Required]
    public string Name { get; set; }

    [EmailAddress]
    public string Email { get; set; }

    [StringLength(20, MinimumLength = 8)]
    public string Password { get; set; }
}

Anyone reading this DTO — or its generated Swagger doc — already knows what's required, without opening the controller.

C# 
[HttpPost]
public IActionResult CreateUser(CreateUserDto dto)
{
    if (!ModelState.IsValid)
        return ValidationProblem(ModelState);  // ✅ names the field, not just 400

    _users.Save(dto);
    return Ok();
}

ValidationProblem() returns Problem Details — the response names which field failed.

C# 
// Program.cs
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();   // reads your DTOs & attributes

var app = builder.Build();
app.UseSwaggerUI();   // renders the same document as a page

Nobody wrote openapi.json by hand — AddSwaggerGen generates it from your controllers and DTOs.

🌍 Real-world example ▾

A consuming team's generated TypeScript client suddenly fails to compile after your API team adds a new required field to a DTO. That's the contract working as intended, not a bug: the OpenAPI document regenerated with the new field, their client generator picked it up, and the compile error is the fastest possible signal that their code needs to change — the fix is "regenerate the client," never "put the field back."
