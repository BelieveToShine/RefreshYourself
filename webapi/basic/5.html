Rate limiting — crowd control, not a security guard

"What is rate limiting, and what is it actually protecting against?"

Why it matters ▾
🪟 Fixed window
❗ ProblemThe counter resets hard on a clock boundary, so a client can burst a full window's worth of requests right before reset, then a full window's worth again right after.
✅ SolutionSimplest to build — just a counter and a clock — worth it when that one brief boundary spike is tolerable.
RecallFixed window = simple counter, resets on the clock — boundary can double the burst.
🎯 Sliding window
❗ ProblemThat same reset boundary is exactly what fixed window can't defend — a burst timed right around it still slips through twice.
✅ SolutionIt tracks usage over a rolling period instead of a hard reset, so the cap holds continuously and the boundary trick disappears.
RecallSliding window = rolling period, not a hard reset — no boundary trick.
🪣 Token bucket
❗ ProblemA perfectly even, steady rate would also block a legitimate short burst from a client that's been idle and then fires off a handful of calls at once.
✅ SolutionA bucket refills with tokens over time; a client spends saved tokens in a quick burst, then falls back to the steady refill rate — capping the long-run average.
RecallToken bucket = refills over time, burst spends saved tokens, average stays capped.
🔥 Easy interview recall

Rate limiting = "cap the requests, reject the extra with a 429."

Think: 100/min allowed → request 101 gets 429 plus Retry-After, not silence.

🧠 Same burst, three different reactions — the differentiator interviewers actually ask about
⚠️ Common Trap

Rate limiting is not a security feature on its own. It's a resilience and fairness mechanism — an API can be fully rate-limited and still wide open to unauthorized access if authentication is missing; the two concerns are separate and both required.

🔄 Likely Follow-up

"What should a well-designed API tell the client when it's rate-limited?" A 429 status plus headers like X-RateLimit-Remaining and Retry-After — telling the client not just THAT it's capped but roughly WHEN it can retry, so it can back off intelligently instead of guessing.

🎯 Say this in the interview — the exact lines to land

"Rate limiting caps how many requests a client — identified by API key, IP, or account — can make in a given time window, rejecting the rest with a 429. It protects against accidental abuse, deliberate abuse, and one noisy client degrading the API for everyone else — but it's a resilience concern, not a substitute for authentication."

  • Identifies the caller by API key, IP address, or account — not by what the request contains.
  • Excess requests get 429 Too Many Requests, ideally with a Retry-After header.
  • Protects against accidental abuse, deliberate abuse, noisy neighbors, and runaway cost — four separate reasons, not just "attackers."
  • Common strategies: fixed window, sliding window, token bucket — token bucket allows a short burst while still capping the average.
  • Never a replacement for authentication or authorization — the two are complementary, not interchangeable.
📖 Explanation ▾

Rate limiting counts requests per identity — an API key, an IP address, or a signed-in account — inside a rolling time window, and rejects anything past the cap with a 429. The point isn't to punish anyone; it's to keep one caller's usage from eating the capacity every other caller is also relying on.

Three strategies show up by name in interviews: fixed window (a simple counter that resets on a clock boundary), sliding window (a rolling period instead of a hard reset, so usage near the boundary can't double up), and token bucket (a bucket that refills over time and lets a client spend saved-up tokens in a quick burst). The mechanics behind each rarely get quizzed at this level — knowing they exist, and that token bucket is the one built for bursts, is enough.

It's easy to file this under "security" because both show up on the same API-hardening checklist. But an attacker holding a stolen, valid API key sails straight through a rate limiter — it only throttles volume, not legitimacy. Authentication and authorization decide who's allowed in; rate limiting decides how much any one caller can do once they're there.

💻 See the code ▾
C# 
// Program.cs — cap each client at 100 requests per 60-second window (.NET 7+)
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("perClient", opt =>
    {
        opt.PermitLimit = 100;
        opt.Window = TimeSpan.FromSeconds(60);
    });
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();

The built-in limiter still needs a partition key (API key, IP) so one caller's usage doesn't count against another's.

C# 
if (requestCount > limit)
{
    context.Response.StatusCode = StatusCodes.Status429TooManyRequests;
    context.Response.Headers["Retry-After"] = "30";             // seconds until it should retry
    context.Response.Headers["X-RateLimit-Remaining"] = "0";     // tells the client exactly where it stands
    return;
}

The status code alone says "you're capped." The headers say what to do next — that second part is what a well-designed API adds.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your own client code gets stuck in a loop and hammers one endpoint nonstop

This is usually a bug, not an attack — a retry with no exit condition, a missing await, a loop that never checks a success flag. The rate limiter doesn't need to know that; it caps that same client at the same limit and returns 429 regardless of intent, so the runaway loop stays contained to that one caller instead of degrading the API for everyone else.

RememberBuggy loop or attacker — the limiter reacts the same way: cap it, then 429.
2 A traffic spike hits your API and you need to tell a real flash sale apart from a deliberate flood

Because the limiter counts per identity — API key, IP, or account — a genuine flash sale is naturally many different customers, each comfortably under their own cap. A coordinated flood usually comes from a small number of identities repeating the same calls, so those specific identities hit their own cap fast. The limiter doesn't have to guess intent — per-identity keying sorts the two apart on its own.

RememberPer-identity caps sort a flash sale from a flood automatically — many callers vs. one.
3 A partner's integration retries every failed call immediately, with no backoff

Once that integration starts getting capped, it keeps retrying just as fast — sometimes faster — turning one rate-limit breach into a self-inflicted retry storm on top of it. Returning 429 alone doesn't fix this; the partner's client actually has to read and respect the Retry-After header for the retries to slow down.

RememberNo backoff → retries pile on retries. 429 alone doesn't fix it — Retry-After has to be respected.
🌍 Real-world example ▾

Scenario: your public search endpoint starts timing out for every customer because one integration partner's script got stuck in a retry loop, firing hundreds of requests a second. The direct fix: a rate limiter keyed on that partner's API key returns 429 the moment they cross their cap — their bug stays their own problem instead of degrading the shared search cluster for every other tenant.
