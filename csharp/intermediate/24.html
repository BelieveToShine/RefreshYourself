Variance — why List<Dog> isn't a List<Animal>

"What are covariance and contravariance in C# generics — why can't a List<Dog> be a List<Animal>?"

Why it matters ▾
🔀 Generic variance
❗ ProblemA Dog is an Animal, so it feels like List<Dog> should be a List<Animal>. But if it were, you could add a Cat through the List<Animal> view and break the dog list from the inside.
✅ SolutionC# allows the conversion only where it is safe: out T (covariant) for interfaces and delegates that only return T, and in T (contravariant) for ones that only take T. List<T> does both, so it stays invariant.
Recallout = only produces T, so a Dog-version works as an Animal-version; in = only consumes T, so the reverse works.
🔥 Easy interview recall

out = "only gives out T." in = "only takes in T." List<T> does both = locked.

Think: Producers can be widened (IEnumerable<Dog> → IEnumerable<Animal>); consumers can be narrowed (Action<Animal> → Action<Dog>).

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Variance works only with reference types. IEnumerable<int> cannot be assigned to IEnumerable<object>, because the conversion would have to box each value. And arrays look covariant (Animal[] a = new Dog[1];) but writing a Cat into one throws ArrayTypeMismatchException at runtime.

🔄 Likely Follow-up

"Where do you see out and in in the framework?" IEnumerable<out T> and Func<out TResult> are covariant; Action<in T> and IComparer<in T> are contravariant. This ties to the Liskov rule in OOP.

🎯 Say this in the interview — the exact lines to land

"Variance lets a generic interface or delegate convert along the inheritance chain when it is safe. out T — covariance — is for types that only return T, like IEnumerable<out T>. in T — contravariance — is for types that only take T, like Action<in T>. List<T> does both, so it is invariant."

  • out T → covariance: IEnumerable<Dog> can be used as IEnumerable<Animal>.
  • in T → contravariance: Action<Animal> can be used as Action<Dog>.
  • List<T> → invariant, because it both reads and writes T.
  • Only interfaces and delegates can declare in/out, and only for reference types.
  • Arrays → covariant but unsafe; a bad write fails at runtime, not compile time.
📖 Explanation ▾

The question is: if Dog derives from Animal, is Thing<Dog> usable as Thing<Animal>? For List<T> the answer is no. A List<Animal> accepts any animal on Add, so if your dog list could be viewed that way, someone could add a Cat to it. The compiler blocks the conversion up front.

Covariance (out T) is safe when T only comes out — as a return value. IEnumerable<out T> only lets you read, so a sequence of dogs really can be treated as a sequence of animals. Contravariance (in T) is safe when T only goes in — as a parameter. A handler that can take any Animal can certainly be used where a handler for Dog is expected, so the direction flips.

You can declare your own: interface IProducer<out T> may only return T; the compiler checks that you keep the promise. Arrays predate generics and were made covariant anyway, which is why they can fail at runtime.

💻 See the code ▾
C# 
IEnumerable<Dog> dogs = new List<Dog>();
IEnumerable<Animal> animals = dogs;       // ✅ out T: covariance

Action<Animal> feed = a => Console.WriteLine(a);
Action<Dog> feedDog = feed;               // ✅ in T: contravariance

Both conversions are safe because T flows only one way.

C# 
List<Animal> list = new List<Dog>();     // ❌ compile error: List<T> is invariant

Animal[] arr = new Dog[1];                // compiles: arrays are covariant
arr[0] = new Cat();                       // ❌ throws ArrayTypeMismatchException at runtime

Generics catch the mistake at compile time; arrays only at runtime.

🌍 Real-world scenario ▾

A method takes IEnumerable<Animal> to print names. Callers holding a List<Dog> can pass it straight in without copying, thanks to covariance — which is why such read-only parameters should be IEnumerable<T>, not List<T>.
