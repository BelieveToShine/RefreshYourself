SDK vs. Runtime — which one do you actually need installed?

"What's the difference between installing the .NET SDK and the .NET runtime?"

Why it matters ▾
  • Install only the runtime on a dev machine and dotnet build simply doesn't exist — a real first-day confusion for a lot of developers.
  • Shipping the full SDK to a production server (or container) unnecessarily bloats the image and adds attack surface nothing there ever uses.
  • A common opener when a candidate says "I installed .NET" without knowing which piece they actually installed.
🔥 Easy interview recall

Runtime → run only — CLR + BCL

SDK → run + build — compiler, CLI, MSBuild

Think: SDK is a superset. Runtime is the part of it you actually ship.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Installing just the runtime on a dev machine, then wondering why dotnet build doesn't exist. The runtime is only the CLR and base class library — the compiler and CLI tools ship with the SDK, not the runtime.

🔄 Likely Follow-up

"What's the difference between a NuGet package and a regular DLL reference?" A NuGet package is a versioned, distributable unit that can bundle several DLLs plus tooling and content, and NuGet resolves its own dependencies automatically; a raw DLL reference is just one file, with none of that resolution.

🎯 Say this in the interview — the exact lines to land

"The runtime is the CLR and the base class library — everything you need to run an already-built app, nothing more. The SDK is a superset: runtime plus the compiler, the CLI, and MSBuild — what a developer needs to build, run, and publish. A .csproj describes the project — target framework, package references, build settings — and NuGet reads those PackageReference entries to resolve the whole dependency graph."

  • Runtime → install this on a production server — just enough to run.
  • SDK → install this on a dev machine — needed to build, compile, publish.
  • .csproj → the project's manifest — target framework, package references, build settings.
  • NuGet → resolves the dependency graph from those references, transitive packages included.
📖 Explanation ▾

The runtime is the CLR (Common Language Runtime) plus the base class library — enough to execute an already-built app. It has no compiler and no build tooling, because running an app was never its job.

The SDK is a superset of the runtime: it includes the runtime, plus the Roslyn compiler, the CLI (dotnet build, dotnet new, dotnet publish), and MSBuild. A developer needs the SDK. A production server only needs the runtime the app was built against.

A .csproj is an MSBuild XML file describing the project: its target framework (net8.0), its package references (NuGet dependencies, each with a version), its project references, and build settings like nullable reference types or implicit usings. NuGet reads the <PackageReference> entries, resolves the full dependency graph — including transitive dependencies — downloads everything into a local cache, and makes those assemblies available at build and run time.

💻 See the code ▾
C# 
// a machine with only the runtime installed
dotnet build              // ❌ no SDK found — there's no compiler here
dotnet MyApp.dll          // ✅ runs fine — running doesn't need a compiler

The runtime can execute an already-built app. It can't build one — that needs the SDK.

C# 
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
  </ItemGroup>
</Project>

.csproj is the project's manifest — target framework, package references, build settings, all in one MSBuild XML file.

C# 
dotnet restore    // NuGet reads the PackageReference entries above,
                  // resolves the full dependency graph, downloads into the local cache
dotnet build      // ✅ compiles against the resolved packages

NuGet resolves transitive dependencies too — one PackageReference can pull in several more behind the scenes.

🌍 Real-world example ▾

A construction site versus the finished building. The site has the cranes, the mixers, the tools — everything needed to build the structure. Once it's built, you only need the building itself to live in it, not the construction equipment.

Scenario: your team's production Docker image is built from the full SDK image, so it ships with a compiler and CLI tools nothing at runtime ever calls. Switch to a multi-stage build instead — the SDK image compiles and publishes the app, then the final image copies the published output onto the smaller runtime-only image. Same app, a smaller image, and less unused tooling sitting inside a production container.
