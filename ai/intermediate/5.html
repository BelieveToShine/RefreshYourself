Searching millions of vectors — compare against all of them, or take a shortcut?

"What is ANN (Approximate Nearest Neighbor) search — like HNSW — and why not just do an exact nearest-neighbor search?"

Why it matters ▾
  • Checks whether you understand why exact nearest-neighbor search doesn't scale, and what an ANN index actually trades away to fix that.
  • Comes up any time a RAG or search system-design question goes one layer deeper than "it searches embeddings."
  • The vector-DB-choice question (pgvector vs. a dedicated store) almost always follows right behind it.
🔥 Easy interview recall

ANN = "skip most of the haystack — trade a little accuracy for a lot of speed."

Think: Exact → checks every vector → accurate, doesn't scale ANN (HNSW, IVF) → follows an index shortcut → fast, occasionally misses

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ANN doesn't mean "unreliable." It means trading a small, tunable amount of recall for a large speedup — widen the search parameters and it gets closer to exact, at the cost of latency. It's a dial, not a broken shortcut.

🔄 Likely Follow-up

"With so many options — pgvector, Pinecone, Qdrant, Azure AI Search — how do you actually pick one?" It comes down to scale, whether you want it managed versus running it yourself, and whether you'd rather keep vectors inside a database you already run (pgvector on Postgres) than stand up a separate system.

🎯 Say this in the interview — the exact lines to land

"Exact nearest-neighbor search compares a query against every stored vector, which doesn't scale past a certain size. ANN indexes like HNSW or IVF trade a small amount of accuracy for a large speedup by avoiding that full scan, and every ANN index exposes tunable parameters that trade search speed against recall."

  • HNSW → a multi-layer graph — search starts coarse, narrows layer by layer to real candidates.
  • IVF → clusters vectors into buckets first, then only searches the closest buckets.
  • Recall vs. latency → a tunable dial, not a fixed accuracy ceiling.
  • Metadata filtering (tenant, date range) → a standard capability, not an edge case, in any real vector DB.
  • Choice of store → scale, managed vs. self-run, and whether it should live inside a database you already use (e.g. pgvector on Postgres).
📖 Explanation ▾

Exact nearest-neighbor search compares a query vector against every vector in the store and returns the true closest matches — accurate, but the cost grows directly with the size of the collection, so past a certain scale it stops being fast enough for real-time use. ANN (Approximate Nearest Neighbor) search fixes that by building an index structure that avoids comparing against everything, trading a small amount of accuracy for a large speedup — the standard approach once a collection gets large.

HNSW (Hierarchical Navigable Small World) is a commonly-used ANN index: it builds a multi-layer graph, where a search starts at a coarse, sparse layer and progressively navigates down to finer, denser layers — narrowing to a small set of likely-nearest candidates without scanning the whole collection. IVF (Inverted File index) takes a different route to the same goal: it clusters vectors into buckets ahead of time, then at query time only searches the handful of buckets closest to the query, instead of the whole dataset.

Every ANN index also exposes tunable parameters that trade search speed against recall — how likely it is to actually find the true nearest neighbors; a tighter, faster setting risks occasionally missing a true match, a wider, slower one gets closer to exact. Real vector search almost always needs metadata filtering too — combining the similarity search with a filter on structured fields like "only this tenant" or "only the last 30 days" — a standard, expected capability, not an edge case.

In practice the choice of where vectors live comes down to pgvector (a Postgres extension — good if you're already on Postgres and want to avoid a separate system), Azure AI Search, or a dedicated vector database like Pinecone, Qdrant, Weaviate, Milvus, Chroma, or Redis with vector support — driven by scale, whether you want it managed, and whether you want it integrated with a database you already run.

Pseudocode 
# Exact — compares against every stored vector
scored = [(v.id, cosine_sim(query_vec, v.embedding)) for v in all_vectors]  # O(n) comparisons
scored.sort(key=lambda x: x[1], reverse=True)
top_k = scored[:5]

Correct, but the comparison count grows directly with the size of the collection.

Pseudocode 
# ANN — the index does the narrowing, plus a metadata filter
results = index.search(
    query_vec,
    k=5,
    ef_search=100,   # ✅ tunable: higher = slower, better recall
    filter={"tenant_id": tenant_id, "date": {"gte": last_30_days}},
)

Same call carries the metadata filter — a normal part of a real vector search query, not an add-on.

🌍 Real-world example ▾

A product-search feature works fine in development against a few thousand items, then crawls in production once the catalog grows into the millions — the query is still doing an exact, compare-against-everything scan. Switching to an ANN index (HNSW or IVF) fixes the latency by skipping most of the collection, at the cost of a small, tunable amount of recall; and because the search almost always needs to stay scoped to one tenant's own catalog, the metadata filter has to run as part of the same query, not as a slow filter pass afterward.
