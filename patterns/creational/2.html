Factory Method — let subclasses decide, not a scattered new

"What is the Factory Method pattern, and how is it different from a plain static method that just returns new X()?"

🧩 Also see the OOP-angle page: Factory vs. Dependency Injection
Why it matters ▾
🏭 Factory Method
❗ ProblemScattering new WindowsButton() / new WebButton() calls through every place a dialog gets rendered ties that code to concrete classes, so adding a new UI variant means hunting down and editing every call site.
✅ SolutionFactory Method pushes the new into one overridable method; each subclass overrides it to return its own concrete product, while the shared logic that calls it never has to change.
RecallThe method decides which concrete type — by being overridden, not by a parameter.
🔥 Easy interview recall

Factory Method = "a method that subclasses override to pick the concrete product."

Think: Creator → declares the factory method, often abstract ConcreteCreator → overrides it, returns its own ConcreteProduct Caller → only ever sees the Product interface

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Any method that returns new X() is not automatically a Factory Method. The GoF-defining trait is a subclass overriding the method to vary the product — a plain static method that branches on a parameter and returns new X() is a related but distinct idiom, often called a "simple factory."

🔄 Likely Follow-up

"Is Dialog allowed to have other logic besides the factory method?" Yes — Creator classes commonly define further behavior, like Render(), that calls the factory method internally. The pattern is about isolating object creation inside one overridable spot, not about the class containing nothing else.

🎯 Say this in the interview — the exact lines to land

"Factory Method defines a method for creating an object but lets subclasses decide which concrete class to instantiate — the Creator declares it, each ConcreteCreator overrides it to return its own ConcreteProduct, and callers only ever see the Product interface. That's different from a plain static method that returns new X() from a parameter — that's a simple factory, not Factory Method, because nothing is being overridden by a subclass."

  • Structure → Creator, ConcreteCreator, Product, ConcreteProduct.
  • The defining trait → subclasses override the method, not just a static helper.
  • Shared logic stays put → Render() never changes even as new ConcreteCreators are added.
  • Not the same question as → Factory vs. Dependency Injection (that's about when you need one in addition to DI).
📖 Explanation ▾

Factory Method's intent: define an interface, or an abstract method, for creating an object — but let subclasses decide which concrete class actually gets built. Four participants make the shape: Creator (declares the factory method, often alongside other logic that calls it), ConcreteCreator (overrides the factory method to return a specific ConcreteProduct), and Product, the interface every concrete product shares.

The nuance worth being precise about: this is different from a plain static method that just returns new X() behind a parameter — people casually call that "a factory" too, and it's a genuinely useful, related idiom. But it isn't Factory Method in the GoF sense, because nothing is being overridden; one static method still owns every branch, and adding a new product type means editing that method instead of adding a subclass.

💻 See the code ▾
C# 
public abstract class Dialog
{
    public abstract Button CreateButton();          // the factory method

    public void Render()
    {
        Button btn = CreateButton();               // Dialog never names a concrete type
        btn.Render();
    }
}

public class WindowsDialog : Dialog
{
    public override Button CreateButton() => new WindowsButton();   // ✅ overrides, returns its own product
}

public class WebDialog : Dialog
{
    public override Button CreateButton() => new HtmlButton();       // ✅ a different override, different product
}

Render() is shared and never changes; each subclass only overrides which product comes back.

C# 
// Related idiom — a "simple factory," not Factory Method itself
public static class ButtonFactory
{
    public static Button Create(string os) =>
        os == "Windows" ? new WindowsButton() : new HtmlButton();   // one method, no subclass override
}

Correct, common, and useful — but nothing here is overridden by a subclass, so a new OS means editing this method.

🌍 Real-world example ▾

A logistics app with RoadLogistics and SeaLogistics. Both inherit the same PlanDelivery() logic from a shared base class, but each overrides a factory method to create its own transport — RoadLogistics returns a Truck, SeaLogistics returns a Ship. The planning logic never has to ask which one it's dealing with.
