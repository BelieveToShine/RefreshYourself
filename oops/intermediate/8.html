Coupling vs. Cohesion — why you want one low and the other high

What's the difference between coupling and cohesion, and why do you want low coupling but high cohesion?

Why it matters ▾
  • Interviewers use this to check you can name what makes a design hard to change, not just recite the two definitions.
  • Comes up in code review, in "why does this refactor matter" conversations, and in "walk me through what makes this class hard to test" questions.
  • A common way in for a system-design or architecture round — it's the vocabulary behind "this service is too tangled to touch safely."
🔥 Easy interview recall

Coupling → low is good

Cohesion → high is good

Think: Coupling is about the wires running out of the box. Cohesion is about what's packed inside the box.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Low coupling does not mean zero dependencies. A class has to call something to be useful — the real goal is depending on stable abstractions instead of volatile concrete details, not eliminating every dependency.

🔄 Likely Follow-up

"Can you have low coupling and low cohesion at the same time?" Yes — a Utils class full of unrelated static helper methods: nothing else depends tightly on it, so coupling looks fine, but internally it's a grab-bag with no shared purpose, which is its own maintainability problem.

🎯 Say this in the interview — the exact lines to land

"Coupling is how much one class depends on or knows about another — I want that low. Cohesion is how strongly the things inside one class belong together — I want that high. A class that's internally scattered but wired to everything else is the worst combination: hard to understand on its own, and hard to change without breaking something else."

  • Single responsibility → one reason to change, which is what keeps cohesion high.
  • Testability → can you unit test it without a real database or network?
  • Low coupling → depend on interfaces, not concrete implementations.
  • Clear naming, no hidden side effects → calling a method shouldn't quietly mutate unrelated state.
📖 Explanation ▾

Coupling measures how much one class or module knows about, or depends on, another. High coupling means a change to one class's internals forces changes somewhere else too — the two are wired together more tightly than they need to be. Low coupling doesn't mean no connections at all; it means the connections point at stable abstractions instead of volatile concrete details.

Cohesion measures how strongly the things inside one class belong together. A highly cohesive class has one clear purpose, and every method and field serves that purpose. This is the same idea the Single Responsibility Principle page covers in depth — cohesion is the property SRP is protecting; this page won't re-teach SRP itself.

You want both at once, and they don't trade off against each other — a class can be low coupling and low cohesion just as easily as high coupling and high cohesion. The worst combination is low cohesion and high coupling: scattered inside, tightly wired outside. That class is hard to understand by reading it alone, and hard to change without breaking something else — the two failure modes stack instead of cancelling out.

💻 See the code ▾
C# 
public class OrderService
{
    private readonly SqlOrderRepository _repo = new();   // concrete type, hardcoded

    public void Place(Order order) => _repo.Save(order);
}   // ❌ high coupling — swapping databases means editing this class

OrderService knows the exact concrete class it depends on — any change to SqlOrderRepository risks breaking it.

C# 
public class OrderService
{
    private readonly IOrderRepository _repo;      // abstraction, injected

    public OrderService(IOrderRepository repo) => _repo = repo;

    public void Place(Order order) => _repo.Save(order);
}   // ✅ low coupling — any IOrderRepository works, real or fake

Depending on IOrderRepository instead means the concrete database can change without touching this class — and it's testable with a fake.

C# 
public static class ReportHelper
{
    public static void SendEmail(string to) { /* ... */ }
    public static decimal CalculateTax(decimal amount) => amount * 0.2m;
    public static string FormatDate(DateTime d) => d.ToString("yyyy-MM-dd");
}   // ❌ low cohesion — three unrelated jobs sharing one class name

Nothing forces these three methods to sit together — each belongs in the class whose one job it actually serves (an emailer, a tax calculator, a formatter).

🌍 Real-world example ▾

A kitchen drawer, not a shared workbench. A drawer holding only knives is high cohesion — everything inside serves one job. A recipe that only works with one specific store-brand spice is high coupling — swap the store and the recipe breaks. A well-written recipe calls for "garlic," an abstraction any brand satisfies, not "Brand X garlic from Store Y" — that's what low coupling looks like in code, too.
