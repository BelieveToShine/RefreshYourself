Conditional rendering — the same JS if/ternary/&&, just returning UI

"How do you conditionally render in React, and what's the classic && gotcha?"

Why it matters ▾
🔀 if / else
❗ ProblemSome branches need to return a completely different tree — a spinner, an error screen, the real content — not just a different value, and that's too much structure for a single JSX expression.
✅ Solutionif / else runs before the return as a plain statement, so each branch can just return its own JSX outright, no expression trick needed.
Recallif/else = full statement before return, for real branch structure.
⚖️ ternary (?:)
❗ ProblemSometimes the choice is small — one inline either/or right inside the JSX being returned — and a full if/else block would be overkill for that.
✅ Solution?: is an expression, so it evaluates to a value in place, cleanly picking one of two things to render inline.
Recallternary = inline either/or expression; nested ternaries get hard to read fast.
⚡ && (short-circuit)
❗ ProblemWriting condition ? <X/> : null just to show-or-hide one thing is verbose for something this simple.
✅ Solution&& short-circuits on the first falsy operand, so condition && <X/> renders <X/> or renders nothing in one compact expression — but only when condition is a real boolean, not a falsy number.
Recall&& = show it or show nothing — unsafe with a falsy number on the left.
🔥 Easy interview recall

if / else → before the return, for full branches

?: ternary → inline in JSX, either/or

&& → inline, show it or show nothing

Think: && is only safe when the left side is a real boolean — a falsy number like 0 slips through and gets rendered as text.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

condition && <Component /> is not always a safe way to conditionally render. If condition evaluates to a falsy number — most commonly 0, e.g. from array.length — JSX renders that literal 0 as visible text instead of rendering nothing.

🔄 Likely Follow-up

"When should conditional logic move out into its own component?" Once the branches get complex enough — multiple conditions, real markup per branch — that inlining hurts readability; extracting a named component like <EmptyState /> or <LoadingSpinner /> makes the intent read clearly at the call site instead of being buried in nested ternaries.

🎯 Say this in the interview — the exact lines to land

"React has no special conditional syntax — I use plain JavaScript: an if before the return, a ternary inline in JSX, or && for a simple show-or-hide. The one trap is count && <Component /> — if count is 0, that's a falsy number, not false, so it renders the literal text 0 instead of nothing."

  • if / else → use before the return when branches need different markup.
  • Ternary (?:) → inline, either-or choice inside JSX.
  • && → only safe with a real boolean on the left side.
  • A falsy number like 0 still renders as text — coerce with > 0 first.
  • Complex branches → extract a named component instead of nesting ternaries.
📖 Explanation ▾

React doesn't add a special conditional-rendering syntax — you reach for the same JavaScript you already know and just return different JSX. An if / else before the return fits when the branches need genuinely different markup; a ternary works inline inside JSX for a clean either/or; && works inline for a simple "show this, or show nothing" case.

The && gotcha comes from what JSX actually does with a value: it skips rendering false, null, and undefined, but a number is a normal, renderable piece of content. && returns whichever operand it stops on — so items.length && <List /> stops on items.length itself when it's 0, and React renders that number as text, because nothing told it not to.

Fallback content — a loading spinner, an empty state — isn't a different mechanism, it's just another branch of the same conditional. Once a branch's condition or markup gets complex, pulling it into its own named component keeps the call site readable instead of nesting ternaries inside JSX.

💻 See the code ▾
JSX 
function ItemList({ items }) {
  return (
    <div>
      {items.length && <List items={items} />}  // ❌ items.length === 0 → renders "0"
    </div>
  );
}

When items is empty, items.length is the number 0 — && stops there and React renders that 0 as visible text.

JSX 
{items.length > 0 && <List items={items} />}  // ✅ a real boolean now

> 0 forces a real boolean, so an empty list renders nothing — the same fix works as items.length ? <List items={items} /> : null.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your component needs to return a genuinely different tree per branch

A loading spinner and the real content aren't the same JSX with one prop swapped — they're two different trees entirely. if / else runs before the return as a plain statement, so each branch can just return its own JSX outright.

RememberDifferent tree per branch → if / else before the return.
2 You want one inline either/or choice sitting right inside the JSX you're already returning

Swapping <AdminPanel/> for <UserPanel/> based on a role check is one small decision inside markup that's otherwise identical. A ternary is an expression, so it drops straight into JSX and evaluates to whichever side applies.

RememberOne inline either/or → ternary (?:), not a full if/else block.
3 You only want to show something when a condition is true, and show nothing otherwise

items.length && <List/> looks like the clean shortcut for this — but when items.length is 0, && stops on that number, and React renders the literal 0 as text instead of nothing.

Remember&& only shows-or-hides safely with a real boolean — coerce with > 0 first.
🌍 Real-world example ▾

A light switch is supposed to be either fully on or fully off. Wire it to something that isn't a clean boolean, though, and it occasionally sits at a dim, confusing half-glow instead of going properly dark — a subtle, real artifact from a condition that was never actually a boolean in the first place.
