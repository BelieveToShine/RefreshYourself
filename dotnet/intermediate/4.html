Middleware — a pipeline where registration order can break everything

What is middleware, and why does registration order matter so much?

Why it matters ▾
  • Interviewers use this to check whether you understand ASP.NET Core's actual request pipeline, not just that middleware "does something."
  • Comes up any time you're wiring exception handling, authentication, or logging — get the order wrong and the pipeline misbehaves silently, with no compiler warning.
  • A favorite scenario question: "write a middleware that logs request duration" — it tests whether you understand the wrap-and-return shape, not just the syntax.
🔥 Easy interview recall

Use → continue the chain (calls next())

Run → terminal — the chain ends here

Map → branch the chain by request path

Think: Use keeps going. Run stops. Map forks.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Registering UseExceptionHandler() anywhere in the pipeline is enough. It isn't — it only catches exceptions thrown by middleware registered after it, so it has to be one of the very first things registered, not squeezed in wherever's convenient.

🔄 Likely Follow-up

"What happens if your middleware forgets to call next()?" The pipeline short-circuits right there — nothing downstream ever runs, including the real endpoint. Sometimes that's intentional (returning a cached response early), but it's also a common accidental bug.

🎯 Say this in the interview — the exact lines to land

"Middleware is a chain of delegates — each one can act before calling next() and again after it returns, which is why registration order controls what actually happens. app.Use() continues the chain, app.Run() ends it, and app.Map() branches it by request path."

  • Use → continues the chain — call next() to hand off, or skip it to short-circuit.
  • Run → terminal middleware — never calls next(), always the end of that branch.
  • Map → branches by path — runs a separate sub-pipeline for requests that match.
  • Order → exception handling must go first — it only wraps what's registered after it.
📖 Explanation ▾

A middleware pipeline is a chain of delegates, each one wrapping the next — the classic "chain of responsibility" shape. Every middleware gets a chance to run code before calling next() (on the way in) and after next() returns (on the way out), which is why the response passes back through the same stages, in reverse.

app.Use(...) registers a middleware that can call next() to continue the chain, or skip it to short-circuit. app.Run(...) registers a terminal middleware — it never calls next(), so it's always the end of whatever branch it sits in. app.Map(path, ...) branches the pipeline conditionally: requests matching that path run a completely separate sub-pipeline instead of continuing through the main one.

Because each middleware only wraps what's registered after it, the order in Program.cs is the actual shape of the pipeline, not just a list. A middleware registered first sees every request before anything below it, and sees every response after everything below it has finished — which is exactly why exception-handling middleware has to be near the top.

💻 See the code ▾
C# 
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();      // before next() — the "in" side
    await next(context);                // hands off to the rest of the pipeline

    sw.Stop();                          // after next() — the "out" side
    Console.WriteLine($"{context.Request.Path} took {sw.ElapsedMilliseconds}ms");
});

The line after await next() only runs once everything downstream has finished — that's exactly why this measures true end-to-end time.

C# 
app.UseRouting();
app.MapGet("/boom", () => { throw new InvalidOperationException(); }); // throws here

app.UseExceptionHandler("/error");   // ❌ too late — never wraps the endpoint above

Registered after the endpoint, so it never wraps the code that throws — the exception escapes as a raw, unhandled 500.

C# 
app.UseExceptionHandler("/error");   // ✅ registered first — wraps everything below it

app.UseRouting();
app.MapGet("/boom", () => { throw new InvalidOperationException(); }); // now caught

Same two lines, swapped order — now UseExceptionHandler wraps the endpoint and actually catches the exception.

C# 
app.Use(async (context, next) =>
{
    if (!context.Request.Headers.ContainsKey("X-Api-Key"))
    {
        context.Response.StatusCode = 401;
        return;                          // 🐛 next() never called
    }

    await next(context);
});

No next() call on that branch means nothing downstream runs — here that's intentional; forgetting it by accident is the common bug.

🌍 Real-world example ▾

Think of airport security checkpoints. Each one can check you on the way to your gate, and some — like customs — check you again on the way back out, at the exact same station, just in reverse. A middleware pipeline works the same way: each one gets a turn on the way in, and again on the way out, through the same stages it already passed through.
