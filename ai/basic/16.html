Classic ML vs. LLM — when is the "boring" model actually the right answer?

"When would you use traditional machine learning instead of an LLM?"

Why it matters ▾
🧮 Classic ML
❗ ProblemRouting a fixed, narrow, high-volume classification job through an LLM pays for a network round trip on every single call, even though ample labeled training data is already sitting there unused.
✅ SolutionA small trained classifier — logistic regression, gradient-boosted trees — answers each call locally in a few ms, and is cheaper, faster, and easier to debug than sending every request through an LLM.
RecallClassic ML = fixed, narrow, well-labeled, high-volume → cheap, fast, predictable.
🤖 LLM
❗ ProblemA dedicated classifier can't get off the ground when labeled training data is scarce, or when the job keeps shifting into new task variants it was never trained on.
✅ SolutionAn LLM handles open-ended language tasks and new task variants without retraining, working with little or no labeled data — at the cost of being slower and pricier per call, and harder to fully predict.
RecallLLM = open-ended, scarce labels, many task variants → flexible, no retraining needed.
🔥 Easy interview recall

High-volume, tabular, well-labeled, narrow? → Classic ML

Open-ended language, scarce labels, many task variants? → LLM

Think: reach for the smallest tool that actually solves the problem — not the most powerful one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for an LLM "because it's the modern tool" on a task that's really a clean, high-volume classification problem. That's a real, common over-engineering mistake — the same "reach for the simplest tool that fits" judgment gets tested with plain classifiers, not just with LLMs.

🔄 Likely Follow-up

"What if you don't have enough labeled data to train a classic model?" That's exactly when an LLM becomes the better fit — it can handle the task with little or no labeled training data, where a dedicated classifier can't get off the ground.

🎯 Say this in the interview — the exact lines to land

"Traditional ML still wins for well-defined, high-volume tabular classification with ample labeled data — it's cheaper, faster, and easier to debug than routing that same task through an LLM."

  • Classic ML → use for narrow, tabular, well-labeled problems called at high volume or low latency.
  • LLM → use for open-ended language work, scarce labeled data, or many task variants you can't retrain a model for each time.
  • Reaching for an LLM on a clean classification task just because it's the modern tool is the real interview red flag — over-engineering, not good judgment.
📖 Explanation ▾

Classic ML — logistic regression, gradient-boosted trees, or a small trained classifier — still wins whenever the problem has clear, structured, tabular features, the volume is high, latency has to stay low, and there's a real, fixed labeled dataset to train on. In that shape of problem, a small model is cheaper per call, faster, more predictable, and easier to debug and monitor than sending every request through an LLM.

LLMs win once the task moves into open-ended language understanding or generation, once labeled training data is scarce, or once the system needs to flexibly handle many task variations it hasn't seen before — without retraining a dedicated model for each new variation. The tradeoff isn't "old vs. new," it's "fixed, narrow, and well-scoped" vs. "open-ended and shifting."

🧭 Use Cases — recognize these when they happen to you ▾
1 You must score thousands of tabular events per second, and years of labeled history already exist

This is the #1 scenario you'll actually run into. A small trained classifier already fits the data you have and answers each call locally in a few ms — no network round trip, no per-call LLM cost, and it's easier to debug and monitor.

RememberHigh-volume + already-labeled → grab the classic model, not the LLM.
2 You're asked to handle a task with barely any labeled examples, or one that keeps shifting shape

A dedicated classifier can't get off the ground here — this is exactly when an LLM becomes the better fit, handling the task with little or no labeled data and no retraining for each new variant it hasn't seen before.

RememberScarce labels or a shifting task shape → LLM, not a dedicated classifier.
3 Someone suggests routing a clean, high-volume classification job through an LLM "because it's the modern tool"

The job already has ample labeled data and doesn't need an LLM's flexibility, so the LLM route just adds cost and latency for nothing. A common interview trap — candidates often assume "AI-first" thinking is automatically the better engineering call.

RememberModern ≠ better fit — check the job's shape before reaching for the LLM.
🌍 Real-world example ▾

Your team needs to flag risky transactions in real time, thousands per second. A small gradient-boosted classifier trained on transaction features beats routing each one through an LLM — it's cheaper per call, keeps latency low, and there's already plenty of historical labeled fraud data to train it on. Save the LLM for the parts of the same product that are genuinely open-ended, like summarizing a disputed-charge case for a human reviewer.
