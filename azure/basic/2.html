🔥 Azure · Basic · Must Know

App Service — how much of the server is actually yours?

"What is Azure App Service, and what does it manage for you?"

Why it matters ▾
  • Almost always the first hosting question in an Azure interview — the entry point for putting a .NET web app or API in the cloud.
  • Separates candidates who understand PaaS from those who think "cloud" just means "a VM someone else owns for me."
  • Sets up the very next question this track asks: Functions vs. App Service.
🔥 Easy interview recall

App Service = "a managed home for your code — Azure runs the server, you just deploy."

Think: App Service → PaaS, Azure owns the box. VM → IaaS, you own the box.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

App Service is basically a VM you can install anything on. It's PaaS, not IaaS — there's no OS-level access, so you can't run arbitrary background services outside the app's own process model.

🔄 Likely Follow-up

"How is this different from a VM?" A VM (IaaS) requires you to patch and manage the OS yourself; App Service abstracts all of that away.

🎯 Say this in the interview — the exact lines to land

"App Service is PaaS — Azure owns the OS and runtime, you own the code. I just push my app and Azure handles the scaling, patching, and SSL underneath it."

  • Autoscale → Azure adds or removes instances under load, no servers to manage yourself.
  • Deployment slots → swap staging and production with effectively zero downtime.
  • SSL handled → certificates and termination are managed by the platform, not your code.
  • No OS access → that's the PaaS trade-off — full convenience, no server-level control.
📖 Explanation ▾

App Service is Azure's Platform-as-a-Service (PaaS) for hosting web apps, APIs, and mobile backends. You deploy your code — or a container — and Azure runs it: patching the operating system, keeping the language runtime current, load-balancing traffic across instances, and terminating SSL, all without you provisioning or logging into a server.

The trade-off for that convenience is control. Compared to a virtual machine (IaaS), App Service takes over everything below the app itself — that's what makes it fast to ship on, and it's exactly why it can't run arbitrary background processes the way a general-purpose VM can.

App Service (PaaS)Virtual Machine (IaaS)
OS patchingAzure handles ityou handle it
Runtime updatesAzure handles ityou handle it
Scalingautoscale rules, built inyou provision and manage instances
SSLcertificates managed by the platformyou install and renew it yourself
💻 See the code ▾
Azure CLI 
az webapp up --name mywebapp --runtime "DOTNETCORE:8.0"
# no server to create first — this one command does that too

One command creates the App Service plan, creates the app, and deploys the code — Azure provisions everything underneath it.

🌍 Real-world example ▾

A team ships a .NET API to App Service and never once touches server patching — no maintenance windows, no OS updates to schedule. That's time back for the team to spend purely on the application itself, not the box it runs on.
