Adapter — same job, a different-shaped interface

What is the Adapter pattern, and how does it let two incompatible interfaces work together?

🧩 Also see the OOP-angle page: Adapter vs. Facade
Why it matters ▾
🔌 Adapter
❗ ProblemYour code is written against IPaymentGateway.Charge(decimal), but the third-party SDK you must use only exposes ProcessPayment(int cents, string currency) — you can't rewrite either side.
✅ SolutionAn Adapter class implements IPaymentGateway and translates each call into the SDK's actual shape, so the mismatch is isolated inside one small class.
RecallAdapter = implements the interface callers expect, translates calls to the class that doesn't.
🔥 Easy interview recall

Adapter = "makes one interface look like another, without changing either."

Think: Target → the interface callers expect Adaptee → the incompatible class you can't change Adapter → implements Target, translates to Adaptee

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Adapter changes behavior." It doesn't — it only changes the interface shape. If you need new behavior layered on top of the call, that's Decorator, not Adapter.

🔄 Likely Follow-up

"Isn't there a 'class adapter' version too?" GoF's original class adapter uses multiple inheritance to adapt the Adaptee directly. C# doesn't support that for classes, so the object adapter shown here — composition, holding a reference to the Adaptee — is the idiomatic C# shape, and the only one worth knowing.

🎯 Say this in the interview — the exact lines to land

"Adapter converts the interface of a class into another interface my code expects, so two pieces with mismatched shapes can work together. I write one small class that implements the interface I need and holds a reference to the incompatible class, translating each call. It changes the shape of the call, never the behavior underneath."

  • Adapter → converts one interface into another the client expects.
  • Structure → Target interface, Adaptee the incompatible class, Adapter translates between them.
  • C# shape → the object adapter (composition) — holds a reference, not multiple inheritance.
  • Versus Decorator → Adapter changes the interface; Decorator keeps it and adds behavior.
📖 Explanation ▾

An Adapter sits between two pieces of code that should work together but can't, purely because of how each one's interface is shaped. The Target is the interface your code already expects. The Adaptee is the existing class you can't or won't change — usually a third-party SDK or legacy code. The Adapter implements Target and holds a reference to an Adaptee instance, translating every call it receives into the Adaptee's own method shape.

This composition-based shape is called the object adapter — it's the one that's idiomatic in C#. GoF's original book also describes a class adapter, built with multiple inheritance so the adapter directly inherits from the Adaptee. C# classes can't do that, so that variant isn't covered here; every real C# adapter you'll see is an object adapter.

The adapter's whole job is translation, not transformation — it never decides to do something different, it only speaks the Adaptee's language on the Adaptee's behalf. The moment you want genuinely new behavior layered on top of a call, you've left Adapter territory and need a Decorator instead.

💻 See the code ▾
C# 
public interface IPaymentGateway   // Target — the interface your code expects
{
    void Charge(decimal amount);
}

public class LegacyBillingSdk   // Adaptee — can't change this, it's third-party
{
    public void ProcessPayment(int cents, string currency) { /* ... */ }
}

Two unrelated shapes: your app wants Charge(decimal), the SDK only offers ProcessPayment(int, string).

C# 
public class PaymentGatewayAdapter : IPaymentGateway   // ✅ object adapter
{
    private readonly LegacyBillingSdk _sdk;
    public PaymentGatewayAdapter(LegacyBillingSdk sdk) => _sdk = sdk;   // holds the Adaptee

    public void Charge(decimal amount)
        => _sdk.ProcessPayment((int)(amount * 100), "USD");   // ✅ translates the call shape
}

The rest of the app only ever talks to IPaymentGateway — it never sees LegacyBillingSdk directly.

🧭 Use Cases — recognize these when they happen to you ▾
1 A third-party SDK has the wrong method shape for your code

Your code expects IPaymentGateway.Charge(decimal) but the SDK only offers ProcessPayment(int, string). The Adapter implements your interface and translates each call into the SDK's shape. This is the main reason to write an Adapter.

RememberImplement what callers expect; translate to what exists.
2 The vendor SDK might be replaced someday

Because the rest of the app only talks to IPaymentGateway, switching SDKs means writing one new adapter class. The calling code does not change.

RememberThe mismatch lives in one small class.
3 You want to add logging or retry around every charge

An Adapter only changes the interface shape; it does not decide to do anything different. If you want new behavior layered on top of a call, that is a Decorator, not an Adapter.

RememberChanging shape → Adapter. Adding behavior → Decorator.
🌍 Real-world example ▾

A travel power-plug adapter. The wall socket's shape didn't change and your appliance's plug didn't change — the adapter just sits between them. Wrapping a third-party SDK behind your own interface is the same move: the rest of your app never touches the SDK's actual shape.
