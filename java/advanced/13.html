⭐ Java · Advanced · Should Know

sleep() holds the lock. wait() lets it go.

"Why does wait() release the lock it's called under, but sleep() doesn't?"

Why it matters ▾
😴 sleep()
❗ ProblemA thread sometimes just needs to pause for a fixed duration without giving up anything it's holding — using the wrong tool for that can accidentally block other threads too.
✅ SolutionThread.sleep() pauses the current thread for a duration without releasing any lock it holds — if it's holding one, every other thread waiting on that lock blocks until sleep() returns.
Recallsleep() = pause, keep the lock.
⏸️ wait()
❗ ProblemA thread waiting for some condition set by another thread (a queue becoming non-empty, a buffer draining) needs to give up the lock while it waits — otherwise the other thread could never acquire it to make the condition true.
✅ SolutionObject.wait() — called while holding that object's monitor, inside a synchronized block — releases the monitor and blocks until another thread calls notify()/notifyAll() on the same object.
Recallwait() = pause, release the lock so someone else can finish the job.
🔔 notify() / notifyAll()
❗ ProblemOnce the condition a waiting thread cared about is actually true, something has to wake it back up — it can't just poll forever.
✅ Solutionnotify() wakes one waiting thread on that object's monitor; notifyAll() wakes all of them. Both must also be called while holding the same monitor.
Recallnotify()/notifyAll() = wake the thread(s) waiting on this object.
🔥 Easy interview recall

sleep() → keeps the lock, just pauses

wait() → releases the lock while paused

notify()/notifyAll() → wakes a waiting thread

Think: sleep() pauses alone. wait() steps aside so someone else can work, then waits to be notify()'d back in.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

wait() must be called inside a loop, not a single if. A spurious wakeup — the thread waking with no notify() having happened, a documented possibility — can return from wait() before the condition it's actually waiting for is true.

🔄 Likely Follow-up

"What happens if notify() is called but no thread is currently waiting?" The notification is simply lost — notify()/notifyAll() don't queue up for a future waiter. This is exactly why the waiting side must always re-check its condition itself, in a loop, rather than assume a wake-up means the condition is now true.

🎯 Say this in the interview — the exact lines to land

"Thread.sleep() pauses the current thread without releasing any lock it holds. Object.wait() — called while holding that object's monitor — releases the monitor and blocks until another thread calls notify()/notifyAll() on the same object, which is the real coordination primitive beneath synchronized."

  • sleep() → keeps every lock it holds while paused.
  • wait() → releases the monitor it was called under while paused.
  • notify()/notifyAll() → wakes waiting thread(s) on that same object.
  • Always call wait() → inside a loop checking the real condition, never a single if.
  • A notify() with nobody waiting → is simply lost, not queued.
📖 Explanation ▾

Thread.sleep() is a static method with no relationship to any lock at all — it just parks the current thread for roughly the requested duration. If that thread happens to be holding a lock when it calls sleep(), the lock stays held for the entire pause, and every other thread waiting on it blocks right along with it. That's rarely what anyone actually wants, which is exactly why sleep() belongs to situations with no lock coordination involved — a fixed retry delay, a rate-limiting pause.

Object.wait() exists specifically for the opposite case: a thread that needs to pause until another thread changes something, without blocking that other thread from making the change. Called while holding the object's monitor (inside a synchronized block on that object), wait() atomically releases the monitor and parks the thread — letting another thread acquire that same monitor, do its work, and call notify()/notifyAll() to wake the waiter back up. The woken thread then has to re-acquire the monitor before continuing, and per the JLS, a wakeup can occur without any notify() at all (a "spurious wakeup") — which is why the waiting side must re-check its actual condition in a loop, never assume a return from wait() alone means the condition is now true.

💻 See the code ▾
Java 
synchronized (lock) {
    updateSharedState();
    Thread.sleep(5000); // ❌ still holding "lock" for all 5 seconds
}

Every other thread waiting on lock blocks for the full pause — sleep() has no idea a lock is even involved.

Java 
// consumer
synchronized (queueLock) {
    while (queue.isEmpty()) {   // ✅ loop, not if — guards spurious wakeups
        queueLock.wait();     // releases queueLock while paused
    }
    Item item = queue.poll();
}

// producer
synchronized (queueLock) {
    queue.add(newItem);
    queueLock.notify();      // ✅ wakes one waiter — re-checks the while above
}

The consumer gives up queueLock entirely while waiting — that's the only reason the producer can ever acquire it to add an item.

🧭 Use Cases — recognize these when they happen to you ▾
1 A retry loop just needs to back off for a fixed delay

A fixed back-off delay before retrying, with no shared lock in the picture at all, is exactly what sleep() is for — simple and correct.

RememberNo lock, no coordination → sleep() is enough.
2 A consumer thread waits until a shared buffer has an item

A consumer that needs to pause until another thread changes a shared condition is the textbook wait()/notify() case — releasing the lock while paused is what lets the producer in to make the change.

RememberWaiting on another thread's change → wait()/notify(), not sleep().
3 wait() is called inside an if instead of a while

A spurious wakeup can return from wait() with the condition still false — checking it once in an if before the call lets the thread proceed on a condition that was never actually satisfied.

Rememberif + wait() → re-check missed. Always use while.
🌍 Real-world example ▾

sleep() is like stepping away from a shared meeting-room table for a nap without giving up your seat — nobody else can sit down. wait() is like actually getting up and giving the seat away, agreeing to come back only once someone taps you (notify()) to say your turn is ready.
