UseHttpsRedirection + HSTS — why redirecting alone leaves the first request exposed

"What's the difference between UseHttpsRedirection and HSTS, and why can't redirection alone protect the first request?"

Why it matters ▾
🔀 UseHttpsRedirection
❗ ProblemA request that arrives over plain http could be handled by the rest of the pipeline unencrypted.
✅ SolutionThe middleware answers it with a redirect to the https URL, early, so nothing downstream handles the plain version.
RecallRedirection = the server bounces http to https.
🧠 HSTS
❗ ProblemRedirection still lets the browser send that first plain-http request every time it starts from an http:// link.
✅ SolutionThe server sends a Strict-Transport-Security header over https; the browser then goes straight to https for that host until max-age runs out.
RecallHSTS = the browser remembers "never http again".
🔥 Easy interview recall

UseHttpsRedirection → the server redirects http to https

UseHsts → the browser remembers to skip http

Think: Redirection fixes this request's next hop. HSTS fixes future first hops.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming the redirect protects the very first request. It only answers a plain-http request that has already arrived, so that first request travelled unencrypted. HSTS cannot help that very first visit either, because the browser has not seen the header yet.

🔄 Likely Follow-up

"The app sits behind a load balancer that handles TLS — what goes wrong?" The app only ever sees plain http, so it can think every request needs a redirect and bounce forever. Run UseForwardedHeaders first so the app learns the original scheme from X-Forwarded-Proto.

🎯 Say this in the interview — the exact lines to land

"UseHttpsRedirection answers a plain-http request with a redirect to https, but that first request has already left unencrypted. HSTS closes the gap for later visits: the server sends a Strict-Transport-Security header over https, and the browser then refuses to use http for that host until max-age expires. In production TLS usually ends at the proxy, so the app needs forwarded headers to know the original scheme."

  • Redirection → server bounces http to https — a redirect (307 by default), placed early in the pipeline.
  • HSTS → browser remembers "https only" — via the Strict-Transport-Security header, for max-age.
  • Behind a proxy → forwarded headers first — otherwise the app thinks every request is plain http.
  • Dev vs. prod → dev certificate locally, real certificate in production — and UseHsts normally stays out of Development.
📖 Explanation ▾

UseHttpsRedirection is middleware. When a request arrives over plain http, it replies with a redirect to the https address (status 307 by default; the status code is configurable). It sits early, so nothing later in the pipeline handles the plain request. It is a server-side fix: the browser still sent that first request unencrypted.

HSTS (app.UseHsts()) adds a Strict-Transport-Security header to https responses, with a max-age (30 days by default; change it with AddHsts). A browser that has seen it will upgrade http to https by itself before sending anything. Browsers ignore the header when it arrives over plain http, and the default setup skips localhost. The very first visit stays exposed unless the host is on the browser preload list.

Locally, Kestrel uses a development certificate (dotnet dev-certs https --trust). In production, TLS is usually ended by a reverse proxy or load balancer that forwards plain http to the app, so call UseForwardedHeaders first and only trust your own proxy. Many teams also redirect at the proxy. More on proxies: Kestrel & Reverse Proxies; on why order matters: Middleware; the filter side of the old combined page: Filters.

💻 See the code ▾
C# 
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddHsts(o => o.MaxAge = TimeSpan.FromDays(365));
builder.Services.Configure<ForwardedHeadersOptions>(o =>
    o.ForwardedHeaders = ForwardedHeaders.XForwardedProto);   // trust only your own proxy

var app = builder.Build();
app.UseForwardedHeaders();       // behind a proxy: restore the original scheme first
if (!app.Environment.IsDevelopment())
    app.UseHsts();               // adds Strict-Transport-Security on https responses
app.UseHttpsRedirection();       // ✅ early: http in, redirect out
app.UseRouting();

Order matters: forwarded headers first, then HSTS and redirection, then everything else.

HTTP 
GET  http://example.com/    ->  307  Location: https://example.com/
GET  https://example.com/   ->  200  Strict-Transport-Security: max-age=31536000

The first line is the unprotected hop; the header on the second is what the browser caches.

🌍 Real-world example ▾

A shop with two doors. The redirect is the guard at the side door who walks you round to the secure entrance every single time; HSTS is the note you keep in your pocket after that, saying "always use the secure entrance for this shop," so you never bother the side door again.
