ACID — the four promises a transaction makes

"What does ACID actually stand for, and what does each letter guarantee?"

Why it matters ▾
  • The literal opening question in almost every SQL interview about transactions — expect to define all four letters cold, not just name them.
  • Mixing up "Consistency" here with the CAP theorem's version is one of the fastest ways to lose credibility on this exact question.
  • Sets up every later transaction topic on this site — Isolation is the hook into isolation levels, locking, and deadlocks.
🔥 Easy interview recall

A → all-or-nothing.

C → never leaves data broken.

I → concurrent transactions don't see each other's mess.

D → survives a crash the instant it commits.

Think: each letter is its own separate guarantee, and Isolation is the one with its own adjustable strictness dial (isolation levels).

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Consistency in ACID means the same thing as consistency in the CAP theorem. It doesn't — ACID's Consistency means a transaction only ever moves the database between states that satisfy its own constraints, while CAP's consistency is about every node in a distributed system seeing the same data at the same time. Same word, genuinely different concept.

🔄 Likely Follow-up

"Which letter does an isolation-level setting actually control?" Isolation — the isolation level (Read Uncommitted, Read Committed, Repeatable Read, Serializable) is exactly the dial that decides how strictly the "I" guarantee is enforced, trading strictness for concurrency.

🎯 Say this in the interview — the exact lines to land

"ACID stands for Atomicity, Consistency, Isolation, and Durability — the four guarantees a database gives every transaction. Atomicity makes it all-or-nothing, Consistency keeps every constraint intact, Isolation hides one transaction's in-progress work from every other transaction, and Durability makes a commit survive a crash right after it happens."

  • Atomicity → the whole transaction succeeds, or none of it does.
  • Consistency → only ever moves between valid states — not the CAP-theorem meaning of the word.
  • Isolation → concurrent transactions never see another one's uncommitted work.
  • Durability → once committed, the result survives a crash right after.
  • Isolation level → the actual dial — Read Uncommitted through Serializable trade strictness for concurrency.
📖 Explanation ▾

A transaction can bundle several statements together. Atomicity treats them as one unit — the engine only finalizes a transaction if every statement inside it completes; if one fails, everything else already run in that same transaction gets undone too, not just the one that failed. Consistency means a commit can never land in a state that breaks a constraint the database already knows about — a primary key, a foreign key, a check constraint. It's a different idea from the "C" in the CAP theorem, which is about distributed nodes agreeing on the same data — same word, unrelated definitions.

Isolation stops one transaction from seeing another's half-finished work while it's still running. How strict that protection is isn't fixed — the isolation level (Read Uncommitted, Read Committed, Repeatable Read, Serializable) is the setting that controls it, trading stronger guarantees for lower concurrency as you move up that list.

Durability is the promise that survives the database process itself — once a commit is acknowledged, the result has to still be there after a crash or restart. Most relational engines get this by writing the change to a transaction log on durable storage before the commit finishes, so the log can replay it if everything in memory is lost.

💻 See the code ▾
SQL 
BEGIN TRAN;

UPDATE Accounts SET Balance = Balance - 100 WHERE AccountId = 1;  -- money leaves account 1
UPDATE Accounts SET Balance = Balance + 100 WHERE AccountId = 2;  -- money arrives in account 2

COMMIT TRAN;   -- ✅ only now is the transfer real

Between BEGIN TRAN and COMMIT TRAN, both updates only exist inside the transaction — a crash right here has to undo both, not just the one that already ran.

SQL 
BEGIN TRY
    BEGIN TRAN;
    UPDATE Accounts SET Balance = Balance - 100 WHERE AccountId = 1;
    UPDATE Accounts SET Balance = Balance + 100 WHERE AccountId = 2;
    COMMIT TRAN;
END TRY
BEGIN CATCH
    ROLLBACK TRAN;   -- ❌ undo whatever already ran — neither update survives
END CATCH

Atomicity is what guarantees the ROLLBACK erases the first UPDATE too — without it, account 1 could lose money that never arrives anywhere.

🌍 Real-world example ▾

A bank transfer is money leaving one account and arriving in another, treated as a single unit. A crash halfway through must never leave the money sitting in neither account, or somehow in both — the whole transfer either happens completely or it never happened at all.
