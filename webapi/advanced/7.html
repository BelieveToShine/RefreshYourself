Gateway vs. BFF — one front door, or one door per client?

"What does an API gateway do, and how is a BFF different?"

Why it matters ▾
🚪 Gateway & BFF
❗ ProblemWith many services, every client would need every address, and every service would repeat the same auth and rate-limit code — while a phone and a web app want very different data.
✅ SolutionA gateway gives all clients one entry point and does the shared jobs once; a BFF goes further and gives each client type its own backend shaped to its needs.
RecallGateway = one front door. BFF = one door per client type.
🔥 Easy interview recall

Reverse proxy → forwards traffic

API gateway → one entry + shared rules

BFF → one per client type

Think: A proxy forwards. A gateway forwards and enforces rules. A BFF also shapes data for one client.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 The BFF variant — same idea, one backend per client type
⚠️ Common Trap

"A BFF is just another name for an API gateway." A gateway is one shared entry point for every client; a BFF is built for one client type and shapes its data, so you often run several.

🔄 Likely Follow-up

"Isn't the gateway a single point of failure?" It can be — so run several copies behind a load balancer, and keep it thin: routing and shared rules only, no business logic, or it becomes a bottleneck.

🎯 Say this in the interview — the exact lines to land

"An API gateway is the single entry point for all clients — it routes requests and handles shared jobs like auth, rate limiting and aggregation. A BFF is a gateway-style backend built for one client type, such as web or mobile, that shapes data for that client."

  • Gateway → single entry point: routing, auth offload, rate limiting, TLS.
  • Gateway can aggregate several service calls into one response.
  • BFF → one backend per client type, shaped for that client.
  • Reverse proxy → just forwards; a gateway adds API-aware rules.
  • Keep it thin — no business logic in the gateway.
  • Single point of failure → several instances behind a load balancer.
📖 Explanation ▾

An API gateway is the single front door for all clients. It routes each request to the right service and handles shared jobs in one place: checking the token, rate limiting, TLS, logging, caching, and sometimes combining several service calls into one response. The services behind it stay simpler.

A reverse proxy just forwards traffic (and can spread load) — see Kestrel & Reverse Proxies. A gateway is a reverse proxy plus API-aware rules. A BFF (Backend for Frontend) is a gateway-style server built for one client type: the web BFF and the mobile BFF each return exactly the shape their client needs, so a phone makes one slim call instead of five. The two ideas can be combined. This is the server-side answer to Designing for Multiple Client Types, and it is also where tokens can be kept away from the browser (see Token Storage).

The caveats: a gateway is a single point of failure and a possible bottleneck, so run several instances. Keep business logic out of it, or it becomes a hidden monolith. In .NET, YARP (a reverse-proxy library) and Ocelot are common choices; cloud platforms offer managed gateways such as Azure API Management and AWS API Gateway. Check current docs for setup. See also Distributed Systems Considerations.

💻 See the code ▾
JSON 
{
  "ReverseProxy": {
    "Routes": {
      "orders": {
        "ClusterId": "ordersCluster",
        "Match": { "Path": "/orders/{**catch-all}" }
      }
    },
    "Clusters": {
      "ordersCluster": {
        "Destinations": {
          "d1": { "Address": "https://orders.internal/" }
        }
      }
    }
  }
}

A gateway route written as config with YARP, a .NET reverse-proxy library: requests to /orders/... go to the orders service. The exact config shape can change — check the current YARP docs.

C# 
builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));

app.MapReverseProxy();

Two lines wire the proxy into the app. Auth, rate limiting and other policies are added on top.

C# 
app.MapGet("/mobile/home", async (IHttpClientFactory factory) =>
{
    var http = factory.CreateClient();
    var order = await http.GetFromJsonAsync<OrderDto>("https://orders.internal/orders/latest");
    var stock = await http.GetFromJsonAsync<StockDto>("https://stock.internal/summary");
    return new { order, stock };
});

A BFF endpoint: the phone makes one call, and the BFF fans out to two services and returns one slim result.

🌍 Real-world example ▾

A gateway is a hotel front desk: every guest goes there, and the desk checks their key card and sends them to the right department. A BFF is a personal concierge per guest type — one for business travellers, one for families.

Scenario: the mobile home screen needed four separate calls. A mobile BFF makes those calls on the server and returns one slim response.
