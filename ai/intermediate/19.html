Reasoning models — pay for thinking only when the question needs it

"When would you use a reasoning model instead of a regular one, and what does it cost you?"

Why it matters ▾
💭 Reasoning Models
❗ ProblemSome questions — multi-step logic, tricky code, planning — go wrong when a model answers in one quick pass. But making every call "think harder" makes every call slower and more expensive.
✅ SolutionUse a reasoning model for the hard steps only: it spends extra hidden thinking tokens before it answers (test-time compute), so you trade latency and cost for accuracy exactly where accuracy needs it.
RecallReasoning model = more thinking → better on hard tasks, slower and pricier on all of them.
🔥 Easy interview recall

Reasoning model = "think first, answer second — and you pay for the thinking."

Think: Hard multi-step task → worth the extra thinking Simple extract / classify / chat → don't pay for it

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A reasoning model isn't just a "better" model. It is a model that spends more tokens thinking. On easy tasks that only adds delay and cost, and it can still be wrong — so choose by task, then check on your own eval set.

🔄 Likely Follow-up

"How do you keep the cost under control?" Lower the effort or thinking-budget setting if your provider offers one (names differ — check current docs), cap the output length, and send only the hard requests to the reasoning model with model routing.

🎯 Say this in the interview — the exact lines to land

"A reasoning model spends extra hidden thinking tokens working through a problem before it writes the answer — that's test-time compute. I use it for multi-step logic, code and planning, where accuracy matters more than speed. I keep a regular model for extraction, classification and chat, because thinking adds latency and is billed as tokens."

  • Hard, multi-step task → reasoning model; the extra thinking is where the accuracy comes from.
  • Simple task → regular model; thinking just burns time and money.
  • Cost → thinking tokens are normally billed like output tokens, so the bill grows even when the visible answer is short (check your provider's pricing page).
  • Control → many providers give an effort or thinking-budget setting; names differ, so check current docs.
  • Decide with data → run both on your own eval set, then route only the hard requests.
📖 Explanation ▾

A regular model reads your prompt and starts writing the answer straight away. A reasoning model first writes a long stretch of hidden "thinking" — trying steps, checking itself, backing up — and only then writes the answer. Giving the model more work at answer time, instead of a bigger model, is called test-time compute.

It wins where one quick pass tends to slip: multi-step logic, maths-style problems, tricky code, planning with rules. It costs you time (a longer wait before the first visible word) and tokens (thinking is normally billed like output, even if you only see a summary of it, or none). Check your provider's docs for how thinking is shown and billed.

It is the same idea as chain-of-thought prompting, but done by the model itself — so you often don't need to ask for "step by step". For picking a model family see Model Families; for the bill see Cost Control.

🌍 Real-world example ▾

A support bot sorting tickets into categories is fine on a regular model — fast and cheap. The same team asks a model why a nightly billing job double-charges some customers: that is where a reasoning model earns its extra seconds and tokens.
