Embedding — meaning turned into numbers you can measure

"What is an embedding, and what does cosine similarity actually measure?"

Why it matters ▾
🔢 Embedding call
❗ ProblemSearch, clustering, and dedup all need a fast, comparable score for "how close in meaning are these two pieces of text" — not a written-out answer.
✅ SolutionAn embedding call skips generation entirely: one forward pass turns text into one fixed-length vector, and cosine similarity scores how close two of those vectors are.
RecallEmbedding call = one forward pass → one static vector, used for search/similarity — not for generating text.
💬 Chat completion call
❗ ProblemGetting an actual answer, summary, or reply back is impossible from a single static vector — a vector has no words in it to read.
✅ SolutionA chat completion call runs autoregressively, generating a stream of tokens one at a time until it has produced the actual reply.
RecallChat completion call = token-by-token generation of new text — not a static representation of meaning.
🔥 Easy interview recall

Embedding = "a list of numbers that stands in for meaning — close numbers mean close meaning."

Think: "cat" and "dog" land near each other; "car" lands far away.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A bigger/longer vector isn't a stronger match. Cosine similarity ignores a vector's length entirely — it only measures the angle between two vectors, which is exactly why embeddings get normalized to unit length before comparing them.

🔄 Likely Follow-up

"So why normalize the vectors before comparing them?" Once both vectors are unit length, cosine similarity reduces to a plain dot product — only direction affects the score, not magnitude differences that don't actually reflect meaning.

🎯 Say this in the interview — the exact lines to land

"An embedding is a fixed-length vector of numbers that captures a piece of text's meaning — similar meanings land close together in that space, and cosine similarity is how we score how close two vectors actually are."

  • Embedding → one forward pass, one static vector — not autoregressive generation like a chat reply.
  • Cosine similarity → measures the angle between two vectors, not their length.
  • Normalize first → so only direction, never magnitude, decides the score.
  • Used for → semantic search, RAG retrieval, clustering, dedup, and nearest-neighbor classification.
  • Different embedding models → not directly comparable — different dimension counts, different training data.
📖 Explanation ▾

An embedding is a fixed-length list of floating-point numbers — produced for a piece of text (or an image) by an embedding model. That list is a point in a high-dimensional space, and the model places texts with similar meaning near each other in that space, and unrelated texts far apart. Producing it is a single forward pass through the model: text goes in, one static vector comes out — nothing like the token-by-token loop a chat completion runs.

To score how close two of those points actually are, the standard tool is cosine similarity — it measures the angle between two vectors, ignoring how long each one is. That's why embeddings are almost always normalized to unit length first: once both vectors have the same length, only their direction affects the score, so cosine similarity reduces to a simple dot product.

One catch: embedding models differ — how many numbers they output and what text they were trained on both vary — so a vector from one model can't be compared against a vector from a different model. Once you have comparable vectors, the same trick powers semantic search, retrieval for RAG, clustering, deduplication, and nearest-neighbor classification.

💻 See the code ▾
Python 
vector = embed("cat")
# → [0.02, -0.15, 0.88, …] — one call in, one vector out

One call, one static vector — no streaming, no follow-up tokens.

Python 
def cosine(a, b):
    a = a / norm(a)  # unit length
    b = b / norm(b)  # unit length
    return dot(a, b)  # direction only, magnitude is gone

Once both vectors are unit length, cosine similarity is just their dot product.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're building semantic search or RAG retrieval over a set of documents

You call embed() once per document (and again for the query), then rank by cosine similarity — the same "sneakers" vs. "running shoes" example on this page: no shared words, but close vectors surface the match a keyword search misses.

RememberSemantic search = embed() + cosine similarity ranking, not a chat completion call.
2 You need to flag near-duplicate text — e.g. two support tickets describing the same issue in different words

Embed each item and compare vectors with cosine similarity — pairs above a similarity threshold get flagged as duplicates. This is the same clustering/dedup use from this page's keypoints list, all built on comparing static vectors — no reply ever gets generated.

RememberDedup/clustering = compare embedding vectors, never a generated reply.
3 A user actually needs a written answer back — a summary, an explanation, a generated reply

That's a chat completion call, not an embedding call — the model generates a stream of tokens autoregressively until it has produced actual words to read, the exact opposite job of the embedding call's single static vector.

RememberNeed words back → chat completion call; need a comparable score → embedding call.
🌍 Real-world example ▾

A shopper searches "sneakers" but the product is titled "running shoes" — no words in common. A keyword search misses it; an embedding-based search doesn't, because both phrases land near each other in meaning-space, so a nearest-neighbor lookup finds the match a plain text match never would.
