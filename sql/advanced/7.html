Bulk Loads — same rows, logged one at a time or logged as one big allocation

What makes a bulk insert or update fast at the database's own level, separate from anything an ORM does on top of it?

Why it matters ▾
  • Bulk data jobs — nightly loads, migrations, archiving millions of rows — are routine production work, and the naive way to write one is a classic performance and operational trap: a blown-out transaction log, disk pressure, or hours of blocking.
  • Interviewers use this to check whether you understand what the storage engine itself is doing during a large write, not just which method or keyword to call.
  • A very common senior/architect follow-up: "why would you drop indexes before a huge bulk load instead of leaving them in place?" — see the Follow-up box below.
🔥 Easy interview recall

Logging → minimal beats full — log the allocation, not every row

Batch size → bounds log growth and lock duration

Indexes → drop, load, rebuild once — not row by row

Think: three separate knobs — logging, batch size, indexes — and all three trade a little care up front for a lot less total load time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Loading millions of rows straight into a heavily-indexed table, in one giant batch, is not automatically "the fast way" just because it's one statement. Every index still has to be maintained row by row and the whole load logs and locks as one massive transaction — often far slower, and far riskier for the log and disk, than dropping the indexes and batching the load first.

🔄 Likely Follow-up

"Why would you deliberately drop indexes before a huge bulk load instead of leaving them in place?" Leaving them means every single inserted row incrementally updates every index's structure, one at a time; dropping them and rebuilding once after all the data is loaded is a single efficient sorted build instead of millions of incremental updates.

🎯 Say this in the interview — the exact lines to land

"A bulk load is fast at the database's own level for three separate reasons: minimal logging skips the row-by-row detail and only records that a bulk extent was allocated, batching bounds how much log growth and lock time any one commit holds, and dropping non-critical indexes before the load — then rebuilding them once at the end — turns millions of incremental index updates into a single efficient sorted build."

  • Minimal logging → logs the allocation, not every row — much less log-write overhead, but only under the right recovery model and conditions.
  • Batch size → bounds log growth and lock duration — commit every tens of thousands of rows instead of one giant transaction.
  • Indexes → drop before the load, rebuild once after — one sorted build beats millions of row-by-row updates.
  • This is the engine's own side of the problem → different from an ORM skipping entity tracking — the rows are already arriving as SQL.
📖 Explanation ▾

Minimal logging is the primary lever at the database's own level. A normal write has to log enough detail to replay or undo every single row change — that's what point-in-time recovery depends on. A bulk load under the right conditions (the right recovery model, no existing data being overwritten, certain table and index states) can instead log only enough to know that a bulk extent of pages was allocated, not the full row-by-row detail. That's a dramatically smaller amount of log to write, and it's most of why a well-configured bulk load beats the equivalent one-row-at-a-time inserts.

Batch size is a separate, practical lever. Loading everything as one giant statement or transaction can grow the transaction log far past what a single load should need, and holds locks on the affected rows for as long as that one transaction runs. Committing every tens of thousands of rows instead trades a small amount of overhead for bounded log growth and much shorter lock duration. Indexes add a third cost: every index on a table has to be updated as each new row lands. For a genuinely massive load, it's often faster to drop non-critical indexes first, load the data, then rebuild each index once at the end — one large, efficient sorted build instead of millions of small incremental updates.

This is the database engine's own side of bulk performance — a different angle from EF Core's ExecuteUpdate()/ExecuteDelete() (see EF Core Advanced — Bulk Operations), which speeds things up by skipping the ORM's load-and-track cycle on the application side. Here, the rows are already arriving as SQL — the question is how the engine itself logs, commits, and indexes them once they do.

💻 See the code ▾
SQL 
-- Under the right recovery model and conditions, a bulk load like this can be
-- minimally logged: the engine only records that these pages were allocated,
-- not the full detail of every single row inside them.
SELECT OrderId, OrderDate, Total
INTO Orders_Archive
FROM Orders
WHERE OrderDate < '2020-01-01'; -- ✅ candidate for minimal logging (bulk extent allocation only)

-- An ordinary row-by-row INSERT ... SELECT is logged in full detail regardless
-- of recovery model — there's no bulk extent shortcut for it.
INSERT INTO Orders_Archive (OrderId, OrderDate, Total)
SELECT OrderId, OrderDate, Total
FROM Orders
WHERE OrderDate < '2020-01-01'; -- ❌ full logging: one detailed entry written per row

Minimal logging doesn't skip logging — it logs enough to know a bulk extent was allocated, not a full row-by-row trail. Exact eligibility (recovery model, table/index state) varies by engine and version.

SQL 
-- 5 million rows in ONE transaction: log growth and lock duration scale with
-- the entire load, and every other reader/writer waits behind it.
BEGIN TRANSACTION;
    INSERT INTO Orders_Archive
    SELECT * FROM Orders WHERE OrderDate < '2020-01-01';
COMMIT; -- ❌ one giant commit holds locks and log space for all 5 million rows

-- Same load, in batches of 50,000 — each INSERT auto-commits on its own,
-- so no single transaction ever holds the whole load.
DECLARE @Rows INT = 1;
WHILE @Rows > 0
BEGIN
    INSERT INTO Orders_Archive
    SELECT TOP (50000) * FROM Orders
    WHERE OrderDate < '2020-01-01'
      AND OrderId NOT IN (SELECT OrderId FROM Orders_Archive);
    SET @Rows = @@ROWCOUNT; -- ✅ each batch is its own short, bounded commit
END;

The one-giant-transaction version holds every lock and every byte of log space for the whole load. The batched loop trades a bit of loop overhead for a bounded, predictable footprint per commit.

SQL 
-- A table with several indexes: every inserted row updates every index too
-- ❌ millions of incremental index-page updates during the load, one per row per index

DROP INDEX IX_Orders_CustomerId ON Orders;
DROP INDEX IX_Orders_OrderDate ON Orders;

-- ... bulk load millions of rows here, with no index maintenance cost ...

CREATE INDEX IX_Orders_CustomerId ON Orders(CustomerId);
CREATE INDEX IX_Orders_OrderDate ON Orders(OrderDate); -- ✅ one efficient sorted build, not millions of updates

Dropping the index doesn't remove the work — it defers it to one sorted build at the end, which is far cheaper than millions of incremental page updates during the load.

🌍 Real-world example ▾

Scenario: a nightly job needs to load 200 million historical rows into a reporting table before the morning reports run, without blowing out the transaction log or blocking other traffic. The practical answer combines all three levers: run the load in a statement shape and recovery model that's eligible for minimal logging, load in batches of tens of thousands of rows so no single commit holds locks or log space for the whole 200 million, and drop the table's non-critical indexes before the load so they can be rebuilt once, in one efficient sorted pass, instead of being maintained row by row for 200 million inserts.
