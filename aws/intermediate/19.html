CloudFront caches at the edge — from almost any origin you point it at

"What can act as a CloudFront origin, and how do signed URLs control access to cached content?"

Why it matters ▾
📍 CloudFront
❗ ProblemServing static or media content straight from one origin — an S3 bucket, an ALB, or a custom HTTP origin — means every user's request travels all the way back to that one place, which is slow for users far from it and piles the full load of repeat requests onto the origin itself.
✅ SolutionCloudFront caches responses at edge locations close to users, so most requests never reach the origin at all — and a signed URL or signed cookie can still gate access to private content sitting behind that cache, without ever making the origin itself public.
RecallCloudFront = caches at the edge, from almost any origin — signed URLs gate private content without exposing that origin.
🔥 Easy interview recall

CloudFront = "caches content at the edge, from almost any origin."

Think: a signed URL gates private content without ever making the origin itself public.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Invalidating the cache is instant and free." Invalidation requests have a free tier but cost money beyond it and still take real time to propagate across edge locations — versioned URLs (a new path per release) are often the cheaper, faster alternative to repeated invalidations.

🔄 Likely Follow-up

"CloudFront vs. Global Accelerator — when would you reach for each?" CloudFront caches actual content at the edge (best for cacheable web content); Global Accelerator optimizes network routing to your origin without caching, for non-cacheable, latency-sensitive traffic like gaming or API calls that must always hit the real backend.

🎯 Say this in the interview — the exact lines to land

"CloudFront caches at the edge from any origin — S3, an ALB, or a custom HTTP origin — and signed URLs or signed cookies gate access to private content without exposing the origin itself. Invalidating the cache costs money and time at scale, so I'd rather bust the cache with versioned URLs than invalidate repeatedly."

  • Origins → S3, an ALB, or any custom HTTP origin — CloudFront isn't tied to one AWS service.
  • Cache key → which request attributes (query strings, headers, cookies) get forwarded decides what counts as a "different" cached response.
  • Invalidation → costs money past the free tier and takes real time to propagate — versioned URLs are often cheaper and faster.
  • Signed URLs / cookies → restrict private content by user and time window, without making the origin public.
📖 Explanation ▾

CloudFront is AWS's CDN — it caches content at edge locations physically close to users, so most requests never have to travel back to the origin at all. That cuts latency for the user and cuts load on the origin. The origin itself can be an S3 bucket, an Application Load Balancer in front of an app, or genuinely any custom HTTP origin that can answer a request — CloudFront doesn't require the origin to be an AWS service.

What gets cached, and for how long, is controlled by the TTL and the cache key — the specific request attributes (query strings, headers, cookies) that CloudFront is told to forward and factor into what counts as a "different" response worth caching separately. Forwarding more attributes into the cache key gives more precise responses per request but fragments the cache into more entries, each cached separately.

For private content, a signed URL or signed cookie lets CloudFront check that a request carries a valid signature tied to a specific time window before serving it — the origin behind it never has to be public, and access can be revoked simply by letting the signature's expiry pass.

🧠 Visual Mental Model — signed URLs gate private content
🧭 Use Cases — recognize these when they happen to you ▾
1 Your site serves the same images, JS bundles, or video to users spread across many countries.

This is the #1 scenario CloudFront exists for — the response gets cached at an edge location close to each user, so nobody's request has to cross an ocean back to the single S3/ALB/custom origin on every load.

RememberSame content, users everywhere → cache it at the edge, don't route everyone to one origin.
2 You're serving a paid video, or any file that shouldn't be downloadable by just anyone who has the URL.

A signed URL or signed cookie lets CloudFront check for a valid signature and time window before serving anything — the origin behind it can stay completely private, and access gets cut off just by letting the signature's expiry pass.

RememberPrivate content → sign the URL/cookie, keep the origin itself locked down.
3 You just pushed new content, ran a cache invalidation, and expect it to be instant and free everywhere.

Invalidation requests have a free tier but cost money beyond it and still take real time to propagate across edge locations — assuming it's instant and free is exactly the trap; a versioned URL (a new path per release) is often cheaper and faster than repeated invalidations.

RememberInvalidation isn't instant or free at scale → prefer versioned URLs.
🌍 Real-world example ▾

A media company serves paid video content through CloudFront using signed URLs with a short expiry, so a leaked link stops working shortly after being shared. Free promotional content is served from the exact same distribution with no signing at all — the same CloudFront setup handles both, just with a gate in front of one and not the other.
