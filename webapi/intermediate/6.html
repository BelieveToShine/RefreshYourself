IActionResult vs. ActionResult<T> — the signature Swagger can actually read

"What's the practical difference between IActionResult and ActionResult<T>?"

Why it matters ▾
  • Interviewers use this to check whether you understand what your controller signature actually promises to tooling, not just which keyword compiles.
  • Comes up any time you're picking a return type for a new endpoint, especially once Swagger/OpenAPI generation and typed client SDKs are part of the pipeline.
  • A common follow-up checks whether you think ActionResult<T> changes the actual HTTP response — a good chance to show you know it's compile-time only.
🔥 Easy interview recall

IActionResult → any result, success type hidden

ActionResult<T> → same flexibility, success type declared

Think: IActionResult is an unlabeled box. ActionResult<T> is the same box with a label on it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

IActionResult isn't deprecated or "the old way." It's still the right return type when an action genuinely has no single typed success shape — a health check that just returns 200 or 500 with no body — ActionResult<T> is only the better default when a real success payload type exists.

🔄 Likely Follow-up

"Does using ActionResult<T> change anything about how the client receives the response over the wire?" No — it's purely a compile-time convenience on the C# side; the actual HTTP response bytes are identical either way. The benefit is entirely in Swagger/OpenAPI generation, IntelliSense, and type safety inside the controller.

🎯 Say this in the interview — the exact lines to land

"IActionResult is the base interface every action result implements — Ok(), NotFound(), Created() all return it — but the signature alone doesn't tell tooling what a successful response looks like. ActionResult<T> lets you return either a raw T or any IActionResult from the same method, so you keep the same flexibility for error paths while the signature also declares the real success type."

  • IActionResult → use it when there's no single typed success shape — a health check returning just 200/500.
  • ActionResult<T> → declares the real success type right in the method signature.
  • Both return the same NotFound()/BadRequest() error paths — nothing is lost by switching.
  • Swagger and client-SDK generators only see an accurate schema with ActionResult<T>, not with IActionResult alone.
📖 Explanation ▾

IActionResult is the base interface every action result implements — Ok(), NotFound(), BadRequest(), Created(), and more all return something that satisfies it. That flexibility is exactly the problem for tooling: without extra attributes like [ProducesResponseType], the method signature only promises "some action result," so Swagger/OpenAPI generation has no automatic way to know what a successful response actually contains.

ActionResult<T> is a generic wrapper around that same idea. It has implicit conversions from both T and from any IActionResult, so a method can return a plain Order object — implicitly wrapped into a 200 OK — or return NotFound() for the failure path, the exact same flexibility as IActionResult. The difference is that the signature now also states the real success type, so Swagger reads that declared T and generates an accurate schema automatically.

Not every action has one clean success shape, though. A health-check endpoint might just return Ok() or StatusCode(500) with no body at all — there, IActionResult is still the correct return type. ActionResult<T> only pays off once there's a real T to declare.

💻 See the code ▾
C# 
[HttpGet("{id}")]
public IActionResult GetOrder(int id)
{
    var order = _repo.Find(id);
    if (order is null) return NotFound();   // ❓ Swagger: return type unclear
    return Ok(order);                            // 200 OK — signature just says "IActionResult"
}

Compiles fine — but Swagger only knows this method returns some IActionResult, not an Order.

C# 
[HttpGet("{id}")]
public ActionResult<Order> GetOrder(int id)
{
    var order = _repo.Find(id);
    if (order is null) return NotFound();   // ✅ still allowed — same flexibility
    return order;                                // implicitly wrapped into 200 OK
}

Same behavior, same flexibility — but now Swagger reads Order as the declared success type.

C# 
[HttpGet("/health")]
public IActionResult HealthCheck()
{
    var healthy = _checker.IsHealthy();
    return healthy ? Ok() : StatusCode(500);   // no body either way — no T to declare
}

No success payload exists here, so ActionResult<T> would add nothing — IActionResult is still the right call.

🌍 Real-world example ▾

Your team wires up Swashbuckle or NSwag to auto-generate a TypeScript client from the Web API. Every action still returning IActionResult produces a generic, untyped response in the generated client. Every action returning ActionResult<T> gives the frontend a properly typed model — switching the return type is often the entire fix needed to get accurate generated types, with no change to the actual logic inside the method.
