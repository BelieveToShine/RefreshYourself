Inference speed — a model writes one token at a time, so who guesses ahead?

"How does speculative decoding speed up generation, and what limits your tokens-per-second when self-hosting?"

Why it matters ▾
⏱️ Inference Performance
❗ ProblemA model writes its answer one token at a time, and every step has to read the model and a growing cache from memory. Self-hosted, that is what limits how fast users see words and how many users you can serve at once.
✅ SolutionKnow the levers: a KV cache so the prompt is never recomputed, continuous batching to keep the GPU busy across many users, and speculative decoding — a small draft model guesses ahead and the big model checks the guesses in one pass.
RecallKV cache = don't redo the past. Batching = share the GPU. Speculative = guess, then verify.
🔥 Easy interview recall

Speculative decoding = "a small model guesses ahead, the big model checks them all at once."

Think: Prefill reads the prompt in one go → sets time-to-first-token Decode makes one token per step → sets tokens per second

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Speculative decoding trades quality for speed." Not in its standard form: the big model checks every guess, and the method is designed to keep the same output distribution as the big model alone. What you pay is extra compute and memory for the draft model — and the speed-up depends on how often the guesses are accepted.

🔄 Likely Follow-up

"Does it always make things faster?" No. If the draft model guesses badly, most guesses are thrown away and the gain shrinks or vanishes. It also helps less when the server is already busy with large batches. Measure on your own traffic.

🎯 Say this in the interview — the exact lines to land

"Generation has two phases: prefill reads the prompt in parallel, and decode makes one token per step while re-reading the KV cache. Self-hosted, speed is limited mainly by GPU memory and memory bandwidth, and by how you batch requests. Speculative decoding speeds up decode: a small draft model proposes several tokens and the big model verifies them in a single pass, keeping the same output distribution (up to numerical precision)."

  • Prefill vs. decode → prefill sets time-to-first-token; decode sets tokens per second.
  • KV cache → saves past attention keys and values so they aren't recomputed; it takes GPU memory that grows with context length and with the number of users.
  • Continuous batching → new requests join the running batch as others finish, so throughput rises; each request may wait a bit longer under load.
  • Speculative decoding → draft proposes, target verifies in one pass; same output distribution, speed-up depends on the acceptance rate.
  • Self-hosting limits → GPU memory, memory bandwidth, batch size and model size; quantization helps by shrinking the weights.
📖 Explanation ▾

Generating text has two phases. Prefill reads the whole prompt at once and builds the KV cache — the saved attention keys and values of every token so far. Decode then produces one token per step, and each step reads the model weights and the cache again, so it is usually limited by memory bandwidth, not raw compute. That is why prefill drives time-to-first-token and decode drives tokens per second. Streaming (Prompt vs. Completion Cost & Streaming) hides the wait by showing words as they arrive. The cache is explained in Transformer Basics.

Continuous batching keeps the GPU busy: instead of waiting for a whole batch to finish, a serving engine lets new requests join as others complete (vLLM is one well-known engine that does this). Bigger batches raise total throughput but can slow each single request, and the KV cache of every active request must fit in GPU memory. Quantization shrinks the weights, which frees memory and cuts the bytes read per step.

Speculative decoding attacks the one-token-per-step wall. A small, fast draft model proposes a few tokens. The big target model checks them all in one pass, keeps the ones that match what it would have produced, fixes the first wrong one, and moves on. The accept-or-reject rule is built so the final text follows the same distribution as the target alone. Some variants avoid a separate draft model (vLLM lists n-gram, EAGLE and MTP among its methods). Whether to run all this yourself is the question on Self-Hosted vs. Managed Models; for non-interactive work, queue-based inference trades latency for throughput.

🌍 Real-world example ▾

A self-hosted chat feature gets slow at peak hours. The first word still appears quickly, but streaming crawls. The team checks GPU memory (the KV caches of many users are filling it), turns on continuous batching, quantizes the weights, and tests speculative decoding on real traffic to see if the acceptance rate justifies it.
