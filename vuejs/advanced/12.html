Unit, component, E2E — which test actually catches which bug

"How would you structure a real Vue app's test suite across unit, component, and E2E layers?"

Why it matters ▾
🧪 Testing strategy
❗ ProblemTesting everything at one layer either misses real bugs (unit tests alone never catch a broken page flow) or makes the suite painfully slow and brittle (E2E tests alone take forever and break on unrelated UI changes).
✅ SolutionSplit coverage across three layers by what each is actually good at: many fast unit tests for logic, a solid middle layer of component tests for template/logic integration, and a small number of E2E tests for the critical flows only.
RecallMore tests the lower/faster the layer — fewer the higher/slower it gets.
🔥 Easy interview recall

Unit → fast, logic only, no DOM

Component → medium, real component + template

E2E → slow, real browser, real app

Think: a pyramid — many unit tests at the base, few E2E tests at the top.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"E2E is the most realistic, so test everything there" is backwards. E2E is also the slowest and most brittle layer — the standard guidance is many unit tests, a solid middle layer of component tests, and only a small number of E2E tests for critical flows.

🔄 Likely Follow-up

"Where would testing a Pinia store itself fit?" Largely at the unit level — a store's actions/getters are plain-enough logic to test directly without mounting any component, same as testing a composable.

🎯 Say this in the interview — the exact lines to land

"Unit tests target a composable or plain function in isolation — fast, no DOM. Component tests mount a real component with Vue Test Utils and assert on rendered output and interaction. E2E tests drive a real browser against the running app — slow, but the only layer that catches real cross-page and network issues. Most of the suite should be unit tests, a smaller set component tests, and only critical flows covered end-to-end."

  • Unit → logic in isolation, no DOM, fastest to run.
  • Component → template + logic together, medium speed.
  • E2E → real browser, real app — slow, so keep it to critical flows.
  • Pinia store logic → test at the unit level, same as a composable.
📖 Explanation ▾

Unit tests call a composable or plain function directly and assert on its return value — no component, no template, no DOM at all. They're the cheapest tests to write and the fastest to run, which is exactly why there should be the most of them.

Component tests, using Vue Test Utils, actually mount a real component and let its template render — this is the layer that catches a bug where the logic is correct but the template binds it wrong (a typo'd prop name, a missing v-if). It's slower than a unit test because it has to render, but far faster than spinning up a real browser.

E2E tests (Cypress, Playwright) drive an actual browser against the actual running app, including real network calls. They're the only layer that catches a genuinely cross-page or cross-service issue — but they're slow and more likely to break from an unrelated UI change, which is why they're reserved for the handful of flows that matter most (checkout, login).

💻 See the code ▾
Vue 
// unit test — no component, no DOM
import { useCounter } from './useCounter'

test('increments the count', () => {
  const { count, increment } = useCounter()
  increment()
  expect(count.value).toBe(1)   // ✅ just calling a function
})

No rendering happens here at all — this is as fast and cheap as a test gets.

Vue 
// component test — mounts the real component
import { mount } from '@vue/test-utils'
import Counter from './Counter.vue'

test('clicking the button updates the displayed count', async () => {
  const wrapper = mount(Counter)
  await wrapper.find('button').trigger('click')
  expect(wrapper.text()).toContain('1')  // ✅ catches a template/logic mismatch
})

This catches a bug a unit test can't — the logic could be correct while the template binds it to the wrong place.

Vue 
// E2E test — a real browser against the running app
it('completes checkout', () => {
  cy.visit('/cart')
  cy.get('[data-test=checkout]').click()
  cy.get('[data-test=confirmation]').should('be.visible')
  // ✅ real navigation, real network calls — reserved for critical flows
})

Slow enough that only the handful of flows that truly matter get this level of coverage.

🧭 Use Cases — recognize these when they happen to you ▾
1 A price-calculation composable used across several components

Discount math has no DOM dependency at all — call it directly with a range of inputs. This is the cheapest, most valuable place to put edge-case coverage (zero, negative, over-100%-off).

RememberNo DOM involved → it belongs at the unit layer.
2 A form that should show a validation error on bad input

This needs the actual template to react to state — mount the component, trigger the input, and assert the error message actually shows up in the rendered output.

RememberDoes the template react correctly? → component test.
3 The checkout flow, end to end

Checkout spans multiple pages and a real payment call — exactly the cross-page, cross-service behavior only an E2E test actually exercises. It's slow, so it's one of the very few flows that earns this level of test.

RememberSpans pages/services and it's business-critical → E2E, sparingly.
🌍 Real-world example ▾

A mid-size e-commerce app with hundreds of components. Its suite might run 800 unit tests covering composables and store logic, 150 component tests covering individual UI pieces, and 10 E2E tests covering login, search, and checkout — the shape of the pyramid in practice, not just in theory.
