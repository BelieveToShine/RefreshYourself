Repository over EF Core — a layer on top of a layer?

Do you need a repository pattern on top of EF Core?

Why it matters ▾
🧱 Extra layer
❗ ProblemWrapping EF Core in a generic IRepository<T> is a habit from older data access — but it often just forwards calls and hides the features that make EF Core useful.
✅ SolutionDbSet<T> is already a repository and DbContext is already a unit of work, so add a wrapper only when it has a real job: named queries, a testing seam, an aggregate boundary.
RecallDbSet = repository. DbContext = unit of work. Wrap only for a reason.
🔥 Easy interview recall

DbSet<T> → already a repository

DbContext → already a unit of work

Your wrapper → only if it earns its place

Think: Don't wrap what is already wrapped — a layer needs a job.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A generic IRepository<T> over EF Core is automatically good architecture" is a common mistake. It usually just forwards to DbSet and hides Include, projection and AsNoTracking — so people leak IQueryable out of it or load more data than they need.

🔄 Likely Follow-up

"Then why do many teams still add one?" For a small, intention-revealing interface — reusable named queries and a seam for tests — not to re-expose generic CRUD. Keep it specific to the use case.

🎯 Say this in the interview — the exact lines to land

"Not by default — DbSet is already a repository and DbContext is already a unit of work, so a generic repository on top mostly forwards calls. I add a thin, specific one only when it earns its place: reusable named queries, a testing seam, or an aggregate boundary."

  • DbSet<T> → already a repository.
  • SaveChanges() → the unit of work, one transaction per call.
  • Generic IRepository<T> → hides Include, projection, AsNoTracking.
  • A wrapper earns its place for named queries or a test seam.
  • With repositories, share one scoped DbContext per request so they share one unit of work.
📖 Explanation ▾

A repository is a collection-like gateway to data; a unit of work tracks changes and commits them together. EF Core already ships both: each DbSet<T> is the repository, and the DbContext is the unit of work — it tracks changes, and SaveChanges() writes them in one transaction.

A generic IRepository<T> on top usually forwards calls. Worse, it tends to hide what makes EF Core useful — Include, projection with Select, AsNoTracking, ExecuteUpdate — so teams leak IQueryable through it or fetch whole entities they don't need.

A wrapper earns its place when it has a job: named queries used in many places (GetOverdueOrders), a seam for tests, or a domain-driven aggregate boundary. Keep it specific, not generic CRUD. If you do have repositories, register one scoped DbContext per request and share it. See DbContext & DbSet, The Change Tracker & SaveChanges() and Testing EF Core Code.

💻 See the code ▾
C# 
public class OrderService(AppDbContext db)
{
    public async Task CancelAsync(int id)
    {
        var order = await db.Orders.FindAsync(id);   // DbSet = repository
        order!.Status = OrderStatus.Cancelled;
        await db.SaveChangesAsync();                 // DbContext = unit of work
    }
}

No wrapper needed — the two EF Core types already play both roles.

C# 
public class OrderQueries(AppDbContext db) : IOrderQueries
{
    public Task<List<Order>> GetOverdueAsync(DateTime today) =>
        db.Orders.AsNoTracking()
            .Where(o => o.DueDate < today && !o.Paid)
            .ToListAsync();                          // ✅ named, reusable, still full LINQ
}

A thin wrapper that earns its place: one named query, not generic CRUD.

C# 
public interface IRepository<T>
{
    IEnumerable<T> GetAll();   // ❌ no Include, no projection, no paging
    void Add(T entity);
}

The generic version — everything EF Core can do beyond this is now out of reach.

🌍 Real-world example ▾

A team wrapped every entity in IRepository<T> plus an IUnitOfWork. Each new screen needed a new method, and the interface slowly leaked IQueryable anyway. They kept a few named-query classes and used the DbContext directly everywhere else.
