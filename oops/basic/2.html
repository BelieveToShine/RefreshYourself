Is it a kind of that thing, or does it just have one? — is-a vs. has-a

"What's the difference between inheritance and composition, and how do you decide which one to use?"

Why it matters ▾
👪 Inheritance
❗ ProblemWanting to reuse another class's behavior can tempt you to inherit from it even when the relationship isn't genuinely "is a" — and if it isn't true, the hierarchy fights you later.
✅ SolutionInheritance's real job is modeling a true is-a relationship: the subclass gets the base's members automatically and can be used anywhere the base type is expected.
RecallInheritance = genuine is-a → automatic members + substitutable.
📦 Composition
❗ ProblemSometimes a class needs another class's behavior without actually being that type — like a Car needing an Engine's Start() — and inheriting there would wrongly claim Car is a kind of Engine.
✅ SolutionComposition holds the other object as a field and delegates to it, borrowing behavior without claiming to be that type — the safer default when the relationship is unclear.
RecallComposition = has-a → holds a field, delegates instead of claiming to be it.
🔥 Easy interview recall

is-a → inherits everything automatically

has-a → holds a reference, delegates to it

Think: Dog : Animal → a Dog IS an Animal Car { Engine _engine; } → a Car HAS an Engine

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Inheriting from a class just to reuse its methods. If the real relationship is "has a," not "is a" — like writing class Car : Engine just to call Engine's methods — that's composition pretending to be inheritance.

🔄 Likely Follow-up

"So when would you actually prefer inheritance?" When the is-a relationship is genuinely true and you need polymorphic substitutability — e.g. every Shape subtype has to be usable anywhere a Shape is expected.

🎯 Say this in the interview — the exact lines to land

"Inheritance means a subclass IS the base type — it gets the base's members automatically, so Dog : Animal makes a Dog an Animal. Composition means a class HOLDS a reference to another object as a field and delegates to it, so a Car has an Engine without being one. I decide by asking: is this genuinely a kind of that, or does it just use one?"

  • is-a → use when the subtype must be substitutable wherever the base type is expected.
  • has-a → use when one class just needs to delegate work to another, unrelated object.
  • Reaching for inheritance to reuse code, not to model a true type relationship, is the sign to switch to composition.
📖 Explanation ▾

Inheritance makes a subclass literally the base type — class Dog : Animal means every Dog automatically gets Animal's members, and can be used anywhere an Animal is expected. It's a strict is-a claim: if it isn't genuinely true, the hierarchy fights you later. Composition makes a class hold another object as a field and call into it — class Car { private Engine _engine; } means Car has an Engine, but a Car is not itself a kind of Engine. It borrows behavior without claiming to be that other type.

The deciding question is always the same shape: "is X a kind of Y?" If yes, inheritance is the honest model. If the honest sentence is "X has a Y" instead, composition is the correct relationship — even when inheritance would technically compile and save a few lines.

💻 See the code ▾
C# 
class Animal
{
    public virtual void Speak() => Console.WriteLine("...");
}

class Dog : Animal   // Dog IS an Animal
{
    public override void Speak() => Console.WriteLine("Woof");
}

Animal a = new Dog();  // ✅ a Dog can stand in for an Animal
a.Speak();                     // "Woof" — inherited member, used automatically

Dog gets Animal's members for free, and can be used anywhere an Animal is expected — that's the is-a payoff.

C# 
class Engine
{
    public void Start() => Console.WriteLine("Vroom");
}

class Car
{
    private readonly Engine _engine = new();  // Car HAS an Engine

    public void Start() => _engine.Start();   // ✅ delegates, doesn't inherit
}

Car holds an Engine as a field and delegates Start() to it — a Car is never treated as an Engine.

C# 
class Car : Engine   // ❌ compiles, but wrong model
{
    // reused Engine.Start() for free — but now a Car IS an Engine
}

This compiles and "works," but the relationship it claims — a Car is a kind of Engine — isn't true. That's the trap: reusing code by inheriting from the wrong thing.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're modeling a type that's genuinely a specialized version of another

The subtype genuinely is a kind of the base type, and it needs to be usable anywhere the base type is expected — like passing a Dog into code that expects an Animal. Inheritance models that relationship directly and gives you substitutability for free. This is the most common correct use of inheritance.

RememberGenuine is-a + need substitutability → inheritance.
2 A class needs another class's behavior without actually being that type

The class needs another class's behavior but isn't a kind of it — a Car needs to Start(), but a Car isn't a kind of Engine. Composition holds the Engine as a field and delegates the call, without ever claiming Car is an Engine.

RememberNeeds the behavior, isn't that type → composition.
3 You inherit from a class purely to reuse its methods

Writing class Car : Engine just to call Engine's methods for free compiles fine, but it wrongly claims a Car is a kind of Engine. This is composition pretending to be inheritance — the real relationship was always has-a. A common interview trap.

RememberInheriting purely for code reuse → composition disguised as inheritance.
🌍 Real-world example ▾

A Dog being an Animal is like a Manager being an Employee — one is genuinely a specialized version of the other. A Car having an Engine is like a Manager having a laptop — useful, even essential, but the Manager isn't a kind of laptop.

Scenario: you're modeling a Car and an Engine — why is that composition, not inheritance? A Car isn't a kind of Engine; it uses one. So Car holds an Engine as a field (private Engine _engine;) and delegates calls like Start() to it — that's composition, not inheritance.
