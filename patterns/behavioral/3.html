State — the object's own behavior changes, no giant switch required

"What is the State pattern, and how is it different from a plain enum with a switch?"

Why it matters ▾
🚦 State
❗ ProblemAn order/workflow object with a switch (status) scattered across several methods grows unwieldy as states and transitions multiply, and it's easy to forget to update one of those switches when a new state is added.
✅ SolutionState gives each state its own class holding both its behavior and the logic for what the next state should be, so the Context just delegates — adding a state means adding one new class, not editing every existing switch.
RecallState = the object's behavior changes with its internal state — modeled as one class per state.
🔥 Easy interview recall

State = "the object appears to change its class."

Think: Context → holds a State reference, delegates to it each state → implements the behavior AND decides the next state who decides → the object's own lifecycle, not an outside caller

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

State looks like Strategy, but the intent is different. Ask who drives the choice: if the object itself decides the next behavior based on its own lifecycle, that's State; if the caller picks the behavior up front for reasons external to the object, that's Strategy.

🔄 Likely Follow-up

"Why not just use an enum with a switch?" It works for a couple of states, but a switch (status) repeated across several methods grows unwieldy as transitions multiply, and it's easy to forget to update one of those switches when a new state is added — State puts each state's behavior and its legal transitions in one place instead.

🎯 Say this in the interview — the exact lines to land

"State lets an object change its behavior when its internal state changes, by giving each state its own class that implements the shared behavior and decides its own legal next state. Unlike Strategy, the object itself drives the transition based on its own lifecycle, not a caller picking the behavior from outside."

  • Context → holds a State reference, delegates every call to it.
  • Each ConcreteState → implements the behavior AND decides the next state.
  • Adding a state → add one new class, not edit every existing switch.
  • vs. Strategy → the object drives its own transitions, not an outside caller.
  • Real example → a traffic light or a vending machine.
📖 Explanation ▾

State has three parts: the Context holds a reference to a State object and delegates behavior to it instead of handling that behavior itself; the State interface declares the state-specific methods; and each ConcreteState (Pending, Paid, Shipped…) implements those methods and usually decides what the next state should be, by reassigning the Context's State reference. The Context never asks "what state am I in" — it just calls the current State object and lets that object handle it, including moving itself forward.

The natural alternative is a plain enum plus a switch repeated in every method that needs state-specific behavior:

enum + switchState pattern
Adding a new stateedit every switch across the codebaseadd one new class
Where the behavior livesscattered across every method's switchone class per state, in one place
Risk of missing a caseeasy to forget updating one switchthe compiler requires every interface member implemented
💻 See the code ▾
C# 
public interface IOrderState
{
    void Pay(OrderContext ctx);
    void Ship(OrderContext ctx);
}

public class PendingState : IOrderState
{
    public void Pay(OrderContext ctx) => ctx.State = new PaidState(); // ✅ transitions itself
    public void Ship(OrderContext ctx) => throw new InvalidOperationException("Can't ship an unpaid order");
}

public class PaidState : IOrderState
{
    public void Pay(OrderContext ctx) => throw new InvalidOperationException("Already paid");
    public void Ship(OrderContext ctx) => ctx.State = new ShippedState(); // ✅ moves to the next state
}

Each state decides its own legal transitions — PendingState knows it can only move to Paid, never straight to Shipped.

C# 
public class OrderContext
{
    public IOrderState State { get; set; } = new PendingState(); // starts here

    public void Pay() => State.Pay(this);   // delegates — doesn't know which state it's in
    public void Ship() => State.Ship(this);
}

var order = new OrderContext();
order.Pay();   // PendingState → PaidState
order.Ship();  // PaidState → ShippedState

OrderContext never checks "what state am I in" — it just asks the current State object to handle the call.

🌍 Real-world example ▾

A traffic light. Each color decides what happens while it's showing and which color comes next — Green knows it leads to Yellow, Yellow knows it leads to Red — the light doesn't run one giant switch checking its own color on every tick. A vending machine's NoCoin/HasCoin/Dispensing states work the same way.
