A hydration mismatch only happens in production — is it really your code?

"A hydration mismatch error shows up in production logs but you can't reproduce it locally — how do you investigate?"

Why it matters ▾
💧 Hydration Mismatch, Production-Only
❗ ProblemA hydration mismatch that only reproduces in production, never locally, looks unexplainable — but it almost always traces back to an environment difference: a direct window/localStorage/navigator read during initial render, a timezone difference in date formatting, or even a browser extension injecting into the DOM before React hydrates.
✅ SolutionMove any genuinely environment-dependent read into useEffect (client-only, post-hydration) with a safe placeholder for the initial shared render, and don't assume the cause is your own code until a browser extension and a timezone difference have both been ruled out.
RecallProduction-only, not locally reproducible → check environment differences before blaming your own code.
🔥 Easy interview recall

A hydration mismatch = the server's output didn't match the client's first render — often an environment difference, not a code bug.

Think: a window/localStorage read outside useEffect, a timezone difference, or a browser extension — roughly in that order.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming a hydration mismatch is always a code bug in your own app. A browser extension injecting into the DOM, or a timezone difference between your machine and production, is a real external cause worth ruling out first — especially when it reproduces for real users in production but never locally.

🔄 Likely Follow-up

"Why would this reproduce in production but not locally?" Production and local environments can genuinely differ in timezone, locale, or which browser extensions are active — exactly the kind of environment-dependent factor that causes server and client output to diverge unpredictably.

🎯 Say this in the interview — the exact lines to land

"A hydration mismatch means the server's HTML didn't match what React rendered on the client's first pass. I'd check the usual code causes first — a direct window/localStorage read outside useEffect, or date formatting that differs by timezone — but I'd also rule out a browser extension injecting into the DOM, since that's a real cause that's not my own code's fault at all."

  • Direct window/localStorage read during render → move it into useEffect, with a safe placeholder for the first render.
  • Date/time formatting → can differ by server vs. client timezone, a frequent silent cause.
  • A browser extension → can inject into the DOM before hydration, a real cause outside your own code.
  • Reproduces in production only → check environment differences before assuming it's a code bug.
📖 Explanation ▾

React's hydration step assumes the server-rendered HTML and the client's own first render produce exactly the same markup — it attaches event handlers and internal state to the existing DOM instead of rebuilding it, and a mismatch means that assumption broke. Anything that can produce a different result on the server than it does in the browser — reading window or localStorage directly in a component body, instead of inside useEffect, is the most common code-level cause, since those values don't exist on the server at all.

Date and time formatting is a quieter version of the same problem: formatting a date using the server's timezone/locale can genuinely produce different text than formatting it on a client machine set to a different timezone — both renders are "correct" for their own environment, which is exactly why this one is easy to miss in testing.

A browser extension modifying the DOM before React hydrates is a cause that's genuinely outside the application's own code — some extensions inject attributes or elements into the page on load, and React sees that injected markup as a mismatch against what it rendered server-side. This is worth ruling out specifically when a mismatch reproduces for real users in production but never on a clean local environment.

💻 See the code ▾
JSX 
function Banner() {
  const saved = localStorage.getItem('theme'); // ❌ doesn't exist on the server
  return <div className={saved}>Hi</div>;    // server renders "null", client renders real value
}

The server has no localStorage — it renders a different result than the client does on its first pass.

JSX 
function Banner() {
  const [saved, setSaved] = useState('default'); // ✅ same for server + first client render

  useEffect(() => {
    setSaved(localStorage.getItem('theme')); // ✅ runs only after hydration
  }, []);

  return <div className={saved}>Hi</div>;
}

The first render is identical on both sides — the real value is applied only after hydration completes.

🌍 Real-world example ▾

Error-tracking shows hydration mismatch reports from real users in production, but the exact same page never fails on a developer's own machine. Checking the actual error details shows an extra data-* attribute present only in the client's DOM snapshot — a sign of a browser extension injecting into the page before React hydrates, not a bug in the app's own rendering code at all.
