Decorator — stack behavior, without a new subclass per combo

What is the Decorator pattern, and how does it let you add behavior to an object at runtime?

🧩 Also see the OOP-angle page: Decorator Pattern
⚡ Also see the JavaScript-angle page: Higher-Order & Functional JavaScript
Why it matters ▾
🎁 Decorator
❗ ProblemA sales report needs caching and logging layered on top of the real report-generation logic. Subclassing every combination means CachingReport, LoggingReport, LoggingCachingReport — the classes multiply with every new behavior.
✅ SolutionEach extra behavior is its own small wrapper that implements the same interface as the thing it wraps. Stack any combination you want at runtime, with no new subclass per combination.
RecallDecorator = same interface, wraps another instance, adds one behavior around the delegated call.
🔥 Easy interview recall

Decorator = "wraps an object behind the same interface and adds behavior around the delegated call."

Think: Component → the shared interface ConcreteComponent → the real, base object ConcreteDecorator → same interface, adds behavior, forwards to the one it wraps

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just make a subclass for each combination." That's exactly the problem Decorator avoids — two behaviors need 4 subclasses, three need 8; wrapping composes them at runtime with zero new classes.

🔄 Likely Follow-up

"Is ASP.NET Core middleware literally this pattern?" Yes — each middleware wraps the next with the same RequestDelegate shape, adding behavior before or after calling the inner one. That's a textbook Decorator running at the framework level.

🎯 Say this in the interview — the exact lines to land

"Decorator wraps an object behind the same interface and adds behavior before or after forwarding the call to the thing it wraps. Decorators stack at runtime, so two behaviors need two small classes, not one subclass per combination. ASP.NET Core's middleware pipeline is exactly this pattern running in production code."

  • Decorator → same interface, wraps, adds one behavior, then forwards.
  • Structure → Component interface, ConcreteComponent the base, ConcreteDecorator the wrapper.
  • Versus subclassing → compose at runtime, no combinatorial explosion.
  • Real framework example → ASP.NET Core middleware wraps the next delegate the same way.
📖 Explanation ▾

A Component is the shared interface. A ConcreteComponent is the real base object that does the actual work. A Decorator implements that same Component interface and also holds a reference to another Component — usually the inner object it wraps. A ConcreteDecorator is a specific wrapper (logging, caching, retry) that adds its own bit of behavior right before or after forwarding the call to the Component it holds.

Because every layer shares the same interface, you can stack them in any order you like: new LoggingReportDecorator(new CachingReportDecorator(new SalesReport())). Order isn't cosmetic — logging on the outside logs every call, including cache hits; logging placed inside the cache never sees a cache hit at all.

You've already used a production version of this: ASP.NET Core's middleware pipeline. Each middleware takes the next RequestDelegate, does its own work around calling it, and the whole chain looks identical to the next link in it — the same wrap-and-forward shape as a decorator, just applied to a request pipeline instead of an object.

💻 See the code ▾
C# 
public interface IReportGenerator   // Component
{
    string Generate();
}

public class SalesReport : IReportGenerator   // ConcreteComponent
{
    public string Generate() => "sales report data";   // the real work
}

One shared interface, one class that actually does the work.

C# 
public class CachingReportDecorator : IReportGenerator   // ConcreteDecorator
{
    private readonly IReportGenerator _inner;
    private string? _cached;
    public CachingReportDecorator(IReportGenerator inner) => _inner = inner;

    public string Generate() => _cached ??= _inner.Generate();   // ✅ adds caching, then forwards
}

public class LoggingReportDecorator : IReportGenerator   // ConcreteDecorator
{
    private readonly IReportGenerator _inner;
    public LoggingReportDecorator(IReportGenerator inner) => _inner = inner;

    public string Generate()
    {
        Console.WriteLine("Generating report...");   // adds logging
        return _inner.Generate();                      // ✅ then forwards
    }
}

IReportGenerator report =
    new LoggingReportDecorator(
        new CachingReportDecorator(
            new SalesReport()));   // ✅ stack at runtime, any order

Two decorators, zero new subclasses — reorder the constructors and the behavior changes, the interface doesn't.

🌍 Real-world example ▾

ASP.NET Core's middleware pipeline is this pattern in production. Each middleware wraps the next RequestDelegate, running its own logic before or after calling it — the exact wrap-and-forward shape a Decorator uses, just applied to a request instead of a report.
