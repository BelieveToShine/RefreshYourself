⭐ Java · Advanced · Should Know

High CPU rules out one usual suspect — let the profiler find the other three

"CPU usage is high but requests are still slow — how do you figure out whether it's allocation, GC, lock contention, an inefficient algorithm, or blocking I/O?"

Why it matters ▾
🔥 High CPU, Still Slow
❗ Problem"High CPU" sounds like one problem, but it's actually a symptom shared by at least three very different root causes — excess allocation driving GC, lock contention, and a genuinely inefficient algorithm — and guessing which one wastes exactly the time an incident doesn't have.
✅ SolutionLet a profiler point at the actual mechanism — GC logs for allocation pressure, a lock-contention profile for synchronization, CPU sampling for a hot method — and use the fact that high CPU itself already rules out pure blocking I/O, which would show as low CPU with parked threads instead.
RecallHigh CPU rules out blocking I/O — the profiler, not a guess, tells you which of the other three it is.
🔥 Easy interview recall

GC logs spiking → allocation pressure

lock-contention profile hot → synchronization

CPU-sampling hot method → inefficient algorithm

low CPU, threads parked → blocking I/O instead

Think: a thread parked on I/O isn't burning CPU — so high CPU already hands you a shortlist of three, not five.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

High CPU usually means a database or network call is the bottleneck. A thread genuinely blocked waiting on I/O isn't consuming CPU at all — that symptom shows up as low CPU with threads parked, not high CPU; high CPU points to allocation/GC, lock contention, or an inefficient algorithm instead.

🔄 Likely Follow-up

"If it turns out to be GC, what would you actually change?" Depends on what the allocation profile shows — reducing avoidable object creation in the hot path first, then, only if that's not enough, revisiting heap sizing or the collector itself (see Advanced #3's generational trade-offs) — never jump straight to "just tune the GC" before confirming the allocation source.

🎯 Say this in the interview — the exact lines to land

"High CPU with slow requests already rules out pure blocking I/O, since a blocked thread doesn't burn CPU — I'd profile for the other three: GC logs for allocation pressure, a lock-contention profile for synchronization overhead, and CPU sampling for a hot method doing more work than it needs to."

  • High CPU → rules out blocking I/O as the direct cause — that shows as low CPU with parked threads.
  • GC logs/pause frequency → check for excessive allocation driving constant collection.
  • Lock/thread-contention profile → check for threads burning CPU on spin-wait or context-switch overhead.
  • CPU sampling, hot methods → check for a genuinely inefficient algorithm, not just "slow code".
📖 Explanation ▾

The first useful move is what the symptom itself already rules out: blocking I/O — a thread parked waiting on a socket read, a database round-trip, or a disk operation — doesn't consume CPU while it waits; the OS simply isn't scheduling it. That pattern shows up as low CPU alongside high latency and a pool full of waiting threads, the opposite of what this scenario describes. Seeing genuinely high CPU is itself a diagnostic fact: whatever's slow is actually doing CPU work, not waiting for something external.

From there, a profiler — not a guess — separates the three real suspects. Allocation pressure shows up in GC logs and pause-frequency metrics: a request path creating far more short-lived objects than it needs to forces the collector to run constantly, and that collection work itself consumes CPU cycles that never show up as "my code is slow" in a naive read. Lock contention shows up in a thread/lock-contention profile: threads burning CPU cycles spin-waiting for a lock, or paying repeated context-switch overhead fighting over a shared resource, can look like "busy" CPU that's actually mostly wasted coordination rather than useful work. An inefficient algorithm shows up directly in CPU sampling as one or a few hot methods consuming a disproportionate share of samples — genuinely necessary work, just more of it than the problem requires (an O(n²) scan where a map lookup would do).

These three aren't mutually exclusive in a real incident — allocation pressure can itself cause lock contention inside the allocator/GC, for instance — but a profiler run first, before any fix is attempted, is what tells you which one to actually chase instead of tuning the wrong layer first.

💻 See the code ▾
Java 
for (Order o : orders) {
    String summary = String.format("%s: %d", o.id(), o.qty()); // ❌ new String + format allocation per row
    log.add(summary);
}

Harmless-looking per-row formatting, multiplied over a large hot-path loop, is exactly the kind of allocation pressure that GC logs would surface.

Java 
synchronized (sharedLock) { // ❌ one lock guarding the whole hot path
    cache.put(key, computeExpensiveValue()); // threads queue up, burning CPU on contention
}

A lock-contention profile — not CPU sampling alone — is what reveals threads spending cycles waiting on sharedLock rather than doing useful work.

🧭 Use Cases — recognize these when they happen to you ▾
1 GC pause frequency in the logs climbs right alongside the slowdown

This is a very common real pattern: a code path creates far more short-lived objects than it needs to, forcing the collector to run constantly. The fix starts with an allocation profile pointing at the actual source, not a heap-size or collector-tuning change made before confirming where the allocation is coming from.

RememberGC pause frequency rising with load → check allocation before touching GC settings.
2 Many threads are runnable but a thread dump shows most of them stuck on the same lock

High CPU with most threads piled up behind one shared lock, visible in a thread dump or contention profile, points straight at synchronization as the cause — widening the lock's scope, splitting it per-key, or moving to a concurrent collection are the real fixes, not adding more threads.

RememberThreads piled on one lock in a dump → it's contention, not raw CPU work.
3 CPU sampling shows almost all time inside one specific method

No GC spike, no lock contention — just one method dominating the CPU-sampling profile. This is the straightforward case: the code is doing real, necessary-looking work, just a lot more of it than the problem actually requires (a nested scan where an index or map lookup would do).

RememberA single dominant hot method in sampling → an algorithmic fix, not an infrastructure one.
🌍 Real-world example ▾

A service's CPU climbs to 95% during peak traffic while response times triple. Pull a CPU-sampling profile first — it will point at one of allocation/GC, lock contention, or a specific hot method, and that evidence decides the fix, rather than reaching straight for "add more instances" or "tune the garbage collector."
