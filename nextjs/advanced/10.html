params, cookies(), headers() — why they all turned async in Next.js 15

"Why did cookies(), headers(), and params become async in Next.js 15?"

Why it matters ▾
⏳ Async request APIs
❗ ProblemRendering can't start on any part of a page that genuinely needs request-specific data (a cookie, a header, a route param) until that request has actually arrived — synchronous access forced Next.js to treat the whole page as blocked on it.
✅ SolutionStarting in Next.js 15, cookies(), headers(), draftMode(), and the params/searchParams props all became Promise-based — awaited instead of read synchronously — so Next.js can start rendering the parts of a page that don't depend on them sooner.
RecallAsync request APIs = don't block the whole page on data that hasn't arrived yet.
🔥 Easy interview recall

Next.js 14 → sync, params.slug

Next.js 15 → async, await params

Next.js 16 → sync access removed

Think: Next.js 15 is the deprecation window — the old sync call still runs, but it's already on borrowed time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Writing const { slug } = params in Next.js 15+ code is not safe long-term. It still technically runs during the deprecation window, with a warning — the forward-compatible form is const { slug } = await params.

🔄 Likely Follow-up

"Why make these async in the first place?" It lets Next.js start rendering the parts of a page that don't depend on request-specific data before the request itself (and its headers/cookies) has even fully arrived — a performance/architecture change, not arbitrary API churn.

🎯 Say this in the interview — the exact lines to land

"Starting in Next.js 15, cookies(), headers(), draftMode(), and the params/searchParams props all became Promise-based — you await them instead of reading them synchronously. The old synchronous access still works with a deprecation warning in Next.js 15, and is removed starting in Next.js 16."

  • Next.js 15 → await params / cookies() / headers(), sync still runs but warns.
  • Next.js 16 → sync access removed entirely.
  • Why → lets non-request-dependent parts of a page start rendering sooner.
  • Forward-compatible form → await params, not params.slug.
📖 Explanation ▾

Before this change, params, searchParams, cookies(), and headers() were read synchronously — a plain object or function call, available the instant the component ran. That convenience came with a cost: anything touching these values had to wait for request data that genuinely isn't known until the request itself has arrived.

Starting in Next.js 15, all of these became Promise-based. await cookies(), await headers(), await params — the shape of the call barely changes, but it lets the framework start rendering everything that doesn't depend on request data while that data is still arriving, instead of serializing the whole page behind it.

Next.js 15 keeps the old synchronous form working, with a console warning — a real deprecation window, not a hard break yet. That sync fallback is removed starting in Next.js 16, so code still written the old way needs to move to await before upgrading past 15.

💻 See the code ▾
JSX 
// Next.js 14 and earlier — synchronous
export default function Page({ params }) {
  const { slug } = params; // plain object, no await
  return <h1>{slug}</h1>;
}

Still the only form that exists before Next.js 15 — nothing to await yet.

JSX 
// Next.js 15 — correct, forward-compatible form
export default async function Page({ params }) {
  const { slug } = await params; // ✅ ready for Next.js 16
  return <h1>{slug}</h1>;
}

// const { slug } = params;   // ⚠️ still runs in 15, warns, removed in 16

Same destructure, same variable — only the await changes, and it's the part that keeps working past Next.js 15.

🌍 Real-world example ▾

Your build logs suddenly fill with deprecation warnings after upgrading to Next.js 15, even though nothing visibly broke. That's expected — every route/layout still reading params or cookies() synchronously keeps working during this release, just noisily. Treat the warnings as a to-do list: fix them before the jump to Next.js 16, where the old sync calls stop working entirely.
