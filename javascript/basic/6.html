Scope & Hoisting — your code never actually moves to the top

"What's the difference between global, function, and block scope, and what does 'hoisting' actually do to var, let, const, and function declarations?"

Why it matters ▾
🔧 var
❗ ProblemA var declared inside an if/for block isn't sealed inside it — it silently leaks out and can clash with a variable of the same name outside the block.
✅ Solutionvar is scoped to the whole enclosing function, not the block — it's hoisted and auto-initialized to undefined during the creation phase, so it's already usable (just undefined) before its own line runs.
Recallvar → function-scoped, hoisted and auto-set to undefined.
🔒 let
❗ ProblemReading a let before its declaration line doesn't quietly return undefined like var does — it throws, and without knowing about the TDZ that looks like a completely different bug.
✅ Solutionlet is hoisted into its block scope but left uninitialized in the Temporal Dead Zone until its own declaration line actually executes — read it early and it's a ReferenceError, not undefined.
Recalllet → block-scoped, hoisted into the TDZ, throws if read early.
📌 const
❗ ProblemSitting in its own column right next to let, it's tempting to assume const must hoist or scope differently since it's the "stricter" one.
✅ SolutionOn scope, hoisting, and the TDZ it doesn't — const is block-scoped and hoisted into the TDZ exactly like let, with the same ReferenceError if read before its own line.
Recallconst → same scope/hoisting/TDZ behavior as let.
✅ function declaration
❗ ProblemCalling a function before the line it's written on looks like it should throw the same "used before declaration" error as let — but it works, which is confusing without knowing why.
✅ SolutionA function declaration is hoisted with its entire body, not just its name, and made callable immediately during the same creation phase that only sets var to undefined and leaves let/const in the TDZ.
Recallfunction declaration → fully hoisted with its body, callable before its own line.
🔥 Easy interview recall

var → function-scoped, hoisted and set to undefined

let / const → block-scoped, hoisted into the TDZ

function declaration → fully hoisted, callable before its own line

Think: hoisting just records the declaration early — it never moves the code. That's why a let in the TDZ throws instead of quietly returning undefined.

🧠 Visual Mental Model — nesting decides who's visible, timing decides who's usable
⚠️ Common Trap

Hoisting does not move your code to the top. The engine records that a declaration exists during a creation phase before execution — the code's physical position never changes; that's exactly why a let/const read before its own line throws a ReferenceError in the TDZ, instead of quietly returning undefined the way a hoisted var does.

🔄 Likely Follow-up

"If both are hoisted, why does var give undefined but let throws?" Hoisting only reserves the name for both. var is also auto-initialized to undefined right away, while let/const stay uninitialized — in the TDZ — until their own declaration line actually executes.

🎯 Say this in the interview — the exact lines to land

"JavaScript has global, function, and block scope, nested lexically into a scope chain — an inner scope can see its outer scopes, never the reverse. During a creation phase, before any code actually runs, var and function declarations are hoisted and already usable — var starts out as undefined. let and const are hoisted too, but sit in the Temporal Dead Zone until their own line executes, so reading them early throws instead."

  • var → function-scoped only; ignores block boundaries like if/for.
  • let / const → respect block scope, unlike var.
  • Scope chain lookup → walks inward to outward, stopping at the first match.
  • var hoisting → hoisted, starts out as undefined.
  • let / const hoisting → hoisted into the TDZ — read early and it throws.
  • Function declarations → fully hoisted, safe to call before their line.
📖 Explanation ▾

Every { } block, every function, and the whole file itself create their own scope — a bucket of names that live inside it. These scopes nest inside each other exactly where they're written in the code (that's what lexical means), and that nesting forms the scope chain: to resolve a name, the engine looks in the current scope first, then walks outward one level at a time until it finds a match — never inward, and never sideways. This builds directly on var vs. let vs. const — once let/const are block-scoped and var isn't, hoisting is what explains why that difference actually bites in real code.

Hoisting is what happens during a short creation phase, before the engine executes a single line of the current scope: it scans ahead and records every declaration it finds. var declarations and function declarations are recorded and initialized immediately — a var gets the placeholder value undefined, and a function declaration gets its entire body, which is why it's safely callable before the line it's written on. let and const are recorded too, but not initialized — they exist in a state called the Temporal Dead Zone (TDZ) from the top of their scope until their own declaration line actually runs.

This same lexical-scope chain is exactly what closures (the next tier up) build on — a closure is just a function that keeps its own scope chain alive even after the outer function that created it has already returned.

💻 See the code ▾
JavaScript 
console.log(x);   // 👉 undefined (hoisted, not yet assigned)
var x = 5;

console.log(y);   // 👉 ❌ ReferenceError: Cannot access 'y' before initialization
let y = 5;

Same "used before its declaration line" mistake, two different outcomes — var is hoisted and initialized to undefined; let is hoisted but left uninitialized in the TDZ.

JavaScript 
if (true) {
  var a = 1;
  let b = 2;
}
console.log(a);   // 👉 1 — var ignores the block
console.log(b);   // 👉 ❌ ReferenceError: b is not defined

var leaks out of the { } because it's function-scoped, not block-scoped — let stays sealed inside it.

JavaScript 
sayHi();   // 👉 "Hi!" — works before the declaration below

function sayHi() {
  console.log("Hi!");
}

A function declaration is hoisted with its whole body, not just its name — so it's safe to call above where it's written.

🧭 Use Cases — recognize these when they happen to you ▾
1 You log a var and a let, both before their own declaration line, in the same function

Same "used before its declaration line" mistake, two different outcomes. The var read early comes back undefined because it was already hoisted and auto-initialized. The let read early throws instead, because it's hoisted into the TDZ and only initializes when its own line actually runs — const behaves the same way as let here.

RememberRead early → var gives undefined, let/const throw (TDZ).
2 You declare a variable inside an if/for block, then read it right after the block closes

Declare it with var and the read outside the block succeeds — var is function-scoped, so it was never sealed inside that block to begin with. Swap in let or const for the same read and it throws a ReferenceError, because the block boundary is real for both of them.

Remembervar leaks past { }; let/const stay sealed inside it.
3 You call a function on a line above where it's actually declared, further down in the same file

It works — a function declaration is hoisted with its entire body, not just its name, and is made callable immediately during the creation phase. That's the same creation phase that only sets var to undefined and leaves let/const parked in the TDZ, so a function declaration is the one of these four that's actually safe to use before its own line.

RememberFunction declaration → hoisted with its whole body, callable before its own line.
🌍 Real-world example ▾

Hoisting is like printing name badges before an event starts. Every attendee's badge exists early, no matter when that person actually shows up — a var badge comes with a placeholder "TBD" you can read right away, but a let/ const badge is blank and roped off until that person actually walks in, and anyone who tries to read it before then gets turned away.
