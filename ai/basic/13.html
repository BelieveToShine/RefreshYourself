Tokens, not words, decide what a prompt actually costs

"If token count isn't the same as word count, how do you actually estimate what a prompt or response will cost, or whether it fits the context window?"

Why it matters ▾
🔤 Tokenizer
❗ ProblemAn LLM API bills and limits by token count, not word count — and a subword tokenizer can split one ordinary word into several tokens, so a word-based estimate can quietly run over budget or over the context window, especially outside English.
✅ SolutionRun the exact text through the model's real tokenizer, or the API's token-counting endpoint, and use that count directly — it's the number that actually gets billed and limited, never a word-count guess.
RecallTokenizer = the real word-to-piece cutter an LLM bills and limits by — always count tokens directly, never estimate from words.
🔥 Easy interview recall

Token count = "however the tokenizer sliced up the text," not how many words you'd count by eye.

Think: tokenization → token + ization — one word, two tokens; the same sentence in a low-resource language can need even more.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming a word is roughly one token. A subword tokenizer can split one word into several tokens (or fold a common whole word into just one) — so word count is never a reliable stand-in for token count, especially outside English.

🔄 Likely Follow-up

"So how would you actually estimate cost or context usage before sending a prompt?" Run the exact text through the model's real tokenizer (or the API's token-counting endpoint) and count the tokens directly — never approximate from word or character counts, especially for multilingual input.

🎯 Say this in the interview — the exact lines to land

"Token count, not word count, is what an LLM actually bills and limits — a subword tokenizer can split one word into several tokens, and non-English text often needs even more tokens for the same meaning."

  • Subword tokenizer → splits text into pieces smaller, or sometimes larger, than a whole word — not word-by-word.
  • Common short words → often exactly one token; longer or rarer words → several tokens each.
  • Non-English / low-resource languages → typically more tokens per word or character than English, from tokenizer training-data bias, not longer meaning.
  • Always measure real token counts with a tokenizer library or API — never estimate from word or character counts for cost or context budgeting.
📖 Explanation ▾

Most modern LLMs read text as tokens, produced by a subword tokenizer — commonly from the BPE (byte-pair encoding) family. It's less like counting words on a page and more like counting puzzle pieces after someone else already decided where to cut. Those cuts fall wherever a chunk showed up often enough during training, not at the edges of what you'd call a word — so a very common whole word can be exactly one token, while a longer or rarer word gets sliced into several. The result: the token count for a piece of English text is almost always higher than its word count, and there's no fixed ratio you can multiply by to guess it.

The gap gets worse across languages. A tokenizer's vocabulary is shaped by whatever text it was trained on, and that training data usually leans heavily toward some languages (often English) over others. Common words and scripts from the well-represented languages compress down to single tokens; text in a less-represented language, especially one using a different script, often has to be rebuilt from many more, smaller pieces to carry the exact same meaning. Same information, same sentence length in the reader's mind — a bigger token bill and a bigger bite out of the context window.

The practical fix is simple: never guess. Run the exact text through the model's real tokenizer, or its API's token-counting endpoint, before you quote a cost estimate or check whether something fits the context window — especially for multilingual input, where eyeballing word or character counts can be badly wrong.

💻 See the code ▾
Python 
import tiktoken

encoder = tiktoken.get_encoding("cl100k_base")
prompt = "Please summarize this ticket for me."

word_count = len(prompt.split())          # ❌ not the real cost
token_count = len(encoder.encode(prompt)) # ✅ what actually gets billed

Same string, two different numbers — the tokenizer's count is the one that actually determines billing and context usage, not the word split.

🌍 Real-world example ▾

A team budgets prompt costs by counting words in support tickets, then ships multilingual support — and the real invoice comes in far above projection for the non-English traffic. The fix: run the actual text through the tokenizer per language before estimating, never approximate from word counts, and give multilingual traffic extra context-window headroom.
