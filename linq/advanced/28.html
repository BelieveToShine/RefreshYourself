Write your own Where — and don't break deferred execution doing it

"How would you write your own LINQ-style extension method — say, a custom filter like Where — and apply it in a query chain exactly like a built-in operator?"

Why it matters ▾
🛠️ Writing a LINQ Operator From Scratch
❗ ProblemA custom filter written as a static method that loops, collects matches into a List<T>, and returns it looks correct — the results are right — but it silently breaks the deferred-execution contract every built-in LINQ operator honors, eagerly enumerating the whole source the moment it's called instead of only when the caller actually iterates the result.
✅ SolutionWrite it as an iterator block using yield return — the exact mechanism the real Where uses — so it stays lazy, streams one item at a time, and chains with other LINQ operators exactly like a built-in one.
Recallyield return = lazy, like Where. return list; = eager, not like Where.
🔥 Easy interview recall

A custom LINQ operator = "an iterator block with yield return, not a method that builds a list."

Think: yield return one item at a time keeps it lazy, just like the real Where — return list; enumerates the whole source immediately, the moment the method is called.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"As long as the method returns the right items, how it's written doesn't matter." A version that loops and returns a List<T> produces correct results but silently loses laziness — it enumerates the entire source the instant it's called, instead of only when the caller actually iterates the result, breaking the exact contract every built-in LINQ operator honors.

🔄 Likely Follow-up

"How would you prove your version is actually lazy?" Pass it a source that throws if enumerated (or just prints when its enumerator is pulled), call MyWhere(...) without enumerating the result, and confirm nothing has happened yet — then enumerate it and confirm the source only gets pulled from at that point, same as Deferred vs. Immediate Execution for the built-in operators.

🎯 Say this in the interview — the exact lines to land

"I'd write it as a static extension method on IEnumerable<T>, implemented as an iterator block with yield return — not a method that loops and returns a built List<T> — so it preserves the same deferred-execution contract the real Where has, and chains with other LINQ operators exactly like one."

  • yield return → stays lazy, one item pulled at a time, exactly like Where.
  • return list; → eager, enumerates the whole source immediately, the moment it's called.
  • Static extension on IEnumerable<T> → chains like a built-in operator, no special syntax needed.
  • Correct output alone → isn't the whole bar — streaming behavior is part of the contract too.
📖 Explanation ▾

Every built-in LINQ-to-Objects operator that returns IEnumerable<T> — Where chief among them — is implemented as an iterator block: a method containing one or more yield return statements. The compiler turns that method into a hidden state machine that does nothing at all when called — it only actually runs the body, one step at a time, as something pulls items from it via MoveNext(). That's the entire mechanism behind Deferred vs. Immediate Execution, and it's exactly what a hand-written MyWhere needs to reproduce to behave like a real LINQ operator.

A version written as a normal method — foreach over the source, collect matches into a List<T>, return list; — runs its entire body the instant it's called, because there's no iterator state machine involved; it's just a regular method call that happens to return something enumerable. The output is correct, but the behavior isn't: it enumerates the whole source immediately, rather than only when the caller actually iterates the result — and it no longer streams, since the whole list exists in memory before the method even returns.

Because MyWhere is a static extension method on IEnumerable<T> with a Func<TSource, bool> parameter — the same signature shape as the real Where — it chains with other LINQ operators the normal way, with no special syntax: people.MyWhere(p => p.Active).OrderBy(p => p.Name) reads and behaves exactly like calling the built-in Where there instead.

💻 See the code ▾
C# 
public static IEnumerable<TSource> MyWhere<TSource>(
    this IEnumerable<TSource> source,
    Func<TSource, bool> predicate)
{
    foreach (var item in source)
        if (predicate(item))
            yield return item; // ✅ one item at a time, exactly like Where
}

The yield return is what makes this an iterator block — the method body doesn't run until something actually enumerates the result.

C# 
var result = people.MyWhere(p => p.Name == "Prem");

var chained = people
    .MyWhere(p => p.Active) // ✅ chains like any built-in operator
    .OrderBy(p => p.Name);

No special syntax needed — it's an extension method on IEnumerable<T>, same as every built-in operator.

C# 
public static IEnumerable<TSource> MyWhereEager<TSource>(
    this IEnumerable<TSource> source,
    Func<TSource, bool> predicate)
{
    var list = new List<TSource>();
    foreach (var item in source)
        if (predicate(item))
            list.Add(item);
    return list; // ❌ the whole source already ran, the moment this was called
}

Same results, different contract — this version is no longer lazy, and never streams.

🧭 Use Cases — recognize these when they happen to you ▾
1 A business rule needs to read as a named, self-documenting filter instead of a repeated inline lambda

A custom operator like WhereIndexed (a filter that also sees each item's index) or ActiveOnly() names a rule once instead of repeating the same lambda everywhere it's needed — written as an iterator block, it costs nothing in laziness compared to the inline version.

RememberA named custom operator documents intent — as long as it's built on yield return.
2 Deciding whether this is even worth writing, versus just calling .Where(predicate) directly

A one-off filter used in exactly one place is usually simpler as a plain .Where(predicate) call — writing a custom operator earns its keep when the same rule needs a clear name, gets reused across the codebase, or needs logic Where itself can't express (like also seeing the item's index).

RememberReach for a custom operator for reuse or clarity — not for a true one-off.
3 Writing return list; instead of yield return item;, one line per match

This is the single wrong turn a candidate is most likely to make: the method still returns the right items, so it "passes" a quick glance, but it no longer defers execution or streams — it eagerly enumerates the whole source the moment it's called, unlike every built-in LINQ operator.

Rememberreturn list; "works" but isn't lazy — yield return is what makes it a real LINQ operator.
🌍 Real-world example ▾

A reporting module repeats the same "active, non-deleted, within the current fiscal year" filter across a dozen queries. Wrapping that rule in a custom .ReportableOnly() extension method — written as an iterator block with yield return — names the rule once, keeps it chainable with every other LINQ operator, and costs nothing in laziness compared to writing the lambda out each time.
