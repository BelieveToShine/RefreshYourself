filter() vs. map() — fewer elements, or different elements

"What's the difference between filter() and map() on a Stream?"

Why it matters ▾
🧮 Narrow vs. Reshape
❗ ProblemSometimes the goal is a shorter list of the same kind of thing (only the matching orders); sometimes it's the exact same number of items reshaped into something new (each order's total). Reaching for the wrong one either drops data that should have stayed, or leaves data unreshaped that needed converting.
✅ Solutionfilter() narrows the stream down using a Predicate — same shape, possibly fewer elements. map() reshapes every element using a Function — same count, possibly a different type.
Recallfilter() = fewer, same shape. map() = same count, different shape.
🔥 Easy interview recall

filter() → fewer out, never transformed

map() → same count, different shape

Think: filter() answers "does it belong?" map() answers "what does it become?"

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A filter() lambda can also change the value it returns. It can't — filter() only ever accepts a Predicate, so its lambda must return true/false; no matter how complex the condition looks, the element itself passes through completely unchanged. Only map() changes what the element actually is.

🔄 Likely Follow-up

"Does it matter whether you call filter() before or after map()?" Yes — putting filter() first discards the elements that don't match before an expensive map() ever runs on them; doing it the other way around wastes that transformation work on elements that get thrown away right afterward.

🎯 Say this in the interview — the exact lines to land

"filter() takes a Predicate and keeps only the elements that return true — same shape, possibly fewer elements. map() takes a Function and transforms every element — same count, possibly a different shape or type."

  • filter() → narrows down, same shape, never transforms.
  • map() → transforms every element, same count.
  • Order → filter before an expensive map() avoids wasted transformation work.
  • Need both fewer and different → chain filter().map(), they're not exclusive.
📖 Explanation ▾

filter() takes a Predicate<T> — a function that returns true or false for each element — and only lets the ones that return true continue down the pipeline. Every element that survives is the exact same value it was before; filter() has no way to change it, only to decide whether it stays.

map() takes a Function<T,R> and runs it against every single element, with no decision involved — every element goes in, and every element comes out, just possibly as a different type or value. The two are often chained together (filter().map()) because narrowing down and reshaping are usually two separate, composable steps rather than one operation trying to do both.

💻 See the code ▾
Java 
List<Integer> nums = List.of(1, 2, 3, 4);

List<Integer> evens = nums.stream()
    .filter(n -> n % 2 == 0)   // ✅ keeps 2 and 4, unchanged
    .collect(Collectors.toList());

Same Integer type throughout — fewer elements, nothing transformed.

Java 
List<String> labels = nums.stream()
    .map(n -> "#" + n)        // ✅ all 4 kept, Integer → String
    .collect(Collectors.toList());   // ["#1", "#2", "#3", "#4"]

Every element survives — same count, different type entirely.

🧭 Use Cases — recognize these when they happen to you ▾
1 You only want the active users from a bigger list

This is the #1 scenario you'll actually run into: narrowing a list down to only the ones that matter, still as the same User objects. filter(User::isActive) is exactly that — no transformation, just fewer.

RememberWant fewer of the same thing → filter(), nothing more.
2 Converting entities into DTOs for an API response

Every order becomes its own DTO — same count going in as coming out, just a different, API-friendly shape. map(Order::toDto) is reshaping, not narrowing, so map() is the correct tool here, not filter().

RememberSame count, new shape for every item → map(), not filter().
3 You try to validate and transform in the same filter() call

Writing .filter(x -> parse(x) != null) to both validate and secretly compute a value throws that computed value away — filter() only keeps the original x. Whatever parse() returned has to be computed again inside a following map(), doubling the work for no reason.

Rememberfilter() can't hand its computed value forward — map() afterward recomputes it from scratch.
🌍 Real-world example ▾

An inventory report needs only in-stock products, shown as a short price list. filter(p -> p.getStock() > 0) narrows the catalog down to what's actually available, then map(p -> p.getName() + ": $" + p.getPrice()) turns each surviving product into the display line the report actually needs — two separate, composable steps, not one operation doing both jobs.
