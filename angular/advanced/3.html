Zoneless Angular — removing the safety net that used to catch every async event automatically

"If you remove Zone.js, what tells Angular anything changed at all — and what's the actual trade-off?"

Why it matters ▾
  • Zoneless is now the default for new apps from Angular v21 onward — interviewers expect a senior candidate to know what that default is actually opting them into.
  • It's a natural, deeper follow-up once a candidate explains how OnPush and Signals drive change detection — this is "what happens if you take Zone.js away entirely."
  • A common opener for testing whether a candidate assumes zoneless is a free, drop-in performance win with no other work involved.
🔥 Easy interview recall

Zone.js → any async event triggers a tick

Zoneless → only Signals (or an explicit call) trigger one

Think: Zone.js is a blanket alarm that notices almost anything. Zoneless swaps it for a doorbell per Signal — precise, but nothing rings unless something is actually wired to it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Zoneless is not "flip one provider and get free performance." Any state that isn't a Signal (or explicitly notified via markForCheck()) and gets mutated from a raw setTimeout callback or a non-Signal-aware third-party library can silently stop updating the UI — with no error — until those exact spots are found and fixed.

🔄 Likely Follow-up

"Does moving to zoneless mean you can never use a plain class property for component state again?" Not literally never — but that property needs some explicit way to tell Angular it changed. Converting it to a Signal is the natural fix, or calling markForCheck()/detectChanges() explicitly after mutating it. Mutate it with no explicit notification and it simply won't trigger a re-render anymore — there's no Zone.js safety net quietly doing that job in the background.

🎯 Say this in the interview — the exact lines to land

"Zoneless means running Angular without Zone.js's monkey-patched async-triggers-a-tick mechanism — the app relies entirely on explicit signals, primarily Signals, to know when to re-render. You opt in with provideZonelessChangeDetection() in bootstrapApplication()'s providers, which has been stable since v20.2 and is the default for new apps from v21 onward. The real cost isn't the provider — it's finding any code that quietly relied on Zone.js's automatic catch-all and giving it an explicit notification instead."

  • Zone.js → patches async APIs broadly: extra bundle size, real runtime overhead, triggers checks indiscriminately.
  • Zoneless → Signals notify Angular directly, no patching needed — the Signal itself knows when it was read and when it changed.
  • provideZonelessChangeDetection() → stable since v20.2, and the default for new apps from v21 onward.
  • Real risk → plain properties mutated outside Angular's flow (a raw setTimeout, an unaware third-party library) go silently stale.
  • Trade-off → smaller, more targeted re-rendering in exchange for identifying and fixing every implicit dependency on Zone.js first.
📖 Explanation ▾

Zone.js works by patching a wide swath of async browser APIs — timers, promises, DOM events — so that almost anything happening anywhere can trigger a change-detection tick. That's convenient, but it isn't free: it adds tens of KB to the bundle, every patched async call carries real runtime overhead, and it triggers a full tree walk somewhat indiscriminately, even when nothing relevant to most components actually changed.

Zoneless Angular removes that mechanism entirely and relies on explicit, targeted notifications instead — primarily Signals. A Signal's read and write are inherently trackable by Angular itself, no monkey-patching required, so reading a Signal in a template registers exactly which binding depends on it, and changing that Signal notifies only that binding. markForCheck() still works too, since it's an explicit call Angular understands directly, never something that depended on Zone.js patching anything.

The catch is anything that quietly relied on Zone.js's implicit catch-all. A plain, un-Signal-wrapped class property mutated inside a setTimeout callback used to get picked up by the next automatic tick Zone.js guaranteed — without Zone.js, and without that property being a Signal or an explicit markForCheck() call, nothing tells Angular to re-check that component. The same problem shows up through third-party code: a library that fires its own callback (a WebSocket message, a charting library's internal event) and expects Angular to "just notice" may update its own state without Angular ever re-checking the surrounding component.

💻 See the code ▾
TypeScript 
bootstrapApplication(AppComponent, {
  providers: [
    provideZonelessChangeDetection(), // ✅ stable since v20.2, default from v21
    provideRouter(routes)
  ]
});

Same pattern as provideRouter()/provideHttpClient() — one more provider in the array your app already bootstraps with.

TypeScript 
setTimeout(() => {
  this.count++; // ❌ plain property, zoneless never notices
}, 1000);

setTimeout(() => {
  this.count.update(c => c + 1); // ✅ Signal — Angular is notified directly
}, 1000);

Same callback, same timing — only the Signal version actually reaches Angular once Zone.js is gone.

🌍 Real-world example ▾

Zone.js is like a building-wide fire alarm wired to notice almost any disturbance and alert everyone, whether or not it's actually relevant to them. Going zoneless is like removing that blanket system and giving each resident (each Signal) their own doorbell, wired specifically to whoever actually needs to know when something at their door changes — faster and more targeted, but anyone quietly relying on the old blanket alarm to notice something unrelated needs their own doorbell installed first, or they simply won't be notified anymore.
