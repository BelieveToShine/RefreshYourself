One Pinia store, or four? Split by domain, not by convenience

"How would you structure Pinia stores for a large, multi-feature application?"

Why it matters ▾
🧩 Domain-Split Stores
❗ ProblemOne giant store holding every feature's state becomes impossible to test in isolation, and every unrelated change risks touching state another feature depends on.
✅ SolutionSplit stores by domain/feature — userStore, cartStore, productStore — each independently testable and loaded, grouping state that's genuinely used together.
RecallSplit by domain, not by file convenience.
🔁 Cross-Store Composition
❗ ProblemSplitting stores doesn't mean they can never talk to each other — a cart action genuinely needs to know a product's current stock, which lives in a different store.
✅ SolutionOne store's action can call another store's action/state directly — fine and common — as long as the dependency direction stays one-way, never circular.
RecallCross-store reads are fine — as long as they're one-way.
🔥 Easy interview recall

Split by domain → each store independently testable

Cross-store read → fine, but keep it one-way

Circular dependency → avoid it entirely

Think: stores are modules in a dependency graph — the graph should never loop back on itself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Creating a circular dependency — store A imports store B which imports store A — can cause subtle initialization-order bugs; keep the dependency graph acyclic.

🔄 Likely Follow-up

"When would a store legitimately need to read from another store?" A cartStore action checking productStore's current stock before allowing an add-to-cart — a one-way, intentional composition, not a mutual dependency.

🎯 Say this in the interview — the exact lines to land

"I'd split Pinia stores by domain or feature — user, cart, product — rather than one giant store, so each is independently testable. Cross-store composition, one store's action reading or calling another's, is fine and common, as long as the dependency direction stays one-way; a circular dependency between two stores is the thing to actually avoid."

  • Split by domain/feature, not by file convenience.
  • Cross-store reads → fine, as long as the direction is one-way.
  • Circular dependency → avoid it — causes subtle initialization-order bugs.
  • Grain size → group state that's genuinely used together, not too fine or too coarse.
📖 Explanation ▾

For a large app, splitting stores by domain/feature keeps each one small enough to reason about and test on its own — a userStore test doesn't need to set up cart or product state just to run. The right grain is the state that's genuinely used together: too many tiny stores fragments related state awkwardly across files, while one giant store loses the modularity Pinia is actually there to give you.

Cross-store composition — one store's action calling another store's action or reading its state — is normal and common, not a smell on its own. A cartStore action checking productStore's current stock before allowing an add-to-cart is exactly this: a one-way read, where cart depends on product but product never needs to know cart exists.

The thing to actually avoid is a circular dependency — store A importing store B, which itself imports store A. Because Pinia stores are set up via module imports, a cycle like that can produce a store that's only partially initialized by the time the other one tries to use it, a subtle and hard-to-reproduce bug. Keeping the dependency graph acyclic — always one direction — avoids this entirely.

💻 See the code ▾
Vue 
// stores/cart.js
import { defineStore } from 'pinia';
import { useProductStore } from './product'; // ✅ one-way: cart depends on product

export const useCartStore = defineStore('cart', {
  actions: {
    addItem(productId) {
      const products = useProductStore();
      if (products.stockFor(productId) <= 0) return; // ✅ reads product's state, doesn't own it
      // ...add to this.items
    }
  }
});

productStore never imports cartStore back — the dependency only runs in one direction.

🧭 Use Cases — recognize these when they happen to you ▾
1 A new feature is being added and it's unclear whether it needs its own store

Ask whether this state is genuinely used together with an existing domain's state, or is its own concern. This is the #1 scenario — most new-store decisions come down to "does this belong with a domain that already exists."

RememberGroup state by what's actually used together, not by when it was built.
2 One store's action needs data that genuinely lives in another store

Calling useProductStore() directly inside a cartStore action is normal, intentional composition — not a design smell — as long as productStore never needs to call back into cartStore.

RememberReading another store's state/actions is fine — it's a one-way dependency, not a shortcut.
3 Two stores end up importing each other

A candidate might assume "stores are just modules, importing each other is fine" — but a true cycle risks one store being only partially initialized when the other first uses it. Break the cycle by moving the shared piece into a third store, or by making only one direction depend on the other.

RememberA ↔ B import cycle risks a partially-initialized store — keep the graph one-way.
🌍 Real-world example ▾

An e-commerce app's checkout flow needs to know both the cart's contents and whether each item is still in stock. Rather than merging cart and product state into one store "to make it easier," cartStore's checkout action simply reads productStore's stock levels directly — two focused stores, one clean, one-directional dependency between them.
