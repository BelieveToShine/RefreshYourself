🔥 .NET · Intermediate · Must Know

The container resolves your dependencies — so why would you ever ask it yourself?

What problem does the built-in DI container solve, and why is constructor injection preferred over service-locator resolution?

Why it matters ▾
  • Every ASP.NET Core app already runs on this container — Program.cs is registering things in it before your first line of business logic ever runs.
  • Comes up whenever testability comes up — constructor injection is the reason a unit test can swap in a fake without touching a container at all.
  • A common follow-up opener: "why not just pull what you need from IServiceProvider when you need it?" — this page is the answer.
🔥 Easy interview recall

Constructor injection → dependency is visible, container fills it in

Service locator → dependency is hidden, you reach in yourself

Think: the constructor shows what a class needs. GetService hides it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling IServiceProvider.GetService<T>() yourself is not "more flexible." It reintroduces the exact service-locator problem constructor injection exists to avoid — the dependency disappears from the constructor, so nothing about the class's public API says it needs it. The one legitimate exception is a factory that has to pick a type only known at runtime.

🔄 Likely Follow-up

"What happens if you register a service twice with different implementations?" For a normal constructor injection, the last registration wins — only one instance ever gets built for that parameter. Call GetServices<T>() instead if you need every registered implementation.

🎯 Say this in the interview — the exact lines to land

"ASP.NET Core ships Microsoft.Extensions.DependencyInjection because the framework itself — middleware, controllers, everything — already resolves its own dependencies through it, so most apps never need a third-party container. Constructor injection declares what a class needs right in its signature, so the container resolves it automatically and a test can fake it; calling the container yourself from inside a method hides that dependency and makes testing harder."

  • AddScoped/AddSingleton/AddTransient → registration only — resolution happens automatically through constructor parameters.
  • Constructor injection → dependencies are visible in the signature, testable with any fake.
  • Service locator (IServiceProvider.GetService<T>()) → hides the dependency — an anti-pattern outside factories.
  • Register the same interface twice → last registration wins for one resolve; GetServices<T>() returns all of them.
  • Third-party containers like Autofac → still swappable in — the built-in one just already covers most apps.
📖 Explanation ▾

ASP.NET Core ships a built-in DI container because the framework itself is built on it — middleware, MVC controllers, minimal API handlers, all of it gets its own dependencies through the same container your code registers into. Leaving that to a third-party library would mean every single ASP.NET Core app needs one just to boot. A third-party container (Autofac, and others) can still replace it for advanced scenarios, but the built-in one already covers the overwhelming majority of apps with zero extra dependency.

Registration is a one-line call — builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>() — and resolution happens automatically: when the container builds an object, it looks at the constructor, sees a parameter of type IOrderRepository, and hands it the registered SqlOrderRepository. No code anywhere calls "resolve" by name.

That automatic wiring is exactly why constructor injection is preferred over service-locator resolution. A constructor parameter is part of a class's public signature — read it once and you know everything the class needs, and a test can pass in a fake without a working container at all. A service locator call like provider.GetService<IFoo>() sitting inside a method body is invisible from the outside; you'd only find that dependency by reading every method. This is about container mechanics, not the design principle behind it — see Dependency Inversion on the OOP track for why depending on abstractions matters in the first place.

💻 See the code ▾
C# 
// Program.cs — registration
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();

public class OrderService
{
    private readonly IOrderRepository _repo;

    public OrderService(IOrderRepository repo)   // ✅ container fills this in
    {
        _repo = repo;
    }
}

The container builds OrderService's whole graph — nothing here ever calls GetService.

C# 
public class OrderService
{
    private readonly IServiceProvider _provider;

    public OrderService(IServiceProvider provider) => _provider = provider;

    public void Ship(int orderId)
    {
        var repo = _provider.GetService<IOrderRepository>();   // ❌ hidden dependency
        // ...
    }
}

The constructor now only asks for IServiceProvider — nothing tells you it needs IOrderRepository until you read Ship.

C# 
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddScoped<IOrderRepository, MockOrderRepository>();   // registered again

public OrderService(IOrderRepository repo)   // repo is MockOrderRepository — last one wins

var all = provider.GetServices<IOrderRepository>();   // ✅ returns both

A single constructor parameter only ever gets the last registration — GetServices<T>() is the only way to see every one.

🌍 Real-world example ▾

Ordering off a menu vs. walking into the kitchen. Constructor injection is like ordering a dish by name — the kitchen (the container) decides which ingredients and steps to use, and you never need to know. Calling GetService<T>() yourself is like walking past the waiter straight into the kitchen to grab what you want — it might work today, but nobody watching your table can tell what you actually ordered.
