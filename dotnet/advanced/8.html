Don't block the order on the notification — decouple with a queue

"You need a new service that sends email or SMS notifications, driven by configuration in a database, and it has to scale — how do you design it?"

Why it matters ▾
📨 Notification Service
❗ ProblemSending the notification synchronously, inline, from the same request that triggered it means a slow or down email/SMS provider directly slows down or breaks that triggering action — like placing an order — which has nothing to do with notifications.
✅ SolutionPublish the event to a queue and let a separate worker pool consume it, look up the user's configured channel, and send. Scale by adding more workers; a provider outage never blocks the trigger.
RecallDecouple the trigger from the send with a queue.
🔥 Easy interview recall

Step 1 → trigger publishes an event to a queue

Step 2 → worker pool consumes, looks up channel in the DB

Step 3 → sends via email or SMS provider

Think: decouple the trigger from the send — a slow provider never blocks the order.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Sending the notification synchronously from the same request that triggered it. A slow or down email/SMS provider now directly slows down or breaks the triggering action — like placing an order — that has nothing to do with notifications.

🔄 Likely Follow-up

"How do you avoid sending the same notification twice if the worker retries after a transient failure?" Track which notification — by a unique ID tied to the triggering event — has already been sent before sending it again. It's the same idempotency principle used anywhere a message might be redelivered.

🎯 Say this in the interview — the exact lines to land

"I'd decouple 'something happened' from 'send the notification' with a queue. The triggering event publishes a message, a separate worker consumes it, looks up the user's configured channel from the database, and calls the right provider. This scales by adding more worker instances, and a slow or down provider never blocks whatever triggered the notification in the first place. I'd also track sent notifications by a unique ID so a retry after a transient failure doesn't send it twice."

  • Decouple → trigger publishes an event to a queue, it never sends directly.
  • Worker pool → consumes the queue, scales by adding more instances.
  • Channel lookup → email vs. SMS preference comes from the DB, per user.
  • Isolation → a slow or down provider never blocks the trigger.
  • Idempotency → track sent notifications by ID so a retry doesn't double-send.
📖 Explanation ▾

If the code that places an order also directly calls the email provider, the order's own success now depends on an email service it has nothing to do with. A slow provider makes checkout slow; a down provider can make checkout fail entirely.

The fix is to decouple the two: the triggering code just publishes a small message ("order 123 shipped") to a queue and moves on immediately. A separate worker pool consumes that queue, looks up the user's configured channel and preferences in the database, and calls the email or SMS provider. Because the workers are separate processes consuming the same queue, scaling is just adding more worker instances — no change to the code that triggers the notification.

Messaging systems can redeliver a message after a timeout even if it was actually processed, so the worker needs to be idempotent: before sending, check whether a notification for that same triggering event's ID has already been recorded as sent, and skip it if so. That turns an occasional duplicate delivery from the queue into a no-op instead of a duplicate email or text message.

💻 See the code ▾
C# 
// ❌ the order's own request now waits on the email provider
await _db.SaveOrderAsync(order);
await _emailProvider.SendAsync(order.CustomerEmail, "Order shipped");

// ✅ publish and move on — the order never waits on notifications
await _db.SaveOrderAsync(order);
await _queue.PublishAsync(new OrderShippedEvent(order.Id));

The triggering request's success no longer depends on an email or SMS provider being up.

C# 
public async Task HandleAsync(OrderShippedEvent evt)
{
    // idempotency: skip if this exact event was already handled
    if (await _sent.ExistsAsync(evt.Id)) return;

    var prefs = await _db.GetNotificationPrefsAsync(evt.UserId);
    if (prefs.Channel == NotificationChannel.Sms)
        await _sms.SendAsync(prefs.PhoneNumber, "Your order shipped!");
    else
        await _email.SendAsync(prefs.Email, "Order shipped");

    await _sent.RecordAsync(evt.Id);         // ✅ mark it sent
}

A redelivered message hits the ExistsAsync check and becomes a no-op instead of a duplicate text or email.

🧭 Use Cases — recognize these when they happen to you ▾
1 An order confirmation needs to go out right after checkout

Checkout publishes "order placed" and returns immediately. The confirmation email goes out moments later from the worker — checkout never waits on it.

RememberThe trigger publishes and moves on — it never waits for the send.
2 A marketing blast needs to reach a very large number of users at once

The queue absorbs the burst. Adding more worker instances drains it faster, with no change to whatever triggered the notifications.

RememberA burst → add workers, not a change to the trigger.
3 The SMS provider has an outage during a busy sales period

Without a queue between them, an SMS outage would make checkout itself fail — exactly the coupling a queue exists to prevent. With a queue, the messages just wait.

RememberA provider outage should queue up messages, not break the trigger.
🌍 Real-world example ▾

An online store needs to text or email customers when their order ships. The shipping service publishes an "order shipped" event to a queue the moment it updates the order, and returns immediately. A small worker pool consumes that queue, checks each customer's saved preference for email or SMS, and sends through the matching provider — so a slow SMS gateway during a big sale never slows down the part of the system that actually ships orders.
