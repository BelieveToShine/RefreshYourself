copy = obj — why changing one changes both

"If you assign an object to another variable and mutate the copy, does the original change too — and why?"

Why it matters ▾
  • The exact bug behind "I only changed one variable, why did the other one change too?"
  • Comes up constantly with app state — passing an object into a function, or storing it in two places, without meaning to share it.
  • A classic interview opener: a short "predict the output" snippet, answered wrong more often than you'd expect.
🔥 Easy interview recall

number / string / boolean → copy the value

object / array → copy the reference

{...obj} → a real, separate copy

Think: a variable holding an object is a sticky note with an address on it, not the house itself — copying the note copies the address, not the house.

⚠️ Common Trap

{...obj} is not a deep copy. It only copies the top-level properties — a nested object or array inside still points at the same shared nested object, so mutating a nested field still changes both.

🔄 Likely Follow-up

"So how would you make a true deep copy?" Use structuredClone(obj) — it copies nested objects too, not just the top level. The older JSON.parse(JSON.stringify(obj)) trick works for simple data but silently drops functions, undefined, and Date objects.

🎯 Say this in the interview — the exact lines to land

"Objects and arrays are stored by reference — a variable holding one doesn't hold the data itself, it holds a pointer to where that data lives. Assigning it to another variable copies the pointer, not the object, so both variables end up pointing at the same thing; making a real copy needs an explicit shallow copy like spread or Object.assign."

  • Primitives copy by value. Objects & arrays copy by reference.
  • {...obj} or Object.assign({}, obj) makes a real, separate shallow copy.
  • Object.keys/values/entries return arrays of a plain object's own keys, values, or pairs — ready to loop or map over.
  • obj?.prop stops safely and returns undefined instead of throwing when something in the chain is missing.
  • ?? only falls back when the left side is null or undefined — 0 and "" are kept as-is.
📖 Explanation ▾

A variable holding a number, string, or boolean holds the actual value. A variable holding an array or object holds a reference — like an address — pointing to where that data actually lives. Copying the variable (copy = obj) copies the address, not the data, so both variables end up pointing at the exact same object; mutating through either name changes the one thing both point at.

Arrays and objects share that reference behavior — the difference between them is shape. An array is an ordered list keyed by number (arr[0]); an object is a bag of named properties keyed by string or symbol. Reading a property works two ways: dot access (obj.prop) when the key is a fixed, known name, or bracket access (obj['prop'] or obj[someVariable]) — a computed property — when the key comes from a variable or isn't a valid identifier.

Object.keys(), Object.values(), and Object.entries() turn a plain object's own properties into arrays, so the same array methods work on objects too. Optional chaining (?.) and nullish coalescing (??) both exist to handle "this might not be there" safely — one stops a property chain early instead of throwing, the other supplies a fallback only when the value is actually missing.

💻 See the code ▾
JS 
const obj = { a: 1 };
const copy = obj;   // copy is just another reference to the SAME object

copy.a = 2;
console.log(obj.a);   // 2 — obj changed too, even though we never touched "obj" directly

copy was never a separate object — it's the same object with two names pointing at it, so mutating through either name mutates the one thing both point at.

JS 
const obj2 = { a: 1 };
const realCopy = { ...obj2 };   // or Object.assign({}, obj2) — a NEW object

realCopy.a = 2;
console.log(obj2.a);   // 1 — obj2 is untouched

Spread builds a brand-new object and copies the top-level properties into it — now there are genuinely two objects, so mutating one leaves the other alone.

JS 
const user = { name: "Sam", "full-name": "Sam Lee" };

user.name;             // "Sam" — dot access, key is a fixed identifier
user["full-name"];    // "Sam Lee" — bracket needed, key has a dash

const key = "name";
user[key];              // "Sam" — computed property, the key comes from a variable

Bracket access is required whenever the key isn't a valid identifier, or the key itself comes from a variable or expression at runtime.

JS 
const scores = { math: 90, art: 75 };

Object.keys(scores);     // ["math", "art"]
Object.values(scores);   // [90, 75]
Object.entries(scores);  // [["math", 90], ["art", 75]]

Each one returns a plain array, so every array method (map, filter, for...of) works on an object's data too.

JS 
const user2 = { profile: null };

user2.profile.city;     // ❌ throws — "Cannot read properties of null"
user2.profile?.city;    // ✅ undefined — stops safely, no throw

const count = 0;
count ?? 10;    // 0 — ?? only falls back on null/undefined
count || 10;    // 10 — || falls back on ANY falsy value, including 0

?. stops a property chain early instead of throwing. ?? only supplies its fallback for null/undefined — unlike ||, it keeps legitimate falsy values like 0 or "".

🌍 Real-world example ▾

A shared document link vs. printing your own copy. Two people editing through the same shared link both see each other's changes instantly — that's a reference. Print your own copy instead, and scribbling on it never touches the original; that's what {...obj} gives you.
