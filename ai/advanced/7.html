🔥 AI · Advanced · Must Know

Your provider just rate-limited you — does your feature go down too?

How do you design an LLM-calling system so a provider outage or rate limit doesn't take your feature down with it?

Why it matters ▾
  • Every LLM provider has real production outages and per-key rate limits — a system hard-wired to one provider's exact SDK shape has no fallback the day that happens.
  • A standard senior/architect resilience question, usually phrased almost exactly like the title above — it checks whether you design for the failure path, not just the happy one.
  • Builds directly on the AI Gateway pattern (an earlier page) — routing and failover are exactly why that one abstraction layer exists in the first place.
🔥 Easy interview recall

Task is simple → cheap model first, escalate only if it needs more

Provider down / rate-limited → retry with backoff, then fail over

Think: routing picks a model by need; failover picks a provider by health — same abstraction underneath, two different reasons to switch.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"We mostly use one provider, so multi-provider design doesn't matter." Being able to route elsewhere IS the resilience — a system wired to one provider's exact SDK shape has no fallback option the day that provider has an outage, even if it never actually switches on an ordinary day.

🔄 Likely Follow-up

"Isn't retrying enough, without failover?" No — retries alone only help with a transient blip; if the provider is genuinely down or the whole rate-limit window is exhausted, retrying against the same provider just keeps hitting the same wall. Failover is what actually gets the request answered.

🎯 Say this in the interview — the exact lines to land

"Route requests by what they actually need — a cheap model for simple tasks, escalating to a stronger one only when the task calls for it — and put every provider call behind one gateway interface, so a rate limit or outage triggers an automatic retry-then-failover instead of a failed request."

  • Model routing → cheap model first, escalate only when the task's complexity actually needs it.
  • Rate limit / outage → retry with backoff, then automatically fail over to another provider.
  • Failover only works cleanly behind one gateway interface — never hard-code a provider's SDK straight into business logic.
  • Being able to route to more than one provider is itself a resilience strategy — even if one provider is used almost all the time.
  • Nothing available? → degrade gracefully — a cached answer, a queued retry, or a clear "temporarily degraded" message, never a crash.
📖 Explanation ▾

Model routing is deciding, per request, which model actually handles it — not always the same one. A short classification or simple extraction can go to a cheap, fast model; something that genuinely needs deeper reasoning escalates to a stronger, more expensive one only when the task calls for it. This is the same "cheap model first, escalate" idea introduced briefly on the Cost Control page, given its own full treatment here because resilience adds a second, independent reason to route: not just what a request needs, but which provider is actually healthy right now.

Multi-provider failover is that second reason. If a provider is down, rate-limited, or responding with server errors, requests get retried with backoff first — waiting longer between attempts so a brief blip doesn't turn into a request storm — and if that still fails, routed to a different provider automatically instead of failing outright. This only works cleanly if the application already calls one consistent interface — the AI Gateway pattern — rather than a specific provider's SDK directly; adding or swapping a provider then means a configuration change, not a rewrite of every call site.

Being able to route to more than one provider is itself a resilience strategy, even for a system that mostly uses just one provider day to day — a system wired to a single provider's exact API shape simply has no fallback option the moment that provider has an outage. And when truly nothing is available, the system should degrade gracefully rather than fail hard: a cached response, a queued retry for later, or a plain "this feature is temporarily degraded" message — never a crash or an indefinite hang.

💻 See the code ▾
Pseudocode 
# Model routing — decide WHICH model, per request
def choose_model(task):
    if task.is_simple():        # short classification, simple extraction
        return "cheap_model"    # fast and inexpensive — most traffic stays here
    return "strong_model"       # ✅ escalate — task genuinely needs more reasoning

Routing checks the task's actual need first — reaching for the cheap model isn't a compromise when the task never called for more.

Pseudocode 
# Multi-provider failover — WHICH provider, and what to do if none answer
def call_llm(request, providers):
    for provider in providers:              # e.g. [primary, backup]
        for attempt in range(3):
            try:
                return gateway.send(provider, request)
            except (RateLimited, ProviderDown):
                wait(backoff(attempt))     # waits longer each retry
    return degrade_gracefully(request)  # ❌ all providers failed — cached answer, queue, or a clear message

Retries happen first, failover happens next, and graceful degradation is the last resort — never an unhandled crash.

🌍 Real-world example ▾

Your primary provider starts returning rate-limit errors during a traffic spike. Because every call already goes through one gateway with retry-then-failover built in, new requests shift automatically to a backup provider — users see a few seconds of extra latency, never a failed request.
