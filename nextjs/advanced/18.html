A Server Action is just another endpoint — does your authorization check know that?

"A security review flags that a Server Action performs a privileged operation with no independent authorization check — walk through the fix."

Why it matters ▾
🔓 Missing Server-Side Authorization
❗ ProblemA Server Action performs a privileged operation — a refund, a role change — based only on client-supplied data, with no independent server-side re-check of the caller's actual permission to do that specific operation on that specific target. The action's endpoint is independently callable no matter what the UI shows.
✅ SolutionAdd an explicit auth/ownership check as the very first lines inside the Server Action itself, re-deriving the caller's identity and permissions from the server-side session — never trust an argument the client passed claiming who it is or what it's allowed to do.
RecallHiding a button is not a security boundary — the Server Action itself has to check.
🔥 Easy interview recall

A Server Action with no server-side check = a public API endpoint anyone can call directly.

Think: a Server Action is callable independently of the UI that renders it — the UI hiding a button is not the real boundary, a check inside the action itself is.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Hiding the Server Action's import path, or renaming it to something less obvious, is not a fix. Obscurity is not a security boundary — the action is still directly callable by anyone who can see the network request, so the real fix is the server-side check itself, not making the endpoint harder to find.

🔄 Likely Follow-up

"How would you catch this kind of bug before it ships?" A code-review checklist item for every Server Action: "does this independently verify the caller's authorization, not just trust the UI that calls it?" — the same question you'd ask of any public API endpoint.

🎯 Say this in the interview — the exact lines to land

"A Server Action is independently callable, the same as any API endpoint, so I'd put the authorization check as the first lines inside the action itself, re-deriving the caller's identity from the server-side session — never trusting the UI to be the actual boundary."

  • UI restricting who sees a control → not a security boundary, the action is still directly callable.
  • The real fix → an explicit check as the first lines inside the Server Action.
  • Trust the caller's identity from → the server-side session, never a client-supplied argument.
  • Obscuring the action's name/path → doesn't fix anything, it's still callable by anyone who sees the request.
📖 Explanation ▾

A Server Action compiles down to its own POST endpoint — the client-side function call is really a network request under the hood, and that request can be sent directly, with any arguments, by anyone who can see it in the browser's network tab. The UI only deciding whether to show the control that triggers the action never stops the action itself from being called a different way.

The fix has to live inside the action, not around it. That means re-deriving who the caller actually is from the server-side session or auth token — never trusting an argument like userId or role that the client itself passed in — and then checking that this specific caller is allowed to perform this specific operation on this specific target (not just "is logged in," but "owns this record" or "holds this role").

This is exactly the same discipline as securing any other API endpoint: authentication (who is this?) and authorization (are they allowed to do this?) both have to happen on the server, every time, regardless of what a trusted-looking UI already checked before the request was sent.

💻 See the code ▾
JS 
'use server';

export async function issueRefund(orderId, amount) {
  // ❌ no check at all — trusts whoever can call this endpoint
  await db.refunds.create({ orderId, amount });
}

Anyone who can see this request in the network tab can replay it with a different orderId — nothing here checks who's asking.

JS 
'use server';

export async function issueRefund(orderId, amount) {
  const session = await getServerSession(); // ✅ server-derived identity
  const order = await db.orders.find(orderId);

  if (!session?.user || !canRefund(session.user, order)) {
    throw new Error('Not authorized'); // ✅ checked first, every call
  }
  await db.refunds.create({ orderId, amount });
}

The check is the first thing the action does, and it's derived from the server-side session — not from anything the caller supplied.

🌍 Real-world example ▾

A security review flags a "Change user role" Server Action that only support staff should be able to call — but it has no server-side permission check. The UI only shows the button to support staff, which stops nothing: the action's endpoint is directly callable by any authenticated user who finds it. The fix is adding the role check as the first lines of the action itself, re-derived from the server session.
