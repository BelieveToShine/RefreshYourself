<Suspense> — a loading screen for a component that isn't ready yet

"What does <Suspense> coordinate, and is it production-stable?"

Why it matters ▾
⏳ <Suspense>
❗ ProblemA component whose setup() is async (or loaded via defineAsyncComponent) has no data to render for a moment — without something coordinating that gap, every async child ends up inventing its own ad-hoc spinner, so a screen with three async widgets can flash three unrelated loading states at three different times.
✅ Solution<Suspense> wraps one or more async descendants and shows a single #fallback slot until every one of them resolves, then swaps to the real content all at once.
Recall<Suspense> = one shared fallback for every async child inside it — and it's still experimental.
🔥 Easy interview recall

<Suspense> = "one loading screen for everything inside it — and it's still experimental."

Think: fallback shows until every async setup() inside resolves; it does not catch errors on its own.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Presenting <Suspense> as a finished, stable API. It remains an experimental Vue feature as of this writing — its behavior, especially around nested <Suspense> and error handling, can still change.

🔄 Likely Follow-up

"What happens if the async component rejects?" <Suspense> itself doesn't catch errors — you still need an error boundary (onErrorCaptured on an ancestor) alongside it.

🎯 Say this in the interview — the exact lines to land

"<Suspense> coordinates a loading state around async descendants — components with an async setup(), or loaded via defineAsyncComponent — showing its #fallback slot until all of them resolve. It's still an experimental Vue feature, so I wouldn't ship it somewhere that needs guaranteed stability without checking the current docs."

  • Coordinates one shared fallback, not a spinner per async child.
  • Swaps to real content only once every async dependency inside resolves.
  • Still experimental — never present it as finished/stable.
  • Doesn't catch errors itself → pair it with onErrorCaptured for a rejected async component.
📖 Explanation ▾

<Suspense> wraps one or more descendant components that either declare an async setup() or are loaded through defineAsyncComponent. While any of those async dependencies is still pending, <Suspense> renders its #fallback named slot instead of the real tree — once every async dependency inside has resolved, it swaps to the #default slot's real content in one move.

That "wait for all of them, then swap once" behavior is the whole point: instead of each async widget managing its own loading flag and spinner, one <Suspense> boundary gives a consistent, single loading state to everything inside it.

It's worth repeating plainly: <Suspense> has carried an experimental label since it shipped, and Vue's own docs still flag it as such — don't describe it in an interview as a finished, guaranteed-stable API.

💻 See the code ▾
Vue 
<!-- Dashboard.vue -->
<Suspense>
  <template #default>
    <AsyncWidget />             <!-- has an async setup() -->
  </template>
  <template #fallback>
    <p>Loading widget…</p>      <!-- ✅ shown until setup() resolves -->
  </template>
</Suspense>

One <Suspense> boundary, one fallback — even if AsyncWidget renders several async children of its own.

Vue 
<!-- Shell.vue — the error boundary Suspense itself doesn't provide -->
<script setup>
import { onErrorCaptured, ref } from 'vue'

const failed = ref(false)
onErrorCaptured(() => {
  failed.value = true
  return false              // ✅ stop the error here
})
</script>

If AsyncWidget's setup() rejects, this catches it — <Suspense> wouldn't on its own.

🌍 Real-world example ▾

A dashboard tile that fetches its own data inside setup() before it has anything to render. Wrapping it in <Suspense> means the rest of the page keeps rendering immediately, the tile shows a simple "Loading…" fallback for that one spot, and the moment the fetch resolves the real chart swaps in — no manual loading flag inside the component at all.
