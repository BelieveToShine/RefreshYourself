Composition — building UI by nesting, not by inheriting

"What is component composition, and how is it different from inheritance?"

Why it matters ▾
  • Interviewers use "composition vs. inheritance" to check you understand why React favors one over the other, not just that it does.
  • Portals come up any time you're building a modal, tooltip, or dropdown that has to visually escape a clipped or stacked parent container.
  • A common opener before drilling into compound components, render props, or higher-order components specifically.
🔥 Easy interview recall

Composition = "nesting and combining components, not extending a base class."

Think: wrap and combine, don't extend a base class.

📖 Explanation ▾

Composition means building UI by nesting and combining smaller components together — passing a component as a prop or as children, wrapping one component around another — rather than through a class-inheritance hierarchy. React's own documentation explicitly favors composition over inheritance: inheritance hierarchies for UI components tend to become rigid and hard to extend, while composing smaller, focused pieces stays flexible as requirements change.

Two families of pattern grew out of this. Compound components (like <Tabs><Tabs.Tab/></Tabs>) coordinate implicitly through shared context or state owned by one parent, so the pieces read naturally as one unit. Render props and higher-order components (HOCs) are older patterns for sharing behavior across otherwise-unrelated components — Hooks have replaced most, though not all, of their real-world use cases.

A Portal is a different kind of composition tool: it renders a child into a different DOM node than its parent — commonly used to escape a container's overflow:hidden or a z-index stacking context — while the child still behaves like a normal part of the React tree logically (events still bubble through the React hierarchy, not the physical DOM location). React.Children utilities and cloneElement let a component inspect, filter, or augment arbitrary children without knowing their shape in advance — mostly a library-author's tool, rarely reached for in everyday application code.

💻 See the code ▾
JSX 
function Card({ children }) {
  return <div className="card">{children}</div>;
}
Card.Header = function Header({ children }) {
  return <div className="card-header">{children}</div>;
};
Card.Body = function Body({ children }) {
  return <div className="card-body">{children}</div>;
};

// Usage — smaller pieces combined, not one big inherited component
<Card>
  <Card.Header>Title</Card.Header>
  <Card.Body>Some content goes here</Card.Body>
</Card>

Card.Header and Card.Body are separate small components combined by nesting — no shared base class involved.

JSX 
import { createPortal } from 'react-dom';

function Modal({ children }) {
  // Renders into #modal-root, NOT inside App's own DOM subtree —
  // but still a normal child in the React tree logically
  return createPortal(
    <div className="modal">{children}</div>,
    document.getElementById('modal-root')
  );
}

createPortal escapes the current DOM position — the second argument is the real DOM node it mounts into, wherever that lives on the page.

🌍 Real-world example ▾

Building furniture by combining separate, well-designed pieces — a tabletop, a set of legs, a shelf — is composition: each piece stays simple and you recombine them differently later. Trying to inherit "chair-ness" through a rigid family tree of chair subtypes is the inheritance approach — it locks the design in early and gets harder to change the more subtypes you add.
