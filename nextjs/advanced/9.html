Turbopack vs. Webpack — faster, but is it the default yet?

"Is Turbopack Next.js's default bundler now?"

Why it matters ▾
⚡ Turbopack
❗ ProblemWebpack's incremental rebuilds and hot-reload get noticeably slower as a Next.js codebase grows, so local development itself becomes the bottleneck long before any user sees a slow page.
✅ SolutionTurbopack, Next.js's Rust-based successor bundler, rebuilds and hot-reloads significantly faster — stable specifically for next dev --turbopack as of the Next.js 15 release, not yet the default for production builds.
RecallTurbopack = a faster dev server, not (yet) a faster production build.
🔥 Easy interview recall

next dev → Webpack (default)

next dev --turbopack → Turbopack, stable, faster

Production build → still Webpack by default

Think: Turbopack's Next.js 15 stability claim has one word attached to it — dev. Drop that word and the claim stops being true.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Turbopack is not Next.js's default production bundler. Its stability claim at the Next.js 15 release is scoped to next dev --turbopack only — production builds (next build) still default to Webpack at that point.

🔄 Likely Follow-up

"What's the actual user-visible benefit of Turbopack in dev mode?" Significantly faster local server startup and hot-reload/refresh times on large codebases — a developer-experience improvement, not something an end user of the deployed app would notice directly.

🎯 Say this in the interview — the exact lines to land

"Turbopack is Next.js's Rust-based successor bundler. As of the Next.js 15 release, it's stable for next dev --turbopack — local development only — and production builds still default to Webpack at that point."

  • next dev --turbopack → stable as of Next.js 15, dev only.
  • Production builds → still default to Webpack at the Next.js 15 release.
  • Real benefit → faster local rebuilds and hot-reload, a developer-experience win.
  • Version claims that move fast → re-verify against current docs before stating them.
📖 Explanation ▾

Turbopack is Next.js's own successor to Webpack, written in Rust, built specifically to make incremental builds and hot-reloading fast even as a codebase grows into hundreds or thousands of modules — the exact place Webpack's rebuild times start to drag on a developer's everyday loop of save-and-check-the-browser.

At the Next.js 15 release, that speed claim is explicitly scoped: stable for local development via next dev --turbopack. Production builds still default to Webpack at that point — Turbopack support for next build was still moving toward stability separately, on its own timeline. Stating "Turbopack is Next.js's default bundler now," without that one-word qualifier, overstates what actually shipped.

This is exactly the kind of fast-moving, version-specific detail worth re-checking against current docs before repeating it in an interview — tooling claims like this are a common place for stale information to linger.

💻 See the code ▾
CLI 
# default dev server — Webpack
next dev

# opt in to Turbopack — stable for dev as of Next.js 15
next dev --turbopack

# production build — still Webpack by default at Next.js 15, NOT Turbopack
next build

One flag changes the dev server only — next build's default bundler is a separate question with a separate answer.

🌍 Real-world example ▾

A teammate says "we should drop Webpack entirely, Turbopack's the default now." Worth checking before acting on it: at the Next.js 15 release, that's true for next dev only. Your CI's production build step is still running on Webpack by default — switching it over isn't a no-op, and isn't something the dev-mode flag already did for you.
