emit — asking the parent, not changing it yourself

"How does a child component communicate back up to its parent?"

Why it matters ▾
📣 Custom Events
❗ ProblemA child can't reach up and change a prop or a parent's data directly — props only flow down — so a button inside a child has no built-in way to tell the parent "the user just clicked me."
✅ SolutionThe child calls emit('eventName', payload) to ask the parent to react — the parent listens with @event-name="handler" on the child's tag and decides what actually happens.
Recallemit = the child's way of asking, never telling, the parent.
🔥 Easy interview recall

emit = "child raises a hand, parent decides what to do."

Think: emit('update', val) up, @update="handler" down — the mirror image of props.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Skipping defineEmits because the event still fires without it. It works at runtime either way, but you lose validation and the documentation value of an explicit contract for what the component emits.

🔄 Likely Follow-up

"Is this how v-model on a custom component works under the hood?" Yes — v-model on a component is sugar for a modelValue prop plus an update:modelValue emit, covered fully in Intermediate.

🎯 Say this in the interview — the exact lines to land

"A child can't change its parent's data directly, so it calls emit('eventName', payload) to ask the parent to react. The parent listens with @event-name="handler" on the child's tag, and decides what actually changes."

  • emit is the child's way to ask, never to directly change, the parent's state.
  • defineEmits makes the event contract explicit — skip it and it still works, but loses validation.
  • The parent listens with @event-name="handler", the same kebab-case event name the child emitted.
  • v-model on a component is exactly this pattern — a prop plus a matching emit.
📖 Explanation ▾

Props only flow one way, so a child needs a separate channel to tell its parent anything — that channel is emit. Calling emit('save', payload) inside the child doesn't change anything by itself; it just raises an event. The parent is the one that decides what happens, by listening with @save="onSave" on the child's tag.

defineEmits(['save']) in <script setup> declares which events a component can emit, the same way defineProps declares what it accepts. It's optional for the event to actually fire, but skipping it means no validation and no visible contract for anyone reading the component later.

Put together, props down and events up form a small cycle: the child emits, the parent's handler updates its own data, and the new value flows back down through the same prop the child started from. This exact cycle is also what powers v-model on a custom component — a modelValue prop paired with an update:modelValue emit.

💻 See the code ▾
Vue 
<!-- Child.vue -->
<script setup>
const emit = defineEmits(['save']);   // explicit contract
function onClick() { emit('save', { id: 1 }); }
</script>

<template>
  <button @click="onClick">Save</button>
</template>

The child raises save with a payload — it doesn't decide what saving actually does.

Vue 
<!-- Parent.vue -->
<Child @save="handleSave" />   // ✅ parent decides what "save" means

Same kebab-case name as the emit — @save catches exactly what emit('save', …) raised.

🧭 Use Cases — recognize these when they happen to you ▾
1 A child button, form, or widget needs to report a user action

A reusable button or form component emits an event instead of deciding what the click should do — the parent attaches whatever logic actually belongs to that page. This is the #1 scenario you'll actually run into.

RememberReusable widget + user action → emit it, don't hardcode the behavior.
2 You're building a custom input that needs v-model support

A modelValue prop plus an update:modelValue emit, together, are exactly what lets a parent write v-model="value" on a custom component — this event pattern is what's underneath it.

RememberCustom v-model → modelValue prop + update:modelValue emit.
3 You emit an event the parent never declared a listener for

Emitting an event nobody is listening for isn't an error — it's just a no-op. This is a common silent-bug source: the child believes it told the parent something, but without a matching @event-name, nothing reacts.

RememberNo listener on the parent → emit silently does nothing, no error thrown.
🌍 Real-world example ▾

Think of a doorbell. Pressing it (the child's emit) doesn't open the door by itself — it just signals that someone's there. Whoever's inside (the parent) decides whether to open up, ignore it, or call out first. The button never controls the door directly.
