Interface Segregation Principle — don't force a fake method

What problem does a "fat interface" cause, and how does splitting it fix that?

Why it matters ▾
  • Checks whether you see an interface as a set of capabilities a client depends on — not just a convenient bucket for related methods.
  • Shows up any time a class is stuck implementing a method it has no honest use for, usually as a stub or a thrown exception.
  • A common opener when an interviewer works through all five SOLID letters back to back.
🔥 Easy interview recall

ISP = "clients shouldn't depend on methods they don't use."

Think: IWorker with Work() + Eat() → split into IWorkable and IFeedable.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ISP does not mean "make every interface small." It means an interface should represent one cohesive capability from the client's point of view — splitting an interface that already represents one real capability just adds files, it doesn't fix anything.

🔄 Likely Follow-up

"How is this different from just following Single Responsibility?" It isn't a separate rule — ISP is Single Responsibility applied to an interface's contract, viewed from the client's side: a client should never have to depend on a capability it never calls.

🎯 Say this in the interview — the exact lines to land

"A fat interface forces every implementer to support every method on it, even ones that make no sense for that class. The fix is splitting it into smaller, cohesive interfaces so each implementer only takes the capabilities it actually has."

  • IWorker with Work() + Eat() forces RobotWorker to fake Eat().
  • Split into IWorkable / IFeedable → each class implements only what it needs.
  • ISP isn't "interfaces must be small" → it's one cohesive capability per interface.
  • Closely tied to Single Responsibility → same idea, applied to a contract.
📖 Explanation ▾

A fat interface bundles more than one unrelated capability into a single contract. The Interface Segregation Principle says a class should never be forced to depend on — or implement — a method it has no real use for, just because that method happens to live on the same interface as one it does need.

The damage shows up the moment a class can't honestly satisfy every member. IWorker.Eat() on a RobotWorker has no real behavior to run, so the implementer is stuck choosing between a silent no-op (a bug waiting to be called later) or a thrown NotImplementedException (a runtime failure for code that compiled fine) — both are the interface's fault, not the class's.

Splitting the interface doesn't shrink it for its own sake — it draws the contract around what the client actually calls. IWorkable and IFeedable are each one capability a caller can depend on without dragging in the other, so RobotWorker can honestly implement one and skip the other entirely.

Fat interface (before)Segregated interfaces (after)
What the implementer must handleEvery method, even irrelevant onesOnly the methods for its own capability
Unused methods❌ stubbed out or throw NotImplementedException✅ none — nothing to fake
Cohesion (client's view)❌ multiple unrelated capabilities bundled together✅ one capability per interface
Worked exampleIWorker.Eat() on RobotWorkerRobotWorker : IWorkable only
💻 See the code ▾
C# 
public interface IWorker
{
    void Work();
    void Eat();
}

public class RobotWorker : IWorker
{
    public void Work() { /* ... */ }              // ✅ makes sense
    public void Eat() => throw new NotImplementedException(); // ❌ forced fake

RobotWorker has no real Eat() behavior — the interface forced a method it can't honestly implement.

C# 
public interface IWorkable { void Work(); }
public interface IFeedable { void Eat(); }

public class RobotWorker : IWorkable
{
    public void Work() { /* ... */ }   // ✅ only what it needs
}

public class HumanWorker : IWorkable, IFeedable
{
    public void Work() { /* ... */ }
    public void Eat() { /* ... */ }    // ✅ genuinely applicable

Neither class fakes a capability it doesn't have — RobotWorker never even sees Eat().

🌍 Real-world example ▾

One IRepository interface declares Save(), Delete(), AND GenerateReport(). A ReadOnlyAuditRepository that must never write or delete ends up implementing Save()/Delete() as no-ops or thrown exceptions just to satisfy the interface. Splitting it into IReadableRepository and IWritableRepository lets the read-only class implement only the read side — no fake methods, and no risk of someone calling a stubbed Delete() in production.
