Cost control — four levers before you ever touch a cheaper model

How do you control LLM cost and latency in a high-traffic app?

Why it matters ▾
  • Every production LLM app eventually gets asked "why is the bill this high" — this is the standard senior/architect answer, not a single trick but a set of levers matched to the actual traffic pattern.
  • Interviewers use this to check whether a candidate actually understands token billing mechanics, not just "use a cheaper model" as a one-line answer.
  • Caching in particular is commonly misunderstood — treating exact-match, semantic, and provider-native prompt caching as the same thing is a real, catchable gap.
🔥 Easy interview recall

Caching → don't reprocess what you've already paid for

Model tiering → cheap model first, escalate only when needed

Context trimming → send less history, not the full transcript

Token budgets → a hard ceiling per feature, set in advance

Think: caching and smaller models cut cost AND latency together — streaming only helps the feel of latency, it doesn't cut cost at all.

⚠️ Common Trap

Treating "caching" as one thing. Semantic caching matches on similar meaning and reuses a past response; provider-native prompt caching matches an exact, repeated prefix of the input and still calls the model every time — mixing these up in an interview is an easy, catchable mistake.

🔄 Likely Follow-up

"Does streaming reduce cost the same way caching does?" No — streaming only improves how fast the response feels by showing tokens as they're generated; the total tokens processed and billed are unchanged. Caching and smaller models are what actually cut cost, and they cut latency too, as a side effect.

🎯 Say this in the interview — the exact lines to land

"I'd reach for four levers: caching so I never reprocess text I've already paid for, model tiering so only the requests that truly need it hit the expensive model, context trimming so the prompt doesn't grow every turn, and a token budget per feature so cost per request stays bounded — and I'd be careful not to conflate exact-match, semantic, and provider-native prompt caching, since they solve different problems."

  • Exact-match caching → reuse a response for an identical repeated request.
  • Semantic caching → reuse a response for a differently-worded, equivalent request — matched by meaning, not bytes.
  • Provider-native prompt caching → reuse a repeated PREFIX of the input — only the new suffix is reprocessed and billed each call.
  • Model tiering → cheap model first, escalate only when the task needs it — the deeper routing logic is its own topic.
  • Context trimming and token budgets → bound how much gets sent and how much a feature is allowed to cost, per request.
📖 Explanation ▾

Token budgeting means setting an explicit limit on how much context or output a given feature is allowed to use, so cost per request stays bounded and predictable instead of drifting up as prompts and histories grow.

Caching is really three distinct mechanisms, not one. Exact-match caching reuses the response for an identical repeated request. Semantic caching reuses a response when a differently-worded request is close enough in meaning — matched by similarity, not by exact text. Provider-native prompt caching (Anthropic's prompt caching, OpenAI's cached input tokens) is a different mechanism entirely: the provider caches the exact repeated prefix of a prompt — a long system prompt or reused document — so that prefix doesn't have to be reprocessed, and billed in full, on every call. The model still runs on every call; only the shared prefix is cheap to reuse. Confusing this with semantic caching is a real, common mistake — semantic caching is about matching a differently-worded whole request, prompt caching is about reusing a shared prefix.

Model tiering routes easy or cheap requests to a smaller, cheaper model, and only escalates to a larger model when the task actually needs it — sometimes called "cheap model first, escalate." Context trimming cuts how much text actually gets sent in the prompt, for example summarizing older conversation turns instead of resending the full transcript every call. Latency and cost levers overlap but aren't identical: streaming improves how fast a response feels without cutting cost at all, while smaller models and caching cut cost and latency together.

💻 See the code ▾
Python 
# provider-native prompt caching — mark the long, reused part as cacheable
response = client.messages.create(
    model="...",
    system=[{
        "type": "text",
        "text": LONG_SHARED_SYSTEM_PROMPT,   # same bytes, every call
        "cache_control": {"type": "ephemeral"}  # ✅ cache this prefix
    }],
    messages=[{"role": "user", "content": new_question}]  # varies — never cached
)

The marker goes on the last block of the stable content. The varying question after it is never part of the cached prefix — that's exactly why only it gets reprocessed and billed in full on every call.

Python 
# model tiering — cheap model first, escalate only if it says it's unsure
result = call_model("small-cheap-model", request)

if result.needs_escalation:
    result = call_model("large-expensive-model", request)  # rare path

Most traffic never reaches the second call — the expensive model only runs for the minority of requests that actually justify its cost.

🌍 Real-world example ▾

A support-chat product pins a 2,000-token product manual at the front of every request as a system prompt. Without provider-native prompt caching, that manual gets reprocessed and billed on every single message. With it turned on, the manual is billed once, then read from cache at a fraction of the price on every later message in the conversation — only the customer's new message is billed in full each time.
