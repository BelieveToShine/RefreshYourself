The event loop gets the credit — what structure underneath actually makes it possible?

"Walk me through what actually happens when the JavaScript engine runs your code — execution contexts, the call stack, the heap — before we even get to the event loop's ordering?"

Why it matters ▾
  • Every other topic in this tier quietly assumes you already have this picture — Advanced Async Concurrency, Memory & Garbage Collection, and Performance & Rendering all lean on "execution context, call stack, heap" without re-explaining it.
  • A common senior-level follow-up right after the Event Loop question: once you've named the task/microtask order correctly, the next question is "okay, but what structure is the engine actually operating on to make that order possible?"
  • It ties together three things most candidates have studied as separate facts — scope/hoisting, closures, and the event loop's ordering — into one picture of the whole machine.
🔥 Easy interview recall

Runtime = "the structure the engine builds to run your code — the event loop only decides the ORDER on top of it."

Think: source → context → call stack → heap → async APIs → event loop — built once per script, then the loop just keeps going.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The event loop is not "the whole runtime." It's one piece that decides ORDER; the execution context, the call stack, and the heap are the STRUCTURE it operates on — describing only the loop is describing the last stage, not the machine.

🔄 Likely Follow-up

"Where does a closure's variable actually live once the function that created it has already returned?" On the heap — the outer function's execution context is normally discarded when it returns, but if an inner function still references its variables, the engine keeps that lexical environment alive on the heap for as long as the closure exists.

🎯 Say this in the interview — the exact lines to land

"Running a script builds a structure first — a global execution context, then a new execution context pushed onto the call stack for every function call, with objects and closures kept alive on the heap. The event loop is a separate piece that only decides what order queued work runs in, on top of that structure."

  • Execution context → one global, one new per function call, pushed onto the call stack.
  • Call stack = which context is running right now; heap = where objects and closures are actually kept.
  • Variable lookup walks the lexical environment outward — the same mechanism behind Scope & Hoisting and Closures.
  • Async APIs (setTimeout, fetch, DOM events) run outside the call stack entirely — that's why they need the event loop to hand work back.
  • This page is structure, not order — Event Loop (Intermediate) covers task/microtask sequencing on top of it.
📖 Explanation ▾

Running a file is not one flat step — the engine builds a structure first. Before any of your code executes, it creates the global execution context and pushes it onto the call stack. Every function call pushes its own fresh execution context on top of that; when a call finishes, its context is normally popped and its local variables are thrown away — unless a closure still points at them, in which case the underlying lexical environment survives on the heap for as long as that closure is reachable.

There's exactly one global execution context per running program, created once, before any of your code runs. A function execution context is different — a brand new one is created every single time that function is called, even the same function called twice in a row, which is exactly why recursion works: each call gets its own independent context and its own copy of the local variables.

Resolving a variable means walking that context's lexical environment outward — first its own, then the environment it was defined inside, and so on, based on where the code was written, not where it was called from. This is the same mechanism behind Scope & Hoisting and Closures — this page is just naming the structure that makes both of those possible. The Event Loop page is a different layer entirely: it covers order — the call stack empties, microtasks drain, then the next macrotask runs. This page covers the structure underneath that ordering — the execution contexts, the call stack, and the heap that the event loop is handing work back into.

💻 See the code ▾
JS 
// global execution context already pushed before this line runs
function outer() {
  console.log("outer starts");   // outer's context is on top of the stack
  inner();                        // inner's context gets pushed ON TOP of outer's
  console.log("outer ends");     // inner already popped — outer resumes
}
function inner() {
  console.log("inner runs");      // top of the call stack right now
}
outer();
// stack: [global] → [global, outer] → [global, outer, inner] → back down

Every call pushes a brand-new execution context — even the SAME function called twice gets two independent ones.

JS 
function makeCounter() {
  let count = 0;              // lives in makeCounter's lexical environment
  return function increment() {  // this inner function is a closure over count
    count++;
    return count;
  };
}
const counter = makeCounter();  // makeCounter's execution context is popped...
counter();                       // ...but count is still reachable — kept on the heap
counter();                       // 2

makeCounter's execution context is gone from the call stack, but its lexical environment survives on the heap because increment still references count.

🌍 Real-world example ▾

Think of the call stack as a stack of sticky notes on your desk — each note is one execution context, and you can only work on whichever note is on top. The heap is the filing cabinet behind you: anything a note needs to keep around after it's thrown away, like a closure's variables, gets filed there instead of tossed out.
