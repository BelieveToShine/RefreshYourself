Garbage Collection — why gen 0 gets checked far more than gen 2

"What are generations 0, 1, and 2, and why do they exist?"

Why it matters ▾
  • A leading cause of mysterious latency spikes in high-throughput services — a full Gen 2 collection can pause the app for milliseconds to seconds.
  • Interviewers use it to check whether you see the GC as a performance concern, not just "automatic memory cleanup."
  • The LOH's fragmentation behavior is a real production surprise most developers only learn about after hitting it.
🔥 Easy interview recall

Gen 0 → checked constantly, cheap

Gen 1 → buffer in between

Gen 2 → checked rarely, expensive

Think: Gen 0 is nearly free to scan. Gen 2 is expensive to scan — so it's checked least.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A garbage collection always scans the whole heap." It doesn't — a Gen 0 collection only scans Gen 0; Gen 1 and Gen 2 are left completely untouched unless a higher-generation collection is actually triggered.

🔄 Likely Follow-up

"What about really large objects — do they also start in Gen 0?" No — allocations of roughly 85KB or more go straight to a separate heap, the Large Object Heap, skipping Gen 0 entirely; it's collected less often and, unlike the rest of the heap, historically isn't compacted by default, which can fragment it over time.

🎯 Say this in the interview — the exact lines to land

"Most objects die young, so the runtime organizes the heap into generations. Gen 0 is checked constantly because it's small and cheap to scan; Gen 2 is checked rarely because scanning long-lived survivors is expensive. Large allocations — roughly 85KB or more — skip the generations entirely and go straight to a separate Large Object Heap, which historically isn't compacted by default."

  • Gen 0 → checked on almost every collection — small, cheap, most objects die here.
  • Gen 2 → checked rarely — only long-lived survivors end up there, and scanning it is expensive.
  • LOH → separate heap for big allocations (~85KB+), bypassing the generations entirely.
  • In a low-latency service, the real fix is allocating less — pool buffers, avoid boxing/LINQ allocations — not tuning GC settings first.
📖 Explanation ▾

Most objects allocated in a request or a loop iteration — temporaries, small helper objects — never live long enough to see a second collection. The runtime builds its whole strategy around that one observation: check the newest allocations (Gen 0) constantly, since that's where almost all the garbage actually is, and check older survivors far less, since scanning them rarely finds anything to reclaim.

An object that survives a Gen 0 collection is promoted to Gen 1; survive again and it's promoted to Gen 2. Gen 2 is where genuinely long-lived objects — caches, singletons, static state — end up, and a full Gen 2 collection is the expensive one, because it has to walk everything still alive across the whole heap.

The Large Object Heap is a separate concern entirely: any allocation at or above roughly 85KB goes straight there, never touching Gen 0. It's collected on its own schedule and, unlike the generational heap, historically isn't compacted by default — repeated large allocations can leave it fragmented with unusable gaps even when there's technically enough free memory.

💻 See the code ▾
C# 
Console.WriteLine(GC.CollectionCount(0));  // Gen 0 — this climbs constantly
Console.WriteLine(GC.CollectionCount(2));  // Gen 2 — this barely moves

Watch the two numbers in a busy app — Gen 0's count climbs constantly while Gen 2's barely moves.

C# 
var small = new byte[1_000];    // ~1KB — lands in Gen 0, normal heap
var big   = new byte[100_000];  // ~100KB — over ~85KB, straight to the LOH

Crossing roughly 85KB sends the allocation straight to the LOH — it never touches Gen 0 at all.

C# 
ArrayPool<byte> pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(4096);   // ✅ reused — no new Gen 0 allocation
pool.Return(buffer);          // back in the pool for next time

In a low-latency service, this is the real fix — fewer allocations means fewer, cheaper collections, not tuning the collector itself.

🌍 Real-world example ▾

Analogy: Gen 0 is the inbox on your desk — checked constantly because that's where new, quickly-resolved things pile up. Gen 2 is the archive room — checked rarely, because going through it is expensive and most of what's there is staying for good.

Architecture scenario: You're designing a low-latency service where an occasional multi-second GC pause is unacceptable — what do you actually do about it? Start by minimizing the allocation rate in hot paths — pool and reuse buffers, avoid boxing and LINQ allocations that create hidden garbage — since fewer allocations mean fewer, cheaper collections. Beyond that, evaluate Server GC vs. Workstation GC and concurrent/background GC settings, and in the most extreme cases redesign around Span<T>-based buffer reuse to avoid large short-lived allocations entirely. Calling GC.Collect() and hoping is not the fix.
