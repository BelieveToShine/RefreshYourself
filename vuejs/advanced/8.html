pinia.use() — one registration, every store gets it

"How would you add shared behavior — like persistence — to every Pinia store at once?"

Why it matters ▾
🔌 pinia.use(plugin)
❗ ProblemWriting the same cross-cutting logic — like persisting state to localStorage — individually inside every store's own actions duplicates code that drifts out of sync as more stores get added.
✅ Solutionpinia.use(plugin) registers a function that runs once per store creation, receiving context — the store, the pinia instance, the app. It adds shared behavior to every store at once: persistence, logging every action, or a shared property or method, without repeating code in each one.
Recallpinia.use() = shared store behavior, written once.
🔥 Easy interview recall

Pinia plugin = "written once, applied to every store."

Think: pinia.use(plugin) → registered once, globally runs per store → receives { store, pinia, app }

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Copy-pasting the same persistence logic into every store's own actions is not the right pattern. That duplicated code drifts out of sync as more stores are added — exactly what a single pinia.use() plugin exists to prevent.

🔄 Likely Follow-up

"Give a concrete example of what a plugin adds to a store." A persistence plugin might watch the whole store's state and write it to localStorage on every change, then read it back in on store creation — added to every store that opts in, with zero per-store code.

🎯 Say this in the interview — the exact lines to land

"pinia.use(plugin) registers a function that runs once per store creation, receiving context — the store, the pinia instance, the app. It's used to add shared behavior to every store at once: persisting state to localStorage, logging every action, or adding a shared property or method — without repeating that code inside each store."

  • pinia.use(plugin) → runs once per store creation, not once globally.
  • Plugin context → { store, pinia, app } — everything needed to extend a store.
  • Repeating cross-cutting logic per store → duplicated code that drifts out of sync.
  • A persistence plugin → watches state, writes to localStorage, reads it back on creation.
📖 Explanation ▾

A Pinia plugin is just a function. pinia.use() registers it against the pinia instance, and Pinia calls it once for every store created from that point on, passing a context object — the store being created, the pinia instance itself, and the Vue app. A plugin can also return a plain object, and Pinia merges its properties straight onto the store — a clean way to add a shared helper method to every store without editing each store file.

A real persistence plugin typically does two things: on creation, it checks localStorage for previously saved state and applies it with store.$patch(); then it calls store.$subscribe() to run a callback on every future mutation, writing the current state back out. Neither step needs to know anything about which store it's attached to — store.$id gives it a unique key automatically.

Order matters: a plugin only applies to stores created after pinia.use() runs. Registering plugins before any useStore() call anywhere in the app is what guarantees every store actually picks it up.

💻 See the code ▾
JavaScript 
function persistPlugin({ store }) {
  const saved = localStorage.getItem(store.$id)
  if (saved) store.$patch(JSON.parse(saved))   // read back on creation

  store.$subscribe(() => {
    localStorage.setItem(store.$id, JSON.stringify(store.$state))  // ✅ write on every change
  })
}

store.$id makes this the same function work for every store, with no per-store branching.

JavaScript 
const pinia = createPinia()
pinia.use(persistPlugin)   // ✅ every store created after this line gets it

No individual store file needs to know this plugin exists.

🧭 Use Cases — recognize these when they happen to you ▾
1 You want every store's state to survive a page refresh

No individual store needs its own localStorage code — registering the plugin once covers every store the app has, now and later.

RememberOne plugin registration → every store gains it automatically.
2 You register the plugin after a store has already been used elsewhere

A common interview trap: assuming a plugin retroactively applies to every store, including ones created before registration. It only runs for stores created after pinia.use() executes.

RememberRegister plugins before any store is ever used, not after.
3 You want a shared helper method, like a logger, on every store

A plugin returning { logAction } makes store.logAction() available on every store, with no per-store wiring.

RememberA returned object from a plugin → merged onto every store.
🌍 Real-world example ▾

It's like adding a universal surge protector at the wall outlet instead of buying a separate one for every single device you plug in — install it once, and anything plugged in afterward is automatically covered.
