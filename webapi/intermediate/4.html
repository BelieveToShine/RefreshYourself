Request body vs. headers — the payload vs. the metadata

What actually belongs in the request body versus the headers?

Why it matters ▾
📦 Body
❗ ProblemCram an order's line items into a custom header instead and you hit real header size limits, and tools like Swagger and request loggers never find the payload where they expect it.
✅ SolutionThe body carries the resource's actual field values — the fields your model-binding code reads directly, with no practical size ceiling the way headers have.
RecallBody = the payload — read by your model-binding code.
📋 Headers
❗ ProblemHide the auth token or a content-negotiation hint inside the JSON body and the framework's own middleware never sees it — nothing reads a custom {"token": "..."} field without bespoke code.
✅ SolutionHeaders carry metadata about the request itself — identity, format, and cross-cutting concerns — exactly where framework middleware like auth and content negotiation already looks.
RecallHeaders = metadata — read automatically by middleware.
🔥 Easy interview recall

Body → the payload — what the request is about

Headers → the metadata — how to handle it

Think: Body is the letter. Headers are the envelope — address, postage, "handle with care."

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Business data doesn't belong in a header, and identity/format info doesn't belong in the body. Jamming an order's line items into a custom header breaks at real header size limits and skips tooling that expects the body to hold the payload — and putting a token or Accept preference inside the JSON body bypasses the middleware that already reads Authorization/Accept automatically.

🔄 Likely Follow-up

"Where does something like an idempotency key belong — body or header?" Header — Idempotency-Key: <uuid> — because it's metadata about how to process the request (retry/dedupe logic), not part of the resource data being created. See Idempotency for how the server actually uses that key.

🎯 Say this in the interview — the exact lines to land

"The body carries the actual payload — the data the operation is fundamentally about. Headers carry metadata about the request itself: identity, format, and cross-cutting concerns like auth and tracing — not the core content."

  • Content-Type → what format the body is in, JSON or form data.
  • Authorization → who's making the request, a bearer token.
  • Accept → what format the client wants back, content negotiation.
  • Rule of thumb → identity, format, or cross-cutting is a header; the actual resource data is the body.
📖 Explanation ▾

The body exists to carry the fields of the resource the request is fundamentally about — the fields of a new order being created, the updated values for a PUT. It's the "content" of the request, the same way a letter's content is what's written on the page inside the envelope.

The headers exist to describe how to interpret or process that content, not to add more content of their own. Content-Type says what format the body is in. Authorization says who's making the request. Accept says what format the client wants the response in. A custom header like a correlation ID or an idempotency key follows the same pattern — it's an instruction about handling the request, not a piece of the resource itself.

Both directions of the mistake break something real. A large or structured value stuffed into a header runs into size limits most servers and proxies enforce, and it hides the "real" data from tools like Swagger/OpenAPI and request loggers that expect the payload to live in the body. Going the other way — putting a token or a content-negotiation hint inside the JSON body — means standard HTTP-aware middleware never sees it: authentication middleware reads the Authorization header automatically, but nothing reads a custom {"token": "..."} field without bespoke code written just for that.

💻 See the code ▾
C# 
public class CreateOrderRequest
{
    public int ProductId { get; set; }   // resource data → body
    public int Quantity { get; set; }    // resource data → body
}

[HttpPost]
public IActionResult CreateOrder(
    [FromBody] CreateOrderRequest request,       // ✅ payload in the body
    [FromHeader(Name = "Idempotency-Key")] Guid key)  // ✅ retry metadata in a header

The order's own fields bind from the body; the retry-handling key binds from a header — each in the slot the framework already expects.

C# 
// ❌ wrong: business data jammed into a custom header
request.Headers.Add("X-Order-Items", jsonLineItems);  // hits header size limits

// ❌ wrong: identity info hidden inside the JSON body
public class LoginRequest
{
    public string Token { get; set; }  // auth middleware never reads this
}

Both directions of the mistake compile fine — the bug only shows up when a proxy truncates the header, or auth middleware silently finds no Authorization header to check.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to send an auth token with every request

The token authenticates the request itself, not the resource being created or read — and the framework's auth middleware is already built to read it straight off the Authorization header. Put it in the JSON body instead and that middleware never sees it; you'd need bespoke code just to pull it back out.

RememberAuth token → Authorization header, never the body.
2 Your POST creates a resource and the client might retry it

The idempotency key tells the server how to handle a duplicate retry — it's an instruction about processing the request, not one of the order's own fields. It rides in the Idempotency-Key header while the actual order data (productId, quantity) stays in the body.

RememberIdempotency-Key → header; the resource fields still go in the body.
3 You need to say what format you're sending and what format you want back

Content-Type describes the format of the body you're sending; Accept tells the server what format you want the response back in. Both are instructions about format, not the payload itself, so both live in headers — the body never states its own format.

RememberFormat in/out → Content-Type and Accept headers, not body fields.
🌍 Real-world example ▾

A teammate's pull request adds a new field by stuffing it into a custom header instead of the DTO, "to avoid a breaking change." It works locally, then a corporate proxy in production silently strips or truncates the oversized header, and the field goes missing on some requests but not others. The fix is the same rule this page teaches: a new field is resource data, so it belongs in the body — versioning or extending the DTO is the correct way to add it, not smuggling it through a header never meant to carry payload.
