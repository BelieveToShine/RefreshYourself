useEffect — code that reacts to a render, not code that causes one

"What is useEffect for, and when exactly does its cleanup function run?"

Why it matters ▾
  • Interviewers use this to check you actually understand the render cycle, not just that you can paste a useEffect call.
  • Comes up any time a component talks to something outside React — a subscription, a timer, a manual DOM measurement, or a fetch.
  • The dependency-array and cleanup-timing details are a favorite follow-up trap — a lot of candidates get the empty-vs-missing array distinction backwards.
🔥 Easy interview recall

useEffect = "code that runs after the screen updates, to keep something outside React in sync."

Think: The dependency array decides WHEN it reruns. Cleanup fires before the next effect — and on unmount, not just at the very end.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Leaving the dependency array off entirely is not the same as using an empty array. No array at all means the effect runs after every single render; an empty array [] means it runs once, after the first render only — mixing these up is a common, real bug, usually an effect firing far more often than intended.

🔄 Likely Follow-up

"What's a stale closure inside useEffect?" The effect function captures the props/state values from the exact render it was created in — if a dependency the effect actually reads wasn't listed in the dependency array, the effect keeps using that old, stale snapshot on every later render instead of picking up the current value.

🎯 Say this in the interview — the exact lines to land

"useEffect runs code after a render is committed to the screen, to synchronize the component with something outside React — a subscription, a timer, or manual DOM work. The dependency array controls how often it reruns: an empty array means once, after the first render; no array at all means after every render. Its cleanup function runs before the effect runs again, and one final time when the component unmounts."

  • Empty array [] → runs once, after mount. No array at all → runs after every render.
  • Cleanup → runs before the next effect AND on unmount, not only at the very end.
  • Stale closure → effect keeps an old snapshot of any value it reads but doesn't list as a dependency.
  • Not everything belongs in an effect → logic that can run during render or inside an event handler usually shouldn't be routed through useEffect.
  • A new object/function every render → is a new reference, so using it as a dependency can rerun the effect on every render.
📖 Explanation ▾

useEffect lets a component reach outside React's own rendering — a subscription, a timer, a manual DOM read, a fetch — without doing that work during render. React commits the render to the screen first, then runs the effect afterward, asynchronously, after paint. That ordering is the whole point: the user already sees the updated UI before this "extra" work happens.

The dependency array is what controls whether that extra work runs again. Skip it, and React reruns the effect after every render, no matter what changed. Pass an empty array, and it only runs once, right after the very first render. Pass actual values, and it reruns only when one of those values is different from last time — which is also why a fresh object or function literal (a new reference every render, even with identical-looking contents) can quietly make an effect rerun constantly.

The function an effect optionally returns is its cleanup. React calls it right before running the effect again (so a stale subscription or timer never survives past its own dependency change), and one final time when the component unmounts. A stale closure happens when the effect reads a value from its own render's snapshot instead of the current one — the fix is almost always "list it as a dependency," not "ignore the linter."

💻 See the code ▾
JSX 
useEffect(() => {
  // runs after render — sets up the subscription
  const sub = subscribe(id);

  return () => sub.unsubscribe();  // 🧹 cleanup: before next effect, and on unmount
}, [id]);

Cleanup fires twice in this component's life: once before this effect reruns (id changed), and once on unmount — never only at the end.

JSX 
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);  // ❌ always logs 0 — closure never updates
    }, 1000);
    return () => clearInterval(id);
  }, []);  // ❌ count is read above but missing from deps

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

The effect captured count from the render where it was created (0) and, with an empty array, never reruns to pick up a newer value — a classic stale closure.

🌍 Real-world example ▾

Renting a projector for a meeting. Setting it up is the effect — you don't do it before the room is ready. Packing it back up is the cleanup, and it happens twice in practice: right before the next meeting needs a different setup, and again if the room gets vacated for good — never just once at the very end of the day.
