Same object, or just same content?

Why it matters ▾
  • Explains why two "obviously equal" objects sometimes fail an equality check.
  • Tells you exactly which check means "the exact same instance," not just "looks the same."
  • Comes up the moment classes and comparisons show up in an interview.
🔥 Easy interview recall

== → default check

.Equals() → override-able value check

ReferenceEquals() → nobody can fool it

Think: string/record already override Equals → content match, not identity

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

== isn't always a value check. On a plain class it's identity by default — the same answer as ReferenceEquals() — until someone overloads it.

🎯 Say this in the interview — the exact lines to land

"== defaults to identity for classes. .Equals() is the one you override for value equality. ReferenceEquals() always means the exact same object, no matter what's overridden."

  • .Equals() → use for value equality — two strings, two records, dictionary/HashSet keys.
  • ReferenceEquals() → use when it MUST be the same object — cache hits, singletons, node identity.
📖 Explanation ▾

For a plain class, all three checks do the same thing by default: they ask "is this literally the same object in memory?" Two different Person objects with identical data are still two different objects — so ==, .Equals(), and ReferenceEquals() all say false.

.Equals() is the one you can change — override it (and GetHashCode()) to compare content instead of identity. Types like string and record already do this for you.

ReferenceEquals() never changes its mind — it always means "the exact same object," no matter what you've overridden. That makes it the one truly reliable identity check.

So which one do you actually reach for? Use ReferenceEquals() when the question really is identity — is this the same cached object, the same node, the same singleton. Use .Equals() (or == once it's overloaded) when the question is about value — do these two represent the same data, like two strings or two DTOs with matching fields. Plain == on ordinary classes is identity by default, same as ReferenceEquals() — until someone overloads it.

💻 See the code ▾
C# 
var p1 = new Person("Sam");
var p2 = new Person("Sam");
p1 == p2;              // ❌ false — identity by default, not value

Same data, two different objects — == says no unless someone overloads it.

C# 
var a = "cat";
var b = "cat";
a.Equals(b);            // ✅ true — string overrides Equals for content

.Equals() is the one you (or the BCL) can override to compare content instead of identity.

C# 
var p3 = p1;
ReferenceEquals(p1, p3);   // ✅ true — same object
ReferenceEquals(p1, p2);   // ❌ false — different objects, even same data

ReferenceEquals() never changes its answer — not even string can override it.

🌍 Real-world example ▾

Twins vs. the same person. Two identical twins can look exactly alike (.Equals()-style content match, if you taught someone to compare by appearance) — but they are still two different people (ReferenceEquals() says no). == defaults to asking the twin question too, unless you specifically teach it to compare by looks instead.
