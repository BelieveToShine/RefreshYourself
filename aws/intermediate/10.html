Cognito authenticates people; IAM authenticates AWS itself

"How would you protect a public API, and how does API Gateway plug into Cognito for end-user auth?"

Why it matters ▾
📄 REST API
❗ ProblemA public API that needs request/response transformation, usage plans, or API keys can't get any of that from the leaner HTTP API type — that feature set simply isn't there.
✅ SolutionREST API is the older, fuller-featured type — it keeps transformation, usage plans, and API keys built in, at the cost of higher cost and latency than HTTP API.
RecallREST API = more built-in features, higher cost and latency.
⚡ HTTP API
❗ ProblemPaying REST API's extra cost and latency for a straight proxy to Lambda that never touches transformation, usage plans, or API keys wastes both money and speed.
✅ SolutionHTTP API trims to a leaner feature set built for exactly that case — cheaper and lower latency — which is why most new serverless APIs default to it.

⚠️ Common Trap

"IAM auth and Cognito solve the same problem." They don't — an IAM authorizer checks a SigV4-signed request from an AWS principal (another service, another account), while a Cognito user pool authorizer checks a token issued to an actual human user of the app. Swapping one for the other doesn't just fail, it answers the wrong question entirely.

🔄 Likely Follow-up

"How would you handle API versioning?" The common approaches are a version in the URL path (/v1/, /v2/) or via a custom header — API Gateway stages themselves can also represent different deployed versions.

📖 Explanation ▾

API Gateway sits in front of your backend — usually Lambda — as a managed front door for every request. Two flavors exist: the older REST API type has more built-in features (request/response transformation, usage plans, API keys), while the newer HTTP API type is cheaper and has lower latency, at the cost of fewer features. Most new serverless APIs default to HTTP API unless a REST-only feature is actually needed.

The most common integration pattern is Lambda proxy integration — API Gateway forwards the whole request (headers, body, query string) to Lambda as-is, instead of you mapping every field by hand. Two protective features live at the gateway layer itself: throttling (rate limits that reject excess requests before they ever reach the backend) and caching, which can serve a repeated GET response straight from the gateway without invoking Lambda at all.

Authorization is where the real distinction lives. A Cognito user pool authorizer validates a token issued to an actual end user of the app — the right choice for a public-facing mobile or web app. An IAM authorizer checks a signed (SigV4) request from an AWS principal — another service, another account, anything acting as AWS itself, not a human user. A Lambda authorizer is custom code you write when neither built-in option fits the auth scheme you actually need.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your API is a straight pass-through to Lambda — no transformation, usage plans, or API keys

A straight proxy to Lambda never touches REST API's extra machinery, so paying its higher cost and latency buys nothing here — HTTP API gives the same proxy behavior for less. This is the default for most new serverless APIs.

RememberPlain Lambda proxy → HTTP API is the default.
2 Partners need API keys, usage plans, or request/response transformation

Usage plans, API keys, and request/response transformation only exist on the REST API type — HTTP API's leaner feature set has no built-in way to add them. This is the one case where REST API's extra cost and latency earns its keep.

RememberUsage plans / API keys / transformation → REST API.
3 Your API is public-facing, called by real people signing into your app

This is a Cognito user-pool job, not an IAM job — Cognito validates a token issued to an actual human user of the app, while IAM checks a signed request from an AWS principal, which a real end user's login never is.

RememberReal human sign-in → Cognito, not IAM.
🌍 Real-world example ▾

A public mobile app authenticates its end users via a Cognito user pool, which issues a token API Gateway validates before ever invoking the backend Lambda.
