revalidate: 60 is set — so which cache is actually serving the stale page?

"A page has revalidate: 60 set but users still report seeing stale data — how do you track down which layer is actually serving it?"

Why it matters ▾
🗂️ Four Possible Layers, One Symptom
❗ ProblemStale data looks identical no matter which of four caching layers — the Data Cache, the Full Route Cache, the client's Router Cache, or a CDN/edge cache in front of the whole deployment — is actually responsible, so fixing the wrong one wastes effort and still doesn't fix anything.
✅ SolutionTriage in order: check the Data Cache's actual elapsed time against the revalidate window (remembering ISR serves one more stale response before regenerating), try router.refresh() to rule out the client's Router Cache, and check response headers for a CDN/edge cache sitting in front of everything else.
RecallSame symptom, four possible layers — confirm which one before reaching for a fix.

Data Cache → revalidateTag/revalidatePath

Full Route Cache → revalidatePath

Router Cache → router.refresh()

CDN / edge → purge, or a Cache-Control header

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"I set revalidate, so it must be the Data Cache." The symptom looks identical whether it's the Data Cache, the Full Route Cache, the client's Router Cache, or a CDN sitting in front of the whole deployment — skipping the other three layers means calling revalidateTag and still seeing stale data, with no idea why.

🔄 Likely Follow-up

"What's the fastest way to rule layers in or out?" Hard-refresh with caching disabled in devtools to rule out the client's Router Cache, check the response headers for a CDN cache indicator, and — if you can — log or inspect the Data Cache's actual last-fetched timestamp directly.

🎯 Say this in the interview — the exact lines to land

"Stale data can come from four different layers — the Data Cache, the Full Route Cache, the client's Router Cache, or a CDN/edge cache — and the symptom looks the same from all four, so I'd confirm which layer is actually responsible before reaching for a fix, instead of assuming it's the one I happened to configure."

  • Data Cache past its window → revalidateTag/revalidatePath, the layer-specific fix.
  • Stale client-side RSC payload → router.refresh() clears the Router Cache, not a server-side call.
  • A CDN in front of the deployment → it caches independently of Next.js's own layers — purge it or fix its headers.
  • ISR specifically → serves one more stale response before regenerating, so "just past 60s" can still look stale once.
📖 Explanation ▾

Each of the four layers caches independently, and none of them know about the others — which is exactly why a Data Cache fix doesn't help if the real culprit is the client's Router Cache holding an old React Server Component payload from before the last navigation. router.refresh() re-fetches the current route from the server without a full page reload or losing client state — that's the targeted fix for this one layer only.

The Full Route Cache stores the rendered result of a whole route segment at build time (or after ISR regenerates it); it sits on the server, one layer up from the Data Cache that individual fetch calls populate. revalidatePath clears both — the route's cached render and the underlying data — while revalidateTag targets only the tagged data fetches.

A CDN or edge cache in front of the whole deployment is the layer easiest to forget, because it isn't part of Next.js at all — it's infrastructure sitting between the browser and the deployment, caching the response by its own rules (often an HTTP Cache-Control header) regardless of what Next.js's own revalidation does underneath it.

💻 See the code ▾
JS 
// Data Cache / Full Route Cache — clear by tag or by path
import { revalidateTag, revalidatePath } from 'next/cache';

await revalidateTag('products');   // ✅ targets tagged fetch() calls only
await revalidatePath('/products/42'); // ✅ clears the route's cached render too

Neither call touches the client's Router Cache — a user already on that page still sees the old RSC payload until they navigate again, or it's refreshed.

JSX 
'use client';
import { useRouter } from 'next/navigation';

const router = useRouter();
router.refresh(); // ✅ re-fetches the current route — clears only the Router Cache

This is the one tool that reaches the client-side layer — the server-side calls above can't touch it.

🌍 Real-world example ▾

A product page sets revalidate: 60, but a customer reports seeing a price that's several minutes old. First check the Data Cache's actual elapsed time — ISR still serves one more stale hit before regenerating, so "just past 60 seconds" can genuinely look stale once. If the timing checks out, the next suspects are the client's Router Cache (try router.refresh()) and then a CDN or edge cache sitting in front of the deployment entirely, which Next.js's own revalidation can't reach.
