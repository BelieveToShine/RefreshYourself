Generics — one method, any type, still type-safe

"Why do generics exist — what do they solve over object-based collections?"

Why it matters ▾
  • An object-based collection makes every read a cast — get the cast wrong and it's a runtime crash, not a compile error.
  • Any reusable method or class that should work across many types without copy-pasting one version per type needs this.
  • One of the first questions once an interview moves past syntax basics into "how do you write reusable code."
🔥 Easy interview recall

Generics = "one piece of code, many types, checked by the compiler — not you."

Think: List<T> → the same code works for int, string, Customer — no casts, no runtime surprises.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Generics aren't just about skipping casts. The bigger win for value types is avoiding boxing — an object-based collection boxes every int it stores, a List<int> never does.

🔄 Likely Follow-up

"What's a generic constraint, and why would you need one?" where T : ... restricts T to types with a specific capability — an interface, a base class, or new() — so the generic method can actually call members on T instead of only object's.

🎯 Say this in the interview — the exact lines to land

"Generics let one method or class work across many types with full compile-time type safety — no casting, and for value types, no boxing. The compiler checks the real type up front instead of throwing an InvalidCastException at runtime."

  • Type safety → the compiler enforces the type, not a runtime cast.
  • No boxing → a List<int> stores real ints, never boxed objects.
  • where T : IEntity → unlocks calling members on T that only that constraint guarantees.
📖 Explanation ▾

A generic method or class is written once against a placeholder type, T, and the compiler fills in the real type at each call site. List<int> and List<string> behave like two different classes, but they both come from the one List<T> definition — nothing was copy-pasted per type.

By default, T could be anything, so the compiler only lets the method call members every possible type shares — which is almost nothing. A constraint (where T : IEntity) narrows that promise: now the compiler knows every T has an Id, so calling item.Id is allowed to compile.

💻 See the code ▾
C# 
ArrayList list = new ArrayList();
list.Add(42);                 // boxes the int going in
int n = (int)list[0];      // ❌ needs a cast on every read

An object-based collection forces a cast on every read — and boxes every value type going in.

C# 
List<int> nums = new List<int>();
nums.Add(42);                  // ✅ stored as a real int, never boxed
int n = nums[0];             // ✅ no cast — already an int

List<int> is the generic equivalent — the compiler already knows the type.

C# 
T GetById<T>(int id) where T : IEntity
{
    T item = _repository.Find(id);
    return item.Id == id ? item : default;  // ✅ compiles — every T has .Id
}

where T : IEntity is what lets item.Id compile — remove it and the compiler rejects the call.

🌍 Real-world example ▾

You're writing a generic repository and it needs to call .Id on T. Without a constraint, the compiler only allows calls to members every possible type shares — which is basically nothing. Add where T : IEntity, and the compiler knows every T has an Id, so the call compiles.
