with doesn't just save a line — it guarantees __exit__ runs even if the block raises

"What does with actually guarantee, and how would you write your own context manager?"

Why it matters ▾
  • Tests whether you know with is a real guarantee — not just nicer syntax for closing a file.
  • Comes up any time cleanup matters: files, database connections, locks, network sockets.
  • Writing your own context manager (class-based or @contextmanager) is a common practical follow-up, not just theory.
🔥 Easy interview recall

with = "__exit__() ALWAYS runs — clean exit or exception."

Think: with is a try/finally you can't forget to write.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"My __exit__ ran, so I'm done." __exit__ also receives the exception's type, value, and traceback as arguments, and unless it returns a truthy value the exception still propagates after it finishes — returning True by accident silently swallows a real error.

🔄 Likely Follow-up

"contextlib.contextmanager vs. a class-based context manager — when would you pick each?" @contextmanager is fastest for a simple enter/exit pair — one generator function with a single yield; a class is better when you need more state, several methods, or a reusable, documented type used across many with sites.

🎯 Say this in the interview — the exact lines to land

"with calls __enter__() at the start and guarantees __exit__() runs when the block ends — whether it finished normally or raised — that's the whole point, not just fewer lines than try/finally. I'd write my own with a class defining __enter__/__exit__, or faster, with @contextlib.contextmanager on a generator with one yield: code before the yield is __enter__, code after is __exit__."

  • with → guarantees __exit__ runs — on success or exception, no manual try/finally needed.
  • @contextlib.contextmanager → fastest for a simple pair — one generator, one yield, wrapped in try/finally.
  • Class-based (__enter__/__exit__) → pick it for more state or reuse across many with sites.
  • __exit__ → receives exception info — return truthy only when you intend to suppress it.
📖 Explanation ▾

with expr as x: calls expr.__enter__() and binds its return value to x, then runs the block. When the block ends — normally or through an exception — Python calls expr.__exit__() before control leaves the with statement. That's the entire value over a hand-written try/finally: the same guarantee, just declarative and impossible to forget.

There are two ways to write your own: a class implementing __enter__ and __exit__, or the shortcut, @contextlib.contextmanager on a generator function with exactly one yield — everything before the yield runs as __enter__, everything after runs as __exit__, wrapped in try/finally so cleanup still runs if the block raises.

Common real examples all lean on the same guarantee: file handling closes the file automatically, a database connection commits on success and rolls back on an exception, and a lock releases even if the code inside the critical section raises.

💻 See the code ▾
Python 
class Locking:
    def __init__(self, lock):
        self.lock = lock

    def __enter__(self):
        self.lock.acquire()
        return self.lock          # bound to `as lock`

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.lock.release()       # always runs
        return False              # never suppress the exception

__exit__ always releases the lock — even if the block raised — and returning False lets a real exception keep propagating.

Python 
from contextlib import contextmanager

@contextmanager
def locking(lock):
    lock.acquire()          # __enter__ logic
    try:
        yield lock          # value bound to `as lock`
    finally:
        lock.release()      # __exit__ logic, always runs

Code before yield is __enter__; code after is __exit__ — the try/finally is what still runs it on an exception.

🌍 Real-world example ▾

A database transaction wrapped in with connection.transaction(): commits automatically when the block finishes cleanly, and rolls back automatically if the block raises — exactly the guarantee with provides: the rollback runs from inside __exit__ whether the code failed on line one or line ten, so a half-finished update never gets committed by accident.
