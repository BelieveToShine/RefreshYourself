More threads, less throughput — know what contention actually costs

"Your app adds more threads but throughput actually drops — what's going on?"

Why it matters ▾
🔒 Lock contention
❗ ProblemWhen many threads frequently compete for the same lock, each extra thread adds more waiting and context-switching rather than more real work — so throughput can go down as thread count goes up, the opposite of the usual "add threads to scale" instinct.
✅ SolutionShrink what the lock actually protects, split one lock into several independent locks for independent data, or move to a lock-free/concurrent-collection design — "add more threads" is never the fix for a contention-bound system.
RecallContention = threads paying more for the lock than they get from the work.
🔥 Easy interview recall

Contention = "past a point, threads spend more time waiting than working."

Think: one checkout counter and a growing line — adding more customers doesn't check anyone out faster, it just makes the line longer.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding more threads is not a universal fix for low throughput. Past the contention point, every additional thread adds more waiting and context-switching on the same lock instead of more completed work — the system can get slower, not faster.

🔄 Likely Follow-up

"How would you actually confirm the bottleneck is lock contention, not something else?" Lock/contention profiling (e.g. thread dumps showing many threads `BLOCKED` on the same monitor, or a profiler's lock-contention view) — see this track's JVM-profiling page for the full "profile first" approach.

🎯 Say this in the interview — the exact lines to land

"Contention is multiple threads frequently competing for the same lock — past a certain point, adding threads reduces throughput instead of increasing it, because threads spend more time waiting and context-switching than doing work. The fix is shrinking the lock's scope, splitting one lock into several independent locks, or moving to a lock-free/concurrent-collection design — never just adding more threads."

  • Contention → more waiting than working, past a certain thread count.
  • Reduce lock scope → protect only what truly needs it, not a whole method.
  • Split one lock into several → independent data gets independent locks.
  • Lock-free / concurrent collections → avoid the lock entirely for hot paths.
  • "Just add more threads" → never the fix for a contention-bound system.
📖 Explanation ▾

A lock (synchronized, a ReentrantLock) exists to protect shared mutable state, but it also serializes access to whatever it protects — only one thread can hold it at a time. With few threads, that serialization barely matters; as thread count grows, more threads arrive wanting the same lock at the same moment, and each one past the first has to wait. Waiting threads aren't idle for free either — they're often parked and later rescheduled, and that context-switching itself costs CPU time that produces no useful work.

Reducing the lock's scope is usually the cheapest fix: lock only the few statements that actually touch shared state instead of an entire method, so threads spend less time holding the lock and more time doing independent work outside it. Splitting one lock into several helps when the protected data is actually independent — two unrelated fields guarded by the same lock create contention between operations that never needed to block each other at all; giving each its own lock lets them run concurrently for real.

When contention is still too high after that, a lock-free or concurrent-collection design (CAS-based structures, ConcurrentHashMap's per-bin locking) removes the single shared lock as the bottleneck entirely — at the cost of real implementation complexity, which is why it's a step up from "just split the lock," not the first thing to reach for.

💻 See the code ▾
Java 
public synchronized void handleRequest(Request r) {
    validate(r);              // doesn't touch shared state
    this.counter++;        // the only line that actually needs the lock
    writeAuditLog(r);         // slow I/O — held the lock the whole time
}
// ❌ the lock is held for validate() + writeAuditLog() too — pure contention under load

Locking the entire method serializes work that never needed to be serialized — every thread queues behind the slow I/O call too.

Java 
public void handleRequest(Request r) {
    validate(r);                 // now runs lock-free, in parallel
    synchronized (this) { this.counter++; } // ✅ lock held for one line only
    writeAuditLog(r);            // slow I/O, also outside the lock now
}

Shrinking the lock to the single statement that needs it cuts how long every thread spends waiting, without changing what's actually protected.

Java 
private final Object ordersLock = new Object();
private final Object metricsLock = new Object();
// two independent fields, two independent locks — no false contention between them

void recordOrder() { synchronized (ordersLock) { orders.add(newOrder); } }
void recordMetric() { synchronized (metricsLock) { metrics.increment(); } }
// ✅ a thread calling recordOrder() never blocks a thread calling recordMetric()

One shared lock for both fields would make unrelated operations block each other for no real reason — splitting the lock removes that false contention.

🧭 Use Cases — recognize these when they happen to you ▾
1 Throughput drops after the team doubles the thread pool size

Past the contention point, more threads just means more threads queued on the same lock. A common interview trap: assuming "throughput problem" always means "not enough threads."

RememberMore threads on a saturated lock → lower throughput, not higher.
2 One method synchronizes on this for its entire body

Locking only the statement that touches shared state — moving slow I/O or validation outside the synchronized block — is usually the cheapest way to cut contention, with no design change needed.

RememberShrink the lock to what actually needs protecting.
3 Two unrelated fields share one lock

An orders list and a metrics counter guarded by the same lock block each other for no real reason — they're independent data. Giving each its own lock lets operations on one run concurrently with operations on the other.

RememberIndependent data → independent locks.
🌍 Real-world example ▾

A service's response times get worse after the on-call engineer bumps the thread pool from 50 to 200 "to handle more load." A thread dump shows most of those 200 threads sitting `BLOCKED` on the same monitor. The real fix isn't more threads — it's finding what that lock protects, shrinking its scope, or splitting it so independent work stops queuing behind unrelated work.
