LoRA / QLoRA — freeze the base model, train almost nothing

"What is LoRA, and why would you use it instead of fully fine-tuning a model?"

Why it matters ▾
  • Tests whether you understand the actual tradeoff behind fine-tuning, not just that "LoRA is a thing people use."
  • Comes up any time someone asks how to customize a model's style, tone, or task behavior for a product without the cost of a full retrain.
  • A natural follow-up right after a RAG-vs-fine-tuning discussion — interviewers often check whether you know fine-tuning itself has a cheap flavor before asking when to reach for it at all.
🔥 Easy interview recall

Full fine-tune → update every weight, one full copy per variant

LoRA → freeze the base, train a tiny adapter

QLoRA → LoRA on a quantized (compressed) base

Think: LoRA is a small patch bolted onto a frozen model, not a rewrite of it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

LoRA doesn't unfreeze "a few" of the original weights. Every single base weight stays completely frozen — the adapter is a brand-new, separate set of parameters added alongside the model, not a subset of the original weights being made trainable.

🔄 Likely Follow-up

"If LoRA already makes training cheap, why does QLoRA exist at all?" LoRA still needs the full base model loaded in memory for every forward and backward pass, even though only the adapter trains. QLoRA quantizes that base down to lower precision so the whole setup fits on far more modest hardware.

🎯 Say this in the interview — the exact lines to land

"Full fine-tuning updates every weight and needs a full copy of the model per variant — expensive, and rarely necessary in practice. LoRA freezes the base model entirely and trains only a small set of added low-rank matrices, producing a tiny adapter instead of a new model copy. QLoRA adds quantization on top, running that frozen base at lower precision so the whole setup fits on much more modest hardware."

  • Full fine-tune → rarely necessary — every weight updates, huge compute and memory, one full copy per variant.
  • LoRA → freeze the base, train a small adapter — cheap, and most of the practical benefit.
  • QLoRA → LoRA + a quantized base — reach for it when the base model itself barely fits in memory.
  • PEFT → the umbrella term for LoRA/QLoRA — adapt behavior by training a few new parameters, not the whole model.
  • Multiple adapters → swappable on top of the same frozen base for different tasks or clients.
📖 Explanation ▾

Full fine-tuning updates every weight in the model. That's extremely expensive in compute and memory, and it leaves you with a full separate copy of the model for every fine-tuned variant you want to keep around. LoRA (Low-Rank Adaptation) takes a different approach: it freezes the original model's weights completely and instead trains a small set of additional low-rank matrices that get added into the model's computation. Because there are far fewer trainable parameters, LoRA needs far less compute and memory to train, and what it produces is a small adapter file — not a whole new copy of the model.

QLoRA combines LoRA with quantization: it fine-tunes a LoRA adapter on top of a quantized, lower-precision version of the base model. That further shrinks the memory needed to hold the base model during training, which is what makes fine-tuning genuinely large models feasible on comparatively modest hardware. Both LoRA and QLoRA belong to a broader family called PEFT (Parameter-Efficient Fine-Tuning) — techniques that adapt a model's behavior by training a small number of additional parameters instead of the model's full parameter set.

Because of this efficiency, full fine-tuning is rarely necessary in practice. LoRA- and QLoRA-style adapters get most of the practical benefit — adapting a model's style, format, or task behavior — at a small fraction of the cost, and multiple adapters can even be swapped in and out on top of the same frozen base model for different use cases.

💻 See the code ▾
Python 
# LoRA — base model stays frozen, adapter is added on top
base_model = load_pretrained(model_name)
lora_config = LoraConfig(target_modules=["q_proj", "v_proj"])
model = get_peft_model(base_model, lora_config)  # base frozen, adapter trainable
train(model, dataset)  # only the adapter's params update

The base model's own weights never receive a gradient update — only the small adapter added by lora_config does.

Python 
# QLoRA — same adapter, but the frozen base is quantized first
base_model = load_pretrained(model_name, quantize=True)  # lower-precision base
model = get_peft_model(base_model, lora_config)  # same LoRA adapter as before
train(model, dataset)  # fits in far less memory

Only the base model's precision changes. The adapter being trained is the exact same idea as plain LoRA.

🌍 Real-world example ▾

A product needs a slightly different "voice" of the same model for five different clients, but can't afford five full copies of a large model sitting in memory. The fix: train five small LoRA adapters on top of one shared, frozen base model, and swap in the right adapter per request — one base model, five lightweight personalities.
