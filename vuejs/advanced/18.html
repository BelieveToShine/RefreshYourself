v-for state follows the wrong row — position-based keys vs. identity-based keys

"Users report that reordering or filtering a list causes inputs/focus to end up on the wrong row — how do you diagnose and fix it?"

Why it matters ▾
🔀 Reorder/Filter a v-for List
❗ ProblemReordering or filtering a v-for list causes input values, focus, or component-local state to appear attached to the wrong row — because the array index (or no key at all) was used as :key.
✅ SolutionUse a stable, unique identifier from the data itself (an id field) as :key — never the index — so Vue's diffing tracks each item's own DOM node across reorders, not just its slot.
RecallKey by identity (id), never by position (index).
🔥 Easy interview recall

:key="index" → tracks the slot, not the item

:key="item.id" → tracks the item, wherever it moves

Think: index-as-key is a locker number; id-as-key is the name tag on the thing inside it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just add any :key to make the warning go away." An unstable or index-based key technically satisfies the compiler/linter, but it doesn't fix the actual tracking problem — Vue still matches old DOM nodes to new positions instead of to the real data.

🔄 Likely Follow-up

"What if the data genuinely has no unique id field?" Generate and attach a stable synthetic id when the data first enters your app's state (e.g. on fetch) — never invent a key at render time, since that regenerates a "new" key every render and defeats the whole point.

🎯 Say this in the interview — the exact lines to land

"Index-based (or missing) keys make Vue track a DOM node by its position in the list, not by the item it represents — reordering or filtering then shows the old node's state attached to the wrong data. The fix is a stable, unique id from the data itself as :key, so each node moves with its own item."

  • :key="index" → tracks the slot, not the item.
  • :key="item.id" → tracks the item, wherever it moves.
  • No real id field → attach a synthetic id when data enters state, not at render time.
  • Symptom to recognize → input values/focus landing on the wrong row after a reorder or filter.
📖 Explanation ▾

Vue's v-for diffing uses :key to decide whether an existing DOM node can be reused for an item, or whether a new node needs to be created. Without a key — or with the array index used as one — Vue has nothing but position to match on: slot 0 before the reorder is treated as "the same thing" as slot 0 after it, even though a completely different item now occupies that slot.

That mismatch is invisible until a row carries its own local state — a text input's typed value, scroll position, or focus — because Vue reuses the existing DOM node (and whatever the browser is holding in it) for the new item sitting in that slot, instead of recreating it. The result looks exactly like the bug report: "my input values swapped rows."

A stable id-based key fixes this because the key now identifies the item, not the slot. When the data reorders, Vue sees the same key still present and moves that item's actual DOM node to its new position — carrying its real state along with it — instead of reusing whatever node happened to be sitting in that slot before.

💻 See the code ▾
Vue 
<li v-for="(item, index) in items" :key="index">  // ❌ tracks the slot, not the item
  <input v-model="item.value" />
</li>

Reorder items and each row's typed input value stays in its old slot — attached to whatever item now sits there.

Vue 
<li v-for="item in items" :key="item.id">  // ✅ tracks the actual item
  <input v-model="item.value" />
</li>

Reorder items and each input's DOM node moves with its own item — the typed value travels along with it.

🧭 Use Cases — recognize these when they happen to you ▾
1 A sortable table has per-row inputs, and sorting swaps which row holds which typed value

Sorting reorders the array but the index-based keys don't move — each row's typed value stays pinned to its old slot number. This is the #1 scenario you'll actually run into.

RememberSortable table + index key → inputs land on the wrong row after a sort.
2 A search box filters a list, and the wrong item appears to be expanded/selected afterward

Removing an item from the middle of a filtered list shifts every later item up a slot — with index keys, local component state (like "expanded") stays attached to the slot number, not the item that was actually expanded.

RememberFiltering shifts slots — local per-row state needs id-based tracking to follow correctly.
3 The data genuinely has no unique id field to key on

Attach a stable synthetic id once, when the data first enters your app's state (right after a fetch) — not at render time, where generating an id on every render just creates a new "unique" key every time and defeats the purpose entirely.

RememberGenerate the id on arrival, never during render.
🌍 Real-world example ▾

A to-do app lets users mark items done, which moves completed items to the bottom of the list. With index-based keys, the checkbox state visibly jumps to a different task the moment the list reorders. Switching to :key="todo.id" fixes it immediately — each checkbox now belongs to its own task, wherever that task ends up in the list.
