Composite Index — order is the whole point

"What is a composite index, and does column order in it matter?"

Why it matters ▾
🗂️ Composite Index
❗ ProblemA multi-column index looks like it should speed up a search on any column it contains, but a search that only filters on a later column can't jump anywhere — the engine falls back to scanning the whole index instead.
✅ SolutionA composite index is sorted by its leading column first, then by the next column within each matching group — so only a search that includes that leading column can seek straight to the right spot.
RecallComposite index = one index, several columns, efficiently searchable only starting from the leading column.
🔥 Easy interview recall

Composite index = "one index, several columns — but only the leading column is efficiently searchable alone."

Think: index on (A, B) → helps A, or A + B. Doesn't help B alone.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Column order in a composite index doesn't matter as long as all the right columns are in it somewhere." It matters a lot — the index is only efficiently searchable from its leading (leftmost) column inward, so skipping the first column defeats the index for that search, the same way you can't efficiently look someone up in a last-name-sorted phone book by first name alone.

🔄 Likely Follow-up

"If you have an index on (A, B), does it help a query filtering only on B?" No, not efficiently — without A in the filter, the engine generally can't jump straight to the right spot in that index; it falls back to scanning through it (or the table) instead.

🎯 Say this in the interview — the exact lines to land

"A composite index is one index built across more than one column, and column order decides how it can actually be searched — it's efficiently searchable starting from its leftmost column inward. An index on (LastName, FirstName) speeds up a search on LastName alone, or on LastName plus FirstName together, but not a search on FirstName by itself."

  • (LastName, FirstName) → helps LastName, or LastName + FirstName — the leading column, alone or combined.
  • FirstName alone → not efficiently helped — it isn't the leading column here.
  • Column order → decides what the index actually speeds up, not just which columns are present.
  • Same idea as a phone book sorted by last name first.
📖 Explanation ▾

A composite index is a single index built on more than one column together, stored sorted by the first column, then by the second column within each group of matching first- column values, and so on. That physical sort order is exactly why the leading (leftmost) column is special — it's the only column the engine can use to jump straight to the right spot, the same way a sorted list can only be searched quickly on the value it's actually sorted by.

A search that includes the leading column can seek directly into the matching group. A search that only filters on a later column — FirstName without LastName — can't do that seek, because rows with that first name are scattered across every last-name group instead of sitting together. The engine falls back to scanning, which is exactly what the index exists to avoid.

💻 See the code ▾
SQL 
CREATE INDEX IX_Employees_LastFirst
    ON Employees(LastName, FirstName);   -- LastName is the leading column

SELECT * FROM Employees
WHERE LastName = 'Smith';                  -- ✅ helped — starts from the leading column

SELECT * FROM Employees
WHERE FirstName = 'John';                 -- ❌ not helped efficiently — FirstName isn't leading

Same index, same table — only the column being filtered on changes whether it's actually used efficiently.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your query filters on the leading column alone

LastName is the leading column, so the index can jump straight to the matching group instead of scanning past every other name. This is the #1 case the index was built for.

RememberLeading column alone → still a direct seek.
2 Your query filters on the leading column plus the next one

The leading column is still there, so the index seeks straight to the Smith group first — then FirstName narrows that already-small group down further. Still efficient, because the search never dropped the leading column.

RememberLeading + next column together → still helped.
3 Your query filters only on a later column, skipping the leading one

FirstName isn't the leading column, so rows named "John" are scattered across every LastName group instead of sitting together — the engine can't seek and falls back to scanning. A great interview trap — candidates often assume any column inside a composite index gets helped on its own.

RememberSkip the leading column → scan, not seek.
🌍 Real-world example ▾

A phone book sorted by last name first. Finding everyone named "Smith" is instant — flip straight to the S section. Finding everyone whose first name is "John" means reading through the entire book, because it was never sorted that way.
