Multiple createApp() instances — same page, zero shared state

"Can you mount more than one independent Vue app on the same page, and do they share state?"

Why it matters ▾
🧰 App-level API
❗ ProblemNot every page is a full Vue SPA — sometimes only a widget or two on an otherwise server-rendered page needs to be interactive, and a convenience value (like an HTTP client) shouldn't have to be imported into every single component that needs it.
✅ SolutionMultiple independent createApp() instances can coexist on one page, each with its own plugins and config; app.config.globalProperties adds a value every component in that app's tree can read without an import.
RecallEach createApp() is its own island — nothing links two instances automatically.
🔥 Easy interview recall

Two createApp() calls = "two fully independent apps that happen to share one page."

Think: each instance is its own island — its own plugins, its own config, its own state, with no bridge unless you build one yourself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

app.config.globalProperties is not a safe dumping ground for convenience helpers. Overusing it reintroduces the same implicit, hard-to-trace problem Vue 2's mixins had — an explicit import or a composable is almost always clearer.

🔄 Likely Follow-up

"Do two separate app instances on one page share any state automatically?" No — each createApp() call is fully independent; any sharing between them has to be built explicitly (a shared module-level store, browser storage, or custom events).

🎯 Say this in the interview — the exact lines to land

"Multiple createApp() instances can coexist on one page, each fully independent — its own plugins, config, and component tree. app.config.globalProperties adds a property every component in that one app's template can read without importing it, used sparingly for something like a global HTTP client. Two separate instances share nothing automatically."

  • Multiple createApp() calls → fully independent apps, same page.
  • globalProperties → no-import access within one app's tree — use sparingly.
  • Cross-instance state → never automatic — build it explicitly if needed.
  • Good use case → hydrating one widget on an otherwise non-Vue page.
📖 Explanation ▾

Each call to createApp() returns a brand-new app instance with its own plugin registrations, its own config, and its own mounted component tree. Nothing about calling it twice implies any relationship between the two results — they just happen to render into different elements of the same page.

app.config.globalProperties attaches a value onto that one app's internal component instance prototype, so every component mounted under it can reference it directly in a template with no import — handy for something genuinely global to that app, like a shared HTTP client, but easy to overuse into an untraceable grab-bag the same way Vue 2 mixins became.

The practical reason to mount more than one app on a page: a mostly server-rendered or legacy page that only needs one or two small interactive widgets doesn't need a full SPA — each widget can be its own tiny, independently mounted Vue app.

💻 See the code ▾
Vue 
<!-- one page, two unrelated interactive widgets -->
<div id="app1"></div>
<div id="app2"></div>

createApp(CartWidget).mount('#app1')     // instance 1
createApp(NewsletterForm).mount('#app2') // ✅ fully independent instance 2

Neither app knows the other exists — each has its own component tree and its own config.

Vue 
const app = createApp(App)
app.config.globalProperties.$http = httpClient  // available everywhere in THIS app

<!-- inside any component mounted under this app -->
<!-- this.$http.get('/api/data') — no import needed -->

Reach for this sparingly — an explicit import or a composable is usually clearer than a property nobody can trace back to its source.

🧭 Use Cases — recognize these when they happen to you ▾
1 A mostly server-rendered page needs one interactive widget

No need to rebuild the whole page as a SPA — mount one small createApp() instance just onto the one element that needs interactivity.

RememberOnly part of the page needs Vue → mount just that part.
2 Several unrelated helpers get dumped onto globalProperties

A component using this.$util.whatever() gives no clue where that came from. A common interview trap: treating globalProperties as a free convenience layer instead of recognizing it reintroduces exactly the traceability problem mixins had.

RememberConvenience helpers → an explicit import or composable, not globalProperties.
3 The same widget is embedded multiple times on one page

A "rating widget" that appears three times on one page gets three separate createApp() calls, one per mount point — each with its own isolated state, which is usually exactly what's wanted.

RememberRepeated widget → repeated independent instance, by default.
🌍 Real-world example ▾

A marketing site built in a traditional CMS with a few interactive islands. A newsletter signup form and a product configurator are each their own small createApp() instance, mounted into different parts of the server-rendered page — no SPA rewrite needed, and the two widgets never need to know about each other.
