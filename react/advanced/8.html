Structuring a React app — where a decision lives, not just where a file lives

"How would you structure a large React application, and how do you avoid a 'god component'?"

Why it matters ▾
📁 Layer-based
❗ ProblemA growing codebase needs some agreed rule for where a file goes — without one, similar files end up scattered with no predictable home.
✅ SolutionLayer-based structure groups every file by what type it is — every component in one components/ folder, every hook in hooks/, every API call in services/.
RecallLayer-based = grouped by type (component / hook / service).
📁 Feature-based
❗ ProblemUnder layer-based structure, working on one feature means jumping across every type folder, and adding a brand-new feature touches all of them too — it gets worse the more teams share those same folders.
✅ SolutionFeature-based structure groups by domain instead — each feature (users/, orders/) holds its own components, hooks, and API calls together in one self-contained folder.
RecallFeature-based = grouped by domain, each feature self-contained.
🔥 Easy interview recall

Splitting a god component into more files doesn't fix it — separating the actual tangled responsibilities does.

Think: Many small, still-tangled files are still a god component — just spread out.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Small components don't guarantee good structure. A codebase can have many small components that are still tightly coupled, with business logic, API calls, and UI all tangled together across them — the real fix is separating those concerns regardless of file size, or a god-component problem just becomes a god-folder problem spread across more files.

🔄 Likely Follow-up

"Feature-based vs. layer-based folder structure — what's the actual trade-off?" Layer-based (group by type) scales poorly as an app grows, because working on one feature means jumping across many separate folders; feature-based (group by domain, each feature self-contained) keeps related code together and scales better, especially for multiple teams working on different features at once.

🎯 Say this in the interview — the exact lines to land

"I'd structure by feature, not by type — each feature folder holds its own components, hooks, and API calls, with business logic pulled out into custom Hooks or plain functions so the UI stays thin. Splitting a god component into more files only helps if the underlying responsibilities are actually separated, not just spread across smaller files."

  • Layer-based (by type) → scatters one feature across every folder, harder to scale.
  • Feature-based (by domain) → keeps one feature self-contained, scales better across teams.
  • UI vs. business logic → pulled apart via custom Hooks or plain functions, not tangled together in one component.
  • API and validation logic → each lives in one predictable place, never duplicated per component.
  • Component boundaries → decided by responsibility and reuse, never by file size alone.
  • Circular dependencies → avoided with a one-directional dependency flow — shared code at the bottom, features depend on it, never the reverse.
📖 Explanation ▾

Layer-based structure groups files by what TYPE they are — every component in one components/ folder, every hook in one hooks/ folder, every API call in one services/ folder. That mixes many unrelated features inside each folder, so working on a single feature means jumping across all of them. Feature-based structure groups files by DOMAIN instead — a users/ folder and an orders/ folder, each holding its own components, hooks, and API code — which keeps related code together and scales better once several teams are working on different features at the same time.

Layer-basedFeature-based
Groups bytype (component, hook, service)domain (users, orders)
Working on one featuretouches many separate foldersstays inside one folder
Scaling across teamsgets harder as the app growseach team owns its own folder
Adding a new featuretouches every top-level folderadds one new self-contained folder

Folder shape alone doesn't separate concerns. The UI should stay focused on rendering, while validation rules, calculations, and API orchestration live behind a custom Hook or a plain function the component simply calls — and that API logic and validation logic should each live in one clear, predictable place, not duplicated across every component that reaches out on its own.

A god component — one component fetching, transforming, validating, and rendering everything itself — doesn't get fixed just by splitting it into more, smaller files if the underlying responsibilities never actually get separated; that just spreads the same tangle across more files. Component boundaries should come from responsibility and reuse, not an arbitrary size cutoff. The same discipline applies to dependencies between modules: keep them flowing one direction only — shared/common code sits at the bottom depending on nothing, feature-specific code depends on it, never the reverse — which is what keeps two modules from ever importing each other (a circular dependency).

💻 See the code ▾
JSX 
// feature-based — everything for "orders" lives together
// src/
//   features/
//     orders/
//       components/   // OrderList, OrderRow
//       hooks/         // useOrders, useOrderValidation
//       api/           // ordersApi.js
//     users/
//       components/
//       hooks/
//       api/
//   shared/            // depends on nothing — features depend on it, never the reverse

Everything orders needs — its components, its hooks, its API calls — sits under one folder, instead of being spread across shared components/, hooks/, and services/ folders.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app has grown past a couple of features and you have to pick a folder structure

This is the #1 scenario you'll actually run into: layer-based structure (group by type) is the easy default, but it scatters every feature across components/, hooks/, and services/. Regrouping by domain instead means each feature's components, hooks, and API calls live together in one folder, which stays easier to work in as more features (and teams) are added.

RememberMore features and teams → feature-based scales better than layer-based.
2 One component is fetching, validating, and rendering everything itself

This is a god component — splitting it into more, smaller files won't fix it if the same fetching, validating, and rendering responsibilities stay tangled together across those files. The fix is pulling the business logic out into a custom Hook (or a plain function), so the component itself stays thin and focused on rendering.

RememberMore files ≠ fixed — separating responsibilities is what fixes a god component.
3 Two feature folders start importing from each other

Two modules importing from each other is a circular dependency. Keeping dependencies flowing one direction only — shared/common code at the bottom depending on nothing, feature-specific code depending on it, never the reverse — is what keeps that from happening in the first place.

RememberDependencies flow one direction only — shared code never depends on a feature.
🌍 Real-world example ▾

Organizing a toolbox by TYPE means every screwdriver lives together, every wrench lives together, no matter which project each one belongs to. Organizing it by PROJECT means everything for "build the shed" sits together in one bin. The project-based bin is far faster to work from once several projects are going at once — the same reason feature-based folders are faster to work in once an app has multiple active feature areas.
