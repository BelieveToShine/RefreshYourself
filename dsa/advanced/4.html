A stream too big to store — bounded memory vs. the whole dataset

"How would you find the top-K items, take a random sample, or check for duplicates in a data stream that's too large to fit in memory, or that never actually ends?"

Why it matters ▾
  • Senior/architect interviewers use this exact scenario to check whether "just load it all into memory and process it normally" is even a valid instinct once the data is this size.
  • Comes up for real: log pipelines, click-stream analytics, and dedup jobs over datasets that dwarf any single machine's RAM.
  • A common opener before a harder follow-up on the running-median problem, or on approximate-counting techniques for a truly unbounded stream.
🔥 Easy interview recall

Top-K → bounded heap of size k

Reservoir sampling → keeps k, odds shrink over time

Bloom filter → tunable false positive rate

Think: Top-K → keeps the best k, forgets the rest Reservoir → keeps k items, never sees the "whole" stream Bloom filter → keeps bits, not items — trades certainty for size

🧠 Visual Mental Model — understand it in 5 seconds

Worked example: a Bloom filter's actual bits. The same "bounded memory, give something up" trade shows up in Top-K and reservoir sampling too — see 🎯 and 📖 below.

⚠️ Common Trap

"I'd just load it all into memory and sort/scan it normally." That instinct is the wrong first move here — the whole point of a streaming/large-dataset question is that the data is either unbounded or too big for that, and the interviewer is checking whether you reach for a bounded-memory, single-pass technique instead.

🔄 Likely Follow-up

"How would you find the median of a very large stream, without storing it all?" Harder than top-K — a median needs the relative rank of everything, not just the best few, so there's no clean exact O(k)-memory answer the way top-K has. If you're willing to hold the running stream, two heaps (a max-heap for the lower half, a min-heap for the upper half) give an exact running median; for a genuinely memory-bounded unbounded stream, only approximation techniques exist.

🎯 Say this in the interview — the exact lines to land

"Whenever a dataset is too big to hold, or a stream never really ends, I reach for a technique that answers one specific, narrower question using bounded memory — a fixed-size heap for top-K, reservoir sampling for a uniform random sample, or a Bloom filter for approximate membership — instead of assuming I can load everything and process it the normal way."

  • Need the top/bottom k at scale → bounded min/max-heap of size k, the same trick as k-th largest in a stream, just at millions or billions of records.
  • Need a random sample without knowing the stream's length → reservoir sampling — keep k, replace item i with probability k/i.
  • Need "have I seen this before?" without a full hash set → Bloom filter — no false negatives, a tunable rate of false positives.
  • Asked for the exact median of a giant stream → flag it as the harder case; two heaps give an exact running median if you hold the stream, otherwise it needs an approximation technique.
  • The trap to avoid → never assume you can just load it all into memory first.
📖 Explanation ▾

A stream is data that keeps arriving — sometimes it never truly ends, and sometimes it's just plain too big to fit in whatever memory you actually have, even though it's technically finite. Either way, the usual move — load everything into an array, then sort or scan it like normal — isn't available. Every technique below exists to answer one useful, narrower question about that data using a small, fixed amount of memory instead.

The trade is always the same shape: give something up in exchange for bounded memory. A bounded top-K heap only ever tracks the current best k, and forgets everything it already beat — this is exactly the k-th-largest-in-a-stream trick from Heaps / Priority Queues, just recognized at genuinely massive scale. Reservoir sampling never holds more than k items at once, and never needs to know the stream's total length in advance. A Bloom filter gives up perfect accuracy — it can occasionally say "maybe seen" about something it never actually saw, because two different items' hashes can land on the same bits, but it can never wrongly say "definitely not seen."

Recognizing which of these narrower questions is actually being asked is the real skill being tested. Some questions — the exact median of an unbounded stream, or the exact count of distinct items seen — don't have a clean exact answer in O(1) or O(k) memory at all; they need an approximate-counting or approximate-median technique that's beyond this page's scope, but worth naming if an interviewer pushes that far.

💻 See the code ▾
C# 
PriorityQueue<int, int> heap = new(); // min-heap: root = worst of the top k
const int k = 100;

foreach (var value in hugeStream)
{
    if (heap.Count < k)
    {
        heap.Enqueue(value, value);         // still filling the k slots
    }
    else if (value > heap.Peek())      // beats the current worst of the k
    {
        heap.Dequeue();                     // ✅ drop the smallest of the k
        heap.Enqueue(value, value);
    }
    // else: discard — never touches memory beyond the heap
}

The heap never grows past k — the same trick as k-th largest in a stream (see Heaps / Priority Queues), just applied at millions or billions of records.

C# 
T[] reservoir = new T[k];
int i = 0;

foreach (var item in stream)
{
    i++;
    if (i <= k)
    {
        reservoir[i - 1] = item;      // fill the reservoir first
    }
    else
    {
        int j = random.Next(1, i + 1);  // 1..i inclusive
        if (j <= k)
            reservoir[j - 1] = item;  // ✅ replace with probability k/i
    }
}

No total stream length needed up front — by the time the stream ends, every item that ever appeared has had an equal chance of surviving into the reservoir.

C# 
bool[] bits = new bool[size]; // small, fixed-size bit array

void Add(string item)
{
    bits[Hash1(item) % size] = true;
    bits[Hash2(item) % size] = true;
}

bool MightContain(string item)
{
    return bits[Hash1(item) % size] &&  // ❌ any 0 here → definitely not seen
           bits[Hash2(item) % size];       // ✅ both 1 → *might* have been seen
}

MightContain can only ever say "definitely no" or "maybe yes" — never "definitely yes," because a bit could always have been set by a different item's hash.

🌍 Real-world example ▾

Your service ingests a click-stream of billions of events a day and needs to flag repeat visitors within the last hour. Keeping a full hash set of every visitor ID would blow through memory long before the day ends. A Bloom filter sized for the expected traffic answers "have I seen this before?" using a small, fixed bit array instead — accepting a tunable rate of false positives in exchange for the memory a real set would need.
