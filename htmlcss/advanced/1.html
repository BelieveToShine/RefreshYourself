From HTML/CSS to pixels — how many of the five pipeline stages does one change actually trigger?

"Walk me through what happens inside the browser between parsing your HTML/CSS and pixels actually showing up on screen — DOM, CSSOM, render tree, layout, paint, and compositing?"

Why it matters ▾
  • Every other page in this track that touches performance points here instead of re-explaining it — HTML Fundamentals, CSS Fundamentals & Cascade, the Box Model, Display & Visibility, and Transitions & Animations all lean on this exact pipeline rather than repeating it.
  • The near-guaranteed follow-up once someone says "the page feels janky" — the real answer is almost always which pipeline stage a change forces, not a code-style opinion.
  • CSS Performance, right after this page, assumes this five-stage picture as a given and builds the deeper optimization advice on top of it.
🔥 Easy interview recall

Browser Rendering = "one fixed pipeline: DOM + CSSOM merge into a Render Tree, then Layout sizes it, Paint colors it, Composite assembles the final frame."

Think: HTML → DOM, CSS → CSSOM, both → Render Tree → Layout → Paint → Composite → screen.

🧠 Visual Mental Model — understand it in 5 seconds

Not every change re-runs all three of those last stages — here's what one property change actually costs:

⚠️ Common Trap

The render tree isn't just "the DOM with styles attached." An element with display: none (and everything inside it) is left out of the render tree entirely, while ::before/::after generated content, which never had its own DOM node at all, still gets a render tree node.

🔄 Likely Follow-up

"So do visibility: hidden or opacity: 0 get left out of the render tree too?" No — both stay in the render tree and still run Layout, since the element still takes up space. They only change what happens after that: visibility: hidden paints nothing, and opacity: 0 still paints but ends up fully transparent once composited.

🎯 Say this in the interview — the exact lines to land

"The browser builds two trees — the DOM from HTML and the CSSOM from CSS — and merges only the visible parts into a Render Tree. From there, Layout computes exact size and position, Paint fills in pixels, and Composite assembles the final frame. Changing a layout-affecting property like width or position forces Layout, Paint, and Composite to all run again; changing a purely visual property like background-color skips Layout but still repaints; changing transform or opacity can often skip Layout AND Paint and go straight to Composite."

  • DOM + CSSOM → merged into the Render Tree — only nodes that will actually show.
  • display: none → excluded from the Render Tree entirely; ::before/::after get their own node despite never being in the DOM.
  • width / position / margin → forces Layout, then Paint, then Composite — the expensive path.
  • background-color / box-shadow → skips Layout, still repaints — medium cost.
  • transform / opacity → can skip Layout AND Paint — straight to Composite, the cheapest to animate.
📖 Explanation ▾

Two trees get built before a single pixel shows up. The DOM comes from the browser parsing your HTML — a tree of every element, covered in full on HTML Fundamentals. The CSSOM comes from parsing your CSS the same way — a tree of every matched rule, covered on CSS Fundamentals & Cascade. Neither tree by itself says anything about what actually appears on screen — that's what the next four stages figure out.

The Render Tree merges the two: it walks the DOM and attaches each node's final computed style from the CSSOM, but it only keeps what will actually be visible — an element with display: none (and its whole subtree) is left out completely, while generated content from ::before/::after, which never existed as a DOM node, still gets a render tree node of its own. Layout (also called reflow) then walks that tree and works out the exact size and position of every remaining node — the box-model math from Box Model, applied to the whole page at once. Paint fills in the actual pixels for each node — color, text, borders, shadows, images — generally onto its own layer rather than one flat canvas. Composite is the last step: it takes those painted layers and combines them in the correct order, applying any transforms, to produce the frame that actually reaches the screen.

Not every change re-runs all of that. A property that affects size or position — width, margin, position — forces Layout to run again, which then forces Paint and Composite too, since the geometry genuinely changed. A purely visual property — background-color, box-shadow — doesn't move anything, so it skips Layout but still has to repaint and recomposite. transform and opacity can often skip Layout AND Paint entirely and go straight to Composite, which is exactly why Transitions & Animations calls them the cheap properties to animate. Inefficient or deeply-nested CSS selectors add their own separate cost on top of all this — more matching work for the browser on every element it checks — covered in full on CSS Performance.

💻 See the code ▾
CSS 
.box.expanded { width: 320px; }             /* ❌ Layout → Paint → Composite */
.box.active   { background-color: #dbeafe; }  /* ⚠️ skips Layout, still Paint → Composite */
.box.moved    { transform: translateX(40px); } /* ✅ can skip straight to Composite */

Same kind of class toggle, three very different costs — the property being changed decides how much of the pipeline has to run again.

CSS 
/* ❌ browser checks every <a>, then walks up checking ancestors */
nav ul li a { color: #1d4ed8; }

/* ✅ same result, far less matching work */
.nav-link { color: #1d4ed8; }

A deep descendant selector makes the browser check more ancestors for every candidate element — a flatter class selector matches the same elements with less work.

CSS 
.hidden-a { display: none; }      /* ❌ removed from the Render Tree — no Layout, no Paint */
.hidden-b { visibility: hidden; }  /* ✅ still in the Render Tree — still runs Layout */

Both are invisible, but only display: none actually removes the element from the Render Tree — visibility: hidden still takes up space and still runs Layout.

🌍 Real-world example ▾

A dashboard widget slides itself into view by updating left inside a scroll handler, and it drops frames on anything but a high-end laptop. That's forcing Layout and Paint on every single scroll tick. Switching the same slide to transform: translateX() keeps the exact same visual move but lets most frames skip straight to Composite.
