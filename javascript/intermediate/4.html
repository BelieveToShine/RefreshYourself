import vs. require — why one can be analyzed before it even runs

"What's the difference between ES modules and CommonJS, and why does that difference matter for something like tree-shaking?"

Why it matters ▾
  • Almost every real codebase still mixes both systems — Node scripts and older packages in CommonJS, everything newer in ES modules — so knowing why they behave differently avoids real bugs, not just trivia.
  • Bundler features people rely on daily (tree-shaking, code-splitting) only work because of a specific property of ES modules — being able to explain *why* separates "used the tool" from "understands the tool."
  • Circular dependencies are a genuine, occasionally-surprising production bug source, and a common interview probe right after the basic import/export syntax.
🔥 Easy interview recall

CommonJS → runs to figure out what's exported

ES Modules → reads the imports/exports without running anything

Think: CommonJS's require() is a function call happening live; ES modules' import/export are a fixed, static shape a tool can see ahead of time.

🧠 Visual Mental Model — each module's own private room, plus how the two systems get read differently
⚠️ Common Trap

A circular import does not throw an error by itself. One of the two modules simply finishes importing before the other has finished running, so it gets a partially-initialized version of that module — usually showing up as "works fine" for one value and undefined for another, depending on import order.

🔄 Likely Follow-up

"Why can a bundler tree-shake ES modules but not CommonJS?" ES module imports/exports are a fixed, static shape the bundler can read straight from the source text without executing it; require() is a real function call that can happen conditionally or with a computed path, so the bundler would have to actually run the code to know what's used — it can't safely assume, so it keeps everything.

🎯 Say this in the interview — the exact lines to land

"ES modules use static import/export that a tool can analyze without running any code, support export default alongside named exports, and can load asynchronously — including on demand with dynamic import(). CommonJS's require/module.exports is Node's older system: synchronous, and resolved by actually running the required file, which is why bundlers can tree-shake ES modules but not CommonJS."

  • Named vs. default export — named exports import by exact name in braces; default export is one per module, imported under any name.
  • Module scope → nothing leaks to global by default, unlike a plain <script> tag.
  • import() → dynamic, returns a promise — load a module on demand instead of upfront.
  • CommonJS → sync, runs the file to resolve exports; ES modules → can be async, resolved statically.
  • Circular imports → one side gets a partially-initialized module, not an error.
📖 Explanation ▾

An ES module is any file using import/export. export a value by name (export const add = ...) to import it back with the exact same name in braces (import { add } from './math.js'), or mark one value as the module's default export (export default fmt) to import it under any name with no braces (import fmt from './format.js'). Every module also gets its own top-level scope — a variable declared at the top of one file simply doesn't exist in another, unlike two plain <script> tags sharing one global scope.

Dynamic import() is a function call, not a static keyword — it returns a promise and can sit inside an if or run only on a button click, which is how code-splitting loads a heavy module only once it's actually needed. CommonJS is Node's original system: require('./math') actually runs math.js synchronously, right then, and hands back whatever module.exports was set to. Because that's a real function call, it can be conditional or use a computed path — flexible, but it means a tool can't know what a file exports without running it. ES modules trade that flexibility for a fixed, static shape: import/export are read straight from the source text, before anything runs, which is exactly what lets a bundler statically trace which exports are actually used and drop the rest — tree-shaking. CommonJS's dynamic require makes that same analysis far harder, since the bundler would have to actually execute code to be sure.

A circular dependency (A imports B, B imports A) doesn't crash by itself. Whichever module finishes its import first receives whatever the other module had exported up to that point — often an incomplete or partially-initialized version — because the second module hasn't finished running yet. It's a real, occasionally-surprising bug: a value that's undefined only depending on which file happened to import first.

💻 See the code ▾
JavaScript 
// math.js
export const add = (a, b) => a + b;    // ✅ named export
export default function summarize() { return "done"; } // one default per module

// app.js
import summarize, { add } from './math.js';  // default + named together

Named exports must match their exact name in braces; a default export is imported under any name you choose, no braces needed.

JavaScript 
button.addEventListener('click', async () => {
  const { openModal } = await import('./modal.js'); // ✅ loaded only on click
  openModal();
});

Dynamic import() returns a promise and can run inside a conditional — the module isn't fetched at all until this line executes.

JavaScript 
// CommonJS — math.js
const add = (a, b) => a + b;
module.exports = { add };            // exports resolved by actually running this file

// CommonJS — app.js
const { add } = require('./math');   // synchronous — blocks until math.js finishes

require() is a normal function call — it can be wrapped in an if or given a computed path, which is exactly what makes its exports hard to analyze statically.

🌍 Real-world example ▾

Your production bundle only ships the three lodash functions you actually import, not the whole library — that's tree-shaking, and it only works because your ES module imports are a static shape the bundler can trace without running your code. Swap that same library for a CommonJS require-based one and the bundler often can't safely drop anything, because it can't prove which properties of module.exports are actually used.
