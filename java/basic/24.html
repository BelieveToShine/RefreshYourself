record — one line, a whole immutable data class

"What does declaring a record actually generate for you, and what's the mutable-component pitfall?"

Why it matters ▾
📦 record
❗ ProblemA hand-written immutable data class needs a constructor, private final fields, accessors, and a correct equals()/hashCode()/toString() — 30-40 lines of boilerplate that's easy to get subtly wrong, like a field forgotten in equals().
✅ Solutionrecord (finalized in Java 16, JEP 395) generates all of that from one declaration — the canonical constructor, private final fields, accessors named like the component, and equals()/hashCode()/toString() based on every component.
Recallrecord = one line, the whole immutable data class, generated for you.
🔥 Easy interview recall

record = "one line that writes the whole immutable data class for you."

Think: record Point(int x, int y) {} is a complete, correct equals()/hashCode()/toString() — with none of the thirty lines it would normally take.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A record's generated equals() isn't automatically deep. It just calls each component's own equals() — an array component never compares by content even inside a record, and a mutable List component still needs a defensive copy in a custom constructor to be truly immutable.

🔄 Likely Follow-up

"So is a record always immutable?" Its own fields can never be reassigned, but if a component is itself a mutable object — an array, a mutable List — the record is only shallowly immutable unless you defensively copy that component yourself.

🎯 Say this in the interview — the exact lines to land

"record (finalized in Java 16) is compact syntax for an immutable data-carrier — declaring the components generates the canonical constructor, private final fields, accessors named like the component (not getX()), and equals()/hashCode()/toString() based on every component, all in one line."

  • One declaration → constructor, fields, accessors, equals/hashCode, toString.
  • Accessors → named like the component, e.g. x(), not getX().
  • Mutable component (array/List) → still needs a defensive copy for true immutability.
📖 Explanation ▾

A record declares its components once, in the header, and the compiler generates everything else: a canonical constructor that assigns each component to a private final field, an accessor per component named after it (x(), not getX()), and equals()/hashCode()/toString() built from every component.

The catch is that equals() is generated from the components' own equality — it doesn't recursively deep-copy or deep-compare anything on its own. If a component is a mutable reference type, the record only guarantees the reference can't be reassigned, not that the thing it points to can never change.

💻 See the code ▾
☕ Java 
public record Point(int x, int y) {}

Point p = new Point(3, 4);
p.x();                              // 3 — accessor named like the component
p.equals(new Point(3, 4));    // true — based on every component

One line generates the constructor, the fields, the accessors, and equals()/hashCode()/toString().

☕ Java 
public record Team(List<String> members) {}

Team t = new Team(new ArrayList<>(List.of("Ann")));
t.members().add("Bob");     // 🐛 no defensive copy — mutates the "immutable" record

record didn't write a defensive copy for you — add one yourself in a custom constructor whenever a component is mutable.

☕ Java 
public record Tag(int[] codes) {}

new Tag(new int[]{1,2}).equals(new Tag(new int[]{1,2}));  // false!

Arrays never compare by content via equals() — not even inside a record's generated equals().

🧭 Use Cases — recognize these when they happen to you ▾
1 You replace a 30-line POJO with one record declaration

Every field, the constructor, the accessors, and a correct equals()/hashCode()/toString() all come from the one declaration. This is the #1 scenario you'll actually reach for a record.

RememberPure data holder, all-primitive components → record every time.
2 You return a record as an immutable DTO from a service layer

Safe to hand out with no defensive copying — but only as long as every component is itself immutable (String, int, another record). One mutable component breaks the guarantee for the whole record.

RememberRecord is only as immutable as its least-immutable component.
3 A record component is a mutable array or List

An array component never compares by content, and a List component can still be mutated by whoever holds a reference to it — unless you add a defensive copy in a custom constructor, the record only looks immutable.

RememberMutable component → add your own defensive copy, record won't do it for you.
🌍 Real-world example ▾

A pre-printed form with fixed fields. Fill it out once and every blank is locked. But if one of those blanks is itself a notepad glued onto the form — a mutable list — someone can still scribble on the notepad after the form is "finished," unless you handed them a photocopy instead of the original.
