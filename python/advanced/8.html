A shared counter without a lock isn't wrong sometimes — it's wrong by a genuinely unpredictable amount, every time

"Two threads increment a shared counter without a lock, many times each — what does the final count actually end up being, and why isn't it simply 200,000?"

Why it matters ▾
🏁 Race condition
❗ Problemcount += 1 is really read, add, write back, so if another thread reads in between, two increments can leave only one and the count silently comes up short.
✅ SolutionThe GIL does not keep those three steps together, so a shared update like this has to be protected by you.
RecallThe GIL does not make count += 1 atomic.
🔒 Lock
❗ ProblemNothing stops a second thread from entering the same update while the first is halfway through it.
✅ SolutionA lock can be held by only one thread at a time, so the whole read-modify-write finishes before another thread starts its own.
RecallLock = one thread in the critical section at a time.
🔥 Easy interview recall

Race condition = "the result depends on unlucky timing between threads."

Think: count += 1 → read, add, write-back — 3 steps, not 1 two threads can interleave between those steps → an increment gets lost

🧠 Visual Mental Model — understand it in 5 seconds
🔮 Predict the Output
Python 
count = 0

def increment():
    global count
    for _ in range(100_000):
        count += 1

t1 = threading.Thread(target=increment)
t2 = threading.Thread(target=increment)
t1.start(); t2.start()
t1.join(); t2.join()
print(count)

What does this print, and why isn't it simply 200,000?

Answer: Some number less than 200000 — and exactly how much less is unpredictable, varying run to run. count += 1 is a read-modify-write, not one atomic step; without a lock, the two threads can interleave between those steps, both reading the same old value and one of them overwriting the other's update. The GIL guarantees only one thread runs Python bytecode at a time — it does NOT make a multi-step operation like count += 1 atomic.

⚠️ Common Trap

The GIL does not make count += 1 atomic. Only one thread runs Python bytecode at a time, but the GIL can still switch threads in the middle of a multi-step operation like count += 1 — read, add, and write-back are three separate steps, not one, and that's exactly where the switch can land.

🔄 Likely Follow-up

"How would you fix the shared-counter race?" Wrap the increment in a Lock (with lock: count += 1), which makes the read-modify-write atomic with respect to every other thread.

🎯 Say this in the interview — the exact lines to land

"count += 1 is read-modify-write, not atomic — that's why an unlocked shared counter loses increments unpredictably, even under the GIL."

  • Lock → the standard fix — wrap the critical section so the read-modify-write happens atomically with respect to other threads.
  • RLock → re-entrant — the same thread can acquire it again without deadlocking itself, e.g. in recursive calls.
  • Semaphore → up to N holders — caps concurrent access to a limited resource pool instead of allowing just one.
  • Event → a flag, not mutual exclusion — one thread sets it, others wait on it.
  • "Thread-safe" means correct no matter how threads interleave — usually because it's properly locked.
📖 Explanation ▾

A race condition happens when a result depends on the unpredictable order two threads' operations happen to interleave in. count += 1 looks like one step but is actually three: read the current value, add one, write the new value back. If Thread B reads the old value before Thread A writes its update back, both threads compute the same "new" number and one of the two increments is silently lost. The GIL guarantees only one thread executes Python bytecode at any instant — it does not guarantee those three steps happen back-to-back without another thread getting scheduled in between.

A lock fixes this by mutual exclusion: only one thread can hold it at a time, so wrapping the counter update in a lock forces the read-modify-write to finish before any other thread can start its own. The other primitives solve related but different problems:

LockRLockSemaphoreEvent
Holders at once11 — but the same thread can re-acquire itup to Nnot a lock at all
Typical useprotect one critical sectionrecursive calls into locked codecap concurrent access to a resource poolone thread signals, others wait

Thread-safe just means an operation or data structure behaves correctly no matter how concurrent threads' operations happen to interleave — usually because it's already protected with the right locking, not because of anything special about the GIL.

💻 See the code ▾
Python 
import threading

count = 0
lock = threading.Lock()

def increment():
    global count
    for _ in range(100_000):
        with lock:
            count += 1  # ✅ read-modify-write is now atomic

t1 = threading.Thread(target=increment)
t2 = threading.Thread(target=increment)
t1.start(); t2.start()
t1.join(); t2.join()
print(count)  # always 200000

The with lock: block forces the two threads to take turns — no interleaving is possible in the middle of the update, so no increment is ever lost.

🧭 Use Cases — recognize these when they happen to you ▾
1 Several threads run count += 1 on a shared counter

count += 1 is three steps: read, add, write. If a thread switch happens in between, two threads can write the same new value, so one increment vanishes. The GIL does not prevent this.

RememberThe GIL does not make += safe.
2 You need only one thread at a time inside a critical section

The lock lets one thread hold it at a time, so the whole read-add-write finishes before another thread starts its own. The result is always the full count.

RememberLock the whole read-modify-write.
3 A function holding a lock calls another function that locks the same lock

A plain Lock cannot be taken twice, even by the thread that holds it, so the second attempt waits forever. An RLock lets the same thread take it again.

RememberRLock: same thread may re-acquire.
🌍 Real-world example ▾

A production metrics counter silently under-reported request counts for months — several worker threads incremented the same in-memory counter without a lock, so a steady trickle of increments simply vanished under load. The dashboards looked plausible enough that nobody noticed until someone cross-checked the numbers against the load balancer's own logs and root-caused it back to exactly this race.
