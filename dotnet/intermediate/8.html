ViewBag vs. ViewData vs. TempData — only one survives the redirect, and only once

What's the difference between ViewBag, ViewData, and TempData?

Why it matters ▾
📋 ViewData
❗ ProblemA controller action needs to hand a value to the view it's about to render, but the two don't share variables directly.
✅ SolutionViewData is a string-keyed dictionary the controller fills in that the view reads back — but only for that one request/response cycle.
RecallViewData = one request, string key.
🎁 ViewBag
❗ ProblemWriting ViewData["Key"] everywhere works, but string-keyed lookups read more awkwardly than plain property access.
✅ SolutionViewBag wraps that exact same dictionary in a dynamic object, so the same value can be read with dot syntax — same lifetime, no functional difference.
RecallViewBag = same dictionary, dot syntax.
⏳ TempData
❗ ProblemViewData and ViewBag are both gone the instant the response is sent, so neither survives a redirect — but a POST-then-redirect flow needs a value to reach the next request.
✅ SolutionTempData is stored server-side and survives exactly one redirect — though by default it's consumed the moment it's read.
RecallTempData = the only one that survives a redirect, and only once.
🔥 Easy interview recall

ViewData → one request, string key

ViewBag → same dict, dot syntax

TempData → one redirect, then gone

Think: ViewData/ViewBag die at the end of the request. TempData rides one redirect — then it vanishes too.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

TempData is not a longer-lasting ViewData. The instant it's read on the page you redirected to, the framework marks it for removal — reload that page, or navigate away and back, and it's gone, unless you called Keep() or Peek() to read it without consuming it.

🔄 Likely Follow-up

"Why not just use TempData for everything, since it lasts longer?" Because it's backed by session/cookie storage and has to serialize the data — real overhead for something plain ViewData already handles. Reach for TempData specifically when a value must survive a redirect, not as a bigger, longer-lived ViewData.

🎯 Say this in the interview — the exact lines to land

"ViewData is a string-keyed dictionary the controller passes to the view for that one request. ViewBag is the exact same dictionary, just accessed with dot syntax — same lifetime, no functional difference. TempData is different: it's stored server-side and survives exactly one redirect, but it's consumed the moment it's read, so it won't still be there after that."

  • ViewData/ViewBag → same dictionary, one request — gone once the response is sent.
  • ViewBag is ViewData wrapped in dynamic — dot syntax, no compile-time type checking.
  • TempData → survives exactly one redirect — built for the post-redirect-get pattern.
  • Default behavior is consumed on first read — call Keep() or Peek() if you need it again.
📖 Explanation ▾

ViewData is a ViewDataDictionary the controller action fills in and hands to the view it renders — a plain string-keyed, object-valued dictionary that only exists for that one request/response cycle. Once the response is sent, it's gone; the next request starts with a brand new, empty one.

ViewBag is a dynamic wrapper sitting on top of that exact same dictionary — ViewBag.Title and ViewData["Title"] read and write the same underlying entry. There's no difference in lifetime or scope, only in syntax, and ViewBag loses compile-time type checking in exchange for the dot syntax, since dynamic resolves members at runtime.

TempData exists for a different problem entirely: the classic post-redirect-get pattern, where a POST action redirects to a GET action and needs to hand it one short-lived value (a "your order was placed" message, for example). It's stored server-side and survives exactly one redirect — but by default it's read-once: the framework flags it for removal as soon as it's read, which is why it can quietly vanish if you read it more than once.

💻 See the code ▾
C# 
public IActionResult Details()
{
    ViewData["Message"] = "Saved!";
    return View();
}

// In the view:
<p>@ViewData["Message"]</p>   // object → cast for anything but strings

ViewData is a plain dictionary — the key is a string, the value is object.

C# 
ViewBag.Message = "Saved!";   // writes to the SAME dictionary as ViewData
return View();

// In the view:
<p>@ViewBag.Message</p>        // dynamic — no compile-time check

Swap ViewData["Message"] for ViewBag.Message — identical data, just syntax.

C# 
// POST action
TempData["Success"] = "Order placed!";
return RedirectToAction("Confirmation");

// GET Confirmation — first load
var msg = TempData["Success"];   // ✅ "Order placed!" — now marked for removal

// Refresh the SAME page again
var msg2 = TempData["Success"];  // ❌ null — already consumed

Reading TempData once consumes it — call TempData.Keep() right after reading to keep it for one more request.

🧭 Use Cases — recognize these when they happen to you ▾
1 A GET action needs to hand a value straight to the view it's about to render

No redirect involved — the action sets ViewData or ViewBag and returns View() in the same request, so either one works identically. This is the #1 scenario you'll actually reach for either type.

RememberNo redirect → ViewData/ViewBag either works.
2 A POST action redirects to a GET action and needs to carry one message along

ViewData and ViewBag are already empty by the time the GET action runs — only TempData survives the redirect, which is exactly the post-redirect-get pattern it was built for.

RememberRedirect in between → only TempData survives.
3 The confirmation page gets reloaded, or that same TempData key gets read twice

TempData is consumed the moment it's read by default, so reloading the confirmation page or reading the same key a second time returns null. A common interview trap — call Keep() or Peek() if the value genuinely needs to survive being read again.

RememberRead once by default → reload/re-read returns null.
🌍 Real-world example ▾

Your checkout POST action redirects to an order-confirmation page. Store the "order placed" message in TempData before the redirect — ViewData and ViewBag would already be empty by the time the confirmation GET action runs, because neither one survives past the request that set it.
