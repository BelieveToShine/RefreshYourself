error.js vs. not-found.js — a crash vs. a genuinely missing page

"How does error.js act as a React error boundary, and how is it different from not-found.js?"

Why it matters ▾
💥 error.js
❗ ProblemAn unhandled error thrown anywhere while rendering a route segment would otherwise crash the whole app with a blank white screen.
✅ Solutionerror.js is a Client Component automatically wrapped around that segment as a React error boundary — it catches the error and shows a fallback UI with a reset() function to retry.
Recallerror.js = the automatic catch for a crash in this segment.
🔍 not-found.js
❗ ProblemA genuinely missing resource (a deleted blog post, an unmatched route) still needs to tell both the visitor and search engines "this doesn't exist" — not just render a blank or generic page.
✅ SolutionCalling notFound() from a Server Component (or hitting a route that matches nothing) renders not-found.js with a real HTTP 404 status.
Recallnot-found.js = a real 404, triggered on purpose.
🔥 Easy interview recall

error.js → catches a crash, offers retry

not-found.js → real 404, called on purpose

Think: one catches something going wrong, the other announces something that's genuinely missing.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

error.js can't catch an error thrown inside the root layout.js itself. An error boundary can't catch an error in its own parent — a root-level error needs the special global-error.js file instead.

🔄 Likely Follow-up

"What's the difference between calling notFound() and just returning null/empty content?" notFound() actually sets the HTTP response to a real 404 status and renders not-found.js — returning empty content would still respond 200 OK with a blank page, wrong for a genuinely missing resource (bad for SEO/crawlers too).

🎯 Say this in the interview — the exact lines to land

"error.js is a Client Component automatically wrapped around a route segment as a React error boundary — it catches a rendering error and shows a fallback with a retry. not-found.js renders when notFound() is explicitly called, or a route matches nothing, and actually returns a real 404 status."

  • error.js → catches a thrown error, offers reset() to retry.
  • not-found.js → a real 404, triggered by notFound() or an unmatched route.
  • Root layout errors need global-error.js — a boundary can't catch its own parent.
  • notFound() → sets a genuine HTTP status, unlike returning empty content.
📖 Explanation ▾

An error.js file is automatically wrapped around its route segment as a React error boundary — no manual <ErrorBoundary> component needed. If anything thrown during rendering in that segment bubbles up uncaught, Next.js renders error.js instead of crashing the whole app, passing it the error and a reset() function that attempts to re-render the segment.

A not-found.js file handles a completely different situation: a resource that genuinely doesn't exist. It renders either when a route itself matches nothing, or when a Server Component explicitly calls notFound() (e.g. after a database lookup comes back empty) — and either way, the response's actual HTTP status becomes 404, not 200.

Because an error boundary can never catch an error in its own parent, a thrown error inside the root layout.js escapes every error.js in the app — that edge case is what the special global-error.js file exists to cover.

💻 See the code ▾
Next.js 
// app/dashboard/error.js
'use client';  // error.js must be a Client Component

export default function Error({ error, reset }) {
  return (
    <div>
      <p>Something went wrong.</p>
      <button onClick={() => reset()}>Try again</button>   // ✅ re-renders the segment
    </div>
  );
}

Next.js wires this up as the error boundary automatically — no <ErrorBoundary> import needed.

Next.js 
// app/blog/[slug]/page.js
import { notFound } from 'next/navigation';

export default async function BlogPost({ params }) {
  const post = await getPost(params.slug);
  if (!post) {
    notFound();   // ✅ real 404, renders not-found.js
  }
  return <Article post={post} />;
}

notFound() is explicit — a missing post is handled on purpose, not treated as a crash.

🧭 Use Cases — recognize these when they happen to you ▾
1 A data fetch inside a page throws unexpectedly

A flaky upstream API or an unhandled exception is caught right where it happened, and the visitor gets a way to retry without a full page reload.

Remembererror.js is for things that went wrong, not things that are missing.
2 A record genuinely doesn't exist (deleted, wrong ID)

Calling notFound() explicitly after a lookup comes back empty is the correct way to report "this genuinely doesn't exist," with a real 404 for crawlers and the visitor alike.

RememberMissing data → notFound(), not a thrown error.
3 An error thrown inside the root layout.js itself

Expecting the normal error.js to catch this fails silently as an app-wide crash — the root layout sits above every error.js boundary, so only the dedicated global-error.js file can cover it.

RememberRoot-level crash → global-error.js is the only thing that catches it.
🌍 Real-world example ▾

A third-party API your page depends on goes down. The fetch throws, and error.js catches it — showing "Something went wrong, try again" with a reset() button, instead of a blank crashed page. A visitor who instead requests a blog post that was deleted gets routed through notFound() to a proper 404 page — a different outcome for a genuinely different situation.
