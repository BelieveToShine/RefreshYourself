⭐ Vue.js · Advanced · Should Know

Same component, two different outputs — server vs. client

"Your SSR app logs a hydration mismatch warning in production that you can't reproduce locally — how do you track it down?"

Why it matters ▾
⚡ Hydration Mismatch
❗ ProblemCode reading a browser-only API (window, localStorage, Date.now() producing a different value) during a render path that runs on both server and client produces different markup on each side — flagged as a mismatch, often with a visible flash where content briefly shows the wrong thing before "correcting" itself.
✅ SolutionIsolate browser-only logic to run only after mount (onMounted, which never runs during SSR) instead of in the initial render path both environments share.
RecallAnything browser-only belongs in onMounted, never the shared render path.
🔥 Easy interview recall

Hydration mismatch = "the server and client rendered different markup from the same component."

Think: if the render path reads window, it can't be the same on both sides — the server never has one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming a hydration mismatch is always a code bug in your own app. A browser extension injecting DOM attributes before Vue hydrates is a real, external cause worth ruling out, especially when it reproduces in production but not locally.

🔄 Likely Follow-up

"Why would this reproduce in production but not locally?" Production and local environments can genuinely differ in timezone, locale, or which browser extensions are active — exactly the kind of environment-dependent factor that causes server/client output to diverge unpredictably.

🎯 Say this in the interview — the exact lines to land

"I'd look for code reading a browser-only API, or anything environment-dependent like Date.now() or locale, inside a render path that runs on both server and client — the fix is moving that logic into onMounted, which only ever runs on the client, after hydration's initial comparison is already done."

  • window/localStorage read during render → different output on each side.
  • Fix → move browser-only logic into `onMounted`, never the shared render path.
  • Reproduces in prod, not locally → check timezone, locale, and browser extensions, not just your own code.
  • Visible symptom → a brief flash of the wrong content before it "corrects" itself.
📖 Explanation ▾

Server-side rendering runs the exact same component code on the server to produce initial HTML, then again on the client to "hydrate" that HTML into a live, interactive app. Vue compares what the client would have rendered against what the server actually sent — if they don't match, it logs a hydration mismatch and falls back to re-rendering the affected part on the client, which is what causes the visible flash.

The most common cause is a browser-only API read during that shared render path. window, document, and localStorage simply don't exist on the server — code that reads them there either throws or silently takes a different branch than the client would. A value that's environment-dependent in a subtler way, like Date.now() or the user's locale, can also legitimately differ between the moment the server rendered and the moment the client hydrates.

The fix is to keep that logic out of the shared render path entirely — run it inside onMounted, which Vue guarantees never executes during server rendering, so it only ever runs once on the real client, after the initial hydration comparison has already happened.

💻 See the code ▾
Vue 
<script setup>
const isMobile = window.innerWidth < 768; // ❌ window doesn't exist on the server
</script>
<template>
  <p>{{ isMobile ? 'Mobile' : 'Desktop' }}</p>
</template>

The server can't evaluate window.innerWidth at all — whatever it renders for this branch will not match what the client renders.

Vue 
<script setup>
import { ref, onMounted } from 'vue';
const isMobile = ref(false); // ✅ same initial value, both sides

onMounted(() => {
  isMobile.value = window.innerWidth < 768; // ✅ only ever runs on the client
});
</script>
<template>
  <p>{{ isMobile ? 'Mobile' : 'Desktop' }}</p>
</template>

Server and client agree on the initial render (false) — onMounted then updates it safely, after hydration already succeeded.

🧭 Use Cases — recognize these when they happen to you ▾
1 A component branches on window.innerWidth or another browser-only read, directly in its render path

This is the #1 scenario you'll actually run into — the server simply has no window to read, so whatever branch that code takes can never match what the client later renders.

RememberMove any window/localStorage read into onMounted.
2 A timestamp or locale-dependent value is computed during render

The server renders at one moment and the client hydrates at a slightly later one — a value that's legitimately time- or locale-dependent can genuinely differ between the two without either side having a "bug" in the usual sense.

RememberTime/locale-dependent values need the same onMounted treatment as browser APIs.
3 The mismatch reproduces for real users in production, but never on your own machine

A candidate might assume the bug has to be in their own render logic — but a real user's browser extension injecting attributes into the DOM before Vue hydrates is a genuine external cause, and it's exactly the kind of thing that shows up only on real users' machines.

RememberRule out browser extensions and environment differences, not just your own code.
🌍 Real-world example ▾

A production SSR app occasionally logs hydration warnings on a "last updated X minutes ago" label, but the local dev team can never reproduce it. The label was computed from Date.now() directly in the render path — moving that calculation into onMounted, so it only ever runs once on the real client, eliminates the mismatch entirely.
