HTML5's built-in toolkit — which of these actually need JavaScript, and which don't?

"What newer HTML5 elements have you used, and how would you decide between a <canvas> and an <svg> for drawing something on a page?"

Why it matters ▾
  • These elements exist so you stop reaching for a JavaScript plugin/library for jobs the browser already does natively — knowing them signals you're not writing 2010-era markup.
  • "Canvas vs. SVG" is a genuinely common follow-up once you mention drawing anything — interviewers use it to check you understand *why*, not just that both exist.
  • data-* attributes come up constantly in real code reviews (custom attributes vs. data-* vs. a JS framework's own binding), so it's worth being able to say the plain rule in one line.
🔥 Easy interview recall

New HTML5 elements = "native mini-tools that replace an old JS/plugin trick."

Think: canvas → draws pixels (JS redraws the whole thing to change it) svg → draws shapes (each one is its own DOM node, stays sharp)

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

<canvas> is not just "SVG that's faster." Canvas has no DOM node for anything you draw — you can't select or style a shape after the fact, and to change one pixel you redraw the whole scene; SVG keeps every shape as its own element you can still find, style, and animate later.

🔄 Likely Follow-up

"So when would you actually reach for canvas over SVG?" When you're drawing a lot of things that change every frame (games, charts with thousands of points, image/pixel manipulation) — redrawing a bitmap is cheaper there than asking the DOM to track thousands of individual nodes.

🎯 Say this in the interview — the exact lines to land

"HTML5 added several elements that replace things people used to build with JavaScript or plugins — native video/audio playback, <picture> for responsive images, <dialog> for a built-in modal, and <details> for a collapsible section with no script at all. data-* attributes and <template> are different — they're markup meant to be read or cloned by JavaScript, not shown as-is. And canvas vs. SVG is a raster-vs-vector choice: canvas draws pixels you must redraw to update, SVG keeps each shape as its own stylable DOM node."

  • <video>/<audio> → native playback, no plugin.
  • <picture>/<source> → responsive images decided in markup, not JS.
  • <dialog> → native modal — show()/showModal(), a free backdrop.
  • <details>/<summary> → disclosure widget with zero JS.
  • <template> → parsed but not rendered until cloned into the DOM.
  • canvas = raster, redraw everything · svg = vector, each shape stays its own node.
📖 Explanation ▾

Media without a plugin. <video> and <audio> play files directly, with the browser supplying its own play/pause/volume controls — no Flash, no third-party player just to press play. <picture> wraps one or more <source> elements so the browser can pick a different image file — a different format (WebP vs. JPEG) or a different size for a small screen — before it ever downloads one, which plain <img> can't do on its own.

<dialog> is a real modal element: call .showModal() and the browser gives you a centered box, a dimmed backdrop, focus trapped inside it, and an Esc key that closes it — all things a hand-rolled "modal div" usually has to reimplement. <details>/<summary> is the plainer case: clicking the summary line shows or hides the content beneath it, with no click handler written at all.

<template> holds markup the browser parses but never renders or runs — images inside it don't load, scripts inside it don't execute — until JavaScript clones its .content and inserts the copy into the real document. data-* attributes let you park any custom value directly on an element (data-user-id="42") and read it back in JS through that element's dataset object (el.dataset.userId) — plain HTML, no framework required.

💻 See the code ▾
HTML 
<picture>
  <source srcset="photo.webp" type="image/webp">  // tried first
  <img src="photo.jpg" alt="A cat">             // fallback
</picture>

The browser picks the first <source> it supports — <img> is the required fallback, never optional.

HTML/JS 
<div id="card" data-user-id="42" data-role="admin"></div>

const card = document.getElementById("card");
card.dataset.userId;   // "42"
card.dataset.role;     // "admin"

Any data-* attribute shows up on that element's dataset object, camelCased automatically — no parsing needed.

HTML/JS 
<template id="row"><li class="item"></li></template>  // never rendered as-is

const node = document.getElementById("row").content.cloneNode(true);
list.appendChild(node);   // now it's real, visible DOM

Nothing inside <template> renders, loads, or runs until script clones and inserts it.

🌍 Real-world example ▾

Canvas is a whiteboard; SVG is a stack of labelled cutouts. Draw on a whiteboard and the marker strokes aren't separate objects — to erase one line you wipe the board and redraw the rest. Cutouts pinned to a corkboard are each their own piece — pick one up, recolor it, or move it, and every other cutout stays exactly where it was.
