Vue 2 → Vue 3 — incremental migration, not a rewrite

"How would you approach migrating a real production Vue 2 app to Vue 3?"

Why it matters ▾
🔀 Vue 2 → Vue 3 migration
❗ ProblemA big production app can't just stop shipping for weeks while every component gets rewritten at once, but it also can't stay on an unsupported major version forever.
✅ SolutionThe official migration build runs a Vue 2 app temporarily under Vue 3, surfacing runtime warnings for anything that changed behavior — so the move happens incrementally, one real breaking change at a time, not as a single big-bang rewrite.
RecallMigration build = Vue 3 engine, Vue 2 app, warnings instead of a hard break.
🔥 Easy interview recall

Migration = "incremental, warning-driven — never a rewrite."

Think: the migration build is training wheels — your Vue 2 app rides on the Vue 3 engine while it still looks like Vue 2.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

This is not "basically a rewrite." Most Options API component logic itself ports with only modest changes — the real effort is app-level setup, code depending on removed features (filters, $listeners), and third-party library compatibility.

🔄 Likely Follow-up

"What would you check first before starting a real migration?" Every major third-party dependency's own Vue 3 support status — a library with no Vue 3-compatible version is a bigger blocker than any of Vue's own breaking changes.

🎯 Say this in the interview — the exact lines to land

"The official migration build lets a Vue 2 app run temporarily under Vue 3 with runtime warnings for anything that changed behavior, so the move is incremental rather than a big-bang rewrite. The main breaking changes to budget time for are the reshaped global API, some lifecycle hook renames, filters being removed, and v-model's default prop/event being renamed."

  • Migration build → incremental, warning-driven, not a rewrite.
  • new Vue() → createApp() → global API reshaped.
  • Filters → removed — replace with a computed or method.
  • Third-party library Vue 3 support → check this first, often the real blocker.
📖 Explanation ▾

The migration build is an official package that runs the Vue 3 engine but keeps most Vue 2 behavior working, logging a console warning wherever your code hits something that changed. That turns "upgrade the whole app" into "fix one warning at a time, ship in between" — the incremental path that makes migrating a real production app realistic.

The breaking changes worth specifically budgeting time for: the global API moved from a singleton (new Vue(), Vue.use()) to an app instance (createApp(), app.use()); a few lifecycle hooks were renamed (destroyed → unmounted, beforeDestroy → beforeUnmount); filters were removed entirely — the fix is a computed property or a plain method call in the template instead; and v-model's default prop/event pair changed from value/input to modelValue/update:modelValue.

None of these changes touch the actual business logic inside most Options API components — that logic (data, methods, computed) still works close to as-is. The real cost center is almost always app-level wiring and third-party packages that haven't shipped a Vue 3-compatible version yet.

💻 See the code ▾
Vue 
// Vue 2
new Vue({ render: h => h(App) }).$mount('#app')

// Vue 3
createApp(App).mount('#app')   // ✅ app instance, not a global singleton

Every plugin/global registration moves from Vue.use(...) to app.use(...) on this same instance.

Vue 
<!-- Vue 2 filter — removed in Vue 3 -->
<!-- {{ price | currency }} -->

<!-- Vue 3 fix — a computed instead -->
{{ formattedPrice }}
<!-- computed: formattedPrice = () => formatCurrency(price.value) -->

Every filter in the app needs this same one-line swap — mechanical, but it has to happen everywhere a filter was used.

🧭 Use Cases — recognize these when they happen to you ▾
1 A key UI library the app depends on has no Vue 3 release

No Vue 3 build means no path forward until the library updates or gets replaced — this blocks the migration harder than any of Vue's own breaking changes. A common interview trap: budgeting all the migration time for Vue's own API changes and skipping this check entirely.

RememberCheck third-party Vue 3 support before anything else.
2 Hundreds of ordinary Options API components with plain logic

The bulk of a typical app's components don't touch the handful of things that actually broke — their Options API logic ports with only modest edits, which is why "this is basically a rewrite" overstates the real cost.

RememberMost component logic → low-effort to port.
3 The app uses filters throughout its templates

Every filter usage needs the same mechanical swap to a computed or method call — simple per occurrence, but worth a dedicated pass across the codebase since the migration build will keep flagging each one.

RememberFilters removed → find-and-fix every usage, one pattern.
🌍 Real-world example ▾

A 3-year-old internal dashboard still on Vue 2, shipping weekly. The team installs the migration build first, fixes warnings in small batches alongside normal feature work, swaps out the one UI library with no Vue 3 support, and only converts to <script setup> afterward as a separate, optional cleanup — the app never stops shipping during the move.
