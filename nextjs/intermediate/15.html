redirects() vs. rewrites() — does the address bar actually change?

"What's the difference between a redirect and a rewrite in next.config.js?"

Why it matters ▾
🔀 Redirect
❗ ProblemA page moved or got renamed (an old marketing URL, a renamed product slug) — visitors and search engines following the old link need to land somewhere real, not a 404.
✅ SolutionA redirects() entry in next.config.js sends a real HTTP 301/302 response, so the browser's address bar actually updates to the new URL.
RecallRedirect = the browser is told to go somewhere new.
🪟 Rewrite
❗ ProblemA clean public path (/blog/my-post) needs to map to a differently-structured internal route, or an external API needs proxying behind your own domain — without exposing that internal shape to the visitor.
✅ SolutionA rewrites() entry serves the matched route's content while the browser keeps showing the original URL — the mapping is invisible to the end user.
RecallRewrite = the content changes, the address bar doesn't.
🔥 Easy interview recall

redirects() → address bar changes (301/302)

rewrites() → address bar stays (proxy)

Think: redirects() sends the browser somewhere new. rewrites() just serves different content at the same address.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Using a rewrite when the user should actually see the new URL. A rewrite is invisible by design — if the visitor needs to see, share, or bookmark the new address, that's a redirect's job, not a rewrite's.

🔄 Likely Follow-up

"Can these be conditional, e.g. based on headers or locale?" Yes — both redirects() and rewrites() entries can match on headers, cookies, or query values, not just a flat source-to-destination mapping.

🎯 Say this in the interview — the exact lines to land

"A redirect sends the browser a real 301 or 302 response, so the address bar updates to the new URL. A rewrite serves a different route's content while the browser keeps showing the original URL — it's invisible to the visitor."

  • redirects() → address bar changes, a real HTTP redirect.
  • rewrites() → address bar stays, content swapped behind the scenes.
  • Rewrites are common for proxying an external API behind your own domain.
  • Both support conditional matching on headers, cookies, or query values.
📖 Explanation ▾

Both redirects() and rewrites() live in next.config.js and share the same basic shape — a source pattern and a destination. The difference is what Next.js tells the browser to do with that match.

A redirect returns a real HTTP redirect status (301 permanent, 302/307 temporary), so the browser itself navigates to the new URL and updates what's shown in the address bar — a search engine following an old link learns the page moved. A rewrite never tells the browser to go anywhere; the server resolves the request against the destination route internally and sends that content back, so the browser has no idea a different route actually served it.

This makes rewrites a natural fit for mapping a clean public path onto a differently-shaped internal route, or for proxying an external service through your own domain without a visible redirect hop.

💻 See the code ▾
JS 
async function redirects() {
  return [
    {
      source: '/old-path',
      destination: '/new-path',
      permanent: true,  // ✅ 301 — bar updates to /new-path
    },
  ];
}

The browser receives a real 301 and navigates itself — the URL bar changes.

JS 
async function rewrites() {
  return [
    {
      source: '/blog/:slug',
      destination: '/posts/:slug',  // ✅ served, bar stays /blog/:slug
    },
  ];
}

The visitor's address bar never leaves /blog/:slug — the mapping is invisible.

🧭 Use Cases — recognize these when they happen to you ▾
1 You renamed a product page and old links/bookmarks still point at the old slug

A permanent redirects() entry sends a 301, so the browser lands on the new slug and search engines update their index to the new address instead of treating the old one as dead.

RememberOld URL needs to actually disappear → redirect, not rewrite.
2 You want a clean public path without exposing your real folder structure

A rewrites() entry serves the /posts/[slug] route's content for a request to /blog/post-1 — the visitor only ever sees the public path.

RememberPublic path should look different from the real route → rewrite.
3 You're proxying a third-party API through your own domain

A rewrite maps your own /api/weather path to the real third-party endpoint — client code only ever calls your domain, and the actual provider URL stays out of the browser entirely.

RememberHiding a real backend URL behind your own domain → rewrite.
🌍 Real-world example ▾

Marketing renames /pricing-old to /pricing, and the old link is already indexed by Google and shared in emails. A permanent redirect keeps every old link working and passes the SEO value to the new page — a rewrite would leave visitors staring at /pricing-old in the address bar forever, which is exactly the wrong fix here.
