v-once vs v-memo — frozen forever, or re-checked on your terms?

"When would you reach for v-memo instead of trusting the compiler's own optimization?"

Why it matters ▾
🧊 v-once
❗ ProblemSome subtrees are genuinely static after the first render, but the compiler can't know that from the template alone — it still has to treat an ordinary binding as potentially dynamic.
✅ Solutionv-once tells Vue to render an element or subtree exactly once, then skip it on every future re-render, regardless of any data changes.
Recallv-once = frozen after first render, forever.
🎯 v-memo
❗ ProblemIn a large v-for list, most rows' relevant data often doesn't change on a given update — but the compiler's own patch-flag optimization still checks every row.
✅ Solutionv-memo="[dep1, dep2]" skips re-rendering a subtree unless one of the listed dependencies actually changed — a manual override for exactly that case.
Recallv-memo = skip unless a listed dependency changed.
🔥 Easy interview recall

v-once → frozen after first render, forever

v-memo → skip unless a listed dependency changed

Think: v-once = never again. v-memo = only if these changed.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

v-once is not a "mostly static" hint. It's a one-way decision — the subtree is frozen after its first render, full stop — so using it on content that actually does need to update later leaves that content permanently stale.

🔄 Likely Follow-up

"When does v-memo actually earn its keep over just trusting the compiler?" A large list where per-row re-render cost is real and most rows' relevant data genuinely doesn't change on a given update — v-memo skips re-executing the row's own render function entirely, not just skipping a cheap diff.

🎯 Say this in the interview — the exact lines to land

"v-once renders an element or subtree exactly once, then skips it on every future re-render regardless of data changes — a one-way decision for genuinely static-after-first-render content. v-memo="[dep1, dep2]" skips re-rendering a subtree unless one of the listed dependencies actually changed, which is a manual override for when the compiler's own patch-flag optimization isn't precise enough — most often a large v-for list where most rows don't need to re-render."

  • v-once → frozen after first render, a one-way decision.
  • v-memo="[...]" → skips unless a listed dependency changed.
  • Best v-memo use case → large v-for lists where most rows' data doesn't change.
  • A skipped row → skips its render function entirely, not just a cheap diff.
📖 Explanation ▾

v-once is the simpler of the two: Vue renders the element or subtree on mount, then treats it as permanently done — no amount of reactive change ever touches it again. It's a good fit for content that's computed once and never needs to react afterward, like a one-time welcome message built from a prop that never changes.

v-memo stays reactive, but gates the work: on every re-render, Vue does a shallow comparison of the current dependency array's values against the values from the previous render. If every value in the array is the same, Vue skips re-executing that subtree's render logic entirely and reuses its existing output; if anything in the array differs, the subtree re-renders normally, fully reactive, as if v-memo wasn't there at all.

v-oncev-memo
Checked again?❌ never — one-time only✅ yes, every render
Dependenciesnone — just "once"an explicit array you list
Can it un-skip later?❌ no, permanent✅ yes, when a listed value changes

💻 See the code ▾
Vue 
<template>
  <div v-once>
    <h2>{{ staticWelcomeMessage }}</h2>  // ✅ rendered once, frozen forever
  </div>
</template>

Even if staticWelcomeMessage changes later, this <h2> never reflects it — v-once already froze it.

Vue 
<div v-for="item in list" :key="item.id" v-memo="[item.id, item.selected]">
  {{ item.name }}   // skips re-render unless id or selected changed
</div>

Renaming or re-sorting elsewhere in list doesn't touch this row at all — only a change to this row's own id or selected does.

🧭 Use Cases — recognize these when they happen to you ▾
1 A one-time welcome banner built from text that never changes after mount

Nothing about a welcome message changes after it's first shown — v-once removes it from every future diff entirely, at zero risk.

RememberTruly static after mount → v-once, no ongoing cost.
2 You mark something v-once that turns out to need updating later

A common interview trap: treating v-once as a "probably won't change much" optimization. It's absolute — once applied, there is no code path that makes that subtree reactive again.

Rememberv-once is permanent — never a "mostly static" shortcut.
3 A list of 10,000 rows where only a handful of rows' selection state changes

This is exactly the case v-memo is for — per-row cost is real at this scale, and the vast majority of rows' own dependency values genuinely didn't change.

RememberLarge list, mostly-unchanged rows → v-memo earns its keep.
🌍 Real-world example ▾

v-once is like laminating a poster — once it's printed, it's done, no edits possible. v-memo is like a bouncer checking an ID against a short list of rules before deciding whether to let one specific person back in, instead of re-checking everyone in line every single time.
