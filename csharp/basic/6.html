Who's allowed to see in? Four rings of visibility

Why it matters ▾
🔒 private
❗ ProblemNothing would stop outside code from directly overwriting a field like balance, corrupting an object's internal state without going through its own logic.
✅ Solutionprivate limits access to the containing type only, so reaching it from outside is a compile-time error, not a runtime surprise.
Recallprivate = containing type only — the narrowest single modifier.
👪 protected
❗ ProblemA base class needs to hand some state to its subclasses for real inheritance to work, but marking it internal would leak that state to every unrelated type in the assembly too.
✅ Solutionprotected opens access to the containing type plus its derived types — even across assemblies, since the boundary it checks is the class hierarchy, not the assembly.
Recallprotected = containing type + derived types, any assembly.
🏢 internal
❗ ProblemA helper member used only inside one assembly still needs to be reachable across unrelated classes in it, but marking it public would commit that assembly to supporting outside callers forever.
✅ Solutioninternal allows access anywhere in the same assembly, with no inheritance relationship required at all — safe to change later since outside code never sees it.
Recallinternal = same assembly, zero family relationship required.
🌐 public
❗ ProblemAn API's real entry points need to be callable by any consumer in any project, or the type is useless to anyone outside its own assembly.
✅ Solutionpublic is accessible wherever the containing type itself is accessible — the broadest of the six, reserved for the actual surface area.
Recallpublic = accessible anywhere the type itself is accessible.
🔀 protected internal
❗ ProblemCandidates often read protected internal as stacking both restrictions — "protected AND internal," same-assembly subclass only — which gets the rule backwards.
✅ SolutionIt's protected OR internal — access is granted if either condition holds, so a derived type in another assembly and an unrelated type in the same assembly both get in.
Recallprotected internal = OR — either boundary satisfies it.
🧩 private protected
❗ ProblemRight next to protected internal, this one gets mixed up the opposite way — assumed to be another either/or combo instead of the narrowest modifier of the six.
✅ Solutionprivate protected requires derived type AND same assembly — both conditions together, narrower than protected or internal alone.
Recallprivate protected = AND — both boundaries required together.
🔥 Easy interview recall

private → me

protected → me + children

internal → my assembly

public → everyone

Think: protected internal = OR · private protected = AND

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

protected internal is not "protected AND internal at once." It's an OR — either boundary satisfies it. private protected is the AND: derived type and same assembly, both required.

🎯 Say this in the interview — the exact lines to land

"private is limited to the containing type, protected allows derived types, internal allows access within the same assembly, and public is accessible wherever the type itself is accessible. protected internal means protected OR internal, while private protected means derived type AND same assembly."

  • If they dig deeper: protected internal → OR. private protected → AND.
📖 Explanation ▾

Think of access modifiers as who is allowed through the door. private allows only the containing type. protected allows the containing type and derived types — and that's true even if the derived type lives in a completely different assembly, which surprises people expecting "protected" to mean "same project." internal allows access anywhere within the same assembly, with no inheritance relationship required at all. public is accessible wherever the containing type itself is accessible.

The combined modifiers are the important interview detail. protected internal means protected OR internal — access is allowed if either condition is satisfied. private protected means derived type AND same assembly — both conditions must be satisfied, which makes it the narrowest of the six. Access modifiers therefore control two different, independent boundaries: the type hierarchy (protected's axis) and the assembly boundary (internal's axis). private is the narrowest single modifier, public the broadest.

Default access (no modifier written) depends on context — private for class members, internal for a top-level class — so leaving it blank isn't "no restriction," it's a specific, easy-to-forget default.

💻 See the code ▾
C# 
public class Account
{
    private decimal balance;         // this class only
    protected string owner;          // this class + subclasses
    internal string branchCode;      // same assembly only
    public string AccountNumber;     // anywhere
}

Four fields, four different visibility rules — same class, same syntax pattern.

C# 
var acc = new Account();
acc.AccountNumber = "123";   // ✅ public — always fine
acc.balance = 100;           // ❌ "balance" is inaccessible due to its protection level

Reaching a private member from outside the class is a compile-time error, not a runtime surprise.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your base class ships in one library, and a subclass in a totally different app needs one of its fields.

protected crosses the assembly boundary automatically as long as the accessing type is a real subclass — there's no assembly restriction on protected at all, only an inheritance one.

Rememberprotected reaches across assemblies through inheritance alone.
2 Two classes with no inheritance relationship at all, compiled into the same assembly, need to share a helper member.

internal doesn't check the class hierarchy at all — any type compiled into the same assembly gets in, related or not, which is exactly why it's the right choice for that shared helper.

Rememberinternal = same assembly, zero family relationship required.
3 You read protected internal on a member and assume it means only a same-assembly subclass can reach it.

That's backwards — protected internal is an OR, so a derived type in a completely different assembly still gets in, and so does any unrelated type that merely shares the same assembly; only excluding both together fails.

Rememberprotected internal = OR — assuming AND is the #1 trap on this topic.
🌍 Real-world example ▾

A house. private is your bedroom — just you. protected is shared with family (subclasses). internal is the whole street having a key (same assembly), regardless of who's related to whom. public is a shop with its front door wide open.
