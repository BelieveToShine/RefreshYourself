Materialized/Indexed Views — fast reads, but never free

"A materialized/indexed view vs. a regular view — what's the actual trade-off?"

Why it matters ▾
🪟 Regular View
❗ ProblemA view whose stored result could silently drift out of sync with the base tables could never be fully trusted to reflect the latest data.
✅ SolutionA regular view stores nothing — it's just a saved SELECT that re-runs live against the base tables on every read, so it's always exactly current, at the cost of paying the full query cost every single time.
RecallRegular view = re-runs live, always fresh, full cost every read.
💾 Materialized / Indexed View
❗ ProblemRe-running the same expensive query against data that barely changes, on every single read, wastes real work over and over for a result that's mostly unchanged.
✅ SolutionA materialized view — SQL Server calls it an indexed view — computes the result once and stores it physically, so reads are as cheap as reading a normal table, but that stored copy can go stale until refreshed, or costs extra write-side work if kept auto-synced.
RecallMaterialized/indexed view = stored result, fast reads, can go stale.
🔥 Easy interview recall

Regular view → re-runs live, always fresh

Materialized/indexed view → stored result, fast but can go stale

Think: regular → you pay at read time, every time materialized → you pay at refresh time, or on every write if it's kept auto-synced

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A materialized/indexed view is a free performance upgrade. It isn't — you're trading the full query cost at read time for either stale data (if refreshed periodically) or extra write-side work (if kept automatically in sync), and skipping over that trade-off is the actual mistake.

🔄 Likely Follow-up

"When would a regular view genuinely not be good enough anymore?" When the underlying query is expensive and runs very often against data that doesn't change much — the read-cost savings from materializing it clearly outweigh the staleness/refresh-overhead cost in that specific case.

🎯 Say this in the interview — the exact lines to land

"A regular view is just a saved query — it re-runs live every time, so it's always current but pays the full query cost on every read. A materialized view, which SQL Server specifically calls an indexed view, actually stores the result physically, so reads are fast — but that stored copy can go stale and has to be refreshed, or kept in sync at the cost of extra work on every write."

  • Regular view → always fresh, but pays the full query cost on every single read.
  • Materialized/indexed view → fast reads, but the stored data can go stale until it's refreshed.
  • Not a free upgrade → refreshing costs either batch time or write-side overhead if auto-synced — always weigh it.
  • Worth it when → the query is expensive, runs often, and the base data changes slowly.
📖 Explanation ▾

A regular view never stores anything — every SELECT against it re-runs the saved query against the live base tables. A materialized view (SQL Server calls it an indexed view, since it's implemented as a unique clustered index over the view's result) is the opposite: the engine computes the result set once and stores it physically, so reading it is like reading an ordinary table — no re-computation needed.

That stored copy doesn't automatically know about every change to the base tables. Depending on the engine, it's refreshed on a fixed schedule, refreshed on demand, or maintained automatically/incrementally as the base data changes. SQL Server's indexed views update themselves as part of the same transaction that changes the base data — which is exactly the "extra write-side work" side of the trade-off: every INSERT/UPDATE/DELETE against the base tables now also has to maintain the index.

The choice is never "materialized is just faster." It's always-fresh-but-expensive-reads versus cheap-reads-but-either-stale-or-expensive-writes — pick based on how often the query runs, how expensive it is, and how fast the base data actually changes.

Regular ViewMaterialized/Indexed View
What's storedNothing — just the saved SELECTThe actual computed result rows
Read costFull query cost, every timeCheap — reads like a normal table
FreshnessAlways current (re-runs live)Can be stale until refreshed
Extra costNone beyond the read itselfRefresh time, or write-side overhead if auto-synced
Best forCheap or rare queries, or data that must be exact right nowExpensive, frequent queries over slow-changing data
💻 See the code ▾
SQL 
CREATE VIEW dbo.OrderTotals
WITH SCHEMABINDING AS
SELECT CustomerId, SUM(Amount) AS TotalSpent, COUNT_BIG(*) AS OrderCount
FROM dbo.Orders
GROUP BY CustomerId;   -- still just a saved query — reads still recompute this every time

This alone is still a regular view — nothing is stored yet until an index is added to it.

SQL 
CREATE UNIQUE CLUSTERED INDEX IX_OrderTotals
ON dbo.OrderTotals (CustomerId);   -- ✅ this is what actually materializes it

This second statement is what turns it into an indexed (materialized) view — the index forces the engine to physically store and maintain the result, kept in sync as the base tables change.

🧭 Use Cases — recognize these when they happen to you ▾
1 The query is cheap, rare, or the data must be exact right now

Nothing expensive is actually being repeated here, or the data has to be exact at the moment of the read — either way there's no real read-cost problem worth paying a staleness/refresh price to solve. A plain regular view is already the right call.

RememberCheap or must-be-exact → a regular view is enough.
2 An expensive query runs constantly against data that barely changes

A reporting dashboard re-running the same "total revenue by region" query on every page load, against a database only getting a handful of new orders per minute, is exactly the case where materializing pays off — the read-cost savings clearly outweigh being a few minutes stale. This is the #1 scenario you'll actually reach for one.

RememberExpensive + frequent + slow-changing → materialize it.
3 You expect materializing to be a free performance win

It isn't a free upgrade. If it's refreshed periodically, reads stay stale until the next refresh; if it's kept auto-synced (SQL Server's indexed views do this), every INSERT/UPDATE/DELETE against the base tables now also has to maintain the stored result. A common interview trap — candidates often describe materializing as pure upside.

RememberNo refresh is free — the cost moves to write time or shows up as staleness.
🌍 Real-world example ▾

Your reporting dashboard runs the same expensive "total revenue by region" query on every page load, against a database that only gets a handful of new orders per minute. Materializing that query — refreshed every few minutes, or auto-maintained if the engine supports it — turns a multi-second page load into an instant read, at the cost of the dashboard being a few minutes behind reality.
