⭐ Java · Advanced · Should Know

One call fails, two succeed — don't let one failure swallow the results you already have

"Three remote calls run concurrently via CompletableFuture; one fails. How do you return the successful results and represent the failed one explicitly?"

Why it matters ▾
💥 One Failure, Three Futures
❗ ProblemCompletableFuture.allOf(futures) waits for every future to finish, but the moment any one of them completes exceptionally, the combined future it returns also completes exceptionally — the two calls that actually succeeded never get surfaced on their own.
✅ SolutionGive each individual future its own recovery with exceptionally() or handle() before combining them with allOf(), so a failure turns into a normal, inspectable result instead of an exception that poisons the whole group.
RecallallOf() waits for all — it never protects you from one failure wiping out the rest; recover each future first.
🔥 Easy interview recall

Recover each future first, then combine. exceptionally() / handle() on every individual call before allOf() is what keeps one failure from erasing the successes sitting right next to it.

Think: allOf() is a finish line, not a safety net — it only tells you everyone arrived, not that everyone arrived in one piece.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

allOf() tells you which call failed. It doesn't — it only completes exceptionally the moment any input future fails, with no built-in way to tell you which one or to read the others' results from the combined future itself; each future still has to be inspected on its own.

🔄 Likely Follow-up

"What happens to the other two calls if Call B hangs instead of failing?" Nothing, by default — allOf() and a plain get() will wait indefinitely. Put a timeout on each individual future (orTimeout(), or a timed get(timeout, unit)) so one stuck call can't block the whole group, and cancel calls that are no longer needed once enough results are already in.

🎯 Say this in the interview — the exact lines to land

"I'd wrap each individual future with exceptionally() or handle() so a failure becomes a normal result instead of an exception, combine those wrapped futures with allOf(), and give each call its own timeout so one hung remote call can't block the whole group."

  • allOf() → waits for all, but propagates the first failure — it doesn't protect the others.
  • exceptionally() / handle() → apply per-future, before allOf(), to turn a failure into an inspectable result.
  • orTimeout() / timed get() → per-call timeout so a hung remote call doesn't block the group.
  • Cancellation → cancel futures no longer needed once enough results have arrived.
📖 Explanation ▾

CompletableFuture.allOf(f1, f2, f3) returns a CompletableFuture<Void> that completes once every one of its inputs has completed — but "completed" includes completing exceptionally. If any single input future finishes with an exception, the combined future finishes exceptionally too, and that's all it tells you: it doesn't name which input failed, and it gives you no access to the others' successful values through itself. Each original future still has to be inspected individually to get anything useful out of a partial failure.

The fix is to never let a raw, unrecovered future reach allOf() in the first place. Call .handle((value, ex) -> ...) or .exceptionally(ex -> ...) on each future right after it's created, turning a possible exception into an ordinary return value — a small wrapper type holding either the success or the failure works well here. Once every future in the group is guaranteed to complete normally (even the one representing a failure), allOf() on the wrapped futures never throws, and join() after it is safe to call without a surrounding try/catch.

A timeout is a separate concern from recovery, and both are usually needed together: a remote call that never returns at all — no exception, no success, just silence — will hold up allOf() forever unless each future has its own bound, via orTimeout(duration, unit) (which completes that future exceptionally once the time is up, feeding straight into the same handle()/exceptionally() recovery) or a timed get() call used individually. Cancelling a future that's no longer useful — for example, once two of three results are already enough to proceed — frees up the thread/connection it was using instead of letting it run to completion for nothing.

💻 See the code ▾
Java 
CompletableFuture<Result<String>> a = callA()
    .orTimeout(2, TimeUnit.SECONDS)      // ✅ one call can't hang forever
    .handle((v, ex) -> ex == null ? Result.ok(v) : Result.failed(ex)); // ✅ failure becomes data

Each call gets its own timeout and its own recovery — a failure (or a timeout) turns into a normal Result value, never an exception.

Java 
CompletableFuture.allOf(a, b, c).join();      // ✅ never throws — every input already recovered
List<Result<String>> results = List.of(a.join(), b.join(), c.join());
                                                   // ✅ 2 ok + 1 failed, both visible explicitly

By the time allOf() runs, every future is guaranteed to complete normally — the failure is just one more Result in the list.

🧭 Use Cases — recognize these when they happen to you ▾
1 A dashboard fans out to three independent services and one of them is flaky

This is the #1 scenario you'll actually run into: one service is slow or down while the others are fine. Wrapping each call with handle() before combining them means the dashboard shows two working panels and one clear "unavailable" state, instead of the whole page erroring out because of one dependency.

RememberRecover first, combine second — one dependency going down shouldn't blank the whole page.
2 One of the remote calls doesn't fail — it just never comes back

No exception ever arrives, so there's nothing for handle() to recover from — the whole group just waits. A per-future orTimeout() (or a timed get()) is what turns silence into an explicit, recoverable failure on a schedule you control, instead of an indefinite hang.

RememberRecovery only runs if something actually completes — a timeout is what forces that.
3 Enough results are already in — the remaining calls are now pointless

A race against several redundant providers, or a request that's already satisfied by the first N responses, doesn't need the last straggler to finish at all. Calling cancel() on the futures still outstanding frees the thread pool or connection they were holding instead of letting an unneeded call run to completion.

RememberA future nobody needs anymore should be cancelled, not just ignored.
🌍 Real-world example ▾

A product page calls pricing, inventory, and reviews services concurrently, and the reviews service times out. Wrap each call's future with handle() so the reviews failure becomes an explicit "unavailable" result rather than an exception, combine the three recovered futures with allOf(), and render pricing and inventory normally while showing a graceful placeholder for reviews.
