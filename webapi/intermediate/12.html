async/await isn't an async API — 202 + polling is

What makes an API genuinely "async" beyond using async/await?

Why it matters ▾
🔵 Sync request/response
❗ Problemasync/await frees the server's thread, but the client's single HTTP call is still open the whole time, waiting on that same response.
✅ SolutionThat's the right shape for normal request/response work: one call in, the full result out, as soon as it's ready.
Recallasync/await → same request, thread just freed.
🟢 Async (202 + polling)
❗ ProblemA report or bulk import can run for minutes — long enough to blow past any request timeout, no matter how much thread-freeing async/await does.
✅ SolutionThe endpoint returns 202 Accepted with a status URL immediately, the real work runs out-of-band, and the client polls for the result.
Recall202 + polling → new request, work decoupled.
🔔 Webhook callback
❗ ProblemPolling still means the client keeps asking "done yet?" on a timer, even when nothing has changed.
✅ SolutionThe client gives a callback URL and the server calls it once the job finishes, so nobody has to poll.
RecallDon't want to poll → let the server call back.
🔥 Easy interview recall

async/await → same request, thread just freed

202 + polling → new request, work decoupled

Think: Async API = 202 now, answer later Done? → poll the Location URL, or get a webhook

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A bigger timeout fixes a slow endpoint." A three-minute job still holds the client's connection open, and proxies, gateways and clients each have their own timeouts — hand back 202 and let the client collect the result instead.

🔄 Likely Follow-up

"For the long-running pattern, what should the initial 202 response actually contain?" A Location header pointing at the status-polling URL — the same convention 201 Created uses — so the client doesn't have to construct that URL itself.

🎯 Say this in the interview — the exact lines to land

"async/await just means the thread isn't blocked while it waits — the client is still in one continuous HTTP call. A genuinely async API returns 202 Accepted immediately with a status URL, and the client polls it or gets a webhook callback once the work is actually done."

  • async/await → frees the thread, not the client — still one round trip.
  • 202 Accepted → work happens out-of-band, client polls a Location URL.
  • Status endpoint → running until done, then the result.
  • Webhook → the server calls the client back instead of being polled.
  • Going async → a contract change, not a security upgrade.
📖 Explanation ▾

async/await is a threading detail, not an API contract. It stops the server thread from sitting idle while it waits on I/O — a database call, another service — but the HTTP request the client made is still exactly one round trip. The client's connection stays open the whole time, waiting for that same response.

A genuinely async API changes the contract itself: for work that can run long (a report, a bulk import), the initial call returns almost instantly with 202 Accepted and a Location header, and the real work continues somewhere else entirely — a queue, a background worker. The client finds out it's done by polling a status endpoint (which says running until it's finished) or by receiving a webhook, not by waiting on the original connection.

One more thing candidates mix up: going async changes the threading and the request contract, not the security. Who may call, what they may send and what they may see is a separate job — see API Security Beyond Authentication.

💻 See the code ▾
C# 
[HttpGet("orders/{id}")]
public async Task<IActionResult> GetOrder(int id)
{
    var order = await _db.Orders.FindAsync(id);  // thread freed while it waits
    return Ok(order);
    // ❌ still ONE HTTP call — client waits for this to finish
}

await here only frees the thread — the client's single request is still open the whole time.

C# 
[HttpPost("reports")]
public IActionResult StartReport([FromBody] ReportRequest req)
{
    var jobId = _jobs.Enqueue(req);    // ✅ real work runs out-of-band
    return Accepted($"/reports/{jobId}/status", new { jobId });
    // ✅ 202 + Location — client polls this URL, doesn't wait here
}

The controller returns in milliseconds — the report itself might take minutes, running somewhere else entirely.

C# 
[HttpGet("reports/{id}/status")]
public IActionResult Status(string id)
{
    var job = _jobs.Find(id);
    if (job is null) return NotFound();
    return job.IsDone
        ? Ok(new { status = "done", resultUrl = job.ResultUrl })   // ✅ finished — here's the result
        : Ok(new { status = "running" });                  // ⏳ client asks again later
}

The status URL is a normal GET — it answers "running" until the job is done, then points at the result (_jobs is your own job store).

🧭 Use Cases — recognize these when they happen to you ▾
1 A report or bulk-import job that would time out as a normal synchronous request

The job itself can run for minutes — longer than any request timeout allows. Returning 202 Accepted immediately and letting a background worker do the real work is exactly the pattern this page's diagram shows: one fast call now, the actual result found later by polling.

RememberJob runs longer than a request should wait → 202 + polling.
2 A webhook notifies the caller once background work finishes, instead of the caller polling forever

Polling still means the client keeps asking "done yet?" on a timer. A webhook flips that around — the server calls the client back the moment the job actually finishes, so nobody has to poll at all.

RememberDon't want to poll → let the server call back instead (webhook).
3 A team raises the timeout to 5 minutes instead of changing the contract

A longer timeout only moves the failure point — a proxy, a gateway or the client can still cut the connection first, and the user stares at a spinner meanwhile. A classic interview trap — the fix is a new contract, not a bigger number.

RememberLong job → change the contract (202), don't raise the timeout.
🌍 Real-world example ▾

An "export annual report" endpoint starts timing out under load because the export itself takes three minutes, and the request lifecycle only allows thirty seconds. The fix isn't a bigger timeout — it's changing the contract: the endpoint returns 202 Accepted with a job id immediately, a background worker builds the report, and the client polls /reports/{id}/status until it flips to done. Going async doesn't touch security — see API Security Beyond Authentication for that, and Rate Limiting for abuse control.
