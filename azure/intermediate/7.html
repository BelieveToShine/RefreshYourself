Troubleshooting with App Insights — following the request, not guessing

"How would you use Application Insights to troubleshoot a production issue?"

Why it matters ▾
🔎 Troubleshooting With App Insights
❗ ProblemA vague "users are seeing errors" report doesn't say which request is failing or why — and the Exceptions view alone misses it when the real cause is a slow or failing downstream dependency, since that never throws an app exception at all.
✅ SolutionA fixed triage path — Failures finds the specific failing request, then its End-to-end transaction view points straight at the exact dependency — turns "something's broken" into the real root cause without guessing.
RecallTroubleshooting = follow the request — Failures → End-to-end → dependency — never guess from Exceptions alone.
🔥 Easy interview recall

Failures → which request is failing

End-to-end → which dependency is slow

Live Metrics → watch it happen, right now

Think: follow the request — failure → dependency → root cause — don't stare at the exception count and guess.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The Exceptions view will show me the real problem." Not when the failure is a slow or failing dependency — a downstream API or database timing out shows up in the Dependencies view and the end-to-end transaction, not as an exception the app itself threw.

🔄 Likely Follow-up

"What's Live Metrics for, specifically?" A near-real-time view — seconds old, not the usual few-minutes ingestion delay — for watching an incident as it's happening, e.g. confirming a fix actually dropped the error rate right now.

🎯 Say this in the interview — the exact lines to land

"Start at Failures, follow the End-to-End transaction to the actual failing dependency — that's the fastest way from 'something's broken' to the real cause, without guessing."

  • Failures/Performance → find the specific failing or slow request first.
  • End-to-end transaction → shows the exact dependency call that's slow or throwing.
  • Live Metrics → a real-time view for watching an active incident as it happens, right now.
  • KQL → query the Log Analytics workspace for anything the built-in blades don't cover.
📖 Explanation ▾

Real triage starts with the Failures (and Performance) blade — it narrows a vague "users are seeing errors" report down to the specific request that's actually failing or running slow. From there, opening that request's End-to-end transaction view lays out every step the request took, including the exact downstream call — a database query, an HTTP call to another API — that's the one throwing or timing out. Most production issues are found right there, not by reading application code.

If the incident is still unfolding, Live Metrics gives a near-real-time feed — useful specifically for watching whether a fix you just shipped actually brought the error rate down, since the normal blades run a few minutes behind. For anything the built-in blades don't already show — a custom aggregation, a trend across a specific time window — App Insights data lives in a Log Analytics workspace underneath, and a KQL query against it can answer almost anything the UI can't.

KQL 
requests
// ✅ only the failed calls
| where success == false
// group them by error code, in 5-minute buckets
| summarize count() by resultCode, bin(timestamp, 5m)

A quick KQL query against Log Analytics — exactly the kind of question no built-in blade has a chart for.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're paged with a spike in failing requests, and don't have a specific one yet

This is the #1 scenario you'll actually run into — a vague "users are seeing errors" report. The Failures (or Performance) blade is what narrows that down to the one specific request that's actually failing or slow.

RememberNo lead yet → start at Failures, not Exceptions.
2 You already know which request is failing, but not why

Opening that request's End-to-end transaction view lays out every step it took — including the exact downstream call, a database query or another API, that's actually throwing or timing out.

RememberKnow which request, not why → End-to-end shows the real dependency.
3 You just shipped a fix and need to know, right now, whether it actually worked

Live Metrics gives a near-real-time feed — seconds old, not the usual few-minutes ingestion delay — so it's the way to confirm the error rate actually dropped right now, without waiting on the normal blades.

RememberConfirming a live fix → Live Metrics, not the delayed blades.
🌍 Real-world example ▾

A sudden spike in 500 errors gets traced through App Insights' End-to-end transaction view straight to a downstream payment API timing out — not a bug in the app's own code at all. The Failures blade found the failing checkout request in seconds; the end-to-end view is what actually pointed at the real cause.
