Maintaining Financial Data History — Triggers?

You need to keep a full history of changes to financial data — can a database trigger do that?

Why it matters ▾
🧾 Audit Trail for Financial Data
❗ ProblemFinancial systems often have to prove exactly what a record looked like before every change — an auditor or a dispute has no way to reconstruct the previous value without a real history of it.
✅ SolutionA trigger can capture the before/after row into a history table automatically, inside the same transaction as the change — though a purpose-built feature like SQL Server's Temporal Tables often does the same job more reliably, with no hand-written trigger code at all.
RecallTrigger = automatic history capture, inside the same transaction as the change.
🔥 Easy interview recall

Trigger-based history = "captured automatically, inside the same transaction — but not always the best tool."

Think: AFTER UPDATE fires → writes the old row to a history table → same COMMIT as the change itself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"If I need history, I should just write a trigger." Not always — check for a built-in temporal/audit feature first: SQL Server's Temporal Tables track full row history automatically, with zero hand-written trigger code.

🔄 Likely Follow-up

"Why does firing inside the same transaction matter here?" It guarantees the history record and the actual change are atomic — either both commit or neither does. Capturing history in a separate, later step (e.g. in application code after the database call returns) risks the app crashing in between, leaving a change with no history record.

🎯 Say this in the interview — the exact lines to land

"Yes — a trigger can capture the before/after row into a history table automatically, and it's reliable because it fires inside the same transaction as the change, so the history write is atomic with the change itself. But triggers are invisible in application code, add write overhead on high-write tables, and are harder to debug than the alternatives — capturing history explicitly at the application/ORM layer, like an audit interceptor in EF Core, or using a built-in feature like SQL Server's Temporal Tables."

  • Same transaction → the history write is atomic with the change — both commit or both roll back.
  • Invisible in app code → a developer reading the application layer won't see a database trigger running.
  • Write overhead → every change to the table now does extra work, which matters on a high-write table.
  • Alternative: app/ORM layer → e.g. an audit interceptor in EF Core, explicit and easy to version-control.
  • Alternative: built-in feature → SQL Server's Temporal Tables track history with zero custom trigger code.
📖 Explanation ▾

An AFTER UPDATE (or AFTER DELETE) trigger runs inside the exact same transaction as the statement that fired it — not as a separate follow-up step afterward. The engine gives the trigger access to the old row version (via deleted on SQL Server, or equivalent row-level access on other engines) and whatever it writes from there, like an insert into a history table, is bound to the same commit/rollback boundary as the original change. That's what makes it reliable for an audit trail: there's no window where the change succeeded but the history write didn't, or vice versa.

The cost is real, though. A trigger is logic a developer reading the application code will never see — it only shows up by looking at the database schema directly — and it adds work to every single write against that table, which matters more as write volume grows. Many teams get the same guarantee with less hidden logic by capturing history at the application/ORM layer instead (an audit interceptor in EF Core, for example), or by reaching for a database feature built specifically for this: SQL Server's Temporal Tables maintain full row history automatically, with no trigger to write or maintain at all.

💻 See the code ▾
SQL 
-- SQL Server syntax; fires inside the same transaction as the UPDATE
CREATE TRIGGER trg_Invoices_History
ON Invoices
AFTER UPDATE
AS
BEGIN
    INSERT INTO InvoiceHistory (InvoiceId, OldAmount, OldStatus, ChangedAt)
    SELECT d.InvoiceId, d.Amount, d.Status, SYSUTCDATETIME()
    FROM deleted d;  -- old row version, same transaction
END;

deleted holds the pre-update row — the INSERT and the UPDATE it's reacting to commit or roll back together, never one without the other.

🧭 Use Cases — recognize these when they happen to you ▾
1 An auditor asks "show me exactly what this invoice looked like before the change"

A trigger-captured history table already has the exact before-value, with a timestamp, because it was written in the same transaction as the original change. This is the #1 scenario a trigger-based history exists for.

RememberNeed the old value, proven? → the history table already has it.
2 You already have stored procedures writing to the table, and want zero app-code changes

An app/ORM-layer audit interceptor only sees writes that go through that one code path — a trigger on the table catches every write, no matter which stored procedure or app made it.

RememberMany write paths into one table → a trigger catches all of them.
3 Your team is about to hand-write a trigger for this on SQL Server, from scratch

On SQL Server specifically, check for Temporal Tables before writing any custom trigger for this — it's the same guarantee with no custom code to maintain or debug later.

RememberAbout to hand-write a history trigger on SQL Server → check Temporal Tables first.
🌍 Real-world example ▾

Scenario: a fintech company needs to prove to an auditor exactly what an invoice's amount and status were before every change. A trigger on the Invoices table writes the pre-update row into InvoiceHistory inside the same transaction, so there's never a gap where a change exists without its history record. On SQL Server, the same team could also have reached for Temporal Tables instead and gotten the identical guarantee with no trigger code to write or maintain.
