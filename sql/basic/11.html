Views — a saved query that behaves like a table

"What is a view, and how is it different from just saving a query as text?"

Why it matters ▾
  • A near-guaranteed follow-up any time "what is a view" comes up — the interviewer wants to see if you know it's live, not a stored copy.
  • Real reason to reach for one: hiding a messy join or filter behind a simple, reusable name for reporting tools or other developers.
  • Sets up the natural next questions — materialized views, and whether a view can be updated.
🔥 Easy interview recall

View = "a saved query that behaves like a table."

Think: SELECT * FROM ActiveCustomers is really running the view's whole underlying query, live, every single time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A view stores a snapshot of the data at the time it was created. A regular view stores no data at all — it re-runs its underlying query every time you select from it, so it's always live; a materialized view is the separate feature that actually stores a snapshot and needs an explicit refresh.

🔄 Likely Follow-up

"Can you update data through a view?" Sometimes — a simple view over a single table with no aggregation or DISTINCT can often be updated directly; a view joining multiple tables or using GROUP BY/DISTINCT generally can't be updated directly through the view.

🎯 Say this in the interview — the exact lines to land

"A view is a saved SELECT statement registered as its own database object — I can query it with normal SELECT and JOIN syntax like a table, but it doesn't store any data itself. Every time I select from it, it re-runs the underlying query live, which is what actually separates it from just saving a query as text."

  • Query it like a table → normal SELECT/JOIN syntax works directly against a view.
  • No data of its own → a plain view only stores the saved SELECT, never a copy of the rows.
  • Always current → it re-runs live every time, so it can't go stale the way a snapshot could.
  • Materialized view is different → that variant does store a physical snapshot and needs an explicit refresh.
📖 Explanation ▾

A view is a SELECT statement saved under its own name inside the database — not a string sitting in a script file. Because it's registered as a real database object, it can be granted its own permissions (someone can be allowed to SELECT from a view without having any access to the tables underneath it), and it can be queried with ordinary SELECT/JOIN syntax exactly like a table, hiding whatever joins or filters live inside it from whoever's writing the outer query.

That registration is what actually separates it from "just saving a query as text." A saved query string has to be copy-pasted or interpolated back into a new statement every time; a view is already a queryable object other statements can reference directly. A plain view still stores none of the underlying rows — every SELECT against it re-runs the saved query against the live tables, so it's always current. A materialized view is the separate, less common feature that does store a physical snapshot of the result and needs an explicit refresh to catch up with the underlying data.

💻 See the code ▾
SQL 
CREATE VIEW ActiveCustomers AS
SELECT Id, Name, Email
FROM Customers
WHERE IsActive = 1;   -- saves the SELECT itself, no rows are copied

This registers the query under a name — nothing here actually runs yet or stores any rows.

SQL 
SELECT * FROM ActiveCustomers
WHERE Email LIKE '%@example.com';   -- ✅ runs just like querying a normal table

This re-runs the view's full underlying SELECT, then filters those live results — nothing was cached in between.

🌍 Real-world example ▾

A saved search filter in an email client works the same way. It's not a separate copy of your inbox sitting off to the side — it's a live lens that re-runs its own search every time you open it, so it always shows whatever mail matches right now, not whatever matched when you first saved the filter.
