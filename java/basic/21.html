Autoboxing & Integer caching — where == quietly stops working

"What is autoboxing, and where does the Integer caching trap actually bite you?"

Why it matters ▾
🔄 Autoboxing & Unboxing
❗ ProblemGenerics like List<T> can only hold objects, never a raw primitive — using int values with them would otherwise require manual wrapping everywhere.
✅ SolutionThe compiler automatically converts between a primitive and its wrapper — Integer i = 5; boxes, int j = i; unboxes — so primitives and generic collections work together with no extra code.
RecallAutoboxing = the compiler wraps and unwraps for you, automatically.
🎯 Integer Caching
❗ ProblemComparing wrappers with == can look perfectly correct while testing with small numbers, then silently break in production the first time a larger value shows up.
✅ SolutionInteger.valueOf (used by autoboxing) only caches instances from -128 to 127 — == happens to "work" by coincidence inside that range and compares different objects outside it.
Recall== on wrappers is never safe — use equals().
🔥 Easy interview recall

Autoboxing → compiler converts automatically

Integer == → never reliable, cache is only -128 to 127

Think: == on wrappers compares identity, not value. equals() is the one that's always right.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Integer caching is not a reason to ever use == for wrapper comparison. It only happens to "work" for values -128 to 127 because those instances are cached and reused — outside that range, two equal-looking Integers are different objects and == returns false.

🔄 Likely Follow-up

"What happens if you unbox a null Integer?" It throws NullPointerException at the exact unboxing point — e.g. inside a ternary that mixes a wrapper and a primitive branch — which can look completely unrelated to null at a glance.

🎯 Say this in the interview — the exact lines to land

"Autoboxing/unboxing is the compiler converting between a primitive and its wrapper automatically. Integer caches instances only from -128 to 127, so == happens to work there by coincidence and breaks outside it — always use equals() for wrapper comparison, and watch for NullPointerException when a wrapper gets unboxed while null."

  • Autoboxing → compiler-inserted conversion, never something you call yourself.
  • == on wrappers → never reliable — use equals() always.
  • Unboxing a null wrapper → throws NullPointerException at that exact line.
📖 Explanation ▾

Every primitive has a matching wrapper class — int→Integer, boolean→Boolean, and so on. Autoboxing is the compiler calling Integer.valueOf(...) for you whenever a primitive is used where an object is expected; unboxing is the reverse, calling .intValue() for you.

The cache is what makes this risky: Integer.valueOf keeps a pool of shared objects for -128 to 127 and hands one of those back instead of building a new object every time. Two boxed 100s inside that range are genuinely the same object, so == returns true — not because == started comparing values, but because both variables happen to point at the one cached object.

💻 See the code ▾
☕ Java 
List<Integer> nums = new ArrayList<>();
nums.add(5);              // autobox: int → Integer
int first = nums.get(0);  // unbox: Integer → int

The compiler inserts Integer.valueOf(5) and .intValue() for you — you never call either one yourself.

☕ Java 
Integer a = 100, b = 100;
System.out.println(a == b);   // true  — same cached object

Integer x = 200, y = 200;
System.out.println(x == y);   // false — two different objects

Same code shape, different outcome, purely because of the value — exactly why == is unsafe for wrappers.

☕ Java 
Integer bonus = null;
int payout = hasBonus ? bonus : 0;  // ❌ NullPointerException when hasBonus is true

One branch is int, so the whole expression's type becomes int — picking the bonus branch unboxes it, and unboxing null throws right there.

🧭 Use Cases — recognize these when they happen to you ▾
1 You store numbers in a List<Integer> or use one as a Map key

Autoboxing is what makes this work at all — generics can only hold objects, so every int added to the list is silently boxed on the way in. This is the #1 scenario you'll actually run into.

RememberPrimitive into a generic collection → autoboxed automatically.
2 You compare two boxed Integers above 127 with ==

Small test values (under 128) stayed inside the cache and passed every time — the bug only surfaces once a real value above 127 shows up in production.

RememberPassed in testing with small numbers ≠ safe — always use equals().
3 A ternary mixes an Integer branch with a primitive int branch

Because the other branch is a primitive int, the whole expression's type becomes int — selecting the bonus branch unboxes it, and a null there throws from a line that doesn't obviously mention null anywhere.

RememberWrapper + primitive in one ternary → check for null before it unboxes.
🌍 Real-world example ▾

A locker vs. the item inside it. int is the raw item; Integer is a labeled locker holding that item so it can go into a system (a generic collection) that only accepts lockers, never loose items. Comparing two lockers with == asks "is this the exact same locker?" — not "do they hold the same item?"
