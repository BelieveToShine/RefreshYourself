A query's gone slow — what do you actually check first?

What are the performance improvements you would make to a slow SQL database or query?

Why it matters ▾
🔑 Indexing
❗ ProblemA query that filters or sorts on a column with no useful index forces the engine to scan far more rows than it needs to.
✅ SolutionBuild the index to match the actual query — equality columns first, then range/sort columns — but every added index also costs every write, so it's a trade-off, not "add more indexes."
RecallIndex for the real query pattern — and remember writes pay for it too.
🎯 SARGable Queries
❗ ProblemWrapping an indexed column in a function (WHERE YEAR(OrderDate)=2024) or a leading wildcard (LIKE '%foo') stops the optimizer from using an index seek at all.
✅ SolutionRewrite so the column sits bare on one side of the comparison (OrderDate >= '2024-01-01') — that's what makes a predicate "SARGable" and index-seekable.
RecallFunction on the column = no seek. Keep the column bare.
📊 Plan & Statistics
❗ ProblemGuessing at a fix without looking at the execution plan means the optimizer might already be choosing a bad plan because its row-count estimates (statistics) are stale.
✅ SolutionRead the plan for a scan where a seek was expected and a big estimated-vs-actual row mismatch, then refresh statistics after a large bulk load/delete.
RecallDiagnose from the plan first — stale statistics can beat a perfectly good index.
✂️ Query Rewriting
❗ ProblemSELECT * pulls extra columns off disk and can block a covering index; a correlated subquery can re-run once per outer row.
✅ SolutionName only the columns you need, prefer a JOIN where it's equivalent to a correlated subquery, and filter before joining where possible.
RecallAsk for less data, and ask for it in one pass, not per row.
📦 Set-Based Operations
❗ ProblemA cursor that updates one row at a time (RBAR — "row-by-agonizing-row") pays per-row overhead on every single row of a large change.
✅ SolutionRewrite the change as one set-based UPDATE/INSERT statement — the engine processes the whole set in one operation instead of one row at a time.
RecallA cursor loop over big data is almost always slower than one set-based statement.
⚡ Caching Above the Database
❗ ProblemA read-heavy, rarely-changing query can get re-run thousands of times a minute, repeatedly doing the same work for the same answer.
✅ SolutionPut an application-level or distributed cache in front of it — the fastest query is the one that never has to run against the database at all.
RecallThe cheapest query is the one that never reaches the database.
🔥 Easy interview recall

🔑 Indexing → match the real query, column order matters

🎯 SARGable → keep the column bare so a seek is possible

📊 Plan & stats → diagnose before you change anything

✂️ Rewrite → less data, fewer passes

📦 Set-based → one statement, not a row-by-row cursor

⚡ Caching → a query that never runs costs nothing

Think: the execution plan tells you which box above you're actually in — check it before reaching for any one fix.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for a bigger server is not a performance fix. More CPU/memory/faster storage can mask a bad query or a missing index for a while, but it's the last resort after the query, index, and plan work above — not the first thing to ask for.

🔄 Likely Follow-up

"Which of these do you actually check first in a real incident?" The execution plan — it tells you whether you're looking at a missing/wrong index, stale statistics, or a non-SARGable predicate, instead of guessing which fix to try.

🎯 Say this in the interview — the exact lines to land

"I'd start with the execution plan to see what the engine is actually doing, check that the indexes match the query's real filter/sort columns and that predicates are SARGable, and make sure statistics are current. After that I'd look at the query itself — avoiding SELECT *, preferring joins over correlated subqueries, and using set-based operations instead of row-by-row cursors — and only reach for more hardware as a last resort."

  • Indexing → match the actual query pattern, equality columns before range columns.
  • SARGable → never wrap the indexed column in a function or leading wildcard.
  • Plan & statistics → diagnose first; a scan-not-seek or stale statistics explains a lot.
  • Query rewriting → less data, fewer passes; avoid SELECT * and correlated subqueries.
  • Set-based & caching → bulk operations over cursors, and a cache removes repeat load entirely.
  • Hardware → last resort, after the query/index/plan work, not the first move.
📖 Explanation ▾

Diagnose before changing anything. The execution plan shows what the engine actually did — a scan where a seek was expected, an expensive sort or key lookup, or a large gap between estimated and actual row counts, which usually means statistics are stale (common right after a large bulk load or delete, even with the right indexes in place). Fixing the real cause the plan points at beats guessing.

Most of the rest is a short, well-known list: build indexes for the columns the query actually filters and sorts on (equality columns first, then range columns), keep predicates SARGable so an index can be used at all, rewrite the query to ask for less data and fewer passes, do large changes as one set-based statement instead of a row-by-row cursor, and consider partitioning once a table is genuinely large enough that partition elimination skips real work. An application-level cache in front of a read-heavy, rarely-changing query removes repeat load from the database entirely — the fastest query is the one that never runs.

Two more levers are easy to forget: an unnecessarily strict isolation level (e.g. SERIALIZABLE where READ COMMITTED would do) can serialize work that didn't need to be, and more hardware — memory for the buffer pool/cache, faster storage — is a real lever but should be the last resort, reached for after the query/index/ plan work above, not instead of it.

💻 See the code ▾
SQL 
-- Not SARGable: the function on OrderDate blocks an index seek
SELECT OrderId FROM Orders
WHERE YEAR(OrderDate) = 2024;   // ❌ scans every row to compute YEAR()

-- SARGable: OrderDate itself is bare, so an index seek can be used
SELECT OrderId FROM Orders
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';  // ✅ seekable

Same result, but only the second query can use an index on OrderDate.

SQL 
-- Composite index: equality column first, then the range/sort column
CREATE INDEX IX_Orders_CustomerId_OrderDate
  ON Orders(CustomerId, OrderDate);  // ✅ matches WHERE CustomerId=@id ORDER BY OrderDate

Column order has to match how the query actually filters and sorts — swapping it breaks the seek.

SQL 
-- Row-by-row cursor (RBAR) over a large change
DECLARE cur CURSOR FOR SELECT OrderId FROM Orders WHERE Status = 'Pending';
-- ...FETCH/UPDATE one row per loop iteration...  // ❌ per-row overhead, repeated thousands of times

-- Set-based equivalent: one statement, the whole set at once
UPDATE Orders SET Status = 'Expired'
WHERE Status = 'Pending' AND OrderDate < '2024-01-01';  // ✅ one operation, no per-row loop

Same end result, but the set-based statement lets the engine process the whole batch at once instead of row by row.

🧭 Use Cases — recognize these when they happen to you ▾
1 A report that joins three tables started timing out after the tables grew

This is the #1 scenario you'll actually run into — a query that was fine at a small table size scans more and more rows as the tables grow. Add the index that matches the join/filter columns, and check the join itself isn't pulling more columns or rows than it needs.

RememberGrowth exposes a missing index first — check that before anything else.
2 A query is fast in dev but slow in production with 10x the data

Different data volume usually means a different plan, not just "more work" — pull the production execution plan and check statistics before assuming the box just needs to be bigger.

RememberDev-vs-prod slowness → compare plans and statistics, not just hardware.
3 After 10x data growth, the team's first move is to ask for a bigger database server

More CPU/memory can mask a missing index or a non-SARGable query for a while, but the same query keeps getting slower as data keeps growing — it didn't fix the actual cause. Look at the query/index/plan first; hardware is the last lever, not the first.

RememberScaling up the server treats the symptom — the query still isn't fixed.
🌍 Real-world example ▾

Scenario: a dashboard endpoint that was fine for months starts timing out after a new filter was added to it. Pulling the execution plan shows a table scan where a seek was expected — the new filter wraps a date column in a function, so it isn't SARGable, and the existing index can't be used at all. Rewriting the predicate so the date column is bare, with a composite index matching the filter and sort columns, brings the query back to its old speed without touching the schema or the server.
