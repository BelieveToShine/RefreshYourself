OAuth2 says what an app may do, OIDC says who the user is — and ASP.NET Core Identity is neither

"What's the difference between OAuth2 and OIDC, and where does ASP.NET Core Identity fit?"

Why it matters ▾
🔑 OAuth2
❗ ProblemAn app needs to use your data on another service, but you don't want to hand it your password.
✅ SolutionYou approve once, and the app gets a limited access token to call that service for you.
RecallOAuth2 = delegated access, no password shared.
🪪 OpenID Connect
❗ ProblemAn access token says what the app may do, but not clearly who just signed in.
✅ SolutionOIDC sits on top of OAuth2 and adds an ID token that tells the app who the user is.
RecallOIDC = OAuth2 + an ID token for sign-in.
🧩 ASP.NET Core Identity
❗ ProblemSome apps need their own users, passwords, and roles stored in their own database.
✅ SolutionIdentity is a library that manages that local user store — it is not a login protocol.
RecallIdentity = your own user database, not a protocol.
🔥 Easy interview recall

OAuth2 → what the app may do (access token)

OIDC → who the user is (ID token)

ASP.NET Core Identity → where local users are stored

Think: a hotel. The key card opens certain doors (OAuth2). The ID at the desk proves who you are (OIDC). The hotel's guest book is where it keeps its own guests (Identity).

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

OAuth2 on its own is not a login system. An access token says what the app may do — it is not meant to tell the app who the user is. "Sign in" is what OIDC's ID token adds. And ASP.NET Core Identity is not an OAuth2 or OIDC server — it is a local user store.

🔄 Likely Follow-up

"Why do we need PKCE in the auth-code flow?" The one-time code comes back through the browser, so someone could try to steal it. With PKCE, the app first sends a hash (code_challenge) and later proves it started the flow by sending the original secret (code_verifier). A stolen code alone can't be exchanged. It is essential for apps that can't keep a client secret, like SPAs and mobile apps.

🎯 Say this in the interview — the exact lines to land

"OAuth2 is about authorization — it lets an app get a limited access token to call an API for the user. OpenID Connect is a thin layer on top that adds an ID token, so the app knows who signed in. ASP.NET Core Identity is a different thing: a library for keeping your own users, passwords, and roles in your own database. In a real app I'd usually use an external identity provider with the auth-code flow and PKCE."

  • OAuth2 → delegated authorization — an access token with scopes, no password shared.
  • OIDC → identity layer on top of OAuth2 — adds the ID token that says who signed in.
  • Auth-code + PKCE → the recommended browser/mobile flow — a code comes back, the app swaps it for tokens with a secret only it holds.
  • ID token vs access token → ID token is for the client app; the API checks the access token.
  • ASP.NET Core Identity → your own user store (users, password hashes, roles, claims) — not a protocol.
  • Scopes and claims → scopes limit the token; claims describe the user — both reach your code as claims on the signed-in user.
📖 Explanation ▾

OAuth2 is about authorization. A user approves an app once, and the identity provider hands the app an access token with limited scopes. The app uses that token to call an API for the user — without ever seeing the user's password. OAuth2 by itself does not say who the user is.

OpenID Connect (OIDC) adds sign-in on top. The app asks for the openid scope and also gets an ID token, a signed token that says who just signed in. In the auth-code flow with PKCE, the app sends the user to the provider, the user signs in, and the app gets back a one-time code. It then swaps the code for tokens in a direct call, proving it started the flow with the code_verifier.

ASP.NET Core Identity is a different tool. It stores your own users, password hashes, roles, and claims, usually through EF Core, and handles things like lockout and two-factor sign-in. It is a user-management library, not an OAuth2 or OIDC server. For most real systems you either use Identity for a small self-contained app, or you trust an external identity provider and use AddOpenIdConnect in your web app and AddJwtBearer in your API. For which exact handlers, default claim-name mappings, and options apply to your version, check the current docs. (Schemes and policies are on Authentication Schemes and Authorization Policies & Claims.)

💻 See the code ▾
C# 
builder.Services.AddAuthentication(o =>
{
    o.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    o.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
})
.AddCookie()
.AddOpenIdConnect(o =>
{
    o.Authority = "https://login.example.com";      // the identity provider
    o.ClientId = "my-web-app";
    o.ClientSecret = builder.Configuration["Oidc:ClientSecret"];
    o.ResponseType = "code";                        // ✅ auth-code flow
    o.UsePkce = true;                                // ✅ PKCE
    o.SaveTokens = true;
});

The web app sends users to the provider (OIDC). After sign-in, a cookie keeps them signed in to your app.

C# 
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "https://login.example.com";
        o.Audience = "my-api";                      // the access token must be meant for this API
    });

The API checks the access token, not the ID token — the ID token is for the client app.

C# 
// ASP.NET Core Identity — your OWN user store, no external provider
builder.Services.AddDefaultIdentity<IdentityUser>()
    .AddEntityFrameworkStores<AppDbContext>();

Users and password hashes live in your database. This is not OAuth2 or OIDC — it is just the local user store.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your site needs "Sign in with" a company or social account

You need to know who signed in, so you use OIDC. The provider signs the user in and sends an ID token, and your app never handles the password.

Remember"Who signed in?" → OIDC and the ID token.
2 A single-page app calls your protected API

A browser app can't keep a client secret, so it uses the auth-code flow with PKCE to get tokens. The API then validates the access token it receives.

RememberSPA → auth code + PKCE; API → checks the access token.
3 A small internal app just needs its own users and passwords

ASP.NET Core Identity keeps users and password hashes in your own database. Use it when one app owns its users and no outside provider is involved.

RememberOwn users, own database → ASP.NET Core Identity.
🌍 Real-world example ▾

A company runs several web apps and an API, and wants people to sign in once. They put one external identity provider in front of everything. Each web app uses OIDC with the auth-code flow and PKCE to find out who signed in, and the API validates the access token it gets. None of the apps store a password, and ASP.NET Core Identity isn't needed at all.
