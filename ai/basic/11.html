⭐ AI · Basic · Should Know

Your prompt just regressed in production — can you roll back to a known-good version?

"How do you manage prompts in production — where do they live, how are they versioned, and what does it mean for a prompt call to be idempotent?"

Why it matters ▾
  • A prompt hardcoded into application code can't be updated, A/B tested, or rolled back without a full redeploy — a real production pain point.
  • Interviewers ask this to see whether you treat a prompt as a production artifact with its own lifecycle, not just clever wording in a string.
  • Production code has to retry failed calls (timeouts, rate limits) — if a prompt triggers a side effect, that retry has to be safe to repeat.
🔥 Easy interview recall

Where do prompts live? → config, a database, or a prompt registry — never hardcoded

Versioned → every change gets an ID, so you can trace and roll back

Idempotent → the same call, same inputs, safe to retry

Think: the version tells you which prompt made an output; idempotent tells you it's safe to run that call again.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Idempotent doesn't mean the model gives the identical answer every time. It means the same call is safe to retry — the model's own sampling non-determinism is a separate issue (see the previous topic).

🔄 Likely Follow-up

"What's a concrete example of what could go wrong without this?" A tool call with a real side effect — like sending an email or charging a payment — retried blindly after a timeout could fire twice; the fix is making that specific action safe to repeat, not just retrying blindly.

🎯 Say this in the interview — the exact lines to land

"Production prompts live in config, a database, or a prompt registry — never hardcoded — so they can be versioned, updated, and rolled back without a redeploy. Idempotent means a retried call with the same inputs is safe to repeat."

  • Store prompts in config, a DB, or a registry— never hardcoded in app code.
  • Versioned → every prompt change gets an ID, so you can trace which version produced an output and roll back a regression.
  • Idempotent → safe to retry the same call — needed because production has to retry on network errors and rate limits.
  • A non-idempotent side effect (a tool call) retried blindly can duplicate a real action — design that action to be safe to repeat.
📖 Explanation ▾

Treat a prompt like a config value, not a piece of source code: store it in config, a database, or a dedicated prompt registry, not baked into the application itself. That's what lets you change wording, run an A/B test, or fix a bad prompt without shipping a new deploy — someone updates a row or a config value, and the running application picks up the new text on its next call.

Versioning gives every change its own identifier. When an output looks wrong, you can check exactly which version produced it. If a new version causes a regression, you roll back by pointing the app's "current" lookup at the last known-good version — a config change, not a redeploy.

Idempotent here is about the surrounding system, not the model. Production code needs to retry failed calls — a timeout, a rate limit — so a repeated call with the same inputs has to be safe. If a prompt triggers a tool call with a real side effect, that side effect needs its own protection (like an idempotency key) so a retry doesn't fire it twice; this is a separate concern from the model's own sampling randomness, covered on the previous topic.

💻 See the code ▾
Python 
def get_prompt(name: str, version: int) -> str:
    return prompt_registry.fetch(name, version)  # 🗄️ not a hardcoded string

current_version = 1  # ✅ rolled back after v2's regression
prompt = get_prompt("summarize_ticket", current_version)

Rolling back is changing which version number is "current" — no code deploy needed, because the app never called a hardcoded string.

Python 
for attempt in range(3):
    try:
        payment_api.charge(order_id, idempotency_key=key)  # ✅ same key every retry
        break
    except TimeoutError:
        # 🐛 without the key, a retry here could double-charge
        continue

The retry loop itself is fine — it's the side effect (the charge) that needs its own protection so repeating the call doesn't repeat the effect.

🌍 Real-world example ▾

A versioned prompt is like a feature flag stored in a config service instead of a value buried in code — someone can update it, roll it back, or check exactly which value was live when something went wrong, all without touching the application's deployed code.
