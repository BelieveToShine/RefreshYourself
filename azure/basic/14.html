Private Endpoint — giving a public service a private IP

"What is a Private Endpoint, and what does it change about how a service is reached?"

Why it matters ▾
🔌 Private Endpoint
❗ ProblemA compliance or security rule that says a PaaS service like Storage, SQL, or Key Vault must never be reachable from the public internet isn't satisfied by firewall or IP allow-list rules alone — the service still sits on a public IP, so traffic still crosses the public internet to reach it before the firewall ever decides who's let in.
✅ SolutionA Private Endpoint gives the service an actual private IP inside your VNet, so traffic never leaves the VNet at all — it removes the public path instead of just filtering who's allowed through it.
RecallFirewall rules filter the public path; a Private Endpoint removes it.
🔥 Easy interview recall

Private Endpoint = "a private IP for a public service, inside your VNet."

Think: no Private Endpoint → traffic still leaves over the public internet, even with firewall rules on. Private Endpoint + matching DNS → traffic never leaves the VNet.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Turning on a Private Endpoint is enough by itself. The resource is technically reachable on its private IP the moment the endpoint exists, but unless the matching Private DNS Zone is linked to the VNet, name resolution can still point clients at the public endpoint instead.

🔄 Likely Follow-up

"How is this different from a Service Endpoint?" A Service Endpoint keeps traffic on the Azure backbone, but the service still has a public IP; a Private Endpoint gives the service an actual private IP inside your VNet — a stronger isolation guarantee.

🎯 Say this in the interview — the exact lines to land

"A Private Endpoint gives a PaaS service a private IP inside your VNet, but you also need the matching Private DNS Zone — otherwise name resolution can still point at the public endpoint."

  • Private IP → the service gets a network interface inside your VNet; traffic never crosses the public internet.
  • DNS matters too → without the linked Private DNS Zone, the service's name can still resolve to the public IP.
  • vs. Service Endpoint → a Service Endpoint stays on the Azure backbone but keeps a public IP; a Private Endpoint is the stronger, private-IP isolation.
  • Real use → pair it with disabling public network access when a compliance rule says "never reachable from the internet."
📖 Explanation ▾

By default, a PaaS service like Storage, Azure SQL, or Key Vault is reached through a public endpoint — even when access is locked down with firewall/IP allow-list rules, traffic still crosses the public internet to get there; the firewall only decides who's let in once it arrives. A Private Endpoint changes that: it creates a network interface with a private IP address inside your VNet, and DNS resolution for that service's name switches to resolve to the private IP instead of the public one.

The part that's easy to miss: creating the Private Endpoint doesn't automatically redirect existing traffic. The resource is reachable on its private IP the moment the endpoint exists, but clients only start using it once the name actually resolves there — which needs the matching Private DNS Zone linked to the VNet (or your own DNS updated to match). Skip that step and the name keeps resolving publicly, so traffic keeps going out over the internet even though the private path exists.

💻 See the code ▾
Azure CLI 
az network private-endpoint create \
    --name pe-storage \                                   # the private endpoint's own name
    --vnet-name vnet1 \
    --subnet subnet1 \
    --private-connection-resource-id <storage-id> \    # the target PaaS resource
    --group-id blob \                                      # which sub-resource to target
    --connection-name conn1

--group-id blob targets Blob storage specifically — a Storage Account needs its own Private Endpoint per sub-resource (blob, file, queue, table) it exposes privately.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your compliance rule says a PaaS service must never be reachable from the public internet

This is the actual use case Private Endpoints are built for — the service gets a private IP inside your VNet, and once public network access is disabled there's no public IP left to lock down at all. This is the #1 scenario you'll actually run into.

RememberNo public IP left → nothing left to lock down.
2 You already locked the resource down with firewall / IP allow-list rules

Firewall and allow-list rules only decide who's let in once traffic arrives — the resource is still sitting on a public IP, so it's still technically reachable from the public internet. Only a Private Endpoint actually removes that path.

RememberFirewall rules filter; only a Private Endpoint removes the public path.
3 You create the Private Endpoint but never link the Private DNS Zone

The private IP exists the moment the endpoint is created, but clients only start using it once the service's name actually resolves there. Skip linking the Private DNS Zone and the name keeps resolving to the public IP — traffic keeps leaving over the internet even though the private path already exists. A great interview trap — candidates often assume turning on the endpoint is enough by itself.

RememberEndpoint alone isn't enough — DNS has to point at it too.
🌍 Real-world example ▾

A bank's compliance rule says its Storage Account must never be reachable from the public internet, full stop. A firewall allow-list still leaves the resource sitting on a public IP, which doesn't satisfy that. A Private Endpoint plus disabling public network access does — the account only has a private IP inside the bank's VNet, with no public path left to lock down.
