HashMap Internals — hashing, collisions, and the resize nobody sees

"Walk through what actually happens inside a HashMap when you call put()."

Why it matters ▾
🗂️ HashMap Internals
❗ Problem"It's O(1)" is only true if you know what's actually happening when two different keys land in the same bucket, or when the map quietly outgrows its current size — treating it as a black box leads to surprise O(n) lookups and slow startups nobody can explain.
✅ SolutionA key's hash gets spread and masked into a bucket index; collisions chain per bucket and treeify into a balanced tree past 8 entries; and the whole array doubles — rehashing everything — once the map grows past capacity × load factor.
RecallHashMap = hash → bucket, chain or tree on collision, double on growth.
🔥 Easy interview recall

HashMap = "hash the key, pick a bucket, chain (or tree) the collisions, double and rehash when it grows."

Think: 2-7 colliding entries → linked list per bucket 8+ colliding entries → red-black tree, O(log n) size > capacity × loadFactor → double the array, rehash every entry

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Not every bucket just chains linearly forever. Since Java 8, a bucket that collects 8 or more colliding entries (in a sufficiently large table) converts to a balanced red-black tree, turning a worst-case O(n) lookup into O(log n).

🔄 Likely Follow-up

"What triggers a resize, and what does it cost?" Once size exceeds capacity × loadFactor (16 and 0.75 by default), the bucket array doubles and every existing entry gets rehashed into the new array — an O(n) one-time cost, which is why pre-sizing a HashMap you know will grow large avoids repeated resizes.

🎯 Say this in the interview — the exact lines to land

"put() spreads and masks the key's hashCode() to pick a bucket; collisions chain as a linked list per bucket, and a bucket with 8 or more colliding entries treeifies into a red-black tree since Java 8. The table resizes — doubling and rehashing everything — once size exceeds capacity times load factor."

  • hashCode() → spread + masked into a bucket index.
  • Collisions → linked list per bucket, up to 8 entries.
  • 8+ colliding entries → treeified into a red-black tree, O(log n).
  • size > capacity × loadFactor → doubles the array, rehashes everything.
📖 Explanation ▾

When put() runs, the key's hashCode() goes through a supplemental spreading step and then gets masked down to fit the current bucket array's size — that result is the bucket index. Two unrelated keys can land in the same bucket; that's a collision, not a bug, and it's expected by design once enough keys exist.

A bucket's colliding entries start as a simple linked list — fine for a handful of entries. Once a single bucket accumulates 8 or more entries (and the table itself is large enough to make it worthwhile), Java 8+ converts that one bucket into a small balanced red-black tree, so a pathological bucket still resolves in O(log n) instead of a straight-line O(n) walk.

Separately, the whole map tracks how full it is. Once its size passes capacity × loadFactor — 16 and 0.75 by default, so the first resize happens around 12 entries — the bucket array doubles in size and every existing entry gets rehashed into its new position. That rehash is the real cost of a resize, which is why pre-sizing a HashMap constructor with the expected entry count avoids repeated resizes during a known bulk load.

💻 See the code ▾
☕ Java 
class BadKey {
    public int hashCode() { return 1; } // ❌ every key → bucket 0
}
// every BadKey collides in the same bucket — O(n) lookups,
// until there are enough of them to treeify into O(log n)

Treeification softens a bad hashCode() — it doesn't fix the underlying problem.

☕ Java 
Map<String, Row> table = new HashMap<>(200_000); // ✅ pre-sized
// loading 150k rows now triggers zero resizes along the way

Knowing the expected size up front skips every intermediate resize during a bulk load.

🧭 Use Cases — recognize these when they happen to you ▾
1 You know you'll load 100k+ entries into a map right at startup

Passing the expected entry count to the HashMap constructor sizes the bucket array up front, so a known bulk load never pays for a single intermediate resize.

RememberKnown size up front → pre-size the HashMap.
2 A custom key class has a weak hashCode() (e.g. it always returns a constant)

Every key lands in the same bucket, so treeification softens the damage (O(log n) instead of O(n)) but never replaces the fix — write a real hashCode() that spreads keys across buckets.

RememberWeak hashCode() → tree helps, but it's not the real fix.
3 You assume resizing just allocates more space without touching existing entries

A resize isn't just "allocate a bigger array" — every single existing entry gets rehashed into its new bucket, which is exactly why repeated resizes during a big, un-pre-sized bulk load show up as real, visible startup slowness.

RememberResize = bigger array + rehash everything, not just more space.
🌍 Real-world example ▾

A service loading a 500k-row lookup table into a default-sized HashMap hits several slow resizes during startup — pre-sizing the map with the expected entry count removes that cost entirely, because the bucket array never has to grow and rehash mid-load.
