Karma is deprecated — what do you run Angular tests with now?

Why it matters ▾
🧪 Test runner
❗ ProblemA team on the old default (Karma) hears it is deprecated, and nobody knows what to move to or whether every test must be rewritten.
✅ SolutionKnow the options: Jest or Vitest run tests in Node with a simulated DOM. The TestBed code inside the tests stays almost the same — mostly the spy and mock calls change.
RecallKarma = real browser, deprecated. Jest/Vitest = Node + fake DOM.
🔥 Easy interview recall

Karma = "real browser, deprecated." Jest / Vitest = "Node + fake DOM, faster."

Think: TestBed tests barely change — only the runner and the spy helpers do.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Jest/Vitest passed" does not mean it works in a real browser. A simulated DOM has no real layout, no real CSS, and some browser features are missing — so a test that passes in Node can still miss a visual or browser-only bug. Keep a few end-to-end tests in a real browser for that.

🔄 Likely Follow-up

"What do you lose by leaving a real browser?" Real layout, real CSS and real browser behaviour — the simulated DOM only imitates them. You gain speed and a simpler setup; end-to-end tests (Playwright/Cypress) cover what the fake DOM cannot.

🎯 Say this in the interview — the exact lines to land

"Karma was the old Angular default and it is deprecated. The alternatives are Jest and Vitest — they run tests in Node with a simulated DOM instead of a real browser. My TestBed tests stay almost the same; I just swap the runner and the spy helpers, and I check the current Angular docs for the default in my version."

  • Karma is deprecated — it ran tests inside a real browser.
  • Jest and Vitest run in Node with a simulated DOM (such as jsdom).
  • TestBed and the component tests stay almost the same — spy helpers differ (jasmine.createSpy → jest.fn / vi.fn).
  • A simulated DOM is fast but not a real browser — keep a few end-to-end tests.
  • Which runner is the default in new projects depends on your CLI version — check the current docs.
📖 Explanation ▾

For years the Angular CLI ran unit tests with Karma (the runner that opens a real browser) and Jasmine (the test framework: describe, it, expect). Karma has been deprecated, and the Angular team has been moving towards other runners. The common alternatives are Jest and Vitest. Which one the CLI sets up for a brand-new project depends on your CLI version, so check the current Angular docs instead of trusting memory.

Jest and Vitest do not open a browser. They run inside one Node.js process and use a simulated DOM such as jsdom, which imitates the browser's elements. That makes them quick to start and easy to run in a build pipeline. The price is that nothing is truly rendered: no real layout, no real CSS, and a few browser features are missing. Karma gave you the real thing, but it was slower and needed a browser installed.

The good news for a migration: your tests are mostly TestBed, ComponentFixture and expect calls, and those stay the same. What changes is the config and the helpers — Jasmine's jasmine.createSpy() or spyOn() becomes jest.fn() / jest.spyOn() in Jest, or vi.fn() / vi.spyOn() in Vitest. For anything that truly needs a browser, use an end-to-end tool.

💻 See the code ▾
TypeScript 
const fixture = TestBed.createComponent(CartComponent);   // same in all three runners
fixture.detectChanges();
expect(fixture.nativeElement.textContent).toContain('Total');  // ✅ unchanged

The test itself does not change when you swap the runner — it is all TestBed and the rendered DOM.

TypeScript 
const save = jasmine.createSpy('save');   // Jasmine (Karma)
const save = jest.fn();                    // Jest
const save = vi.fn();                      // Vitest

Only the spy helper is different — three lines for the same idea (they are alternatives, not meant to sit in one file).

🌍 Real-world example ▾

Like moving a test kitchen from a full dining room to a quick prep counter. You get results much faster and set-up is simple, but you no longer see how the dish looks on a real table — so you still run a few real tastings (end-to-end tests) before you serve customers.
