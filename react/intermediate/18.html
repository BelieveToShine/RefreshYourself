useReducer — many related fields, one front door for every change

"When would you reach for useReducer instead of useState?"

Why it matters ▾
🔹 useState
❗ ProblemWrapping a lone toggle or text input in actions and a reducer adds ceremony and nothing else.
✅ SolutionuseState gives you a value and a setter — the right fit for one independent piece of state.
RecalluseState = one simple value, one setter.
🧮 useReducer
❗ ProblemWhen several fields must change together, scattered setters can leave them out of sync — loading is true while an old error still shows.
✅ SolutionuseReducer sends every change through one reducer, (state, action) → next state, so the update rules live in one place.
RecalluseReducer = every change goes through one function.
🔥 Easy interview recall

useState → one simple value

useReducer → many fields, one rulebook

Think: reducer = (state, action) → new state. Plain React — not Redux.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A reducer must never change the old state in place. Pushing into an array or setting a field on state and returning the same object looks fine, but React compares references — the update can be skipped, and StrictMode may call a reducer twice in development. Always return a new object.

🔄 Likely Follow-up

"So is useReducer just Redux inside a component?" Same idea — actions plus a reducer — but it is local state in one component. There is no global store, middleware, or devtools unless you add them; to share it, pass it down or put it in context.

🎯 Say this in the interview — the exact lines to land

"useState is for one simple value. When several related fields change together, or the next state depends on the previous one in several ways, I use useReducer: every change is a dispatched action, and one pure reducer returns the next state — so all the update rules live in one testable place."

  • Several related fields → one reducer keeps them in sync.
  • Reducer = (state, action) → new state, and it must be pure — never mutate.
  • dispatch has a stable identity — safe to pass down.
  • Not Redux — it is local to one component unless you share it through context.
  • One independent value → stay with useState.
📖 Explanation ▾

A reducer is a plain function: it takes the current state and an action and returns the next state. You call dispatch(action) to ask for a change; React runs the reducer and re-renders with its result. Because every change passes through that one function, related fields (like loading, error, data) always change together.

Reach for it when the next state depends on the previous state in several ways, or when many handlers update the same group of fields. The reducer can live outside the component, so you can test it without rendering anything. Keep it pure: no fetching, no timers, no random values, and never change the old state in place — return a new object. In development, StrictMode may call a reducer twice to help catch impure ones.

This is not Redux: the state lives inside one component, and you share it further down with props or context if you need to (see Context API). dispatch keeps the same identity between renders, so passing it down or listing it as a dependency does not cause extra reruns. For one simple value, useState is still the right tool.

💻 See the code ▾
JSX 
function reducer(state, action) {
  switch (action.type) {
    case 'start':   return { ...state, loading: true, error: null };
    case 'success': return { loading: false, error: null, data: action.data };
    case 'fail':    return { ...state, loading: false, error: action.error };
    default:        return state;  // unknown action: keep state
  }
}

const [state, dispatch] = useReducer(reducer, { loading: false, error: null, data: null });
dispatch({ type: 'start' });  // ✅ one call changes loading and error together

Handlers only say what happened. The reducer decides the new state, so loading and error can never disagree.

JSX 
function reducer(state, action) {
  state.items.push(action.item);  // ❌ changes the old state in place
  return state;                   // ❌ same reference — React may skip the update
}

// ✅ return a new object instead:
// return { ...state, items: [...state.items, action.item] };

A reducer must return new state, never edit the old one — React compares references to decide whether anything changed.

🌍 Real-world example ▾

A shop's order counter. Instead of every customer scribbling on the order sheet, each request — add, cancel, refund — goes to one clerk who follows a rulebook and hands back the updated sheet.
