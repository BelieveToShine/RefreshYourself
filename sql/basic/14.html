CASCADE vs. SET NULL vs. RESTRICT — what really happens to the child rows?

"A foreign key can specify ON DELETE and ON UPDATE behavior — what do CASCADE, SET NULL, and RESTRICT actually do?"

Why it matters ▾
  • The natural next question right after Primary Key vs. Foreign Key — once a FK blocks a bad insert, the interviewer wants to know what it does on a delete.
  • Explains a real production incident pattern: an unreviewed ON DELETE CASCADE quietly wiping out related data across several tables at once.
  • Tests whether a candidate knows FK behavior on delete is configurable, not one fixed rule.
🔥 Easy interview recall

CASCADE → deletes child rows too

SET NULL → clears the child's FK column

RESTRICT → blocks the delete (the default)

Think: CASCADE → follows the parent down SET NULL → cuts the link, keeps the row RESTRICT → stops it cold, no clause needed to get this

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ON DELETE CASCADE is just a convenience that saves an extra DELETE statement. It can silently delete every dependent row across several cascading levels of related tables — a real, easy-to-underestimate data-loss risk if it wasn't deliberately chosen for that specific relationship.

🔄 Likely Follow-up

"You delete a Customer row with no ON DELETE clause specified at all, and it still has Orders referencing it — what happens?" The default RESTRICT (or NO ACTION, depending on the system) blocks it — the delete fails with a foreign key constraint violation, the same failure mode as the bad INSERT on the Primary Key vs. Foreign Key page.

🎯 Say this in the interview — the exact lines to land

"An ON DELETE or ON UPDATE clause on the foreign key decides what happens to the child rows when the parent row goes away. CASCADE deletes the matching children automatically. SET NULL clears their foreign key column instead, which only works if that column allows NULL. Leave it unspecified and most systems default to RESTRICT — the same constraint violation as a bad insert, just triggered by a delete instead."

  • CASCADE → deletes matching child rows automatically — powerful, but can ripple through several related tables at once.
  • SET NULL → clears the child's foreign key column instead of deleting the row — the column must actually allow NULL.
  • RESTRICT / NO ACTION → the default when nothing is specified — blocks the delete outright while any child row still references it.
  • Same error family → a blocked delete raises the exact same constraint-violation error as a bad insert with an invalid foreign key.
📖 Explanation ▾

Every foreign key can carry an ON DELETE and an ON UPDATE clause — they decide what the database does to the child rows when the parent row they point at disappears or its key changes. Without that decision, deleting a referenced row would either have to silently orphan the children or be refused outright; these clauses give the database an explicit, enforced answer instead of leaving it to chance.

CASCADE and SET NULL both let the delete succeed — they only differ in what happens to the child row afterward: deleted along with the parent, or kept with its link cleared. RESTRICT, and the closely related NO ACTION (the default in most systems when no clause is written at all), refuses the delete altogether the moment it finds a single row still referencing the parent.

💻 See the code ▾
SQL 
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    CustomerId INT NOT NULL,
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(Id)
        ON DELETE CASCADE   -- delete Customer -> its Orders go too
);

Delete a Customer here and every Order pointing at it disappears in the same statement — no separate cleanup DELETE needed, and no warning either.

SQL 
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    CustomerId INT NULL,              -- must allow NULL for SET NULL to work
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(Id)
        ON DELETE SET NULL
);

CustomerId can't be NOT NULL here — SET NULL needs somewhere to put the NULL once the parent is gone.

SQL 
-- No ON DELETE clause specified at all
DELETE FROM Customers WHERE Id = 1;
-- ❌ Error: The DELETE statement conflicted with the FOREIGN KEY constraint
-- "FK_Orders_Customers". At least one Order still references Customer Id = 1.

Same failure mode as the bad INSERT on the Primary Key vs. Foreign Key page — RESTRICT/NO ACTION is the silent default when nothing else is written.

🌍 Real-world example ▾

CASCADE is like closing a company and deactivating every employee badge tied to it in the same moment. SET NULL is like closing that one department but keeping the employees — they just lose their department field until reassigned. RESTRICT is HR refusing to close the company at all while active employee records still point at it — the closure has to wait until every employee is moved or removed first.
