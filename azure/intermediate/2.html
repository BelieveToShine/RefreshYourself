ACI vs. Container Apps vs. AKS — how much orchestration do you actually need?

"What's the actual decision between ACI, Container Apps, and AKS for running containers on Azure?"

Why it matters ▾
  • Checks whether you understand the real operational tradeoff between "no orchestration," "serverless containers," and "full Kubernetes" — not just naming the three services.
  • Comes up any time a team is deciding how to run containerized workloads without over- or under-provisioning operational effort.
  • A common way interviewers probe whether you reach for the simplest tool that fits, instead of defaulting to the most powerful one.
🔥 Easy interview recall

ACI → one container, no orchestration

Container Apps → serverless microservices, scale-to-zero

AKS → full Kubernetes, full control

Think: ACI for one job. Container Apps for most microservices. AKS only when you actually need Kubernetes itself.

⚠️ Common Trap

"We should use AKS because Kubernetes is the standard." For most microservice workloads, Container Apps gives the same scaling and ingress benefits without the operational overhead of running and patching your own cluster.

🔄 Likely Follow-up

"When do you actually need AKS over Container Apps?" When you need direct Kubernetes API access, custom controllers/operators, or you're migrating existing Helm charts/K8s manifests as-is.

🎯 Say this in the interview — the exact lines to land

"ACI is for a single container with no orchestration, Container Apps is for serverless microservices with built-in scaling, and AKS is for full Kubernetes control — I pick the least orchestration that still does the job."

  • ACI → use for a short-lived or batch job that doesn't need scaling or ingress.
  • Container Apps → use for microservices that need scaling and ingress without managing a cluster.
  • AKS → use when you need real Kubernetes control — custom operators, complex networking, existing manifests.
  • Reaching for AKS "by default" is the real signal of over-engineering — most microservice workloads don't need it.
📖 Explanation ▾

ACI (Azure Container Instances) is the simplest option: it runs a single container (or a small group) with no orchestration layer at all, billed per second — good for a short-lived or batch job that starts, does its work, and exits. Container Apps is a serverless container platform built on Kubernetes under the hood, but it hides the cluster from you: it gives built-in scaling (including scale-to-zero), Dapr/KEDA integration, and ingress, so you get microservice-style deployment without managing Kubernetes yourself.

AKS is full managed Kubernetes — the same API, controllers, and networking model as Kubernetes anywhere else, with Azure managing the control plane. It's the right choice when a team genuinely needs Kubernetes' full feature set (custom operators, complex networking, existing manifests) and is willing to own the operational complexity that comes with running a cluster.

💻 See the code ▾
CLI 
az containerapp create --name myapp --resource-group rg-demo \
  --image myregistry.azurecr.io/myapp:latest \
  --min-replicas 0 # ✅ scale-to-zero — no traffic, no idle containers

--min-replicas 0 is a flag ACI can't offer and AKS makes you configure yourself — Container Apps gives it as one line.

🌍 Real-world example ▾

A startup runs its dozen microservices on Container Apps — scaling, ingress, and service-to-service calls all work out of the box, with nobody on the team patching a cluster. They only reach for AKS once a later acquisition brings in a service that already depends on a custom Kubernetes operator someone else built — a real need for the Kubernetes API itself, not just more traffic.
