🧠 Deep Dive

Zone.js isn't the change-detector — it's a monkey-patch that only knows "something async just happened"

"Mechanically, how does Zone.js actually trigger Angular's change detection, and what does OnPush skip at that level?"

Why it matters ▾
  • The natural follow-up once someone says "Zone.js triggers change detection" — interviewers push for the actual mechanism, not the one-line summary.
  • Explains the real cause behind "why does my whole app re-check on one keystroke" and "why won't this OnPush component update," not just the trigger list from Intermediate.
  • Sets up zoneless Angular directly — reasoning about removing Zone.js only makes sense once you know exactly what it was doing underneath.
🔥 Easy interview recall

Zone.js → monkey-patches async, notices it finished

tick() → walks every component, no exceptions

OnPush skip → happens per component, not in the walk

Think: Zone.js is a doorbell, not a cleaner — it only rings "something happened," it never decides who actually has to clean.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

tick() doesn't prune OnPush branches from its walk. The walk still reaches every component structurally — it's that OnPush component's own update instructions that don't run, unless something marked it dirty first.

🔄 Likely Follow-up

"If markForCheck() walks up marking ancestors, does that mean it also marks the component's own children as needing a check?" No — it walks toward the root, not down. The component's children still get checked through the normal top-down walk, based on their own strategy and dirty state, which markForCheck() has nothing to do with.

🎯 Say this in the interview — the exact lines to land

"Zone.js monkey-patches common async APIs so Angular's NgZone notices when a callback finishes, which schedules ApplicationRef.tick() to walk the whole component tree — a Default component gets checked outright, but an OnPush component's own update instructions are skipped unless something marked it dirty first: a new @Input reference, a template event, markForCheck(), an async pipe, or a changed Signal."

  • Zone.js → monkey-patches async APIs (timers, promises, DOM events, XHR/fetch) so Angular notices when one finishes.
  • tick() → walks the whole tree unconditionally; the skip happens at each component's own execution, not the walk itself.
  • markForCheck() → flags ancestors dirty for the next tick — it checks nothing right now.
  • detectChanges() → runs the check immediately, synchronously, without waiting for a tick.
  • Signals → notify Angular directly, per binding, with no need for Zone.js to have noticed anything.
  • Zoneless Angular → removes Zone.js's auto-trigger entirely, so it requires Signals (or manual scheduling) to render at all.
📖 Explanation ▾

Zone.js doesn't run change detection itself — it monkey-patches the common asynchronous browser APIs (setTimeout, promises, DOM event listeners, XHR/fetch) so Angular's own zone wraps every callback that goes through them. When any patched operation completes and its callback runs inside that zone, NgZone gets notified that some async work just finished — once the current batch of callbacks has fully drained, that notification is what schedules ApplicationRef.tick(). Zone.js's job stops there: it's a signal that something happened, not a decision about what to check.

tick() then walks the whole component tree from the root, unconditionally — every component is structurally visited on every run. What actually happens at each one depends on its own strategy: a Default component's update instructions run outright, while an OnPush component's own instructions are skipped unless it was already marked dirty — by one of the specific triggers from the Intermediate Change Detection page (a new @Input reference, an internal template event, markForCheck(), an async-pipe emission, or a changed Signal). detach() goes further than any of those: it pulls a component out of tick()'s walk entirely, so even a Default component stops being checked automatically until reattach() — or a direct detectChanges() call — brings it back.

Signals skip this whole path. Reading a Signal inside a template wires up a fine-grained dependency between that exact binding and that Signal, so when its value changes it can mark the relevant view directly — no dependence on Zone.js having noticed some unrelated async event at all. That's exactly why removing Zone.js (zoneless Angular, next in this track) forces a Signals-first architecture: without Zone.js's automatic "something happened, let's tick" signal, and without Signals telling Angular precisely what changed, nothing would render on its own.

💻 See the code ▾
TypeScript 
this.websocket.onmessage = (msg) => {
  this.data = msg.data;
  this.cdr.markForCheck();  // ✅ tell Angular this component needs checking
};
// WebSocket's onmessage runs outside anything Zone.js patches

This callback never runs inside Angular's zone, so nothing would notice this.data changed without the explicit markForCheck() call.

TypeScript 
// markForCheck() — flags it, waits for the next tick
this.cdr.markForCheck();

// detectChanges() — runs the check right now, synchronously
this.cdr.detectChanges();

markForCheck() only sets a flag for the next scheduled tick; detectChanges() runs the check immediately, without waiting for one.

🌍 Real-world example ▾

A fire-drill supervisor checking every floor. After any alarm, the supervisor walks every single floor of the building — that's tick()'s walk, unconditional. Floors running OnPush have their own "please check me" light that has to be switched on before the supervisor actually inspects that floor, even though the supervisor still walks right past its door. Calling markForCheck() is someone on a high floor flipping on their own light — and every floor's light between them and the ground — so the next patrol doesn't walk past any of them.
