🧠 Java · Advanced · Deep Dive

A version bump is not just a number change — it's four things to evaluate on purpose

"Your application is moving to a newer Java release. What do you actually need to evaluate?"

Why it matters ▾
⬆️ Upgrading Isn't Free
❗ ProblemTreating a Java upgrade as "change the version number and redeploy" skips the real risk: the module system has progressively restricted internal API access across versions, so code reaching into JDK internals can silently stop compiling or throw at runtime.
✅ SolutionEvaluate four things deliberately before moving — removed/encapsulated internal APIs, third-party dependency support, GC default/behavior changes, and whether virtual threads are actually worth adopting — rather than discovering any of them in production.
RecallA real upgrade has four checkpoints — APIs, dependencies, GC, virtual threads — not one version number.
🔥 Easy interview recall

internal APIs → removed/encapsulated, check reflective access

dependencies → third-party support for the target version

GC → defaults/behavior may have changed

virtual threads → worth evaluating, never mandatory

Think: four deliberate checkpoints, not one version number — each one can break something a simple compile won't catch.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A Java upgrade is just changing a version number and redeploying. The module system has progressively restricted reflective access to internal APIs across versions — code reaching into com.sun.* or similar internals can fail to compile or start throwing at runtime, something a version bump alone will never surface until it's tried.

🔄 Likely Follow-up

"Should every application adopt virtual threads once it's on Java 21+?" No — it's worth evaluating deliberately, not a mandatory migration. Virtual threads help a thread-per-request style workload that's often blocked on I/O; they don't speed up CPU-bound work, and a codebase leaning on synchronized blocks around blocking calls needs that pinning caveat checked before adopting them.

🎯 Say this in the interview — the exact lines to land

"I'd evaluate four things deliberately: whether the code touches any removed or newly-encapsulated internal APIs, whether every third-party dependency actually supports the target version, whether the garbage collector's defaults or behavior changed between versions, and — only if we're moving to 21 or later — whether the concurrency model would genuinely benefit from virtual threads."

  • Internal APIs → the module system restricts reflective access further with each release — check for breakage.
  • Dependencies → confirm every library actually supports the target version before moving.
  • GC behavior → defaults can change between versions — old tuning may need revisiting.
  • Virtual threads → worth evaluating on 21+, never a mandatory migration.
📖 Explanation ▾

The module system introduced in Java 9 has steadily tightened what code outside the JDK itself can reach into. Code that depends on an internal class (anything under a package like com.sun.* or a JDK-internal module not meant for public use) risks breaking on a newer release — sometimes a compile failure, sometimes a runtime IllegalAccessException depending on how strict that particular release's encapsulation is. This is the single most underestimated risk in a version bump, precisely because it's invisible until the code path that touches the internal API actually runs.

Third-party dependency support is the second checkpoint, and it's organizational as much as technical: a library that hasn't published a release validated against the target JDK can fail in ways that have nothing to do with the application's own code. Garbage collector behavior is the third — default collectors and their tuning defaults have changed across major releases, so GC flags and heap settings tuned carefully for one version aren't guaranteed to still be the right choice on another; this deserves the same re-evaluation Advanced #3's generational/collector trade-offs page already covers, just triggered by the version move instead of a fresh problem.

Virtual threads are the fourth checkpoint and the easiest one to get wrong in either direction: skipping the evaluation entirely leaves real throughput on the table for a thread-per-request workload blocked often on I/O, but treating it as mandatory is just as wrong — virtual threads don't speed up CPU-bound work, and a codebase that leans on synchronized blocks around blocking operations needs the carrier-thread pinning caveat checked first, since a pinned virtual thread loses the exact benefit it exists to provide.

💻 See the code ▾
Java 
import com.sun.security.util.SomeInternalHelper; // ❌ internal API — not a public contract
// risks a compile failure or IllegalAccessException on a newer release

A dependency on a JDK-internal class is exactly the kind of thing a plain version bump won't catch until the affected code path actually runs.

Java 
ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor();
                                                   // ✅ worth evaluating on 21+ for blocked-on-I/O workloads
                                                   // not a speedup for CPU-bound work — evaluate, don't assume

Adopting virtual threads is checkpoint four — deliberate, not automatic, and only relevant once the target version is actually 21 or later.

🧭 Use Cases — recognize these when they happen to you ▾
1 A library or internal utility reaches into a JDK-internal class

This is the highest-risk checkpoint precisely because it's invisible at compile time on some releases and only surfaces as a runtime failure on others. Searching the codebase for internal-package imports before the upgrade, not after it ships, is what catches this.

RememberInternal-API usage is the checkpoint most likely to fail silently until it runs.
2 A key dependency hasn't published a release validated against the target JDK yet

This is an organizational risk, not a code-level bug: a dependency the team doesn't control may need its own upgrade, a pinned older version, or a replacement before the move is even possible — worth checking before any code change begins.

RememberAn unsupported dependency can block the whole upgrade before code is even touched.
3 The team asks whether this upgrade should also mean adopting virtual threads

Only relevant once the target is Java 21+: a thread-per-request service often blocked on I/O is a genuine candidate, but this is a deliberate evaluation (including the synchronized-block pinning caveat) — never an automatic "because we can now" decision.

RememberVirtual threads are the fourth checkpoint to evaluate, never an automatic add-on to the upgrade.
🌍 Real-world example ▾

A service moves from an older LTS release to the current one, and a batch job that used a JDK-internal reflection helper starts throwing on startup. A deliberate pass through internal-API usage before the upgrade — not just a clean compile on the old version — is what would have caught it first.
