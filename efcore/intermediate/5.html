IQueryable<T> vs. IEnumerable<T> — who actually runs your query?

IQueryable<T> vs. IEnumerable<T> — where does the query actually execute for each, and what's the practical consequence of switching between them mid-query?

Why it matters ▾
  • Checks whether you actually know where LINQ executes — not just that both types "work with LINQ."
  • Comes up the moment you review or write a repository/service method that wraps an EF Core query.
  • A favorite trap question, because the mistake compiles and runs fine — nothing crashes, nothing warns you.
🔥 Easy interview recall

IQueryable<T> → keeps building, translates to SQL

IEnumerable<T> → already running, LINQ-to-Objects only

Think: IQueryable<T> is still writing the SQL. IEnumerable<T> already stopped writing it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

This is not a compile error or a runtime exception. A repository method declared to return IEnumerable<Order> that actually does return _context.Orders; compiles and runs perfectly — it just silently pulls every row into memory before filtering, every single time, because the compiler resolved .Where() against the declared type.

🔄 Likely Follow-up

"A repository method is declared to return IEnumerable<Order> but internally does return _context.Orders;. A caller chains .Where(o => o.Status == "Open") onto the result. Does that filter get pushed down to SQL?" No — the compile-time type is IEnumerable<Order>, so .Where() resolves to Enumerable.Where at compile time; EF Core's SQL translator never sees it, so every row is pulled from the database first and filtered in memory afterward.

🎯 Say this in the interview — the exact lines to land

"IQueryable<T> is a query that hasn't run yet — each LINQ method chains onto its expression tree, and EF Core translates the whole thing into one SQL statement only once something enumerates it. IEnumerable<T> is already executing or already materialized, so anything chained onto it compiles against LINQ-to-Objects and runs in memory in C#."

  • IQueryable<T> → expression tree, translated to SQL once enumerated.
  • IEnumerable<T> → already running or in memory, further LINQ stays in C#.
  • Overload resolution always uses the compile-time declared type, never the runtime object.
  • A method declared IEnumerable<T> that's really an IQueryable<T> underneath is a silent full-table fetch waiting to happen — no error, just wasted rows.
📖 Explanation ▾

IQueryable<T> is a query, not a result. Every LINQ method chained onto it — Where, Select, OrderBy — gets captured into the same expression tree instead of running immediately. EF Core only translates that whole tree into one SQL statement once something actually enumerates it: a foreach, .ToList(), .First(), and so on.

IEnumerable<T> means the sequence is already executing, or already sitting fully in memory. Once something is typed as IEnumerable<T>, any further LINQ chained onto it compiles against Enumerable's in-memory extension methods — plain C#, not SQL — regardless of what the object actually is underneath.

That last part is what makes the trap possible: C# resolves an extension method like .Where() using a variable's compile-time type, never the object it happens to be holding at runtime. A repository can return a real IQueryable<Order> from a method declared to return IEnumerable<Order>, and the compiler still binds every chained call to Enumerable, because that declared type is the only thing it can see.

💻 See the code ▾
C# 
public IQueryable<Order> GetOpenOrders()
{
    return _context.Orders;   // ✅ declared AND returned as IQueryable<Order>
}

var orders = repo.GetOpenOrders()
                  .Where(o => o.Status == "Open");   // ✅ joins the SAME expression tree

var list = orders.ToList();   // ✅ ONE query — WHERE runs in SQL

The declared return type is IQueryable<Order> — the caller's .Where() keeps building the same tree.

C# 
public IEnumerable<Order> GetOpenOrders()
{
    return _context.Orders;   // ❌ still an IQueryable<Order> at runtime
}

var orders = repo.GetOpenOrders()
                  .Where(o => o.Status == "Open");   // compiles against Enumerable.Where

var list = orders.ToList();   // ❌ TWO steps: fetch everything, THEN filter in C#

The declared type is IEnumerable<Order>, so the compiler picks Enumerable.Where — EF Core's SQL translator never sees this filter.

C# 
public IQueryable<Order> GetOpenOrders()   // ✅ fix: declare the real type
{
    return _context.Orders;
}

Changing only the declared return type — same method body — restores SQL translation for every caller.

🌍 Real-world example ▾

Your API is fast in dev with 200 rows but times out in production with 2 million. A repository method is quietly declared IEnumerable<Order>, so it pulls the whole Orders table into memory before every single filter runs. Fix: change the declared return type to IQueryable<Order> (or return an already-filtered IQueryable) so the SQL translator actually sees the .Where() the caller chains on.
