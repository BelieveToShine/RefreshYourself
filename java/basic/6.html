equals() and hashCode() — break the contract, break every hash-based collection

"What's the contract between equals() and hashCode(), and what breaks if you violate it?"

Why it matters ▾
🧩 The equals()/hashCode() contract
❗ ProblemA HashMap/HashSet finds entries by their hash code first, then checks equals() only within that one bucket — if an object's hash code doesn't match where it "should" be, it's never found, even though it's genuinely in the collection.
✅ SolutionThe contract requires that any two objects that are equals() also return the same hashCode() — guaranteeing they're always looked for in the same bucket.
RecallEqual objects must share a hash code, or hash-based lookups silently fail.
🔥 Easy interview recall

The contract = "if two objects are equal, their hash codes must be equal too."

Think: equals() says "same." hashCode() has to agree — or HashMap/HashSet lose the object.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Overriding equals() without also overriding hashCode(). An object that equals() another one already in a HashMap/HashSet can land in a different bucket and silently never be found — always override both together.

🔄 Likely Follow-up

"Does the reverse hold — do equal hash codes mean the objects are equal?" No — two genuinely unequal objects can share a hash code (a collision); only the forward direction, equals() implies same hashCode(), is required by the contract.

🎯 Say this in the interview — the exact lines to land

"If two objects are equal by equals(), they must return the same hashCode(). The reverse isn't required — different objects can share a hash code as a collision — but breaking the forward rule breaks lookups in any hash-based collection."

  • Forward rule → equals() implies same hashCode(), mandatory.
  • Reverse rule → not required — a hash collision between unequal objects is fine.
  • Override one → always override both together.
📖 Explanation ▾

A HashMap or HashSet finds an entry in two steps: first it computes the key's hashCode() to jump straight to a bucket, then it uses equals() to find the exact match within that bucket. If an equal object's hash code doesn't land it in the same bucket as the one already stored, that second step never even gets a chance to run.

That's the whole reason for the forward rule: two equals() objects must produce the same hashCode(). The reverse isn't required — two unequal objects landing in the same bucket is just a normal hash collision, handled correctly by the equals() check inside that bucket.

Overriding only one of the pair is the classic way to violate this. If a class overrides equals() to compare fields but leaves the inherited identity-based hashCode() in place, two field-equal instances will usually get different hash codes — and a hash-based collection will never recognize them as the same key.

💻 See the code ▾
Java 
class Person {
    String name;

    public boolean equals(Object o) {
        if (!(o instanceof Person p)) return false;
        return name.equals(p.name);   // ✅ overridden — compares content
    }
    // ❌ hashCode() NOT overridden — still identity-based from Object
}

Two Persons with the same name are equals() — but with no matching hashCode(), a HashSet still won't find one using the other.

Java 
public int hashCode() {
    return name.hashCode();   // ✅ fixed — matches equals(), same bucket now
}

Deriving hashCode() from the exact same field equals() checks is what keeps the contract intact.

🧭 Use Cases — recognize these when they happen to you ▾
1 You store a custom object as a HashMap key

Override both together, or a key that's logically equal to one already stored can still fail to find it. This is the #1 scenario you'll actually run into.

RememberCustom HashMap key → override equals() and hashCode() together.
2 Two different objects happen to land in the same bucket

That's expected and harmless — the map still finds the right entry using equals() among the entries sharing that bucket.

RememberShared bucket between unequal objects → a normal collision, not a bug.
3 You override equals() and skip hashCode() because "nothing changed"

The class is now unsafe in any hash-based collection — a logically equal object can hash to a different bucket and never be found.

RememberOverride equals() alone → silently breaks every hash-based lookup.
🌍 Real-world example ▾

Think of a library's shelving system by call number. If two copies of the exact same book get different call numbers, the librarian will look on the wrong shelf for one of them and conclude it's missing — even though it's sitting right there in the building, just filed under the wrong number.
