Managed Identity vs. Service Principal — who's actually the caller?

"When does an Azure resource use Managed Identity vs. a Service Principal, and why is Managed Identity generally preferred where it's available?"

Why it matters ▾
  • Checks whether you understand who's actually authenticating — the caller, not just "the app has permissions."
  • Comes up any time a design touches how a service reaches Key Vault, storage, or a database without a secret sitting in config.
  • A common follow-up once a candidate says "we use Managed Identity" — the interviewer wants to know you also know when that answer doesn't apply.
🔥 Easy interview recall

Managed Identity → Azure creates & rotates it — no secret at all

Service Principal → you create the secret, and you rotate it

Think: caller is an Azure resource → Managed Identity. Caller is outside Azure → Service Principal.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for a Service Principal with a long-lived secret "because that's what older docs showed," even for an Azure-to-Azure call. If the caller is itself an Azure resource, Managed Identity removes the entire credential-rotation problem — Service Principal is really for callers that aren't Azure resources at all: a CI/CD pipeline, an on-prem app, a non-Azure cloud.

🔄 Likely Follow-up

"So when do you still need a Service Principal?" CI/CD pipelines authenticating from outside Azure, or cross-tenant scenarios where a Managed Identity's single-resource binding doesn't apply.

🎯 Say this in the interview — the exact lines to land

"If the caller is an Azure resource, use Managed Identity — Azure creates and rotates the credential for you, so there's nothing to manage. Service Principal is for callers outside Azure: a standalone identity with a secret or certificate you create, store, and rotate yourself."

  • Managed Identity → use whenever the caller is an Azure resource — no credential to manage at all.
  • Service Principal → use when the caller isn't Azure itself — a CI/CD pipeline, an on-prem app, another cloud.
  • CI/CD exception → a pipeline running outside Azure still needs a Service Principal, even in an all-Azure architecture.
  • Rotation → Managed Identity's credential rotates itself — a Service Principal's secret rotation is on you.
📖 Explanation ▾

A Service Principal is a standalone application identity in Entra ID with its own credential — a secret or a certificate — that you create, store, and rotate. Because the credential is just a value someone can hold, a Service Principal can authenticate from anywhere that can safely store that credential, including code running outside Azure entirely.

A Managed Identity is an identity Azure creates and rotates for you, tied directly to a specific Azure resource — an App Service, a Function, a VM. There's no credential to type into config or a pipeline secret store, because there's no credential to hold in the first place. The tradeoff is scope: a Managed Identity only works from that one bound resource, so it can't help a caller that isn't running inside Azure.

💻 See the code ▾
C# 
var credential = new DefaultAzureCredential(); // ✅ no secret anywhere in this code
var client = new SecretClient(keyVaultUri, credential);
// on the deployed resource, this resolves to its own Managed Identity

Same line of code works locally (falls back to your dev credentials) and in Azure — it just picks up that resource's Managed Identity there.

Azure CLI 
az ad sp create-for-rbac --name deploy-pipeline-sp \
  --role contributor \
  --scopes /subscriptions/<sub-id>/resourceGroups/rg-demo
// ❗ returns a client secret you must store safely — this IS the credential

This command hands back a real secret — someone (or a pipeline vault) now owns storing and rotating it.

🌍 Real-world example ▾

Scenario: a GitHub Actions pipeline deploys code to Azure. GitHub's runners aren't Azure resources, so the pipeline authenticates with a Service Principal — there's no Azure resource for a Managed Identity to attach to. Once the deploy finishes, the App Service that's now running is an Azure resource, so it reaches Key Vault at runtime using its own Managed Identity instead — no secret for either the pipeline's target or the running app to leak.
