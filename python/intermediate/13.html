A build backend exists because setup.py being executable code is itself a security and reproducibility problem

⚠️ Common Trap

"Just install the latest — it'll be fine." Skipping version pins works right up until an unrelated dependency ships a breaking change, and a production deploy starts failing (or silently behaving differently) with zero code changes on your side.

🔄 Likely Follow-up

"Package vs. module?" A module is a single .py file; a package is a directory of modules — with an __init__.py, or as a namespace package — grouped under one importable name.

🎯 Say this in the interview — the exact lines to land

"pyproject.toml is the modern, standardized replacement for the old setup.py/requirements.txt sprawl — a build backend like setuptools or poetry reads its [build-system] table and turns the source tree into an installable package. I'd always pin or lock dependencies for production so every install resolves to the exact same versions."

  • venv → one isolated Python + package set per project — no interference with the system Python or a sibling project's venv.
  • pip install → installs into whichever env is active — always confirm the right one is activated first.
  • Always pin or lock dependencies for production — an unpinned "latest" install can break with zero code changes on your side.
  • A version conflict gets caught by pip's resolver (or fails outright) — the fix is a lockfile or a narrower, compatible version range.
  • module = one file, package = a directory of modules grouped under one import name.
📖 Explanation ▾

A virtual environment (venv) is an isolated Python installation plus its own package set, scoped to one project. Two projects on the same machine can depend on different — even conflicting — versions of the same library without stepping on each other or on the system Python. pip install always installs into whichever environment is currently active, which is exactly why "which venv am I in" is the first thing to check when an import behaves unexpectedly.

requirements.txt is a flat list of dependencies — pinned or not — and has been the standard for years, but it has no standard place to declare how a project should actually be built or configured. pyproject.toml (PEP 518/621) is the modern, single config file for a project's build system, dependencies, and tool settings, replacing the old setup.py + setup.cfg + requirements.txt sprawl. A build backend — setuptools, poetry, hatch — is the tool named in pyproject.toml's [build-system] table that actually knows how to turn a source tree into an installable package. That's the whole point of moving away from a bare setup.py: setup.py is arbitrary, executable Python code that runs just to install a package, while pyproject.toml is a declarative description a backend reads — safer and more reproducible.

A dependency conflict happens when two packages need incompatible versions of the same shared dependency. pip's resolver either fails outright or, on older pip versions, silently installs an incompatible combination. The real fix is pinning more carefully, or using a lockfile (poetry.lock, compiled requirements from pip-tools, etc.) so every install — yours, CI's, production's — resolves to the exact same versions.

💻 See the code ▾
requirements.txt 
requests==2.31.0
flask>=2.0,<3.0

A flat list — no standard place to declare a build backend or tool settings; those still need separate files.

TOML 
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"          # reads this file, no code runs

[project]
name = "my-service"
dependencies = ["requests==2.31.0"]

One file: the [build-system] table names the backend that reads it — nothing here is executable, unlike a bare setup.py.

🌍 Real-world example ▾

Two microservices on the same host each need a different major version of the same library — one hasn't been upgraded off an old client SDK yet, the other already moved on. Two separate venvs (or, one level further, two separate containers) let both run side by side on that one machine with zero version conflict — that isolation is the entire reason venvs exist.
