Re-renders — what state, props, and context actually trigger

"What actually causes a React component to re-render, and does a parent re-rendering always cascade to its children?"

Why it matters ▾
⚙️ Render Phase
❗ ProblemComponent functions have to run and get diffed against the previous tree before React knows what actually changed — if that work touched the real DOM immediately, React could never safely pause, discard, or redo it for a newer update.
✅ SolutionThe render phase keeps that work purely in memory — running your component function(s) and diffing the result — so React is free to pause, throw it away, or redo it, since nothing has touched the real DOM yet.
RecallRender phase = pure and interruptible — builds and diffs in memory, DOM untouched.
🔒 Commit Phase
❗ ProblemIf applying a diffed result to the real DOM could be interrupted halfway through, the page could end up stuck showing a mix of old and new UI.
✅ SolutionThe commit phase applies that diff to the real DOM and runs layout effects synchronously, then regular effects after paint — once it starts, it runs to completion, never stopping partway.
RecallCommit phase = writes to the real DOM synchronously — once started, it finishes.
🔥 Easy interview recall

Parent re-renders → children re-render too, by default — React.memo is what breaks that cascade, not the other way around.

Think: memo is the exception you opt into, not the default behavior.

🔍 What each one actually does — the real mechanic, not just the label

"Render" and "commit" get used almost interchangeably in casual talk, but React treats them as two genuinely different phases with different rules. These two small diagrams show what each phase actually does.

⚙️ Render Phase & 🔒 Commit Phase
⚠️ Common Trap

"A component only re-renders when its own state, props, or context changes — a parent re-rendering shouldn't affect a child whose own props didn't change." By default it does — a parent re-rendering cascades to re-render every child too, even one whose own props are unchanged; React.memo is the specific, opt-in tool that breaks that cascade, not the default behavior.

🔄 Likely Follow-up

"Does changing a ref cause a render?" No — mutating ref.current is completely invisible to React's render-scheduling; it's a plain mutable value living outside the render cycle entirely, by design.

🎯 Say this in the interview — the exact lines to land

"A component re-renders on its own state, props, or context change — and by default, a parent's re-render cascades to every child too, even one with unchanged props, unless that child is wrapped in React.memo."

  • state / props / context change → each one alone is enough to trigger a render.
  • Parent re-renders → children cascade too, by default.
  • React.memo → the opt-in that skips an unaffected child's re-render.
  • Render phase → computes the next UI, pure and interruptible Commit phase → applies it to the DOM, synchronous

  • Mutating ref.current → never triggers a render, invisible to React's scheduler.
📖 Explanation ▾

A component re-renders for exactly three reasons: its own state changes, the props it receives change, or a context value it reads changes. Any one of those alone is enough — nothing else causes a render.

By default, a parent re-rendering also re-renders every child underneath it, even a child whose own props stayed exactly the same — React re-runs the whole subtree unless told otherwise. React.memo is that "told otherwise": it wraps a component and skips its re-render whenever its props haven't changed.

Once React knows what should render, reconciliation is the diffing step that compares the new result to the previous one to work out what the real DOM actually needs to change. That work happens in two phases: render computes the next UI — pure, and safe for React to pause or throw away — then commit applies the result to the real DOM and runs effects, synchronously, without stopping partway.

💻 See the code ▾
JSX 
function Child({ label }) {
  console.log("Child rendered");  // runs every time
  return <p>{label}</p>;
}

function Parent() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Tick</button>
      <Child label="Same every time" />  // re-renders anyway
    </div>
  );
}

Parent re-renders on every click — Child cascades with it, even though label never changes.

JSX 
const Child = React.memo(function Child({ label }) {
  console.log("Child rendered");  // only logs when label changes
  return <p>{label}</p>;
});

Same Child, wrapped in React.memo — it now skips its re-render because label stayed the same.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your parent's state changes, and you assumed a child whose own props never changed would skip re-rendering

By default, React re-renders every child underneath a re-rendered parent, even one whose own props stayed exactly the same — the cascade only stops for a child specifically wrapped in React.memo, so this is the default behavior, not an edge case.

RememberParent re-renders → every child cascades too, by default.
2 You wrap one specific child in React.memo because it re-renders too often for no visible reason

React.memo skips that one child's re-render whenever its own props haven't changed — its siblings that aren't wrapped still cascade normally, so only the memoized child opts out.

RememberReact.memo blocks the cascade for just the child it wraps — every other child still re-renders.
3 You mutate ref.current directly and expect the UI to update

Mutating ref.current is completely invisible to React's render-scheduling — it's a plain mutable value living outside the render cycle, so changing it never triggers a re-render on its own.

RememberMutating a ref never triggers a render — it's invisible to React's scheduler.
🌍 Real-world example ▾

A fire drill clears an entire office floor. Every desk (child) evacuates when the alarm (parent) goes off, whether or not anything on that particular desk changed. One desk with a "do not disturb unless something on MY desk changed" sign — React.memo — is the one exception that gets to sit out the drill if its own props never moved.
