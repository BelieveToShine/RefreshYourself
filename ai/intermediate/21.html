Beyond MCP — agent-to-tool, agent-to-agent, or screen?

"How do MCP and agent-to-agent protocols differ, and when would an agent drive a GUI instead of an API?"

Why it matters ▾
🧭 Beyond MCP
❗ ProblemNot everything an agent needs is a clean tool. Some skills live in another team's agent, and some software has no API at all — only a screen.
✅ SolutionMatch the link to the target: MCP for tools and data, an agent-to-agent protocol (like A2A) for handing work to a peer agent, and computer use — a see-and-click loop — only as the last resort when no API exists.
RecallTool → MCP. Peer agent → A2A. No API → drive the screen, last.
🔥 Easy interview recall

MCP = agent → tool; A2A = agent ↔ agent; computer use = agent → screen, last resort.

Think: A real API or MCP tool exists → use it Another agent owns the skill → delegate to it Only a screen exists → click, sandboxed and supervised

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A2A is just MCP version 2." They solve different problems. MCP plugs tools and data into an agent; an agent-to-agent protocol lets agents that you don't control talk to each other. You can use both in one system.

🔄 Likely Follow-up

"How would you make a GUI-driving agent safe?" Run it in a sandbox or disposable machine, give it least privilege, log every step, and ask a human before anything irreversible. What is on the screen can carry prompt injection, so treat it as untrusted.

🎯 Say this in the interview — the exact lines to land

"MCP connects an agent to tools and data; an agent-to-agent protocol like A2A is about agents talking to other agents; and computer use lets an agent operate a screen when there's no API. I reach for them in that order — a real API or MCP tool first, a peer agent next, and a sandboxed GUI agent only as a last resort."

  • MCP → agent-to-tool: a standard way to plug tools and data into an agent.
  • A2A → agent-to-agent: lets agents from different teams or vendors find each other and hand over tasks. It is young — check its current standing before relying on it.
  • Computer use → the model looks at screenshots and clicks or types in a loop; the last resort when no API exists.
  • Limits → slower, brittle when the screen layout changes, and every click can go wrong.
  • Safety → sandbox it, least privilege, human approval before anything irreversible.
📖 Explanation ▾

MCP (see MCP) is about agent → tool: it gives an agent a standard way to discover and call tools and data. Agent-to-agent protocols, such as A2A, are about agent ↔ agent: one agent finds another agent (A2A uses a published description of what an agent can do), hands it a task, and gets a result back, without seeing how the other agent works inside. A2A was announced in 2025 and the space is moving fast, so check the current spec and who supports it before you quote it as settled.

Inside one codebase you rarely need a protocol — the multi-agent patterns are just function calls. A protocol earns its place across a boundary: different teams, vendors or frameworks. For the plain mechanics of a model calling a function, see Function / Tool Calling.

Computer use gives a model a screen: it takes a screenshot, decides where to click or type, acts, and looks again. It is useful for old software with no API. It is also slow and fragile — a moved button can break it — so prefer an API whenever one exists. Availability and status differ by provider, so check current docs.

🌍 Real-world example ▾

An expense agent must file a claim in a legacy desktop app that has no API. It runs a sandboxed screen-driving agent and pauses for a human click before the final submit — while for flight prices it simply asks a travel agent that another team owns.
