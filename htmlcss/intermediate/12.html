transition vs. animation — and the CSS choice that decides whether the browser redoes Layout on every frame

"What's the difference between a CSS transition and an animation, and why does animating transform tend to be cheaper for the browser than animating top or left?"

Why it matters ▾
  • "Why is my animation janky?" is a real, common interview and real-world question — the usual answer is which property is being animated, not the easing curve.
  • Knowing when to reach for a triggered transition versus a self-running animation comes up in almost every component-styling discussion (hover states vs. loading spinners).
  • prefers-reduced-motion is a genuine accessibility requirement now, not a nice-to-have, and interviewers focused on accessibility ask about it directly.
🔥 Easy interview recall

transition → reacts to a property change (like :hover)

animation → runs itself, via @keyframes — no trigger needed

Think: transform / opacity → cheap, usually skips Layout top / left / width → forces Layout on every frame

🧠 Visual Mental Model — same visual move, two very different costs
⚠️ Common Trap

Smoothness isn't just about the easing curve. Animating left with a perfect ease-in-out can still look janky, because it's forcing Layout on every frame — the same visual move done with transform usually doesn't.

🔄 Likely Follow-up

"So should I always animate with transform instead of top/left?" For anything moving every frame, generally yes — same visual result, meaningfully cheaper to compute. It's a well-established rule of thumb, not a guarantee on every browser or element, but it's the right default to reach for.

🎯 Say this in the interview — the exact lines to land

"A transition is an implicit animation between two states that fires when a property actually changes, like on :hover. An animation is explicit — I define stages with @keyframes, and it can run on its own, loop, or move through several stages without any trigger at all. For performance, I animate transform and opacity wherever I can, because those changes typically skip the browser's Layout step, while animating top, left, width, or margin forces Layout — and often Paint — to run again on every frame, which is what actually causes jank. I also wrap animation in a prefers-reduced-motion media query so it respects that accessibility setting."

  • transition → fires on a property change — one trigger, two states.
  • animation → runs itself via @keyframes — can loop, no trigger needed.
  • transform / opacity → typically skip Layout — cheap to animate every frame.
  • top / left / width / margin → force Layout every frame — the real cause of jank.
  • prefers-reduced-motion → respect it — a real accessibility requirement, not polish.
📖 Explanation ▾

A transition is implicit — it needs an actual property change to fire, like a class toggle or :hover, and it only interpolates between two states: whatever the value was, and whatever it becomes. An animation is explicit: @keyframes names two or more stages by percentage (or from/to), and once the animation shorthand is applied, it runs on its own — no property change required — and can repeat forever with animation-iteration-count: infinite, which is exactly how a loading spinner keeps spinning.

A timing function (ease, linear, ease-in-out, or a custom cubic-bezier()) controls the rate of change across the duration — not just the start and end values. linear moves at a constant speed; ease-in-out starts and ends slowly with a faster middle, which is why it usually reads as more natural. prefers-reduced-motion is a media feature that reflects a system-level setting some users turn on for motion-sensitivity or vestibular reasons — checking for it with @media (prefers-reduced-motion: reduce) and cutting or shortening animation there is a real accessibility requirement, not a finishing touch.

💻 See the code ▾
CSS 
.card {
  /* transition: property duration timing-function */
  transition: transform .2s ease-in-out;
}
.card:hover {
  transform: translateY(-4px);  /* fires only because :hover changed */
}

Nothing moves until the property actually changes — remove the :hover, and this transition never runs.

CSS 
/* @keyframes names the stages — no trigger involved */
@keyframes spin {
  from { transform: rotate(0deg); }
  to   { transform: rotate(360deg); }
}
.spinner {
  animation: spin 1s linear infinite;  /* starts by itself, loops forever */
}

No property change needed — as soon as .spinner exists on the page, it starts spinning, and infinite keeps it going.

CSS 
@media (prefers-reduced-motion: reduce) {
  .spinner {
    animation: none;  /* ✅ honors the user's system setting */
  }
}

This checks the reader's own OS-level "reduce motion" setting — when it's on, this turns the spinner's animation off instead of ignoring the preference.

CSS 
/* ❌ forces Layout on every frame */
.panel { transition: left .3s; }
.panel.open { left: 0; }

/* ✅ same visual move, usually skips Layout */
.panel { transition: transform .3s; }
.panel.open { transform: translateX(0); }

Both slide the panel to the same place — the second version just doesn't make the browser recompute the page's layout to get there.

🌍 Real-world example ▾

A dimmer switch vs. a wind-up toy. A transition is a dimmer switch — it only moves when you actually push it (a property changes), and it settles between exactly two positions. An animation is a wind-up toy — once you set it going, it runs through its own sequence on its own, no one has to keep touching it.

On the performance side: a slide-in navigation menu that feels janky on a low-end phone is almost always animating left or margin-left. Switching that same slide to transform: translateX() usually fixes the stutter without changing a single visual pixel of the design.
