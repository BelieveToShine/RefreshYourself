orElse() vs. orElseGet() vs. orElseThrow() — eager, lazy, or an exception

"What's the difference between orElse() and orElseGet(), and why does it matter for performance?"

Why it matters ▾
⏱️ Eager vs. Lazy Fallbacks
❗ ProblemWriting orElse(computeExpensiveDefault()) looks perfectly normal, but it runs computeExpensiveDefault() on every single call — even when the Optional already had a value and that fallback was never actually needed.
✅ SolutionorElse(value) always evaluates its argument eagerly; orElseGet(supplier) only invokes its Supplier lambda when the Optional is actually empty — lazy, and the right choice whenever the fallback is expensive.
RecallorElse() always runs. orElseGet() runs only if empty.
🔥 Easy interview recall

orElse(value) → always evaluates, even if present

orElseGet(supplier) → only if empty, lazy

orElseThrow(...) → throws if empty

Think: orElse() pays upfront no matter what. orElseGet() only pays if it has to. orElseThrow() walks away empty-handed, loudly.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

orElse(computeExpensiveDefault()) only computes the default when it's actually needed. It doesn't — Java evaluates a method's arguments before the method itself runs, so computeExpensiveDefault() executes on every call, present or not; only passing a Supplier to orElseGet() defers that call.

🔄 Likely Follow-up

"What's the difference between orElseThrow() with no arguments and orElseThrow(supplier)?" The no-argument form throws a default NoSuchElementException with a generic message. Passing a Supplier<? extends Throwable> lets the caller throw a specific, meaningful exception type with its own message instead.

🎯 Say this in the interview — the exact lines to land

"orElse(value) always eagerly evaluates its argument, even when the Optional is present — wasted work if that argument is expensive. orElseGet(supplier) only calls its Supplier lambda when the Optional is actually empty. orElseThrow() throws a default or supplied exception when there's nothing there."

  • orElse(value) → always evaluates eagerly, fine only for cheap constants.
  • orElseGet(supplier) → lazy, runs only if empty — correct for expensive fallbacks.
  • orElseThrow() → throws instead of falling back, default or custom exception.
  • orElse(expensiveCall()) → a very common accidental performance bug.
📖 Explanation ▾

Java evaluates a method call's arguments before it makes the call — that rule applies to orElse(x) like any other method, so whatever expression is passed as x runs immediately, regardless of whether the Optional ends up using it. That's exactly why orElse() is eager: there's no way to pass it an unevaluated expression.

orElseGet() and orElseThrow() both sidestep that by taking a lambda instead of a value — a Supplier isn't run until something explicitly calls it, so the Optional only invokes it after confirming it's actually empty. The fallback computation or the exception is described upfront, but only runs on demand.

💻 See the code ▾
Java 
Optional<User> found = repo.findById(id);   // present
User user = found.orElse(fetchDefaultUser());
                           // ❌ fetchDefaultUser() runs every time, even here

The argument is evaluated before orElse() even gets called — there's no way around it.

Java 
User user2 = found.orElseGet(() -> fetchDefaultUser());
                           // ✅ the lambda only runs if found was empty

Wrapped in a Supplier — nothing runs until orElseGet() decides it has to.

Java 
User user3 = found.orElseThrow(() ->
    new UserNotFoundException(id));   // ✅ throws only if empty

Absence here is treated as a real error, not something to quietly paper over with a default.

🧭 Use Cases — recognize these when they happen to you ▾
1 The fallback is a cheap constant, like "Guest"

This is the #1 scenario you'll actually run into: a literal or an already-computed value costs nothing extra to evaluate, so orElse() is simpler and just as fast as orElseGet() here.

RememberFallback is already cheap/computed → orElse() is fine, no need to complicate it.
2 The fallback needs a database call or real computation

A fallback that hits a database, calls a remote service, or does real computation must never run unconditionally — orElseGet(() -> queryDefault()) is what keeps that call from firing on every present value.

RememberFallback is expensive → always orElseGet(), never orElse().
3 Absence should actually be an error, not quietly papered over

Falling back to null (or a silently wrong default) just moves a real "this record must exist" bug further down the call stack, where it surfaces as a confusing NullPointerException. orElseThrow() surfaces the real problem immediately, at the point where it's actually known.

RememberA missing value that's really a bug → orElseThrow(), don't mask it with a default.
🌍 Real-world example ▾

A profile page falls back to a freshly generated avatar image when a user has none. Generating that avatar is real work (rendering, maybe a remote call) — writing avatar.orElseGet(this::generateAvatar) instead of orElse(generateAvatar()) is the difference between generating it only for the users who actually need it, and generating it for every single profile view.
