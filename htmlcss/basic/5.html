The Cascade — who actually wins when two rules disagree?

"What is a CSS rule, and how does the browser decide which rule wins when two rules conflict?"

Why it matters ▾
  • Every "why isn't my style applying" moment traces back to this exact order of checks — it's almost never a CSS bug, just a cascade step nobody traced yet.
  • Sets up the vocabulary — rule, cascade, specificity, source order — that every later CSS topic on this site leans on, including Selectors right after this page and Specificity's own deeper page later.
  • A near-guaranteed opener, or the "walk me through it" warm-up before a CSS interview moves on to layout.
🔥 Easy interview recall

1) Importance → !important cuts the line first

2) Origin → author beats the browser's own default

3) Specificity → the more specific selector wins

4) Source order → whichever rule was written later wins the tie

Think: !important first, then origin, then specificity, then order written — and a plain inline style="" jumps ahead of all of it except !important.

⚠️ Common Trap

Higher specificity doesn't automatically win. Importance and origin are checked before specificity ever comes up — an !important declaration, or even a plain inline style="" attribute, can already have decided the winner first.

🔄 Likely Follow-up

"So does an inline style always beat a stylesheet rule?" Yes, unless that stylesheet rule uses !important — a normal inline style="" attribute outranks every ordinary author-stylesheet rule no matter how specific its selector is, but an author rule marked !important still wins over a plain inline style.

🎯 Say this in the interview — the exact lines to land

"CSS resolves a conflict in a fixed order — importance first (!important), then origin (author beats the browser's own defaults), then cascade layers if the page uses @layer, then specificity, then source order as the final tie-break. Inline styles outrank every normal author rule too, short of !important."

  • Importance first — an !important declaration jumps every other check.
  • Origin second — your own stylesheet beats the browser's built-in defaults automatically.
  • Specificity third — the deeper math for this lives on its own page; here, just know it's step three, not step one.
  • Source order last — when everything else ties, whichever rule is written later in the stylesheet wins.
  • Inline beats normal author rules — a style="" attribute outranks any selector-based rule in its own origin, short of !important.
📖 Explanation ▾

A CSS rule is a selector (what it targets) plus a declaration block (the property: value; pairs inside the curly braces). The browser reads every stylesheet it's given — its own built-in defaults, then yours — and turns them into a tree of matched rules called the CSSOM (CSS Object Model), the CSS-side counterpart to the DOM tree an HTML page becomes. This page's job is what happens next: which rule actually wins. For the fuller DOM + CSSOM → Render Tree picture, see Browser Rendering.

The cascade is the fixed order the browser checks every time two rules try to set the same property on the same element: importance (does either side carry !important?), then origin (your stylesheet beats the browser's user-agent defaults, with a user's own stylesheet sitting in between), then cascade layers if the page declares any with @layer, then specificity (the full calculation for this has its own page — see Specificity), and finally source order — whichever rule was written later wins any remaining tie. An inline style="" attribute skips specificity entirely: it outranks every ordinary author-stylesheet rule no matter how specific the selector is, though an author rule marked !important still beats it.

💻 See the code ▾
CSS 
.hero-text {              /* selector */
  font-size: 1.2em;      /* declaration: property: value; */
}

A rule is just those two pieces — a selector picking a target, and a declaration block saying what to do to it.

CSS 
.lead      { font-size: 14px; }   /* written first */
.hero-text { font-size: 1.2em; }  /* written later — same specificity, this one wins */

Both are single-class selectors — tied specificity — so the browser falls back to source order, and the later rule wins.

CSS 
.lead      { font-size: 14px !important; }  /* now THIS wins, no matter what's written after it */
.hero-text { font-size: 1.2em; }

!important is checked before specificity or order — adding it to .lead flips the winner back, even though .hero-text is written later.

🌍 Real-world example ▾

Think of a company memo chain: the building's default policy (the browser's own default) gets overridden by your team's own memo (your stylesheet), which loses to a director's "URGENT — overrides everything" email (!important) — and if two memos are equally specific, whichever one landed in the inbox last is the one everyone actually follows.
