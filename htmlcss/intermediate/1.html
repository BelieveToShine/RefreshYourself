Specificity — which rule wins, and why

"How is CSS specificity actually calculated, and which rule wins if #app .button and .button both set a different color on the same element?"

Why it matters ▾
  • Almost every "why did my CSS get overridden" bug traces back to a specificity number nobody actually calculated — not a browser bug.
  • It's the near-guaranteed follow-up right after the cascade-order question — interviewers love asking you to work the math out live on a real selector pair.
  • Knowing the real tier-by-tier math is what separates memorizing "IDs beat classes" from being able to solve an actual selector conflict on the spot.
🔥 Easy interview recall

1) Inline style → beats every selector, no contest

2) ID → beats any number of classes combined

3) Class / attribute / pseudo-class → beats any number of elements combined

4) Element / pseudo-element → weakest tier, only settles ties among themselves

Think: a hundred chained div selectors still lose to one single .button.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

More selectors chained together doesn't mean higher specificity. Ten classes chained onto one selector (.a.b.c.d.e.f.g.h.i.j) are still just class-tier — a single #id selector still outranks all ten combined, because specificity compares tier by tier, not by total selector count.

🔄 Likely Follow-up

"Does :not() or an attribute selector like [type="text"] add to the specificity score?" An attribute selector counts in the same tier as a class. :not() itself adds nothing, but whatever selector is written inside it still counts normally — :not(.btn) still counts as one class.

🎯 Say this in the interview — the exact lines to land

"CSS specificity is a four-part score — inline style, then ID count, then class/attribute/pseudo-class count, then element/pseudo-element count — compared left to right. The first tier where the counts differ wins outright, so #app .button (one ID, one class) beats .button (one class only) no matter which was written first, though !important, origin, and cascade layers are all checked before specificity even runs."

  • Tier beats count — one #id outranks any number of chained classes; specificity never just adds selectors up.
  • Worked example — #app .button (ID+class) beats .button (class only), regardless of source order.
  • Inline beats everything — a plain style="" attribute outranks any selector's specificity entirely.
  • Not the whole cascade — !important, origin, and layers are checked first; specificity only decides once those are all tied.
  • Attribute & pseudo-class = class tier — [type="text"] and :hover count the same as a class, not lower.
📖 Explanation ▾

Specificity is the score the browser gives a selector so it can compare it against another one competing for the same property. It isn't one number — it's counted in tiers: how many ID selectors, how many class, attribute, or pseudo-class selectors, and how many element or pseudo-element selectors appear in the selector text (a plain inline style="" attribute sits in its own tier above all three). The browser compares tier by tier, left to right — the first tier where the counts differ decides the winner outright; it never adds every selector up into one total. That's why an entire tier of lower-ranked selectors, chained together however many times, can never outscore a single selector one tier higher.

Take #app .button { color: red; } against .button { color: blue; }. #app .button scores one ID and one class; .button scores zero IDs and one class. They tie on classes, but #app .button has an ID and .button doesn't — the ID tier decides it immediately, so #app .button wins and the element renders red, regardless of which rule appears first or last in the stylesheet.

Specificity is only one step in a bigger resolution order, though: importance (!important), origin, and cascade layers are all checked before specificity ever runs, and source order still breaks a genuine specificity tie afterward. A single !important on the losing rule flips this exact example around, no matter how the specificity math comes out. See CSS Fundamentals & Cascade for the full order this page fits inside.

💻 See the code ▾
CSS 
#app .button { color: red; }   /* 1 ID + 1 class */
.button      { color: blue; }  /* 1 class only    */
/* → red wins: ID tier beats class tier, no tie to break */

Specificity decides this one outright — source order (which rule is written first) never even gets checked.

CSS 
.a.b.c.d.e.f.g.h.i.j { color: blue; }  /* 10 classes chained */
#app                 { color: red; }   /* 1 ID               */
/* → red still wins: ID tier outranks class tier at any count */

Ten chained classes never climb into the ID tier — specificity compares tiers, not the total number of selectors written.

CSS 
/* <button id="save" class="btn" style="color: green;"> */
#save.btn { color: red; }  /* any specificity, still loses */
/* → green wins: inline sits above the whole specificity scale */

Inline isn't "higher specificity" — it's checked in an earlier cascade step altogether, so specificity math never even runs against it.

🌍 Real-world example ▾

Think of building-access badges. A master key (an ID selector) opens more doors than any number of department badges (classes) stacked together — no matter how many department badges someone piles on, they never out-rank one master key. Two department badges only settle it between themselves when no master key is in play at all.
