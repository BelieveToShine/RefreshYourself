Equality Comparers and Custom Equality — how GroupBy/Distinct/Join decide "equal"

"How do Distinct, GroupBy, Join, and the set operators decide that two elements are 'equal'?"

Why it matters ▾
⚙️ Default Comparer
❗ ProblemCalling Distinct() on a list of a custom reference type with no overridden Equals silently returns duplicates you expected removed — two objects holding identical data don't collapse into one.
✅ SolutionWithout an explicit comparer, these operators fall back to EqualityComparer<T>.Default, which for a reference type with no override means reference equality — "same object," not "same data" — so you know exactly what to fix.
RecallNo override, no comparer → compares identity, not content.
🧩 Custom IEqualityComparer<T>
❗ ProblemA single call needs "equal" to mean something specific to it — a case-insensitive string match, or comparing only one property — without changing the type's own Equals everywhere else it's used.
✅ SolutionPass an explicit IEqualityComparer<T> (or use a *By key-selector overload like DistinctBy) to swap the comparison rule just for that one call.
RecallCustom comparer → equality rule for this call only.
🔥 Easy interview recall

No comparer passed → EqualityComparer<T>.Default

No Equals override → reference equality

Think: Two Product objects, same Sku — Distinct() keeps both unless you override Equals or pass a comparer.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Distinct() "just working" on your own class is a myth unless you've overridden Equals. It doesn't know which properties define "the same" — without an override or explicit comparer, two instances with identical data are still two different objects to EqualityComparer<T>.Default.

🔄 Likely Follow-up

"Is DistinctBy the same thing as passing a custom comparer?" For a single-property key, yes — same result, but DistinctBy needs no comparer class, just a key selector. A custom IEqualityComparer<T> is still needed for multi-property or non-trivial equality logic a key selector alone can't express.

🎯 Say this in the interview — the exact lines to land

"Distinct, GroupBy, Join, and the set operators all fall back to EqualityComparer<T>.Default — which falls back to Equals/GetHashCode — unless I pass an explicit IEqualityComparer<T>. For a reference type with no overridden Equals, that default is reference equality, not value equality."

  • Default comparer → reference equality for unoverridden reference types, never "same data."
  • Value types → default already compares field values, no surprise there.
  • Explicit IEqualityComparer<T> → swaps the rule for one call only, type untouched.
  • *By overloads → simplest fix for a single-key comparison, no comparer class needed.
📖 Explanation ▾

Every operator that needs to decide "are these two the same" — Distinct, GroupBy, Join, Union, Intersect, Except — takes an optional IEqualityComparer<T> parameter. Leave it out, and they all resolve to the same place: EqualityComparer<T>.Default, which in turn calls the type's own Equals and GetHashCode.

For a reference type with no overridden Equals, the inherited behavior from object is reference equality — "is this literally the same instance." Two Product objects built from the same database row on two different calls are, as far as the default comparer is concerned, as unrelated as two completely different products. Records and value types don't have this problem: records generate a value-based Equals automatically, and structs already compare fields by default.

To change the rule for one specific call without touching the type everywhere else it's used, pass a custom IEqualityComparer<T> (implementing Equals and GetHashCode yourself), or use a *By overload — DistinctBy, UnionBy, ExceptBy, IntersectBy — which takes a key selector instead and needs no comparer class at all for the common single-key case.

💻 See the code ▾
C# 
class Product { public string Sku; }   // no Equals override

var items = new[] { new Product { Sku = "A1" }, new Product { Sku = "A1" } };
Console.WriteLine(items.Distinct().Count());   // ❌ 2 — "duplicates" not removed

Same Sku, but two different objects — the default comparer sees no duplicate.

C# 
class SkuComparer : IEqualityComparer<Product>
{
    public bool Equals(Product a, Product b) => a.Sku == b.Sku;
    public int GetHashCode(Product p) => p.Sku.GetHashCode();
}

items.Distinct(new SkuComparer()).Count();   // ✅ 1 — now compared by Sku

A custom comparer swaps the equality rule just for this call.

C# 
items.DistinctBy(p => p.Sku).Count();   // ✅ 1 — same result, no comparer class needed

DistinctBy is the simpler fix for a single-property key.

🧭 Use Cases — recognize these when they happen to you ▾
1 Deduplicating value objects or records

Calling Distinct() on a list of record values works out of the box, because records generate a value-based Equals automatically — the default comparer already does exactly what you'd expect, no custom comparer needed.

Rememberrecord → the default comparer already compares values.
2 Case-insensitive string comparison for one call

Passing StringComparer.OrdinalIgnoreCase to Distinct() treats "Admin" and "admin" as the same role name for that one call, without changing how strings compare anywhere else in the codebase.

RememberBuilt-in IEqualityComparer<T> implementations exist — check before writing your own.
3 GroupBy on a plain POCO with no override

Grouping directly on a POCO instance (instead of a property) with no overridden Equals produces one group per object, since every instance is "unequal" to every other — the fix is grouping by a specific key property, not the whole object.

RememberGroup by a key property, never by a whole unoverridden reference type.
🌍 Real-world example ▾

A product catalog calls Distinct() on a list of Product POCOs expecting duplicates removed by SKU. It does nothing, because Product has no Equals override — switching to DistinctBy(p => p.Sku) (or passing a custom comparer) fixes it without touching the class itself.
