Pattern matching — two ways to stop re-checking characters you already matched

How would you search for a pattern inside a large text efficiently — what's wrong with the naive way, and how do KMP and Rabin-Karp fix it?

Why it matters ▾
  • This is a Deep Dive topic, not core interview prep — it's split out from Bit Manipulation specifically because the two "are conceptually unrelated and interviewers test them differently," per this track's own scoping decision.
  • The naive character-by-character search looks "fine" on a whiteboard-sized example, which is exactly why interviewers use it to check whether a candidate notices the cost only shows up at real scale (a large document, a genome-scale string).
  • Worth knowing the name and the core idea of KMP and Rabin-Karp exist for this exact problem — not worth memorizing either one's implementation line by line.
🔥 Easy interview recall

Naive search → O(n·m), re-checks characters from scratch

KMP → O(n+m), never re-checks a matched character

Rabin-Karp → hash + rolling hash, verify on a match

Think: KMP remembers the pattern's own overlap so it never looks back. Rabin-Karp fingerprints each window and only double-checks when two fingerprints agree.

🧠 Visual Mental Model — same mismatch, two different reactions
⚠️ Common Trap

"Strings are usually short, so naive search is fine" is the actual mistake being tested. On a genuine large text — a big document, a genome-scale string — O(n·m) cost is real, and recognizing that a specialized algorithm exists for exactly this case is the interview signal, not reciting KMP's failure-function construction from memory.

🔄 Likely Follow-up

"How is Rabin-Karp's rolling hash different from a regular hash function?" A regular hash has no relationship between overlapping-but-different strings — you'd hash each window from scratch. A rolling hash is built specifically so shifting the window by one character updates the hash in O(1), instead of rehashing the whole window.

🎯 Say this in the interview — the exact lines to land

"Naive substring search is O(n·m) because it can re-compare characters at every shifted position. KMP gets to O(n+m) by precomputing a failure function on the pattern so it never re-examines a text character it's already matched. Rabin-Karp instead hashes each window with a rolling hash and only does a real character check when two hashes collide."

  • Naive search → O(n·m) worst case — a near-match that fails late forces a lot of re-comparison.
  • KMP → O(n+m), no re-checking — the failure function tells it how far to shift using the pattern's own self-overlap.
  • Rabin-Karp → average close to O(n+m), via a rolling hash that updates in O(1) per window instead of rehashing from scratch.
  • Hash collision risk → Rabin-Karp's real trade-off — always verify a hash match character-by-character before trusting it.
  • Multiple patterns at once → Rabin-Karp extends naturally by comparing against a set of pattern hashes; KMP doesn't as directly.
📖 Explanation ▾

The problem both algorithms solve: given a text and a shorter pattern, find every place the pattern occurs inside the text. The naive approach tries every starting position in the text and, for each one, compares the pattern character by character until it either matches fully or hits a mismatch. That's correct, but a near-match that fails late — many characters in — forces the same kind of comparison work to repeat at the next shifted position, which is what pushes the worst case to O(n·m) (n = text length, m = pattern length).

KMP fixes this by never re-examining a text character it has already matched. Before searching, it precomputes a failure function (also called a partial match table) for the pattern itself — a table that says, for a mismatch after matching some number of characters, exactly how far the pattern can shift without re-checking characters it already knows still line up, based on the pattern's own self-overlapping structure. The result is a single pass over the text, O(n+m) total, with no backtracking on the text side.

Rabin-Karp takes a completely different approach: hash the pattern once, then slide a same-length window across the text, comparing each window's hash to the pattern's hash. The part that makes this fast is the rolling hash — a hash function designed so the next window's hash can be computed in O(1) from the current one, by removing the outgoing character's contribution and adding the incoming one, instead of hashing the whole window again. That's the same "update incrementally instead of recomputing from scratch" idea the Prefix Sum & Difference Array page uses for range sums. Only when two hashes match does Rabin-Karp pay for a real character-by-character check — needed because different strings can, in theory, hash to the same value, the same collision risk the Hash Tables page already covers.

💻 See the code ▾
Python 
def naive_search(text, pattern):
    n, m = len(text), len(pattern)
    for s in range(n - m + 1):
        if text[s:s+m] == pattern:  # re-scans from scratch every position
            yield s

Simple and correct — but each slice comparison can re-walk characters a nearby slice already looked at, which is exactly the O(n·m) cost KMP removes.

Python 
# KMP, sketch — the failure table build itself is intentionally left out here,
# this is the idea, not the derivation (Deep Dive scope)
def kmp_search(text, pattern, lps):
    i = j = 0                      # i: text pointer, j: pattern pointer
    while i < len(text):
        if text[i] == pattern[j]:
            i += 1; j += 1
            if j == len(pattern):
                yield i - j             # ✅ match found, i never moved backward
                j = lps[j - 1]
        elif j > 0:
            j = lps[j - 1]         // shift using the pattern's own overlap
        else:
            i += 1

i only ever moves forward — the failure table (lps) is what lets j jump back without ever re-reading a text character a second time.

Python 
# Rabin-Karp, sketch — rolling hash update, not the full modular-arithmetic derivation
def next_window_hash(old_hash, out_char, in_char, base, mod, high_pow):
    h = (old_hash - ord(out_char) * high_pow) * base + ord(in_char)
    return h % mod   # O(1): drop outgoing char, add incoming char

No rehashing the whole window — just remove one character's contribution and add the new one. When this new hash matches the pattern's hash, then verify character-by-character to rule out a collision.

🌍 Real-world example ▾

Searching for a substring inside a large log file or a DNA sequence is where the naive approach's cost stops being theoretical — a text with millions of characters makes O(n·m) genuinely slow, which is why real text search, editors, and bioinformatics tools use something closer to KMP or Rabin-Karp instead of a plain character-by-character scan.
