Text Blocks (""") — no more escaping every quote

"What problem do text blocks solve, and how is indentation handled?"

Why it matters ▾
📄 Text Blocks
❗ ProblemWriting a multi-line JSON, SQL, or HTML snippet as a regular String means escaping every embedded double quote and concatenating each line with + and \n — noisy, and easy to get wrong.
✅ SolutionText blocks ("""....""", finalized Java 15, JEP 378) let you write the multi-line literal almost exactly as it should look, with incidental leading whitespace stripped automatically based on the closing delimiter's indentation.
RecallText block = write the string as it actually looks — no escaping, no + concatenation.
🔥 Easy interview recall

Text block = "a multi-line string you write as it actually looks."

Think: the closing """'s own indentation is the ruler every line's leading whitespace gets measured against and stripped to.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The closing """'s position controls the stripping, not the first line's. If the closing """ sits further left than intended, extra leading whitespace is removed from every line that didn't need it — moving the closing delimiter changes the string's actual indentation even though no line of the text itself changed.

🔄 Likely Follow-up

"What other 'modern Java' features usually get grouped with text blocks?" Records (Java 16), sealed classes (Java 17), and pattern matching with record patterns (Java 21) are the other headline language features from this era — text blocks is the one usually remembered as "the multi-line string literal."

🎯 Say this in the interview — the exact lines to land

"Text blocks, written with triple quotes and finalized in Java 15, let a multi-line string literal be written without escaping embedded quotes or concatenating lines — the compiler strips incidental leading whitespace automatically, based on where the closing triple quote is indented."

  • Text block → no escaping, no + concatenation for multi-line strings (Java 15).
  • Indentation stripped → measured from the closing """, not the first line.
  • Embedded straight quotes → no longer need escaping inside a text block.
  • Same era as records (16), sealed (17), pattern matching (21) — Java's modern-language-feature push.
📖 Explanation ▾

A text block starts with """ followed immediately by a line break, and ends with a closing """. Everything in between is the string, written as plain text — straight double quotes don't need escaping unless three of them appear in a row, and line breaks are just... line breaks, no \n required.

The compiler decides how much leading whitespace is "incidental" (just there for the source code's own indentation, not part of the string's real content) by looking at the minimum indentation across every line, including the closing """'s own position. That's exactly why moving the closing delimiter changes the result: it's one of the lines the compiler measures against.

💻 See the code ▾
Java 
String json = "{\n" +
    "  \"name\": \"Sam\"\n" +     // ❌ escape every quote, every line
    "}\n";

Every embedded quote and line break needs manual handling.

Java 
String json = """
    {
      "name": "Sam"
    }""";  // ✅ reads exactly like the JSON it represents

The closing """'s column sets how much gets stripped from every line.

🧭 Use Cases — recognize these when they happen to you ▾
1 Embedding a JSON payload in a test

A unit test comparing an API response to an expected JSON body can embed the expected payload as a text block — the literal reads like the JSON itself, instead of a wall of escaped quotes.

RememberExpected JSON/XML in a test → a text block, not escaped strings.
2 Writing a multi-line SQL query inline

A multi-line SELECT with several JOIN clauses reads naturally as a text block, formatted the same way a SQL editor would show it — no line-by-line string concatenation to maintain.

RememberMulti-line SQL inline → a text block keeps it readable.
3 Moving the closing """ without checking the result

Re-indenting code and accidentally moving the closing """ further left silently strips more whitespace than intended from every line — the text content didn't change, but its leading spaces did.

RememberAlways re-check output after moving a closing """.
🌍 Real-world example ▾

A test fixture builds an expected SQL query as a text block, then someone re-indents the surrounding method and the closing """ shifts two spaces left. The test starts failing on a whitespace mismatch alone — the query text is identical, but the stripped indentation changed because the closing delimiter moved.
