Comparable vs. Comparator — one natural order, or as many as you need

"What's the difference between implementing Comparable and passing a Comparator?"

Why it matters ▾
🧬 Comparable
❗ ProblemCollections and sorted structures like TreeSet need some default way to decide "which of these two comes first" without being told separately every time.
✅ SolutionA class implements Comparable<T> and defines compareTo() once — that becomes its single, built-in "natural ordering" that Collections.sort() and sorted collections use by default.
RecallComparable = inside the class, one fixed order.
🧭 Comparator
❗ ProblemThe same list of employees needs to be sorted by name on one screen and by salary on another — a class can only implement Comparable once, so that's not enough orderings.
✅ SolutionA Comparator<T> is a separate object passed into the sort call — write as many as you need, with zero changes to the class, and compose them with thenComparing().
RecallComparator = outside the class, as many orders as you want.
🔥 Easy interview recall

Comparable → inside the class, one natural order

Comparator → outside the class, as many as you need

Think: compareTo() is the class's own opinion. A Comparator is someone else's opinion, handed to the sort call instead.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

You can't have "as many Comparable orderings as you want." A class implements Comparable exactly once, defining a single natural order — any additional ordering has to come from a separate, external Comparator object instead.

🔄 Likely Follow-up

"How do you combine multiple sort keys with a Comparator?" Comparator.comparing(Employee::getDept).thenComparing(Employee::getSalary) — compose comparators instead of writing one giant compareTo() full of nested if/else.

🎯 Say this in the interview — the exact lines to land

"Comparable is implemented by the class itself and defines exactly one natural ordering via compareTo(). Comparator is a separate object passed into a sort call, so you can define as many orderings as you need without touching the class, and compose them with thenComparing()."

  • Comparable → inside the class, one fixed natural order.
  • Comparator → outside the class, as many orderings as you need.
  • Comparator.comparing().thenComparing() → compose multi-key sorts, Java 8+.
  • Same class, two different sort screens → Comparator, not a second compareTo().
📖 Explanation ▾

Comparable<T> is a promise the class makes about itself: "I know how to put myself in order relative to another instance of my own type." compareTo() returns negative, zero, or positive the same way equals() returns a boolean — and because it lives inside the class, there's exactly one of it.

Comparator<T> moves that decision outside the class entirely — it's its own small object implementing compare(a, b), handed to Collections.sort() or list.sort() as an argument. Nothing about the class changes, so you can write a second, third, or tenth Comparator for the exact same type with no conflict.

Since Java 8, Comparator got genuinely composable: Comparator.comparing(Employee::getName) builds one from a method reference, and .thenComparing(...) chains a tiebreaker onto it — which is how real multi-key sorting is written now, instead of a hand-rolled compareTo() full of nested conditionals.

💻 See the code ▾
☕ Java 
class Employee implements Comparable<Employee> {
    int id; String name; double salary;

    public int compareTo(Employee other) {
        return Integer.compare(this.id, other.id); // ✅ one natural order: by id
    }
}

Collections.sort(employees) now sorts by id with no extra argument needed.

☕ Java 
Comparator<Employee> byName = Comparator.comparing(Employee::getName);
employees.sort(byName);            // ✅ sorted by name, Employee untouched

Comparator<Employee> byDeptThenSalary =
    Comparator.comparing(Employee::getDept)
              .thenComparing(Employee::getSalary); // ✅ two keys, composed

Each new Comparator is a separate object — the class never needs a second compareTo().

🧭 Use Cases — recognize these when they happen to you ▾
1 A domain object has one obvious, default order (e.g. an invoice by invoice number)

When there's genuinely one natural order every caller would expect — invoice number, account ID — baking it into compareTo() means every plain sort() call just works without anyone having to supply an ordering.

RememberOne obvious default order → Comparable.
2 The same list needs to be shown sorted by name on one screen, by date on another

Two screens wanting two different orderings of the same list is exactly what Comparator exists for — each screen's own Comparator object, the underlying class never has to pick a side.

RememberDifferent views, different orders → separate Comparators.
3 You try to "add another compareTo()" overload to sort a different way

compareTo(T o) has one fixed signature from the Comparable<T> interface — you can't overload it to mean "a different ordering." A second ordering has to be a separate Comparator object instead.

RememberSecond ordering → a new Comparator, never a second compareTo().
🌍 Real-world example ▾

A product's natural order (Comparable) might be by SKU for inventory systems, while the storefront needs name order and the discount page needs price order — those extra views are Comparator objects, not changes to Product.
