Before you write a line of code — what shape is this problem?

"How do you decide which algorithm or data structure to use when you see a problem you've never seen before?"

Why it matters ▾
  • Every real interview eventually hands you a problem you've never seen — the actual skill being tested isn't "do you know DP," it's "can you tell this is a DP problem in the first 30 seconds."
  • Reaching for the first familiar-looking technique instead of the one the signal actually points to is one of the most common reasons a strong candidate stumbles on an otherwise solvable question.
  • This is explicitly not another algorithm page — it's the layer that sits on top of every technique from every earlier page in this track, and it's the difference between "knowing algorithms" and "applying the right one under pressure."
🔥 Easy interview recall

Pattern recognition = "match the problem's shape to a toolkit — before writing any code."

Think: ask WHAT is being asked (count? optimum? exists? enumerate?) plus WHAT SHAPE is the input (sorted? graph? interval? small alphabet?) — those two answers narrow 30 pages of technique down to 1-2 real candidates.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for the first familiar-looking technique is not the same as matching the real signal. "Find pairs that sum to X" looks like two pointers, but two pointers needs a sorted array first — if the array isn't sorted, the actual signal is a hash-map complement lookup, not two pointers.

🔄 Likely Follow-up

"Given a totally novel problem you've never seen before, how would you approach picking a technique?" Walk through it in two steps out loud: what's actually being asked — count, optimum, existence, or enumeration — then what the input looks like — sorted, graph-shaped, interval-shaped, or a small fixed alphabet. Those two answers narrow this page's own signal list down to 1-2 realistic candidates.

🎯 Say this in the interview — the exact lines to land

"Before I write any code, I spend about 30 seconds asking what shape the problem is — counting/lookup, a contiguous range, a sorted search space, a bounded top-K selection, overlapping ranges, connectivity, or a choice with memory of past choices. That shape points straight at one or two techniques instead of thirty."

  • "Count, duplicates, anagram" → hash map frequency lookup, not a sort.
  • "Range sum asked many times" → prefix sums; "longest/shortest window" → sliding window.
  • "Sorted input, or minimize-the-max/maximize-the-min" → binary search on the answer, not a full scan.
  • "k largest/smallest/most frequent" → a bounded heap, never sort the whole thing.
  • "Connectivity, cycles, grouping" → graph traversal or union-find — a grid is secretly a graph.
  • "Counting ways, or min/max cost with repeating subproblems" → DP; a locally-best choice you'd never revisit → greedy, but only after trying to break it with a counter-example.
📖 Explanation ▾

Every technique on this track answers a narrow question well and a different question badly. The fast way in is two crossed questions: what is actually being asked — a count, an optimum, an existence check, or every possibility enumerated — and what does the input look like — sorted or unsorted, a grid or a graph, a range of possible answers, a small fixed alphabet. Cross those two answers and the candidate list drops from "everything covered in this track" to one or two real options almost immediately.

The DP vs. greedy split deserves its own care, because both look like "make a good choice repeatedly." The signal that separates them: if the same smaller subproblem keeps recurring inside a naive recursive solution, or the question asks for a count/min/max over many overlapping states, that's dynamic programming. Greedy only earns trust once you've tried, and failed, to construct a counter-example where the locally-best choice at one step forces a worse outcome later — greedy is a claim you have to try to break before you rely on it, not a default.

The two-pointers trap is worth stating precisely, because it's the one candidates fall into most: two pointers narrows a search space by shrinking it from both ends, and that only works because the array is sorted — moving a pointer inward is a valid move only when order guarantees what's on the other side. Drop the sorted precondition and that shrinking logic simply isn't valid anymore, and a single pass with a hash set (store what you've seen, check for the complement) is both simpler and correct.

💻 See the code ▾
C# 
// "Find two numbers that sum to target" — array is NOT guaranteed sorted
int[] Sort(int[] nums) { var copy = (int[])nums.Clone(); Array.Sort(copy); return copy; }

// ⚠️ Reached for two pointers because the shape "looked" right — pays for a sort it didn't need
var sorted = Sort(nums);
int left = 0, right = sorted.Length - 1;   // O(n log n) sort, then O(n) scan
while (left < right) {
    int sum = sorted[left] + sorted[right];
    if (sum == target) return true;
    if (sum < target) left++; else right--;
}

Correct, but the signal was never "sorted input" — two pointers' precondition had to be manufactured with an extra sort that a different technique doesn't need.

C# 
// ✅ Matches the real signal: "does the complement exist?" → hash map lookup
var seen = new HashSet<int>();
foreach (var n in nums) {
    if (seen.Contains(target - n)) return true;  // complement already seen
    seen.Add(n);
}
return false;                             // O(n) time, no sort required

No order needed at all — the signal was "check if something exists," which is exactly what a hash lookup answers in one pass.

🌍 Real-world example ▾

Your interviewer says: "Given a list of numbers, find two that add up to a target — what's your approach?" The fast wrong instinct is two pointers from both ends. The right first question to ask out loud is "is this array sorted?" — if it isn't, a single pass with a hash set beats sorting first just to make two pointers possible.
