Id, OrderId, and the day convention stops guessing right

"How does EF Core map primary keys and relationships by convention?"

Why it matters ▾
  • No attributes to write for the common case — one less thing to configure and review.
  • A quick interview opener: "what does EF Core figure out on its own, and what doesn't it?"
  • The ambiguous-navigation case is a common follow-up probe to check you know where convention actually stops.
🔥 Easy interview recall

Id / OrderId → convention finds it alone

two navs, same type → convention gives up

Think: Id and <Type>Id are the shape EF Core looks for. Two roads to the same place, and it can't tell which is which.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming convention always "just works," even for ambiguous cases. Two navigation properties on the same entity pointing at the same related type — like Customer.BillingOrder and Customer.ShippingOrder, both Order — can't be told apart by shape alone, so EF Core needs explicit Fluent API or annotation configuration to know which foreign key belongs to which navigation.

🔄 Likely Follow-up

"A Customer has both a BillingOrder and a ShippingOrder navigation property, both pointing at Order. Does convention handle this correctly on its own?" No — it's an ambiguous relationship EF Core can't resolve by shape alone; it has to be configured explicitly via Fluent API, naming which foreign key belongs to which navigation.

🎯 Say this in the interview — the exact lines to land

"By convention, EF Core treats a property named Id or <TypeName>Id as the primary key with no attribute needed, and it infers foreign keys from a navigation property plus a matching FK-shaped property. But when two navigations on the same entity point at the same type, that shape is ambiguous, and it has to be configured explicitly with Fluent API or annotations."

  • Id / <Type>Id → primary key, detected automatically, no attribute required.
  • matching nav + FK-shaped property → relationship inferred; a single reference means one, a collection means many.
  • two navs to the same type → convention can't disambiguate; needs Fluent API to say which FK maps to which nav.
📖 Explanation ▾

EF Core's default convention checks for a property named exactly Id, or <TypeName>Id (like OrderId on Order), and treats it as the primary key automatically. No [Key] attribute, no Fluent API call — the shape alone is enough.

The same idea drives relationships. When a navigation property (a reference to another entity) sits next to a property shaped <NavigationType>Id, EF Core reads that pairing as a foreign key and wires up the relationship. Whether it's one-to-many or one-to-one follows from the navigation's own shape: a single reference on one side and a collection on the other means many; a single reference on both sides means one.

That inference breaks down the moment two navigation properties on the same entity point at the same related type. EF Core has no way to know which FK-shaped property belongs to which navigation, so it throws when it builds the model instead of guessing wrong. The fix is explicit: Fluent API's HasOne().HasForeignKey(...), or a [ForeignKey]/[InverseProperty] pair on the navigation properties, naming the match yourself.

💻 See the code ▾
C# 
public class Order
{
    public int Id { get; set; }              // 🔑 primary key — no attribute needed
    public string CustomerName { get; set; }
}

A property literally named Id is enough — EF Core finds it by shape alone.

C# 
public class OrderLine
{
    public int Id { get; set; }
    public int OrderId { get; set; }         // FK shape: <Type>Id
    public Order Order { get; set; }         // nav → matches OrderId
}

public class Order
{
    public int Id { get; set; }
    public List<OrderLine> Lines { get; set; }  // ✅ collection → one-to-many
}

Nav property + a <Type>Id-shaped property is all EF Core needs to wire up the foreign key and the cardinality.

C# 
public class Customer
{
    public int Id { get; set; }
    public Order BillingOrder { get; set; }    // ❌ ambiguous — same type as below
    public Order ShippingOrder { get; set; }   // ❌ ambiguous — same type as above
}

// fix: name each FK explicitly in OnModelCreating
modelBuilder.Entity<Customer>()
    .HasOne(c => c.BillingOrder)
    .WithMany()
    .HasForeignKey("BillingOrderId");   // ✅ this FK belongs to BillingOrder

Two navigations, same target type — EF Core throws building the model until Fluent API says which FK is which.

🌍 Real-world example ▾

A shipping-address feature gets added next to billing. Customer already had a BillingOrder navigation; someone adds a ShippingOrder pointing at the same Order type and migrates. The app throws the moment the model builds — two roads now lead to the same destination, and convention can't pick one. The fix is one Fluent API call naming each foreign key, not a redesign.
