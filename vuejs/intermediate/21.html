Error boundaries in Vue — catching a crash before it takes down the page

"How does Vue's errorCaptured work like an error boundary?"

Why it matters ▾
🛑 onErrorCaptured
❗ ProblemOne failing widget deep in the component tree — a chart that throws while rendering bad data — can crash the entire page if nothing stops the error from propagating all the way up.
✅ SolutiononErrorCaptured on an ancestor catches an error thrown by any descendant during render/watcher/lifecycle execution, like an error boundary, and can stop it from going further.
RecallonErrorCaptured = a local error boundary for one branch of the tree.
🌐 Global handler
❗ ProblemNot every component tree has an ancestor with onErrorCaptured — an error with no local boundary above it would otherwise crash the app with no record of what happened.
✅ Solutionapp.config.errorHandler catches anything that escapes every component-level boundary, app-wide — the last-resort place to log and report it.
Recallapp.config.errorHandler = the app-wide catch-all, last resort only.
🔥 Easy interview recall

onErrorCaptured → local boundary, can stop it

app.config.errorHandler → app-wide catch-all

Think: onErrorCaptured is tried first, per branch; errorHandler only sees what nothing else stopped.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

errorCaptured doesn't catch an error from async code inside an event handler the same way. It only catches errors synchronously thrown during Vue's own render/lifecycle/watcher execution paths — a rejected promise in a click handler needs its own try/catch.

🔄 Likely Follow-up

"What should a well-behaved errorCaptured hook actually do?" Log/report the error, show a fallback UI, and return false to stop the error from propagating further up — returning nothing (undefined) lets it keep bubbling.

🎯 Say this in the interview — the exact lines to land

"onErrorCaptured on an ancestor component catches an error thrown by any descendant during render, watchers, or lifecycle hooks, like an error boundary — returning false stops it there. Anything that escapes every component boundary ends up in app.config.errorHandler, the app-wide catch-all."

  • onErrorCaptured → catches descendant errors, can stop them with return false.
  • app.config.errorHandler → app-wide last resort, catches whatever escapes.
  • Doesn't catch async errors in event handlers — those still need their own try/catch.
  • A good handler logs, shows a fallback, and decides whether to keep bubbling.
📖 Explanation ▾

onErrorCaptured (Composition API) / errorCaptured (Options API) is a lifecycle hook on an ancestor component. Vue calls it whenever a descendant throws during render, inside a watcher, or inside one of its own lifecycle hooks — the same shape as an error boundary in other component frameworks.

Returning false from that hook tells Vue the error has been handled and should stop bubbling any further up the tree. Returning nothing (undefined) lets it keep propagating to the next ancestor with its own onErrorCaptured, and eventually to app.config.errorHandler if nothing above ever stops it.

💻 See the code ▾
Vue 
import { onErrorCaptured, ref } from 'vue'

const failed = ref(false)

onErrorCaptured((err) => {
  console.error('Widget crashed:', err)
  failed.value = true
  return false              // ✅ stop it here, show a fallback instead
})

Without return false, the same error would keep bubbling upward past this ancestor.

Vue 
const app = createApp(App)

app.config.errorHandler = (err, instance, info) => {
  reportToMonitoring(err, info)   // last resort — nothing caught it below
}

This only ever sees an error if no onErrorCaptured above it returned false.

🌍 Real-world example ▾

A dashboard with several independent widgets, each fetching its own data. One widget throwing while rendering a malformed response shouldn't take the whole dashboard down — an onErrorCaptured boundary around each widget shows "widget unavailable" locally, while app.config.errorHandler still logs every such failure to a monitoring service app-wide.
