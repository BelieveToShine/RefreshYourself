Backward compatible ≠ frozen — what's actually allowed to change?

"What does backward compatibility mean concretely, and how would you change a response shape without breaking existing clients?"

Why it matters ▾
  • Every API that survives long enough gets used by clients you can't force to update on your schedule — this is what keeps them working anyway.
  • A frequent pairing in real interviews: the definition question ("what counts as breaking?") right alongside the scenario question ("how would you evolve this shape safely?").
  • Mixing this up with "the API can never change" is a common wrong turn — see the Trap below.
🔥 Easy interview recall

Backward compatible = "old clients don't even notice the change."

Think: Add → safe, old clients ignore what they don't recognize Remove / rename / retype → breaking, old clients misread or crash

⚠️ Common Trap

"Backward compatible" does not mean "never changes." It means every contract a client already relies on keeps working — the shape is free to grow additively, and only removing, renaming, or quietly repurposing something already depended on actually breaks it.

🔄 Likely Follow-up

"How would you communicate a planned breaking change to consumers before making it?" A deprecation notice — often a Deprecation or Sunset response header with a date, documentation callouts, and a real overlap window where both the old and new versions run at the same time, never a surprise cutover.

🎯 Say this in the interview — the exact lines to land

"Backward compatibility means a client written against today's contract keeps working after the API changes — you can grow the contract, but you can't remove or repurpose something a client already depends on. To change a response shape safely, I'd add the new field alongside the old one so each client reads what it understands; I'd only reach for a version bump when the change is genuinely incompatible."

  • Add → new field, endpoint, or optional param — never breaks an old client.
  • Remove / rename / retype → always breaking, even a silent meaning change counts.
  • Changing a shape? → add the new field alongside the old one first — often no version bump needed.
  • Genuinely incompatible → version the endpoint, run both in parallel with a deprecation timeline.
📖 Explanation ▾

Backward compatible means a client written against today's contract still works after the API evolves — the contract is free to grow, but nothing it already depends on is allowed to disappear or change meaning underneath it.

The test isn't how big a change looks — it's whether an already-working client can still parse the response and trust what it says. In most systems, an old client's deserializer simply skips a field it's never heard of, which is why adding one is invisible to it. Removing, renaming, or quietly repurposing a field breaks that same client, because it changes something already being relied on — a field that used to mean "shipped" now meaning something else is exactly as breaking as deleting it, even though the field is still there.

The safe way to change a response shape is to add the new field alongside the old one and keep both populated through a transition window — each client reads what it understands, and this alone is often enough with no version bump at all. Reach for an actual version, run in parallel with a clear deprecation timeline for the old one, only when the change is genuinely incompatible — see Versioning Strategies for how a version actually gets exposed once you decide you need one.

💻 See the code ▾
C# 
public class OrderDto
{
    public string Status { get; set; } = "Shipped";      // ✅ old clients keep reading this
    public OrderStatusInfo? StatusInfo { get; set; }    // ✅ new clients opt into this instead
}

public class OrderStatusInfo
{
    public string Code { get; set; } = "SHIPPED";
    public DateTime UpdatedAtUtc { get; set; }
}

Both fields are populated during the transition — nothing already deployed has to change.

C# 
public class OrderDto
{
    public string OrderState { get; set; } = "Shipped";   // ❌ renamed from Status — old clients now read nothing
}

Same information, new name — an old client's deserializer finds a missing field, not an error it can react to.

C# 
[ApiController]
[Route]("api/v1/orders")
public class OrdersV1Controller : ControllerBase
{
    [HttpGet("{id}")]
    public OrderDtoV1 Get(int id) => _service.GetV1(id);   // ✅ untouched, still served
}

[ApiController]
[Route]("api/v2/orders")
public class OrdersV2Controller : ControllerBase
{
    [HttpGet("{id}")]
    public OrderDtoV2 Get(int id) => _service.GetV2(id);   // ✅ new shape, new clients only
}

Both versions run side by side, with a deprecation timeline for v1 — not a same-day cutover.

🌍 Real-world example ▾

Your mobile app is on an old build in production and can't be forced to update overnight, but the new web client needs a richer order-status object. Add the richer field alongside the existing one and ship it — the old app keeps working completely untouched, and the web client adopts the new field immediately. No version bump, no coordinated release, no breakage.
