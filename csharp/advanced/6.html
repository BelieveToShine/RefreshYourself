Span<T> — a view over memory, not a copy of it

"What problem do Span<T>/Memory<T> solve that array/string slicing doesn't?"

Why it matters ▾
  • Shows up the moment you're optimizing a hot path — parsing, buffer handling, high-throughput APIs — where "just slice it" was quietly allocating on every call.
  • Explains a real compiler error you'll eventually hit: "cannot use a Span<T> here" inside an async method or a class field.
  • A strong signal you know modern .NET performance work, not just the syntax of arrays and strings.
🔥 Easy interview recall

Span<T> = "a window over memory — same bytes, zero copies."

Think: arr[2..5] allocates a brand-new array; Span<T> just narrows the view over the one that's already there — Memory<T> is the heap-safe version you can actually store and await on.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Span<T> is just a faster array slice, so I can store it anywhere like normal data." It's a ref struct that might be pointing at stack memory — the compiler blocks it from class fields and from crossing an await specifically so it can never outlive the stack frame that created it.

🔄 Likely Follow-up

"Why can't Span<T> be a field on a class, or used across an await?" Because it can point at stack memory, and both of those situations could let it outlive the stack frame that created it — the compiler enforces this by making Span<T> a ref struct.

🎯 Say this in the interview — the exact lines to land

"Span<T> is a zero-allocation view over existing contiguous memory — an array, a string, or even stack memory — while slicing an array or string the normal way allocates a brand-new copy. It's a ref struct, so the compiler restricts where it can live specifically to stop it from outliving the memory it points at."

  • Span<T> → use for a synchronous, short-lived zero-copy view — parsing or buffer work inside one method call.
  • Memory<T> → use when the view needs to survive an await or live on the heap — async I/O, stored buffers.
  • Normal slicing (arr[2..5], Substring()) → simplest code, but it allocates — fine off the hot path.
  • It's a ref struct → can't be boxed, can't be a heap field, can't cross an await.
📖 Explanation ▾

Span<T> is like getting a bookmark and a page range for a book you already own, instead of photocopying those pages. Reading through the bookmark costs nothing extra; slicing an array or calling Substring() is the photocopy — quick to write, but every call pays for fresh memory.

Memory<T> is the same idea, minus the one restriction that makes Span<T> fast: it's a normal struct, not a ref struct, so it can live on the heap and survive an await. Reach for it exactly when a Span<T> would need to live longer than the current method call — call .Span on it to get a real Span<T> back for the actual work.

The field-and-await restriction isn't arbitrary: a Span<T> can point at memory on the stack, which disappears the moment its method returns. Letting it sit in a class field or survive across an await (where execution can resume on a different point in the call stack) would let a program read memory that's already gone — the compiler removes that possibility entirely by making Span<T> a ref struct.

💻 See the code ▾
C# 
int[] data = { 10, 20, 30, 40, 50, 60, 70, 80 };
Span<int> span = data.AsSpan(2, 3);  // ✅ points into `data` — 0 bytes copied
span[0] = 99;                       // ✅ mutates data[2] too — same memory

Writing through the span changes the original array — that's the proof it's a view, not a copy.

C# 
int[] slice = data[2..5];   // ❌ allocates a brand-new 3-element array
slice[0] = 99;              // only changes the copy — `data` is untouched

Range slicing on an array looks the same but silently copies — exactly what Span<T> was built to avoid.

C# 
class Cache
{
    Span<byte> _bytes;      // ❌ Span<T> can't be a field on a heap class
}

async Task ReadAsync(byte[] data)
{
    Span<byte> span = data.AsSpan();
    await Task.Delay(1);       // ❌ span can't stay alive across an await
    span[0] = 1;
}

Both errors exist for the same reason — span might be pointing at the stack, and the compiler won't let it outlive that stack frame.

🌍 Real-world example ▾

Span<T> is a bookmark and a page range for a book you already own — you read exactly the pages you need without photocopying them. Slicing the array is the photocopy: quick to write, but every request pays for fresh paper.

You're parsing thousands of incoming byte buffers a second and profiling shows GC pressure coming from array slicing in that hot path. Swapping the slices for Span<T>/ ReadOnlySpan<T> removes the copies entirely, because the code is now just narrowing the view instead of allocating a new array per request.
