Props — read-only, one-way, and never yours to change

"What are props, and how is a child allowed to communicate back to its parent?"

Why it matters ▾
  • Almost every "how do two components talk to each other" question starts here.
  • Thinking a child can just change a prop it received is the single most common early mistake in a real codebase.
  • Prop drilling and the callback pattern show up the moment an app has more than two component levels — which is almost immediately.
🔥 Easy interview recall

Props = "data flows down; a callback prop carries the message back up."

Think: a child never edits a prop — it calls a function the parent handed it, and the parent decides what happens next.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"You can mutate a prop directly if you just need to tweak something quickly." Props are read-only from the child's side — mutating one breaks React's data-flow model, and since the parent still owns the real value, that change is usually silently overwritten the next time the parent re-renders anyway.

🔄 Likely Follow-up

"How does a child communicate back to a parent, since props only flow one way?" The parent passes a callback function down as a prop; the child calls that function (optionally with data) when something happens, and the parent updates its own state in response — the data itself never flows backward, only the function call does.

🎯 Say this in the interview — the exact lines to land

"Props are read-only data passed from a parent down to a child — the child can read them but never change them. Because data only flows one way, a child talks back to its parent by calling a callback function the parent passed down as a prop; the parent owns the real state and decides how to update it."

  • Props flow down, one-way — a child never mutates a prop it receives.
  • A child talks back by calling a callback prop, not by editing data directly.
  • Prop drilling — passing a prop through components that don't need it, just to reach one that does; fixed with Context or composition.
  • Spreading props ({...props}) can accidentally forward — or override — a prop the component never meant to expose.
  • A new object/array/function literal passed as a prop is a new reference every render, which can defeat React.memo downstream.
📖 Explanation ▾

Props are the data a parent hands down to a child — plain values, objects, arrays, even functions, passed the same way HTML attributes are written but received as one object argument. They're read-only from the child's side: a component's output is supposed to depend only on its inputs (props and state), and mutating an input directly breaks that assumption, for React and for anyone reading the code.

Data only moves one way — top-down. There's no built-in way for a child to reach up and change something inside its parent. The fix is the callback prop: the parent writes a function that updates its own state, then hands that function down like any other prop. The child just calls it — it never touches the parent's state directly, it only reports that something happened.

Passing a prop through two or three components that never use it, just to reach one deeply nested child, is prop drilling — Context or restructuring the component tree (composition) is the usual fix. Spreading ({...props}) is a handy shortcut for forwarding whatever a wrapper doesn't care about, but it can accidentally forward, or override, a prop the component never meant to expose. And because a new object, array, or inline function is a new reference every render, passing one as a prop can quietly defeat React.memo on whatever receives it.

💻 See the code ▾
JSX 
function Parent() {
  const [value, setValue] = useState("");

  function handleSave(v) {          // Parent owns the real state
    setValue(v);
  }

  return <Child onSave={handleSave} />;   // pass the FUNCTION down as a prop
}

function Child({ onSave }) {
  return (
    <button onClick={() => onSave("new value")}>   {/* calls it, never touches state */}
      Save
    </button>
  );
}

Child never edits Parent's state — it just calls the function Parent handed it, and Parent decides what happens next.

JSX 
function App() {
  const theme = "dark";
  return <Layout theme={theme} />;      // Layout never uses theme itself
}

function Layout({ theme }) {
  return <Sidebar theme={theme} />;     // neither does Sidebar
}

function Sidebar({ theme }) {
  return <ThemeIcon theme={theme} />;   // only ThemeIcon actually needs it
}

theme passes through two components that never touch it — this is the exact pain prop drilling causes, and exactly what Context or composition exists to remove.

🌍 Real-world example ▾

A manager (parent) hands a sealed assignment (props) to an employee (child). The employee can read it and act on it, but can't rewrite the original — if something about it needs to change, they report back up the chain instead of editing the assignment themselves. That's exactly what a callback prop is: the reporting channel, never a rewrite privilege.
