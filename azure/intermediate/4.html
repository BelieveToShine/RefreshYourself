Key Vault access — one vault, two very different permission models

"How does something actually reach a Key Vault secret without a stored credential — RBAC vs. the older access-policy model?"

Why it matters ▾
🛡️ Azure RBAC
❗ ProblemAccess Policies can only grant access at the whole-vault level and use a vault-only workflow instead of Azure's normal role-assignment model — so there's no way to give one app fine-grained access without also learning a Key-Vault-specific permission system.
✅ SolutionAzure RBAC brings Key Vault into the same role-assignment model used for every other Azure resource, with built-in roles like "Key Vault Secrets User" scoped down to one secret, key, or certificate — exactly why it's now the recommended model.
RecallRBAC = fine-grained, same model as everything else, the current recommendation.
📜 Access Policies
❗ ProblemA policy entry only ever grants across the WHOLE vault — there's no way to hand one app read access to a single secret without also exposing every other secret sitting in that same vault.
✅ SolutionAccess Policies is the vault-specific model that predates RBAC's Key Vault integration — coarse policy entries attached directly to the vault, granting a security principal a set of operations (get, list, set…) across everything in it. Still supported, just not the default anymore.
RecallAccess Policies = whole-vault grants only, legacy, still supported.
🔥 Easy interview recall

RBAC → fine-grained, the current default

Access Policies → vault-wide, the older model

Think: a vault runs on ONE model at a time — never both together.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"RBAC and Access Policies both apply, so I can mix and match." Not true — a vault runs on exactly ONE permission model at a time (a setting on the vault itself), so an app built against the model the vault ISN'T using is exactly why "why can't my app read this secret" comes up so often.

🔄 Likely Follow-up

"Why does Microsoft now recommend RBAC over Access Policies?" Consistency — it's the same role-assignment model used for every other Azure resource — plus finer granularity, since RBAC can scope down to an individual secret instead of only the whole vault.

🎯 Say this in the interview — the exact lines to land

"A Key Vault uses either RBAC or Access Policies, never both at once — RBAC is the current recommendation."

  • Azure RBAC → recommended — fine-grained, same role-assignment model as every other Azure resource.
  • Access Policies → legacy — coarse, vault-wide grants only.
  • A vault picks ONE model, never both — it's a permission-model setting on the vault itself.
  • Either model: the caller presents an Entra ID token — never a stored credential.
📖 Explanation ▾

Every Key Vault is set to exactly one permission model. Access Policies is the older model — coarse-grained entries attached to the vault itself, granting a security principal a set of operations (get, list, set…) across the whole vault. Azure RBAC is the newer integration — the same role-assignment model used for every other Azure resource, with built-in roles like "Key Vault Secrets User" that can be scoped down to an individual secret, key, or certificate instead of the entire vault.

The reach-in mechanic is the same regardless of which model the vault uses: the caller (often a Managed Identity, see the previous topic) requests a token from Entra ID, then presents that token to Key Vault. Key Vault checks the token's identity against whichever model is configured — the assigned RBAC role, or the legacy access policy entry — and grants or denies the operation. No credential is ever stored in the app itself.

💻 See the code ▾
CLI 
az role assignment create // ✅ RBAC: grant read access to secrets
  --assignee <principal-id>
  --role "Key Vault Secrets User"
  --scope <keyvault-id>

A normal role assignment, scoped to this one vault — no vault-specific access-policy syntax to learn.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app gets access denied right after you create a brand-new RBAC role assignment for it

This is the #1 scenario you'll actually run into — the vault itself is still set to the Access Policies model, so a brand-new RBAC role assignment has no effect at all. A vault only ever checks whichever ONE model it's configured to use.

RememberAccess denied after adding a role → check which model the vault is set to, not the role assignment itself.
2 You inherit an existing vault that's still on the older Access Policies model and need to give a new app read access to secrets

Because the vault hasn't moved to RBAC, the grant has to be a policy entry on the vault itself — and that policy can only be scoped to the whole vault, never down to the one secret the app actually needs.

RememberAccess Policies grants → whole vault, never a single secret.
3 You're setting up a brand-new vault and want an app to read exactly one secret, nothing else stored in it

This is exactly the case RBAC is built for — assign a built-in role like "Key Vault Secrets User" scoped down to that one secret, so the app can't touch anything else stored in the vault.

RememberNeed one-secret-only access → an RBAC role scoped to that secret.
🌍 Real-world example ▾

A new project sets its Key Vault to RBAC mode from day one, so its access can be managed with the exact same az role assignment commands already used for every other resource in the subscription — no separate, vault-only permission workflow to remember.
