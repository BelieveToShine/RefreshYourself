Walk me through RAG, end to end — where does it break?

"Walk me through a RAG pipeline end to end. Where does it usually go wrong?"

Why it matters ▾
  • RAG is flagged as the single most-asked area in real GenAI interviews — expect this exact framing, not a vaguer "what is RAG" ask.
  • It's the fastest way an interviewer can tell whether you understand the whole system, or just "stuff some documents into the prompt."
  • Almost every real production LLM feature that touches private, fresh, or frequently-changing data is a RAG pipeline under the hood.
🔥 Easy interview recall

RAG pipeline = "ingest → chunk → embed → index, then retrieve → rerank → assemble → generate → cite."

Think: Build the index once, offline: ingest → chunk → embed → index Answer every question, online: retrieve → rerank → assemble → generate → cite

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The model is hallucinating" isn't always the model's fault. Most quality problems trace back to retrieval — bad chunking or an embedding mismatch handing the model irrelevant chunks, or a stale index serving outdated content — the model can only ground its answer in whatever actually reached its context.

🔄 Likely Follow-up

"What happens when the answer genuinely isn't in the retrieved context?" That case has to be handled on purpose — the system should recognize it and have the model say it doesn't know, instead of quietly generating a confident, unsupported answer.

🎯 Say this in the interview — the exact lines to land

"RAG grounds an LLM's answer in retrieved, verifiable context instead of relying only on what it memorized during training. Offline, you ingest, chunk, embed, and index the documents once; online, every question retrieves, reranks, assembles context, generates, and cites — and most failures trace back to the retrieval half, not the model."

  • Chunk size → the core tradeoff: too small loses context, too large drowns out the signal.
  • Rerank → a slower, more precise model fixes the ordering the first retrieval pass got roughly right.
  • Irrelevant chunks retrieved → usually bad chunking or an embedding mismatch, not a bad model.
  • Answer not in context → say so, don't guess — handling that gracefully is what separates a real system from a demo.
  • Stale index → stale, confidently-cited answers — a vector store is only as fresh as its last refresh.
📖 Explanation ▾

A RAG pipeline splits cleanly into two halves. Offline, you prepare the knowledge once: ingest pulls the source documents in from wherever they live, chunk splits each one into smaller pieces, embed turns every chunk into a vector, and index stores those vectors — plus the original text and metadata — in a vector store built for fast lookup. Online, every user question runs the second half fresh: retrieve embeds the question and pulls back the most similar chunks, rerank re-scores those candidates with a slower, more precise model to fix the ordering, assemble builds the actual prompt from the best few chunks, generate lets the LLM write an answer grounded in that context, and cite attributes the answer back to the chunks it came from.

The reason RAG exists at all: an LLM's own training data goes stale and can never contain private or frequently-changing information. Grounding the answer in retrieved context — instead of only what the model memorized during training — makes fresh, private, and constantly-changing data usable without ever retraining the model itself.

Two specific stages get their own deep-dive pages, so keep this page's version of each brief: chunking strategy and reranking. Everything else on this page is the full, ordered shape a candidate should be able to say out loud without missing a stage.

💻 See the code ▾
Python 
# OFFLINE — build the index once
docs = ingest(source_locations)
chunks = chunk(docs)
vectors = [embed(c) for c in chunks]
index = build_index(vectors, chunks)  # vectors + text + metadata

This half runs once up front, then again only when the source documents change.

Python 
# ONLINE — runs fresh for every question
query_vector = embed(user_query)
candidates = index.search(query_vector, k=20)
reranked = rerank(user_query, candidates)      # fixes top-k order
context = assemble(reranked[:5])
answer = generate(user_query, context)
cited_answer = attach_citations(answer, reranked[:5])

Same shape every time: narrow the candidates down, then hand only the best few chunks to the model.

🌍 Real-world example ▾

A support bot confidently cites a return policy that changed last quarter. The index was never refreshed after the policy page was updated, so retrieval finds and cites the old version with total confidence — a stale index looks exactly like a correct answer until someone checks the source date.
