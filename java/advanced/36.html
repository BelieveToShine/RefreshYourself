A concurrent cache is four hard problems wearing one name — know all four, then reach for Caffeine

"Design a cache that supports concurrent access, expiry, bounded memory, and safe loading. What are the real design decisions?"

Why it matters ▾
🧰 Four Problems, One Box
❗ Problem"Just use a HashMap" solves none of the four real requirements a cache actually has — concurrent access, safe loading without a stampede, bounded memory, and expiry — and getting any one of them wrong under load causes either corrupted state, duplicate expensive work, or an unbounded memory leak.
✅ SolutionConcurrentHashMap.computeIfAbsent for safe concurrent loading, an eviction policy for bounded memory, and a time-based expiry or soft references for staleness — ties together concurrency and collections knowledge this track already covers, and the honest senior answer is to reach for a proven library (Caffeine) instead of hand-rolling all four correctly.
RecallA cache is four problems at once — concurrency, loading, memory, expiry — which is exactly why "just use Caffeine" is the senior answer.
🔥 Easy interview recall

concurrent access → ConcurrentHashMap

safe loading → computeIfAbsent, no stampede

bounded memory → eviction policy (LRU/LFU/max-size)

expiry → time-based policy or soft references

Think: four separate requirements, one proven answer — Caffeine already solves all four correctly.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Checking containsKey() then calling put() is a safe way to load a cache. That check-then-act is a race: two threads can both miss the cache and both compute/load the same expensive value concurrently — a cache stampede — exactly what ConcurrentHashMap.computeIfAbsent's atomic read-then-load-if-absent exists to prevent.

🔄 Likely Follow-up

"Why not just hand-roll this with a ConcurrentHashMap and a background cleanup thread?" It can be done, but correctly handling eviction ordering, expiry timing, and loading atomically all at once is genuinely hard to get right under concurrent load — a proven library like Caffeine has already solved that combination, which is why reaching for it is the honest, senior-level answer for anything beyond a toy example.

🎯 Say this in the interview — the exact lines to land

"I'd back it with ConcurrentHashMap and use computeIfAbsent for atomic, stampede-free loading, add an eviction policy for bounded memory, and either a time-based expiry or soft references for staleness — but for anything beyond a toy example, I'd actually reach for a proven library like Caffeine rather than hand-rolling all of that correctly myself."

  • Concurrent access → ConcurrentHashMap (or a proven library) as the backing store.
  • Safe loading → computeIfAbsent is atomic read-then-load, avoiding a cache stampede.
  • Bounded memory → an eviction policy (LRU/LFU/max-size), never an unbounded cache.
  • Expiry → a time-based policy, or soft references for a weaker GC-driven guarantee.
  • Senior answer → reach for Caffeine/Guava Cache instead of hand-rolling all four.
📖 Explanation ▾

ConcurrentHashMap is the natural backing store for concurrent access — it's already covered on this track (Advanced #18) for exactly this per-bin-locking, high- throughput reason. The harder problem sitting right next to it is safe loading: checking whether a key is present and then computing/loading its value only if it's missing has to happen as one atomic step, or two threads that both miss the cache at the same moment will both pay the cost of computing or fetching the same expensive value — a cache stampede. computeIfAbsent does exactly that atomic read-then-load-if-absent in one call, which is the real reason it's the right tool here, not just a shorter way to write the same two lines.

Bounded memory is a separate requirement from loading correctness: without an eviction policy, a cache is just a slow-motion memory leak with extra steps — the same lesson Advanced #4 covers for leaks in general, applied deliberately here instead of discovered by accident. An LRU or LFU policy, or simply a hard maximum-size bound, is what keeps the cache's footprint predictable under sustained load.

Expiry answers a different question than eviction: eviction answers "what do we drop when we're full," expiry answers "how long is a value allowed to stay valid at all, even if there's room for it." A time-based policy built into the chosen library is the direct way to express that; soft references (Advanced #5) are a weaker, different guarantee — "let the garbage collector reclaim this under real memory pressure" rather than "expire this value on a schedule." The honest, senior-level close to this whole design: correctly combining atomic loading, eviction, and expiry under real concurrent load is genuinely hard to get exactly right by hand, which is exactly why reaching for a proven cache library (Caffeine, or Guava Cache) is the answer an experienced engineer actually gives for anything beyond a toy example.

💻 See the code ▾
Java 
if (!cache.containsKey(key)) {        // ❌ check-then-act — a race
    cache.put(key, loadExpensiveValue(key)); // two threads can both reach here
}

Two threads can both see the key missing and both pay the full cost of loading it — a textbook cache stampede.

Java 
cache.computeIfAbsent(key, k -> loadExpensiveValue(k)); // ✅ atomic — only one thread loads

One atomic step: whichever thread gets there first loads the value, every other thread just waits for that same result.

Java 
Cache<String, Value> cache = Caffeine.newBuilder()
    .maximumSize(10_000)                       // ✅ bounded memory
    .expireAfterWrite(10, TimeUnit.MINUTES)  // ✅ expiry
    .build(key -> loadExpensiveValue(key));    // ✅ atomic, stampede-free loading

All four requirements in a handful of lines — the senior-level answer for anything beyond a toy example.

🧭 Use Cases — recognize these when they happen to you ▾
1 Several threads miss the cache for the same key at almost the same moment

This is the #1 scenario you'll actually run into under real load: a cold or just-evicted key gets hit by several requests before any of them has loaded it. computeIfAbsent's atomicity is what keeps that from turning into N duplicate loads of the same expensive value.

RememberA simultaneous miss on the same key is exactly what atomic loading exists to prevent.
2 The cache has no size limit and memory grows as traffic patterns shift over time

An ever-growing key space (per-user data, long-tail lookups) with no eviction is the same leak lesson from Advanced #4, just happening deliberately inside a cache instead of by accident. An LRU/LFU policy or a hard maximum size is what keeps this predictable instead of a slow-motion OutOfMemoryError.

RememberAn unbounded cache is a memory leak with a friendlier name.
3 A cached value is technically still present but is now stale

Room in the cache and a stale value are two different problems — eviction handles the first, expiry handles the second. A time-based policy forces a reload on a known schedule; soft references are a looser, GC-driven version of "let this go eventually," not a substitute for a real expiry policy when staleness genuinely matters.

RememberHaving room for a value and that value still being fresh are two separate questions.
🌍 Real-world example ▾

A pricing lookup is expensive enough that a cold cache under real traffic causes dozens of threads to recompute the same price at once. Backing it with Caffeine's build() loader (atomic, stampede-free loading, a size bound, and a write-expiry policy all in one configuration) is the honest answer — not a hand-rolled ConcurrentHashMap with a background cleanup thread trying to replicate all three correctly.
