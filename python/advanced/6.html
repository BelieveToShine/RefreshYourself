🔥 Python · Advanced · Must Know

Reference counting frees an object the instant its count hits zero — cyclic references are the one case that needs a separate garbage collector

How does Python manage memory? Can a Python application actually leak memory, and how would you investigate growing memory usage?

Why it matters ▾
  • Tests whether you know Python's primary memory mechanism is deterministic reference counting, not a background sweep like some other garbage-collected languages — and that a separate cyclic collector only exists for the one case refcounting can't solve on its own.
  • Explains why a "garbage-collected" language can still leak memory in production — a very common misconception this exact question is designed to probe.
  • A frequent opener before asking how you'd actually investigate rising memory in a live service — the answer needs real tools, not just "call gc.collect()."
🔥 Easy interview recall

Reference counting = "frees an object the instant its refcount hits zero."

Think: a cycle (A ↔ B) can never hit zero alone — that's exactly what the gc module's cyclic collector exists to clean up.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Python has garbage collection, so it can't leak memory" is not true. Reference cycles are only one source — a forgotten global cache, an event-handler registry that never unregisters, or an unclosed resource all cause very real, very common memory growth in production.

🔄 Likely Follow-up

"What does __slots__ actually save, and what do you give up?" It saves the per-instance __dict__ overhead — meaningful at scale with many instances of a simple data-holding class — but gives up dynamic attribute assignment and complicates certain inheritance/pickling patterns.

🎯 Say this in the interview — the exact lines to land

"Reference counting frees objects immediately at refcount zero — the cyclic GC exists specifically for reference cycles that refcounting alone can never resolve."

  • gc module → collects reference cycles refcounting alone can never resolve, via periodic sweeps.
  • Real leaks happen via forgotten caches or registries and unclosed resources, not just reference cycles.
  • __slots__ trades dynamic attributes for real per-instance memory savings at scale.
  • tracemalloc / objgraph → the tools to actually investigate growing memory in a live service.
📖 Explanation ▾

CPython's primary memory-management mechanism is reference counting — every object tracks how many references point to it, and the moment that count hits zero, the object is freed immediately. That's deterministic, not "eventually" the way some other garbage-collected languages behave. The problem is a reference cycle — object A refers to B, and B refers back to A — which can never naturally reach a refcount of zero through refcounting alone, even when nothing outside the cycle refers to either one.

CPython's separate cyclic garbage collector (the gc module) periodically detects and cleans up exactly this pattern. Objects involved in a cycle that also define __del__ were historically harder for the cyclic collector to handle safely — modern CPython handles most of these cases correctly too, but it's still the sharper edge case to know about.

Genuine leaks come from three places: real reference cycles, something holding an object alive that you forgot about (a growing cache, an event-handler registry that never unregisters, a closure capturing more than intended), or C-extension memory that Python's own allocator never tracked in the first place.

💻 See the code ▾
Python 
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(1, 2)
p.z = 5   # ✅ works — instance has a normal __dict__

A plain object stores its attributes in a per-instance __dict__ — any new attribute name is allowed at any time.

Python 
class Point:
    __slots__ = ('x', 'y')

    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(1, 2)
p.z = 5   # ❌ AttributeError: 'Point' object has no attribute 'z'

__slots__ skips the per-instance __dict__ entirely — real memory savings at scale, but no attribute outside the declared set.

🌍 Real-world example ▾

A long-running service's memory grew unbounded — a request-scoped object was being appended to a module-level list used as an ad-hoc cache that never evicted anything. tracemalloc pinpointed the exact allocation site: the list kept growing on every request, with nothing ever removed. The fix was bounding (or removing) the cache — not chasing a phantom "garbage collector problem."
