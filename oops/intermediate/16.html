Adapter vs. Facade — change the shape, or hide the mess?

What's the difference between the Adapter and Facade patterns?

Why it matters ▾
🔌 Adapter
❗ ProblemYour code expects IPaymentGateway.Pay(), but the library you must use exposes MakePayment(int cents). Neither side should be rewritten.
✅ SolutionAn adapter implements the interface you expect and translates each call to the library's shape.
RecallAdapter = make one interface look like another.
🚪 Facade
❗ ProblemPlacing an order means calling stock, payment, and shipping in the right order. Every caller repeats that and has to know all three.
✅ SolutionA facade gives one method, PlaceOrder(), that runs the steps. Callers use the simple front and ignore the parts behind it.
RecallFacade = one simple front over many parts.
🔥 Easy interview recall

Adapter → converts an interface to the one you expect

Facade → simplifies a group of parts behind one door

Think: Adapter is a travel plug converter: same power, new shape. Facade is a hotel front desk: one place to ask, many people behind it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Adapter and Decorator are the same — both wrap an object." A decorator keeps the same interface and adds behavior. An adapter changes the interface so two mismatched pieces can talk.

🔄 Likely Follow-up

"Does a Facade stop callers from using the subsystem directly?" No. It is a convenience, not a lock. Callers who need more control can still use the parts.

🎯 Say this in the interview — the exact lines to land

"An Adapter converts one interface into the one my code expects, so I can reuse a class without changing it. A Facade gives a simpler front to a group of classes. Adapter is about compatibility; Facade is about simplicity."

  • Adapter → converts an interface to the one the client expects.
  • Facade → one simple entry point over a complex subsystem.
  • Versus Decorator → decorator keeps the interface, adapter changes it.
  • Ask yourself → wrong shape (adapter) or too many steps (facade)?
📖 Explanation ▾

An Adapter fixes a mismatch. Your code speaks IPaymentGateway; the library speaks MakePayment(cents). The adapter implements the first and calls the second. Typical uses are old code and third-party libraries you cannot change.

A Facade fixes complexity. A checkout needs stock, payment, and shipping calls in the right order. The facade wraps those steps in one method, so callers do not repeat the recipe or know the parts. It does not hide the parts from anyone who wants them.

Both wrap other classes, so they are easy to mix up with each other and with Decorator. The question to ask is what changes: Adapter changes the interface, Facade reduces the number of things you must know, Decorator keeps the interface and adds behavior.

💻 See the code ▾
C# 
public interface IPaymentGateway { void Pay(decimal amount); }

public class LegacyPayAdapter : IPaymentGateway
{
    private readonly LegacyPayClient _legacy;
    public LegacyPayAdapter(LegacyPayClient legacy) => _legacy = legacy;

    public void Pay(decimal amount)
        => _legacy.MakePayment((int)(amount * 100));   // ✅ translate the call
}

The adapter implements the interface you expect and speaks the library's language underneath.

C# 
public class CheckoutFacade
{
    // _stock, _payment, _shipping are injected in the constructor
    public void PlaceOrder(Order o)
    {
        _stock.Reserve(o);      // step 1
        _payment.Charge(o);     // step 2
        _shipping.Schedule(o);  // step 3
    }   // ✅ callers make one call
}

The facade holds the recipe; callers just call PlaceOrder.

🌍 Real-world example ▾

You switch payment providers, but your checkout code speaks IPaymentGateway. A small adapter makes the new provider fit, with no checkout changes. Separately, a CheckoutFacade lets the controller place an order with one call instead of three.
