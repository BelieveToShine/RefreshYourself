Scenario: the same query, run twice — diagnosing multiple enumeration

"Your application logs show the exact same SQL query running twice per request — how do you diagnose and fix it?"

Why it matters ▾
🔁 Two round trips, one query in the code
❗ Problemvar q = db.Users.Where(...); if (q.Any()) { foreach (var u in q) { ... } } enumerates the same un-materialized q twice — once inside Any(), once in the foreach — and each enumeration of an IQueryable is its own real database round trip.
✅ SolutionMaterialize once, right after building the query — var list = await q.ToListAsync(); — then call list.Any() and foreach (var u in list) against the already-materialized list, which costs nothing more than reading memory.
RecallAn un-materialized IQueryable re-runs the whole pipeline every time it's enumerated.
🔥 Easy interview recall

left un-materialized → every enumeration = a new round trip

.ToList() once → every later use is free

Think: an IQueryable is a plan, not a result — asking it for an answer twice runs the plan twice.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling .Any() before a foreach doesn't make the check "free." On a still-deferred IQueryable, .Any() is itself a full enumeration (translated to SELECT TOP(1) ... WHERE EXISTS or similar) — it's a real round trip, not a cheap peek.

🔄 Likely Follow-up

"How would you actually catch this in a real application, before a user reports it?" EF Core's own logging (or ToQueryString()) shows the generated SQL and how often it runs per request — seeing the identical statement logged twice for one request is the exact signal to look for the point where the same IQueryable got enumerated more than once.

🎯 Say this in the interview — the exact lines to land

"I'd look for the same IQueryable being enumerated more than once — here, .Any() and the foreach each trigger their own round trip against an un-materialized query. The fix is to materialize once, right after building the query, with ToListAsync(), and then operate on that already-materialized list for everything after."

  • Same query logged twice → look for one IQueryable enumerated more than once.
  • .Any() on an IQueryable → a real round trip, not a free check.
  • Fix → materialize once with ToListAsync(), right after building the query.
  • After materializing → Any()/foreach on the list cost nothing more.
📖 Explanation ▾

A variable holding an unfinished LINQ query — var q = db.Users.Where(...) — is a plan, not a result, thanks to deferred execution: nothing runs against the database until something actually enumerates q. q.Any() is one such enumeration (it forces execution to check for a match); the foreach right after it is a second, completely separate enumeration — the query provider has no memory that this exact plan already ran a moment ago, so it runs the whole thing again from scratch.

Against an in-memory List<T>, running the same filter twice is cheap enough to go unnoticed. Against a real database, each enumeration is its own round trip — the same SELECT statement, logged twice, for what the code reads as one logical operation. That mismatch between "looks like one query" and "runs as two round trips" is exactly what application logs showing a duplicated statement are pointing at.

The fix isn't to avoid calling .Any() — it's to materialize the query exactly once, as early as possible, and treat everything after that point as operating on a real, already-fetched list rather than a query. list.Any() and foreach (var u in list) both just read memory; neither one touches the database again.

💻 See the code ▾
C# 
// Two round trips for what reads like one query
var q = db.Users.Where(u => u.IsActive); // still just a plan

if (await q.AnyAsync())        // ❌ round trip #1 — enumerates q
{
    await foreach (var u in q.AsAsyncEnumerable())
    {
        Process(u);             // ❌ round trip #2 — enumerates q AGAIN, from scratch
    }
}

Application logs show the exact same generated SQL statement twice — one per enumeration of q.

C# 
// Materialize once, reuse the already-fetched list
var q = db.Users.Where(u => u.IsActive);
var list = await q.ToListAsync(); // ✅ the ONLY round trip

if (list.Any())              // in-memory — free
{
    foreach (var u in list)   // in-memory — free
        Process(u);
}

Exactly one statement shows up in the logs now — list.Any() and the foreach both just read the already-fetched rows.

🧭 Use Cases — recognize these when they happen to you ▾
1 The canonical pattern: Any() as a guard, then a foreach over the same query

This is the pattern most teams actually hit — it reads completely innocent, since both lines look like simple checks on the same variable. The logs are the tell: the exact same statement, twice, for one request.

RememberAny() + foreach on the same q → two round trips, not one.
2 The same un-materialized query gets passed into two different methods

The same bug wearing a different disguise: passing an un-materialized q into two separate methods — one that counts, one that displays — means each one enumerates it independently. No Any() in sight, same root cause.

RememberPassing an un-materialized query to two call sites doubles the trip, no Any() required.
3 Logging middleware re-iterates a result for diagnostics before the controller enumerates it again

The hardest version to spot — a cross-cutting concern like logging enumerates the query "just to log the count," handing it back un-materialized, and the controller's own code enumerates it again downstream with no idea it already ran once.

RememberCross-cutting code can double-enumerate a query with no Any() or foreach visible at the call site.
🌍 Real-world example ▾

APM tooling flags an endpoint as making two identical database calls per request, and the controller code only has one line that looks like a query. The actual cause is almost always a guard clause — if (q.Any()) — sitting in front of a foreach over the same un-materialized q. Materializing once with ToListAsync() right after building the query collapses it back to one round trip.
