JSON mode guarantees valid JSON — but not the shape you asked for

"How do you force a model to return valid JSON, and what do you do when it doesn't?"

Why it matters ▾
  • Any production system that hands an LLM's output to code instead of a human lives or dies on this — a fragile parser is a guaranteed on-call incident.
  • Explains a real gap: a lot of teams flip on "JSON mode" and assume the problem is solved, then get surprised the first time a required field is just missing.
  • A common opener for "how would you get reliable structured data out of an LLM" system-design-style questions.
🔥 Easy interview recall

Prompting alone → guarantees nothing — can add prose or break

JSON mode → guarantees valid syntax, not your shape

Schema-constrained / tool calling → enforces your exact fields

Think: each rung up promises more — first just valid syntax, only the top rung actually checks your field names and types.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"JSON mode" means the output will match my schema. It only guarantees syntactically valid JSON — the model can still return valid JSON with a missing key, an extra key, or the wrong type.

🔄 Likely Follow-up

"If I use schema-constrained output, do I still need to validate the result?" Yes — schema constraints stop a malformed shape, not a bad value; still run real validation (business-rule checks a schema can't express) and keep a repair/retry step for the rare malformed case.

🎯 Say this in the interview — the exact lines to land

"Prompting alone can't guarantee valid JSON; JSON mode guarantees syntactically valid JSON but not my schema; schema-constrained output or tool/function calling is what actually enforces my exact fields and types — and I'd still validate and retry on top of that."

  • Prompting alone → weakest, can add prose or malformed JSON.
  • JSON mode → guarantees valid syntax, not your shape.
  • Schema-constrained / tool calling → enforces the exact fields and types you defined.
  • Under the hood → constrained decoding restricts token sampling to grammar-valid tokens, step by step.
  • Even with a schema → still validate and keep a repair/retry step for the rare malformed case.
📖 Explanation ▾

Getting an LLM to return something a program can actually parse escalates through a few approaches. Prompting alone — just asking for JSON in plain instructions — is the weakest: the model can still wrap the JSON in a sentence, drop a comma, or otherwise produce something that doesn't parse. JSON mode, a provider-level setting, fixes the syntax problem: the output is guaranteed to be valid JSON. What it doesn't guarantee is the shape — nothing stops the model from using different field names, skipping a required key, or sending a number as a string.

Prompting aloneJSON modeSchema-constrained / tool calling
Guaranteesnothingvalid JSON syntaxvalid JSON + your exact fields/types
Shape enforced?❌ no❌ no✅ yes
Risk if relied on aloneextra prose, broken syntaxright syntax, wrong shapestill needs validation for business rules

Underneath most "guaranteed JSON" tooling is constrained (grammar-based) decoding: instead of generating freely and hoping the result matches, the token-sampling step itself is restricted at each position to only the tokens that keep the output consistent with the target grammar or schema. That's what lets schema-constrained output and tool/function calling promise field names and types, not just "some valid JSON."

Even so, a schema can't express everything — it can require age to be a number, but not that it's non-negative. Production systems still validate the parsed result against real business rules and keep a repair/retry step for the rare case the model's output still comes back malformed.

💻 See the code ▾
JSON mode 
{ // ✅ valid JSON — syntax parses fine
  "result": "the user's age is 29"
} // ❌ still not the {name, age} shape the caller expected

JSON mode never checked field names — it only promised the output would parse.

JSON Schema 
{
  "type": "object",
  "properties": { "name": {"type": "string"}, "age": {"type": "number"} },
  "required": ["name", "age"]
} // ✅ the provider enforces this exact shape while generating

With schema-constrained output, the model can't finish a response that skips age or sends it as a string — the shape itself is enforced during generation.

Pseudocode 
result = callModel(prompt, schema)
if not passesBusinessRules(result):  # e.g. age must be >= 0
    result = callModel(prompt, schema, retry=1)  # ✅ repair/retry on the rare failure

A schema can't express "age must be non-negative" — that check, and the retry path, still belong to your own validation layer.

🌍 Real-world example ▾

Your service turns on JSON mode for an extraction endpoint and ships it, confident the "valid JSON" guarantee closes the problem. Weeks later a downstream job starts failing intermittently — the model is still returning valid JSON, just occasionally with a renamed key or a number sent as a string. The fix isn't a smarter prompt; it's moving to schema-constrained output for the fields that matter, plus a validation-and-retry step for anything that still slips through.
