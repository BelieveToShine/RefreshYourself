Why a long-running JVM gets faster, not slower, over time

"Why does a long-running JVM process often get faster over its first few minutes?"

Why it matters ▾
🔥 JIT Warm-Up
❗ ProblemInterpreting every single bytecode instruction is reliable but slow — and benchmarking a JVM app without accounting for this produces numbers that don't reflect its real steady-state performance.
✅ SolutionThe JIT compiler profiles running code and compiles "hot" methods — the ones actually called often — into optimized native machine code at runtime, so the parts of the program that matter stop being interpreted at all.
RecallHot methods get compiled to native code — that's the warm-up curve.
🔥 Easy interview recall

JIT = "the JVM watches what actually runs a lot, and turns just that into fast native code."

Think: a cold JVM interprets everything slowly at first, then the hot paths get compiled and speed up — benchmark after warm-up, not before.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Benchmarking a cold JVM measures the interpreter, not your code's real speed. A microbenchmark that runs a method once or twice and times it is almost entirely measuring interpretation and class-loading overhead, before the JIT has had any chance to compile anything.

🔄 Likely Follow-up

"How does the JVM decide a method is 'hot'?" It counts invocations (and loop back-edges) per method against a threshold — HotSpot JVMs typically use tiered compilation, promoting a method from the interpreter to a fast-but-less-optimized compiler (C1) and, if it stays hot, on to the more aggressively optimizing compiler (C2).

🎯 Say this in the interview — the exact lines to land

"The JIT compiler profiles running bytecode and compiles methods that get called often — 'hot' methods — into optimized native machine code at runtime, instead of interpreting every call forever. That's why a long-running JVM often gets faster over its first minutes: as more hot paths get compiled, less of the program is still running through the interpreter. It also means you have to account for warm-up when benchmarking, or the numbers mostly measure the interpreter, not the real steady-state performance."

  • JIT compiles only the hot methods, not the whole program at once.
  • Warm-up means early calls are interpreted and slower on purpose, by design.
  • A fair benchmark discards the warm-up phase before measuring.
  • HotSpot uses tiered compilation — interpreter → C1 → C2 — for hot enough methods.
📖 Explanation ▾

The JVM starts by interpreting bytecode directly — simple and portable, but each instruction is re-decoded every time it runs. While it does this, the JVM also profiles: counting how often each method is invoked (and how often its loops run). Once a method crosses an invocation threshold, it's handed to the JIT compiler, which compiles it down to native machine code specific to the actual CPU — from then on, calls to that method run the compiled version directly, skipping interpretation entirely.

HotSpot (the JVM used by OpenJDK and most production Java) does this in tiers: the interpreter first, then C1 (the client compiler — compiles quickly, with modest optimization) for methods that are warming up, and C2 (the server compiler — slower to compile, but far more aggressively optimized, including inlining and speculative optimizations based on what it's actually observed about the running code) for methods that stay hot. This tiering is why the speedup isn't a single jump — it ramps up as more methods cross each threshold.

The practical consequence is warm-up: a JVM process is measurably slower in its first seconds-to-minutes than at steady state, purely because the JIT hasn't finished compiling the hot paths yet. Reliable Java benchmarking tools (JMH is the standard one) explicitly run warm-up iterations and discard them before measuring, specifically to avoid reporting interpreter-dominated numbers as if they were the program's real speed.

💻 See the code ▾
Java 
long start = System.nanoTime();
for (int i = 0; i < 1; i++) compute();
System.out.println(System.nanoTime() - start);
// ❌ measures mostly interpretation + class loading, not real speed

for (int i = 0; i < 100_000; i++) compute(); // warm-up — let the JIT kick in
long start2 = System.nanoTime();
for (int i = 0; i < 100_000; i++) compute();
System.out.println((System.nanoTime() - start2) / 100_000); // ✅ measures the actual compiled, steady-state speed

Hand-rolled timing like this is fragile — a real benchmark should use JMH, which handles warm-up, JIT effects, and measurement noise properly.

🧭 Use Cases — recognize these when they happen to you ▾
1 A quick "time this method once" benchmark gives a suspiciously high number

A candidate often assumes a single-call timing test reflects "how fast this code is." It doesn't — it mostly reflects interpretation and class-loading cost, since the JIT hasn't compiled anything yet by the first call.

RememberNo warm-up → the number you measured is the interpreter, not your code.
2 A short-lived CLI tool or serverless function never seems to speed up

A process that exits before any method gets called often enough never benefits from JIT compilation at all — warm-up only pays off for processes that run long enough to repeat the same hot paths many times.

RememberProcess exits too soon → JIT never gets the chance to help.
3 A long-running service's p99 latency is highest right after a fresh deploy

Freshly deployed instances behind a load balancer genuinely are slower right after startup — a traffic ramp-up or "warm-up traffic" period before sending full load gives the JIT time to compile the real hot paths first.

RememberFresh instance → expect slower latency until warm-up finishes.
🌍 Real-world example ▾

A newly deployed instance behind a load balancer shows noticeably worse p99 latency for its first few minutes, then matches the rest of the fleet. That's warm-up, not a regression — many deployment pipelines send a ramp of low-volume "warm-up" traffic to a new instance before routing it full production load, specifically to let the JIT compile the hot paths before it has to perform under real pressure.
