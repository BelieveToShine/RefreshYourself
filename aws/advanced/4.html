RDS Proxy exists because Lambda's own burst concurrency can exhaust a database

Design a serverless REST API — and what breaks when many concurrent Lambda invocations hit a connection-limited database?

Why it matters ▾
  • API Gateway → Lambda → a database is the default shape of a serverless REST API — expect a "design this" whiteboard question built exactly on this pattern.
  • Connection exhaustion under Lambda's burst concurrency is a real, well-known production failure, not a theoretical edge case — naming RDS Proxy as the fix is a strong signal in an interview.
  • Step Functions vs. chaining Lambda calls by hand is a common comparison question inside this same design.
🔥 Easy interview recall

RDS Proxy = "a connection pool between bursty Lambda and a database with a connection limit."

Think: API Gateway → Lambda → RDS Proxy → RDS — never Lambda → RDS directly.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Skipping RDS Proxy and connecting Lambda straight to RDS/Aurora "works" at low volume — but under real burst concurrency, each concurrent invocation opens its own connection, and that's exactly how teams accidentally exhaust the database's connection limit and cause cascading failures under load.

🔄 Likely Follow-up

"When is Lambda a bad choice?" Long-running processes past its max execution timeout, workloads needing very low, consistently predictable latency with zero cold-start tolerance, or steady very-high-throughput workloads where a persistent server/container ends up cheaper than paying per invocation.

🎯 Say this in the interview — the exact lines to land

"RDS Proxy exists specifically because Lambda's burst concurrency can exhaust a relational database's connection limit — it pools and reuses connections so a spike of invocations doesn't each grab their own."

  • API Gateway → Lambda → DynamoDB is the default serverless REST shape, with Cognito or a Lambda authorizer handling auth.
  • Step Functions → coordinates a multi-step workflow with built-in state, retries, and branching — chaining Lambdas by hand gives you none of that for free.
  • SQS or EventBridge → decouples slow work from the request/response cycle instead of making the caller wait.
  • RDS Proxy → pools connections in front of RDS/Aurora so Lambda's burst concurrency can't exhaust the connection limit.
  • Lambda is the wrong choice for long-running or steady very-high-throughput workloads.
📖 Explanation ▾

API Gateway → Lambda → DynamoDB is the classic serverless REST pattern: API Gateway is the entry point, Lambda runs the business logic, and Cognito or a Lambda authorizer handles auth on the way in. Slow work doesn't have to sit inside that request/response cycle — handing it to SQS or EventBridge lets Lambda respond fast and process the rest asynchronously. DynamoDB fits this pattern well partly because it's reached over HTTP calls rather than a pooled database connection, so it doesn't carry a fixed connection-limit problem the way a relational database does.

When a workflow has several steps that depend on each other's results, Step Functions coordinates them with built-in state, retries, and branching. Chaining Lambdas by having one invoke the next does something similar, but clumsily — there's no built-in visibility into which step you're on, and retries/error handling have to be hand-rolled in every function instead of configured once.

The trouble starts when the database behind the API is relational (RDS or Aurora) instead of DynamoDB. Lambda scales by running many invocations at once, and each one can open its own database connection — under a real burst, that adds up fast enough to hit the database's connection limit. RDS Proxy sits between Lambda and the database specifically to absorb this: it holds a pool of real connections and lets a burst of Lambda invocations share and reuse them, instead of each invocation needing a brand-new one.

🌍 Real-world example ▾

A retailer's serverless order API works fine under normal traffic, then starts throwing database connection errors during a flash sale. Lambda's concurrency scales up with the traffic spike, each invocation opens its own connection to the relational order database, and the database's connection limit gets exhausted. The fix: add RDS Proxy in front of the database so the burst of Lambda invocations shares a pooled set of connections instead of each grabbing its own.
