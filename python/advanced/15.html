A Python API suddenly becomes slow. Memory usage keeps increasing. CPU hits 100%. What do you actually check for each?

Why it matters ▾
  • Production incidents — "the API is slow," "memory keeps growing," "CPU is pegged" — are exactly where an interviewer checks whether a candidate narrows down a cause systematically, or just guesses out loud.
  • Several of the symptoms below trace directly back to specific traps this track already covers on their own pages — mutable defaults, unlocked races, blocking-inside-async, the GIL — and recognizing that pattern fast is itself the skill being tested.
  • A senior/architect interview often frames this as "walk me through how you'd debug X in production" — a strong answer names specific tools (cProfile, tracemalloc), not vague steps like "check the logs."

API suddenly slow → profile first (cProfile/APM), don't guess

Memory keeps growing → tracemalloc/objgraph, not "restart it"

CPU at 100% → profile for the hot loop, then check if it's real load

Threads not helping throughput → CPU-bound + GIL, needs multiprocessing

📖 Explanation ▾

A production alert almost never says what's actually wrong — "the API is slow" fits a dozen different causes equally well. The fastest way through it is the same every time: profile or trace first, then check whether the symptom matches a trap this track already has a name for, before treating it as a brand-new mystery.

Some of the most common pairings:

  • API suddenly slow → a new N+1 query pattern (its own dedicated Advanced page), a recent deploy, a downstream dependency slowing down, or a sudden traffic-pattern change — profile with cProfile/an APM tool first, don't guess.
  • Memory keeps increasing → a reference cycle involving __del__, an unbounded cache/list/registry that never evicts, or a genuine C-extension leak — use tracemalloc/objgraph to see what's actually being held (its own dedicated Memory Management page).
  • CPU at 100% → a genuinely CPU-bound hot loop (profile to find it), an infinite/runaway loop bug, or unexpectedly high real load.
  • Async API slower under concurrent load → a blocking call with no await hiding inside a handler (its own dedicated asyncio-page trap), or a shared resource pool (a DB connection pool) too small for the concurrency level.
  • Threads not improving throughput → check whether the workload is actually CPU-bound — GIL-blocked, needs multiprocessing instead — rather than I/O-bound (its own dedicated GIL page).
  • One request blocks every other async request → the exact asyncio-page trap: a blocking call with no await freezing the whole event loop for everyone.
  • Intermittent KeyError crash → an assumption that a dict/config always has a certain key that isn't actually guaranteed — a missing environment variable, an evolving external API response shape — often a data/environment assumption bug, not a "random" crash.
  • A function unexpectedly retains values between calls → the mutable-default- argument trap (its own dedicated Intermediate page), showing up as a real production symptom.
  • Threads occasionally corrupt shared state → an unlocked shared-state race (its own dedicated Threading-page trap) surfacing as intermittent, hard-to-reproduce data corruption.
  • Production and development behave differently → environment-specific config/dependency-version differences, or a CPython-implementation detail (interning, etc.) that only "worked" by coincidence in one environment.
  • A dependency upgrade breaks production → check the changelog for breaking changes, verify dependency pinning/locking actually caught the version bump, and consider whether tests would have caught this.
🌍 Real-world example ▾

An on-call engineer gets paged because adding more worker threads to a CPU-heavy image-resizing service didn't move throughput at all. Instead of treating it as a fresh mystery, they recognized the exact shape from the GIL page — genuinely CPU-bound work under the GIL doesn't parallelize across threads — confirmed it with a quick profile in minutes, and swapped to multiprocessing instead of spending the rest of the night adding still more threads.
