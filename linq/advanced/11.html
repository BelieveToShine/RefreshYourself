N+1 Queries and Navigation Properties — an innocent foreach, hundreds of queries

"How does an innocent-looking foreach over navigation properties turn into hundreds of queries?"

Why it matters ▾
😱 N+1 queries
❗ ProblemA foreach that reads a navigation property on every loaded row looks like ordinary C# — but if that property isn't already loaded, each access is a brand-new database query, and the count scales with however many rows the outer query returned.
✅ SolutionShape the LINQ query itself to avoid the per-row trip — load the navigation up front with Include, or project exactly the field the loop needs with Select — so nothing inside the loop ever has to go back to the database.
RecallN+1 = 1 query to load rows, +1 more per row for the navigation.
🔥 Easy interview recall

N+1 = "1 query to load the rows, +1 more per row for the navigation."

Think: the query count scales with how many rows came back, not with anything the developer wrote as a loop count.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The foreach itself isn't the bug. It's reading an un-included, un-projected navigation property inside it — the exact same loop over an already-projected or already-included result triggers nothing extra.

🔄 Likely Follow-up

"If Include fixes this, why would I ever use a Select projection instead?" Because Include still loads the entire related entity. If the loop only reads one field off the navigation, a Select projection naming just that field avoids the per-row trip without pulling the whole related entity either.

🎯 Say this in the interview — the exact lines to land

"Reading a lazy-loaded or un-included navigation property inside a loop fires one new round trip per iteration. The fix is shaping the query itself, up front, with Include or a Select projection — so nothing inside the loop ever has to go back to the database."

  • Query count scales with → the outer result set's size, not a loop count written in code.
  • Include up front → loads the navigation before the loop even starts.
  • Select projection → names just the one field the loop actually needs.
  • The foreach isn't the bug → an un-included navigation access inside it is.
📖 Explanation ▾

Nothing about foreach itself talks to a database. The trigger is what happens inside the loop body: if book.Author wasn't loaded by the original query — no Include, no projection that already pulled it in — then reading book.Author for the first time on each iteration causes a lazy-loading proxy (if enabled) to go fetch it right then, one brand-new query per row.

The EF Core track already owns this from the database-performance side — see "The N+1 Problem" and "Beyond N+1 — Common Performance Pitfalls" for detecting it (query logging, counting statements) and the loading-strategy options in general. This page's job is narrower and LINQ-specific: the query-shape decision that causes or avoids it in the first place. Writing the original query as .Select(b => b.Author.Name) instead of navigating book.Author.Name inside a later loop moves the join into the one original SQL statement — there's nothing left for the loop to lazily trigger.

Include works too, but loads the full related entity rather than just the field used — see "Include vs. Projection Using Select" for that trade-off. Either fix shares the same underlying move: decide what the loop needs before the loop runs, not while it's running.

💻 See the code ▾
C# 
List<Book> books = context.Books.ToList();  // 1 query

foreach (var book in books)
    Console.WriteLine(book.Author.Name);       // ❌ +1 query, every single book

book.Author was never loaded, so each access lazily fetches it — one extra round trip per book.

C# 
List<string> authorNames = context.Books
    .Select(b => b.Author.Name)   // ✅ one join, one SQL query
    .ToList();

foreach (var name in authorNames)
    Console.WriteLine(name);       // already in memory — no extra queries

The join happens once, inside the original query — the loop afterward never touches the database.

🧭 Use Cases — recognize these when they happen to you ▾
1 A foreach reads a lazy-loaded navigation property every iteration

This is the textbook N+1 — nothing about the code looks wrong on screen, and it gets slower in exact proportion to how many rows the outer query returned.

RememberNavigation read inside a loop → one round trip per row.
2 The loop only needs one field off the navigation

A projection naming just the one field the loop reads turns the whole operation into a single SQL join — there's nothing left for the loop to lazily trigger.

RememberOnly need one field → Select it up front, don't navigate in the loop.
3 The loop genuinely needs the whole related entity

When the loop needs more than one field off the related entity, Include up front still avoids the per-row trip — the real decision is Include vs. Select, not whether to fix it at all.

RememberNeed the whole related entity → Include it before the loop, not inside it.
🌍 Real-world example ▾

An order-list endpoint loops over 500 orders and reads order.Customer.Name inside the loop. Nobody wrote "500 queries" anywhere in the code, but that's exactly what runs, because Customer was never included or projected up front — each access lazily fetches it. Changing the original query to .Select(o => new { o.Id, o.Customer.Name }) collapses it back down to the single query it should have been.
