🔥 AWS · Basic · Must Know

CloudWatch watches performance; CloudTrail watches who did what

"How would you set up an alert for high CPU on an EC2 instance, and what's the difference between CloudWatch and CloudTrail?"

Why it matters ▾
  • Monitoring and alerting comes up in almost every AWS interview — anyone running production workloads needs to know how they'll find out something is wrong.
  • Tests a mix-up interviewers actually probe: confusing "how is it performing" with "who did this" because the two service names sound similar.
  • Threshold-based alarms are a practical, hands-on skill — setting one up is a common live-coding or whiteboard ask.
🔥 Easy interview recall

CloudWatch → performance monitoring

CloudTrail → who-did-what audit trail

Think: CloudWatch watches the metrics. CloudTrail watches the people.

📡 CloudWatch vs. CloudTrail — the runtime mechanic
⚠️ Common Trap

Reaching for CloudTrail to debug a performance problem. CloudTrail only tells you which API calls were made and by whom — it has no idea about CPU, memory, or latency; that's squarely CloudWatch's job.

🔄 Likely Follow-up

"How would you detect Lambda failures?" Put a CloudWatch alarm on the function's Errors or Throttles metric, or a metric filter on its CloudWatch Logs that watches for exception patterns.

🎯 Say this in the interview — the exact lines to land

"CloudWatch monitors performance and metrics; CloudTrail audits who did what through the API — genuinely different jobs, not two flavors of the same log."

  • CloudWatch → metrics, logs, dashboards, and alarms — the performance/availability side.
  • CloudTrail → records every API call: who made it, what action, and when — the audit/compliance side.
  • Alarms are threshold-based → they fire when a metric like CPUUtilization crosses a value you set, e.g. above 80%.
  • Pick by the question you're asking → "why is it slow" is CloudWatch; "who did this" is CloudTrail.
📖 Explanation ▾

CloudWatch is AWS's monitoring and observability service. It collects metrics — numeric, time-series data like CPUUtilization or a custom application number — and Logs, the actual text log streams your applications and services write. On top of that you build dashboards to see it visually, and alarms that watch one metric and fire an action the moment it crosses a threshold you define.

CloudTrail is a completely different service, even though the two names sound alike. It doesn't know anything about performance — it records every AWS API call made in your account: which identity made it, which action they called, and exactly when. It's the account's own audit log, not a monitoring tool.

💻 See the code ▾
AWS CLI 
aws cloudwatch put-metric-alarm \
  --alarm-name high-cpu \              -- the alarm's name
  --metric-name CPUUtilization \       -- which metric to watch
  --namespace AWS/EC2 \
  --statistic Average \
  --period 300 \                       -- one 5-minute window
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 1

This alarm fires the moment average CPU is above 80% for one 5-minute period — CloudTrail never enters the picture here, because this is purely a performance check.

🌍 Real-world example ▾

A team gets a CloudWatch alarm the moment an EC2 instance's CPU stays above 80% for 5 minutes straight. Later, they use CloudTrail to check the account's API history and confirm which engineer's automation script accidentally launched the extra instances that drove CPU up in the first place — one tool caught the symptom in real time, the other explained the cause after the fact.
