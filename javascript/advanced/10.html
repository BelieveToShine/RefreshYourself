Service Worker — who actually answers when your page asks for data?

"What is a Service Worker, and how does it make offline support possible in a web app?"

Why it matters ▾
⚙️ Service Worker
❗ ProblemA normal fetch just fails outright the moment there's no network at all — nothing in the page's own code sits in front of it to answer another way.
✅ SolutionA Service Worker sits in the network request path itself and persists independent of any one open page, so it can intercept requests, cache responses, and serve them straight back even fully offline.
RecallService Worker = lives in the request path, outlives the page, makes offline possible.
🧵 Web Worker
❗ ProblemNot every background task is a network request — a worker that persisted past the page and intercepted every request would be the wrong tool for something that's just computation.
✅ SolutionA Web Worker stays scoped to the page that created it, has no special relationship to the network, and exists only to offload computation off the main thread — it ends the moment its page closes.
RecallWeb Worker = scoped to its page, no network role, just offloads computation.
🔥 Easy interview recall

Service Worker → sits between your page and the network

Lifecycle → install → activate → running

Keeps running → even with no tab open

Think: it's a gatekeeper for every request the page makes — once it's active, the page never reaches the network directly.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Registering a Service Worker does not make an app offline by itself. Registration only gives the page a worker that can intercept requests — caching responses and deciding when to serve them is logic you still have to write yourself.

🔄 Likely Follow-up

"If it can run with no page open, does it run forever in the background?" No — the browser can stop an idle Service Worker to save resources and wake it back up on the next relevant event, like a fetch or a push notification; it's event-driven, not a process that stays running non-stop.

🎯 Say this in the interview — the exact lines to land

"A Service Worker is a special kind of worker that sits between the page and the network like a proxy. It goes through an install-then-activate lifecycle before it starts running, and once active it can intercept requests, cache responses, and serve them back even with no network — that's what makes offline support possible. It also isn't tied to one open tab, so it can keep running or get woken up for events on its own. A Progressive Web App builds on exactly this, plus a manifest, to feel like an installable native app."

  • Service Worker → a network proxy between the page and the network — it can intercept every request.
  • Lifecycle → install → activate → running, at a high level.
  • Offline support → comes from caching responses and serving them without touching the network.
  • Background behavior → can keep running or receive events with no page using it currently open.
  • Service Worker vs. Web Worker → a Service Worker sits in the network path and persists independent of any page; a Web Worker is scoped to one page and only offloads computation.
  • PWA → a Service Worker plus a manifest = installable, offline-capable, feels like a native app.
📖 Explanation ▾

A Service Worker is a special kind of worker that sits between your page and the network — once it's registered, it can intercept every request the page makes and decide how to answer it. It goes through a lifecycle before it's actually usable: it's installed first, then activated, and only after that does it start running and intercepting requests. A fresh registration doesn't take control on the very first load — install and activate have to happen first.

It enables offline support because it can cache responses itself and hand them straight back on a later request, with no network involved at all — check the cache first, fall through to a real network request only when nothing matches. Because it isn't tied to one open tab, it can also keep running, or get woken back up, to handle something like a push notification even when the app isn't open in any window.

A Progressive Web App (PWA) builds on exactly this: a Service Worker for offline behavior, plus a manifest file describing the app (name, icon, colors) so the browser can offer to install it to the home screen and run it more like a native app. Both stay high-level here — this page is the mental model, not manifest fields or cache-strategy code.

💻 See the code ▾
JavaScript 
// In the page's own script
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js"); // starts install → activate
}

Registration alone doesn't cache anything — it just hands control to sw.js once it finishes activating.

JavaScript 
// Inside sw.js — this is the actual interception
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) =>
      cached || fetch(event.request) // ✅ cache hit, or fall through to network
    )
  );
});

The proxy decision, in one line: check the cache first, only reach the real network when nothing matches.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app needs to keep working with no network connection at all

Once it's installed and activated, the Service Worker is already sitting in the request path — it can answer straight from its own cache with no network involved, which is exactly what makes offline support possible in the first place.

RememberOffline still works → the Service Worker answers from cache.
2 You just called register() and assume caching is already happening

Registration only starts the install → activate lifecycle and hands control to sw.js once that finishes — it doesn't cache anything by itself. A common trap — deciding what to cache and when to serve it is logic the worker's own fetch handler still has to write.

Rememberregister() ≠ offline yet — caching is your own fetch-handler logic.
3 What you actually need is heavy computation, not network behavior

No network interception, no offline caching, no persisting past the page — just computation that shouldn't block the main thread. That's a Web Worker's job, scoped to the page that created it, not a Service Worker's.

RememberJust need off-main-thread computation → Web Worker, not Service Worker.
🌍 Real-world example ▾

Think of it like a front-desk receptionist who intercepts every call to an office. If they already know the answer, they answer immediately — no need to transfer the call anywhere. Only when they don't know it do they patch the call through to someone else. That's exactly how a Service Worker treats every request the page makes.
