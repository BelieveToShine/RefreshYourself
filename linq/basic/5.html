Any() vs. Count() > 0 — the classic existence-check pitfall

"Why is Any() preferred over Count() > 0 to check for existence?"

Why it matters ▾
🔍 Any() vs. Count() > 0
❗ ProblemChecking "does anything match" by writing Count() > 0 forces an exact count to be computed, even though the caller only needs a yes/no answer.
✅ SolutionAny() short-circuits and stops at the very first match. Count() on a general IEnumerable<T> has to walk the entire sequence to produce an exact number first.
RecallAny() stops at one; Count() walks everything — but only when it actually has to.
🔥 Easy interview recall

Any() → stops at the first match

Count() > 0 → walks the whole sequence first

Think: a List<T>'s Count is already O(1) — the real cost only shows up on a lazy query or a database IQueryable.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming Count() > 0 is always just as fast as Any(). True for a List<T> or array — false, and potentially costly, for a lazy LINQ query or an EF Core IQueryable, where it changes the actual SQL that gets generated.

🔄 Likely Follow-up

"Does this matter on a List<T>?" Not really — List<T> and arrays implement ICollection<T>, which keeps Count as a stored field, so it's already O(1). The real cost only appears on a general IEnumerable<T> that's still a lazy query, or on an IQueryable<T> against a database.

🎯 Say this in the interview — the exact lines to land

"Any() short-circuits — it stops at the very first match. Count() on a general IEnumerable<T> has to walk the entire sequence to produce an exact number, even though you only wanted yes or no. On a List<T> or array there's no real difference, since Count is already a stored field — the risk is a lazy query or a database IQueryable, where Count() can force a full scan instead of the short-circuit Any() gets."

  • Any() → stops at the first match, every time.
  • Count() > 0 → walks the whole sequence on a lazy IEnumerable or IQueryable.
  • List<T> / array → no real difference — Count is already O(1).
📖 Explanation ▾

Any() is a short-circuiting check: it asks "is there at least one?" and returns the moment it finds one, without looking at anything after it.

Count() answers a different question — "exactly how many?" — and on a plain IEnumerable<T> with no fast path, the only way to answer that honestly is to look at every element. Comparing the result to 0 afterward doesn't get any of that work back. The one exception worth knowing: collection types that implement ICollection<T> (List<T>, arrays) already track their count in a stored field, so Count there is O(1) — the difference only matters for a source that's still a lazy query, in memory or against a database.

💻 See the code ▾
C# 
bool hasAdmin = users.Any(u => u.Role == "Admin");        // ✅ stops at the first admin found

One match is enough — the rest of users is never looked at.

C# 
bool hasAdmin = users.Count(u => u.Role == "Admin") > 0;  // ❌ counts every admin first

Same answer, but every matching user gets counted before the > 0 check even runs.

🧭 Use Cases — recognize these when they happen to you ▾
1 Checking existence on a lazy LINQ query

A query that's still a lazy IEnumerable<T> pipeline hasn't materialized anything yet — Any() keeps that cheap by stopping at the first match. This is the #1 case the difference is real.

RememberLazy query → Any() avoids walking the whole thing.
2 Checking existence on an already-materialized List<T> or array

Count on a List<T> or array is a stored field — no walk happens either way. Any() still reads as clearer intent, but there's no real performance difference to defend here.

RememberList/array → Count is O(1), performance is a non-issue.
3 Calling Count() > 0 on an EF Core IQueryable

Any() translates to an EXISTS-style query that stops at the first matching row. Count() > 0 translates to a full COUNT(*) that has to tally every matching row before the comparison even runs — same answer, a measurably heavier query.

RememberIQueryable → Any() becomes EXISTS, Count() > 0 becomes COUNT(*).
🌍 Real-world example ▾

It's checking "is there any mail in the box" two ways. Any() opens the lid and stops the moment it sees one envelope. Count() > 0 pulls out and counts every single envelope first, then answers "yes" with a number it never needed.
