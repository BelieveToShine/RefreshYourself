Multiprocessing helps CPU-bound work because each process gets its own GIL — the price is serialization overhead crossing process boundaries

"Why does multiprocessing actually help CPU-bound workloads where threading doesn't?"

Why it matters ▾
🏭 Separate GILs
❗ ProblemThreads share one GIL, so CPU-bound work never runs in parallel, even on a multi-core machine.
✅ Solutionmultiprocessing starts separate processes, each with its own interpreter, memory and GIL, so CPU-bound work runs on several cores at once.
RecallProcesses = separate GILs = real CPU parallelism.
📦 Serialization cost
❗ ProblemProcesses do not share memory, so every value crossing a process boundary is pickled and unpickled, and for large objects that can eat the parallel gains.
✅ SolutionPass data explicitly with a Queue or Pool, and use processes when the CPU work outweighs the cost of moving the data.
RecallParallel gain minus pickling cost.
🔥 Easy interview recall

Threading → one process, one GIL — no real parallel CPU

Multiprocessing → separate processes, separate GILs — real parallel CPU

Think: multiprocessing trades one shared GIL for N processes, each paying a serialization tax to talk to each other.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Multiprocessing is always faster than threading" is not true. For I/O-bound work, or when the data passed between processes is large, the process-startup and pickling overhead can cost more than the GIL ever did — threading or asyncio is often the cheaper, right tool there.

🔄 Likely Follow-up

"When is multiprocessing a bad choice?" I/O-bound workloads (threading or asyncio is lighter-weight and better suited); work needing frequent, large data exchange between workers (serialization overhead dominates); and very short-lived tasks where process-startup overhead outweighs the work itself.

🎯 Say this in the interview — the exact lines to land

"Multiprocessing gets real parallel CPU execution because each process has its own GIL — the cost is serialization overhead moving data across process boundaries."

  • Pool → manages worker processes for you, distributing work through .map() or .apply_async().
  • Queue → a safe way to pass messages or results between processes that don't share memory.
  • Every value crossing a process boundary gets pickled and unpickled — that's the real cost multiprocessing pays.
  • Wrong tool for I/O-bound work or huge payloads — threading, asyncio, or smaller task chunks is the fix there instead.
📖 Explanation ▾

Threading shares one process's memory and one GIL across every thread it spawns — even on a multi-core machine, only one thread runs Python bytecode at a time, so CPU-bound work never actually runs in parallel. multiprocessing sidesteps that limit entirely: it spins up separate OS processes, each with its own Python interpreter, its own memory space, and its own GIL — so CPU-bound work genuinely runs across multiple cores at the same time.

Because processes don't share memory, they can't pass a Python object by reference the way threads can — data has to be explicitly sent between them. multiprocessing.Queue is a thread-and-process-safe FIFO for passing messages or results between processes, and Pool manages a fixed set of worker processes for you, handling the process lifecycle and distributing work through .map() or .apply_async().

Starting a new process has real overhead — spawning a fresh interpreter, and on platforms where the default start method re-runs your script, re-importing your module too — heavier than starting a thread. And every value that crosses a process boundary must be pickled on one side and unpickled on the other; for large or complex objects, that serialization cost is a genuine bottleneck, and can eat into or even exceed the parallel gains multiprocessing was supposed to provide.

💻 See the code ▾
Python 
from multiprocessing import Pool

def cpu_heavy_func(chunk):
    return sum(x * x for x in chunk)  # pure CPU work, no I/O

if __name__ == "__main__":            # ✅ required so workers don't re-spawn this
    with Pool() as pool:                # one worker process per CPU core, by default
        results = pool.map(cpu_heavy_func, data_chunks)  # each chunk pickled to a worker

Pool.map() pickles each item in data_chunks, sends it to a worker process, runs cpu_heavy_func there, then pickles the return value back — keep each chunk small, or that pickling cost eats the parallel speedup you were after.

🌍 Real-world example ▾

A data pipeline had an image-resizing step running on a thread pool — the actual resizing math is CPU-bound, so it never sped up no matter how many threads were added, because the GIL kept every thread's real work serialized onto one core. Switching that one step to a multiprocessing.Pool spread the resizing work across every core and got close to linear speedup. The team still had to keep each task's payload small — passing just the image path instead of the raw pixel bytes — otherwise the cost of pickling large image buffers across the process boundary started eating the gains multiprocessing was supposed to provide.
