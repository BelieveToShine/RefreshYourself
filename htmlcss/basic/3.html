Forms & Validation — the browser's checks are a courtesy, the server's are the lock

"How would you validate a form, and can you actually trust validation that runs in the browser?"

Why it matters ▾
  • Almost every real app has a form somewhere — login, checkout, search, settings — and getting name/value and GET vs. POST wrong sends the wrong data to the wrong place.
  • "Never trust client input" is one of the most common follow-up lines in any web interview, not just security-focused ones.
  • Skipping a real <label> in favor of a placeholder is an easy, extremely common accessibility mistake that shows up in real code review.
🔥 Easy interview recall

Client-side → fast feedback, but skippable

Server-side → the real security boundary

Think: required/pattern are UX, not security — the server never gets to skip its own check.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It already passed required/pattern in the browser, so the data is valid." Those attributes only stop the browser's own form UI — a request sent straight to the same endpoint via DevTools, curl, or a rewritten client skips them completely, so the server has to validate the exact same fields again on its own.

🔄 Likely Follow-up

"If the server re-checks everything anyway, why bother with client-side validation at all?" Speed and experience — it gives instant feedback with no round trip and keeps obviously-bad requests from ever leaving the browser, but that's a UX improvement, not a security measure; the server's check is the one that actually protects the data.

🎯 Say this in the interview — the exact lines to land

"A form's inputs are sent as name/value pairs — as a GET query string or a POST request body depending on the method. Native attributes like required, pattern, and min/max give the browser built-in validation before any JavaScript runs, but that check happens on the client and can be bypassed, so the server has to validate the same data again — client-side validation is for user experience, server-side is the actual security and data-integrity boundary."

  • GET → idempotent and cacheable, data sits in the URL — use it for reads, never for anything that changes state.
  • POST → sends data in the request body — use it for anything that creates, changes, or deletes data.
  • Every input needs a real <label>, not just a placeholder — a placeholder disappears the moment someone starts typing.
  • Native attributes (required, pattern, min/max) run before JavaScript, but can be removed or bypassed by anyone controlling the request.
  • Server validation is mandatory, not optional — a direct API call never goes through the browser's form at all.
📖 Explanation ▾

A <form> collects input and sends it somewhere. Each field has a name (the key the server reads) and a value (what the user typed or picked) — common input types are text, email, number, checkbox, and radio, each giving the browser a slightly different keyboard, keyboard layout, or picker. A <label> ties a piece of text to its field, either by wrapping the input or by matching a for attribute to the input's id.

The form's method decides how the data travels. GET appends the fields to the URL as a query string — it's idempotent (repeating it is safe) and cacheable/bookmarkable, which is why it's the right choice for reads and searches. POST sends the fields in the request body instead, which is what any state-changing submission — login, checkout, saving a record — should use.

GETPOST
Where data goesAppended to the URL as a query stringSent in the request body
Idempotent / cacheableYes — safe to repeat, browsers can cache or bookmark itNo — meant to change something on the server
Typical useSearch, filtering, reading dataLogin, checkout, anything that creates or changes data
Data visibilityVisible in the URL and browser historyNot shown in the URL

Before any JavaScript runs, the browser already applies native validation: required blocks an empty field, pattern checks against a regular expression, min/max bound a number or date, and autocomplete hints what kind of value a field expects. A field failing any of these shows the browser's own validation bubble and the form never submits.

A real <label> matters for reasons a placeholder can't cover: the label grows the clickable/tappable target to the whole label text, not just the small input box; a screen reader announces the label as the field's name every time it's focused; and a placeholder's text disappears the moment someone starts typing, so it can never work as a persistent name for the field.

Client-side validation is for fast feedback — it tells the user about a mistake in milliseconds, with no network round trip. It is never a security boundary on its own, because anything running in the browser is under the user's control and can be edited or skipped. Server-side validation is the real boundary — the same checks have to run again on the server, independent of whatever the client already did, because that's the only validation an attacker can't bypass by sending the request a different way.

💻 See the code ▾
HTML 
<label for="email">Email</label>
<input id="email" name="email" type="email" required> <!-- native check -->
<input name="age" type="number" min="18" max="120"> <!-- range check -->

required, type="email", and min/max all run in the browser before submit — no JavaScript needed.

HTML 
<form method="get" action="/search"> <!-- read: q ends up in the URL -->
<form method="post" action="/checkout"> <!-- state change: body, not URL -->

Same shape, different method — get for reading, post for anything that changes data on the server.

🌍 Real-world example ▾

Picture a club's door greeter and the register's ID scanner. The greeter (client-side validation) gives a quick look and waves obvious problems away fast — but someone can walk in through a side door and skip the greeter entirely. The register's scanner (server-side validation) has to check ID every single time, no matter which door someone came through, because that's the check nobody can walk around.
