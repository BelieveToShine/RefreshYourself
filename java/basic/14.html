Four levels, one spectrum — no combining them

"What are the access modifiers in Java, and how do they differ from something like C#'s protected internal?"

Why it matters ▾
🔒 private
❗ ProblemNothing would stop another class from reaching straight into a field and setting it to an invalid value, bypassing any logic that's supposed to guard it.
✅ Solutionprivate limits access to the containing class only — even a subclass in the same file can't reach it directly.
Recallprivate = this class only — the narrowest of all.
📦 default (package-private)
❗ ProblemClasses that belong together in the same package often need to share helper members, but making every one of them public would expose internal wiring to every outside caller too.
✅ SolutionWriting no modifier at all grants access to any class in the same package — a real, deliberate level, not "forgot to write one."
RecallNo modifier = same package only, still a real access level.
👪 protected
❗ ProblemA base class needs to hand state to subclasses for real inheritance to work, even when a subclass lives in a completely different package from the parent.
✅ Solutionprotected grants the same-package access default already gives, plus any subclass anywhere, in any package.
Recallprotected = same package + subclasses, any package.
🌐 public
❗ ProblemA class's real entry points need to be callable from any other code in any package, or the class is useless to any outside caller.
✅ Solutionpublic is accessible from anywhere — the broadest of the four, reserved for the actual API surface.
Recallpublic = accessible from anywhere, full stop.
🔥 Easy interview recall

private → this class

(no modifier) → same package

protected → package + subclasses

public → everyone

Think: each level is a superset of the one before it — Java has no way to combine two of them into a fifth option, unlike C#'s protected internal.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

protected is not "subclasses only." It also includes every class in the same package, with no inheritance relationship required at all — the same access default already grants, plus subclasses anywhere.

🔄 Likely Follow-up

"Why doesn't Java have a protected internal-style combined modifier like C#?" Because it doesn't need one — Java's protected already bundles "same package" (what default covers) together with "subclass, any package," so there's no gap for a separate combinable modifier to fill.

🎯 Say this in the interview — the exact lines to land

"Java has four access levels — private, default (package-private), protected, and public — each one a strict superset of the one narrower than it. Unlike C#, there's no combinable modifier: protected already includes same-package access, so it doesn't need an internal-style partner."

  • No modifier written → package-private, a real deliberate level.
  • protected → package AND subclasses, not subclasses alone.
  • Default for a top-level class → package-private if no modifier is written.
📖 Explanation ▾

Think of the four levels as nested rings, each one strictly bigger than the last. private allows only the containing class — not even a subclass in the same file gets in. Writing no modifier at all gives package-private (sometimes just called "default") access: any class compiled into the same package, with zero inheritance relationship required. protected takes everything package-private already allows and adds one more group: subclasses, even ones that live in a totally different package. public is accessible from anywhere, no restriction at all.

This is exactly why Java never needed a combinable modifier the way C# has protected internal (an OR of two independent boundaries — assembly and inheritance). In C#, internal and protected check two separate things that don't overlap on their own, so a combined OR/AND modifier adds real new options. In Java, protected is already defined to include package access — it's a superset of default, not an independent axis — so every possible combination is already covered by one of the four existing keywords.

💻 See the code ▾
☕ Java 
public class Account {
    private double balance;      // this class only
    String branchCode;          // no modifier — same package only
    protected String owner;      // package + subclasses anywhere
    public String accountNumber; // anywhere
}

Four fields, four different visibility rules — same class, same syntax pattern.

☕ Java 
Account acc = new Account();
acc.accountNumber = "123";   // ✅ public — always fine
acc.balance = 100;           // ❌ balance has private access in Account

Reaching a private member from outside the class is a compile-time error, not a runtime surprise.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your base class ships in one package, and a subclass lives in a completely different one

protected crosses the package boundary automatically as long as the accessing class really is a subclass — there's no package restriction on protected at all once inheritance is in play.

Rememberprotected reaches across packages through inheritance alone.
2 Two unrelated classes in the same package need to share a helper, without exposing it outside

Leaving off the modifier entirely gives both classes access with no inheritance relationship needed — exactly the package-private level, used deliberately rather than left blank by accident.

RememberNo modifier = same package, zero family relationship required.
3 You read protected and assume only a subclass can reach it

Both get in — a subclass in a different package, and any unrelated class that merely shares the same package. Only excluding both of those groups fails the check.

Rememberprotected = package OR subclass, not subclass alone.
🌍 Real-world example ▾

An office building. private is your own locked office. Writing no modifier is your whole floor having a key (same package). protected is that same floor, plus anyone from a "family" department even if they sit on another floor entirely (subclasses). public is the lobby — open to anyone who walks in.
