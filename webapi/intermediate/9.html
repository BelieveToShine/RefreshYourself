JWT — signed, not secret

"What's actually inside a JWT, and why use a refresh token instead of a long-lived access token?"

Why it matters ▾
  • Interviewers ask this to check you know a JWT is signed, not encrypted — a real source of security bugs when secrets end up in the payload.
  • Comes up the moment an API design conversation moves past "just use JWT" into how access actually gets renewed and revoked.
  • A common lead-in to a revocation/security follow-up — see below.
🔥 Easy interview recall

header → algorithm + token type

payload → claims, readable by anyone

signature → proof, not encryption

Think: JWT is signed, not sealed — readable by anyone, forgeable by no one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A long-lived access token isn't "more convenient," it's unrevocable. JWTs are self-contained by design — a leaked long-lived token stays valid for its entire lifetime with no way to cancel it early, unless extra server-side infrastructure (a denylist) is built specifically to check for that.

🔄 Likely Follow-up

"If JWTs are stateless, how do you actually revoke one immediately if it's compromised?" Generally you can't cleanly — the practical answer is a short access-token lifetime plus a server-side revocation list checked on each request, which quietly reintroduces some of the statefulness JWT was meant to avoid.

🎯 Say this in the interview — the exact lines to land

"A JWT has three base64url-encoded parts — header, payload, and signature — separated by dots. The signature proves the header and payload weren't tampered with; it does not encrypt them, so anyone can read the payload. Access tokens are kept short-lived on purpose, and a longer-lived refresh token is exchanged for a new access token so the user isn't forced to log in again — and because the refresh token, unlike the access token, is checked against server state, it's the one that can actually be revoked."

  • header.payload.signature → signed, never encrypted.
  • Payload claims → readable by anyone, never put secrets in one.
  • Short access + long refresh → small exposure window, real revocation point.
  • Long-lived access token instead → convenient but unrevocable.
📖 Explanation ▾

A JWT is three base64url-encoded segments joined by dots — not an encrypted blob. The signature is a cryptographic hash computed over the header and payload using a key only the server holds; verifying it means recomputing that same hash and comparing, which proves the content wasn't altered. It proves nothing about who can read the payload — that part was always just base64, decodable by anyone with no key at all.

That's exactly why access tokens are kept short-lived: a JWT can't be individually cancelled once it's out in the world, so the only real defense against a leaked one is making it expire soon. A refresh token is what makes that tolerable — it's longer-lived, stored more carefully, and unlike the access token, the server actually keeps a record of it. Exchanging it for a new access token means the user never re-enters credentials, but every exchange is a chance for the server to say no.

💻 See the code ▾
C# 
var parts = token.Split('.');
var payloadJson = Encoding.UTF8.GetString(
    Base64UrlDecode(parts[1]));   // ✅ no secret key needed to read this

Console.WriteLine(payloadJson);
// {"sub":"1234","role":"admin","exp":1735689600}

Decoding the payload takes zero cryptography — only producing a valid new signature does.

C# 
// ❌ Never put secrets in the payload — anyone can decode this
var badClaims = new[] { new Claim("password", user.PlainTextPassword) };

// ✅ Claims should only carry identity/authorization data
var goodClaims = new[] {
    new Claim(JwtRegisteredClaimNames.Sub, user.Id),
    new Claim(ClaimTypes.Role, user.Role)
};

Same payload mechanics either way — the only difference is what you choose to put in it.

C# 
[HttpPost("refresh")]
public IActionResult Refresh(string refreshToken)
{
    var stored = _store.Find(refreshToken);     // ✅ checked against server state
    if (stored is null || stored.IsRevoked)
        return Unauthorized();                // ❌ this is the actual revocation point

    var newAccessToken = _tokens.IssueAccessToken(stored.UserId);  // short-lived, e.g. 15 min
    return Ok(new { accessToken = newAccessToken });
}

The access token itself is never looked up in a database — only the refresh token is, and that's exactly where revocation becomes possible.

🌍 Real-world example ▾

A JWT's payload is a printed name badge; the signature is the hologram sticker on it. Anyone nearby can read the badge — the hologram doesn't hide the print, it just proves the badge wasn't forged.

Scenario: a user's laptop is stolen while logged in. With only a long-lived access token, nothing stops it working until it naturally expires — hours or days later. With the short-access + refresh pattern, revoking that one refresh token blocks every future renewal; the stolen access token still works for its last few minutes, but the account is effectively locked out almost immediately after.
