Retrieval keeps missing the answer — do you need a smarter architecture, or just better basics?

"Your RAG system's retrieval quality is off — when would you reach for GraphRAG or an agentic retrieval loop instead of just improving chunking, hybrid search, or reranking?"

Why it matters ▾
  • Senior/architect RAG interviews push past the basic pipeline to see whether you know these refinements exist — and, more importantly, whether you know when each one is actually the right fix, not just the name of it.
  • Reaching for GraphRAG or an agent loop when better chunking, hybrid search, or reranking would already solve the problem is a real architecture smell interviewers listen for.
  • All four build directly on the basic pipeline from The RAG Pipeline End to End — this page assumes that shape and doesn't re-explain it.
🔥 Easy interview recall

GraphRAG → connect entities, not just chunks

Agentic RAG → retrieve, check, retry — dynamically

Parent-document → small chunk to find it, big chunk to answer it

Contextual retrieval → add context before embedding

Think: the basic pipeline is one fixed pass over isolated chunks — each of these four fixes a specific way that assumption breaks down.

⚠️ Common Trap

Reaching for GraphRAG or an agent loop as the first fix for a retrieval-quality problem. Most retrieval problems are still solved by the basic-pipeline levers — better chunking, hybrid search, or reranking — before any of these four architectural refinements are actually needed.

🔄 Likely Follow-up

"What stops an agentic RAG loop from retrying forever?" The same guardrails as any agent loop — a maximum number of retrieval attempts, or a check that the reformulated query is actually making progress — otherwise a query that genuinely has no good answer just keeps triggering another retrieval pass.

🎯 Say this in the interview — the exact lines to land

"Before reaching for a more sophisticated retrieval architecture, I'd confirm better chunking, hybrid search, or reranking wouldn't already fix it. If the real problem is multi-hop reasoning across documents, I'd reach for GraphRAG; if it's a single retrieval pass sometimes not getting enough context, I'd make retrieval agentic so it can decide to retry with a reformulated query."

  • GraphRAG → use when the answer connects facts across multiple documents, not one chunk that directly answers it.
  • Agentic RAG → use when a single retrieval attempt sometimes isn't enough and the system should retry instead of giving up or guessing.
  • Parent-document retrieval → use when small chunks match well but lack context — match small, then hand the model the larger parent section.
  • Contextual retrieval → use when chunks are ambiguous read on their own — enrich each one with a short summary before embedding it.
  • All four are refinements on top of the basic pipeline — never the first thing to reach for.
📖 Explanation ▾

GraphRAG builds (or uses) a knowledge graph of entities and their relationships extracted from the source documents, alongside or instead of plain text chunks. Retrieval can then traverse relationships between entities — what connects to what — rather than relying purely on the semantic similarity of chunk text. This is what makes it possible to answer a question that requires connecting several pieces of information spread across documents, instead of finding one chunk that directly answers it.

Agentic RAG takes the fixed retrieve-then-generate pass and puts it inside an agent loop: the system can decide, dynamically, whether to retrieve again, retrieve from a different source, or reformulate the query — based on whether the first attempt actually got what's needed. If the retrieved context doesn't look sufficient to answer, the agent retries with a refined query instead of giving up or generating an answer it can't actually support.

Parent-document (small-to-big) retrieval and contextual retrieval both fix a chunk-level problem rather than a pipeline-level one. Parent-document retrieval matches on small, precise chunks — good for retrieval accuracy — then expands to the larger parent document or section those chunks belong to when assembling the final context, balancing precise matching with enough surrounding context for the model to actually use. Contextual retrieval enriches each chunk with extra context (e.g. a short summary of the document it came from) before embedding and indexing it, so the chunk's own embedding captures more of its true meaning even when read in isolation.

💻 See the code ▾
Python 
# AGENTIC RAG — the agent decides whether to retry
query = user_query
for attempt in range(max_attempts):
    chunks = retrieve(query)
    if is_sufficient(chunks, user_query):   # the decision step
        break
    query = reformulate(user_query, chunks)  # retry with a refined query
answer = generate(user_query, chunks)

The stopping check and max_attempts are the same guardrails any agent loop needs — without them a genuinely unanswerable query just keeps retrying.

Python 
# PARENT-DOCUMENT (small-to-big) retrieval
small_hits = index.search(query_vector, k=10)  # match on small, precise chunks
parent_ids = {hit.parent_id for hit in small_hits}
context = [get_parent_document(pid) for pid in parent_ids]  # expand to the larger section

Matching happens on the small chunk for precision; the model actually reads the larger parent section so it has enough surrounding context to use.

🌍 Real-world example ▾

A compliance assistant is asked whether a recent incident violates a specific policy — the answer depends on connecting the incident report to a policy clause that was updated in a separate document months later. No single chunk states that connection; a plain vector search over isolated chunks keeps returning "relevant-looking" but incomplete text. A GraphRAG index, built with entities like "incident," "policy clause," and "update date" and the relationships between them, can traverse that connection directly instead of hoping one chunk happens to contain it.
