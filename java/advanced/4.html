Still reachable, no longer needed — how Java leaks anyway

"How can a Java application leak memory even though it has a garbage collector?"

Why it matters ▾
🧟 A "Leak" in a GC'd Language
❗ ProblemAssuming the garbage collector makes memory bugs impossible leads teams to miss the much more common bug: an object the program is logically done with that something still refers to, so the heap keeps growing anyway.
✅ SolutionA GC can only collect what's unreachable — a reference it never knows is "stale" keeps the object alive correctly, by its own rules, while the app slowly runs out of memory.
RecallThe GC isn't wrong — the code is still holding a reference it shouldn't be.
🔥 Easy interview recall

Java memory leak = "an object that's still reachable, but the program is actually done with it."

Think: growing static collections, forgotten listeners, stale ThreadLocal values, unbounded caches.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Java doesn't leak memory because it has a garbage collector" is wrong. The GC only frees what's unreachable — a reference the code simply forgot to drop (a growing static list, a never-unregistered listener) keeps the object alive correctly by the GC's own rules, which is exactly how Java leaks.

🔄 Likely Follow-up

"How would you actually find one of these in production?" Take a heap dump and look at what's retaining the most memory and through what reference chain (see the dedicated Heap Dumps page) — the GC log alone won't show *why* something is still reachable, only that the heap keeps growing.

🎯 Say this in the interview — the exact lines to land

"A Java memory leak isn't a GC bug — it's an object that's still reachable from a GC root, so the collector correctly refuses to collect it, even though the program logically no longer needs it. Common causes are a growing static collection nothing removes from, listeners registered but never unregistered, a ThreadLocal value outliving its task in a pooled thread, and an unbounded cache with no eviction policy."

  • Static collection → grows forever if nothing ever removes entries.
  • Listeners/callbacks → leak if never unregistered, especially across long-lived publishers.
  • ThreadLocal in a pool → value outlives the task that set it unless explicitly cleared.
  • Unbounded cache → no eviction policy means no upper bound on retained memory.
  • The fix is always the same → find and break the reference chain, not "collect harder."
📖 Explanation ▾

Garbage collection is a reachability algorithm, not an "is this still useful" algorithm — it walks from a set of GC roots (static fields, local variables on active stacks, JNI references) and anything it can reach through that walk survives. A reference the program never clears is, to the GC, indistinguishable from a reference the program is actively using.

The usual suspects share one shape: something long-lived (a static field, a singleton, a thread-pool thread that outlives any one task) holds a reference to something that was supposed to be short-lived. A listener registered with a long-lived event source and never removed keeps every object it closes over alive for as long as that source exists. A ThreadLocal set inside a pooled thread and never remove()d survives to be reused — and misread — by whatever task that thread picks up next. An unbounded cache is a leak by design unless something (size limit, TTL, weak references) eventually evicts entries.

The fix is always the same shape: find the reference chain keeping the object alive, and break it deliberately — remove the entry, unregister the listener, clear the ThreadLocal, or add an eviction policy. "Run the GC more" never helps, because the object is reachable on purpose, even if by accident.

💻 See the code ▾
Java 
static final List<Order> cache = new ArrayList<>();

void handleOrder(Order order) {
    cache.add(order); // ❌ nothing ever calls cache.remove(order)
}

Every Order ever handled stays reachable through this static list forever — the heap grows with every request, by design of this bug.

Java 
static final ThreadLocal<User> currentUser = new ThreadLocal<>();

void handleRequest(User user) {
    currentUser.set(user);
    // ... handle the request ...
    // ❌ no currentUser.remove() — on a pooled thread, this value outlives the request
}

On a thread-pool thread, the thread itself is reused — without remove(), the previous request's User stays reachable (and can even leak into the next, unrelated request).

🧭 Use Cases — recognize these when they happen to you ▾
1 Heap usage climbs steadily, request after request, with no drops

A heap graph that only ever climbs, even right after a full GC, is the signature of a growing reachable collection — something is being added that nothing ever removes.

RememberHeap never drops after full GC → something reachable keeps growing.
2 UI components or publishers get swapped out, but old subscribers don't disappear

An event source that outlives whatever registered with it keeps every un-removed listener (and everything that listener closes over) reachable — a classic leak in long-running UI apps and pub/sub-style services alike.

RememberLong-lived publisher → every un-removed listener stays reachable too.
3 A pooled worker thread occasionally sees another request's leftover data

A candidate often assumes ThreadLocal values automatically disappear when a task ends. They don't. In a thread pool the thread itself survives to run the next task, so a value set but never remove()d stays reachable — and can even get read by whichever unrelated task runs next on that same thread.

RememberPooled thread → always remove() a ThreadLocal when the task ends.
🌍 Real-world example ▾

A long-running service gets slower and eventually throws OutOfMemoryError after running for days, but works fine right after a restart. That pattern — fine at first, steadily worse over time, cured by a restart — almost always points at something reachable growing without bound, not at a sudden single bad request; a heap dump comparison between "just started" and "about to fail" usually shows exactly which collection kept growing.
