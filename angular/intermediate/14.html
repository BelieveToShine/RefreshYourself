A route guard is just a function now — not a class you have to inherit from

What's the difference between a class-based CanActivate guard and a functional guard, and what does CanMatch add that CanActivate doesn't?

Why it matters ▾
  • Functional guards are the current recommended style for new route configs — interviewers check you know the shift, not just the older class-based syntax.
  • Comes up any time you're protecting a feature area, or building route trees that differ by role or feature flag.
  • CanMatch vs. CanActivate is a favorite follow-up trap — both sound like "can this navigation proceed," and they're not testing the same thing.
🔥 Easy interview recall

CanMatch → is this config even ELIGIBLE?

CanActivate → already matched — allowed to activate?

Think: a functional guard is just a function (CanActivateFn) — no class, no interface, registered right in the route config.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ngOnInit doesn't always fire again just because a route parameter changed. Navigating from /users/1 to /users/2 can reuse the same component instance for the same route config, so the fix is subscribing to ActivatedRoute.paramMap — which DOES emit on every parameter change — not assuming a lifecycle hook will catch it.

🔄 Likely Follow-up

"If CanMatch returns false, does the navigation fail?" Not necessarily — the router just treats that route config as not matching and tries the next config that could also match the same path; a CanActivate guard returning false, by contrast, blocks or redirects the navigation outright instead of trying an alternate config.

🎯 Say this in the interview — the exact lines to land

"A class-based CanActivate guard and a functional guard decide the exact same thing — whether a navigation may proceed — the difference is purely structural: a class implementing CanActivate versus a plain function matching CanActivateFn, which is less boilerplate and the current recommended style. CanMatch is a different question entirely — it decides whether a route config is even eligible to match at all, before one is selected, so returning false there lets the router try a completely different config for the same URL, which CanActivate alone can never do."

  • Functional guard → a plain function, registered directly in canActivate: [...], can use inject().
  • CanMatch → eligibility, before selection — false tries another config.
  • CanActivate → activation, after selection — false blocks or redirects.
  • Route-level providers → a fresh injector scoped to that feature, alive only while it's active.
  • Lazy loading + standalone → loadComponent/loadChildren download only on navigation.
  • A resolver's Observable that never completes → navigation just hangs on the previous page, no visible error.
📖 Explanation ▾

A functional guard is a plain function matching a signature like CanActivateFn, instead of a class implementing an interface — it's registered directly in the route config (canActivate: [authGuard]) rather than through a provider, and it can call inject() internally because it still runs inside an injection context. It's functionally equivalent to a class-based guard — both decide whether a navigation may proceed — the difference is purely structural, and functional is the current recommended style for new code, the same standalone-first shift seen elsewhere in modern Angular.

CanMatch asks a different question than CanActivate: whether a route config is even eligible to match a given URL at all, before any route has been selected. That's what makes it uniquely useful for serving entirely different route trees for the same URL — a feature flag or a user's role can pick between two whole route configs, something CanActivate can't do, since it only ever allows, blocks, or redirects the one route it's already attached to.

A resolver runs before a route activates, and its return value becomes available to the activated component through ActivatedRoute data. The easy-to-miss part: if the resolver's Observable never completes — a Subject nobody ever completes, or a stream with no natural end — the router just keeps waiting for it, so the navigation never finishes and the user stays stuck on the previous page indefinitely, with no visible error at all.

Preloading works at two speeds: the built-in PreloadAllModules loads every lazy route's code in the background right after the app starts, while a custom strategy implements PreloadingStrategy's preload(route, load) to call load() only for routes that meet your own condition — a user's role, or a deliberate delay — and skip the rest.

Nested routes — declared inside a parent route's own children array — render into that parent's own <router-outlet>, which is how a shared layout wraps a whole family of sub-routes. Separately, Angular's router may reuse an already-instantiated component across a parameter change on the "same" route config, which is why relying on ngOnInit alone to react to a changing /users/:id is the trap above — a custom RouteReuseStrategy is the other way to control it.

For a large application, the practical pattern is feature-based route trees — each feature area owns its own lazy-loaded route file, with its guards and resolvers kept close to that feature instead of centralized in one giant file — plus a deliberate preloading policy: not preloading everything blindly, not preloading nothing either.

💻 See the code ▾
TypeScript 
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);   // ✅ inject() works — runs inside an injection context
  return auth.isLoggedIn() || inject(Router).parseUrl('/login');
                                          // ❌ not logged in → returns a UrlTree, router redirects
};

Just a function matching CanActivateFn — no class, no interface, no boilerplate.

TypeScript 
this.route.paramMap.subscribe(params => {  // ✅ emits on EVERY param change
  this.userId = params.get('id');
  this.loadUser();                       // re-fetches even if the instance is reused
});

Relying on ngOnInit alone misses this — Angular can reuse the same component instance across a param change, so ngOnInit may only ever fire once.

🌍 Real-world example ▾

Two different bouncers. CanMatch is the bouncer deciding whether a specific venue even applies to your ticket type at all — if not, you're sent to try the venue next door. CanActivate is the bouncer at the door of the venue you're already confirmed to be attending, deciding whether you personally get let in right now.
