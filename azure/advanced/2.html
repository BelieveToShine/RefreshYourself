500s in production — is it the code, or something downstream?

Your API is deployed to Azure App Service and suddenly starts returning 500 errors. How would you troubleshoot it?

Why it matters ▾
  • A production 500 spike is a real on-call scenario, not trivia — how you triage it tells an interviewer more about seniority than knowing every Azure service name.
  • Jumping straight to "roll back the code" without checking evidence first can waste precious minutes, or fix nothing, if the real cause is somewhere else entirely.
  • This is a favorite senior/architect scenario question because it tests process under pressure, not memorized facts.
🔥 Easy interview recall

1. Deploy → did something just ship?

2. Dependency → is something downstream down?

3. Metrics → is CPU/memory maxed out?

Think: Log Stream shows you what broke, App Insights shows you when it broke — check both before you touch anything.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A sudden batch of 500s doesn't always mean new code shipped. A downstream dependency (a database, an external API) failing produces the exact same symptom, and checking dependency health or Application Insights takes minutes — rolling back code as the first move can waste time, or be the wrong fix entirely.

🔄 Likely Follow-up

"What's the fastest safe mitigation while you're still diagnosing?" If a deployment slot swap was involved, swap back immediately — it's near-instant and reversible — while root-causing in parallel, rather than waiting for a full diagnosis before doing anything.

🎯 Say this in the interview — the exact lines to land

"Check recent deploys, dependency health, and resource metrics — in that order — before assuming it's a code bug. If a slot swap shipped the change, swap back immediately since it's fast and reversible, and keep root-causing the real issue in parallel."

  • Log Stream / Diagnostics → first stop for the actual exception — see the real error before guessing.
  • Application Insights Failures blade → the exact stack trace, correlated against the deployment timeline.
  • Dependency health → produces an identical symptom to a bad deploy — check it before rolling back code.
  • CPU/memory near 100% → timeouts that look like exceptions, not a real code defect.
  • Slot swap involved → swap back immediately — near-instant and fully reversible.
📖 Explanation ▾

Start with the App Service's own Diagnostics / Log Stream — it's the fastest way to see the actual exception as it's thrown, live, with no extra setup. From there, Application Insights' Failures blade gives the exact stack trace and lets you correlate the first failing request against the deployment timeline — a bad deploy is the single most common real cause of a sudden 500 spike, so checking "did anything ship recently" early is worth it.

If nothing shipped, check whether a downstream dependency — a database, an external API, a queue — is actually healthy; a dependency outage produces the exact same wall of 500s a bad deploy would, from the caller's point of view. Then check resource metrics: CPU or memory pinned near 100% causes requests to time out and fail, which looks like an application exception but is really a capacity problem. Also worth a glance: a recent scale event, or a deployment slot swap that may have shipped untested configuration along with the code.

🌍 Real-world example ▾

A 500 spike starts right after a deploy. The direct answer: swap the deployment slot back within a minute — the fast, reversible move — which immediately stops the bleeding for users while the actual bug gets found and fixed properly before the next, better-tested release goes out.
