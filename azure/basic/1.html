Subscriptions, Resource Groups & Regions — what's actually grouping what?

"What is an Azure subscription, resource group, and region, and how do they relate to each other?"

Why it matters ▾
💳 Subscription
❗ ProblemSomeone has to own who gets billed for a set of Azure resources and who's allowed to manage them, tied to a real identity source rather than left implicit.
✅ SolutionThe subscription is that billing + access-management boundary, tied to one Entra ID tenant, and it can hold as many resource groups underneath it as needed.
RecallSubscription = billing + access boundary, tied to an Entra ID tenant.
📁 Resource Group
❗ ProblemResources inside a subscription still need to be deployed, managed, and eventually deleted together as one unit, without accidentally leaving something behind.
✅ SolutionThe resource group is that lifecycle container — it isn't tied to a region itself, so it can hold resources spread across several regions, and each resource sits in exactly one group.
RecallResource Group = lifecycle boundary — one group can span many regions.
🔥 Easy interview recall

Subscription → billing + access boundary

Resource Group → lifecycle container

Region → where it actually runs

Think: a Resource Group groups by lifecycle, not by location — one group can hold resources spread across several regions at once.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A resource group must contain resources from the same region. It doesn't — region is a property each resource carries on its own; the resource group is purely a management/lifecycle container and can freely hold resources spread across multiple regions.

🔄 Likely Follow-up

"Can two resource groups reference the same resource?" No — a resource belongs to exactly one resource group at a time, though it can be moved to a different group later.

🎯 Say this in the interview — the exact lines to land

"A resource group is a lifecycle boundary, not a region boundary — it groups resources that get deployed, managed, and deleted together, and those resources can live in different regions. The subscription above it is the billing and access boundary, and the region is just a property each individual resource carries."

  • Resource group → lifecycle boundary — deploy, manage, and delete as one unit.
  • Region → a per-resource property, not a group-level one — one group can span many regions.
  • Subscription → the billing + access-management boundary, tied to an Entra ID tenant.
  • One group at a time → a resource lives in exactly one resource group, though it can be moved later.
📖 Explanation ▾

A subscription is Azure's billing and access-management boundary — the unit tied to an Entra ID tenant that decides who gets billed and who can manage what. Below it sits the resource group, a logical container for resources that share the same lifecycle: everything inside it gets deployed, managed, and deleted together as one unit.

Region is a separate idea entirely — it's the physical Azure datacenter location where a resource actually runs, and it's a property of that individual resource, not of the group holding it. A resource group can freely contain a web app in one region and a database in another; nothing about the group forces them to match.

💻 See the code ▾
Azure CLI 
az group create --name rg-demo --location eastus   -- just the group's own metadata

A resource group's own --location is only where its metadata lives — it doesn't force any resource inside it into that region.

Azure CLI 
az vm create \
  --resource-group rg-demo \
  --location westus \          -- a different region than the group's own metadata
  --name demo-vm ...

Same resource group, different region — the VM genuinely runs in westus, proving region is the resource's own property, not the group's.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're decommissioning a whole environment and need it gone in one clean action

Because the resource group is a lifecycle boundary, deleting it deletes every resource inside it as one action — nothing has to be tracked down and removed separately. This is the #1 reason resource groups exist.

RememberDelete the group → everything inside goes with it.
2 Resources need to sit in different regions but still be managed as one unit

The resource group itself isn't tied to a region, so nothing stops it holding resources spread across several regions at once — each resource just carries its own region independently.

RememberA group's job is lifecycle, not location.
3 One subscription needs to organize dev, test, and prod separately

One subscription can hold many resource groups, each with its own lifecycle — you don't need a separate subscription just to keep environments apart, only when billing or access actually needs to split too.

RememberMany groups, one subscription — split by lifecycle, not billing.
🌍 Real-world example ▾

A company names one resource group rg-prod-webapp and puts the App Service, its database, and Key Vault inside it — not because they share a region, but because they share one lifecycle. When that environment is decommissioned, deleting the resource group removes all three in a single action, with nothing left behind to clean up separately.
