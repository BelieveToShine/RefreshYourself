A clean automated scan — does that mean the page is actually accessible?

"How do you audit an existing page or app for accessibility, and what's the real difference between what a tool like axe or Lighthouse catches and what a manual screen-reader pass catches?"

Why it matters ▾
  • Most real accessibility work is auditing and fixing something that already shipped, not building a new page accessible from scratch — this is the exact scenario senior accessibility questions are actually probing for.
  • A common curveball right after "how do you test for accessibility" is "what can't your tool catch?" — answering "nothing, it catches everything" is an instant red flag.
  • Retrofitting a legacy page under a deadline, and deciding what to fix first, is a far more realistic interview scenario than describing how to build something accessible on a blank page.
🔥 Easy interview recall

Automated scan → catches STRUCTURAL gaps (missing alt, low contrast, missing label)

Manual screen-reader pass → catches SEMANTIC gaps (bad reading order, confusing flow)

Think: automated asks "is it there?" — manual asks "does it make sense?"

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A passing automated scan does not mean the page is accessible. Tools like axe or Lighthouse check structural, code-level rules — they can't judge whether that alt text is actually accurate, whether the tab order makes logical sense, or whether a screen-reader user can really finish the task end-to-end.

🔄 Likely Follow-up

"You found more issues than you can fix before the deadline — how do you decide what to fix first?" Prioritize by how many users are affected and how critical the flow is — a focus trap in the login flow outranks a missing label on a rarely-used settings page, even if both are technically valid findings.

🎯 Say this in the interview — the exact lines to land

"I'd treat auditing as its own skill, separate from building something accessible from scratch. I'd start with an automated scan — axe or Lighthouse — to catch the easy structural wins, then a manual keyboard-only pass to confirm everything's reachable and operable, then a manual screen-reader pass on the most critical flows, because automated tools only check structure and can't judge whether the experience actually makes sense."

  • Automated scanners (axe, Lighthouse) catch structural issues fast — missing alt, low contrast, missing labels, invalid ARIA.
  • Automated tools can't judge semantics — accurate alt text, a logical reading order, and whether an interaction actually makes sense end-to-end.
  • Common real audit findings → focus traps, icon-only buttons with no accessible name, and color-only error states.
  • Retrofit order → scan first, then a keyboard-only pass, then a manual screen-reader pass on critical flows.
  • Prioritize fixes by how many users / how critical the flow is — not by trying to clear every finding at once.
📖 Explanation ▾

Building something accessible from scratch and auditing something that already exists are different skills — see Accessibility for what the underlying pieces (ARIA, labels, focus) actually are. Most real-world accessibility work is the second one: a page already shipped, and the job is finding what's broken and fixing the highest-impact issues first. Common findings: a focus trap (keyboard focus gets stuck inside a widget like a modal with no way to tab back out, or an interactive element focus never reaches at all), an icon-only button with no text or aria-label (a screen reader announces only "button," nothing about what it does), and a color-only state indicator (an invalid form field shown only by a red border, with nothing a colorblind or screen-reader user can perceive).

Automated scanners check structural, code-level correctness — is there an alt attribute, is the contrast ratio above the threshold, is a form control's label present, is the ARIA syntactically valid. That's genuinely useful and catches a real category of issues fast, but it's a limited one: a scanner can't check meaning — whether the alt text is actually accurate and descriptive, whether the tab order makes logical sense, or whether a real screen-reader user could finish the task end-to-end. That's why a manual screen-reader spot-check on the app's most important flows still matters — it catches what structural analysis literally cannot see, like a live region that updates on screen but is never announced out loud.

Retrofitting accessibility into something that wasn't built with it in mind works best incrementally: run an automated scan first for the easy structural wins, then do a manual keyboard-only pass — try reaching and operating everything using only Tab, Shift+Tab, Enter, Space, and the arrow keys — then a manual screen-reader pass on the handful of flows that matter most. Fix in priority order — how many users are affected and how critical that flow is — rather than trying to clear every finding at once.

💻 See the code ▾
HTML 
<button>🗙</button>                       <!-- ❌ announces only "button" -->
<button aria-label="Close">🗙</button>   <!-- ✅ announces "Close, button" -->

An automated scan flags a missing accessible name in seconds — this is the easy structural win a scan is genuinely good at finding.

HTML 
<input aria-invalid="true" style="border:1px solid red">
<!-- ❌ only the red border shows the error -->

<input aria-invalid="true" aria-describedby="email-err" style="border:1px solid red">
<p id="email-err">⚠ Enter a valid email address</p>
<!-- ✅ error is announced AND visible, not just colored -->

Color alone doesn't reach a colorblind or screen-reader user — pairing aria-invalid/aria-describedby with visible text is what a manual pass catches that a scan on its own might miss the intent of.

🌍 Real-world example ▾

You're handed a legacy admin dashboard with no accessibility work ever done and two weeks before a compliance deadline. Run an automated scan first to clear the fast structural wins — alt text, contrast, labels. Then do a keyboard-only pass across the app's main flows. Then spend the limited manual screen-reader time only on the highest-traffic screens — login, the primary workflow, checkout — not the rarely-used settings page nobody hits.
