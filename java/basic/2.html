How Java code executes — compiled once, run by two different engines

"Walk through what happens from writing a .java file to it actually running."

Why it matters ▾
☕ Compile → bytecode → run
❗ ProblemA program compiled straight to one CPU's machine code only runs on that one platform — "write once, run anywhere" needs a different plan.
✅ Solutionjavac compiles source to platform-independent bytecode once; any JVM, on any platform, can interpret and JIT-compile that same bytecode into real machine code at runtime.
RecallCompile once to bytecode — every JVM turns it into native code locally.
🔥 Easy interview recall

Java execution = "compile once to bytecode, let the JVM turn it into native code wherever it runs."

Think: .java → javac → .class bytecode → JVM interprets, then JIT-compiles the hot paths.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Java source does not compile straight to native machine code. javac only produces platform-independent bytecode — turning that into real machine instructions is the JVM's job, done at runtime, and only for the methods that actually run often enough to earn JIT compilation.

🔄 Likely Follow-up

"Why does a long-running Java process often get faster over its first minute?" Early execution is interpreted bytecode, which is slower; the JIT compiler profiles which methods run often and compiles those "hot" paths into optimized native code as the program keeps running — that warm-up is why naive benchmarking can be misleading.

🎯 Say this in the interview — the exact lines to land

"javac compiles .java source into platform-independent .class bytecode. The JVM then interprets that bytecode and JIT-compiles the frequently-run paths into native machine code at runtime — that combination is what 'write once, run anywhere' actually means."

  • javac → produces bytecode, not native machine code.
  • JVM → interprets first, JIT-compiles hot paths as it keeps running.
  • Early execution is slower → warm-up matters for benchmarking.
📖 Explanation ▾

Compilation happens once, ahead of time: javac reads your .java source and produces .class files — bytecode, not machine code for any particular CPU. That bytecode is the same no matter which operating system eventually runs it.

Execution happens on whatever JVM you launch it with. At first, the JVM simply interprets the bytecode instruction by instruction — correct, but slower than running real machine code directly. As the program keeps running, the JIT (Just-In-Time) compiler profiles which methods are called often enough to be worth optimizing, and compiles exactly those into native machine code.

This two-phase split — a single ahead-of-time compile, then a runtime-specific interpret/JIT step per platform — is the actual mechanism behind "write once, run anywhere." Nothing about the .class file itself is platform-specific; only the JVM running it is.

💻 See the code ▾
Java 
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java");
    }
}

javac Hello.java produces Hello.class (bytecode) — java Hello then hands that bytecode to the JVM to run.

🧭 Use Cases — recognize these when they happen to you ▾
1 You run java MyApp with no separate compile step visible

A build tool or an earlier javac call already produced the .class file — java never compiles anything itself, it only launches the JVM against bytecode that already exists.

Rememberjava runs bytecode — it never compiles source.
2 A service feels sluggish for a few seconds, then speeds up

Early calls run interpreted; once a method has run enough times, the JIT compiles it to native code — that's the normal "warm-up" curve, not a bug.

RememberEarly slowness → JIT hasn't compiled the hot paths yet.
3 You benchmark a method by timing just its first call

That measurement includes interpretation and JIT warm-up overhead, not steady-state performance — a fair benchmark has to warm the code up first.

RememberTiming a cold first call → measuring warm-up, not real speed.
🌍 Real-world example ▾

Think of sheet music versus a musician. The sheet music (bytecode) is written once and is the same no matter who plays it. Each musician (JVM) reads it and performs it in their own way — slowly at first while sight-reading, faster and smoother once they've played the piece enough times to know it by heart.
