Calling a generator function doesn't run any of its code — only iterating it does

"A generator function is called, nothing happens yet, then it's iterated once — where does execution actually start, and what happens when it's resumed a second time?"

Why it matters ▾
  • Checks whether you actually understand that yield makes a function lazy, not just that the keyword exists — a lot of candidates can define "generator" but can't trace when code actually runs.
  • Comes up any time memory efficiency with large, unbounded, or streamed data is discussed.
  • A very common way interviewers separate "knows the syntax" from "understands the pause/resume model" in one short exercise.
🔥 Easy interview recall

Generator = "a paused function — it starts on the first next(), and resumes exactly where it left off."

Think: yield pauses. next() resumes. Just calling it runs nothing.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A generator function does not "run like a normal function" the moment it's called. Calling it only builds and returns a generator object — not one line inside the function body executes until you actually start iterating it, whether with a for loop or a direct next() call.

🔄 Likely Follow-up

"What do itertools.chain, islice, and groupby solve?" chain iterates several iterables as one sequence without concatenating them into a new list; islice lazily slices an iterator (works even on an infinite iterator, unlike list[a:b]); groupby groups consecutive items that share the same key — all three avoid a hand-rolled loop that would otherwise force materializing an intermediate list.

🎯 Say this in the interview — the exact lines to land

"Calling a generator function returns a generator object immediately — the body only runs once you iterate it, pausing at each yield and resuming exactly there next time."

  • yield pauses execution — the function's local state stays alive until the next next() call.
  • A generator is lazy — it produces one value at a time instead of holding the whole sequence in memory like a list does.
  • StopIteration signals "no more values" — a for loop catches it automatically; calling next() by hand raises it visibly.
  • itertools.chain/islice/groupby avoid hand-rolled iterator loops — each one stays lazy instead of building an intermediate list.
📖 Explanation ▾

An iterable is anything you can loop over — it has an __iter__ method that hands back an iterator. An iterator is the thing actually doing the walking: it has both __iter__ (which returns itself) and __next__ (which produces the next value, then raises StopIteration once there's nothing left). iter(x) calls x.__iter__(); next(x) calls x.__next__() — that's genuinely all a for loop is doing underneath.

A function containing yield is a generator function. Calling it doesn't run the function body at all — it immediately hands back a generator object, which is already both an iterable and an iterator. Only iterating that object actually starts running code, and it runs only up to the next yield before pausing again.

This laziness is the whole reason generators exist: a list holds every value in memory at once, while a generator produces one value at a time and lets go of it right after. For a huge or even unbounded sequence, building the list version could exhaust memory before processing even starts — a generator never tries to hold more than the current value.

💻 See the code ▾
Python 
def my_generator():
    print("start")
    yield 1
    print("resumed")
    yield 2

gen = my_generator()                      # returns a generator object, body does NOT run
print("called, nothing printed yet")  # confirms nothing above has printed
print(next(gen))                          # runs to first yield -> prints "start", returns 1
print(next(gen))                          # resumes after yield 1 -> prints "resumed", returns 2

🔮 Predict the output: Where does execution actually start, and what happens when the generator is resumed a second time?

Calling my_generator() runs nothing inside the function body yet — no "start" is printed. The first next(gen) is what actually starts execution: it runs from the top of the function until the first yield (printing "start"), then pauses there and returns 1. The second next(gen) resumes exactly where it paused — every local variable's state is preserved — and runs until the next yield (printing "resumed"), returning 2.

🌍 Real-world example ▾

Processing a multi-gigabyte log file. Reading it into a list of every line first tries to hold the entire file in memory at once — on a big enough file, that can run out of memory before processing even starts. Looping over the file line by line with a generator instead processes one line at a time, using only as much memory as a single line needs, no matter how large the file actually is.
