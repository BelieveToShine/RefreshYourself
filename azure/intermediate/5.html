Queues vs. topics — one consumer, or many?

"Service Bus queues vs. topics/subscriptions — when do you need one vs. the other?"

Why it matters ▾
  • Checks whether you know Service Bus has two genuinely different delivery models, not just "a messaging queue product."
  • Comes up any time the design needs multiple independent systems to react to the same event.
  • A common opener before a deeper Service Bus/Event Grid/Event Hubs comparison question.
🔥 Easy interview recall

Queue → one consumer gets it

Topic → every subscription gets its own copy

Think: queue = one hand takes the ticket. topic = everyone on the list gets their own copy.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Always use a topic — it's more flexible." Not if there's genuinely only one logical consumer group — reaching for a topic "just in case something else needs the message later" adds subscription and filter-rule management overhead a plain queue with competing consumers doesn't need.

🔄 Likely Follow-up

"Can a subscription filter which messages it receives?" Yes — SQL-like filter rules on message properties, so one topic can serve very different downstream consumers off the same published messages.

🎯 Say this in the interview — the exact lines to land

"A queue delivers a message to exactly one consumer — competing consumers just spread that load across a pool. A topic publishes one message and every independent subscription gets its own full copy, and each subscription can filter which messages it actually wants."

  • Queue → use when there's one logical consumer group and you just need to spread load.
  • Topic → use when multiple independent systems each need their own copy of the same message.
  • Subscription filters → SQL-like rules on message properties decide which messages a subscription actually receives.
  • Don't reach for a topic "just in case" — it adds filter/subscription overhead a single consumer doesn't need.
📖 Explanation ▾

A queue is point-to-point — a message sits in the queue until exactly one receiver locks and processes it. Adding more receiver instances doesn't multiply delivery; it just spreads the same messages across a competing pool, so each message is still only ever handled once. A topic is pub/sub — publishing a message doesn't deliver it to "the" consumer, it copies it into every subscription underneath that topic, and each subscription keeps its own copy independently of what the others do with theirs.

What makes topics genuinely different from just "queues with extra steps" is that each subscription can carry its own filter rule — a SQL-like condition on the message's properties. That's how one published event can feed a shipping system, a billing system, and an analytics pipeline off the exact same publish call, each only seeing the messages that actually match its own filter (or all of them, if it has none).

💻 See the code ▾
C# 
ServiceBusSender sender = client.CreateSender("orders-queue");
await sender.SendMessageAsync(new ServiceBusMessage("Order #1042"));
// ⚠️ exactly ONE receiver instance ends up processing this message

Same send API as a topic — the topology on the other end decides who gets a copy, not this code.

C# 
ServiceBusSender sender = client.CreateSender("orders-topic");
var msg = new ServiceBusMessage("Order #1042");
msg.ApplicationProperties["Type"] = "OrderPlaced"; // subscriptions filter on this
await sender.SendMessageAsync(msg);
// ✅ every subscription matching Type = OrderPlaced gets its OWN copy

Shipping and Billing subscriptions can each filter on Type = OrderPlaced and both independently receive this exact message.

🌍 Real-world example ▾

An order-placed event publishes to a topic once. A shipping subscription and a billing subscription each get their own independent copy of that exact message and process it on their own schedule — shipping kicks off a warehouse pick, billing charges the card, neither one waits on or competes with the other.
