Hydration only works if the client's first render matches the server's — or it's a mismatch

"What's hydration, and what's a classic cause of a hydration mismatch?"

Why it matters ▾
💧 Hydration
❗ ProblemRe-building the entire DOM from scratch on the client, after the server already sent fully-rendered HTML, would waste the work the server just did and cause a visible flash.
✅ SolutionHydration walks the existing server-sent DOM and attaches event listeners/state without rebuilding it — as long as the client's render output matches what the server already sent.
RecallHydration = reuse the server's DOM, don't rebuild it — if the outputs match.
🔥 Easy interview recall

Hydration mismatch = "client's first render disagreed with the server's."

Think: window.innerWidth, localStorage, and non-deterministic Date.now() formatting are the classic culprits — the server has no window at all.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reading a browser-only value in a path that runs on both server and client is the classic cause. window.innerWidth, localStorage, Math.random(), or an inconsistently-formatted Date.now() can all differ between the server pass (where window doesn't even exist) and the client's first render.

🔄 Likely Follow-up

"What's the actual fix for a value that legitimately differs between server and client?" Render a deterministic/neutral value (or nothing) on the initial pass, then update it inside useEffect — which only runs client-side, after hydration — so the first render matches on both sides.

🎯 Say this in the interview — the exact lines to land

"Hydration attaches event listeners and state to the server's existing DOM instead of rebuilding it, as long as the client's render output matches the server's. A mismatch happens when they disagree — often from reading a browser-only value like window.innerWidth in a path that runs on both — and React discards and rebuilds that subtree."

  • Hydration → reuses the server's DOM, doesn't rebuild it.
  • Mismatch → client's first render ≠ server's, triggers a rebuild + warning.
  • Classic cause → window, localStorage, Math.random(), Date.now() in a shared path.
  • Real fix → neutral value first render, update inside useEffect.
📖 Explanation ▾

After the server sends fully-rendered HTML, the client doesn't throw that markup away — React "hydrates" it, walking the existing DOM nodes and attaching event listeners and component state to them directly. This only works because React assumes the client's own render of the same component tree would have produced identical output — it skips re-creating the DOM and just wires it up.

A hydration mismatch happens when that assumption breaks: the client's first render genuinely differs from what the server sent. The most common cause is a value that's only available in the browser — window.innerWidth, localStorage, Math.random(), or a Date formatted in a way that depends on the browser's local timezone — read during a render path that executes identically on both server and client. The server simply has no window object at all, so it renders one thing; the client, running the exact same code, renders another.

When React detects the mismatch, it discards the mismatched subtree's attempt to reuse the server markup and rebuilds that piece of the DOM from the client's own render, logging a warning. The real fix is to make the two passes agree: render a neutral, deterministic value on the very first pass (identical on both server and client), then update it from inside useEffect, which only ever runs in the browser, after hydration has already completed.

💻 See the code ▾
JavaScript 
'use client';
function ScreenInfo() {
  // ❌ window doesn't exist during the server's pass
  return <p>Width: {window.innerWidth}</p>;
}

Server renders with no window at all; the client's first render reads a real value — guaranteed mismatch.

JavaScript 
'use client';
import { useState, useEffect } from 'react';

function ScreenInfo() {
  const [width, setWidth] = useState(null); // ✅ same on both passes
  useEffect(() => setWidth(window.innerWidth), []); // ✅ client-only, after hydration
  return <p>Width: {width ?? '--'}</p>;
}

First render is null on both server and client — identical — then useEffect fills in the real value after hydration.

🧭 Use Cases — recognize these when they happen to you ▾
1 A component reads localStorage directly during render

The server has no localStorage at all, so it renders a fallback; the client reads the real stored value on its first pass. A common interview trap: not realizing this applies to every browser-only API, not just window.

RememberAny browser-only API read during shared render → same risk as window.
2 Showing a value that's genuinely different per device, correctly

A neutral first render plus a client-only useEffect update is the standard, safe pattern for anything that's legitimately different between server and client.

RememberNeutral first render + useEffect update → no mismatch, by design.
🌍 Real-world example ▾

A "time since posted" label shows "5 minutes ago" on the server and briefly flashes "5 minutes ago" then a console warning in production. If the exact formatting depends on the viewer's local timezone or the precise millisecond it's computed, the server's and client's first renders can genuinely differ. The fix: render a stable placeholder (or the raw timestamp) on the first pass, then compute and swap in the relative time inside useEffect once the component is safely client-side.
