⭐ Should Know

Part of your template doesn't exist at all — until it's actually needed

"What can @defer actually defer, and what are @placeholder/@loading/@error for?"

Why it matters ▾
  • Route-level lazy loading only splits code at the page boundary — @defer is the tool for shrinking the bundle for one heavy widget inside a page that's otherwise needed right away.
  • A frequent senior-level question once someone already knows @if/@for: "what's newer in the template syntax that actually changes performance, not just readability?"
  • Misusing it is a real, easy-to-make mistake — deferring content the user needs immediately trades a smaller initial bundle for a visibly janky page.
🔥 Easy interview recall

@placeholder → before the trigger fires

@loading → while it's fetching

@error → if the fetch fails

Think: @defer carves a piece out of the template into its own separate chunk — it isn't downloaded at all until something decides it's actually needed.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

@defer is not a "wrap anything heavy" default. Deferring content the user sees or interacts with almost immediately — primary, above-the-fold content — trades a slightly smaller initial bundle for a visible "wait for it to pop in" delay right where the user is actually looking.

🔄 Likely Follow-up

"If a deferred block has no explicit trigger, when does it load?" Angular still loads it eventually using a sensible built-in default — but the reason explicit triggers like on idle and on viewport exist is so you deliberately choose the right moment for that specific piece of content, instead of relying on one default for every deferred block on the page.

🎯 Say this in the interview — the exact lines to land

"@defer marks a template block whose content, and the code it depends on, isn't downloaded or rendered until a trigger condition is met. @placeholder shows before that trigger fires, @loading shows while the code is being fetched after it fires, and @error shows if that fetch fails."

  • @defer → splits that content into its own chunk, left out of the initial bundle entirely.
  • @placeholder → shown before the trigger fires — the very first state, nothing loading yet.
  • @loading → shown while fetching, after the trigger but before the content is ready.
  • on viewport → loads once scrolled into view on idle → loads once the browser isn't busy with anything more urgent
  • Don't defer → primary, above-the-fold content — that's exactly what turns a bundle win into visible jank.
📖 Explanation ▾

A normal template block ships as part of the page it's on — its markup and the code it needs are downloaded and rendered as soon as that page loads. @defer changes that for one specific block: the content inside it, and any component/directive code that block alone depends on, can be split into a separate chunk that isn't part of the initial bundle at all. That's the same "don't download it until it's needed" benefit as route-level lazy loading, just applied to an arbitrary piece of a template instead of a whole page.

Until the trigger condition is met, Angular shows @placeholder — the very first state, before any loading has started. Once the trigger fires, it shows @loading while the deferred chunk is actually being fetched, and only then swaps in the real content. If that fetch genuinely fails, @error shows instead. on idle and on viewport are the two most common triggers: on idle loads once the browser isn't busy with higher-priority work — a reasonable default for "eventually, but don't compete" — while on viewport loads only once the block (or its placeholder) actually scrolls into view, which is the direct way to lazy-load something genuinely below the fold.

None of this is free reach-for-it-everywhere tooling. It earns its keep on content that's genuinely secondary, below the fold, or heavy and rarely needed — a chart library, a comments section, related-articles widget. Wrapping a page's primary content in @defer "because it's heavy" just moves the wait to the moment the user is actually looking at that spot.

💻 See the code ▾
HTML 
<!-- chart code isn't in the initial bundle at all -->
@defer (on viewport) {
  <heavy-chart [data]="data" />   // loads once scrolled into view
} @placeholder {
  <div>Chart will load when scrolled into view</div>  // shown first, before the trigger
} @loading {
  <div>Loading chart…</div>         // shown while the chunk fetches
} @error {
  <div>Couldn't load the chart</div>  // ❌ shown only if the fetch fails
}

Four blocks, one lifecycle — heavy-chart's own code ships as a separate chunk that's only downloaded once the trigger actually fires.

HTML 
<!-- lower priority than the chart above — no rush to load this one -->
@defer (on idle) {
  <related-articles />   // loads once the browser isn't busy
}

on idle doesn't wait for scroll position at all — it loads as soon as the browser has spare time, unlike on viewport, which waits until the block is actually about to be seen.

🌍 Real-world example ▾

@defer is like not setting up a guest room until a guest actually says they're staying. @placeholder is the closed door before anyone's asked; @loading is you quickly getting the room ready once they say they need it; @error is what you tell them if you genuinely can't get it ready in time. You'd never do this for the living room everyone walks through the moment they arrive — only for the room nobody visits on a normal day.
