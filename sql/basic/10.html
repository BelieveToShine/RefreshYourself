Stored Procedures — SQL that lives on the server, not in your app

"What is a stored procedure, and what's a real reason to use one?"

Why it matters ▾
  • Comes up as a natural follow-up any time raw SQL, an ORM, or app-layer query logic gets discussed.
  • Explains a real production choice: fewer network round trips, tighter permissions, and one shared place to fix a query.
  • A common opener before diving into permissions, SQL injection, or performance topics.
🔥 Easy interview recall

Stored procedure = "named SQL saved on the server, called instead of sent."

Think: EXEC GetCustomerOrders @id=7 — short call, real logic hidden and reused server-side.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Stored procedures are always faster because they're precompiled. Modern database engines already cache and reuse execution plans for parameterized ad-hoc queries too, so the reliable wins are less network traffic, a tighter security boundary (EXECUTE instead of table access), and shared logic — not a guaranteed speed advantage by itself.

🔄 Likely Follow-up

"How do stored procedures help with SQL injection?" Using parameters — never string-concatenating raw values into the procedure's SQL — keeps user input as data, never as executable SQL text, the same protection parameterized queries already give outside a procedure.

🎯 Say this in the interview — the exact lines to land

"A stored procedure is SQL logic saved on the database server and called by name with parameters, instead of sending the full SQL text over the network every time. I'd reach for one to cut network round-trips, to grant EXECUTE permission instead of direct table access, or to centralize logic that many callers share."

  • Named, saved logic → lives on the server, called instead of sent.
  • Less network chatter → a short call replaces the full SQL text every time.
  • Tighter security surface → grant EXECUTE without granting direct table access.
  • Not an automatic speed win → parameterized ad-hoc queries get cached plans too.
📖 Explanation ▾

A stored procedure is SQL logic saved once on the database server, under a name, and invoked with parameters instead of sending the full SQL text over the wire on every call. The app sends something like EXEC GetCustomerOrders @id=7 — a short call — and the server runs the logic it already has saved.

Three real reasons to reach for one: less network chatter (a short call beats a full query string every time), a tighter security boundary (an account can be granted EXECUTE on the procedure without ever being granted direct SELECT/INSERT/UPDATE access to the underlying tables), and one shared place to fix or change logic that multiple callers use, instead of copies of the same query scattered across an app.

💻 See the code ▾
SQL 
CREATE PROCEDURE GetOrdersByCustomer
    @CustomerId INT
AS
BEGIN
    SELECT * FROM Orders WHERE CustomerId = @CustomerId;
END;

The query is written once and saved on the server under this name — every caller shares the same saved logic.

SQL 
EXEC GetOrdersByCustomer @CustomerId = 7;   -- short call, no SQL text sent

Every caller sends this one short line — the actual query behind it never travels over the network again.

🌍 Real-world example ▾

A restaurant's numbered menu. Saying "I'll have #14" is a short call — the kitchen already knows exactly what #14 means and how to make it, so nobody re-explains the whole recipe every time. A stored procedure works the same way: the caller sends a short, named request, and the server already has the real logic saved and ready to run.
