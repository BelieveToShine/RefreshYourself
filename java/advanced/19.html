Blocking vs. Non-Blocking Algorithms — wait your turn, or retry on contention

"What's the real trade-off between a blocking (lock-based) algorithm and a non-blocking (CAS-based) one?"

Why it matters ▾
🚦 Blocking (lock-based)
❗ ProblemMultiple threads need exclusive turns on shared state — letting them all barge in at once corrupts it.
✅ SolutionA blocking (lock-based) algorithm parks a contending thread — no CPU spent while waiting — until it can proceed, at the cost of latency and context-switch overhead.
RecallBlocking = park and wait, zero CPU, real latency.
🔁 Non-blocking (CAS-based)
❗ ProblemParking and waking threads has real overhead — under heavy contention, that overhead itself can dominate.
✅ SolutionA non-blocking algorithm (typically CAS-based, "lock-free") lets a thread retry immediately instead of waiting — higher potential throughput, at the cost of real implementation complexity.
RecallNon-blocking = retry now, spend CPU instead of waiting.
🔥 Easy interview recall

Blocking → parked, 0% CPU, real latency

Non-blocking → retries, burns CPU, no parking cost

Think: blocking is a line at a door. Non-blocking is rattling the handle until it happens to be unlocked.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Non-blocking doesn't mean free. A thread retrying a failed CAS in a tight loop still burns real CPU cycles — under very heavy contention, that spinning can cost more than a short, well-managed block would.

🔄 Likely Follow-up

"Does a non-blocking algorithm guarantee no thread ever starves?" No — CAS-based retry gives no absolute starvation-freedom guarantee the way a fair lock can; a thread can in theory keep losing the race on every retry, though in practice this is rare.

🎯 Say this in the interview — the exact lines to land

"A blocking algorithm parks a contending thread — no CPU spent while waiting, but real latency and context-switch overhead — until it can proceed. A non-blocking, typically CAS-based algorithm lets a thread retry immediately on contention instead of waiting, which can mean higher throughput under contention, at the cost of real implementation complexity."

  • Blocking → parked thread, zero CPU, real wait latency.
  • Non-blocking → retries immediately, spends CPU instead of waiting.
  • Heavy contention → non-blocking can out-throughput locking, or waste CPU spinning — depends on the workload.
  • Starvation → no absolute guarantee under CAS retry, unlike a fair lock.
  • Real cost → implementation complexity, not a free upgrade.
📖 Explanation ▾

A blocking algorithm relies on the OS to park a thread that can't proceed — the thread is descheduled, consumes no CPU, and is woken (a real context-switch) once the resource is free. That's efficient when contention is low or moderate, but every wake-up and lock hand-off has a real, measurable cost.

A non-blocking algorithm never parks — a thread that loses a compare-and-swap just retries the whole operation against the (now-changed) current state. Under light contention, this is usually cheaper than a lock, because there's no park/wake round-trip at all. Under very heavy contention, the same retry loop can waste CPU cycles that a well-designed lock would have spent more productively.

💻 See the code ▾
Java 
// Blocking — contending threads park until the lock is free
synchronized (lock) {
    balance += amount;
}

A contending thread is parked by the JVM/OS — no CPU spent, but it waits its turn.

Java 
// Non-blocking — AtomicLong's internal CAS retry loop, conceptually:
long current, updated;
do {
    current = balance.get();
    updated = current + amount;
} while (!balance.compareAndSet(current, updated)); // ✅ retries on failure

No thread ever parks — a failed compareAndSet just means the loop reads the latest value and tries again.

Java 
AtomicLong counter = new AtomicLong();
counter.incrementAndGet(); // ✅ the same CAS loop, already written for you

In practice you rarely hand-write the CAS loop — java.util.concurrent.atomic classes already implement it correctly.

🧭 Use Cases — recognize these when they happen to you ▾
1 A simple shared counter under light-to-moderate contention

For most counters, an AtomicLong/AtomicInteger (non-blocking) is simpler and usually faster than a synchronized block — there's no park/wake overhead for what's normally a very short operation.

RememberSimple counter, light contention → AtomicLong.
2 An extremely hot counter, updated by hundreds of threads per millisecond

Under genuinely extreme contention, even a plain CAS loop spends a lot of CPU retrying — LongAdder spreads updates across internal cells specifically to reduce that contention, at the cost of a slightly more expensive read.

RememberExtreme contention → consider LongAdder over a single AtomicLong.
3 Assuming "non-blocking" always means "faster"

Under very high contention, a tight CAS retry loop can burn more CPU than a short, well-managed lock would have cost. A common interview trap: treating "lock-free" as a synonym for "always faster," regardless of contention level.

RememberNon-blocking can lose to blocking under extreme contention.
🌍 Real-world example ▾

A payment service increments a shared "transactions processed" counter from thousands of threads per second at peak load. A plain synchronized increment would park most of those threads waiting their turn; an AtomicLong avoids that parking cost, and if profiling later shows even the CAS loop is contended enough to matter, LongAdder is the next practical step — not a hand-rolled lock-free algorithm.
