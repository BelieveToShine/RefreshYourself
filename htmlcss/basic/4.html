Accessibility — what a screen reader actually announces, not what's on screen

"What does 'accessible' really mean here — labels, keyboard navigation, ARIA, screen readers — and when should you reach for ARIA instead of native HTML?"

Why it matters ▾
  • "How would a screen-reader user use this button?" is a common curveball on almost any UI-heavy interview — it catches candidates who only ever tested with a mouse.
  • Every later UI topic (custom widgets, modals, forms) eventually turns into "is this accessible," so this vocabulary — accessible name, focus order, landmark — has to be second nature.
  • The senior filter question is almost always "ARIA vs. native HTML" — answering it backwards signals ARIA is your default fix instead of your last resort.
🔥 Easy interview recall

alt → the words a screen reader says instead of the image

ARIA → extra meaning added only when HTML alone can't say it

Landmark → a named region (nav, main) a screen reader can jump straight to

tabindex → 0 joins the tab order, -1 pulls it out

Think: native HTML first — reach for ARIA only when there's genuinely no native tag that already does the job.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding an ARIA role doesn't make something fully accessible. role="button" on a <div> announces the role, but you still have to hand-wire the keyboard behavior (focusable, Enter/Space activates it) that a real <button> gives you automatically.

🔄 Likely Follow-up

"When should you use ARIA vs. prefer native HTML?" Native HTML first — reach for ARIA only when there's genuinely no native element with the semantics or behavior you need, like a custom widget with no native equivalent. This is often summarized as the first rule of ARIA: don't use ARIA if you don't have to.

🎯 Say this in the interview — the exact lines to land

"Accessible means the accessibility tree — built from the DOM plus any ARIA — announces the right role, name, and state for every element, keyboard users can reach and see focus on everything interactive, and the heading and landmark structure lets someone navigate without looking at the screen. Native HTML gives most of that for free; ARIA only fills in what native elements genuinely can't cover."

  • Native HTML first — a real <button> gets keyboard behavior and a role for free; ARIA on a <div> only adds the label, never the behavior.
  • alt → the words announced instead of the image — empty alt="" for a purely decorative image, real text for anything meaningful.
  • Heading levels → never skip one — screen-reader users jump the page by heading level, and a skipped level breaks that map.
  • Landmarks (header, nav, main, footer) → named regions a screen reader can jump straight to.
  • tabindex="0" joins the tab order; tabindex="-1" removes it from Tab but keeps it script-focusable; a positive value reorders tabbing and is almost always a mistake.
  • Skip link → lets keyboard users jump past repeated navigation straight to the main content.
📖 Explanation ▾

Semantic HTML is the foundation this whole topic sits on — a real <button>, <nav>, or <label> already carries a role, and often keyboard behavior, that a browser and a screen reader both understand automatically. A <label> tied to an input (via for/id, or by wrapping it) is what gives that input its accessible name — without one, a screen reader announces an unlabeled field with nothing to say about what it's for. Keyboard navigation follows the same idea: every interactive element needs to be reachable by Tab, in a sensible order, with a visible focus indicator so a sighted keyboard user can see where they are.

ARIA (Accessible Rich Internet Applications) is a set of HTML attributes — roles, states, and properties — that fill in meaning native HTML can't express on its own: role says what something is ("this is a tab"), aria-expanded/aria-checked say what state it's in, and aria-label/aria-labelledby give it an accessible name when there's no visible text to use. ARIA changes what gets announced; it never adds keyboard behavior by itself — that part is still the page's job.

A screen reader reads the accessibility tree: a structure the browser builds from the DOM plus any ARIA, exposing each element's computed role, name, and state to assistive technology. Heading hierarchy (h1 → h2 → h3, never skipping a level) lets someone navigate by jumping between headings instead of reading everything; landmark elements (header, nav, main, footer) work the same way for whole regions. Color contrast is checked as a ratio between text and background — WCAG's commonly cited baseline is at least 4.5:1 for normal-size text. A skip link is a normally-hidden link, first in the page, that jumps straight to main content so a keyboard user doesn't have to tab through the same navigation on every page. tabindex="0" adds an element to the natural tab order; tabindex="-1" removes it from Tab while keeping it focusable by script (useful for a dialog you focus programmatically); a positive tabindex forces a custom order ahead of the document's natural flow, which is why it's usually a mistake — it's easy to get out of sync with the visual layout.

💻 See the code ▾
HTML 
<button>🗙</button>                       <!-- ❌ no accessible name -->
<button aria-label="Close">🗙</button>   <!-- ✅ announces "Close, button" -->

A screen reader reads the accessible name, not the glyph — an icon with no name announces nothing useful.

HTML 
<h1>Order history</h1>
<h2>Recent orders</h2>   <!-- ✅ one level down -->
<h4>Order #1234</h4>     <!-- ❌ skipped h3 -->

Screen-reader users often jump the page by heading level — a skipped level makes the structure look broken even though it renders fine visually.

HTML 
<div tabindex="0">Custom control</div>    <!-- ✅ joins tab order -->
<div tabindex="-1">Dismissed toast</div>  <!-- ✅ script-focusable, skipped by Tab -->
<div tabindex="3">Do not do this</div>    <!-- ❌ hijacks tab order -->

0 joins the natural tab order, -1 keeps it focusable by script only, and a positive number forces a custom order that's easy to get out of sync with the layout.

🌍 Real-world example ▾

Picture reading a page over the phone to someone who can't see it. You wouldn't describe colors or pixel positions — you'd say "heading: Order history," "link: Contact us," "button: Close." That spoken description is exactly what a screen reader gives its user: not the visual page, but the roles, names, and structure sitting underneath it.
