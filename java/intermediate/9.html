Generics and type erasure — gone by runtime, enforced at compile time

"What is type erasure, and what are its real consequences at runtime?"

Why it matters ▾
🧬 Generics & Type Erasure
❗ ProblemWithout any generic type information at runtime, a method could get handed a List built to hold Strings and silently stuff an Integer into it — nothing would notice until some unrelated line downstream casts the wrong element and blows up far from the real mistake.
✅ SolutionThe compiler fully type-checks every generic usage against List<String> at compile time, inserting the necessary casts automatically — by the time the code reaches runtime it's just a raw List with those casts already in place, so the safety work happens once, up front, for free.
Recallcompile time checks it, runtime never sees it.
🔥 Easy interview recall

Compile time → type-checked, distinct types

Runtime → erased, identical class

Think: the compiler erases List<String> down to raw List plus casts — by runtime, List<String> and List<Integer> are the exact same class.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

foo(List<String>) and foo(List<Integer>) cannot coexist as overloads. After erasure both signatures are literally foo(List), so the compiler rejects it as a duplicate method, not two valid overloads.

🔄 Likely Follow-up

"Why can't I write new T[10]?" Because erasure means the JVM has no real type to tag the array with at runtime, and array creation needs one — the compiler blocks it outright (the usual workaround is allocating an Object[] internally and casting, exactly what ArrayList itself does).

🎯 Say this in the interview — the exact lines to land

"Generic type information only exists at compile time for type-checking. The compiler erases it down to a raw type with inserted casts for the actual bytecode, so at runtime List<String> and List<Integer> are genuinely indistinguishable — same class, same getClass()."

  • Compile time → full type checking, List<String> ≠ List<Integer>.
  • Runtime → erased to raw List, getClass() identical for both.
  • Bounded type (<T extends Number>) → restricts substitution, still type-safe for the bound's own members.
  • Can't new T[10] or overload by erased type → direct consequences of erasure, not arbitrary rules.
📖 Explanation ▾

Generics exist entirely for the compiler's benefit. When code reads List<String>, the compiler checks every add, every get, every assignment against that type — and once it's satisfied nothing can go wrong, it rewrites the code to the raw List the JVM has always understood, inserting an invisible cast everywhere an element comes back out. The type parameter itself never makes it into the compiled bytecode.

A bounded type parameter like <T extends Number> narrows what's substitutable for T — only Number and its subtypes qualify — while still letting the compiler type-check calls to Number's own methods (like .doubleValue()) on a value of type T, something it couldn't do with an unbounded T.

Erasure has two concrete, commonly-asked consequences: you can't create a generic array (new T[10]) because the JVM needs a real runtime type to tag an array with, and you can't overload two methods that differ only by a generic type argument, because after erasure they're the exact same signature.

💻 See the code ▾
Java 
List<String> strings = new ArrayList<>();
List<Integer> ints = new ArrayList<>();
System.out.println(strings.getClass() == ints.getClass());  // ✅ true — both ArrayList

The type parameter is gone by runtime — only the raw class survives.

Java 
static <T extends Number> double sum(List<T> list) {
    double total = 0;
    for (T n : list) total += n.doubleValue();  // ✅ Number's own method
    return total;
}

The bound lets the compiler trust T has .doubleValue() — without it, that call wouldn't compile.

Java 
void process(List<String> list) { }
void process(List<Integer> list) { }  // ❌ compile error — duplicate erasure

Both erase to process(List) — the compiler sees one method declared twice.

🧭 Use Cases — recognize these when they happen to you ▾
1 Writing a generic utility that needs to compare its elements

A generic max(List<T> items) method can't call .compareTo() on a bare T — the compiler has no idea T supports it. Bounding it to <T extends Comparable<T>> makes the call type-check while still working for any comparable type.

RememberNeed a method on T → bound T to an interface that declares it.
2 Mixing generics with older, raw-typed legacy code

Assigning a raw-typed legacy collection into a generic one compiles but produces an "unchecked" warning — the compiler can't verify the raw side actually only contains the expected type, because that check was already erased away.

RememberAn "unchecked" warning means the compiler is trusting you, not verifying you.
3 You try to overload a method by its generic type parameter

foo(List<String>) and foo(List<Integer>) read like two valid overloads, but they're not — after erasure both are literally foo(List), so the compiler flat-out refuses to compile it.

RememberCan't overload by erased generic type — give the methods different names instead.
🌍 Real-world example ▾

Generics are like a shipping label taped onto a box before it's loaded onto a truck — the warehouse worker (the compiler) reads the label and checks it matches the manifest before loading. Once the truck (the JVM) is actually driving down the highway, nobody on the road can see that label anymore; the truck is just carrying boxes.
