property is just a descriptor with a friendlier syntax — that's the whole trick behind ORM field definitions too

What is a descriptor? How does property actually work internally?

Why it matters ▾
  • Separates "used @property" from "understands how Python's attribute lookup actually works" — a common way interviewers test real object-model depth.
  • Comes up any time framework internals get discussed — Django model fields, SQLAlchemy columns, and even classmethod/staticmethod lean on this exact mechanism.
  • A frequent follow-up right after any property question, since most candidates can use it but few can explain what it actually is underneath.
🔥 Easy interview recall

Descriptor = "a class attribute with __get__ (and maybe __set__) that Python calls instead of just handing back a plain value."

Think: property IS one — built into the language, not a separate feature.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assigning self.x = value doesn't always create a normal instance attribute. That's only true for a non-data descriptor (just __get__, like a plain method) — a data descriptor such as property (__get__ + __set__) always intercepts the assignment first, so it can never be shadowed by an instance __dict__ entry of the same name.

🔄 Likely Follow-up

"How do descriptors relate to ORM field definitions?" An ORM field descriptor's __get__/__set__ can transparently translate attribute access into database reads/writes (or at least tracked, dirty-checked in-memory state) — that's exactly how user.name = "Alice" can trigger an ORM's change-tracking without the calling code knowing anything about descriptors.

🎯 Say this in the interview — the exact lines to land

"property is a built-in data descriptor — that's literally the mechanism, not a separate feature. Any object implementing __get__/__set__ as a class attribute can intercept attribute access exactly the same way property does."

  • property is sugar for a property object — a data descriptor assigned to a class attribute, nothing more exotic.
  • Data descriptor (__get__ + __set__) → always wins over an instance __dict__ entry of the same name.
  • Non-data descriptor (__get__ only, e.g. a plain method) → an instance __dict__ entry of the same name wins instead.
  • ORM fields (Django, SQLAlchemy) → implemented as descriptors — a plain-looking attribute can transparently read or write a database row.
📖 Explanation ▾

A descriptor is any object that implements __get__ (and optionally __set__ or __delete__) and is stored as a class attribute. When you access that attribute through an instance, Python's normal attribute-lookup machinery doesn't just hand back a value sitting in __dict__ — it calls the descriptor's __get__ (or __set__) instead, letting the class intercept and customize what "reading" or "writing" that attribute actually does.

Descriptors split into two kinds, and the split decides who wins a naming conflict. A non-data descriptor defines only __get__ — a plain method is exactly this (accessing it produces a bound method), and an instance __dict__ entry of the same name shadows it. A data descriptor defines __get__ and __set__ (or __delete__) — it always wins over an instance __dict__ entry instead, no exceptions. property is a data descriptor built into the language: @property is just shorthand for building a property object — a class attribute whose __get__/__set__/ __delete__ call your getter/setter/deleter functions — and assigning it to the attribute's name.

This is also exactly how ORM field definitions work. A Django model field or a SQLAlchemy column is typically a descriptor: accessing model.some_field looks like reading a plain attribute, but really triggers descriptor logic that can read from or write to database-backed row data instead of a plain in-memory value.

💻 See the code ▾
Python 
class PositiveNumber:                 # a data descriptor: __get__ AND __set__
    def __set_name__(self, owner, name):
        self._name = "_" + name          # e.g. "quantity" -> "_quantity"

    def __get__(self, instance, owner):
        return getattr(instance, self._name)

    def __set__(self, instance, value):
        if value <= 0:
            raise ValueError("must be positive")
        setattr(instance, self._name, value)

class Order:
    quantity = PositiveNumber()               # class attribute — a descriptor instance

The hand-written descriptor spelled out: a class attribute whose __get__/__set__ intercept every read and write on quantity.

Python 
class Order:
    def __init__(self):
        self._quantity = 1

    @property
    def quantity(self):
        return self._quantity

    @quantity.setter
    def quantity(self, value):
        if value <= 0:
            raise ValueError("must be positive")
        self._quantity = value

Same behavior, friendlier syntax: @property just builds a property object — a ready-made data descriptor — and assigns it to quantity on the class. That object is the same mechanism as PositiveNumber above, just written for you.

🌍 Real-world example ▾

user.email looks like a plain attribute — it isn't. Django's CharField and SQLAlchemy's Column are typically implemented as descriptors: reading user.email calls the field descriptor's __get__, and writing user.email = "sam@co.com" calls its __set__, which can validate the value and mark the row as changed for the next database write. The calling code never has to know any of this — it just looks like ordinary attribute access.
