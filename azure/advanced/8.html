Pods scale with HPA, nodes scale with the cluster autoscaler — you need both

"Design an AKS cluster for production: networking model, scaling, and how traffic gets in."

Why it matters ▾
🧱 Node pools
❗ ProblemRunning core cluster pods and your own apps on the same nodes means a noisy app can starve the system, and every app gets the same VM size.
✅ SolutionA system pool hosts the cluster's own components, and separate user pools host your apps, each with its own VM size and scaling.
RecallSystem pool = cluster's own pods. User pools = your apps.
🌐 Networking & ingress
❗ ProblemPods need IP addresses that fit your network, and outside traffic needs one smart front door instead of a public address per service.
✅ SolutionPick a pod networking model that fits your IP space, and route outside traffic through one ingress controller or Application Gateway to your services.
RecallIP plan first. One ingress in front.
📈 Autoscaling
❗ ProblemFixed capacity is either too small at peak or wasteful the rest of the day.
✅ SolutionThe Horizontal Pod Autoscaler adds pods when load rises; the cluster autoscaler adds nodes when pods have no room to run.
RecallHPA scales pods. Cluster autoscaler scales nodes.
🔥 Easy interview recall

System pool → cluster's own pods

User pool → your apps, own VM sizes

Ingress → one front door, L7 routing

HPA vs. cluster autoscaler → pods vs. nodes

Think: HPA makes pods; if they do not fit, the cluster autoscaler makes nodes.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"HPA scales the cluster." HPA only changes the number of pod replicas. If there is no room left on the nodes, the new pods sit Pending until the cluster autoscaler adds a node — or forever, if it is not enabled or has hit its maximum. Also, with a flat Azure CNI setup (Node Subnet or Pod Subnet) every pod takes a VNet IP, so a small subnet can run out of addresses before you run out of CPU.

🔄 Likely Follow-up

"Why not Container Apps instead?" If you do not need direct Kubernetes API access, custom operators or fine control of the cluster, Container Apps gives scaling and ingress with far less to own. AKS is justified when you need that control — see the three-way container choice page.

🎯 Say this in the interview — the exact lines to land

"I would use a small system node pool and separate user pools sized per workload, Azure CNI Overlay (or Pod Subnet) planned for IP space, an ingress controller or Application Gateway in front, the HPA for pods and the cluster autoscaler for nodes, spread across availability zones."

  • System pool → the cluster's own pods; user pools run your apps.
  • Pod networking → plan IP space; CNI Overlay saves VNet addresses; kubenet ends 31 March 2028.
  • Ingress → one front door, routing by host and path.
  • HPA → pods; cluster autoscaler → nodes.
  • Production → spread across zones, use managed identity.
📖 Explanation ▾

An AKS cluster has a control plane that Azure manages and node pools you own. Keep a system node pool for the cluster's own components and add user node pools for your apps, so you can pick different VM sizes, scale each separately, and keep apps off the system nodes. For production, spread nodes across availability zones.

For pod networking, Azure CNI Overlay gives only the nodes VNet addresses and gives pods addresses from a separate private range, which avoids running out of VNet space. Azure CNI Pod Subnet gives pods real VNet addresses from a dedicated subnet, and Microsoft recommends these two for most cases. The older Azure CNI Node Subnet also uses VNet addresses for pods, and kubenet is legacy: AKS stops supporting it on 31 March 2028. Either way, plan IP space early. For ingress, an in-cluster ingress controller (for example NGINX) routes by host and path behind a load balancer; Application Gateway can play that role with a web application firewall; Front Door sits in front for global traffic.

Two autoscalers work at two levels. The Horizontal Pod Autoscaler changes how many pod replicas run, usually based on CPU or custom metrics. The cluster autoscaler watches for pods that cannot be placed and adds nodes, then removes underused ones later. Use both: HPA decides the pod count, and the cluster autoscaler makes sure there is room for them.

💻 See the code ▾
Azure CLI / kubectl 
# a user node pool that the cluster autoscaler can grow and shrink
az aks nodepool add --resource-group rg-aks --cluster-name aks-prod --name userpool --mode User --enable-cluster-autoscaler --min-count 1 --max-count 5

# HPA: keep 2 to 10 replicas of "web" around 70% CPU
kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10

The first command lets that node pool scale between 1 and 5 nodes, the second lets pods scale. Names and counts are examples only; the pods also need CPU requests set for CPU-based HPA to work.

🌍 Real-world example ▾

An online shop runs its checkout and catalog services in a user pool behind an ingress controller. On sale day the HPA adds checkout pods, the pool runs out of room, the cluster autoscaler adds nodes, and after the rush both scale back down.
