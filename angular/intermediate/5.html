🔥 Must Know

One error, one dead stream — forever, unless you plan for it

If one request inside a stream errors, does the whole stream die — and how do you stop a subscription from leaking after a component is destroyed?

Why it matters ▾
🔗 takeUntil(destroy$)
❗ ProblemA subscription that never completes on its own has no built-in signal for when its component is gone — left alone, it keeps running after that component is destroyed.
✅ SolutionA destroy$ Subject you create and .next() inside ngOnDestroy, piped in via takeUntil, tells the subscription exactly when to stop.
RecalltakeUntil(destroy$) → you own the Subject, and you own remembering to fire it.
🧹 takeUntilDestroyed()
❗ ProblemThe takeUntil(destroy$) pattern only works if every component remembers to create the Subject and call .next() in ngOnDestroy — miss one and that subscription leaks silently.
✅ SolutiontakeUntilDestroyed() reads Angular's own DestroyRef directly, so the same cleanup fires automatically with no Subject to create.
RecalltakeUntilDestroyed() → same cleanup as takeUntil(destroy$), no Subject to forget.
📺 async pipe
❗ ProblemEven takeUntilDestroyed() still needs a manual .subscribe() call whose only job is copying a value onto a property so the template can show it.
✅ SolutionThe async pipe subscribes — and unsubscribes — for you straight in the template, whenever the goal is only to display the latest value.
Recallasync pipe → nothing to subscribe to, and nothing to clean up.
🔥 Easy interview recall

catchError on the inner call → outer stream survives

catchError missing / on the outer → outer stream dies, forever

Think: catchError wrapped around the inner call = one bad search, line stays open. catchError missing, or wrapping the outer, = the whole line goes dead.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Wrapping catchError around the outer switchMap-based stream instead of the inner request Observable. One failed search then silently kills the entire search feature for the rest of the component's life — no crash, no visible error — so it can go unnoticed until a real user hits it in production.

🔄 Likely Follow-up

"Does takeUntilDestroyed() work anywhere, or only inside a component?" It needs an injection context (or an explicit DestroyRef passed as an argument) to know which "destroy" event to key off — callable directly as a field initializer inside an injectable class (same injection-context rule as inject() from the DI page), or from outside one if you explicitly pass in the relevant DestroyRef.

🎯 Say this in the interview — the exact lines to land

"An unhandled error is a terminal notification — the Observable stops for good, so catchError has to wrap the exact call that might fail, not the whole outer stream, or one bad request kills everything after it. And any subscription that doesn't complete on its own needs takeUntilDestroyed(), the takeUntil pattern, or the async pipe so it doesn't outlive the component."

  • catchError on the inner call → wraps just the risky request, so only that one attempt fails, not the whole stream.
  • takeUntil(destroy$) → the classic pattern — a Subject you call .next() on inside ngOnDestroy.
  • takeUntilDestroyed() → the modern replacement — hooks into Angular's own DestroyRef, no manual Subject.
  • async pipe → subscribes and unsubscribes for you automatically; reach for it whenever you're just displaying a value.
  • Manual .subscribe() → still justified only for a side effect — navigation, a toast — never just to display a value.
📖 Explanation ▾

An RxJS stream treats an error very differently from a value. A value emission just means "here's the next thing" — the stream keeps going. An error is a terminal notification: the Observable stops completely and nothing else it would have emitted ever arrives, unless something intercepts that error first. catchError intercepts it and lets you return a replacement Observable instead — a fallback value (of(...)), an empty stream (EMPTY), or the original error rethrown after logging it, if you still want it to propagate.

Where catchError sits in the pipe decides whose life it saves. Wrapped around just the inner call inside switchMap (or immediately after it, still inside that inner pipe), it only catches failures from that one request — the outer stream, and its subscription, keep running for the next value. Wrapped around the whole outer stream instead, an inner failure propagates all the way out and the outer stream dies for good — a search box with no catchError on its inner request simply stops responding to every keystroke after the first failed search.

A subscription that never completes on its own has to be told when to stop, or it leaks — still listening, still doing work, after the component that created it is gone. The takeUntil(destroy$) pattern, the newer takeUntilDestroyed(), and the async pipe are three ways to guarantee that cleanup; a manual .subscribe() is still the right call when you need to run actual logic — navigation, a toast, another method call — in response to a value, not just show it.

💻 See the code ▾
TypeScript 
this.results$ = this.search$.pipe(
  switchMap(q => this.api.search(q)),
  catchError(() => of([]))   // ❌ catches AFTER switchMap — one failure kills the whole outer stream
);

By the time this catchError runs, the outer stream has already errored — it's done, forever.

TypeScript 
this.results$ = this.search$.pipe(
  switchMap(q => this.api.search(q).pipe(
    catchError(() => of([]))   // ✅ catches only THIS search — outer stream keeps running
  ))
);

catchError wraps just the inner Observable — only that one search fails gracefully; the next keystroke still triggers a new search.

TypeScript 
this.data$.pipe(takeUntilDestroyed()).subscribe(value => this.handle(value));

takeUntilDestroyed() completes the stream automatically when this component's DestroyRef fires — no manual destroy$ Subject needed.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're maintaining an older component that predates DestroyRef

This file already has its own destroy$ Subject wired up and calls .next() inside ngOnDestroy — keep using takeUntil(destroy$) here so the whole file follows one consistent cleanup pattern instead of mixing two.

RememberOlder code already using destroy$ → keep takeUntil(destroy$), don't mix patterns.
2 You're writing a brand-new component or directive from scratch

New code has no legacy Subject to match, so takeUntilDestroyed() gets the exact same guaranteed cleanup with no Subject to create and no .next() call to remember.

RememberNew code, no legacy Subject → takeUntilDestroyed().
3 You're only binding a value straight into the template — no side-effect logic runs on it

If the only thing that happens with the emitted value is displaying it, the async pipe subscribes and unsubscribes automatically — there's no manual .subscribe() call to write or clean up in the first place.

RememberJust displaying a value → async pipe, no manual subscribe at all.
🌍 Real-world example ▾

An unhandled error in a stream is like a single dropped call permanently disconnecting your entire phone line, not just that one call — the next call, and every call after it, goes nowhere. Catching the error at the right, inner level is like having call waiting instead: one bad connection gets logged and dismissed, and the line itself stays open for the next call.
