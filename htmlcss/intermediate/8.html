:hover vs. :focus-visible — works for a mouse, invisible to everyone else

"What's the difference between a pseudo-class and a pseudo-element, and why can relying only on :hover to reveal something be an accessibility problem?"

Why it matters ▾
  • A hover-only menu or tooltip is one of the most common real accessibility bugs — interviewers like to describe one and ask you to spot exactly why it breaks for some users.
  • :nth-child() comes up constantly for zebra-striping tables/lists and picking specific items without adding extra classes just to target them.
  • ::before/::after come up any time the conversation turns to icons, decorative content, or clearfix-style techniques — knowing they're not real DOM nodes is the exact detail interviewers probe.
🔥 Easy interview recall

:hover → mouse only

:focus-visible → shows a ring when keyboard nav needs it

::before / ::after → generated content, never in the DOM

Think: one colon (:hover) → a real element in a state two colons (::before) → a made-up sub-part CSS invents

🧠 Visual Mental Model — what a pseudo-element actually is
⚠️ Common Trap

A :hover-only menu isn't just a style choice. Keyboard-only and touch-only users never trigger :hover at all, so anything that only appears on hover is functionally unreachable for them — it needs an equivalent :focus/:focus-visible rule (or a different interaction pattern) to stay usable.

🔄 Likely Follow-up

"So how do you fix a hover-only dropdown without redesigning it?" Add the same reveal rule for :focus-visible on the trigger element, so Tabbing to it produces the same result a mouse hover already does — no visual redesign needed.

🎯 Say this in the interview — the exact lines to land

"Pseudo-classes target a real element in a certain state or position — :hover, :focus, :focus-visible, :disabled, :checked, and structural ones like :nth-child() — while pseudo-elements like ::before and ::after generate a sub-part that was never a real DOM node. The practical trap: anything that only appears on :hover is invisible to keyboard-only and touch-only users, so it needs an equivalent :focus-visible rule to stay usable."

  • :hover → mouse-only — never the only way to expose something interactive.
  • :focus → fires for any focus method, including a plain click :focus-visible → shows a ring only when the browser judges it's actually needed
  • :disabled / :checked → target real form state directly, no extra class needed.
  • :nth-child() → structural/positional selection — picks by position among siblings, not by type or class.
  • ::before / ::after → generated content, never a real DOM node — JavaScript can never select it.
📖 Explanation ▾

The interaction/state pseudo-classes all target a real element that's already in the DOM — they just react to something happening to it. :active fires while it's being pressed down. :disabled and :checked read a real form state straight from the markup, no extra class needed. :focus fires the moment an element receives focus, by any method at all — a click, a tap, a Tab press, even a script calling .focus(). :focus-visible narrows that down: it's still :focus, but the browser adds its own judgment about whether a visible ring is actually useful right now — typically yes for keyboard navigation, typically no for a plain mouse click on a button. That judgment is a browser heuristic, not something a page controls directly.

:nth-child() is a structural pseudo-class — it selects by position among siblings, counting every sibling regardless of tag, not just matching ones. That's the same idea behind picking "any position pattern" without adding a class to every single item just to target one of them.

::before and ::after insert generated content right next to an element's real content, driven entirely by a content value in CSS. Because that content is invented at render time, it never becomes a real node — there's nothing for document.querySelector, .children, or any DOM API to ever find. That's also why they're limited to decorative or purely visual roles (icons, quote marks, the old clearfix trick) — real, interactive, or meaningful content still belongs in the actual markup.

💻 See the code ▾
CSS 
button:hover { background: #f4f4f5; }         // pointer is over it right now
button:focus { outline: 2px solid #2563eb; }  // focused by ANY method — click, tap, Tab
button:focus-visible { outline: 2px solid #2563eb; } // focused AND browser thinks a ring is needed
button:active { transform: translateY(1px); }  // being pressed down, right now
button:disabled { opacity: .5; }             // real disabled form state
input:checked + label { font-weight: 700; } // paired checkbox/radio is checked

:focus-visible narrows :focus down to the cases a browser actually judges need a visible ring — typically keyboard navigation, not a plain mouse click.

CSS 
li:nth-child(odd) { background: #f8fafc; }  // 1st, 3rd, 5th…
li:nth-child(3) { color: #b91c1c; }        // exactly the 3rd item, nothing else

:nth-child() counts position among all siblings, not just matching ones — the same idea works for table rows, cards, or any repeated list.

CSS 
.badge::before { content: "🔥 "; }              // generated text, before the real content
.tooltip-trigger::after { content: attr(data-tip); } // pulls a value from a data attribute

Neither ::before nor ::after creates a real element — document.querySelector can never find them, because they were never added to the DOM.

CSS 
.info-btn:hover .tooltip,
.info-btn:focus-visible .tooltip {   // same rule, added for keyboard focus
  display: block;
}

Without the second selector, Tab moves right past .info-btn and the tooltip never appears — exactly the failure shown in the first diagram above.

🌍 Real-world example ▾

A dropdown that only a mouse can open. A nav menu built with .menu:hover .dropdown { display: block; } looks perfect in every manual click-through, but a keyboard-only tester tabbing through the page finds it simply never opens — Tab moves past the trigger and nothing shows. Adding the identical rule for :focus-visible on the trigger fixes it with zero change to how the menu looks or works for a mouse user.
