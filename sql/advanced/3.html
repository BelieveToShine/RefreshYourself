Execution Plans — what the database actually did, not what you asked for

What is a query execution plan, and what does reading one actually tell you?

Why it matters ▾
  • Reading a plan is the core skill behind almost every "why is this query slow" interview question — you can't answer that question without one.
  • Interviewers use it to check whether you actually understand index seek vs. table scan, not just that you know the term "execution plan."
  • A frequent follow-on trap: knowing the term but not knowing that an estimated plan's percentages aren't real, measured timing.
🔥 Easy interview recall

Execution plan = "the real route the engine took, not the destination you asked for."

Think: the same SQL text can get a different plan next time — the engine decides fresh from the current data and indexes, it isn't fixed by the query text alone.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A high percentage cost in the plan is not automatically the real bottleneck. In an estimated plan, that percentage is the optimizer's relative-cost guess from statistics, not measured wall-clock time — to see real timing you need an actual/runtime plan, one that actually ran the query.

🔄 Likely Follow-up

"What's the difference between an estimated and an actual execution plan?" An estimated plan is generated without running the query, using statistics to guess row counts and costs; an actual plan runs the query for real and reports the true row counts and timings alongside the same plan shape — a big mismatch between estimated and actual row counts is itself a red flag, often meaning stale statistics.

🎯 Say this in the interview — the exact lines to land

"An execution plan is the real step-by-step strategy the engine chose to run the query — which operations it uses, in what order, and roughly how expensive each step is estimated to be. Reading one tells you whether it's doing an index seek or a table scan, and which step is doing the most work."

  • Index Seek → jumps straight to matching rows using an index — usually the cheap step.
  • Table Scan → reads every row in the table — usually the expensive step.
  • Estimated cost → the optimizer's statistics-based guess, not measured time.
  • Actual/runtime plan → run it to see the real row counts and real timings, not just the estimate.
  • Same SQL text → can get a different plan later if the data or indexes it depends on change.
📖 Explanation ▾

An execution plan is the step-by-step strategy the database engine actually picked to run a query — which operations it performs (a scan, a seek, a join, a sort), in what order, and roughly how much relative work the optimizer expects each step to cost. It's produced by the query optimizer, which weighs the available indexes and the table's statistics before choosing a route — that's why the same SQL text can get a different plan later, once the data or the indexes it depends on have changed.

The two operations worth recognizing on sight are an Index Seek — the engine jumps straight to the rows it needs using an index, touching only what matches — and a Table Scan — the engine reads every row in the table to find what matches, because no useful index exists, or the optimizer decided one wasn't worth using. A scan sitting on a large table is usually the first place to look when a query is slow.

🌍 Real-world example ▾

An execution plan is like getting a delivery driver's actual route instead of just the destination — it tells you whether they took the highway (an index seek) or drove down every side street first (a table scan) to get there.
