Lambdas & Closures — lambdas that remember variables

"What is a closure, and what's the classic bug when you capture a loop variable?"

Why it matters ▾
🎒 Closure
❗ ProblemA lambda often needs a variable from the method around it, but it may run later — after that code has moved on — so it has to carry that variable along somehow.
✅ SolutionThe compiler moves the captured variable into a hidden class and the lambda uses it there — the lambda captures the variable itself, not a copy of its value.
RecallClosure = a lambda plus the variables it captured.
🔥 Easy interview recall

Closure = "a lambda that remembers the variable, not the value."

Think: for → one shared variable → all show the last value foreach → a new variable each pass → each shows its own

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A lambda does not copy the variable's value when it is created. It captures the variable itself, so if the variable changes later, the lambda sees the new value — that is the loop bug.

🔄 Likely Follow-up

"How do you fix it, and does capturing cost anything?" Copy the loop variable into a local inside the loop (int copy = i;). Capturing makes the compiler allocate a hidden object, so it can matter in hot code — a static lambda promises to capture nothing (see the performance checklist).

🎯 Say this in the interview — the exact lines to land

"A closure is a lambda that captures variables from the surrounding method. The compiler stores them in a hidden class, so the lambda shares the variable, not a copy of its value. In a for loop every lambda shares one i and sees its final value; foreach gives each iteration its own variable. The fix is to copy into a local inside the loop."

  • Lambdas capture variables, not values — later changes are visible to the lambda.
  • The compiler builds a hidden class to hold captured variables — that is an allocation.
  • for → one shared i, so 3, 3, 3; foreach (since C# 5) → a fresh variable each pass.
  • Fix: copy into a local inside the loop body.
  • A static lambda can't capture anything — the compiler rejects it if it tries.
📖 Explanation ▾

A lambda is a short inline method like x => x * 2. If it uses a variable from the method around it, it is a closure. The compiler creates a hidden class, makes that variable a field of it, and both the method and the lambda use that field — which is why the lambda sees changes. It builds on delegates.

The classic bug: in for (int i = 0; i < 3; i++) every lambda captures the same i. By the time they run, the loop has finished and i is 3. A foreach loop variable is fresh on each pass (since C# 5), so it does not have this bug. The same "runs later, sees the current value" effect shows up in deferred LINQ queries and iterators.

To fix the loop, copy i into a local declared inside the loop body — each pass then has its own variable. The cost is a hidden object plus a delegate allocation, which is fine normally and worth knowing in hot paths.

💻 See the code ▾
C# 
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));

foreach (var a in actions) a();   // 3 3 3 — they all share one i

The bug: three lambdas, one shared i.

C# 
var fixedActions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    int copy = i;                       // a new variable each pass
    fixedActions.Add(() => Console.WriteLine(copy));
}

foreach (var a in fixedActions) a();   // 0 1 2

Copy into a local and each lambda captures its own variable.

🌍 Real-world example ▾

Wiring a button per row. Creating a handler like () => Delete(i) inside a for loop makes every handler see the same final i — copying i to a local first gives each row its own.
