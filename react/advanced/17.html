⭐ React · Advanced · Should Know

The codebase didn't get worse overnight — it just outgrew its own shape

"A component has grown to 1000+ lines — how would you refactor it?"

Why it matters ▾
  • A component crossing 1000+ lines, or a value threaded through five layers just to reach one child, is one of the clearest "this codebase outgrew its own shape" signals a real interviewer probes for.
  • It checks whether a candidate reaches for Context/composition and splits along real responsibility boundaries — not whether they can just chop a file into pieces.
  • Comes up specifically in senior and team-lead interviews, where ownership across multiple teams is as much the question as the code itself.
🔥 Easy interview recall

Splitting into more files ≠ fixing it — extracting along the actual tangled responsibilities does.

Think: many small, still-tangled files are still the same god component, just spread across more places.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Splitting a giant component into more, smaller components always fixes it. Splitting alone can just spread the same tangled logic across more files without actually separating concerns — the real fix is identifying the distinct responsibilities tangled together (data fetching, business logic, presentation) first, then splitting specifically along those boundaries, not by size or file count.

🔄 Likely Follow-up

"How would you structure ownership and shared components across multiple teams on one app?" Carve the app into feature areas each team clearly owns, with a deliberately-governed shared component library — its own review process and versioning — for the pieces that genuinely need to be common. Ambiguous, everything-is-shared ownership is exactly what causes this growing-pain friction; clear boundaries fix it.

🎯 Say this in the interview — the exact lines to land

"For excessive prop drilling, I'd redesign using Context or composition instead of threading props through every layer. For a component past 1000 lines, I wouldn't just split it into more files — I'd find the distinct responsibilities tangled together — fetching, business logic, presentation — and extract along those boundaries. And across multiple teams, I'd carve out feature ownership per team plus a small, deliberately-governed shared library for what's genuinely common."

  • Context or composition → reach for these instead of threading a value through every intermediate layer.
  • 1000+-line component → split along distinct responsibilities (fetching, business logic, presentation), not by size.
  • More, smaller files alone → doesn't fix a god component if the same tangled logic just spreads across them.
  • Multiple teams on one app → clear feature-area ownership, one team per area.
  • Shared component library → its own review process and versioning, not an ambiguous "everything is shared."
📖 Explanation ▾

Excessive prop drilling means a value gets passed through several components that don't use it themselves, just to reach the one that does. The fix isn't a fourth prop three layers down — it's Context for a value many components genuinely need, or composition (passing a component as a prop or as children) so the value skips straight past the layers that don't care about it.

A 1000+-line component is rarely one big problem — it's usually three or four small ones stacked in the same file: fetching data, running business rules or validation, and rendering markup. Splitting it into more files only helps if the split follows those actual seams. Cutting it in half by line count, or by guesswork, just produces several tangled files instead of one.

When multiple teams build the same app, the friction is usually ownership, not code. Carving the app into feature areas — each clearly owned by one team — removes the "who's allowed to touch this" ambiguity. A shared component library still exists for the genuinely common pieces, but it needs its own review process and versioning discipline — otherwise "shared" quietly becomes "unowned."

💻 See the code ▾
JSX 
// BEFORE — one file, three jobs tangled together
function UserDashboard() {
  // fetching + business logic + rendering, all mixed into ~1000 lines
}

// AFTER — split along responsibility, not by size
function useUserData() { /* data fetching only */ }
function getTotal(orders) { /* business logic only */ }
function UserCard({ user, total }) { /* presentation only */ }

Same three jobs as before — the fix isn't more files, it's each file owning exactly one of those jobs.

🌍 Real-world example ▾

A core component has grown past 1000 lines, mixing data fetching, validation, and rendering, and nobody wants to touch it anymore. Identify the distinct responsibilities tangled together — fetching, business logic, presentation — and extract each into its own focused piece. Split by responsibility, not by an arbitrary line count.
