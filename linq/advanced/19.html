Scenario: when "unique" is only a promise, reach for Single

"You're looking up a user by email, where email is supposed to be unique but isn't actually enforced by a DB constraint — which of the four would you reach for, and why?"

Why it matters ▾
🔎 Unique by promise, not by constraint
❗ ProblemReaching for FirstOrDefault "to be safe" on a lookup that's supposed to be unique means a real duplicate — caused by a missing DB constraint, a race condition, or a bad migration — silently returns whichever row happened to come first, and the data bug keeps happening invisibly.
✅ SolutionSingle/SingleOrDefault throw the moment there's more than one match — when uniqueness is supposed to be true, that exception is a feature: it surfaces the data-integrity problem immediately instead of hiding it behind a quietly wrong answer.
RecallSingle = "this MUST be unique — throw if it isn't." That throw is doing its job.
🔥 Easy interview recall

FirstOrDefault → hides a duplicate, returns row #1

SingleOrDefault → throws on a duplicate, surfaces the bug

Think: not found → null either way. Found twice → Single/SingleOrDefault throw, and that's correct.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

SingleOrDefault is not "the safe version of Single." It only tolerates the zero-match case by returning the type default instead of throwing — it still throws on 2+ matches, exactly like Single, because the uniqueness claim is the same.

🔄 Likely Follow-up

"What would you actually do once that exception gets thrown in production?" Let it surface as a real error (log it with the offending email), not swallow it with a try/catch that falls back to FirstOrDefault — that would just reintroduce the exact bug Single was added to catch. The right fix is adding the missing unique constraint at the database.

🎯 Say this in the interview — the exact lines to land

"Since email is supposed to be unique, I'd use SingleOrDefault — null on zero matches, the user on exactly one match, and a thrown exception the moment there are two or more. That exception is intentional: it surfaces a real data-integrity bug immediately instead of FirstOrDefault silently returning whichever duplicate row happened to come first."

  • Uniqueness is a real data rule → reach for Single/SingleOrDefault, not FirstOrDefault.
  • A thrown exception on a duplicate → a feature here, not a bug to suppress.
  • FirstOrDefault on "unique" data → hides a real duplicate instead of catching it.
  • Zero matches → null either way — that part isn't the decision point.
📖 Explanation ▾

This scenario is exactly where Single earns its keep over First. First/FirstOrDefault say "I expect at least one match, and I don't care if there's more" — the right contract when multiple matches are a normal, expected outcome. Single/SingleOrDefault say "I expect exactly one, and more than one is a bug" — the right contract here, because the application's own data model claims email addresses are unique.

Without a real unique constraint on the Email column, nothing in the database actually stops two rows from sharing one — a bad migration, a race between two concurrent sign-ups, or manually edited data can all produce exactly that duplicate. If the lookup code uses FirstOrDefault, that duplicate is invisible: the query still returns a user, the request still succeeds, and the only symptom is whichever row happens to sort first quietly winning every time — until two different parts of the system start disagreeing about which "the" user with that email actually is.

SingleOrDefault turns that same duplicate into a thrown InvalidOperationException the instant it's hit — loud, immediate, and attributable to the exact query that found it. That's strictly more useful than a silent wrong answer, even though it means the endpoint fails instead of "working." The real fix is adding the unique constraint the data model always should have had; the exception is just what surfaces that it's missing.

💻 See the code ▾
C# 
// Looks "safe," but hides a real duplicate
var user = await db.Users
    .FirstOrDefaultAsync(u => u.Email == email); // ❌ picks row #1 if two rows share this email

If two rows share this email, this line always returns the same one — silently, with no signal anything is wrong.

C# 
// Documents the uniqueness assumption AND enforces it
var user = await db.Users
    .SingleOrDefaultAsync(u => u.Email == email); // ✅ null if none, throws if 2+

if (user is null)
    return NotFound(); // zero matches — a normal, expected outcome

A genuine duplicate now throws right here, with a stack trace pointing at this exact query — not a quiet wrong answer three layers downstream.

🧭 Use Cases — recognize these when they happen to you ▾
1 The email genuinely doesn't exist yet — a new sign-up check

A clean "not found" case — behaves exactly like FirstOrDefault here, returning the type default. This isn't the part of the decision that matters.

RememberZero matches → null either way, nothing special yet.
2 Exactly one match — the common, expected case

The normal path, but SingleOrDefault still earns its keep here — it documents, in the code itself, that this lookup assumes uniqueness, which FirstOrDefault never communicates.

RememberEven the happy path benefits — Single documents the uniqueness assumption.
3 A missing DB constraint let two rows end up with the same email

This is exactly the case Single/SingleOrDefault exist for. FirstOrDefault would silently return one of the two rows forever; SingleOrDefault throws the moment it's hit. A common interview trap: treating the thrown exception as the bug, when the duplicate data is the actual bug — the exception is just the messenger.

RememberA duplicate "unique" value → let it throw, then fix the missing constraint.
🌍 Real-world example ▾

A login endpoint using FirstOrDefaultAsync(u => u.Email == email) has been quietly authenticating users against whichever duplicate row sorts first, for months, after a bad data migration created a handful of duplicate emails. Switching to SingleOrDefaultAsync doesn't fix the data — it makes the next duplicate throw immediately instead of silently picking a winner, turning an invisible correctness bug into a loud, fixable one.
