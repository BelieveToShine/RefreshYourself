Aurora's replicas share one storage layer — that's the whole trick

"How does Aurora's storage architecture let it scale reads further than standard RDS?"

Why it matters ▾
  • Tests whether you know what actually makes Aurora different from "RDS but faster," not just a marketing name.
  • A natural entry point into the RDS vs. Aurora vs. DynamoDB decision question.
  • Explains why Aurora failover feels near-instant compared to standard RDS Multi-AZ failover.
🔥 Easy interview recall

Aurora = "one shared storage layer under many computes."

Think: a replica reads the same live data as the primary — it isn't waiting for its own copy to catch up.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Aurora replicas lag the same way RDS read replicas do." They don't — Aurora replicas read from the same shared storage layer as the primary, so lag is typically single-digit milliseconds, while standard RDS read replicas copy over the network asynchronously, so their lag is real and meaningfully higher.

🔄 Likely Follow-up

"RDS vs. Aurora vs. DynamoDB — how do you pick?" RDS for a standard relational workload that doesn't need Aurora's extras; Aurora when you need higher read scaling, faster failover, or serverless elasticity within a relational model; DynamoDB when the access pattern is key-value/document at massive scale and you don't need relational joins or transactions across arbitrary tables.

🎯 Say this in the interview — the exact lines to land

"Aurora's shared storage layer is why it scales reads further and fails over faster than standard RDS."

  • Shared storage → every replica reads live data, never a separate copy playing catch-up.
  • Up to 15 replicas, because none of them duplicate the primary's data.
  • RDS → standard relational, no Aurora premium needed.
  • Aurora → read scaling, fast failover, serverless elasticity within a relational model.
  • DynamoDB → key-value/document at massive scale, no relational joins/transactions across arbitrary tables.
📖 Explanation ▾

Aurora decouples compute from storage. Underneath the primary and every read replica sits one distributed, self-healing storage layer, automatically replicated across 6 copies in 3 Availability Zones. Because replicas read that same shared layer instead of keeping their own copy, replication lag is typically single-digit milliseconds, and Aurora supports up to 15 read replicas without each one duplicating the primary's data.

Aurora Serverless auto-scales compute capacity up and down — even close to zero — based on load, which fits unpredictable or intermittent workloads well. Failover is faster than standard RDS Multi-AZ for the same reason replicas scale further: the storage layer is already shared, so promoting a replica means pointing traffic at data that's already current, not re-attaching storage first.

🌍 Real-world example ▾

A reporting-heavy app adds 5 Aurora read replicas to handle analytics queries without touching the primary's write capacity — the shared storage layer is what keeps replica lag negligible even as those replicas get added.
