ETag + If-Match — stop the lost update over HTTP

Two clients update the same resource — how do you stop a lost update over HTTP?

Why it matters ▾
🔖 ETag + If-Match
❗ ProblemTwo clients read the same record and both edit it; the second PUT silently overwrites the first, so one person's change is lost with no error anywhere.
✅ SolutionThe server hands out a version (ETag) on every read; the client sends it back in If-Match on write, and a stale version is rejected with 412 Precondition Failed.
RecallETag = the version. If-Match = "only if it's still that version."
🔥 Easy interview recall

ETag → the resource's version, sent on read

If-Match → write only if still that version

Think: Stale version → 412 Precondition Failed Header missing, but required → 428 Precondition Required

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"ETag is just for caching." If-None-Match on a GET saves bandwidth with a 304; If-Match on a PUT is the write-side use that stops two clients overwriting each other.

🔄 Likely Follow-up

"Where does the ETag value come from?" From a version of the row — usually a row-version / concurrency-token column (or a hash of the content). It's opaque to the client, which just echoes it back; the database check on save is what makes it safe.

🎯 Say this in the interview — the exact lines to land

"On read I return a strong ETag — an opaque version of the resource, often built from a row-version column. On write the client sends it back in If-Match; if it no longer matches I return 412 Precondition Failed, so the second writer re-reads and retries instead of silently overwriting. If I want to force clients to send it, a missing header gets 428."

  • ETag on every read → an opaque version of the resource.
  • If-Match on PUT/PATCH/DELETE → "only if it's still this version".
  • Mismatch → 412; header missing but required → 428.
  • If-None-Match vs. If-Match → cache reads (304) vs. protect writes.
  • EF Core concurrency token → the database enforces it, not just the handler.
📖 Explanation ▾

This is optimistic concurrency: nobody takes a lock, the server just detects a conflict at write time. Every read returns an ETag — a quoted, opaque version string like "v1". The client keeps it, edits, then sends it back as If-Match on the update. If the resource changed in between, the versions differ and the server answers 412 Precondition Failed. The client re-reads, merges or asks the user, and tries again.

Use a strong ETag here — If-Match compares strongly, so a weak ETag (W/"…") won't match. To force the habit, answer 428 Precondition Required when a write arrives with no If-Match. In ASP.NET Core you build the header yourself; the value usually comes from an EF Core row-version concurrency token, so the database also rejects a stale save (see Optimistic Concurrency & Row Versioning). It's the write-side partner of the If-None-Match caching on Caching Strategies.

💻 See the code ▾
C# 
var p = await _db.Products.FindAsync(id);
if (p is null) return NotFound();
Response.Headers["ETag"] = ETagOf(p);   // ✅ version goes out on every read
return Ok(p);

static string ETagOf(Product p) => $"\"{Convert.ToBase64String(p.RowVersion)}\"";   // helper on the controller: quoted, opaque

The ETag is just the row version, quoted — the client never needs to understand it.

C# 
[HttpPut("{id}")]
public async Task<IActionResult> Put(int id, ProductDto dto,
    [FromHeader(Name = "If-Match")] string? ifMatch)
{
    if (ifMatch is null) return StatusCode(StatusCodes.Status428PreconditionRequired);   // ✅ header required
    var p = await _db.Products.FindAsync(id);
    if (p is null) return NotFound();
    if (ETagOf(p) != ifMatch) return StatusCode(StatusCodes.Status412PreconditionFailed);   // ❌ stale
    p.Name = dto.Name;
    // ...save — see next card
}

Missing header → 428; stale header → 412; only a matching version reaches the update.

C# 
_db.Entry(p).Property(x => x.RowVersion).OriginalValue = Convert.FromBase64String(version);
try { await _db.SaveChangesAsync(); }
catch (DbUpdateConcurrencyException)
{
    return StatusCode(StatusCodes.Status412PreconditionFailed);   // ✅ lost the race after the check
}

Checking in code and then saving still leaves a gap — the concurrency token makes the database refuse a stale save too (version is the If-Match value with its quotes removed).

🧭 Use Cases — recognize these when they happen to you ▾
1 A user keeps an edit form open for ten minutes while a colleague saves a change

The form still holds the ETag from when it loaded. The save is rejected with 412, and the UI re-fetches the latest copy and lets the user merge — instead of quietly wiping the colleague's edit.

RememberStale edit → 412 → re-read, then retry.
2 A script updates resources without ever sending If-Match

If the API must never allow blind overwrites, it answers 428 Precondition Required when the header is absent — so clients learn to send a version rather than guess.

RememberNo header, but required → 428.
3 The code compares the ETag, then saves — and two requests squeeze through together

Two requests can pass the version check at the same moment, then both save. Put the version into the database update itself (an EF Core concurrency token) so one of them fails with DbUpdateConcurrencyException. A classic follow-up.

RememberLet the database enforce the version too.
🌍 Real-world example ▾

Two support agents open the same customer record. Agent A saves a new phone number; agent B, still on the old copy, saves a new address a minute later. Without If-Match, B's save puts the old phone number back. With it, B gets 412, the screen reloads with A's change, and B re-applies the address.
