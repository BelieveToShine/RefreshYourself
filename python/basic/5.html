str is immutable — every "modification" actually creates a new string

"Are Python strings mutable? Why immutable? What's the difference between str and bytes?"

Why it matters ▾
  • String questions show up in almost every Python interview — knowing *why* strings are immutable, not just that they are, separates a candidate who understands the language from one who's memorized syntax.
  • The +=-in-a-loop performance trap is a real bug that shows up in code review, not a textbook curiosity.
  • str vs. bytes confusion is a common real bug the moment file I/O or network data enters the picture.
🔥 Easy interview recall

str = "immutable — every 'change' builds a brand-new string."

Think: += in a loop → copies everything so far, O(n²) "".join() → builds the result once, O(n)

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

+= in a loop is not free. It looks fine on a handful of strings, but because str is immutable, each += copies everything built so far — at scale that's O(n²); build with "".join(parts) instead.

🔄 Likely Follow-up

"Why can't you decode a str or encode bytes?" str is already decoded text — encode it to get bytes. bytes is already raw data — decode it to get text. Calling the wrong direction raises an AttributeError, a common trap for anyone used to Python 2's looser split between the two.

🎯 Say this in the interview — the exact lines to land

"String concatenation with += in a loop is quietly O(n²) — because str is immutable, every += copies everything built so far, so "".join(parts) is the fix. Separately, str is Unicode text and bytes is raw binary data — I never conflate the two, and I always know the encoding when moving between them with .encode()/.decode()."

  • += in a loop → a real copy every iteration, O(n²) at scale; "".join() is O(n).
  • str → immutable Unicode text; every "change" returns a new object, never mutates in place.
  • bytes → raw binary data (integers 0–255); convert with .encode()/.decode(), always naming the encoding.
  • Immutability → what makes a str safely hashable as a dict key and safe to pass around without a defensive copy.
📖 Explanation ▾

Every string operation that looks like a change — concatenation, .replace(), .upper() — returns a brand-new string object; the original is untouched. That's not an accident of implementation: because a str can never change after creation, Python can hash it once and reuse that hash safely forever, which is exactly what lets a string be used as a dictionary key or set member. It also means a string can be passed around without a defensive copy — nothing downstream can mutate it out from under the caller.

Slicing (s[start:stop:step]) works like list slicing, including negative indices to count from the end. f-strings (f"{x}") embed expressions directly inside the literal — the fastest and most readable formatting option. split() breaks a string into a list on a delimiter; join() reverses that, called on the delimiter string itself with an iterable of pieces (",".join(parts)).

str holds Unicode text — a sequence of Unicode code points. bytes holds raw binary data — a sequence of integers from 0 to 255, with no idea of "text" at all. Moving between them is always explicit and always needs an encoding (commonly UTF-8) to map characters to byte values. Internally, CPython doesn't store a str as a flat array of UTF-8 bytes — it picks the smallest fixed-width representation (1, 2, or 4 bytes per character) that fits the widest character actually present in that specific string (PEP 393, "flexible string representation").

💻 See the code ▾
Python 
# ❌ O(n²) — each += copies everything built so far
result = ""
for word in words:
    result += word + " "

# ✅ O(n) — one final string, built once
result = " ".join(words)

Same output, very different cost once words gets long.

Python 
text = "café"
data = text.encode("utf-8")     # str -> bytes
print(data)                     # b'caf\xc3\xa9'

back = data.decode("utf-8")     # bytes -> str
print(back == text)             # True

Always know the encoding on both sides — decoding with the wrong one can raise UnicodeDecodeError or silently produce garbled text.

🌍 Real-world example ▾

Reading a file opened as open(path, "rb") gives back bytes, not str. Calling line.split(",") on that bytes object raises TypeError: a bytes-like object is required, not 'str', because the separator itself is a str. The fix is one .decode("utf-8") right after reading, before any text processing starts.
