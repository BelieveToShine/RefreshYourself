Cast vs. OfType — throw on a mismatch, or quietly skip it?

"Both Cast<T>() and OfType<T>() work on object-typed/non-generic sequences — what's the actual difference in behavior?"

Why it matters ▾
🎯 Cast<T>()
❗ ProblemSometimes a mismatched element in a supposedly-uniform sequence is itself a real bug you need to know about immediately, not silently lose.
✅ SolutionCast<T>() converts every element and throws InvalidCastException the instant one doesn't match T — it asserts the whole sequence is uniform.
RecallCast = "I'm asserting this, not checking it" — throws on the first mismatch.
🧹 OfType<T>()
❗ ProblemOther times a mixed sequence is expected on purpose, and you only want the elements that happen to be T — the rest are irrelevant, not an error.
✅ SolutionOfType<T>() filters to just the elements that match T and silently skips everything else — no exception, ever.
RecallOfType = "give me only the ones that fit" — skips the rest, no exception.
🔥 Easy interview recall

Cast<T>() → throws on the first mismatch

OfType<T>() → skips every mismatch, silently

Think: Cast trusts the data is already uniform. OfType doesn't trust it, and doesn't need to.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Picking the wrong one hides a real bug, or crashes for no reason. OfType on data that should have been uniform quietly swallows the exact mismatch you needed to know about; Cast on data you merely wanted to filter crashes the whole pipeline over an element you never actually needed.

🔄 Likely Follow-up

"Isn't list.Where(x => x is Cat) the same as OfType<Cat>()?" Almost — but OfType filters and casts in one step and skips null entries automatically, where a Where + manual cast still needs that separate cast written out by hand.

🎯 Say this in the interview — the exact lines to land

"Cast<T>() throws InvalidCastException on the first element that isn't T — it asserts uniformity. OfType<T>() silently skips anything that isn't T — it filters, it never throws."

  • Cast<T>() → use when you're certain every element is T and want a loud failure if you're wrong.
  • OfType<T>() → use when you expect a genuinely mixed sequence and only want the matching subset.
📖 Explanation ▾

Both methods exist for the same starting point: a sequence typed as object or a non-generic IEnumerable (an ArrayList, a mixed object[]) that you want to treat as IEnumerable<T>. Where they diverge is entirely about what happens when an element genuinely isn't T.

Cast<T>() makes a promise on your behalf: "every element here really is T." The moment it hits one that isn't, that promise is broken and it throws InvalidCastException right there, mid-enumeration. OfType<T>() makes no such promise — it tests each element first and only yields the ones that actually match, quietly dropping the rest (including any null entries, which fail a type check the same way a wrong type would).

Cast<T>()OfType<T>()
On a matching elementyields it, convertedyields it, converted

On a null element❌ throws (for a value-type T) or passes through as null (reference T)skips it — never matches a type check
What it's really saying"I already know these are all T""give me only the ones that are T"
💻 See the code ▾
C# 
object[] items = { new Cat(), new Cat(), 42, new Cat() };

foreach (var c in items.Cast<Cat>())
    c.Meow();   // ❌ throws InvalidCastException on the 42

Cast gets exactly two Cats meowing, then crashes on the third item.

C# 
foreach (var c in items.OfType<Cat>())
    c.Meow();   // ✅ runs for all three Cats — the 42 is just skipped

OfType never sees the 42 as a problem — it just isn't a Cat.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're looping through an intentionally mixed collection

A UI event bus, a plugin list, a JSON payload parsed into object — these are mixed by design. OfType<Cat>() pulls out exactly what you want and ignores everything else, safely. This is the #1 scenario you'll actually run into.

RememberMixed on purpose → OfType.
2 You're validating that a sequence is already supposed to be uniform

Working with an old, non-generic ArrayList or object[] that a contract already guarantees holds only one type? Cast<T>() is the deliberate choice — if that guarantee is ever broken, you want to know immediately, not silently lose data.

RememberContract guarantees uniformity → Cast, fail loudly if that's wrong.
3 You reach for OfType out of habit on data that should be uniform

OfType never tells you it dropped something. If the source was supposed to be entirely Cat and one record got corrupted upstream, OfType just quietly produces one fewer Cat — no exception, no log line, nothing to notice until the count looks wrong later.

RememberShould-be-uniform data hidden behind OfType → a silently lost bug.
🌍 Real-world example ▾

You're emptying a box labelled "circles only." Cast<Circle>() is grabbing each shape and trusting the label — if a square turns up, that's a packing mistake worth stopping for. OfType<Circle>() is sorting a box you already know is mixed, picking out just the circles and leaving everything else in the box without a second thought.
