Abstraction isn't free — but is it ever actually your bottleneck?

Does using design patterns and abstraction cost you performance — and when does that actually matter?

Why it matters ▾
🧮 Virtual Dispatch
❗ ProblemA virtual method or interface call can't be resolved and inlined at compile time the way a direct call can — the runtime looks up the right implementation through a vtable (or interface dispatch table) on every single call.
✅ SolutionThat lookup is real but tiny — it only becomes measurable in an extremely hot loop doing millions of calls a second; against a database call, a network round trip, or any I/O, it's noise.
RecallVirtual/interface call = one extra lookup step — real, almost never the actual bottleneck.
📦 Boxing Through an Abstraction
❗ ProblemPassing a value type through a non-generic interface, or as object — which happens when a pattern is implemented against a non-generic abstraction — boxes it onto the heap, a real, measurable allocation in a hot path.
✅ SolutionThis is a cost of that specific abstraction choice, not of OOP itself — see Boxing & Unboxing and the C# Performance Checklist; a generic interface or method keeps the value in place with no box at all.
RecallBoxing is the abstraction's fault, not abstraction's fault — a generic version removes it.
🎁 Decorator / Wrapper Chains
❗ ProblemEach layer in a Decorator stack is its own object and its own extra method call in the chain — stack several layers deep on a hot path and that's several extra calls and allocations per operation.
✅ SolutionFor a handful of layers this is negligible — a small, real cost traded deliberately for composing behavior at runtime instead of writing one fixed class per combination.
RecallEach decorator layer = one more object, one more call — fine in moderation.
🧱 Too Many Layers "Just in Case"
❗ ProblemInterfaces and layers added for a flexibility nobody has asked for yet make code harder to follow and slower to debug — a real cost, just not a runtime-performance one.
✅ SolutionThis is exactly what YAGNI already warns against — add the abstraction when a second real implementation actually shows up, not speculatively.
RecallOver-abstraction's real cost is readability and debugging time, not CPU time.
🔥 Easy interview recall

🧮 Virtual/interface call → one extra vtable lookup, real but tiny

📦 Boxing → only when a value type crosses a non-generic abstraction

🎁 Decorator layers → one call + one allocation per layer

🧱 Too many layers → costs readability, not CPU

Think: profile before optimizing — I/O, database calls, and network round trips dominate almost every real app's latency budget, so abstraction cost is rarely the actual bottleneck.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Ripping out an interface "for speed" without a profiler number is premature optimization. Outside a measured hot loop, virtual dispatch and a layer of abstraction are essentially never what's actually slow.

🔄 Likely Follow-up

"So when would you actually remove an abstraction for performance?" Only after a profiler shows the abstraction itself — not a query, not I/O, not an allocation elsewhere — is the measured cost in a path that's genuinely hot; then a generic or non-virtual alternative is worth considering.

🎯 Say this in the interview — the exact lines to land

"Virtual dispatch, boxing through a non-generic abstraction, and decorator wrapper chains all have a small, real performance cost — but I'd profile first. In almost every real application, I/O, database calls, and network round trips dominate the latency budget long before any of that shows up."

  • Virtual/interface calls → one extra vtable lookup, measurable only in extremely hot loops.
  • Boxing → only when a value type crosses a non-generic interface or object; a generic version avoids it.
  • Decorator chains → one call + one allocation per layer, negligible for a handful of layers.
  • Over-abstraction → costs readability and debugging time, not CPU time.
  • The defensible answer → profile before you simplify good design.
📖 Explanation ▾

A direct call can be resolved — and often inlined — by the compiler/JIT, because there's only one possible method it could mean. A virtual or interface call can't be pinned down that early: the runtime has to look up the actual implementation through a vtable (or interface dispatch table) at the moment the call happens. That lookup is a real, extra step — it just rarely costs enough to matter next to a database round trip.

Boxing is a separate, sharper cost: it only happens when a value type crosses into a non-generic reference-typed slot — object, a non-generic interface, a non-generic collection. That's a cost of *that* abstraction choice, not of abstraction in general — a generic interface or List<T> keeps the value type in place with no box at all.

A Decorator chain trades a small, real cost — one extra object and one extra call per layer — for the ability to compose behavior at runtime instead of writing one fixed class per combination. And piling on interfaces "just in case," with no second implementation in sight, has a cost too — just not a runtime one: it's dev time spent reading and debugging layers that never earned their keep.

💻 See the code ▾
C# 
public interface IArea { double GetArea(); }

public struct Circle : IArea
{
    public double Radius;
    public double GetArea() => Math.PI * Radius * Radius;
}

IArea shape = new Circle { Radius = 2 };  // ❌ boxed the moment it's stored as IArea
double a = shape.GetArea();                     // ❌ runtime looks up GetArea via the interface

Storing a struct behind a non-generic interface reference boxes it onto the heap — the abstraction, not the struct itself, is what costs here.

C# 
double GetAreaOf<T>(T shape) where T : IArea
    => shape.GetArea();  // ✅ T is the concrete struct — no boxing

A generic constraint keeps the struct's real type — no box, and the call can be resolved far more directly than through a non-generic interface reference.

C# 
ICoffee coffee = new Espresso();
coffee = new MilkDecorator(coffee);         // layer 1: +1 object, +1 call
coffee = new SugarDecorator(coffee);        // layer 2: +1 object, +1 call
coffee = new WhippedCreamDecorator(coffee); // layer 3: +1 object, +1 call
coffee.Cost();                                   // ✅ 3 calls deep — negligible outside a hot loop

Each wrap is a small, real cost traded for composing behavior without writing one class per combination.

🧭 Use Cases — recognize these when they happen to you ▾
1 A teammate argues against adding an interface for testability because "it'll be slower"

Outside a hot loop, that extra virtual call is immeasurable next to the database call or network round trip the method is actually making. Ask for a profiler number before changing the design — testability, with a tiny measured cost, almost always wins.

Remember"It'll be slower" → ask for the profiler number, not the design change.
2 A profiler on an actually-hot path shows boxing coming from a non-generic interface

This is the one case where the abstraction choice is genuinely the measured cost — not a guess. Swap the non-generic interface or List<object> for a generic constraint or List<T>, and the box disappears with no change to the design's shape.

RememberBoxing shown by a profiler on a hot path → the one abstraction cost worth actually fixing.
3 A request's hot path runs through a dozen stacked Decorator layers, each doing almost nothing

A couple of layers is free; a dozen on a path that runs on every single request adds up to real, measurable overhead. This is the one legitimate case for collapsing some of them — backed by a profiler, not gut feel.

RememberA handful of decorator layers is free; a dozen on every request isn't — profile, then collapse if it's real.
🌍 Real-world example ▾

Scenario: ahead of a big sale event, the team debates stripping the Repository and Strategy interfaces out of a checkout service "to make it faster," with no profiler data yet.

The direct answer: don't — profile the actual request path under realistic load first. In the overwhelming majority of cases, the database queries, external API calls, and serialization dominate the time budget; removing the interfaces would save microseconds at best, while making an already time-pressured change riskier to review and roll back.
