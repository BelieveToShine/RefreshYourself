Hooks — why they can never live inside an if

"What are the Rules of Hooks, and why do they exist?"

Why it matters ▾
  • Comes up almost every time Hooks are discussed — usually as the very next question after "what is useState."
  • Explains a real, easy-to-hit bug: a Hook tucked inside an if, loop, or early return silently attaches its state to the wrong slot.
  • Separates someone who's memorized the syntax from someone who actually understands how React keeps track of Hook state.
🔥 Easy interview recall

Hooks = "matched by call order, not by name."

Think: Skip one conditionally, and every Hook after it shifts to the wrong slot — if (x) { useState() } breaks the fixed sequence React depends on.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"You can call a Hook conditionally if you're confident the condition will always evaluate the same way." React tracks Hooks purely by call order/position, not by any awareness of the condition itself — skip one on even a single render and every Hook called after it shifts to the wrong stored slot, no matter how "certain" the condition seemed.

🔄 Likely Follow-up

"Why were Hooks introduced instead of relying only on class lifecycle methods?" To let stateful logic be reused across components without wrapper-hell (HOCs/render props stacking on top of each other), and to keep related logic — like a subscription's setup and its own teardown — together in one place, instead of split across componentDidMount/componentWillUnmount in separate parts of a class.

🎯 Say this in the interview — the exact lines to land

"Hooks must be called at the top level, on every render, in the same order — never inside a condition, loop, or nested function, and only from a function component or another custom Hook. React matches each Hook to its stored state purely by call position, so skipping one on any render shifts every Hook after it into the wrong slot."

  • Never inside if / loop / nested function — the call position has to stay fixed every render.
  • React tracks Hooks by call order, not by name — there's no lookup by variable name underneath.
  • Skip one, and everything called after it shifts into the wrong stored slot.
  • Only call Hooks from function components or other custom Hooks — never a plain helper function.
  • They exist to reuse stateful logic without wrapper-hell, and to keep setup and teardown together.
📖 Explanation ▾

Hooks — useState, useEffect, useRef, useMemo, useCallback, and any custom Hook built from them — let a plain function component hold state and tie into React's lifecycle without needing a class at all.

The Rules of Hooks follow directly from how React stores that state: only call Hooks at the top level of a component or custom Hook, never inside a condition, loop, or nested function, and only call them from a React function component or another custom Hook. React doesn't track a Hook's state by its variable name — it matches each call to its internally stored slot by position, in a fixed sequence, on every single render. Skip a Hook conditionally and everything called after it lines up against the wrong slot instead.

Hooks replaced relying purely on class lifecycle methods for two concrete reasons: they let stateful logic move between components without stacking higher-order components or render props on top of each other, and they keep one piece of logic's setup and cleanup together in a single place, instead of split across separate lifecycle methods in a class.

💻 See the code ▾
JSX 
function Profile({ isLoggedIn }) {
  if (isLoggedIn) {
    const [name, setName] = useState('');  // ❌ Rules of Hooks violation
  }
  // ...
}

The Hook only runs when isLoggedIn is true — on renders where it's false, every Hook after this one would shift into the wrong slot.

JSX 
function Profile({ isLoggedIn }) {
  const [name, setName] = useState('');  // ✅ always called, top level

  if (isLoggedIn) {
    // the condition goes around USING the state, not around the Hook call
  }
}

useState runs unconditionally on every render — the condition moves inside the Hook's own logic or around its usage, never around the call itself.

🌍 Real-world example ▾

Think of a coat-check with numbered hooks on a wall. Every ticket number always corresponds to the same numbered hook. If the attendant skips ticket #3 sometimes, every coat behind it ends up hung on the wrong numbered hook whenever that skip happens — the same mismatch React's Hook order depends on never happening.
