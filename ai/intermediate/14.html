⭐ AI · Intermediate · Should Know

One gateway in front of every provider — so one going down never takes your app down

"What does an AI gateway actually give you — caching, fallback, rate limiting, observability — that calling a provider SDK directly doesn't?"

Why it matters ▾
  • Every part of an app that calls an LLM provider directly ends up re-implementing its own retry logic, rate-limit handling, and provider-specific SDK code — a gateway is how you stop repeating that.
  • Comes up once a candidate has shipped more than a toy LLM feature — interviewers use it to check you've thought about production reliability, not just prompts.
  • This page is scoped to "what is this piece of infrastructure" — the deeper cost-optimization and routing-decision mechanics are their own later topics.
🔥 Easy interview recall

AI gateway = "one door in front of every provider — it caches, throttles, and swaps providers for you."

Think: App code calls the gateway, never the provider SDK directly Gateway tries Provider A → down or rate-limited? → gateway retries Provider B automatically

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Thinking a gateway is only about hiding an API key. Its real job is centralizing retries, caching, and rate limiting so no single call site has to reinvent them — hiding the key is a side effect, not the point.

🔄 Likely Follow-up

"Does the gateway retry inside the same request, or does my app have to handle the retry?" Inside the same request — the gateway sits between your app and every provider, so it can retry against another provider before ever returning a response. Your app just sees one call that succeeded.

🎯 Say this in the interview — the exact lines to land

"An AI gateway sits between my application and the LLM providers, so every call goes through one place instead of hitting a provider SDK directly. That one place gives me caching, rate limiting, automatic fallback between providers, and centralized observability — for free, on every call site."

  • Caching → avoids paying for a repeated or near-identical request twice.
  • Rate limiting → protects both my own budget and the provider's own limits.
  • Fallback → Provider A down or throttled? The gateway retries Provider B automatically — no code change.
  • Unified API → switching providers doesn't mean rewriting every call site.
  • Observability → every call is logged and traced in one place, not scattered across the codebase.
📖 Explanation ▾

An AI gateway — also called an LLM proxy — sits between your application and the LLM provider(s), so the app makes one consistent call instead of every part of the codebase reaching for a provider SDK directly. That single integration point is what makes everything else possible.

Without a gateway, every call site that talks to an LLM has to separately handle its own retries, its own rate-limit backoff, and its own provider-specific SDK code. A gateway centralizes all of that: application code just makes one call and gets caching, rate limiting, provider fallback, and logging "for free," instead of that logic being copied into every place an LLM gets called.

💻 See the code ▾
Pseudocode 
# Without a gateway — every call site owns its own retry + provider logic
try:
    result = provider_a_sdk.chat(prompt)      # provider-specific client
except RateLimitError:
    result = provider_b_sdk.chat(prompt)      # ❌ hand-rolled here, and again everywhere else it's called

This retry/fallback logic has to be copied into every place in the codebase that calls an LLM.

Pseudocode 
# Behind a gateway — one call, same result, on every call site
result = gateway.chat(prompt)                 # ✅ caching, rate limiting, fallback already applied

The gateway holds the provider list, cache, and rate-limit rules once — every caller just makes this one call.

🌍 Real-world example ▾

An app calls an LLM provider directly from several different code paths, and one day that provider has an outage — every one of those code paths goes down with it. The production fix: put the LLM behind a gateway specifically for caching, rate limiting, provider fallback, and per-call cost and latency tracing, instead of calling a provider SDK directly from application code. A single provider having a bad day no longer takes the whole app down with it.
