[] == false is true — do you know why?

"What are JavaScript's data types, and why does [] == false evaluate to true?"

Why it matters ▾
🧮 Primitive
❗ ProblemIf a function "changed" a number or string you passed in and that change leaked back to your original variable, you could never trust a value stayed put after calling anything.
✅ SolutionPrimitives (string, number, bigint, boolean, undefined, null, symbol) are copied and compared by value — every assignment or call gets its own full copy, so === just compares the values themselves.
RecallPrimitive = copied by value, compared by value.
🔗 Reference (Object)
❗ ProblemTwo arrays or objects built with the exact same contents can still fail a === check, and mutating an object through one variable silently changes what every other variable pointing at it sees.
✅ SolutionObjects, arrays, functions, and dates are copied and compared by reference — assigning one hands over a pointer to the same underlying object, so === checks identity ({} === {} is false), not contents.
RecallReference (Object) = copied by reference, compared by identity.
🔥 Easy interview recall

Type Coercion = "JavaScript automatically converts a value's type so an operation can complete."

Think: typeof null lies — it says "object". == converts types first; === never does.

🧠 Visual Mental Model — watch both sides collapse to the same number
⚠️ Common Trap

An empty array is truthy — even though [] == false is true. if ([]) always runs, because truthiness checks the value directly (any object is truthy); == instead converts both sides to primitives first, which is a completely different rule.

🔄 Likely Follow-up

"So does [] === false avoid this?" Yes — [] === false is false, because === never converts types; an array and a boolean are different types, so strict equality stops right there.

🎯 Say this in the interview — the exact lines to land

"JavaScript has seven primitive types — string, number, bigint, boolean, undefined, null, and symbol — plus object for everything else. typeof null famously returns "object", a long-standing bug kept for compatibility. When == compares different types, it coerces both sides toward numbers before comparing, which is exactly why [] == false is true."

  • typeof null → "object" — a decades-old bug, not a design choice.
  • NaN → never equal to itself; check with Number.isNaN(), not ===.
  • Falsy values → only six exist: false, 0, "", null, undefined, NaN — everything else is truthy.
  • [] == false → both sides convert down to 0 before comparing.
  • Primitive vs. reference → primitives copy by value, objects and arrays copy by reference.
📖 Explanation ▾

JavaScript has eight data types in total: seven primitives — string, number, bigint, boolean, undefined, null, and symbol — plus one composite type, object, which covers plain objects, arrays, and dates too. Primitives are copied and compared by value; objects are copied and compared by reference. That value/reference split is exactly what typeof is trying to report — and exactly where it gets one case wrong: null is a primitive, but typeof null returns "object", a bug that shipped in JavaScript's very first version and can't be fixed now without breaking existing sites.

NaN is the oddest primitive value: it's the only value in JavaScript that isn't equal to itself, so x === NaN never works — use Number.isNaN(x) instead. Truthy/falsy decides what counts as true inside an if, and only six values are falsy: false, 0, "", null, undefined, NaN. Everything else — including [] and {} — is truthy, no matter how "empty" it looks.

Coercion is JavaScript changing a value's type automatically so an operation can go ahead. Explicit conversion is you asking for it — Number("5"), String(5), Boolean(0). Implicit conversion is JavaScript doing it without being asked, usually through ==, +, or an if check. == is exactly this: keep converting both sides until they're the same type, then compare.

💻 See the code ▾
JavaScript 
typeof "hi";        // "string"
typeof 42;           // "number"
typeof 10n;          // "bigint"
typeof true;         // "boolean"
typeof undefined;    // "undefined"
typeof Symbol();     // "symbol"
typeof {};            // "object"
typeof null;          // "object" ❌ — null is NOT an object

null is a primitive — typeof just gets it wrong, and always will.

JavaScript 
[] == false;
// Step 1: [] is an object → ToPrimitive([]) → "" (array's default toString())
// Step 2: "" == false → still different types (string vs boolean)
// Step 3: ToNumber("")    → 0
// Step 4: ToNumber(false) → 0
// Step 5: 0 == 0 → true

Every step pushes toward a number — that's what "loose" equality actually means: keep converting until both sides are comparable.

JavaScript 
NaN === NaN;              // ❌ false — NaN is never equal to itself
Number.isNaN(NaN);       // ✅ true  — the correct check
isNaN("abc");            // ❌ true  — isNaN() coerces its argument first
Number.isNaN("abc");   // ✅ false — no coercion, the safer check

Prefer Number.isNaN() — the global isNaN() coerces its argument first, which causes its own false positives.

🧭 Use Cases — recognize these when they happen to you ▾
1 You use == and get a match you didn't expect, like [] == false

This is the #1 scenario you'll actually run into: == sees two different types, so it keeps converting both sides — toward a number, in this case — until they're the same type, then compares. Every step pushes toward a number; that's what "loose" equality actually means.

Remember== converts types first; === never does.
2 An if (someArray) or if (someObject) check always runs, even when it "looks empty"

Only six values are falsy (false, 0, "", null, undefined, NaN) — everything else is truthy, no matter how "empty" it looks. [] and {} are objects, so they're truthy every time; the check tests whether the value exists at all, not whether it's empty.

RememberAny object is truthy — emptiness isn't falsiness.
3 You compare two object or array literals and expect === to say they're equal because they "look the same"

Objects and arrays are compared by reference, not by their contents — two separately created objects with identical properties are still {} === {} → false, unless they're literally the same object in memory. A common trap — candidates often assume "equal-looking" means equal.

Remember{} === {} → false. Reference types compare identity, not content.
🌍 Real-world example ▾

Comparing [] == false is like a bouncer accepting two totally different IDs — a laminated card and a verbal claim — because both get converted to the same format (a number) before he compares them. === is a stricter bouncer who refuses to compare an ID card to a spoken claim at all, no conversion allowed.
