Every tier that must survive a failure has to be stateless

How would you design a highly available web application, and what happens if one AZ disappears entirely?

Why it matters ▾
🧩 Statelessness across every tier
❗ ProblemA candidate makes the web servers stateless and stops there — but a background worker or the app tier holding a job's progress in local memory loses that work the instant its AZ disappears, even though the ALB and ASG are still happily routing traffic to the AZs that survived.
✅ SolutionSessions and job state live in a shared external store like ElastiCache or DynamoDB instead of any one instance's memory, so any instance in any AZ can pick up the exact same request or job after a failure — and the data tier gets its own separate plan (RDS Multi-AZ failover, graceful degradation) since it can't be made stateless the same way.
RecallEvery tier that must survive a failure has to be stateless — not just the web tier.
🔥 Easy interview recall

Web tier → stateless, spread across AZs

App tier → stateless too — no local job/session state

Data tier → Multi-AZ failover + a plan for graceful degradation

Think: if any instance can die and a stranger instance in another AZ can pick up the exact same request, that tier survives an AZ failure.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Statelessness applies to the web tier only. A candidate makes the web servers stateless and stops there — but a background worker or the app tier holding a job's progress in local memory fails an AZ outage just as badly; every tier that needs to survive a failure has to be stateless, not just the front door.

🔄 Likely Follow-up

"Where would sessions actually live?" A shared, external store like ElastiCache or DynamoDB — never local instance memory — so any instance in any AZ can serve any user's next request without needing "their" specific instance.

🎯 Say this in the interview — the exact lines to land

"Every tier that needs to survive a failure must be stateless — sessions live in a shared store, not local memory. Spread the web, app, and data tiers across multiple AZs so the ALB and Auto Scaling Group can keep serving traffic if one AZ disappears."

  • Web and app tier → stateless, so any instance in any AZ can handle any request.
  • Sessions → live in a shared external store like ElastiCache or DynamoDB, never local instance memory.
  • Database failure → the plan is RDS Multi-AZ failover, not a hope it never happens.
  • Cache or DB trouble → answer with graceful degradation — serve stale/cached data or a reduced feature set instead of a hard failure.
  • Losing an AZ → the ALB and ASG only keep serving if capacity was actually provisioned across every AZ to begin with.
📖 Explanation ▾

A highly available design spreads every tier's instances across at least two, ideally three, AZs behind an Application Load Balancer and an Auto Scaling Group. Because the web and app tiers hold no local state, the ALB's health checks can pull a failed instance out of rotation and the ASG can launch a replacement in a healthy AZ, all without any user noticing — traffic simply keeps flowing to whichever AZs are still up.

The data tier can't be made stateless the same way, so it needs its own failure plan instead: RDS Multi-AZ keeps a synchronously replicated standby in a different AZ and fails over to it automatically if the primary is lost. A cache (like ElastiCache) or the database itself can still go down for a stretch — the answer there is graceful degradation: serve slightly stale or cached data, or temporarily disable a non-essential feature, rather than returning a hard error to every user.

🧭 Use Cases — recognize these when they happen to you ▾
1 An entire AZ goes dark while your web and app tiers are properly stateless

Because nothing in the web or app tier holds local state, the ALB's health checks pull the failed instances out of rotation and the ASG replaces them in a healthy AZ — requests just keep landing on us-east-1a and us-east-1c. This is the #1 scenario you'll actually be asked to walk through.

RememberProperly stateless tiers survive an AZ loss with zero user impact.
2 A background worker (or the app tier) kept a job's progress in local instance memory

That instance's AZ failure destroys the job progress that lived only on the vanished instance, even though the ALB is still happily routing new requests elsewhere — the exact trap this page's Common Trap box calls out: statelessness has to cover every tier, not just the front door.

RememberLocal memory anywhere → that state dies the moment its AZ does.
3 The primary RDS instance itself is what fails, not just a web/app AZ

The data tier can't be made stateless the way the web/app tiers can, so it needs its own separate plan: RDS Multi-AZ keeps a synchronously replicated standby in a different AZ and fails over to it automatically when the primary is lost.

RememberData tier failure → RDS Multi-AZ failover, not "add more stateless instances."
🌍 Real-world example ▾

A web app keeps every user's session in ElastiCache instead of the instance's own memory. When the ALB sends that user's next click to a completely different instance — maybe even one in a different AZ, because their original instance's AZ just went down — that new instance reads the same session from the shared cache and picks up right where the last one left off. The user never notices anything happened.
