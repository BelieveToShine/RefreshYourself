.AsParallel() — real in-memory parallelism, never database parallelism

"What does .AsParallel() actually change about how a LINQ-to-Objects query runs?"

Why it matters ▾
⚡ PLINQ
❗ ProblemA CPU-heavy LINQ-to-Objects query over a large in-memory collection runs on a single thread by default, leaving every other core idle while one thread grinds through genuinely expensive per-item work.
✅ Solution.AsParallel() partitions the source across multiple threads and merges the results back — real speedup for genuinely expensive, parallelizable per-item work, at the cost of losing default ordering and paying a real partition/merge overhead that can backfire on cheap work.
RecallAsParallel() = split the work across threads, merge it back — a real trade, not a free speedup.
🔥 Easy interview recall

AsParallel() → partitions across threads, merges back

AsOrdered() → restores order, at a real cost

cheap per-item work → can get slower, not faster

Think: AsParallel() only ever touches in-memory LINQ-to-Objects — it has nothing to say about an IQueryable database query.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

.AsParallel() does not speed up a database query. It only exists for IEnumerable<T> LINQ-to-Objects — it has no meaning at all over an IQueryable, and the database is already doing its own query-level parallelism, if any, completely independently of PLINQ.

🔄 Likely Follow-up

"Would you reach for PLINQ in a typical ASP.NET Core request handler?" Rarely — most request-handling work is I/O-bound (waiting on a database or network call), which async/await already handles without burning extra threads. PLINQ earns its keep for genuinely CPU-bound batch work over an in-memory collection, not for everyday request processing.

🎯 Say this in the interview — the exact lines to land

".AsParallel() partitions an in-memory sequence across multiple threads and merges the results back — real speedup for genuinely CPU-heavy per-item work, but ordering isn't preserved by default, and AsOrdered() to get it back has a real cost. It only applies to LINQ-to-Objects; it has no meaning over an IQueryable database query."

  • Genuinely CPU-heavy work, large collection → real speedup is possible.
  • Small or cheap-per-item work → partition/merge overhead can make it slower.
  • Order matters → AsOrdered() restores it, at a real cost.
  • IQueryable database query → .AsParallel() has no meaning there at all.
📖 Explanation ▾

PLINQ (Parallel LINQ) works by splitting the source sequence into partitions and running the rest of the query's operators on each partition on a separate thread, drawn from the thread pool. Once every partition finishes, the results are merged back into a single sequence — that partition-then-merge step is real coordination work, not free, which is exactly why it only pays off when the per-item work inside the query is expensive enough to outweigh it.

Ordering is the first casualty. Because partitions finish in whatever order their threads happen to complete, the default merge doesn't preserve the source sequence's original order at all. AsOrdered() tells PLINQ to track and restore that original order — which is a real, meaningful cost, since now output can't be yielded until its correct position is known, giving back some of the parallelism's benefit.

The trade only works out for work that's actually expensive per item — a non-trivial CPU computation, not a cheap comparison or arithmetic op. On small collections or cheap per-item work, the fixed cost of partitioning the source and merging the results can be larger than the work being parallelized, making the parallel version measurably slower than the plain sequential query it replaced.

💻 See the code ▾
C# 
// Genuinely CPU-heavy per-item work — a real PLINQ win
var hashes = largeImageBatch
    .AsParallel()                       // ✅ partitions across threads
    .Select(img => ComputePerceptualHash(img))
    .ToList();

ComputePerceptualHash is expensive enough per item that spreading it across cores outweighs the partition/merge overhead.

C# 
// Order matters — pay for it explicitly
var ranked = scores
    .AsParallel()
    .AsOrdered()                        // ✅ restores the original sequence order
    .Select(s => Normalize(s))
    .ToList();

Without AsOrdered(), ranked could come back in any order the partitions happened to finish in.

C# 
// No meaning over a database query — doesn't parallelize the SQL
var active = db.Users
    .Where(u => u.IsActive)
    .AsParallel()                       // ❌ IQueryable has no PLINQ behavior to opt into
    .ToList();

db.Users.Where(...) is an IQueryable<T> — .AsParallel() here is meaningless; the database, not PLINQ, controls any parallelism in running the SQL.

🧭 Use Cases — recognize these when they happen to you ▾
1 A batch job hashes or resizes thousands of images already loaded into memory

This is PLINQ's home turf: real, expensive CPU work per item, over a large in-memory collection, where order genuinely doesn't matter. Spreading it across cores is a straightforward win here.

RememberExpensive per-item work + large collection → AsParallel() is a real win.
2 The output has to stay in the same order it was read in

A ranked report or a sequence that feeds into something position-sensitive still needs the original order back. AsOrdered() gets it, but accept the trade — some of the parallel speedup is spent restoring it.

RememberOrder matters → AsOrdered(), and accept the real cost.
3 A small list with cheap, simple per-item logic gets .AsParallel() added "for speed"

Simple arithmetic over a short list finishes so fast sequentially that partitioning it across threads and merging the pieces back costs more than the work itself ever did. A common interview trap: assuming .AsParallel() is a free speedup you can sprinkle anywhere.

RememberCheap work, small collection → the overhead can make it slower, not faster.
🌍 Real-world example ▾

A nightly job recomputes a derived score for every product already loaded into memory, and the calculation itself is genuinely expensive per product. Adding .AsParallel() cuts the job's wall-clock time roughly in proportion to available cores — a legitimate win, because the per-item work is heavy enough to justify the partition/merge overhead, and the job doesn't care what order the scores come back in.
