Monorepo vs. Multi-Zone — one repo is not one app

"What's the difference between a monorepo and a multi-zone architecture in Next.js?"

Why it matters ▾
📁 Monorepo
❗ ProblemSeveral related apps and shared packages scattered across separate repos make shared tooling, dependency versions, and cross-package changes painful to coordinate.
✅ SolutionA monorepo (Turborepo, Nx, etc.) is a code-organization/tooling choice — multiple apps and shared packages live in one repository with shared build tooling and dependency management.
RecallMonorepo = where the code lives and how it's built.
🌐 Multi-Zone
❗ ProblemDifferent teams want to independently ship and deploy different sections of one site (a blog, a shop) without being blocked on each other's release schedule, but users still expect one seamless domain.
✅ SolutionMulti-Zone composes several independently deployed Next.js apps under one domain via rewrites that route different path prefixes to different deployments.
RecallMulti-Zone = how several separately-deployed apps appear as one site.
🔥 Easy interview recall

Monorepo → code organization, one repo

Multi-Zone → runtime composition, one domain

Think: monorepo is about where the source lives. Multi-Zone is about what the deployed site actually serves.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A monorepo and a multi-zone setup are not the same decision. Monorepo is a code-organization/tooling choice; Multi-Zone is a runtime-composition/deployment architecture — a project can use either without the other.

🔄 Likely Follow-up

"What's the main cost of a multi-zone architecture?" Each zone ships its own separate Next.js runtime/framework overhead with no shared client-side bundle across zones, and cross-zone navigation between different apps is a full page load, not a client-side transition — a real trade-off against true independence.

🎯 Say this in the interview — the exact lines to land

"A monorepo is about where the code lives — several apps and shared packages in one repository with shared tooling. Multi-Zone is a specific Next.js technique that composes several independently deployed Next.js apps under one domain via rewrites, so they appear as one site while teams ship them separately."

  • Monorepo → code organization and shared tooling, one repository.
  • Multi-Zone → runtime composition of independently deployed apps under one domain.
  • Main multi-zone cost → no shared client bundle, full page load across zones.
  • They're independent choices → use either, both, or neither.
📖 Explanation ▾

A monorepo (Turborepo, Nx, and similar tools) puts multiple apps and shared packages in one repository, with shared dependency management and build tooling across them. It solves a code-organization problem — how teams share code and coordinate changes, not how anything gets served to a browser.

Multi-Zone is a specific Next.js technique for composing several independently deployed Next.js applications under one domain. Rewrites route different path prefixes (/blog, /shop) to different deployments, so a visitor experiences one seamless site even though each zone is its own separate application, built and shipped on its own schedule.

Nothing stops a team from doing both at once (zones whose source happens to live in a shared monorepo) or either alone (a monorepo with one deployed app; multi-zone apps each in their own separate repo) — they answer different questions.

💻 See the code ▾
JS 
// next.config.js — the "main" zone app routes /blog to a separately deployed app
module.exports = {
  async rewrites() {
    return [
      { source: "/blog", destination: "https://blog-zone.example.com/blog" },
      { source: "/blog/:path*", destination: "https://blog-zone.example.com/blog/:path*" },
    ];
  },
};

blog-zone.example.com is a completely separate Next.js deployment — the rewrite is what makes it look like part of the same domain.

🌍 Real-world example ▾

Marketing wants the blog to ship weekly while the core product app ships on a much slower, carefully-tested cadence. Multi-Zone lets the blog be its own deployment, released on its own schedule, while still living at example.com/blog — without either team's releases blocking the other's.
