Every structure is fast at something — never everything

"Why would you choose a HashMap over a TreeMap? Why use a heap instead of sorting everything? Array or linked list — when does each make sense?"

Why it matters ▾
  • Interviewers ask this specifically to check judgment, not memorization — anyone can recite "HashMap is O(1)"; naming why you'd give that up for a TreeMap is the real signal.
  • It's the natural follow-up after almost any single-structure question — expect it right after "what is a HashMap" or "what is a heap."
  • A classic senior/architect opener: "you need X across 10 million records — what would you use, and why?"
🔥 Easy interview recall

Array → O(1) index, O(n) middle insert

Linked List → O(1) insert at a node, O(n) to find it

HashMap → O(1) lookup, no order

TreeMap → sorted + range, pays O(log n)

Heap → fast min/max, not fully sorted

Think: name the one operation that happens most in the scenario, then pick whichever structure wins at exactly that one — accept the cost everywhere else.

⚠️ Common Trap

"Simple" doesn't mean "fast enough." Defaulting to an array (or a plain list) because it feels obvious, without checking whether the workload does frequent middle inserts, silently turns every one of those inserts into an O(n) shift instead of the O(1) a linked list — or a better-suited structure — would give.

🔄 Likely Follow-up

"You need to repeatedly check whether an ID has already been seen, across 10 million records — what would you use, and why?" A HashSet/ HashMap — O(1) average per check. Scanning an array is O(n) per check (O(n²) total across all 10 million), and a TreeMap's O(log n) pays for sorted order you don't actually need for a pure existence check.

🎯 Say this in the interview — the exact lines to land

"Every data structure trades one operation's speed for another's — there's no single structure that's fastest at everything, so I'd name the operation that happens most in this scenario and pick whichever structure wins at exactly that one, accepting the cost on the others."

  • Array → use for fast indexed access; inserts/deletes should mostly happen at the end.
  • Linked List → use when you insert/delete from the middle or front often and don't need random access.
  • HashMap → use for fast exact-key lookup when you don't care about order.
  • TreeMap → use when you need sorted iteration or range queries, and can pay O(log n) for it.
  • Heap → use for repeated min/max access as the collection changes; sort once only if you truly need every element ordered.
  • Stack/Queue → use the dedicated structure (or a deque) so both ends stay O(1) — a plain array simulating FIFO by shifting from the front quietly becomes O(n) per operation.
📖 Explanation ▾

Comparing structures isn't about which one is "better" — every structure is optimized for some operations at the cost of others, so the real question is which operation actually happens most in the workload. Array vs. Linked List is the clearest version of this: an array gives O(1) access by index, but inserting or deleting in the middle means shifting every element after it — O(n). A linked list flips that trade: insert/delete at a node you already hold is O(1), but reaching that node in the first place means walking from the head — O(n).

HashMap vs. TreeMap is the same trade one layer up: a HashMap's O(1) average get/put/delete comes with no ordering guarantee at all — iteration order is effectively arbitrary. A TreeMap (typically backed by a self-balancing tree — see Balanced Trees) pays O(log n) for every operation, but keeps keys sorted and supports range queries — "everything between X and Y" — that a HashMap simply can't answer.

A heap vs. sorting everything makes the same point from the other direction: fully sorting is O(n log n) up front and solves a more general problem — the full order of every element — than most workloads actually need. If the only thing that's ever needed is the current min or max as the collection changes, a heap's O(log n) insert and extract stays cheaper than re-sorting, because it never pays for ordering the n-1 elements nobody looks at.

💻 See the code ▾
Pseudocode 
function insertMiddle(array, index, value):
    array.length += 1                          // grow by one slot
    for i from array.length-1 down to index+1:
        array[i] = array[i-1]            // ❌ O(n) — every element after index moves
    array[index] = value

The cost scales with how many elements sit after index — not with the array's total size alone, but it's still O(n) in the worst case.

Pseudocode 
function insertAfter(node, value):
    newNode = Node(value)
    newNode.next = node.next        // ✅ O(1) — no other node moves
    node.next = newNode

Only two pointers change, no matter how long the list is — the trade for that O(1) is that node had to already be in hand.

Pseudocode 
function hasDuplicate(records):          // 10,000,000 ids
    seen = new HashSet()
    for id in records:
        if seen.contains(id): return true   // ✅ O(1) average per check
        seen.add(id)
    return false

function hasDuplicateSlow(records):      // same logic, array instead
    seen = []
    for id in records:
        if id in seen: return true       // ❌ O(n) — scans everything seen so far
        seen.append(id)
    return false

Same logic, one swapped structure: the HashSet version stays fast at 10 million records; the array version's id in seen check gets slower every time seen grows — close to O(n²) total.

🌍 Real-world example ▾

Your service ingests 10 million transaction IDs a day and has to reject duplicates before they hit the database. Scanning a list of previously-seen IDs for every new one feels fine at small volume and becomes the actual bottleneck as it grows — O(n) per check, O(n²) across the whole day's batch. Swapping that list for a HashSet keeps every check O(1) average no matter how large the batch gets — the fix isn't a smarter loop, it's the right structure for the one operation (existence check) that actually matters here.
