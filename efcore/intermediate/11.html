HasQueryFilter — write the WHERE once, apply it everywhere

How would you implement soft delete or multi-tenancy once, for every query?

Why it matters ▾
🔍 Global query filter
❗ ProblemSoft delete or tenant scoping means a WHERE on every single query — and one forgotten condition shows deleted rows or another tenant's data.
✅ SolutionA global query filter, set once with HasQueryFilter, makes EF Core add that condition to every query on the entity automatically.
RecallHasQueryFilter = a WHERE EF Core adds for you, on every query.
🔥 Easy interview recall

HasQueryFilter → automatic WHERE on every query

Soft delete → filter !IsDeleted + flip the flag in SaveChanges

IgnoreQueryFilters() → opt out for one query

Think: Filter hides. SaveChanges flags. IgnoreQueryFilters() shows it all again.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A query filter does not make Remove() a soft delete. It only hides rows that are already flagged — without a SaveChanges override or interceptor, Remove() still issues a real DELETE.

🔄 Likely Follow-up

"How can an admin still see the deleted rows?" Call IgnoreQueryFilters() on that query — it turns the global filter off for that one query only.

🎯 Say this in the interview — the exact lines to land

"A global query filter, set once with HasQueryFilter, is added to every query on that entity — I use it for soft delete and multi-tenancy. It doesn't turn Remove() into a soft delete; I do that in SaveChanges or an interceptor. And IgnoreQueryFilters() bypasses it when I need the hidden rows."

  • HasQueryFilter → a WHERE on every query, automatically.
  • Soft delete → flip Deleted to Modified and set IsDeleted in SaveChanges or an interceptor.
  • Multi-tenancy → filter on TenantId read from the context.
  • IgnoreQueryFilters() → admin, audit, restore screens.
  • Gotcha → a filtered parent hides children that reach it through a required navigation.
📖 Explanation ▾

A global query filter is a WHERE that EF Core adds to every query for an entity — written once in OnModelCreating with HasQueryFilter. It is the clean way to do soft delete (hide rows flagged IsDeleted) and multi-tenancy (only this tenant's rows).

The filter hides rows; it doesn't delete them. A normal Remove() still becomes a real DELETE. For soft delete, override SaveChanges (or use a SaveChangesInterceptor) and turn Deleted entries into Modified with IsDeleted = true. For tenants, the filter can read a field on the DbContext, such as the current tenant id. Before EF Core 10 an entity type has one filter (a second HasQueryFilter overwrites the first), so combine conditions with &&; EF Core 10 adds named filters that IgnoreQueryFilters(["name"]) can switch off one at a time.

IgnoreQueryFilters() switches the filter off for one query. One catch: if a parent is filtered out, children that reach it through a required navigation are hidden too — give the child a matching filter or make the navigation optional. See LINQ → SQL Translation; interceptors come in Interceptors & Audit Trails.

💻 See the code ▾
C# 
modelBuilder.Entity<Post>().HasQueryFilter(p => !p.IsDeleted);
// ✅ every query on Post now has WHERE IsDeleted = 0

modelBuilder.Entity<Order>().HasQueryFilter(o => o.TenantId == _tenantId);
// _tenantId is a field on this DbContext — set per request

One line per rule — queries written later get the filter without anyone remembering it.

C# 
public override Task<int> SaveChangesAsync(CancellationToken ct = default)
{
    foreach (var e in ChangeTracker.Entries<ISoftDelete>()
                 .Where(e => e.State == EntityState.Deleted))
    {
        e.State = EntityState.Modified;   // DELETE becomes UPDATE
        e.Entity.IsDeleted = true;        // ✅ the flag the filter hides
    }
    return base.SaveChangesAsync(ct);
}

The filter only hides — this is what makes a delete soft. (Override SaveChanges the same way if you call it synchronously.)

C# 
var all = await db.Posts.IgnoreQueryFilters().ToListAsync();   // ✅ includes IsDeleted rows

IgnoreQueryFilters() — an explicit, visible opt-out for one query.

🌍 Real-world example ▾

A multi-tenant SaaS app used to rely on every developer adding Where(x => x.TenantId == …); one forgotten condition leaked another customer's rows. One HasQueryFilter on TenantId scoped every query by default.
