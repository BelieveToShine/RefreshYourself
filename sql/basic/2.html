WHERE vs. HAVING — know which one runs before grouping

"What's the difference between WHERE and HAVING, and why can't you filter on an aggregate in WHERE?"

Why it matters ▾
🚪 WHERE
❗ ProblemA query needs to drop rows before grouping even starts — but a value like COUNT(*) doesn't exist yet at that point in the query.
✅ SolutionWHERE filters individual rows on their real columns, before any grouping or aggregation happens — filtering early means less data to group.
RecallWHERE = filters rows, before grouping.
🚪 HAVING
❗ ProblemOnce rows are collapsed into groups, a query often needs to keep only the groups whose aggregate result — like COUNT(*) — meets some condition.
✅ SolutionHAVING filters groups after GROUP BY has run, which is the only place a condition on an aggregate is legal.
RecallHAVING = filters groups, after aggregation.
🔥 Easy interview recall

WHERE → filters rows, before grouping

HAVING → filters groups, after aggregation

Think: WHERE runs first. HAVING only sees what's left after GROUP BY.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"HAVING is just a slower WHERE." They're not swappable — WHERE can't reference an aggregate result because aggregates don't exist yet at that point in the query; using HAVING for a plain, non-aggregate row filter technically runs, but it wastes effort grouping data that should have already been filtered out by WHERE first.

🔄 Likely Follow-up

"Can you use HAVING without GROUP BY?" Yes — HAVING can filter on an aggregate over the whole table treated as one implicit group, e.g. SELECT COUNT(*) FROM Orders HAVING COUNT(*) > 100.

🎯 Say this in the interview — the exact lines to land

"WHERE filters individual rows before any grouping or aggregation happens. HAVING filters the groups after GROUP BY has run, which is why it's the only place you can put a condition on an aggregate like COUNT(*) — that value doesn't exist yet when WHERE runs."

  • WHERE → use it for row-level conditions on real columns, and use it first — filtering early means less data to group.
  • HAVING → use it only when the condition is on an aggregate result, like COUNT(*) or SUM(...).
  • Can't swap them → WHERE COUNT(*) > 5 fails because the count isn't computed yet at that stage.
  • Works without GROUP BY too → HAVING can filter an aggregate over the whole table as one implicit group.
📖 Explanation ▾

WHERE filters individual rows before any grouping or aggregation happens — it only ever sees the raw columns of a single row at a time. By the time HAVING runs, GROUP BY has already collapsed the matching rows into groups and computed any aggregate functions, so HAVING is filtering on groups and their aggregate results, not individual rows.

This ordering is exactly why an aggregate can't appear in WHERE: a value like COUNT(*) doesn't exist until grouping has actually happened, and WHERE runs before that point in the query. HAVING exists specifically to give aggregate results somewhere to be filtered.

💻 See the code ▾
SQL 
SELECT CustomerId, COUNT(*) AS OrderCount
FROM Orders
WHERE Status = 'Completed'          -- row filter: only completed orders count at all
GROUP BY CustomerId                -- collapse the remaining rows into one group per customer
HAVING COUNT(*) > 5              -- group filter: only customers with more than 5 orders

WHERE narrows the rows first, GROUP BY collapses what's left, then HAVING narrows the resulting groups.

SQL 
SELECT CustomerId, COUNT(*)
FROM Orders
WHERE COUNT(*) > 5                -- ❌ error: COUNT(*) doesn't exist yet, WHERE runs before grouping
GROUP BY CustomerId

-- fixed: move the aggregate condition into HAVING, after GROUP BY
SELECT CustomerId, COUNT(*)
FROM Orders
GROUP BY CustomerId
HAVING COUNT(*) > 5               -- ✅ works: COUNT(*) is computed by the time HAVING runs

Same intent, different clause — the aggregate condition only becomes legal once it moves to HAVING.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to drop rows before any grouping happens

Status is a real column on every row, so it's checkable immediately — WHERE drops the non-matching rows before GROUP BY even runs, which also means less data left to group. This is the #1 scenario you'll actually run into.

RememberReal column, no aggregate → WHERE.
2 You need to keep only the groups whose aggregate meets a condition

COUNT(*) only exists once GROUP BY has collapsed the rows into groups, so the condition has to live in HAVING — the only clause that runs after aggregation.

RememberCondition on an aggregate → HAVING.
3 You put the aggregate condition in WHERE instead

WHERE runs before grouping, so COUNT(*) hasn't been computed yet at that point in the query — the database rejects the condition instead of silently doing something else. A common interview trap — candidates often assume HAVING is just a slower, swappable WHERE.

RememberAggregate in WHERE → error, not just slower.
🌍 Real-world example ▾

Sorting mail before delivery. WHERE is tossing out mail with the wrong zip code before you even start sorting anything into bins. HAVING is what happens after — once the remaining mail is grouped into bins by street, you throw out any bin that ended up with fewer than 3 letters in it. You can't check "fewer than 3 letters" before the bins exist.
