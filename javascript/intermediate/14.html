Cookies vs. localStorage vs. sessionStorage vs. IndexedDB — where should that token actually live?

"What's the difference between cookies, localStorage, sessionStorage, and IndexedDB — and where would you store an authentication token?"

Why it matters ▾
  • Almost everyone can name all four storage options, but far fewer can say which one an XSS bug can actually read — that gap is exactly what this question is testing.
  • Comes up any time the discussion turns to "how do we keep a user logged in" or "how do we cache data for offline use."
  • A common interview opener that's really a security question wearing a storage-APIs costume.
🔥 Easy interview recall

Cookies → small, auto-sent with every matching request

localStorage → sticks around, but any JS can read it

sessionStorage → same as localStorage, gone when the tab closes

IndexedDB → a real database in the browser, for bigger data

Think: the easier a storage is for your own JS to read, the easier it is for an attacker's injected JS to read too — except one option can opt out of that entirely.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An auth token in localStorage isn't automatically safe just because cookies feel old-fashioned. Any JavaScript running on the page — including a script an XSS bug injected — can read localStorage in full; an httpOnly cookie can't be read by JavaScript at all, which is exactly why sensitive tokens are still often kept there instead.

🔄 Likely Follow-up

"So why doesn't everyone just use an httpOnly cookie for tokens?" Cookies are attached automatically to every matching request, so they need their own protection against forged requests (like a SameSite attribute or an anti-CSRF token) — the trade-off shifts from "can JavaScript read it" to "does it get sent somewhere I didn't intend."

🎯 Say this in the interview — the exact lines to land

"Cookies are sent automatically with every matching HTTP request and can be marked httpOnly so JavaScript can't read them at all. localStorage and sessionStorage are plain JavaScript-readable key-value storage — localStorage persists until it's cleared, sessionStorage disappears when the tab closes — and IndexedDB is a real, structured database in the browser for larger data. That's exactly why a sensitive auth token is often kept in an httpOnly cookie instead of localStorage: it's the one option JavaScript, including injected XSS, can't touch."

  • Cookies → auto-sent with every request, can be httpOnly.
  • localStorage → persists across tabs and reloads, but any JS can read it.
  • sessionStorage → same API, gone when the tab closes.
  • IndexedDB → the real database — for larger or structured data the others aren't built for.
  • Storing a sensitive token? → httpOnly cookie beats localStorage against XSS.
📖 Explanation ▾

Cookies were built for the server, not for JavaScript: the browser attaches any cookie that matches the current domain/path to every request it sends there, automatically. That's what makes them small by necessity — a few KB is plenty when the content rides along on every single request — and it's what makes an httpOnly cookie special: the browser still sends it to the server, but no JavaScript on the page can read or write it at all, not even a script an attacker managed to inject.

localStorage and sessionStorage are the opposite trade-off: plain key-value storage that only JavaScript touches — nothing is ever sent to the server on its own. localStorage survives closing the tab, closing the browser, even restarting the machine, until something explicitly clears it. sessionStorage uses the exact same API but is scoped to one tab — close that tab and it's gone. Both share the same weakness: because reading them is just a normal JavaScript call, any script running on the page can read them, which includes a script an XSS vulnerability injected.

IndexedDB exists for the case where localStorage genuinely isn't enough — a real, structured database running inside the browser, built for larger amounts of data (or data that needs indexes and queries, not just flat string values) rather than a handful of settings. Reach for it for things like offline caches, large local datasets, or structured records — not as a place to memorize an API in depth for an interview, just as the answer to "what do I use when localStorage's simple string storage isn't shaped right for the data."

💻 See the code ▾
JS 
// document.cookie can only see a cookie WITHOUT the httpOnly flag
document.cookie = "theme=dark; path=/; max-age=3600";
console.log(document.cookie);              // ✅ "theme=dark" — this one is readable

// a Set-Cookie response header with HttpOnly is set by the SERVER, not JS —
// and document.cookie will never show it, on purpose
// Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict

Only the server can set an httpOnly cookie — once it's set that way, no client-side JavaScript can ever read it back, injected or not.

JS 
localStorage.setItem("draft", "hello");     // survives closing the tab
sessionStorage.setItem("draft", "hello");   // gone once THIS tab closes

// both are string-only, and both are readable by ANY script on the page:
console.log(localStorage.getItem("draft"));  // ✅ "hello" — no permission check

Same read/write API for both — the only real difference is how long the value survives, not who's allowed to read it.

🌍 Real-world example ▾

A single-page app needs to keep the user logged in after a refresh, and also remember an in-progress form draft. The session token goes in an httpOnly cookie the server sets and reads — JavaScript never touches it, so an XSS bug can't steal it. The form draft, which isn't sensitive, is a fine fit for localStorage — quick to read and write, and there's nothing valuable for an attacker to gain even if a script could see it.
