Hydration — the server already drew it, the client just wires it up

"What does 'hydration' actually mean, and where does Nuxt fit in?"

Why it matters ▾
🖥️ Server-side rendering & hydration
❗ ProblemA client-only Vue app sends the browser a nearly-empty HTML shell — the user (and any crawler) sees a blank page until JavaScript downloads, parses, and builds the whole UI from scratch.
✅ SolutionSSR renders the app to real HTML on the server first, so content is visible immediately; the client then "hydrates" that same markup — attaching reactivity and listeners to the existing DOM instead of rebuilding it.
RecallSSR = content first, JS second. Hydration = reuse, never rebuild.
🔥 Easy interview recall

Hydration = "the client reuses the server's HTML and just wires up the reactivity."

Think: the house is already built (server HTML) — hydration just turns on the electricity (listeners), it doesn't rebuild the walls.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Hydration is not the client re-rendering everything. It specifically reuses the existing server-rendered DOM and wires up reactivity/listeners onto it — a mismatch between server and client output, not a full re-render, is what triggers a hydration error.

🔄 Likely Follow-up

"What causes a hydration mismatch in practice?" Server and client producing different output for the same initial render — e.g. code that reads window/localStorage (unavailable on the server) or renders a date/random value differently on each side.

🎯 Say this in the interview — the exact lines to land

"SSR renders the Vue app to an HTML string on the server so the user gets real content immediately. The client then hydrates that same markup — it attaches Vue's reactivity and event listeners to the existing DOM instead of re-creating it. Nuxt is a separate framework layered on top of Vue that provides SSR, file-based routing, and data fetching out of the box."

  • SSR → real HTML on arrival, before any JS runs.
  • Hydration → reuses the existing DOM, attaches listeners — never rebuilds nodes.
  • Hydration mismatch → server/client output differed, not "it re-rendered."
  • Nuxt → a separate layer on Vue, the way Next.js sits on React — not built into Vue core.
📖 Explanation ▾

Server-side rendering runs the same Vue app on the server to produce a plain HTML string, sent to the browser as the initial response. The browser can paint that HTML right away — a user sees real content before a single line of the app's JavaScript has even downloaded.

Hydration is the step after the client's JavaScript does load: Vue walks the already-rendered DOM and attaches its reactive instance and event listeners directly to those existing nodes, rather than throwing them away and rendering a fresh tree. That's the entire idea behind the word — the markup was "dry" (static HTML), now it becomes "wet" (interactive) without being rebuilt.

Nuxt.js is Vue's separate framework layer — the same relationship Next.js has to React. It provides SSR, file-based routing, and data-fetching conventions as a built-in setup, where wiring up raw SSR by hand with Vue alone would otherwise take significant configuration. Nuxt's own API is outside this track's scope — the interview-relevant fact is that it sits on top of Vue, not inside it.

💻 See the code ▾
Vue 
// server.js — conceptually what Vue's own SSR package does
import { renderToString } from 'vue/server-renderer'

const html = await renderToString(app)  // real HTML string, server-side
// ✅ sent to the browser — visible before any client JS runs

The browser paints this string immediately — no JavaScript execution required to see real content.

Vue 
// client.js — the exact same app, now hydrating
import { createSSRApp } from 'vue'

const app = createSSRApp(App)
app.mount('#app')  // ✅ attaches to the EXISTING server-rendered #app
// ❌ does not delete and re-create the DOM under #app

createSSRApp (not plain createApp) is what tells Vue to hydrate the existing markup instead of mounting onto an empty element.

🧭 Use Cases — recognize these when they happen to you ▾
1 SEO matters and the page must show real content to crawlers

A crawler that never executes JavaScript still sees the fully-rendered content, because the server already produced real HTML — a client-only SPA would show it an empty shell instead.

RememberSEO-critical page → SSR means crawlers see content either way.
2 Code reads window during the initial render

The server has no window/localStorage — code that branches on them renders differently server-side than it does client-side, and that difference is exactly what a hydration mismatch warning is reporting. A common interview trap: assuming the warning means the client "failed to re-render," when it actually means the two passes disagreed.

RememberBrowser-only API during render → guaranteed mismatch risk.
3 Choosing SSR tooling for a new Vue project

Nuxt sits on top of Vue, providing SSR/routing/data-fetching conventions out of the box — picking it saves the setup that building raw SSR with Vue alone would require, the same role Next.js plays for React.

RememberNuxt → a framework built on Vue, never "Vue's built-in SSR mode."
🌍 Real-world example ▾

An e-commerce product page needs to be indexable by search engines and fast on first load. SSR renders the product details to HTML on the server so both crawlers and users see content instantly; the client then hydrates it to make "Add to cart" interactive — without the page visibly flashing or re-rendering.
