Suspense — pausing a render, not just showing a spinner

"What problem does Suspense solve, and how is it different from a normal loading state?"

Why it matters ▾
  • Interviewers use this to check whether you see Suspense as a real rendering primitive, not just another way to spell isLoading.
  • Comes up any time a page has independent sections that load at different speeds — a dashboard of widgets, or a page with one slow section next to a fast one.
  • A natural follow-up after any question about lazy() or code splitting, since Suspense is what actually shows something while the split chunk loads.
🔥 Easy interview recall

Suspense → the pending half

Error Boundary → the rejected half

Think: Suspense pauses rendering while waiting. Error Boundary catches it if the wait ends in a rejection — different halves of the same async operation.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Suspense does not automatically handle a rejected promise the same way it handles the pending state. Suspense only covers the pending half of an async operation — a rejection is a thrown error during render like any other, and needs an Error Boundary wrapped around the Suspense boundary to actually show an error UI.

🔄 Likely Follow-up

"What's a request waterfall, and how does naive Suspense-for-data usage create one?" Fetching sequentially — one component renders and starts its own fetch, and only once that resolves does the next component even start rendering (and start its own fetch) — each one waiting on the one above it. The fix is "render-as-you-fetch": start every fetch immediately, before rendering, and let Suspense coordinate the waiting instead of letting one fetch trigger the next.

🎯 Say this in the interview — the exact lines to land

"Suspense lets a component pause rendering while it's waiting on something async — code with lazy(), or data with a supporting fetching approach — and shows the nearest fallback until it's ready. It only covers the pending half, though: a rejected promise still needs an Error Boundary around the Suspense boundary to show an error."

  • Suspense → pauses rendering, shows the nearest fallback — not a hand-rolled isLoading boolean.
  • Boundaries compose → nested Suspense boundaries decide what waits together vs. independently.
  • Rejections → Suspense doesn't catch them — wrap it in an Error Boundary.
  • Request waterfall → sequential fetch-then-render, one blocking the next.
  • The fix → render-as-you-fetch — start every fetch immediately, let Suspense coordinate the wait.
📖 Explanation ▾

Suspense lets a component "pause" rendering while it's waiting on something async — code that hasn't loaded yet (lazy()), or, with a supporting data-fetching approach, data that hasn't arrived yet. When a component suspends, React shows the nearest Suspense boundary's fallback instead of that component's output. Boundaries can sit at different granularities — around a whole page section, or around one small piece — deciding what shows a fallback on its own versus what waits together as a group.

Suspense only handles the pending half of the operation. If the underlying promise rejects, that surfaces as a thrown error during render, the same as any other render-time error — Suspense has no built-in error UI for it. Pairing an Error Boundary around the Suspense boundary is what catches that rejection gracefully instead of crashing the tree.

Handlesthe pending half — waitingthe rejected half — a thrown error

💻 See the code ▾
JSX 
<ErrorBoundary fallback={<ErrorUI />}> // catches a rejection
  <Suspense fallback={<Spinner />}>   // shows this while pending
    <ProfileData />
  </Suspense>
</ErrorBoundary>

Two different jobs, stacked on purpose: Suspense shows the spinner while pending, the Error Boundary catches it if the underlying promise rejects.

JSX 
// ❌ Waterfall — Posts's own fetch doesn't start until Profile resolves
function Profile() {
  const profile = useProfileData(); // suspends here
  return <Posts />;           // Posts only starts rendering (and fetching) now
}

// ✅ Render-as-you-fetch — kick off both immediately, before rendering
const profilePromise = fetchProfile(); // started immediately
const postsPromise = fetchPosts();     // started immediately too — not nested

Starting both fetches before rendering — instead of one nested inside the other — is exactly what avoids the waterfall.

🌍 Real-world example ▾

Ordering at a restaurant. Order several dishes all at once and the kitchen starts cooking everything in parallel — that's render-as-you-fetch. Order one dish, wait for it to fully arrive, then order the next, and so on — that's the waterfall. The second approach takes far longer purely because of how the orders were sequenced, not because the food itself takes longer to cook.
