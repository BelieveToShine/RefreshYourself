⭐ AI · Basic · Should Know

temperature = 0 promises the top token — not a byte-for-byte identical answer

"If I set temperature to 0, will the model give me the exact same output every time?"

Why it matters ▾
  • A direct follow-up whenever someone says "I use temperature 0 for consistency" — it checks whether they know what that setting actually controls.
  • Matters for anyone building automated tests, caching, or exact-match evals on top of an LLM API.
  • Comes up in system-design discussions about retries and whether an LLM call can be trusted as idempotent.
🔥 Easy interview recall

Temperature 0 = "always pick the top token" — but different runs can compute a slightly different "top."

Think: same recipe, different kitchen (GPU batch, hardware) → tiny rounding shifts → occasionally a different token wins.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Temperature 0 does not mean fully deterministic. It only fixes the decoding rule — always take the top token — not the floating-point math, batching, or GPU execution order that computed those probabilities in the first place.

🔄 Likely Follow-up

"Does setting a seed fix this?" It can help — some providers expose a seed parameter — but it's documented as improving reproducibility, not guaranteeing it, so the underlying variation is never fully eliminated.

🎯 Say this in the interview — the exact lines to land

"Temperature 0 means greedy decoding — always the single highest-probability token — but that doesn't make output fully deterministic, because floating-point math, batching, and GPU execution order can all shift by tiny amounts between runs."

  • temperature = 0 → greedy decoding, not a determinism guarantee.
  • Floating-point sums are not perfectly associative — a different batch of concurrent requests can shift the order.
  • GPU parallel execution and provider-side load balancing across replicas add more variation.
  • seed parameter → improves reproducibility, never guarantees it.
  • Never design a system assuming byte-for-byte identical output for the same input.
📖 Explanation ▾

Temperature controls how the model samples the next token. At temperature = 0, sampling turns off entirely — the model always takes greedy decoding: whichever token currently has the highest probability, every single time. That sounds like it should be perfectly repeatable, since the decision rule itself has no randomness left in it.

The variation that's left over isn't in the decision rule — it's in the arithmetic that produces the probabilities. Floating-point addition isn't perfectly associative: summing the same numbers in a different order can produce a tiny, different result. Production servers batch many requests together to run efficiently, and which other requests happen to share that batch (and how they're grouped) can shift the summation order from run to run. GPU parallel execution adds another source: the order operations finish in isn't always perfectly fixed either. Either is enough to nudge a probability by a tiny amount — and when the top two tokens are close, that nudge can flip which one wins.

Providers add further variation on their own end — a request can land on a slightly different model replica, or the model version behind the API can be updated. Some providers expose a seed parameter specifically to help with this, but it's documented as improving reproducibility, not guaranteeing it. The practical takeaway: never build a system — tests, caching, exact-match evals — on the assumption that the same input always produces byte-for-byte identical output, even at temperature 0 with a fixed seed.

💻 See the code ▾
Pseudocode 
response1 = callModel(prompt, temperature=0)
response2 = callModel(prompt, temperature=0)
# same prompt, same greedy rule — still not guaranteed identical

Both calls use the exact same decoding rule, back to back — the rule being identical doesn't make the underlying math identical.

Request 
{
  "model": "…",
  "temperature": 0,
  "seed": 42
}
// ✅ narrows the variation further, on providers that support it
// ❌ still not a byte-for-byte guarantee

A fixed seed is documented as improving reproducibility — never as a guarantee of it.

🌍 Real-world example ▾

A team writes an automated eval that calls the same prompt at temperature 0 and asserts the raw output string matches exactly. It passes locally, then flakes intermittently in CI. The fix isn't hunting for a bug in the eval — it's comparing on parsed, structured fields (or a similarity check) instead of an exact string match, since exact byte-for-byte output was never something the API promised in the first place.
