Dynamic Programming — solving each subproblem once, not a hundred times

"How do you know a problem needs dynamic programming, and what's the difference between memoization and tabulation?"

Why it matters ▾
  • Interviewers use DP to separate someone who recognizes a keyword from someone who can actually spot overlapping subproblems in a brand-new question.
  • Comes up constantly — resource-limited choices (knapsack-style), comparing two sequences (diffing, DNA alignment), and "best path/best split" problems all reduce to DP.
  • "Can you reduce the space?" is one of the most common DP follow-ups — worth having a ready answer, not improvising it live.
🔥 Easy interview recall

DP = "solve each unique subproblem once, then reuse the answer."

Think: memoization caches top-down, on top of the natural recursion. tabulation builds the same answers bottom-up, with no recursion at all.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding a cache to a recursive function doesn't automatically make it "dynamic programming." If you can't state in one sentence what dp[i] (or dp[i][j]) actually means, the state isn't well-defined and the solution is likely wrong, not just unclear.

🔄 Likely Follow-up

"Can you reduce the space complexity?" Often yes — when dp[i][j] only depends on row i-1, roll the table down to two 1D arrays (or one, updated carefully), cutting O(n·m) memory to O(m).

🎯 Say this in the interview — the exact lines to land

"DP applies when a problem has optimal substructure — the best answer is built from the best answers to its subproblems — and overlapping subproblems — a naive recursive solution solves the same subproblem more than once. The entire benefit is caching each unique subproblem's result so it's computed exactly once, whether that's done top-down with memoization or bottom-up with tabulation."

  • Overlapping subproblems the same call repeats — that's the actual signal to reach for DP, not just "this feels hard."
  • Memoization reach for it when the recursion is already natural — you just want to stop re-solving repeats.
  • Tabulation reach for it to avoid recursion/call-stack risk and to reason bottom-up.
  • 1D state is one index, 2D state is two — always be able to say what the state means in one sentence.
  • A 2D table that only needs the previous row can roll down to O(m) space — the standard follow-up answer.
📖 Explanation ▾

Optimal substructure means the best answer to the whole problem is genuinely built out of the best answers to its pieces — like knowing the fastest route home is built from the fastest route to each intersection along the way. Overlapping subproblems means a plain recursive solution asks the exact same question — the same parameters, like fib(2) or lcs(i, j) — more than once across different call paths. DP only pays off when both are true; a problem with optimal substructure but no repeated calls is just recursion, not DP.

Memoization and tabulation solve the identical problem, at the identical time complexity — they only differ in direction. Memoization starts from the natural recursive definition and bolts a cache onto it, so it usually reads closer to how you'd first describe the problem out loud. Tabulation starts from the smallest subproblem and iterates upward with no recursion at all, which avoids call-stack depth entirely — a real concern once the input is large enough that recursion could overflow the stack.

The state shape follows the problem, not the other way around: one index (dp[i]) for something like the house-robber problem, two indices (dp[i][j]) for comparing two sequences like LCS. The knapsack family (0/1 — each item taken once — and unbounded — an item reusable) builds its table over (item, remaining capacity) pairs. LIS has a straightforward O(n²) DP, and a faster O(n log n) version exists using binary search over a maintained array — worth knowing it exists, not something to derive live. State-machine DP just names a small, fixed set of states (say, "holding a stock" vs. "not holding one") and tracks the best value in each state after each step, instead of one sprawling table.

💻 See the code ▾
C# 
Dictionary<int, long> cache = new();

long Fib(int n)
{
    if (n <= 1) return n;                    // base case
    if (cache.TryGetValue(n, out var hit))
        return hit;                             // ✅ already solved — return cached
    long result = Fib(n - 1) + Fib(n - 2);      // same recursive shape as brute force
    cache[n] = result;                          // cache before returning
    return result;
}

Memoization (1D, top-down) — the cache is the entire fix; fib(2) is now computed once, not three times.

C# 
int Rob(int[] nums)
{
    int n = nums.Length;
    int[] dp = new int[n + 1];        // dp[i] = best sum using the first i houses
    dp[0] = 0;
    dp[1] = nums[0];
    for (int i = 2; i <= n; i++)
        dp[i] = Math.Max(dp[i - 1], dp[i - 2] + nums[i - 1]); // skip house i, or rob it
    return dp[n];
}

Tabulation (1D, bottom-up) — no recursion at all; every dp[i] is built strictly from smaller i values already in the array.

C# 
int[,] dp = new int[a.Length + 1, b.Length + 1]; // dp[i,j] = LCS length of a[..i], b[..j]

for (int i = 1; i <= a.Length; i++)
    for (int j = 1; j <= b.Length; j++)
        dp[i, j] = a[i - 1] == b[j - 1]
            ? dp[i - 1, j - 1] + 1          // characters match — extend the diagonal
            : Math.Max(dp[i - 1, j], dp[i, j - 1]); // no match — best of skipping either side

2D DP (LCS) — dp[i,j] means exactly one thing, the LCS length of the first i and first j characters. Say that sentence before writing the line.

🌍 Real-world example ▾

Your recursive solution times out on a larger input, but the logic looks correct. That's almost always overlapping subproblems, not a slow language — check whether the same (i, j, …) call happens repeatedly across different call paths, add a cache (or rewrite it bottom-up), and the same exponential-looking recursion usually drops to low-order polynomial time.
