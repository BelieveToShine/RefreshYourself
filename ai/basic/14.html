Big on paper, cheap to run — how do Mixture-of-Experts and quantization pull that off?

"Why can a model with a huge number of parameters still be cheap to run per request, and why can a model like a 7B-parameter one run on a laptop?"

Why it matters ▾
  • Explains why "parameter count" alone doesn't tell you how expensive a model actually is to run — a common trap when comparing models casually.
  • Comes up whenever someone asks how an open-weight model can run on consumer hardware instead of a data-center GPU cluster.
  • A very likely follow-up the moment a candidate mentions "the model has X billion parameters" in any other answer.
🔥 Easy interview recall

Mixture-of-Experts → many experts, only a few run per token

Quantization → same weights, stored in fewer bits

Think: MoE cuts how much compute runs per token; quantization cuts how much memory each weight takes — two different knobs, same goal: cheaper to run.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"More total parameters always means more compute per request." Not for a Mixture-of-Experts model — its total parameter count and its per-token compute cost are different numbers, because only the routed experts actually run; a large MoE model can cost about the same per token as a much smaller dense model.

🔄 Likely Follow-up

"Doesn't quantization make the model worse?" Usually a little, not a lot — it's a real trade of some output quality for a much smaller memory footprint and often faster inference, not a free lunch and not a disaster either.

🎯 Say this in the interview — the exact lines to land

"Mixture-of-Experts keeps the total parameter count high but only runs a handful of experts per token, so compute per request stays cheap. Quantization stores those weights in fewer bits, so the model takes far less memory to hold and run — they solve two different costs and are often combined."

  • Mixture-of-Experts → only a few experts run per token, even though the model holds many.
  • Quantization → fewer bits per weight, smaller memory footprint, usually a modest accuracy cost.
  • Different knobs → MoE cuts compute per token; quantization cuts memory per weight.
  • Distillation (related, not the same) → a smaller student model trained to mimic a bigger teacher — changes the model itself, not just how its weights are stored.
📖 Explanation ▾

A Mixture-of-Experts model is built from many expert sub-networks, but for any given token, a small router picks just a handful of them to actually run — the rest sit idle for that token. So the model's total parameter count can be huge, while the compute spent on any single token stays close to what a much smaller dense model would spend. That's how a model can feel very capable overall while still being relatively cheap to run per request.

Quantization is a completely different lever: it lowers the numeric precision used to store and compute a model's weights — for example, from 16-bit floating point down to 8-bit or 4-bit. Fewer bits per weight means a much smaller memory footprint and often faster inference, at some — usually modest — cost to output quality.

A related but separate idea worth knowing by name: distillation trains a smaller "student" model to mimic a larger "teacher" model's outputs, producing a cheaper model that keeps much of the teacher's capability. Distillation changes the model itself; quantization only changes how an existing model's weights are stored and computed — and the two, along with MoE, can all be combined in the same deployed model.

💻 See the code ▾
Pseudocode 
# simplified top-2 routing for one token
scores = router(token)              # one score per expert
chosen = top_k(scores, k=2)         # ✅ e.g. Expert 2 and Expert 5
output = sum(weight_i * expert_i(token) for i in chosen)

Every other expert is simply never called for this token — that's the whole saving, not a background optimization.

Pseudocode 
# 16-bit weight -> 4-bit weight (illustrative)
weight_fp16 = 0.734563            # original value
weight_int4 = quantize(weight_fp16, bits=4)  # ✅ rounded, far fewer bits stored

The stored number shifts slightly (rounding) — that small shift is the "modest cost to accuracy" quantization trades for the memory savings.

🌍 Real-world example ▾

A large hospital keeps many specialists on staff, but any one patient visit only routes to the two or three doctors actually relevant to it, not every specialist in the building — that's Mixture-of-Experts. Quantization is like sending a compressed photo instead of the raw file: far less space, nearly identical to look at, with a little fine detail traded away.
