Quickselect — why sort everything to find one element?

"Find the kth largest element faster than sorting — and when is a heap better?"

Why it matters ▾
🎯 Quickselect
❗ ProblemSorting the whole array costs O(n log n) just to read one position, and most of that ordering work is thrown away.
✅ SolutionQuickselect partitions around a pivot and keeps going into only the side that holds the target position, so the average cost is O(n).
RecallQuickselect = quicksort that follows only one side.
🔥 Easy interview recall

Quickselect = "partition, then chase only the side that holds your answer."

Think: quickselect → O(n) average, O(n²) worst, reorders the array heap of size k → O(n log k), safe, works on a stream

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Quickselect is O(n)." Only on average — a bad pivot every round (for example, always the last element of already-sorted data) degrades it to O(n²), so pick the pivot at random.

🔄 Likely Follow-up

"So when would you use a heap instead?" When the numbers arrive as a stream, don't fit in memory, or the array must stay untouched — a min-heap of size k costs O(n log k) with O(k) memory, and quickselect needs all the data in an array it is allowed to reorder.

🎯 Say this in the interview — the exact lines to land

"I'd use quickselect: partition around a pivot, then recurse into only the side that contains the target index. That is O(n) on average and O(n²) in the worst case, and it avoids a full sort. If the data is a stream, too big for memory, or must not be reordered, I'd use a min-heap of size k instead — O(n log k) with O(k) memory."

  • Quickselect → O(n) average, because each round drops a chunk of the array.
  • Worst case → O(n²) on bad pivots; a random pivot makes that unlikely.
  • Heap of size k → O(n log k), safe on streams, doesn't reorder the input.
  • Full sort → O(n log n) — simplest, fine when n is small.
  • Many duplicates → a 3-way partition (Dutch national flag) keeps the loop short.
📖 Explanation ▾

Quickselect is quicksort that stops chasing both sides. Pick a pivot and partition: smaller values go left, larger go right, and the pivot lands in its final sorted position. Compare that position with the target index. If they match, you're done. If not, repeat on only one side — the other side can't contain your answer. For the kth largest, the target index in ascending order is n - k. The side sizes shrink round after round, so the work adds up to about n + n/2 + n/4 + …, which is O(n) on average (see Sorting for the partition step itself).

The catch is the pivot. If it keeps splitting the range into "everything" and "nothing" — a fixed last-element pivot on sorted input does exactly that — the work becomes O(n²). A random pivot makes that unlikely. Lots of equal values can also slow a two-way partition; a 3-way partition (less than / equal to / greater than the pivot, the Dutch national flag idea) handles them in one pass. A "median of medians" pivot gives a guaranteed O(n) but is heavier, so it is rarely what an interview wants coded.

A heap answers the same question differently: keep a min-heap of the k largest values seen, and the top is the kth largest. It never needs all the data at once, which is why it is the natural fit for streams (see Streaming / Large-Dataset Problems).

💻 See the code ▾
C# 
int KthLargest(int[] nums, int k)
{
    int target = nums.Length - k;          // index in ascending order
    int lo = 0, hi = nums.Length - 1;
    var rng = new Random();

    while (lo < hi)
    {
        int pivot = nums[rng.Next(lo, hi + 1)];   // ✅ random pivot
        int lt = lo, i = lo, gt = hi;       // 3-way partition (Dutch flag)
        while (i <= gt)
        {
            if      (nums[i] < pivot) Swap(nums, lt++, i++);
            else if (nums[i] > pivot) Swap(nums, i, gt--);
            else                      i++;
        }
        // [lo..lt-1] < pivot · [lt..gt] == pivot · [gt+1..hi] > pivot
        if      (target < lt) hi = lt - 1;   // answer is on the left
        else if (target > gt) lo = gt + 1;   // answer is on the right
        else return pivot;                    // ✅ target sits in the equal block
    }
    return nums[lo];
}

static void Swap(int[] a, int x, int y) => (a[x], a[y]) = (a[y], a[x]);

Expected O(n), O(1) extra memory. It reorders nums. Assumes 1 <= k <= nums.Length. On [3, 2, 7, 1, 5, 6, 4] with k = 2 it returns 6.

C# 
int KthLargestHeap(IEnumerable<int> nums, int k)
{
    var minHeap = new PriorityQueue<int, int>();   // smallest on top (.NET 6+)
    foreach (int x in nums)
    {
        minHeap.Enqueue(x, x);
        if (minHeap.Count > k)
            minHeap.Dequeue();                 // ✅ drop the smallest — keep the k biggest
    }
    return minHeap.Peek();                  // smallest of the top k = kth largest
}

O(n log k) time, O(k) memory, the input is never reordered — and it works one item at a time, so the numbers can be a stream. Assumes the input has at least k items.

🌍 Real-world example ▾

You need the median response time from a big batch of measurements already in memory. The median is just the element at the middle position, so quickselect finds that one value without sorting the whole list.
