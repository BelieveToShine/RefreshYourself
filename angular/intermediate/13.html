Signals + RxJS — two models that convert into each other, not compete

How do toSignal() and toObservable() actually bridge the two models, and should every Observable become a Signal?

Why it matters ▾
  • Interviewers use this to check whether you understand the actual boundary between the two models, not just whether you can define Signals and Observables separately.
  • Comes up any time an HTTP call or a router-derived value needs to become template-friendly state, or a Signal-held form value needs to be debounced.
  • A near-guaranteed follow-up once you mention either function: whether converting is always a good idea — it isn't, and that's the trap below.
🔥 Easy interview recall

toSignal(obs$) → Signal, latest value

toObservable(sig) → Observable, value stream

Think: done streaming → toSignal() need a stream again → toObservable()

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Signals are the newer, better way — just convert everything to one." Once an in-progress RxJS pipeline (still being composed with switchMap/debounceTime) becomes a Signal partway through, you're out of the Observable operator world — convert deliberately at a genuine boundary, not mid-pipeline out of habit.

🔄 Likely Follow-up

"If you toSignal() an HTTP Observable, what value does the Signal have before the first response arrives?" Whatever initialValue you explicitly pass in — commonly undefined, null, or a sensible default — there's necessarily a gap between "the Signal exists" and "the real data has arrived," and the template needs to handle that state explicitly.

🎯 Say this in the interview — the exact lines to land

"toSignal() subscribes to an Observable and keeps a Signal updated with its latest emitted value, so templates and computed()s can just read it synchronously. toObservable() does the reverse — it emits whenever the Signal changes, handing that value back into RxJS's operators. Not every Observable should become a Signal, though — only convert once you're actually done streaming, not while you're still composing operators on it."

  • toSignal() → Observable's latest value, read synchronously.
  • toObservable() → Signal's changes, as a stream you can pipe again.
  • Still mid-pipeline with switchMap/debounceTime? Stay an Observable — converting early throws away the composability.
  • Shared value that's also piped through RxJS elsewhere? BehaviorSubject, not a Signal.
📖 Explanation ▾

The real decision isn't "which model is generally better" — it's whether this particular piece of data is fundamentally a stream of async events over time (debounced search input, combining multiple sources, retry/cancellation — RxJS's strength) or a value that's already resolved and you mostly just need to read and derive from synchronously right now (a Signal's strength). toSignal() and toObservable() are the two doors between those rooms, not a replacement for either one.

toSignal(observable$) subscribes internally and keeps a Signal pointed at the Observable's latest emitted value — reach for it once an async operation has resolved into "the current value I have," and what's left is simple template/computed() reads. toObservable(signal) goes the other way, emitting an event every time the Signal's value changes, so a Signal-held value can start a new RxJS pipeline (debounce, switchMap, and the rest) when it needs to.

Handling an HTTP call with Signals is the direct combination of the two: fetch with HttpClient exactly as before — still an Observable — then toSignal() the result with an explicit initial value, since the HTTP call is async and the Signal needs some value before the first response arrives. The newer resource()/ httpResource() family, covered on a later Advanced page, is a more purpose-built tool for exactly this pattern — worth knowing it exists, not needed to answer this question.

💻 See the code ▾
TypeScript 
readonly user = toSignal(
  this.http.get<User>('/api/me'),
  { initialValue: undefined }  // HTTP is async — Signal needs a value before the first response
);

No initialValue and the Signal has nothing to read on the very first render — the template has to handle that gap.

TypeScript 
toObservable(this.searchTerm).pipe(
  debounceTime(300),
  switchMap(q => this.api.search(q))
).subscribe(results => this.results.set(results));

searchTerm is a Signal from the template — but debounceTime/switchMap only exist as RxJS operators, so it has to cross back into Observable-land first.

🌍 Real-world example ▾

Observables and Signals are like two currencies at a border crossing. toSignal() and toObservable() are the exchange booths — you convert one into the other exactly when you're crossing from "still actively trading/composing" (RxJS) into "just need to hold and spend a current amount simply" (Signals). You exchange at the border, not constantly back and forth mid-transaction.
