The N+1 query problem is what happens when "just loop over the results and access a relationship" quietly becomes one query per row

What is the N+1 query problem, and how would you troubleshoot slow database queries from Python?

Why it matters ▾
  • N+1 is one of the most common real production slowdowns in anything built on an ORM — an endpoint that "just" loops over results and touches a relationship, nothing more exotic than that.
  • It's a troubleshooting question, not trivia — "why did this endpoint get slower as the data grew" is a real interview scenario, and N+1 is the first thing a strong candidate checks for.
  • A common follow-up chain in Python interviews using SQLAlchemy or Django: what's the DB-API, what does an ORM trade off for convenience, then straight into N+1.
🔥 Easy interview recall

order.customer → fetched lazily, on the first access

Loop + lazy access → N+1 queries, not 1

Fix → eager-load before the loop starts

Think: N+1 code looks completely ordinary — the query count is invisible until you actually count round-trips.

🧠 Visual Mental Model — the same loop, two very different query counts
⚠️ Common Trap

"It's just a for loop with a property access — nothing expensive is happening there." Each access to a lazily-loaded relationship inside that loop is its own database round-trip, so looping over 100 rows and reading .customer on each one turns 1 intended query into 101 real ones — and the code reads as completely ordinary Python, which is exactly why this bug is so easy to write by accident.

🔄 Likely Follow-up

"How do you actually fix an N+1 once you've found one?" Eager-load the relationship up front — joinedload/selectinload in SQLAlchemy, select_related (to-one) or prefetch_related (to-many) in Django — so the related rows come back in one query, or one small constant number of queries, instead of one per row.

🎯 Say this in the interview — the exact lines to land

"N+1 looks like perfectly ordinary code — it's a lazy-loaded relationship accessed inside a loop, turning 1 intended query into N+1 actual ones. The fix is eager loading — joinedload/selectinload in SQLAlchemy, select_related/prefetch_related in Django — so the related data comes back in one query instead of one per row."

  • DB-API → the standard low-level interface every Python database driver implements (connect, cursor, execute, fetch).
  • ORM lazy loading → fetches a relationship only on first access, not together with the parent row.
  • N+1 → 1 intended query becomes N+1 actual ones when a loop accesses a lazy relationship per row.
  • Fix → eager-load before the loop (joinedload/ selectinload, select_related/prefetch_related).
  • Async database access → needs an async-native driver, not a sync driver wrapped in async def.
📖 Explanation ▾

Python's DB-API is the standardized low-level interface — connect, cursor, execute, fetch — that different database drivers implement consistently, so code written against one driver reads the same way against another. On top of that, connection pooling reuses a fixed set of already-open connections across requests instead of opening and closing one per request, and transactions group related writes so they succeed or fail together — both matter more as traffic grows, not less.

An ORM (SQLAlchemy, Django ORM) maps rows to Python objects and lets you write queries in Python instead of raw SQL strings — trading some control and transparency for productivity, plus parameterized queries by default, which reduces SQL-injection risk. Part of that convenience is lazy loading: a relationship like order.customer is only actually fetched the first time it's accessed, not eagerly with the parent row. That's the direct cause of N+1 — looping over 100 orders and accessing .customer on each one fires 100 separate queries instead of one query that fetches everything needed up front.

Troubleshooting a slow endpoint follows in that order: check for an N+1 pattern first (a loop plus a relationship access is the tell), then check for a missing index, then look at actual query plans and timing — usually via the ORM's own query-logging, or the database's slow-query log. Async database access needs an async-native driver to actually avoid blocking the event loop during that I/O — just wrapping a sync driver's calls in async def doesn't make them non-blocking.

💻 See the code ▾
Python 
orders = session.query(Order).all()  # 1 query

for order in orders:
    print(order.customer.name)  # ❌ lazy load — 1 query PER row

100 orders → 101 queries total: 1 for the list, plus 1 more for every .customer access inside the loop.

Python 
from sqlalchemy.orm import joinedload

orders = (
    session.query(Order)
    .options(joinedload(Order.customer))  # ✅ eager-load up front
    .all()
)  # still 1 query

for order in orders:
    print(order.customer.name)  # already loaded, no extra query

Same loop, same output — joinedload fetches every customer in that same query (or one extra, constant-size query), not one query per row.

🌍 Real-world example ▾

An API endpoint kept getting slower as its result set grew — not crashing, just steadily heavier under load. The root cause was an N+1 query hidden inside a serializer: it accessed a lazy-loaded relationship once per item being serialized. The fix was a single eager-loading change to the query — no other code touched — and the endpoint's response time stopped scaling with row count.
