Lazy Evaluation vs. Materialization — a plan, or a result?

"What's the practical difference between keeping a query 'live' and calling ToList() on it?"

Why it matters ▾
🔗 Multiple enumeration
❗ ProblemChecking query.Any() and then running foreach (var x in query) on the very same un-materialized query looks like two cheap reads of one result — but it's actually two full runs of the entire pipeline from scratch, and against a database that means two full round trips instead of one.
✅ SolutionCall ToList() (or another materializing operator) once the result needs to be read more than once — that locks the data into memory as a concrete result, so every later read is a cheap in-memory read instead of a re-run of the whole pipeline.
RecallUn-materialized + read twice = the pipeline runs twice, not once.
🔥 Easy interview recall

Lazy query = "a live plan — enumerate it twice, it runs twice."

Think: .Any() then foreach on the same lazy query = two full pipeline runs, not one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reading a lazy query twice is not "reading a result twice" — it's running the whole pipeline twice. A .Any() check followed by a foreach over the same un-materialized query re-executes everything from the source, including a second full database round trip if the query targets one.

🔄 Likely Follow-up

"How do you fix multiple enumeration?" Call ToList() (or ToArray()) once, right after the query is built, and read from that materialized list for every subsequent check or loop — one execution, as many reads as you want afterward.

🎯 Say this in the interview — the exact lines to land

"A lazy query re-runs its entire pipeline every time it's enumerated — it has no memory of a previous run. If the same query gets checked with .Any() and then looped with foreach, that's two full executions, which against a database means two round trips. Calling ToList() once locks in the result so everything after that is a cheap in-memory read."

  • Lazy query → re-runs from scratch on every enumeration.
  • Multiple enumeration → multiple database round trips, not one.
  • ToList()/ToArray() → materializes once, every later read is free.
  • Same engine as deferred execution → this page's job is the multiple-enumeration consequence.
📖 Explanation ▾

Lazy evaluation and materialization are two states of the same query. A lazy query (the default) is still just a plan — every time it's enumerated, it walks the source and every operator in the chain again, with zero memory of any earlier run. A materialized query has already been run once, via ToList(), ToArray(), or similar, and the result now lives as a concrete, fixed collection in memory.

The practical consequence is multiple enumeration: code that reads the same lazy query more than once — once to check .Any(), again in a foreach — isn't reusing a result, it's triggering the entire pipeline again from the original source. Against an in-memory list that's wasted CPU; against a database, via EF Core or similar, it's a second full round trip, running the same generated SQL twice.

The fix is to materialize once, deliberately, at the point the result needs to be read more than once — not to avoid deferred execution altogether, just to stop paying for it repeatedly.

💻 See the code ▾
C# 
var active = dbContext.Users.Where(u => u.IsActive);   // still IQueryable, lazy

if (active.Any())              // ❌ round trip #1 — runs the query
    foreach (var u in active)  // ❌ round trip #2 — runs the SAME query again
        Process(u);

Same active variable, two full executions — nothing was cached between them.

C# 
var active = dbContext.Users.Where(u => u.IsActive).ToList();   // ✅ one round trip, now

if (active.Any())              // ✅ reads the in-memory list
    foreach (var u in active)  // ✅ same in-memory list again
        Process(u);

ToList() materializes once — every read after that is a free, in-memory read.

🧭 Use Cases — recognize these when they happen to you ▾
1 You check .Any(), then foreach the same un-materialized query against a database

This is the single most common real-world instance of this page's trap — two round trips where the developer intended one, because the query object itself was reused without ever materializing it.

RememberReused lazy query → reused pipeline run, every single time.
2 You need the same query's results for a count, a loop, and a display list

Materializing once up front, then passing the resulting List<T> to every consumer, means every one of those reads is free — no re-execution, no matter how many times the data is touched afterward.

RememberMultiple consumers of one result → materialize once, hand out the list.
3 You deliberately keep a query lazy because the source changes between reads

Staying lazy is correct, not a bug, when each read is genuinely supposed to reflect the latest source state — e.g. polling a live in-memory collection. The risk is only when the *same* read is unintentionally repeated.

RememberLazy is a feature when you want fresh data each time, not a default mistake.
🌍 Real-world example ▾

An API endpoint logs "found N matching rows" then returns those same rows in the response body. If both the count and the body read the same un-materialized IQueryable, the database gets hit twice for one logical request — the fix is a single ToList() right after the query is built, then reading .Count and the list itself from that.
