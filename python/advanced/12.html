⭐ Python · Advanced · Should Know

A cache should make things faster when it works and merely unhelpful when it doesn't — never a source of wrong answers

What happens when cached data becomes stale? How would you prevent a cache stampede?

Why it matters ▾
  • Caching is one of the fastest, cheapest wins for a slow endpoint — but a cache with no invalidation plan turns that win into a correctness bug that's hard to notice.
  • Cache stampede is a real production incident shape, not a textbook scenario — a popular entry expiring during a traffic spike can knock a database over.
  • A very common senior/architect follow-up once caching comes up at all: "how do you know it's not lying to you?"
🔥 Easy interview recall

lru_cache → memoize per args, evict least recently used

No invalidation → cache serves confidently wrong data

Cache stampede → one entry expires, everyone recomputes at once

Think: a cache doesn't need to be smart, it needs to know when to forget — that's the whole hard problem.

🧠 Visual Mental Model — the same expiring entry, two different outcomes
⚠️ Common Trap

Caching data with no invalidation strategy at all — "cache it and forget it." That works fine until the underlying data changes, and the cache keeps confidently serving the now-wrong old value forever, which is strictly worse than not caching at all for correctness-sensitive data.

🔄 Likely Follow-up

"In-memory cache vs. Redis — when do you actually need Redis?" As soon as multiple app processes/instances need to share the same cached state — a per-process in-memory cache can't do that — or the cache needs to survive an individual process restart.

🎯 Say this in the interview — the exact lines to land

"A cache with no invalidation strategy eventually serves confidently wrong data — that's worse than no cache at all. The standard fix for a stampede specifically is jittered TTLs plus a recompute lock."

  • lru_cache → memoizes a function's return value per distinct set of arguments, evicting the least-recently-used entries once maxsize is hit.
  • TTL → the simplest invalidation strategy — expire after a fixed duration, trading staleness tolerance for simplicity.
  • In-memory vs. Redis → Redis is for state shared across multiple processes, or that needs to survive a restart; in-memory is faster but local to one process.
  • Cache stampede fix → a lock so only one request recomputes while others wait, plus jittered TTLs so entries don't all expire at the same instant.
📖 Explanation ▾

Caching stores the result of an expensive computation or lookup so a repeated request for the same thing can skip redoing the work. functools.lru_cache is the standard, simplest in-process tool for this — a decorator that memoizes a pure(ish) function's return value per distinct set of arguments, and once the call count for distinct arguments passes maxsize, it evicts the least recently used entries first to make room.

Cache invalidation — knowing when a cached value is no longer valid and must be refreshed or evicted — is the famously hard part. Get it wrong and the cache doesn't just become unhelpful, it silently serves stale or wrong data as if it were current. TTL (time-to-live) is the common, simple answer: expire an entry automatically after a fixed duration. An in-memory cache (lru_cache, a plain dict) is the fastest option but lives inside one process — it doesn't share state across multiple app instances/workers, and it's lost on restart. Redis (or similar) is a separate, shared cache service reachable from multiple processes or machines, at the cost of a network round-trip on every access.

A cache stampede is many concurrent requests all missing the cache at the exact same moment — classically, right when a popular entry's TTL just expired — and all simultaneously recomputing or re-fetching the same expensive thing at once, hammering whatever is behind the cache. The standard mitigations: a lock so only one request recomputes while the rest wait for that result, staggered/jittered TTLs so many entries don't expire at the exact same instant, or serving a slightly-stale value while one background refresh happens.

💻 See the code ▾
Python 
from functools import lru_cache

# ✅ memoizes per distinct (user_id) argument
@lru_cache(maxsize=128)
def get_user(user_id):
    return db.fetch_user(user_id)  # only runs once per user_id

Same user_id again → returns instantly from cache. A new user_id still hits the database. Once 128 distinct users are cached, the least recently used one gets evicted to make room.

Python 
_lock = threading.Lock()

def get_cached(key):
    value = cache.get(key)
    if value is None:
        with _lock:                     # 🔒 only one request recomputes
            value = cache.get(key)         # re-check: another request may have just filled it
            if value is None:
                value = expensive_fetch(key)
                cache.set(key, value, ttl=60)
    return value

Every other request blocks on _lock, then finds the cache already filled by the first one — so only one call ever reaches expensive_fetch, not four.

🌍 Real-world example ▾

A popular product page's cache entry expired at the exact same moment a traffic spike hit — every one of those requests missed the cache together and hit the database at once, briefly overwhelming it. The fix was jittered TTLs, so entries for popular keys don't all expire in sync, plus a recompute lock so only one request ever rebuilds a given entry.
