Multi-agent systems don't add N calls — they add N loops

"What are multi-agent patterns like planner/worker and supervisor, and what do they actually cost you?"

Why it matters ▾
🧭 Planner/Worker
❗ ProblemOne agent both deciding what to do and doing every piece of it can't split sub-tasks out to run separately or hand a narrower job to a specialized worker.
✅ SolutionOne planner agent breaks the goal into sub-tasks up front, then separate worker agents actually execute each piece and report a result back.
RecallPlanner/worker = one agent plans upfront, workers execute.
🧭 Supervisor
❗ ProblemA one-time upfront plan has no one watching once it's dispatched, so a worker that gets stuck or misbehaves mid-task can run unnoticed until the whole thing stalls.
✅ SolutionA supervisor agent keeps coordinating and monitoring the workers continuously as work runs, catching a stuck or misbehaving one instead of just trusting the plan.
RecallSupervisor = coordinates & monitors ongoing, not a one-time plan.
🧭 Debate
❗ ProblemA single agent's one-pass answer has no independent check on it, so a reasoning error in that first pass just ships as the final result.
✅ SolutionMultiple agent instances run the same problem and argue or critique each other's answers before one gets picked, catching mistakes a single pass would miss.
RecallDebate = agents critique each other before one answer is picked.
🔥 Easy interview recall

Planner/worker = one agent decides, others execute. Supervisor = one agent keeps coordinating and watching as the work runs.

Think: N agents talking to each other ≠ N calls it's N × (each agent's OWN multi-call loop)

⚠️ Common Trap

Adding agents isn't free — it's not even cheap. Each extra agent brings its own multi-call reasoning loop, so a 3-agent system can easily mean 10+ LLM calls before anyone gets an answer a single agent (or even a fixed chain) might have handled in one or two.

🔄 Likely Follow-up

"When would you NOT use a multi-agent setup?" When a single agent's own loop — or even a fixed, non-agentic chain — can already handle the task. Multi-agent coordination adds real latency, cost, and failure surface, so it earns its place only when the task genuinely splits into separate specialized roles.

🎯 Say this in the interview — the exact lines to land

"Planner/worker splits deciding-what-to-do from doing-it; supervisor keeps coordinating and monitoring multiple specialized workers as the work runs; debate has agents critique each other before settling on an answer. The real cost is that each agent's own reasoning loop is itself several LLM calls, so N agents isn't N calls — it's N times whatever each one's loop takes — which is why I'd only reach for multi-agent when a single agent's loop genuinely can't cover the task."

  • Supervisor → coordinates & monitors ongoing, not just a one-time upfront plan.

  • Risky action in the flow → add a human-approval gate before it executes, same spirit as guarding a side-effecting tool.
📖 Explanation ▾

Planner/worker splits a goal into two jobs: one agent — the planner — breaks it into smaller sub-tasks, then separate worker agents actually execute each sub-task. Supervisor is the close cousin: instead of one upfront plan, a supervisor agent keeps coordinating and monitoring several specialized workers as the task runs, deciding which worker handles which part and folding their results back together.

Debate takes a different angle: instead of splitting the work, it runs the same problem through multiple agent instances — sometimes different roles, sometimes even different models — that argue or critique each other's answers before one gets picked, catching mistakes a single pass could miss. Frameworks like LangGraph, Microsoft's Semantic Kernel, AutoGen, and CrewAI exist to implement these coordination patterns — worth knowing the ecosystem exists, without needing to memorize any one framework's exact API.

The part interviewers actually probe: coordinating N agents is not N LLM calls. Each agent's own reasoning/tool-use loop is itself a sequence of calls, so the real cost is N × (however many calls each agent's own loop takes) — latency and spend can blow up fast. That's the case for weighing whether the task truly needs multiple specialized agents, or whether a single agent (or a fixed chain) already covers it — and for any risky, consequential action inside a multi-agent flow, adding a required human-approval gate before it executes.

💻 See the code ▾
Pseudocode 
# Planner/worker — plan once, dispatch to workers
sub_tasks = planner.plan(goal)                      # ✅ one call: break the goal down
results = [worker.run(t) for t in sub_tasks]      # each worker.run() is its OWN loop, not 1 call
final = planner.combine(results)                    # ✅ one call: merge the results

planner.plan and planner.combine are 2 calls total — but every worker.run() above hides several more.

Pseudocode 
# What worker.run(task) is actually doing underneath
def worker.run(task):
    calls = 0
    while not done:
        thought = llm.reason(task, history)   # ⚠️ one LLM call, EVERY time through the loop
        calls += 1
        if thought.needs_tool:
            result = call_tool(thought.tool)
        else:
            done = True
    return result   # ⚠️ calls is usually > 1, not 1

3 agents (1 planner + 2 workers), each looping 3-4 times, is 10+ LLM calls before anyone gets an answer — not 3.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to split one big goal into sub-tasks that different workers can execute

The planner agent breaks the goal into sub-tasks and dispatches each one to a separate worker; each worker then runs its own reasoning/tool-use loop independently until it returns a result. This is the #1 pattern you'll actually reach for once a task genuinely splits into separate pieces.

RememberPlanner/worker = split deciding from doing, once upfront.
2 A worker might get stuck or go off track partway through, and something needs to catch that

Instead of one upfront plan, a supervisor agent keeps coordinating and monitoring the workers continuously as work runs — deciding which worker handles which part and folding results back together, and catching a stuck or misbehaving worker instead of finding out too late.

RememberSupervisor = ongoing coordination and monitoring, not a one-time plan.
3 One agent's answer needs an independent second opinion before it ships

Debate runs the same problem through multiple agent instances — sometimes different roles, sometimes even different models — that argue or critique each other's answers before one gets picked, catching a reasoning mistake a single pass would have missed.

RememberDebate = agents critique each other before one answer is picked.
🌍 Real-world example ▾

A team wants a "research assistant" that searches, summarizes, and fact-checks — tempting to spin up three separate agents coordinated by a supervisor. But if the summarizer never really needs to push back on the searcher's results, a single agent looping through search → summarize → fact-check tool calls does the same job for a fraction of the LLM calls. The multi-agent split only earns its cost once fact-checking genuinely needs to critique the summarizer's output independently — that's closer to the debate pattern, and worth its own agent.
