ALB routes to healthy targets — the ASG is what actually adds capacity

"How do an ALB and an Auto Scaling Group work together to provide high availability?"

Why it matters ▾
⚖️ ALB
❗ ProblemA web app or microservices setup needs traffic routed by URL path or hostname, not just by IP and port — a balancer that only sees packets has no way to make that call.
✅ SolutionThe ALB operates at Layer 7, reading the actual HTTP/HTTPS request, so it can route by path, host, or headers — the right fit for web apps and microservices.
RecallALB = Layer 7, routes by path/host — the web-app and microservices choice.
🔌 NLB
❗ ProblemNon-HTTP TCP/UDP traffic has no HTTP request for a Layer 7 balancer to read, and traffic that needs extreme throughput, the lowest possible latency, or a fixed IP to point at doesn't need the ALB's HTTP-aware overhead.
✅ SolutionThe NLB operates at Layer 4, forwarding by IP and port only — that's exactly what gives it ultra-low latency, extreme throughput, and support for static IPs.
RecallNLB = Layer 4, IP + port only — the non-HTTP, high-throughput, static-IP choice.
🔥 Easy interview recall

ALB → routes to healthy targets

ASG → adds/removes capacity

Think: the ALB is the traffic cop directing cars to open lanes; the ASG is the one who calls in more lanes when traffic backs up.

⚠️ Common Trap

The ALB alone provides elasticity. It doesn't — the ALB only distributes traffic across whatever's currently registered in its target group; it's the ASG that actually launches or terminates instances in response to load or failures.

🔄 Likely Follow-up

"What happens during a sudden traffic spike?" A target-tracking scaling policy kicks in once the tracked metric (e.g. average CPU) crosses its threshold, launching new instances that join the target group only after passing their health check — there's real lag, minutes not seconds, before that new capacity is actually live.

🎯 Say this in the interview — the exact lines to land

"ALB routes to healthy targets; the ASG is what actually adds or removes capacity. Health checks decide who's in the rotation, and the scaling policy decides how many instances exist to be in it."

  • ALB → Layer 7, understands HTTP/HTTPS, routes by path or host — the right choice for web apps and microservices.
  • NLB → Layer 4, ultra-low latency and extreme throughput, static IPs — the right choice for non-HTTP TCP/UDP traffic.
  • Target group → the set of instances, IPs, or Lambdas the load balancer health-checks and routes to.
  • ASG → target-tracking or step scaling policies decide when to add or remove instances, and replace ones that fail health checks.
📖 Explanation ▾

An Application Load Balancer operates at Layer 7, so it understands HTTP/HTTPS and can route by path, host, or headers — the natural fit for web apps and microservices. A target group is the set of instances, IPs, or Lambda functions it routes to, and each target is continuously checked with a health check; a target that fails it is pulled out of rotation immediately, no traffic sent its way until it passes again.

An Auto Scaling Group is the separate piece that actually changes how many instances exist. A target-tracking policy (e.g. keep average CPU near 50%) or a step scaling policy watches a metric and launches or terminates instances to match it. The two work together: the ALB never adds capacity on its own, and the ASG doesn't route traffic — it just keeps the pool the right size, replacing any instance that fails its health check if that instance belongs to the ASG.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your web app or microservices need traffic routed by URL path or hostname

The ALB reads the actual HTTP/HTTPS request and routes it by path, host, or header — this is the #1 scenario you'll actually run into for a web app or microservices setup.

RememberLayer 7 request → ALB reads it → routes by path/host.
2 Traffic suddenly spikes and your current instances start getting overloaded

A target-tracking scaling policy launches new instances once the tracked metric crosses its threshold — the ALB doesn't need to be told anything, it starts routing to each new instance the moment it passes its health check.

RememberMetric crosses threshold → ASG launches → ALB picks it up automatically.
3 Your traffic is non-HTTP TCP/UDP, or needs extreme throughput and a static IP

An ALB has no HTTP request to read here, so it's the wrong tool — the NLB forwards by IP and port only, which is exactly what gives it ultra-low latency, extreme throughput, and support for a static IP.

RememberNon-HTTP or extreme throughput → NLB, not ALB.
🌍 Real-world example ▾

A retailer's web tier scales from 4 to 20 instances during a flash sale, driven by a target-tracking policy watching average CPU. The ALB doesn't need to be told anything new — it automatically starts routing to each new instance the moment it passes its health check.
