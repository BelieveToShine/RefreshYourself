IHostApplicationLifetime — three signals, one narrow window to actually act

"What are the application lifetime events, and when would you actually hook into each?"

Why it matters ▾
  • Comes up when you need warm-up logic (cache priming, connection pool init) to run only once the app is truly live — not scattered in Program.cs before the host even exists.
  • Container orchestrators (Kubernetes, Docker) send a shutdown signal and then wait a limited grace period before force-killing the process — this tests whether you know that window is real but finite.
  • The three stages themselves are named in passing on What Happens When a .NET App Starts — this page is where you actually learn to hook into each one.
🔥 Easy interview recall

ApplicationStarted → ready — start warm-up work

ApplicationStopping → grace period — finish in-flight work

ApplicationStopped → already dead — final cleanup only

Think: Started → the "go" signal Stopping → the "hurry up" warning Stopped → the "too late" line

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ApplicationStopping does not mean "unlimited time to clean up." Most hosting environments — Kubernetes, Docker, IIS — give only a fixed grace period (e.g. Kubernetes' terminationGracePeriodSeconds) before force-killing the process, so genuinely slow shutdown work needs its own timeout awareness, not an assumption that it'll always finish.

🔄 Likely Follow-up

"How is this different from IHostedService.StopAsync?" StopAsync is one hosted service's own cleanup, invoked as part of the overall shutdown sequence. IHostApplicationLifetime's events are app-wide signals — any component, hosted service or not, can subscribe to them.

🎯 Say this in the interview — the exact lines to land

"IHostApplicationLifetime gives you three events: ApplicationStarted, to run warm-up work once the app is truly live; ApplicationStopping, to finish in-flight work during a limited grace period; and ApplicationStopped, for final cleanup after everything has already torn down."

  • ApplicationStarted → safe to run warm-up work — the app is fully live.
  • ApplicationStopping → your only window to finish cleanly — but it's timed, not unlimited.
  • ApplicationStopped → final cleanup only — nothing meaningful can still depend on the app being up.
  • Different from IHostedService.StopAsync → app-wide signal, not one service's own shutdown.
📖 Explanation ▾

IHostApplicationLifetime is injected through DI like any other service. It exposes three CancellationTokens — not events — named ApplicationStarted, ApplicationStopping, and ApplicationStopped. You hook into any of them with token.Register(callback); the token itself gets cancelled at that stage, which is what triggers your callback.

ApplicationStarted only fires once the host has actually finished starting — running warm-up work any earlier risks colliding with services that are still being constructed. ApplicationStopping fires the moment a shutdown has been requested, but the process is still alive — this is the one stage with genuine time to act, which is exactly why cleanup logic belongs here.

ApplicationStopped fires only after the host has already finished tearing down. By then nothing that depends on the app still running can meaningfully happen — it exists for truly final bookkeeping, not application logic.

💻 See the code ▾
C# 
public class WarmupNotifier
{
    public WarmupNotifier(IHostApplicationLifetime lifetime, ICache cache)
    {
        lifetime.ApplicationStarted.Register(() =>
        {
            _ = cache.PrimeAsync();   // ✅ app is fully live — safe to warm up
        });

        lifetime.ApplicationStopping.Register(() =>
        {
            cache.FlushToDisk();      // ⏳ shutdown requested — finish work here
        });
    }
}

Each token's Register callback runs once that stage's CancellationToken is cancelled — no event subscription needed.

C# 
lifetime.ApplicationStopping.Register(() =>
{
    Thread.Sleep(30000);   // ❌ assumes unlimited time to clean up
});

If the host's shutdown grace period is shorter than this, the process is killed mid-sleep — the cleanup never finishes.

C# 
public class QueueListener : BackgroundService
{
    public override async Task StopAsync(CancellationToken cancellationToken)
    {
        // cancellationToken is cancelled once the grace period runs out
        await _channel.DrainAsync(cancellationToken);
        await base.StopAsync(cancellationToken);
    }
}

StopAsync's token is scoped to this one service — ApplicationStopping is the app-wide signal any component can listen to instead.

🌍 Real-world example ▾

Pods keep getting killed with "work still in progress" errors during a rolling deployment. That's almost always ApplicationStopping cleanup running longer than the pod's configured grace period. The fix is either to shorten the cleanup work, extend the grace period in the deployment manifest, or make the cleanup itself cancellation-aware instead of relying on a blind wait.
