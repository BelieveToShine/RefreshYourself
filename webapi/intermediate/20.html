Where does the token live — XSS risk or CSRF risk?

"Where should a SPA store its JWT/refresh token?"

Why it matters ▾
💾 localStorage
❗ ProblemAny script on the page can read localStorage — your own code, a compromised package, or an injected script — so one XSS bug hands over the token.
✅ SolutionKeep long-lived tokens out of it; if you must use it, keep the token short-lived.
RecalllocalStorage = readable by any script.
🍪 HttpOnly cookie
❗ ProblemThe token needs a home that script can't read, but cookies are sent automatically — so another site can trick the browser into using it (CSRF).
✅ SolutionHttpOnly hides it from JavaScript; Secure and SameSite plus an anti-forgery token cover the CSRF side.
RecallHttpOnly cookie = hidden from script, needs CSRF defence.
🔥 Easy interview recall

localStorage → XSS reads it

HttpOnly cookie → CSRF is the risk

BFF → no token in the browser

Think: XSS steals from storage. CSRF abuses cookies. A BFF leaves nothing to steal.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 The strongest option — keep tokens on a server you own
⚠️ Common Trap

"HttpOnly makes XSS harmless." It only stops script from reading the cookie — injected script can still send requests as the logged-in user, so fixing XSS still comes first.

🔄 Likely Follow-up

"So how do you protect the cookie from CSRF?" Set SameSite on it (Lax or Strict), keep it Secure, and require an anti-forgery token on requests that change state.

🎯 Say this in the interview — the exact lines to land

"I wouldn't keep a long-lived token in localStorage — one XSS bug leaks it. An HttpOnly, Secure, SameSite cookie keeps it away from JavaScript, but then I need CSRF protection, and a BFF is the strongest option because the tokens never reach the browser."

  • localStorage → any script can read it, so one XSS bug leaks the token.
  • HttpOnly cookie → JavaScript can't read it, but the browser sends it automatically.
  • Cookie flags → HttpOnly + Secure + SameSite, plus an anti-forgery token.
  • Common middle path → short-lived access token in memory, refresh token in an HttpOnly cookie.
  • Strongest → a BFF that keeps the tokens server-side.
  • No storage choice saves you from XSS — fix XSS first.
📖 Explanation ▾

A single-page app has to keep a token somewhere between page loads. localStorage is easy, but any JavaScript running on your page can read it — your own code, a compromised package, or a script injected through an XSS bug. A stolen token works from the attacker's own machine until it expires.

An HttpOnly cookie can't be read by JavaScript at all, so XSS can't copy the token. The price: the browser attaches the cookie to requests on its own, which opens the door to CSRF — another site tricking the browser into sending a request. Counter it with SameSite, the Secure flag (HTTPS only), and an anti-forgery token on requests that change state. HttpOnly still doesn't make XSS harmless: injected script can call your API from inside the victim's page — it just can't carry the token away.

A common middle path keeps a short-lived access token in memory and the refresh token in an HttpOnly cookie (see JWT & Refresh Tokens). The most locked-down option is a BFF (see API Gateway & BFF): a small server that keeps the tokens and gives the browser only a session cookie.

💻 See the code ▾
C# 
Response.Cookies.Append("refresh_token", token, new CookieOptions
{
    HttpOnly = true,
    Secure = true,
    SameSite = SameSiteMode.Strict,
    Expires = DateTimeOffset.UtcNow.AddDays(7)
});

HttpOnly hides it from JavaScript, Secure keeps it on HTTPS, SameSite is the first line of CSRF defence.

JavaScript 
await fetch("https://api.example.com/orders", { credentials: "include" });

The browser attaches the cookie for you — the SPA code never touches the token. A cross-origin call also needs the API's CORS policy to allow credentials (see CORS).

🌍 Real-world example ▾

localStorage is a house key under the doormat — anyone who reaches the porch can pick it up. An HttpOnly cookie is a doorman who holds the key and lets you in when you walk up — but a trickster can walk you to the door too (CSRF).

Scenario: a React SPA calls your API. Instead of storing the JWT, the team puts a small BFF in front: the browser gets only a session cookie, and the BFF attaches the access token when it calls the API.
