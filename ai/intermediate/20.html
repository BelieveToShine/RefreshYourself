Context engineering — the window is a budget, and memory lives outside it

"A chat gets long — what do you keep in the context window, and how do you give the bot memory across sessions?"

Why it matters ▾
🧳 Context & Memory
❗ ProblemThe model only sees what you put in the window this turn, and the window has a limit. Send everything and it gets slow, costly and noisy; send too little and the bot forgets what the user just said.
✅ SolutionTreat the window as a budget you fill on purpose each turn: instructions, the best few retrieved chunks, tool results and recent turns. Squeeze older turns into a summary, and keep facts that must last in an external memory store you retrieve from.
RecallWindow = this turn's budget. Memory = a store outside it.
🔥 Easy interview recall

Context engineering = "choose what goes in each turn; keep the rest outside."

Think: Short-term memory → the chat inside the window Long-term memory → facts saved outside, retrieved when relevant

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just use the biggest window and send everything." A bigger window still costs more and runs slower on every call, can bury the useful lines in noise, and forgets everything when the session ends — long-term memory needs a store, not a bigger window.

🔄 Likely Follow-up

"How do you stop a summary from losing important details?" Don't summarize everything. Pin the instructions and the user's stated constraints outside the summary, summarize only the older turns, and save durable facts as small structured records.

🎯 Say this in the interview — the exact lines to land

"The context window is a budget, not a bucket. Each turn I decide what goes in: the instructions, the few most relevant retrieved chunks, tool results and recent turns. Older turns get trimmed or summarized, and anything that must survive across sessions goes into an external memory store that I retrieve from when it's relevant."

  • Rebuilt every turn → most chat APIs are stateless, so the model sees only what you send.
  • Short-term memory → the conversation inside the window.
  • Long-term memory → facts saved outside (a database or vector store) and retrieved when relevant.
  • Overflow → trim the oldest turns or roll them into a summary — and pin anything that must not be lost.
  • Memory is user data → keep it per user, let it be corrected or deleted, and don't store secrets.
📖 Explanation ▾

Most chat APIs are stateless: the model remembers nothing between calls, so "memory" is just what your app puts back into the window. Context engineering is choosing that content well — the instructions, the best few retrieved chunks, tool results and the recent turns — inside a fixed token budget. Put stable parts, like instructions, first. Details and size limits are on Tokens & Context Window and Context-Window Tricks.

When the chat outgrows the budget you have three tools. Trim the oldest turns (simple, but it forgets). Summarize them into a short rolling note (keeps the gist, can lose detail). Retrieve only the past facts that matter right now. Models can also pay less attention to material buried in a very long window, so less and better beats more.

Long-term memory is a store outside the window — a database or vector store — holding facts like "prefers short answers". The app, or the model through a tool, saves them; at the start of a turn you retrieve the relevant ones. Treat them as user data: keep them per user, allow correction, and watch for stale or wrong entries. The rules that keep each user's data separate are on Multi-Tenant Retrieval Isolation, and layered instructions on Prompt Layering.

💻 See the code ▾
JSON 
{
  "user_id": "user-123",
  "fact": "prefers short answers",
  "source": "said in chat",
  "updated": "2026-01-15"
}

One small record per fact — easy to search, correct or delete. The fields are an example shape, not a standard.

🌍 Real-world example ▾

A customer comes back to a support bot a week later. The bot doesn't replay the old chat — it pulls two saved facts ("on the Pro plan", "uses Windows") from its memory store into the window and carries on.
