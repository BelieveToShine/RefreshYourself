The String pool — same text, same object… or not?

"Why does "abc" == "abc" return true, but new String("abc") == "abc" return false?"

Why it matters ▾
🗄️ String Pool
❗ ProblemTwo == checks that look identical in code — "abc" == "abc" and new String("abc") == "abc" — return different answers, which looks like Java being inconsistent if you don't know why.
✅ SolutionString literals are stored in a special pool inside the heap, so identical literals share exactly one object. new String(...) always creates a separate object outside that pool — the two checks are comparing genuinely different situations, not behaving inconsistently.
RecallLiterals share the pool. new String(...) always opts out of it.
🔥 Easy interview recall

"abc" (literal) → shares the pool, == is true

new String("abc") → separate object, == is false

Think: literal → pool. new String(...) → always separate — compare content with .equals(), never ==.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"== on Strings is usually fine because most strings are literals." Any string built at runtime — user input, a value read from a file, string concatenation of non-constant values — is not guaranteed to be pooled, so code that only ever tested with literals can break the moment a real runtime string reaches the same comparison. Always use .equals() for content comparison.

🔄 Likely Follow-up

"How would you force a runtime-built String into the pool?" Call .intern() on it — it returns the pooled match if one already exists, or adds this string to the pool and returns it if not, so a subsequent == against a literal with the same content would then be true.

🎯 Say this in the interview — the exact lines to land

"String literals are stored in a shared pool inside the heap, so two identical literals point to the same object and compare equal with ==. new String(...) always creates a separate object outside the pool, so == against it is false even with identical content — which is exactly why String comparison should always use .equals()."

  • Literal pool → identical literals share one object, compile-time and runtime.
  • new String(...) → always bypasses the pool, a fresh object every time.
  • .intern() → manually pulls a string into the pool (or returns the existing match).
📖 Explanation ▾

Every time the compiler sees a string literal, it checks a special pool of strings living inside the heap (moved there from the old PermGen space as of Java 7). If an identical literal is already in the pool, the new reference just points at that existing object — nothing new gets created. That's why "abc" == "abc" is true: both variables hold a reference to the exact same pooled object.

new String("abc") explicitly asks for a brand new object, so it deliberately skips the pool — even though its content is identical, it lives at a different address. == compares addresses (identity) for reference types, so it correctly reports false.

.intern() is the manual escape hatch: call it on any String and it returns the pool's existing match for that content, adding it to the pool first if no match exists yet. After interning, comparing the result to an equivalent literal with == is true.

💻 See the code ▾
Java 
String s1 = "abc";
String s2 = "abc";
System.out.println(s1 == s2);            // ✅ true — same pooled object

Both literals resolve to the exact same object already sitting in the pool.

Java 
String s3 = new String("abc");
System.out.println(s3 == s1);             // ❌ false — a separate heap object
System.out.println(s3.equals(s1));        // ✅ true — same content

new String(...) always makes a fresh object — compare content with .equals(), not ==.

Java 
String s4 = s3.intern();
System.out.println(s4 == s1);             // ✅ true — now pulled into the pool

.intern() manually pulls a runtime string into the pool, or returns the existing match.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two literals, anywhere in your code, with the same text

Status codes, config keys, hardcoded labels — compared with == by habit, and it happens to work because both sides are literals sharing the pool. This is the #1 case that makes people think == is fine for strings.

RememberTwo literals → pool makes == look safe, but don't rely on it.
2 A string built from user input or file/network data

Anything read at runtime — console input, a database row, a parsed JSON field — is never guaranteed to be the pooled object, even if its text matches a literal exactly. Always compare it with .equals().

RememberRuntime-built text → never assume it's pooled.
3 Code that "worked" with == suddenly breaks

role read from a database row isn't the pooled "ADMIN" object, even though it says "ADMIN" — == returns false with no error at all, just a wrong decision made quietly.

RememberA runtime string entering an == check → the classic silent bug.
🌍 Real-world example ▾

The pool is a shared bulletin board, not a filing cabinet. Two people pinning up a note that says "Lunch at noon" can point at the exact same pinned note instead of each printing their own copy — that's two literals sharing the pool. Photocopying your own note with the same words written on it is new String(...): it reads identically, but it's a different piece of paper.
