this — decided at the call site, never where the function was written

"What does this refer to in JavaScript, and how do call, apply, and bind change it?"

Why it matters ▾
  • The single most common "explain this output" question in JS interviews — a method handed off as a callback and losing this is a real, everyday bug, not a trick question.
  • Every framework/library convention around binding methods (class fields, .bind(this) in a constructor, arrow-function class methods) exists purely to work around this one rule.
  • Almost always followed immediately by "what does an arrow function do differently?" — treat the two as one topic, because interviewers do.
🔥 Easy interview recall

Plain call foo() → undefined (strict) / global object

Method call obj.foo() → the object before the dot

new Foo() → the new instance

call/apply/bind → whatever you pass in

Think: a regular function's this is decided by how it's called, every single time. An arrow function has no this of its own — it just borrows whatever this already means where it was written, exactly like a closure borrows a variable.

⚠️ Common Trap

"Arrow functions bind this to the object" is not quite right. An arrow function doesn't bind this to anything — it has no this slot at all, so it just reads whatever this already means in the surrounding code where it was defined.

🔄 Likely Follow-up

"Can you change what this means inside an arrow function with call?" No — call/apply/bind only affect functions that read this from their own call site; an arrow function ignores the this argument entirely and keeps its lexical one.

🎯 Say this in the interview — the exact lines to land

"A regular function's this is determined entirely by its call site, not where it's defined — plain call gives undefined or the global object, a method call gives the object before the dot, new gives the new instance, and call/apply/bind set it explicitly. An arrow function has no this of its own — it lexically inherits this from whichever scope it was defined inside, the same way a closure captures a variable."

  • call(thisArg, a, b) invokes immediately, args listed individually.
  • apply(thisArg, [a, b]) invokes immediately, args as one array.
  • bind(thisArg) returns a brand-new function, doesn't call it — permanently locked to that this.
  • Call-site, not definition-site — the same function can have a different this every time it's called.
  • Arrow functions have no this of their own — they inherit it lexically, like a closure inherits a variable.
📖 Explanation ▾

In JavaScript, this is not fixed to a function when it's written — it's a value re-decided every time the function is called, based on how it was called. The same function assigned to a variable, called as a method, and called with new can have three completely different this values, because none of those differences live in the function's own code — they live entirely at the call site.

call() and apply() both invoke the function right away with an explicit this you supply — the only difference is how the remaining arguments are passed: call lists them one by one, apply takes them as a single array. bind() is different in kind, not just in argument shape: it doesn't call the function at all — it returns a new function, permanently wired to the this you gave it, that you can call (or hand off) later.

Arrow functions don't participate in any of this. A regular function has a this binding that its own call site fills in; an arrow function simply has none — when its body reads this, JavaScript looks it up the same way it looks up any other outer variable, walking out to the nearest enclosing scope that does have one. That's why an arrow function defined inside a method keeps that method's this even when called later as a detached callback, while a regular function in the same spot doesn't.

💻 See the code ▾
JavaScript 
function greet(greeting) { return `${greeting}, ${this.name}`; }
const ctx = { name: "Sam" };

greet.call(ctx, "Hi");              // runs now, args listed individually
greet.apply(ctx, ["Hi"]);           // runs now, args as one array

const greetSam = greet.bind(ctx);   // does NOT run yet —
                                     // returns a new function, this locked to ctx
greetSam("Hi");                    // ✅ called later, this is still ctx

Same function, same explicit this — call/apply run it immediately; bind hands back a new function that hasn't run yet.

JavaScript 
class Timer {
  seconds = 0;
  start() {
    setTimeout(function() {
      this.seconds++;               // ❌ this is NOT the Timer here
    }, 1000);                       // plain call rule — this is undefined
  }
}

The classic bug: a regular function passed as a callback gets a brand-new this from its own (plain) call — it's not the Timer instance anymore.

JavaScript 
class Timer {
  seconds = 0;
  start() {
    setTimeout(() => {
      this.seconds++;               // ✅ this is still the Timer instance
    }, 1000);                       // arrow has no own this — inherits start()'s
  }
}

The fix: swap in an arrow function — it has no call site of its own, so it keeps reading this from start(), where it was written.

🌍 Real-world example ▾

Think of this as "whoever handed me the phone," not a name printed on the phone itself. The same phone (function) answers differently depending on who's holding it when it rings — hand it off with bind and it's permanently wired to call back the same person no matter who picks it up next.
