Immutable objects — safe to share across threads, by design

"What actually makes an object immutable, beyond just 'no public setters'?"

Why it matters ▾
  • A natural follow-up to "what is immutability" — it probes whether you know the surface API (no setters) isn't the same as the real guarantee.
  • Shared config objects, cache entries, and value objects passed between threads all lean on this to skip locking entirely.
  • An easy way to look sloppy: calling a readonly List<T> field "immutable" when the list itself can still be changed.
🔥 Easy interview recall

Immutable = "every field set once at construction, then frozen — including whatever it points to."

Think: a readonly List<T> freezes the reference, not the list inside it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It's readonly, so it's immutable." A readonly List<T> field can never be reassigned to a new list, but the list it points to can still be cleared, sorted, or added to — the reference is frozen, not the contents.

🔄 Likely Follow-up

"So why does immutability specifically help with multi-threaded code?" An immutable object can be freely shared across threads with zero locking, because no thread can ever observe a partial or changing state.

🎯 Say this in the interview — the exact lines to land

"An object is truly immutable only when every field is set once at construction and never changes afterward — including any mutable object it holds a reference to. A readonly field just freezes the reference itself, not what it points to."

  • Truly immutable → every field frozen after construction, not just missing setters.
  • readonly List<T> → the reference is frozen, but the contents are still mutable.
  • Multi-threaded code → no lock needed to read an immutable object, because its state can't change under a reader.
  • Reach for it for shared config, cache entries, and value objects passed between threads.
📖 Explanation ▾

No public setters only proves the field can't be reassigned from outside the class — it says nothing about what happens if that field holds a reference type. A List<T>, an array, or any other mutable object can still be changed through the exact same reference, because Add, Sort, and Clear aren't reassignments at all.

Real immutability means the entire object graph is frozen, not just the outer field — either by only exposing value types and other immutable objects, or by handing back a read-only view backed by a private copy the caller can never reach.

That's exactly why it matters for threads: a lock exists to stop one thread from reading state while another is mid-write. If nothing can ever write again after construction, there's no unsafe moment left to protect against — the lock has nothing left to do.

💻 See the code ▾
C# 
public class Order
{
    public readonly List<string> Items = new();   // ❌ looks immutable — isn't
}

var order = new Order();
order.Items.Add("Widget");   // ✅ compiles — Items was never reassigned

readonly only stops Items from being pointed at a new list — it never stops the list it already points to from changing.

C# 
public sealed class Order
{
    public Order(IEnumerable<string> items) =>
        Items = items.ToList().AsReadOnly();

    public IReadOnlyList<string> Items { get; }   // ✅ no way back in to mutate
}

A private copy behind an IReadOnlyList<T> closes exactly the door the previous example left open.

C# 
var config = new Config(timeoutMs: 30_000);   // built once, never touched again

Task.Run(() => Use(config));   // Thread A reads config
Task.Run(() => Use(config));   // Thread B reads config — no lock needed

Because config can never change after construction, both threads can read it at the same time with zero synchronization.

🌍 Real-world example ▾

Your service caches a shared Config object read by every request-handling thread, with no locking anywhere near it. That's safe only as long as Config is truly immutable — every thread sees a fully built instance and nothing can modify it after that. It stops being safe the moment Config exposes a mutable collection or field underneath its "immutable" surface.
