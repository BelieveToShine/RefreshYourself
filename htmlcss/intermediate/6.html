Responsive Design — it works at both extremes, so why does 768px break?

"What is responsive design, and what techniques do you actually use to make a layout adapt across screen sizes?"

Why it matters ▾
📱 Mobile-first
❗ ProblemLoading a full desktop-sized layout as the base styles wastes work on a low-powered phone that never needed most of that complexity in the first place.
✅ SolutionMobile-first writes the simplest, smallest layout as the plain base styles — no query needed — then min-width queries layer on more complexity only as the screen gets bigger.
RecallMobile-first = simplest layout is the base; min-width adds complexity as it grows.
🖥️ Desktop-first
❗ ProblemMobile-first only helps if the base styles start out simplest; a site already built as one full desktop layout doesn't have that simple base to start from.
✅ SolutionDesktop-first keeps the full, most complex layout as the base styles, then max-width queries strip that complexity back down as the screen shrinks.
RecallDesktop-first = full layout is the base; max-width strips complexity away as it shrinks.
🔥 Easy interview recall

Mobile-first → start simple, add with min-width

Desktop-first → start complex, strip with max-width

Think: Breakpoints are just @media rules that reshape the SAME content — a real breakpoint is wherever THIS content breaks, not a number copied off a device chart.

⚠️ Common Trap

Breakpoints are not a fixed list of device widths. 768px/1024px are common starting points, but the right breakpoint is wherever THIS content actually starts to look wrong — not a number copied off a device chart.

🔄 Likely Follow-up

"Isn't there a newer way to do this than viewport media queries?" Yes — container queries size an element based on its own containing element instead of the whole viewport, which matters for a reusable component that needs to look right in differently-sized spots on the same page. That's a deep enough topic on its own to get its own page.

🎯 Say this in the interview — the exact lines to land

"Responsive design means one layout that reshapes itself across screen sizes using CSS — media queries, flexible units, and images that scale — instead of a separate site per device. I build mobile-first: write the simplest, stacked layout first, then add complexity with min-width media queries as the viewport grows, and I pick breakpoints from where the actual content breaks, not a fixed device-size list."

  • Mobile-first → base styles are the simplest layout; min-width queries add complexity, never strip it away.
  • Fluid layout → percentages, fr, and flex instead of fixed pixel widths, so the layout itself can stretch between breakpoints.
  • Flexible images → max-width: 100% stops an image from overflowing its container; object-fit controls how it crops inside a fixed-size box.
  • Responsive type → clamp(min, preferred, max) lets font size scale smoothly between two limits instead of jumping at each breakpoint.
  • Debugging a breakpoint bug → resize through the actual range to find the real failing width, then check for a gap/overlap between two @media rules or a fixed-width element that never shrank.
📖 Explanation ▾

A media query — @media (min-width: 768px) { ... } — applies a block of CSS only when a condition about the viewport (usually its width) is true. There are two ways to organize a whole stack of them. Mobile-first writes the simplest, smallest layout as the plain base styles, then uses min-width queries to layer on more complexity as the screen gets bigger. Desktop-first does the opposite: the base styles are the full desktop layout, and max-width queries strip complexity back down as the screen shrinks. Mobile-first is the more common default today, partly because it naturally matches how much CSS a small, low-powered device actually has to load and apply first.

Mobile-firstDesktop-first
Starting layoutSimplest, smallest layoutFull, most complex layout
Query directionmin-width — add as it growsmax-width — strip as it shrinks
Base styles apply toEvery screen, until told otherwiseOnly large screens, until told otherwise

Breakpoints — the widths where those queries kick in — are only a starting point, never gospel. Common numbers like 768px or 1024px are worth knowing because they roughly match common device sizes, but the breakpoint that actually matters is wherever a specific piece of content starts to look wrong, which is often a number nobody put on a device chart. On top of the breakpoints themselves, a layout needs to be fluid between them — percentages, fr (in Grid), and flex instead of fixed pixel widths, so it stretches smoothly rather than jumping between a few hardcoded sizes. Flexible images use max-width: 100% so an image never overflows its container, with object-fit controlling how it crops inside a fixed-size box. Responsive typography uses clamp(min, preferred, max) to scale a font size smoothly with the viewport instead of snapping to a new value at every breakpoint. Responsive navigation usually means collapsing a full nav bar into a hamburger menu below some width — same links, a different interaction pattern for a narrow screen. Container queries are a newer alternative to all of this for one specific case — sizing by a component's own container instead of the viewport — covered on their own page.

The 768px bug in the diagram below is exactly what happens when this system has a hole in it. Media queries don't have to tile the width axis perfectly — nothing stops someone from writing @media (max-width: 767px) for the mobile layout and @media (min-width: 900px) for the desktop layout, leaving 768px–899px covered by neither rule. A width landing in that gap gets whichever styles were never meant to be final on their own, which is a very different bug from "the CSS is wrong" — the CSS at each end is fine, there's just a range nothing was ever written for. A fixed-width element (a hardcoded px width instead of a percentage or fr) causes the same visible symptom a different way: it can sit inside a working layout at both 375px and 1440px and still never actually shrink in between, because nothing tells it to.

🧠 Visual Mental Model — why 768px specifically breaks
💻 See the code ▾
CSS 
/* mobile-first: base = simplest layout, no query needed */
.grid { display: grid; grid-template-columns: 1fr; gap: 16px; }

@media (min-width: 768px) {           /* add: second column */
  .grid { grid-template-columns: 1fr 1fr; }
}

@media (min-width: 1200px) {          /* add: third column */
  .grid { grid-template-columns: 1fr 1fr 1fr; }
}

Base styles are the mobile layout. Each query only adds more columns as the viewport grows — it never redefines the base from scratch.

CSS 
.card img {
  max-width: 100%;   /* ✅ never wider than its container */
  height: auto;      /* keeps the image's aspect ratio */
  object-fit: cover; /* fills a fixed-size box without distorting */
}

max-width: 100% is the one rule that keeps an image from ever overflowing its container, at any width.

CSS 
h1 {
  font-size: clamp(1.5rem, 4vw + 1rem, 3rem); /* min, preferred, max */
}

clamp() lets the heading scale smoothly with the viewport between 1.5rem and 3rem — no separate font-size line needed at every breakpoint.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your layout looks right at 375px and 1440px but breaks around 768px

This is the classic gap-between-queries bug: one query's max-width and the next one's min-width don't actually meet, so a width landing between them gets neither rule's styles. Dragging through the whole range in devtools — not just checking the two known-good widths — finds the exact width where it first goes wrong.

RememberBreaks between two working widths → check for a gap between two @media ranges.
2 Every @media range is covered, but one element still looks wrong in between

A hardcoded px width on one element produces the exact same visible symptom as a query gap, for a completely different reason — it can sit fine inside a working layout at both ends and still never actually shrink in between, because nothing ever told it to. Swapping the fixed width for a percentage or fr fixes it.

RememberSame symptom, different bug — check for a fixed-width element too, not just a query gap.
3 The same component needs to look right in a wide column and a narrow sidebar

A viewport media query can't tell those two spots apart — they're on the same page at the same viewport width. Container queries size the component by its own containing element instead of the whole viewport, which is exactly the case a reusable component in more than one spot needs.

RememberSame component, different-sized spots → container queries, not a viewport media query.
🌍 Real-world example ▾

Scenario: "The page works at 1440px and 375px but breaks at 768px — how do you investigate?" Answer: Open devtools' responsive mode and actually drag through the range between 375px and 1440px instead of only checking the "known" breakpoints — find the exact width where something first looks wrong. Inspect that one element: is it overflowing its container, or overlapping another element? Then check the CSS causing it — either a gap or overlap between two @media ranges (one query's max-width and the next one's min-width don't actually meet), or a fixed-width element with a hardcoded px width that never got told to shrink between the two sizes that do work.
