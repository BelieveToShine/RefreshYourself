Lifecycle hooks — where does DOM code actually go?

"What are Vue's component lifecycle hooks, and where does DOM-dependent code go?"

Why it matters ▾
⏱️ Lifecycle Hooks
❗ ProblemCode that measures an element or initializes a third-party library needs the real DOM to already exist — run it one moment too early and it silently fails or crashes, because there's nothing there yet.
✅ SolutionVue's lifecycle hooks are named checkpoints in a component's life — onMounted specifically guarantees the real DOM is in place, giving DOM-dependent code one safe, well-known place to live.
RecallLifecycle hooks = named checkpoints; onMounted = "the DOM is ready now."
🔥 Easy interview recall

setup() → no DOM yet

onMounted → DOM guaranteed to exist

onBeforeUnmount → cleanup time

Think: DOM-dependent code → always onMounted, never setup()'s own top-level code.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reading a template ref's DOM element inside setup()'s own top-level code. It's still null there — refs only get populated by the time onMounted fires.

🔄 Likely Follow-up

"What's onBeforeMount actually for?" It's rare in practice — code that must run right before the first render but doesn't need the real DOM yet. onMounted covers the vast majority of real use cases.

🎯 Say this in the interview — the exact lines to land

"A Vue component moves through creation, mounting, updating, and unmounting, and the Composition API gives a hook for each point — onMounted, onUpdated, onBeforeUnmount, and so on. DOM-dependent code always goes in onMounted, because that's the first point the real DOM is guaranteed to exist."

  • onMounted → DOM guaranteed to exist, the default spot for DOM-dependent code.
  • setup()'s own top-level code → runs before mount, template refs are still null there.
  • onBeforeMount → rare — code that must run right before first render but doesn't touch the DOM.
  • Update hooks (onBeforeUpdate/onUpdated) fire on every reactive re-render, not just once.
📖 Explanation ▾

A component's life has four stages: create, mount, update, and unmount. The Composition API exposes a hook function for the start and end of each one — onBeforeMount/onMounted, onBeforeUpdate/onUpdated, and onBeforeUnmount/onUnmounted — each taking a callback that runs at that exact moment.

setup()'s own top-level code (or everything at the top level of <script setup>) runs before any of these hooks, while the component is still being built — there is no real DOM yet, so a template ref read at that point is null. onMounted is the first point that guarantees the real DOM exists, which is why it's where measuring an element, focusing an input, or handing a DOM node to a charting library all belong.

The update hooks aren't one-time events — beforeUpdate/updated fire every time reactive state used by the template changes and Vue re-renders, which can be many times over a component's life. The unmount hooks are the mirror image of mount: the last safe place to tear down anything the component set up for itself.

💻 See the code ▾
Vue 
const box = ref(null);
console.log(box.value);           // ❌ null — the DOM doesn't exist yet

onMounted(() => {
  console.log(box.value);         // ✅ the real <div> element
  box.value.focus();
});

The exact same ref read is null at the top of setup() and real inside onMounted — only the timing changed.

Vue 
let timerId;
onMounted(() => { timerId = setInterval(tick, 1000); });
onBeforeUnmount(() => { clearInterval(timerId); });  // cleanup, mirrors the setup

Anything started in onMounted (a timer, a listener, a subscription) is torn down in onBeforeUnmount to avoid leaking it.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to measure an element or hand it to a third-party library

A charting library, a map widget, or anything that needs a real element node has to wait for onMounted — handing it a ref any earlier means handing it null. This is the #1 scenario you'll actually run into.

RememberNeeds the real element → onMounted, not setup()'s own top-level code.
2 You start a timer, listener, or subscription that must be cleaned up

A setInterval, a window event listener, or a WebSocket subscription started in onMounted keeps running after the component is gone unless something stops it — onBeforeUnmount is that mirror-image cleanup point.

RememberAnything started in onMounted gets torn down in onBeforeUnmount.
3 You read a template ref right at the top of setup()

This is the classic trap: a template ref exists as a variable from the first line of setup(), but it doesn't point at a real element until Vue has actually mounted the component — reading .value before that always gives null.

RememberTemplate ref at top of setup() → always null. Wait for onMounted.
🌍 Real-world example ▾

Think of a building under construction. setup() is the architectural plan — detailed, but no walls exist yet. mounted is the inspection sign-off: only now can you walk in and actually measure a room. You wouldn't try to hang a picture on a wall that doesn't exist yet — that's exactly why DOM-dependent code waits for onMounted.
