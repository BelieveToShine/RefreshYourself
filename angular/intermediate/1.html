What are standalone components, and are NgModules still relevant now that they exist?

Why it matters ▾
🅰️ Standalone component
❗ ProblemWith an enclosing NgModule as the only source of context, figuring out "what can this template actually use" meant tracing through a separate module file — a real, often confusing extra layer of indirection.
✅ SolutionA standalone component sets standalone: true and lists its own dependencies directly in its own imports array — visible and local, no module required to exist first.
RecallStandalone = self-contained — imports live on the component itself.
📦 NgModule-based component
❗ ProblemA component that doesn't declare its own dependencies can't compile on its own — it needs somewhere else to supply them, or its template has no idea what it's allowed to use.
✅ SolutionAn NgModule's declarations/imports supplies that context instead — still fully supported, and a huge amount of production Angular code is built this way.
RecallNgModule-based = imports live in the module, not the component.

⚠️ Common Trap

"Standalone" doesn't mean a component has no dependencies. It means the component declares those dependencies itself, in its own imports array — a standalone component can and often does import several other things.

🔄 Likely Follow-up

"If I have an existing NgModule-based app, do I have to migrate everything to standalone before I can use any standalone component?" No — a standalone component can be imported directly into an NgModule's imports array, which is exactly why the official migration path is component-by-component, not a rewrite.

  • Self-contained → dependencies live on the component's own @Component decorator.
  • NgModule not removed → still supported, huge numbers of production apps still use it.
  • bootstrapApplication() skips the root module entirely — no AppModule needed to start the app.
  • Interop → a standalone component drops into an NgModule's imports, and vice versa — migration is incremental, not big-bang.
📖 Explanation ▾

An NgModule used to be the thing that decided what a component's template could use — its declarations made the component itself visible, and its imports pulled in whatever other components, directives, and pipes that template needed. Figuring out "what can this template actually use" meant tracing through the module it belonged to, a real, often confusing extra layer of indirection. A standalone component removes that layer: it sets standalone: true (the default in current Angular versions) and lists its own dependencies right there, in its own imports array — visible and local, not borrowed from a separate file.

NgModules haven't been removed or deprecated — they're still fully supported, and a huge amount of production Angular code is built on them. What changed is the ecosystem's default: new apps and the CLI itself now lean standalone-first. The two are designed to interoperate, which is what makes an incremental migration possible — a standalone component can sit inside an NgModule's imports array, and an NgModule-based component can still be used inside a standalone component (through the module it belongs to). Angular also ships an official schematic, ng generate @angular/core:standalone, to help automate that conversion.

💻 See the code ▾
TypeScript 
@Component({
  selector: 'app-user-card',
  standalone: true,                           // default in current Angular
  imports: [CommonModule, RouterLink],       // its OWN template deps, listed here
  templateUrl: './user-card.component.html'
})
export class UserCardComponent {}

No NgModule anywhere — this imports array is the complete list of what the template needs.

TypeScript 
bootstrapApplication(AppComponent, {
  providers: [
    provideRouter(routes),      // replaces RouterModule.forRoot(routes)
    provideHttpClient()         // replaces HttpClientModule
  ]
});

Older NgModule apps instead call platformBrowserDynamic().bootstrapModule(AppModule) — bootstrapApplication skips the root module entirely.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're starting a brand-new Angular project today

The CLI scaffolds the project standalone-first, and bootstrapApplication(AppComponent, ...) skips the root module entirely — no AppModule needed to start the app. This is the path most new Angular code takes today.

RememberNew project today → standalone by default, no AppModule needed.
2 You have an existing NgModule-based app and want to drop in one new standalone component

A standalone component can be imported directly into that NgModule's imports array — it works immediately, with no rewrite of the existing module structure required.

RememberStandalone component → drops straight into an NgModule's imports array.
3 You're migrating an existing NgModule-based codebase toward standalone, piece by piece

Angular ships an official schematic, ng generate @angular/core:standalone, that helps convert components one at a time — migration happens component-by-component, not as a single big-bang rewrite.

RememberMigrating? → ng generate @angular/core:standalone, one component at a time.
🌍 Real-world example ▾

An employee who packs their own toolbox vs. one whose toolkit is decided by their department. An NgModule-based component is like an employee whose tools come from whichever department (module) they're assigned to. A standalone component packs its own toolbox directly — more visible and portable, and easier to move to a different team without renegotiating what's in the shared supply closet.
