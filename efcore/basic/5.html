N+1 — it worked with 3 rows, it won't work with 10,000

"What is the N+1 problem, and how does it show up with EF Core specifically?"

Why it matters ▾
  • Shows up the moment lazy loading is on and a navigation property is touched inside a loop.
  • Passes every test against a small seed dataset, then floods the database the moment real data shows up.
  • A near-guaranteed interview opener for anyone who's touched an ORM — expect a follow-up right behind it.
🔥 Easy interview recall

N+1 = "1 query for the list, plus N more — one per row — hiding inside a loop."

Think: 1 Customers query becomes 1 + N Orders queries the instant something inside the loop touches .Orders.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"My query log looked fine, so there's no N+1 here." A log with 3-5 extra lines during testing is exactly what N+1 looks like at small scale — the bug doesn't grow more queries once the row count grows, it was already there, just easy to miss.

🔄 Likely Follow-up

"How would you actually catch this before it reaches production?" Log or count queries during development, add an integration test that asserts the number of round trips for a given operation, and treat a navigation property touched inside a loop over its parents as a code-review flag.

🎯 Say this in the interview — the exact lines to land

"N+1 means fetching a list of N parent rows in one query, then triggering N more separate queries — one per parent — because a navigation property gets touched inside the loop instead of being fetched up front. It's invisible with a handful of test rows and expensive at real scale."

  • Total round trips = 1 + N, no matter how small N looks in a demo.
  • Catch it with query-count checks in tests, and by flagging a navigation property accessed inside a loop during review.
  • EF Core's fix for this shape is Include() — covered in full in Loading Strategies, not on this page.
📖 Explanation ▾

N+1 is a shape, not one specific bug: 1 query fetches a list of N parent rows, then something inside a loop over that list fires N more queries — one per row — instead of one. With EF Core specifically, this happens when lazy loading is turned on: the context hands back proxy objects, and the first time code inside the loop touches a navigation property (like customer.Orders), that single property access quietly sends its own separate query to the database.

The dangerous part isn't the mechanism — it's the scale. Nothing about the code changes between a demo and production; only the row count does.

Small test data (N=3)Production data (N=10,000)
Total round trips4 (1 + 3)10,001 (1 + 10,000)
Shows up in a quick glance at the log?Easy to miss — looks like 3 harmless extra linesImpossible to miss — requests queue up or time out
What actually changed in the code?Nothing — same loop, same statementNothing — only the row count grew

EF Core has a built-in fix for exactly this shape — fetching the related data up front instead of one row at a time — but that's its own topic with its own trade-offs, covered in Beyond N+1 and in the dedicated loading-strategies page linked above. This page's job is just to recognize the N+1 shape the moment it shows up.

💻 See the code ▾
C# 
var customers = context.Customers.ToList();   // 1 query — N Customers

foreach (var c in customers)
{
    var orderCount = c.Orders.Count;        // ❌ 1 extra query, every single time
    Console.WriteLine($"{c.Name}: {orderCount}");
}
// 3 customers      → 4 queries total (barely visible)
// 10,000 customers → 10,001 queries total (the outage)

Same loop, same code — only the customer count decides whether this is invisible or catastrophic.

C# 
var customers = context.Customers
    .Include(c => c.Orders)                  // 👉 fetch related data up front
    .ToList();                                // ✅ 1 query total, not N+1

foreach (var c in customers)
    Console.WriteLine($"{c.Name}: {c.Orders.Count}");  // no extra query — already loaded

Include() is the fix — see Eager vs. Explicit vs. Lazy Loading and Beyond N+1 for how it actually works.

🌍 Real-world example ▾

An endpoint that lists customers with their order counts works fine in every demo and every test run. Then support reports it's timing out for real traffic. Nothing in the code changed — the customer table just grew from 20 rows to 40,000, and the same loop that was quietly firing 21 queries is now firing 40,001.
