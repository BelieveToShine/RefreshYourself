A hot partition means the key, not the table, is throttled

"What causes a hot partition in DynamoDB, and how do you design around it?"

Why it matters ▾
  • Checks whether you understand that DynamoDB's scaling story lives at the partition level, not just the table's headline capacity number.
  • Comes up any time a "why is my table throttling even though I over-provisioned it" story is discussed, or any NoSQL data-modeling question.
  • A common opener before a deeper question about GSIs, LSIs, or capacity modes.
🔥 Easy interview recall

Hot partition = "a partition key with too few distinct values."

Think: userId spreads traffic evenly across many keys — status crowds almost everything onto the same few values.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Plenty of provisioned capacity means no throttling." A low-cardinality key like a fixed status field crowds nearly all traffic onto the same few physical partitions — that one partition throttles no matter how much capacity the table as a whole has provisioned.

🔄 Likely Follow-up

"GSI vs. LSI — when do you actually need an LSI?" Only when you need strong consistency on an alternate sort order and can commit to that index at table-creation time — a GSI covers almost every other "query by a different attribute" need and is far more flexible, since it can be added anytime.

🎯 Say this in the interview — the exact lines to land

"A hot partition comes from a low-cardinality partition key — high cardinality plus a matching access pattern is the fix."

  • GSI → flexible, add anytime, eventually consistent, own partition/sort key; LSI → same partition key, needs strong consistency, must exist at table creation.
  • Partition key → decides physical placement; add a sort key to store related items together under one partition key, sorted — together that's a composite key.
  • On-demand → auto-scales and bills per request; provisioned capacity is cheaper at steady, predictable volume.
  • High cardinality plus a matching access pattern fixes a hot key — raising table-level capacity does not.
📖 Explanation ▾

DynamoDB is a managed NoSQL key-value/document database. The partition key is what DynamoDB actually hashes to decide which physical partition an item lives on — it's the single biggest lever over how evenly traffic spreads. A sort key lets several related items share one partition key while staying individually addressable and sorted; partition key + sort key together is a composite key. A hot partition happens when a disproportionate share of requests target the same partition key value — that one physical partition throttles on its own, regardless of how much capacity the table overall has.

A GSI (Global Secondary Index) is a different partition/sort key combination for querying by an alternate access pattern — it can be added or removed at any time and is eventually consistent. An LSI (Local Secondary Index) keeps the same partition key but a different sort key, has to be declared when the table is created, and is the only one of the two that supports strongly consistent reads.

Capacity modes are a separate choice: on-demand auto-scales and bills per request, while provisioned capacity requires specifying read/write capacity units up front — cheaper when volume is steady and predictable, but it's still per-partition capacity underneath, which is exactly why provisioning more of it doesn't fix a hot key.

💻 See the code ▾
JSON 
{
  "userId": "u123",   // partition key
  "orderId": "o456",  // sort key
  "total": 82.50
}

userId decides which partition this item lands on; orderId just sorts items within that same partition key.

🌍 Real-world example ▾

An orders table partitioned by userId lets each customer's order history be a fast, single-partition query — spread naturally across as many partitions as there are customers. A global status partition key would do the opposite: nearly every "pending" order crowding onto the same hot partition.
