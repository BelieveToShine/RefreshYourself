GROUP BY — one row in, one row per group out

"What does GROUP BY actually do to the rows returned?"

Why it matters ▾
  • The mechanism behind almost every reporting query — "get the count/total per customer" only works because of this.
  • Explains a genuinely common error: "column X is invalid in the select list because it's not contained in an aggregate function or the GROUP BY clause."
  • Sets up aggregate functions and window functions — both build directly on what GROUP BY collapses.
🔥 Easy interview recall

GROUP BY = "collapse many rows sharing a value into one row per group."

Think: CustomerId 1, 1, 1, 2, 2 → GROUP BY CustomerId → just two rows out, each carrying an aggregate like COUNT(*).

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"You can SELECT any column alongside a GROUP BY, even one not in the group list." Standard SQL requires every non-aggregated column in SELECT to appear in GROUP BY — an engine that tolerates it anyway (some MySQL modes) just picks an arbitrary row's value for that column, which isn't the same as a valid, well-defined result.

🔄 Likely Follow-up

"Can you GROUP BY more than one column?" Yes — grouping by multiple columns creates one group per unique combination of those values, e.g. GROUP BY CustomerId, OrderMonth groups by each customer and month together.

🎯 Say this in the interview — the exact lines to land

"GROUP BY collapses every row that shares the same value in the grouped column(s) into a single output row per distinct group. Every column I select alongside it either has to be one of the grouped columns or wrapped in an aggregate — otherwise the database has no defined way to pick which row's value to show."

  • One row per group — CustomerId 1, 1, 1, 2, 2 becomes exactly two output rows.
  • Every non-aggregated SELECT column must appear in GROUP BY — standard SQL, no exceptions.
  • Group by more than one column → one group per unique combination, e.g. CustomerId + OrderMonth.
  • An engine that lets it slide is picking an arbitrary row's value, not producing a defined result.
📖 Explanation ▾

GROUP BY takes the rows a query would otherwise return and collapses every row that shares the same value in the listed column(s) into a single output row per distinct group. If five Orders rows have CustomerId values 1, 1, 1, 2, 2, grouping by CustomerId produces exactly two rows — one for customer 1, one for customer 2 — each free to carry an aggregate like COUNT(*), SUM(), or AVG() computed across just the rows in that group.

Because the engine keeps only one row per group, every column in the SELECT list needs one clear value for that whole group. Standard SQL enforces this literally: any selected column that isn't itself in the GROUP BY list has to be wrapped in an aggregate function, or the query is invalid — there's no "which row wins" ambiguity to resolve.

Grouping by more than one column groups by the unique combination of those columns together, not by each column independently — GROUP BY CustomerId, OrderMonth produces one row per customer-and-month pair, so the same customer can appear in several output rows, once per month they ordered.

💻 See the code ▾
SQL 
SELECT CustomerId, COUNT(*) AS OrderCount
FROM Orders
GROUP BY CustomerId;

One output row per distinct CustomerId — COUNT(*) counts how many raw rows collapsed into each one.

SQL 
SELECT CustomerId, OrderMonth, SUM(Amount) AS TotalAmount
FROM Orders
GROUP BY CustomerId, OrderMonth;   -- groups by the combination of BOTH columns

One row per customer per month, not per customer overall — the same customer can appear in several output rows.

🌍 Real-world example ▾

Sorting a pile of mixed coins into stacks by denomination. Once every coin is in its stack, you no longer see individual coins — you just report how many coins ended up in each stack. GROUP BY does the same thing to rows: after grouping, you get one summary row per group, not the original rows back.
