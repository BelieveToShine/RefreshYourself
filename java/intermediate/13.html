Try-with-Resources and AutoCloseable — automatic close(), no manual finally

"What does try-with-resources actually do, and what happens if both the body and close() throw?"

Why it matters ▾
🔒 Try-with-Resources
❗ ProblemClosing a resource — a file, a database connection, a socket — in a hand-written finally block is easy to get subtly wrong: a forgotten null-check before closing, a leaked resource on an early return, or a close() exception that silently replaces the real exception that caused the failure.
✅ Solution(Java 7+) Declaring any AutoCloseable resource in a try's own header gets its close() called automatically when the block exits, in reverse declaration order, with no hand-written finally — and if close() itself throws while another exception is already in flight, that close() exception is attached as suppressed instead of hiding the real failure.
Recalltry-with-resources = close() called for you, in order, exceptions kept not lost.
🔥 Easy interview recall

Try-with-resources = "close() called for you automatically, in reverse declaration order."

Think: body throws, close() throws too → the body's exception wins, close()'s becomes suppressed, not lost.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A close() exception doesn't replace or hide the body's exception. It's attached as a suppressed exception (visible via getSuppressed()), while the body's original exception remains the one actually thrown and caught.

🔄 Likely Follow-up

"What if only close() throws, and the body completes normally?" Then close()'s exception becomes the one that actually propagates — there's no suppression needed, because there's no competing exception from the body to protect.

🎯 Say this in the interview — the exact lines to land

"Try-with-resources (Java 7+) calls close() automatically on every AutoCloseable declared in the try header, in reverse declaration order, with no manual finally block. If both the body and close() throw, the body's exception propagates and close()'s exception is attached to it as a suppressed exception, not lost."

  • AutoCloseable in the header → close() called for you, automatically.
  • Multiple resources → closed in reverse declaration order.
  • Body and close() both throw → body's exception wins, close()'s is suppressed.
  • Suppressed exceptions → read via getSuppressed(), never silently dropped.
📖 Explanation ▾

Any type implementing AutoCloseable (a single abstract close() method) can be declared inside a try's own parentheses — try (Resource r = new Resource()) — instead of a separate variable above the block. When the block exits, for any reason at all, the JVM calls r.close() automatically, the same guarantee a manual finally block used to provide, without anyone having to write that block by hand.

Declaring more than one resource closes them in reverse order — the last one opened is the first one closed, mirroring how nested resources usually depend on each other (a Statement built from a Connection should close before the connection it came from).

The suppressed-exception behavior exists specifically so a failure during cleanup never erases the failure that caused the cleanup to run in the first place. The body's exception is what propagates and what a catch block actually sees; close()'s exception rides along on it, retrievable through Throwable.getSuppressed() whenever someone needs the full picture.

💻 See the code ▾
Java 
try (BufferedReader br = new BufferedReader(new FileReader(path))) {
    return br.readLine();
}  // ✅ br.close() called automatically — no finally written

No finally block anywhere — close() still always runs.

Java 
try (Connection conn = openConnection();
     Statement stmt = conn.createStatement()) {
    stmt.execute(sql);
}  // ✅ stmt.close() runs first, then conn.close() — reverse order

Multiple resources close in reverse declaration order, automatically.

Java 
try {
    try (Resource r = new Resource()) {
        throw new DataException();   // the body's exception
    }  // r.close() throws IOException here too
} catch (DataException e) {
    for (Throwable s : e.getSuppressed())   // ✅ IOException is in here
        System.out.println(s);
}

DataException is caught; close()'s IOException is attached, not lost.

🧭 Use Cases — recognize these when they happen to you ▾
1 Reading a file with a BufferedReader

This is the #1 scenario you'll actually run into. Any early return or thrown exception inside the block still triggers close() — there's no code path that leaks the file handle.

RememberFile/stream handling → always reach for try-with-resources.
2 Opening several related resources together, like a Connection and a Statement

Declaring several resources in one try header closes them in the exact reverse of their declaration order — the dependent resource closes before the one it depended on, automatically, with no manual nesting required.

RememberLast opened → first closed, every time.
3 The body throws AND close() throws in the same block

A developer who assumes the close() error is simply lost is wrong — it's attached to the body's exception as a suppressed exception, retrievable with getSuppressed() any time the full picture is needed.

RememberBoth throw → body wins, close()'s exception is suppressed, not dropped.
🌍 Real-world example ▾

JDBC code used to leak connections whenever an early return skipped a manual close() call sitting inside a hand-written finally block. Wrapping the Connection, Statement, and ResultSet declarations in a single try-with-resources header eliminates the leak entirely — every early return, every exception path, still closes all three, with no finally block left to forget.
