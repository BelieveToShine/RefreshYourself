Include vs. Projection Using Select — the whole graph, or just the shape you need

"Both Include and a Select projection can get you related data — what's the actual trade-off?"

Why it matters ▾
📦 Include
❗ ProblemYou need to actually change the related entity and save it back — a read-only shaped DTO has nothing a SaveChanges() call could update.
✅ SolutionInclude loads the entire related entity, tracked by default, so it's ready to be modified and saved exactly like any other tracked entity.
RecallInclude = the whole graph, tracked, ready to edit.
🎯 Select projection
❗ ProblemA read-only page that only shows a book's title and author name still pays for every column on both entities, plus change-tracking overhead, if it loads the full graph through Include.
✅ SolutionA Select projection names only the fields actually used, fetches nothing else, and is untracked by construction — no wasted columns, no tracking cost.
RecallSelect projection = only the shape you asked for, untracked.
🔥 Easy interview recall

Include → whole entity graph, tracked

Select projection → named fields only, untracked

Think: Include hands you the real, editable object. Select hands you just the shape you asked for.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Include doesn't always produce exactly one SQL query. Split-query configuration and multiple collection Includes on the same root entity can each add their own separate query — one query is the common case, not a guarantee.

🔄 Likely Follow-up

"Is the related entity tracked by default when you use Include?" Yes — it comes through the same tracked DbContext unless you've called AsNoTracking(). A Select projection is untracked regardless, because it's never mapped back to a real entity type.

🎯 Say this in the interview — the exact lines to land

"Include loads the entire related entity graph — every column, tracked by default. A Select projection fetches only the fields I name into a shaped DTO — narrower, usually faster, and untracked by construction. I reach for Include when I need to edit and save the related entity, and for Select when I only need a shape to display."

  • Include → whole graph, every column, tracked.
  • Select projection → only the named fields, untracked DTO.
  • Include isn't guaranteed one query → split-query config or multiple collection Includes can add more.
  • Editing the related entity afterward → needs Include's tracked entity, not a projection.
📖 Explanation ▾

Include tells EF Core to eagerly load a navigation property as a real, tracked entity of its actual type — every column comes along, whether the code uses it or not, because the result still has to be a complete, update-ready Author (or whatever the navigation points to). The LINQ-shape mechanics of Include/ThenInclude themselves, and how they compare to explicit and lazy loading, already have their own page — see "Eager vs. Explicit vs. Lazy Loading" in the EF Core track.

A Select projection never materializes a real Author at all — it builds a brand-new shape (an anonymous type or a named DTO) containing only the properties named inside the lambda. Because that shape isn't an entity EF Core's change tracker recognizes, it's untracked automatically — there's no tracked object to accidentally edit and no tracking overhead to pay for.

Neither option is the "correct" default — the decision is what happens to the result afterward. A page that will call SaveChanges() on the related data needs the real tracked entity Include provides. A page that only displays a few fields is better served by a projection sized exactly to what it uses.

💻 See the code ▾
C# 
Book book = context.Books
    .Include(b => b.Author)        // ✅ real, tracked Author entity
    .First(b => b.Id == id);

book.Author.Name = "Updated Name";  // editing a tracked entity
context.SaveChanges();                  // works — it's tracked

book.Author is a real, tracked Author — every column loaded, ready to be modified and saved.

C# 
BookDto dto = context.Books
    .Select(b => new BookDto
    {
        Title = b.Title,               // ✅ only these two fields
        AuthorName = b.Author.Name      // ✅ ever leave the database
    })
    .First(b => b.Id == id);

dto is a plain shape with no tracked entity behind it — nothing about it can be saved back, and nothing extra was ever fetched.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to edit the related entity and save the change

Include is the right call here — a Select projection would hand back a shape with nothing for SaveChanges() to recognize and persist.

RememberNeed to save the related data → Include, not a projection.
2 A read-only page only shows two or three related fields

Loading the full Author entity through Include here would fetch and track columns the page never reads — a projection sized to exactly what's displayed avoids that cost entirely.

RememberOnly displaying a few fields → Select, not Include.
3 One query has multiple collection Includes on the same root entity

Assuming "one Include, one query" still holds once a second collection Include joins the chain is the exact trap above — the real query count depends on EF Core's split-query behavior, not a fixed rule.

RememberMultiple collection Includes → check the actual query count, don't assume one.
🌍 Real-world example ▾

A book details page only needs to show the title and the author's name. Loading it through Include(b => b.Author) pulls and tracks every column on the full Author row for a page that will never call SaveChanges(). A Select projection naming just Title and Author.Name fetches exactly what the page renders — nothing tracked, nothing extra.
