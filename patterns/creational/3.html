Builder — assemble it step by step, not through a 10-parameter constructor

"What problem does the Builder pattern solve, and how is it different from a Factory?"

Why it matters ▾
🧱 Builder
❗ ProblemA constructor with many optional parameters (size, crust, toppings, extra cheese, gluten-free, …) forces every caller to pass a long positional argument list in exactly the right order — the "telescoping constructor" problem.
✅ SolutionBuilder separates step-by-step construction from the finished object: one method per optional piece, each returning the builder itself, so a caller chains only the steps it actually needs and calls Build() at the end.
RecallSame construction process, assembled one named step at a time.
🔥 Easy interview recall

Builder = "assemble it step by step, then call Build()."

Think: Builder → declares the steps (WithSize, AddTopping, …) ConcreteBuilder → implements them, accumulates the state Director → optional; most C# builders skip it and let the caller chain steps directly

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Builder is not just Factory with extra steps. A Factory returns a fully-built object in one call, usually picking among different types; a Builder assembles one object across multiple calls, usually the same concrete type, varying by which optional steps were invoked.

🔄 Likely Follow-up

"Can you name a real .NET API shaped like a Builder?" WebApplicationBuilder in ASP.NET Core — WebApplication.CreateBuilder(args) returns a builder, you chain configuration like builder.Services.AddControllers(), and builder.Build() produces the finished WebApplication.

🎯 Say this in the interview — the exact lines to land

"Builder separates the construction of a complex object from its representation, so the same step-by-step process can produce different configurations of it. It solves the telescoping constructor problem — instead of one constructor with many optional parameters, each optional piece gets its own method, usually chained fluently, ending in a Build() call."

  • Solves → the telescoping constructor problem — many optional parameters.
  • Shape → one method per step, each returning this, then Build().
  • Director → optional — most C# builders let the caller chain steps directly instead.
  • vs. Factory → one object, many steps — not one call, many possible types.
📖 Explanation ▾

Builder's intent: separate the construction of a complex object from its final representation, so the same step-by-step construction process can produce different representations of it. The structure has three real participants: a Builder (declares the construction steps), a ConcreteBuilder (implements them and accumulates state), and the Product it eventually returns. A Director — something that orchestrates which steps run in what order — is part of the original GoF shape, but many real-world C# builders skip it entirely and just let the caller chain steps directly; the fluent style itself does the directing.

The problem it solves is the telescoping constructor: a constructor with several optional parameters forces every caller into a long positional argument list, or forces the class into an overload for every combination. A fluent builder instead gives each optional piece its own named method, each returning this, so a caller chains only what it actually needs.

A genuine, real-world .NET example of the shape: WebApplicationBuilder in ASP.NET Core — var builder = WebApplication.CreateBuilder(args); hands back a builder, configuration gets chained onto it (builder.Services.AddControllers();), and var app = builder.Build(); produces the finished, immutable WebApplication.

💻 See the code ▾
C# 
public class PizzaBuilder
{
    private Size _size;
    private readonly List<string> _toppings = new();

    public PizzaBuilder WithSize(Size size) { _size = size; return this; }       // ✅ returns this
    public PizzaBuilder AddTopping(string topping) { _toppings.Add(topping); return this; }

    public Pizza Build() => new Pizza(_size, _toppings);   // assembled from every step so far
}

Each step returns this, which is what makes the fluent chain possible.

C# 
Pizza pizza = new PizzaBuilder()
    .WithSize(Size.Large)
    .AddTopping("pepperoni")
    .AddTopping("mushroom")
    .Build();                                   // no Director — the caller chains the steps itself

No separate Director here — the caller is doing the directing, by choosing which steps to chain.

🌍 Real-world example ▾

WebApplicationBuilder in ASP.NET Core. WebApplication.CreateBuilder(args) hands back a builder; you chain configuration onto it (builder.Services.AddControllers();); builder.Build() returns the finished WebApplication — the exact same shape as PizzaBuilder, just configuring a web host instead of a pizza.
