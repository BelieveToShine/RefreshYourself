🔥 Python · Advanced · Must Know

The GIL is a real constraint on CPU-bound threads — but it's not, and has never quite been, "Python can't use more than one core, period"

What is the GIL, and why does CPython have one? Does async sidestep the GIL problem, or not?

Why it matters ▾
  • Separates people who understand CPython's actual constraint from people who've only memorized "Python is single-threaded" as a blanket rule.
  • Comes up the moment a candidate proposes threading to speed up a CPU-heavy loop, or calls asyncio "true parallelism."
  • A common opener before a "how would you scale a CPU-bound Python service" architecture question.
🔥 Easy interview recall

GIL → one thread runs Python bytecode at a time

Threading → helps I/O-bound work (GIL released while waiting)

Multiprocessing → helps CPU-bound work (separate GILs)

asyncio → single-threaded, cooperative — not parallel

Think: I/O-bound → threading or asyncio help CPU-bound → needs multiprocessing (or a still-experimental free-threaded build)

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Python can only use one CPU core, period" is not quite right. That's true only for CPU-bound bytecode execution inside one standard, GIL-holding CPython process — multiprocessing has always given genuine parallel execution across cores, and free-threaded CPython (PEP 703, still experimental) is actively changing even the GIL-bound picture.

🔄 Likely Follow-up

"When does threading actually help despite the GIL, and when does multiprocessing help instead?" Threading helps I/O-bound work — a network or disk wait releases the GIL. Multiprocessing helps CPU-bound work — separate processes, separate GILs, genuine parallel execution — at the cost of serialization overhead to move data between processes.

🎯 Say this in the interview — the exact lines to land

"The GIL blocks parallel Python bytecode execution across threads in one process — I/O-bound work releases it, so threading still helps there; CPU-bound work needs multiprocessing, or a GIL-releasing extension, for real parallelism."

  • The GIL lets only one thread run Python bytecode at a time, in one process.
  • I/O-bound work releases the GIL while it waits — threading genuinely helps here.
  • CPU-bound work can't parallelize across threads — it needs multiprocessing (separate GILs) instead.
  • asyncio is single-threaded, cooperative concurrency — it helps I/O concurrency, it doesn't add parallel CPU execution.
  • Free-threaded CPython (PEP 703) is real but still experimental, starting with Python 3.13 — not yet the mainstream default.
📖 Explanation ▾

The GIL (Global Interpreter Lock) is a single lock that CPython holds while executing Python bytecode, so only one thread executes bytecode at a time inside one process. It exists largely because CPython's memory management — reference counting — isn't itself thread-safe without a lock protecting it, and historically, adding fine-grained locking everywhere was judged not worth the added complexity and performance cost for the common, mostly single-threaded case.

The GIL doesn't mean zero concurrency. I/O-bound work — waiting on a network call, a disk read — releases the GIL while it waits, so threading genuinely helps I/O-bound workloads. It's specifically CPU-bound bytecode execution that can't parallelize across threads in one process. Multiprocessing sidesteps the GIL entirely by using separate processes, each with its own interpreter, own GIL, and own memory — genuinely parallel for CPU-bound work, at the cost of serialization overhead to pass data between processes.

asyncio does not sidestep the GIL in the sense of true parallel CPU execution — it's still single-threaded, cooperative concurrency: one thing runs at a time, everything else waits its turn at an await point. It helps I/O-bound concurrency for essentially the same underlying reason threading does, not by escaping the GIL's CPU-bound limitation. Separately, free-threaded CPython (PEP 703) is an active, still-experimental development — a no-GIL build shipping starting with Python 3.13 — worth knowing about, but not yet a settled, mainstream default.

🌍 Real-world example ▾

A team tried to speed up a CPU-heavy image-processing pipeline by adding more threads — pure-Python resize and filter loops running on several threads showed no real speedup at all, because every thread was still fighting over the same GIL to run Python bytecode. Switching the hot loop to multiprocessing (separate processes, separate GILs) gave a real, close-to-linear speedup across cores; moving the same loop into NumPy, which releases the GIL during its heavy C-level computation, would have worked too.
