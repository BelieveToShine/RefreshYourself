Trie — the tree built to answer "does anything start with this?"

"How would you implement autocomplete — and why not just use a hash set of strings?"

Why it matters ▾
  • Interviewers ask this to see if you know why a trie exists — not just that the name happens to mean "prefix tree."
  • Autocomplete, typeahead search boxes, and spell-check dictionaries all lean on the exact same "walk one character at a time" idea.
  • The space-vs-hash-set tradeoff is a common follow-up that separates "knows the name" from "knows when to actually reach for it."
🔥 Easy interview recall

Trie = "a tree where every path from the root spells a prefix."

Think: hash set → "is this EXACT word here?" in O(1) trie → "does ANY word START WITH this?" in O(L)

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for a trie just because you have a set of strings is overkill. If the real question is only "does this EXACT string exist," a plain hash set already answers that in O(1) with less code — a trie only earns its complexity when prefixes themselves are part of the problem (autocomplete, longest common prefix, routing-table lookups).

🔄 Likely Follow-up

"How would you find the longest common prefix among a list of strings using a trie?" Insert every string, then walk down from the root as long as each node has exactly one child and isn't itself flagging a shorter word's end — the path you can walk without hitting a branch is the longest common prefix.

🎯 Say this in the interview — the exact lines to land

"A trie is a tree where each node is one character, and a path from the root spells a prefix — insert, exact search, and prefix search all cost O(L), the length of the word, no matter how many other words are already stored. That last part — prefix search that doesn't depend on how many words share the prefix — is exactly what a hash set can't do, since hashing throws away any shared structure between similar strings."

  • insert / search → O(L), cost depends only on the word's own length.
  • Exact search only counts if the final node is flagged end-of-word, not just reachable.
  • startsWith → O(L), regardless of trie size — the one thing a hash set can't do.
  • Tradeoff → a trie can cost more memory than a hash set when words don't share prefixes.
📖 Explanation ▾

A trie (short for "retrieval," pronounced "try") is a tree where each node represents one character, and the path from the root down to a node spells out a prefix. Insert car and card into the same trie and they share the exact same c-a-r path — card simply keeps going one level deeper. A node only gets flagged "end of word" when a real, complete word actually stops there, which is why car being a prefix of card doesn't automatically make car itself a stored word.

Insert, exact search, and prefix search all walk down one character at a time, so every one of them costs O(L) — L being the length of the word or prefix being processed, never the number of other words already sitting in the trie. That's the whole reason a trie exists: it turns "does any word start with this?" into the same cheap, length-bound walk as an exact lookup — a question a hash set can only answer by scanning every entry it holds, because hashing a string destroys any notion of shared structure with other strings.

The honest cost is memory. Every distinct character-path segment needs its own node, so a trie can end up using more space than a hash set holding the exact same words — especially when those words don't share much structure with each other. A trie only earns that cost when prefixes are genuinely part of the problem.

💻 See the code ▾
Pseudocode 
function insert(word):
    node = root
    for ch in word:
        if ch not in node.children:
            node.children[ch] = new TrieNode()   // ✅ create the missing node
        node = node.children[ch]
    node.isEndOfWord = true                    // ✅ mark the complete word

Cost is O(L) — the word's own length — never touches any OTHER word already stored.

Pseudocode 
function search(word):
    node = root
    for ch in word:
        if ch not in node.children:
            return false      // ❌ path breaks — word not stored
        node = node.children[ch]
    return node.isEndOfWord   // must be flagged, not just reachable

Reaching the last node isn't enough — car being a prefix of card doesn't make car itself a stored word unless its own node is flagged.

Pseudocode 
function startsWith(prefix):
    node = root
    for ch in prefix:
        if ch not in node.children:
            return false
        node = node.children[ch]
    return true    // ✅ prefix exists — no isEndOfWord check needed

This is the one a hash set cannot do without checking every stored string — O(L) here, O(n) for a hash set.

🌍 Real-world example ▾

Every time an IDE suggests matching variable names as you type, or a phone's contacts app narrows the list letter by letter, that's this exact mechanism at work — walk down to the node matching what's been typed so far, then list everything stored below it.
