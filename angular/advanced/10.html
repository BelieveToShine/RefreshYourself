Micro frontends — independently deployed pieces that still have to feel like one single app

When would micro frontends actually be the right call, and when is a modular monolith the better one instead?

Why it matters ▾
🏗️ Modular monolith
❗ ProblemMultiple teams own different feature areas of the same app, and with no structural boundaries between them their code quietly tangles together — changes start blocking each other even before any team is actually blocked on a release.
✅ SolutionFeature-based folders, disciplined dependency direction, and clear per-team ownership inside one codebase give every team the same independent lane, with none of the operational cost of separate deployments — everyone still ships together in one build.
RecallModular monolith = independent ownership, one shared release, no extra deploy cost.
🧩 Micro frontends
❗ ProblemEven a well-structured modular monolith still ships every team's code in one build — so once teams are genuinely, currently blocked on each other's release schedules, good internal structure alone can't unblock them.
✅ SolutionSplitting the app into independently built and deployed pieces, assembled at runtime via module federation, lets each team ship on its own schedule — at the real cost of more deployable units, version drift, and harder debugging.
RecallMicro frontends = independent deploys, real operational cost — only worth it when teams are actually blocked.
🔥 Easy interview recall

Micro frontends → independently deployed pieces, one app to the user

Modular monolith → independently owned code, one shared release

Reach for micro frontends → only when teams are genuinely blocked on each other's releases

Think: both give teams their own lane. Only micro frontends give each lane its own finish line.

⚠️ Common Trap

"It's a large app" is not a reason to reach for micro frontends. Size alone doesn't justify the operational cost — a currently-felt deployment-coordination problem a well-structured modular monolith couldn't already solve does.

🔄 Likely Follow-up

"If a modular monolith already gives most of the same benefits, what's the one thing it genuinely can't give you that real micro frontends can?" Independent deployment — even with perfect internal boundaries, every team's changes in a modular monolith still ship together in one build; only genuinely separate deployable units let one team ship a change without every other team also being ready to ship at that exact moment.

🎯 Say this in the interview — the exact lines to land

"Micro frontends compose independently built and deployed frontend pieces, often owned by different teams, into what feels like one app. That independence is real, but it's expensive — more deployable units to version and monitor, and shared-dependency version drift becomes its own class of bug. I'd only reach for it when multiple teams are genuinely blocked on each other's release schedules right now; otherwise a modular monolith with feature-based folders and clear ownership gets most of the same benefit for far less operational cost."

  • Micro frontends → justified by a felt deployment-coordination problem, not by app size.
  • Module federation → lets separately-built apps load each other's code at runtime, no shared compile step.
  • What to share → keep it narrow: design system, auth state, and framework singletons only.
  • Authentication → centralized in one shell/host, every micro frontend defers to it — log in once.
  • Modular monolith → same ownership boundaries, one release — the right default for most large apps.
📖 Explanation ▾

Micro frontends split one application into pieces that are built and deployed independently — often by different teams — then assembled at runtime (or build time) so the end user still experiences one cohesive app. Module federation (Webpack's, which Angular's build tooling can be configured to use) is the mechanism that makes this work technically: it lets separately-built applications load and share code/modules from each other at runtime, without being compiled together into one build.

The trade is real independence for real complexity. Sharing has to stay deliberately narrow — a design system, authentication state, and core framework dependencies (so Angular itself isn't loaded multiple times) — because anything shared becomes a coordination point between teams that are supposed to be independent. Authentication in particular is usually centralized in one shell/host application every micro frontend defers to, so a user only logs in once across what's meant to feel like a single app.

A modular monolith gets most of the same real benefit — clear ownership, decoupled feature areas — through good internal architecture alone: feature-based folders, disciplined dependency direction, and clear per-team ownership within one codebase (the same structure covered on the Large Application Architecture page). It pays none of the operational cost of multiple deployable units, but it also can't give teams independent release schedules — everyone's code still ships together in one build.

💻 See the code ▾
TS 
// conceptual sketch — shared singletons across micro frontends
// (illustrative shape, not an assertion of exact current Webpack syntax)
shared: {
  '@angular/core': { singleton: true },   // one copy of Angular, not one per micro frontend
  '@angular/common': { singleton: true },
}

Marking a dependency singleton: true is the idea that matters here — every independently-built micro frontend uses the same one copy of the framework at runtime, instead of each bundling and loading its own.

TS 
// modular-monolith alternative — same feature-based folder idea
src/app/
  features/
    billing/       // one team's boundary, still one build
    reporting/      // another team's boundary, still one build
  shared/           // the narrow, deliberate shared surface

This gets most of the same isolation as micro frontends — clear ownership, decoupled feature areas — without paying for separate deployments.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app is large, but no team is actually blocked waiting on another team's release

This is the decision tree's NO branch: a well-structured modular monolith — feature folders, clear ownership, one build — already gives every team its own lane, and there's no currently-felt deployment conflict forcing anything more expensive.

RememberNo felt release conflict yet → modular monolith is still the right default.
2 Multiple teams are genuinely, right now, blocked waiting on each other's release windows

This is the tree's YES branch — the one case worth paying for independent deploys. Module federation lets each team's separately-built app load the others' code at runtime, so one team can ship without every other team also being ready to ship at that exact moment.

RememberGenuinely blocked release schedules, right now, → that's what actually earns micro frontends.
3 You (or a candidate) reach for micro frontends just because the app is “large,” with no actual deployment conflict named

Size alone was never the question the decision tree asks — only a currently-felt, cross-team release conflict is. Picking micro frontends here pays the real operational cost (more deployable units, version drift, harder debugging) for a problem a modular monolith would already have solved.

Remember“It's a large app” is not a reason — check for a real release conflict first.
🌍 Real-world example ▾

A modular monolith is several chefs sharing one kitchen with clearly assigned stations — independent day-to-day work, but the kitchen opens and closes together as one unit. Micro frontends are those same chefs running fully separate food trucks parked next to each other so customers experience them as one food court — genuinely independent hours and schedules, but now each truck needs its own generator, its own health inspection, and someone has to make sure they all still look like they belong together.
