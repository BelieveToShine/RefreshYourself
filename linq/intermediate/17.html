Multiple Enumeration and Side Effects — why a query that looks like it ran once, ran twice

"Why is a Select with a side effect — a counter, logging, an API call — dangerous inside a deferred query?"

Why it matters ▾
🔁 Multiple Enumeration
❗ ProblemChecking query.Any() to validate results, then enumerating the same query again in a foreach, looks like it ran once — but a deferred LINQ query re-executes its entire pipeline on every single enumeration, so any side effect inside it fires once per enumeration, not once per item overall.
✅ SolutionMaterialize the query once with ToList()/ToArray() before anything with a side effect runs more than once, so the pipeline — and whatever it does — runs exactly one time.
RecallEnumerated twice → side effect runs twice.
🔥 Easy interview recall

Multiple enumeration = "the same query re-runs its whole pipeline every time something enumerates it."

Think: Any() then foreach on the same un-materialized query → two full runs, not one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Looks like it ran once" is not the same as "it ran once." Calling query.Any() to check for results, then enumerating the same un-materialized query again in a foreach, independently re-runs the whole pipeline both times — a side effect inside Select fires on both passes, not just the second one.

🔄 Likely Follow-up

"Does ToList() always fix this?" Yes for this specific problem — materializing once with ToList()/ToArray() runs the pipeline exactly once, so the side effect fires exactly once per item. It's a separate decision from performance, though: materializing early against an IQueryable can mean losing provider-side translation, which is its own, different pitfall.

🎯 Say this in the interview — the exact lines to land

"A deferred LINQ query re-runs its whole pipeline every time it's enumerated — so a Select with a side effect like counter++ fires once per enumeration, not once overall. Checking Any() and then looping over the same un-materialized query counts as two enumerations, and the side effect runs twice."

  • Deferred query → re-executes the pipeline on every enumeration, nothing is cached.
  • Side effect inside Select/Where → runs once per enumeration, not once per item overall.
  • Fix → materialize once with ToList()/ToArray() before enumerating more than once.
  • Common trigger → checking Any()/Count() then looping the same query again.
📖 Explanation ▾

A deferred LINQ query is a plan, not a stored result — every time something enumerates it (foreach, Any(), Count(), ToList(), another foreach...), the whole chain of Where/Select/etc. runs again from the source, from scratch. That's fine when every step is a pure calculation — running it twice gives the same answer twice. It stops being fine the moment a step has a side effect: a counter increment, a log line, an API call, a database write.

The classic trigger is validating before using: calling query.Any() to check "is there anything to process," then running a separate foreach over the exact same query variable to actually process it. Both calls look like they're working with "the query's result," but each one is an independent enumeration that reruns every Select/Where in the chain — including whatever side effect lives inside them.

The fix is to decide, once, when the pipeline should actually run: call ToList() or ToArray() right after building the query, then do every check and every loop against that materialized list instead of the original query variable. The side effect then runs exactly once per item, because the pipeline itself only ran once.

💻 See the code ▾
C# 
int counter = 0;
var query = items.Select(x => { counter++; return x; });   // not run yet

if (query.Any())        // 1st enumeration — counter now 3
{
    foreach (var x in query)   // 2nd enumeration — counter now 6, not 3
        Process(x);
}

Same query variable, two full enumerations — the side effect doubles.

C# 
int counter = 0;
var results = items.Select(x => { counter++; return x; }).ToList();   // runs once here

if (results.Any())       // checking a List<T>, no re-run
{
    foreach (var x in results)   // looping a List<T>, no re-run
        Process(x);
}
Console.WriteLine(counter);   // ✅ 3 — exactly once per item

ToList() fixes the count by running the pipeline exactly once, up front.

🧭 Use Cases — recognize these when they happen to you ▾
1 Validate with Any(), then process the same query in a foreach

The single most common way this bug ships: a null/empty guard that calls Any(), then a foreach right after it over the same un-materialized query — doubling any API call, log line, or counter inside the pipeline.

RememberAny() + foreach on the same query → materialize first, or it runs twice.
2 Debug logging inside a Select bound to something that re-reads it

A deferred query bound to a grid or view that reads it more than once (e.g. once to measure a count, once to render rows) logs every line 2-3 times — not because the logging code is wrong, but because the query it's attached to was never materialized.

RememberDuplicate log lines from one request → suspect multiple enumeration first.
3 Counting processed items with a counter inside the Select itself

Calling both query.Count() and query.ToList() separately on the same deferred query — instead of calling one and deriving the other from its result — is another common double-enumeration source, and the counter ends up twice the real item count.

RememberNeed both a count and the items? Materialize once, then use .Count on the list.
🌍 Real-world example ▾

A batch job builds a deferred query whose Select calls an external API per item for enrichment, checks query.Any() to decide whether to proceed, then runs a foreach over that same query to process it. Every item's enrichment API call fires twice, doubling API cost and risking rate limits — purely because the same un-materialized query was enumerated twice, not because of anything wrong with the enrichment logic itself.
