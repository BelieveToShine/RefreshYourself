Server data is a cache you don't own — stop hand-rolling it with useEffect

"Why use React Query or SWR instead of useEffect + fetch + useState?"

Why it matters ▾
🧍 Client state
❗ ProblemMixing every kind of state in one tool hides which parts can silently go out of date.
✅ SolutionKeep values the browser owns — a modal, a form draft — in useState, useReducer, or a store.
RecallClient state = you own it.
🌐 Server state
❗ ProblemA copy of server data in useState goes stale, and a hand-written fetch effect must also handle loading, errors, races, and duplicate requests.
✅ SolutionA cache library (TanStack Query, SWR) stores each response under a key and handles dedupe, refetching, retries, and invalidation.
RecallServer state = a cached copy of someone else's data.
🔥 Easy interview recall

client state → you own it

server state → a cached copy of the server's data

Think: same key → one request. Stale → show cached, refetch behind the scenes. Save → invalidate.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Copying fetched data into useState (or a global store). You now own a second copy that nothing keeps fresh. Leave server data in the query cache and read it from there; keep only real client state in your own state.

🔄 Likely Follow-up

"What does 'stale' mean here?" Fresh data is served from the cache without a refetch. Once stale, the library still shows the cached copy right away and refetches in the background — on triggers like a remount or window focus, depending on settings. Defaults differ by library, so check the current docs.

🎯 Say this in the interview — the exact lines to land

"Fetched data is server state — a cache of data I don't own — so I use a library like TanStack Query or SWR instead of useEffect + fetch + useState. It caches by key, shares identical requests, refetches stale data in the background, retries failures, and invalidates after a mutation. Client state, like an open modal, stays in useState."

  • Same key → one cache entry, one request, shared by components.
  • Stale data → show cached, refetch in the background.
  • After a mutation → invalidate the key so it refetches.
  • Hand-rolled effect → you handle loading, errors, and races yourself.
  • These libraries do not do the fetching — you still supply the function.
  • A modal or form draft → still plain client state.
📖 Explanation ▾

Server state is data that lives on a server — you only hold a copy, and that copy can be out of date at any moment. Client state (an open modal, a form draft) is owned by the browser. useEffect + fetch + useState can load server data, but you soon also need loading and error flags, a guard against out-of-order responses, sharing the result between components without fetching twice, refetching when it gets old, and updating after a save.

A library like TanStack Query or SWR does this with a cache keyed by a query key such as ['user', 1]. Components asking for the same key share one entry and one in-flight request. Data is "fresh" for a window; once it is stale, the cached copy still shows instantly while a background refetch brings the new data. After a mutation (a save), you invalidate the related key and it refetches.

These libraries do not fetch for you — you still supply the fetch function. This page is the concept only: names, defaults, and options differ between libraries and versions, so check the current docs. Frameworks and newer React features (see State Management Architecture and Actions & use()) can move some fetching to the server, but a client cache still matters for data that changes after load. Basics of fetching are in Data Fetching.

💻 See the code ▾
JSX 
useEffect(() => {
  let ignore = false;  // guard against out-of-order responses
  setLoading(true);
  fetchUser(id)
    .then((u) => { if (!ignore) setUser(u); })
    .catch(setError)
    .finally(() => setLoading(false));
  return () => { ignore = true; };
}, [id]);  // ❌ still no cache, no sharing, no retry, no refetch

Hand-rolled, and this is only the loading part. Each component using it would fetch again on its own.

JSX 
const { data, isPending, error } = useQuery({
  queryKey: ['user', id],        // ✅ cache key — same key = shared entry
  queryFn: () => fetchUser(id),  // you still supply the fetch
});

Same job, with caching and dedupe built in. Result field names can differ by library and version — check the current docs.

JSX 
const queryClient = useQueryClient();
const save = useMutation({
  mutationFn: saveUser,
  onSuccess: () =>
    queryClient.invalidateQueries({ queryKey: ['user', id] }),  // ✅ mark stale → refetch
});

After a save, invalidate the key instead of patching state by hand.

🌍 Real-world example ▾

One newspaper for the whole office. Everyone reads the same copy on the table instead of ordering their own; when it gets old, someone brings in today's issue, and readers keep the old one until the new one arrives.
