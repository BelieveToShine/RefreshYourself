HttpContext is per request — so why can the accessor hand you null?

"How do you get the current user or request outside a controller, and what's wrong with IHttpContextAccessor?"

Why it matters ▾
📦 HttpContext
❗ ProblemCode deep inside a service sometimes needs to know who the caller is, but only controllers and middleware get HttpContext handed to them.
✅ SolutionRegister IHttpContextAccessor and read the current request from it — but treat it as a tool for specific cases, not a place to hang application logic.
RecallThe accessor reaches the current request — if there is one.
🔥 Easy interview recall

HttpContext lives one request — no request, no context.

Think: controller / middleware → HttpContext is already right there IHttpContextAccessor → for deep services, and always check for null

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming IHttpContextAccessor.HttpContext is never null. It is null whenever no request is in flow — a BackgroundService, a startup task, work that outlived the request. And HttpContext isn't thread-safe, so don't read it from parallel work.

🔄 Likely Follow-up

"How would you avoid the accessor altogether?" Pass what you need — user id, tenant — as method parameters, or read it once in middleware or the controller into a small scoped service. Then the service depends on that value, not on the web layer.

🎯 Say this in the interview — the exact lines to land

"HttpContext is created per request and carries the request, response, user and items. Controllers and middleware get it directly; deeper services can use IHttpContextAccessor, which finds the current request through an AsyncLocal. It returns null when there is no request — in a background service, for example — so I handle that, or pass the values I need in explicitly."

  • HttpContext → one per request: request, response, user, items.
  • AddHttpContextAccessor() → must be registered — it isn't there by default.
  • The accessor → AsyncLocal, so it follows the request through awaits.
  • No request (background job) → HttpContext is null; and it isn't thread-safe.
  • Better design → pass the values in instead of reaching out for them.
📖 Explanation ▾

HttpContext is the object for one request. It holds Request, Response, User (the authenticated ClaimsPrincipal), Items (a per-request dictionary) and RequestServices (that request's scoped container). Middleware receives it as a parameter and controllers expose it as this.HttpContext — see Middleware.

A service three layers down has neither. IHttpContextAccessor bridges that: it is registered with AddHttpContextAccessor() and exposes HttpContext for the request the current async flow belongs to, stored in an AsyncLocal. The accessor itself is a singleton — the value it returns changes per request, which is why it's safe to inject into any lifetime.

Use it sparingly. It quietly ties a service to the web layer, it is null where there is no request (a hosted service, startup code), and HttpContext must not be read from several threads or kept after the request ends. Never store an HttpContext in a field of a singleton; read what you need and let go.

💻 See the code ▾
C# 
builder.Services.AddHttpContextAccessor();   // not registered by default

public class CurrentUser
{
    private readonly IHttpContextAccessor _accessor;
    public CurrentUser(IHttpContextAccessor accessor) => _accessor = accessor;

    public string? Id =>
        _accessor.HttpContext?.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;   // ✅ null-safe
}

Register it, then read with ?. — there may be no request.

C# 
protected override Task ExecuteAsync(CancellationToken stoppingToken)
{
    var user = _accessor.HttpContext?.User;   // ❌ always null — no request here
    return Task.CompletedTask;
}

In a background service there is no request, so the accessor has nothing to give.

C# 
public Task SendReceiptAsync(string userId, int orderId)   // ✅ the caller passes the user id in
{
    return _sender.SendAsync(userId, orderId);
}

The simpler design: pass the value the service needs, no accessor at all.

🌍 Real-world example ▾

An audit log written from a repository, three layers below the controller. The accessor supplies "who did this" for normal requests. The same repository, called from a nightly job, gets null — so the audit row records "system" instead of crashing.
