NgRx — when does justifying it matter more than defining it?

"When does state management actually need NgRx, versus when are Signals plus a plain service genuinely enough?"

Why it matters ▾
  • Interviewers use this to check whether you understand when to reach for NgRx — not just whether you can name Store/Actions/Reducers.
  • Comes up any time a team is debating adding a state-management library to a growing Angular app.
  • Reaching for NgRx just because "that's what serious Angular apps use" is a classic over-engineering red flag interviewers listen for.
🔥 Easy interview recall

Signals + service → simple, few consumers

NgRx → complex, cross-cutting, needs traceability

Think: reach for NgRx only when the pain — untraceable state changes across a large team — is real and already felt, not "just in case."

⚠️ Common Trap

Reciting Store/Actions/Reducers/Selectors/Effects is not the same as answering the question. Interviewers are listening for the judgment call — "this app's state is simple enough that Signals plus a service is genuinely sufficient, and NgRx here would be pure overhead" — not just the vocabulary.

🔄 Likely Follow-up

"Can you use NgRx and Signals together in the same app?" Yes — current NgRx exposes Signal-based ways to read from the store, so a component can consume store state as a Signal instead of subscribing to an Observable selector; many real apps use NgRx for the genuinely complex, cross-cutting slices of state and plain Signals plus services for everything simpler. It's not an app-wide either/or choice.

🎯 Say this in the interview — the exact lines to land

"Local component state belongs to one component instance and dies with it. Global state has to be shared and stay consistent across unrelated parts of the app. A Signals-based service is genuinely enough when a slice of state is simple with few consumers; NgRx earns its overhead only when state changes are complex, cross-cutting, and hard to trace across a large team."

  • Signals + service → use when state is simple, few consumers — no library needed at all.
  • NgRx → use when state changes need traceability across a large team or genuinely complex cross-cutting interactions.
  • NgRx enforces action → reducer → store → selector, unlike a plain service, which can be mutated from anywhere it's injected.
  • Not either/or — NgRx has Signal-based integration too, so the real question is whether the app needs NgRx's structure at all.
📖 Explanation ▾

Local state belongs to one component instance — a form's current draft, a toggle's open/closed flag — and it disappears the moment that component is destroyed. Global state is shared across multiple, unrelated parts of the app and has to stay consistent no matter which component is currently looking at it, like the logged-in user or a shopping cart.

A common, lightweight way to hold shared state without any library at all: an injectable service holds one or more Signals as private state, exposes them (often read-only) plus methods that call .set()/.update(). Because the service is providedIn: 'root' — a singleton — every component that injects it shares the exact same Signal instances. That's genuinely shared state, for free.

NgRx doesn't do anything a service technically couldn't do — it trades flexibility for enforced structure. An action only describes intent, a reducer is the only thing allowed to compute the next state, and a selector is the only sanctioned way to read a derived slice. That structure is what makes time-travel debugging, a consistent pattern across a large team, and tracing "what caused this state to change" in a big app actually work — a plain service can be mutated from anywhere it's injected, which is fine at small scale and untraceable at large scale.

💻 See the code ▾
TypeScript 
@Injectable({ providedIn: 'root' })   // one shared instance
export class CartStore {
  private items = signal<Item[]>([]);      // private Signal state
  readonly items$ = this.items.asReadonly();  // read-only outside

  add(item: Item) {
    this.items.update(list => [...list, item]);  // only way to change it
  }
}

Every component that injects CartStore shares the same Signal — genuinely shared state, no library.

TypeScript 
export const addItem = createAction(
  '[Cart] Add Item',               // describes intent, changes nothing
  props<{ item: Item }>()
);

const cartReducer = createReducer(
  initialState,
  on(addItem, (state, { item }) =>
    ({ ...state, items: [...state.items, item] })  // only the reducer computes next state
  )
);

Same "add an item" idea as the card above — but here only a reducer may compute the next state; the first snippet's service could be mutated from anywhere it's injected, this one enforces the path.

🌍 Real-world example ▾

Signals plus a service is a small team sharing one whiteboard everyone's allowed to walk up and edit directly — fast, informal, fine at small scale. NgRx is a large newsroom's formal editorial process: a reporter files a request, an editor is the only one who actually changes the published story, and every change is logged. More overhead, but essential once enough people are touching the same story for informal edits to become untraceable chaos.
