There's no real distributed lock across microservices — that's what Saga is for

How do you prevent cascading failures across microservices, and what is the Saga pattern for?

Why it matters ▾
🔀 Saga Pattern
❗ ProblemEach microservice owns its own database, so there's no shared lock to hold across all of them — if a later step in a multi-service operation fails after earlier steps already committed, those committed changes are left stuck with nothing coordinating a rollback.
✅ SolutionThe Saga pattern defines a compensating action for every step, so a failure triggers those compensating actions in reverse commit order — undoing what already committed without ever needing a distributed lock.
RecallSaga = local transactions + a compensating action per step, run backward on failure.
🔥 Easy interview recall

Saga → local transactions + compensating actions

Circuit breaker → stops calling a failing service

Bulkhead → isolates failure so it can't exhaust shared resources

Think: Saga fixes consistency across services. Circuit breakers + bulkheads fix cascading failure.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A "distributed transaction" across microservices isn't a real ACID transaction. Trying to hold locks across service boundaries doesn't hold up at scale — the Saga pattern's compensating actions are the actual accepted way to keep multi-service data consistent.

🔄 Likely Follow-up

"How do you implement centralized observability across services?" Distributed tracing (X-Ray) with a shared correlation ID propagated through every service call, plus centralized logging/metrics aggregation — without this, debugging a multi-service issue means guessing.

🎯 Say this in the interview — the exact lines to land

"The Saga pattern coordinates a sequence of local transactions across services, using compensating actions to undo earlier steps if a later one fails — there's no real distributed lock across microservices."

  • Saga → compensating actions undo already-committed steps when a later step fails.
  • Circuit breakers, timeouts, and bulkheads → prevent cascading failures from one struggling service.
  • Async messaging (SQS/SNS/EventBridge) → decouples service availability; direct sync calls couple it.
  • Idempotency → makes safe retries possible when a network call fails or duplicates.
  • Service discovery (e.g. Cloud Map) → services find each other's current network location dynamically.
📖 Explanation ▾

Service discovery lets services find each other's current network location dynamically instead of relying on hardcoded addresses — options range from DNS-based lookup (Cloud Map) to a service mesh. How services talk to each other matters just as much: synchronous calls (a direct API request) are simpler to reason about but couple the caller's availability to the callee's; asynchronous messaging (SQS, SNS, EventBridge) decouples them, trading immediate consistency for resilience.

A traditional single-database ACID transaction doesn't work across service boundaries — there's no shared lock to hold. The Saga pattern instead coordinates a sequence of local transactions, one per service, and defines a compensating action for each step that can undo it if a later step in the sequence fails. Because network calls between services can fail or duplicate, every step (and every compensating action) also needs to be idempotent — safe to retry without corrupting state.

Cascading failure is a different problem: one struggling service's slowness or errors spread to every caller that depends on it, and can take the whole system down. Circuit breakers stop calling a service that's already failing, timeouts cap how long a caller waits, and bulkheads isolate failure domains so one service's problem can't exhaust a shared resource, like a thread pool, that healthy services also depend on.

🧭 Use Cases — recognize these when they happen to you ▾
1 A step in your saga fails after earlier steps already committed

This is the #1 scenario the Saga pattern exists for: the shipping step fails after inventory and payment already committed as separate local transactions. There's no cross-service lock to roll back, so the failure instead triggers each already-committed step's own compensating action, undone in reverse order — refund the payment, then release the inventory reservation.

RememberFailure after commit → run compensating actions backward, not a rollback.
2 A downstream service starts timing out under load, and every caller keeps waiting on it

Without protection, every caller piles up threads or connections waiting on the slow service, and that pileup can exhaust a shared resource pool that healthy services also depend on — turning one slow service into a system-wide outage. A circuit breaker stops calling the failing service, a timeout caps how long a caller waits, and a bulkhead isolates the resource pool so the slowdown can't spread.

RememberOne slow service, no circuit breaker/timeout/bulkhead → cascading failure.
3 A payment call times out, and your caller retries it

If the retry isn't idempotent, the customer could be charged twice — the original call may have actually succeeded server-side even though the response never made it back. An idempotency key lets the payment service recognize the retry as the same request and return the original result instead of repeating the charge.

RememberRetry without idempotency → possible double charge; retry with it → safe.
🌍 Real-world example ▾

An order-fulfillment Saga. Step 1 reserves inventory, step 2 charges payment, and step 3 ships the order — each a local transaction in its own service. If the payment step fails, the compensating action releases the inventory reservation instead of leaving it stuck, restoring consistency without ever needing a lock held across all three services.
