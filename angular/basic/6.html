Lifecycle hooks — not a list to memorize, a sequence with a reason

"Why shouldn't initialization logic go in the constructor, and what does ngOnInit actually guarantee?"

Why it matters ▾
  • Almost every Angular interview opens with "walk me through a component's lifecycle" — and the real test hiding inside it is the constructor/ngOnInit timing.
  • A component that subscribes in ngOnInit and never cleans up in ngOnDestroy is one of the most common real-world memory leaks in Angular apps.
  • Reading an @Input one hook too early is a bug that only shows up at runtime — the compiler won't catch it.
🔥 Easy interview recall

constructor() → too early — @Input not set

ngOnInit() → right time — @Input guaranteed

Think: the order alone isn't the fact worth knowing — the reason is: Angular finishes binding your inputs after the constructor runs, but before ngOnInit runs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Constructor and ngOnInit both run once at creation, so it doesn't really matter which you use." It matters specifically because of @Input timing — reading a bound property in the constructor can see undefined, while the exact same read in ngOnInit is guaranteed to see the real, bound value.

🔄 Likely Follow-up

"Does ngOnChanges fire on the very first render, before ngOnInit?" Yes — if the component has any @Input-bound properties, ngOnChanges fires once before the first ngOnInit call to deliver the initial values, then again on every later change to those inputs. A component with no @Inputs at all never gets ngOnChanges called.

🎯 Say this in the interview — the exact lines to land

"The constructor runs the moment the class is instantiated, before Angular has applied any @Input bindings or initialized the view. ngOnInit runs once, right after the first change-detection check, by which point every @Input-bound property is guaranteed to have its real value — so initialization logic belongs in ngOnInit, and the constructor stays limited to basic setup and dependency injection."

  • constructor() → basic setup and DI only, never logic that reads an @Input.
  • ngOnInit() → real initialization, once @Input values are guaranteed set.
  • ngOnChanges(changes) → fires on every @Input reference change, with old and new values via SimpleChanges — not on mutation.
  • ngAfterViewInit / ngAfterContentInit → the first point @ViewChild / projected content is guaranteed to exist.
  • ngOnDestroy() → unsubscribe, clear timers, remove listeners — anything Angular didn't create itself.
📖 Explanation ▾

The constructor runs the instant the class is built — Angular hasn't finished setting up @Input bindings yet, and the view doesn't exist yet either. Angular does call it with your injected dependencies already resolved, but that's a separate, unrelated timing fact from the @Input one. ngOnInit runs once, right after the very first change-detection check — by then every @Input-bound property is guaranteed to hold its real starting value. Constructor first (bindings not ready), ngOnInit second (bindings ready) — that ordering, and the reason behind it, is what an interviewer is actually checking for.

ngOnChanges(changes: SimpleChanges) runs whenever an @Input-bound property's reference changes — once before that first ngOnInit call, and again on every later change — handing you both the old and new value. It does not fire when something inside that object or array is only mutated, the same reference-vs-mutation rule that keeps a pure pipe from re-running on mutation. ngAfterViewInit and ngAfterContentInit follow the same idea for two other things: the first is the earliest point a @ViewChild query is guaranteed to be filled in, the second is the same guarantee for content projected in through <ng-content>. Querying either one earlier can find undefined.

ngOnDestroy runs once, right before Angular tears the instance down — release anything there that would otherwise outlive the component: a manual .subscribe(), a setInterval/setTimeout handle, a window.addEventListener. A component that subscribes in ngOnInit and never unsubscribes keeps that subscription — and whatever it's holding onto — alive after the component is gone from the DOM, a common real memory leak. The async pipe handles its own unsubscription, so it doesn't need this; a manual subscription does. A later page in this track covers takeUntilDestroyed(), the modern fix for exactly this problem.

💻 See the code ▾
TypeScript 
@Input() userId!: string;

constructor() {
  console.log(this.userId);  // ❌ undefined — binding not applied yet
}

The constructor runs before Angular applies @Input bindings — the value simply isn't there yet.

TypeScript 
@Input() userId!: string;

ngOnInit() {
  console.log(this.userId);  // ✅ the real, bound value
}

Same property, one hook later — ngOnInit is guaranteed to run after the binding is applied.

TypeScript 
private sub = this.data$.subscribe(this.handleData);

ngOnDestroy() {
  this.sub.unsubscribe();  // ✅ releases it before the component is gone
}

Skip this for the async pipe — it unsubscribes itself. A manual .subscribe() does not.

🌍 Real-world example ▾

The constructor is a new employee's first minute on the job — before anyone has handed them their assignment. ngOnInit is their first real day at the desk, once the assignment (the @Input values) has actually arrived. Trying to start the "real" work during that first minute means working off nothing.
