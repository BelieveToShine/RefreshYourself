== vs. === — which one actually checks the type?

"What's the difference between == and === in JavaScript, and what does Object.is() add on top?"

Why it matters ▾
  • One of the very first things a JS interviewer checks — get it wrong and it signals you haven't looked at the language closely.
  • Loose equality's coercion rules cause real bugs: form input ("0") compared to a number, or a stray falsy value slipping through a check.
  • The NaN/+0/-0 edge cases are a favorite "predict the output" follow-up right after this one.
🔥 Easy interview recall

== → converts first, then compares

=== → no conversion, type must already match

Object.is() → === plus the NaN/±0 fix

Think: === = "same type AND same value." == = "make the types match first, then ask the same question."

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

NaN === NaN is false. NaN is defined as "not equal to anything, including itself" — use Number.isNaN(x) or Object.is(x, NaN) to actually detect it.

🔄 Likely Follow-up

"What does Object.is() give you that === doesn't?" Two things: Object.is(NaN, NaN) is true (unlike ===), and Object.is(+0, -0) is false (unlike ===, which treats +0 and -0 as equal). It exists specifically to tell same-value identity from mathematical equality.

🎯 Say this in the interview — the exact lines to land

"== converts operands to a matching type before comparing, which can produce surprising results. === never converts — if the types differ, it's immediately false. Object.is() behaves like === but treats NaN as equal to itself and tells +0 apart from -0."

  • === → use it as the everyday default — no hidden conversion to reason about.
  • == → the one defensible use is x == null, which catches both null and undefined in one check.
  • Object.is() → reach for it only for NaN checks or +0/-0 — not a general replacement for ===.
📖 Explanation ▾

== (loose equality) converts one or both operands to a common type before comparing — a string gets turned into a number, a boolean gets turned into a number, and so on, following a fixed set of coercion rules. === (strict equality) skips that step entirely: if the two operands aren't already the same type, the answer is false, full stop.

That single difference is the whole story. 5 == "5" is true because "5" gets coerced to 5 first. 5 === "5" is false because a number is never a string, no conversion happens, and the check stops right there.

So when is == actually the right call? Comparing against null and undefined together: x == null is true for both null and undefined, and false for everything else — a genuinely useful one-line check. Outside that one case, prefer ===; the coercion rules for other type pairs are easy to misremember and rarely worth the risk.

💻 See the code ▾
JavaScript 
5 == "5";    // ✅ true  — "5" is coerced to the number 5
5 === "5";   // ❌ false — number vs string, no coercion

Same two values — == makes the types match first, === refuses to.

JavaScript 
// predict these before you run them
NaN === NaN;              // ❌ false — NaN is never equal to anything
Object.is(NaN, NaN);   // ✅ true  — Object.is fixes this one case
+0 === -0;                // ✅ true  — === treats them as equal
Object.is(+0, -0);      // ❌ false — Object.is tells them apart

Object.is() and === disagree on exactly two things: NaN, and the sign of zero.

JavaScript 
let user;
if (user == null) { /* ✅ catches both null and undefined */ }
if (user === null || user === undefined) { // same result, two checks }

The one defensible ==: x == null is a single check for "missing," instead of two === checks.

🌍 Real-world example ▾

A form field reads back as the string "0". "0" == false is true (both coerce to 0), which can silently trip an "empty or false" check that was only meant to catch an actual boolean. "0" === false is false — the strict check never falls into that trap.
