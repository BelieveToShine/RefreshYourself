@dataclass writes your boilerplate __init__/__repr__/__eq__ for you — nothing more mysterious than that

"What is @dataclass, and why use it over a normal class?"

Why it matters ▾
  • Tests whether you know @dataclass is boilerplate generation, not magic — the natural follow-up drills into frozen=True and the mutable-default trap.
  • Explains why a bare = [] default on a dataclass field fails loudly at class-definition time instead of silently causing a shared-state bug months later.
  • A common entry point into the dataclass vs. namedtuple vs. Pydantic decision question.
🔥 Easy interview recall

@dataclass = "auto-writes __init__, __repr__, and __eq__ from your annotated fields."

Think: add frozen=True and it locks into a read-only value object.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A dataclass field with a bare mutable default (items: list = []) is safe to write. It's not — @dataclass raises a ValueError the moment the class is defined, specifically to catch this (a plain function lets the same mutable-default bug through silently). The fix is still field(default_factory=list).

🔄 Likely Follow-up

"Dataclass vs. Pydantic — when do you actually need Pydantic?" Whenever the data comes from outside your trust boundary — an API request, a config file, user input — and needs real validation/coercion at construction time. Use a plain dataclass for internal, already-trusted data where you just want less boilerplate.

🎯 Say this in the interview — the exact lines to land

"@dataclass generates the __init__, __repr__, and __eq__ boilerplate you'd otherwise write by hand, straight from the class's type-annotated fields."

  • frozen=True → locks instances immutable after __init__, approximating a value-object/record type.
  • field(default_factory=list) → fixes a mutable default, the same trap functions have — but the dataclass catches it at definition time instead of at runtime.
  • namedtuple → always immutable; a dataclass is mutable by default and supports methods, type hints, and inheritance more naturally.
  • Pydantic → real runtime validation — reach for it once the data crosses a trust boundary, not just to cut typing.
📖 Explanation ▾

@dataclass looks at a class's type-annotated fields and writes __init__ (assigns each field), __repr__ (a readable printout), and __eq__ (field-by-field equality) for you. frozen=True makes every instance read-only after construction — any attempted attribute assignment raises, which is what makes it a reasonable stand-in for a value-object/record type.

field() lets you customize one field's default — most importantly a mutable default like a list or dict, via field(default_factory=list). A bare = [] would be shared across every instance, exactly the mutable-default bug functions have; @dataclass just refuses to let it through quietly.

💻 See the code ▾
Python 
from dataclasses import dataclass, field

@dataclass
class Cart:
    items: list = []          # ❌ ValueError at class definition

@dataclass catches this immediately — a plain function would let the same bug slide silently.

Python 
@dataclass
class Cart:
    items: list = field(default_factory=list)  # ✅ each instance gets its own list

list(), dict(), set() — any mutable default needs default_factory, never a bare literal.

Python 
@dataclass(frozen=True)
class Point:
    x: int
    y: int

p = Point(1, 2)
p.x = 5   # ❌ raises FrozenInstanceError

frozen=True approximates a value-object/record type — no attribute can change after __init__.

🌍 Real-world example ▾

An internal DTO class was hand-rolled with its own __init__/__eq__ — one code path was quietly mutating a cached instance in place, and a later reader silently saw the changed version. Rewriting it as @dataclass(frozen=True) turned that accidental shared-mutable state into an immediate, loud error: any attempted attribute assignment on the cached object now raises the moment it's introduced, instead of surfacing as a confusing bug hours later.
