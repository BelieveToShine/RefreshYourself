🔥 Must Know

A dashboard with 300 widgets got slow — profile before you guess

"A dashboard rendering hundreds of components has become slow — how do you actually investigate it, in order?"

Why it matters ▾
  • "The app is slow" is one of the most common performance interviews openers — and it's deliberately vague, because a real senior candidate has to ask what's actually happening before reaching for a fix.
  • Interviewers use this to check whether a candidate profiles first or jumps straight to a favorite fix (OnPush, virtual scrolling, code-splitting) without confirming it's the right one.
  • A wrong-cause fix doesn't just waste time — it can make the real bug harder to find later, which is exactly the trap this scenario is built to expose.
🔥 Easy interview recall

"Slow" has several causes = "profile first, then match the fix to the actual cause."

Think: CD overhead → OnPush / Signals Bundle size → lazy load / @defer / SSR DOM node count → virtual scrolling

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding OnPush everywhere is not a safe default fix. Without first checking whether inputs are mutated in place, flipping a component to OnPush can silently stop a binding that was quietly relying on Default's unconditional checking — reaching for any specific fix before profiling risks missing the real cause entirely.

🔄 Likely Follow-up

"If profiling shows change detection running fine and bundle size is reasonable, but the page still feels slow — what's left to check?" The number of actual DOM nodes on screen at once (a large, unvirtualized list or table) and plain browser-level rendering cost — heavy CSS, large images, layout thrashing. Not every performance problem is Angular-specific; sometimes the bottleneck is simply "too much real DOM" or paint cost outside Angular's own mechanisms entirely.

🎯 Say this in the interview — the exact lines to land

"I'd profile with Angular DevTools before touching anything — see which components are checked, how often, and how long each check takes. Excessive checks point to missing OnPush/Signals, a large initial payload points to lazy loading, @defer, or SSR, and a huge unvirtualized list points to virtual scrolling. Each cause has a different fix, so guessing wastes effort and can hide the real problem."

  • Profile first with Angular DevTools — see what's checked, how often, and how long, before picking a fix.
  • Excessive checks → OnPush / Signals, but only after confirming no in-place mutation is feeding the inputs.
  • Slow initial load → lazy loading, @defer, or SSR, chosen by whether it's a whole route, a heavy section, or first paint itself.
  • UI freeze on a big list → virtual scrolling plus a correct track, so reorders don't destroy and recreate rows.
  • Bundle doubled → compare against a known-good baseline with a bundle analyzer to see what actually grew.
📖 Explanation ▾

Every one of these scenarios starts with the same complaint — "it's slow" — and that's exactly why profiling comes first. The Profiler shows which components get checked, how often, and how long each check takes. If components are checked far more often than their underlying data actually changes, that's change-detection overhead — missing OnPush or fine-grained Signal updates. If the checks themselves are individually slow, look for expensive work sitting directly in a template binding or method call instead of being precomputed or moved into a pure pipe or computed().

A different symptom — a big list freezing the UI — is usually just too many real DOM nodes on screen at once, which change detection alone doesn't explain. Virtual scrolling keeps the actual node count roughly constant regardless of list size, and a correct track (or legacy trackBy) stops reorders from destroying and recreating rows that didn't actually change. Slow initial load is a third, separate question entirely — check the build's bundle size, what isn't lazy-loaded yet that could be, and whether the app is client-side-only when server-side rendering would make first paint visible sooner.

When a bundle has genuinely doubled in size, compare the current build output against a known-good baseline and run a bundle analyzer — the extra weight is usually one new dependency, an import that quietly stopped tree-shaking, or a piece of code that used to be lazy and became eager. Deciding between the loading tools themselves comes down to scope, not preference:

💻 See the code ▾
TypeScript 
@Component({
  selector: 'app-dashboard-widget',
  // profiler showed this widget checked on every tick, data changes every few minutes
  changeDetection: ChangeDetectionStrategy.OnPush // ✅ fix chosen from profiler evidence, not a guess
})
export class DashboardWidgetComponent {}

The comment matters as much as the code — OnPush was chosen because the profiler showed excess checks against rarely-changing @Input data, not because it's a reasonable-sounding default.

TypeScript 
this.widgets.push(newWidget);          // ❌ mutation — OnPush widgets never see this

this.widgets = [...this.widgets, newWidget]; // ✅ new reference — OnPush widgets see it

This is exactly the check the Common Trap above points at — switching to OnPush without fixing an in-place mutation like the first line quietly breaks the update, not the framework.

🌍 Scenario ▾

A dashboard with 300 widget components has grown sluggish over several months, as widgets were added one at a time. Profiling shows most widgets are being checked on every tick despite their underlying data changing only once every few minutes. The direct fix: switch the widget components to OnPush — their data arrives through @Input and rarely changes — verify nothing is still feeding those inputs through an in-place mutation, and re-profile afterward to confirm the check count actually dropped, rather than assuming the fix worked because it "should have."
