Binary Search Tree — why walking left → node → right always comes out sorted

"What's a binary tree vs. a binary search tree, and how do the tree traversals — in-order, pre-order, post-order — actually differ?"

Why it matters ▾
  • The foundation everything else in the Trees section builds on — Balanced Trees, Tries, and Heaps either extend this exact shape or exist to fix its weak spot.
  • "Walk this tree and print it sorted" is a classic in-order-traversal warm-up before deeper tree questions.
  • A frequent follow-on: proving whether a given tree is actually a valid BST (see the Follow-up box).
🔥 Easy interview recall

in-order → left, node, right — sorted order

pre-order → node, left, right — copy / serialize

post-order → left, right, node — delete bottom-up

Think: the BST invariant (left < node < right) is exactly why in-order always comes out ascending.

⚠️ Common Trap

A BST's operations are always O(log n). That only holds while the tree is balanced — insert already-sorted data one at a time with no rebalancing and it degrades into a linked-list shape (height h = O(n)), making search, insert, and delete O(n) too; self-balancing variants like AVL or Red-Black trees (their own Balanced Trees page) exist specifically to prevent this.

🔄 Likely Follow-up

"How would you check if a binary tree is a valid BST?" Checking only that each node beats its immediate left/right child isn't enough — the correct check carries a valid (min, max) range down through the recursion, since a node deep in a subtree must stay within every earlier left- or right-turn ancestor's bound, not just its direct parent's.

🎯 Say this in the interview — the exact lines to land

"A binary tree is a hierarchy where each node has at most two children. A binary search tree adds one rule — everything in the left subtree is smaller, everything in the right subtree is bigger. That rule is why in-order traversal (left, node, right) always visits nodes in ascending sorted order, and why search, insert, and delete run in O(h) — which is only O(log n) if the tree stays balanced."

  • in-order (left, node, right) → always ascending on a BST.
  • pre-order (node, left, right) → copying or serializing the tree's shape.
  • post-order (left, right, node) → safe bottom-up delete, or evaluating an expression tree.
  • O(log n) → only holds if the tree is balanced; a skewed insert order degrades it to O(n).
📖 Explanation ▾

A binary tree is just a hierarchy where every node has at most two children — left and right, nothing fancier. A binary search tree (BST) adds exactly one rule on top of that shape: for every node, everything in its left subtree is smaller, and everything in its right subtree is bigger.

That single rule is what makes search fast: comparing the target against the current node tells you which whole subtree to ignore, so a lookup only ever walks one path from the root down to a leaf. Its cost is proportional to the tree's height, not the number of nodes in it — which is exactly why the tree's actual shape, not just the invariant, decides how fast that lookup really turns out to be.

Walking a tree can happen in different orders, depending on when the current node gets visited relative to its children:

💻 See the code ▾
Pseudocode 
function inorder(node):
    if node == null: return   // base case
    inorder(node.left)             // 1. left first
    visit(node.value)              // 2. then this node
    inorder(node.right)            // 3. then right

Left, then node, then right — on a BST this always visits values in ascending order.

Pseudocode 
function search(node, target):
    if node == null: return false      // fell off the tree
    if target == node.value: return true  // ✅ found
    if target < node.value:
        return search(node.left, target)   // smaller → left
    return search(node.right, target)      // bigger → right

Each comparison throws away one whole subtree — that's what makes search O(h), not the invariant alone.

🌍 Real-world example ▾

A BST is a filing cabinet where every folder already knows its place. Anything smaller than the current folder lives to its left, anything bigger lives to its right — so reading the cabinet left to right (in-order) hands you every folder already sorted, with no separate sorting step needed.
