Error Boundaries — catch render crashes, not everything

"What is an Error Boundary, and what kinds of errors does it NOT catch?"

Why it matters ▾
🛡️ Error Boundary
❗ ProblemWithout anything catching it, a single component throwing during render unmounts the whole React tree, leaving the user with a blank white screen and no way to recover.
✅ SolutionAn Error Boundary — a class component implementing getDerivedStateFromError/componentDidCatch — catches errors thrown while rendering the tree below it and shows a fallback UI instead, but only for that render-time case, not event handlers or async code.
RecallError Boundaries catch render-time crashes only — not event handlers, not async code.
🔥 Easy interview recall

Error Boundaries catch render-time crashes only — not event handlers, not async code.

Think: a thrown error inside onClick sails right past a boundary, untouched.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An Error Boundary does not catch every kind of error in the app. It only catches errors thrown during rendering (and related lifecycle/constructor errors) in the tree below it — errors inside event handlers, async code (a rejected promise, a timer callback), and server-side rendering itself all need their own separate handling; an Error Boundary structurally cannot see them.

🔄 Likely Follow-up

"How do you show a global error UI if an Error Boundary doesn't catch everything?" Wrap the whole app in a top-level Error Boundary for render errors, and separately set up a global handler (window.onerror / unhandledrejection listeners, or a try/catch per async call) for the errors an Error Boundary can't see — funnel both into the same reporting/UI path.

🎯 Say this in the interview — the exact lines to land

"An Error Boundary is a component — implemented with getDerivedStateFromError and componentDidCatch, there's no Hook equivalent — that catches JavaScript errors thrown while rendering its child tree and shows a fallback UI instead of crashing the whole app. It only sees render-time errors; event handlers, async code, and SSR itself need their own try/catch or .catch() instead."

  • Catches render-time errors in the tree below it — logs them, shows a fallback UI.
  • Event handler errors → not caught — needs its own try/catch inside the handler.
  • Async errors (a rejected promise, a timer) → not caught — needs a .catch() at the call site.
  • API/fetch errors → handled at the fetch itself, setting an error state to display — not left to the boundary.
  • A real global error UI needs both a top-level boundary and a separate window.onerror/unhandledrejection handler.
📖 Explanation ▾

An Error Boundary is a component — there's no Hook equivalent as of now, so it has to be a class — that implements static getDerivedStateFromError(error) and/or componentDidCatch(error, info). React calls those when a JavaScript error is thrown anywhere in the render of the child tree below it (rendering itself, plus the lifecycle methods and constructors of that tree), and the boundary swaps in a fallback UI instead of unmounting the whole app with a blank screen.

What it explicitly does not see: an event handler (onClick, onChange, …) runs as ordinary JavaScript outside of React's render call stack, so a throw inside one never reaches the boundary. The same is true for async code — a rejected promise or a setTimeout callback fires after React has already finished that render pass — and for server-side rendering itself. Each of those needs its own handling: a try/catch around the handler, a .catch() on the promise.

API errors follow the same pattern — they're normally handled right where the request is made (try/catch or .catch(), setting an error state to render), not left for a boundary to notice. A genuinely global error UI needs both pieces at once: a top-level Error Boundary for render errors, and a separate window.onerror/unhandledrejection handler (or per-call try/catch) for everything a boundary structurally can't see — production logging should funnel both into the same reporting service.

Error sourceCaught by an Error Boundary?
Render (incl. lifecycle methods, constructors)✅ yes
Event handlers (onClick, onChange, …)❌ no — needs its own try/catch
Async code (promise, setTimeout, fetch callback)❌ no — needs .catch()
Server-side rendering itself❌ no — separate handling required
💻 See the code ▾
JSX 
class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    return { hasError: true };  // flips state so the next render shows the fallback
  }

  componentDidCatch(error, info) {
    logErrorToService(error, info);  // send it to your reporting service
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;  // fallback UI
    }
    return this.props.children;  // render children normally
  }
}

getDerivedStateFromError + componentDidCatch are what make this an Error Boundary — there's no Hook equivalent as of now.

JSX 
function SubmitButton() {
  const handleClick = () => {
    try {
      submitOrder();  // may throw — this is an event handler, not a render
    } catch (err) {
      logErrorToService(err);   // the ErrorBoundary above CANNOT see this
      showInlineError();        // handle it here instead
    }
  };

  return (
    <button onClick={handleClick}>Submit</button>
  );
}

This throw happens inside a click handler, not during render — the Error Boundary above it never sees it.

🧭 Use Cases — recognize these when they happen to you ▾
1 A component throws while it's rendering, like BuggyList above

This is the boundary doing exactly the job it exists for — the throw happens during render, so getDerivedStateFromError/componentDidCatch fire and the fallback UI replaces the crash instead of blanking the whole app.

RememberRender-time throw → the one case an Error Boundary was actually built to catch.
2 The throw happens inside an event handler, like SubmitButton's onClick

The handler runs as ordinary JavaScript outside React's render call stack, so the boundary above it never even sees the error — it needs its own try/catch right at the handler, same as the SubmitButton example.

RememberEvent handler throw → the nearest Error Boundary isn't watching; wrap it yourself.
3 You wrap the whole app in a top-level boundary and assume that now covers everything

A great interview trap — a top-level Error Boundary only ever catches render-time crashes in the tree below it; a rejected fetch promise or an async callback still needs its own .catch() or a global window.onerror/unhandledrejection handler, boundary or no boundary.

RememberOne top-level boundary ≠ full error coverage — async/API errors still need their own handling.
🌍 Real-world example ▾

A building's fire suppression system only activates for fires inside the building itself. An Error Boundary works the same way — it only catches problems inside its own "building" (the render tree below it). It does nothing for someone getting hurt outside on the sidewalk (an event handler or async error) — that needs its own, separate first-aid plan: a try/catch or .catch() at the point it actually happens.
