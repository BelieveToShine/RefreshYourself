'use client' — a boundary, not a "browser-only" switch

"Does 'use client' mean a component only runs in the browser?"

Why it matters ▾
🚧 'use client'
❗ ProblemSomething in a component tree needs useState, an event handler, or a browser API — but without a clear signal, Next.js has no way to know which files are allowed to ship that kind of code to the browser.
✅ Solution'use client' at the top of a file marks the boundary where the module tree switches from server-only to client-capable — everything that file imports becomes part of the client bundle from that point down.
Recall'use client' = "allowed to hydrate," not "server never touches this."
🔥 Easy interview recall

'use client' = "this file, and everything below it, may hydrate in the browser."

Think: it still renders on the server first for the initial HTML — the directive only unlocks what happens after that.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

'use client' does not mean a component only runs in the browser. It doesn't opt a component out of server rendering — the initial HTML is still server-rendered; 'use client' only enables hydration and interactivity afterward.

🔄 Likely Follow-up

"Where should the 'use client' boundary actually be drawn — top of the tree or as low as possible?" As low/small as possible — marking only the specific interactive leaf component, not an entire page, keeps the rest of the tree as zero-JS Server Components, minimizing the client bundle.

🎯 Say this in the interview — the exact lines to land

"'use client' marks the boundary where a module tree switches from server-only to client-capable — it doesn't mean the component only runs in the browser. It still does an initial server render for its HTML; the directive just allows it, and everything it imports, to also hydrate and use client-only features afterward."

  • 'use client' → allowed to hydrate, not "server never touches this."
  • Everything imported below it → also joins the client bundle, unless passed in as children.
  • Boundary placement → as low/small as possible, to keep the client bundle minimal.
📖 Explanation ▾

'use client' is a file-level directive — the very first line of a module. It doesn't describe what that one component does; it draws a boundary in the module graph. Everything that file imports, directly or indirectly, becomes part of the client bundle from that point down (a Server Component can still be passed in as children/a prop from above the boundary, without crossing it).

The component under 'use client' still renders once on the server, the same as any other component — that's how the initial HTML reaches the browser at all. What the directive actually unlocks is everything that happens after: hydration, React state, effects, event handlers, browser-only APIs.

Because everything below the boundary gets pulled in, where you draw it matters a lot. A 'use client' on a small leaf component (a single button) keeps the client bundle tiny. The same directive placed near the root of a large subtree drags everything underneath it into the bundle too — even parts that never needed to be there.

💻 See the code ▾
JSX 
// Content.jsx — no directive, Server Component
import LikeButton from './LikeButton';

export default function Content({ post }) {
  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton />  // ✅ only this one small island hydrates
    </article>
  );
}

The boundary sits on LikeButton alone — Content and its article markup stay server-only.

JSX 
'use client';  // ❌ placed on Content instead — drags the whole article into the bundle

import LikeButton from './LikeButton';

export default function Content({ post }) {
  return <article><h1>{post.title}</h1><LikeButton /></article>;
}

Now Content and LikeButton both ship JS — the article markup gained no new behavior, just extra bytes.

🧭 Use Cases — recognize these when they happen to you ▾
1 Only one small widget on the page needs state

Put 'use client' directly on that widget's own file, as deep in the tree as it can go — never on a parent "just to be sure." This is the #1 scenario you'll actually run into.

RememberOne interactive leaf → directive on that leaf, nowhere higher.
2 A whole page is a genuinely interactive dashboard

If nearly every piece of the page genuinely needs state or live updates, a higher boundary isn't a mistake — it just means that page really is mostly client-rendered, and there isn't much server-only content to lose.

RememberGenuinely all-interactive page → a high boundary isn't wrong, just honest.
3 A layout file gets 'use client' added to fix one error

A layout sits near the root of the whole app — marking it 'use client' forces every page it wraps into the client bundle. The actual fix is almost always to push the directive down onto the one small piece that needed it.

RememberError "fixed" by adding the directive high up → push it down to the real leaf instead.
🌍 Real-world example ▾

It's a door into one room, not a switch for the whole building. 'use client' opens that one room (and anything placed inside it) up to the client — the rest of the building keeps running exactly as it did before, server-only.
