output: 'standalone' — why your Docker image doesn't need the whole project

"What does output: 'standalone' actually do, and why does it matter for Docker?"

Why it matters ▾
🐳 Standalone output
❗ ProblemDocker-izing a Next.js app by copying the whole project — full node_modules, dev dependencies and all — produces a needlessly large image and slower deploys.
✅ Solutionoutput: 'standalone' in next.config.js traces only the dependencies actually used and produces a minimal, self-contained build — ideal as the basis for a small, efficient Docker image.
Recallstandalone = trace what's actually used, skip the rest.
🔥 Easy interview recall

standalone output = "only the files your server genuinely needs to run."

Think: packing for a trip with a checklist, not hauling the whole closet.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Docker-izing by copying the whole project, including full node_modules and dev dependencies, isn't harmless. It produces a needlessly large image and slower deploys for no functional benefit over output: 'standalone'.

🔄 Likely Follow-up

"Does self-hosting lose access to Server Actions, Middleware, or ISR?" No — all of those are framework-level features that run on any Node.js-capable (or Edge-Runtime-capable, for Middleware) host; self-hosting doesn't disable core Next.js functionality, just some platform-specific infrastructure optimizations unique to Vercel's own hosting.

🎯 Say this in the interview — the exact lines to land

"output: 'standalone' produces a minimal build that traces only the dependencies actually used, instead of the whole node_modules tree — I'd COPY just that traced output into a slim Docker image, rather than the entire project."

  • output: 'standalone' → traces only the dependencies actually used.
  • Naive full-project copy → needlessly large image, slower deploys.
  • Self-hosting → Server Actions, Middleware, ISR all still work on a Node/Edge-capable host.
  • What's lost → only Vercel-specific hosting infrastructure optimizations, not core functionality.
📖 Explanation ▾

output: 'standalone' in next.config.js tells next build to additionally produce a self-contained output folder — the server files, plus only the node_modules entries that build actually traced as used, copied in automatically. It's meant to be the thing you COPY into a container, not the whole repository.

Without it, a naive Dockerfile copies the entire project — full node_modules (including dev-only dependencies never needed at runtime) and everything else in the repo — into the image. The app still runs, but the image is larger than it needs to be, and every deploy pays for rebuilding/pushing that extra weight.

Self-hosting this way doesn't give up any framework capability — Server Actions, Middleware, and Incremental Static Regeneration are all things the Next.js server itself handles, and that server runs the same way inside your own container. What's genuinely Vercel-specific is infrastructure-level optimization (their own edge network, their own caching layer tuning) — not a feature of Next.js itself being withheld.

💻 See the code ▾
JS 
// next.config.js
module.exports = {
  output: "standalone", // ✅ produces .next/standalone, traced deps only
};

One config line — the rest of the win comes from what you COPY in the Dockerfile.

Dockerfile 
# ❌ naive: copies the whole project, including full node_modules
COPY . .
RUN npm install && npm run build

# ✅ copy only the standalone traced output
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static

The second form ships only what next build already proved the server needs.

🌍 Real-world example ▾

Your team is moving off Vercel to self-host on its own infrastructure. The app's behavior doesn't change — Server Actions, Middleware, and ISR all keep working on any Node.js-capable host. The thing actually worth engineering carefully is the Docker image itself, and output: 'standalone' is the one-line change that keeps it small.
