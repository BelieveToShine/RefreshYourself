EXISTS vs. IN vs. JOIN — filtering looks the same, until a NULL shows up

"EXISTS vs. IN vs. a JOIN for filtering on a related table — how do they differ once NULL values are involved?"

Why it matters ▾
  • All three look interchangeable for "find rows related to another table" — but they check different things and fail in different ways.
  • Comes up any time a query filters by "has a matching row" instead of returning that row's own columns.
  • A very common follow-up: why a seemingly correct NOT IN query returns nothing at all.
🔥 Easy interview recall

IN → compares the value to a list

EXISTS → checks if any row comes back

JOIN → returns matched rows (can duplicate)

Think: NOT IN + a NULL in the list → matches nothing, silently NOT EXISTS → never has that problem

⚙️ EXISTS vs. IN vs. JOIN — the runtime mechanic
⚠️ Common Trap

NOT IN behaves like NOT EXISTS. It doesn't — WHERE CustomerId NOT IN (SELECT CustomerId FROM Orders) compares against every value the subquery returns, and comparing against a single NULL makes that whole condition UNKNOWN (not false) for every outer row, so the query can return zero rows even when it obviously shouldn't; NOT EXISTS never compares values, so it's immune.

🔄 Likely Follow-up

"Why does WHERE CustomerId NOT IN (SELECT CustomerId FROM Orders) sometimes return zero rows even when it clearly shouldn't?" Because at least one row in Orders.CustomerId is NULL — NOT IN checks the outer value against every item in that list, and a NULL in the list turns the comparison UNKNOWN for every row, so nothing passes. Rewriting it as NOT EXISTS (or filtering the NULLs out first) fixes it.

🎯 Say this in the interview — the exact lines to land

"IN compares the outer value against a list or subquery result, EXISTS only checks whether a correlated subquery returns any row at all — it never compares values, so it's immune to NULLs — and a JOIN combines and returns matching rows directly, which means it can duplicate outer rows when there's more than one match. The gotcha is NOT IN against a subquery that can return NULLs: it can silently return zero rows, which NOT EXISTS never does."

  • IN → compares the actual value against a list or subquery result.
  • EXISTS → only checks that a row comes back — no value comparison, so NULLs inside the subquery don't matter.
  • JOIN → can duplicate outer rows when the related table has more than one match — IN and EXISTS never do.
  • NOT IN with a NULL in the list → silently returns zero rows, because the comparison becomes UNKNOWN for every row.
  • Optimizer performance → IN and EXISTS are usually similar today — "IN is always slower" is outdated; the NULL gotcha is the real, still-current risk.
📖 Explanation ▾

IN takes the outer column's value and checks it against a fixed list or a subquery's result set — it's a value comparison, plain and simple. EXISTS doesn't compare values at all: it runs a correlated subquery per outer row and asks only "did anything come back?" — a pure yes/no, so what the subquery actually returns (including a NULL) never gets compared against anything. A JOIN works differently again — it combines rows from both tables directly wherever the join condition matches, so it returns actual data, not just a filter decision.

That last difference matters beyond style: IN and EXISTS only ever filter the outer rows, so the outer row count can shrink but never grow. A JOIN has no such guarantee — if one customer has three matching orders, an inner join returns that customer three times, once per order. On speed, modern query optimizers commonly rewrite IN and EXISTS into the same semi-join plan, so treating one as categorically slower than the other is outdated. The one thing optimizer improvements never fixed is the NOT IN plus NULL behavior above — that's a logical consequence of three-valued NULL comparison, not a performance detail, so no smarter query plan makes it go away.

💻 See the code ▾
SQL 
-- Customers who have placed at least one order
SELECT Name FROM Customers
WHERE Id IN (SELECT CustomerId FROM Orders); -- ✅ compares Id against the list

SELECT Name FROM Customers c
WHERE EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerId = c.Id); -- ✅ just checks a matching row exists

Same result here — IN compares values, EXISTS only checks that a row exists.

SQL 
-- Orders.CustomerId has one NULL row (e.g. a guest checkout)
SELECT Name FROM Customers
WHERE Id NOT IN (SELECT CustomerId FROM Orders); -- ❌ returns ZERO rows — one NULL breaks the whole list

SELECT Name FROM Customers c
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerId = c.Id); -- ✅ still works — never compares values

One NULL in Orders.CustomerId makes NOT IN match nothing. NOT EXISTS is unaffected because it never compares values.

SQL 
-- A customer with 3 matching orders
SELECT c.Name FROM Customers c
JOIN Orders o ON o.CustomerId = c.Id; -- ⚠️ one row PER matching order — duplicates possible

Unlike IN/EXISTS, a JOIN returns one row per match — add DISTINCT, or use EXISTS if you only need a yes/no filter.

🌍 Real-world example ▾

Your "customers with no orders" report suddenly comes back empty — but the UI clearly shows unmatched customers. A bad import left one guest-checkout row in Orders with a NULL CustomerId, and the report's WHERE CustomerId NOT IN (SELECT CustomerId FROM Orders) silently breaks the moment that single NULL lands in the list. Swapping it for NOT EXISTS fixes the report without changing what it's actually asking for.
