Kestrel — capable enough to face the internet alone, almost never left to do it

Is Kestrel meant to be exposed directly to the internet, and what does a reverse proxy actually add?

Why it matters ▾
📡 Kestrel Alone
❗ ProblemRunning Kestrel by itself means your app manages its own TLS certificate, serves static files with no edge cache, runs as one instance with no load balancing, and takes traffic directly with no rate-limiting buffer — a crash just stays down until something outside the process restarts it.
✅ SolutionThat's acceptable only in narrow cases — local development, or a simplified setup where something upstream already terminates TLS and just forwards plain HTTP in.
RecallKestrel alone = your app owns cert management, caching, balancing, protection, and recovery itself.
🛡️ Kestrel + Reverse Proxy
❗ ProblemLeft running alone under real production traffic, Kestrel has no answer for centralizing certs across many instances, caching static content at the edge, spreading load, or recovering after a crash.
✅ SolutionA reverse proxy in front takes over all of it: centralizes and rotates TLS certs, caches static content at the edge, load-balances across Kestrel instances, buffers/rate-limits traffic, and restarts a crashed process while draining connections gracefully.
RecallReverse proxy = certs + caching + balancing + protection + recovery — Kestrel just serves.
🔥 Easy interview recall

Kestrel alone → can serve traffic, does the bare minimum

Proxy in front → adds certs, balancing, caching, protection

Think: Kestrel is the engine. The reverse proxy is the rest of the car — brakes, lights, bumpers — you don't take onto the highway without them.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A reverse proxy isn't there because Kestrel is insecure. Kestrel can terminate TLS itself — the proxy is standard practice for operational reasons (cert management at scale, load balancing, edge caching, DDoS-style buffering), not because Kestrel can't be trusted with HTTPS.

🔄 Likely Follow-up

"If Kestrel sits behind a reverse proxy, what does the app need to know to behave correctly?" It needs UseForwardedHeaders() — without it, the app reads the proxy's own IP and protocol as if they were the real client's, breaking HTTPS-redirect logic and request logging alike.

🎯 Say this in the interview — the exact lines to land

"Kestrel is a real, capable HTTP server — it can serve traffic directly — but the near-universal practice is to front it with a reverse proxy like IIS, Nginx, or a cloud load balancer, because Kestrel deliberately leaves TLS management at scale, load balancing, edge caching, and DDoS-style protection to infrastructure built for those jobs, not to itself."

  • Kestrel → a capable, cross-platform HTTP server built into ASP.NET Core, not a toy.
  • Reverse proxy → owns cert management, load balancing, caching, and traffic protection — jobs Kestrel deliberately skips.
  • Not a security patch → Kestrel can terminate TLS itself; fronting it is an operational default, not a fix for something unsafe.
  • Behind a proxy → call UseForwardedHeaders() so the app reads the real client IP and protocol, not the proxy's.
  • Process recovery → a proxy or process manager restarts a crashed Kestrel process and drains it gracefully during deploys.
📖 Explanation ▾

A separate Intermediate page, What Happens When a .NET App Starts, already covers Kestrel as the embedded HTTP server that app.Run() starts listening on. This page assumes that and goes one level deeper: Kestrel is genuinely fast, cross-platform, and capable — it can terminate TLS itself, and in some simplified containerized setups it's exposed directly behind a cloud load balancer that already handles TLS and just forwards plain HTTP internally.

Even so, the default recommendation is still to put something in front of it in production. A reverse proxy centralizes and rotates certificates for many backend apps instead of managing one per instance, serves and caches static content at the edge before it ever reaches app code, spreads traffic across multiple Kestrel instances, and buffers or rate-limits requests before they reach app logic at all.

Kestrel's own design is deliberately minimal — it does HTTP serving well and leaves those broader operational concerns to infrastructure built specifically for them, rather than reinventing load balancing or process supervision inside the app server. That includes recovery: a proxy or process manager can restart a crashed Kestrel process and drain connections gracefully during a deploy, which Kestrel does not do for itself.

💻 See the code ▾
C# 
var app = builder.Build();

// ❌ without this, behind a proxy every request looks like it's from the proxy
app.UseForwardedHeaders(new ForwardedHeadersOptions
{
    ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto
});

app.MapGet("/", (HttpContext ctx) =>
    $"Client IP: {ctx.Connection.RemoteIpAddress}"); // ✅ now the real client, not the proxy

Without UseForwardedHeaders(), RemoteIpAddress and the request's scheme both belong to the proxy, not the caller — breaking IP-based logging and HTTPS-redirect checks alike.

C# 
builder.WebHost.ConfigureKestrel(options =>
{
    options.ListenAnyIP(443, listenOptions =>
    {
        listenOptions.UseHttps("cert.pfx", "password"); // Kestrel CAN do this itself
    });
});

This proves Kestrel really can terminate TLS on its own — fronting it with a proxy is a deliberate operational choice, not a workaround for something Kestrel can't do.

C# 
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    // ❌ trusting every proxy blindly is a security hole
    options.KnownProxies.Add(IPAddress.Parse("10.0.0.5")); // ✅ only trust proxies you actually run
});

Blindly trusting forwarded headers from anyone lets a malicious client fake its own IP or protocol — only trust headers coming from a proxy you actually control.

🧭 Use Cases — recognize these when they happen to you ▾
1 Every request in your logs shows the proxy's IP, not the caller's

Kestrel reads the IP address and scheme straight off its own TCP connection — which belongs to whatever sits directly in front of it. Without UseForwardedHeaders(), that's the proxy on every request, breaking IP-based logging and looping any HTTPS-redirect check that trusts the connection's scheme. This is the #1 scenario you'll actually run into.

RememberNo UseForwardedHeaders() → the proxy's IP and protocol, not the caller's.
2 Your app runs in a container behind a cloud load balancer that already terminates TLS

Kestrel only ever sees plain HTTP forwarded in — the cloud load balancer is filling the reverse-proxy role here, even though it isn't Nginx or IIS. The app still needs UseForwardedHeaders() to know the original request actually arrived over HTTPS.

RememberA cloud load balancer in front still counts as "behind a proxy."
3 A traffic spike hits and one Kestrel instance can't keep up

A single Kestrel process has no built-in way to spread requests across other instances or buffer/rate-limit a surge before it reaches app code — spreading load and absorbing spikes is exactly the job a reverse proxy in front is built for.

RememberScaling and buffering traffic → the proxy's job, not Kestrel's.
🌍 Real-world example ▾

Your app sits behind a cloud load balancer that already terminates TLS and forwards plain HTTP to Kestrel — and now every request in your logs comes from the load balancer's own IP, while HTTPS-redirect middleware keeps looping. Both symptoms trace back to the same missing piece: UseForwardedHeaders(). Once it's wired up, Kestrel reads the real client IP and protocol from X-Forwarded-For / X-Forwarded-Proto instead of the load balancer's own connection details, and both the redirect loop and the wrong-IP logs disappear.
