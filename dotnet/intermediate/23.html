Bad config — crash at startup, or fail on the first request?

"How do you make the app fail at startup if a config section is invalid?"

Why it matters ▾
🧩 Options validation
❗ ProblemA missing or wrong config value usually isn't noticed at startup — it blows up later, on whichever request first reads it, often in production.
✅ SolutionBind the section to an options class and validate it; with ValidateOnStart() the app refuses to start on bad configuration.
RecallBad config should fail the deploy, not a customer.
🔥 Easy interview recall

Bind it, validate it, validate on start.

Think: ValidateDataAnnotations() → rules come from attributes like [Required] ValidateOnStart() → checked when the host starts, not on first use

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Thinking ValidateDataAnnotations() alone checks at startup. It doesn't — by default validation runs lazily, the first time the options value is read. Add ValidateOnStart() to move the check to host startup.

🔄 Likely Follow-up

"How do you validate a rule that attributes can't express?" Use .Validate(predicate, message) for a quick rule, or implement IValidateOptions<T> for a reusable validator that can take dependencies — it returns ValidateOptionsResult.Fail(...) or Success.

🎯 Say this in the interview — the exact lines to land

"I bind the section with AddOptions<T>().Bind(...), add ValidateDataAnnotations for attribute rules or an IValidateOptions<T> for custom ones, and finish with ValidateOnStart — so invalid configuration stops the app at startup with an OptionsValidationException instead of failing on a later request."

  • .Bind(section) → maps configuration into a typed class.
  • ValidateDataAnnotations() → attribute rules such as [Required] and [Range].
  • IValidateOptions<T> → custom rules, registered in DI.
  • ValidateOnStart() → fails at host startup, not on first use.
  • Failure → an OptionsValidationException that names what failed.
📖 Explanation ▾

The options pattern turns a configuration section into a typed class. AddOptions<T>().Bind(section) does the binding, and you can chain validation onto the same builder. Where the values come from, and how options lifetimes differ, is on Configuration Sources; this page is only about rejecting bad values.

By default, validation is lazy: it runs when the options value is first read, and a failure throws an OptionsValidationException right there — maybe in the middle of a request. ValidateOnStart() asks the host to validate during startup instead, so a bad value stops the app before it serves anything. That is the same "startup failures happen before Kestrel listens" idea from What Happens When a .NET App Starts.

ValidateDataAnnotations() reads attributes on the options class. For anything else, add .Validate(predicate, message), or write a class implementing IValidateOptions<T> and register it in DI — useful when the rule is reused or needs another service.

💻 See the code ▾
C# 
public class SmtpOptions
{
    [Required] public string Host { get; set; } = "";
    [Range(1, 65535)] public int Port { get; set; }
    public bool UseTls { get; set; }
}

builder.Services.AddOptions<SmtpOptions>()
    .Bind(builder.Configuration.GetSection("Smtp"))
    .ValidateDataAnnotations()   // rules from the attributes
    .ValidateOnStart();          // ✅ checked when the host starts

Bind, validate with attributes, then move the check to startup.

C# 
public class SmtpValidator : IValidateOptions<SmtpOptions>
{
    public ValidateOptionsResult Validate(string? name, SmtpOptions o)
        => o.Port == 25 && !o.UseTls
            ? ValidateOptionsResult.Fail("Port 25 needs TLS")   // ❌ startup throws
            : ValidateOptionsResult.Success;
}

builder.Services.AddSingleton<IValidateOptions<SmtpOptions>, SmtpValidator>();

A custom validator handles the rule attributes can't express — it runs together with the other validation.

C# 
builder.Services.AddOptions<SmtpOptions>()
    .Bind(builder.Configuration.GetSection("Smtp"))
    .ValidateDataAnnotations();   // ❌ no ValidateOnStart — only checked on first use

Without ValidateOnStart(), a bad value hides until something reads the options.

🌍 Real-world example ▾

A production deploy is missing the SMTP__HOST environment variable. Without ValidateOnStart() the app looks healthy until the first password-reset email fails. With it, the container fails at startup and the rollout stops before any user is affected.
