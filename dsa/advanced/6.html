100 million records — will it fit, and what do you even ask next?

"You have 100 million records — can you keep them all in memory? How would you find the shortest path at scale? When does O(n) become unacceptable?"

Why it matters ▾
  • An interviewer asking "how would this work at scale" is checking whether you estimate real numbers before proposing a fix — not fishing for a brand-new algorithm.
  • It's the natural follow-up on almost any DSA topic once the dataset gets big enough — the same knowledge map, just walked at a size where guessing stops working.
  • A common trap for anyone who treats a clean Big-O as proof something will actually run fast enough in production.
🔥 Easy interview recall

"Does it fit?" → do the math, don't assume it

"Fast enough?" → depends on how often it runs

"Need something new?" → usually no — route to what you already know

Think: every "at scale" question is really "estimate first, then route to a technique already on this track" — not a request for an exotic new algorithm.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reciting a technique's Big-O is not the same as answering "will this scale." "It's O(n log n)" says nothing about whether n is 10 thousand or 10 billion, or whether it runs once or on every request — plug in the real numbers before trusting the complexity class.

🔄 Likely Follow-up

"Your solution works for 1 million records — will it still work for 1 billion?" Redo the size estimate at the new scale (a working set that fit in memory at 1M may not at 1B), check whether the per-operation constant factor now matters more, and ask whether a single-machine approach needs to become chunked or distributed — the exact same estimate-then-route reasoning, just re-run at 1000x.

🎯 Say this in the interview — the exact lines to land

"First I'd size it: 100 million records at roughly 1KB each is about 100GB, which almost never fits comfortably in memory, so the real question becomes what I actually need to do with it. For shortest path at millions of nodes, Dijkstra is still correct, but real systems layer extra techniques like precomputed hierarchies or bidirectional search on top of it to stay fast. And O(n) isn't automatically fast enough — that depends on how often it runs and the latency budget, not just the complexity class."

  • 100M records won't fit → estimate the size first, then ask what operation is actually needed.
  • Need the full order → external sort, not an in-memory sort.
  • Need existence or top-K only → Bloom filter or bounded heap, no full pass needed.
  • Shortest path at millions of nodes → Dijkstra alone isn't the whole answer — real systems add hierarchies or bidirectional search on top.
  • O(n) "fast enough"? → depends on how often it runs, not on the complexity class alone.
📖 Explanation ▾

100 million records at roughly 1KB each is about 100,000,000 × 1KB ≈ 100GB. A single machine's real RAM is typically far below that, so the honest first answer is that it almost certainly does not comfortably fit — which makes the real interview question "what do I actually need to do with these records," not "how do I fit them." A full sort needs an external sort (the "External / Distributed Processing" page, topic 5 in this tier); checking existence or duplicates needs a Bloom filter; keeping only the best few needs a bounded top-K heap (both on the "Streaming / Large-Dataset Problems" page, topic 4); and a plain total or count needs nothing more than a single streaming pass over the data.

Shortest path at real scale — a road network with millions of nodes and edges — is where plain Dijkstra's algorithm stays correct but its cost starts to matter: O((V+E) log V) is fine on a moderate graph, and genuinely slow once V and E are both in the millions. Real-world routing systems layer extra techniques on top of Dijkstra — precomputed hierarchies, bidirectional search, and other domain-specific speedups — to keep queries fast at that size. Naming that such techniques exist is the honest answer here; teaching any one of them in depth is beyond this track's fundamentals.

O(n) is often treated as "the good, fast answer," but that only holds up if you check how often it runs. Scanning a dataset once, occasionally, is fine; scanning it on every incoming request with a tight millisecond budget usually isn't — the fix is normally a precompute-once technique already on this track ( Prefix Sum & Difference Array's "O(n) once, O(1) per query" idea, or a hash-map lookup), not a different algorithm. Big-O alone never says whether something is fast enough — that depends on the system the algorithm lives inside, not the complexity class by itself.

💻 See the code ▾
C# 
long records = 100_000_000;              // 100M
long bytesEach = 1024;                    // ~1KB per record
long totalBytes = records * bytesEach;    // ≈ 100 GB

long ramAvailable = 32L * 1024 * 1024 * 1024; // e.g. a 32GB box
bool fitsInMemory = totalBytes <= ramAvailable; // ❌ false — 100GB > 32GB

The number that actually answers the question is 100GB vs. 32GB — not the phrase "big data."

C# 
// ❌ O(n) work repeated on every single request
int SumRange(int[] data, int i, int j)
{
    int total = 0;
    for (int k = i; k <= j; k++) total += data[k]; // re-scans every call
    return total;
}

// ✅ O(n) once, O(1) per request after that
int[] prefix = BuildPrefixSum(data);       // precompute once
int FastSumRange(int i, int j) =>
    i == 0 ? prefix[j] : prefix[j] - prefix[i - 1]; // one subtraction

Same operation, same per-call Big-O idea — the difference is when the O(n) work happens: once up front, or all over again on every request.

🌍 Real-world example ▾

An interviewer says "we have 100 million user records and need to find duplicates — walk me through it." The right first move, out loud: estimate the total size (100M × ~1KB ≈ 100GB), state plainly that this is unlikely to fit in a typical machine's RAM, then ask what "find duplicates" really needs — an exact answer needs an external sort or a hash-based external pass, while a "good enough, low false-positive" answer can use a Bloom filter instead. That sequence — estimate, compare, then route to a known technique — is the actual signal being graded, not which specific technique gets named first.
