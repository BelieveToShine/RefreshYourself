Scenario: HashMap Behaves Unexpectedly with a Mutable Key

"A custom object is used as a HashMap key. After modifying one of its fields, the entry becomes difficult to retrieve. Why?"

Why it matters ▾
🗝️ Mutable HashMap Key
❗ ProblemAn entry looks like it should be right there — the exact same object reference is used for the lookup — yet map.get(key) returns null, and the data is silently stuck, unreachable through the normal API.
✅ SolutionA HashMap decides a key's bucket from its hashCode() at insertion time. Mutating a field the key's hashCode() depends on changes what that method now returns, so a later lookup computes a different bucket than where the entry actually lives.
RecallThe bucket is fixed at insertion time — mutate a hash-affecting field afterward and the key points at the wrong bucket forever.
🔥 Easy interview recall

HashMap bucket = hashCode() at insertion time. Mutate a field used in hashCode() after that, and the key now points at the wrong bucket.

Think: the entry doesn't move when the key changes — only the key's own compass starts pointing somewhere else.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The entry isn't "lost" or moved — it never leaves bucket 3. What breaks is the key's own hashCode(), which now resolves to bucket 7, so every lookup searches the wrong place; the map itself didn't rehash or relocate anything.

🔄 Likely Follow-up

"Would iterating the whole map still find the entry?" Yes — entrySet()/values() walk every bucket directly and don't call hashCode() at all, so the entry is still there and still visible; only hash-based lookups (get, containsKey, remove) are broken, because only those recompute the key's hash to pick a bucket.

🎯 Say this in the interview — the exact lines to land

"A HashMap picks a key's bucket from hashCode() at insertion time. If a field that hashCode() uses gets mutated afterward, the key now computes a different hash, so get() looks in the wrong bucket and never finds the entry — it's not lost, it's just unreachable through the hash path."

  • Bucket choice → fixed once, at insertion, from that moment's hashCode().
  • Mutating a hash-affecting field → changes what hashCode() returns, not where the entry sits.
  • Fix → never use a mutable object as a key; base equals()/hashCode() only on fields that never change after insertion.
  • A safe alternative → an immutable key class, or a record, so hashCode() can never drift after insertion.
📖 Explanation ▾

HashMap doesn't search its buckets by comparing every stored key with equals() — that would be slow. Instead, it calls the key's hashCode() once, turns that number into a bucket index, and only compares equals() against the few keys already sitting in that one bucket. This is exactly what makes HashMap fast, and exactly what breaks when a key mutates: the bucket decision was made and is never revisited.

When a field feeding that key's hashCode() changes after insertion, nothing about the stored entry moves — it is still physically sitting in its original bucket. What changes is what hashCode() now returns when called again on a lookup. get(key) computes a bucket from the current, mutated state, walks into that (likely different, often empty) bucket, and reports no match — even when the exact same object reference is passed in.

This is why the standard advice is so blunt: don't use a mutable object as a HashMap key unless you're certain its equals()/ hashCode() fields never change for the lifetime of that entry. A key built from fields that are set once in the constructor and never touched again — or a record, which is immutable by construction — never has this failure mode.

💻 See the code ▾
Java 
class Point {
    int x, y; // ❌ mutable — part of equals()/hashCode()

    @Override
    public int hashCode() { return Objects.hash(x, y); }
}

Map<Point, String> map = new HashMap<>();
Point p = new Point(1, 1);
map.put(p, "origin");   // stored using hashCode() for (1,1)
p.x = 99;                   // ❌ mutated — hashCode() now different
map.get(p);                  // ❌ returns null — looks in the wrong bucket

Same reference, same equals() logic — but hashCode() now returns something else, so the lookup bucket is wrong.

Java 
record Point(int x, int y) {} // ✅ immutable — fields can never change

Map<Point, String> map = new HashMap<>();
map.put(new Point(1, 1), "origin");
map.get(new Point(1, 1)); // ✅ "origin" — hashCode() can never drift

A record (or any key with fields set once and never reassigned) can't drift — its hashCode() is identical for its whole life.

🧭 Use Cases — recognize these when they happen to you ▾
1 A cache keyed by a mutable DTO stops returning hits after the DTO is updated in place

An in-memory cache keyed by an entity object silently "forgets" entries whenever a cached field used in equals()/hashCode() is edited after the object was cached. The cache doesn't break loudly — it just looks like a lower hit rate, which is easy to misdiagnose as something else entirely.

RememberA falling cache hit rate with no code change is a classic symptom of a mutable cache key.
2 A key stored inside a Set appears to "duplicate" after being mutated and re-added

A HashSet has exactly the same bucket mechanism as HashMap. Mutate an object already stored in the set, and contains() stops finding it — a careless re-add then creates what looks like a duplicate, even though it's the same underlying problem: the element's hash moved, the set's bucket for it didn't.

RememberHashSet uses the exact same bucket logic as HashMap — mutable elements have the identical failure mode.
3 A code review correctly flags a mutable field inside an equals()/hashCode() pair before it ships

This is the scenario worth aiming for: a reviewer sees a class with a setter used as a key type, or fields feeding hashCode() that aren't final, and asks for it to be made immutable — a record, or a class with only a constructor and getters — before it ever ships as a map or set key.

RememberThe real fix is caught in review, not in production — make key classes immutable by construction.
🌍 Real-world example ▾

A session object is used as a HashMap key, and its status field (included in hashCode()) is updated in place as the session moves through its lifecycle. After that update, sessionMap.get(session) starts returning null for the exact same reference that was inserted — the entry is still in the map, just in a bucket the key's new hash no longer points at.
