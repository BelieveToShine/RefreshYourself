Strategy Pattern vs. Conditional Logic — the switch that never stops growing

What problem does the Strategy pattern solve, and how is it better than a growing switch statement?

Why it matters ▾
  • Interviewers use this to see whether you reach for polymorphism instead of a conditional that grows every time a new case shows up.
  • Comes up anywhere behavior varies by type — payment methods, shipping options, pricing rules, notification channels.
  • A common opener right after Open/Closed Principle, since Strategy is literally the pattern OCP's switch example resolves into.
🔥 Easy interview recall

Switch → caller decides every time

Strategy → caller just calls the interface

Think: new payment type with a switch means edit existing code; new payment type with Strategy means add one class.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Moving the switch into a factory method is not Strategy. If that factory still branches on a string or enum to decide which class to build, the conditional logic didn't disappear — it just moved; real Strategy means the caller never branches once it's holding the right IPaymentProcessor.

🔄 Likely Follow-up

"How does the caller actually get the right IPaymentProcessor without writing its own switch?" A small factory, a DI container keyed by type, or a dictionary lookup makes that one choice — which is exactly the next question: Factory vs. Dependency Injection.

🎯 Say this in the interview — the exact lines to land

"Strategy lets you swap an algorithm or behavior at runtime without a growing conditional — CreditCardPayment, PayPalPayment, and BankTransferPayment each implement the same IPaymentProcessor, and the caller just calls processor.Pay(amount) instead of branching on a type string."

  • Growing switch → every new case means editing existing code and re-testing every branch already inside it.
  • IPaymentProcessor → one shared contract, each payment type implements it independently.
  • Adding CryptoPayment later → one new class, caller code never changes.
  • Directly resolves the Open/Closed switch example — Strategy is the pattern that switch turns into.
  • Real Strategy → caller never branches once it holds the right instance; a factory that still branches on a string doesn't count.
📖 Explanation ▾

A growing switch statement puts every payment type's behavior in one method. ChargeCreditCard, ChargePayPal, and ChargeBankTransfer all live inside the same block, so testing one path drags every other case in that method along with it. Every new payment type means opening this method again and adding one more case.

The Strategy pattern breaks that method into one class per behavior. IPaymentProcessor states the one thing every payment type must do — Pay(decimal amount) — and CreditCardPayment, PayPalPayment, and BankTransferPayment each implement it on their own, with no shared method to edit. The caller holds a reference typed as IPaymentProcessor, chosen once however that choice gets made, and just calls processor.Pay(amount) — it never asks what kind of processor it's holding.

This is the same shape as Open/Closed Principle's classic payment-switch example — Strategy is the pattern that switch resolves into once you stop branching and start substituting. Adding CryptoPayment later is one new class implementing IPaymentProcessor; the switch-based version needed you to edit existing, already-tested code instead.

💻 See the code ▾
C# 
void Pay(string type, decimal amount)
{
    switch (type)
    {
        case "CreditCard": ChargeCreditCard(amount); break;
        case "PayPal": ChargePayPal(amount); break;
        case "BankTransfer": ChargeBankTransfer(amount); break;
        // ❌ every new type means editing this method again
    }
}

Every new payment type means opening this method again and re-testing every case already inside it.

C# 
interface IPaymentProcessor
{
    void Pay(decimal amount);
}

class CreditCardPayment : IPaymentProcessor
{
    public void Pay(decimal amount) => Charge(amount);   // ✅ owns its own behavior
}
// PayPalPayment and BankTransferPayment implement IPaymentProcessor the same way

Each payment type implements the same interface independently — no shared method for them to fight over.

C# 
IPaymentProcessor processor = GetProcessor(type);   // a small factory or DI, not a switch here
processor.Pay(amount);   // ✅ no switch — the caller doesn't ask what kind it's holding

The caller never branches on type — it just calls Pay() on whatever IPaymentProcessor it was handed.

🌍 Real-world example ▾

Scenario: your team ships a fifth payment provider next quarter, and today's code is one switch inside PaymentService.Pay().

What happens: with the switch, provider five adds one more case to a method four other providers already share — a mistake in the new branch risks breaking tests for the other four during review. With IPaymentProcessor, provider five is one new class implementing Pay(decimal amount) — the other four classes, and the caller, never change.
