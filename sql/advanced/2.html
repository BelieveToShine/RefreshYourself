Deadlock vs. Blocking — one resolves itself, one doesn't

What's the actual difference between a deadlock and blocking?

Why it matters ▾
  • Blocking is completely normal under load — a genuine deadlock is the thing an interviewer actually wants you to be able to spot and explain.
  • Interviewers use this to check whether you understand why a deadlock can never clear on its own, not just that "the database throws an error."
  • A frequent follow-on tests whether you know how the database decides which transaction to kill.
🔥 Easy interview recall

Blocking → waiting your turn, resolves on its own

Deadlock → a real cycle, only the engine can break it

Think: blocking ends when the other transaction finishes; a deadlock never ends on its own.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A deadlock is not just a really long block. No amount of waiting resolves it — it's a genuine cycle where neither transaction can ever proceed, so the engine has to detect the cycle and forcibly kill one transaction to break it; blocking, by contrast, always ends on its own once the blocking transaction finishes.

🔄 Likely Follow-up

"How does the database decide which transaction to kill in a deadlock?" It typically picks whichever is cheaper or faster to roll back — for example, the one that's done less work so far — not necessarily the transaction that "caused" or started the problem.

🎯 Say this in the interview — the exact lines to land

"Blocking is one transaction simply waiting its turn for a lock held by another — it always resolves on its own once the lock-holding transaction finishes. A deadlock is two or more transactions each waiting on a lock the other one holds — a real cycle that can never resolve by itself, so the database has to detect it and kill one transaction, the deadlock victim, to break the cycle."

  • Blocking → resolves on its own the moment the lock-holding transaction commits or rolls back.
  • Deadlock → a real cycle, each transaction waiting on a lock the other one holds.
  • Neither side in a deadlock can move → it never resolves on its own, no matter how long you wait.
  • The engine detects the cycle → picks a "victim" to kill, usually whichever is cheaper to roll back.
  • Not about who's "at fault" → rollback cost decides the victim, not who started it.
📖 Explanation ▾

Blocking is completely ordinary: one transaction asks for a lock another transaction already holds, and it simply waits in line. There's nothing stuck about it — the moment the lock-holding transaction commits or rolls back, the lock is released, the waiting transaction picks it up, and everything carries on normally.

A deadlock is a different shape entirely. Transaction 1 holds a lock Transaction 2 wants, and Transaction 2 holds a lock Transaction 1 wants — each side is waiting for the other to let go first, and neither ever will, because neither can reach the point where it releases its own lock. Waiting longer changes nothing; the cycle doesn't loosen on its own.

Because a deadlock can never resolve by itself, the database engine has to step in. It periodically checks for exactly this kind of waiting cycle, and once it finds one, it picks one transaction — the deadlock victim, usually whichever is cheapest to undo — rolls it back, and lets the other one continue.

💻 See the code ▾
SQL 
-- Transaction 1
BEGIN TRANSACTION;
UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;   -- locks Row 1
-- ...pauses here — Transaction 2 has already locked Row 2...
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;   -- ❌ waits on Row 2 — held by Transaction 2

-- Transaction 2 (running at the same time)
BEGIN TRANSACTION;
UPDATE Accounts SET Balance = Balance - 50 WHERE Id = 2;    -- locks Row 2
UPDATE Accounts SET Balance = Balance + 50 WHERE Id = 1;    -- ❌ waits on Row 1 — held by Transaction 1
-- 🐛 classic deadlock: each transaction locked the two rows in the opposite order

Both transactions touch the same two rows, just in reverse order — each ends up waiting on the row the other one already locked, closing the cycle.

🌍 Real-world example ▾

Blocking is one person waiting outside a single bathroom for it to free up — annoying, but the moment the person inside is done, the door opens and the wait is over. A deadlock is two people locked in two different rooms, each holding the only key to the OTHER person's door. Neither can move, no matter how long they wait — someone from outside (the database engine) has to step in, force one door open, and let that person out so the other can finally get their key back.
