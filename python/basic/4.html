Order, duplicates, hashing — three axes that actually decide which one you need

"List vs. tuple vs. set vs. dictionary — how do you decide, and which preserves order / allows duplicates / supports indexing / is hash-based?"

Why it matters ▾
  • Picking a list for repeated membership checks is a real, silent performance bug — fine at 10 items, painfully slow at 100,000.
  • A near-guaranteed warm-up question: "why would you ever use a tuple instead of a list?"
  • defaultdict and Counter are two of the most common collections imports in real code — knowing when they beat a plain dict shows practical fluency, not memorized syntax.
🔥 Easy interview recall

list → ordered, growable

tuple → ordered, frozen

set → no order, fast lookup

dict → keyed, insertion-ordered

Think: list → ordered & growable tuple → ordered & frozen set → unordered, hash-based, no duplicates dict → hash-based keys, insertion-ordered

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for a list to check membership. x in my_list scans every element — O(n) — while x in my_set is a hash lookup — O(1); if the code repeatedly asks "is this here," convert to a set first.

🔄 Likely Follow-up

"When would namedtuple beat a dataclass?" When you need tuple-compatible unpacking, equality, and hashability with zero mutability and don't need methods or default-value machinery — reach for dataclass otherwise, especially once mutability or typed defaults are involved.

🎯 Say this in the interview — the exact lines to land

"Set for membership speed, tuple for a fixed hashable record, dict for keyed lookup, list for an ordered growable sequence."

  • set → reach for it when checking membership repeatedly — O(1) instead of a list's O(n) scan.
  • tuple → a fixed, small, immutable record — hashable enough to use as a dict key.
  • dict → keyed lookup, insertion-ordered since Python 3.7, keys unique.
  • list → the default ordered, growable, index-accessed sequence.
  • defaultdict / Counter → replace manual "if key not in d" checks and hand-rolled tally loops.
📖 Explanation ▾

list is a resizable array — cheap to index and append, but checking x in my_list walks every item, so it's O(n). tuple is shaped the same way but frozen after creation; that immutability is exactly what lets it be hashed (as long as every item inside it is itself hashable) and used as a dict key. set and dict are both backed by a hash table — that's the actual mechanism behind their O(1) membership test and O(1) key lookup, and why neither one keeps a positional index.

collections.defaultdict is a dict subclass that calls a factory function to create a value the first time a missing key is touched, removing the "if key not in d" boilerplate. collections.Counter is a dict subclass built for counting hashable items — its .most_common() replaces a hand-rolled tally-and-sort loop.

namedtuple and dataclass both give named fields instead of positional ones, but they solve different problems:

namedtupledataclass
Mutable?❌ no✅ yes (unless frozen=True)
Auto __init__/__repr__/__eq__?✅ yes✅ yes
Type hints + defaults?Only via typing.NamedTuple✅ built in
Best forfixed, hashable, tuple-compatible recordmutable data holder with real methods
💻 See the code ▾
Python 
from collections import defaultdict

counts = defaultdict(int)              # 🔧 factory: int() -> 0
for word in ["a", "b", "a"]:
    counts[word] += 1              # ✅ no manual "if word not in counts"

plain = {}
for word in ["a", "b", "a"]:
    if word not in plain:      # ❌ boilerplate defaultdict removes
        plain[word] = 0
    plain[word] += 1

The factory function (here int) supplies the default the first time a key is touched — defaultdict just swallows the missing-key check.

Python 
from collections import Counter

tally = Counter(["a", "b", "a", "c", "a", "b"])
tally.most_common(2)   # -> [('a', 3), ('b', 2)]

One line replaces a hand-rolled counting dict plus a manual sort by value.

🌍 Real-world example ▾

Deduplicating a huge list of user IDs while repeatedly checking "have I seen this one already" is a classic case: doing that check against a plain list is an O(n) scan every single time, so the whole loop degrades to O(n²). Converting the IDs to a set first turns each check into an O(1) hash lookup, and the whole loop drops to O(n).
