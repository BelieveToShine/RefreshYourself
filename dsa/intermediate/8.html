Topological Sort vs. Union-Find — order vs. connection

"How do you produce a valid order for tasks that depend on each other, and how do you efficiently track which elements already belong to the same group?"

Why it matters ▾
  • Any "these tasks depend on each other" problem — build order, course prerequisites, task scheduling — is a topological sort in disguise.
  • Any "are these already connected?" problem — network components, Kruskal's MST from the previous page — is a Union-Find problem in disguise.
  • Both have a cycle-detection angle interviewers love to probe: "is this ordering even possible?" vs. "would this one edge create a cycle?" — genuinely different questions, see the trap below.
🔥 Easy interview recall

Topological Sort → a valid order for a DAG

Union-Find → fast group membership

Think: Topological Sort answers "what order?" — Union-Find answers "same group, or not?"

🧠 Visual Mental Model — two different questions, two different tools
⚠️ Common Trap

A graph having a cycle and one edge creating a cycle are not the same problem. Topological sort's cycle check means the whole graph has no valid order at all; Union-Find's check during Kruskal's just means skip this one edge — the rest of the MST is still fine.

🔄 Likely Follow-up

"How would you detect a cycle in an undirected graph using Union-Find instead of DFS?" Process edges one at a time — before adding edge (u, v), call FIND on both ends; if they're already in the same group, that edge would create a cycle, so skip it; otherwise UNION them and continue.

🎯 Say this in the interview — the exact lines to land

"Topological sort only works on a DAG — it orders nodes so every edge points forward, using Kahn's in-degree-zero removal or a DFS post-order, and if a cycle exists, no valid order exists at all. Union-Find tracks group membership with FIND and UNION, and with path compression plus union by rank, both run in amortized O(α(n)) — practically constant time."

  • Topological Sort → DAG only, no cycle allowed.
  • Kahn's algorithm → removes in-degree-zero nodes one at a time, queue-driven.
  • Union-Find → FIND tells you the group, UNION merges two.
  • Path compression + union by rank → amortized O(α(n)), effectively constant.
  • Kruskal's MST → uses FIND to skip edges that would close a cycle.
📖 Explanation ▾

Topological sort only makes sense on a DAG — a directed graph with no cycles. It produces one linear ordering of every node where, for every edge u → v, u comes before v. Kahn's algorithm builds that order by repeatedly pulling out whatever node currently has in-degree zero (no prerequisites left), adding it to the result, and decrementing the in-degree of everything it pointed to — like clearing tasks off a to-do list once nothing is blocking them anymore.

The DFS-based alternative does the same job differently: run a DFS, and only add a node to the front of the result once every node it can reach has already been fully explored. Cycle detection here reuses the "currently on the recursion stack" tracking from Graph Problem Patterns — if DFS ever revisits a node still on that stack, there's a cycle and no valid order exists.

Union-Find answers a completely different question: "are these two elements in the same group?" FIND walks up parent pointers to a group's root; UNION merges two groups by attaching one root under the other. Two optimizations make this fast: path compression flattens every pointer FIND just walked so it points straight at the root, and union by rank always attaches the shallower tree under the deeper one. With both, every operation runs in amortized O(α(n)), where α is the inverse Ackermann function — it grows so slowly that it's effectively a small constant for any input size that could ever come up in practice.

💻 See the code ▾
Pseudocode 
Queue<Node> ready = new();
foreach (var n in graph.Nodes)
    if (inDegree[n] == 0) ready.Enqueue(n);   // no prerequisites left

var order = new List<Node>();
while (ready.Count > 0) {
    var n = ready.Dequeue();
    order.Add(n);                              // ✅ n's spot is locked in
    foreach (var next in graph.Neighbors(n)) {
        inDegree[next]--;
        if (inDegree[next] == 0) ready.Enqueue(next);
    }
}
if (order.Count != graph.Nodes.Count)
    throw new Exception("Cycle detected");     // ❌ some nodes never hit in-degree 0

Every node with zero remaining prerequisites gets queued — if the final order is shorter than the node count, a cycle blocked some nodes forever.

Pseudocode 
int Find(int x) {
    if (parent[x] != x)
        parent[x] = Find(parent[x]);   // ✅ path compression — point straight at the root
    return parent[x];
}

void Union(int a, int b) {
    int ra = Find(a), rb = Find(b);
    if (ra == rb) return;                // already same group
    if (rank[ra] < rank[rb]) (ra, rb) = (rb, ra);
    parent[rb] = ra;                     // attach the shallower tree under the deeper one
    if (rank[ra] == rank[rb]) rank[ra]++;
}

Find rewrites every pointer it walks to point at the root; Union always hangs the smaller tree off the bigger one — together, near O(1) per call.

Pseudocode 
foreach (var edge in edgesSortedByWeight) {
    if (Find(edge.From) == Find(edge.To))
        continue;                        // ❌ same group already — would create a cycle
    Union(edge.From, edge.To);
    mst.Add(edge);                       // ✅ safe — connects two different groups
}

Same trick as undirected cycle-detection — check FIND before adding an edge, UNION only when the two sides differ.

🌍 Real-world example ▾

Your build pipeline needs to compile modules in an order that respects their dependency graph — that's topological sort deciding what can build before what. Kruskal's MST from the previous page needs a fast "would this edge close a loop?" check before adding each edge — that's exactly what Union-Find's FIND call answers, in close to constant time.
