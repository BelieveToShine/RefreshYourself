print() has no levels, no destinations, and no way to turn it off in production without editing code

"Why shouldn't production code use print()? What do Logger, Handler, and Formatter each actually do?"

🔥 Easy interview recall

Logger → what you call (.info(), .error())

Handler → decides WHERE it goes

Formatter → decides what it LOOKS like

Think: DEBUG < INFO < WARNING < ERROR < CRITICAL print() has none of this — no levels, no routing, no off switch.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Logging the whole exception or request object is safe — it's just for debugging." It isn't: arguments, headers, and payloads routinely carry passwords, API keys, or tokens straight into a log aggregator that's usually far less access-controlled than the system it's describing.

🔄 Likely Follow-up

"How do you decide which level a given log statement should be?" DEBUG for developer-only diagnostic detail, INFO for normal expected events worth recording, WARNING for something unexpected but recoverable, ERROR for a failure that needs attention, and CRITICAL for something threatening the whole application.

🎯 Say this in the interview — the exact lines to land

"Logging levels let you filter what's emitted without touching call sites — print() can't do that."

  • Logger → what you call — usually one per module, via logging.getLogger(__name__).
  • Handler → decides WHERE a record goes — one logger can have several handlers, each with its own destination.
  • Formatter → decides the TEXT — timestamp, level, message layout, independent per handler.
  • Never log secrets — passwords, tokens, and full card numbers leak into log aggregators this way constantly; it's a real, recurring incident category, not a rare edge case.
📖 Explanation ▾

print() always writes to stdout, always runs, and has no concept of severity — silencing it in production means editing or wrapping every call site by hand. The logging module fixes all three at once: it has five standard levels of rising severity — DEBUG < INFO < WARNING < ERROR < CRITICAL — so setting a single threshold (e.g. only WARNING and above in production) changes what actually gets emitted without touching a single call site.

Three objects split the job. A Logger is what code calls (logger.info(...)), usually one per module. A Handler decides where a record actually goes — console, a file, a remote service — and one logger can have several handlers at once, each sending the same record somewhere different. A Formatter decides the text layout of a record — timestamp, level, message shape — and belongs to one handler at a time, so two handlers on the same logger can format identically or completely differently.

💻 See the code ▾
Python 
import logging

logger = logging.getLogger(__name__)              # one logger per module
logger.setLevel(logging.INFO)                      # filter: INFO and above only

handler = logging.StreamHandler()                  # WHERE it goes: console
handler.setFormatter(logging.Formatter(
    "%(asctime)s %(levelname)s %(name)s: %(message)s"  # WHAT it looks like
))
logger.addHandler(handler)

logger.info("Order %s placed", order_id)  # ✅ no secrets in the message

setLevel controls what's emitted; the Formatter string controls the text layout — either can change without touching this call site.

Python 
try:
    connect(db_url)
except Exception:
    logger.exception(f"DB connection failed: {db_url}")  # ❌ db_url may embed a password
    logger.exception("DB connection failed")             # ✅ log the failure, not the value

A connection string often has a password baked into it — log that the failure happened, not the value that caused it.

🧭 Use Cases — recognize these when they happen to you ▾
1 You want detailed messages in development but quiet logs in production

One level threshold decides what gets emitted. Records below it are dropped, so you change a setting instead of editing every call site, which is what print() would force.

RememberOne level setting filters every call.
2 You need the same log line on the console and in a file

One logger can have several handlers, and each handler has its own destination and its own formatter. Both outputs get the record, and can look different.

RememberHandler = where it goes.
3 You log a failure message that includes the database URL

A common trap — a connection string often has the password inside it. Once logged, it sits in an aggregator that many people can read.

RememberLog the failure, not the value.
🌍 Real-world example ▾

A caught exception's stack trace included the full database connection string — password embedded — because the whole exception object had been logged as-is. It sat in the log aggregator, readable by anyone with log access, until a custom logging filter was added to strip connection-string and token-shaped values before a record ever left the process.
