Idempotent deployment — why re-running it twice should change nothing

"What does 'idempotent deployment' mean for IaC, and why does that matter more than just 'it's written as code'?"

Why it matters ▾
  • Checks whether you understand what actually makes IaC safe, not just that it's "code" instead of clicking in a portal.
  • Comes up any time a CI/CD pipeline step fails partway through and has to be retried.
  • A common follow-up once you've named Bicep/ARM/Terraform as your IaC tool of choice.
🔥 Easy interview recall

Idempotent deployment = "run it 1 time or 10 times, you land in the same place."

Think: a declarative template describes the destination, not a list of turns — Resource Manager just checks if you're already there.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It's IaC, so it must be safe to re-run." Not automatically true — a script written as a sequence of imperative steps (e.g. "always create resource X") isn't idempotent at all, and errors or duplicates resources on a second run; it's the declarative, desired-state shape of a Bicep/ARM template that actually earns the safe-to-retry property.

🔄 Likely Follow-up

"Is Terraform idempotent the same way?" Yes, by the same principle — it compares its state file against the declared desired state and only changes what's actually different, not by blindly re-running create commands.

🎯 Say this in the interview — the exact lines to land

"A declarative deployment describes desired state, so re-running it is a no-op once it matches — that's what makes retries safe. Terraform follows the same principle through its state file, comparing declared state against actual state instead of blindly replaying create commands."

  • Idempotent → same end state no matter how many times it runs.
  • Declarative → describes the destination, not a list of steps to replay.
  • ARM/Bicep → reconciles the diff — it only changes what doesn't already match.
  • Imperative "always create" scripts break this — they duplicate or fail on a second run.
📖 Explanation ▾

Idempotent means running the same deployment definition twice produces the same end state, without erroring and without duplicating resources. Azure Resource Manager is naturally idempotent when it's driven by an ARM template or Bicep file, because that file describes the desired end state — "there should be a storage account named X with these settings" — rather than a sequence of commands to carry out. Resource Manager's job on every deployment is to compare that desired state against what's actually there and only change the difference.

This is exactly what makes it safe to retry a deployment step in a CI/CD pipeline after a transient failure, like a dropped network connection. Re-running the same template doesn't redo work that already succeeded — it just confirms the difference is now zero and stops. That property only holds because the template is declarative; a script that issues imperative steps has no such guarantee.

💻 See the code ▾
Bicep 
// ✅ declarative — states the end state, safe to apply repeatedly
resource storageAcct 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'mystorageacct001'
  location: 'eastus'
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}

Run this template 1 time or 10 times with no changes — Resource Manager reconciles to the same account, no duplicates.

Pseudocode 
// ❌ imperative — a step list, not a desired state
always create storageAccount('mystorageacct001')
// second run: fails "already exists," or creates a duplicate

There's nothing here to compare against — it just replays the same "create" step every time, whether or not the resource already exists.

🌍 Real-world example ▾

A CI/CD pipeline step deploys a Bicep template and hits a transient network failure partway through. The pipeline just retries the same step — no manual cleanup, no "did it half-apply" investigation — because re-running it only reconciles to the same declared end state instead of creating duplicate resources.
