Design DynamoDB from the access patterns — not from the tables

Model orders, customers and items in DynamoDB — how do you design keys, and when single-table?

Why it matters ▾
🎯 Access patterns first
❗ ProblemModelling DynamoDB like a relational schema — a table per entity, join later — leaves you with Scans, because DynamoDB has no joins.
✅ SolutionWrite down the questions the app asks first. Then choose the partition key and sort key so each question is a single Query.
RecallQuestions first, keys second.
🧩 Single-table design
❗ ProblemRelated items spread over several tables need several round trips to fetch together.
✅ SolutionSingle-table keeps different item types under a shared partition key, so one Query returns a customer and their orders. The cost is a design that is harder to read and needs the patterns known up front.
RecallSingle-table = one Query, harder to read.
🧰 Indexes, transactions, Streams, TTL
❗ ProblemA new question later doesn't fit the table's keys, and some jobs — all-or-nothing writes, reacting to changes, expiring old data — aren't about keys at all.
✅ SolutionA GSI re-keys a copy for another pattern. Transactions give all-or-nothing writes, Streams publish every change, and TTL expires items for you.
RecallDesign tools beyond the base key.
🔥 Easy interview recall

Design → start from the access patterns, not the entities

PK + SK → PK picks the partition, SK orders and slices it

Single-table → mixed item types, one Query for related items

Query not Scan → every pattern should be a Query

Think: Write the questions down first — the keys fall out of them. No joins means the key has to do the joining.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Drawing the entities first, like an ER diagram, and hoping Query will fit. DynamoDB has no joins, so a question the keys don't serve turns into a Scan. Single-table isn't automatically better either — it only pays off when the patterns are known and related items are read together.

🔄 Likely Follow-up

"A new query pattern shows up after launch — now what?" Add a GSI keyed for it — a GSI can be added at any time, and it is eventually consistent. An LSI can only be created together with the table, so it is not the fix here.

🎯 Say this in the interview — the exact lines to land

"I start from the access patterns, then choose the partition key and sort key so each pattern is one Query, never a Scan. I go single-table when related items are read together and the patterns are known, and I add a GSI for any pattern the main key can't serve."

  • Access patterns first → each is one Query on a partition key, with an optional sort-key condition.
  • Composite sort key → ORDER#date lets begins_with or between slice one partition.
  • Single-table → one Query for related items — harder to read; multi-table is fine for independent entities.
  • GSI → another access pattern, addable later; an LSI only at table creation.
  • Transactions / Streams / TTL → all-or-nothing writes, react to changes, auto-expire items.
📖 Explanation ▾

Access patterns first. DynamoDB has no joins, so the key has to do the work. List the questions the app asks — "all orders for a customer", "one order with its items", "shipped orders" — and choose keys so each one is a Query: an exact partition key, plus an optional condition on the sort key (begins_with, between). A composite sort key such as ORDER#2026-10-01#o9 lets one partition hold several kinds of item and be sliced by prefix or date. A Scan reads the whole table — the sign a pattern was never designed for.

Single-table vs. multi-table is a trade-off, not a rule. Single-table is a tool for access patterns you know well; it is not the mandatory "right" DynamoDB design.

Design tools beyond the key. A GSI adds a second access pattern and can be added later; the GSI-vs-LSI differences are on the DynamoDB page. Transactions make writes to several items all-or-nothing (they cost more than plain writes). Streams publish a log of item changes, in order for each item — often read by a Lambda to react or keep a copy in sync. TTL expires items from a timestamp attribute; deletion happens in the background, so an expired item can linger briefly — filter it out when reading if that matters.

💻 See the code ▾
CLI 
aws dynamodb query \
  --table-name AppTable \
  --key-condition-expression "PK = :pk AND begins_with(SK, :prefix)" \
  --expression-attribute-values '{":pk":{"S":"CUSTOMER#c1"},":prefix":{"S":"ORDER#"}}'

Pattern 1 as one Query: the exact partition key, plus a sort-key prefix that picks only the order items. No Scan, no join.

JSON 
{
  "PK": { "S": "CUSTOMER#c1" },
  "SK": { "S": "ORDER#2026-10-01#o9" },
  "total": { "N": "42.50" },
  "status": { "S": "SHIPPED" },
  "GSI1PK": { "S": "STATUS#SHIPPED" },
  "GSI1SK": { "S": "2026-10-01" }
}

One order item, in DynamoDB's JSON form. PK/SK serve patterns 1 and 2; the GSI1PK/GSI1SK attributes are what the status index is keyed on for pattern 3.

🌍 Real-world example ▾

A "My orders" screen runs one Query on the customer's partition with an ORDER# prefix and gets the orders in one round trip, while an ops dashboard reads the status GSI for shipped orders. A Streams-triggered Lambda sends the shipped email, and TTL clears abandoned carts.
