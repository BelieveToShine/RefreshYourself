Subqueries vs. Joins — same answer, different plan

"What is a subquery, and when would you use one instead of a join?"

Why it matters ▾
  • Checks whether you understand what a subquery actually hands back (a value or a list) versus what a join actually produces (combined columns).
  • Comes up any time you're deciding how to write a filter that depends on data in another table.
  • A very common opener when an interviewer wants to see how you reason about query shape, not just syntax.
🔥 Easy interview recall

Subquery → a value or a yes/no filter check

Join → columns from both tables, side by side

Think: need extra columns in the result → join. Just need a filter/check → subquery.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Subqueries are always slower than joins." Not universally true — a well-written correlated subquery (especially an EXISTS check) can perform the same as or comparably to an equivalent join under a modern optimizer; the real deciding factor is what you actually need in the result, not a blanket performance rule.

🔄 Likely Follow-up

"What's a correlated subquery?" A subquery that references a column from the outer query, so it's tied to each outer row — e.g. WHERE EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerId = c.Id) — different from a simple, independent subquery that just runs once on its own.

🎯 Say this in the interview — the exact lines to land

"A subquery is a query nested inside another one — in the WHERE, SELECT, or FROM clause — and I reach for it when I only need a single value or a filter/membership check. I reach for a join when I actually need columns from both tables side by side in the same result row."

  • Subquery → use for a single value or a filter/membership check against a list.
  • Join → use when you need real columns from both tables in the result.
  • Correlated subquery → references the outer row — a plain subquery runs once, independently.
  • An EXISTS subquery → isn't automatically slower than an equivalent join.
📖 Explanation ▾

A subquery is a query nested inside another query — inside its WHERE, SELECT, or FROM clause. It hands the outer query a single value, a list to check membership against, or a yes/no result — nothing more. A join instead combines rows from two tables directly, based on a matching condition, producing one wider result set that carries columns from both sides in the same row.

The real decision isn't about speed — it's about shape. If the outer query only needs to filter on a condition ("does this customer have a US order?"), a subquery says exactly that, and nothing about the other table's own columns leaks into the result. If the query needs to display or return columns that live in the other table, a subquery can't do that on its own — only a join lines both tables' columns up in the same row.

💻 See the code ▾
SQL 
SELECT Name
FROM Customers
WHERE Id IN (-- ✅ subquery: hands back a plain list of IDs
    SELECT CustomerId FROM Orders WHERE Country = 'US'
);

Only needs a filter — the result never touches Orders' own columns.

SQL 
SELECT DISTINCT c.Name
FROM Customers c
JOIN Orders o ON o.CustomerId = c.Id
WHERE o.Country = 'US';
-- ✅ same filtered customers, but this version could also SELECT o.OrderDate, o.Total, …
-- DISTINCT is needed here: one customer can match more than one US order

This version could also return real Orders columns in the same row — the subquery version above physically can't.

🌍 Real-world example ▾

"Which of my friends live in cities with a population over 1 million?" A subquery approach first builds the list of qualifying cities, then checks each friend's city against that list — a plain yes/no per friend. A join approach lines your friends and the city data up side by side in one combined table, so you could also see each friend's exact city population in the same row, not just a yes/no.
