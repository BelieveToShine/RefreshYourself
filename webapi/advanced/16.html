Can't lose a single request — do you process it inline, or durably queue it?

"10,000 requests arrive in 3 minutes and you can't afford to lose a single one — what's the architecture?"

Why it matters ▾
🧯 Zero-Loss Under Throughput
❗ ProblemProcessing a request fully, inline, before responding means anything that crashes or times out mid-processing during a burst is lost — with no durable record it ever arrived.
✅ SolutionAccept and durably persist the request first — a message queue, not an in-memory one — acknowledge immediately, then let a pool of workers process it at a sustainable pace, acking only after success.
RecallPersist first, process after — the queue absorbs the burst so nothing has to be dropped.
🔥 Easy interview recall

Zero-loss at scale = "durable queue absorbs the burst, workers drain it at their own pace."

Think: Accept → persist durably, acknowledge fast Queue → absorbs the burst, survives a crash Workers → scale independently, ack only after success

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Processing the request fully before responding is not "zero loss." Under a burst, requests pile up waiting for a thread, and anything that times out or crashes mid-processing is lost with no durable record it ever arrived.

🔄 Likely Follow-up

"What guarantees a worker crash mid-processing doesn't lose a message?" The queue's own acknowledgment model — a worker only removes/acks a message after it's fully processed; if it crashes first, the un-acked message becomes visible again for another worker to pick up.

🎯 Say this in the interview — the exact lines to land

"I wouldn't process the request inline with the HTTP call if 'can't lose any' is the real requirement. I'd accept the request, durably persist it as fast as possible — a real message queue like Azure Service Bus or Kafka, not an in-memory one that dies with the process — and return an acknowledgment. A separate pool of workers consumes the queue at whatever pace they can sustain, so the burst is absorbed by the queue instead of overwhelming the processing layer, and I can scale producers and consumers independently."

  • Accept, then persist → durably, before doing any real work, not after.
  • Durable queue → survives a crash, unlike an in-memory queue.
  • Workers drain independently → scale consumers separately from producers.
  • Ack only after success → a crash mid-processing re-surfaces the message, nothing vanishes.
  • The queue absorbs the burst → not the processing layer.
📖 Explanation ▾

"Zero loss" is a durability requirement, and durability has to happen before any real work, not after. The fix is to split the request into two phases: accept and persist — write the request to a durable message queue (Azure Service Bus, Kafka, or equivalent — specifically not an in-memory queue, which disappears the moment the process restarts or crashes) and return an acknowledgment as fast as possible — and process, handled by a separate pool of workers that pull from the queue at whatever pace they can sustain. Because the queue itself durably holds everything that hasn't been processed yet, a burst of 10,000 requests in three minutes is absorbed by the queue's own buffer instead of overwhelming whatever does the real processing.

The number of workers can scale independently of the number of producers — more consumers during a known burst, fewer the rest of the time — which is the whole point of decoupling the two. The piece that actually delivers the "zero loss" guarantee is the queue's acknowledgment model: a worker that pulls a message doesn't permanently remove it until it finishes processing successfully and explicitly acks it. If that worker crashes mid-processing, the un-acked message becomes visible again (often after a short visibility timeout) for another worker to pick up — so a crash loses time, not the message itself.

💻 See the code ▾
C# 
[HttpPost]
public async Task<IActionResult> Submit(OrderRequest req, CancellationToken ct)
{
    await _queue.SendAsync(req, ct); // ✅ durably persisted before responding
    return Accepted();         // 202 — caller knows it's received, not yet processed
}

// a worker, running separately, scaled independently of the API:
await foreach (var msg in _queue.ReceiveMessagesAsync(ct))
{
    await ProcessAsync(msg, ct);
    await msg.CompleteAsync(); // ✅ ack only now — a crash before this re-surfaces the message
}

The API's job ends at "durably received." The worker's ack is the only thing that ever removes a message for good.

🌍 Real-world example ▾

A flash sale drives 10,000 order submissions in a three-minute window. Accepting each order, writing it to a durable queue, and responding "received" immediately means the API never falls behind — and even if a worker crashes halfway through fulfilling an order, the un-acked message reappears for another worker to finish, so no order submitted during the rush is ever silently dropped.
