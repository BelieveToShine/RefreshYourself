foreach — what is really happening under the hood?

"What is the Iterator pattern, and what does yield return actually compile to in C#?"

☕ Also see the Java-angle page: Iterator vs. ListIterator
Why it matters ▾
🔁 Iterator
❗ ProblemLooping code that reaches into a collection's internal array, list, or tree directly breaks the moment that internal structure changes, and duplicates traversal logic across every caller.
✅ SolutionIterator gives a collection one small interface — MoveNext() and Current — so any caller can walk its elements one at a time without ever seeing how they're actually stored; foreach and yield return in C# are this exact pattern built into the language.
RecallIterator = walk the elements one at a time, without exposing how they're stored.
🔥 Easy interview recall

Iterator = "IEnumerable/IEnumerator, baked straight into foreach."

Think: foreach → compiles to GetEnumerator() once, then MoveNext()/Current in a loop yield return → compiler builds a hidden state machine implementing IEnumerator<T> MoveNext() → resumes right after the last yield, not a one-shot call

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

yield return is not "just a shortcut for building a list and returning it." It's lazy — each value is produced only when MoveNext() is actually called, which is why it can iterate an infinite sequence without ever materializing one.

🔄 Likely Follow-up

"What does yield return actually compile to?" The compiler generates a hidden class implementing IEnumerator<T> as a state machine; each MoveNext() call resumes execution right after the previous yield return instead of running the method from the top.

🎯 Say this in the interview — the exact lines to land

"Iterator gives a collection a way to expose its elements one at a time without revealing how they're stored. In C#, IEnumerable<T> and IEnumerator<T> are this pattern built into the language — foreach compiles to calling GetEnumerator() once, then MoveNext() and reading Current in a loop. yield return lets me implement IEnumerator<T> without hand-writing that state machine; the compiler generates one, and each MoveNext() call resumes right after the last yield return."

  • IEnumerable<T> → the Aggregate — GetEnumerator() hands back an iterator.
  • IEnumerator<T> → the Iterator — MoveNext()/Current, GoF's HasNext()/Next() by another name.
  • foreach → sugar for GetEnumerator() once, then MoveNext()/Current in a loop.
  • yield return → compiler-generated state machine, lazy — not a list built up front.
  • Why Deep Dive → rarely asked as "name this pattern," often asked as "what does yield compile to".
📖 Explanation ▾

GoF's Iterator is an interface with HasNext()/Next(); .NET's shape of the same idea is IEnumerator<T>'s MoveNext()/Current. The Aggregate that hands one back is IEnumerable<T>'s GetEnumerator(). foreach is literally syntactic sugar over those two interfaces: it calls GetEnumerator() once, then repeatedly calls MoveNext() and reads Current until MoveNext() returns false.

yield return is what makes implementing IEnumerator<T> painless — the C# compiler generates a hidden class implementing it for you, a real state machine, not a loop that builds a list up front. Each call to MoveNext() resumes execution right after the previous yield return rather than re-running the method from the start, which is exactly why a yield return method can produce an infinite sequence lazily — nothing downstream of the next unread value is ever computed.

💻 See the code ▾
C# 
class EvenNumbers : IEnumerable<int>
{
    private readonly int _max;
    public EvenNumbers(int max) => _max = max;

    public IEnumerator<int> GetEnumerator()
    {
        for (int i = 0; i <= _max; i += 2)
            yield return i;         // ✅ compiler builds the state machine from this
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();

ConcreteAggregate — one yield return loop is all it takes; no hand-written IEnumerator<int> class.

C# 
foreach (var n in new EvenNumbers(10))
{
    Console.WriteLine(n);
}

// what the compiler actually generates for the loop above:
var e = new EvenNumbers(10).GetEnumerator();   // GetEnumerator() called ONCE
while (e.MoveNext())                             // resumes after the last yield, each call
{
    var n = e.Current;
    Console.WriteLine(n);
}

This is literally what foreach compiles to — the sugar, not a different mechanism underneath.

🧭 Use Cases — recognize these when they happen to you ▾
1 You write your own collection and want callers to use foreach on it

Implement IEnumerable<T> and foreach works on your type. It calls GetEnumerator() once, then MoveNext() and Current in a loop. This is the #1 scenario you'll actually run into.

Rememberforeach = GetEnumerator once, then MoveNext.
2 You yield return a huge or never-ending sequence and expect a list

The values are not built up front into a list. Each MoveNext() call produces just the next value, which is why a never-ending sequence is fine as long as the caller stops reading.

Rememberyield return is lazy, not a built list.
3 You'd rather not hand-write an enumerator class with its own bookmark

A yield return loop lets the compiler generate the enumerator class for you. Each MoveNext() resumes right after the last yield return.

RememberThe compiler writes the enumerator for you.
🌍 Real-world example ▾

A TV remote's channel-up button. Pressing it moves to the next channel one at a time, without needing to know how the channel list is actually stored. A playlist's "next song" button works the same way.
