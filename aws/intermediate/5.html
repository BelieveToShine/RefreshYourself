Instance refresh — rolling out a new version without anyone noticing

"How do you deploy an EC2-based application without downtime, and what's a launch template for?"

Why it matters ▾
🗂️ Launch configuration (legacy)
❗ ProblemAn ASG needs a fixed blueprint — AMI, instance type, security groups — to know what to launch, and the earliest way to define that blueprint was a launch configuration.
✅ SolutionA launch configuration works, but it's immutable once created and has no versioning or mixed-instance-type support — any change means creating a brand-new one and swapping the ASG over to it.
RecallLaunch configuration = the original launch blueprint — locked the moment it's created.
🧩 Launch template
❗ ProblemOnce teams needed to update that blueprint — a new AMI, mixed instance types for cost savings — swapping in a whole new launch configuration every time got unworkable.
✅ SolutionA launch template versions the same blueprint: create a new version, point the ASG at it, and it also supports mixed instance types and purchase options — AWS's current default for any new ASG.
RecallLaunch template = the versioned, current-default blueprint — same job, but editable.
🔥 Easy interview recall

Instance refresh = "a rolling deploy for an Auto Scaling Group."

Think: launch template says what to launch; instance refresh rolls it out gradually, always keeping a minimum healthy count in service.

⚠️ Common Trap

"A launch configuration works fine for a new ASG." It technically launches instances, but launch configurations are immutable once created and have no versioning or mixed-instance-type support — AWS's current guidance is to use launch templates for anything new.

🔄 Likely Follow-up

"How do lifecycle hooks help during termination?" A termination lifecycle hook can pause the instance in a "Terminating:Wait" state long enough to drain connections or deregister cleanly from a service registry before it's actually removed.

🎯 Say this in the interview — the exact lines to land

"Launch templates — not configurations — define what an ASG launches; instance refresh is how I roll out a new version without downtime, replacing instances a few at a time while keeping a minimum healthy count in service."

  • Launch template → versioned, supports mixed instance types — the modern replacement for launch configurations.
  • Instance refresh → rolling replacement that always maintains minimum healthy capacity.
  • Lifecycle hooks → pause launch or termination to run a custom action before the instance goes live or is removed.
  • Warm pools → pre-initialized instances standing by, cutting scale-out latency — the same idea as Lambda's provisioned concurrency.
📖 Explanation ▾

A launch template defines the configuration an ASG uses to launch new instances — AMI, instance type, security groups, key pair, and more. It's the current, recommended replacement for the older launch configuration, which can't be changed once created and has no versioning or mixed-instance-type support.

Launch configuration (legacy)Launch template
Modify after creation?❌ no — immutable✅ yes — create a new version
Versioningnonemultiple versions, ASG picks one
Mixed instance types / purchase options❌ not supported✅ supported
AWS's current guidancelegacy, avoid for new ASGsdefault choice

Instance refresh uses that versioning directly: point the ASG at a new launch template version, start a refresh, and it gradually terminates old instances and launches new ones — a rolling deployment — while never letting healthy capacity drop below the minimum you set.

Lifecycle hooks pause an instance mid-launch or mid-termination so a custom action (registering with a service mesh, draining connections) can finish before it goes into service or gets removed. Warm pools keep a set of instances pre-initialized and ready, so scaling out doesn't have to wait on a full boot/bootstrap cycle.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're creating a brand-new Auto Scaling Group today

Any new ASG should launch from a launch template, not a launch configuration — templates are versioned, support mixed instance types and purchase options, and are AWS's current default for a brand-new setup.

RememberNew ASG → launch template, not a launch configuration.
2 You need to roll out a new AMI version with zero downtime

Point the ASG at the new launch template version and start an instance refresh — it replaces instances a few at a time while never letting healthy capacity drop below your minimum, so the rollout finishes with zero downtime.

RememberNew version + instance refresh → rolling replacement, minimum healthy always kept.
3 You inherit an ASG still wired to an old launch configuration

It still technically launches instances, but a launch configuration can't be modified or versioned and doesn't support mixed instance types — the safe move is migrating that ASG to a launch template, not leaving it as-is. A common interview trap — candidates often assume "it still works" means "it's still fine to keep."

RememberOld launch configuration still works → but migrate it; it can't version or mix instance types.
🌍 Real-world example ▾

A team rolls out a new AMI version by triggering an ASG instance refresh, which replaces instances in small batches while the ALB keeps routing only to the currently-healthy ones — zero downtime, no manual coordination.
