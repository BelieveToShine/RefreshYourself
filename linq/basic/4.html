First vs. FirstOrDefault vs. Single vs. SingleOrDefault — zero, one, or many matches?

"What's the difference between First, FirstOrDefault, Single, and SingleOrDefault?"

Why it matters ▾
🥇 First
❗ ProblemYou need "at least one match is enough, I don't care if there are more" — but it still shouldn't crash on an empty sequence silently going unnoticed.
✅ SolutionFirst returns the first matching element and throws InvalidOperationException only when the sequence has zero matches.
RecallFirst = "at least one is enough" — throws only on zero.
🥈 FirstOrDefault
❗ ProblemSame "any match is fine" need, but here finding nothing is a normal, expected outcome — not something that should throw.
✅ SolutionFirstOrDefault returns the first match, or default(T) when there are none — it never throws because of a missing match.
RecallFirstOrDefault = "at least one is enough, and zero is fine too."
🎯 Single
❗ ProblemYou need "exactly one must exist" — and finding a second one means the data has a real bug that should surface immediately, not get quietly ignored.
✅ SolutionSingle returns the one match, but throws InvalidOperationException on zero matches and throws again on two-or-more matches.
RecallSingle = "exactly one, or I want to know why not."
🎯❓ SingleOrDefault
❗ ProblemSame "exactly one, duplicates are a bug" need, but it's normal for this particular lookup to sometimes find nothing at all.
✅ SolutionSingleOrDefault returns the one match, or default(T) on zero matches — but still throws on two-or-more. It only tolerates the zero case, never the many case.
RecallSingleOrDefault = "exactly one or none — more than one is still a bug."
🔥 Easy interview recall

First → zero throws, many is fine

FirstOrDefault → zero is fine, many is fine

Single → zero or many both throw

SingleOrDefault → zero is fine, many still throws

Think: SingleOrDefault is not "the safe Single" — it only forgives zero, never many.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for FirstOrDefault out of habit even where the data model guarantees uniqueness (a lookup by primary key). That silently hides a real bug — two rows sharing a "unique" key — that Single/SingleOrDefault would have caught immediately.

🔄 Likely Follow-up

"Is FirstOrDefault just the 'safe' version of Single?" No — they solve different problems. SingleOrDefault is the zero-tolerant version of Single; FirstOrDefault tolerates duplicates by design and always just returns the first one. They aren't a strict/relaxed pair of each other.

🎯 Say this in the interview — the exact lines to land

"The real split is zero vs. many, not just 'throws more.' First and Single both throw on zero matches; FirstOrDefault and SingleOrDefault return default(T) instead. But on two or more matches, First and FirstOrDefault just take the first one — Single and SingleOrDefault both throw, because SingleOrDefault only forgives zero, never many."

  • First → use when at least one is guaranteed, extras are fine.
  • FirstOrDefault → use when zero is a normal outcome, extras are fine.
  • Single → use when exactly one is guaranteed — more than one is a bug worth knowing about.
  • SingleOrDefault → use when zero is normal but duplicates still aren't.
📖 Explanation ▾

First vs. Single isn't just "one throws in more cases than the other" — it's a different correctness claim. First says "I expect at least one, and I don't care if there are more." Single says "I expect exactly one, and finding more than one means something is wrong."

The OrDefault variants only change what happens on zero matches — they return default(T) (null for a reference type, 0 for an int, and so on) instead of throwing. Critically, SingleOrDefault does not extend that same tolerance to the many-matches case — it still throws there, exactly like plain Single.

FirstFirstOrDefaultSingleSingleOrDefault
Zero matches❌ throws✅ default(T)❌ throws✅ default(T)
One match✅ that element✅ that element✅ that element✅ that element
Two or more matches✅ first one, ignores rest✅ first one, ignores rest❌ throws❌ throws
💻 See the code ▾
C# 
User u1 = users.Where(u => u.Role == "Admin").First();          // throws only if zero admins
User? u2 = users.Where(u => u.Role == "Admin").FirstOrDefault();   // null if zero admins — fine

Both are happy with two-or-more admins — they just take the first and move on.

C# 
User u3 = users.Where(u => u.Id == id).Single();           // ❌ throws if 0 OR 2+ matching ids
User? u4 = users.Where(u => u.Id == id).SingleOrDefault();  // null on 0 — still throws on 2+

SingleOrDefault only relaxes the zero case — two matching ids still throws, catching a real data bug.

🧭 Use Cases — recognize these when they happen to you ▾
1 Looking up a row by primary key or another unique column

When the schema promises at most one row for this key, use the Single family — it turns a broken uniqueness guarantee into an immediate, loud exception instead of a silently wrong answer. This is the #1 real reason to reach for Single.

RememberUnique-key lookup → Single family, not First family.
2 Grabbing "any" match when duplicates are normal and expected

Grabbing "the first error in the log" or "any admin on the team" is fine with several matches existing — Single would wrongly throw on a perfectly normal duplicate here, so First/FirstOrDefault is the correct choice.

RememberDuplicates expected and fine → First family, not Single family.
3 Checking a result against null on a value-type sequence

On IEnumerable<int>, the "not found" default from FirstOrDefault/SingleOrDefault is 0, not null — a plain if (result != null) check against it never fires, even when nothing actually matched.

RememberValue-type sequence → check against default(T), not null.
🌍 Real-world example ▾

FirstOrDefault is asking "is anyone home?" — fine with silence, fine with a crowd answering. Single is asking "who is the one person who lives here?" — more than one voice answering means something is wrong, not just noisy.
