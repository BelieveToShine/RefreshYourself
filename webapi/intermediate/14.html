?sort= & ?status= — one predictable pattern, or a guess every endpoint?

What conventions make sorting and filtering as query parameters predictable to consume?

Why it matters ▾
  • Interviewers use this to check you design for the consumer, not just "it returns the right rows."
  • Comes up on any collection endpoint — /orders, /customers, /products all eventually need sorting and filtering.
  • A sibling page covers Pagination (?page=/?cursor=) — that's the "how many, which chunk" question. This page is the different question of "which fields, in what order" — the two live in the same query string but are separate conventions to get right.
🔥 Easy interview recall

Sort → comma list, leading - = descending

Filter → one param per filterable field

Think: -field → descending, plain field → ascending status= → one query param per filterable field

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Letting clients sort or filter on every field isn't extra flexibility — it's a performance cliff. A column with no index looks fine in dev with 50 rows and locks the table at scale; a documented allow-list matched to real indexes is safer than blanket support.

🔄 Likely Follow-up

"If a client requests ?sort=nonExistentField, what should the API do?" Return a clear 400 naming the invalid field — silently ignoring it, or silently falling back to a default sort, both hide a client-side bug from the person who'd want to know about it.

🎯 Say this in the interview — the exact lines to land

"Sort and filter both belong in the query string, since they refine a request that's already valid. Sort as ?sort=-createdAt,name — a comma list where a leading - means descending. Filter as one query parameter per filterable field, like ?status=shipped&minTotal=50, and keep both to a documented allow-list matched to real indexes."

  • Sort convention → comma list, leading "-" = descending, no prefix = ascending.
  • Filter convention → one param per field — simplest, most discoverable; a generic ?filter= expression is only worth the trade once per-field params genuinely aren't enough.
  • Predictable → the same convention on every endpoint in the API, documented which fields qualify.
  • Sorting/filtering on an unindexed field → a performance cliff, not generosity — gate it with an allow-list.
📖 Explanation ▾

Sorting and filtering are both query parameters, not route parameters — see Route Parameters vs. Query Parameters. Neither one changes which resource you're asking for; both just reshape the collection that /orders already returns on its own.

A sort convention needs to express direction and multiple fields without inventing new syntax per field. ?sort=-createdAt,name — a comma-separated list, leading - for descending, no prefix for ascending — is compact and unambiguous, and it's the shape JSON:API and similar specs settled on. A filter convention has the opposite bias: one query parameter per filterable field (?status=shipped&minTotal=50) is the simplest, most discoverable option, because a consumer can read the field names straight off the response body. A single combined filter expression (?filter=status:shipped,total:gt:50) is more expressive but harder to discover and parse — reach for it only once separate per-field params genuinely run out of room.

"Predictable" is decided across the whole API, not one endpoint. If /orders uses ?sort= and /customers uses ?orderBy= for the same idea, that inconsistency costs every consumer who has to remember which endpoint uses which word. The other half of predictability is what happens when a client asks for something the API doesn't support — silently ignoring an unknown sort/filter field is far harder to debug against than a clear error naming exactly what was wrong.

💻 See the code ▾
C# 
private static readonly HashSet<string> SortableFields =
    new(StringComparer.OrdinalIgnoreCase) { "createdAt", "name" };   // allow-list, matches real indexes

foreach (var term in sort.Split(','))
{
    var desc = term.StartsWith("-");   // leading - = descending
    var field = desc ? term[1..] : term;
    if (!SortableFields.Contains(field))
        return BadRequest($"Unknown sort field '{field}'");   // ❌ 400, never silent
    query = desc ? query.OrderByDescending(field) : query.OrderBy(field);
}

One allow-list, one loop — every field goes through the same rule, including the 400 on an unknown one.

C# 
[HttpGet("orders")]
public IActionResult GetOrders(
    [FromQuery] string? status,      // one param per filterable field
    [FromQuery] decimal? minTotal)
{
    var query = _repo.AllOrders();
    if (status is not null)
        query = query.Where(o => o.Status == status);
    if (minTotal is not null)
        query = query.Where(o => o.Total >= minTotal);   // ✅ discoverable, no operator syntax to learn
    return Ok(query);
}

Each filterable field is its own parameter — a consumer can guess the shape without reading extra docs.

🌍 Real-world example ▾

Two endpoints on the same API, two different words for the same idea. /orders supports ?sort=-createdAt, but /customers only supports ?orderBy=lastName. A consumer building one generic API client now has to special-case every endpoint just to sort a list — the exact cost the "consistency across endpoints" rule exists to avoid. The fix isn't cleverer syntax on either endpoint, it's picking one convention and documenting it once for the whole API.
