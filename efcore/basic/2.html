DbContext & DbSet<T> — one request's session, not a shared cache

"What is DbContext, and what is DbSet<T>?"

Why it matters ▾
🗄️ DbContext
❗ ProblemOne request needs its own session — sharing one corrupts shared state.
✅ SolutionDbContext is scoped in DI — one instance per request, never shared.
RecallDbContext = the session, scoped one-per-request.
📋 DbSet<T>
❗ ProblemCode needs a queryable, typed way to reach one table.
✅ SolutionDbSet<T> is the entry point for one entity type, inside its DbContext.
RecallDbSet<T> = the table, living inside its DbContext.
🧠 Change Tracker
❗ ProblemSaveChanges() needs to know exactly what changed before writing anything.

🔥 Easy interview recall

DbContext → the session, one per request

DbSet<T> → one table, inside that session

Change Tracker → watches everything that session loaded

Think: DbContext is scoped per request — DbSet<T> and the Change Tracker live and die with it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

DbContext isn't a cache you keep around. A shared, long-lived instance keeps tracking more and more entities, starts serving stale data, and isn't safe to call from multiple threads at the same time.

🔄 Likely Follow-up

"What actually goes wrong if you register DbContext as a Singleton in DI instead of Scoped?" One shared instance now serves every concurrent request — it isn't thread-safe, so concurrent use can corrupt its internal state or throw; and its Change Tracker keeps growing, because nothing ever disposes the instance to release what it's tracked.

🎯 Say this in the interview — the exact lines to land

"DbContext is the unit-of-work — it represents one database session, holds the change tracker and model configuration, and is the entry point for querying and saving. DbSet<T> is the queryable entry point for one entity type inside that context, like context.Orders. It's registered scoped in DI — one instance per HTTP request — because it isn't thread-safe and shouldn't outlive one unit of work."

  • DbContext → the session, one unit of work, holds the change tracker and model.
  • DbSet<T> → the table, the queryable entry point for one entity type.
  • Lifetime → scoped, not singleton — one instance per request in ASP.NET Core.
  • Thread-safety → never share one instance across concurrent operations.
📖 Explanation ▾

DbContext represents a connection to the database for a logical session. It's the entry point for every query and every save, and it holds two things behind the scenes: the model configuration (what your entities map to) and the Change Tracker, which remembers every entity the context has loaded, added, or modified.

DbSet<T> is how you reach one entity type through a DbContext — context.Orders is the queryable, working entry point for the Order table. It doesn't hold its own separate state; it's a view into the same DbContext instance and the same Change Tracker.

Lifetime is the part that actually bites people. A DbContext is typically registered scoped in DI — one instance per HTTP request in ASP.NET Core — because it accumulates tracked entities in memory over its lifetime and its instance methods aren't safe to call concurrently from multiple threads.

💻 See the code ▾
C# 
public class StoreContext : DbContext
{
    public DbSet<Order> Orders { get; set; }        // one DbSet per entity type
    public DbSet<Customer> Customers { get; set; }
}

Each DbSet<T> property is a queryable entry point into one table, reached through the context.

C# 
builder.Services.AddDbContext<StoreContext>(opt =>
    opt.UseSqlServer(connectionString));   // ✅ registers StoreContext as Scoped by default

AddDbContext registers the context Scoped — one instance built and disposed per HTTP request.

C# 
private static readonly StoreContext _context = new(options);  // ❌ shared across every request

IActionResult Get() => Ok(_context.Orders.ToList());  // ❌ same instance, every request, forever

A static/singleton DbContext keeps every tracked entity forever and isn't safe under concurrent requests — this is the trap above, in code.

🧭 Use Cases — recognize these when they happen to you ▾
1 A single HTTP request comes in and saves an order

ASP.NET Core builds one DbContext for this request via AddDbContext, then disposes it when the request ends. This is the #1 scenario you'll actually run into.

RememberOne request → one DbContext, created and disposed with it.
2 One request loads both Orders and Customers

context.Orders and context.Customers are two views into the same DbContext — one SaveChanges() call writes every tracked change from both at once.

RememberDifferent DbSets, same DbContext, same Change Tracker.
3 Someone caches the DbContext in a static field

Every request now shares one instance — the Change Tracker never empties, and it isn't safe to call from multiple threads at once. A great interview trap — candidates often assume caching the context "saves time."

RememberStatic/singleton DbContext → shared state, not thread-safe.
🌍 Real-world example ▾

Think of a DbContext like a shopping cart for one visit to the store. You fill it, check out (SaveChanges()), and it's thrown away — you'd never hand the next customer the same cart, still holding last week's items.

Scenario: your API's memory keeps climbing under load, and requests occasionally throw unexplained exceptions. A common cause is a DbContext registered as a Singleton (or cached in a static field) — its Change Tracker never empties, and concurrent requests hit the same instance at once. The fix: register it Scoped (the AddDbContext default) and never store it in a static or singleton field.
