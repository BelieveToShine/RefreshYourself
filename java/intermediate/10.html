Wildcards: ? extends vs. ? super — Producer Extends, Consumer Super

"What's the PECS rule, and what can you actually do with a List<? extends Number> vs. a List<? super Number>?"

Why it matters ▾
📤 ? extends T (Producer)
❗ ProblemA method that just wants to read numbers out of any list of numbers-or-subtypes can't accept a plain List<Number> parameter — a caller's List<Integer> isn't a List<Number> in Java's type system, so the method would reject perfectly safe callers.
✅ Solution? extends T widens the parameter to accept List<Integer>, List<Double>, or List<Number> itself — anything that produces a T or narrower, safe to read, but writing is blocked because the compiler can't know the real element type.
Recallextends = read-only producer.
📥 ? super T (Consumer)
❗ ProblemA method that wants to add Integers into a caller-supplied list can't accept a List<Integer> parameter only — a caller holding a List<Number> or List<Object> to collect results into would be rejected even though adding an Integer into either is perfectly safe.
✅ Solution? super T widens the parameter to accept List<T>, List<Number>, or List<Object> — anything that can consume a T, safe to write into, but reading back only gives you Object.
Recallsuper = write-only consumer.
🔥 Easy interview recall

? extends T → producer, read-only

? super T → consumer, write-only

Think: PECS — Producer Extends, Consumer Super.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

? extends T is not read-and-write. You can't call list.add(...) on a List<? extends Number> (beyond null) — the compiler doesn't know the real element type, so it can't guarantee what you're adding is actually compatible.

🔄 Likely Follow-up

"Why not just use a plain List<Number> parameter?" Because Java generics aren't covariant — a List<Integer> is not a List<Number>, so a plain List<Number> parameter would reject a caller's List<Integer> entirely; wildcards exist specifically to accept that whole family of related types.

🎯 Say this in the interview — the exact lines to land

"? extends T makes the generic type a producer you can safely read a T from but not write into. ? super T makes it a consumer you can safely write a T into but can only read back as Object. PECS: Producer Extends, Consumer Super."

  • ? extends T → read-safe, write blocked except null.
  • ? super T → write-safe, reads only come back as Object.
  • Need both read and write → skip the wildcard, use a plain type parameter <T>.
  • PECS → Producer Extends, Consumer Super, the standard interview mnemonic.
📖 Explanation ▾

A producer wildcard (? extends T) says "this list holds some unknown subtype of T." Reading is safe — anything that comes out is guaranteed to be at least a T — but writing isn't, because the compiler has no way to confirm the value you're adding matches that specific unknown subtype, so it refuses every add() except null.

A consumer wildcard (? super T) says "this list holds T or something further up the hierarchy." Writing a T is always safe — any supertype slot can hold it — but reading only gives back the one type the compiler can be certain of: Object, since the real element type could be anything from T up to Object itself.

PECS exists because this choice isn't arbitrary — it follows directly from how the parameter is actually used. If a method only reads from the collection, it's a producer; if it only writes into it, it's a consumer; if it genuinely needs both, a wildcard is the wrong tool entirely — use a plain type parameter instead.

💻 See the code ▾
Java 
static double sum(List<? extends Number> nums) {
    double total = 0;
    for (Number n : nums) total += n.doubleValue();  // ✅ safe read
    return total;
}

Accepts List<Integer>, List<Double>, anything — reading is always safe.

Java 
static void addIntegers(List<? super Integer> list) {
    list.add(1);               // ✅ safe write
    Object o = list.get(0);  // only Object comes back
}

Accepts List<Integer>, List<Number>, List<Object> — writing is always safe.

Java 
static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (int i = 0; i < src.size(); i++)
        dest.set(i, src.get(i));   // ✅ read from src, write into dest
}

The JDK's own Collections.copy signature — textbook PECS, both roles at once.

🧭 Use Cases — recognize these when they happen to you ▾
1 Writing a generic utility that only reads values, like sum()

This is the #1 scenario you'll actually run into. A method that only reads elements should take the producer wildcard so it can accept List< Integer>, List<Double>, or any other Number subtype list, not just an exact List<Number>.

RememberOnly reading → ? extends T.
2 Writing a generic utility that only adds values into a caller's list

A method that collects results into a caller-supplied list should take the consumer wildcard, so a caller can hand in a List<Number> or List<Object> to gather results into, not only an exact-match list.

RememberOnly writing → ? super T.
3 You try to call .add() on a List<? extends T> parameter

The compiler genuinely cannot know whether the real list is a List<Integer>, List<Double>, or something else — so it blocks every write that isn't null, no matter how "obviously safe" the value being added looks.

Remember? extends T blocks writes — that's the whole point, not a bug.
🌍 Real-world example ▾

The JDK's own Collections.copy(List<? super T> dest, List<? extends T> src) is the canonical PECS example: src only ever gets read from, so it's a producer (extends); dest only ever gets written into, so it's a consumer (super) — the same method signature almost every PECS explanation ends up pointing back at.
