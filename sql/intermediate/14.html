Index Seek vs. Scan vs. Table Scan — is a table scan always bad?

"Index seek vs. index scan vs. table scan — what does each actually mean in an execution plan?"

Why it matters ▾
  • Almost every execution-plan review starts with "is this a seek, a scan, or a table scan" — reading a plan correctly starts here.
  • Explains why "I saw a table scan" isn't automatically a performance complaint — a lot of candidates get this backwards.
  • A near-universal follow-up the moment query tuning or execution plans come up in an interview.
🔥 Easy interview recall

Seek → jumps straight to the row(s)

Scan → reads the whole index

Table Scan → reads every row, no index used

Think: Seek → dictionary jump straight to the page Scan → reads the whole index anyway Table Scan → reads the whole table — fine if it's small

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A table scan in the plan means something's wrong." A table scan on a genuinely small table is often the CORRECT, fastest choice — the real problem is only a scan on a LARGE table where a seek should have been possible.

🔄 Likely Follow-up

"You see a table scan and assume something's wrong — what should you check first?" How large the table actually is — a scan on a handful of rows or a small lookup table is expected and cheap; the concern only becomes real once the table is big enough that a scan is genuinely expensive.

🎯 Say this in the interview — the exact lines to land

"An index seek jumps straight to the matching row(s) using the index's B-tree — efficient, especially for selective queries. An index scan reads every entry in the index because the predicate isn't selective enough, or the query needs most of the data anyway. A table scan reads every row in the table, ignoring indexes entirely — that's only a real problem when the table is large; on a small table it's often the fastest plan available."

  • Seek → direct B-tree jump to the matching row(s).
  • Scan → reads the entire index, even though it's using one.
  • Table Scan → reads every row, ignoring indexes entirely.
  • On a small table, a table scan can be the correct, cheapest plan.
  • The real red flag is a scan/table scan on a large table where a seek should have worked.
📖 Explanation ▾

An index seek uses the index's B-tree structure to navigate directly to the specific row(s) that match the query — a few page reads down the tree, not a walk through the whole thing. An index scan still uses an index, but reads every entry at its leaf level from start to end. The optimizer picks a scan over a seek when the predicate isn't selective enough to justify navigating the tree, or when the query needs most or all of the indexed rows anyway — at that point, reading the leaf level in order is cheaper than repeated tree lookups.

A table scan reads every row in the table itself, bypassing indexes altogether — a clustered index scan if the table has one (the data pages are read in their physical order), or a heap scan if it doesn't (an unordered read of every page). This happens when there's no useful index for the predicate — or, importantly, when the table is small enough that reading all of it outright is cheaper than the overhead of using an index at all. The optimizer is cost-based: it isn't "avoiding indexes," it's picking whichever plan actually reads less work overall.

💻 See the code ▾
SQL 
SELECT * FROM Orders
WHERE OrderId = 48213;  -- Index Seek: one exact key, straight B-tree jump

A highly selective, indexed equality predicate — the exact case a seek is built for.

SQL 
SELECT OrderId FROM Orders
WHERE Status <> 'Cancelled';  -- Index Scan: matches most rows, not selective

The predicate excludes only a handful of rows, so the engine reads the whole index leaf level instead of seeking.

SQL 
SELECT * FROM OrderStatusLookup
WHERE Code = 'SHIPPED';  -- Table Scan: only 6 rows, correct + fastest plan

A tiny lookup table — the optimizer correctly skips indexing overhead and just reads all 6 rows.

🌍 Real-world example ▾

A seek is flipping straight to the right page in a dictionary. A scan is reading every entry in the dictionary's index at the back, front to back. A table scan is reading the whole book, page by page, ignoring the index at the back entirely — silly for a 900-page novel, but perfectly reasonable for a 6-page pamphlet.

Scenario: a dashboard query against a 50-million-row Orders table is timing out, and the plan shows a Table Scan on Orders. That's a genuine red flag at that size — check whether a useful index exists on the filtered column, and whether the predicate is actually selective enough for the optimizer to choose a seek over it.
