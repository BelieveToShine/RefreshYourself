How the optimizer picks an index — and when it decides not to

How does the query optimizer decide which index to use, or decide not to use one at all?

Why it matters ▾
⚖️ Cost-Based Index Choice
❗ ProblemA common real bug report: "I added an index and the query still isn't using it" — engineers stare at an execution plan assuming the index must be broken, when the optimizer is often correctly deciding a scan is cheaper.
✅ SolutionThe optimizer always picks whichever plan it estimates does the least total work, using row-count and value-distribution statistics — not "index exists → use it," so an unused index can be the correct decision, not a bug.
RecallOptimizer picks lowest estimated cost — not "index exists → use it."
🔥 Easy interview recall

Optimizer = "picks whichever plan it estimates does the least total work — not whichever plan has an index."

Think: a flag that's true 90% of the time → index skipped, plain scan wins.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An index existing doesn't mean it gets used. The optimizer can deliberately skip it if it estimates a full scan will be cheaper — common on a low-selectivity column, where most rows match and the extra hops through the index end up costing more than just scanning straight through the table.

🔄 Likely Follow-up

"Why would the optimizer ignore an index on a low-selectivity column, like a boolean IsActive flag?" Because if most rows match (say 90% are IsActive = true), using the index would mean almost as many row lookups as the table has rows anyway, plus the added overhead of each index hop — a plain scan ends up being the cheaper estimated plan.

🎯 Say this in the interview — the exact lines to land

"The optimizer always picks whichever plan it estimates does the least total work, using table and column statistics to guess how many rows each candidate plan would touch. An index sitting unused isn't automatically a bug — it can be the optimizer correctly deciding a scan is cheaper for that specific query."

  • Decision is by → estimated cost, using row-count and value-distribution statistics.
  • Not "index exists → use it" → it's whichever plan does less total work.
  • Low-selectivity column (most rows match) → index often skipped, plain scan wins instead.
  • An unused index → not automatically a bug → can be the correct decision.
  • Stale or missing statistics → bad cost estimates, so the "cheapest" guess can turn out wrong.
📖 Explanation ▾

The optimizer is cost-based: for a given query it works out several candidate plans, and for each one estimates how many rows and pages it would have to touch. Those estimates come from statistics the database keeps on each table/column — row counts and a histogram-like summary of how values are distributed. It then picks whichever candidate plan has the lowest total estimated cost, index or not.

An index seek isn't free even when it matches the filter — each match still needs a lookup step to fetch the actual row. On a low-selectivity column (a large fraction of rows match, like a flag that's true 90% of the time), that adds up to nearly as many lookups as the table has rows, on top of the extra hop through the index itself. A single pass straight through the table ends up estimated as less total work, so the optimizer takes that instead.

This whole decision only holds up if the statistics themselves are reasonably current. Statistics drift out of date as a table's data changes, and stale row-count or distribution numbers can make the optimizer's "cheapest" guess wrong even though its reasoning process was correct.

🧭 Use Cases — recognize these when they happen to you ▾
1 You filter on a low-selectivity column, like a boolean flag that's true 90% of the time

Using the index would still mean almost as many row lookups as the table has rows, plus the extra hop through the index — so a plain scan comes out as the cheaper estimated plan and wins. This is the #1 scenario behind the "I added an index and it's still not used" bug report.

RememberLow-selectivity flag → scan usually wins, not the index.
2 You filter on a highly selective column, where only a small fraction of rows match

The flip side of scenario 1, same reasoning: with only a few matching rows, the index's per-match lookup stays cheap, so the total estimated cost comes out lower than scanning the whole table — the same optimizer logic just lands on the opposite plan.

RememberHigh-selectivity filter → index seek usually wins.
3 The chosen plan is wrong even though nothing about the query or indexes changed

The optimizer's cost comparison is only as good as its statistics. If row-count or value-distribution stats went stale after the table's data changed, the optimizer's reasoning process is still correct but its estimate isn't — an easy plan to mistake for the optimizer itself being broken.

RememberBad plan + healthy indexes → check statistics, not the index.
🌍 Real-world example ▾

If you only need milk, checking the store directory for "aisle 3" is a quick, targeted shortcut — worth the extra step. But if you're already grabbing nearly everything in the store, checking the directory for almost every single item on your list isn't actually faster than just walking straight through every aisle once. That's the same trade-off the optimizer is weighing when it chooses between an index and a scan.
