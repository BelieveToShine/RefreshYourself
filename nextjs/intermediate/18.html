The App Router dropped the i18n config — so how does locale routing even work now?

"How does i18n routing work in the App Router, compared to the Pages Router's built-in config?"

Why it matters ▾
🌐 i18n Routing in the App Router
❗ ProblemA global product needs each visitor served content in their own language, with a URL structure that reflects it — but the App Router removed the Pages Router's old built-in i18n config option entirely.
✅ SolutionThe current approach is a pattern, not a flag: Middleware detects the visitor's locale (cookie, Accept-Language header, or an existing URL segment) and routes into a dynamic [locale] segment, which Server Components then read.
Recalli18n in the App Router = a pattern you build, not a switch you flip.
🔥 Easy interview recall

Pages Router → built-in i18n config flag

App Router → Middleware + [locale], by hand

Think: The Pages Router flipped a switch. The App Router makes you wire it yourself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Looking for the Pages Router's i18n config inside the App Router's next.config.js. It doesn't exist there — App Router i18n is a pattern built with Middleware and dynamic segments, not a single config flag.

🔄 Likely Follow-up

"How would translated content actually get loaded per locale?" Typically a dictionary/JSON file per locale, loaded inside the Server Component based on the [locale] param — kept server-side so translation data never needs its own separate client fetch.

🎯 Say this in the interview — the exact lines to land

"The App Router has no built-in i18n config — that was a Pages Router feature. The current pattern is Middleware detecting the locale from a cookie, header, or URL segment, then routing into a [locale] dynamic segment that Server Components read to load the right translations."

  • App Router → no built-in i18n config, unlike the Pages Router.
  • middleware.js → detects the locale from cookie, header, or URL.
  • [locale] segment → every route lives under it once detected.
  • Translation dictionaries → loaded server-side, keyed by the locale param.
📖 Explanation ▾

The Pages Router shipped i18n as a single configuration object — set a list of locales, and Next.js handled locale-prefixed routing automatically. The App Router has no equivalent built-in option; the framework intentionally leaves routing composition (including locale routing) to patterns built from its existing primitives instead of a dedicated feature.

The common pattern: middleware.js inspects the incoming request for a locale signal — a cookie from a previous visit, the Accept-Language header on a first visit, or an existing /en/-style segment already in the URL — and redirects or rewrites into a route tree organized under a dynamic [locale] folder.

From there, every page under [locale] receives that value as a route param, and can use it to look up the matching translation dictionary before rendering — no different from reading any other dynamic segment.

💻 See the code ▾
JS 
// middleware.js
export function middleware(request) {
  const hasLocale = /^\/(en|fr|de)(\/|$)/.test(request.nextUrl.pathname);
  if (hasLocale) return;  // ✅ already under /[locale] — nothing to do

  const locale = request.cookies.get('locale')?.value ?? 'en';
  return NextResponse.redirect(
    new URL(`/${locale}${request.nextUrl.pathname}`, request.url)
  );  // ✅ /blog/post → /en/blog/post
}

This is the whole trick — there's no config flag doing it for you.

JSX 
// app/[locale]/blog/[slug]/page.jsx
export default async function Page({ params }) {
  const { locale } = await params;
  const dict = await getDictionary(locale);  // ✅ server-side, no client fetch
  return <h1>{dict.title}</h1>;
}

locale is just a normal route param — read the same way any other dynamic segment is.

🧭 Use Cases — recognize these when they happen to you ▾
1 A visitor arrives for the first time with a French browser, no cookie set yet

With no cookie to read yet, Middleware falls back to the Accept-Language header and redirects into the matching [locale] segment on the very first request.

RememberFirst visit, no cookie → the header is the only signal Middleware has.
2 A user picks a different language from a selector in the UI

Once a cookie is set, Middleware prefers it over the Accept-Language header on every later request — the explicit choice a visitor made overrides what their browser happens to report.

RememberAn explicit cookie choice outranks the header, every time after.
3 You add an i18n key to the App Router's next.config.js, expecting it to just work

That config key only ever applied to the Pages Router. In an App Router project it has no effect on routing at all — locale handling still has to be built with Middleware and a [locale] segment, config key or not.

RememberThe old i18n config key has no routing effect in the App Router.
🌍 Real-world example ▾

A SaaS product rolling out French and German support migrates from the Pages Router to the App Router. The old i18n: { locales: ['en','fr','de'] } config stops doing anything, and the team has to rebuild locale detection by hand — Middleware reading the cookie/header, and every route moved under a new [locale] folder — before localized URLs work again.
