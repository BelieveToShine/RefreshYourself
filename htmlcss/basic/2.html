Semantic HTML — a div can look like a button. It can't act like one.

"What is semantic HTML, and why is <button> better than a <div onclick="">?"

Why it matters ▾
🚫 <div onclick>
❗ ProblemA styled <div> with a click handler can look pixel-identical to a button, but a keyboard user can't Tab to it, Enter/Space does nothing, and a screen reader announces nothing about it.
✅ SolutionMatching that behavior by hand means adding tabindex="0" for focus, role="button" for the announcement, and a keydown handler for Enter/Space — real extra work, and easy to leave incomplete.
Recalldiv onclick = looks like a button, gives keyboard/screen-reader users nothing for free.
✅ <button>
❗ ProblemHand-writing ARIA, tabindex, and key handling on a div just to reach basic button behavior is real work, and easy to get subtly wrong or leave half-done.
✅ SolutionA real <button> is focusable by Tab, activates on both Enter and Space, and announces its own role and name ("Submit, button") — all built into the browser for free.
Recallbutton = focus + keyboard + announced name/role, zero ARIA needed.
🔥 Easy interview recall

<div> → a box, no built-in meaning or behavior

<button> → free focus, keyboard, and an announced name/role

<a> → goes somewhere (has a URL); <button> does something

Think: <div> is invisible to a screen reader. <button> announces itself without you writing a line of ARIA.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It looks and clicks the same, so it IS the same." Identical CSS makes two elements look alike — it never gives a <div> the keyboard focus, key handling, or accessible name a real <button> gets automatically; those come from the element itself, not from how it's styled.

🔄 Likely Follow-up

"So can't I just fix it by adding tabindex='0' to the div?" That only makes it reachable by Tab — you'd still have to hand-write role="button", an accessible name, and a keydown handler for Enter and Space just to reach the parity a real <button> gives you with zero extra code.

🎯 Say this in the interview — the exact lines to land

"Semantic HTML means picking elements for what they mean, not just how they look — <header>, <nav>, <main>, <section>, <article>, and <footer> carry that meaning into the DOM and the accessibility tree, which a generic <div> never does no matter how it's styled. That's exactly why <button> beats <div onclick>: it's focusable, activates on Enter and Space, and announces its own role and name — a div needs ARIA, tabindex, and manual key handling just to catch up."

  • Semantic ≠ prettier tags — it's information the browser hands to assistive tech, not a styling choice.
  • Accessibility tree — built alongside the DOM; a screen reader reads it directly, and a bare <div> contributes nothing to it.
  • <button> vs. <div onclick> → native focus + keyboard + role/name, with zero ARIA to write.
  • <a> navigates, <button> acts — a link has a URL and works with the browser's back button and "open in new tab"; a button doesn't.
  • SEO angle — crawlers use <header>/<nav>/<main>/<article> as a structure/relevance signal a div-only page can't offer.
📖 Explanation ▾

Semantic HTML means choosing an element for what it means, not just how it can be made to look. <header>, <nav>, <main>, <section>, <article>, and <footer> can all be visually recreated with a plain <div> plus CSS — but only the semantic tag also tells the browser what that chunk of the page is. That information flows into the accessibility tree, a structure the browser builds alongside the DOM specifically for assistive tech — a screen reader reads it directly to announce landmarks like "navigation" or "main content." A <div>, styled identically, gives the accessibility tree nothing at all.

That's the same reason <button> beats <div onclick="...">. A native <button> is focusable by Tab, activates on both Enter and Space, and is announced with its own role ("button") and name — all of that comes free from the browser. A <div> with a click handler gets none of it; matching that behavior means adding tabindex="0" for focus, role="button" for the announcement, and a keydown handler for Enter/Space by hand — real work to reach a baseline the real element already has.

<div onclick><button>
Focusable by Tab?❌ No — needs tabindex✅ Yes, built in
Enter/Space activates it?❌ No — needs a manual keydown handler✅ Yes, built in
Screen reader announces it?❌ Silent — no role, no name, unless ARIA is added✅ Announces role + name, e.g. "Submit, button"
Extra work to match?tabindex + role + key handling, all by handNone

The same "meaning over look" idea separates <a> and <button>: a link navigates — it has an href, works with the browser's back button, and can be opened in a new tab — while a button performs an action on the current page (submitting a form, opening a menu) with no URL behind it. Using the wrong one breaks something real: a "button" built from <a href="#"> confuses browser history and link-sharing; a "link" built from <button> can't be opened in a new tab or bookmarked. Semantics also help SEO the same way they help accessibility — search crawlers use <header>/<nav>/<main>/<article> as a structural signal for what matters on the page, something a page built entirely from <div>s can't offer.

💻 See the code ▾
HTML 
<div onclick="submitForm()">Submit</div>  // ❌ not focusable, silent to screen readers

<button onclick="submitForm()">Submit</button>  // ✅ same handler, real behavior for free

Same click handler, same look with CSS — only <button> is reachable by Tab, fires on Enter/Space, and gets announced as "Submit, button."

HTML 
<div id="top"><div id="nav">...</div></div>  // ❌ a div is a div is a div — no meaning

<header>...</header>
<nav>...</nav>  // ✅ names the landmark for the a11y tree + crawlers

Same nested boxes, but only the semantic version tells the browser (and a screen reader, and a search crawler) what each part of the page actually is.

HTML 
<a href="/cart">View cart</a>  // goes somewhere — has a URL

<button type="button">Add to cart</button>  // does something — no URL at all

<a> works with back/forward, bookmarking, and "open in new tab" because it navigates; <button> has none of that because it isn't going anywhere.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're styling a custom clickable card, dropdown trigger, or menu item and reach for a div with an onclick handler because it's quicker to skin

This is the #1 scenario you'll actually run into. The div looks and clicks exactly like a button because CSS made it look that way — but nothing gives it Tab focus, Enter/Space activation, or an announced name, because those come from the element itself, not its styling.

RememberFast to style ≠ usable — swap it for a real <button>.
2 You add tabindex to the div, thinking that's the whole fix

A common trap — tabindex="0" only makes the div reachable by Tab. Enter/Space still do nothing without a hand-written keydown handler, and a screen reader still announces nothing without a hand-written role="button" and accessible name — a real <button> gives all three for free.

Remembertabindex fixes focus only — not keyboard activation or the announcement.
3 You're laying out a page's structure — header, nav, main content — and it's all just nested divs

A screen reader can jump straight to "navigation" or "main content" as landmarks, and a search crawler can weigh what's actually structural — but only once <header>/<nav>/<main> name those regions. Nested <div>s give both of them nothing to go on, no matter how the page looks.

RememberLandmark tags feed the accessibility tree and crawlers — div soup feeds neither.
🌍 Real-world example ▾

A styled <div> pretending to be a button is like a photograph of a doorknob taped to a wall. It looks exactly right, but nothing happens when someone reaches for it in the dark — no Tab focus, no Enter/Space, no announcement. A real <button> is the actual doorknob: turn it with a mouse click, or find it purely by feel with the keyboard, and it opens the door either way.
