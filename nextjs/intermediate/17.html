fetch() already caches on the server — so why would you still reach for SWR?

"When would you still reach for SWR or TanStack Query in a Next.js App Router project?"

Why it matters ▾
🗄️ fetch() Data Cache
❗ ProblemA Server Component re-fetching the same rarely-changing data on every single request would be slow and wasteful.
✅ SolutionNext's own fetch() caching (the Data Cache, revalidate options) caches a server-side fetch automatically, scoped to the server-rendering lifecycle.
Recallfetch() caching = server-side, settled once per cache window.
🔄 SWR / TanStack Query
❗ ProblemSome data genuinely needs to refetch based on client-side events — the window regaining focus, an interval, a search box's own keystrokes — which a one-time server fetch can't react to after the page has already loaded.
✅ SolutionA client-side library refetches on those events automatically, inside a Client Component, with built-in loading/error state and cache-sharing across components.
RecallClient libraries = reactive to whatever happens after the page already loaded.
🔥 Easy interview recall

fetch() → server-side, one-time per cache window

SWR / TanStack → client-side, reactive to focus/interval

Think: fetch() answers "what's true right now, on the server." SWR/TanStack answers "keep this updated while the user's looking."

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for SWR or TanStack Query inside a Server Component. Their value — client-side caching, refetch-on-focus, state tied to React re-renders — only applies in a Client Component; a Server Component should just call Next's own fetch() directly.

🔄 Likely Follow-up

"When would a Client Component need its own data-fetching library instead of just receiving server-fetched data as a prop?" When the data genuinely needs to update after the initial load based on client-side interaction — live polling, refetch-on-window-focus, or a search-as-you-type result list.

🎯 Say this in the interview — the exact lines to land

"Next's own fetch() caching is for server-side data fetching inside Server Components — it settles once per request or revalidate window. SWR and TanStack Query solve a different problem: client-side data that needs to refetch based on client events like focus or an interval, with their own loading and error state built in."

  • fetch() → Server Component default, no library needed.
  • SWR / TanStack Query → Client Component only, reactive to focus/interval.
  • Built-in loading/error state and cache-sharing is the real value they add.
  • Never the two in the same spot — pick by which component type is doing the fetching.
📖 Explanation ▾

Next.js extends the native fetch() so a call made inside a Server Component can be cached (the Data Cache) and revalidated on a schedule or on demand. It's built for data that's genuinely a server-side concern — fetched once as part of producing a response, not something the already-rendered page keeps checking on.

SWR and TanStack Query are client-side libraries solving a different problem entirely: data that needs to stay current *after* the page has already loaded, driven by things that only happen in the browser — the tab regaining focus, a polling interval, a user typing into a search box.

They're not competitors so much as tools for two different lifecycles — a Server Component's fetch happens once as part of rendering a response; a client library's fetch happens again and again, for as long as the component stays mounted and something tells it to refetch.

💻 See the code ▾
JSX 
// Server Component — no client library needed
export default async function Page() {
  const res = await fetch('https://api.example.com/stats', {
    next: { revalidate: 60 },  // ✅ cached, refreshed at most once a minute
  });
  const stats = await res.json();
  return <Stats data={stats} />;
}

One fetch, cached by Next — no loading state to write, because it resolves before the page renders.

JSX 
'use client';  // ✅ required — this is a Client Component

function LiveTicker() {
  const { data, isLoading } = useSWR('/api/price', fetcher, {
    refreshInterval: 5000,  // 🔁 refetches every 5s while mounted
  });
  if (isLoading) return <Spinner />;
  return <p>{data.price}</p>;
}

The loading state and the repeating refetch are the whole reason SWR is here.

🧭 Use Cases — recognize these when they happen to you ▾
1 A dashboard page just needs today's numbers when it loads

Nothing on this page needs to update after it loads, so plain fetch() inside the Server Component covers it completely — this is the most common case, and no client library is needed at all.

RememberNo reason to refetch after load → fetch() alone is the right call.
2 A live price ticker or notification badge needs to stay current while the tab is open

A server fetch only runs once when the page first renders — it has no way to keep updating after that. useSWR's refreshInterval keeps polling for as long as the component stays mounted.

RememberNeeds to stay live after load → a client-side library, not fetch().
3 You call useSWR inside a Server Component

Hooks like useSWR/useQuery rely on React state and effects, which don't exist in a Server Component — it has to be marked 'use client' first, and even then the value this library adds (refetch-on-focus, client cache) is wasted if the data never needed to update after load in the first place.

RememberA client data hook needs a Client Component — no exceptions.
🌍 Real-world example ▾

A trading dashboard shows a price that updates every few seconds, inside a page that was otherwise server-rendered. The surrounding layout and static data load once via fetch() in a Server Component, while just the price widget is a small Client Component using useSWR with a short refreshInterval — each tool handles the half of the page it's actually good at.
