Open/Closed Principle — open for extension, closed for modification

What does "open for extension, closed for modification" actually mean, and what does violating it look like in real code?

Why it matters ▾
🔓 Open/Closed Principle
❗ ProblemA method like PaymentProcessor.Process(string type) with a growing if/else chain means every new case requires reopening and editing that same already-tested code — risking the branches that already worked.
✅ SolutionExtract an interface like IPaymentMethod so each new case becomes its own new class — the existing class stays closed, with zero edits needed.
RecallOCP = add new behavior with new code, never by editing existing, tested code.
🔥 Easy interview recall

OCP = "add new behavior without editing the old, tested code."

Think: new payment type → new class, never a new if-branch.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

OCP does not mean "never change code." It means the existing, already-tested class doesn't need internal changes — you still write new code, just in a new class, never inside the old one.

🔄 Likely Follow-up

"Isn't this just the Strategy pattern?" No — OCP is the principle (behavior should be extendable without modifying existing code); Strategy is one common pattern that satisfies it. You can also satisfy OCP with other mechanisms, like plugin or extension points.

🎯 Say this in the interview — the exact lines to land

"Open/Closed means a class should be open for extension but closed for modification — you can add new behavior without editing its existing, tested source code. The classic violation is a Process(string type) method with a growing if/else chain; the fix is extracting an interface like IPaymentMethod so each new case becomes its own class instead of a new branch."

  • if (type == "X") chains → every new case means editing tested code.
  • Extract an interface → one class per case, zero changes to the caller.
  • The fix is the Strategy pattern emerging from OCP pressure — same idea, different name.
  • OCP isn't a ban on writing code → you still add a new class, you just don't touch the old one.
📖 Explanation ▾

Open for extension means you can genuinely add new behavior to a system. Closed for modification means you don't have to edit a class's existing, already-shipped source to do it. The "closed" half is what actually matters day to day — every time you re-open a class that's already working and already tested, you risk breaking the branches that were fine before you touched it, not just failing to add the new one.

The classic violation is a method like PaymentProcessor.Process(string type) with a growing if (type == "CreditCard") … else if (type == "PayPal") … chain. Every new payment type means opening this same method again, adding another branch, and re-testing everything — the new case and every old one — because they all live in one place.

The fix is to extract an IPaymentMethod interface with a single Pay() method, give each payment type its own class implementing it, and have PaymentProcessor depend on the interface instead of a string and an if/else chain. Adding PayPal support now means writing a PayPalPayment class — zero edits to PaymentProcessor. This is exactly the Strategy pattern emerging from OCP pressure: OCP is the goal, Strategy is one common way to reach it.

💻 See the code ▾
C# 
public class PaymentProcessor
{
    public void Process(string type, decimal amount)
    {
        if (type == "CreditCard")
        {
            // charge card
        }
        else if (type == "PayPal")
        {
            // charge PayPal
        }
        // ❌ new type? edit this method again
    }
}

Every new payment type means opening this method again — and risking the branches that already work.

C# 
public interface IPaymentMethod
{
    void Pay(decimal amount);
}

public class CreditCardPayment : IPaymentMethod
{
    public void Pay(decimal amount) { /* charge card */ }
}

public class PaymentProcessor
{
    public void Process(IPaymentMethod method, decimal amount)
        => method.Pay(amount);   // ✅ no if/else at all
}

PaymentProcessor no longer knows how many payment types exist — it just calls Pay().

C# 
public class PayPalPayment : IPaymentMethod
{
    public void Pay(decimal amount) { /* charge PayPal */ }
}
// ✅ PaymentProcessor.cs — untouched, 0 lines changed

Adding PayPal support is one new class — PaymentProcessor's source doesn't change at all.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're reviewing a method with a growing if/else chain

Every new case added another branch to the same method, and every addition means re-touching and re-testing all the old branches too. This is the classic interview opener: "here's a method with a growing if/else — what's wrong with it?"

RememberGrowing if/else in one method → OCP violation, first thing to name.
2 A new case needs to be added (e.g. a new payment type)

With IPaymentMethod already extracted, adding PayPal support is one new class implementing Pay() — PaymentProcessor's source doesn't change at all. This is the #1 scenario you'll actually run into.

RememberNew case → new class behind the interface, not a new branch.
3 You assume OCP means "never touch any code again"

OCP does not mean "never change code" — it means the existing, already-tested class doesn't need internal changes. You still write new code, just in a new class, never inside the old one.

Remember"Closed" means closed to edits, not closed to new code.
🌍 Real-world example ▾

Every time your product adds a payment provider, someone edits PaymentProcessor.Process and risks breaking CreditCard or PayPal along the way. Extract IPaymentMethod, and adding a provider becomes: write one new class that implements Pay(). PaymentProcessor, and every payment type that already shipped, stays untouched.
