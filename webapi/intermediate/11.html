Caching — does the work get skipped before your API, or inside it?

What are the common caching strategies for an API, and when would you reach for each?

Why it matters ▾
🌐 Response caching
❗ ProblemWithout a way to tell the client or a CDN a response is still fresh, every request — even one asking for something that hasn't changed — has to hit the API all over again.
✅ SolutionCache-Control and ETag let the client/CDN answer repeat requests themselves — a 304 Not Modified skips resending the body when nothing changed.
RecallCache-Control/ETag → the client/CDN skips asking again.
🗄️ Distributed cache
❗ ProblemWith more than one instance behind a load balancer, an in-memory cache local to just one instance leaves every other instance still redoing the same slow query or call.
✅ SolutionA shared store like Redis gives every instance the same cached result, computed once, instead of each instance doing the work itself.
RecallDistributed cache → the API skips redoing the work.
🔥 Easy interview recall

Cache-Control / ETag → the client/CDN skips asking again

Distributed cache → the API skips redoing the work

Think: Cache-Control stops the question at the door. Redis stops the work once it's already inside.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Caching a response doesn't automatically ask who it's for. Caching GET /me/orders under a shared cache key with no Vary or private distinction can serve one user's order history straight to a different user.

🔄 Likely Follow-up

"How do you invalidate a distributed cache entry when the underlying data changes?" The same code path that writes the update also deletes or refreshes that cache key — explicit invalidation on write, with a short TTL underneath it only as a safety net. Relying on the TTL alone means every client can read stale data for up to the full TTL window after every write.

🎯 Say this in the interview — the exact lines to land

"Response caching lets the client or a CDN reuse a response without asking the server again, using Cache-Control and ETag. A distributed cache lets the API itself skip redoing expensive work — like a slow query — by sharing one cached result across every instance behind the load balancer."

  • Cache-Control → tells the client/CDN how long to reuse a response, no server round-trip needed.
  • ETag + If-None-Match → a 304 Not Modified skips resending the body when nothing changed.
  • Distributed cache (Redis) → one shared result across every instance — a local in-memory cache leaves the others still doing the slow work.
  • Invalidate on write → delete or refresh the key the moment the data changes; TTL is only the safety net.
  • Never key a cache by URL alone → per-user data needs a private/Vary-aware key, not a shared one.
📖 Explanation ▾

Response caching moves the answer as close to the client as possible. A response carries a Cache-Control header telling the browser or a CDN how long it's safe to reuse that response without asking again (max-age=60), and whether it's shareable at all (public vs. private). An ETag is a fingerprint of the response body — the client sends it back on the next request as If-None-Match, and the server can reply 304 Not Modified with no body at all if nothing changed. Done well, a CDN can answer most repeat requests without your API ever seeing them.

A distributed cache solves a different problem: the API itself doing the same expensive work — a slow query, a call to another service — over and over. It matters specifically because there's more than one instance behind a load balancer. An in-memory cache local to one instance leaves every other instance still hitting the slow path, and the instances can end up disagreeing with each other as data changes. A shared store like Redis gives every instance the same answer, computed once.

Both layers still need an expiry even when nothing invalidates them on purpose — max-age on the response side and a TTL on the distributed-cache side both put a ceiling on how stale an answer can get.

💻 See the code ▾
C# 
[HttpGet]
[ResponseCache(Duration = 60, Location = ResponseCacheLocation.Any)]
public IActionResult GetCatalog()
{
    var items = _catalog.GetAll();   // ✅ same for everyone — safe to cache
    return Ok(items);
}

This sends Cache-Control: max-age=60 on the response — a CDN can now answer the next 60 seconds of requests itself.

C# 
[HttpGet("{id}")]
public IActionResult GetProduct(int id)
{
    var product = _catalog.Find(id);
    var etag = ComputeETag(product);        // fingerprint of the response

    if (Request.Headers.IfNoneMatch == etag)
        return StatusCode(304);          // ✅ nothing changed — no body sent

    Response.Headers.ETag = etag;
    return Ok(product);
}

Same data, same ETag — the second request costs a tiny header exchange instead of the full body.

C# 
public async Task<Report> GetReportAsync(int id)
{
    var key = $"report:{id}";
    var cached = await _cache.GetStringAsync(key);
    if (cached != null)
        return Deserialize(cached);         // ✅ every instance shares this

    var report = await _db.BuildExpensiveReportAsync(id);  // slow — runs once
    await _cache.SetStringAsync(key, Serialize(report),
        new DistributedCacheEntryOptions { SlidingExpiration = TimeSpan.FromMinutes(10) });
    return report;
}

public async Task UpdateReportAsync(int id, Report updated)
{
    await _db.SaveAsync(updated);
    await _cache.RemoveAsync($"report:{id}");   // ✅ invalidate on write, not just TTL
}

The write path deletes the cache key itself — the 10-minute expiry underneath it is only the safety net, not the plan.

🧭 Use Cases — recognize these when they happen to you ▾
1 A read-heavy endpoint that's hit far more often than its underlying data actually changes

The data behind this endpoint barely changes, but it's asked for constantly — that's exactly what Cache-Control/ETag response caching is for: the client or a CDN answers most of those repeat requests, and your API only sees the ones that actually need something fresh.

RememberRead-heavy + rarely changes → reach for response caching first.
2 Your API runs on more than one instance behind a load balancer — where does a shared cache actually need to live?

An in-memory cache local to just one instance doesn't help the other instance at all — the shared cache has to live somewhere every instance can reach over the network, like Redis, not inside any single instance's own memory.

RememberMore than one instance → the cache lives outside all of them, not inside one.
3 Data looks visibly stale right after an update, because the cache was never invalidated

The write path saved the new value to the database, but nothing deleted or refreshed the matching cache key — every client keeps reading the old value until the TTL underneath it finally expires on its own.

RememberInvalidate the key on write — TTL is only the safety net underneath it.
🌍 Real-world example ▾

Response caching is like handing someone a photocopy of a public poster so they stop asking the front desk for it. A distributed cache is the front desk itself keeping one shared answer on a sticky note instead of re-working it out for every single visitor.

Scenario: your API runs on four instances behind a load balancer, and one report endpoint starts timing out under load because each instance recomputes the same report independently. The fix is a distributed cache keyed by report ID, with invalidation wired into the write path — every instance now shares one computed result instead of four separate slow paths, and a response-caching layer on top of that handles any client that asks for the exact same report again.
