SOLID as a whole — one bloated method, five different breaking points

Walk me through applying all five SOLID principles to one real, moderately complex service — where does each one actually bite?

Why it matters ▾
  • Interviewers ask this to see whether you understand how the five principles interact on one real class — not whether you can recite five separate definitions.
  • It's the natural follow-up after any single-letter SOLID question: "okay, now show me all five on one service."
  • It's also a real legacy-code skill — the same lens you'd use to triage a class like this the first day it lands on your desk.
🔥 Easy interview recall

S → one class, five reasons to change

O → a new payment/discount means editing the method

L → a new payment type can't surprise callers

I → don't force one fat interface on everyone

D → depend on abstractions, not built-inline concretes

Think: same OrderProcessingService, same ProcessOrder() method — each letter names a different way it's already broken.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

SOLID is not five independent checkboxes graded one at a time. Extracting an interface to fix OCP (so a new payment type plugs in without touching existing code) usually satisfies DIP in the same stroke — the letters compound on one class, they don't fix in isolation.

🔄 Likely Follow-up

"Which principle would you fix FIRST in a real legacy-code triage, and why?" Usually SRP — splitting the one method into its separate responsibilities is what makes the other four principles even visible; you can't meaningfully apply ISP or DIP to a single undifferentiated blob.

🎯 Say this in the interview — the exact lines to land

"On this one service: SRP splits the one method into five separate reasons to change; OCP and LSP both live at the payment boundary — add a new type without editing code, and never surprise a caller; ISP stops one fat interface forcing every dependency on every caller and test; and DIP is the fix underneath all of it — four small abstractions injected in, not built inline."

  • S → splits one method into five separately-changeable responsibilities.
  • O → a new discount rule or payment method plugs in without editing existing branches.
  • L → any new IPaymentMethod must honor the same contract — never throw where another implementation wouldn't.
  • I → one fat dependency bag becomes small, focused interfaces, so a test only satisfies what it touches.
  • D → the service depends on injected abstractions, not concrete classes it builds itself.
  • Legacy triage order → fix SRP first — it's what makes the other four actionable at all.
📖 Explanation ▾

Take one moderately complex, very real service: OrderProcessingService.ProcessOrder() validates an order, calculates pricing and discounts, charges a payment method, sends a confirmation email, and persists the order — all inline, in one method, constructing StripeGateway, SmtpEmailSender, and SqlOrderRepository with new right where they're used. Every SOLID letter names a different, real symptom of that same class — not five unrelated rules that happen to apply to different code.

SRP asks how many unrelated reasons this one method has to change — a discount-rule tweak, a new payment provider, an email-template rewrite, a schema change are four different teams' reasons to touch the same file. OCP and LSP both live at the exact same seam: the moment ProcessOrder accepts an abstraction like IPaymentMethod instead of an if/else on provider name, OCP is satisfied — a new provider is a new class, not a new branch — but only if every implementation genuinely honors that contract; a payment type that throws where another one wouldn't breaks LSP right at that boundary. ISP and DIP are the two structural fixes: split one bundled IOrderDependencies into four focused interfaces so a pricing test never has to fake an email sender, then have the service receive those four interfaces through its constructor instead of constructing the concrete classes itself.

The shape that survives all five fixes is a thin OrderProcessingService orchestrating four small, independently-testable collaborators — IPaymentGateway, IPricingEngine, IEmailSender, and IOrderRepository — each injected in rather than built inline.

SOLID
Symptom in ProcessOrder one method, 5 change-reasons new provider = new if/else no abstraction yet to break one interface bundles everything new StripeGateway() inline
Fix in the redesign 5 single-purpose classes new IPaymentMethod class, no edits every implementation keeps the same contract 4 focused interfaces, one per concern gateway/pricing/email/repo injected in
💻 See the code ▾
C# 
public class OrderProcessingService
{
    public void ProcessOrder(Order order)
    {
        if (order.Items.Count == 0)
            throw new InvalidOperationException("Empty order"); // SRP: validation too

        decimal total = order.Items.Sum(i => i.Price);
        if (order.CustomerType == "VIP") total *= 0.9m; // OCP: new discount = new branch

        if (order.PaymentType == "CreditCard")
        {
            var gateway = new StripeGateway();       // DIP: concrete built inline
            gateway.Charge(order.CardToken, total);
        }
        else if (order.PaymentType == "PayPal")   // OCP: new provider = new branch
        {
            var gateway = new PayPalGateway();
            gateway.Charge(order.PayPalAccount, total);
        }

        new SmtpEmailSender().Send(order.Email, "Order confirmed"); // SRP: email too
        new SqlOrderRepository().Save(order);                          // SRP: persistence too
    }
}

Five unrelated reasons to touch this one method, and every dependency is a concrete class built right here instead of received from outside.

C# 
public interface IPaymentGateway   { void Charge(string token, decimal amount); }
public interface IPricingEngine    { decimal CalculateTotal(Order order); }
public interface IEmailSender      { void Send(string to, string subject); }
public interface IOrderRepository  { void Save(Order order); }

ISP fix: four small interfaces instead of one IOrderDependencies bundle — a pricing test only has to satisfy IPricingEngine, not fake an email sender too.

C# 
public class OrderProcessingService
{
    private readonly IPaymentGateway _gateway;
    private readonly IPricingEngine _pricing;
    private readonly IEmailSender _email;
    private readonly IOrderRepository _repo;

    public OrderProcessingService(IPaymentGateway gateway,
        IPricingEngine pricing, IEmailSender email, IOrderRepository repo)
    {
        _gateway = gateway; _pricing = pricing; _email = email; _repo = repo; // ✅ injected, not built
    }

    public void ProcessOrder(Order order)
    {
        var total = _pricing.CalculateTotal(order);   // OCP: new rule = new IPricingEngine
        _gateway.Charge(order.PaymentToken, total);      // OCP + LSP: any IPaymentGateway works
        _email.Send(order.Email, "Order confirmed");
        _repo.Save(order);
    }
}

DIP fix: each collaborator is injected, not constructed — swap StripeGateway for a test double, or add a new payment type, without touching this class at all.

🌍 Real-world example ▾

Scenario: your tech lead asks you to add a new payment provider by tomorrow. On the original ProcessOrder(), that means finding the if/else chain, adding another branch, and hoping every other provider's path still works — with no test boundary around the change at all.

On the redesigned service: it means writing one new class implementing IPaymentGateway and registering it — OrderProcessingService itself never changes, and every other payment path is untouched, because the service depends on the abstraction, not on any specific provider.
