OWASP Top 10 for LLMs — how many can you name cold?

"What security risks does the OWASP Top 10 for LLM Applications cover — can you name a few?"

Why it matters ▾
🛡️ OWASP Top 10 for LLMs
❗ ProblemTreated as one problem, LLM-specific risk gets reduced to "watch out for prompt injection" — leaving genuinely distinct failure modes like training data poisoning, excessive agency, and supply chain risk unconsidered until each one causes its own production incident.
✅ SolutionOWASP's list gives each real failure mode its own named category to check, and you can remember them in three buckets — what goes in, what comes out, and how much power the system has — instead of one repeated worry.
RecallOWASP Top 10 for LLMs = distinct risk categories grouped into three buckets — in, out, power/infra — not prompt injection restated. Names changed between the 2023 and 2025 lists.
🔥 Easy interview recall

Input-side → attacker controls what goes IN

Output & trust → risk in what comes OUT, or what you assume is true

Agency & infra → how much power it has, what it's built from

Think: three buckets — in, out, and how much power / what it runs on.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Treating this list as "prompt injection, restated ten ways." Misinformation, data poisoning, supply chain risk, and unbounded consumption have nothing to do with a crafted prompt at all — this is a checklist of genuinely distinct risk categories, not one problem repeated.

🔄 Likely Follow-up

"How would you actually defend against Excessive Agency?" Give the agent only the permissions the task needs — read-only where read-only is enough — and require a human-approval step before anything side-effecting, like a delete, a send, or a payment. Same least-privilege idea applied to an agent instead of a user account.

🎯 Say this in the interview — the exact lines to land

"OWASP publishes a Top 10 of security risks specific to LLM applications — prompt injection, sensitive information disclosure, supply chain, data and model poisoning, improper output handling, excessive agency and so on — and since names and ranking change between versions, I remember them as three buckets: what goes in, what comes out, and how much power the system has."

  • Input-side → Prompt Injection, Data and Model Poisoning, Vector and Embedding Weaknesses — what the model reads or retrieves.
  • Output & trust → Improper Output Handling, Sensitive Information Disclosure, System Prompt Leakage, Misinformation — what comes out, or what you assume is true.
  • Agency & infrastructure → Excessive Agency, Unbounded Consumption, Supply Chain — how much power it has, and what it's built from.
  • Names changed between the 2023 and 2025 lists — say "categories such as," never a fixed #1–#10.
  • Being able to name five or six cold, one line each, is the actual bar.
📖 Explanation ▾

OWASP — the group behind the classic web-app Top 10 — publishes a Top 10 for LLM applications: security risks that are new or reshaped by putting a language model in a system. It's a living document, and names changed between the 2023 and 2025 lists — Insecure Output Handling became Improper Output Handling, Overreliance became Misinformation, Model Denial of Service became Unbounded Consumption, and Training Data Poisoning widened to Data and Model Poisoning. Plugin and tool-design risk now sits mainly under Excessive Agency, and Model Theft is not a separate entry in the 2025 list. Check OWASP's current page before quoting exact names; the useful skill is naming several categories with a one-line description each.

Input-side risks are about what the model reads: Prompt Injection (broad enough for its own deep dive), Data and Model Poisoning (training or fine-tuning data as the attack surface), and Vector and Embedding Weaknesses (poisoned or poorly-secured embeddings and vector-store access skewing what a RAG system retrieves). Output & trust risks are about what the model produces or reveals: Improper Output Handling (acting on output without validating it — rendering it as raw HTML, for example), Sensitive Information Disclosure, System Prompt Leakage (a crafted input getting the model to reveal its instructions, so never put secrets in a system prompt), and Misinformation (trusting a confident but wrong answer without verification).

Agency & infrastructure risks are about power and plumbing: Excessive Agency (an agent given more permission than the task needs — least privilege, applied to an agent), Unbounded Consumption (an attacker or runaway usage driving up cost or degrading availability), and Supply Chain (a third-party model, plugin, or dataset with unknown provenance).

💻 See the code ▾
JavaScript 
const answer = await llm.chat(userQuestion);
resultDiv.innerHTML = answer;  // ❌ trusts model output completely

If the response contains a <script> tag — from an injection, or the model just imitating markup it saw — it executes on the page. This is Improper Output Handling: acting on model output as if it were already safe.

JavaScript 
const answer = await llm.chat(userQuestion);
const safe = sanitizeHtml(answer);  // ✅ never trust it, validate first
resultDiv.innerHTML = safe;

Same idea applies beyond HTML — output that gets eval()'d, run as a shell command, or dropped into a SQL string needs the same treatment: validate or sanitize before acting on it, every time.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app drops the model's raw answer straight into the page as HTML

Whatever the model returns — a stray script tag slipped in by an injection, or the model just imitating markup it saw — runs on the page because nothing validated it first. This is Improper Output Handling: acting on the model's output as if it were already safe. This is the #1 scenario you'll actually hit — it takes exactly one unguarded line.

RememberModel output → treat it like any other untrusted input, sanitize before acting on it.
2 A debugging agent gets one generic tool that can run any shell command

The task only ever needed to read log files, never delete one or push a commit — but the tool itself can do anything a shell can. That's Excessive Agency: granting more permission than the task actually requires.

RememberAgent tool scope → give it only the permission the task needs, not everything it could theoretically use.
3 Someone hears "OWASP Top 10 for LLMs" and assumes it's just ten ways to say prompt injection

Misinformation, data poisoning, supply chain risk, and unbounded consumption have nothing to do with a crafted prompt — treating the whole checklist as prompt injection restated ten ways means the other genuinely distinct categories never get considered. A classic interview trap — the bar is naming several categories, not one.

RememberOne risk category ≠ the whole checklist — many distinct categories, not one repeated.
🌍 Real-world example ▾

An internal coding-assistant agent gets a single generic "run any shell command" tool so it can help debug — that's Excessive Agency. The task only ever needed to read log files, never delete one or push a commit, so the fix is scoping the tool down to exactly what's needed (read-only where read-only is enough) instead of handing the model a blank check.
