Locking — the mechanism blocking is made of

What is locking, mechanically, and how does it lead to blocking?

Why it matters ▾
  • Almost every "the app just hangs" incident that isn't a bug is really one transaction waiting on another transaction's lock — you can't diagnose that without knowing what a lock actually is.
  • Interviewers ask this to see whether you treat locking and blocking as the same word, or correctly separate the mechanism from the symptom it produces.
  • It's the foundation the Isolation Levels and Deadlock vs. Blocking questions build on — neither makes sense without this one first.
🔥 Easy interview recall

lock → a claim on data

blocking → waiting for that claim to release

Think: locking is the mechanism. blocking is what you see happen because of it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Locking only happens on writes — reads never lock anything. Reads can take locks too, depending on the isolation level in effect (a shared lock under a stricter isolation level, for example) — which is exactly how a reader can end up blocking a writer, or the other way around; it isn't a writes-only phenomenon.

🔄 Likely Follow-up

"What's the difference between a shared lock and an exclusive lock?" A shared lock (typically for reading) can coexist with other shared locks on the same data at the same time; an exclusive lock (for writing) can't coexist with any other lock on that data — it needs exclusive access.

🎯 Say this in the interview — the exact lines to land

"A lock is a claim a transaction takes on a piece of data so other transactions can't touch it in a conflicting way. Blocking is what happens when another transaction has to wait for that lock to be released — locking is the mechanism, blocking is the symptom you actually notice."

  • A lock → a claim on a row, page, or table, not the waiting itself.
  • Blocking → one transaction waiting on another transaction's lock to release.
  • Reads lock too → depends on the isolation level in effect, so a reader can block a writer.
  • Shared vs. exclusive → shared locks can coexist, an exclusive lock can't.
📖 Explanation ▾

A lock is a claim a transaction takes on a specific piece of data — usually a row, sometimes a whole page or table — before it reads or changes it. The database hands out locks so two transactions can't make conflicting changes to the same data at the same moment.

Not every lock is the same strength. A shared lock lets other transactions also take a shared lock on the same data at the same time — fine when everyone only wants to read. An exclusive lock, needed to write, can't coexist with any other lock on that data. Whether a plain read even takes a lock at all depends on the isolation level in effect — under a stricter isolation level, reads take locks too, which is exactly how a read can end up waiting on a write, or a write can end up waiting on a read.

Blocking is the visible result: whenever a transaction asks for a lock that conflicts with one already held, it simply waits in line — no error, just a queue. See the separate Deadlock vs. Blocking page for how this differs from an actual deadlock, where two transactions end up waiting on each other and neither can ever move.

💻 See the code ▾
SQL 
BEGIN TRAN;
UPDATE Accounts
SET Balance = Balance - 100
WHERE Id = 1;
-- (no COMMIT yet)

Row 1 stays locked from this UPDATE until a COMMIT or ROLLBACK — any other transaction that tries to touch Row 1 in the meantime just has to wait.

🌍 Real-world example ▾

Think of a single-occupancy meeting room. Once someone is inside, the door is locked — anyone else who wants that room has to wait in the hallway. They haven't done anything wrong by waiting; they're simply blocked until the person inside is done and unlocks the door (a COMMIT or ROLLBACK).
