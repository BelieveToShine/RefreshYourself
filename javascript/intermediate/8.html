DOM & Browser Events — which way does a click actually travel?

"Walk me through what happens, step by step, when a click fires on a deeply nested element — and what's the difference between preventDefault() and stopPropagation()?"

Why it matters ▾
🚫 preventDefault()
❗ ProblemA link click still navigates and a form submit still reloads the page by default, even when a handler needs to take over that action itself.
✅ SolutionCalling preventDefault() on the event cancels only that browser default action — the event still propagates untouched to every other listener along its path.
RecallpreventDefault() = stops the browser's own action, not propagation.
🛑 stopPropagation()
❗ ProblemBecause clicks bubble by default, a listener on a child element and a listener on one of its ancestors both fire from the exact same click — sometimes the ancestor's listener shouldn't run at all.
✅ SolutionCalling stopPropagation() stops the event from reaching any other listener further along the capture/bubble path — it never touches the browser's own default action.
RecallstopPropagation() = stops other listeners, not the default action.
🔥 Easy interview recall

DOM Events = "capture goes down, the target fires once, bubble goes back up — bubbling is the default."

Think: Capturing → root to target, only if a listener opts in Target → the clicked element itself, fires exactly once Bubbling → target back to root, the default for every listener preventDefault() → stops the browser's own action (e.g. a link navigating) stopPropagation() → stops the event reaching other listeners further along the path

🧠 Visual Mental Model — understand it in 5 seconds
🧠 Don't mix these two — preventDefault() vs. stopPropagation()
⚠️ Common Trap

preventDefault() does not stop the event from bubbling. It only cancels the browser's own default action (a link navigating, a form submitting) — other listeners further up the chain still run; stopping them is stopPropagation()'s job, not preventDefault()'s.

🔄 Likely Follow-up

"If bubbling is the default, why does delegation matter?" Because one listener on a shared ancestor still sees every click from its children — including children added later — since the click bubbles up to it regardless; that's exactly what Event Delegation (next topic) is built on.

🎯 Say this in the interview — the exact lines to land

"A click on a nested element travels down from the root in the capture phase, fires once at the target, then travels back up to the root in the bubble phase — bubbling is the default unless a listener explicitly opts into capturing. preventDefault() stops the browser's own default action; stopPropagation() stops the event from reaching other listeners further along that path."

  • Default phase → bubbling, target to root, unless capture is explicitly requested.
  • Capturing → root to target, opt in with a third addEventListener argument.
  • preventDefault() → stops the browser's own action — a link navigating, a form submitting.
  • stopPropagation() → stops other listeners from ever seeing the event.
  • Event delegation → relies entirely on bubbling reaching one shared ancestor listener.
📖 Explanation ▾

The DOM is the browser's live tree of every element on the page. document.querySelector() and querySelectorAll() find nodes already in that tree; createElement() plus appendChild() add a new node, and remove() takes one out — all changes happen immediately, live on the page. An event listener (element.addEventListener('click', handler)) is a function the browser calls when something happens, and it always receives one argument, the event object — carrying event.target (the actual element that was clicked) and event.currentTarget (the element this particular listener is attached to, which can be a different, higher-up element).

Every DOM event travels a fixed path. Capturing goes from the document root down to the clicked element, but only for listeners that explicitly opt in (a third true argument, or { capture: true }) — most code never uses this. The event then fires once at the target itself. Then bubbling carries it back up from the target to the root, and this is the phase almost every listener actually runs in, because it's the default one. This exact bubbling path is what makes Event Delegation possible — a single listener on a shared ancestor still sees a click from any of its children, because the click bubbles up to reach it.

Two methods on the event object are easy to conflate, but they stop two completely different things:

preventDefault()stopPropagation()
Stopsthe browser's own default actionthe event traveling on to other listeners
Examplea link not navigating, a form not submittinga click on a child not also triggering its parent's click listener
Does NOT stop❌ propagation — other listeners still run❌ the default action — that still happens unless preventDefault() is also called
💻 See the code ▾
JavaScript 
const list = document.querySelector('#list');        // find one element
const items = document.querySelectorAll('.item');     // find every match

const li = document.createElement('li');              // ✅ create a new node
li.textContent = 'New item';
list.appendChild(li);                                  // add it to the tree

list.firstElementChild.remove();                       // ✅ remove a node

Nothing here waits for a re-render — each call changes the live tree on the page immediately.

JavaScript 
button.addEventListener('click', (event) => {
  console.log(event.target);         // the exact element clicked
  console.log(event.currentTarget);  // the element this listener is on
});

// ✅ opts into the capture phase — runs BEFORE any bubbling listener
ancestor.addEventListener('click', handler, { capture: true });

event.target is always the clicked element; event.currentTarget depends on which element's listener is currently running.

JavaScript 
link.addEventListener('click', (event) => {
  event.preventDefault();     // ✅ stops the link from navigating
  // the click still bubbles up to any listener on document
});

child.addEventListener('click', (event) => {
  event.stopPropagation();    // ✅ stops it reaching the parent's listener
  // the browser's default action (if any) still happens
});

Calling one does nothing to the other — a real fix sometimes needs both, on purpose, not either as a substitute.

🧭 Use Cases — recognize these when they happen to you ▾
1 A link's click handler needs to stop navigation, but a delegated listener up the tree still needs to see the click

Only the browser's own navigation gets cancelled — the click keeps bubbling exactly as before, so a delegated listener sitting higher up the tree still fires for it, no differently than any other click.

RememberOnly need to stop navigation → preventDefault(), bubbling keeps working.
2 A button nested inside a clickable card shouldn't also trigger the card's own click listener

Calling stopPropagation() inside the button's own handler stops the click from ever reaching the card's ancestor listener further along the bubble path — the card's own click handler simply never runs for this click.

RememberDon't want the ancestor's listener to fire too → stopPropagation().
3 You call preventDefault() and assume it also stopped the event from bubbling

preventDefault() only cancels the browser's own default action — it does nothing to propagation, so every other listener still along the path still runs. A common trap — candidates often assume the two methods are interchangeable, or that one implies the other.

RememberpreventDefault() ≠ stopPropagation() — calling one does nothing to the other.
🌍 Real-world example ▾

Think of it like a note passed down a chain of managers to one specific employee, then that employee's reply traveling back up the same chain. The reply going back up (bubbling) is what almost every manager actually waits for — that's why it's the default — while a manager choosing to read the note on its way down (capturing) is the rare, opt-in exception.
