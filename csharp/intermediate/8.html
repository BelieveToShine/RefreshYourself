record vs. class — equality you didn't have to write

"What does a record give you that a class doesn't, by default?"

Why it matters ▾
  • Interviewers use this to check you know what record actually buys you — not just "it's a newer keyword."
  • Comes up any time you're modelling a DTO, a value object, or a dictionary key that needs to compare by content.
  • The immutability pitfall is a favorite follow-up trap — a lot of candidates state it backwards.
🔥 Easy interview recall

record → value equality, free

class → reference equality only

Think: Same values, different instances — a record says true, a class says false.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A record is not automatically immutable. Immutability only comes from init-only properties (or positional parameters, which are init by default) — a record written with normal set properties is just as mutable as a class.

🔄 Likely Follow-up

"What does the with expression do?" It creates a new record instance, copies every property from the original, then overwrites only the ones you specify — non-destructive mutation that only records support; a plain class has no with at all.

🎯 Say this in the interview — the exact lines to land

"A record gets compiler-generated value equality, GetHashCode, and ToString() for free — two records with the same property values are equal without writing any code. A class only gets reference equality unless you override Equals yourself."

  • record → value equality by default, no override needed.
  • class → reference equality unless you write your own Equals.
  • Not immutable by default → only init/positional params lock it, plain set stays mutable.
  • with expression → non-destructive copy, available only on records.
📖 Explanation ▾

A record is a class the compiler does extra work for: it generates Equals, GetHashCode, and ToString() based on the record's properties, so two records holding the same values are equal — the same way you'd expect two receipts with the same amount and date to represent "the same purchase," even though they're two different pieces of paper.

A class gets none of that generated behavior. Its inherited Equals from object just checks "is this literally the same instance in memory" — so a class needs a hand-written Equals override before two instances with matching data will ever compare equal.

The mutability piece is a separate decision entirely. A record's positional syntax (record Point(int X, int Y)) generates init-only properties, which is why records read as "immutable by default" — but nothing stops you writing a record with ordinary get; set; properties, and if you do, it mutates exactly like a class.

💻 See the code ▾
C# 
record Point(int X, int Y);

var p1 = new Point(1, 2);
var p2 = new Point(1, 2);
Console.WriteLine(p1 == p2);   // ✅ true — compared by value

The positional record generates Equals for you — no override, no boilerplate.

C# 
class PointClass
{
    public int X { get; set; }
    public int Y { get; set; }
}

var c1 = new PointClass { X = 1, Y = 2 };
var c2 = new PointClass { X = 1, Y = 2 };
Console.WriteLine(c1 == c2);   // ❌ false — different objects on the heap

Same fields, same values — but a plain class only compares identity, not content.

C# 
record Point2
{
    public int X { get; set; }   // set, not init
}

var p = new Point2 { X = 1 };
p.X = 99;                  // ❌ compiles — record is still mutable

record alone guarantees nothing about mutability — only init does.

🌍 Real-world example ▾

Your test asserts two DTOs are equal after a round-trip through JSON. Make the DTO a record and Assert.Equal(expected, actual) already works by comparing every property — with a class, the same assertion silently passes or fails on object identity instead, until you write an Equals override yourself.
