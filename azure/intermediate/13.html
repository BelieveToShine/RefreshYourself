Secrets management — storing it in Key Vault isn't the finish line

"What does 'secrets management' mean as a broader practice beyond just 'use Key Vault'?"

Why it matters ▾
🔐 Secrets Management
❗ ProblemStoring a secret in Key Vault only keeps it out of source control and plain config files — it can still sit there for years, readable by far more identities than it needs, with no rotation plan and no record of who ever read it.
✅ SolutionSecrets management treats storage as just step one: rotate the value on a schedule, grant read access only to the identities that actually need it, and log every access — so the practice keeps going long after the secret first lands in the vault.
RecallSecrets management = store it, rotate it, limit who can read it, log who did — storage is only step one of four.
🔥 Easy interview recall

Secrets management = "store it, rotate it, limit who can read it, log who did."

Think: Key Vault storage is only the first of those four.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It's in Key Vault, so we're covered." A secret sitting in Key Vault for years, readable by half the subscription, with no rotation plan, is still a real risk — the vault protects the value at rest, it doesn't decide who should read it or how long it should stay valid.

🔄 Likely Follow-up

"What does automated rotation actually look like?" Key Vault can auto-rotate certain secret types (e.g. storage account keys) on a schedule, or trigger a Function/Event Grid notification near expiry so an app can pick up the new value without a manual scramble.

🎯 Say this in the interview — the exact lines to land

"Storing a secret in Key Vault is step one — rotation, least privilege, and auditing are the rest of the practice."

  • Rotation → change the value on a schedule, ideally automated or backed by an expiry notification, not a manual one-off.
  • Least privilege → only the identities that actually need a secret can read it — never a broad, subscription-wide grant.
  • Auditing → log every access so "who read this, and when" has a real answer.
  • A secret can still leak through logs, source control, or build output — storage location alone doesn't stop that.
📖 Explanation ▾

Storing a secret in Key Vault solves one problem: keeping it out of source control and plain config files. Real secrets management goes further. Rotation means changing the secret's value on a schedule, ideally automated, so a leaked or aging value doesn't stay valid forever. Least-privilege access means only the specific identities — managed identities, service principals, specific users — that actually need a secret get a policy or role assignment to read it, not everyone in the subscription. Auditing means every access is logged, so "who read this secret, and when" has a real answer after the fact.

The trap isn't misunderstanding any one of these — it's stopping the discipline once the secret is stored. A secret sitting in Key Vault for years, readable by far more identities than it needs to be, with no expiry and no rotation plan, is still a real risk. The vault protects the value at rest; it doesn't decide who should be allowed to read it or how long it should stay valid — that's the practice around it, not the storage service itself.

The practice also extends past Key Vault's own walls: a secret can still leak if it's ever printed to a log, checked into source control, or baked into a build artifact or container image. The same discipline that keeps a secret out of plain text at rest — never hardcode it, never print it — has to hold everywhere it travels downstream, not just at the point of storage.

💻 See the code ▾
CLI 
az keyvault secret set-attributes \
  --vault-name MyKeyVault \
  --name DbConnectionString \
  --expires "2026-12-31T00:00:00Z" # ✅ makes staleness visible

Setting an expiry doesn't rotate the secret by itself — it just stops a stale value from staying invisible.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're deciding which identities get to read a secret you just stored

The policy or role assignment names one specific identity — the app's managed identity — not every identity in the subscription. Only that identity gets to read the secret. This is the #1 decision you'll actually make with Key Vault day to day.

RememberLeast privilege → grant access to the identity that needs it, not everyone.
2 Someone asks who read a secret, and when

Every read is recorded — so if someone asks "who accessed this secret, and when," there's a real answer instead of a guess.

RememberRead a secret → it shows up in the audit log.
3 The app reads the secret out of Key Vault — then what?

The vault only protects the value at rest. Once the app reads it, the same value can still leak downstream — printed in a log line, checked into source control, or baked into a build artifact or container image. A common trap — candidates often assume Key Vault storage alone prevents this, but the discipline has to hold everywhere the secret travels, not just at the point of storage.

RememberStorage isn't the finish line — the secret can still leak after it's read.
🌍 Real-world example ▾

A team sets its Key Vault secrets to expire every 90 days and wires an Event Grid notification to fire ahead of that expiry, so someone gets an alert and rotates the value in time — instead of finding out a secret was stale when production broke.
