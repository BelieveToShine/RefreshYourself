A BackgroundService is a singleton — so where does your scoped service come from?

"How do you run recurring background work in ASP.NET Core — and how do you use a scoped service from it?"

Why it matters ▾
🔁 BackgroundService
❗ ProblemRecurring work — cleanup, polling, sending queued emails — has no request to run inside, and the hosted service itself is a singleton, so injecting a scoped service like a DbContext into it is the classic lifetime mistake.
✅ SolutionDerive from BackgroundService, loop in ExecuteAsync, and open a fresh DI scope on each tick for anything scoped.
RecallOne loop, a new scope per tick.
🔥 Easy interview recall

Background work = "one loop, one scope per tick."

Think: ExecuteAsync → your loop, runs until the token is cancelled IServiceScopeFactory → a fresh scope on every tick

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Injecting a scoped service (like a DbContext) straight into the BackgroundService. The worker is a singleton, so that scoped object would be held for the life of the app — and scope validation (on by default in Development) throws. Inject IServiceScopeFactory and create a scope per tick.

🔄 Likely Follow-up

"What happens if ExecuteAsync throws?" In .NET 6 and later, an unhandled exception is logged and the host stops by default (changeable through HostOptions.BackgroundServiceExceptionBehavior). For work that should keep going, catch and log inside the loop.

🎯 Say this in the interview — the exact lines to land

"I derive from BackgroundService and write the loop in ExecuteAsync, using a PeriodicTimer for the schedule and passing the stopping token to every await. Because the worker is a singleton, I inject IServiceScopeFactory and create a fresh scope on each tick to use scoped services like a DbContext."

  • ExecuteAsync → one loop that runs until the stopping token is cancelled.
  • PeriodicTimer → waits tick by tick, so one run finishes before the next starts.
  • Scoped services → new scope per tick via IServiceScopeFactory.
  • Exceptions → catch and log inside the loop, or (.NET 6+) the host stops.
  • Shutdown → pass stoppingToken to every await so the loop exits promptly.
📖 Explanation ▾

BackgroundService is a base class that implements IHostedService for you. You override one method, ExecuteAsync(CancellationToken stoppingToken), and register the class with AddHostedService<T>(). The host starts it at startup and cancels the token at shutdown. Keep the beginning of ExecuteAsync quick — long synchronous work before the first await can hold up host startup.

For a schedule, wrap the loop around PeriodicTimer: await timer.WaitForNextTickAsync(stoppingToken) pauses until the next tick, and cancelling the token ends the wait. Because you await each tick, runs never overlap. The worker is registered as a singleton, so a scoped service can't simply be injected — open a scope per tick with IServiceScopeFactory and dispose it when the work is done. Lifetimes are explained on Service Lifetimes.

This page is about writing the worker; how the host starts and stops it is on The Generic Host & Application Lifetime. For async pitfalls in general, see the Web API track's Async APIs & API Security.

💻 See the code ▾
C# 
public class CleanupWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopes;
    private readonly ILogger<CleanupWorker> _log;

    public CleanupWorker(IServiceScopeFactory scopes, ILogger<CleanupWorker> log)
    {
        _scopes = scopes;
        _log = log;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
        while (await timer.WaitForNextTickAsync(stoppingToken))   // waits for each tick
        {
            try
            {
                using var scope = _scopes.CreateScope();   // ✅ new scope per tick
                var cleaner = scope.ServiceProvider.GetRequiredService<ICleaner>();
                await cleaner.RunAsync(stoppingToken);     // token passed down
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                _log.LogError(ex, "Cleanup failed");       // keep the loop alive
            }
        }
    }
}

The worker holds only the scope factory — scoped services are created and disposed inside the loop.

C# 
builder.Services.AddScoped<ICleaner, Cleaner>();   // scoped
builder.Services.AddHostedService<CleanupWorker>();   // registered as a singleton

// ❌ public CleanupWorker(ICleaner cleaner) { ... }

Taking the scoped ICleaner in the constructor is the lifetime mismatch — use the scope factory instead.

🌍 Real-world example ▾

A nightly "expire old sessions" job. There is no controller to host it, so a BackgroundService wakes on a timer, opens a scope, calls the scoped cleaner that uses the DbContext, and disposes the scope — every run gets a fresh DbContext instead of one that lives forever.
