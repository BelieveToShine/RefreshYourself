gRPC vs. REST — pick by who is calling

"When would you choose gRPC over a REST API?"

Why it matters ▾
⚡ gRPC vs. REST
❗ ProblemServices that call each other many times per request pay for every byte and every loosely-defined contract, while browsers and partners need something they can call from anywhere.
✅ SolutiongRPC gives services compact binary messages, a strict generated contract and streaming; REST keeps the public edge simple, readable and cacheable.
RecallInside → gRPC. Outside → REST.
🔥 Easy interview recall

gRPC → binary over HTTP/2

REST → readable JSON, works everywhere

Think: gRPC between services. REST at the public edge.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"gRPC is just faster REST, so use it everywhere." Browsers can't make full gRPC calls, the binary body is hard to inspect, and it doesn't fit standard HTTP caching — so public APIs usually stay REST.

🔄 Likely Follow-up

"Can a browser call a gRPC service?" Not directly. Browsers don't give JavaScript the HTTP/2 control gRPC needs — you use gRPC-Web (with a proxy or middleware), or put a REST edge in front.

🎯 Say this in the interview — the exact lines to land

"I'd choose gRPC for internal service-to-service calls where I want compact binary messages, a strict contract and streaming, and keep REST for public and browser-facing APIs because it is readable, cacheable and works everywhere."

  • gRPC → HTTP/2 + protobuf: compact binary messages.
  • Contract-first → a .proto file generates typed clients and servers.
  • Streaming → server, client, or both directions.
  • REST → public APIs and browsers, easy to cache and debug.
  • Choose gRPC → internal, low-latency, streaming calls.
  • Browser → gRPC-Web with extra setup, or a REST edge.
📖 Explanation ▾

gRPC lets one service call another service's methods over the network. You write the contract once in a .proto file and tools generate typed client and server code. Messages travel as compact binary Protocol Buffers over HTTP/2.

That gives it its strengths: small messages, a strict shared contract, and built-in streaming — the server can stream, the client can stream, or both at once. It also has limits: browsers can't make full gRPC calls (the browser variant, gRPC-Web, needs extra setup), the binary body isn't human-readable, and it doesn't use verbs and URLs the way standard HTTP caching expects.

REST with JSON is the opposite trade: bigger messages and a looser contract, but every browser, tool, cache and developer already speaks it (see What Is REST). So the usual split is REST at the public edge and gRPC between internal services (see Distributed Systems Considerations). In ASP.NET Core, gRPC services are mapped through the same endpoint system as everything else (see Routing).

💻 See the code ▾
Protobuf 
syntax = "proto3";

service OrderService {
  rpc GetOrder (OrderRequest) returns (OrderReply);
}

message OrderRequest { int32 id = 1; }
message OrderReply { int32 id = 1; string status = 2; }

The .proto file is the contract. Client and server code are generated from it, so both sides share the exact same types.

C# 
public class OrderGrpcService : OrderService.OrderServiceBase
{
    public override Task<OrderReply> GetOrder(OrderRequest request, ServerCallContext context)
    {
        return Task.FromResult(new OrderReply { Id = request.Id, Status = "Shipped" });
    }
}

builder.Services.AddGrpc();
app.MapGrpcService<OrderGrpcService>();

The server overrides the method from the generated base class. Registration uses AddGrpc and MapGrpcService (the Grpc.AspNetCore package) — check the current docs for setup details.

🌍 Real-world example ▾

REST is a postcard anyone can read and answer. gRPC is a pre-agreed, sealed form between two offices — quicker to process, but outsiders can't read it.

Scenario: a checkout service asks the inventory service about stock many times per order — gRPC between them. The mobile app and partners call the public REST API in front.
