Millions of rows — buffer them all, or let the database do the work?

"You need to process millions of rows from a database table — what are your real options, and what are the trade-offs?"

Why it matters ▾
🚚 Millions of Rows, Four Real Options
❗ ProblemThe obvious approach — .ToList() the whole table, then process it in memory — either crashes with an out-of-memory exception or hammers the server with a single enormous allocation, and it gets strictly worse as the table grows, not better.
✅ SolutionStream instead of buffering for constant memory use, batch into bounded chunks (keyset-paginated, not offset, at this scale) when the work has to happen row by row, and push the computation itself into the database with Sum/Count/GroupBy-style aggregation whenever the end goal is a number, not the raw rows.
RecallOnly pull across the wire what you actually need — rows, a batch, or just the answer.
🔥 Easy interview recall

Buffer everything → one huge spike, worst

Stream / batch → bounded memory, scales

Aggregate in the database → least data moved, best for a number

Think: if the goal is a sum or a count, never pull the rows at all — let the database compute it and send back one number.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Streaming and batching are basically the same thing." Streaming processes one row at a time with no chunk boundary at all; batching deliberately groups rows into fixed-size chunks, which matters when the processing itself needs to happen in bounded units (a bulk update per batch, a transaction per chunk), not row by row.

🔄 Likely Follow-up

"Why keyset pagination instead of Skip/Take for batching at this scale?" Skip(n) still has to scan and discard the first n rows every single call, so it gets slower as the offset grows. Keyset pagination seeks directly from the last key seen in the previous batch — the Offset Pagination vs. Keyset Pagination page covers this trade-off in full.

🎯 Say this in the interview — the exact lines to land

"I wouldn't buffer the whole table into memory — I'd stream it for constant memory use, or batch it into bounded, keyset-paginated chunks if the work needs to happen in units. And if the actual goal is a sum or a count, I'd push that computation into the database itself instead of pulling millions of rows across the wire just to aggregate them client-side."

  • Buffering everything → one huge memory spike, the worst option at this scale.
  • Streaming → constant, low memory, one row at a time, no chunk boundary.
  • Batching → bounded chunks, keyset-paginated to avoid offset's re-scan cost.
  • Database-side aggregation → least data transferred of all, when the goal is a number, not the rows.
📖 Explanation ▾

Buffering — a plain .ToList() over millions of rows — allocates space for the entire result set at once, which is exactly why it's the option most likely to run out of memory or blow past a reasonable timeout. Streaming fixes the memory side of that by never materializing more than one row (or a small internal buffer) at a time — see Streaming vs. Buffering Large Results for the full mechanics of why an IEnumerable<T> source can do this and a materialized list can't.

Batching is a different axis from streaming, not a stronger version of it — it deliberately groups rows into fixed-size chunks because the processing itself needs a unit boundary, like a bulk update per batch or a transaction per chunk, not because streaming alone isn't fast enough. At millions of rows, the batching technique matters too: a Skip(n).Take(pageSize) loop re-scans and discards the first n rows on every call, getting slower as n grows — keyset pagination (seeking from the last key seen) avoids that entirely, see Offset Pagination vs. Keyset Pagination.

Database-side aggregation is the option that doesn't transfer the rows at all — a Sum, Count, or GroupBy-with-aggregate query translates into SQL that computes the answer on the server and sends back one number (or one row per group), instead of millions of rows crossing the network just to be summed client-side. Whenever the actual end goal is a computed value rather than the raw rows themselves, this is strictly less work than any of the other three options.

💻 See the code ▾
C# 
await foreach (var order in db.Orders.AsAsyncEnumerable())
{
    Process(order); // ✅ one row in memory at a time
}

Streaming keeps memory constant, independent of table size.

C# 
int lastId = 0;
while (true)
{
    var batch = await db.Orders
        .Where(o => o.Id > lastId) // ✅ keyset — no offset re-scan
        .OrderBy(o => o.Id).Take(1000).ToListAsync();
    if (batch.Count == 0) break;
    ProcessBatch(batch);
    lastId = batch[^1].Id;
}

Bounded chunks, seeking from the last key instead of an offset that keeps growing.

C# 
var totalsByRegion = await db.Orders
    .GroupBy(o => o.Region)
    .Select(g => new { g.Key, Total = g.Sum(o => o.Amount) })
    .ToListAsync(); // ✅ the database sums — one row per region comes back

Millions of rows never leave the database — only the computed totals do.

🧭 Use Cases — recognize these when they happen to you ▾
1 The end goal is a dashboard number — a total, a count, an average — not the individual rows

This is the option that beats the other three outright, not just a trade-off among equals: if the answer is a computed value, let the database compute it. There's no reason for millions of rows to cross the network at all.

RememberNeed a number, not the rows → aggregate in the database, every time.
2 Every row genuinely needs individual processing — sent to an external API, written to a file, transformed and re-saved

When the rows themselves have to be touched, pick streaming for simple one-row-at-a-time work, or keyset-paginated batching when the work needs a chunk boundary (a transaction per batch, a bulk call per chunk) — either way, memory stays bounded as the table grows.

RememberReal per-row work → stream or batch, never buffer the whole table.
3 A nightly job that worked fine for months suddenly throws an out-of-memory exception

Buffering "worked" for a long time simply because the table was small enough — it was never actually safe, just not yet tested against real scale. The fix is switching to streaming or batching, not raising the memory limit and hoping the table stops growing.

RememberA job that "always worked" until now is a sign buffering was never the right choice, just untested at scale.
🌍 Real-world example ▾

A nightly job recalculates total revenue per region across tens of millions of order rows, and a separate job re-exports every individual order to a partner system. The revenue job should never pull a single order row — GroupBy(o => o.Region).Select(g => g.Sum(o => o.Amount)) gets the database to compute it directly. The export job genuinely needs every row, so it streams or keyset-batches through the table instead of loading it all into memory at once.
