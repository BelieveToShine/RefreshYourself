The App Router has four caching layers — not one

"Name the four caching layers in the Next.js App Router and what each one actually stores."

Why it matters ▾
🗂️ Four independent caches
❗ ProblemA bug report says "the data looks stale" — but the App Router has four separate caching layers, each populated and invalidated differently, so clearing or checking the wrong one wastes the whole investigation.
✅ SolutionTreat each layer as its own thing — Request Memoization, Data Cache, Full Route Cache, Router Cache — and diagnose by asking which ONE of the four is still holding the old value.
RecallFour caches, four different jobs — never debug "the cache" as if it were one thing.
🔥 Easy interview recall

Request Memoization → one render pass, dedupes fetch()

Data Cache → server, across requests & deploys

Full Route Cache → server, rendered HTML + RSC

Router Cache → client, this browser session

Think: the first three live on the server and are shared by every user. The last one lives in one person's browser tab.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The cache" is not one thing. A caching bug can only be diagnosed by naming which of the four layers is actually holding the stale value — they invalidate completely independently of each other.

🔄 Likely Follow-up

"Which of the four is scoped to a single user's browser session, not shared across users?" The Router Cache — it's entirely client-side, per browser tab. The other three are server-side and shared by every user hitting that server or deployment.

🎯 Say this in the interview — the exact lines to land

"The App Router has four caching layers: Request Memoization dedupes identical fetch() calls within one render pass, the Data Cache persists fetch() results across requests and deployments, the Full Route Cache stores a static route's rendered HTML and RSC payload, and the Router Cache holds RSC payloads client-side for routes the user has already visited this session."

  • Request Memoization → one render pass only, always on, never persists.
  • Data Cache → server-side, across requests & deployments, controlled by fetch options.
  • Full Route Cache → rendered HTML + RSC payload, cleared by revalidatePath()/revalidateTag().
  • Router Cache → client-side only, makes back/forward feel instant.
  • Stale-data bugs → name the exact layer before touching anything — they invalidate independently.
📖 Explanation ▾

Request Memoization is the shortest-lived of the four — it only exists for the duration of a single render pass on the server, automatically deduping identical fetch() calls (same URL, same options) so ten components asking for the same data only trigger one real network call. It resets on the very next request and is never something you configure.

The Data Cache and Full Route Cache both live on the server and both outlive a single request, but they cache different things: the Data Cache stores raw fetch() results (keyed by URL and options), while the Full Route Cache stores the already-rendered output — HTML plus the RSC payload — for an entire static route. A route can lose its Full Route Cache entry via revalidatePath()/revalidateTag() while the underlying Data Cache entries that fed it are invalidated by the exact same calls, which is why the two are easy to conflate even though they're genuinely separate stores.

The Router Cache is the odd one out: it runs entirely in the browser, holding RSC payloads for routes already visited in this session so navigating back doesn't re-fetch anything. It has nothing to do with any other user's browser and nothing to do with the server at all — it's cleared by router.refresh() or on its own timer.

💻 See the code ▾
JavaScript 
async function Header() {
  const user = await fetch('https://api.example.com/user'); // call #1
  ...
}

async function Sidebar() {
  const user = await fetch('https://api.example.com/user'); // ✅ deduped — same call, same render pass
  ...
}

Two components both call the exact same fetch() during one render — Request Memoization means only one real network request happens.

JavaScript 
const res = await fetch('https://api.example.com/posts', {
  next: { tags: ['posts'] }, // tags the Data Cache entry
});

Tagging a fetch() call writes into the Data Cache, not the Full Route Cache — the two are invalidated together by revalidateTag but are physically separate stores.

🧭 Use Cases — recognize these when they happen to you ▾
1 A page shows the same data twice, fetched by two different components

This is Request Memoization doing its job within a single render — it's automatic and resets on the next request, so don't reach for it to explain data staying fresh across page loads.

RememberSame fetch(), same render → deduped to one call, nothing more.
2 You call revalidatePath() but the page still shows old data

The server-side Full Route Cache may be cleared correctly while the client's Router Cache still has the old RSC payload for that visited route. A common interview trap: assuming one invalidation call reaches every layer.

RememberEach layer needs its own trigger — one call doesn't clear all four.
3 You're diagnosing exactly where a stale value is sitting

Before touching any config, ask which of the four layers is actually responsible — server-side (Data/Route) vs. client-side (Router) fixes are completely different, and guessing wastes the investigation.

RememberName the layer before you reach for a fix.
🌍 Real-world example ▾

A teammate reports "the dashboard still shows yesterday's numbers after I fixed the data." The fix: ask which layer. If they changed the database directly, the Data Cache entry for that fetch() may still be valid. If they called revalidateTag() server-side but the user never reloaded or navigated, the client's Router Cache for that already-visited route can still be serving the old RSC payload until a router.refresh() or a fresh navigation happens.
