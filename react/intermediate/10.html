Client-side routing — swapping views without leaving the page

"How does client-side routing work, and what happens when a user refreshes on a nested route?"

Why it matters ▾
🔑 Route parameter
❗ ProblemWithout a way to embed a value inside the path itself, the router would need a separate, hardcoded route for every single resource — one route for user 42, another for user 99 — instead of one pattern that matches them all.
✅ SolutionA route parameter like :id in /users/:id lets one pattern match any value in that URL segment, and is usually required for the route to match at all — useParams() then reads it to know which specific resource to render.
RecallRoute parameter = part of the path, usually required to match.
🏷️ Query parameter
❗ ProblemIf every optional bit of extra state — a sort order, a filter, a page number — had to be baked into the path itself, the app would need a whole new route for every combination, even though it's still the exact same resource underneath.
✅ SolutionA query parameter like ?sort=name rides along after the path as optional extra info — the route still resolves with or without it, so filtering/state can be layered on top without multiplying the number of routes needed.
RecallQuery parameter = optional extra info, not required to resolve.
🔥 Easy interview recall

/users/:id → route param — part of the URL's identity

?sort=name → query param — optional extra info

Think: a hard refresh on a nested route hits the SERVER — it needs a fallback configured, or it 404s.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Client-side routes don't behave exactly like server routes — a refresh isn't a quiet re-serve of the same page. On a pure client-side-rendered app, hard-refreshing a nested URL like /users/42 sends that exact URL straight to the server, which has to be explicitly configured to serve the same single-page-app shell for every route (a fallback) — without that configuration, the refresh 404s, since the server has no route matching that URL on its own.

🔄 Likely Follow-up

"What's the difference between a route parameter and a query parameter?" A route parameter (/users/:id) is part of the URL's path structure, usually identifying a specific resource, and is often required for the route to match at all; a query parameter (?sort=name) is optional, additional filtering or state information layered on top, typically not required for the route itself to resolve.

📖 Explanation ▾

Client-side routing means the app itself decides which component tree to show for a given URL, instead of asking a server for a whole new page every time. The router listens for navigation, updates the address bar through the browser's History API, matches the current path against a list of registered patterns, and renders whichever component matches — all without a full page reload.

Route parameterQuery parameter
Where it lives/users/:id — inside the path itself?sort=name — appended after the path
Required to match the route?✅ usually — the pattern won't match without it❌ no — the route resolves with or without it
What it's foridentifying a specific resourceoptional filtering/state on top of that resource

Three common variants build on this same mechanism: nested routes render a parent layout with the matched child route filled into a slot inside it; protected routes check whether the user is authenticated before rendering the target, redirecting elsewhere if not; and lazy-loaded routes only download that route's own code the moment it's actually navigated to, keeping the initial bundle smaller.

The refresh gotcha comes from where the matching actually happens. Once the app's JavaScript is loaded, the router owns navigation entirely — but a hard refresh throws that JavaScript away and asks the server directly for that exact URL. A server that only knows how to serve one index.html shell has to be told to return that same shell for every path (a fallback rule), or it has nothing to match /users/42 against and returns a 404.

💻 See the code ▾
JSX 
import { Route, useParams } from 'react-router-dom';

// route definition — :id is the route parameter
<Route path="/users/:id" element={<UserProfile />} />

function UserProfile() {
  const { id } = useParams();   // reads the matched :id
  return <h2>User #{id}</h2>;
}

useParams() reads whatever the router matched into :id — no manual URL parsing.

JSX 
import { lazy, Suspense } from 'react';

const UserProfile = lazy(() => import('./UserProfile'));   // downloaded only when visited

<Suspense fallback={<Spinner />}>
  <Route path="/users/:id" element={<UserProfile />} />
</Suspense>

The UserProfile bundle only downloads the moment someone navigates to /users/:id — smaller initial load.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app needs a shared layout (nav, sidebar) around several different pages

This is the #1 scenario you'll actually run into: a nested route renders the parent layout first, then fills the matched child route into a slot inside it — so /dashboard/settings gets the same nav/sidebar as every other page under /dashboard, without repeating that layout markup per page.

RememberNested route = parent layout renders, matched child fills a slot inside it.
2 A route should only render for a logged-in user

A protected route checks whether the user is authenticated before rendering the target component — if not, it redirects elsewhere (usually a login page) instead of ever rendering the page the route points to.

RememberProtected route = check auth first, redirect away if unauthorized.
3 Your app has routes most visitors never actually open (e.g. an admin panel)

A lazy-loaded route only downloads that route's own code the moment someone actually navigates to it, instead of shipping every route's code in the initial bundle — keeping the first load smaller for routes most visitors never open.

RememberLazy-loaded route = code downloads only when that route is actually visited.
🌍 Real-world example ▾

A hotel room number vs. a note left at the front desk. The room number is the route parameter — it identifies exactly which room, and you can't find the room without it. A request for extra pillows written on a note is the query parameter — useful, optional extra information, but the front desk doesn't need it to find the room in the first place.
