SaveChanges() — one call, one transaction. A second call is a separate bet.

How does EF Core handle transactions by default around SaveChanges()?

Why it matters ▾
  • Checks whether you know SaveChanges() has real transactional behavior, not just "it writes rows to the database."
  • Comes up any time a feature needs two or more writes — including raw SQL, or writes split across DbContexts — to succeed or fail together.
  • A very common interview opener into transaction scope, because most candidates have never had to think about it until something actually broke in production.
🔥 Easy interview recall

1× SaveChanges() → one transaction

2× SaveChanges() → two transactions

Think: SaveChanges() draws its own boundary around itself — nothing outside that one call is included, not even the very next line of your code.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Two SaveChanges() calls next to each other in the same method are not automatically atomic together. Each call opens and closes its own independent implicit transaction, so the first can commit successfully while the second fails later — leaving the database in an inconsistent in-between state unless an explicit transaction wraps both calls.

🔄 Likely Follow-up

"You call SaveChanges() once to insert an Order, then call it again to insert that Order's audit-log entry. The second call throws. What's the actual state of the database afterward?" The Order is already committed from the first successful call — only the audit-log insert failed and rolled back. The database is left inconsistent unless an explicit transaction had wrapped both calls together.

🎯 Say this in the interview — the exact lines to land

"By default, a single SaveChanges() call wraps every INSERT, UPDATE, and DELETE it generates in one implicit database transaction, so that one call is all-or-nothing. If I need multiple SaveChanges() calls — or EF Core mixed with raw SQL — to succeed or fail together, I wrap them in an explicit transaction with BeginTransaction(), or a TransactionScope when the unit of work spans more than one DbContext."

  • One SaveChanges() → one implicit transaction, every statement in that batch commits or rolls back together.
  • Two separate SaveChanges() calls → two independent transactions, not atomic together by default.
  • Need them atomic together → wrap both in BeginTransaction(), commit only once every call succeeded.
  • Unit of work spans multiple DbContexts or resources → use a TransactionScope instead.
📖 Explanation ▾

When SaveChanges() runs, EF Core translates every tracked change into INSERT, UPDATE, and DELETE statements and sends them to the database inside one transaction it opens and closes for you. If any statement in that batch fails, EF Core rolls the entire batch back — nothing partial is ever left behind from a single call.

That transaction's boundary is exactly one call wide. A second call to SaveChanges() — or a raw ADO.NET command run outside EF Core's own connection — isn't automatically part of it. Each database operation gets its own boundary unless you explicitly say otherwise, the same way two separate trips to the post office are two separate deliveries, even if you make them minutes apart.

context.Database.BeginTransaction() gives you that explicit boundary: nothing inside it is written to disk until you call Commit(), so every SaveChanges() call (and any raw SQL run on the same connection) between the begin and the commit rises or falls together. When the unit of work spans more than one DbContext, or a non-EF resource, a System.Transactions.TransactionScope wraps all of them under one ambient transaction instead.

💻 See the code ▾
C# 
using var context = new AppDbContext();

context.Orders.Add(new Order { CustomerId = 42 });       // tracked only
context.OrderLines.Add(new OrderLine { ProductId = 7 }); // tracked only

context.SaveChanges();   // ✅ ONE transaction — both inserts commit together

Every statement SaveChanges() generates here — both inserts — commits or rolls back as one unit.

C# 
context.Orders.Add(order);
context.SaveChanges();          // ✅ commits immediately — its own transaction

context.AuditLogs.Add(new AuditLog { OrderId = order.Id });
context.SaveChanges();          // ❌ throws — only THIS insert rolls back
                                 // the Order above is already saved

The first SaveChanges() already wrote to the database before the second one ever threw — nothing ties them together.

C# 
using var txn = context.Database.BeginTransaction();
try
{
    context.Orders.Add(order);
    context.SaveChanges();               // not committed yet — still inside txn

    context.AuditLogs.Add(new AuditLog { OrderId = order.Id });
    context.SaveChanges();               // not committed yet either

    txn.Commit();                        // ✅ both inserts commit together
}
catch
{
    txn.Rollback();                      // ❌ both inserts undone together
}

Nothing is written to disk until Commit() — the explicit transaction is what makes both calls atomic together.

🌍 Real-world example ▾

Your checkout flow saves an Order, then calls SaveChanges() again to write a separate AuditLog row. If the audit-log table is ever out of sync, that second call throws — but the Order is already committed, so every checkout still succeeds while the audit trail silently goes missing. Wrapping both calls in one BeginTransaction() turns that into a clean, whole failure instead of a silent partial one — exactly the trade-off explicit transactions exist to make.
