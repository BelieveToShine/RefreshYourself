Resilience patterns — failing on purpose, before you fail by accident

"What does resilience mean for a cloud application beyond just 'the service didn't go down'?"

Why it matters ▾
🔁 Retry
❗ ProblemA call can fail from a short-lived blip — a dropped connection, a one-off 503 — and giving up right away treats a passing glitch as a real failure.
✅ SolutionRetry waits (with exponential backoff + jitter) and tries again, recovering from the blip instead of piling more load on immediately.
RecallRetry = wait, then try again — never without backoff, or it becomes a retry storm.
⏱️ Timeout
❗ ProblemA dependency that's merely slow — not down — can hang a single attempt indefinitely, tying up the caller waiting on it.
✅ SolutionTimeout caps how long one attempt is allowed to run and cancels it at N seconds, so a hang can't block the request forever.
RecallTimeout = cap how long you'll wait on a single attempt.
🚦 Circuit breaker
❗ ProblemOnce a dependency is clearly down, retrying it anyway just hammers a struggling service with more load and wastes time on calls that won't succeed.
✅ SolutionAfter N consecutive failures the breaker opens and skips the call instantly for a cooldown period, giving the dependency room to recover.
RecallCircuit breaker = stop calling, fail fast, until the cooldown passes.
🛟 Fallback
❗ ProblemEven after retry, timeout, and the breaker, a call can still ultimately fail — and the caller shouldn't just be handed a raw error.
✅ SolutionFallback returns a safe, degraded answer — a cached or default value — instead of failing the whole request outright.
RecallFallback = hand back a safe default instead of an error.
🔥 Easy interview recall

Retry → wait, then try again

Timeout → cap how long you'll wait

Circuit breaker → stop calling, fail fast

Fallback → hand back a safe default

Think: each layer catches exactly what the one before it couldn't.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just retry it — that fixes flaky calls." Retrying without backoff can make an outage worse: a burst of immediate retries piles more load onto a dependency that's already struggling (a "retry storm"), which is exactly what exponential backoff + jitter exists to prevent.

🔄 Likely Follow-up

"What's a circuit breaker, concretely?" After N consecutive failures it "opens" and short-circuits further calls immediately — no wait, no retry — for a cooldown period, giving the failing dependency room to recover instead of being hit harder.

🎯 Say this in the interview — the exact lines to land

"Retry with backoff, timeout, circuit breaker, and fallback each protect against a different failure shape — retry recovers from a blip, timeout stops a hang, the circuit breaker stops hammering a dependency that's clearly down, and fallback keeps the caller from failing outright."

  • Retry (backoff + jitter) → use for a transient blip — a dropped connection, a one-off 503.
  • Timeout → use so a slow dependency can't hang the whole request indefinitely.
  • Circuit breaker → use to stop hammering a dependency that's clearly down, failing fast instead.
  • Fallback → use to degrade gracefully instead of failing the whole request.
  • Retry storms are the trap — never retry blindly, always pair it with backoff + jitter.
📖 Explanation ▾

Resilience isn't just "the service stayed up" — it's how gracefully a call behaves when a downstream dependency doesn't cooperate. A dependency can be slow, briefly flaky, or fully down, and each of those calls for a different response — treating them all the same way (just wait, or just fail) either wastes time or gives up too easily.

The four patterns stack, each one covering what the last one leaves open. Retry handles a short-lived blip by trying again after a wait. Timeout makes sure a single attempt can't hang forever. Circuit breaker notices when retrying is pointless — the dependency is clearly down — and stops sending traffic at it. Fallback is the last line: instead of the caller seeing an error, it gets something usable.

💻 See the code ▾
C# 
Policy
  .Handle<HttpRequestException>()
  .WaitAndRetryAsync(// ✅ 3 retries, exponential backoff
    retryCount: 3,
    sleepDurationProvider: attempt =>
      TimeSpan.FromSeconds(Math.Pow(2, attempt))
      + TimeSpan.FromMilliseconds(Random.Shared.Next(0, 250))); // jitter

Each retry waits longer than the last (2s, 4s, 8s…) plus a small random jitter — that spacing is exactly what stops a retry storm.

🧭 Use Cases — recognize these when they happen to you ▾
1 A call fails once with a dropped connection, then succeeds on the very next try

This is the #1 scenario you'll actually run into — a transient blip, not a real outage. The short wait-then-retry with backoff quietly fixes it before the caller ever notices.

RememberTransient blip → retry (with backoff) is all it takes.
2 A downstream call just sits there — no error back, the request never returns on its own

No response isn't the same as a fast failure — without a cap, this attempt hangs indefinitely and ties up the caller. A per-attempt timeout cancels it at N seconds so the caller isn't stuck waiting forever.

RememberSilence ≠ safe — cap the wait or it's indefinite.
3 The same dependency has already failed N times in a row and is clearly down

Retrying here is pointless — the dependency is clearly down, not blipping. The breaker has already opened and skips the call instantly, and fallback hands back a safe default in its place, so the caller never even feels the outage.

RememberConsecutive failures → breaker skips the call, fallback covers the gap.
🌍 Real-world example ▾

A checkout service wraps its payment-gateway call with a circuit breaker. When the gateway has an outage, the breaker opens and checkout fails fast with a clear "payments are temporarily unavailable" message — instead of every single checkout request hanging for 30 seconds before timing out on its own.
