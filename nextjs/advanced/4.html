One route, one instant shell, a few dynamic holes — still experimental

"What is Partial Prerendering, and is it production-stable?"

Why it matters ▾
🧩 Static shell + dynamic holes
❗ ProblemA route with any genuinely dynamic/personalized part is usually rendered dynamically as a whole, even though most of the page is actually static and could be served instantly.
✅ SolutionPartial Prerendering serves the static shell from a prerendered cache instantly, while the dynamic parts stream in as separate <Suspense> "holes" — one route, two speeds.
RecallPPR = instant static shell + streamed dynamic holes, in one response.
🔥 Easy interview recall

PPR = "instant shell, dynamic holes stream in after."

Think: a store page where the layout and price show instantly, but "items left in stock" fades in a beat later. As of the Next.js 15 release, this is still experimental, opt-in per route.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

PPR is not a stable default. As of the Next.js 15 release it remains experimental and opt-in per route via experimental_ppr — always check the current docs before claiming otherwise, since this is exactly the kind of fast-moving detail that goes stale fastest.

🔄 Likely Follow-up

"How is this different from just using Suspense and streaming normally?" Without PPR, a route with any dynamic part is typically rendered dynamically as a whole. PPR specifically keeps the static parts served instantly from a prerendered shell while only the genuinely dynamic holes stream in — a finer-grained mix than all-static or all-dynamic.

As of the Next.js 15 release it's still experimental and opt-in, not a stable default."

  • Static shell → served instantly from the prerendered build.
  • Dynamic holes → stream in via <Suspense> at request time.
  • Status at Next.js 15 → experimental, opt-in per route, not default.
  • Enabled via → experimental_ppr route config.
📖 Explanation ▾

A normal route without PPR picks one rendering mode for the whole page: fully static, or fully dynamic if any part of it needs request-time data. PPR splits that choice per-section — everything NOT wrapped in a dynamic boundary gets prerendered once at build time into a static shell, and anything that genuinely needs per-request data is wrapped in its own <Suspense> boundary, which Next.js treats as a "hole" to fill in after the shell is already on the wire.

The response the browser gets is a single stream: the shell arrives first (because it was already rendered, no work needed), and each hole's real content streams in as it resolves — the same mechanism as regular streaming SSR, just applied to a page that's mostly static instead of mostly dynamic.

The status matters as much as the mechanism. PPR shipped as an opt-in, experimental feature — enabled per route with experimental_ppr = true in that route's config — and remained experimental as of the Next.js 15 release. It is not something every route gets automatically, and its exact production-readiness should always be checked against current docs rather than assumed.

💻 See the code ▾
JavaScript 
// app/product/[id]/page.js
export const experimental_ppr = true; // ✅ opt in, per route

export default function ProductPage({ params }) {
  return (
    <main>
      <ProductInfo id={params.id} />  // static — part of the shell
      <Suspense fallback={<Skeleton />}>
        <LiveStock id={params.id} />  // ✅ dynamic hole, streams in
      </Suspense>
    </main>
  );
}

<ProductInfo> becomes part of the static shell; <LiveStock> is the hole that streams in separately.

🧭 Use Cases — recognize these when they happen to you ▾
1 A page is mostly static, with one personalized widget

This is PPR's ideal case — one small dynamic widget shouldn't force the whole route to render dynamically; wrapping just that widget in <Suspense> under experimental_ppr keeps the rest instant.

RememberMostly-static page + one dynamic widget → PPR's best fit.
2 Someone claims PPR is production-ready and on by default

At the Next.js 15 release, PPR is explicitly experimental and opt-in. A common interview trap: presenting it as a stable default without that caveat.

RememberPPR at Next.js 15 → experimental, opt-in. Always say so.
🌍 Real-world example ▾

A product page's price, images, and description never change per visitor, but a "recommended for you" rail does. Without PPR, that one rail forces the whole route into dynamic rendering. With experimental_ppr enabled and the rail wrapped in its own <Suspense>, the price and images still render instantly from the prerendered shell, and only the recommendation rail streams in a moment later.
