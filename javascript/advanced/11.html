Polyfill vs. transpile — missing feature or syntax the parser can't read?

"What's the difference between a polyfill and transpilation — and why can't a polyfill fix code that uses syntax an old engine's parser can't even read?"

Why it matters ▾
🧩 Polyfill
❗ ProblemAn old engine simply doesn't have a method your code calls — no Array.prototype.flat, no Promise.all, no fetch — so calling it throws at runtime.
✅ SolutionA polyfill is ordinary JavaScript that checks whether the method is missing and, if so, defines it at runtime — the same shape used to implement map, bind, or Promise.all yourself.
RecallPolyfill = adds the missing feature, at runtime.
🛠️ Transpilation
❗ ProblemNewer syntax like arrow functions throws a SyntaxError on an old parser before a single line of your code — or any polyfill — ever runs.
✅ SolutionBabel rewrites that syntax into older syntax the parser can read, once, at build time, before the engine ever sees the file.
RecallTranspile = rewrites the syntax, before runtime.
🔥 Easy interview recall

Polyfill → adds the missing feature, at runtime

Transpile → rewrites the syntax, before the engine ever runs it

Feature detection → check if (Array.prototype.flat), never guess from the browser name

Think: a polyfill fills in a missing tool. Transpiling rewrites the sentence into words the reader already knows.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A polyfill can't fix syntax the parser can't even parse. A polyfill is just an ordinary function added at runtime — the engine still has to successfully parse the whole file first. Arrow functions on a truly ancient engine throw a SyntaxError before a single polyfill has a chance to run; that's a transpilation problem, not a polyfill problem.

🔄 Likely Follow-up

"So do I always need both?" Often, yes — a typical production build ships a Babel-transpiled bundle for older syntax plus a targeted polyfill set (like core-js) for missing runtime features, with a browserslist config deciding how much of each is actually needed for the browsers you claim to support.

🎯 Say this in the interview — the exact lines to land

"A polyfill adds a missing feature or method at runtime, so the engine has it by the time your code calls it. Transpilation rewrites newer syntax into older syntax before the engine ever sees the file, because that's a parsing problem, not a missing-feature problem — and a polyfill can never fix code the parser can't parse in the first place."

  • Polyfill → use when a feature or method is missing at runtime — e.g. Array.prototype.flat, Promise.all, fetch.
  • Transpile (Babel) → use when the syntax itself is too new for the parser — e.g. arrow functions, optional chaining, classes.
  • Feature detection → check if (Array.prototype.flat) before relying on it; never sniff the browser name or version — that's unreliable.
  • Bundle size → shipping every polyfill and transpiled helper to every visitor is real dead weight; differential (modern-vs-legacy) bundling sends the extra weight only to the browsers that actually need it.
  • A polyfill is just a plain function added onto a prototype or global if it's missing — "implement map/bind/Promise.all yourself" is the classic coding exercise that makes this concrete.
📖 Explanation ▾

These are two different problems that get conflated constantly. A polyfill is ordinary JavaScript that adds a feature the runtime doesn't have yet — check whether Array.prototype.flat exists, and if it doesn't, define it yourself so code that calls .flat() doesn't crash. Transpilation (Babel is the standard tool) solves a different problem entirely: converting newer JS syntax into older syntax an old parser can actually read, before the file ever reaches the engine.

The reason they aren't interchangeable is where each one operates. A polyfill runs at runtime, after the file has already parsed successfully — so it can never rescue a file the parser rejects outright. An engine that has never heard of arrow functions throws a SyntaxError on () => {} before a single polyfill gets a chance to run; only rewriting that syntax into function(){} ahead of time, at build time, actually fixes it.

Feature detection is the discipline that decides whether a polyfill is even needed: check the real capability directly — if (window.IntersectionObserver) — never assume it from a browser name or version string, which is unreliable and goes stale the moment a browser updates. The production trade-off is bundle size: a polyfill/transpilation-runtime bundle sent to every visitor, including the ones on a fully modern browser who need none of it, is dead weight. Differential ("modern"/"legacy") bundling is the usual answer — serve a small bundle to capable browsers and the heavier fallback only to the ones that actually need it.

💻 See the code ▾
JavaScript 
// ✅ Feature detection — ask the engine directly
if (!Array.prototype.flat) {
  // engine doesn't have it yet — safe to polyfill
}

// ❌ Browser sniffing — brittle, guesses instead of checking
if (navigator.userAgent.includes("Chrome")) { /* ... */ }

Feature detection asks "can I actually do this?" directly. Sniffing guesses from a string that lies constantly (spoofed, changed, or just wrong per version).

JavaScript 
// A simplified sketch of the shape every polyfill has
if (!Array.prototype.map) {
  Array.prototype.map = function(callback, thisArg) {
    const result = [];
    for (let i = 0; i < this.length; i++) {
      if (i in this) result[i] = callback.call(thisArg, this[i], i, this);
    }
    return result;
  };
}

Check first, then define the missing method — only if it's actually missing. Same shape used for bind, Promise.all, and every other "implement it yourself" exercise.

JavaScript 
// Source you write (newer syntax)
const double = (n) => n * 2;

// ✅ What Babel outputs for an older parser — same behavior, older syntax
var double = function (n) {
  return n * 2;
};

Nothing runs this twice — Babel rewrites it once, at build time, before the browser ever downloads the file.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your code calls a method the engine doesn't have yet — flat, Promise.all, fetch

The file already parses fine — the engine just doesn't have this specific method yet. A polyfill (core-js, or a hand-written shim) checks that it's actually missing, then defines it at runtime — the exact shape behind "implement map/bind/Promise.all yourself."

RememberMethod missing at runtime → polyfill fills it in.
2 Your source uses syntax an older parser has never seen — arrow functions, optional chaining, classes

This isn't a missing-feature problem — the parser can't even read the file yet. Babel rewrites that syntax into older syntax the parser can read, once, at build time, before the browser ever downloads the file.

RememberSyntax too new for the parser → transpile, not polyfill.
3 You assume a polyfill can rescue code the parser rejects outright

A polyfill is ordinary JavaScript — it only runs after the file has already parsed successfully. An engine that's never heard of arrow functions throws a SyntaxError on () => {} before a single polyfill gets the chance to execute. A common trap — reaching for "just add a polyfill" when the real fix is transpilation.

RememberParser rejects the file → no polyfill can save it.
🌍 Real-world example ▾

Your bundle analyzer shows a chunk half its size is polyfills for features every one of your actual users' browsers already supports natively. That's exactly why browserslist and differential bundling exist — set browserslist to the browsers you really support, let @babel/preset-env and core-js include only what's still missing for that list, and consider a type="module"/nomodule split so modern browsers skip the legacy bundle entirely instead of downloading fixes they never needed.
