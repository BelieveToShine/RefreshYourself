Observer — one change, many listeners, no hard-wiring

What is the Observer pattern, and how do C# events relate to it?

Why it matters ▾
📢 Observer
❗ ProblemWhen a price changes, an EmailAlert, a phone app, and a dashboard all need to know. If the price class calls each of them by name, it must be edited every time a new listener appears.
✅ SolutionThe subject only keeps a list of subscribers and notifies whoever is on it. New listeners join or leave without touching the subject.
RecallObserver = subject notifies a list of subscribers it does not know by name.
🔥 Easy interview recall

Subject → keeps the list, sends the news

Observer → subscribes, reacts when told

Think: Observer is a newsletter. The sender never knows who reads it. In C#, the event keyword is that newsletter built in.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Events are free — I can subscribe and forget." Not quite. The publisher holds a reference to every subscriber, so a short-lived subscriber on a long-lived publisher cannot be garbage collected until you unsubscribe with -=.

🔄 Likely Follow-up

"Is IObservable<T> the same as a C# event?" Same idea. IObservable<T> adds a returned IDisposable to unsubscribe, plus OnError and OnCompleted signals.

🎯 Say this in the interview — the exact lines to land

"Observer lets one subject notify many subscribers without knowing who they are — the subject keeps a list and calls each one. C# builds it in as event: publishers raise it, subscribers use += and -=."

  • Subject → keeps the list and notifies it, never names an observer.
  • Observer → subscribes itself and reacts when notified.
  • C# events → the built-in Observer; IObservable<T> is the richer form.
  • Pitfall → forgotten -= keeps subscribers alive and causes leaks.
📖 Explanation ▾

Observer removes direct calls. Instead of PriceFeed calling EmailAlert.Send(), it just says "price changed" to a list. Each listener decides what to do. That is low coupling — the subject depends on nothing concrete.

C# gives you this as event. The publisher declares it and raises it; subscribers attach with += and detach with -=. Only the publisher can raise the event, which keeps outsiders from firing it by mistake.

The cost is lifecycle. The publisher keeps a reference to each subscriber, so a forgotten -= on a long-lived publisher can keep a subscriber alive longer than intended.

💻 See the code ▾
C# 
public class PriceFeed
{
    public event Action<decimal>? PriceChanged;   // ✅ subject exposes the event

    public void Publish(decimal price) => PriceChanged?.Invoke(price);
}

The feed never mentions an observer — it just raises PriceChanged.

C# 
Action<decimal> alert = p => Console.WriteLine($"Alert: {p}");

feed.PriceChanged += alert;   // ✅ subscribe
feed.Publish(10m);            // alert runs
feed.PriceChanged -= alert;   // ✅ unsubscribe — alert can be collected

Subscribe with +=, and always unsubscribe with -= when the subscriber should go away.

🌍 Real-world example ▾

A stock app shows one price on a screen, a mobile alert, and an email rule. The price feed raises one event; each of the three subscribes on its own. Adding a fourth, say an audit log, means one new subscription — the feed is not edited at all.
