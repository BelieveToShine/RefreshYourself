🔥 EF Core · Basic · Must Know

EF Core — you write C#, it writes the SQL

"What is EF Core, and what problem does it actually solve over writing raw SQL by hand?"

Why it matters ▾
  • Comes up as the very first EF Core question in almost every .NET backend interview.
  • Explains why "slow LINQ" and N+1 bugs happen — they trace back to not knowing what SQL actually got generated.
  • Sets up every later EF Core topic — DbContext, tracking, and migrations all sit on top of this one idea.
🔥 Easy interview recall

EF Core = "an ORM that turns your C# LINQ into SQL, and rows back into C# objects."

Think: your code never touches SQL directly — EF Core is the translator standing in between.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

EF Core means you never have to think about SQL again. It removes writing SQL by hand, not understanding it — anything beyond trivial CRUD still needs you to read and reason about the SQL it actually generated.

🔄 Likely Follow-up

"If EF Core just writes SQL for you, when would you deliberately skip it and write raw SQL or use something like Dapper instead?" For bulk operations, complex reporting queries, or anywhere you need full control over the exact generated SQL for a measured performance reason.

🎯 Say this in the interview — the exact lines to land

"EF Core is an ORM for .NET — it lets me write LINQ against plain C# objects instead of hand-writing parameterized SQL and mapping rows back myself. It generates the SQL, tracks changes, and materializes the results into objects. The trade-off is that it's still a real abstraction — I still have to be able to read the SQL it produces for anything beyond simple CRUD."

  • Removes the plumbing → no hand-written ADO.NET commands, parameters, or manual row-to-object mapping.
  • Still generates real SQL → not always optimal, and it can hide performance problems like N+1 if you never check it.
  • Doesn't replace SQL knowledge → using an ORM well still means understanding the SQL it produces.
  • Skip it for → bulk operations, heavy reporting queries, or anywhere the exact generated SQL has to be controlled for performance.
📖 Explanation ▾

EF Core is an ORM (Object-Relational Mapper) for .NET. Writing raw ADO.NET means hand-building a SQL string, wiring up parameters one by one, opening a connection and command, and copying each column off a data reader into a C# object — repetitive, and easy to get wrong (a missed parameter is a SQL injection risk). EF Core lets you write LINQ against ordinary C# classes instead: it builds the parameterized SQL, sends it, and materializes the rows back into objects for you.

That convenience is a real abstraction, and abstractions have a cost. EF Core doesn't always generate the most efficient SQL, and because the SQL is hidden behind LINQ, it's easy to ship a query that quietly does far more work than it looks like it does — the N+1 problem is the classic example. Using an ORM well still means being able to read the SQL it produces, not being freed from ever needing to.

💻 See the code ▾
C# 
using var conn = new SqlConnection(connStr);
using var cmd = new SqlCommand("SELECT Id, Name, Price FROM Products WHERE CategoryId = @cid", conn);
cmd.Parameters.AddWithValue("@cid", categoryId);   // you wire every parameter
conn.Open();
using var reader = cmd.ExecuteReader();
var products = new List<Product>();
while (reader.Read())                          // you map every column, by hand
    products.Add(new Product { Id = reader.GetInt32(0), Name = reader.GetString(1), Price = reader.GetDecimal(2) });

Every query means hand-building SQL, wiring parameters, and mapping columns yourself — repeated for every query in the app.

C# 
var products = await db.Products
    .Where(p => p.CategoryId == categoryId)
    .ToListAsync();                    // ✅ EF Core builds the SQL and maps the rows

Same result, one LINQ statement — EF Core writes the parameterized SQL and does the mapping.

C# 
var query = db.Products.Where(p => p.CategoryId == categoryId);
Console.WriteLine(query.ToQueryString());  // 🔍 prints the exact SQL EF Core generated

Checking the actual generated SQL is what catches an N+1 or an inefficient query before it hits production.

🌍 Real-world example ▾

EF Core is a translator sitting between two people who speak different languages. You speak C#, the database speaks SQL, and the translator converts your sentence into theirs and their answer back into yours. A good translator saves you from learning the other language for every conversation — but for anything important, you still want to know enough of that language to catch a bad translation.
