CORS — does it stop the call, or just the read?

"What is CORS, and what does it actually protect when a browser client calls your API from a different origin?"

Why it matters ▾
🛡️ Same-Origin Policy
❗ ProblemA malicious site open in another tab could quietly ride your browser's existing session on a sensitive site and read what comes back.
✅ SolutionThe browser blocks cross-origin JavaScript reads by default — that default is the Same-Origin Policy.
RecallSame-Origin Policy = browser blocks cross-origin reads by default.
🔓 CORS — the opt-in
❗ ProblemThat same protection also blocks your own legitimate cross-origin app — like a single-page app calling its own API on another subdomain.
✅ SolutionCORS lets the server explicitly tell the browser exactly which origins are allowed to read its response.
RecallSOP blocks → CORS allows specific cross-origin reads.
⚖️ Wildcard vs. allow-list
❗ ProblemOnce you allow cross-origin reads at all, you still have to decide exactly who to trust.
✅ Solution* trusts every origin — fine for public data. An explicit allow-list trusts only named origins — required the moment credentials are involved.
RecallPublic → * can be fine. Credentials → explicit origin.
🚫 CORS ≠ Authentication
❗ ProblemTeams often assume that once CORS is configured, the API itself is protected from unauthorized callers.
✅ SolutionIt isn't — CORS only gates browser reads. Authentication (who you are) and Authorization (what you can do) are separate, still-required layers.
RecallCORS = browser read permission — not who you are, not what you can do.
🔥 Easy interview recall

CORS = "the browser's permission slip to read a response from another origin."

Think: the browser checks it, using headers the API sends back — the request itself already happened.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 Don't mix these three — the single most valuable distinction on this page
🚫 CORS is not an API security or authentication mechanism.
⚠️ Common Trap

CORS stops a malicious script from calling your API. It doesn't — CORS is enforced by the browser, not the server, so the request still fires; a non-browser client (another server, a mobile app, curl) never triggers a CORS check at all.

🔄 Likely Follow-up

"If CORS doesn't stop server-to-server calls, what actually protects this API from anyone who finds the URL?" Authentication and authorization — a completely separate concern; an API with no auth is callable by anyone regardless of CORS, and an API with strict CORS but no auth is still fully callable by any non-browser client.

🎯 Say this in the interview — the exact lines to land

"CORS is a browser-enforced rule — my API returns headers like Access-Control-Allow-Origin that tell the browser which other origins are allowed to read the response. It protects the browser's user, not my server: without it, a malicious site could ride a victim's existing session on another site and read what comes back. A non-browser client — curl, another server, a mobile app — is never affected by CORS at all."

  • Same-origin policy → blocks by default; the API has to explicitly opt an origin in.
  • Access-Control-Allow-Origin → the header that names which origins the browser will trust with the response.
  • Wildcard * vs. allow-list → a real trade-off: easy but permissive, versus safer and matched to who actually needs access.
  • CORS is not authentication → a separate concern; add real auth regardless of how CORS is configured.
📖 Explanation ▾

Same-origin policy is the browser's default: JavaScript running on one origin (scheme, domain, and port together) can't read a response from a different origin — even though the network request itself still goes through. This exists to protect the person using the browser: without it, a malicious page could reuse a victim's existing session on another site and read whatever that site sends back.

CORS is the API opting specific origins back in. The API's response carries headers — Access-Control-Allow-Origin and related ones — naming which origins the browser is allowed to hand the response to. This only matters for an API genuinely called from browser JavaScript hosted on a different origin, like a single-page app served from its own domain.

Configuring it is a real design decision, not a checkbox. A wildcard (*) is the least work but trusts every origin equally, while an explicit allow-list matches exactly which frontends should have access — and it's the only option once the request needs to carry cookies.

Wildcard (*)Explicit allow-list
Who can read the responseany originonly the origins you list
Works with cookies/credentials❌ no — the spec forbids combining * with credentials✅ yes, alongside Access-Control-Allow-Credentials: true
Setup effortone line, no maintenancemaintain the list per environment
Best used fora public, anonymous APIa real frontend calling this API with cookies or auth
💻 See the code ▾
C# 
options.AddPolicy("Frontend", policy =>
    policy.WithOrigins("https://app.example.com")  // exact origin allowed
          .AllowAnyMethod()
          .AllowCredentials());              // ✅ cookies allowed — origin is explicit

An explicit allow-list is the only way to allow cookies or other credentials across origins.

C# 
options.AddPolicy("Public", policy =>
    policy.AllowAnyOrigin()   // any origin can read the response
          .AllowAnyMethod());
// policy.AllowCredentials();   ❌ throws — can't combine with AllowAnyOrigin

AllowAnyOrigin() is easy but can't carry credentials — fine only for a public, anonymous API.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your frontend and API live on the exact same origin

The browser sees the exact same origin on both sides, so the Same-Origin Policy was never blocking anything here — CORS headers never even enter the conversation.

RememberSame origin → CORS isn't the problem.
2 Your frontend calls an API on a different origin

Different origins → the browser applies CORS rules. The API must explicitly allow the frontend's origin, or every request succeeds on the network and still fails inside the browser. This is the #1 scenario you'll actually run into.

RememberDifferent origin + browser → check CORS.
3 That cross-origin call needs to carry cookies or a login session

Once credentials are riding along, the wildcard is off the table by spec — you need an exact origin in the allow-list, plus Access-Control-Allow-Credentials: true on the response and matching credential settings on the client.

RememberCredentials → explicit origin, never *.
4 You're exposing a public, anonymous API to any frontend

If the data is genuinely public with no session or credentials involved, allowing * is a reasonable, low-maintenance choice — every origin gets equal, harmless access.

RememberPublic + no credentials → * may be reasonable.
5 One backend service calls another backend directly

CORS is a browser-enforced mechanism only. A server-to-server HTTP client was never subject to the Same-Origin Policy, so configuring CORS headers has zero effect on whether this call succeeds. A great interview trap — candidates often assume CORS is "API security" that applies everywhere.

RememberNo browser → CORS usually isn't involved.
🌍 Real-world example ▾

Your API is called by a single-page app hosted on its own domain — app.example.com calling api.example.com. The API has to explicitly list https://app.example.com in its CORS policy, or every fetch from that frontend will succeed on the network but fail in JavaScript — a CORS error the browser's console shows, not something that ever shows up in the server's logs.
