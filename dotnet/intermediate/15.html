UseExceptionHandler vs. UseDeveloperExceptionPage — one of these must never reach production

What's the standard pattern for turning an unhandled exception into a clean response, and why must dev vs. production differ?

Why it matters ▾
  • Every real ASP.NET Core app needs one place that turns a crash into a proper response instead of a raw, bodiless 500 — interviewers use this to check you know the standard middleware pattern, not just "wrap it in try/catch."
  • Comes up any time someone asks how your API behaves when something goes wrong, or reviews a Program.cs for a security issue.
  • Classic follow-up bait: "could this app accidentally ship the dev exception page to production?" — yes, and it's a genuinely common misconfiguration.
🔥 Easy interview recall

Development → full stack trace, on screen

Production → generic response, nothing leaked

Think: IsDevelopment() is the gate — flip it, and you flip which page runs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The dev exception page isn't automatically disabled in production. If UseDeveloperExceptionPage() isn't gated behind app.Environment.IsDevelopment() — or worse, hardcoded to always run — it keeps handing out stack traces and file paths to real users after every deploy.

🔄 Likely Follow-up

"For a Web API specifically, what does that clean response actually look like?" Not an HTML error page — a structured JSON error response, often the RFC 7807 "Problem Details" format ASP.NET Core has built-in support for, since API clients expect JSON, not HTML.

🎯 Say this in the interview — the exact lines to land

"Register exception-handling middleware as one of the first things in the pipeline — UseExceptionHandler for a clean fallback response, or UseStatusCodePages for non-exception error codes. In Development that's the developer exception page with the full stack trace; in every other environment it's a generic response — usually a Problem Details JSON payload for an API — because the dev page is a security risk the moment real users can trigger it."

  • UseExceptionHandler → registered first, so it wraps everything downstream.
  • UseDeveloperExceptionPage → gated behind IsDevelopment(), never shipped as-is to prod.
  • Web API → clean response means JSON, typically RFC 7807 Problem Details.
  • MVC exception filters → narrower scope — they only catch what MVC's own action pipeline throws.
📖 Explanation ▾

The standard fix for "an unhandled exception shouldn't blow up as a raw stack trace" is a piece of middleware registered near the very start of the pipeline — either UseExceptionHandler(...), which redirects to an error-handling endpoint or writes a clean response, or UseStatusCodePages() for responses that come back with an error status but no exception at all (a 404, say). Because it sits first, it wraps every downstream middleware and endpoint — much broader than an MVC exception filter, which only ever sees exceptions thrown from inside MVC's own action-invocation pipeline. See MVC-Specific Filters for that narrower tool; the two aren't competing, they just operate at different layers.

UseDeveloperExceptionPage() is genuinely useful while you're coding locally — it shows the full stack trace, the request details, and the exception type directly in the browser. That same detail is exactly why it's an active security liability outside your own machine: internal file paths, stack frames, and sometimes sensitive data become visible to anyone who can trigger an error. That's the whole reason ASP.NET Core's own templates gate it behind if (app.Environment.IsDevelopment()) and fall back to a generic UseExceptionHandler("/Error") everywhere else.

💻 See the code ▾
C# 
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();   // ✅ full details — dev machine only
}
else
{
    app.UseExceptionHandler("/Error"); // ✅ clean fallback everywhere else
}

app.MapControllers();                  // registered AFTER — everything below is covered

This has to run near the top of the pipeline — it can only catch what happens after it.

C# 
app.UseDeveloperExceptionPage();   // ❌ no IsDevelopment() check at all
app.MapControllers();

No gate → this now leaks stack traces to real users after every deploy, not just on your machine.

C# 
app.UseExceptionHandler(exceptionApp =>
{
    exceptionApp.Run(async context =>
    {
        context.Response.StatusCode = 500;
        await context.Response.WriteAsJsonAsync(new
        {
            type = "about:blank",
            title = "An unexpected error occurred.",
            status = 500
        });   // ✅ JSON, not an HTML error page
    });
});

For a Web API, the fallback has to write JSON — these fields match the shape of RFC 7807 Problem Details.

🌍 Real-world example ▾

Production logs are full of 500s, but every affected user just sees a plain {"title":"An unexpected error occurred.","status":500} — no stack trace, no table name, nothing. That's not a bug, that's the exception-handling middleware doing exactly its job. You look up the real exception server-side, from the logs or a correlation/trace ID in the response — never by putting it in front of the user who triggered it.
