Fixed-size vs. semantic chunking — where you cut decides what retrieval finds

"How do you decide how to split a document into chunks for retrieval — fixed-size, semantic, or something else — and how do you choose chunk size and overlap?"

Why it matters ▾
  • Tests whether you understand that chunk boundaries directly affect retrieval precision, not just whether you can call a text-splitter function.
  • The natural follow-up right after any "how does RAG work" question — expect it in almost every RAG-focused interview.
  • A wrong chunk size or a bad splitting rule is a common root cause of "the answer is missing context" or "the answer is full of irrelevant text" bugs.
🔥 Easy interview recall

Chunking = deciding WHERE to cut. Fixed cuts by count, semantic cuts by meaning.

Think: Fixed-size → same rule everywhere, can slice a sentence in half Semantic / by-structure → follows the text's own natural breaks

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Making chunks bigger doesn't fix a bad cut. A fixed-size splitter can still slice a sentence in half at any chunk size — only splitting on a real boundary (sentence, paragraph, heading) avoids that.

🔄 Likely Follow-up

"So why not always use semantic chunking?" It costs extra compute to embed sentences and compare similarity at ingestion time. By-structure chunking is usually cheaper and just as effective whenever the source already has real structure — Markdown headings, HTML sections, list items.

🎯 Say this in the interview — the exact lines to land

"I chunk by structure when the source has real structure — headings or sections — and fall back to recursive or semantic splitting when it doesn't. I always add overlap so an idea near a boundary isn't cut off, and I size chunks by balancing retrieval precision against how much context a good answer actually needs."

  • Fixed-size → simplest and fastest, but can cut a sentence in half — fine when speed matters more than boundary quality.
  • Recursive → tries paragraph, then sentence, then character — more natural boundaries than plain fixed-size.
  • Semantic → splits where embedding similarity shows the topic actually shifts — most self-contained chunks, at the cost of more compute.
  • By-structure → splits on the document's own headings/sections — the best option whenever the source format has real structure.
  • Smaller chunks → better precision, less context Bigger chunks → more context, worse precision
  • Overlap between chunks → safety net against splitting an important idea exactly at the boundary.
📖 Explanation ▾

Fixed-size chunking splits text every N characters or tokens, usually with a little overlap between neighboring chunks so an idea isn't cut off exactly at the boundary. It's simple and fast, but it has no idea where a sentence or an idea actually ends — it can slice straight through one. Recursive chunking tries splitting on bigger, more natural boundaries first — paragraphs — and only drops down to sentences, then raw characters, when a piece is still too big. That tends to land on cleaner edges than blindly counting characters.

Semantic chunking looks at where the meaning actually shifts — often by comparing the embedding similarity between consecutive sentences and marking a drop as a topic boundary — so chunks come out as complete ideas instead of arbitrary slices, at the cost of extra computation to work out where those boundaries are. By-structure chunking is often the simplest good option: when the source already has real structure — Markdown headings, HTML sections, list items — splitting along that structure usually beats guessing at meaning from scratch.

Chunk size is its own tradeoff. Smaller chunks are precise for retrieval — less irrelevant text riding along with the match — but can lose surrounding context an answer needs. Larger chunks preserve more of that context, but dilute retrieval precision and eat more of the model's context window per retrieved chunk. Overlap between neighboring chunks is a cheap way to reduce the risk of an important idea landing exactly on a cut.

💻 See the code ▾
Python 
# fixed-size: counts characters, ignores structure
chunks = split_every_n_chars(text, size=500, overlap=50)

# recursive: try the biggest separator first, fall back if a piece is still too big
chunks = recursive_split(text, separators=["\n\n", ". ", ""])

Recursive splitting only drops to a smaller separator (sentence, then character) when a piece is still too big after trying the bigger one (paragraph).

sims = [cosine_sim(embed(a), embed(b)) for a, b in zip(sentences, sentences[1:])]
# a sharp drop in similarity between two sentences = a topic boundary
boundaries = [i for i, s in enumerate(sims) if s < threshold]

Semantic chunking cuts where consecutive-sentence similarity drops — that drop is the signal the topic actually changed.

🌍 Real-world example ▾

Your support-doc RAG bot keeps giving answers that mention the right policy but miss the one exception sentence right after it. The chunk boundary fell between the rule and its exception, so only one half got retrieved. The fix is splitting by structure — each FAQ entry as its own chunk — or adding overlap so the exception sentence rides along with the rule it modifies, instead of a flat fixed-size cut that has no idea the two sentences belong together.
