The Change Tracker & SaveChanges() — it only writes what actually changed

What is the Change Tracker, and how does SaveChanges() use it to know what to write?

Why it matters ▾
  • Checks whether you actually understand what SaveChanges() does, or just know to call it.
  • Explains a real production question: why an update touches so few columns, and why that's a good thing under load.
  • A common interview opener for anyone who's used EF Core without ever asking what happens underneath a save.
🔥 Easy interview recall

Added → INSERT

Modified → UPDATE (changed columns only)

Deleted → DELETE

Think: SaveChanges() doesn't save the object — it saves only the diff since the last snapshot.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A Modified entity's UPDATE does not set every mapped column. EF Core's generated SET clause only lists the columns whose value actually differs from the tracked snapshot — not the whole row.

🔄 Likely Follow-up

"You change exactly one property on a tracked entity, then call SaveChanges(). What does the generated UPDATE's SET clause actually contain?" Just that one column — not every mapped property on the entity.

🎯 Say this in the interview — the exact lines to land

"The Change Tracker keeps each tracked entity's current state — Added, Modified, Deleted, or Unchanged — plus a snapshot of its original values. SaveChanges() reads those states, diffs against the snapshot, and generates exactly the INSERT, UPDATE, or DELETE each entity needs, then flips it back to Unchanged."

  • Added → becomes an INSERT when SaveChanges() runs.
  • Modified → UPDATE, only the changed columns in the SET clause.
  • Deleted → becomes a DELETE, then the entity is detached.
  • Default tracking is snapshot-based — current values diffed against the original snapshot.
  • After a successful save, state flips back to Unchanged, and database-generated values are written back.
📖 Explanation ▾

Every tracked entity carries two things: a state — Added, Modified, Deleted, or Unchanged — and a snapshot of the property values EF Core last saw for it. By default this is snapshot change tracking: EF Core compares current values against that stored snapshot to see what moved. An entity implementing INotifyPropertyChanged can opt into changed-notification tracking instead, where the property setters themselves report a change instead of waiting for a comparison.

SaveChanges() walks every tracked entity, reads its state, and turns that into SQL: an INSERT for each Added entity, a DELETE for each Deleted one, and for Modified entities an UPDATE whose SET clause is built from the snapshot diff — only the columns that actually changed. Once the database confirms the write, EF Core flips each entity's state back to Unchanged and copies back anything the database generated, such as a new identity value, so the C# object matches the row that's now actually in the table.

💻 See the code ▾
C# 
var blog = await db.Blogs.FindAsync(1);  // tracked, snapshot taken
blog.Title = "New title";                     // only this property changes

await db.SaveChangesAsync();
// UPDATE Blogs SET Title = @p0 WHERE Id = @p1 -- only Title, not every column

The generated SET clause has one column — the only one that actually changed.

C# 
var entry = db.Entry(blog);
Console.WriteLine(entry.State);   // Unchanged

blog.Title = "New title";
Console.WriteLine(entry.State);   // Modified -- flips automatically

The Change Tracker flips an entity's state the moment a tracked property differs from its snapshot — no manual bookkeeping.

C# 
db.Blogs.Add(newBlog);       // state = Added
db.Blogs.Remove(oldBlog);    // state = Deleted

await db.SaveChangesAsync();
// INSERT for newBlog, DELETE for oldBlog
// newBlog.Id is now populated from the database

One SaveChanges() call can emit several different DML statements — one per tracked entity's own state.

🌍 Real-world example ▾

Think of it like editing a shared document with track-changes turned on — only the lines you actually touched show up as edits; everything else on the page is left alone.

Scenario: your API updates User.LastLoginAt on every request under heavy load. Does SaveChanges() rewrite the whole Users row each time? No — the generated UPDATE only sets LastLoginAt, so the lock footprint and the amount of data sent over the wire stay tiny even at high request volume.
