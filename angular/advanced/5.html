🧠 Deep Dive

effect() is the escape hatch — reach for it last, not first.

"How does Signal dependency tracking actually work under the hood, and when does reaching for effect() become an architectural smell?"

Why it matters ▾
  • An effect() quietly setting another Signal is one of the most commonly flagged findings in a Signal-based Angular code review — spotting it instantly separates someone who understands Signals from someone who only learned the syntax.
  • Getting dependency tracking wrong — usually a conditional read — causes stale-UI bugs that are hard to explain without knowing exactly what got tracked on the last run, not just what the function happens to mention.
  • Any team already migrated to Signals asks this specifically to check you won't reintroduce Observable-style side-effect habits into a Signal-based codebase.
🔥 Easy interview recall

computed() → produces a value (pure)

effect() → runs a side effect (rare)

Think: computed() derives. effect() does. Never let effect() secretly derive.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

effect() setting another Signal isn't just a style choice. It's exactly what computed() exists for — doing it via effect() loses the pure, read-only guarantees and risks update-ordering surprises computed() never has.

🔄 Likely Follow-up

"If effect() shouldn't be used to derive state, what IS it actually for?" Genuine external side effects a pure computed value can't express — syncing a Signal to localStorage, imperative DOM work outside template bindings, logging/analytics, or triggering some non-Signal-based API in response to a change.

🎯 Say this in the interview — the exact lines to land

"Angular tracks exactly which Signals a computed() or effect() actually read on its last run, and only re-runs it when one of those tracked Signals changes. computed() should produce every derived value; effect() is reserved for genuine external side effects — using effect() to set another Signal is the architectural smell interviewers are listening for."

  • Dependency tracking → tracks only the Signals actually read on that specific run, not every Signal the function mentions.
  • computed() vs. effect() → computed() produces a value, effect() does something.
  • Architectural smell → effect() setting another Signal is computed()'s job, done the hard way.
  • input() / output() / model() → all participate in the same fine-grained tracking a plain @Input property never did.
  • resource() / httpResource() → the purpose-built way to fetch async data from a Signal-based request, stable since Angular v22.
  • When NOT to use Signals → a real async stream with operator needs stays an Observable; converting it too early throws away exactly the tooling that made it the right fit.
📖 Explanation ▾

Every time a computed() or effect() callback runs, Angular watches which Signals actually get read — every call to a Signal as a function — during that specific run, and builds a concrete list: the Signals this particular execution genuinely depended on. The next time one of those specific Signals changes, Angular re-runs it. A Signal that isn't read on a given run isn't tracked for that run at all, even if some other branch inside the same function reads it — a conditional read means the dependency list can genuinely change between runs.

computed() produces a value — pure, derived, read like any other Signal, with no side effects of its own. effect() runs a side effect — it produces nothing you read; its whole job is to do something. State only needs to be a writable signal() if nothing else can compute it — anything derivable from other Signals should be a computed(), never a second Signal kept in sync by hand, the same don't-store-what-you-can-derive principle already covered on the React track's own State page.

Signal inputs (input()), outputs (output()), and two-way model() bindings — all stable since Angular v19 — replace @Input()/@Output() with primitives that plug straight into that same tracking system, so a template reading a Signal input gets the same precise, per-binding recompute a plain @Input property never had (it only triggered a coarser whole-component check). For async data fetching, resource() — and its httpResource()/rxResource() entry points, stable as of Angular v22 — is the more purpose-built current answer: it automatically re-runs whenever a Signal it reads changes, and httpResource() stays backed by the normal HttpClient, interceptors included.

💻 See the code ▾
TypeScript 
// ❌ effect() deriving a value — computed()'s job, done the hard way
effect(() => {
  this.total.set(this.price() * this.qty());
});

// ✅ computed() — pure, derived, no side effect needed
total = computed(() => this.price() * this.qty());

Same number on screen either way — but only the second version is pure, read-only, and can't create an update-ordering surprise.

TypeScript 
// signal input — replaces @Input()
count = input<number>(0);

// computed — derived value, never a second signal kept in sync by hand
doubled = computed(() => this.count() * 2);

// signal output — replaces @Output() + EventEmitter
changed = output<number>();

// model — input AND output at once, powers [(value)] two-way binding
value = model<string>('');

input() reads like any Signal, output() emits like the old EventEmitter, and model() is both at once — its auto-named ...Change output is what makes [(x)] work.

🌍 Real-world example ▾

computed() is like a calculator display that always shows the correct total the instant any input number changes — nobody has to press "=" again. effect() is like a person standing next to the calculator whose job is to physically walk over and update a separate whiteboard whenever the display changes: useful when something genuinely has to happen out in the world, but a wasteful, indirect way to just keep a second number in sync when the calculator could show the right total directly.
