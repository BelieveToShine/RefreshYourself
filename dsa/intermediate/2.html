Binary Search — when there's no array to search at all

"How does binary search work, and how would you use the same idea to find the smallest or largest value that satisfies some condition, instead of finding an element in an array?"

Why it matters ▾
  • Shows up disguised as an optimization problem — "minimize the largest load," "find the smallest capacity that works" — that doesn't look like a search problem at all.
  • An expert vendor review of this track's roadmap called this exact generalization "the biggest omission" in an earlier draft — it's a real gap, not a minor variant.
  • Rotated arrays and first/last-occurrence variants are how interviewers check you understand the mechanic, not just the textbook loop.
🔥 Easy interview recall

classic search → the array tells you which half to keep

search on answer → a feasibility check tells you which half to keep

Think: classic halves an array. search on answer halves a range of possible values — same halving move, different space.

⚠️ Common Trap

Binary search doesn't check that the input is sorted (or monotonic) for you. Run it on unsorted data, or on a feasibility check that isn't monotonic, and it won't error out — it just silently returns the wrong answer, because the halving logic assumes an ordering property that isn't actually there.

🔄 Likely Follow-up

"How do you know binary search on the answer even applies here?" Check monotonicity: as the candidate value increases, does "is this feasible" flip from false to true (or true to false) exactly once, with no flipping back and forth? If yes, binary search on the answer works; if feasibility bounces around, it doesn't.

🎯 Say this in the interview — the exact lines to land

"Binary search isn't just 'find a number in a sorted array' — it's a general technique for cutting any monotonic search space in half. That includes searching an array by index, and it includes searching a range of possible answer values by feasibility, which turns a lot of optimization problems into an O(n log(range)) search instead of testing every value one by one."

  • classic binary search sorted array, halve by index, O(log n).
  • first/last occurrence keep narrowing after a match instead of stopping at the first one found.
  • rotated array find which half is sorted, then apply the normal check to that half.
  • search on answer halve a range of candidate values using a feasibility check, O(n log(range)).
  • min/max feasible value flip the feasibility check's direction to switch between "smallest that works" and "largest that works."
  • litmus test — feasibility must flip exactly once as the candidate value increases.
📖 Explanation ▾

Classic binary search only needs one thing to be true: the search space has an order a middle value can be judged against. Check the middle element — if it's the target, stop; if the target is smaller, the whole right half can be thrown away; if it's larger, throw away the left half instead. Because the remaining space cuts in half every step, it finishes in O(log n) instead of checking every element.

When duplicates exist, first/last occurrence means not stopping at the first match. On a match, record it as the current best answer, then keep narrowing into the half that could still hold an earlier match (for the first occurrence, move high = mid - 1 and keep going left) or a later one (for the last occurrence, move low = mid + 1 and keep going right) — the loop only actually stops once low > high. That's the same idea behind lower bound (the first position where a value ≥ target could go) and upper bound (the first position where a value > target could go) — the building blocks behind library functions like lower_bound/upper_bound or bisect_left/bisect_right.

🧠 Visual Mental Model — first occurrence, traced step by step

A rotated sorted array still works too: at each step, figure out which half is itself sorted by comparing arr[low] against arr[mid] — if arr[low] <= arr[mid], the left half is sorted; otherwise the right half is. Once the sorted half is known, check whether the target falls inside that half's value range; if it does, apply the normal sorted-range check to that half, otherwise search the other half instead.

🧠 Visual Mental Model — rotated array, one decision traced

The real generalization: binary search on the answer stops searching an array altogether and instead searches a range of candidate answer values, using a feasibility check ("does this value actually work?") in place of comparing array elements. It only works when feasibility is monotonic — it flips from false to true (or true to false) exactly once as the candidate increases — which is what lets the same halving trick run in O(n log(range)) instead of testing every value one at a time.

The same loop finds a maximum feasible value just as easily as a minimum one — only the direction of the feasibility check flips. Searching for the smallest value that works, shrink toward the LEFT (smaller candidates) whenever the current one is feasible; searching for the largest value that works, shrink toward the RIGHT (bigger candidates) whenever the current one is feasible. Same halving, same monotonicity requirement, opposite side of the range being kept.

💻 See the code ▾
Pseudocode 
function binarySearch(arr, target):
    low = 0
    high = arr.length - 1
    while low <= high:
        mid = (low + high) / 2            // integer division
        if arr[mid] == target:
            return mid                    // ✅ found — stop
        else if arr[mid] < target:
            low = mid + 1                // discard the left half
        else:
            high = mid - 1               // discard the right half
    return -1                          // not found

Every step throws away a half that has already been ruled out by comparing against arr[mid] — never a half that could still hold the target.

Pseudocode 
function minFeasibleValue(low, high, isFeasible):
    while low < high:
        mid = (low + high) / 2
        if isFeasible(mid):
            high = mid                    // ✅ works — try smaller
        else:
            low = mid + 1                // ❌ doesn't work — go bigger
    return low                          // smallest feasible value

Same shrinking loop as classic binary search — arr[mid] is just replaced with isFeasible(mid), and there's no array at all.

Pseudocode 
function maxFeasibleValue(low, high, isFeasible):
    while low < high:
        mid = (low + high + 1) / 2       // ceiling division
        if isFeasible(mid):
            low = mid                     // ✅ works — try bigger
        else:
            high = mid - 1              // ❌ doesn't work — go smaller
    return low                           // largest feasible value

Mirror image of the min version — feasible now means "try BIGGER," so it rounds mid up ((low+high+1)/2) instead of down, otherwise low = mid could stop making progress and loop forever.

🌍 Real-world example ▾

Your service needs the smallest per-worker memory limit that still lets every job in a batch finish without an out-of-memory error. Instead of testing every possible limit one at a time, binary search the range of candidate limits: at each candidate, run one feasibility pass over the jobs ("does everything fit under this limit?"), then shrink toward smaller limits when it's feasible and bigger limits when it isn't. That's binary search on the answer — not a separate algorithm, the same halving trick applied to a value instead of an array.
