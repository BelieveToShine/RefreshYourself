Pagination — why a big OFFSET gets slower the deeper you page

"What are common pagination strategies, and what goes wrong with a large OFFSET on a big table?"

Why it matters ▾
🔢 OFFSET / FETCH
❗ ProblemAn API's "page 500" endpoint keeps getting requested as the table grows, and every request has to figure out where page 500 actually starts.
✅ SolutionIt walks and discards every earlier row to get there — an index on the sort column only speeds up the ordering, not that walk, so the cost still grows with how deep the page is.
RecallOFFSET → can jump to any page number, but cost grows with depth.
🔑 Keyset (Cursor)
❗ ProblemThat same "page 500" query keeps getting slower the deeper it pages, even with an index on the sort column already in place.
✅ SolutionIt filters on the last row's key instead of a row count, so an index can seek straight there — the same flat cost at any depth, though it can only move forward from that last row, not jump straight to a page number.
RecallKeyset → flat cost at any depth, but no jumping straight to page N.
🔥 Easy interview recall

OFFSET → walk & discard every skipped row first

Keyset → index seeks straight to the last spot

Think: page 500 with OFFSET means silently discarding 500 pages' worth of rows first, every single time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A large OFFSET is fine as long as you have an index on the sort column." An index helps the engine find the correct order quickly, but it still has to walk past and count every skipped row to reach the requested offset — the cost still grows with how deep you page, index or not.

🔄 Likely Follow-up

"What's the alternative that doesn't have this problem?" Keyset (cursor-based) pagination — remember the last row's key/sort value from the previous page and filter WHERE SortColumn > @lastValue ORDER BY SortColumn, which an index can jump straight to, regardless of how deep you are in the results.

🎯 Say this in the interview — the exact lines to land

"OFFSET/FETCH-style pagination has to walk through and discard every skipped row before it can return the page I asked for, so the deeper the page number, the more work gets thrown away — an index on the sort column speeds up finding the order, but it doesn't remove that walk. Keyset (cursor-based) pagination avoids this entirely: filter on the last row's key with WHERE SortColumn > @lastSeenValue and let an index seek straight there, at the same cost no matter how deep I'm paging."

  • OFFSET n → walks & discards n rows before returning anything.
  • Index on the sort column → speeds up ordering, not the skip — cost still grows with depth.
  • Keyset pagination → index seeks directly using the last row's key, same cost at any depth.
  • Use keyset → for deep pages (infinite scroll, large tables); a plain OFFSET is fine for shallow ones.
📖 Explanation ▾

OFFSET/FETCH-style (or LIMIT/OFFSET-style) pagination has to walk through and discard every skipped row before it can return the requested page. The engine doesn't know in advance which rows are "the ones you want" — it has to count past every row in front of them first, so the deeper the page number, the more work gets thrown away before anything useful comes back.

An index on the sort column speeds up finding the correct order — the engine no longer has to sort the whole table from scratch. It still has to count/skip past every offset row to reach the requested page, though, so the cost still grows with how deep you page, index or not.

Keyset (cursor-based) pagination sidesteps the walk entirely. Instead of asking "skip N rows," it remembers the last row's key/sort value from the previous page and asks "give me rows after this value" — a query an index can jump straight to, regardless of how many pages deep that value actually is.

💻 See the code ▾
SQL 
SELECT * FROM Orders
ORDER BY Id
OFFSET 10000 ROWS FETCH NEXT 20 ROWS ONLY;
-- ❌ walks & discards 10,000 rows before returning these 20

The engine walks past and discards all 10,000 skipped rows before it can return this page — every single time this exact query runs.

SQL 
SELECT * FROM Orders
WHERE Id > @lastSeenId
ORDER BY Id
FETCH NEXT 20 ROWS ONLY;
-- ✅ keyset pagination — index seeks straight to @lastSeenId

Same page size, but the index seeks straight to @lastSeenId — no rows walked past or thrown away, no matter how deep the page.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your table only ever has a handful of pages (an admin list, a settings history)

With so few rows to skip, OFFSET's walk-and-discard cost stays tiny no matter which of these first few pages someone requests — this is exactly the shallow-paging case the comparison table above calls OFFSET/FETCH's best fit.

RememberFew pages total → plain OFFSET is genuinely fine.
2 An infinite-scroll feed, or a "page 500" endpoint, that keeps getting requested deeper

The deeper the page, the more rows OFFSET has to walk past and discard before returning anything — exactly the cost growth the comparison table shows, and this is the scenario the interview question is actually asking about. Keyset pagination keeps that cost flat by letting an index seek straight to the last row seen, so it's the right fit here.

RememberDeep paging / infinite scroll → reach for keyset instead.
3 The UI needs numbered links so a user can jump straight to page 47

OFFSET/FETCH can jump straight to any page by number, because it computes exactly how many rows to skip from the number alone. Keyset can only move forward relative to the last row it already saw, so it can't answer "give me page 47" directly — a real limitation the comparison table calls out.

RememberNeed to jump straight to page N → that's OFFSET's one advantage.
🌍 Real-world example ▾

Reading page 500 of a physical book. OFFSET-style pagination is flipping through every single page from page 1 until you reach 500. Keyset-style pagination is opening straight to a bookmark that already says "page 500" — same destination, no flipping required.
