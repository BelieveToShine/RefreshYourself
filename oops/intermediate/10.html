Singleton — one instance, and why people distrust the global access

"What is the Singleton pattern, how do you make it thread-safe, and why is it often called an anti-pattern?"

Why it matters ▾
1️⃣ Singleton
❗ ProblemSome things should exist once, like configuration or a cache, but a hand-rolled global Instance hides who depends on it, can be created twice by racing threads, and cannot be swapped for a fake in tests.
✅ SolutionSingleton guarantees one instance with one access point; make it thread-safe with Lazy<T>, and prefer letting the DI container own a single instance instead of reaching for a global.
RecallOne instance. Thread-safe with Lazy. Prefer DI.
🔥 Easy interview recall

Singleton = "one instance, one global access point."

Think: Thread-safe → Lazy<T> or a static initializer Anti-pattern → hidden dependency, hard to test Better → AddSingleton in the DI container

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A static Instance with a null check is not thread-safe. if (_instance == null) _instance = new Foo(); can run twice when two threads arrive together and create two objects; use Lazy<T> or a static initializer.

🔄 Likely Follow-up

"So is a singleton always bad?" No. One shared instance is often right, like configuration or a cache. The trouble is the hand-rolled global access. Let the DI container manage the single instance with AddSingleton, and the code still receives it through its constructor.

🎯 Say this in the interview — the exact lines to land

"Singleton means one instance of a class with a global access point. In C# I make it thread-safe with Lazy<T> or a static initializer, not a bare null check. It's often called an anti-pattern because the global access hides dependencies and makes tests hard, so I prefer registering the class as a singleton in the DI container and injecting it."

  • Singleton → one instance, one global access point.
  • Thread-safe → Lazy<T> or a static initializer, not an unguarded null check.
  • Anti-pattern → hidden dependency: the constructor doesn't show that the class needs it.
  • Tests → shared state leaks between tests and can't be swapped for a fake.
  • Better → services.AddSingleton<IFoo, Foo>(): same one-instance lifetime, still injectable.
  • A shared singleton's own state must be thread-safe, because many requests use it at once.
📖 Explanation ▾

A Singleton has a private constructor and a static property that returns the one shared object. Two parts of the idea are worth separating: one instance (often fine) and global access (the risky part). Anyone can call AppConfig.Instance from anywhere, so a class can quietly depend on it without saying so.

In C#, make creation thread-safe with Lazy<T>, which is thread-safe by default, or with a static field initializer, which the runtime runs once. A plain if (_instance == null) check can create two objects when two threads race.

The criticism is hidden coupling and test pain: the dependency isn't in the constructor, and the state lives for the whole process. The usual fix keeps the benefit and drops the global: register it with AddSingleton and take it as a constructor parameter, as in Dependency Inversion and Factory vs. Dependency Injection. A DI singleton is one instance per container, and because it is shared, its own state must be thread-safe.

💻 See the code ▾
C# 
public sealed class AppConfig
{
    private static readonly Lazy<AppConfig> _lazy =
        new Lazy<AppConfig>(() => new AppConfig());   // thread-safe, created on first use

    public static AppConfig Instance => _lazy.Value;  // the one global access point

    private AppConfig() { }                           // nobody else can call new
}

Classic singleton — Lazy<T> makes creation thread-safe, and the private constructor blocks extra instances.

C# 
services.AddSingleton<IAppConfig, AppConfig>();   // the container keeps one instance

public class ReportService
{
    private readonly IAppConfig _config;

    public ReportService(IAppConfig config)           // ✅ dependency is visible
        => _config = config;
}

DI singleton — still one instance, but now it is passed in, so it is visible and can be replaced in tests.

🌍 Real-world example ▾

One shared office printer. Having a single printer is fine. The trouble is when every team's code secretly walks to that exact printer: nobody can see the dependency, and you can't point them at a different one for a test. Having the office manager hand each team a link to it is the DI version.
