Don't rewrite the monolith — strangle it one seam at a time

"You're asked to break a monolith into microservices — what's your actual approach?"

Why it matters ▾
🧩 Monolith → Microservices
❗ ProblemA big-bang rewrite stops feature work for months, and you only find out whether it actually works the day you flip the switch on the whole system at once.
✅ SolutionExtract one bounded seam at a time behind a facade (the strangler fig pattern) — the monolith keeps running the whole time, and each extraction is small enough to prove on its own.
RecallStrangler fig = route new traffic to the new service, let the monolith shrink over time.
🔥 Easy interview recall

Step 1 → find the seams — bounded contexts by business capability

Step 2 → extract the least-coupled one first, route new traffic to it

Step 3 → give it its own database once reads/writes are separated, then repeat

Think: big-bang rewrite = high risk, all-or-nothing. strangler fig = the monolith shrinks safely, one proven seam at a time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Extracting a service but leaving it on the monolith's own database. That's a distributed monolith, not microservices — you now pay network latency AND still have the same shared-schema coupling, which can be worse than the monolith alone.

🔄 Likely Follow-up

"How do you handle a transaction that used to be a single DB transaction across two now-separate services?" Use the Saga pattern — break it into a sequence of local transactions, each with a compensating action to undo it if a later step fails, since one ACID transaction can no longer span two independent databases.

🎯 Say this in the interview — the exact lines to land

"I wouldn't rewrite it from scratch. I'd find the bounded contexts along business capabilities, extract the least-coupled, highest-value one first using the strangler fig pattern — routing new traffic to it while the monolith still serves everything else — give it its own data store once reads and writes are cleanly separated, and repeat. The monolith shrinks incrementally instead of disappearing in one risky cutover."

  • Seams → bounded contexts by business capability, not by technical layer.
  • First extraction → least-coupled, highest-value service — prove the pattern cheaply.
  • Strangler fig → route new traffic to the new service, old traffic stays on the monolith.
  • Data → never share a database between the monolith and the new service — that's a distributed monolith.
  • Per extraction → its own pipeline, logging, and a clear API contract back to the monolith.
📖 Explanation ▾

Start by finding the seams — the boundaries between business capabilities (orders, billing, shipping), not technical layers (UI, business logic, data access). Those capability boundaries are where a service can genuinely stand on its own.

Pick the seam that's least coupled to the rest of the system and has real value extracted on its own, then apply the strangler fig pattern: put a facade or gateway in front of the monolith, route only the traffic for that one capability to the new service, and leave everything else going to the monolith unchanged. The new service only gets its own database once its reads and writes are cleanly separated from the monolith's schema — sharing a database with the monolith defeats the point of extracting it at all.

Repeat this one seam at a time. The monolith shrinks over months or years instead of being rewritten in one risky event, and each extraction needs its own deployment pipeline, its own logging, and a clear API contract back to whatever still depends on it in the monolith.

💻 See the code ▾
C# 
// Reverse-proxy style routing in front of the monolith (YARP)
// ❌ Everything still hits the monolith — no seam extracted yet
app.MapReverseProxy();

// ✅ Route one capability's new traffic to the extracted service,
//    leave every other route pointing at the monolith
app.MapForwarder("/api/orders/{**catch-all}", "https://orders-service");
app.MapForwarder("/{**catch-all}", "https://legacy-monolith");

The facade decides by route which requests go to the new service and which still go to the monolith — that's the whole strangler fig mechanism.

🧭 Use Cases — recognize these when they happen to you ▾
1 Leadership wants "microservices" and proposes a full rewrite

A full rewrite risks months of frozen feature work with one big cutover. Extracting one seam at a time proves the approach early and keeps the monolith shippable.

RememberIncremental extraction beats a big-bang rewrite.
2 The team extracts a service but it still reads the monolith's tables directly

Sharing the monolith's schema means a column rename on either side can silently break the other — that coupling never went away, it just hid behind a network call.

RememberA shared database makes it a distributed monolith, not a microservice.
3 An order now has to update two separate services' data consistently

With two independent databases, use a Saga: a sequence of local transactions, each with a compensating action to undo it if a later step fails.

RememberCross-service transaction → Saga, not a distributed DB transaction.
🌍 Real-world example ▾

An e-commerce monolith's checkout is the slowest, most-changed part of the system. Instead of rewriting the whole app, the team puts a gateway in front of it, extracts checkout into its own service with its own database, and routes only checkout traffic there. Everything else — catalog, reviews, admin — keeps running in the monolith, which now shrinks by exactly the part that was causing the most pain.
