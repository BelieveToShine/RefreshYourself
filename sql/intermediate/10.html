SARGable — the difference between using an index and ignoring it

What makes a query SARGable, and what breaks it?

Why it matters ▾
  • Wrapping an indexed column in a function or an implicit conversion is one of the most common, easy-to-miss performance killers in real codebases — it compiles fine and looks harmless in a code review.
  • Interviewers use it to check whether you understand indexing operationally, not just "add an index and queries get faster."
  • A frequent follow-up right after any indexing question, and a common root cause behind "this query used to be fast" investigations.
🔥 Easy interview recall

SARGable = "the engine can seek straight to matching rows using the index, without touching every row."

Think: wrap the column in a function, and the index usually can't help anymore.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Wrapping a column in a function only slows things down a little. Wrapping an indexed column in a function (or an implicit type conversion) commonly defeats the index entirely for that predicate, forcing a full scan of every row in the table — it's not a minor slowdown, it can be a fundamentally different, much slower plan.

🔄 Likely Follow-up

"How would you fix WHERE YEAR(OrderDate) = 2024 to stay SARGable?" Rewrite it as a range — WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01' — same logical result, but the column itself is left untouched, so the index can still be used to seek directly to that range.

🎯 Say this in the interview — the exact lines to land

"SARGable means the predicate is written so the engine can seek directly to matching rows using the index. Wrapping the indexed column in a function or letting an implicit type conversion sneak in commonly defeats that seek entirely, forcing a full scan instead — the fix is almost always rewriting it as a range on the bare column."

  • SARGable → engine seeks directly to matching rows via the index.
  • Wrapping the column in a function → defeats the index for that predicate, not just a minor slowdown.
  • WHERE YEAR(OrderDate) = 2024 → not SARGable — the column itself is wrapped.
  • Rewrite as a range (>= ... AND ... <) → SARGable again, same result, column left untouched.
  • Same rule applies to → implicit type conversions, not just explicit functions.
📖 Explanation ▾

"SARGable" stands for Search ARGument-able — a predicate is SARGable when it's written so the engine can seek directly to the matching rows using an index, instead of pulling every row and computing something on each one just to check the condition. It's the same index structure covered on the Clustered vs. Non-Clustered Index page — SARGable is really asking whether a given predicate can actually use that structure.

Wrapping the indexed column itself in a function (YEAR(), UPPER(), a calculation) or letting an implicit type conversion sneak in commonly defeats the index for that predicate entirely. This isn't a minor slowdown — the engine can no longer look up "where does this column's value fall in the index," so it can end up with a fundamentally different plan for the whole query, typically scanning every row instead of seeking straight to a range.

The fix is almost always the same shape: leave the column bare and move the transformation to the other side of the comparison. WHERE YEAR(OrderDate) = 2024 becomes WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01' — the same rows come back, but now the column itself is untouched, so the index can seek straight to that range.

💻 See the code ▾
SQL 
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;   -- ❌ column wrapped in a function — forces a full table scan

The column itself is wrapped in a function, so the engine can't seek using the index — it scans every row to evaluate YEAR() on each one.

SQL 
SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01'
  AND OrderDate < '2025-01-01';   -- ✅ same result, index-seekable

Same logical result, but the column itself is left untouched — the engine can seek directly to this date range using the index.

🌍 Real-world example ▾

Looking up a word in a paper dictionary works instantly because it's alphabetically sorted. Asking "find every word whose reversed spelling starts with 'a'" makes that same sorted order useless — you'd have to check every single word by hand. Wrapping a column in a function does the same thing to a sorted index: the sort order is still there, it just doesn't line up with the question you're asking anymore.
