Hashability is what actually decides what can be a dict key — not "is it simple"

"What can be used as a dictionary key? Why can't a list?"

Why it matters ▾
  • Explains the exact TypeError: unhashable type almost everyone hits the first time they try a list or dict as a key.
  • Directly relevant to caching/memoizing a function's results by its arguments — the arguments have to be hashable first.
  • A common opener for Python fundamentals — it tests real understanding of the object model, not memorized syntax.
🔥 Easy interview recall

Hashable → immutable, can be a dict key

Unhashable → mutable, can't be a dict key

Think: list is out, tuple is in — swap the brackets for parentheses and it's hashable.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Getting TypeError: unhashable type: 'list' doesn't mean any type will fix it. The real fix is usually a tuple — if the contents are meant to stay fixed — not casting to whatever type happens to make the error disappear.

🔄 Likely Follow-up

"When would you reach for IntEnum vs. plain Enum?" Reach for IntEnum when the members genuinely need to compare or interoperate with plain ints — e.g. matching a legacy status-code integer; use plain Enum when you want strict type safety and don't want accidental int comparisons to silently succeed.

🎯 Say this in the interview — the exact lines to land

"Hashable means immutable, essentially — that's the real rule behind what can be a dict key. Numbers, strings, tuples of hashable items, and frozensets are hashable; lists, dicts, and sets are mutable, so they can't be."

  • Hashable → its hash never changes over the object's lifetime, so it's safe as a dict key or set member.
  • Mutable types → list/dict/set can't be hashed — their contents can change, which would break the hash table storing them.
  • Fix → convert to a tuple when the contents are meant to stay fixed, not to "whatever type removes the error."
  • Enum → strict type safety, no accidental int comparisons. IntEnum → members compare and interoperate with plain ints.
📖 Explanation ▾

Python's built-in types split into numeric types (int, float, complex), str, bool, None, and the containers list, tuple, set, and dict. Hashability is the property that actually decides dict-key/set-member eligibility: a hashable object has a __hash__ that returns the same value for as long as that object exists.

Immutable built-ins — int, str, tuple (as long as everything inside it is also hashable), frozenset, bool — are hashable, because their value can't change after creation. Mutable built-ins — list, dict, set — are not: if their contents changed after being used as a key, their hash would change too, and that would silently corrupt the hash table they're stored in.

enum.Enum defines a class of named constant members — comparable and iterable, and more expressive and type-safe than a bare string or int constant. IntEnum is the same idea, except its members also behave like plain ints and compare directly to them. Reach for an enum whenever there's a genuinely fixed, small set of named options.

💻 See the code ▾
Python 
❌ Raises: TypeError: unhashable type: 'list'
d = {[1, 2]: "x"}

A list is mutable, so Python refuses it as a dict key — it has no stable hash to store it by.

Python 
✅ Works — a tuple is immutable, so it's hashable
d = {(1, 2): "x"}

Same values, different container — swapping brackets for parentheses is the actual fix, not casting to an unrelated type.

Python 
from enum import Enum, IntEnum

class Status(Enum):        # plain Enum
    ACTIVE = 1

class Priority(IntEnum):   # behaves like an int too
    HIGH = 1

Priority.HIGH == 1   # ✅ True — IntEnum compares to plain ints
Status.ACTIVE == 1   # ❌ False — Enum does not

IntEnum members compare directly to plain ints; a plain Enum member doesn't — that's the type-safety trade-off.

🌍 Real-world example ▾

A function caches its results keyed by its own arguments, so repeated calls with the same input skip the expensive work. That cache key has to be hashable — so if one of the arguments is naturally a list (say, a list of IDs), it has to be converted to a tuple before it can be used as (or inside) the cache key.
