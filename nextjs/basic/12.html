Env variables — one prefix away from shipping a secret to the browser

"What's the difference between a regular env variable and one prefixed NEXT_PUBLIC_?"

Why it matters ▾
🔑 Environment variables
❗ ProblemA server needs secrets (database passwords, API keys) available to its code, but the exact same code sometimes also needs to run in the browser — where any secret would be visible to anyone who opens devtools.
✅ SolutionEvery .env.local variable is server-only by default. Only a variable explicitly prefixed NEXT_PUBLIC_ gets inlined into the client bundle at build time — an opt-in, not an accident.
RecallNo prefix = server only. NEXT_PUBLIC_ = ships to the browser.
🔥 Easy interview recall

Plain var → server only, never shipped

NEXT_PUBLIC_ → inlined into the browser bundle

Think: NEXT_PUBLIC_ happens at build time, not request time — changing one after deploy needs a rebuild.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Prefixing a secret — an API key, a database credential — with NEXT_PUBLIC_. That deliberately ships it into the public client bundle, visible to anyone who opens devtools; only genuinely public values, like a public analytics ID, should ever get that prefix.

🔄 Likely Follow-up

"Why 'build time' specifically for the public prefix, not request time?" NEXT_PUBLIC_ values get statically inlined into the JS bundle during the build — changing one after deployment requires a rebuild, unlike a server-only env var, which is read fresh at runtime.

🎯 Say this in the interview — the exact lines to land

"Variables in .env.local are server-only by default — available in Server Components, Route Handlers, Server Actions, but never sent to the browser. Only a variable explicitly prefixed NEXT_PUBLIC_ gets inlined into the client bundle at build time, and it's then visible in browser devtools."

  • No prefix → server-only, safe for secrets.
  • NEXT_PUBLIC_ → inlined into the client bundle at build time, visible to anyone.
  • Only genuinely public values → get the NEXT_PUBLIC_ prefix, never a credential.
📖 Explanation ▾

Everything in .env.local is loaded into process.env on the server — available to Server Components, Route Handlers, and Server Actions — but none of it is sent to the browser unless you say otherwise. That's the safe default: a database password sitting in .env.local never leaves the server.

Prefixing a variable with NEXT_PUBLIC_ changes that: at build time, Next.js finds every reference to a NEXT_PUBLIC_ variable in your code and replaces it with its literal value, baked directly into the JavaScript bundle that ships to the browser. From that point on, it's just a string sitting in your client-side code — visible in devtools, in the page source, everywhere.

Because the substitution happens at build time, not when a request comes in, changing a NEXT_PUBLIC_ value after deployment has no effect until the app is rebuilt and redeployed — a server-only variable, by contrast, is read fresh from the environment every time the server code runs.

💻 See the code ▾
Shell 
# .env.local
DB_PASSWORD=sup3rSecret            // ✅ server-only, never shipped
NEXT_PUBLIC_API_URL=https://api.example.com   // visible in the browser

Same file — the prefix alone decides which side of the boundary a value ends up on.

JSX 
// a Client Component
fetch(process.env.NEXT_PUBLIC_API_URL);     // ✅ works — inlined at build time
fetch(process.env.DB_PASSWORD);             // ❌ undefined in the browser

The non-prefixed variable simply isn't there once the code runs client-side.

🧭 Use Cases — recognize these when they happen to you ▾
1 A Server Component or Route Handler needs a database connection string

This code only ever runs on the server, so the variable just stays unprefixed — it's already reachable exactly where it needs to be. This is the #1 scenario you'll actually run into.

RememberServer-only code → no prefix, nothing extra to do.
2 A Client Component needs to know which API base URL to call

A base URL isn't a secret — it's fine for anyone to see it. Prefixing it NEXT_PUBLIC_ is exactly the intended use of the prefix.

RememberNon-secret value the browser needs → NEXT_PUBLIC_ prefix.
3 Someone renames STRIPE_SECRET_KEY to NEXT_PUBLIC_STRIPE_SECRET_KEY "to fix" a Client Component error

The real fix is to move the code that needs the secret key to the server (a Server Action or Route Handler) — adding the prefix "fixes" the error by publishing the credential to every visitor's browser instead.

RememberA secret failing in client code → move the code server-side, never add the prefix.
🌍 Real-world example ▾

It's a backstage pass versus a poster on the wall. A server-only variable is the backstage pass — only staff (server code) ever see it. A NEXT_PUBLIC_ variable is the poster — printed and hung up (built into the bundle) for every visitor to read.
