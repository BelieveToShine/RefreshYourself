⭐ Azure · Intermediate · Should Know

Copy it to another region, put one listener in front

"How do you make Azure SQL survive a regional outage, and when would you use an elastic pool?"

Why it matters ▾
🌍 Active geo-replication
❗ ProblemBuilt-in high availability protects against a failure inside a region, but if the whole region goes down, a single database has nowhere else to run.
✅ SolutionGeo-replication keeps a readable secondary copy in another region, continuously updated, that you can fail over to.
RecallGeo-replication = a readable copy in another region.
🔗 Failover group
❗ ProblemWith plain geo-replication each database fails over separately and apps must switch connection strings by hand mid-incident.
✅ SolutionA failover group fails over a set of databases together and gives you listener endpoints whose names stay the same, so the app does not change.
RecallFailover group = group failover + one stable endpoint.
🏊 Elastic pool
❗ ProblemMany small databases with different busy times each sized for their own peak waste money, since most sit idle most of the time.
✅ SolutionAn elastic pool lets them share one set of resources, so one database's busy hour uses what the quiet ones are not.
RecallPool = shared budget for many small, uneven databases.
🔥 Easy interview recall

In-region failure → built-in HA covers it

Region outage → geo-replica / failover group

Apps keep one name → failover group listener

Many small DBs → elastic pool

Think: copy it across regions, front it with a listener, pool the small ones.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Geo-replication means zero data loss." The copy to the other region is asynchronous, so a failover after a real outage can lose the most recent writes — your recovery point is not zero. Quote RPO and RTO as targets you would check in the current docs, not as promises.

🔄 Likely Follow-up

"Automatic or manual failover?" A failover group can be set to automatic, with a grace period before it fires, or to manual. Automatic is faster to recover, but a short blip could trigger a failover you did not want, so many teams keep control and test the failover regularly.

🎯 Say this in the interview — the exact lines to land

"Built-in high availability handles failures inside a region. For a regional outage I would use a failover group — geo-replicated databases with a listener endpoint that stays the same after failover. An elastic pool is a different tool, for many small databases that share resources."

  • In-region HA → built in, zone-redundant options on supported tiers.
  • Geo-replication → readable secondary in another region.
  • Failover group → one listener that survives the failover.
  • Replication is async → RPO is not zero, so recent writes can be lost.
  • Elastic pool → cost sharing, not a disaster-recovery feature.
📖 Explanation ▾

Azure SQL already keeps your database highly available inside a region, and some tiers can spread copies across availability zones. That does not help if the whole region is lost, so you add a second region on purpose. Active geo-replication keeps a readable secondary copy of a database in another region; you fail it over yourself when you need to.

A failover group builds on that for a set of databases on a pair of servers. It fails them over together and exposes listener endpoints (read-write, and optionally read-only) that keep the same name after a failover, so the app's connection string does not change. Because replication is asynchronous, a forced failover can lose the latest writes; check the current docs for the RPO and RTO to expect.

An elastic pool is about cost, not resilience: many small databases with busy times at different hours share one pool of resources instead of each being sized for its own peak. It suits many tenants with uneven load, not one big steady database.

💻 See the code ▾
Azure CLI 
# group two servers so the listener name survives a failover
az sql failover-group create --name orders-fg --resource-group rg-data --server sql-eastus --partner-server sql-westus --add-db ordersdb --failover-policy Automatic

Apps connect to the failover group's listener name, not to either server, so the connection string stays the same after a failover. Server names here are made up for the example.

🌍 Real-world example ▾

A SaaS vendor hosts hundreds of small tenant databases in an elastic pool so quiet tenants fund the busy ones, and puts the pool's important databases in a failover group so one region outage does not take every customer down.
