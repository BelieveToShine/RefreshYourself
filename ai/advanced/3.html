"It looks good" isn't evaluation — what actually belongs in an eval set?

What would you put in an eval set for an LLM feature, and how would you score a RAG answer specifically?

Why it matters ▾
🧪 What's Actually In An Eval Set
❗ ProblemA handful of examples you eyeballed doesn't tell you how a prompt behaves across the real input space — and for a RAG feature, "the answer sounds right" doesn't tell you whether it's actually grounded in what was retrieved.
✅ SolutionBuild an eval set — common, edge, and known-hard cases, each with a known answer or rubric — and for RAG, score more than the final answer: faithfulness, answer relevancy, context precision, and context recall.
RecallEval set = a representative, labeled set of cases; for RAG, score retrieval quality and groundedness too, not just "did it answer."
🔥 Easy interview recall

Eval set → a fixed, representative set of real cases, not a vibe check

RAG metrics → faithfulness, answer relevancy, context precision, context recall

Think: an eval set is a structured test suite for a prompt — and for RAG, it scores the retrieval step, not just the final answer.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Scoring only "did it answer" and stopping there. A RAG system can give a fluent, confident-sounding answer built on the wrong retrieved chunks — a generation-only check won't catch that; only a faithfulness or context-precision score will.

🔄 Likely Follow-up

"How do you score a case when there's no single correct wording?" Use a grading rubric and an LLM-as-judge instead of exact-match — the judge checks whether the answer satisfies the rubric's criteria (grounded, on-topic, no hallucinated specifics), not whether it matches one fixed string. Once the eval set exists, it also becomes the baseline a change gets checked against before shipping — see Regression Testing Prompts.

🎯 Say this in the interview — the exact lines to land

"I'd build a representative eval set — common cases, edge cases, known-hard cases, and past regressions — each with a known correct answer or a clear rubric. For a RAG feature specifically, I'd score more than just the final answer: faithfulness and answer relevancy on the generation side, context precision and context recall on the retrieval side."

  • Eval set → sampled from real, representative usage, not just cases the developer happened to think of.
  • Known answer or rubric → every case needs one or the other, otherwise scoring it is just as subjective as eyeballing a single example.
  • Faithfulness / groundedness → does the answer stay consistent with the retrieved context, with no unsupported claims added.
  • Answer relevancy → does the answer actually address the question that was asked, independent of whether it's grounded.
  • Context precision → of the chunks retrieved, how many were actually relevant Context recall → of the relevant chunks that exist, how many retrieval actually found
📖 Explanation ▾

An eval set is a curated collection of realistic input cases — the common ones, the edge cases, and the ones already known to be hard — each paired with either a known correct answer or a clear rubric for judging the response. It's built by sampling real, representative usage, not just cases a developer happened to think of, and it deliberately includes past problem cases (regression cases) so a known failure mode is still being watched for, not just the cases that are easy to think up.

For a RAG feature specifically, a good eval set scores more than "did it answer." Faithfulness (or groundedness) checks whether the generated answer actually stays consistent with what the retrieved context said, without adding claims the context doesn't support. Answer relevancy checks whether the answer actually addresses the question that was asked. Context precision and context recall score retrieval itself — precision is how many of the retrieved chunks were actually relevant, recall is how many of the truly relevant chunks that exist were actually found.

Where do the cases actually come from? In practice: real traffic logs, support tickets, and anything a teammate had to hand-fix before. A case without a known answer or a grading rubric isn't usable yet — if there's no single correct wording, score it with a rubric and an LLM-as-judge instead of exact-match (see LLM-as-Judge). Once this set exists, it becomes the fixed baseline every future prompt or model change gets checked against — that mechanics (candidate vs. baseline, blocking a regression, automating it in CI) is its own topic: see Regression Testing Prompts.

💻 See the code ▾
Eval case 
{
  "id": "case_014",
  "category": "regression",  // common | edge | known-hard | regression
  "input": "What's the refund window for a damaged item?",
  "expected": "Rubric: cites the 30-day damaged-item policy, no invented dates"
}

Each case is a realistic input plus either the exact right answer or a rubric — this is what makes "looks good" testable instead of a feeling.

RAG metrics 
# faithfulness: is every claim in the answer supported by the retrieved context?
faithfulness = supported_claims / total_claims_in_answer

# context precision: of what was retrieved, how much was actually relevant?
context_precision = relevant_retrieved_chunks / total_retrieved_chunks

# context recall: of what's actually relevant, how much did retrieval find?
context_recall = relevant_retrieved_chunks / total_relevant_chunks_that_exist

A RAG answer can read perfectly and still fail here — fluent wording says nothing about whether it's grounded in the right chunks, which is exactly what these three numbers check instead.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're starting a new RAG feature and there's no eval set yet

Sample real queries and support tickets, sort them into common, edge, and known-hard, and write a known answer or rubric for each before scoring anything — without that label, "did it pass" is just an opinion.

RememberNo case counts until it has a known answer or a rubric attached.
2 A RAG answer reads fluently and confidently — but cites an outdated policy

A generation-only check ("did it answer, does it read well") will pass this case. Only scoring faithfulness (is the claim actually supported by what was retrieved) and context precision (was the retrieved chunk even relevant) exposes that the answer was built on the wrong context.

RememberFluent ≠ grounded — score retrieval, not just the final answer's tone.
3 Your eval set is a dozen cases — and every one of them is an easy, common case

A set with no edge cases and no known-hard cases scores well for the wrong reason — it was never going to catch anything, because nothing in it was hard to get right in the first place.

RememberAn eval set that's all easy cases isn't representative — it's a false sense of safety.
🌍 Real-world example ▾

A support RAG bot gets asked about a return policy. It retrieves a chunk from last year's policy doc — now outdated — and generates a fluent, confident answer citing a 14-day window that no longer applies. A rubric checking "did it answer the question" passes this case outright. Only computing faithfulness (is the claim actually supported by the retrieved chunk) and context precision (was the retrieved chunk even the current, relevant one) catches it — which is exactly why a RAG eval set needs retrieval-specific metrics, not just an answer-quality rubric.
