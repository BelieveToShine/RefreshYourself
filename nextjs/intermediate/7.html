Route Handlers — named exports replace the method if-chain

"How does defining an API endpoint differ between the App Router and the Pages Router?"

Why it matters ▾
🧩 Route Handlers
❗ ProblemA Pages Router API file exports one default function for the whole endpoint, so every HTTP method it supports has to be handled by branching on req.method inside that one function — easy to get the branching wrong or forget a method.
✅ SolutionA route.js file exports a separate named function per HTTP method (GET, POST, …) — Next.js calls the matching one directly, so there's no manual method branching at all.
Recallroute.js = one named function per HTTP method, no if-chain.
🔥 Easy interview recall

pages/api/x.js → one default export, branches on method

app/api/x/route.js → named exports, one per method

Think: GET(), POST() — the function name is the routing.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A route.js file can't export a single default handler the way Pages API Routes did. Route Handlers require named exports matching HTTP methods (export async function GET(){...}) — a default export is simply never called.

🔄 Likely Follow-up

"Can a Route Handler and a page.js coexist in the same folder?" No — a route segment can have either a page.js or a route.js, not both; they're mutually exclusive ways of resolving that URL.

🎯 Say this in the interview — the exact lines to land

"In the App Router, a route.js file exports named functions per HTTP method — GET, POST, and so on — directly. The Pages Router instead exported one default function from pages/api/x.js that branched internally on req.method."

  • route.js → named exports per method, no branching.
  • pages/api/*.js → one default export, branches on req.method.
  • GET handlers → cacheable by default, unlike Pages API Routes (always dynamic).
📖 Explanation ▾

A Pages API Route (pages/api/x.js) exports a single default function that receives req/res for every HTTP method hitting that URL — handling more than one method means checking req.method yourself and branching inside that one function.

A Route Handler (app/api/x/route.js) instead exports a separate named function per method — GET, POST, PUT, DELETE, and so on. Next.js calls whichever one matches the incoming request directly; there's no method check to write yourself.

One more real difference, not just a syntax change: a Route Handler's GET function is cacheable by default when it isn't reading request-specific data — closer to how a static page behaves. Pages API Routes were always treated as dynamic, with no equivalent caching behavior.

💻 See the code ▾
Next.js 
// pages/api/todos.js — Pages Router
export default function handler(req, res) {
  if (req.method === 'GET') {
    return res.json(getTodos());
  } else if (req.method === 'POST') {
    return res.json(createTodo(req.body));
  }
  res.status(405).end();   // manual fallback for unhandled methods
}

One function, responsible for every method itself.

Next.js 
// app/api/todos/route.js — App Router, same two methods
export async function GET() {
  return Response.json(getTodos());   // ✅ called only for GET
}

export async function POST(request) {
  const body = await request.json();
  return Response.json(createTodo(body));   // ✅ called only for POST
}

No method check anywhere — the function name is the dispatch.

🧭 Use Cases — recognize these when they happen to you ▾
1 A REST-style resource that supports GET, POST, and DELETE

A resource endpoint needing multiple methods just adds another named export to the same route.js — each method stays in its own clearly separated function instead of one growing if/else chain.

RememberMultiple methods → multiple named exports, same file.
2 A read-only endpoint that should be cached like static data

A GET Route Handler that doesn't read request-specific data can be cached the same way a static route can — something a Pages API Route, always treated as dynamic, never offered.

RememberPlain GET, no request data read → can be cached.
3 You export default from a route.js out of Pages Router habit

Next.js only looks for the named HTTP-method exports in a route.js — a default export is never invoked, so every request to that route 404s even though the file compiles and a function is clearly exported.

Rememberroute.js needs named method exports — default export is dead code.
🌍 Real-world example ▾

A webhook endpoint that only ever needs to handle POST. app/api/webhook/route.js exports a single POST function — no method check, no default export, no risk of a stray GET request accidentally running the webhook's processing logic.
