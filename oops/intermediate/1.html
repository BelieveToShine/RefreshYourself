interface vs. abstract class — "can do" or "is a"?

What's the real difference between an interface and an abstract class, and how do you decide which one to use?

Why it matters ▾
🔌 Interface
❗ ProblemOrder, PaymentGateway, and UserSession need the exact same one capability (logging) but have nothing in common as types — forcing them under one shared base class just to reuse Log() would invent a fake "is-a" relationship.
✅ SolutionAn interface defines only the Log() contract; any unrelated class can implement it on its own, with zero shared implementation forced on any of them.
Recallinterface = can-do contract, any unrelated class can implement it.
🎭 Abstract Class
❗ ProblemA base like RepositoryBase<T> needs to share real implementation (the Save() plumbing) across its subclasses, but a plain concrete class can't also force every subclass to still supply its own required piece (GetById()).
✅ SolutionAn abstract class implements the shared members itself and leaves the rest abstract, so every type in that one lineage inherits the shared code while still being forced to finish its own piece.
Recallabstract class = shared lineage + shared implementation, single inheritance.
🔥 Easy interview recall

abstract class → is-a, one shared lineage

interface → can-do, any unrelated class

Think: abstract class is a family tree. interface is a skill any class can pick up.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An abstract class that implements an interface must finish every member itself. It doesn't — it can implement some members and leave the rest abstract for its own subclasses to finish, e.g. abstract class RepositoryBase<T> : IRepository<T> implementing the shared CRUD plumbing but leaving one method abstract for each concrete repository.

🔄 Likely Follow-up

"Can a class inherit an abstract class AND implement multiple interfaces at the same time?" Yes — that combination is exactly the point: one shared base for common state and behavior, plus as many interface contracts as the type actually needs.

🎯 Say this in the interview — the exact lines to land

"An abstract class models 'these types ARE the same kind of thing' — one shared lineage and shared implementation, single inheritance. An interface models 'these types CAN do the same thing' — any number of unrelated classes can implement it, with no shared code forced on any of them."

  • abstract class → use it when types share real lineage and implementation, like Shape → Circle.
  • interface → use it when unrelated classes just need the same capability, like ILoggable across Order, PaymentGateway, UserSession.
  • Pitfall → an abstract class CAN implement an interface, and can leave some members abstract for subclasses to finish.
  • Combine both → one base class plus many interfaces is exactly how C# is designed to be used.
📖 Explanation ▾

The real difference isn't the constructor rule — abstract class can have one, interface can't — that's a surface detail. The real difference is the relationship each one expresses. An abstract class says "these types ARE fundamentally the same kind of thing": one shared lineage, one set of shared implementation, single inheritance. An interface says "these types CAN do the same thing," no matter how unrelated they otherwise are: as many interfaces as needed, with no shared implementation forced on anyone.

Order, PaymentGateway, and UserSession have nothing in common in a class-hierarchy sense — nothing about a payment gateway is fundamentally the same kind of thing as an order. Forcing all three under one shared LoggableBase abstract class just to reuse a Log() method would be an artificial, wrong "is-a" relationship. ILoggable lets each implement Log() independently while still being usable polymorphically wherever "a loggable thing" is expected.

That's also why an abstract class implementing an interface isn't a contradiction. It can implement some interface members with real shared logic and leave the rest abstract — a common real pattern is a base repository that implements the shared CRUD plumbing and leaves one method abstract for each concrete repository to finish.

💻 See the code ▾
C# 
public interface ILoggable
{
    void Log(string message);
}

public class Order : ILoggable
{
    public void Log(string m) => Console.WriteLine($"[Order] {m}");
}

public class PaymentGateway : ILoggable
{
    public void Log(string m) => Console.WriteLine($"[Payment] {m}");
}   // ✅ unrelated classes, same capability — no shared base needed

Order and PaymentGateway share nothing else — ILoggable is the only thing they have in common.

C# 
public abstract class RepositoryBase<T> : IRepository<T>
{
    public void Save(T item) { /* shared plumbing */ }   // ✅ implemented here
    public abstract T GetById(int id);                     // ✅ left abstract on purpose
}

An abstract class can implement an interface — and doesn't have to finish every member itself.

C# 
public class InvoiceService : ServiceBase, ILoggable, IDisposable
{
    // one shared base (ServiceBase) + two interface contracts
}

One abstract base for shared state, plus as many interfaces as the type actually needs.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your types genuinely share lineage and some real implementation

Reach for an abstract class. Circle IS a Shape, so it inherits Shape's shared implementation through one lineage — exactly what the diagram above shows on the left.

RememberReal lineage + shared code → abstract class.
2 Unrelated classes just need one shared capability

Reach for an interface. Order and PaymentGateway have nothing in common architecturally, so a shared ILoggable contract is the only thing they need to have in common. This is the #1 scenario you'll actually run into.

RememberUnrelated types + one capability → interface.
3 A type needs one shared base AND several unrelated capabilities at once

Reach for both together — that's exactly the point, not a contradiction. InvoiceService : ServiceBase, ILoggable, IDisposable gets one shared base for common state (solid line) plus as many interface contracts as it needs (dashed lines).

RememberOne base class + many interfaces is the normal, designed-for combination.
🌍 Real-world example ▾

Your codebase has Order, PaymentGateway, and UserSession — three types with nothing in common architecturally, but all three need to write structured logs. Forcing them under a shared LoggableBase abstract class would invent a fake "is-a" relationship just to reuse one method. Giving each a small ILoggable interface instead leaves their real class hierarchies untouched, and any code that receives an ILoggable can log all three the exact same way.
