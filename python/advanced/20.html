except* — take the errors you handle, let the rest keep travelling

"What is except* and why was ExceptionGroup added?"

Why it matters ▾
📦 ExceptionGroup
❗ ProblemA normal raise carries one exception, so when several concurrent tasks fail at once, all but one error would be lost.
✅ SolutionExceptionGroup bundles many errors into one exception, and except* handles the matching ones by type while the rest keep propagating.
RecallExceptionGroup = many errors in one exception.
🔥 Easy interview recall

except* = "take the errors I handle, leave the rest in the group."

Think: ExceptionGroup → many errors in one box except* T → takes the T errors, as a group leftovers → re-raised as a group

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

except ValueError will not catch a ValueError inside an ExceptionGroup. The group itself is not a ValueError — you need except*.

🔄 Likely Follow-up

"If I write two except* clauses, does only the first one run?" No — each clause takes its own matching errors, so both can run. Anything no clause matched is re-raised as a group.

🎯 Say this in the interview — the exact lines to land

"An ExceptionGroup carries several unrelated exceptions at once — it was added in Python 3.11 for cases like TaskGroup, where more than one task can fail. except* matches by type, handles the matching ones, and re-raises the rest as a group."

  • ExceptionGroup("msg", [e1, e2]) → bundles errors; read them from .exceptions.
  • except* T as eg → only the T errors; eg is always a group.
  • Several except* clauses can all run — plain except stops at the first match.
  • Unmatched errors → re-raised as a group after the handlers.
  • Plain except ValueError misses errors inside a group.
  • Can't mix except and except* in one try; no return, break or continue inside except*.
📖 Explanation ▾

A normal raise carries one exception. But concurrent code can fail in several places at once — three requests, three different errors. ExceptionGroup (Python 3.11+) solves this: ExceptionGroup("message", [err1, err2, ...]) is a single exception that contains other exceptions, available as .exceptions. TaskGroup raises one when its tasks fail. (BaseExceptionGroup is the version that can also hold exceptions like KeyboardInterrupt.)

except* is how you handle one. except* ValueError as eg: pulls out only the ValueErrors, and eg is itself a group holding just those. Every except* clause that matches something runs. Whatever nobody handled is re-raised as a group. Even a lone ordinary exception caught by except* arrives wrapped in a group, so write handlers that loop over eg.exceptions.

Rules to remember: a plain except ValueError misses a ValueError inside a group, because the group is not one. You can't mix except and except* in the same try, and return, break and continue aren't allowed inside an except* block. Outside a try, eg.split(T) and eg.subgroup(T) slice a group by type.

💻 See the code ▾
Python 
def run():
    raise ExceptionGroup("batch failed", [
        ValueError("bad id"),
        TypeError("bad type"),
        ValueError("bad date"),
    ])

try:
    run()
except* ValueError as eg:
    print("values:", [str(e) for e in eg.exceptions])
except* TypeError as eg:
    print("types:", [str(e) for e in eg.exceptions])

Prints values: ['bad id', 'bad date'] then types: ['bad type']. Both handlers ran, each on its own matching errors, and nothing was left over to re-raise.

Python 
try:
    try:
        raise ExceptionGroup("g", [ValueError("a"), KeyError("b")])
    except* ValueError:
        print("handled ValueError")
except ExceptionGroup as rest:
    print("left over:", repr(rest.exceptions[0]))

Prints handled ValueError then left over: KeyError('b'). The KeyError had no handler, so it was re-raised inside a new group.

🌍 Real-world example ▾

Five API calls run together in a TaskGroup; two time out and one returns a bad payload. except* TimeoutError retries the two, while the bad-payload error keeps travelling up to be logged.
