CancellationToken — asking nicely, not forcing a stop

"How does cooperative cancellation actually work in .NET?"

Why it matters ▾
🛑 Cooperative Cancellation
❗ ProblemForcibly killing a running thread from outside — what the now-obsolete Thread.Abort tried to do — can leave shared state, open resources, or a half-finished write in an unknown, unsafe condition.
✅ SolutionA CancellationToken only carries a request — .Cancel() sets a flag, and the running code itself checks that flag and decides when it's safe to stop.
RecallCancellation = a flag the operation has to check for itself, not a switch that stops it.
🔥 Easy interview recall

Cancellation = "a polite request, not a kill switch."

Think: the token can't stop anything by itself — the operation has to check it and stop itself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Passing a CancellationToken into a method isn't the same as making that method cancellable. If the method never checks IsCancellationRequested (or calls ThrowIfCancellationRequested()), calling .Cancel() does nothing — the operation runs to completion anyway.

🔄 Likely Follow-up

"What's the difference between checking IsCancellationRequested and calling ThrowIfCancellationRequested()?" Checking the flag lets you exit cleanly on your own terms — return, break a loop. ThrowIfCancellationRequested() throws an OperationCanceledException for you, the standard way a caller tells cancellation apart from a real failure.

🎯 Say this in the interview — the exact lines to land

"A CancellationTokenSource creates a CancellationToken and hands it to the operation. The operation has to cooperate — it periodically checks IsCancellationRequested and stops itself. Calling .Cancel() only sets a flag; nothing forces the operation to stop immediately."

  • A token can't force anything to stop — it only carries the request.
  • .Cancel() → sets a flag, it doesn't interrupt running code.
  • Cancellation is only noticed at the next check — could be milliseconds away, or never, depending on the loop.
  • A token accepted but never checked makes that method silently uncancellable.
📖 Explanation ▾

Cancellation in .NET is cooperative — there's no API that reaches into another thread and forcibly halts it (that's exactly what the now-obsolete Thread.Abort tried to do, and why it was dangerous). Instead, a CancellationTokenSource hands out a lightweight CancellationToken, and it's entirely up to the code holding that token to notice the request and stop itself.

Calling .Cancel() just flips a flag on the source — it never touches the call stack of the running operation. If that operation is deep in a loop and never looks at the token, .Cancel() returns instantly and the loop keeps running exactly as before, unaware anything happened.

💻 See the code ▾
C# 
using var cts = new CancellationTokenSource();
CancellationToken token = cts.Token;
cts.Cancel();   // just sets a flag — nothing is running yet

The source creates the token and later requests cancellation — it never touches the code that will use the token.

C# 
void DoWork(CancellationToken token)
{
    while (!token.IsCancellationRequested)  // checked every iteration
    {
        // ... do one small unit of work ...
    }
}                                          // ✅ exits cleanly, on its own terms

The loop only stops because it chooses to check — nothing external interrupts it mid-iteration.

C# 
void DoWork(CancellationToken token)  // takes the token...
{
    for (int i = 0; i < 1_000_000; i++)
    {
        Heavy();   // ❌ token never checked — Cancel() is ignored
    }
}

Accepting a token isn't enough — a method that never checks it can't actually be cancelled.

🧭 Use Cases — recognize these when they happen to you ▾
1 A loop checks the flag on every pass

This is the #1 scenario you'll actually run into: the loop calls IsCancellationRequested on every iteration, so .Cancel() is noticed on the very next pass and the method returns cleanly on its own terms.

RememberChecking every iteration is what makes cancellation feel almost immediate.
2 A deep call chain uses ThrowIfCancellationRequested()

The code is nested several calls deep, so returning cleanly from every level would be clunky. ThrowIfCancellationRequested() throws an OperationCanceledException instead, which unwinds the whole chain automatically and tells the caller "cancelled," not "failed."

RememberThrowing beats manual returns once cancellation has to unwind several call levels.
3 A method accepts the token but never checks it

Candidates often assume passing a CancellationToken into a method is enough on its own. It isn't — if that method never reads IsCancellationRequested (or calls ThrowIfCancellationRequested()), .Cancel() has nothing to notice, and the method runs to completion anyway.

RememberAccepting a token is not the same as being cancellable.
🌍 Real-world example ▾

A user cancels a long-running report export halfway through. The button click calls cts.Cancel() — but the export only actually stops if the code generating it is periodically checking IsCancellationRequested between rows or pages. If it's one giant, uninterruptible database call instead, the click does nothing until that call finishes on its own.
