Segment Tree vs. Fenwick Tree — same O(log n), different trade-off

"When would you reach for a Segment Tree or a Fenwick Tree instead of a plain prefix sum array?"

Why it matters ▾
  • This is a judgment question, not a build-it-live one — interviewers use it to see if you recognize "queries and updates are interleaved" as the real signal, not to watch you implement bit tricks on a whiteboard.
  • It's the direct sequel to Prefix Sum & Difference Array's own follow-up: "what if the array itself changes between queries?"
  • A favorite trap is reaching for either structure when the data never actually changes — spotting "no updates happening" as the cue to fall back to a plain prefix sum is itself the tested judgment.
🔥 Easy interview recall

Segment Tree → general aggregate, supports range updates too

Fenwick Tree (BIT) → compact, sum-specialized, point updates

Think: Both trade a full O(n) rebuild for O(log n) per query and per update. Fenwick is the lean specialist for sums. Segment Tree is the generalist that costs more to build.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A Segment Tree isn't the default answer just because "updates" got mentioned. If the underlying array is actually static between queries, a plain prefix sum array is simpler and already O(1) per query — save the extra complexity for when point/range updates are genuinely interleaved with the queries.

🔄 Likely Follow-up

"Your data is static here — do you actually need a Segment Tree?" No — recognizing "no updates are happening" as the signal to fall back to the simpler prefix-sum technique, instead of reflexively reaching for the more powerful structure, is exactly the judgment this question is testing.

🎯 Say this in the interview — the exact lines to land

"A plain prefix sum answers range-sum queries in O(1) but needs a full O(n) rebuild after every update. A Segment Tree or a Fenwick Tree (Binary Indexed Tree) both support range queries and point updates in O(log n) each — the Segment Tree is the more general, more expensive structure; the Fenwick Tree is the lean, sum-specialized one."

  • Prefix Sum → use when the array is static between queries — simplest, O(1) per query, no tree needed.
  • Fenwick Tree → use when the aggregate is a sum and you want the smaller, simpler structure.
  • Segment Tree → use when you need a general aggregate (min/max/GCD) or range updates, not just point updates.
  • Both cost O(log n) per query and per point update — the real trade-off is flexibility vs. simplicity, not speed.
  • Range updates on a Segment Tree → needs lazy propagation, a real technique worth naming, not one to implement from memory here.
📖 Explanation ▾

A plain prefix sum array answers a range-sum query in O(1) — but that only holds while the underlying array never changes. The moment one element needs to be updated, the whole prefix sum array is stale and needs an O(n) rebuild before the next query can trust it. When updates and queries are genuinely interleaved, that rebuild cost defeats the entire point of precomputing. A Segment Tree and a Fenwick Tree both exist to close exactly that gap — a real middle ground between "O(1) query, O(n) rebuild" (plain prefix sum) and "O(n) query, O(1) update" (no precomputation at all).

A Segment Tree is a binary tree where every node holds the aggregate — sum, min, max, whatever the problem needs — of a range of the underlying array. The root covers the whole array, each level below splits its range in half, down to leaves that each cover a single element. A range query walks down and combines the aggregates from the O(log n) nodes whose ranges together exactly cover the query. A point update walks down to the one affected leaf and recomputes every ancestor on the way back up — also O(log n). It's more flexible than a Fenwick Tree — it supports a wider range of aggregates, and with an extra technique called lazy propagation it can support range updates too, not just point updates — at the cost of being more complex to build and using somewhat more memory.

A Fenwick Tree (Binary Indexed Tree) is a more compact answer to the same problem, purpose-built for prefix-sum-style aggregates. It's implemented as a single array, using the binary representation of an index to decide which positions to touch — still O(log n) per query and per point update, but with a smaller memory footprint and a simpler implementation than a full Segment Tree. The trade is flexibility: it's naturally suited to sums (or similar), and adapting it to min/max-style aggregates is possible but far less natural than reaching for a Segment Tree instead.

🌍 Real-world example ▾

You're told a large array needs to answer "sum of this range" queries while individual elements also get updated, many times, in the same run. That interleaving is the actual signal: if the aggregate is a sum, a Fenwick Tree is the leaner choice; if it needs to be min/max instead, or the range updates themselves (not just single elements) need to change, a Segment Tree is the more natural fit. And if it turns out nothing ever gets updated after all, the right move is to drop back to a plain prefix sum array — the simplest structure that already solves it.
