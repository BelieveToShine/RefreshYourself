The same message, twice — does your code even notice?

Your message consumer occasionally processes the same message twice — how do you prevent that from causing real problems?

Why it matters ▾
🔁 Duplicate Delivery
❗ ProblemA consumer can crash — or just run past the lock's visibility timeout — after doing the real work but before acknowledging the message, so the broker redelivers it; if processing isn't safe to run twice, a customer can get charged twice or an order can ship twice.
✅ SolutionMake the processing itself idempotent — track a unique message/business ID and check whether it's already been handled before acting, so a duplicate delivery produces the exact same end result as the first one.
RecallAt-least-once delivery is normal — idempotent processing is the fix, not fighting the redelivery.
🔥 Easy interview recall

At-least-once delivery = "it will arrive — maybe more than once."

Think: Idempotent processing checks before it acts, so twice feels exactly like once.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Exactly-once delivery isn't something to chase at the queue level. Service Bus — like most message queues — guarantees at-least-once delivery, not exactly-once; a redelivery after a timeout or a crash before the ack is normal, expected behavior, not a bug to "fix" in the transport.

🔄 Likely Follow-up

"What's a simple, concrete idempotency mechanism?" Store processed message IDs (with a TTL) in a fast lookup — a database unique constraint or a cache — and check it before acting; if the ID's already there, skip reprocessing and just re-acknowledge the message.

🎯 Say this in the interview — the exact lines to land

"Most queues, Service Bus included, guarantee at-least-once delivery, not exactly-once, so an occasional duplicate is expected. The real fix is making processing idempotent — track a unique message ID and check before acting, so processing it twice has the same effect as processing it once."

  • At-least-once, not exactly-once — redelivery after a crash or timeout is normal, expected behavior.
  • Idempotent processing → check a unique ID before acting, instead of trying to eliminate duplicates at the transport layer.
  • A dedicated message/business ID with a TTL in a database unique constraint or cache → the simplest real mechanism.
  • Exactly-once across a distributed system is a famously hard, often impractical guarantee — idempotency sidesteps it instead of chasing it.
📖 Explanation ▾

Most message queues, Azure Service Bus included, promise at-least-once delivery: once a message is sent, it will eventually be delivered, but it might be delivered more than once. A redelivery happens when a consumer picks up a message, starts working, and then either crashes before acknowledging it or takes longer than the lock's visibility timeout — the broker assumes the delivery failed and hands the same message out again. This is normal, expected behavior, not a defect in the queue.

The fix isn't trying to stop the redelivery — it's making the processing itself idempotent: give every message a unique ID (an order ID, a payment ID) and check, before acting, whether that ID has already been handled. If it has, skip the work and just acknowledge the message; if it hasn't, process it and record the ID. Done this way, processing the same message once or twice produces the exact same end result.

Azure Service Bus also offers a built-in duplicate-detection window (RequiresDuplicateDetection) that filters resends of the same MessageId within a configurable time window — useful for sender-side retries, but it's not a substitute for your own idempotency check, since it only covers that one queue for that one window, not every way a duplicate can reach your consumer.

💻 See the code ▾
C# 
var alreadyHandled = await db.ProcessedMessages
    .AnyAsync(m => m.MessageId == message.MessageId); // check first

if (alreadyHandled)
{
    await receiver.CompleteMessageAsync(message); // ✅ just re-ack, don't redo the work
    return;
}

await MarkOrderPaidAsync(orderId);                  // do the real work
db.ProcessedMessages.Add(new(message.MessageId));   // record the ID
await db.SaveChangesAsync();
await receiver.CompleteMessageAsync(message);

The unique constraint on MessageId is what makes this safe even if two redeliveries somehow land at the same time — one insert wins, the other fails and is treated as "already handled."

🧭 Use Cases — recognize these when they happen to you ▾
1 The consumer finishes the real work, then crashes before it can acknowledge

The broker never saw the acknowledgment, so it assumes delivery failed and sends the same message out again — even though the work actually finished. This is the single most common way a "duplicate" shows up in practice.

RememberNo ack ≠ no work done — it just means the broker couldn't tell.
2 Processing runs past the lock's visibility timeout while the consumer is still alive

The broker gives up on the lock and hands the message to a second receiver while the first one is still working — so both can genuinely run at the same time. A simple in-memory "already seen" flag isn't enough here; the check needs to be atomic (a database unique constraint), since two checks can race each other.

RememberTwo receivers can run at once — make the check atomic, not just present.
3 You turn on Service Bus's built-in duplicate detection

RequiresDuplicateDetection filters a resend of the same MessageId within a configurable time window — a real, built-in feature. It doesn't cover a redelivery outside that window, a different queue, or any duplicate your own consumer-side check wasn't already expecting — it's a helpful extra, not a replacement for idempotent processing.

RememberA sender-side, time-boxed filter — not a substitute for your own idempotency check.
🌍 Real-world example ▾

A payment consumer charges the card, then crashes before it can ack. Service Bus redelivers the message a few seconds later. Without an idempotency check, the customer gets charged twice; with one — checking "has this payment ID already been marked paid?" before charging — the second delivery sees it's already done and just skips straight to acknowledging it.
