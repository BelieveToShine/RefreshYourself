Keys — how React tells one list item from another across renders

"Why does React need keys on list items, and what breaks when they're unstable?"

Why it matters ▾
  • Every dynamic list in React — a todo app, a table, a feed — needs keys; get it wrong and you get a subtle UI bug, not a crash.
  • It's the reason behind that "each child in a list should have a unique key" console warning almost every React developer has seen.
  • A near-guaranteed interview question for anyone claiming real React experience, often followed by the deliberate-remount trick question.
🔥 Easy interview recall

Key = "identity, not position."

Think: index as key + a list that can reorder = state lands on the wrong row.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Using the array index as the key is always fine as a default. It only holds up for a list that never reorders, inserts, or deletes — the moment it can, React matches old and new elements by that key, so inserting an item at the top makes it think everything after that position "changed," and can silently attach the wrong state (like a half-typed input value) to the wrong data row.

🔄 Likely Follow-up

"Can a component read its own key via props.key?" No — React reserves key (along with ref) as special and strips it out of the props object a component actually receives; if you need that value inside the component, you have to pass it again under a different prop name.

🎯 Say this in the interview — the exact lines to land

"Keys are how React tells list items apart between renders — by identity, not position. Once a list can reorder, insert, or delete, the array index stops being safe, because React matches old and new elements by that index and can attach the wrong internal state to the wrong row; a stable, data-based id like item.id fixes it."

  • key → lets React match list items by identity, not position, across renders.
  • Array index as key → breaks the moment the list can reorder, insert, or delete — state can attach to the wrong row.
  • Good key → a stable, data-based id (a database id), never derived from position.
  • Changing a key on purpose → forces React to unmount and remount, fully resetting that component's state.
  • A component can't read its own key through props.key — React strips it out before props ever reach it.
📖 Explanation ▾

Keys tell React which list item is which, across renders. React doesn't throw a list away and rebuild it from scratch on every render — it looks at the old list and the new list and matches items up by key, then decides which existing item to keep updating, which one is genuinely new, and which one was removed. Without a stable key, React falls back to matching by position, which is exactly where things go wrong.

The array index looks like a convenient key, but it's really just the item's position, not its identity. The moment a list can reorder, insert, or delete, the item that used to sit at index 2 might now sit at index 3 — but React still treats "index 2" as the same identity it was before. That's how an internal state, like a checked checkbox or a half-typed input, ends up glued to the wrong data row after a single insert.

A stable key fixes this because it travels with the data, not the position — a database id is the standard choice. This same mechanism is also a deliberate tool: changing a component's key on purpose is a normal way to force React to tear it down and rebuild it from scratch, wiping its internal state intentionally. One thing a key can't do: be read back inside the component through props.key — React strips key (and ref) out of props before the component ever sees them.

💻 See the code ▾
JSX 
{items.map((item, i) => (
  <Row key={i} data={item} />   // ❌ key = position, not identity
))}

Looks fine until the list reorders or something gets inserted at the top — then key={i} quietly relabels every row from that point down.

JSX 
{items.map(item => (
  <Row key={item.id} data={item} />   // ✅ key = the data's own id
))}

item.id travels with the row no matter where it moves — insert, delete, or reorder, React still knows exactly which row is which.

🌍 Real-world example ▾

A coat-check ticket tied to your actual coat is a stable key — no matter which hook it ends up on, the ticket finds it. A ticket that just says "the third hook from the left" is the array index — the moment someone rehangs the coats, that ticket now points at a stranger's coat instead of yours.
