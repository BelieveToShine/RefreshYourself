Scenario: A Race Condition on a Shared Balance

"Two threads update the same account balance concurrently. Why doesn't marking the balance field volatile make balance += amount thread-safe, and what would actually fix it?"

Why it matters ▾
💸 Lost Update
❗ ProblemTwo deposits that should add up to +100 sometimes only show +50 in the final balance — money silently disappears from the books with no exception thrown and nothing obviously wrong in the code.
✅ Solutionbalance += amount is read-then-write, not one step; volatile only guarantees visibility, not exclusive access, so two threads can both read the same stale value before either writes it back. Making the whole read-modify-write a single atomic step — with synchronized, a Lock, or an atomic compound method — closes the gap.
Recallvolatile makes a value visible, not safe to update in two steps — the gap between read and write is still wide open.
🔥 Easy interview recall

volatile ≠ atomic. balance += amount is read-then-write — two threads can both read the same stale value before either writes, and one update is silently lost.

Think: for a single counter-style field, reach for an Atomic* compound method first — it's exactly built for this.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Marking balance volatile does NOT make balance += amount thread-safe. volatile only guarantees every thread sees the latest written value — it says nothing about two threads reading, modifying, and writing back without interleaving, which is exactly what a compound assignment needs.

🔄 Likely Follow-up

"Why not just use synchronized everywhere?" It's correct and simple, but every call pays lock-acquisition overhead and serializes all callers; for a single numeric field like this, an AtomicLong's getAndAdd() gives the same correctness with a lock-free compare-and-swap, which scales better under contention.

🎯 Say this in the interview — the exact lines to land

"volatile only guarantees visibility, not atomicity — balance += amount is a read-then-write, so two threads can both read the same stale value before either writes back, silently losing one update. The fix is making the whole operation one atomic step: synchronized, a Lock, or — the best fit for a single counter — an Atomic class's compound method like getAndAdd()."

  • synchronized → simple and correct, but every caller is serialized through one lock.
  • Lock → more control (tryLock, fairness), same mutual-exclusion idea.
  • AtomicLong.getAndAdd() → lock-free, best fit here — it IS a single numeric counter.
  • Why volatile fails → it publishes the latest value, it never locks out a concurrent reader.
📖 Explanation ▾

balance += amount compiles to three separate steps: read balance, compute balance + amount, write the result back. volatile guarantees that any thread reading balance sees the most recently written value — it does not reserve that value for the reading thread, and it does nothing to stop a second thread from reading the exact same value before the first thread's write lands. Both threads can legitimately read 100, both compute 150, and whichever writes last simply overwrites the other's update — one deposit is gone with no error raised anywhere.

The fix, in every case, is making the read-modify-write a single indivisible operation. synchronized around the whole statement is the simplest correct option — only one thread can be inside the block at a time, so no second thread can read a value that's mid-update. A Lock (ReentrantLock) gives the same guarantee with more control, like a timed or interruptible acquire. For exactly this shape — one numeric field, one compound update — an Atomic* class's own compound method (getAndAdd(), accumulateAndGet()) is usually the best fit: it performs the read-modify-write as one hardware-level compare-and-swap, with no lock to acquire and no thread ever blocked waiting for another.

The three options aren't interchangeable in general — synchronized/ Lock can protect a block covering several related fields or operations at once, while an atomic class only protects the single value it wraps. For a lone counter like a balance, that narrower guarantee is exactly enough, and it's the cheaper one.

💻 See the code ▾
Java 
private volatile long balance = 100;

void deposit(long amount) {
    balance += amount; // ❌ read + write, NOT atomic — volatile doesn't help
}

Two threads calling deposit(50) at the same time can both read 100 before either writes — one +50 is silently lost.

Java 
private final AtomicLong balance = new AtomicLong(100);

void deposit(long amount) {
    balance.getAndAdd(amount); // ✅ one atomic compare-and-swap step
}

No second thread can ever observe balance mid-update — the read-modify-write happens as one indivisible step.

🧭 Use Cases — recognize these when they happen to you ▾
1 A shared counter under load reports a total lower than the number of increments actually made

This is the #1 scenario you'll actually run into: a metrics counter or request tally using a plain long count++ under real concurrent load, reporting a number smaller than the actual event count. Swapping to AtomicLong.incrementAndGet() fixes it with no lock needed.

RememberA shared counter that undercounts under load is a lost-update bug, almost always fixed by an Atomic class.
2 Several related fields need to change together and stay consistent with each other

An Atomic* class only protects the single value it wraps — it can't keep a balance and a transaction-history list consistent with each other as one unit. Once more than one related field must change together, synchronized or a Lock around the whole operation is the right tool, not a collection of separately-atomic fields.

RememberAtomics protect one value each — multiple fields that must stay consistent need a real lock.
3 A load test shows synchronized working correctly, but throughput drops under heavy contention

Correctness isn't the only axis — synchronized is right, but every caller queues for the same lock, so throughput drops as thread count rises. If the protected section really is just one numeric field, replacing it with a lock-free Atomic* compound method removes the queueing entirely.

RememberCorrect and slow under contention is a sign to narrow the lock down to a lock-free atomic, not to remove synchronization.
🌍 Real-world example ▾

A banking service's account balance is declared volatile long balance, and two concurrent deposit requests for the same account each add 50. Both threads read the same starting value before either writes, so the final balance only reflects one of the two deposits — switching the field to an AtomicLong and using getAndAdd() makes the read-modify-write indivisible and fixes it.
