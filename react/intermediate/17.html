Automatic Batching — React 18 widened where batching happens

"Two setState calls happen inside a .then() — how many renders does that cause?"

Why it matters ▾
  • A very common "what changed in React 18" comparison question — easy to get backwards if you learned batching before React 18 existed.
  • Explains a real, observable behavior difference: the exact same code can re-render once on React 18+ and twice on React 17.
  • Sets up flushSync as the deliberate escape hatch, for the rare case a synchronous update is genuinely required.
🔥 Easy interview recall

Before React 18 → batches only inside React event handlers

React 18+ → batches everywhere — promises, timeouts, native listeners too

Think: React 18 didn't change how batching works — it widened where it applies.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Code written and tested on React 17 can silently change behavior on React 18 with zero code changes. A setTimeout callback with two setState calls used to render twice; on React 18+ it renders once. That's rarely a bug in practice — but it explains why an older mental model of "batching only happens inside event handlers" gives the wrong answer once the app has moved to React 18.

🔄 Likely Follow-up

"When would you actually reach for flushSync?" When something after the state update genuinely depends on the DOM already reflecting it — e.g. measuring a layout, or scrolling to a node, right after a change that would otherwise still be batched. It's rare, and reaching for it often means reconsidering the design first, since it forces a synchronous render/commit outside React's normal scheduling.

🎯 Say this in the interview — the exact lines to land

"Before React 18, updates only batched inside a React event handler — a promise, timeout, or native event listener each triggered its own render. React 18's automatic batching extends the same batching behavior everywhere, so multiple updates in any of those contexts now produce one render, same as inside a handler."

  • Before 18 → event handlers only — everywhere else, each setState re-rendered separately.
  • React 18+ → batches everywhere — promises, timeouts, native listeners included.
  • flushSync → the deliberate opt-out — forces a synchronous update when the DOM must already reflect it.
  • Reaching for flushSync often → worth reconsidering the design — it's the exception, not a routine tool.
📖 Explanation ▾

Batching itself has always meant the same thing: React collects multiple state updates together and applies them in one pass, triggering a single re-render instead of one per update. What changed in React 18 is where that collecting happens. Before 18, React only knew to batch updates that happened synchronously inside a React event handler — its own call stack made that easy to detect. Anything outside that stack (a promise's .then(), a setTimeout callback, a native addEventListener handler) fell outside React's own tracking, so each setState call there triggered its own separate render.

React 18's automatic batching removes that distinction — the new root API (createRoot) batches updates no matter where they originate, so the exact same "two setState calls in a .then()" code goes from two renders to one, with no code change required. This is almost always a pure performance win — fewer renders for the same end result — and rarely something application code needs to notice at all.

flushSync is the explicit way to opt back out when a synchronous update is genuinely required — it forces React to apply an update and flush the DOM immediately, before the next line of code runs, rather than batching it. It exists for a narrow set of real cases (measuring layout right after a change, certain DOM-library integrations) — reaching for it as a general habit usually means something about the design should be reconsidered first.

💻 See the code ▾
JSX 
fetch(url).then(() => {
  setStatus('done');   // React 17: render #1 — React 18+: batched
  setCount(c => c + 1);   // React 17: render #2 — React 18+: same pass
});   // React 18+: exactly one render total

No code change between the two versions — only the number of renders changes.

JSX 
flushSync(() => {
  setCount(c => c + 1);
});
// DOM already reflects the new count here — safe to measure/scroll now
listRef.current.scrollTop = listRef.current.scrollHeight;

Forces the update and DOM flush to happen before the next line runs, instead of batching it.

🌍 Real-world example ▾

A cashier ringing up a cart. Whether items get scanned one by one at the counter (an event handler) or added while restocking a shelf across the store (outside it), React 18's cashier now waits until the whole order is settled before printing one receipt — one total, not a separate receipt for every single item, no matter where in the store the scanning happened.
