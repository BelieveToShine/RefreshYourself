Repository pattern — a collection-like door to your data, and whether EF Core already is one

"What is the Repository pattern, and is it still worth it on top of EF Core?"

Why it matters ▾
🗄️ Repository
❗ ProblemWhen services call data-access code directly, query details spread through the business logic and every test needs a real database.
✅ SolutionA repository hides the data source behind a collection-like interface, so the service asks for orders by name and the storage can be swapped or faked.
RecallRepository = a collection-like front door to data.
🔥 Easy interview recall

Repository = "a collection-like front door to your data."

Think: Service → IOrderRepository → EF or in-memory EF Core → DbSet already acts like one, DbContext like a unit of work Worth it? → only if the layer earns its keep

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A repository is not just "a class that wraps EF." A thin wrapper that mirrors every DbSet method or returns IQueryable hides nothing — it adds a layer and still leaks EF to the callers.

🔄 Likely Follow-up

"So should you wrap EF Core in a repository or not?" It depends on what the layer buys. It earns its place when it hides real query logic behind domain-shaped methods like GetOverdueAsync(), or when you need to swap the data source. A generic wrapper that only forwards to DbSet usually doesn't.

🎯 Say this in the interview — the exact lines to land

"A repository is a collection-like abstraction over data access: the service asks for orders through an interface and doesn't know where they are stored. On top of EF Core it's debatable, because DbSet already behaves like a repository and DbContext like a unit of work. I add one when it hides real query logic or helps testing, and I avoid a generic wrapper that just forwards calls."

  • Repository → collection-like interface with domain-shaped methods, like GetOverdueAsync().
  • Benefit → the service depends on the interface, so a fake can replace the real storage.
  • EF Core → DbSet ≈ repository, DbContext ≈ unit of work.
  • Generic wrapper over EF → often adds a layer and hides nothing.
  • Don't leak → returning IQueryable<T> lets callers build EF queries outside the repository.
  • Worth it when → complex queries named once, swappable storage, or strict layering.
📖 Explanation ▾

A repository makes data access look like a collection: you add, find and list things, and the service never sees SQL or the ORM. The service depends on IOrderRepository, a concrete class implements it, and tests can use a fake. It's the Dependency Inversion idea applied to data.

The debate starts with EF Core. EF's documentation describes DbContext as a mix of the unit-of-work and repository patterns, and DbSet<T> already behaves like a collection. So a repository that just forwards Add, Find and Where to DbSet mostly repeats what EF already gives you. Returning IQueryable<T> from it is worse, because callers can now compose EF queries and the abstraction leaks (see IEnumerable vs. IQueryable).

A repository earns its keep when it names a real query once (GetOverdueAsync()), keeps persistence out of the domain, or lets you swap the data source. If it doesn't do any of that, use DbContext directly and test against a test database.

💻 See the code ▾
C# 
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(int id);
    Task<IReadOnlyList<Order>> GetOverdueAsync();   // a named query, not raw IQueryable
    void Add(Order order);
}

public class EfOrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
    public EfOrderRepository(AppDbContext db) => _db = db;

    public Task<Order?> GetByIdAsync(int id) => _db.Orders.FindAsync(id).AsTask();

    public async Task<IReadOnlyList<Order>> GetOverdueAsync()
        => await _db.Orders.Where(o => o.DueDate < DateTime.UtcNow).ToListAsync();

    public void Add(Order order) => _db.Orders.Add(order);   // saved later via SaveChangesAsync
}

The query lives in one named method, and EF stays behind the interface.

C# 
public class OrderService
{
    private readonly IOrderRepository _orders;
    public OrderService(IOrderRepository orders) => _orders = orders;   // sees only the interface
}

The service has no idea whether orders come from EF, SQL or memory.

🌍 Real-world example ▾

A librarian. You ask for a book by title and never walk the shelves. But if the librarian only repeats "go to shelf 12" back to you, they add nothing — a repository is worth having only when it actually does the finding.
