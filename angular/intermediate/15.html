ControlValueAccessor — teaching a custom component to speak Angular's forms language

"How does ControlValueAccessor actually let a completely custom component plug into Angular's reactive forms?"

Why it matters ▾
  • Comes up the moment you've built a reusable design-system input (a date picker, a rating widget, a tag input) — interviewers want to know it works with formControlName like any native control, not just visually.
  • Typed reactive forms, dynamic FormArray, and cross-field/async validation are the practical checks an interviewer runs once they know you've used reactive forms beyond a simple login form.
  • ControlValueAccessor's exact methods are a near-guaranteed follow-up once "have you built a custom form control" comes up — interviewers want the four method names, not just "I implemented the interface."
🔥 Easy interview recall

writeValue → Angular pushes a value in

registerOnChange → your component pushes changes out

registerOnTouched → your component flags it touched

Think: Angular never guesses — your component has to call the callbacks itself, every single time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Angular does not automatically detect when your custom component's value changes. Your component has to call the onChange callback captured from registerOnChange every time the value changes internally — otherwise the surrounding FormControl never finds out, no matter how clearly the UI shows the new value on screen.

🔄 Likely Follow-up

"Does cross-field validation run if one of the two fields is individually invalid already?" Typically yes, when the validator is attached to the FormGroup itself — a group-level validator can still read both controls' raw values regardless of either one's own validity, which is exactly why cross-field checks belong at the group level, not bolted onto either individual control.

🎯 Say this in the interview — the exact lines to land

"ControlValueAccessor is the interface — writeValue, registerOnChange, registerOnTouched, and optionally setDisabledState — that lets a fully custom component behave like a native form control. Angular pushes values in through writeValue, but my component has to push changes out itself by calling the callbacks Angular registered with it."

  • writeValue → Angular pushes a value in, e.g. when the form is patched programmatically.
  • registerOnChange → your component calls it back every time the value changes internally — Angular never guesses.
  • Cross-field validation → belongs on the FormGroup, never on either individual control — neither field alone can decide it.
  • Typed reactive forms → FormControl<string> catches a mismatched value at compile time instead of silently accepting any.
  • Dynamic FormArray → .push() / .removeAt() add and remove controls at runtime.
  • Signal Forms vs. Reactive Forms → a "which model fits this codebase" decision, not a replacement.
📖 Explanation ▾

Reactive forms hold up better in large applications because their state and validation live as explicit, testable TypeScript objects — a FormGroup you can build and check without touching a template — instead of being entangled with template directives. Current Angular pushes this further with typed reactive forms: FormControl/FormGroup/FormArray are generic over the actual value type (FormControl<string>), so a mismatched value is a compile-time error instead of a form silently accepting any.

Two validation edges show up constantly once forms get real. A cross-field validator attached to the FormGroup itself — not either control — can read multiple sibling controls together, like a password/confirm-password pair where neither field alone can decide validity. An async validator returns an Observable or Promise, for checks that need an API call ("is this username taken") — Angular marks the control PENDING while it waits, and debouncing (updateOn: 'blur', or the validator's own scheduling) keeps it from firing on every keystroke. Dynamic FormArray's .push()/.removeAt() is the direct mechanism behind "let the user add another phone number."

ControlValueAccessor is the interface that makes a fully custom component behave like a native control. writeValue(value) is called by Angular forms to push a value into your component — e.g. when the form is patched programmatically. registerOnChange(fn) hands you a callback your component must call itself, every time the user changes the value internally, to tell Angular forms about it. registerOnTouched(fn) similarly gives you a callback to call when the control should be marked touched, typically on blur. Angular never inspects your internal UI — your component is responsible for calling these callbacks at the right moments.

Building a reusable date picker means implementing that interface on the component, calling the registered onChange whenever the user picks a date, updating the displayed value inside writeValue, and registering the component as an NG_VALUE_ACCESSOR provider so formControlName/ngModel route through it. For a form-heavy component, the same OnPush plus "don't call expensive methods from a template bound to form state" rule from Change Detection and Performance applies here too.

💻 See the code ▾
TypeScript 
class DatePickerComponent implements ControlValueAccessor {
  value = '';
  onChange = (_: string) => {};              // placeholder until Angular registers the real one

  writeValue(val: string) { this.value = val; }        // Angular → component
  registerOnChange(fn: any) { this.onChange = fn; }   // Angular hands you the callback
  registerOnTouched(fn: any) { this.onTouched = fn; }  // same, for "touched"

  onInternalChange(newVal: string) {
    this.value = newVal;
    this.onChange(newVal);              // ✅ component → Angular — you must call this yourself
  }
}

Angular calls writeValue and registerOnChange for you — only your component calling onChange back actually tells the FormControl anything changed.

TypeScript 
function passwordsMatch(group: AbstractControl): ValidationErrors | null {
  const pass = group.get('password')?.value;
  const confirm = group.get('confirm')?.value;
  return pass === confirm ? null : { mismatch: true };   // checked together, not per-field
}

this.form = new FormGroup(
  { password: ..., confirm: ... },
  { validators: passwordsMatch }        // ✅ attached to the group, not either control
);

passwordsMatch is attached to the group, not either individual control — that's what lets it read both values at once.

🌍 Real-world example ▾

Teaching a visitor the local customs. ControlValueAccessor is like teaching a foreign visitor (your custom component) the local customs (Angular forms' expectations) so everyone else at the table (the surrounding FormGroup) can interact with them exactly like any other guest, without special-case handling — but the visitor still has to actually speak up (call the registered callbacks) every time something changes; nobody can read their mind for them.
