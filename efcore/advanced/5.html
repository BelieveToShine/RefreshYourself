ExecuteUpdate() — one SQL statement instead of a million tracked entities

What are bulk operations, and why doesn't EF Core's default SaveChanges() behave well for a large batch update or delete?

Why it matters ▾
  • Nightly price updates, marking millions of stale rows as archived, GDPR-style mass deletes — real backends run jobs like this constantly, and the naive way to write one is a classic performance trap.
  • Interviewers use this to check whether you actually understand what SaveChanges() does under the hood, not just that Entity Framework exists.
  • A very common senior/architect follow-up: "how would you update or delete a million rows without loading them all into memory first?"
🔥 Easy interview recall

SaveChanges() loop → load + track every row first

ExecuteUpdate() → one SQL UPDATE, zero rows loaded

ExecuteDelete() → one SQL DELETE, zero rows loaded

Think: SaveChanges() loads a million rows into memory just to change one column. ExecuteUpdate() never loads a single one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Looping and calling SaveChanges() is not "the EF Core way" to bulk update. It technically works, but it loads every matching row into memory and tracks it just to change one column — a single ExecuteUpdate() call performs the same change directly inside the database with zero entities ever materialized.

🔄 Likely Follow-up

"Why can't ExecuteUpdate()/ExecuteDelete() run arbitrary C# logic per row the way a loaded-and-mutated entity loop could?" Because it translates directly into one set-based SQL statement — there's no per-row C# execution at all, only whatever can be expressed inside that statement's SET or WHERE clause.

🎯 Say this in the interview — the exact lines to land

"By default, SaveChanges() has to load every matching row into the change tracker, mutate each one, and generate one statement per entity — that doesn't scale to millions of rows. ExecuteUpdate() and ExecuteDelete(), added in EF Core 7, skip that entirely: they translate a filtered IQueryable<T> straight into a single set-based UPDATE or DELETE statement, with zero entities ever loaded or tracked."

  • Default SaveChanges() path → loads, tracks, and diffs every affected row before any SQL is generated.
  • ExecuteUpdate() / ExecuteDelete() → one set-based SQL statement, zero entities materialized.
  • Before EF Core 7 → raw SQL or a third-party bulk-extensions library was the only way to skip the load-and-track cycle.
  • The trade-off → no per-row C# logic — only what fits inside a SQL SET/WHERE clause.
📖 Explanation ▾

SaveChanges()'s default behavior for a batch update or delete is a load→track→diff cycle: EF Core first runs a query to bring every matching row into memory, registers each one with the Change Tracker, and only then does the application mutate them — one at a time, in a loop. When SaveChanges() finally runs, it generates a DML statement for every tracked change. Some providers batch those statements into fewer round trips inside one SaveChanges() call, but every affected row still has to be materialized and tracked first — for an operation touching millions of rows, that's millions of tracked entities sitting in memory and millions of generated statements.

ExecuteUpdate() and ExecuteDelete(), added in EF Core 7, skip the load→track→diff cycle entirely. Called directly on an IQueryable<T>, they translate straight into a single UPDATE or DELETE statement with a WHERE clause built from the query's filter — no entity is ever loaded, tracked, or diffed.

Before EF Core 7, getting this same set-based behavior meant dropping to raw SQL or reaching for a third-party bulk-extensions package — worth knowing as history, but ExecuteUpdate()/ExecuteDelete() is the modern, built-in answer now.

💻 See the code ▾
C# 
var products = await db.Products
    .Where(p => p.CategoryId == categoryId)
    .ToListAsync();                       // ❌ loads every matching row into memory

foreach (var p in products)
{
    p.Price *= 1.10m;                     // tracked and mutated one at a time
}

await db.SaveChangesAsync();           // ❌ generates one UPDATE per product

Correct, and fine for a handful of rows — for a million products, this loads a million tracked entities just to change one column.

C# 
await db.Products
    .Where(p => p.CategoryId == categoryId)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(p => p.Price, p => p.Price * 1.10m)); // ✅ one SQL UPDATE, no entities loaded

Same result, translated directly into a single UPDATE ... WHERE ... statement — nothing is ever tracked.

C# 
await db.Products
    .Where(p => p.DiscontinuedOn < cutoffDate)
    .ExecuteDeleteAsync();                // ✅ one SQL DELETE, no entities loaded

Same idea for deletes — ExecuteDeleteAsync() issues one DELETE ... WHERE ... statement directly, no loop required.

🌍 Real-world example ▾

Your nightly job needs to mark 2 million stale orders as archived. Looping over them and calling SaveChanges() tries to track 2 million entities in one process — memory climbs fast and the job can run for hours or crash outright. A single ExecuteUpdateAsync() call does the same update as one statement, with cost that stays close to constant no matter how many rows match.
