Same method call — compiler decides, or runtime decides?

"What is polymorphism, and what's the difference between overloading and overriding?"

Why it matters ▾
  • Comes up almost immediately in an OOP interview — usually right after inheritance.
  • Mixing up overloading and overriding out loud is one of the most common OOP slip-ups.
  • Sets up a classic follow-up trap: hiding a method with new instead of overriding it.
🔥 Easy interview recall

Polymorphism = "one call, many possible behaviors."

Overloading → compiler picks, by signature

Overriding → runtime picks, by real object

Think: Overloading is settled before the program runs. Overriding is settled while it's running.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

new doesn't give you polymorphism just because Derived's version exists. Through a Base-typed reference, b.Method() still calls Base's version — new hides the method instead of overriding it, so the call is resolved by the reference's static type, not the object's actual type.

🔄 Likely Follow-up

"What actually happens at the IL level when you call an overridden method?" An override call is dispatched through the object's virtual method table at runtime — a plain non-virtual call is resolved directly at compile time, no lookup needed.

🎯 Say this in the interview — the exact lines to land

"Polymorphism means the same method call can behave differently depending on the actual type involved. Overloading is resolved at compile time — the compiler matches the call to a signature by argument types and count. Overriding is resolved at runtime, through the object's virtual method table, based on its real type — even when accessed through a base-type reference."

  • Overloading → compile-time, same name, different signatures.
  • Overriding → runtime, resolved by the object's actual type.
  • new hides a method, it doesn't override it → resolved by the reference's static type.
  • Use override when you need true polymorphic behavior through a base reference.
📖 Explanation ▾

Polymorphism lets code written against a base type pick up different behavior from whatever derived type actually shows up at runtime, without the caller needing to know which one it's talking to.

Overloading is settled before the program even runs. The compiler looks at the method name and the arguments you passed — their types and count — and locks in exactly which method body gets called. Two methods can share a name only because their signatures are different enough for the compiler to tell them apart.

Overriding is settled while the program is running. A virtual method call looks up the object's actual type through its virtual method table, so Base b = new Derived(); b.Method(); calls Derived's version — even though b is typed as Base. This is what people usually mean by "true" polymorphism.

When it's decidedCompile time, by the compilerRuntime, by the object's actual type
What resolves the callMatching the method signatureThe object's virtual method table
RequiresSame name, different parameter listvirtual/override, same signature, inheritance
Risk if misusedAmbiguous overload resolution errors❌ using new instead of override silently breaks polymorphism
💻 See the code ▾
C# 
class Announcer {
    public void Speak(string s) { }   // signature #1
    public void Speak(int n) { }      // signature #2
}
new Announcer().Speak(5);   // ✅ compiler picks Speak(int) — decided now

Overloading is picked by argument type at compile time — nothing about the object matters.

C# 
class Base { public virtual void Method() => Console.WriteLine("Base"); }
class Derived : Base { public override void Method() => Console.WriteLine("Derived"); }

Base b = new Derived();
b.Method();   // ✅ prints "Derived" — resolved by the real object at runtime

override keeps the call polymorphic — it runs Derived's version through b's real type.

C# 
class Derived2 : Base { public new void Method() => Console.WriteLine("Derived2"); }

Base b2 = new Derived2();
b2.Method();   // ⚠️ prints "Base" — new resolves by b2's static (Base) type

new hides the base method — the call is resolved by the reference's type, not the object's.

🌍 Real-world example ▾

Think of a universal remote. Every device has a "power" button in the same place, but each brand's remote sends its own actual signal when you press it — that's overriding. Ordering a coffee is overloading: Order(), Order(size), and Order(size, milk) are different requests, picked by what you hand over before the barista even looks at you.
