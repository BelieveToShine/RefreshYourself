Server Actions — a form that mutates data with no API route

"What's a Server Action, and how does it let a form mutate data without a separate API route?"

Why it matters ▾
⚡ Server Actions
❗ ProblemMutating data from a form used to mean hand-building a separate API endpoint, writing a fetch call to it from the client, and wiring up loading/error state around that round-trip — a lot of plumbing for "save this form."
✅ SolutionA Server Action is an async function marked 'use server' that a Client Component can call directly — as a <form>'s action, or from an event handler — so the mutation runs on the server with no hand-built endpoint in between.
RecallServer Action = a server-only function the client calls like it's local.
🔥 Easy interview recall

Server Action = "a server function you call directly from a form or a click, no API route needed."

Think: <form action={saveTodo}> — the function body runs on the server, not in the browser.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A Server Action is not a safely-hidden, un-callable server-only function. Under the hood it compiles into a real HTTP POST endpoint with a generated ID — anyone who can construct that request can call it, so it needs the same input validation and auth checks as any public API endpoint.

🔄 Likely Follow-up

"How does a Server Action integrate with progressive enhancement?" A <form action={myServerAction}> still works even with JavaScript disabled or not yet loaded — the browser submits it as a real form POST, which the Server Action handles either way.

🎯 Say this in the interview — the exact lines to land

"A Server Action is an async function marked 'use server' that a Client Component can call directly — passed as a form's action or invoked from an event handler — so it mutates data on the server without me hand-building a separate API endpoint and fetch call."

  • 'use server' → marks the function as a Server Action, callable from client code.
  • Still a real endpoint — a generated ID makes it a genuine, callable HTTP POST under the hood.
  • <form action={action}> → works without JavaScript, real progressive enhancement.
  • Needs the same validation/auth as any public endpoint — it's reachable, not protected by obscurity.
📖 Explanation ▾

A Server Action is an async function marked with the 'use server' directive — either at the top of its own file, or inline inside a Server Component. Marking it this way lets a Client Component call it directly, the same way it would call any local function, even though the function's body only ever runs on the server.

The most common shape is passing a Server Action as a <form>'s action prop. Next.js wires the submit up so it becomes a real server round-trip: the form's field data is sent to the server, the Server Action runs there with direct access to a database or file system, and the response flows back to re-render whatever Server Components depend on that data — all without writing a separate Route Handler or a client-side fetch call.

It's just as valid to call a Server Action from an onClick handler on a button, not only a form's action — either way, the function body still only executes on the server.

💻 See the code ▾
Next.js 
// app/actions.js
'use server';

export async function saveTodo(formData) {
  const title = formData.get('title');
  await db.todos.create({ title });   // ✅ direct server-side write
}

The 'use server' directive is what turns this plain function into a callable Server Action.

Next.js 
// app/todo-form.jsx — a Client Component
'use client';
import { saveTodo } from './actions';

export default function TodoForm() {
  return (
    <form action={saveTodo}>   // ✅ no fetch(), no API route
      <input name="title" />
      <button type="submit">Add</button>
    </form>
  );
}

The form's action points straight at the Server Action — the "API call" disappears from the client code entirely.

🧭 Use Cases — recognize these when they happen to you ▾
1 A simple form that creates or updates one record

Creating a todo, updating a profile field, deleting a comment — any form whose only job is "save this data" is the textbook Server Action case. No Route Handler, no client-side fetch wiring, just the function and the form.

RememberSimple CRUD form → Server Action is the default choice.
2 An action triggered by a button click, not a form submit

A Server Action isn't limited to forms — calling it from an onClick handler works the same way, the function body still runs on the server. Useful for a one-tap action like "like," "archive," or "mark as read."

RememberNot just forms — any event handler can call a Server Action.
3 Treating a Server Action as inherently safe because it's "never exposed" to the client

Because the function never appears in visible client bundle code, it's tempting to assume it can't be called directly. It compiles to a real POST endpoint with a generated action ID — anyone who can find or guess that request can call it without ever going through the form's UI.

RememberValidate and authorize inside the action itself — don't rely on it being "unreachable."
🌍 Real-world example ▾

A settings page with a "Save" button that updates a user's display name. Before Server Actions, that meant a dedicated /api/update-profile route plus a client fetch call wiring the form to it. With a Server Action, the form's action points straight at a 'use server' function that writes to the database — the same feature, with one less moving part to build and maintain.
