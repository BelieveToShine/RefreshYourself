Indexers — letting your own type support obj[i]

"What is an indexer, and why write one instead of a method like GetAt(i)?"

Why it matters ▾
🗂️ Indexers
❗ ProblemA type that's really a wrapper around an array, list, or dictionary can only offer GetAt(i)/SetAt(i, v) methods, forcing every caller to learn extra method names instead of the [] syntax they already use on every built-in collection.
✅ SolutionAn indexer — this[int i] { get; set; } — is a specially-named property the compiler exposes as get_Item/set_Item, so callers write list[i] directly, with no extra method names to remember.
RecallIndexer = this[] property that lets your type support obj[i] like a built-in collection.
🔥 Easy interview recall

Indexer = "a property named this[] instead of a word — same get/set, [] syntax."

Think: myCollection[2] is really just myCollection.this[2] — a specially-named property, not new syntax the compiler invents.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An indexer's index has to be an int, like an array. It can be any type — string, a tuple, even multiple parameters — because it's really just a property with parameters, not literal array access.

🔄 Likely Follow-up

"Can an indexer take more than one parameter?" Yes — a type can declare several indexers overloaded by parameter type or count, like this[int row, int col] for a grid, or this[string key] alongside this[int index] on the same class.

🎯 Say this in the interview — the exact lines to land

"An indexer is a specially-named property — this[int i] — that lets a type support obj[i] syntax directly. I'd write one instead of a method like GetAt(i) when the type is conceptually a collection, so square-bracket access reads more naturally than a named method call."

  • this[i] compiles to a specially-named property (get_Item/set_Item), not compiler magic.
  • Index type isn't limited to int — string, tuples, custom types all work, and it's overloadable.
  • get and set can carry independent access modifiers, exactly like an ordinary property.
  • Reach for it when the type wraps a collection — skip it for a type that just happens to expose a "get by id" method.
📖 Explanation ▾

An indexer is a property that's named this instead of a word, and takes a parameter in square brackets instead of none. The compiler turns it into a real member named Item underneath, with get_Item and set_Item accessors — list[2] and list[2] = "cat" are just friendlier syntax for calling those.

Unlike array access, the index isn't restricted to int. It's an ordinary parameter list, so a type can take a string key (like Dictionary<TKey,TValue> does), a pair of coordinates, or any type that makes sense for the concept — and a class can declare several indexers side by side, overloaded by parameter type or count.

Writing GetAt(i)/SetAt(i, v) methods instead works fine, but an indexer is the better fit whenever the type is a collection conceptually — it lets callers write the same square-bracket syntax they already use on arrays and lists, with no extra method names to remember.

💻 See the code ▾
C# 
public class WordList
{
    private readonly List<string> _items = new();

    public string this[int i]      // the indexer declaration
    {
        get => _items[i];
        set => _items[i] = value;
    }
}

One declaration lets callers write list[i] instead of list.GetAt(i) / list.SetAt(i, value).

C# 
var list = new WordList();
list[0] = "cat";              // calls the set accessor
Console.WriteLine(list[0]);   // calls the get accessor — prints "cat"

Reading calls get, assigning calls set — same as any other property, just addressed with [] instead of a dot.

C# 
public string this[string key] => _lookup[key];   // overloaded indexer — string key, not int

Indexers can be overloaded like methods — a type can expose both this[int] and this[string] side by side.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're wrapping a List, array, or custom collection inside your own type

A wrapper type like WordList declares one this[int i] indexer that forwards to its internal list, so callers write list[i] and list[i] = value instead of learning GetAt(i)/SetAt(i, v). This is the #1 scenario you'll actually run into.

RememberWrapping a collection → give it this[int i], not GetAt/SetAt.
2 Your type does key-based lookup, like a dictionary or config store

Dictionary<TKey,TValue>'s own config["ConnectionString"] syntax is exactly this — an indexer keyed by string instead of int, since the index parameter is just an ordinary parameter, not restricted to array-style integers.

RememberKey-based lookup → this[string key], not this[int].
3 Your type needs to be indexed by more than one value, like a grid or matrix

A Grid type declares this[int row, int col] so callers write grid[row, col] instead of grid.GetCell(row, col) — the index is just a parameter list, so it can take as many parameters as the concept needs, and a class can declare several such indexers side by side.

RememberMultiple values → this[row, col] is still one property call.
🌍 Real-world example ▾

You've already used one. Dictionary<TKey,TValue>'s config["ConnectionString"] syntax is just its own indexer, keyed by string instead of int. You'd write the same kind of member on a custom Grid type so callers can read grid[row, col] instead of grid.GetCell(row, col).
