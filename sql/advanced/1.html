Isolation Levels — how much of everyone else's mess you're allowed to see

What are isolation levels, and what problem does each one prevent — dirty read, non-repeatable read, phantom read?

Why it matters ▾
  • Two transactions touching the same rows at the same time is a normal production scenario — the isolation level is what decides whether one of them can see the other's half-finished work.
  • Picking a looser level than a piece of code actually needs is a real, hard-to-spot bug source: reports that don't add up, totals that shift mid-calculation, rows that mysteriously appear or vanish inside one transaction.
  • This is one of the most common database interview questions at senior level — expect it to be asked directly, then followed up with "which one prevents X."
🔥 Easy interview recall

Read Uncommitted → dirty reads allowed

Read Committed → no dirty reads, still non-repeatable / phantom

Repeatable Read → no dirty / non-repeatable, still phantoms

Serializable → all three prevented

Think: each step up the scale trades more safety for less concurrency.

⚠️ Common Trap

A dirty read means reading data that's corrupted or wrong. Not quite — it means reading another transaction's uncommitted change; the data itself isn't corrupted, it just might get rolled back later, which would make what you read something that never actually became true.

🔄 Likely Follow-up

"What's a phantom read, specifically, versus a non-repeatable read?" A non-repeatable read is the same row changing value between two reads in your transaction; a phantom read is new rows appearing (or existing ones disappearing) that now match a condition you queried earlier — the size or membership of your result set changes, not just a value inside one existing row.

🎯 Say this in the interview — the exact lines to land

"Isolation levels form an increasing-strictness scale — each one prevents one more concurrency problem than the last. Read Uncommitted allows dirty reads. Read Committed blocks those but still allows non-repeatable and phantom reads. Repeatable Read blocks non-repeatable reads too, but still allows phantoms. Serializable prevents all three, at the cost of the least concurrency."

  • Read Uncommitted → dirty reads allowed — the loosest level, rarely the right default.
  • Read Committed → blocks dirty reads only — the common default on most engines.
  • Repeatable Read → also blocks non-repeatable reads — a re-read of the same row can't change mid-transaction.
  • Serializable → blocks all three — the strongest guarantee, the most blocking.
  • Dirty read → reading someone else's uncommitted change, not reading corrupted data.
  • Phantom read → the result set's membership changes, not a value inside a row you already have.
📖 Explanation ▾

An isolation level is the rule that decides how much of one transaction's in-progress work another concurrent transaction is allowed to see. The four standard levels sit on a single scale — each one is strictly stricter than the one before it, and each strictness step closes off exactly one more of three well-known problems.

A dirty read is reading a value another transaction has changed but not yet committed — if that transaction rolls back, you read something that never really happened. A non-repeatable read is reading the same row twice inside one transaction and getting two different values, because another transaction changed and committed it in between. A phantom read is re-running the same query inside one transaction and getting a different set of rows — new ones matching your condition, or old ones no longer matching it — because another transaction inserted or deleted rows in between. The distinction that matters most between the last two: non-repeatable read is about a value inside a row you already had; phantom read is about which rows exist in your result set at all.

💻 See the code ▾
SQL 
SET TRANSACTION ISOLATION LEVEL READ COMMITTED; -- the common default

BEGIN TRANSACTION;
    SELECT Balance FROM Accounts WHERE AccountId = 42;
    -- ✅ never sees another transaction's uncommitted change
    -- ❌ but a second read here could still see a different value
    --    if someone else commits a change in between
COMMIT;

-- SET TRANSACTION ISOLATION LEVEL SERIALIZABLE would instead hold the
-- row (and the matching range) locked for the whole transaction —
-- ❌ more blocking for other writers, in exchange for a guaranteed-stable read

READ COMMITTED only promises no dirty reads — the same account row can still change value between two reads in this transaction. SERIALIZABLE is the one level that rules that out entirely, at the cost of holding locks for longer.

🌍 Real-world example ▾

A shared spreadsheet, two different ways of protecting it. Reading a shared sheet while someone else is mid-edit and seeing their half-typed formula is the dirty-read risk of a loose isolation level. Locking the whole sheet so nobody else can even open it while you work is Serializable — the safest option, but everyone else waits. Most of the time the right choice is somewhere in between: let people read freely, just never let them see an edit that might still get undone.
