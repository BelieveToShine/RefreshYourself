A slow MVC app under load — measure first, fix second

"You inherit a slow MVC app — what's your first diagnostic step?"

Why it matters ▾
🩺 Triage
❗ ProblemA slow app has many possible causes. Guessing and changing code at random wastes days, adds risk, and you can't prove whether the change helped.
✅ SolutionMeasure first with a profiler or APM to find where the time really goes, fix that one thing, then measure again to prove it worked.
RecallMeasure, find the hot path, fix one thing, measure again.
🔥 Easy interview recall

Step 1 → measure with a profiler, APM, or traces

Step 2 → find the hot path, where time really goes

Step 3 → fix one thing, then measure again

Think: doctor first, medicine second — no one prescribes before the tests come back.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding a cache or more servers before measuring. It feels like action, but if the real cause is something else, you pay for the extra servers and the app is still slow — and you still don't know why.

🔄 Likely Follow-up

"Why does sync-over-async hurt especially under load?" .Result or .Wait() makes a thread sit and wait for a Task. With many requests at once, those waiting threads can use up the thread pool, and new requests queue behind them. The fix is async all the way down.

🎯 Say this in the interview — the exact lines to land

"My first step is to measure, not to change code. I'd use a profiler or APM traces to find the hot path, because guessing wastes time and I couldn't prove a fix worked. Once I know where the time goes, I'd check the usual suspects there, change one thing at a time, and measure again."

  • First step → measure before touching code — a profiler, APM, or distributed traces.
  • Goal → find the hot path, the place the time really goes.
  • Usual suspects → N+1 queries, sync-over-async, repeated work, missing caching, big views — a guide, not a checklist.
  • Discipline → change one thing, then re-measure to prove it helped.
  • Not first → scaling out or adding a cache — they can hide the cause and still miss it.
📖 Explanation ▾

When you inherit a slow app, you don't know yet where it is slow. So the first move is to measure, not to fix. Attach a profiler, look at APM traces (for example Application Insights), or watch live numbers with tools like dotnet-counters and dotnet-trace. Ask one question: which part of a request takes the time?

Once you know the hot path, the usual suspects become useful. A request may fire a query for every row (N+1), or read data it never changes without AsNoTracking(). It may block on .Result or .Wait() and use up the thread pool. It may make many small remote calls or recompute something that could be cached. Rarely, a very large Razor view is the cause. Each of these only matters if the measurement points at it.

Then change one thing and measure again. If the numbers improve, you have proof. If not, undo it and go back to the data. (How the database side goes wrong is on The N+1 Problem and Beyond N+1; the same "diagnose first" habit for an API is on Web API Advanced.)

💻 See the code ▾
C# 
// ❌ blocks a thread-pool thread while it waits
var orders = _repo.GetOrdersAsync().Result;

// ✅ async all the way — the thread is free while it waits
var orders = await _repo.GetOrdersAsync();

Under many concurrent requests, blocked threads can exhaust the thread pool — the app looks slow even though the CPU is idle.

C# 
// ❌ N+1: one query for the orders, then one more per order
var orders = await _db.Orders.ToListAsync();
foreach (var o in orders)
    counts[o.Id] = await _db.OrderLines.CountAsync(l => l.OrderId == o.Id);

// ✅ one query, read-only, only the columns we need
var rows = await _db.Orders
    .AsNoTracking()
    .Select(o => new { o.Id, LineCount = o.Lines.Count })
    .ToListAsync();

A trace full of near-identical queries is the N+1 signature — one query with a projection replaces all of them.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your manager says "just add more servers" before anyone has looked at a trace

More servers can cost a lot and still miss the real cause. Looking at a trace first tells you whether the problem is even something servers can fix.

RememberMeasure first, then decide whether to scale.
2 The trace shows one page firing dozens of near-identical queries

That pattern is the N+1 signature. The fix is one query that fetches what the page needs, not a query per row.

RememberMany identical queries in a trace → N+1.
3 It's fine with one user but crawls at peak, with the CPU mostly idle

Blocking calls hold threads while they wait. At peak, new requests queue up even though the CPU has little to do — a sign to look for sync-over-async.

RememberSlow at peak + idle CPU → suspect blocked threads.
🌍 Real-world example ▾

An MVC order page used to feel fine and now times out during the lunch rush. Instead of guessing, the team opens an APM trace of one slow request and sees most of the time sitting in one action that calls .Result inside a loop. They switch it to await, redeploy, and watch the same trace get shorter — the proof the fix worked.
