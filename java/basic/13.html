The four pillars — one word each, but which actually means what?

"What are the four pillars of OOP, and what does each one actually mean in Java?"

Why it matters ▾
🔒 Encapsulation
❗ ProblemNothing stops outside code from reaching into a field directly and setting it to a value the class never expected, corrupting the object's own invariants.
✅ SolutionMake fields private and expose only the public methods that are allowed to change them — every change now goes through code that can validate it.
RecallEncapsulation = hide state, expose a controlled API.
👪 Inheritance
❗ ProblemWriting the same fields and methods again in every related class wastes effort and means a fix in one copy never reaches the others.
✅ SolutionA subclass extends a parent class and reuses its fields and methods automatically, adding or overriding only what's genuinely different.
RecallInheritance = a class reuses another's behavior via extends.
🔀 Polymorphism
❗ ProblemCalling code that works with a general type (Shape) shouldn't need an if/else chain checking every possible concrete subtype just to call the right method.
✅ SolutionOne call site (shape.draw()) runs a different concrete method depending on the object's actual runtime type — overriding resolves at runtime, overloading at compile time.
RecallPolymorphism = one call, many possible behaviors.
🧩 Abstraction
❗ ProblemIf every caller has to understand a class's full internal logic just to use it, any internal change risks breaking every caller at once.
✅ SolutionExpose what something does through a simple type/interface, and let the caller stay completely unaware of how it's actually implemented underneath.
RecallAbstraction = show the what, hide the how.
🔥 Easy interview recall

Encapsulation → hide state behind methods

Inheritance → reuse via extends

Polymorphism → one call, many behaviors

Abstraction → what, not how

Think: a locked box (encapsulation) that's a kind of something bigger (inheritance), answers calls differently depending what's inside (polymorphism), through a front panel that never shows the wiring (abstraction).

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Inheritance is not the same thing as polymorphism. Inheritance just gives a subclass a parent's code; polymorphism is what happens when a subclass's overridden method actually runs instead of the parent's at runtime.

🔄 Likely Follow-up

"Is overloading polymorphism too?" Yes — it's compile-time (static) polymorphism, resolved by the compiler from the argument types; overriding is runtime (dynamic) polymorphism, resolved from the object's actual type.

🎯 Say this in the interview — the exact lines to land

"Encapsulation hides state behind a controlled API, inheritance lets a class reuse another's behavior via extends, polymorphism lets one call behave differently depending on the actual object, and abstraction exposes what something does without exposing how."

  • private fields + public methods → encapsulation, not the other three.
  • Overriding → runtime polymorphism; overloading → compile-time polymorphism.
  • Abstract classes and interfaces are the tools abstraction is built with, not abstraction itself.
📖 Explanation ▾

Encapsulation is about control, not secrecy for its own sake: marking fields private and only letting outside code touch them through methods means every change can be validated, logged, or rejected in one place.

Inheritance is a code-reuse relationship — a subclass automatically gets a parent's fields and methods via extends, and can override the ones that need to behave differently. It's an "is-a" relationship: a Dog really is an Animal, not just borrowing its code.

Polymorphism is what makes that inheritance relationship useful at a distance: code written against the parent type (Animal a = ...) calls a.makeSound() without knowing or caring which subclass a actually is — the JVM looks up the real object's own overridden method at runtime (dynamic dispatch). Overloading is the compile-time sibling: the compiler picks which same-named method to call purely from the declared argument types, before the program ever runs.

Abstraction is the design habit of exposing only what a caller needs (a type, an interface, a method signature) while keeping the actual implementation free to change underneath it — abstract classes and interfaces are two of the mechanisms Java gives you to do this, not the idea itself.

💻 See the code ▾
☕ Java 
class Account {
    private double balance;         // encapsulation
    public void deposit(double amt) {
        if (amt > 0) balance += amt;  // ✅ validated here, nowhere else
    }
}

Outside code can never set balance directly — only through a method that can check it.

☕ Java 
class Animal { void makeSound() { ... } }
class Dog extends Animal {      // inheritance
    @Override
    void makeSound() { /* bark */ }  // polymorphism — runs for a real Dog
}
Animal a = new Dog();
a.makeSound();                         // ✅ Dog's version runs, decided at runtime

a is declared as Animal, but the actual object's override is what runs.

🧭 Use Cases — recognize these when they happen to you ▾
1 An interviewer asks you to design a class and you jump straight to fields

A public mutable field is the opposite of encapsulation — say it out loud: field stays private, a method controls every change. This is the single fastest way to show (or fail to show) pillar #1 in a live design question.

RememberPublic mutable field → missing encapsulation, every time.
2 Several classes share the same fields and methods, copy-pasted

Duplicated fields/methods across sibling classes is the clearest signal to pull the shared part into a base class and let each sibling extends it — inheritance's whole job is removing exactly this copy-paste.

RememberSame fields in multiple classes → pull up into a shared parent.
3 You call a Dog-typed override but through an Animal reference, and expect Animal's version to run

The declared type (Animal) only matters for what methods you're allowed to call — which override actually runs is always decided from the object's real runtime type, never the variable's declared type.

RememberOverriding dispatches on the real object, not the declared variable type.
🌍 Real-world example ▾

A car. You drive it through a steering wheel and pedals (abstraction) without touching the engine wiring directly (encapsulation). A sports car and a hatchback both extend "vehicle" and inherit things like having wheels and a fuel tank (inheritance), but pressing the accelerator produces a very different result in each one (polymorphism).
