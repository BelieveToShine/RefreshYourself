🔥 Web API · Basic · Must Know

URL, header, or query string — which one is "correct" for versioning?

"What are the common ways to version an API, and what are the trade-offs of each?"

Why it matters ▾
  • Every API that survives long enough has to change — versioning is how you change it without breaking existing callers.
  • Picking a strategy without knowing its trade-off causes real pain later: silent defaults, broken caching, angry consumers.
  • A common interview opener because it's easy to have a favorite, but the actual test is knowing all three trade-offs.
🔥 Easy interview recall

/v2/orders → URL segment, visible & cacheable

Api-Version: 2 → header, clean URL but easy to forget

?api-version=2 → query string, easy to add, easy to omit

Think: URL → shows in the address bar Header → hides in the request Query → hides in plain sight

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming one versioning strategy is objectively "correct." Real APIs split roughly evenly between URL-segment and header-based versioning (Stripe, GitHub, and others both exist) — the interview-worthy point is knowing each option's trade-offs, not picking a winner.

🔄 Likely Follow-up

"Once you've picked a strategy, how do you decide WHEN to bump the version vs. just adding a field?" A genuinely additive, backward-compatible change — a new optional field, a new endpoint — usually doesn't need a version bump at all. A version bump is for breaking changes only: removing or renaming a field, or changing what one means. See Backward Compatibility for the full rule.

🎯 Say this in the interview — the exact lines to land

"There are three common ways to version an API: a URL segment like /v2/orders, a custom header like Api-Version: 2, or a query string like ?api-version=2. None of them is universally correct — it's a trade-off between visibility, caching, and how easy it is for a consumer to forget or omit it."

  • /v2/orders → URL segment: most visible and cache-friendly, but puts something arguably outside the resource's identity into the URI.
  • Api-Version: 2 → header: keeps the URL clean, but isn't discoverable from a browser and is easy for a consumer to forget.
  • ?api-version=2 → query string: quick to add, but easy to omit and can complicate caching at the "same" URL.
  • A version bump is for breaking changes only — additive fields or endpoints don't need one.
📖 Explanation ▾

URL segment versioning puts the version right in the path — /v1/orders vs /v2/orders. It's the most visible option: anyone can see the version just by looking at the request, and caches naturally treat each version as a different resource. The trade-off is that the version isn't really part of what the resource is — /v2/orders and /v1/orders both mean "orders," yet the version now lives inside the identifier for it.

A custom header, like Api-Version: 2, keeps the URL itself clean and stable. The cost is discoverability — you can't just visit a URL in a browser and see which version you're getting, and a consumer who forgets to set the header silently falls back to whatever the server treats as default.

A query string, like ?api-version=2, is the easiest to bolt onto an existing endpoint incrementally. It shares URL segment's visibility, but an omitted parameter is just as silent as a forgotten header — and because it's technically part of the URL, some caches key on it and some strip it, so "the same URL" can quietly mean two different versions depending on the cache in front of it.

💻 See the code ▾
C# 
[ApiController]
[Route]("api/v2/orders")   // the version is just another path segment
public class OrdersV2Controller : ControllerBase
{
    [HttpGet]
    public IActionResult Get() => Ok(GetOrders());  // ✅ /api/v2/orders hits this
}

The version is baked into the route — no extra package needed for this much.

C# 
[HttpGet("orders")]
public IActionResult Get([FromHeader(Name = "Api-Version")] string? apiVersion)
{
    if (apiVersion == "2") return Ok(GetOrdersV2());  // ✅ same URL, different header
    return Ok(GetOrdersV1());  // ❌ forgot the header? silently gets v1
}

Same URL for every version — the header decides, and a missing header fails silently.

C# 
[HttpGet("orders")]
public IActionResult Get([FromQuery(Name = "api-version")] string apiVersion = "1")
{
    // ⚠️ the default is exactly what makes an omitted version silent, not an error
    return apiVersion == "2" ? Ok(GetOrdersV2()) : Ok(GetOrdersV1());
}

Quick to add — a query parameter with a default. That default is the whole risk.

🌍 Real-world example ▾

Think of mailing a letter. A URL segment is like writing the year right on the front of the envelope — anyone sorting the mail sees it immediately. A header is like a sticky note tucked inside — it travels with the letter, but only if someone remembers to look for it. A query string is like adding it to the address line itself — easy to jot down, just as easy to leave off by accident.
