Stacked decorators apply bottom-up but unwind top-down — like nested function calls, because that's exactly what they are

"Two decorators are stacked on the same function — in what order do their 'before call' and 'after call' logic actually execute?"

Why it matters ▾
  • Tests whether @decorator is understood as real code (f = decorator(f)), not "magic syntax."
  • Comes up any time two decorators are combined — logging + caching, or auth + caching — where the actual order changes behavior.
  • A common way interviewers check whether you can trace execution order, not just recite what a decorator "is."
🔥 Easy interview recall

Stacked decorators = "closest to the function wraps first, but runs its 'before' last."

Think: @dec_a over @dec_b over def f is dec_a(dec_b(f)) — nested like matryoshka dolls, and the outer doll is always the first one you see and the last one you close.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Decorator order doesn't matter." It does — the top-listed decorator wraps outermost, not "runs first" in some flat sense, so @login_required above @cache_result checks auth before the cache is ever touched, while swapping the two would let an unauthenticated request hit the cache first.

🔄 Likely Follow-up

"What are decorators actually used for in real code?" Authentication (reject a request before the view even runs), logging/timing (wrap the call with before-and-after logic), caching (skip the real call entirely on a hit), and retry (wrap the call in a loop on failure).

🎯 Say this in the interview — the exact lines to land

"Stacked decorators wrap bottom-up but execute like nested calls — the one closest to the function runs its 'before' logic last and its 'after' logic first, exactly the way nested function calls unwind."

  • @decorator → sugar for f = decorator(f) — no hidden magic.
  • Stacking → wraps bottom-up: @dec_a over @dec_b over f is dec_a(dec_b(f)).
  • functools.wraps → preserves the real function's identity — name, docstring — for introspection and debugging.
  • Order matters → whenever decorators aren't independent, like checking auth before even considering the cache.
📖 Explanation ▾

A decorator is just a function that takes a function and returns another function — usually one that wraps the original with extra behavior. @decorator written above def f(): ... is shorthand for exactly one thing: f = decorator(f), run right after f is defined.

Stack two decorators — @dec_a above @dec_b above def f(): ... — and that sugar applies bottom-up: it's equivalent to f = dec_a(dec_b(f)). dec_b wraps the real f first, since it's closest to the function; dec_a then wraps whatever dec_b produced. That's why dec_a ends up as the outermost layer even though it's listed first — "listed first" means "wraps last," not "runs first" in any flat sense.

functools.wraps copies the original function's __name__, __doc__, and a few other attributes onto the wrapper function. Skip it, and every decorated function's introspection (its name in a debugger, help(), a stack trace) shows the generic wrapper's identity instead of the real function's — a small thing that quietly makes debugging harder.

💻 See the code ▾
Python 
def dec_a(func):
    def wrapper(*args, **kwargs):
        print("A: before")
        result = func(*args, **kwargs)
        print("A: after")
        return result
    return wrapper

def dec_b(func):
    def wrapper(*args, **kwargs):
        print("B: before")
        result = func(*args, **kwargs)
        print("B: after")
        return result
    return wrapper

@dec_a
@dec_b
def f():
    print("f body")

f()

Predict the output: In what order do "before" and "after" logic actually print?

Answer: A: before → B: before → f body → B: after → A: after. dec_a is the outermost wrapper — the whole thing is built as dec_a(dec_b(f)) — so its "before" logic runs first and its "after" logic runs last, nested exactly like the function calls it's built from.

🌍 Real-world example ▾

@login_required above @cache_result above def view(request): ... — the order here is deliberate, not cosmetic. login_required wraps outermost, so it checks authentication before cache_result ever runs; swap the two and an unauthenticated request could hit the cache before anyone checks who's asking.
