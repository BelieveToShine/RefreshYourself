Props — a one-way street, not a shared value

"How does a parent component pass data to a child component in Vue?"

Why it matters ▾
📨 Props
❗ ProblemA child component needs data from the outside world (a title, a user object) but it can't just reach into its parent's data directly — if it could, any child could silently change state the parent thinks it owns.
✅ SolutionProps are an explicit, declared, one-way channel from parent to child — the parent decides what to send, and the child only ever reads it.
RecallProps = explicit, one-way data flow — parent → child, never the other way.
🔥 Easy interview recall

Props = "data the parent hands down, the child only reads."

Think: defineProps declares the contract — the child never writes back through it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Mutating a prop directly inside the child (someProp.value = x). Vue warns against this because the parent is the real source of truth — the child should emit an event asking the parent to change it instead.

🔄 Likely Follow-up

"How do you give a prop a default value or make it required?" Use the object form of props — { type: String, required: true } or { type: Number, default: 0 } — which also gives richer validation than a plain array of prop names.

🎯 Say this in the interview — the exact lines to land

"Props are how a parent passes data down to a child — declared explicitly with defineProps, and strictly one-way. The child can read a prop but never write to it directly; if it needs to change something, it emits an event and lets the parent decide."

  • Props flow parent → child only — never the reverse.
  • Declared explicitly with defineProps (or props: {} in Options API) — never implicit.
  • Object-form props add type, required, and default — richer than a plain name array.
  • A child that needs to change a prop's value emits an event instead of mutating it.
📖 Explanation ▾

A prop is a piece of data a parent hands down to a child, declared explicitly so the contract is visible — defineProps(['title']) in <script setup>, or an equivalent props: {} option. Once declared, the child can read the prop anywhere in its template or script, but it's still the parent's value — the child is only borrowing it.

The object form of a prop declaration — { type: String, required: true }, or { type: Number, default: 0 } — adds validation Vue checks in development: a missing required prop or a wrong type logs a console warning, which a plain array of names can't do.

Because props are one-way, a child is never meant to reassign one. Vue even logs a warning in development if you try. The actual way for a child to influence its parent's data is the mirror-image mechanism — emit — which is its own topic right after this one.

💻 See the code ▾
Vue 
<!-- Parent.vue -->
<UserCard :name="user.name" />

The parent decides the value and passes it down — :name binds it to the name prop.

Vue 
<!-- UserCard.vue -->
<script setup>
const props = defineProps({
  name: { type: String, required: true }  // explicit contract
});
</script>

<template>
  <h3>{{ props.name }}</h3>      // ✅ read-only use
</template>

The object form validates type and required in development — a plain ['name'] array can't.

Vue 
props.name = "Someone Else";  // ❌ Vue warns — props are read-only here

Reassigning a prop doesn't change the parent's value and logs a warning — the fix is to emit a request instead.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're building a reusable display component (a card, a badge, a row)

A <UserCard> or <Badge> that gets reused across the app takes its content entirely through props — the parent always decides what's shown. This is the #1 scenario you'll actually run into.

RememberReusable display component → content comes in entirely through props.
2 You're passing a config/options object down several levels

Each level only forwards what the next one declared as its own props — there's no shortcut that skips a level. At enough levels this gets repetitive, which is exactly the problem provide/inject (Intermediate) solves instead.

RememberDeep prop chains → every level re-declares and re-passes it.
3 A child needs a local, editable copy of a prop's value

An editable form field that starts from a passed-in value shouldn't mutate the prop itself — initialize a local ref from the prop's starting value instead, and keep the two deliberately separate.

RememberNeed to edit it locally → copy into your own ref, don't mutate the prop.
🌍 Real-world example ▾

Think of a form letter. The parent fills in the blanks (name, date, amount) and hands the letter to the child to display. The child can read every field on the page, but it can't reach back and change what the parent originally wrote — if something needs to change, it has to ask.
