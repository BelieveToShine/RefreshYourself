Peek-lock, complete, redeliver — the real lifecycle of one message

"How does a producer/consumer system actually get wired together around Service Bus?"

Why it matters ▾
  • Checks whether you understand how a real messaging system stays reliable — not just that Service Bus exists as a product name.
  • Comes up any time the conversation turns to distributed systems, event-driven design, or "how do you guarantee a message doesn't get lost."
  • A very common follow-up after any "why use a queue" question — interviewers want the actual mechanics, not the marketing pitch.
🔥 Easy interview recall

Peek-lock → locked, invisible to other consumers

Complete → gone for good

No complete → redelivered, not lost

Think: CompleteMessageAsync is the only thing that removes a message for good.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It only got processed once, right?" Forgetting to call CompleteMessageAsync — or crashing before it runs — lets the peek-lock expire, so the message becomes visible again and gets redelivered; that's Service Bus working correctly, not a bug, and it's exactly why a non-idempotent consumer can end up processing the same message twice.

🔄 Likely Follow-up

"So does that mean consumers must be idempotent?" Yes — Service Bus guarantees at-least-once delivery, so a message can arrive more than once in edge cases (a crash mid-processing, a lock timeout); a well-designed consumer has to handle a duplicate delivery safely.

🎯 Say this in the interview — the exact lines to land

"A message is peek-locked while processing and only removed once explicitly completed — that's what makes retries safe, but it also means every consumer has to be idempotent, because the same message can be delivered more than once."

  • Peek-lock → locks a message for you, it doesn't delete it yet.
  • CompleteMessageAsync → the only thing that removes it for good.
  • No complete before the lock times out → automatic redelivery, not data loss.
  • Idempotency key → the standard defense against processing a duplicate twice.
  • Sessions → guarantee ordered processing for a related group of messages.
📖 Explanation ▾

A real architecture around Service Bus has three moving parts. Producers send messages — usually through a client SDK or a binding (e.g. an Azure Functions output binding). The Service Bus namespace hosts the queues or topics that hold those messages. One or more consumers pull messages out, either with a manual receive loop or an event-driven trigger, such as a Function's Service Bus trigger, that fires per message.

When a consumer receives a message under the default peek-lock mode, that message is locked — it stays in the queue but becomes invisible to every other consumer — for a set lock duration while it's being processed. If the consumer calls CompleteMessageAsync before that lock expires, the message is removed for good. If it doesn't — a crash, an unhandled exception, or simply forgetting the call — the lock times out and the message becomes visible again, ready to be redelivered. That's the mechanism that makes safe retries possible without ever losing a message.

Sessions extend this for messages that have to stay in order. Instead of locking one message at a time, a session lock hands a whole related group of messages (all sharing a session ID — e.g. every message for one customer's order) to a single consumer, so they get processed in the order they arrived rather than being picked up out of order by whichever consumer happens to be free.

💻 See the code ▾
C# 
processor.ProcessMessageAsync += async args =>
{
    var order = args.Message.Body.ToObjectFromJson<OrderMessage>();
    await ApplyOrderAsync(order); // do the real work

    // ✅ explicit acknowledgement — this is what removes it from the queue
    await args.CompleteMessageAsync(args.Message);
};

Without that last line, the message stays peek-locked only until the lock times out — then it's redelivered, even though the work above already ran.

🌍 Real-world example ▾

A payment-processing consumer checks an idempotency key — a unique ID carried on the message — before applying its effect, and skips it if that key has already been applied. So on the rare redelivery (a crash right after charging the card but before completing the message), the consumer sees the same key again, does nothing, and the customer is never charged twice.
