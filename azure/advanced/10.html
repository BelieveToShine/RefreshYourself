Deleted the line — but is the secret still there?

Someone accidentally commits a real password to a public GitHub repo — walk through what you actually do.

Why it matters ▾
🔑 Leaked Secret
❗ ProblemA real credential pushed to a public repo is already in the git history of every clone and fork, and quite possibly already scraped by a bot — deleting the line and committing again leaves the actual secret sitting untouched in history.
✅ SolutionRotate the exposed credential immediately — treat it as compromised no matter how fast the repo gets "fixed" — then clean it out of history and move secrets out of source control entirely going forward.
RecallRotate first, clean history second — deleting the line alone fixes nothing.
🔥 Easy interview recall

A leaked secret = "already compromised — rotate it, don't just hide it."

Think: deleting the line only hides it from the latest commit — the history still has it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Delete the line and commit again" is not the fix. The secret is still sitting in the git history of every clone, every fork, and likely GitHub's own cache — the exposed credential must be rotated regardless of what happens to the repo.

🔄 Likely Follow-up

"Why does this specifically push teams toward a secrets manager like Key Vault?" A secrets manager means the real credential never has to exist as a literal string in any file a developer edits or a repo tracks at all — the app fetches it at runtime, so there's nothing in source control to leak in the first place.

Only after that does cleaning the repo matter: remove it from history with a tool like git filter-repo or BFG, force-push the cleaned history, and have everyone re-clone. Going forward, move secrets into something like Key Vault instead of source control."

  • Deleting the line is not a fix — the original commit still exists in history, forks, and clones.

📖 Explanation ▾

The critical first fact: removing the commit from the branch does not remove the secret. Git keeps every commit's full history by default, so the real credential is still sitting in that old commit — in your own local repo, in every teammate's clone, in every fork, and possibly already scraped by a bot (GitHub's own secret scanning, and plenty of third parties, watch public pushes for exactly this). The real first step is rotating the exposed credential immediately, treating it as already compromised no matter how fast the repo gets "fixed."

Only after rotation does cleaning the repo actually matter: remove the secret from history with a history-rewriting tool (git filter-repo or BFG Repo-Cleaner — not just a new commit deleting the line, which leaves the old commit untouched), force-push the cleaned history, and have every collaborator re-clone rather than pull, since their local history still has the old commit too.

Going forward, the fix that actually prevents a repeat is moving secrets out of source control entirely — environment variables or, on Azure, Key Vault — plus a pre-commit secret scanner that catches the next one before it's ever pushed.

🧭 Use Cases — recognize these when they happen to you ▾
1 The repo is public and the secret's format matches a recognized provider pattern

GitHub's secret scanning — and automatic revocation for some partner providers — may already have acted on a recognized token format in a public repo. Never assume that happened for your specific secret: rotate it yourself, immediately, and verify independently rather than waiting to find out.

RememberDon't wait to see if something else caught it — rotate it yourself.
2 The repo is private, so it feels safer

A private repo narrows who could already have the secret — it doesn't make the leak safe. Every collaborator, every CI job that ever cloned it, and the full history forever still has it. Rotate exactly the same way you would for a public repo.

Remember"Private" narrows exposure — it doesn't remove it.
3 History was already force-pushed "clean" days ago, but the credential was never rotated

A force-push rewrites the branch on the server, but any fork, clone, or CI cache made before that still has the original commit with the secret inside it. Cleaning history was never the fix on its own — if the credential wasn't rotated, it's still exactly as compromised as the day it was pushed.

RememberA force-push doesn't reach clones that already exist — only rotation does.
🌍 Real-world example ▾

A connection string with a real password gets pushed to a public repo by accident. The direct answer: rotate that password right away, before touching anything else in the repo — the old commit staying visible in history for a few more minutes while you clean it up properly matters far less than the password itself still being valid.
