track() / trigger() — a dependency list rebuilt every single run

"What actually happens internally when a computed property 're-evaluates'?"

Why it matters ▾
🔁 track() / trigger()
❗ ProblemIf Vue declared a computed's dependencies once upfront, a property only read inside one branch of an if would be wrong half the time — tracked when it shouldn't be, or missed when it should be.
✅ SolutionEvery reactive property keeps its own Set of effects that depend on it. track() (called from get) adds whichever effect is currently running to that property's Set; trigger() (called from set) loops through that Set and re-runs each one. Because track() runs fresh on every execution, only properties actually read on the most recent run stay tracked.
Recalltrack()/trigger() rebuild the list fresh — it's never fixed upfront.
🔥 Easy interview recall

Dependency tracking = "rebuilt from scratch, every single run."

Think: track() → adds the running effect to that property's Set trigger() → loops that Set, re-runs every effect in it

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Dependency tracking is not static or declared upfront. It's dynamic — an effect only depends on whatever reactive properties it actually read during its most recent execution, which is why a conditionally-read property can drop in or out of a dependency Set between runs.

🔄 Likely Follow-up

"Does this mean an effect's dependencies can change between runs?" Yes — if an if branch means a property wasn't read this time, it's no longer tracked as a dependency until a future run reads it again. This is deliberate: it's what lets Vue avoid over-subscribing to properties an effect doesn't currently care about.

🎯 Say this in the interview — the exact lines to land

"Every reactive property keeps its own Set of effects that depend on it. track() — called from the Proxy's get trap — adds the currently-running effect to that property's Set; trigger() — called from set — loops through that Set and re-runs each effect in it. Because track() runs fresh on every execution, dependencies are dynamic: an effect only depends on whatever it actually read on its most recent run, not a fixed list declared upfront."

  • track() → adds the running effect to that property's own dependency Set.
  • trigger() → loops the Set and re-runs every effect inside it.
  • Dependencies → re-evaluated every run, never declared statically upfront.
  • A conditionally-read property → drops out of the Set until a future run reads it again.
📖 Explanation ▾

Internally, Vue keeps a dependency map for every reactive object, with one Set per property — that Set holds every effect currently depending on it. track() is the function the get trap calls to add "whichever effect is running right now" into that Set. trigger() is what the set trap calls to walk that same Set and re-run every effect in it.

Before an effect re-runs, Vue first removes it from every Set it was part of on its previous run, then lets track() re-add it only to the Sets for properties it actually reads this time. That's the real mechanism behind a property "dropping out": if an if-branch skips reading it this run, nothing re-adds the effect back to that property's Set — it simply stops being a dependency until a future run reads that property again.

This dynamic behavior is what makes computed and watch feel effortless: you never declare "this depends on a and b" yourself — Vue figures it out by watching what the function actually touches, every time it runs.

💻 See the code ▾
JavaScript 
const state = reactive({ cond: true, a: 1, b: 2 })

effect(() => {
  console.log(state.cond ? state.a : state.b)  // tracks cond + whichever branch ran
})

state.cond = false   // ✅ re-runs — this time tracks 'b', drops 'a'
state.a = 99        // ❌ no re-run — 'a' isn't tracked anymore

After state.cond flips, the effect's own dependency Set membership for a and b has swapped — not just "both are tracked now."

JavaScript 
const double = computed(() => state.a * 2)  // reading state.a → tracked in a's Set
state.a++                                    // ✅ a's Set re-runs the computed's getter

Exactly the same track()/trigger() mechanism — computed is just an effect like any other.

🧭 Use Cases — recognize these when they happen to you ▾
1 A computed getter branches with if/else on a reactive flag

Only the branch that actually executes gets tracked — the untaken branch's property is never added to anything this run.

RememberOnly the branch that runs gets tracked, not both.
2 You change a property that was tracked on an earlier run, but not the latest one

A candidate might expect this write to still trigger the effect because it "used to" depend on a. A common interview trap: once the branch stopped reading a, the effect was removed from a's Set on that run — the old dependency doesn't linger.

RememberDropped dependencies don't linger — they're gone until re-read.
3 Two separate watchers read two different properties on the same object

Each watcher's effect ends up in only the Set for the property it actually reads — changing count never wakes the name watcher, and vice versa.

RememberSeparate properties → separate Sets → no cross-wake-up.
🌍 Real-world example ▾

Think of each property as its own mailing-list sign-up sheet. Every time an effect runs, it signs up for whichever property's list it actually checked that time — and it's dropped from any list it didn't check this run. When a property changes, Vue just mails everyone currently signed up to that one list.
