⭐ Should Know

<head> — the invisible tags that decide whether your page fits the screen at all

What goes inside the <head> of an HTML document, and if a page looks fine on desktop but tiny on mobile, what's the first metadata tag you'd check?

Why it matters ▾
  • Confirms you actually know the page skeleton — <!DOCTYPE html>, <html>, <head> vs. <body> — not just the tags that show up on screen.
  • "Fine on desktop, tiny on mobile" is one of the most common real front-end bugs, so it's a frequent troubleshooting question, not just trivia.
  • Open Graph tags decide what a shared link looks like on Slack, Twitter/X, and LinkedIn — a "why does our link preview look wrong" question comes up in real team interviews too.
🔥 Easy interview recall

<head> → metadata, never shown on screen

<body> → the content that actually renders

viewport meta → tells the phone to render at its real width

Think: charset → how to read the bytes viewport → how wide to draw the page title/description → what shows in the tab & search results

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The viewport meta tag does not "make a site responsive." It only fixes the scaling baseline — render at the device's real width instead of an assumed desktop width — the page's CSS still has to actually be responsive (media queries, flexible layouts) for it to look good at that width.

🔄 Likely Follow-up

"What's the difference between the favicon link and the Open Graph image tag?" A favicon (<link rel="icon">) is the small icon shown in the browser tab and bookmarks; og:image is a separate, usually much larger image shown only in social/link-preview cards — different surfaces, usually different image files.

🎯 Say this in the interview — the exact lines to land

"The <head> holds a page's metadata — charset, title, meta description, viewport, favicon, and Open Graph tags — none of which render on screen. The single most common real bug tied to this is a missing or misconfigured viewport meta tag, which makes an otherwise-fine page render tiny on mobile because the browser falls back to a wide assumed desktop viewport."

  • Missing viewport meta → the #1 cause of "fine on desktop, tiny on mobile."
  • charset → declares the character encoding so text decodes correctly.
  • title vs. meta description → tab text vs. the snippet shown in search results.
  • canonical link → tells search engines which URL is the "real" one among near-duplicates.
  • Open Graph tags → control how a shared link previews on social platforms — a separate job from the favicon.
📖 Explanation ▾

Every HTML document starts with <!DOCTYPE html> — a signal that tells the browser to use standards mode instead of an old quirks-mode fallback — followed by one <html> root element split into exactly two children: <head> and <body>. The head never renders anything on screen; it's metadata about the page. The body is everything a visitor actually sees.

<meta> tags inside the head are simple name/value pairs the browser and other tools (search engines, chat apps) read. <meta charset="UTF-8"> tells the browser how to decode the page's bytes into text. <title> sets the browser tab text and the clickable link text in search results; a separate <meta name="description"> sets the paragraph shown underneath that link. <link rel="canonical"> points at the "real" URL when the same content is reachable through more than one address, so search engines don't split ranking signal across duplicates. <link rel="icon"> sets the favicon shown in the tab and bookmarks.

The viewport meta tag solves one specific mobile problem: without it, many mobile browsers assume the page was built for a wide desktop screen and render it at that assumed width, then shrink the whole thing down to fit the actual screen — which is why everything looks tiny and zoomed out. With width=device-width, initial-scale=1.0, the browser renders at the device's real width instead. Open Graph tags (og:title, og:description, og:image) are a separate metadata set read by social platforms to build the preview card shown when a link is shared — they don't affect search ranking or how the page looks in a normal browser tab.

💻 See the code ▾
HTML 
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">          // how to decode the bytes
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Product Page</title>
</head>

The minimum every page needs — charset first, viewport right after it, then a real title.

HTML 
<meta name="description" content="Lightweight running shoes for every distance.">
<link rel="canonical" href="https://example.com/shoes/running">
<link rel="icon" href="/favicon.ico">

description feeds the search snippet, canonical points at the one "real" URL, icon is the tab favicon.

HTML 
<meta property="og:title" content="Running Shoes — Example Store">
<meta property="og:description" content="Lightweight and breathable.">
<meta property="og:image" content="https://example.com/shoes-preview.jpg">

Read by social platforms to build the preview card when this link is shared on Slack, Twitter/X, or LinkedIn — a separate job from the favicon.

🌍 Real-world example ▾

Scenario: your page looks fine on desktop but is tiny on mobile — what HTML metadata would you check first?

The viewport meta tag. A missing or misconfigured <meta name="viewport"> is the single most common cause of exactly this symptom — without it, many mobile browsers assume a much wider virtual viewport and shrink everything to fit.
