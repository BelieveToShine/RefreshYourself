Data fetching — the request outlives the component that started it

"How do you avoid a race condition when a component fetches data, and what happens if it unmounts mid-request?"

Why it matters ▾
🐢 Race Condition
❗ ProblemA fetch has no idea its component might unmount or get superseded — a slower, earlier-fired request can still resolve after a faster, later one, silently overwriting the correct, newer data already on screen.
✅ SolutionTrack which request is actually the latest (a ref, an incrementing id, or AbortController) and discard or cancel any response that isn't from it, so a stale result can never overwrite a newer one.
RecallA fetch outlives its component — without cleanup, a slow, now-irrelevant request can overwrite newer data when it finally arrives.
🔥 Easy interview recall

A fetch outlives the component that started it — without cleanup, a slow, now-irrelevant request can still overwrite newer data when it finally arrives.

Think: request A (slow) can land after request B (fast) and stomp on the correct result.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A fetch does not cancel itself when the component unmounts. It keeps running in the background regardless — without explicit cleanup (an AbortController, or checking a mounted flag before calling setState), you risk a "setState on an unmounted component" issue, or applying data after the component has already moved on.

🔄 Likely Follow-up

"What's the actual race-condition risk with two fetches?" If an earlier-fired request is slower than a later one, its response can arrive after the later request's and overwrite the correct, newer result with stale data — you need to track which request is actually the latest and ignore any late-arriving response that's no longer current.

🎯 Say this in the interview — the exact lines to land

"I fetch inside useEffect, track which request is the latest with a ref or an AbortController, and ignore or cancel any response that isn't from that latest request — the same cleanup also stops setState from firing after the component has unmounted."

  • Fetching → a side effect, belongs in useEffect, not the render body.
  • Loading/error/success → three real states, not just "has data or not."
  • Unmount mid-request → the fetch keeps running; clean up with AbortController or a mounted check.
  • Race condition → a slower, earlier request can land after a faster, later one and overwrite it.
  • API state vs. UI state → keep server data separate from purely local state like "is this open."
📖 Explanation ▾

Fetching data is a side effect — it reaches outside the component to talk to a server — so it belongs inside useEffect (or a dedicated data-fetching Hook/library), never directly in the render body. Once the request starts, the component needs three distinct states to track it honestly: loading, error, and success — "do I have data yet" isn't enough, because a failed request and a still-pending one can look identical if you only check for data.

A fetch has no idea the component that started it might disappear. If the component unmounts before the response arrives, the request keeps running in the background regardless — cleanup (an AbortController that cancels the request, or a ref that checks "is this still mounted" before calling setState) is what stops a late response from updating a component that's already gone.

That same lateness causes the classic race condition: if an earlier request is slower than a request fired after it, the earlier one's response can still arrive last and overwrite the correct, newer result with stale data. The fix is tracking which request is actually the latest — a ref, an incrementing id, or AbortController cancellation — and discarding any response that isn't from it. It also helps to keep API state (server data, with its own caching and staleness concerns) conceptually separate from UI state (purely local things like "is this dropdown open") — and once caching, deduplication, and refetch logic start getting hand-rolled repeatedly across the app, that's the point to reach for a dedicated data-fetching library instead of rebuilding it again.

💻 See the code ▾
JSX 
useEffect(() => {
  const controller = new AbortController();

  fetch(url, { signal: controller.signal })
    .then(res => res.json())
    .then(data => setData(data))
    .catch(err => {
      if (err.name !== "AbortError") setError(err); // ignore our own cancel
    });

  return () => controller.abort(); // cancels the in-flight request
}, [url]);

Cleanup runs before the next effect and on unmount — either way, the in-flight request gets cancelled.

JSX 
const latestRequestId = useRef(0);

useEffect(() => {
  const requestId = ++latestRequestId.current; // tag this call as "the current one"

  fetchData(query).then(result => {
    if (requestId === latestRequestId.current) {
      setData(result); // only apply it if nothing newer has started
    } // else: a later request already took over — discard this stale result
  });
}, [query]);

No cancellation here — a stale response just gets ignored instead of applied.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your search box fires a new fetch on every keystroke

Every keystroke can fire its own fetch, so more than one request is often in flight at once — this is the #1 way a real race condition actually gets triggered.

RememberTypeahead/search → multiple in-flight requests is the normal case, not the exception.
2 The user navigates away while a fetch is still in flight

The fetch itself doesn't know the component is gone — without an AbortController or a mounted check, the response still tries to run setState on a component that's no longer there.

RememberUnmount doesn't cancel a fetch — cleanup has to do that explicitly.
3 You assume the request fired last also arrives last

Fire order and arrival order aren't the same thing. A great interview trap — candidates often assume whichever request was sent later must also finish later, when a slow earlier request can land after it and stomp on the right answer.

RememberFire order ≠ arrival order — always check which response is actually the latest.
🌍 Real-world example ▾

You mail two letters on different days — the first by a slower route, the second by a faster one. If you just act on whichever letter arrives last without checking the postmarks, you'd act on the older information by mistake, even though it physically showed up second.
