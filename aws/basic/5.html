S3 — object storage, not a mountable drive

"How would you design secure file storage on S3?"

Why it matters ▾
  • S3 shows up in almost every AWS interview — as file storage, a static website, a data lake, or a backup target.
  • The security question separates candidates who know real AWS incidents from ones who only know the API.
  • Storage classes and lifecycle rules are the standard "how do you control cost" follow-up.
🔥 Easy interview recall

S3 = "a giant key-value store for whole files, not a hard drive."

Think: every object has a bucket + key address, fetched over HTTP — there's no folder tree underneath, just that address.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Locking down IAM is not enough to keep a bucket private. A bucket's own policy or a legacy ACL can make it public regardless of what IAM says about who's allowed to configure it — this exact gap is behind most public S3 data breaches.

🔄 Likely Follow-up

"How do you prevent public S3 access in practice?" Enable "Block Public Access" at the account and bucket level (the current default for new buckets), and manage access through bucket policies/IAM rather than legacy ACLs.

🎯 Say this in the interview — the exact lines to land

"S3 security starts with Block Public Access and bucket policies, not IAM alone — IAM only controls who can configure the bucket, while the bucket policy and Block Public Access setting decide who can actually reach the objects. On top of that, I'd use storage-class lifecycle rules to move older objects to cheaper tiers automatically."

  • Block Public Access → keep it enabled at the account and bucket level; it overrides a policy that would otherwise expose objects.
  • Bucket policy / IAM → the real access controls — legacy ACLs should be avoided for new buckets.
  • Lifecycle rules → Standard → Standard-IA → Glacier, cutting storage cost as objects age and get accessed less.
  • Presigned URLs → grant short-lived access to a private object without ever making the bucket public.
📖 Explanation ▾

S3 is object storage: each object is a whole file plus metadata, stored under a bucket + key address and accessed over HTTP/API calls — there's no filesystem underneath to mount, unlike block storage (EBS) that an EC2 instance attaches to and reads/writes like a disk.

Storage classes trade cost against retrieval speed and access frequency. Standard is the default for frequently accessed data. Intelligent-Tiering watches access patterns and moves objects between tiers automatically. Standard-IA suits data accessed rarely but needed instantly when it is. The Glacier family is for archival data, trading a retrieval delay (minutes to hours, depending on the tier) for a much lower storage price. Versioning keeps every version of an object ever written, so an accidental overwrite or delete can be recovered from an older version.

Encryption at rest comes in two common flavors: SSE-S3 uses keys AWS manages entirely, while SSE-KMS uses customer-managed keys through KMS, giving more control over key rotation and an audit trail of who used the key. Either way, encryption protects data at rest — it says nothing about who can reach the object over the network, which is a separate control.

💻 See the code ▾
Python (boto3) 
import boto3

s3 = boto3.client("s3")
url = s3.generate_presigned_url(          # ✅ temporary, scoped access
    "get_object",
    Params={"Bucket": b, "Key": k},
    ExpiresIn=3600                       # link stops working after 1 hour
)

The bucket itself stays private — this URL is the only thing that's temporarily allowed to reach that one object.

🌍 Real-world example ▾

A company lets users upload profile photos to a private S3 bucket. Instead of ever making the bucket or object public, the backend generates a short-lived presigned URL for each upload or download — the link works for an hour and then stops, and the bucket's own permissions never change.
