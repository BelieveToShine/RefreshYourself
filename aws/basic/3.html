IAM — where would you actually put the credentials?

"An EC2 application needs access to S3. Where would you actually put the credentials?"

Why it matters ▾
  • Almost always one of the first AWS questions asked — it directly tests whether you reach for a role instead of a stored key.
  • Explains a real production risk: a leaked access key is one of the most common real-world AWS security incidents.
  • Sets up the exact distinction interviewers probe next: a role's temporary, assumed credentials vs. a user's long-lived, fixed ones.
🔥 Easy interview recall

IAM Role → temporary creds, auto-rotated

Access Key → long-lived, risky if hard-coded

Policy → least privilege, attached to an identity

Think: EC2 needs S3 → attach a Role via an instance profile, never paste an access key into code.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Hard-coding an AWS access key into the app's code or config is not the right way to give an EC2 instance S3 access. The correct answer is an IAM role attached via an instance profile — it hands the instance temporary, auto-rotated credentials with zero secrets stored anywhere.

🔄 Likely Follow-up

"How does AWS resolve a conflict between an Allow and a Deny across multiple policies?" An explicit Deny anywhere in the evaluation always wins, regardless of how many Allow statements also apply.

🎯 Say this in the interview — the exact lines to land

"An EC2 app reaches S3 via an IAM role and instance profile — temporary credentials, never a stored key. STS issues those credentials on the fly and auto-rotates them, so there's no secret sitting in code or config to leak."

  • IAM role → temporary credentials via STS, auto-rotated, nothing hard-coded.
  • IAM user → long-lived credentials, reserved for a human or an external system that truly needs persistent access.
  • Least privilege → grant only the exact permissions needed, nothing more.
  • Explicit Deny → always wins over an Allow, no matter how many policies apply.
📖 Explanation ▾

IAM is AWS's identity and access system — it decides who (or what) can do what, to which resources. An IAM role is an identity with permissions attached, but with no fixed credentials of its own: something assumes it temporarily through AWS's Security Token Service (STS), which hands back short-lived, auto-rotated credentials for that session. An IAM user instead gets long-lived credentials up front — a better fit for a human logging in, or an external system that genuinely needs persistent access outside AWS's own resources.

Permissions come from policies, which can attach directly to an identity (identity-based) or sit on the resource itself, like an S3 bucket policy (resource-based). Whichever way permissions are granted, least privilege means giving only the exact access actually needed — and when AWS evaluates several policies together, an explicit Deny anywhere in that set always overrides every Allow, no matter how many Allows also apply.

💻 See the code ▾
Python (boto3) 
✅ No access key here — boto3 walks the default credential chain
and picks up the EC2 instance's attached IAM role automatically.
import boto3
s3 = boto3.client('s3')
s3.upload_file('report.csv', 'my-app-bucket', 'reports/report.csv')

Nothing here names a key — the role attached via the instance profile is where the actual credentials come from.

Python (boto3) 
❌ Don't do this — a fixed secret that can leak
s3 = boto3.client(
    's3',
    aws_access_key_id='AKIA...',
    aws_secret_access_key='wJalr...'
)

Any key typed into code or config is a secret that can leak — the role above needs none.

🌍 Real-world example ▾

A company's security review scans their codebase and flags every hard-coded AWS access key it finds — leftover from an early prototype where someone pasted a key straight into a config file. Each one gets replaced with an IAM role attached via an instance profile, so the affected services get the same S3 access with nothing left to leak, and the entire class of "leaked key" incidents disappears from that codebase.
