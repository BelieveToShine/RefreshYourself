MVC vs. Web API vs. Razor Pages — three frameworks, or just one?

"When would you reach for MVC, a Web API controller, or Razor Pages?"

Why it matters ▾
🖼️ MVC
❗ ProblemA feature needs a full server-rendered page with a shared layout, and the logic should stay out of the markup.
✅ SolutionA controller picks a view and hands it a model — the view only renders.
RecallMVC = the controller picks the view.
🔌 Web API
❗ ProblemA SPA, a mobile app, or another service wants data, not HTML.
✅ SolutionAn [ApiController] returns data (usually JSON) and rejects an invalid model with an automatic 400.
RecallWeb API = data out, automatic 400 in.
📄 Razor Pages
❗ ProblemA simple form-style page doesn't need a separate controller, view folder and model wiring.
✅ SolutionOne .cshtml plus its own PageModel — the page owns its handlers.
RecallRazor Pages = page + PageModel.
🔥 Easy interview recall

Same routing base, three shapes.

Think: MVC → controller + view, HTML out Web API → data out, automatic 400 Razor Pages → page + PageModel, no controller

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"They're three separate frameworks, so I pick one per app." They're three shapes on the same ASP.NET Core endpoint routing — one project can register and mix all three: a storefront in MVC, an API for the mobile app, a Razor Page for a small admin form.

🔄 Likely Follow-up

"Is Razor Pages a replacement for MVC?" No — both render HTML with Razor. MVC splits a feature across a controller, a view and a model; Razor Pages keeps each page's handlers next to its markup. Choose per feature, not per application.

🎯 Say this in the interview — the exact lines to land

"MVC, Web API and Razor Pages are three shapes on the same endpoint routing, not three frameworks. MVC controllers return rendered views, an [ApiController] returns data like JSON and rejects an invalid model with an automatic 400, and Razor Pages pair a page with its own PageModel for simple page-by-page work. One project can mix all three."

  • MVC → server-rendered pages with shared layouts — the controller picks a view.
  • Web API → data out (usually JSON) for a SPA, mobile app, or another service.
  • Razor Pages → simple page-by-page work — a .cshtml plus a PageModel, no controller.
  • Invalid model → MVC and Razor Pages you check ModelState.IsValid; [ApiController] answers 400 for you.
  • All three → one project, one routing system — mix them freely.
📖 Explanation ▾

These aren't three frameworks. Every request goes through endpoint routing, and MVC, Web API and Razor Pages are three shapes of endpoint built on it. What differs is what the endpoint produces and how its code is organised.

An MVC controller derives from Controller and returns View(model) — HTML. A Web API controller derives from ControllerBase and carries [ApiController]: it returns data through output formatters (JSON by default), and the attribute makes an invalid model a 400 response before your action even runs. Razor Pages starts each .cshtml with @page and pairs it with a PageModel whose handlers (OnGet, OnPost) play the role of actions. In MVC and Razor Pages the model-state check is yours to write.

Mixing is normal — register only what you use and map each one. Related pages: What Is MVC, Model Binding & Validation, Razor & Routing, Model Binding Internals, and the Web API track's What Is REST.

💻 See the code ▾
C# 
builder.Services.AddControllersWithViews();   // MVC + API controllers + views
builder.Services.AddRazorPages();             // Razor Pages

var app = builder.Build();
app.MapDefaultControllerRoute();   // conventional MVC route
app.MapControllers();              // attribute-routed controllers (API)
app.MapRazorPages();               // ✅ all three on one routing base
app.Run();

Register and map what you use — all three live in the same app.

C# 
// MVC: you check the model
public IActionResult Create(OrderDto dto)
{
    if (!ModelState.IsValid) return View(dto);   // ✅ re-show the form
    return RedirectToAction("Index");
}

// Web API: [ApiController] checks for you
[ApiController]
public class OrdersApiController : ControllerBase
{
    [HttpPost]
    public IActionResult Create(OrderDto dto) => Ok();   // ✅ bad model never gets here — 400 already sent
}

Same invalid input — MVC and Razor Pages need your check, an [ApiController] answers 400 itself.

🌍 Real-world example ▾

One online shop, three shapes. The public storefront is MVC (views with a shared layout), the mobile app calls Web API controllers for JSON, and the back-office "edit tag" form is a single Razor Page — all deployed as one app on the same routing.
