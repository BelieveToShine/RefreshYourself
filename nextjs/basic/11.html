The Metadata API — static for most pages, dynamic when content decides the tags

"How do you set a page's title/description for SEO in the App Router?"

Why it matters ▾
🏷️ The Metadata API
❗ ProblemSearch crawlers and social-media previews read the <head> tags from the initial server-rendered HTML — if a page sets its title/description client-side, the crawler never sees it.
✅ SolutionAn exported metadata object (static) or generateMetadata() function (dynamic, can fetch data first) produces that route's <head> tags server-side, before anything reaches the browser.
RecallMetadata API = SEO tags are already in the HTML before the browser even asks.
🔥 Easy interview recall

metadata object → static, no data needed

generateMetadata() → dynamic, can fetch first

Think: a child route's metadata merges with its parent layout's — it doesn't replace it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Setting document.title manually inside a Client Component for SEO. That only updates the title after the JS runs in the browser — too late for a crawler or social-media preview, which reads the initial server-rendered HTML's <head>, not what JavaScript changes afterward.

🔄 Likely Follow-up

"How does metadata merge across nested layouts?" A child route's metadata merges with — and can override specific fields of — its parent layout's metadata. A title.template lets a child customize just its own title segment while inheriting the rest.

🎯 Say this in the interview — the exact lines to land

"A static export const metadata object in page.js or layout.js sets that route's <head> tags. generateMetadata() is the dynamic equivalent — an async function that can fetch data first, for routes whose SEO tags depend on actual content."

  • metadata object → static, no data fetch needed.
  • generateMetadata() → async, fetches data before producing tags.
  • Nested layouts → child metadata merges with, overrides parts of, the parent's.
📖 Explanation ▾

Every layout.js or page.js can export a static metadata object — { title, description, ... } — and Next.js turns that into the actual <head> tags for that route, rendered server-side before the response is sent.

When the right title or description genuinely depends on data — a blog post's actual title from a database, say — a static object can't know it ahead of time. generateMetadata() is the async equivalent: it runs on the server, can fetch whatever data it needs, and returns the same shape of metadata object once that data is in hand.

Metadata isn't all-or-nothing per route either. A child route's metadata is merged with its parent layout's — fields the child doesn't set are inherited, and fields it does set override the parent. A title.template on the parent (e.g. "%s | My Blog") lets a child contribute just its own title segment while the surrounding template still applies.

💻 See the code ▾
JSX 
// app/about/page.js — static metadata
export const metadata = {
  title: 'About',
  description: 'Who we are',
};

No data fetch needed — this object is known ahead of time.

JSX 
// app/blog/[slug]/page.js — dynamic metadata
export async function generateMetadata({ params }) {
  const post = await getPost(params.slug);  // ✅ fetch first
  return { title: post.title, description: post.summary };
}

Runs on the server, fetches the post, then produces the metadata object.

🧭 Use Cases — recognize these when they happen to you ▾
1 A static marketing page — About, Pricing, Contact

Title and description never change for this route, so there's nothing to fetch — the plain metadata object is simpler and does the job. This is the #1 scenario you'll actually run into.

RememberFixed content → static metadata object.
2 A dynamic route — a blog post, a product page

The real title lives in a database row, keyed by the URL's slug — generateMetadata() fetches that row first, then returns its title/description as the page's metadata.

RememberTitle depends on fetched data → generateMetadata().
3 A teammate sets the title with document.title in a Client Component

By the time that JavaScript runs, the crawler or social-media bot has already read the server-rendered HTML — the title it saw was whatever (or nothing) was there before the client code ran.

RememberSEO tags → the Metadata API, never a client-side document.title set.
🌍 Real-world example ▾

It's the difference between a printed book's cover and a sticky note added after publishing. The Metadata API bakes the title into the page before it ever leaves the printer (the server) — a crawler sees the real cover. Setting it with client-side JS is the sticky note: it's there for a reader holding the book, but the catalog that already photographed the cover never saw it.
