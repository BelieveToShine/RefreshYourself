EF.CompileQuery() — skipping the lookup, not creating the cache

What is a compiled query, and when would you reach for one?

Why it matters ▾
⚙️ Normal Query
❗ ProblemWithout any caching, the same query called again and again would have to be resolved from scratch every single time — a real, repeated cost.
✅ SolutionEF Core resolves each query's shape automatically the first time it's seen, then every later call is just a cache lookup + match before executing — the safe default since the shape can vary freely per call.
RecallNormal query = resolved automatically, shape can vary, the default for virtually every query.
🧩 EF.CompileQuery()
❗ ProblemEven that already-fast cache lookup + match step is a small, real per-call cost — one that only becomes worth removing once profiling shows it matters at a genuinely high call volume.
✅ SolutionIt resolves one fixed-shape query once, explicitly, into a delegate — every call after skips the lookup and executes directly; used outside that measured, extremely hot, simple case, it's just added complexity for a saving too small to matter.
RecallEF.CompileQuery() = resolved once explicitly, shape fixed, only for a measured hot path.
🔥 Easy interview recall

Normal query → cached automatically, still looked up each call

EF.CompileQuery() → skips that lookup, straight to execute

Reach for it → only after measuring a real hot path

Think: EF Core already caches every query's plan. CompileQuery skips the lookup, not the caching itself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Compiled queries are not a default performance fix. EF Core already caches every query's plan automatically by shape — reach for EF.CompileQuery() only after measuring that the small remaining lookup cost matters at your actual call volume.

🔄 Likely Follow-up

"If EF Core already caches query plans automatically, what's actually left for EF.CompileQuery() to save you?" The small remaining cost of looking up and matching against that internal cache, plus the delegate invocation itself — genuinely small, but measurable at very high call volumes on simple queries.

🎯 Say this in the interview — the exact lines to land

"EF Core already caches query plans automatically, keyed by the shape of the query — EF.CompileQuery() just skips that remaining lookup step by pre-building a reusable delegate. It's a narrow, measured optimization for an extremely hot, simple, parameterized query — never a default performance practice."

  • Normal query → cached automatically by EF Core, no extra code needed.
  • EF.CompileQuery() → skips the cache lookup, straight to execution.
  • Query shape → must stay fixed; only parameter values can vary between calls.
  • Reach for it only → after measuring a genuine high-frequency hot path.
  • Default advice → EF Core's own caching is enough for virtually every query.
📖 Explanation ▾

EF Core builds an internal query-plan cache keyed by the shape of the LINQ expression tree, not the parameter values inside it — so calling the same query with a different id still hits the same cache entry. EF.CompileQuery() / EF.CompileAsyncQuery() pre-resolve that one specific shape once, ahead of time, into a plain delegate — so each call skips even that already-fast lookup/match step and goes straight to execution.

The trade-off is flexibility. A compiled query's shape has to stay fixed — the delegate you build can only vary by the parameter values you pass it, never by which Where/Include clauses run. A query that conditionally adds a filter or an include per call doesn't have one fixed shape, so it can't be compiled this way at all.

Because the internal cache lookup EF Core already does is itself a fast dictionary match, the extra saving from compiling is small — real, but only worth the added code at call volumes high enough for that small cost to show up in a profiler.

💻 See the code ▾
C# 
foreach (var id in ids)
{
    var order = db.Orders                     // same LINQ shape every call
        .FirstOrDefault(o => o.Id == id);
    // ✅ EF Core already caches this query's plan after the first call
}

Nothing special here — EF Core's own automatic caching already covers this loop.

C# 
private static readonly Func<AppDbContext, int, Order?> _getOrderById =
    EF.CompileQuery((AppDbContext db, int id) =>
        db.Orders.FirstOrDefault(o => o.Id == id));

// on the hot path:
var order = _getOrderById(db, id); // ✅ skips the cache lookup, straight to execute

Built once, stored as a delegate — every call after that reuses it directly.

C# 
Func<AppDbContext, bool, IQueryable<Order>> bad = EF.CompileQuery(
    (AppDbContext db, bool includeItems) =>
        includeItems
            ? db.Orders.Include(o => o.Items)  // ❌ shape changes per call
            : db.Orders);

A compiled query's shape must stay fixed — only parameter values can vary, not which clauses run.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're calling the same simple query over and over with a different parameter value

This is the "default, for virtually every query" row on the table above — EF Core already resolved this shape automatically the first time it ran, so every later call is just the fast lookup + match before executing. Nothing extra to write.

RememberSame shape, different values → EF Core's own caching already covers it.
2 A profiler shows real, measurable time inside EF Core's own pipeline on one proven, fixed-shape hot path

This is exactly the table's "measured, extremely hot, simple query" row — pull just that one lookup out into a compiled delegate once, and every call after skips straight to execute.

RememberProven, hot, fixed shape → the right candidate for CompileQuery().
3 Your query conditionally adds a different Include or Where clause per call

The table's "Query shape" row says a compiled query's shape must stay fixed. Varying which clause runs per call means there's no single fixed shape to compile in the first place — this can't be compiled this way at all, and forcing it is exactly the "added complexity for a saving too small to matter" the table's last row warns about.

RememberShape varies per call → can't be compiled, don't try.
🌍 Real-world example ▾

A service handles tens of thousands of single-row lookups per second on one simple, by-id query, and a profiler shows measurable time inside EF Core's own query pipeline even though the SQL itself runs fast. That is the specific case EF.CompileQuery() exists for — pull just that one hot, fixed-shape lookup out into a compiled delegate, and leave every other query in the codebase using EF Core's normal, automatic caching.
