Logging vs. App Insights — not competitors, one usually feeds the other

"How does logging fit alongside Application Insights — are they the same thing?"

Why it matters ▾
📝 ILogger / Plain Logging
❗ ProblemA team's own log calls only capture what a developer explicitly wrote — they say nothing about the requests, dependencies, or exceptions the app produces on its own, and each one still needs a logger call written by hand.
✅ SolutionThose ILogger calls don't need to change at all — once the SDK is wired in, the same lines just gain a second destination and flow straight into Application Insights alongside everything it collects automatically.
RecallILogger = the log lines a developer actually writes — nothing auto-collected.
📊 Application Insights
❗ ProblemEven with ILogger calls everywhere, a team still has no record of every request, dependency call, or exception unless someone writes a log line for each one — and no single place to view logging and that data together.
✅ SolutionApplication Insights auto-collects requests, dependencies, and exceptions with zero extra code, and becomes the shared destination where a team's own ILogger lines land too — one timeline in the Logs blade, not two separate systems.
RecallApp Insights = auto-collected telemetry + the shared destination for ILogger's own lines.
🔥 Easy interview recall

Logging vs. App Insights = "one feeds the other, not two rivals."

Think: ILogger calls flow in, auto-collected requests/dependencies/exceptions join them — same destination, one timeline.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It's logging OR Application Insights." They're not alternatives — the common real setup is ILogger calls flowing into Application Insights as one of its telemetry types, right alongside the request/dependency/exception data it collects automatically, not a separate system running next to it.

🔄 Likely Follow-up

"So why would you ever want a separate logging destination too?" Long-term retention or cost — Application Insights/Log Analytics has its own retention and pricing model, and some compliance requirements call for an immutable audit log that doesn't fit that model.

🎯 Say this in the interview — the exact lines to land

"ILogger calls typically flow into Application Insights, alongside its own auto-collected telemetry — it's not a separate system competing with it. I'd still reach for a separate logging destination when long-term retention, cost, or a compliance-driven audit-log requirement doesn't fit Application Insights' own retention model."

  • ILogger → developer-written log lines — the calls you actually write in code.
  • Application Insights → auto-collects requests, dependencies, and exceptions with zero extra code.
  • Wired together, both land in one timeline — the Logs blade, not two separate views.
  • A separate logging destination is still worth it for long retention, cost control, or audit compliance.
📖 Explanation ▾

Traditional logging — an ILogger call, a plain text or structured log line — captures exactly what a developer explicitly wrote. Application Insights captures that too, once ILogger is wired to send its output there, but it also auto-collects request, dependency, and exception telemetry the developer never had to write a single line for.

In practice, Application Insights is usually the destination logs flow into, unified with everything it already collects on its own — not a second, competing system a team has to choose between.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app already has ILogger calls everywhere, and someone just wires in Application Insights

Those exact same ILogger calls automatically start showing up in Application Insights' Logs blade the moment the SDK is wired into the app — no code rewrite, no new log calls, just a new place those same lines already end up. This is the #1 scenario you'll actually run into.

RememberExisting logger calls just gain Application Insights as a second destination.
2 You assume it's logging OR Application Insights — pick one

That's the actual trap — Application Insights isn't an alternative to logging, it's usually where those same log lines end up, right alongside the requests, dependencies, and exceptions it collects automatically. A great interview trap — candidates often assume they're two competing systems you have to choose between.

RememberLogging and Application Insights aren't rivals — one usually feeds the other.
3 You still want a separate, standalone log store even with Application Insights already in place

That's still worth doing — Application Insights has its own Log Analytics retention and pricing model, and some compliance requirements call for an immutable audit log that doesn't fit that model.

RememberA separate destination is about retention, cost, or compliance — not Application Insights being wrong.
