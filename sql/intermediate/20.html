EXCEPT & INTERSECT — in A, not B vs. in both

How do you find rows in A that are not in B, or rows that are in both?

Why it matters ▾
⭕ EXCEPT & INTERSECT
❗ ProblemComparing two result sets with a join or NOT IN gets clumsy fast — you spell out every column, and a single NULL can make NOT IN return nothing at all.
✅ SolutionEXCEPT (in A, not in B) and INTERSECT (in both) compare whole rows directly, remove duplicates, and treat NULLs as equal — set maths in one keyword.
RecallEXCEPT = A minus B. INTERSECT = the overlap.
🔥 Easy interview recall

A EXCEPT B → rows in A, not in B

A INTERSECT B → rows in both

Think: EXCEPT → order matters (A minus B ≠ B minus A) Both → distinct rows, same column count, NULLs treated as equal

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"NOT IN and EXCEPT are interchangeable." If the subquery returns even one NULL, NOT IN returns no rows at all; EXCEPT compares NULLs as equal, so it still works.

🔄 Likely Follow-up

"How is EXCEPT different from NOT EXISTS?" EXCEPT compares the whole select list and removes duplicates; NOT EXISTS can match on just a key, return any other columns, and keeps duplicate rows from A.

🎯 Say this in the interview — the exact lines to land

"EXCEPT returns the distinct rows from the first query that are not in the second; INTERSECT returns the distinct rows that appear in both. They compare whole rows, treat NULLs as equal, and need the same number of columns with compatible types."

  • A EXCEPT B → rows in A, not in B — and the order of the two queries matters.
  • A INTERSECT B → rows in both — same result either way round.
  • Both remove duplicates — T-SQL has no ALL version of either.
  • NULLs are compared as equal, so they are NULL-safe where NOT IN is not.
  • Need other columns, or a match on a key only → use NOT EXISTS or a join instead.
📖 Explanation ▾

EXCEPT returns the distinct rows from the first query that do not appear in the second. INTERSECT returns the distinct rows that appear in both. They look at the whole row, so both queries need the same number of columns, in the same order, with compatible data types. Column names come from the first query.

Two details get tested. First, NULLs: in a set operator two NULLs count as the same value, unlike =. That is why EXCEPT behaves where NOT IN silently returns nothing when the list contains a NULL (see NULL in Comparisons). Second, order: A EXCEPT B is not B EXCEPT A, while INTERSECT is symmetric. UNION is the "A or B" sibling — recap on UNION vs. UNION ALL.

You can always get the same answer with NOT EXISTS (for EXCEPT) or an INNER JOIN plus DISTINCT (for INTERSECT). Reach for the join form when you only match on a key but need to return other columns — see EXISTS vs. IN vs. JOIN. Reach for the set operator when you are comparing whole result sets, because it reads like the question.

💻 See the code ▾
T-SQL 
-- 2023 customers who did NOT order in 2024
SELECT CustomerId FROM dbo.Orders WHERE OrderYear = 2023
EXCEPT
SELECT CustomerId FROM dbo.Orders WHERE OrderYear = 2024;   -- ✅ A minus B

-- customers who ordered in BOTH years
SELECT CustomerId FROM dbo.Orders WHERE OrderYear = 2023
INTERSECT
SELECT CustomerId FROM dbo.Orders WHERE OrderYear = 2024;   -- ✅ the overlap

One keyword each; both return distinct CustomerId values even if a customer has many orders.

T-SQL 
SELECT CustomerId FROM dbo.Customers
WHERE CustomerId NOT IN (SELECT CustomerId FROM dbo.Orders);
-- 🐛 zero rows if any Orders.CustomerId is NULL

SELECT CustomerId FROM dbo.Customers
EXCEPT
SELECT CustomerId FROM dbo.Orders;
-- ✅ customers with no orders, NULL in Orders or not

Same question, two answers: the NOT IN version breaks on a single NULL, the EXCEPT version does not.

🌍 Real-world example ▾

Scenario: to check what changed between yesterday's copy of a table and today's, run Yesterday EXCEPT Today to see rows that were removed or changed, then Today EXCEPT Yesterday for rows that were added or changed — no column-by-column join needed.
