Parameter sniffing — the plan was built for one value, then reused for all of them

The same stored procedure is fast for one customer and slow for another. Why?

Why it matters ▾
👃 Parameter sniffing
❗ ProblemA procedure that is fast for a small customer and slow for a huge one looks random — same code, same data, different speed.
✅ SolutionSQL Server builds the plan from the parameter values of the first call and caches it; later calls reuse that plan, which fits the first value but not always the rest.
RecallSniffing = the cached plan was built for whichever value came first.
🔥 Easy interview recall

Parameter sniffing = "the cached plan was built for the first value that came in."

Think: Small value → plan for few rows (seek + lookup) Huge value → same plan reused → very slow

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Parameter sniffing is a bug, so turn it off." It is normal behaviour that usually helps by reusing a good plan; it only hurts when the data is very uneven, so fix that one query rather than the feature.

🔄 Likely Follow-up

"How do you confirm it, and what is the safest first fix?" Compare the plan and timings for a fast value and a slow value (Query Store keeps plans per query); if the plans differ, try OPTION (RECOMPILE) on the affected statement, then test — pinning a good plan in Query Store is the option when you cannot change the code.

🎯 Say this in the interview — the exact lines to land

"Parameter sniffing is SQL Server compiling a plan using the parameter values of the first call and then reusing it. It works well until the data is skewed — a plan that suits a small value can be very slow for a huge one. I'd confirm by comparing plans, then fix it with OPTION (RECOMPILE), OPTIMIZE FOR, or by forcing a good plan in Query Store."

  • The first call's values are used to compile the plan; later calls reuse it.
  • It hurts with skewed data — one value matches a few rows, another matches millions.
  • Tell-tale: a recompile makes it fast again — until an unlucky value arrives first.
  • OPTION (RECOMPILE) → fresh plan each run, at the cost of compiling every time.
  • OPTIMIZE FOR or the local-variable trick → plan from a chosen or average estimate, not the sniffed value.
  • Query Store → force a known-good plan without touching the code.
📖 Explanation ▾

When a procedure or parameterized query runs, SQL Server compiles an execution plan and caches it. At compile time it "sniffs" the actual parameter value to estimate how many rows will match. That is usually good: later calls skip the compile cost. The catch is that the plan is then reused for every value, whatever it is.

Say CustomerId = 7 matches 3 rows, so the plan uses an index seek plus a key lookup per row — ideal for a few rows. Now CustomerId = 1 matches millions: the same plan does millions of lookups where a scan would have been cheaper (see How the Optimizer Picks an Index and Execution Plans). Reverse the order and the problem flips. A restart (which empties the plan cache) or a statistics update (which can invalidate cached plans), so which value arrives first decides the plan for a while — which is why the same procedure seems fast one day and slow the next.

The fixes all trade something, so choose per query (table below). Newer SQL Server versions also add features aimed at this problem, such as parameter-sensitive plan optimization — check what your version supports. Related reading: Performance Degraded Over Time and Stored Procedures.

FixWhat it doesTrade-off
OPTION (RECOMPILE)fresh plan built for the actual value every runcompile cost on every run; no plan reuse
OPTIMIZE FOR (@p = value)always builds the plan as if the parameter were that valuecan be wrong for other values
OPTIMIZE FOR UNKNOWN / local variableplans from a general average estimate, not a real valuea middle-of-the-road plan, rarely the best for any value
Query Store forcingpins a chosen known-good plan, no code changeforced plan may need review as the data changes
💻 See the code ▾
T-SQL 
CREATE PROCEDURE dbo.usp_OrdersByCustomer @CustomerId INT
AS
BEGIN
    SELECT OrderId, Total
    FROM dbo.Orders
    WHERE CustomerId = @CustomerId
    OPTION (RECOMPILE);                         -- ✅ new plan for each value
    -- or: OPTION (OPTIMIZE FOR (@CustomerId UNKNOWN));  average-case plan
    -- or: OPTION (OPTIMIZE FOR (@CustomerId = 1));      plan for a typical big value
END;

Without the OPTION line, the plan from the first call would be reused for every customer.

T-SQL 
CREATE PROCEDURE dbo.usp_OrdersByCustomer2 @CustomerId INT
AS
BEGIN
    DECLARE @Id INT = @CustomerId;               -- local-variable trick
    SELECT OrderId, Total FROM dbo.Orders WHERE CustomerId = @Id;
END;                                           -- optimizer can't sniff @Id → average estimate

-- Query Store: pin a known-good plan without changing code
EXEC sp_query_store_force_plan @query_id = 42, @plan_id = 7;

The local variable hides the real value from the optimizer, which then uses a general estimate; Query Store forcing needs no code change at all.

🌍 Real-world example ▾

Scenario: after a server restart empties the plan cache, the first call to a report procedure happens to be for a tiny customer — so the plan cached for the rest of the day crawls whenever the biggest customer runs it, and clearing that one plan or adding OPTION (RECOMPILE) makes it fast again.
