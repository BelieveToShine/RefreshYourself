A trigger starts it, a plan decides how fast it wakes up

"Consumption vs. Premium vs. Dedicated plan — and how do you deal with cold starts?"

Why it matters ▾
⚡ Triggers & bindings
❗ ProblemWiring every function by hand to its queue, blob, or database means each one repeats the same connection and polling code before any real logic runs.
✅ SolutionA trigger is the one event that starts the function, and input/output bindings declare the data going in and out, so the platform does that plumbing and your code stays the business logic.
RecallTrigger = what starts it. Binding = data in or out, declared not coded.
💰 Hosting plans
❗ ProblemA function that runs a few times a day does not deserve a server burning money all day, but a busy one cannot tolerate waiting for a server to appear.
✅ SolutionThe plan sets the trade-off: serverless plans scale to zero and bill by use, Premium keeps warm instances ready, and Dedicated runs on VMs you already pay for.
RecallCheaper when idle = slower to wake. Always warm = you pay for it.
🥶 Cold start
❗ ProblemAfter a quiet spell on a scale-to-zero plan, the next request has to wait while a new instance is started and your app loads.
✅ SolutionPick a plan that keeps instances ready (Premium, Dedicated with Always On, or Flex with always-ready instances) and keep startup work light.
RecallCold start = the wait for the first instance after idle.
🔥 Easy interview recall

Trigger → one per function, starts it

Binding → data in or out, optional

Scale to zero → cheap, but cold start

Premium / Dedicated → warm, you pay for it

Think: a trigger starts it, a binding moves data, the plan decides wake-up speed.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Consumption never has cold starts if my app is popular." Cold starts are about whether an instance is ready for this request, not how popular the app is overall — a scale-to-zero plan can still wait when traffic spikes after a quiet spell. If latency matters, choose a plan that keeps instances warm instead of hoping traffic keeps them awake.

🔄 Likely Follow-up

"What about the older vs. newer serverless plan?" Flex Consumption is the newer serverless plan and the one Microsoft recommends for new serverless apps. The classic Consumption plan is now labelled legacy, and Linux hosting on it retires on 30 September 2028. Flex adds VNet integration and optional always-ready instances; Consumption has no VNet integration.

🎯 Say this in the interview — the exact lines to land

"A trigger starts the function and bindings handle its data in and out. For hosting, the serverless plans (Flex Consumption, and the legacy Consumption plan) scale to zero and are cheapest but can have cold starts, Premium keeps warm instances and supports VNet, and Dedicated runs on always-on App Service VMs."

  • Trigger → exactly one per function, it is what starts it.
  • Bindings → optional, declarative data in and data out.
  • Flex Consumption → newer serverless plan, recommended for new apps, always-ready option.
  • Premium → always-ready instances and VNet, avoids cold starts.
  • Dedicated → App Service VMs, enable Always On to stay warm.
  • Legacy Consumption → default timeout 5 min, max 10; the other plans default to 30.
📖 Explanation ▾

Every function has exactly one trigger — the event that starts it, such as an HTTP request, a queue message, a timer, or a blob arriving. Bindings are optional extras: an input binding hands your code data it needs (a row, a blob), and an output binding sends a result somewhere (a queue, a table) without you writing the client code. Connections are declared in configuration, not hard-coded.

The hosting plan decides how your function gets compute. Flex Consumption is the serverless plan Microsoft recommends for new apps: it scales to zero, bills for what runs, supports VNet integration, and can keep optional always-ready instances. The older Consumption plan is now called legacy (Linux hosting on it retires on 30 September 2028); it also scales to zero but has no VNet integration. Premium uses pre-warmed workers and always-ready instances so nothing waits, and supports VNet integration. Dedicated runs on an App Service plan you already size and pay for; turn on Always On so the host does not go idle. Default timeout is 30 minutes on Flex, Premium and Dedicated, and 5 minutes (max 10) on Consumption.

A cold start is the delay when a request arrives and no instance is ready: Azure has to allocate one and load your app. To deal with it: choose a warm plan when latency matters, keep the app small with light startup work, and for long or multi-step work use Durable Functions instead of one long call.

💻 See the code ▾
C# 
[Function("ProcessOrder")]
// output binding: whatever the method returns goes to the "receipts" queue
[QueueOutput("receipts", Connection = "StorageConn")]
public string Run(
    // trigger: a new message on "orders" starts this function
    [QueueTrigger("orders", Connection = "StorageConn")] string order)
{
    return $"receipt for {order}";
}

One trigger starts it, one output binding sends the result on — no queue client code anywhere. This is the isolated worker model; the plan you deploy it to is a separate choice.

🌍 Real-world example ▾

A shop's nightly report function runs once a day, so a Consumption or Flex plan costs almost nothing and nobody minds a cold start. Its checkout-confirmation function must answer within a second, so the team moves that one to Premium with pre-warmed instances.
