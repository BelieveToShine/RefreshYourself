An Angular app is slow — diagnose before you reach for a fix

An Angular app has gotten slow — what do you actually check, in order, before reaching for any specific fix?

Why it matters ▾
🔬 Profile First
❗ ProblemToo much change-detection work, a bloated bundle, and a huge unvirtualized list can all feel like the exact same "the app is slow" from the outside — reaching straight for OnPush/trackBy everywhere without checking first can miss the real bottleneck entirely and waste the fix.
✅ SolutionProfiling with Angular DevTools' Profiler (or the browser's own Performance panel) shows which of the three it actually is — so the fix applied is the one the profile actually points to, not a guess.
RecallDiagnose a slow Angular app by profiling first — the profile says whether it's change detection, bundle size, or DOM node count.
🔥 Easy interview recall

Slow Angular app = "profile first, fix what it actually shows."

Think: Too much CD work → OnPush + trackBy Too much JS → lazy loading + @defer Too many DOM nodes → virtual scrolling

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding OnPush or trackBy everywhere is not automatically the fix. Change detection might not even be the real bottleneck — a bloated bundle or a genuinely huge unvirtualized list can feel identical from the outside; profile first, then reach for the fix the profile actually points to.

🔄 Likely Follow-up

"If OnPush and trackBy don't fix a slow list, what's next?" Check whether the list is simply too large to render as real DOM nodes at all, regardless of how efficiently each check runs — at that point the fix isn't "check less," it's "render fewer actual DOM nodes," which is exactly what virtual scrolling solves.

🎯 Say this in the interview — the exact lines to land

"First I'd profile with Angular DevTools' Profiler, or the browser's own Performance panel, to see which components are being checked, how often, and how expensive each check is — then I'd match the fix to what the profile actually shows: OnPush/trackBy for too much change detection, lazy loading/@defer for too much JavaScript, or virtual scrolling for too many DOM nodes."

  • Profile first → never guess the bottleneck before reaching for a fix.
  • Too much CD work → OnPush + trackBy cut unnecessary checks and DOM node recreation.
  • Too much JS → lazy loading, preloading, @defer shrink or delay what gets downloaded.
  • Too many DOM nodes → virtual scrolling keeps the real DOM node count roughly constant.
  • An impure pipe re-running something expensive every check is an avoidable cost — a pure pipe only re-runs on an input reference change.
📖 Explanation ▾

An Angular app generally slows down for one of a few reasons: too much change-detection work checking things that didn't need checking, an expensive computation running directly inside a template binding (which re-runs on every check), too much JavaScript shipped before the app can even start, or too many DOM nodes rendered at once. The right first move is always the same regardless of which of these it turns out to be: open Angular DevTools' Profiler (or the browser's own Performance panel) and see exactly which components are being checked, how often, and how long each check takes — before reaching for any specific fix.

If the profile points at change detection, OnPush skips checking components that don't meet one of its specific trigger conditions, and trackBy (or track in a modern @for) tells Angular which list item is which across a re-render, so reordering doesn't destroy and recreate DOM nodes that are really just the same items in a new position. A pure pipe only re-runs when its input reference changes; an impure pipe re-runs on every single check, so using one for anything expensive is a real, avoidable cost.

If the profile points elsewhere, the fix is different. Lazy loading keeps a route's code out of the initial bundle until it's actually navigated to; preloading fetches that same code in the background once the app is idle, so it's often already cached by the time the user navigates there; @defer does the same trick for one part of a template instead of a whole route. If the real problem is a huge list, no amount of change-detection tuning helps — virtual scrolling only renders the DOM nodes actually visible in the viewport, so the real node count stays roughly constant no matter how many items exist underneath.

💻 See the code ▾
HTML 
@for (item of items; track item.id) {
  <app-row [data]="item" />
}

track item.id identifies the same item across a reorder — track $index ties identity to position instead, so reordering the list destroys and recreates every row's DOM node rather than just moving it.

HTML 
<img ngSrc="hero.jpg" width="800" height="400" priority>

priority tells NgOptimizedImage this image matters for the very first paint — it skips lazy-loading and fetches it immediately, meant for an above-the-fold image like a hero banner.

🧭 Use Cases — recognize these when they happen to you ▾
1 You open Angular DevTools' Profiler and see one component being checked far more often than expected

The profile is pointing straight at change-detection overhead. OnPush skips checking components that don't meet one of its own trigger conditions, and trackBy (or track in a modern @for) stops a list reorder from destroying and recreating DOM nodes that are really just the same items in a new position.

RememberProfiler shows excess checks → OnPush + trackBy.
2 You check the ng build output and see a large bundle downloading before the app can even start

This is a bundle-size problem, not a change-detection one — no amount of OnPush tuning shrinks a download that's already too big. Lazy loading keeps a route's code out of the initial bundle until it's actually navigated to, preloading fetches that same code in the background once the app is idle, and @defer does the same trick for one part of a template.

RememberLarge ng build output → lazy loading, preloading, or @defer.
3 The profile looks clean, but the page still feels slow — and it turns out to be a huge, unvirtualized list

Neither change detection nor bundle size is the real bottleneck here — the actual DOM node count is just too high. Virtual scrolling only renders the items that are actually visible in the viewport, so the real node count stays roughly constant no matter how many items exist underneath.

RememberProfile looks clean, list is huge → virtual scrolling.
🌍 Real-world example ▾

A doctor who prescribes before running any tests. Treating a slow Angular app without profiling first is like a doctor handing out medicine based only on "the patient said they feel bad" — a racing pulse, too much stress, and a broken bone all feel like "something's wrong" from the outside, but need completely different treatment. Profiling is the test that tells you which of change detection, bundle size, or too many DOM nodes is actually the one worth treating.
