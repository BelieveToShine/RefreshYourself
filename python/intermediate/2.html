is checks identity, == checks equality — and small-int/string caching makes it easy to fool yourself

"== vs. is — and why does relying on is for small integers/strings work until it suddenly doesn't?"

Why it matters ▾
  • Checks whether you understand object identity vs. value equality — not just syntax.
  • Comes up constantly in code review: someone writes if x is 5: and it "works" in a quick test, then breaks later.
  • A near-guaranteed follow-up after any question about Python's object model or singleton checks like x is None.
🔥 Easy interview recall

== → value equality (calls __eq__)

is → identity — same object, same id()

Think: == asks "same value?" is asks "same object?" — caching can make small ints/strings share one, with no promise it always will

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It worked with is in my test, so is must be fine for comparing values." Small-int/string caching is a CPython implementation detail, not a language guarantee — always use == for value comparison, and reserve is for identity/singleton checks.

🔄 Likely Follow-up

"Why does x is None get preferred over x == None?" is None is a true identity check that can never be fooled by a custom __eq__ override, and it signals clear intent — "is this literally the None singleton."

🎯 Say this in the interview — the exact lines to land

"is checks identity — is this literally the same object in memory — while == checks value equality through __eq__. CPython caches small integers (-5 to 256) and some string literals as a performance optimization, so is can appear to work for those values, but that's an implementation detail, not a language guarantee — so I always use == for value comparisons and is only for identity/singleton checks like x is None."

  • == → value equality, calls __eq__ — use it to compare contents.
  • is → identity, compares id() — use it for None/singleton checks.
  • Small-int/string caching is a CPython implementation detail — never rely on it for correctness.
  • x is None → idiomatic and can't be fooled by a custom __eq__.
📖 Explanation ▾

== calls the object's __eq__ method — it checks whether two objects represent the same value, whatever "equal" means for that type. is never calls any method — it compares id(), asking whether two names point at the exact same object in memory. Use is for singleton checks (x is None, x is True) — x == None works too, but it's non-idiomatic and can be fooled by a type with a custom __eq__.

CPython caches small integers (-5 to 256) and some string literals as singleton objects for performance, so a = 5; b = 5; a is b often returns True — not because the language promises this, but because CPython, as a specific implementation, chooses to reuse those objects. Step outside that cached range and the guarantee disappears; each literal typically gets its own object instead.

💻 See the code ▾
Python 
a = 256
b = 256
print(a is b)  # True

a = 257
b = 257
print(a is b)  # often False

Predict the output: why does that happen, and why is relying on it a bug waiting to happen?

256 sits inside CPython's small-int cache (-5 to 256), so a and b point at the same cached object — True. 257 sits outside that range, so each literal typically creates a separate object — often False. This is a CPython implementation detail, not a language guarantee, and can differ across Python versions/implementations (e.g. PyPy).

🌍 Real-world example ▾

A developer wrote if user_id is 12345: and it passed every test in dev, because the test IDs happened to be small cached integers. Once real user IDs in production grew past 256, the same check silently started returning False for a value that was actually equal — a bug that only showed up after shipping.
