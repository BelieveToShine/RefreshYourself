Route 53 decides where; CloudFront decides how

"How would Route 53 help with disaster recovery, and how is it different from CloudFront?"

Why it matters ▾
  • Comes up any time disaster recovery, multi-Region architecture, or "how does traffic actually get routed" is discussed.
  • A very common mix-up — candidates often describe Route 53 and CloudFront as doing the same job.
  • Sets up the routing-policies follow-up almost every interviewer asks right after.
🔥 Easy interview recall

Route 53 → decides WHERE (DNS)

CloudFront → decides HOW (caching/delivery)

Think: Route 53 is the map. CloudFront is the delivery truck.

⚠️ Common Trap

Route 53 failover is not an instant, zero-downtime switch. DNS changes still have to propagate — bounded by the record's TTL — so failover has a real, non-zero recovery time, not an immediate one.

🔄 Likely Follow-up

"What's latency-based routing actually optimizing for?" The Region that gives that specific user the lowest network latency — not necessarily the geographically nearest Region; the two aren't always the same.

🎯 Say this in the interview — the exact lines to land

"Route 53 decides where a request goes — it's DNS, resolving a name to an IP using a routing policy. CloudFront decides how content is delivered once it gets there — it's a CDN, caching content at edge locations close to the user."

  • Route 53 → DNS: decides where a request should go.
  • CloudFront → CDN: decides how content actually gets delivered/cached.
  • Failover routing → health checks redirect traffic to a healthy secondary Region — Route 53's real DR tool.
  • DNS TTL → failover has a real, non-zero recovery time, never instant.
📖 Explanation ▾

Route 53 is AWS's DNS service — it turns a domain name into an IP address, and it can do that in more than one way depending on the routing policy attached to the record: Simple (one static answer every time), Weighted (split traffic across answers by percentage), Latency-based (route to whichever Region gives that user the lowest latency), Failover (route to a healthy primary, and switch to a secondary if it fails a health check), and Geolocation (route based on the user's geographic location).

For disaster recovery specifically, Route 53's health checks combined with failover routing can automatically redirect new DNS lookups away from a failed primary Region to a healthy standby — without anyone manually flipping a switch. CloudFront is a genuinely different layer: it's a CDN, caching and serving content from edge locations physically close to users. Route 53 decides where a request should go; CloudFront decides how content actually gets delivered and cached once it gets there.

🌍 Real-world example ▾

An app uses Route 53 failover routing with health checks against its primary Region's ALB. When the primary starts failing those checks, new DNS lookups automatically start resolving to the secondary Region instead — no manual intervention, just a wait for the old answer's TTL to expire.
