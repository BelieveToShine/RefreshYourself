Guardrails prevent, Config detects — across 50 accounts you need both

How do you govern 50 AWS accounts — guardrails, baseline, and continuous compliance?

Why it matters ▾
🛑 Organizations & SCPs
❗ ProblemWith 50 accounts, one team can switch off logging or use a banned Region — and IAM inside an account can't stop that account's own admins.
✅ SolutionAn SCP (service control policy) sets the maximum permissions for an account or a whole OU. Even an account admin can't go past it. It never grants anything by itself.
RecallSCP = a ceiling that prevents.
🏗️ Control Tower
❗ ProblemSetting up every new account by hand — logging, audit, baseline rules — is slow, and each account drifts from the others.
✅ SolutionControl Tower builds a landing zone: a ready-made multi-account setup with log-archive and audit accounts, plus guardrails on every enrolled account. Account Factory creates new accounts with the same baseline.
RecallControl Tower = the baseline, automated.
🔎 AWS Config
❗ ProblemGuardrails stop some actions, but resources can still end up misconfigured — a public bucket, an unencrypted volume — and nobody notices.
✅ SolutionConfig records resource settings and checks them against rules (bundled as conformance packs). It shows what is compliant and what has drifted, gathered into one central account.
RecallConfig = detects drift.
🔥 Easy interview recall

SCP → a ceiling — blocks, never grants

Control Tower → landing zone — the baseline in every account

Config → detects drift — flags what is non-compliant

Think: SCPs say "you may never". Config says "you did — and here it is". Control Tower sets up both for every new account.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"An SCP gives the account those permissions." It doesn't — an SCP only filters. An action works only if the SCP and the identity's IAM policy both allow it, so an SCP that says Allow on everything still grants nothing by itself.

🔄 Likely Follow-up

"Does an SCP apply to the management account?" No — SCPs restrict member accounts only, not the management account. That is why you keep workloads out of the management account and put them in member accounts under OUs.

🎯 Say this in the interview — the exact lines to land

"I'd use Organizations with OUs and SCPs as the preventive guardrails, Control Tower to set up the landing zone and baseline for every account, and Config with conformance packs, aggregated into a central audit account, to detect drift. In short: prevent with SCPs, detect with Config."

  • SCP → a ceiling, never a grant — inherited down OUs; applies to member accounts, not the management account.
  • Effective permission → IAM allows AND SCP allows — both must say yes.
  • Control Tower → landing zone with Log Archive and Audit accounts; Account Factory builds new accounts to the baseline.
  • Guardrails → preventive = SCP, detective = Config rule.
  • Config → detects drift — rules and conformance packs, aggregated to one account; remediation can fix it.
📖 Explanation ▾

AWS Organizations groups accounts into OUs (organizational units) under one management account. An SCP attached to the root or an OU is inherited by everything below it. An SCP never grants permission — an action works only if both the SCP and the identity's own IAM policy allow it. SCPs apply to member accounts, not to the management account, so keep workloads out of the management account.

Control Tower sits on top of Organizations. It creates a landing zone: a baseline with a Log Archive account and an Audit account, identity set up, and guardrails on each enrolled account (AWS now calls these controls — check current docs for the wording). A preventive guardrail is built on an SCP; a detective one is built on a Config rule. Account Factory creates new accounts that already follow the baseline.

Config keeps a history of resource settings and checks them against rules. A conformance pack bundles rules (and fixes) so one pack can be deployed across many accounts. An aggregator collects the results from all accounts into one central account, so an auditor sees one view. Config detects drift; to fix it, attach a remediation action.

💻 See the code ▾
JSON 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyStoppingCloudTrail",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail"
      ],
      "Resource": "*"
    }
  ]
}

A guardrail SCP: nobody in the target accounts — admins included — can stop or delete a trail. It only removes permissions; it grants nothing.

CLI 
aws organizations create-policy \
  --name DenyStopCloudTrail \
  --type SERVICE_CONTROL_POLICY \
  --description "Block stopping or deleting CloudTrail" \
  --content file://deny-cloudtrail.json

aws organizations attach-policy \
  --policy-id p-examplepolicyid \
  --target-id ou-examp-12345678

Create the policy, then attach it to an OU — every account under that OU inherits it. The IDs here are placeholders.

🌍 Real-world example ▾

A company with 50 accounts attaches an SCP to its Prod OU that blocks stopping CloudTrail, and enrols every account through Control Tower. A Config conformance pack then flags an unencrypted volume in one account, and it shows up in the audit account's single compliance view.
