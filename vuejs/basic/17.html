<script setup> — no return statement, and that's the whole point

"What does <script setup> actually do differently from a plain setup() function?"

Why it matters ▾
⚡ <script setup>
❗ ProblemA plain setup() function has to manually return { ... } every single value the template needs — easy to forget one, and pure boilerplate for something the compiler could just see.
✅ Solution<script setup> is compile-time sugar — everything declared at the top level is automatically exposed to the template, with no manual return needed.
Recall<script setup> = top-level bindings auto-exposed, no return statement.
🔥 Easy interview recall

<script setup> = "write it, and the template can already see it."

Think: Plain setup() needs return {...}; <script setup> never does.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

defineProps/defineEmits are compiler macros, not real imported functions. They only work literally inside <script setup>, and can't be used inside a regular exported function.

🔄 Likely Follow-up

"Does <script setup> change the component's public instance?" Yes — by default it's "closed" (not accessible via template refs/$parent the way an Options API component is) unless defineExpose() explicitly opts properties back in.

🎯 Say this in the interview — the exact lines to land

"<script setup> is compile-time sugar for the Composition API inside a Single File Component — everything declared at the top level is automatically exposed to the template, so there's no manual return {} needed."

  • Top-level variables, functions, and imports → auto-exposed to the template, no return.
  • defineProps/defineEmits → compiler macros, only valid literally inside <script setup>.
  • The component instance is closed by default — defineExpose() opts specific things back in.
  • It's sugar for the same Composition API — not a different reactivity system underneath.
📖 Explanation ▾

A plain setup() function has to explicitly hand back everything the template needs — return { count, increment } — because the template only sees whatever that function returns. <script setup> is a compiler-level shortcut for this exact pattern inside a Single File Component: the compiler already knows everything declared at the top level, so it generates that return for you. There's no new reactivity model here — it's the same Composition API underneath, just less boilerplate to write.

Two helpers only make sense in this compiled context: defineProps and defineEmits. They look like function calls, but they're compiler macros — the compiler recognizes them by name and replaces them entirely at build time. That's why they can't be imported and used inside a regular function elsewhere; outside <script setup>'s top level, they simply don't exist.

One trade-off: because there's no explicit return object, a parent holding a template ref to a <script setup> component can't reach into it by default — its public instance is closed. defineExpose({ ... }) is the explicit opt-in for whichever properties or methods a parent genuinely needs to reach.

💻 See the code ▾
Vue 
// plain setup() — explicit return required
export default {
  setup() {
    const count = ref(0);
    return { count };   // ❌ forget this and the template sees nothing
  }
};

Every binding the template needs has to be listed by hand, by someone, every time.

Vue 
<script setup>
const count = ref(0);   // ✅ already visible to the template, no return
</script>

The compiler generates the equivalent return for you — nothing to forget.

Vue 
function notAllowed() {
  const props = defineProps(['x']);  // ❌ compiler macro, top level only
}

defineProps/defineEmits are erased and replaced at compile time — they don't exist as real functions anywhere else.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're writing any new Single File Component today

For a fresh component, <script setup> is the default choice in current Vue code — less boilerplate, same Composition API underneath. This is the #1 scenario you'll actually run into.

RememberNew component today → <script setup> is the default.
2 A parent needs to call a method on a child directly

An input wrapper component that wants to expose a focus() method to whoever uses it calls defineExpose({ focus }) — without it, the parent's template ref to this component would see nothing usable.

RememberParent needs to call a child method → defineExpose() it explicitly.
3 You try to use defineProps inside a helper function

Compiler macros only work at the literal top level of <script setup> — moving the call inside a nested function, a condition, or a loop isn't a runtime bug, it's a build-time error, because the compiler can't find it where it expects it.

RememberdefineProps/defineEmits → top level only, never nested.
🌍 Real-world example ▾

Think of an auto-fill form versus a form you fill out and mail yourself. A plain setup() is the mail-it-yourself form — you write every field, seal the envelope (return), and send it. <script setup> is the auto-fill version — the information is already there, so nothing extra needs to be collected and sent separately.
