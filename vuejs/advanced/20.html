🔥 Vue.js · Advanced · Must Know

Memory climbs forever — find the listener nobody removed

"Your SPA's memory usage keeps climbing the longer a user stays on the page, even as components come and go — where do you look first?"

Why it matters ▾
👻 Leaking Manual Subscriptions
❗ ProblemA watcher or event listener set up manually — inside onMounted, or a raw addEventListener/subscribe call — that's never torn down keeps a reference (and keeps firing) after the component is gone, worse in an SPA where components mount/unmount constantly with no full page reload to reset things.
✅ SolutionPair every manual subscription with its teardown in onUnmounted — or store the watch() call's own returned stop function and call it there.
RecallEvery manual "on" needs a matching manual "off."
🔥 Easy interview recall

watch() in setup() → auto-stopped on unmount

Manual listener/subscribe → needs manual teardown

Think: Vue cleans up what it created; it can't clean up what you wired yourself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming EVERY watcher needs manual cleanup. A watch()/ watchEffect() call made directly inside setup() is automatically stopped when the component unmounts — it's only manual, non-Vue-tracked subscriptions (raw DOM listeners, third-party library subscriptions) that need explicit teardown.

🔄 Likely Follow-up

"How would you actually confirm this is the cause in a real app?" Browser DevTools' memory profiler — take a heap snapshot, navigate away and back several times, take another snapshot, and look for a growing count of detached/retained component instances or listener closures.

🎯 Say this in the interview — the exact lines to land

"I'd check for a manual subscription — a raw event listener or third-party library subscribe call set up in onMounted — that has no matching teardown in onUnmounted. Composition API watch() calls made directly in setup() are auto-stopped on unmount, so the leak is almost always something wired up outside Vue's own tracked APIs."

  • watch() in setup() → auto-stopped on unmount, no action needed.
  • Manual addEventListener/subscribe → needs its own teardown in `onUnmounted`.
  • Confirm with → DevTools heap snapshots before/after repeated navigation.
  • Worse in an SPA → no full page reload ever resets the leak.
📖 Explanation ▾

Vue's own Composition API APIs clean up after themselves: a watch() or watchEffect() created inside setup() is tied to that component's scope and is automatically stopped the moment the component unmounts. The leak risk is specifically for anything set up outside that tracked scope — a raw window.addEventListener, a third-party event-bus .on(), a WebSocket subscription — none of which Vue knows exists, so none of which it can tear down for you.

In a traditional multi-page site, navigating away reloads the whole page and every JS reference gets wiped automatically. An SPA never does that — components mount and unmount repeatedly on the same page load, so a listener that outlives its component just keeps accumulating: each unmounted component's closure stays referenced by whatever it subscribed to, and the garbage collector can't reclaim it while that reference exists.

The fix is symmetry: every manual subscription gets a matching teardown call in onUnmounted, or you capture the stop function a manual watch() call returns and invoke it there. This is a discipline problem more than a hard one — the bug is almost always a missing line, not a wrong one.

💻 See the code ▾
Vue 
<script setup>
import { onMounted } from 'vue';
import { eventBus } from './eventBus';

onMounted(() => {
  eventBus.on('update', handleUpdate); // ❌ never removed
});
</script>

Every time this component unmounts and a new one mounts, another listener piles onto the same bus — none of them ever go away.

Vue 
<script setup>
import { onMounted, onUnmounted } from 'vue';
import { eventBus } from './eventBus';

onMounted(() => {
  eventBus.on('update', handleUpdate);
});
onUnmounted(() => {
  eventBus.off('update', handleUpdate); // ✅ matching teardown
});
</script>

The listener is removed the moment the component goes away — nothing is left for the garbage collector to be blocked on.

🧭 Use Cases — recognize these when they happen to you ▾
1 A component subscribes to a shared event bus or third-party library in onMounted

This is the #1 scenario you'll actually run into: a subscription Vue has no knowledge of, so it has no way to remove it for you when the component goes away.

RememberA third-party subscription always needs its own explicit teardown.
2 A raw window.addEventListener (resize, scroll) is added directly

The browser's global window/document object outlives every component — a listener attached to it keeps the handler's closure (and whatever it references) alive until removeEventListener is called with the exact same function reference.

Rememberwindow/document outlive the component — always pair add/removeEventListener.
3 A watch() is created directly inside setup()

This one is not a leak risk — Vue tracks a watch() created inside setup() and stops it automatically on unmount, with nothing for you to write.

RememberA setup()-scoped watch() needs no manual cleanup at all.
🌍 Real-world example ▾

A single-page dashboard's memory usage climbs steadily over a work session, and a heap snapshot shows hundreds of retained component instances that should have been collected. The cause: a notification widget subscribes to a shared WebSocket client in onMounted every time it's shown, with no matching onUnmounted teardown — each one piles onto the last.
