Middleware — a gate that runs before the route does

"What is Middleware, and what runtime does it execute on?"

Why it matters ▾
🚧 Middleware
❗ ProblemChecks like "is this request authenticated," "which A/B bucket is this visitor in," or "what country are they in" would otherwise need to be repeated inside every single page/route that needs them.
✅ Solutionmiddleware.js runs once, on the Edge Runtime, before a matching request completes — so it can redirect, rewrite, or inject headers for every route it covers in one place, before the actual page or Route Handler ever runs.
RecallMiddleware = one gate in front of every matching route.
🔥 Easy interview recall

Middleware = "code that runs on the Edge, before the real route, for every request that matches."

Think: a bouncer at the door — checks you before you ever reach the room.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Middleware is not the place for heavy, slow logic like a large database query. It runs on every single matching request, on the Edge Runtime's restricted environment — no full Node.js APIs — so it has to stay fast and lightweight; heavier work belongs in the actual route or Server Component.

🔄 Likely Follow-up

"How do you scope Middleware to only some routes?" The exported config.matcher (or conditional logic checking request.nextUrl.pathname inside the middleware function) — without it, Middleware runs on every request by default, including static assets, unless excluded.

🎯 Say this in the interview — the exact lines to land

"middleware.js at the project root runs on the Edge Runtime before a matching request completes — I use it for things like auth gating, A/B bucketing, geolocation rewrites, or header injection, all before the actual page or route handler runs."

  • Edge Runtime → restricted environment, no full Node.js APIs.
  • Runs before the route handler/page, for every matching request.
  • config.matcher → scope it instead of running on everything by default.
  • Keep it lightweight — it runs on every single request that matches.
📖 Explanation ▾

A middleware.js file at the project root exports a function that runs on the Edge Runtime, for every request whose path matches its scope, before that request reaches the actual route handler or page. It gets the incoming request and can inspect headers, cookies, and the URL — then decide to let the request continue unchanged, rewrite it to a different path, or redirect it entirely.

The Edge Runtime is a deliberately smaller, faster execution environment than full Node.js — it starts instantly and runs close to the visitor geographically, but it doesn't have access to every Node.js API. That trade-off is exactly why Middleware is meant for quick decisions (checking a cookie, reading a header) rather than heavier work like a database call.

Without a config.matcher export, Middleware runs on every request by default, including requests for static files — scoping it down to just the routes that actually need the check keeps it from doing unnecessary work on every page load.

💻 See the code ▾
Next.js 
// middleware.js — project root
import { NextResponse } from 'next/server';

export function middleware(request) {
  const isLoggedIn = request.cookies.has('session');
  if (!isLoggedIn) {
    return NextResponse.redirect(new URL('/login', request.url));  // ✅ gate before the route
  }
  return NextResponse.next();
}

export const config = {
  matcher: ['/dashboard/:path*'],   // only these paths run this check
};

Without config.matcher, this would run on every request, not just /dashboard.

🧭 Use Cases — recognize these when they happen to you ▾
1 Gating a section of the app behind login

Middleware checks for a session cookie on every request to a protected path and redirects unauthenticated visitors before they ever see the dashboard's layout or data.

RememberAuth gating is Middleware's single most common job.
2 Bucketing visitors for an A/B test

Middleware assigns a visitor to variant A or B on their first request, sets a cookie so the decision sticks, and rewrites the response so each variant's experience renders consistently afterward.

RememberBucket once at the edge, stay consistent on every later request.
3 Putting a database lookup straight inside Middleware

A heavy query here runs on every single matching request, on the restricted Edge Runtime — it slows down every page load it touches, not just the one that genuinely needs the data.

RememberHeavy work belongs in the route/Server Component, not Middleware.
🌍 Real-world example ▾

A SaaS app redirects visitors from europe.example.com to a localized pricing page. Middleware reads the request's geolocation data and rewrites the URL to the right regional page before the route even runs — a single rule covering every page under that domain, instead of duplicating the check inside each page.
