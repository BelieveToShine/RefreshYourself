HasNoKey — a read-only shape for views and queries

"How do you map a SQL view or query result with no primary key?"

Why it matters ▾
👁️ Keyless Entities & Views
❗ ProblemA database view or report query has no primary key, but EF Core entities normally need one — so the usual mapping simply does not fit.
✅ SolutionMap it as a keyless entity with HasNoKey() (and ToView() for a view). You can query it with LINQ, but it is never tracked, so it is read-only by design.
RecallKeyless = query it, never save it. HasNoKey().ToView("..."); the change tracker is bypassed.
🔥 Easy interview recall

Keyless entity = "a read-only shape: query it, never save it."

Think: HasNoKey().ToView("vw_...") → map to a view Never tracked → no insert, update or delete through it One-off report → SqlQuery / FromSql projection instead

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A keyless entity works like any other — I can Add and SaveChanges()." Keyless types are never tracked, so EF Core cannot insert, update or delete through them. Write through the normal entities on the underlying tables.

🔄 Likely Follow-up

"Keyless view mapping, or a FromSql projection — which one?" Map the view when you reuse the shape and want to build LINQ on top of it. Use a raw-SQL projection for a one-off report that does not deserve a permanent spot in the model.

🎯 Say this in the interview — the exact lines to land

"For a view or a report query with no primary key, I map a keyless entity with HasNoKey(), and ToView() when it is backed by a database view. I can query it with LINQ, but it is never tracked, so it is read-only. For a one-off report I might use a raw-SQL projection instead."

  • HasNoKey() → entity with no primary key.
  • ToView("...") → read from a database view; migrations do not create a table for it.
  • Never tracked → read-only; no insert, update or delete.
  • One-off report → raw-SQL projection, no model entry needed.
📖 Explanation ▾

A keyless entity is an ordinary class that you register with HasNoKey() (or the [Keyless] attribute). EF Core can query it with LINQ — Where, OrderBy and so on — but with no key it has no identity, so the change tracker never follows it. That is why it can be read but never inserted, updated or deleted through EF Core.

ToView("vw_OrderSummary") tells EF Core the data comes from a database view, which is the usual home for keyless types, and EF Core will not create a table for it in migrations. ToSqlQuery(...) can map it to a query instead. For a one-off result you do not want in the model at all, a raw-SQL projection (FromSql on a mapped type, or Database.SqlQuery<T>, which returns non-entity types from EF Core 8) returns the rows directly.

💻 See the code ▾
C# 
public class OrderSummary { public int OrderId { get; set; } public decimal Total { get; set; } }

modelBuilder.Entity<OrderSummary>()
    .HasNoKey()
    .ToView("vw_OrderSummary");              // ✅ backed by a view, no key

Register the shape as keyless and point it at the view.

C# 
var big = await db.Set<OrderSummary>()
    .Where(s => s.Total > 100)               // ✅ LINQ composes over the view
    .ToListAsync();

db.Set<OrderSummary>().Add(new OrderSummary());   // ❌ not allowed — keyless types are never tracked

Query it freely; saving through it is not possible.

C# 
var min = 100;
var rows = await db.Database
    .SqlQuery<SalesRow>($"SELECT Region, SUM(Total) AS Total FROM Orders WHERE Total > {min} GROUP BY Region")
    .ToListAsync();                          // ✅ one-off report, value is a parameter (EF Core 8+)

For a one-off report, project raw SQL straight into a type — the interpolated value becomes a parameter.

🌍 Real-world example ▾

A reporting screen needs per-customer order totals that a database view already computes and the DBA maintains. Map a keyless OrderSummary to the view and page and filter it with LINQ — no table, no tracking, nothing to accidentally save.
