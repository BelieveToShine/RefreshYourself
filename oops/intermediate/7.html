Factory vs. Dependency Injection — when you need one in addition to the other

What problem does a Factory solve that plain Dependency Injection doesn't?

Why it matters ▾
  • Interviewers use this to check you understand DI's actual limit — not just that you can spell "constructor injection."
  • Comes up whenever the concrete type to build depends on something only known while the app is running, not when it started.
  • A common interview opener right after any DI question — "okay, but what if you don't know which implementation you need until later?"
🔥 Easy interview recall

DI → resolves the factory, once, at startup

Factory → picks the concrete type, at runtime

Think: DI decides who does the deciding. The factory does the actual deciding, using data DI never had.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

DI and Factory are not competing techniques. They compose — forcing everything through constructor DI when the decision genuinely needs runtime data just makes you inject every possible implementation and branch on it yourself, the exact conditional-logic smell Strategy exists to avoid.

🔄 Likely Follow-up

"So is the factory itself just… more Strategy?" Sort of — the factory's job is picking which strategy to use. The two patterns often show up together: Factory decides WHICH Strategy, Strategy is what actually gets executed.

🎯 Say this in the interview — the exact lines to land

"Plain constructor DI works when the container can decide the concrete type once, at startup. A Factory solves a different problem — when the concrete type depends on data that's only known at runtime, inside a method call. So I inject the factory itself through DI, then call it with that runtime value to get back the right concrete type."

  • DI → decides once, at startup, before the runtime data exists.
  • Factory → decides on every call, using data DI never had access to.
  • They compose → DI provides the factory; the factory provides the concrete type.
  • Skipping the factory → forces injecting every implementation and branching by hand in the consumer.
📖 Explanation ▾

A DI container resolves dependencies at construction time — it has to know, right then, exactly which concrete class to hand over. That works perfectly when the choice is fixed: one interface, one registered implementation, decided once when the app starts up.

A Factory exists for the case DI can't reach: the concrete type depends on a value that doesn't exist yet at startup — an order's country, a tenant ID, a file's format — and only shows up inside a method call, long after the container already finished wiring everything together. The factory itself is a perfectly ordinary DI-resolved dependency; its whole job is to make the decision that DI's own resolution moment came too early for.

That's why the two aren't alternatives: DI supplies the factory, and the factory supplies the concrete type — one mechanism handing off to the other at the exact point where "known at startup" runs out.

Plain DIFactory
Decision madeat startup, during constructionat runtime, inside a method call
Who decidesthe container's registrationyour code, using a runtime value
Data availableonly what exists before constructionanything passed into the method
Typical shapeone interface → one registered classone interface → Create(...) branching to several classes

💻 See the code ▾
C# 
// ✅ Plain DI is enough — one interface, one implementation, decided at startup
public class OrderService
{
    private readonly IEmailSender _emailSender;

    public OrderService(IEmailSender emailSender) // resolved once, at construction
    {
        _emailSender = emailSender;
    }
}

The container already knows which IEmailSender to hand over — nothing about that choice depends on runtime data.

C# 
// ❌ The workaround people force through constructor DI alone
public class OrderService
{
    private readonly DomesticShipping _domestic;
    private readonly InternationalShipping _intl;   // every impl injected up front

    public IShippingCalculator CalculateShipping(Order order)
    {
        if (order.Country == "US") return _domestic;   // branching by hand
        return _intl;
    }
}

Compiles fine, but every implementation is injected whether this order needs it or not — the conditional-logic smell Strategy exists to avoid.

C# 
// ✅ The fix — DI provides the factory, the factory picks the type
public class OrderService
{
    private readonly IShippingCalculatorFactory _factory;

    public OrderService(IShippingCalculatorFactory factory) // DI resolves the factory once
    {
        _factory = factory;
    }

    public decimal CalculateShipping(Order order)
    {
        IShippingCalculator calculator = _factory.Create(order.Country); // decided now, with runtime data
        return calculator.Calculate(order);
    }
}

order.Country doesn't exist until this method runs — the factory is the only piece that can use it.

🌍 Real-world example ▾

Your checkout flow needs domestic or international shipping math, and the answer depends on the customer's saved address — data that doesn't exist when the app starts, only once an order comes in. Inject IShippingCalculatorFactory through DI as usual, then call factory.Create(order.Country) inside CalculateShipping — DI never has to know the address exists, and the factory never has to know how it got constructed.
