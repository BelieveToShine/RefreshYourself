OCR reads the pixels. A vision model reads the pixels — and reasons about them, too

"How would you extract structured data — say, a price and product name — from an image using a vision model?"

Why it matters ▾
📄 OCR / Document Intelligence
❗ ProblemA simple, highly structured document still needs its text pulled out of the image, but running a full vision-reasoning model over it spends more compute than the job actually needs.
✅ SolutionOCR/Document Intelligence extracts the raw text straight from the pixels — cheaper, and just as reliable when the layout isn't in question.
RecallOCR = reads the text, blind to layout meaning — cheap and reliable for simple documents.
🤖 Vision-LLM
❗ ProblemA flat OCR transcript strips the layout out, so once a document gets visually busy nothing can reliably tell which price belongs to which product — and if a value is only baked into the image as pixels, OCR has no text there to extract at all.
✅ SolutionA vision-capable model reads the image directly and reasons about its layout and meaning in the same call, so it can still tie values together correctly or recover data a text-only pipeline missed.
RecallVision-LLM = reads the pixels and reasons about them, in one call.
🔥 Easy interview recall

OCR → reads the text, blind to meaning

Vision-LLM → reads the text and reasons about it

Think: OCR transcribes. Vision-LLM transcribes AND understands — one call, not two.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A vision model doesn't replace OCR/Document Intelligence everywhere. For a simple, highly structured document, pure OCR is still cheaper and often just as reliable — reach for a vision model when the layout is genuinely complex, or when the data isn't sitting in any surrounding text at all.

🔄 Likely Follow-up

"Why not just run OCR first and hand the extracted text to a text-only model?" OCR hands back a flat blob of text with the layout stripped out, so a text-only model can't reliably tell which price belongs to which product once the layout gets complex — a vision model looks at the image directly and can still make that association correctly.

🎯 Say this in the interview — the exact lines to land

"A vision-capable model can take an image straight into the prompt alongside instructions and even a few-shot example, then both read the pixels and reason about their layout and meaning in one call — I'd constrain the result with the same JSON-schema or tool-calling techniques as any structured-output task, at a temperature near 0, since extraction should be a read-what's-there task, not a creative one."

  • OCR / Document Intelligence → use for simple, highly structured documents — cheaper, and layout isn't in question.
  • Vision-LLM → use when layout is complex or a value isn't in any surrounding text at all.
  • Temperature → near 0 — extraction is a read-what's-there task, variance shows up as wrong field values.
  • JSON schema / tool calling → same techniques as text-only structured output, applied to the image prompt.
  • Real fallback pattern → a vision pass recovers data a text pipeline missed — e.g. a discount only shown as pixels in a banner.
📖 Explanation ▾

A vision-capable model can take an image — a screenshot, a scanned page, a photo of a banner — directly as part of the prompt, right alongside plain-text instructions. That's different from traditional OCR: OCR pulls the raw text out of an image but has no understanding of layout or meaning on its own — it hands back a flat transcript. A vision model both reads the visual content and reasons about its structure in the same step, so it can correctly tie a price to the product next to it even when the layout is visually busy — something a flat OCR transcript alone can't guarantee.

What it doesExtracts raw text from the imageReads the image and reasons about its structure/meaning
Understands layout?❌ not on its own✅ yes, in the same step

Because the image and the text instructions travel in one request, the same structured-output techniques from constraining any other model call still apply — a JSON schema or tool-calling definition constrains the extracted result's shape, and a few-shot example of the desired output can ride along in the same prompt. And because extraction is meant to be a mostly-deterministic "read what's actually there" task rather than a creative one, temperature should sit at or near 0 — variance here shows up as inconsistent or invented field values, not a more interesting answer.

💻 See the code ▾
Pseudocode 
response = call_vision_model(
    image=promo_banner_image,
    instructions="Extract the product name and price as JSON.",
    response_format=ProductPriceSchema,  # ✅ same schema technique as text-only extraction
    temperature=0                    # ✅ deterministic read, not a creative task
)

The image and the instruction travel in one request — the schema still locks the output's shape, the same way it does for text-only extraction.

Pseudocode 
result = text_extraction_pipeline(page_text)
if not result.discount:      # 🐛 discount only shown as pixels in the banner
    result = vision_model_extract(promo_image, schema=DiscountSchema)  # ✅ fallback recovers it

When the text-based pipeline comes up empty, a vision pass over the image itself can recover structured data that was never in any surrounding text.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're extracting from a simple, highly structured document — like a labeled form

The fields sit in a layout that isn't in question, so a full vision-reasoning pass isn't buying anything extra here. OCR/Document Intelligence pulls the raw text out of the pixels — cheaper, and just as reliable for this case.

RememberSimple, structured layout → OCR/Document Intelligence, it's cheaper.
2 The layout is busy, or a value only exists as pixels — like a discount baked into a promo banner

A flat OCR transcript strips the layout out, so it can't reliably tell which price belongs to which product, and it has nothing to extract at all when a value is only baked into the image. A vision model reads the image directly and reasons about the layout in the same call, so it can still make the right association or recover a value a text pipeline missed entirely.

RememberBusy layout or pixels-only value → Vision-LLM, in one call.
3 You reach for a vision model on every extraction task "just to be safe"

For a simple, highly structured document, pure OCR/Document Intelligence is still cheaper and often just as reliable — running every extraction through a vision model adds cost without adding accuracy. A common trap — save the vision pass for layouts that are genuinely complex, or data that isn't sitting in any surrounding text at all.

RememberSimple doc, no complexity → OCR still wins on cost.
🌍 Real-world example ▾

A promo email renders its discount as text baked into a banner graphic, with no matching text anywhere else on the page. The text-based extraction pipeline finds nothing to work with. A fallback pass sends that one banner image to a vision model with the same "extract as JSON" instruction, and recovers the discount amount and product name the text pipeline missed entirely.
