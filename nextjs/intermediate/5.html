ISR — a static page that refreshes itself, no rebuild needed

"How does ISR let a static page stay fresh without a full rebuild?"

Why it matters ▾
♻️ Incremental Static Regeneration
❗ ProblemA fully static page is fast but goes stale the moment its data changes, and the only fix without ISR is rebuilding and redeploying the whole site every time content updates.
✅ Solutionrevalidate tells Next.js to keep serving the cached static page for N seconds, then regenerate it in the background on the next request after that — fast responses the whole time, with content that still refreshes periodically.
RecallISR = static speed, with a timer that refreshes the page in the background.
🔥 Easy interview recall

ISR = "static page, with a background refresh timer."

Think: revalidate = 60 → fast cached page for 60s, then the next visitor triggers a background rebuild.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ISR doesn't update the page the instant the revalidate window passes. It regenerates on the next request after expiry — so the very first visitor after the window closes can still briefly see the old cached page while the new one regenerates in the background.

🔄 Likely Follow-up

"How is this different from true SSR on every request?" SSR pays the full render cost on every single request; ISR pays that cost only once per revalidation window, serving a fast cached response for every request in between.

🎯 Say this in the interview — the exact lines to land

"revalidate = 60 tells Next.js to serve the cached static page for up to 60 seconds, then regenerate it in the background on the next request after that — users keep getting fast cached responses while the content still refreshes periodically, without a full rebuild."

  • revalidate: N → cached for N seconds, then eligible to refresh.
  • Refresh happens on the next request, not the instant the window expires.
  • Cost paid once per window, not once per request like true SSR.
📖 Explanation ▾

Setting export const revalidate = 60 on a route (or {next: {revalidate: 60}} on a specific fetch()) marks the page's cached HTML as stale after 60 seconds. Until that window passes, every request gets the exact same cached response — no re-render, no network call, just a fast file serve.

Once the window has passed, the next request is the one that triggers regeneration — Next.js serves that request the still-stale cached page one more time, kicks off a fresh render in the background, and swaps in the new version once it's ready. This is the standard "stale-while-revalidate" pattern, not an instant refresh.

The trade-off this buys: SSR pays a full render cost on every request, forever. ISR pays that same cost only once per revalidation window — everyone else in between gets a cached response, at the price of occasionally serving data that's up to revalidate seconds old.

💻 See the code ▾
Next.js 
// app/blog/[slug]/page.js — route-level ISR
export const revalidate = 60;   // ✅ whole route refreshes at most every 60s

export default async function BlogPost({ params }) {
  const post = await getPost(params.slug);
  return <article>{post.title}</article>;
}

Applies to every fetch inside this route unless a call overrides it.

Next.js 
// per-fetch ISR instead — just this call revalidates on its own schedule
const res = await fetch('https://api.example.com/post/' + slug, {
  next: { revalidate: 60 }
});

Scoped to one fetch call — other fetches on the same page can use a different window.

🧭 Use Cases — recognize these when they happen to you ▾
1 A news or content site that updates every few minutes

Headlines don't need to be real-time, but shouldn't be hours stale either — a short revalidate window gives a fast, mostly-static site that still stays reasonably current without redeploying.

RememberChanges every few minutes → ISR with a short window.
2 Traffic spikes right as the revalidation window expires

Even with a flood of requests right after the window expires, Next.js only kicks off one background regeneration — every other request in that moment still gets the stale cached page instead of piling onto a render each.

RememberExpiry under load → one regeneration, not one per request.
3 You expect the page to update the exact second the timer hits zero

That first request after expiry is the one that triggers the rebuild — it does not wait for the rebuild to finish, so it still receives the old cached page. Only requests after the regeneration completes see the fresh version.

RememberWindow expiry triggers regen, doesn't wait for it.
🌍 Real-world example ▾

An e-commerce product page where price and stock change a few times a day. revalidate = 300 keeps every page load fast and cached, while guaranteeing price and stock are never more than 5 minutes out of date — no redeploy needed when the warehouse system updates inventory.
