Minimal APIs — less ceremony, fewer built-in conveniences

"What are minimal APIs, and when would you pick them over controllers?"

Why it matters ▾
⚡ Minimal APIs
❗ ProblemA small service or a few simple endpoints still needed a controller class, attributes, and base-class ceremony.
✅ SolutionMapGet/MapPost map a route straight to a lambda or method, on the same routing, DI, and middleware.
RecallRoute in, lambda out.
🧰 Trade-offs
❗ ProblemControllers came with conventions like MVC filters and the automatic 400 from [ApiController]; a minimal API does not run those.
✅ SolutionUse endpoint filters and MapGroup to share logic, and validate input yourself or with a filter.
RecallLess ceremony, fewer built-in conveniences.
🔥 Easy interview recall

MapGet / MapPost → a route straight to a handler

MapGroup → shared prefix, auth, filters

Endpoint filter → replaces MVC filters here

Think: Same Kestrel, DI, middleware, routing as controllers. No controller class, no automatic 400.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming a minimal API validates input and returns 400 like [ApiController] does. It does not — and MVC filters do not run for it either. Check the input yourself, or use an endpoint filter. (.NET 10 adds opt-in built-in validation: call builder.Services.AddValidation() and DataAnnotations attributes on query, header and body values are checked for you; DisableValidation() turns it off per endpoint.)

🔄 Likely Follow-up

"How do you share auth or logging across many minimal endpoints?" Put them in a group: app.MapGroup("/orders").RequireAuthorization().AddEndpointFilter(...). The group applies the prefix, metadata and filters to every endpoint inside it.

🎯 Say this in the interview — the exact lines to land

"Minimal APIs map a route straight to a lambda or method with MapGet and MapPost, on the same endpoint routing, DI and middleware as controllers, just without controller classes. Parameters are bound from the route, query, body or DI by their type. What I give up are the MVC conventions: no MVC filters and no automatic 400 from [ApiController], so I use endpoint filters and MapGroup instead. I pick them for small services and simple endpoints, and controllers when I want the conventions for a large API."

  • MapGet / MapPost → route straight to a handler — no controller class needed.
  • Binding → inferred from the parameter type — route values, query, body, and DI services, without attributes.
  • Filters → endpoint filters, not MVC filters — attach them to one endpoint or a whole MapGroup.
  • Missing → no automatic 400 by default — validate yourself, with a filter, or opt in with AddValidation() in .NET 10.
📖 Explanation ▾

Minimal APIs are not a different server; they are endpoints registered directly on WebApplication. Routing, DI, authentication, and middleware work as they do for controllers — you simply skip the controller class. Handlers return plain values (serialised as JSON) or Results/TypedResults helpers.

Binding is inferred: a parameter that matches a route value comes from the route, a simple type otherwise comes from the query string, a complex type in a POST comes from the body, and a registered service comes from DI. Endpoint filters (AddEndpointFilter) are the equivalent of MVC action filters, and MapGroup shares a route prefix, authorisation, and filters across a set of endpoints.

The trade-off: none of the MVC conventions come for free — no MVC filters, no automatic 400 from [ApiController], no controller-based organisation. Validation is opt-in too: .NET 10 added AddValidation() for DataAnnotations checks. That is fine for small services; for a large API many teams prefer controllers for the structure. See also: Routing, Model Binding & Validation, MVC-Specific Filters, IActionResult vs. ActionResult<T>.

💻 See the code ▾
C# 
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddScoped<IOrderService, OrderService>();
var app = builder.Build();

var orders = app.MapGroup("/orders").RequireAuthorization();   // shared prefix + auth

orders.MapGet("/{id:int}", async (int id, IOrderService svc) =>
{
    var order = await svc.FindAsync(id);                       // id from route, svc from DI
    return order is null ? Results.NotFound() : Results.Ok(order);
});

orders.MapPost("/", (CreateOrder body, IOrderService svc) =>
{
    if (body.Quantity <= 0)                                    // no automatic 400 — check yourself
        return Results.BadRequest("Quantity must be positive");
    var created = svc.Create(body);
    return Results.Created($"/orders/{created.Id}", created);
})
.AddEndpointFilter(async (ctx, next) =>
{
    // runs before the handler
    var result = await next(ctx);
    // runs after the handler
    return result;
});

app.Run();

No controller class anywhere: id binds from the route, svc from DI, and body from the JSON body.

🌍 Real-world example ▾

A food-truck window vs. a full restaurant. Both cook in the same kitchen (Kestrel, DI, middleware); the truck just skips the dining room, menu printing and waiters — great for a short menu, but you do your own table-service when the menu grows.
