Event Loop — why does setTimeout(fn, 0) run after a Promise?

"Walk me through what the JavaScript engine actually does with the call stack, the task queue, and the microtask queue — and why does a Promise callback run before a setTimeout(fn, 0) callback?"

Why it matters ▾
  • "Predict the output" of a setTimeout / Promise snippet is one of the single most common JavaScript interview screens, at every level.
  • Real production bugs — a UI update that should happen "right after" a promise resolves, but a timer callback jumps in first — trace directly back to not knowing this ordering rule.
  • It's the fastest way an interviewer separates someone who memorized async/await syntax from someone who understands what's actually running underneath it.
🔥 Easy interview recall

The whole microtask queue drains before the next macrotask runs — even a 0ms setTimeout waits its turn.

Think: sync code first, then every microtask (Promise, queueMicrotask), then one macrotask (setTimeout, I/O), repeat.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

setTimeout(fn, 0) does not mean "run immediately." It means "queue this once the call stack is empty AND every pending microtask has drained" — a long enough chain of .then() calls can push that 0ms callback back arbitrarily far.

🔄 Likely Follow-up

"Does the browser get to repaint between every microtask?" No — the browser typically gets a chance to paint between macrotasks, not between each microtask, so a microtask that keeps re-queueing more microtasks can starve rendering entirely, even though the page never technically "freezes" at the JS level.

🎯 Say this in the interview — the exact lines to land

"JavaScript runs one thing at a time on the call stack. setTimeout hands its timer to the Web APIs, which only queue the callback into the macrotask queue once the timer fires; Promise callbacks and queueMicrotask() queue straight into the microtask queue. Once the call stack is empty, the event loop drains the entire microtask queue before it even looks at the macrotask queue — that's why a Promise callback always beats a setTimeout(fn, 0) callback, even at the same 0ms delay."

  • Call stack → runs all synchronous code first, every time, with no interruptions.
  • Web APIs → where a timer actually waits — never on the call stack itself.
  • Microtask queue → drains COMPLETELY before the next macrotask starts, no exceptions.
  • queueMicrotask() → the same queue Promise callbacks use — it's about the queue, not specifically Promises.
  • setTimeout(fn, 0) → means "soon," never "now".
📖 Explanation ▾

JavaScript has one call stack and runs on a single thread — whatever is on the stack runs to completion before anything else gets a turn. Async work never actually pauses that thread; it gets handed off. setTimeout hands its timer to the browser's Web APIs, which only push the callback into a queue once the timer actually fires — the delay is a minimum wait before it's even eligible to run, not a guarantee it runs at that exact moment.

There are two queues, and they are not equal. A microtask (a Promise callback, or anything passed to queueMicrotask()) queues directly, with no Web APIs stop first. A macrotask (a fired setTimeout/setInterval callback, most I/O) queues separately. Once the call stack empties, the event loop's rule is strict: drain the whole microtask queue — including any new microtasks a running one just queued — before it even glances at the macrotask queue, and then run exactly one macrotask before checking the microtask queue again. That single rule is the entire reason a Promise.resolve().then() always "wins" against a setTimeout(fn, 0), no matter how the delay is written.

Rendering sits outside both queues. The browser typically gets a chance to paint an updated frame between macrotasks, not between every individual microtask — so a script that keeps chaining new microtasks can finish all its work before a single frame paints, and a runaway microtask loop (one that keeps re-queueing itself) can block rendering far longer than a runaway setTimeout loop would, even though neither technically "freezes" the JS engine.

💻 See the code ▾
JavaScript 
console.log("A");                                     // ① sync — logs right away

setTimeout(() => console.log("B"), 0);              // ② → Web APIs, then MACROtask queue

Promise.resolve().then(() => console.log("C")); // ③ → MICROtask queue, directly

console.log("D");                                     // ④ sync — logs right away

// ✅ Actual output: A, D, C, B

Sync code (A, D) always finishes first. Then the whole microtask queue drains — just C — before the event loop even checks the macrotask queue, which finally runs B.

JavaScript 
console.log("A");

setTimeout(() => console.log("D (setTimeout)"), 0);        // macrotask

queueMicrotask(() => console.log("B (queueMicrotask)"));  // microtask #1 — queued first

Promise.resolve().then(() => console.log("C (Promise.then)")); // microtask #2 — queued second

console.log("A2");

// ✅ Actual output: A, A2, B (queueMicrotask), C (Promise.then), D (setTimeout)

queueMicrotask() lands in the exact same queue Promise callbacks use — both run after all sync code and before the timer, in the order they were queued.

JavaScript 
setTimeout(() => console.log("timeout 1"), 0);
setTimeout(() => console.log("timeout 2"), 0);
Promise.resolve().then(() => console.log("promise"));

// ✅ Actual output: promise, timeout 1, timeout 2

One microtask still beats two macrotasks — the whole microtask queue empties before the event loop touches the macrotask queue at all, and the two timeouts then run in the order they were scheduled.

🌍 Real-world example ▾

A UI update inside a .then() keeps finishing before an analytics call scheduled with setTimeout(fn, 0) — even though the timer was written first in the code. That's not a bug: the microtask queue always drains before the next macrotask, so any number of chained .then() calls can push that "immediate" 0ms timer back further than it looks like it should wait.
