Large payloads — stream it, don't hold the whole thing in memory

"How do you handle a very large request or response payload without blowing up memory or timing out?"

Why it matters ▾
  • An API that works fine in testing can still fall over in production the moment a few large uploads land at the same time — the failure is about concurrent memory pressure, not any single request being "too big."
  • Interviewers use this to check whether you reach for streaming and limits by design, not "increase the timeout" as a first reflex.
  • A common opener before the interviewer pushes into what you'd do if the client itself can't be changed.
🔥 Easy interview recall

Large payload = "stream it in chunks, never buffer the whole thing."

Think: a Stream is a hallway one box at a time. A buffered body is the whole truckload dumped in the hallway at once.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just raise the timeout / give it more memory" is not a fix. That treats unbounded buffering as a config problem — it only delays the exact same crash to a bigger payload or a busier hour, instead of fixing the design that never releases memory until the whole body is in.

🔄 Likely Follow-up

"What if the client can't be changed to stream or chunk its upload — is there still something you can do server-side?" Yes — you can still read and process the incoming body in chunks on the server even if the client sends it all in one shot; it won't shrink the total transfer time, but it keeps server memory bounded instead of proportional to payload size, and a request size limit still protects you either way.

🎯 Say this in the interview — the exact lines to land

"I'd stream the body in chunks instead of buffering it whole — using Stream or IAsyncEnumerable<T> — keep everything async so the thread isn't held for the transfer, page large response sets instead of returning them in one body, and set an explicit request size limit as a deliberate defensive cap, not an afterthought."

  • Streaming → bounded, constant memory no matter the payload size.
  • Large response sets → page them, never return 500,000 rows in one JSON body.
  • Compression → trades CPU for bandwidth, and does nothing for already-compressed data like images or video.
  • Async I/O → releases the thread while waiting instead of blocking it for the whole transfer.
  • Request size limits → a deliberate defensive cap, not an oversight to raise without thinking.
📖 Explanation ▾

Streaming means reading or writing a payload piece by piece — a Stream, or an IAsyncEnumerable<T> in ASP.NET Core — instead of loading the entire request or response body into one in-memory object first. Memory use stays roughly constant per request no matter how large the payload is, which is the difference between an API that holds up under many concurrent large transfers and one that runs out of memory or times out as soon as a few land together.

Several other techniques attack the same problem from different angles. Pagination keeps a large response set from ever becoming one giant body — see Pagination for the request/response shape. Response compression (gzip/br) trades CPU time for a smaller transfer, but it doesn't help already-compressed data like images or video — compressing a JPEG again mostly just burns CPU. Chunked/multipart uploads let ASP.NET Core stream a file straight to disk or blob storage instead of holding the whole upload in a memory buffer. And a payload held on a blocked synchronous thread ties up a thread-pool thread for the entire transfer — going async all the way down releases that thread while the I/O is in flight.

Request size limits (Kestrel's own limits, or [RequestSizeLimit]) are a deliberate design choice, not a gap to close by raising them — they protect the server from a single oversized request exhausting resources on their own, streaming or not.

💻 See the code ▾
C# 
// ❌ whole file loaded into memory before it's saved anywhere
[HttpPost("upload")]
public async Task<IActionResult> Upload(IFormFile file)
{
    using var ms = new MemoryStream(); // buffers the entire upload
    await file.CopyToAsync(ms);
    await _blob.SaveAsync(ms.ToArray());     // one huge byte[] held at once
    return Ok();
}

Memory use here is proportional to the file's size — a few large uploads at once can exhaust the server, regardless of the timeout setting.

C# 
// ✅ streamed straight through — memory stays flat regardless of file size
[HttpPost("upload")]
[RequestSizeLimit(100_000_000)] // still capped — defense, not an oversight
public async Task<IActionResult> Upload()
{
    await using var input = Request.Body;        // the raw request stream
    await _blob.SaveStreamAsync(input);         // piped through in chunks
    return Ok();
}

Nothing here holds the whole file at once — bytes flow from the request straight to storage, with a size limit as a separate, deliberate safety cap.

C# 
// ✅ a large response streamed row-by-row instead of built as one giant list
[HttpGet("export")]
public async IAsyncEnumerable<OrderRow> ExportOrders()
{
    await foreach (var row in _repo.StreamAllAsync())
        yield return row;   // one row in flight at a time, not 500,000 in a List<T>
}

IAsyncEnumerable<T> writes each row to the response as it's produced — the server never assembles the full result set in memory first.

🌍 Real-world example ▾

Your export endpoint works fine in testing with a few thousand rows, then a customer with 2 million rows triggers timeouts and, under a second concurrent export, an out-of-memory crash. The fix isn't a bigger timeout or more server RAM — both just move the failure to a larger number. Stream the query results row-by-row with IAsyncEnumerable<T> instead of materializing the full list, or offer pagination for interactive callers and a background export job with a downloadable file for the bulk case — either way, memory use stops scaling with row count.
