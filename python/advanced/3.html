super() doesn't mean "my parent class" — it means "the next class in the MRO chain"

What is MRO? How does Python actually resolve the diamond-inheritance problem?

Why it matters ▾
  • MRO questions separate "I memorized super() calls the parent" from actually understanding how Python resolves multiple inheritance.
  • Comes up constantly in real bugs when a codebase stacks several mixins — a wrong assumption about what super() calls next makes logic run in the wrong order, or skip entirely.
  • A common follow-up once someone can explain single inheritance well — interviewers use it to check whether the understanding actually generalizes.
🔥 Easy interview recall

MRO = "the exact order Python walks the base classes to resolve a name."

Think: super() means "next in the MRO," not "my parent."

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

super().__init__() does not always call "my parent class's" __init__. In a multiple-inheritance hierarchy it calls whatever's next in the full MRO — which depends on the entire class graph the final subclass was built from, not just the immediate base list of the class you're standing in.

🔄 Likely Follow-up

"Why can multiple inheritance become dangerous, and when is composition preferable?" Deep or wide multiple-inheritance hierarchies get hard to reason about — which method actually runs, and in what order, stops being obvious without checking ClassName.__mro__ directly. Composition (an object holding another object and delegating to it) is often clearer, and skips MRO complexity entirely when you just need reuse, not a genuine is-a relationship.

🎯 Say this in the interview — the exact lines to land

"super() means 'the next class in the MRO,' not 'my parent' — when multiple inheritance gets non-obvious, I check ClassName.__mro__ instead of guessing."

  • MRO is computed by C3 linearization — deterministic, and it always puts a subclass before its own bases.
  • super() → next in the MRO, not "my direct parent" — the two only differ once multiple inheritance is involved.
  • Check the real order any time it's non-obvious: ClassName.__mro__ — never guess from the class's own base list.
  • Composition is the safer default when you just need reuse, not a genuine is-a relationship.
📖 Explanation ▾

MRO (Method Resolution Order) is the exact, deterministic order Python walks a class's bases when it needs to find an attribute or method. Python computes it with the C3 linearization algorithm, which guarantees two things at once: a subclass always comes before any of its own bases, and each class's own declared base order is preserved. For a standard diamond — D(B, C), where both B and C extend A — the resulting MRO is D, B, C, A, in that exact order.

This is what super() actually means: not "go to my declared parent," but "go to whatever comes next in this instance's MRO." In single inheritance the two are the same thing, so the distinction never shows up. In multiple inheritance they can diverge — a class sitting inside a mixin can't tell, just from its own base list, which sibling class super() will land on next; that depends on the whole hierarchy the final subclass was built from, not just its own declaration.

The diamond problem is exactly the ambiguity C3 resolves: without a defined order, it's unclear whether D should get B's or C's version of an overridden method. C3 linearization removes that ambiguity by computing one consistent order every time, so the same hierarchy always resolves the same way.

💻 See the code ▾
Python 
class A:
    def who(self): return "A"

class B(A):
    def who(self): return "B"

class C(A):
    def who(self): return "C"

class D(B, C): pass

print(D().who())      # "B" — not A, not C
print(D.__mro__)

Predict the output: D overrides nothing itself, so Python looks at D.__mro__ — D, B, C, A — and returns the first override it finds. That's B's, even though C was declared second and A is the "common" base.

Python 
class LoggingMixin:
    def save(self):
        print("LoggingMixin.save")
        super().save()

class ValidationMixin:
    def save(self):
        print("ValidationMixin.save")
        super().save()

class Model:
    def save(self): print("Model.save")

class Article(LoggingMixin, ValidationMixin, Model):
    pass

Article().save()

Prints LoggingMixin.save, then ValidationMixin.save, then Model.save. super() inside LoggingMixin does not call Model.save directly — it calls whatever's next in Article's MRO, which happens to be ValidationMixin.

🌍 Real-world example ▾

A team building on a web framework's class-based views stacked several mixins — logging, permission checks, caching — onto one view class. A developer assumed super().dispatch() inside their custom mixin called the base view's dispatch() directly. It didn't — because of the full MRO across every stacked mixin, it actually called a different mixin's dispatch() next, silently skipping logic the developer thought ran first. The fix was checking the view class's __mro__ to see the real order, instead of guessing from the mixin list.
