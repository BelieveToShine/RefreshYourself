A list of thousands lags — reach for the cheapest fix first, not virtualization first

"A page rendering a few thousand list items is sluggish — walk me through how you'd fix it."

Why it matters ▾
🐢 A Slow, Large List
❗ ProblemA list of a few thousand rows feels sluggish, and the instinct is to reach straight for virtualization — which adds real complexity (scroll-position math, variable row heights) that isn't always the actual bottleneck.
✅ SolutionTriage cheapest-first: confirm it's render cost (not network), check for a missing/unstable :key, consider v-memo for untouched rows, and only virtualize once the list is genuinely huge.
RecallKey → v-memo → virtualize — cheapest fix first.
🔥 Easy interview recall

Slow list fix order = "key → v-memo → virtualize — cheapest first."

Think: don't reach for the most complex tool before ruling out the cheap ones.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for virtualization as the FIRST fix before checking the cheaper, more common causes (key issues, unnecessary per-row computation) — virtualization adds real complexity that isn't always the actual bottleneck.

🔄 Likely Follow-up

"What's the actual trade-off virtualization introduces?" It only renders the visible window of rows, which is fast, but it complicates things like "scroll to a specific item," variable row heights, and browser find-in-page, since most rows aren't in the DOM at all — a real cost, not a free win.

🎯 Say this in the interview — the exact lines to land

"I'd triage cheapest-first: confirm it's actually render cost and not a slow fetch, check for a missing or unstable :key forcing full re-creation instead of patching, consider v-memo to skip untouched rows, and only reach for virtualization once the list is genuinely large enough — hundreds or thousands of visible rows — to need it."

  • Render or network? → confirm it's actually render cost first.
  • Bad/missing :key → forces full DOM re-creation instead of patching.
  • v-memo → skip re-rendering rows whose data hasn't changed.
  • Virtualization → last resort, for genuinely huge lists, real trade-offs attached.
📖 Explanation ▾

Start by confirming the bottleneck is actually render cost — open the browser's performance tab and check whether the time is going into scripting/rendering or into a slow network fetch feeding the list. A sluggish fetch needs a completely different fix than a sluggish render, and treating one as the other wastes effort on the wrong problem.

If it is render cost, check :key first — a missing key, or one that isn't stable across re-renders, forces Vue to tear down and recreate DOM nodes instead of patching them, which is far more expensive than it needs to be for a list this size. Next, v-memo lets a row skip re-rendering entirely when none of the values it's memoized against have changed — useful when most rows in a long list are visually static between updates.

Only once the list is genuinely large — typically many hundreds to thousands of rows actually rendered at once — does virtualization (a library like vue-virtual-scroller) earn its complexity: it renders only the rows currently in the visible scroll window, keeping the DOM small regardless of how many total items exist, at the cost of needing its own logic for scroll position, variable row heights, and anything that expects every row to actually be in the DOM.

💻 See the code ▾
Vue 
<li
  v-for="row in rows"
  :key="row.id"
  v-memo="[row.selected, row.text]"  // ✅ skip re-render unless these change
>
  {{ row.text }}
</li>

A row whose selected/text haven't changed since last render is skipped entirely — real savings for a list where most rows stay static.

🧭 Use Cases — recognize these when they happen to you ▾
1 A list has a missing or unstable :key

This is the #1 scenario you'll actually run into — the cheapest check, and the one most likely to actually be the cause of a "slow list" complaint on a list that isn't even that large.

RememberCheck :key before reaching for anything more complex.
2 Most rows are visually static between updates, only a few actually change

v-memo is the right reach here — it skips re-rendering a row entirely when the values it's memoized against haven't changed, without the complexity of a virtualization library.

Rememberv-memo is for "mostly static rows," not "huge lists."
3 A list is genuinely huge — thousands of rows rendered at once

Only once the cheaper fixes are ruled out and the list is still slow because of its sheer size does virtualization earn its real cost — scroll-position math, variable row heights, and most rows simply not existing in the DOM at any moment.

RememberVirtualize last, and only once size is the actual confirmed cause.
🌍 Real-world example ▾

A support team's ticket list, a few thousand rows, starts lagging noticeably on every status update. The actual cause turns out to be a missing :key on the row component — adding a stable ticket.id key fixes the lag completely, with no virtualization library ever needed.
