== vs. equals() — same object, or just the same content?

"What's the difference between == and equals() in Java?"

Why it matters ▾
🪪 ==
❗ ProblemSometimes you genuinely need to know whether two variables point at the exact same object in memory — a weaker check would give the wrong answer.
✅ SolutionOn reference types, == compares identity — same object or not. On primitives it just compares the value, since there's no identity to compare.
Recall== on objects = are they the same one?
⚖️ equals()
❗ ProblemFar more often you actually want to know if two separate objects represent the same logical value — two Strings with the same text, two records with the same fields.
✅ Solutionequals() is a method, inherited from Object as identity by default, and commonly overridden to compare content instead.
Recallequals() = whatever "same" means for that class.
🔥 Easy interview recall

== → identity for objects, value for primitives

equals() → content — if the class overrides it

Think: == asks "same box?" equals() asks "same stuff inside?"

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Two boxed Integers comparing equal with == means == is safe for objects. It only "works" by coincidence for cached values (-128 to 127, via the Integer cache) and silently breaks outside that range — always use equals() for wrapper/object comparison, never ==.

🔄 Likely Follow-up

"Does == ever make sense for objects?" Only when you deliberately want identity — checking a cache hit, or that two references point at the same singleton — never as a substitute for content comparison.

🎯 Say this in the interview — the exact lines to land

"== on reference types compares identity — same object in memory. On primitives it compares value. equals() is inherited from Object as identity by default, and classes like String override it to compare content instead."

  • == on objects → same object in memory, nothing about content.
  • equals() → whatever "same" means for that class, once overridden.
  • Integer cache (-128–127) → a coincidence of caching, never a reason to use ==.
📖 Explanation ▾

== on a reference type never looks at an object's fields — it only checks whether both variables point at the exact same object. On a primitive, there's no object to point at, so == simply compares the two values directly.

equals() is a real method, inherited from Object. Its default implementation is identity — effectively the same thing == does — but it's commonly overridden (String, records, most custom classes) to compare the object's actual fields instead.

The Integer cache makes small boxed values (-128 to 127) share one object, so == happens to return true in that range — this is a caching detail to recognize as a pitfall, never a reason to reach for == over equals().

💻 See the code ▾
Java 
String a = new String("Sam");
String b = new String("Sam");

a == b          // ❌ false — two separate objects
a.equals(b)     // ✅ true — String overrides equals() to compare content

Same text, two different String objects — == and equals() genuinely disagree.

Java 
Integer x = 100, y = 100;
x == y          // ✅ true — both in the cached -128..127 range (coincidence)

Integer m = 200, n = 200;
m == n          // ❌ false — outside the cache, two separate objects

The Integer cache makes == "work" by accident for small values — never rely on it; use equals().

🧭 Use Cases — recognize these when they happen to you ▾
1 Comparing two String variables built from user input

Different String objects with the same text have to compare equal by content — always equals(), never ==. This is the #1 scenario you'll actually run into.

RememberComparing string content → always equals().
2 Checking whether a cache returned the exact same instance

When you deliberately want to know "is this literally the same object," == is the right, intentional choice — not a shortcut.

RememberGenuinely want identity → == is the deliberate choice.
3 Two small boxed Integers happen to compare equal with ==

That "works" only because of the Integer cache (-128 to 127) — it silently breaks for larger values. Always use equals() for wrapper/object comparison.

RememberBoxed-value == that "works" → coincidence, not a pattern to repeat.
🌍 Real-world example ▾

Two identical twins are still two different people. Asking "are they the exact same person" (==) gets a no, even though asking "do they look the same" (equals()) gets a yes — both questions are valid, they're just not the same question.
