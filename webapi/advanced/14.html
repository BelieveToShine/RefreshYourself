JWT vs. OAuth — are they even competing options?

"When would you reach for a JWT vs. a full OAuth 2.0 flow?"

Why it matters ▾
🔑 JWT
❗ ProblemAn API needs to verify who's calling it without a database lookup on every single request.
✅ SolutionA JWT is a token format — a signed, self-contained set of claims the API can verify on its own, with no round trip to a session store.
RecallJWT = a token FORMAT, not an authorization system.
🔐 OAuth 2.0
❗ ProblemA third-party app or client needs permission to act on a user's behalf — "log in with Google," a mobile app calling your API — without the user ever handing over their password.
✅ SolutionOAuth 2.0 is a delegated-authorization framework — standard flows (like Authorization Code) that grant that access, and typically issue a JWT as the resulting access token.
RecallOAuth = a FRAMEWORK for delegated access — it often hands you a JWT at the end.
🔥 Easy interview recall

JWT → a token format, self-verifiable claims

OAuth 2.0 → a delegated-authorization framework

Think: OAuth decides who's allowed to act on whose behalf; a JWT is often just the token that decision comes wrapped in.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

JWT and OAuth are not mutually exclusive alternatives. A real OAuth flow commonly issues a JWT as its own access token — the real question is "do I need OAuth's full delegation/consent machinery, or just a signed token," not "JWT or OAuth."

🔄 Likely Follow-up

"What does a JWT give you that a plain opaque session token doesn't?" It's self-contained and verifiable without a database lookup — the signature proves it wasn't tampered with — at the cost that it can't be instantly revoked before it expires, unlike a session token the server can invalidate immediately.

🎯 Say this in the interview — the exact lines to land

"These solve different problems, not the same one. OAuth 2.0 is an authorization framework — how a client gets permission to act on a user's behalf through a flow like Authorization Code. A JWT is just a token format — a signed, self-contained set of claims — that OAuth, and plenty of non-OAuth systems, often use as the access token. So the real decision is whether I need delegated access from a third party or multiple client types, which means OAuth, or whether my own API just needs to verify its callers, which a simple self-issued JWT handles on its own."

  • OAuth 2.0 → a delegated-authorization framework, not a token format.
  • JWT → a token format — self-contained, signed claims, verifiable without a lookup.
  • They compose → OAuth flows commonly issue a JWT as the access token.
  • Need 3rd-party/multi-client delegation → OAuth's flows are the right tool.
  • Just verifying your own callers → a self-issued signed JWT is enough.
📖 Explanation ▾

OAuth 2.0 defines standard flows — Authorization Code, Client Credentials, and others — for a client to obtain permission to act on a user's behalf (or its own behalf, for machine-to-machine calls) without ever handling that user's credentials directly. It's the right tool whenever a third-party identity provider is involved ("log in with Google"), or when multiple client types (a web app, a mobile app, a partner integration) all need to obtain access the same standardized way.

A JWT is a much narrower thing: a token format — a Base64-encoded header, payload, and signature — that lets whoever receives it verify the claims inside without calling back to whoever issued it. OAuth's authorization server very commonly issues its access tokens *as* JWTs, because the format is convenient — but a JWT is just as usable outside OAuth entirely, e.g. an API that signs its own short-lived tokens for its own clients with no third party and no delegation involved at all. The decision that actually matters in an interview isn't "JWT vs. OAuth" — it's whether the delegation/consent machinery OAuth provides is actually needed, independent of what token format ends up being used at the end of either path.

💻 See the code ▾
C# 
// Either path — OAuth-issued or self-issued — ends up validated the same way:
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://your-oauth-provider.example"; // OAuth case: delegate trust to the provider
        // — or, for a self-issued JWT, set TokenValidationParameters with your own signing key instead
        options.Audience = "your-api";
    });

The API-side validation code barely changes between the two — what differs is who issued the token and under what flow, not how it's checked.

🌍 Real-world example ▾

A startup's internal admin API only ever gets called by its own backend services. There's no third party, no end-user consent screen, no mobile app — just one service calling another. A full OAuth flow would be unnecessary machinery here; a short-lived, self-issued signed JWT that the API validates against its own signing key is enough. Contrast that with the same company's public API that lets partner apps act on a user's behalf — that one genuinely needs OAuth's Authorization Code flow, which then issues a JWT as the access token anyway.
