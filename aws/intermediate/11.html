At-least-once means your consumer has to be idempotent, full stop

"SQS vs. SNS — and what does 'at-least-once delivery' actually mean for how you build a consumer?"

Why it matters ▾
  • Checks whether you know AWS's two core decoupling primitives, not just that "SQS is a queue."
  • Comes up any time a design question touches order processing, notifications, or fan-out to multiple services.
  • A very common follow-up: "so what happens if a message gets delivered twice?" — this is where idempotency comes in.
🔥 Easy interview recall

SQS → one consumer group per message (queue)

SNS → every subscriber gets a copy (pub/sub)

Think: both are at-least-once by default — duplicates can happen, so the consumer, not AWS, has to guard against processing the same message twice.

⚠️ Common Trap

"SQS and SNS guarantee exactly-once processing." Not by default — Standard SQS and SNS are at-least-once (duplicates happen); FIFO queues add exactly-once processing only within that one queue, and the consumer still has to be idempotent for the guarantee to actually hold end-to-end.

🔄 Likely Follow-up

"How do you make a consumer idempotent?" Track a unique message/idempotency key — e.g. in a database with a unique constraint — and skip processing if that key's already been handled; that's what protects against the redelivery at-least-once delivery guarantees will eventually cause.

🎯 Say this in the interview — the exact lines to land

"SQS is point-to-point — one consumer group processes each message off a queue. SNS is pub/sub — one published message fans out to every subscriber. Either way, delivery is at-least-once, so my consumer has to be idempotent, full stop."

  • FIFO SQS → strict order + exactly-once within that queue — but lower throughput, and the consumer still needs its own idempotency check for true end-to-end safety.
  • Standard SQS/SNS → high throughput, best-effort order, duplicates possible.
  • Visibility timeout hides a received message from other consumers until it's deleted or the timer expires and it's redelivered.
  • SNS → SQS fanout lets several independent queues each get their own copy of one published message.
📖 Explanation ▾

An SQS queue is point-to-point: a message sits in the queue until one consumer, from a single consumer group, picks it up and deletes it — even with several consumers polling the same queue, each message is only actually processed once. An SNS topic is pub/sub: publishing one message fans it out to every current subscriber (SQS queues, Lambda, email, HTTP endpoints…), and each subscriber gets its own independent copy.

Both are at-least-once by default — a message can be delivered more than once because of network retries or a consumer crashing mid-processing. A visibility timeout hides a received message from other consumers for a fixed window while one consumer works on it; if that consumer doesn't delete it before the window ends, the message becomes visible again and gets redelivered. Once a message's receive count passes a configured max, it moves to a dead-letter queue instead of looping forever, so it stops burning processing capacity and someone can go inspect it later.

🌍 Real-world example ▾

A payment-processing consumer checks an idempotency key before applying a message's effect, so an occasional SQS redelivery — guaranteed to happen eventually under at-least-once delivery — never double-charges a customer.
