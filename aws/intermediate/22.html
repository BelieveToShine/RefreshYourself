Which disk? One instance → EBS, many instances → EFS

"gp3 vs. io2, EBS vs. EFS vs. instance store — which for a database and which for shared files?"

Why it matters ▾
💽 EBS (gp3 / io2)
❗ ProblemA database needs a fast disk that survives the instance being stopped or replaced.
✅ SolutionEBS is a network-attached volume that lives on its own, in one Availability Zone, attached to one instance. Use gp3 for most things and io2 when guaranteed IOPS and low latency matter.
RecallEBS = one instance, one AZ, survives a stop.
📁 EFS & FSx
❗ ProblemMany servers need to read and write the same files — a normal EBS volume isn't a shared drive.
✅ SolutionEFS is a managed NFS file system that many Linux instances mount at once, across AZs, and it grows by itself. FSx covers specific needs: Windows (SMB), Lustre for HPC, and others.
RecallEFS = shared files for many instances.
⚡ Instance store
❗ ProblemSome data — cache, buffers, scratch space — needs the fastest disk and doesn't need to survive.
✅ SolutionInstance store is a disk physically on the host: very fast, but wiped when the instance stops or terminates, or its host fails.
RecallInstance store = fast but temporary.
🔥 Easy interview recall

EBS → one instance, one AZ, survives a stop

EFS → many instances, shared files, grows by itself

Instance store → fastest, but gone when the instance stops

gp3 / io2 → default SSD / provisioned IOPS for critical databases

Think: EBS is the disk inside one server. EFS is the shared drive down the hall. Instance store is a scratch pad.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"An EBS volume works like a shared network drive." It doesn't — it is block storage in one AZ, attached to one instance. Sharing files across instances means EFS or FSx. Multi-Attach is a narrow exception (io1/io2, same AZ) and needs software that coordinates concurrent writes.

🔄 Likely Follow-up

"How do you move an EBS volume to another AZ?" Take a snapshot (incremental, held by AWS), then create a new volume from it in the target AZ. To go to another Region, copy the snapshot there first.

🎯 Say this in the interview — the exact lines to land

"For a database on one instance I use EBS — gp3 by default, io2 when I need guaranteed IOPS and low latency. For files shared by many instances I use EFS, or FSx if I need Windows SMB or HPC. Instance store is only for scratch data, because it disappears with the instance."

  • EBS → block, one AZ, one instance — survives a stop; snapshots are the backup.
  • gp3 → the default SSD — IOPS and throughput are set apart from size.
  • io2 → provisioned IOPS for IOPS-critical, latency-sensitive databases.
  • st1 / sc1 → HDD — big sequential reads / cold data; not boot volumes.
  • EFS / FSx → shared files — EFS is NFS for Linux across AZs; FSx for Windows SMB, Lustre HPC and more.
  • Instance store → fast but temporary — gone when the instance stops or terminates.
📖 Explanation ▾

EBS is block storage: a network-attached volume that lives in one Availability Zone and attaches to an instance in that zone. It survives the instance being stopped. gp3 is the general-purpose SSD — you set IOPS and throughput separately from the size. io2 is the provisioned-IOPS SSD for IOPS-critical, latency-sensitive databases. st1 (throughput-optimised HDD) and sc1 (cold HDD) are cheaper hard-disk types for big sequential reads or rarely used data, and can't be boot volumes. Exact IOPS, throughput and size limits change — check current docs.

Snapshots are EBS's backup: incremental, kept by AWS, and the way to rebuild a volume in a different AZ or copy it to another Region. Volumes can be encrypted with KMS. Multi-Attach lets one io1/io2 volume attach to several instances in the same AZ, but it is not a shared file system — your software must coordinate the writes.

💻 See the code ▾
CLI 
aws ec2 create-volume \
  --volume-type gp3 \
  --size 100 \
  --iops 3000 \
  --throughput 125 \
  --availability-zone us-east-1a \
  --encrypted

gp3 lets you set IOPS and throughput on their own, apart from the size. For an IOPS-critical database you would use --volume-type io2 and provision the IOPS you need.

CLI 
aws ec2 create-snapshot \
  --volume-id vol-0123456789abcdef0

aws ec2 create-volume \
  --snapshot-id snap-0123456789abcdef0 \
  --availability-zone us-east-1b

Snapshot the volume, then build a new volume from that snapshot in a different AZ — the standard way to move an EBS volume between zones.

🌍 Real-world example ▾

A web fleet of six instances serves user uploads from one shared EFS mount, while the database primary runs on its own EBS volume with scheduled snapshots — and each instance's cache lives on instance store, because losing it costs nothing.
