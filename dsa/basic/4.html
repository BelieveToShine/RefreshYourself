Stack vs. Queue vs. Deque — which end are you actually allowed to touch?

"What's the difference between a stack and a queue — and what is a monotonic stack actually used for?"

Why it matters ▾
  • Almost every interview opens with "stack or queue?" then immediately follows with "now find the next greater element in O(n)."
  • A queue built the naive way (shifting the array on every dequeue) silently turns an O(n) algorithm into O(n²) — a real bug, not trivia.
  • The monotonic stack/queue trick is the single most reused idea across "this looks like O(n²), make it O(n)" array problems.
🔥 Easy interview recall

Stack → LIFO, touch only the top

Queue → FIFO, in the back, out the front

Deque → touch either end, O(1) both sides

Think: Stack = a stack of plates. Queue = a checkout line. Deque = a line you're also allowed to cut into from the front.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A queue backed by a plain array and shifted left on every dequeue is not O(1). That shift is O(n) per dequeue, which silently turns an algorithm that "should" be O(n) overall into O(n²) — use a circular buffer or a linked list with head/tail pointers instead.

🔄 Likely Follow-up

"How would you find the maximum in every sliding window of size k, in O(n) total?" Keep a monotonic deque of indices, decreasing front-to-back — pop smaller values off the back before adding a new one (they can never be the max again while the new value is still in the window), and pop the front once its index slides out of the window. Never re-scan each window from scratch — that's O(n·k).

🎯 Say this in the interview — the exact lines to land

"A stack is LIFO — push and pop both happen at the top. A queue is FIFO — you add at the back and remove from the front. A deque allows O(1) insert and remove at both ends, which is what makes the monotonic-queue technique possible."

  • Stack → use it for undo/redo, bracket matching, and DFS with an explicit stack instead of recursion.
  • Queue → use it for BFS, task scheduling, and rate limiting — order of arrival matters.
  • Deque → use it for sliding-window maximum/minimum via a monotonic queue.
  • Monotonic stack → pop smaller elements before pushing to answer "next greater element" in O(n), not O(n²).
📖 Explanation ▾

A stack only exposes one end — "the top" — so push and pop are always the same operation on the same spot, both O(1). That single-end rule is exactly what makes an explicit stack a stand-in for recursion: a function call stack is a stack, so any recursive DFS can be rewritten as a loop with your own stack.

A queue exposes two ends — you enqueue at the back and dequeue at the front — and both are still O(1), but only with the right implementation (a circular buffer, or a linked list tracking both head and tail). BFS needs this FIFO order because it has to finish the current "layer" of nodes before moving to the next one.

A monotonic stack stays either strictly increasing or strictly decreasing from bottom to top by popping off anything that would break that order right before pushing. Each element is pushed once and popped at most once across the whole run, so even though there's a loop inside a loop, the total work across every pop is still O(n) — not the O(n²) it looks like at a glance. A monotonic queue (built on a deque) applies the same idea to a sliding window: pop smaller values off the back when a bigger one arrives, and pop the front once its index falls outside the window — the front is always the current window's max.

💻 See the code ▾
Python 
def next_greater(nums):
    result = [-1] * len(nums)
    stack = []                      # holds indices, values decreasing bottom→top
    for i, val in enumerate(nums):
        while stack and nums[stack[-1]] < val:
            result[stack.pop()] = val   # ✅ popped index just found its next greater
        stack.append(i)
    return result

Every index is pushed once and popped at most once — the while loop looks nested, but total pops across the whole run is O(n).

Python 
from collections import deque

def sliding_window_max(nums, k):
    dq = deque()                    # indices, values decreasing front→back
    result = []
    for i, val in enumerate(nums):
        while dq and nums[dq[-1]] <= val:
            dq.pop()                 # ✅ smaller & behind — can never be the max again
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()              # ✅ front fell out of the window
        if i >= k - 1:
            result.append(nums[dq[0]])
    return result

The front of the deque is always the current window's max — no re-scanning, so the whole pass is O(n) instead of O(n·k).

Python 
# ❌ Looks like O(1) dequeue — it isn't
class NaiveQueue:
    def __init__(self):
        self.items = []
    def enqueue(self, x):
        self.items.append(x)          # ✅ O(1)
    def dequeue(self):
        return self.items.pop(0)     # ❌ O(n) — shifts every remaining item left

list.pop(0) (or any "remove first, shift the rest") is the Common Trap in code — it quietly makes every dequeue O(n).

🌍 Real-world example ▾

You're watching stock prices tick by and need each day's "next higher price" instantly. Checking every future day for every day is the O(n²) brute force. A monotonic stack of "still waiting for a higher price" days answers each one the moment a higher price actually shows up — one pass, O(n).
