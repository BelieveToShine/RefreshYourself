HasIndex — index, unique, or composite key?

"How do you add an index or unique constraint in EF Core?"

Why it matters ▾
🗂️ Indexes & Keys in the Model
❗ ProblemA slow lookup or a duplicate email is usually a missing index or constraint — and EF Core only creates what the model says. Nothing is added "because it would help".
✅ SolutionDeclare it in the model: HasIndex for an index, .IsUnique() for a unique one, HasKey for a composite primary key. A migration then creates it.
RecallModel declares it → migration creates it. HasIndex = index; .IsUnique() = constraint; column order matters.
🔥 Easy interview recall

Index in EF Core = "say it in the model, let the migration create it."

Think: HasIndex(...).IsUnique() → unique index HasKey(x => new { ... }) → composite primary key Composite index → put the column you filter on first

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"EF Core checks uniqueness for me before it saves." It does not — a unique index is enforced by the database. A duplicate fails inside SaveChanges() with a DbUpdateException, so catch it rather than relying on a "does it exist?" check first.

🔄 Likely Follow-up

"Unique index or alternate key — what is the difference?" Both give you a unique constraint. An alternate key (HasAlternateKey) also lets other entities use it as the target of a foreign key; a plain unique index is only a constraint.

🎯 Say this in the interview — the exact lines to land

"I declare indexes in the model with HasIndex, add IsUnique() when it must be a constraint, and a migration creates them. For a composite index, column order matters — the column I filter on most goes first. A composite primary key uses HasKey with an anonymous type."

  • HasIndex(...) → creates an index; add .IsUnique() for a constraint.
  • Composite index → first column leads; order it by how you filter.
  • HasKey(x => new { ... }) → composite primary key.
  • HasAlternateKey → unique and usable as a foreign-key target.
  • Duplicate on save → DbUpdateException from the database, not from EF Core.
📖 Explanation ▾

EF Core creates indexes only from your model. Foreign-key columns get an index by convention; everything else you add yourself with HasIndex in the Fluent API (or the [Index] attribute on the class). Add .IsUnique() and the migration produces a unique index — the database, not EF Core, then rejects duplicates.

A composite index lists several columns, and their order matters: an index on (CustomerId, OrderDate) is mainly useful to queries that filter on CustomerId first, not on OrderDate alone. Provider-specific options exist too — a filtered index with HasFilter (the filter text is raw SQL for your provider) and extra included columns on providers such as SQL Server.

For keys: a composite primary key is set with HasKey(x => new { x.A, x.B }) — common on join tables. HasAlternateKey declares a second unique key that other entities can also point a foreign key at. Whatever you add, remember it only exists after a migration has been applied.

💻 See the code ▾
C# 
modelBuilder.Entity<User>()
    .HasIndex(u => u.Email)
    .IsUnique();                              // ✅ unique index

modelBuilder.Entity<Order>()
    .HasIndex(o => new { o.CustomerId, o.OrderDate });   // composite — order matters

modelBuilder.Entity<User>()
    .HasIndex(u => u.Email)
    .IsUnique()
    .HasFilter("[IsDeleted] = 0");            // filtered (SQL Server syntax)

One method, several shapes — unique, composite, and filtered.

C# 
modelBuilder.Entity<OrderLine>()
    .HasKey(l => new { l.OrderId, l.ProductId });   // composite primary key

modelBuilder.Entity<Country>()
    .HasAlternateKey(c => c.Code);                  // unique, and a valid FK target

Keys: a composite primary key, and an alternate key.

C# 
try
{
    await db.SaveChangesAsync();
}
catch (DbUpdateException)
{
    // ❌ the database rejected a duplicate value — tell the caller
}

A unique-index violation surfaces at SaveChanges(), not before.

🌍 Real-world example ▾

A signup endpoint checks "does this email exist?" and then inserts — two requests at once can both pass the check. The unique index on Email is the real guard; catch the DbUpdateException and return "already registered".
