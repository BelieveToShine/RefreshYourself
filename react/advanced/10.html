Patterns — named solutions to problems you'll recognize once you've hit them

"What's a compound component pattern, and why reach for it over just passing a lot of props?"

Why it matters ▾
  • Interviewers use this to see whether you reach for a named pattern because it actually fits the problem, not because it sounds senior.
  • Comes up the moment a shared component (tabs, accordion, modal, form) starts needing a prop for every possible configuration.
  • A common follow-up right after Hooks: "so are render props and HOCs completely dead now?" — the honest answer is more nuanced than yes.
🔥 Easy interview recall

Compound component = "implicit coordination via shared Context, under one parent."

Think: <Tabs><Tabs.Tab/></Tabs> reads clearly; one <Tabs config={ ...huge object... }/> doesn't.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Render props and higher-order components are not outdated relics with no place in a modern, Hooks-based codebase. Hooks replaced MOST of what they were used for — sharing stateful logic across components — but not entirely: a library exposing a flexible rendering API to consumers it doesn't control, or needing to wrap a third-party component you can't directly add Hooks into, can still legitimately reach for either one.

🔄 Likely Follow-up

"When should a pattern NOT be used?" When it adds indirection without solving a real problem the codebase actually has right now — patterns exist for recognized, recurring shapes you've genuinely hit, not something to reach for preemptively just because it's considered "a best practice" in the abstract.

🎯 Say this in the interview — the exact lines to land

"A compound component is a group of components — like Tabs and Tabs.Tab — that implicitly coordinate through shared Context under one parent, instead of one component with a giant prop surface trying to configure every possible variation. I'd reach for it once a flat props API starts feeling like it's fighting the component, not before."

  • Compound component → implicit coordination via Context under one parent, not a flat prop surface.
  • Custom Hook → shares stateful logic across components, never the UI itself.
  • Render props / HOCs → mostly superseded by Hooks, not obsolete — still real for flexible rendering APIs or unhookable third-party wrappers.
  • Provider pattern → Context's own Provider, making one value available to a subtree.
  • State reducer pattern → lets an advanced consumer override internal state transitions by supplying their own reducer.
  • A pattern earns its spot only when it solves a real, present problem — never preemptively "because it's best practice."
📖 Explanation ▾

A compound component is a small family of components that share state through Context instead of through props passed down explicitly — Tabs holds the active tab, and Tabs.Tab/Tabs.Panel just read it. The win is readability: the JSX shape mirrors the actual UI shape, so a consumer never has to learn a config object's worth of prop names just to add one more tab.

Most of what render props and higher-order components used to be reached for — sharing stateful logic between components — is now a custom Hook instead, since a Hook can just call other Hooks directly, no wrapping component required. They still show up where a Hook genuinely can't reach: a library handing a consumer full control over what gets rendered, or wrapping a third-party component whose internals you can't add a Hook to.

Not every named pattern is a distinct new idea. The Provider pattern is just Context's own Provider in regular use, and a controlled component — where a parent or a form library owns and drives the value — is the same idea covered from a form's angle on its own page. A pattern only earns its use when it matches a shape you've actually hit; reaching for one before that just adds a layer of indirection nobody asked for.

💻 See the code ▾
JSX 
<Tabs defaultTab="profile">          // parent owns the active tab
  <Tabs.Tab id="profile" label="Profile" />
  <Tabs.Tab id="settings" label="Settings" />
  <Tabs.Panel id="profile">...</Tabs.Panel>
  <Tabs.Panel id="settings">...</Tabs.Panel>
</Tabs>                            // ✅ children read state via Context — no wiring here

Adding a third tab means adding one more Tabs.Tab/Tabs.Panel pair — nothing else changes.

JSX 
<Tabs
  activeTab={activeTab}
  onTabChange={setActiveTab}
  tabLabels={["Profile", "Settings"]}
  tabContents={[<Profile />, <Settings />]}
  disabledTabs={[]}                // ❌ every new variation is one more prop
/>

Same UI — but adding a third tab now means editing four separate arrays that all have to stay in sync by index.

🌍 Real-world example ▾

A compound component is a modular furniture system. The pieces are designed to silently know how to connect and coordinate the moment you place them together — no instruction sheet needed. The flat-props alternative is a single all-in-one furniture piece with fifty separate configuration knobs, each trying to cover one more possible layout up front, before anyone even asked for it.
