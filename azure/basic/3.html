Azure Functions vs. App Service — who's actually paying for idle time?

"What is Azure Functions, and how is it different from App Service?"

Why it matters ▾
  • Comes up the moment compute/hosting options are discussed — a foundational Azure basics question.
  • Explains a real cost surprise: an idle Function costs close to nothing, while an idle App Service plan keeps billing.
  • Almost always the opening question before serverless, autoscaling, or hosting trade-off questions.
🔥 Easy interview recall

Functions → pay-per-run, scales to 0

App Service → pay-per-hour, always on

Think: Functions sleeps when idle. App Service never does.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Functions is always cheaper than App Service. That's only true for bursty or low-traffic workloads — under high, steady traffic, paying per execution can add up to more than App Service's flat, predictable per-instance-hour billing.

🔄 Likely Follow-up

"Can Functions run on an App Service Plan instead of Consumption?" Yes — that trades away serverless elasticity (scale-to-zero, pay-per-run) for predictable, fixed billing and always-on behavior.

🎯 Say this in the interview — the exact lines to land

"Functions bills per execution and scales to zero when idle; App Service bills per instance-hour and stays on around the clock, whether or not traffic arrives."

  • Functions wins → bursty, event-driven, or infrequent work — near-zero cost while idle.
  • App Service wins → steady, high traffic — flat billing beats paying per execution at scale.
  • Watch the trap → "Functions is always cheaper" breaks down once traffic is constant and heavy.
  • Same code, different host → Functions can also run on an App Service Plan for fixed, always-on billing.
📖 Explanation ▾

Azure Functions is serverless compute — your code only runs when something triggers it (an HTTP call, a timer, a queue message), and on the Consumption plan it scales automatically from zero instances up to many, billing per execution and per resource-second actually used. App Service is a managed web-hosting platform — you provision one or more instances that stay running continuously, and you pay for that capacity by the hour whether or not a request ever arrives.

The two aren't strictly separate ecosystems: Functions can also run on an App Service Plan instead of Consumption, giving up automatic scale-to-zero in exchange for the same predictable, always-on billing App Service already uses. Choosing between them is really about the shape of the traffic — bursty and unpredictable favors Functions, steady and heavy favors App Service.

💻 See the code ▾
C# 
public class HelloFunction
{
    [Function("Hello")]                        // runs only when the HTTP trigger fires
    public static HttpResponseData Run(
        [HttpTrigger(AuthorizationLevel.Function, "get")] HttpRequestData req,
        FunctionContext ctx)
    {
        var res = req.CreateResponse(HttpStatusCode.OK);   // no server was "on" before this call
        res.WriteString("Hello from a Function that scales to zero.");
        return res;
    }
}

Nothing is running before the request arrives — the host spins the instance up, bills for this execution, and can scale back to zero right after.

🌍 Real-world example ▾

A nightly image-resizing job that runs 2 minutes a day is a natural fit for a Function — it's asleep, and costs next to nothing, for the other 23 hours and 58 minutes. A customer-facing web app with constant traffic is a better fit for App Service, where the always-on cost is already justified by the always-on demand.
