HTTP status codes — the answer belongs in the header, not the body

"What's the actual difference between 200 vs. 201 vs. 204, 400 vs. 422, and 401 vs. 403?"

Why it matters ▾
  • Interviewers use this to check you treat status codes as real signals, not decoration sitting on top of a JSON body.
  • Comes up any time you design or review an API's response contract — getting 401 vs 403 wrong is exactly what a careful reviewer catches.
  • 400 vs 422 is a classic tell: plenty of candidates have never had to reach for 422 at all.
🔥 Easy interview recall

2xx → success

4xx → client's fault

5xx → server's fault

Think: 200/201/204 → same success, different flavor 400 vs 422 → can't parse it vs won't accept it 401 vs 403 → not you vs not allowed

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Status codes are not decoration you can replace with a body field. Returning HTTP 200 for everything and putting the real result in something like {"status":"error","code":404} breaks HTTP-aware tooling — caching, monitoring, and automatic retries all key off the actual status code, not a custom body convention.

🔄 Likely Follow-up

"If a resource doesn't exist, should a DELETE on it return 404 or 204?" Reasonable APIs differ — a common, defensible choice is 204 regardless of whether the resource existed, since the end state either way is "it's gone now," which ties back to DELETE being idempotent. Naming both valid conventions shows real understanding, not a memorized rule.

🎯 Say this in the interview — the exact lines to land

"The first digit is the family — 2xx succeeded, 4xx is the client's fault, 5xx is the server's fault. Within that, 201 marks a created resource with a Location header, 204 is success with no body, 422 means the request parsed fine but failed validation, and 403 means you're authenticated but not allowed."

  • 200 → generic success, the default for a GET returning data.
  • 201 → created — pair it with a Location header pointing at the new resource.
  • 204 → success, deliberately no body — the standard choice for a successful DELETE.
  • 400 → can't even parse it 422 → parsed fine, failed validation
  • 401 → not authenticated 403 → authenticated, not permitted
📖 Explanation ▾

The first digit tells you the family before you even read the rest of the number. A 2xx code means the request succeeded. A 4xx code means the client sent something the server won't accept — a bad request, missing permission, or a resource that isn't there. A 5xx code means the server itself broke, regardless of how well-formed the client's request was.

Inside those families, a few specific codes get mixed up constantly. 201 and 204 are both "it worked," but they answer different questions — did something new get created, or is there simply nothing to send back. 400 and 422 both mean "client error," but one is the server saying "I can't even read this," the other is "I read it fine, the values just aren't acceptable." 401 and 403 follow the same split: one is about who you are, the other is about what you're allowed to do once you're known.

💻 See the code ▾
C# 
[HttpGet("{id}")]
public IActionResult GetById(int id)
    => Ok(_repo.Find(id));               // 200 — data comes back

[HttpPost]
public IActionResult Create(Dto dto)
{
    var created = _repo.Add(dto);
    return CreatedAtAction(nameof(GetById),
        new { id = created.Id }, created);  // 201 + Location
}

CreatedAtAction sets the 201 status and the Location header in one call — no manual header-building.

C# 
[HttpDelete("{id}")]
public IActionResult Delete(int id)
{
    _repo.Remove(id);
    return NoContent();          // 204 — worked, nothing to send back
}

NoContent() is the framework's built-in way to say "success, deliberately empty."

C# 
if (!User.Identity.IsAuthenticated)
    return Unauthorized();     // 401 — we don't know who you are

if (!User.HasClaim("workspace", workspaceId))
    return Forbid();           // 403 — we know you, this isn't yours

Same shape, different question: 401 asks "who are you," 403 asks "are you allowed here."

🌍 Real-world example ▾

A user is logged in but opens a document that belongs to another company's workspace. That's 403, not 401 — the token is valid and the server knows exactly who they are, they just aren't allowed into that specific resource. Send 401 here and you're telling a perfectly logged-in user to go log in again, which is the wrong instruction and the wrong fix.
