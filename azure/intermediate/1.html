Deployment slots — shipping code nobody's using yet

"What are the common ways to get code onto App Service, and how does a deployment slot help avoid downtime?"

Why it matters ▾
  • Checks whether you know deployment isn't just "push and pray" — most teams gate a real release through a staging step first.
  • Comes up any time the conversation turns to zero-downtime releases, or a bad-release story.
  • A natural follow-up after any App Service or CI/CD pipeline question.
🔥 Easy interview recall

Slot swap = "a routing change, not a redeploy."

Think: staging is already warmed up and tested — swap just points production's URL at it, instantly and reversibly.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A swap only moves the code." Not quite — any app setting or connection string that isn't explicitly marked slot-specific travels with the swap too, so an unmarked connection string can silently end up pointing staging's config at production's resources (or vice versa) after a swap, unless it was configured deliberately.

🔄 Likely Follow-up

"What happens if the swap goes wrong?" Swap back — the same near-instant operation in reverse, which is the whole point of using slots for safer releases.

🎯 Say this in the interview — the exact lines to land

"A slot swap is a routing change, not a redeploy — that's what makes it near-instant and reversible. I deploy to a staging slot, warm it up and test it against its own URL, then swap it into production; if something's wrong, I can swap back just as fast."

  • Deployment slot → a separate, live instance with its own URL, not just a copy of the code sitting idle.
  • Swap → a routing change — no cold start, near-instant.
  • Rollback → just swap back — the same near-instant operation, reversed.
  • Slot-specific settings are the trap — anything not marked that way moves with the swap.
📖 Explanation ▾

Code usually gets onto App Service one of a few ways: continuous deployment from Git/GitHub Actions/Azure DevOps CI-CD on every push, a one-off ZIP deploy for a quick push, or deploying a container image instead of raw files. All of them end the same way — new code or a new image replaces what's running on that instance.

A deployment slot is a completely separate, live App Service instance — its own URL, its own running process — sitting alongside production. You deploy the risky change there first, so it's already running and warmed up before anyone outside the team touches it. A swap doesn't copy files or restart production; it re-routes which slot answers to the production hostname, so App Service also warms up the target instance ahead of the swap to avoid the usual cold-start delay production traffic would otherwise hit.

💻 See the code ▾
CLI 
az webapp deployment slot swap \
  --resource-group rg-demo \
  --name mywebapp \
  --slot staging \
  --target-slot production

Nothing gets rebuilt or copied here — this just flips which slot answers to production's hostname.

🌍 Real-world example ▾

A team deploys a risky release to the staging slot, runs smoke tests straight against staging's own URL, and only then swaps it into production — confident it's already warmed up and already proven to work, not hoping it works for the first time in front of real users.
