Pinia Store Basics — state, getters, actions

"What are the 3 parts of a Pinia store?"

Why it matters ▾
🍍 Pinia store shape
❗ ProblemShared data (a logged-in user, a shopping cart) duplicated across multiple components via props drifts out of sync the moment one copy changes without the others knowing.
✅ SolutionA Pinia store holds that data once — state for the data, getters for derived values, actions for the logic that changes it — and every component using the store shares the exact same reactive source.
RecallOne store, one source of truth, shared by every component that imports it.
🔥 Easy interview recall

state → the data

getters → cached derived values

actions → methods that read/write state

Think: same 3-part shape as a component's own data / computed / methods.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Pinia does not technically block mutating state directly from a component. Calling the store and setting a property is allowed by Pinia itself — it's a team-discipline convention to route changes through actions, for traceability and devtools clarity, not a hard rule the library enforces.

🔄 Likely Follow-up

"How do getters differ from a plain computed on the state?" Functionally similar — both are cached and reactive. The difference is that a getter lives on the store, so every component using that store shares the SAME cached derivation instead of each one redefining its own local computed.

🎯 Say this in the interview — the exact lines to land

"A Pinia store has three parts: state holds the reactive data, getters are cached derived values like a computed, and actions are the methods — sync or async — where state actually gets changed."

  • state → a function returning the initial data, kept reactive.
  • getters → cached, derived, shared across every consumer of the store.
  • actions → where you mutate state, sync or async, no separate commit step.
  • Direct mutation from a component → allowed by Pinia, discouraged by convention.
📖 Explanation ▾

State is a function that returns the store's initial data — written as a function (not a plain object) so each store instance gets its own fresh copy, the same reason a component's data() is a function too.

Getters compute something FROM state without changing it — Pinia caches the result the same way Vue's computed does, so reading a getter twice without a dependency change doesn't recompute it.

Actions are regular methods that can read and write state directly (this.count++), call other actions, and be async with no special handling — there's no separate "commit" step like Vuex's mutations, which is the single biggest shape difference from the older pattern.

💻 See the code ▾
Vue 
export const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0 }),
  getters: {
    doubleCount: (state) => state.count * 2     // cached, derived
  },
  actions: {
    async increment() {
      this.count++                                // ✅ direct mutation, no commit step
    }
  }
})

All three parts live in one defineStore call — no modules tree.

Vue 
<!-- any component -->
import { useCounterStore } from './counter'
const counter = useCounterStore()
counter.increment()                  // ✅ preferred — goes through the action
counter.count = 99                   // ⚠️ allowed, but skips the convention

Both lines work — only the first follows the team-discipline convention.

🧭 Use Cases — recognize these when they happen to you ▾
1 A logged-in user's profile needed by the header, sidebar, and settings page

Every component calling useUserStore() gets the same reactive instance — update it in one place and the header, sidebar, and settings page all see the change instantly, no prop drilling.

RememberData needed in 3+ unrelated places → a Pinia store, not shared props.
2 A cart total that needs to stay in sync with the cart's items

A total getter computed from items never drifts out of sync, because it's recalculated from the same state every time an item changes — there's no separate "total" value to forget to update.

RememberValue computed FROM other state → a getter, never a second stored field.
🌍 Real-world example ▾

An e-commerce app's cart badge in the header. One useCartStore() with items in state and an itemCount getter means adding a product from any page instantly updates the header badge — no event bus, no prop chain back up to the layout.
