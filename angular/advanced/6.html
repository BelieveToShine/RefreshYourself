🔥 Must Know

The server's HTML and the browser's Angular have to agree on what the page looked like

What actually causes a hydration mismatch, and what code can't safely run during server-side rendering?

Why it matters ▾
  • A page that's fast on the server but visibly "flashes" or re-lays-out right after load is almost always a hydration mismatch, not a real SSR bug.
  • Interviewers use this to check whether you understand hydration as reusing the server's DOM, not just "SSR = faster page."
  • A common trap for anyone assuming code runs the same way on the server as it does in a browser — the server has no window or document at all.
🔥 Easy interview recall

SSR → server sends real HTML, not an empty shell

Hydration → client Angular wakes up that HTML

Mismatch → DOM disagrees, reused becomes rebuilt

Think: SSR plates the dish immediately. Hydration is the kitchen finishing the garnish on that same plate — not swapping it for a new one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A hydration mismatch usually isn't a coding mistake — it's a value computed twice. Reading Date.now(), Math.random(), or a timezone-dependent value directly during rendering lets the server and the client each compute their own answer, and Angular flags the disagreement even though neither computation was "wrong."

🔄 Likely Follow-up

"The app is fast on the server but slow right after — is that an SSR problem?" Not necessarily. SSR already solved first paint; a slow moment right after usually means hydration itself is heavy — a lot of component init work or a large bundle running synchronously — a bundle-size/initialization cost that was always there, just showing up at a different moment now.

🎯 Say this in the interview — the exact lines to land

"SSR renders the page's HTML on the server so the browser has something real to show immediately. Hydration is the client-side Angular app waking that HTML up — attaching listeners and reusing the existing DOM instead of rebuilding it. A hydration mismatch happens when the client's render doesn't match what the server actually sent, which forces Angular to discard and rebuild that part of the DOM instead of reusing it."

  • SSR → real HTML on first paint, better perceived speed and SEO.
  • Hydration → reuses the server's DOM, doesn't rebuild it from scratch.
  • Mismatch → DOM shapes disagree, triggering a destructive rebuild and a visible flash.
  • Browser-only code → guard it with a platform check before touching window/document/localStorage.
  • Non-deterministic values → compute once, pass through — never recompute independently on server and client.
📖 Explanation ▾

Server-side rendering runs Angular inside Node.js to produce the initial HTML for a page, instead of shipping a mostly-empty shell that only becomes visible once the browser downloads, parses, and executes the full JS bundle. That's the whole trade SSR makes: something real to look at right away, better SEO because crawlers see finished content without running JavaScript, and a faster first paint on slow devices or networks.

Hydration is what happens next — the client-side Angular app "wakes up" that server-rendered HTML: attaching event listeners, wiring bindings, taking over the DOM that's already sitting on the page. Angular's modern approach does this non-destructively, reusing the existing nodes directly, rather than the older approach of re-rendering everything client-side and throwing the server's DOM away (which caused a visible flash as real content briefly vanished and came back). @defer blocks let this happen incrementally — different parts of the page becoming interactive at different times instead of the whole page all at once.

A mismatch is simply the client's own render disagreeing with what the server actually sent. Angular expects a specific DOM shape to attach to; if it doesn't find that shape, it falls back to destroying and rebuilding that section — which defeats much of SSR's benefit right there and can cause a visible layout shift. Debugging one means comparing the raw server response (view page source) against what the client would render for the same state — the gap is almost always browser-only code that behaved differently on the server, or data that genuinely came out different in each environment.

💻 See the code ▾
TS 
constructor(@Inject(PLATFORM_ID) private platformId: Object) {
  if (isPlatformBrowser(this.platformId)) {
    // ✅ only reached in the browser — localStorage doesn't exist on the server
    const saved = localStorage.getItem('theme');
  }
}

The platform check has to run before the browser-only API is touched at all — the server throws (or silently misbehaves) the moment code assumes window/document/localStorage exist.

TS 
// ❌ server and client compute this independently — can mismatch
render: new Date().toLocaleString();

// ✅ computed once (e.g. in a resolver), serialized, reused as-is
render: this.pageData.generatedAt;

The server computes new Date() once at request time; the client computes it again during hydration — even a tiny clock/timezone difference makes Angular see two different DOMs for the same page.

🌍 Real-world example ▾

SSR is like a restaurant sending out a fully-plated dish immediately — something real to look at and start eating — while the kitchen (client-side JS) is still finishing the final garnish and setting the table properly (hydration). A hydration mismatch is like that final touch not matching what was already plated: instead of gently finishing the existing plate, the whole dish gets swapped out for a freshly replated one — which the diner notices as an awkward, visible re-do.
