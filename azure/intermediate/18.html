5 consistency levels — how much correctness are you actually paying for?

"What's the actual tradeoff between strong consistency and the weaker levels, and why would you ever pick weaker on purpose?"

Why it matters ▾
  • Checks whether you understand the real CAP-theorem tradeoff Cosmos DB exposes as a dial, not just that "5 levels exist."
  • Comes up any time someone asks "why not just use Strong everywhere" on a multi-region Cosmos DB design.
  • A common way interviewers separate a memorized list of names from someone who's actually reasoned about the latency/availability cost.
🔥 Easy interview recall

Strong → latest write, always

Bounded Staleness → lag capped by time/count

Session → your own writes, always (default)

Consistent Prefix → order kept, staleness allowed

Eventual → no order guarantee, fastest

Think: one slider from Strong to Eventual — every notch right trades a correctness guarantee for lower latency and higher availability.

⚠️ Common Trap

"Just use Strong everywhere to be safe." In a multi-region Cosmos DB account, Strong consistency significantly raises write latency and can reduce availability during a regional failure — a guarantee most applications never actually need.

🔄 Likely Follow-up

"Why is Session the default, and is that usually fine?" Yes, for most apps — a user reliably seeing their own writes covers the vast majority of real UX needs, without paying Strong's full latency cost.

🎯 Say this in the interview — the exact lines to land

"5 levels on a spectrum from Strong to Eventual — Session is the default because it covers 'seeing your own writes' cheaply, without paying for the global Strong guarantee almost nothing actually needs."

  • Strong → always the latest write, at the highest latency cost.
  • Session → the default — a client always sees its own writes, cheaply.
  • Bounded Staleness & Consistent Prefix → middle-ground tradeoffs — capped lag, or in-order but stale.
  • Eventual → no ordering guarantee at all, for the lowest latency and highest availability.
  • Strong in a multi-region account raises write latency and can hurt availability during a regional failure.
📖 Explanation ▾

Cosmos DB doesn't force an all-or-nothing choice between correctness and speed. It exposes 5 consistency levels on one spectrum, set at the account level and overridable per request, so you pick exactly how much freshness and ordering guarantee a given read actually needs — instead of paying the most expensive guarantee for every read by default.

The cost is real, not theoretical. Strong means a write has to be durably confirmed across enough regions before it's considered committed, so a multi-region account pays real cross-region round-trip latency on every write, and can lose write availability if too many regions are unreachable during a network partition. Session sits in the middle by only guaranteeing consistency for the single client that made the write — cheap to track, and it covers what users actually perceive almost all of the time, which is exactly why it's the account default.

💻 See the code ▾
C# 
var options = new CosmosClientOptions
{
    ConsistencyLevel = ConsistencyLevel.Session // ✅ matches the account default
};
var client = new CosmosClient(endpoint, key, options);

Setting ConsistencyLevel here picks the level per request — it doesn't change what the account itself defaults to.

🌍 Real-world example ▾

A social app uses Session consistency so a user always sees their own new post the instant they refresh their own feed. Another user browsing at that exact moment might see the same post appear a moment later, once it replicates — a tradeoff almost nobody actually notices, and exactly the gap Strong consistency would close at a real latency cost.
