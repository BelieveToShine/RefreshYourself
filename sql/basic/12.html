UNION vs. UNION ALL — is removing duplicates ever free?

"UNION vs. UNION ALL — what does UNION actually do that UNION ALL skips, and what does that cost?"

Why it matters ▾
🐢 UNION
❗ ProblemJust concatenating two SELECT results can show the same row twice — a CustomerId matching both a "Pending" filter and a "Total > $1000" filter would appear once per query it matched.
✅ SolutionUNION runs a sort/hash pass over the combined rows and removes exact duplicates, so that row comes out exactly once — at the cost of that extra pass over every row.
RecallUNION = dedup pass over every row, always more work than ALL.
⚡ UNION ALL
❗ ProblemThat same dedup pass still runs even when the two queries structurally can't ever produce the same row — like Orders_2025 and Orders_Archive, which hold different years — so the sort/hash work has nothing to find.
✅ SolutionUNION ALL skips the duplicate check entirely and just concatenates the rows — never more expensive than UNION, and the right call whenever overlap is impossible or duplicates are actually wanted.
RecallUNION ALL = pure concatenation, no dedup check, always cheaper.
🔥 Easy interview recall

UNION → removes duplicates (extra dedup pass)

UNION ALL → keeps everything (pure concatenation)

Think: UNION pays for a sort/hash dedup step. UNION ALL just concatenates — cheaper, every time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

UNION is the "safe default" for combining any two queries. When the two result sets structurally can't overlap — e.g. mutually exclusive filter conditions — that dedup pass is pure wasted cost, and UNION ALL returns the exact same rows for less work.

🔄 Likely Follow-up

"If you know for certain the two queries can never produce overlapping rows, is there ever a reason to still use UNION instead of UNION ALL?" No — if duplicates are structurally impossible, UNION ALL gives identical results for less cost; UNION only earns its cost when duplicates are actually possible and need removing.

🎯 Say this in the interview — the exact lines to land

"UNION combines two SELECT results and removes duplicate rows, which costs an extra sort or hash pass. UNION ALL combines them without checking for duplicates at all — a straight concatenation, so it's always cheaper. Both need the same number of columns with compatible types, and the output column names come from the first query."

  • UNION → removes duplicates, at the cost of a sort/hash pass over every row.
  • UNION ALL → pure concatenation, no dedup check, always cheaper.
  • Same shape required → both queries need the same column count, with compatible types; names come from the first query.
  • Know it can't overlap? Use UNION ALL. Reaching for UNION out of habit pays for dedup work you don't need.
📖 Explanation ▾

UNION combines the result sets of two or more SELECT queries into one set and removes duplicate rows from the combined result — finding those duplicates takes an extra sort or hash step over every row produced. UNION ALL combines the same result sets without that check: it's a straight concatenation, so no extra pass runs at all.

Both operators still require the underlying queries to line up: the same number of columns, in types that can be compared to each other. The final result's column names always come from the first SELECT — a later query's column aliases are ignored.

💻 See the code ▾
SQL 
SELECT CustomerId FROM Orders WHERE Status = 'Pending'
UNION
SELECT CustomerId FROM Orders WHERE Total > 1000;
-- a CustomerId matching BOTH conditions appears only once

Any CustomerId in both queries is deduped down to a single row — that dedup pass runs even if only one row ever actually overlaps.

SQL 
SELECT CustomerId FROM Orders WHERE Status = 'Pending'
UNION ALL
SELECT CustomerId FROM Orders WHERE Total > 1000;
-- the same CustomerId can now appear twice — no dedup pass runs

Same two queries, same possible overlap — UNION ALL just concatenates, so a matching row shows up exactly as many times as it was actually produced.

SQL 
SELECT * FROM Orders WHERE Status = 'Pending'
UNION ALL   -- ✅ Status can only be one value — these sets can't overlap
SELECT * FROM Orders WHERE Status = 'Cancelled';

Status can't hold both values on the same row, so no duplicate can ever occur — UNION here would just pay for a dedup pass with nothing to deduplicate.

🧭 Use Cases — recognize these when they happen to you ▾
1 The same row can genuinely come out of both queries

A "Pending" filter and a "Total > $1000" filter can both match the same CustomerId — a plain concatenation would show that row twice. This is the #1 reason UNION exists. Use UNION so the sort/hash pass actually earns its cost.

RememberOverlap possible → pay for UNION's dedup pass.
2 The two queries structurally can never produce the same row

One column can't hold two values on the same row, and Orders_2025 / Orders_Archive can't share a row either — different years. UNION here would still run a sort/hash pass with nothing to find. Use UNION ALL and skip it.

RememberOverlap impossible → UNION ALL, same result, less work.
3 The "duplicate" rows are actually the data you want to keep

If two rows only look identical but actually represent two separate real orders, UNION silently discards one of them as a "duplicate" — a genuine row of data is gone, not just wasted sort work. A common trap — candidates assume UNION's dedup is always harmless.

RememberDuplicates are meaningful → UNION ALL, never UNION.
🌍 Real-world example ▾

Scenario: a report unions results from Orders_2025 and Orders_Archive — a row can never exist in both tables, they hold different years. Use UNION ALL and skip the dedup pass entirely; reaching for UNION here just adds sort/hash cost for a duplicate that structurally cannot exist.
