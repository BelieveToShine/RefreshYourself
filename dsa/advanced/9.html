LRU cache — a hash map to find, a linked list to rank

"Design an LRU cache with O(1) get and put."

Why it matters ▾
🗃️ LRU cache
❗ ProblemA cache has a size limit, so something must be evicted when it is full — and scanning every entry to find the least recently used one makes every operation slow.
✅ SolutionPair a hash map (find any key in O(1)) with a doubly linked list (keep usage order, move or remove a node in O(1)) so both lookup and eviction are O(1).
RecallLRU = a map to find it, a list to rank it.
🔥 Easy interview recall

LRU cache = "a hash map to find, a doubly linked list to rank."

Think: get → map finds the node, move it to the head put → add at the head; if full, evict the tail

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A hash map alone (or a list alone) is enough." A map has no usage order to evict from, and a list can't find a key in O(1) — you need both, with the map pointing at the list's nodes.

🔄 Likely Follow-up

"Why a doubly linked list — wouldn't a singly linked list do?" To remove a node from the middle in O(1) you must change its previous node's pointer; a singly linked list only knows the next node, so finding the previous one costs O(n).

🎯 Say this in the interview — the exact lines to land

"An LRU cache combines a hash map and a doubly linked list. The map gives O(1) lookup from a key to its list node; the list keeps usage order, most recent at the head and least recent at the tail. A get moves the node to the head, and a put inserts at the head and evicts the tail when the cache is full — so both are O(1)."

  • Hash map alone → no usage order to evict from. List alone → finding a key is O(n).
  • Doubly linked → a node can unlink itself in O(1) using its own prev pointer.
  • A get counts as a use → move the node to the head, even on a read.
  • Each node stores its key → needed to delete the evicted entry from the map.
  • put on an existing key → update and move to head, no eviction.
📖 Explanation ▾

An LRU (least recently used) cache holds a fixed number of items and, when full, throws out the one untouched the longest. The trick is that two jobs need two structures. A hash map is like the index at the back of a book — it finds any key instantly but says nothing about order. A linked list is the ranking — it keeps items in order of recent use, with the most recent at the head. Pointing each map entry at its list node lets you jump straight to a node and re-rank it without searching.

get(k): look up the node in the map, unlink it, put it at the head, return its value. put(k, v): if the key exists, update the value and move the node to the head. If it is new and the cache is full, remove the tail node first — and delete its key from the map too, which is why each node stores its key — then add the new node at the head and record it in the map. Each step is a few pointer changes plus one hash lookup, so both operations are O(1) (hash lookups are O(1) on average). This is the "combine two structures to cover each other's weakness" move — see Data Structure Trade-offs for how to weigh structures like this.

Two details interviewers watch. A get also counts as a use, so reads reorder the list — with several threads, even reads change shared state and need the same lock as writes. And interviewers often ask for your own node class with prev and next (usually with dummy head and tail nodes to avoid null checks) instead of a library list.

💻 See the code ▾
C# 
public class LRUCache<TKey, TValue> where TKey : notnull
{
    private readonly int _capacity;   // assume capacity >= 1
    private readonly Dictionary<TKey, LinkedListNode<(TKey Key, TValue Value)>> _map = new();   // find
    private readonly LinkedList<(TKey Key, TValue Value)> _list = new();                  // rank: First = most recent

    public LRUCache(int capacity) => _capacity = capacity;

    public bool TryGet(TKey key, out TValue value)
    {
        if (!_map.TryGetValue(key, out var node))
        {
            value = default!;
            return false;                  // ❌ miss
        }
        _list.Remove(node);                    // O(1) — we hold the node itself
        _list.AddFirst(node);                  // ✅ a read counts as a use
        value = node.Value.Value;
        return true;
    }
    // Put(...) continues in the same class below
}

The two structures + get — the map finds the node, the list reorders it; neither alone could do both in O(1).

C# 
// inside LRUCache<TKey, TValue>
public void Put(TKey key, TValue value)
{
    if (_map.TryGetValue(key, out var existing))
    {
        _list.Remove(existing);
        existing.Value = (key, value);         // ✅ existing key: update + move, no eviction
        _list.AddFirst(existing);
        return;
    }

    if (_map.Count == _capacity)
    {
        var tail = _list.Last!;              // least recently used
        _map.Remove(tail.Value.Key);           // ❌ forget this and the map keeps a stale entry
        _list.RemoveLast();
    }
    _map[key] = _list.AddFirst((key, value));  // new node at the head, recorded in the map
}

Put + eviction — the node stores its own key so the evicted entry can also be deleted from the map. Every call is O(1) on average.

🌍 Real-world example ▾

A small desk that fits only five folders. Each folder you touch goes on top of the pile; when the desk is full, the folder at the bottom goes back to the cabinet. The map is the index that tells you which folder is where, so you never dig through the pile.
