public/ — the folder Next.js never touches

"How do static assets like a logo or favicon get served in Next.js?"

Why it matters ▾
🗂️ public/ Folder
❗ ProblemWithout a dedicated static-files convention, every logo, favicon, or downloadable file would need its own import or custom server route just to be reachable by a plain URL.
✅ SolutionFiles placed in the public/ directory at the project root are served as-is from the site's root URL — public/logo.png becomes /logo.png — no import needed, just reference the path directly.
Recallpublic/logo.png → /logo.png. No import, no processing.
🔥 Easy interview recall

public/ = "whatever's in here, served exactly as-is at the root URL."

Think: public/logo.png → /logo.png. No build step ever touches it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Putting something in public/ that needs build-time processing. Assets there are served completely unprocessed — reach for next/image (images) or a bundler import (anything that should be optimized or cache-busted) when that matters.

🔄 Likely Follow-up

"Why would you import an image instead of putting it in public/?" Importing it lets next/image automatically determine its dimensions and optimize it; a public/ asset referenced by a plain URL string skips all of that.

🎯 Say this in the interview — the exact lines to land

"Anything placed in the public/ directory at the project root is served exactly as-is from the site's root URL — public/logo.png becomes /logo.png, with no import and no build-time processing involved."

  • public/logo.png → /logo.png, reference by plain URL string.
  • public/ assets → never processed — no optimization, no cache-busting hash.
  • Need optimization → import it instead (or use next/image for images).
📖 Explanation ▾

public/ is deliberately the simplest possible static-file rule: the path inside it is the URL, minus the public prefix. No bundler ever looks inside it, which is exactly why it's the right home for things that must keep an exact, predictable path — favicon.ico, robots.txt, a downloadable PDF.

That same "nothing touches it" property is also its limitation. An asset imported into a component instead goes through the bundler, which is what lets tools like next/image read its real dimensions and optimize it — something a bare public/ file, referenced only as a URL string, never gets.

Referenced asplain URL stringan imported module

💻 See the code ▾
JavaScript 
// file at: public/logo.png
<img src="/logo.png" alt="Logo" />   // ✅ just the path, no import

The public part of the path never appears in the URL — only what's inside it does.

JavaScript 
import logo from "./logo.png";   // goes through the bundler instead
<img src={logo.src} alt="Logo" />   // ✅ width/height now known automatically

Importing it is what unlocks automatic sizing — covered fully on the next/image page next.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need a favicon, robots.txt, or sitemap.xml at an exact, predictable path

This is the #1 scenario you'll actually run into: crawlers and browsers expect these files at one exact URL — public/ guarantees that path, no routing involved.

RememberMust-be-at-this-exact-path files → public/, always.
2 You're linking to a downloadable PDF or a static data file

A file that just needs to be downloadable byte-for-byte doesn't need processing of any kind — a direct link to its public/ path is simpler than any alternative.

RememberPlain downloadable file → public/ + a direct link.
3 You dropped a large hero photo in public/ and it loads slowly on mobile

public/ never resizes or compresses anything — a large photo there always ships at full size. next/image is the fix, and it needs the file imported (or a configured remote source), not just dropped into public/.

RememberSlow-loading image from public/ → that's the sign to use next/image instead.
🌍 Real-world example ▾

A storefront window display. Whatever you put in the window is exactly what passers-by see — nobody rearranges or touches it for you. public/ is that window: predictable, unprocessed, and exactly as placed.
