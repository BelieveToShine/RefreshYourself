Caching — trading a little staleness for a lot of speed

"What is caching for, at an architecture level, not a specific product?"

Why it matters ▾
🗄️ Caching
❗ ProblemWithout a cache, every single read for the same data hits the real source — a database, another service — directly, even when nothing about that data has changed since the last read.
✅ SolutionCache-aside keeps a fast copy of the data close to the request and checks it first; only a miss reads the real source, so repeated reads for the same key stop costing a full round-trip.
RecallCaching trades a little staleness for a lot of speed — the hard part is deciding when to invalidate, not how to read.
🔥 Easy interview recall

Caching = "trade a little staleness for a lot of speed."

Think: cache-aside is the default pattern — the hard part is never the read, it's invalidation.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just cache it" isn't a strategy. Caching something that changes unpredictably without deciding how and when it gets invalidated is how an app ends up confidently serving wrong data.

🔄 Likely Follow-up

"What's the cache-aside pattern, concretely?" The app reads from the cache; on a miss, it reads the real source, writes that value into the cache, then returns it — so the next read for the same key is a hit.

🎯 Say this in the interview — the exact lines to land

"Caching trades staleness risk for speed — cache-aside is the default pattern: check the cache first, and on a miss, read the source and populate the cache before returning. The actual hard part isn't the read path, it's deciding when cached data is no longer trustworthy."

  • Cache-aside → app checks cache first, falls back to the source and writes into the cache on a miss.
  • Write-through → writes go to the cache and the source together, at write time.
  • Invalidation → the real hard part — deciding when a cached value can no longer be trusted.
  • Good fit → data that's read often and changes rarely or predictably.
📖 Explanation ▾

At an architecture level, caching means keeping a cheap, fast copy of data closer to where it's needed, so most reads never have to touch the slower, more expensive source behind it (a database, another service, an external API). The value of that copy decays over time — the source can change after the copy was taken — so every caching decision is really a bet: how much staleness is acceptable in exchange for how much speed and reduced load.

Two common patterns cover most cases. Cache-aside puts the application in charge: it checks the cache first, and only on a miss does it read the real source and write that value into the cache for next time. Write-through keeps the cache in sync at write time — the write goes to the cache and the source together, so a later read is very likely to already be a hit. Either way, the genuinely hard design problem is invalidation — deciding when a cached value has to be evicted or refreshed so a read never trusts data that's already wrong.

💻 See the code ▾
C# 
public async Task<Product?> GetProductAsync(int id)
{
    string key = $"product:{id}";
    var cached = await _cache.GetStringAsync(key); // check cache first
    if (cached is not null)
        return JsonSerializer.Deserialize<Product>(cached); // ✅ hit — no DB call

    var product = await _db.Products.FindAsync(id); // miss — read the real source
    if (product is not null)
    {
        await _cache.SetStringAsync(key,
            JsonSerializer.Serialize(product),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10) // invalidation policy
            });
    }
    return product;
}

Cache-aside in practice: check first, and on a miss, populate the cache with an explicit expiry before returning.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your data is read constantly but barely ever changes

This is the page's own real-world example — a product catalog behind Azure Cache for Redis. Because the data rarely changes, cache-aside's check-cache-first path turns almost every read into a hit, so the database barely gets touched.

RememberRead-heavy, rarely-changing data → cache-aside is the default fit.
2 A write has to be visible to the very next read, immediately

Cache-aside can't guarantee that — it only fills the cache after a read misses. Write-through does: the write goes to the cache and the source together, so the next read for that key is already a hit.

RememberMust-stay-fresh-on-every-write data → write-through, not cache-aside.
3 You cached a value that changes unpredictably and never decided when it expires

This is the actual hard part of caching, not the read path — without a real invalidation decision, the app keeps confidently serving a cached value that's already wrong, not just serving a slow one.

RememberNo invalidation plan → confidently wrong answers, not just slow ones.
🌍 Real-world example ▾

A product catalog page reads from Azure Cache for Redis first, only hitting the database on a cache miss — since the catalog rarely changes, this cuts database load dramatically while most shoppers see the exact same fast, cached response.
