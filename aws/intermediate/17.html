⭐ AWS · Intermediate · Should Know

Blue/green gives the fastest rollback — that's the whole point of it

"How do you achieve zero-downtime deployment, and how would you roll back a bad production release?"

Why it matters ▾
  • Checks whether you know the real trade-off between rollback speed and infrastructure cost across deployment strategies.
  • Comes up in almost every "how would you deploy without downtime" or "tell me about a bad release" question.
  • A natural follow-up after any CI/CD pipeline, ECS/Lambda, or production-incident question.
🔥 Easy interview recall

Blue/green → switch traffic, instant rollback

Canary → small % first, grow if healthy

Rolling → one at a time, stay compatible

Immutable → never patch, always replace

Think: Blue/green is the fastest undo. Canary is the smallest blast radius. Rolling is the one that must stay backward-compatible mid-deploy.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Rolling deployment means zero downtime." Not quite — a rolling deployment still briefly runs both the old and new versions at the same time, which only works cleanly if the two versions are backward-compatible; an incompatible rolling deploy can still throw real errors during that overlap window.

🔄 Likely Follow-up

"How would you roll back a bad production deployment?" With blue/green, switch traffic back to the still-running old environment almost instantly; with rolling or canary, trigger a new deployment of the last known-good version — that rollback-speed gap is a real reason blue/green gets chosen for high-risk releases.

🎯 Say this in the interview — the exact lines to land

"Blue/green gives the fastest rollback, canary limits blast radius, and rolling must stay backward-compatible mid-deploy — CodePipeline orchestrates the overall workflow, CodeBuild compiles, tests, and packages the build, and CodeDeploy handles the actual deployment mechanics, including blue/green for EC2, ECS, and Lambda."

  • Blue/green → switch traffic, instant rollback — two full environments running side by side.
  • Canary → small % first, only scale up if error rates stay healthy.
  • Rolling → must stay compatible — old and new versions run together briefly.
  • Immutable → never patch — always replace with a freshly-built instance.
  • CodePipeline orchestrates; CodeBuild compiles/tests/packages; CodeDeploy deploys.
📖 Explanation ▾

Blue/green deploys the new version alongside the fully-running old one, then flips traffic to it all at once — because the old environment is still sitting there untouched, rollback is just flipping traffic back. Canary instead shifts a small slice of real traffic to the new version first, watching it stay healthy before gradually sending it more — it trades rollback speed for a smaller blast radius if something's wrong.

Rolling replaces instances or tasks with the new version a few at a time, always keeping a minimum healthy capacity serving traffic — cheapest in extra infrastructure, but the old and new versions are genuinely live together for a window, so they have to speak the same contract. Immutable deployment never patches a running instance in place — it always builds a brand-new one from the new version and swaps it in, which is what makes blue/green (and canary, underneath) safe to reason about: nothing already running ever silently changes. On AWS, CodePipeline is the orchestrator stitching the stages together, CodeBuild does the compile/test/package step, and CodeDeploy executes the deployment itself — including blue/green swaps for EC2, ECS, and Lambda.

🌍 Real-world example ▾

A team ships a risky release with a canary deployment, routing just a small percentage of real traffic to the new version and watching its error rate closely. The regression shows up in the canary's metrics before it ever reaches most users, so the team stops the rollout and fixes it — instead of finding out the hard way after 100% of traffic already moved.
