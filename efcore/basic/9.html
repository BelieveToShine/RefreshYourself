Code-first or database-first — who is the source of truth?

"Code-first or database-first — and how do you reverse-engineer an existing DB?"

Why it matters ▾
🧭 Two starting points
❗ ProblemSome projects start with no database and some start with a database that already exists — and keeping C# classes and tables in sync by hand is slow and error-prone.
✅ SolutionCode-first generates and evolves the database from your C# model with migrations. Database-first generates the C# model from an existing database with dotnet ef dbcontext scaffold.
RecallCode-first = model drives the database. Database-first = database drives the model.
🔥 Easy interview recall

Code-first → model drives the database (migrations)

Database-first → database drives the model (scaffold)

Think: Migrations push C# → database.Scaffold pulls database → C#.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Scaffolding is not a live sync. It is a one-time snapshot — when the schema changes you scaffold again, and re-scaffolding with --force overwrites the generated files, so hand-edits in them are lost.

🔄 Likely Follow-up

"Can you start database-first and move to code-first later?" Yes — scaffold once, stop re-scaffolding, and manage changes with migrations from then on. Treat the first migration as a baseline, because the tables already exist.

🎯 Say this in the interview — the exact lines to land

"In code-first I write the entities and DbContext and use migrations to create and evolve the database. In database-first the schema already exists, so I reverse-engineer it with dotnet ef dbcontext scaffold, which generates the entity classes and the DbContext."

  • New project, app owns the schema → code-first with migrations.
  • Existing or DBA-owned database → database-first, scaffold it.
  • Scaffold is a one-time snapshot; --force overwrites the generated files.
  • Keep your own code in partial classes, so a re-scaffold doesn't erase it.
  • Either way you end up with the same thing: entities + a DbContext.
📖 Explanation ▾

Code-first: you write the entity classes and a DbContext, and EF Core builds the database from them. Change the model, run dotnet ef migrations add, then dotnet ef database update. The C# model is the source of truth.

Database-first (reverse engineering): the schema already exists, so you run dotnet ef dbcontext scaffold with a connection string and a provider. EF Core reads the tables and writes the entity classes and a DbContext. The database is the source of truth. EF Core has no EDMX designer — the scaffold command is the workflow.

Scaffolding is a snapshot, not a link. The generated entities and context are partial, so put your own members in separate partial-class files and a re-scaffold won't touch them. Some teams scaffold once and then switch to migrations; from that point the code is the source of truth. See Migrations & SaveChanges() — the Basics and Migrations, Mechanically.

💻 See the code ▾
Shell 
dotnet ef migrations add AddOrders    # code-first: diff the model, write a migration
dotnet ef database update            # code-first: apply it to the database

Code-first: the model changes first, the commands carry the change to the database.

Shell 
dotnet ef dbcontext scaffold "Server=.;Database=Shop;Trusted_Connection=True;TrustServerCertificate=True" Microsoft.EntityFrameworkCore.SqlServer --output-dir Models --context ShopContext

Database-first: connection string + provider in, entity classes and a ShopContext out. Add --force to overwrite files from an earlier run.

C# 
public partial class Customer      // generated file: don't edit
{
    // ...scaffolded properties...
}

public partial class Customer      // your own file: survives a re-scaffold
{
    public string DisplayName => $"{FirstName} {LastName}";   // ✅ safe from --force
}

Generated classes are partial — your extras live in a second file the scaffold never writes.

🌍 Real-world example ▾

A startup building a new API goes code-first — the model is the design, migrations are the history. A company with a ten-year-old SQL Server database that DBAs own scaffolds it once, then builds new features on top.
