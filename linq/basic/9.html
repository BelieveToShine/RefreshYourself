Skip vs. Take — the building blocks of paging

"What's the difference between Skip and Take, and how do they combine for paging?"

Why it matters ▾
🚫 Skip
❗ ProblemShowing "page 2" of a result set means ignoring the rows that already belong to page 1 — doing that by hand means tracking an index offset yourself.
✅ SolutionSkip(n) discards the first n elements and leaves everything after them untouched.
RecallSkip = throw away the first n.
📥 Take
❗ ProblemReturning an entire result set when the caller only asked for one page sends far more data than anyone needs.
✅ SolutionTake(m) keeps only the next m elements and stops pulling anything after that.
RecallTake = keep exactly the next m.
🔥 Easy interview recall

Skip(n) → discard the first n

Take(m) → keep the next m

Think: Skip(n).Take(m) = one page — skip to where you left off, then take exactly a page's worth.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Paging with Skip/Take but no stable OrderBy first. Without a deterministic order, the same "page 2" request can return a row that was already on page 1, or silently miss one, because the underlying sequence order isn't guaranteed to stay the same between calls.

🔄 Likely Follow-up

"What happens if rows are inserted or deleted between page requests?" Even with a stable OrderBy, offset paging can still shift — a deleted row before the page boundary pulls everything after it one position earlier, duplicating or skipping a row; keyset ("seek") pagination avoids this by anchoring to a real column value instead of a row count.

🎯 Say this in the interview — the exact lines to land

"Skip(n) discards the first n elements, Take(m) keeps only the next m, and Skip(n).Take(m) together express one page of a result set — but that only gives consistent pages once the sequence has a stable, deterministic order."

  • Skip(n) → discards and never looks at those elements again.
  • Take(m) → keeps only the next m, then stops pulling more.
  • Always put OrderBy before Skip/Take — otherwise page boundaries aren't guaranteed.
📖 Explanation ▾

Skip walks past the first n elements without doing anything with them, then yields everything after that unchanged.

Take starts yielding from wherever the sequence currently is, and stops the instant it has handed out m elements — it never pulls a single element more than asked.

Chained together, Skip(n).Take(m) is the standard way to express "give me page (n / m) + 1" of a result set — but the page is only meaningful if the underlying order is the same every time the query actually runs.

💻 See the code ▾
C# 
int pageSize = 10, pageNumber = 2;
var page = items
    .OrderBy(x => x.Id)                       // ✅ stable order first
    .Skip((pageNumber - 1) * pageSize)        // skip page 1's rows
    .Take(pageSize)                           // keep exactly page 2
    .ToList();

OrderBy before Skip/Take — this is what makes "page 2" mean the same rows every time.

C# 
var risky = items.Skip(10).Take(10).ToList();  // ❌ no OrderBy — which 10 rows you get isn't guaranteed to repeat

Same two calls, no guaranteed order underneath them — page 2 might not mean the same thing twice.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're building a "page 2, page 3…" control on a results list

A product listing, a search page, an admin table — anywhere a user clicks "next page," the server runs the same OrderBy().Skip().Take() shape with a different offset. This is the #1 scenario you'll actually run into.

Remember"Page 2, page 3…" → Skip/Take with a stable order.
2 You're processing a known-size job in fixed chunks

Splitting a moderate-size job into fixed batches — Skip(i * 500).Take(500) in a loop with an incrementing i — is a plain, readable way to process it without loading everything into memory at once.

RememberFixed-size chunks → an incrementing Skip offset, same Take size.
3 You page through a table that's actively being written to

If a row ahead of the page boundary gets deleted between requests, everything after it shifts one position earlier — the next Skip offset now lands one row too far forward, and a row silently never appears on any page.

RememberLive table + offset paging → a row can vanish between page loads.
🌍 Real-world example ▾

Think of flipping through a stack of printed reports. Skip is flipping past the first stack of pages without reading them. Take is reading exactly the next stack and stopping there. Doing both in order is exactly how you'd turn to "page 3" and read just that page.
