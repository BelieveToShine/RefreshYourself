Traces are what actually let you find the slow hop

"How would you troubleshoot a slow API request across multiple microservices?"

Why it matters ▾
📈 Metrics
❗ ProblemA single slow request buried among thousands of fine ones is invisible until it's already hurting real users — nothing tells a human it's time to even start looking.
✅ SolutionMetrics aggregate numeric measurements like request count, CPU, and latency percentiles into time-series data across every request, so a symptom like elevated error rate or rising p99 latency is the trigger that says "look now."
RecallMetrics = numbers over time, aggregated across many requests.
📝 Logs
❗ ProblemA metric spike tells you something's off in aggregate, but not what actually happened inside any one service at that moment.
✅ SolutionLogs are text records of individual events, scoped to whatever wrote them — one service, one line, one moment — so you can see exactly what happened at that one stop.
RecallLogs = text record of one event, in one service.
🔍 Traces
❗ ProblemEven with metrics and logs in hand, isolated per-service logs only tell you a given service was fine or busy on its own — none of them say which specific hop in a multi-service request is the one actually slow.
✅ SolutionAWS X-Ray gives one request a shared trace ID that follows it through every service it touches, stitching each service's timed segment into one waterfall — so the slow hop is something you point at instead of guess at.
RecallTraces = one request's path across services, stitched by a shared trace ID.
🔥 Easy interview recall

Metrics → numbers over time

Logs → text for one event

Traces → one request's path across services

Think: metrics say something's slow. logs say what happened at one stop. traces say which stop was slow.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 Don't mix these three — the single most valuable distinction on this page
⚠️ Common Trap

"I'll just check each service's own logs and metrics." Without a shared trace ID stitching every hop together, isolated per-service logs only tell you that service was fine or busy — they can't tell you which specific hop in the chain is the one actually making the whole request slow.

🔄 Likely Follow-up

"What should actually trigger an alarm?" A symptom a human needs to act on — an elevated error rate, a p99 latency crossing a real threshold — not every metric that happens to move, which just trains people to ignore alerts.

🎯 Say this in the interview — the exact lines to land

"Metrics, logs, and traces are three different lenses — traces are what actually let you find the slow hop across microservices. I'd pull the trace for the slow request, look at each segment's timing, and see exactly which downstream call is eating the time; metrics and logs then help me confirm and dig into what's happening inside that one service."

  • Metrics → numbers over time — good for "is something wrong right now."
  • Logs → one event's text record — good for "what exactly happened here."
  • Traces → one request's path across every service it touched — good for "which hop is slow."
  • Alarms → symptom-based, like error rate or p99 latency — not every metric that moves.
📖 Explanation ▾

Metrics are numeric measurements tracked over time — CloudWatch stores things like request count, CPU, or latency percentiles as time-series data, aggregated across many requests. Logs are text records of individual events, scoped to whatever wrote them — one service, one line, one moment. Neither one, on its own, can follow a single request as it moves from service to service.

Traces exist to close that gap. AWS X-Ray gives a request one shared trace ID the moment it enters the system, and every instrumented service the request passes through records its own timed segment under that same ID. Correlating a request across microservices depends entirely on that shared trace ID being propagated through every hop — X-Ray's SDK does this automatically once a service is instrumented. Stitched together, those segments become one waterfall view of the whole request, so the slow hop is something you can point at instead of something you have to guess at from separate, disconnected logs.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your on-call dashboard pages you because p99 latency just crossed the alert threshold

A symptom-based alarm firing on a metric like p99 latency is exactly the "look now" signal — it's aggregated across many requests, so it tells you something is wrong right now, but not which single request or service caused it.

RememberMetrics are the trigger to start looking, not the answer for where.
2 A customer reports one exact order that failed at 2:14pm

There's no aggregate number for one specific order, so you go straight to the text record of that one event, in whichever one service wrote it, to see exactly what happened at that moment.

RememberOne event, one service — logs answer "what exactly happened here."
3 Checkout feels slow, so your first instinct is to check each service's own logs and metrics one by one

Without a shared trace ID stitching every hop together, isolated per-service logs and metrics only tell you each service was fine or busy on its own — none of them can say which specific hop is the one actually making the whole request slow. Pulling the X-Ray trace instead is what actually answers it.

RememberPer-service checks can't find a cross-service problem — only a shared trace ID can.
🌍 Real-world example ▾

A checkout flow feels slow, and the checkout service's own metrics look fine — it's just waiting on something. Pulling the X-Ray trace for one of the slow requests shows the payment-service call is what's actually eating 4 of the request's 5 total seconds, not the checkout service itself, so the investigation moves straight to payment-service instead of wasting time on the wrong team's code.
