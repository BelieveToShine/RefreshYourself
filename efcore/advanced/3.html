RowVersion — no lock while it's open, just a bet checked at save time

What is optimistic concurrency, and how does EF Core implement it?

Why it matters ▾
🔄 Optimistic Concurrency
❗ ProblemTwo separate save operations — possibly minutes apart, from two different users — can overwrite each other's changes to the same row, with no error at all.
✅ SolutionA RowVersion/token is checked in the generated WHERE clause; zero rows matched throws DbUpdateConcurrencyException so the app decides what happens next, instead of silently overwriting.
RecallGuards across time — two separate saves, enforced by a version token in the WHERE clause.
🔒 Transaction / Isolation Level
❗ ProblemA single unit of work could leave a partial or inconsistent change if something goes wrong partway through it.
✅ SolutionThe database's locks and isolation level keep that one operation atomic, start to commit, rolling back automatically if it fails — but that protection ends the moment the transaction commits.
RecallGuards within one operation only — doesn't stop a later save, weeks apart, from overwriting it.
🔥 Easy interview recall

Read row → no lock taken

Save row → WHERE RowVersion = original value

0 rows matched → DbUpdateConcurrencyException

Think: optimistic concurrency doesn't ask permission first — it just checks, at save time, whether the row moved on without you.

🧠 Visual Mental Model — understand it in 5 seconds
🧠 Don't mix these two — the single most valuable distinction on this page
⚠️ Common Trap

Optimistic concurrency is not a transaction or isolation level. A transaction guarantees atomicity inside one unit of work; optimistic concurrency guards against two separate save operations — possibly minutes apart, from two different users — stepping on each other's changes to the same row.

🔄 Likely Follow-up

"User A saves a shipping-address change first. User B, still holding the row at its old version, then saves an edit to a completely different field — a note. Does B's save still fail, even though the two edits don't overlap?" Yes — DbUpdateConcurrencyException still fires. The generated WHERE clause checks the whole RowVersion token, not which column changed, so any change since B's read triggers a conflict, regardless of whether the two edits were actually compatible.

🎯 Say this in the interview — the exact lines to land

"Optimistic concurrency assumes conflicts are rare, so EF Core doesn't lock the row while it's being edited. Instead, it adds the originally-read RowVersion value to the WHERE clause of the generated UPDATE — if that value no longer matches, zero rows are affected, and EF Core throws DbUpdateConcurrencyException so the application can decide what to do next."

  • [Timestamp] / RowVersion → the token EF Core checks, a byte[] mapped to SQL Server's rowversion type.
  • [ConcurrencyCheck] / .IsConcurrencyToken() → any column can be a token, not only a dedicated version column.
  • Zero rows affected → EF Core throws DbUpdateConcurrencyException — it never guesses or merges on its own.
  • On conflict → reload and ask the user to reconfirm is the safest default; "client wins" is a deliberate, explicit choice, not a fallback.
  • Not the same as a transaction → isolation levels protect one unit of work; this protects against two separate ones.
📖 Explanation ▾

EF Core needs one column marked as a concurrency token — most commonly a RowVersion property of type byte[], attributed [Timestamp] or configured with Fluent .IsConcurrencyToken(), mapped to SQL Server's rowversion column type, which the database itself updates on every write. Any column can be marked a token with [ConcurrencyCheck] instead — EF Core just folds it into the same check, it doesn't require a dedicated version column.

The value EF Core read when the entity was first loaded gets carried into the WHERE clause of the generated UPDATE (or DELETE) statement, alongside the primary key. If another save already changed that row, the current token in the database no longer matches, the WHERE clause matches zero rows, and EF Core surfaces that as DbUpdateConcurrencyException — not a generic database error, a specific signal that an expected update affected nothing.

EF Core stops there on purpose — it never picks a winner for you. The calling code decides: reload the current row and ask the user to reconfirm, overwrite anyway ("client wins," a deliberate choice), or attempt a field-level merge.

💻 See the code ▾
C# 
public class Order
{
    public int Id { get; set; }
    public string ShippingAddress { get; set; }
    public string Note { get; set; }

    [Timestamp] // maps to SQL Server's rowversion column
    public byte[] RowVersion { get; set; }
}

EF Core folds RowVersion into the WHERE clause of every UPDATE/DELETE for this entity — no extra code needed at the call site.

C# 
try
{
    await db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    // ❌ 0 rows matched — someone else saved this row first
    var entry = ex.Entries.Single();
    var dbValues = await entry.GetDatabaseValuesAsync();
    if (dbValues is null)
        throw; // row was deleted, not just changed

    entry.OriginalValues.SetValues(dbValues); // ✅ reload the current token
    // re-prompt the user here instead of just retrying, in most apps
    await db.SaveChangesAsync();
}

This retries as "client wins." A safer default for a user-facing edit is to stop here and show the current row, letting the person reconfirm instead.

C# 
modelBuilder.Entity<Order>()
    .Property(o => o.Note)
    .IsConcurrencyToken(); // any column, no dedicated RowVersion needed

Works without a rowversion column — EF Core adds Note to the WHERE clause too, but now only a change to Note itself triggers a conflict.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two people save the same row minutes apart

Both read RowVersion = 1. Rep A's save matches and moves the row to v2. Rep B's save still checks WHERE RowVersion = 1, matches zero rows, and throws DbUpdateConcurrencyException. This is the #1 scenario you'll actually run into.

RememberSecond save to match the old version always loses.
2 The two saves touch completely different fields

Rep A changed the shipping address; Rep B, still on the old version, only edits an unrelated Note field. The generated WHERE clause checks the whole RowVersion token, not which column changed, so B's save still throws DbUpdateConcurrencyException even though the two edits never overlapped.

RememberRowVersion checks the whole row, not just the changed column.
3 You reach for a transaction instead of a RowVersion token

A transaction's locks and isolation level only protect one unit of work, start to commit — once it commits, that protection is gone. It never stops a second, unrelated save from overwriting the row weeks later; only a concurrency token checked at save time does that. A great interview trap — candidates often assume a transaction already covers this.

RememberA transaction ends at commit — it can't protect a save that happens later.
🌍 Real-world example ▾

Two reps at a dealership CRM open the same customer's order at the same time. Rep A updates the shipping address and saves — the row moves to version 2. Rep B, still looking at version 1, saves a note a minute later and gets DbUpdateConcurrencyException. The architecture question this raises: should the app block Rep B with a reload-and-reconfirm prompt, let Rep B's save silently win ("client wins"), or merge the two non-conflicting fields automatically? Reload-and-reconfirm is the safest default for user-facing edits — a human makes the final call. Automatic field-level merging looks appealing but is rarely worth building: it quietly reintroduces the exact risk this page's follow-up question exposes, since merging bypasses the same whole-row check that caught the conflict in the first place.
