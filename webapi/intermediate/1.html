Safe vs. idempotent — five verbs, two different promises

"What does each HTTP verb actually promise in terms of safety and idempotency?"

Why it matters ▾
🛡️ Safe methods
❗ ProblemInfrastructure that knows nothing about your app — a browser, a proxy, a CDN — needs a way to tell whether calling a method again is harmless, without asking your server first.
✅ SolutionGET, HEAD, and OPTIONS all promise never to change server state, so that infrastructure is free to retry, prefetch, or cache them.
RecallSafe = never changes state — GET, HEAD, OPTIONS.
🔁 Idempotent methods
❗ ProblemA client whose PUT or DELETE call times out needs to know whether it's safe to just resend the exact same request.
✅ SolutionPUT and DELETE do change state, so neither is safe — but repeating the exact same one still lands in the same end state, so a retry is fine.
RecallPUT/DELETE change state (not safe) — repeat = same result (idempotent).
⚖️ Safety ≠ Idempotency
❗ ProblemPeople treat these as the same property — and wrongly call DELETE "safe" just because a retry is harmless, skipping the caution a real state change deserves.
✅ SolutionThey're independent axes: safe asks whether it ever changes state; idempotent asks whether repeating it changes the outcome further. DELETE proves a method can be idempotent without being safe.
RecallIndependent axes — idempotent doesn't mean safe (see DELETE).
🔥 Easy interview recall

GET → safe + idempotent

POST → neither

PUT → idempotent only

DELETE → idempotent only

PATCH → it depends

Think: Safe = doesn't touch server state. Idempotent = repeat it, land in the same end state either way.

⚠️ Common Trap

"Safe" doesn't mean "harmless." It only means the method causes no server-side state change — a GET that runs an expensive, slow report query is still "safe" in the HTTP sense, even though it's a bad idea performance-wise.

🔄 Likely Follow-up

"Why does this matter beyond a definitions quiz?" Browsers, proxies, and CDNs are allowed to automatically retry safe/idempotent requests on network failure without asking first — if a GET or PUT secretly has non-idempotent side effects, breaking that promise, an automatic retry from infrastructure you don't control can silently double the effect.

🎯 Say this in the interview — the exact lines to land

"GET is safe and idempotent — a pure read. POST is neither — it creates, and repeating it creates more. PUT and DELETE aren't safe, but they are idempotent — repeating them lands in the same end state. PATCH isn't safe, and whether it's idempotent depends entirely on what the patch itself does."

  • GET → safe AND idempotent — the only verb that's both.
  • POST → neither — creates state, and every repeat creates more.
  • PUT / DELETE → not safe, but idempotent — repeating lands in the same state.
  • PATCH → idempotency depends on the operation — "set field to X" is; "increment by 1" isn't.
  • "Safe" only means no server-side state change — not "no downside at all."
📖 Explanation ▾

Safe is a promise about the server, not the client's experience of the request: a safe method must not change any state the server is responsible for. HTTP defines it this way on purpose — it lets a piece of infrastructure that knows nothing about your application (a browser, a proxy, a CDN) reason about a request's effect just by looking at the verb, without having to understand what the endpoint actually does.

Idempotent is a separate promise: repeating the exact same request any number of times leaves the server in the same end state as doing it once. What idempotency itself means, and why the guarantee matters, is covered in full on the Idempotency page — this page is specifically about which verb actually makes that promise. PUT earns it because it replaces a resource wholesale with the body you send; sending the same body twice just replaces it with itself the second time. DELETE earns it because "already gone" is a valid end state — deleting something that's already deleted still leaves it deleted.

PATCH is the one verb where the answer isn't fixed by the verb itself — it's fixed by the semantics of the specific patch. A patch that says "set status to shipped" is idempotent: applying it twice still leaves status as shipped. A patch that says "increment stock by 1" is not: applying it twice increments it twice. Nothing in the framework or the HTTP spec enforces any of this in code — a handler for GET can technically delete a row if you write it that way. Safety and idempotency are a contract with the HTTP infrastructure sitting between your client and your server, not a guarantee the compiler or the framework checks for you.

💻 See the code ▾
C# 
[HttpPut("{id}")]
public IActionResult ReplaceUser(int id, UserDto dto)
{
    var user = _db.Users.Find(id);
    user.Name = dto.Name;    // ✅ same call twice → same end state
    user.Email = dto.Email;
    _db.SaveChanges();
    return NoContent();
}

Call this endpoint once or three times with the same body — the user ends up in the exact same state either way. That's idempotent in practice.

C# 
[HttpPost]
public IActionResult CreateOrder(OrderDto dto)
{
    var order = new Order { ProductId = dto.ProductId };
    _db.Orders.Add(order);   // ❌ every retry adds ANOTHER row
    _db.SaveChanges();
    return CreatedAtAction(nameof(GetOrder), new { id = order.Id }, order);
}

A timeout that makes a client retry this exact call creates two orders, not one — exactly why POST is never safe to auto-retry.

C# 
[HttpPatch("{id}/status")]
public IActionResult SetStatus(int id, string status)
{
    var order = _db.Orders.Find(id);
    order.Status = status;   // ✅ same call twice → still "shipped"
    _db.SaveChanges();
    return NoContent();
}

A "set field to X" PATCH is idempotent — the second call is a no-op.

C# 
[HttpPatch("{id}/stock")]
public IActionResult IncrementStock(int id, int by)
{
    var item = _db.Items.Find(id);
    item.Stock += by;   // ❌ same call twice → DOUBLE the increase
    _db.SaveChanges();
    return NoContent();
}

Same verb, same route shape — but an "increment" PATCH is not idempotent. The verb never guarantees it; the operation's own semantics do.

🧭 Use Cases — recognize these when they happen to you ▾
1 An HTTP client library decides whether to auto-retry a failed call

A retry wrapper firing again after a timeout has no idea what your endpoint does — it can only look at the verb. Because GET, HEAD, PUT, and DELETE are all idempotent, resending the exact same one after a failure can't make things worse. POST gets no such free pass — the library can't tell whether the first attempt already succeeded, so retrying it risks a duplicate create.

RememberIdempotent → safe to auto-retry. POST isn't, even if it already ran.
2 You're choosing PUT vs. POST for an "update" endpoint

PUT expects the client to send the resource's full new state at a known URL and promises repeats land in the same place — pick it for "replace/update this exact resource." POST expects the server to decide what gets created, so a retry can't promise the same outcome — pick it when the server, not the client, decides the new resource's identity.

RememberClient knows the full state and the URL → PUT. Server decides what's created → POST.
3 A caching proxy or CDN decides what it may store or safely replay

Both questions collapse into one from the cache's point of view: GET and HEAD are safe, so a cache can store their responses and reuse them, and can also safely resend one automatically after a dropped connection. A CDN generally won't cache or blindly replay POST, PUT, PATCH, or DELETE — those change (or might change) server state, so replaying one without the origin's knowledge risks an unintended effect.

RememberSafe → OK to cache. Not idempotent → never auto-replay.
🌍 Real-world example ▾

GET is like reading a public noticeboard — looking at it twice never changes what's posted. POST is like dropping a new letter in a mailbox — do it twice, two letters arrive.

Scenario: your payment API's POST /charge occasionally times out on the client side, and a naive retry wrapper resends it. Because POST was never meant to be auto-retried, HTTP itself gives you no protection here — the fix is an application-level idempotency key: the client generates one ID per logical charge attempt, sends it on every retry, and the server deduplicates on that key instead of on the request shape.
