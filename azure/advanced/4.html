Hub-spoke — one firewall to configure, not one per team

Why would a real architecture centralize shared services in a hub VNet instead of every spoke talking directly to everything else?

Why it matters ▾
  • Real Azure environments grow to dozens of team-owned VNets — without a hub, every pair that needs to talk to each other needs its own peering and its own firewall rules, and that stops being manageable fast.
  • Centralizing the firewall/NVA, the VPN/ExpressRoute gateway, and DNS in one hub means a security rule change or a new on-prem connection happens once, not once per spoke.
  • A common senior/architect networking question — expect it phrased as "how would you connect a dozen team VNets together" or "what's the actual point of a hub VNet."
🔥 Easy interview recall

Hub-spoke = "spokes peer to the hub, never to each other."

Think: 10 spokes → 10 peering connections to the hub, not 45 for a full mesh.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Peering isn't transitive. If Spoke A peers with the hub and Spoke B peers with the hub, A and B still can't reach each other through the hub unless the hub is explicitly configured to route between them (e.g. a firewall/NVA acting as the router) — peering alone never chains.

🔄 Likely Follow-up

"How many peering connections would a full mesh of 10 spokes need vs. hub-spoke?" A full mesh needs 45 pairwise connections (n(n-1)/2); hub-spoke needs just 10 — one per spoke to the hub. That management-complexity gap is the whole point of the pattern.

🎯 Say this in the interview — the exact lines to land

"Spokes peer to the hub, not to each other — peering isn't transitive, so cross-spoke traffic needs the hub to route it."

  • Hub VNet holds the shared services — firewall/NVA, VPN/ExpressRoute gateway, DNS — every spoke needs.
  • Each spoke peers only to the hub, never directly to another spoke.
  • Peering count: 10 spokes → 10 connections in hub-spoke, versus 45 in a full mesh (n(n-1)/2).
  • Cross-spoke traffic must be explicitly routed through the hub's firewall/NVA — peering itself never chains.
📖 Explanation ▾

Hub-spoke is a network layout, not a specific Azure resource: one central hub virtual network holds the services every workload needs — a firewall or network virtual appliance (NVA), a VPN or ExpressRoute gateway for on-premises connectivity, and shared DNS. Every workload, team, or environment gets its own spoke VNet, and each spoke connects only to the hub.

VNet peering is the private, low-latency connection Azure uses to link two VNets — traffic stays on Microsoft's backbone, never crossing the public internet. In hub-spoke, every spoke peers to the hub and nowhere else, so adding a new team just means one more peering connection to configure, not a rule change on every existing spoke.

Peering by itself only makes the hub and that one spoke reachable to each other — it does not automatically let two spokes reach each other through the hub. Making spoke-to-spoke traffic work requires the hub to actually route it, typically through the firewall/NVA sitting in the hub together with user-defined routes (UDRs) that send spoke traffic there on purpose.

💻 See the code ▾
Azure CLI 
az network vnet peering create --name hub-to-spoke1 \
  --vnet-name hub-vnet \          -- the hub side
  --remote-vnet spoke1-vnet \    -- the spoke side
  --allow-vnet-access

This creates one direction of the peering. Spoke1's own az network vnet peering create command (hub as the remote) is needed too — peering is configured on both ends before traffic flows either way.

🌍 Real-world example ▾

A large enterprise centralizes its firewall and VPN gateway in a hub VNet, letting a dozen team-owned spoke VNets each peer to it instead of every team managing its own gateway and its own firewall rules. A new team onboarding just needs one peering connection to the hub — nobody has to touch the other eleven spokes.
