IEnumerable<T> vs. IQueryable<T> — running code, or building an expression tree?

"Both are 'a sequence you can LINQ over' — what's the actual difference between them?"

Why it matters ▾
🔗 Where does it run?
❗ ProblemThe exact same Where/Select syntax over a List<T> and over a DbSet<T> can behave completely differently — one filters in memory with real C# code, the other is translated into SQL first — and not knowing which one you're holding leads to code that either runs far slower than expected, or throws at runtime for a method the other side can't translate.
✅ SolutionIQueryable<T> builds an expression tree instead of running anything — a provider (like EF Core) walks that tree and turns it into SQL before anything executes. IEnumerable<T>'s LINQ-to-Objects operators just run as compiled C# delegates directly over data already in memory.
RecallIEnumerable = runs now, in memory. IQueryable = builds a tree, runs later, elsewhere.
🔥 Easy interview recall

IEnumerable<T> → compiled delegate, runs now, in memory

IQueryable<T> → expression tree, a provider translates it later

Think: IEnumerable is already code. IQueryable is still just data describing code.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Writing Where(x => SomeCSharpOnlyMethod(x)) on an IQueryable doesn't "just run" like it would on an IEnumerable. The lambda is data describing a call the provider has to recognize and translate — a method only you and the CLR understand has nothing to translate to, and either throws at translation time or silently gets evaluated client-side.

🔄 Likely Follow-up

"What actually makes this possible under the hood?" Func<T> vs. Expression<Func<T>> — a Func is already-compiled, callable code; an Expression<Func<T>> is a tree a provider can inspect and rewrite instead of running, which is the real mechanism behind this whole difference.

🎯 Say this in the interview — the exact lines to land

"IEnumerable<T>'s LINQ operators compile your lambda into a real delegate and run it immediately, in memory. IQueryable<T>'s operators build an expression tree instead — nothing runs until a provider like EF Core walks that tree and translates it into something else, usually SQL, at the point you call a terminal operator."

  • IEnumerable<T> → runs as compiled C# delegates, right now, in memory.
  • IQueryable<T> → builds an expression tree, data describing the query.
  • A provider → walks the tree and translates it (e.g. to SQL) before anything runs.
  • Same syntax, different boundary → which interface you're holding decides where the work happens.
📖 Explanation ▾

Both interfaces let you write .Where(), .Select(), and the rest — but they build fundamentally different things under that shared syntax. LINQ-to-Objects, the set of extension methods over IEnumerable<T>, takes your lambda and compiles it into a real Func<T,bool> (or similar) delegate — already-executable code that runs the moment the sequence is enumerated, entirely in memory.

LINQ-to-Entities, the IQueryable<T> side (EF Core's DbSet<T> being the common example), instead takes your lambda as an Expression<Func<T,bool>> — a tree of objects describing the code's structure, never compiled into runnable IL at all. Each .Where()/.Select() call just appends another node to that tree. Only when a terminal operator finally runs does a query provider walk the accumulated tree and translate it into something else — SQL, for a database provider.

This is why the same-looking query behaves so differently depending on which interface it's typed as: an IEnumerable<T> query can call any real C# method inside its lambda, because it's going to actually run that method. An IQueryable<T> query can only call what its provider's translator recognizes, because the lambda is never executed as C# at all.

💻 See the code ▾
C# 
IEnumerable<Order> inMemory = orderList;
var big = inMemory.Where(o => IsBigSpender(o));   // ✅ runs real C#, any method works

IsBigSpender is a real compiled method — IEnumerable just calls it.

C# 
IQueryable<Order> fromDb = dbContext.Orders;
var big = fromDb.Where(o => IsBigSpender(o));   // ❌ provider can't translate a custom method

Same-looking call — but IsBigSpender is never actually run here, only inspected as a tree node.

🧭 Use Cases — recognize these when they happen to you ▾
1 You filter an in-memory List<T> with a lambda calling a normal method

IEnumerable<T> has no translator to satisfy — any valid C# compiles and runs, because it's real code executing, not a tree waiting to be understood by something else.

RememberIn-memory + IEnumerable → any C# method is fair game.
2 You write the exact same filter against an EF Core DbSet<T>

A simple comparison like x.Age > 18 is a recognized pattern the provider's translator understands, so it becomes a WHERE clause in SQL — the query never runs as C# at all, it runs as the SQL the tree was translated into.

RememberA recognized expression shape → the provider turns it into SQL.
3 You call a custom C# method inside a lambda on an IQueryable

The provider has no SQL equivalent for a method it doesn't recognize — there's nothing to fall back to translate it with, so this throws at translation time (or, on older providers without strict client-eval blocking, silently pulls far more data than intended).

RememberUnrecognized method on an IQueryable → nothing to translate it to.
🌍 Real-world example ▾

A helper method takes an IEnumerable<T> parameter, and someone passes it an EF Core DbSet<T>. It compiles, because IQueryable<T> implements IEnumerable<T> — but any further LINQ calls inside that helper now run as LINQ-to-Objects, in memory, after the entire table has already been pulled down, instead of staying translatable to SQL.
