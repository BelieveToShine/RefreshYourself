Azure Monitor vs. App Insights — the platform, and your app's own lens on it

"How do Azure Monitor and Application Insights actually relate, and what's the difference between a metric alert and a log alert?"

Why it matters ▾
☁️ Azure Monitor
❗ ProblemIf every Azure resource kept its own separate store for metrics, activity logs, resource health, and alert rules, there'd be nowhere shared to see or query monitoring data across an environment.
✅ SolutionAzure Monitor is the one platform-wide service that collects all of it — platform metrics, activity logs, resource health, alert rules — so every alert reads from the same shared data instead of a per-service silo.
RecallAzure Monitor = the umbrella platform every monitoring signal feeds into.
🔬 Application Insights
❗ ProblemA platform metric like CPU or request count can flag that something's wrong, but it can't say which line of your own code threw the exception or how a dependency call performed.
✅ SolutionApplication Insights is the APM lens built specifically for your app's own code — request rates, dependency calls, exceptions, traces — and its telemetry lands in that same Log Analytics workspace Azure Monitor already uses.
RecallApp Insights = Azure Monitor's own lens, aimed at your app's code.
🔥 Easy interview recall

App Insights = "Azure Monitor's lens, aimed at your app's own code."

Think: Azure Monitor → the whole platform. Application Insights → your app's own view inside that same platform.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Application Insights is a totally separate product from Azure Monitor." It isn't — it's specifically the application-level lens on top of the same underlying platform, and its telemetry lands in the same Log Analytics workspace Azure Monitor already uses.

🔄 Likely Follow-up

"When would you pick a log alert over a metric alert?" When the condition needs to correlate multiple fields or apply real query logic that a raw numeric threshold can't express.

🎯 Say this in the interview — the exact lines to land

"Application Insights is the application-level lens on top of Azure Monitor's platform, not a separate product — its telemetry lands in the same Log Analytics workspace Azure Monitor already uses. A metric alert fires fast on a numeric threshold, while a log alert runs a KQL query on a schedule and fires based on the result, so it's slower but far more flexible."

  • Azure Monitor → the umbrella platform for all monitoring data across Azure.
  • Application Insights → the APM lens for your app's code, feeding that same platform.
  • Metric alert → fast, near real-time — a numeric value crossing a threshold.
  • Log alert → flexible, on a schedule — a KQL query's results decide if it fires.
📖 Explanation ▾

Azure Monitor is the platform-wide service that collects and stores monitoring data across an entire Azure environment — platform metrics, activity logs, resource health, and alert rules, all in one place. Application Insights is the application performance monitoring (APM) piece built specifically for your own code: request rates, dependency calls, exceptions, and traces from inside your app. It isn't a separate system sitting next to Azure Monitor — its telemetry is stored in a Log Analytics workspace, the same kind of store Azure Monitor already queries, so the two share one underlying platform instead of competing.

Alerts sit on top of that same data, in two different shapes. A metric alert watches a single numeric time-series value against a threshold — fast, close to real-time, good for something like "CPU over 90%." A log alert runs a KQL query on a fixed schedule and fires based on whatever that query's results look like — slower, because it waits for the next run, but able to express conditions a plain number never could, like "more than 5 failed logins from the same IP in 10 minutes."

💻 See the code ▾
KQL 
SigninLogs
| where ResultType != 0                    // ❌ failed sign-ins only
| summarize FailCount = count() by IPAddress
| where FailCount > 5                     // fires the log alert

A metric alert can't express "more than 5 failed logins from one IP" — that needs a real query, which is exactly what a log alert runs on its schedule.

🧭 Use Cases — recognize these when they happen to you ▾
1 Response time creeps up and you need to know within minutes

This is the #1 scenario you'll actually run into: a single numeric value crosses a threshold, so a metric alert fires near real-time — exactly the "CPU > 90%" shape a metric alert is good for.

RememberOne number, one comparison, fast — that's a metric alert.
2 You need to catch a pattern across many events, like 5+ failed logins from one IP

A raw number can't express "count failed logins, grouped by IP, over 5" — that needs a real KQL query, so a log alert runs it on a schedule and fires on the result, slower but far more flexible.

RememberCorrelating fields or counting a pattern → a log alert, not a metric alert.
3 You assume Application Insights runs on a separate system from the rest of Azure Monitor

Candidates often assume Application Insights is a competing product sitting next to Azure Monitor, but it isn't — it's specifically the application-level lens on the same platform, and its telemetry lands in the same Log Analytics workspace Azure Monitor already uses.

RememberSame platform, same workspace — App Insights is a lens, not a separate product.
🌍 Real-world example ▾

A team sets a metric alert on "response time > 2s" so they hear about a slowdown within minutes. Alongside it, they run a log alert with a KQL query looking for an unusual pattern of 403s from the same client — something a threshold alone could never express, because it needs real query logic, not just a number.
