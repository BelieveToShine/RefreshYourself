Window functions — see the other rows without collapsing them

"What are window functions, and how are they different from GROUP BY?"

Why it matters ▾
🪟 Window Functions
❗ ProblemReal reporting constantly needs a per-row calculation — a running total, a rank, a "top N per group" — but GROUP BY can't give you that: it collapses matching rows down to one row per group, so the per-row detail is gone.
✅ SolutionA window function calculates across a set of related rows — the window, defined by OVER(...) — without collapsing them, so every row survives with one extra calculated column, completely independent of GROUP BY.
RecallWindow function = calculate across related rows, but keep every row.
🔥 Easy interview recall

Window function = "calculate across related rows, but keep every row."

Think: GROUP BY collapses rows down to one row per group. A window function keeps every row and just adds a column.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Window functions need GROUP BY to work." They don't — a window function uses its own OVER(...) clause (with PARTITION BY / ORDER BY inside it) completely independently of GROUP BY; you can use one, the other, or both together for different purposes in the same query.

🔄 Likely Follow-up

"What does PARTITION BY do inside OVER()?" It resets the window per group, like a GROUP BY just for the window function alone — e.g. SUM(Amount) OVER (PARTITION BY CustomerId) gives each row that customer's own running total without collapsing any rows.

🎯 Say this in the interview — the exact lines to land

"A window function calculates across a set of related rows — the window, defined by OVER(...) — without collapsing them, so every row survives in the output with one extra calculated column. GROUP BY collapses matching rows into a single row per group; a window function never does that, and PARTITION BY inside OVER() resets its window per group completely independently of any GROUP BY in the query."

  • OVER(...) → defines the window — the rows a calculation looks across, without collapsing anything.
  • PARTITION BY → resets the window per group, like a GROUP BY just for the window function.
  • Doesn't need GROUP BY → OVER() is fully independent — use one, the other, or both.
  • Row count → never shrinks — every original row stays, just with a new column.
📖 Explanation ▾

A window function calculates something across a set of related rows — the "window," defined by an OVER(...) clause — without collapsing those rows. Every original row survives in the output; each one just gains an extra calculated column holding the result of that calculation over its own window.

PARTITION BY inside OVER() resets the window per group, the same idea as a GROUP BY but scoped only to the window function itself — and it's a completely separate mechanism, independent of any actual GROUP BY clause in the query. You can write PARTITION BY without ever writing GROUP BY at all.

💻 See the code ▾
SQL 
SELECT OrderId, CustomerId, Amount,
       SUM(Amount) OVER (PARTITION BY CustomerId) AS CustomerTotal
FROM Orders;                       -- ✅ every order row is still here

Every original order row is still present — each one now also shows its own customer's running total.

SQL 
SELECT OrderDate, Amount,
       SUM(Amount) OVER (ORDER BY OrderDate) AS RunningTotal
FROM Orders;                       -- ✅ each row adds itself to the running total

No PARTITION BY needed here — ORDER BY inside OVER() is enough to build a running total across all rows.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need every customer's own running total, without losing a single order row

Each row keeps its place, but also picks up its own customer's total — OVER (PARTITION BY CustomerId) resets the window per customer, the same way GROUP BY would, except no row ever disappears. This is the #1 scenario you'll actually run into.

RememberPer-group total, every row kept → PARTITION BY.
2 You need a running total that grows row by row, in date order

No PARTITION BY at all here — ORDER BY inside OVER() is enough on its own to build a running total across every row, one order at a time.

RememberORDER BY alone in OVER() → running total, no partitions needed.
3 You need to rank every row without hiding anyone — a leaderboard

A leaderboard shows every player's own row plus their rank — nobody is hidden or collapsed into a group total. A plain GROUP BY could only give you totals per group, with no individual rows left to look at.

RememberRank everyone, hide no one → a window function, not GROUP BY.
🌍 Real-world example ▾

A leaderboard. It shows every player's own row plus their rank, without hiding anyone — that's a window function. A plain GROUP BY would leave you with just totals per group, with no individual rows left to look at.
