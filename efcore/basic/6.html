.Select() into a DTO — why pull 15 columns when the screen needs 3?

"What is projection — selecting into a DTO — and why does it help query performance?"

Why it matters ▾
📦 Projection
❗ ProblemPulling every column of a full entity — when a list screen or API response only needs a handful of fields — wastes bandwidth and memory on data nobody asked for.
✅ Solution.Select() into exactly the shape you need — a DTO or anonymous type — so EF Core's query translator only pulls those columns from the database.
RecallProjection = ask the database for only the columns you actually need.
🔥 Easy interview recall

Projection = "asking the database for only the columns you actually need."

Think: .Select() shrinks the SQL column list — and the result is never tracked.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling .Select() after .ToList() is not the same optimization. By the time .ToList() runs, EF Core has already pulled every mapped column into memory and tracked it — the later .Select() only reshapes data that was already fully loaded.

🔄 Likely Follow-up

"What's the actual SQL difference between selecting the full entity vs. projecting into a DTO that only needs 3 of its 15 mapped columns?" Selecting the full entity generates a SELECT listing all 15 mapped columns; projecting generates a SELECT listing only the 3 referenced columns.

🎯 Say this in the interview — the exact lines to land

"Projection means using .Select() to shape the query into exactly what I need — usually a DTO — instead of pulling the full entity. EF Core translates that into a SQL SELECT that only lists the columns I asked for, and the projected result isn't tracked, so there's no change-tracking overhead either."

  • .Select() inside the query → SQL only lists the columns you asked for, not every mapped column.
  • Projected results → never registered with the change tracker — no snapshot, no overhead.
  • .ToList() then .Select() → defeats the point — the full entity was already pulled from the database.
  • Reach for projection whenever a screen or API response needs only a few fields, not the whole entity.
📖 Explanation ▾

Projection means shaping a query's result into exactly what you need — usually a DTO — instead of asking EF Core for the whole entity. Call .Select() as part of the query itself, before anything runs against the database, and EF Core's query translator builds the SQL around that shape: the SELECT clause only lists the columns your DTO actually references, not every column mapped on the entity.

That's also why a projected result skips the change tracker entirely. EF Core only snapshots what it materializes as a tracked entity — a projected DTO was never materialized as one, so there's nothing to snapshot and nothing to compare on the next SaveChanges(). (The Tracking vs. AsNoTracking() page covers the tracker's snapshotting cost in more depth — projection sidesteps that cost by construction, the same way AsNoTracking() does explicitly.)

The two paths produce genuinely different SQL and different runtime behavior:

Full entityProjected DTO
SQL SELECT listevery mapped column✅ only the columns referenced
Change tracked?✅ yes — snapshotted❌ no — read-only result
Best used foryou plan to modify it and call SaveChanges()read-only views, API responses, lists, reports
Risk if projected too late—calling .Select() after .ToList() loses the saving entirely
💻 See the code ▾
C# 
List<Product> products = db.Products.ToList();
// no .Select() — full entity, every column comes back
// SQL: SELECT Id, Name, Price, Sku, Description, ... (all 15 columns)

Every mapped column comes back, and each row is registered with the change tracker.

C# 
var products = db.Products
    .Select(p => new ProductDto
    {
        Id = p.Id,
        Name = p.Name,
        Price = p.Price
    })
    .ToList();   // ✅ SQL: SELECT Id, Name, Price only

The projection happens inside the query — EF Core never asks the database for the other 12 columns, and the result isn't tracked.

C# 
var products = db.Products.ToList();
// ❌ all 15 columns already pulled + tracked, right here

var dtos = products.Select(p => new ProductDto
{
    Id = p.Id, Name = p.Name, Price = p.Price
});
// too late — this runs in memory, not against the database

.Select() here runs on an in-memory List<Product>, not the database query — nothing about what was fetched changes.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your list screen or API response only needs a few fields

This is the #1 scenario you'll actually run into: a grid or API response that only displays a name, price, and SKU. .Select() into a DTO here, and EF Core's SQL only lists those three columns.

RememberList/API screen needing a few fields → project into a DTO.
2 You're about to modify the entity and call SaveChanges()

Here you need change tracking, so pull the full entity instead — a projected DTO is never registered with the change tracker, so there'd be nothing to snapshot or save.

RememberPlanning to modify + save → skip projection, keep the full entity.
3 You call .Select() right after .ToList()

By the time .ToList() ran, every mapped column was already pulled from the database and tracked — the later .Select() only reshapes data that was already fully loaded. A common interview trap — it looks like the same optimization, but the database work is already done.

Remember.Select() after .ToList() → too late, full entity already loaded.
🌍 Real-world example ▾

You need a customer's name and email for a mailing list. Pulling the full entity is like requesting their entire file — address, order history, payment details — just to copy two lines onto a sticky note. Projection is asking for the sticky note directly: the database only hands over the fields the mailing list actually needs.
