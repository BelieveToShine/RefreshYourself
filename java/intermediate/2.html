ArrayList vs. LinkedList — an array that grows, or a chain that links

"When would you actually choose LinkedList over ArrayList?"

Why it matters ▾
📐 ArrayList
❗ ProblemGrowing a plain array means copying the whole thing every time it's full — manual resizing is error-prone and tedious to hand-write for every list operation.
✅ SolutionArrayList wraps a resizable array and grows it automatically — you get O(1) indexed access and amortized O(1) appends with zero manual resizing code.
RecallArrayList = resizable array, O(1) get().
🔗 LinkedList
❗ ProblemInserting or removing at the front of a plain array means shifting every other element down one slot — expensive for a list that grows or shrinks at the ends often.
✅ SolutionLinkedList is a doubly-linked chain of nodes — adding or removing at either end just relinks two pointers, O(1), with no shifting at all.
RecallLinkedList = linked nodes, O(1) at the ends.
🔥 Easy interview recall

ArrayList → array, O(1) get/set

LinkedList → nodes, O(1) at either end

Think: get(i) → ArrayList O(1), LinkedList O(n) (must walk) add(middleIndex, x) → O(n) on both — ArrayList usually still wins (cache locality)

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"LinkedList is faster for insertion" is only true at a known node reference (via an Iterator/ListIterator) — list.add(middleIndex, x) still has to walk to that index first, so it's O(n) either way, and ArrayList is usually faster in practice thanks to cache locality.

🔄 Likely Follow-up

"Why is ArrayList usually faster even when the Big-O ties?" Cache locality — contiguous array elements sit next to each other in memory, so the CPU cache serves sequential access far faster than chasing scattered pointers across LinkedList nodes.

🎯 Say this in the interview — the exact lines to land

"ArrayList is backed by a resizable array — O(1) indexed access, but inserting or removing in the middle shifts elements, O(n). LinkedList is a doubly-linked list — O(1) insert/remove at either end, but O(n) to reach an index because it has to walk the chain."

  • ArrayList → fast random access, amortized O(1) append.
  • LinkedList → fast insert/remove at the ends, O(n) to reach an index.
  • list.add(middleIndex, x) → O(n) on both — ArrayList usually wins anyway.
  • Reach for LinkedList only when inserting at a known node via an iterator, not by index.
📖 Explanation ▾

ArrayList is a parking lot with numbered spaces — the backing array holds every element contiguously in memory, so jumping straight to index 500 is one calculation, O(1). When it fills up, it allocates a bigger array behind the scenes and copies everything over — that copy is occasional and amortizes out, so appends stay effectively O(1) on average.

LinkedList is a treasure hunt — each node only knows its own value plus pointers to the node before and after it. Adding a node at the front or back means creating one node and relinking two pointers, O(1), no copying. But there's no shortcut to "the 500th node" — you have to walk the chain from one end, node by node, which is O(n).

The one case LinkedList genuinely wins is removing or inserting at a position you're already standing on — a ListIterator mid-traversal. Reaching that position by index first erases the advantage, since the walk to get there is already O(n).

💻 See the code ▾
☕ Java 
List<String> arr = new ArrayList<>(List.of("A","B","C"));
arr.get(1);                 // ✅ O(1) — direct array index

List<String> linked = new LinkedList<>(List.of("A","B","C"));
linked.get(1);              // ❌ O(n) — must walk from head or tail

Same call, same result — but LinkedList.get() is walking a chain, not indexing an array.

☕ Java 
ListIterator<String> it = linked.listIterator();
while (it.hasNext()) {
    if (it.next().equals("B")) {
        it.add("B2");     // ✅ O(1) — splices right here, no walk needed
    }
}

LinkedList only wins when you're already standing on the node — not when you look it up by index.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're binary-searching a sorted list of records, checking indexes repeatedly

Binary search repeatedly jumps to get(mid) — each jump is O(1) on an ArrayList but O(n) on a LinkedList, which would turn an O(log n) algorithm into something far slower.

RememberRepeated index access → reach for ArrayList.
2 You're building an undo/redo stack, adding and removing at both ends constantly

Pushing and popping from both ends is exactly LinkedList's (or Deque's) strength — O(1) at either end with no shifting, where an array-backed list pays an O(n) shift every time something leaves the front.

RememberConstant both-ends churn → reach for LinkedList/Deque.
3 You call list.add(middleIndex, x) in a loop and expect LinkedList to win

LinkedList.add(index, x) has to walk from an end to that index before it can splice — it's still O(n), and ArrayList is typically faster for the same call thanks to cache locality.

RememberIndex-based insert → no free win for LinkedList.
🌍 Real-world example ▾

ArrayList is a parking lot with numbered spaces — jump straight to any spot. LinkedList is a treasure hunt — each clue only tells you where the next one is, so reaching clue 500 means reading all 499 before it.
