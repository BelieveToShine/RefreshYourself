CTEs — naming a subquery so you can read your own SQL

"What is a CTE (Common Table Expression), and why use one over a subquery?"

Why it matters ▾
🏷️ CTE
❗ ProblemOnce a query nests two or three subqueries deep, it's hard to tell which SELECT owns what — you end up reading from the innermost layer outward just to follow the logic.
✅ SolutionWITH name AS (...) names that subquery once, up top, so everything below can reference it by name and the whole query reads top-to-bottom instead of inside-out.
RecallCTE = naming a subquery once so the query reads top-to-bottom — not an automatic speed boost.
🔥 Easy interview recall

CTE = "naming a subquery so you can read it top-to-bottom instead of nesting."

Think: WITH RecentOrders AS (...) reads like a named step, not a deeply indented block.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"A CTE is automatically faster than the equivalent subquery." A standard, non-recursive CTE is mainly a readability tool — most optimizers treat it similarly to an equivalent subquery under the hood, so reach for it for clarity, and reach for a recursive CTE specifically when you need to walk a hierarchy.

🔄 Likely Follow-up

"Can a CTE reference itself?" Yes — a recursive CTE (self-referencing via a UNION with itself) can walk a hierarchy, like an org chart or a category tree, which is a genuinely different capability from a plain subquery.

📖 Explanation ▾

A CTE (Common Table Expression) is a subquery you name up front with WITH name AS (...), then reference by that name anywhere later in the same statement — as if it were a real table. Instead of nesting one SELECT inside another inside another, each step gets its own name and the query reads top-to-bottom.

A standard, non-recursive CTE is mainly a structuring tool. Most query optimizers translate it into a plan similar to the equivalent subquery, so naming it doesn't buy speed by itself — the win is that the next person reading the query (including future you) doesn't have to unwind several layers of indentation to see what it does.

A recursive CTE is a genuinely different tool. It references itself: one part picks a starting point (the anchor), and a second part joins back to the CTE's own name, repeating until nothing new is found. That's how a flat Employees table with a ManagerId column turns into a full reporting chain, top to bottom, in one query — something a plain subquery can't easily do.

💻 See the code ▾
SQL 
WITH RecentOrders AS (
    SELECT * FROM Orders WHERE OrderDate > '2024-01-01'
)
SELECT CustomerId, COUNT(*)
FROM RecentOrders
GROUP BY CustomerId;  -- ✅ RecentOrders is named once, read like a table below

One named step instead of a query nested inside another — the GROUP BY at the bottom reads against RecentOrders directly, no unwinding required.

SQL 
WITH OrgChart AS (
    -- anchor: the top of the hierarchy
    SELECT Id, ManagerId, Name FROM Employees WHERE ManagerId IS NULL
    UNION ALL
    -- recursive: joins back to OrgChart itself
    SELECT e.Id, e.ManagerId, e.Name
    FROM Employees e
    JOIN OrgChart o ON e.ManagerId = o.Id
)
SELECT * FROM OrgChart;  -- ✅ walks the whole reporting chain, one query

This is the one thing a plain subquery can't easily do — OrgChart refers back to itself to walk down the management chain.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your query has grown two or three layers of nested subqueries

Every extra layer needs unwinding just to see which SELECT feeds which. Naming the innermost piece as a CTE turns it into one readable step instead of a nested block. This is the #1 reason most people reach for a CTE.

RememberNested layers piling up → name the subquery with a CTE.
2 You reach for a CTE expecting it to run faster than the subquery it replaced

A standard, non-recursive CTE is a readability tool — most optimizers turn it into a plan similar to the equivalent subquery, so naming it doesn't buy speed by itself.

RememberStandard CTE → clarity, not an automatic performance win.
3 You need to walk a self-referencing hierarchy, like an org chart or category tree

A recursive CTE references itself: an anchor picks the starting row, then a recursive part joins back to the CTE's own name, repeating until nothing new is found — something a plain subquery can't easily do.

RememberHierarchy to walk → recursive CTE, not a plain subquery.
🌍 Real-world example ▾

A CTE is like naming a complicated calculation "Step 1" in a spreadsheet so every later formula can just say "Step 1" instead of repeating the whole formula every time. It doesn't make the calculation run faster on its own — it just means nobody has to re-read the whole formula to know what a later cell depends on.
