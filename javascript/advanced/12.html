Proxy — who's actually listening when your code reads or writes a property?

"What is a JavaScript Proxy, and how would you use it to intercept reading or writing a property?"

Why it matters ▾
  • This is a Deep Dive topic, not core interview prep — useful for understanding how frameworks build reactivity, not something you're likely to be asked to implement live on a whiteboard.
  • Recognizing Proxy as the mechanism behind modern reactivity (Vue 3's reactivity system is the well-known example) is the actual signal an interviewer wants, not a recital of every trap type.
  • Most engineers meet it by reading framework internals or a library's source, not by writing it themselves day-to-day.
🔥 Easy interview recall

Proxy → wraps a target object, intercepts operations on it

Reflect → default behavior — called from inside a trap to finish the job

Think: a Proxy is a gatekeeper in front of an object — a get/set trap runs your code first; Reflect does what would've happened anyway.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A set trap that never calls Reflect.set() (or target[key] = value) doesn't just skip validation — it silently drops the write entirely. The property never actually changes, and nothing throws to tell you why.

🔄 Likely Follow-up

"How is this different from what Vue 2 used — Object.defineProperty?" Object.defineProperty defines a getter/setter on one property you name ahead of time; a Proxy intercepts operations on the object as a whole, including ones on keys that don't exist yet — which is part of why Vue 3 moved to Proxy for its reactivity system instead.

🎯 Say this in the interview — the exact lines to land

"A Proxy wraps a target object and lets you define custom behavior — traps — for fundamental operations like reading or writing a property: a get trap runs on read, a set trap runs on write. Reflect gives you the matching default implementation of each operation, so a trap can run its own logic and still forward to the normal behavior. This is the mechanism modern reactive frameworks, like Vue 3, use to know exactly when a piece of state changed and trigger a re-render."

  • get trap → runs on every property read — can log, compute, or restrict access.
  • set trap → runs on every property write — the point where you can act before the value lands.
  • Validation → a set trap can throw before an invalid write is stored, e.g. a wrong type.
  • Reactive systems → a set trap is how a framework knows exactly which state changed, so it only re-renders what needs it.
  • Reflect → the default behavior, called from inside a trap to actually finish the operation.
  • Metaprogramming → code that intercepts other code's behavior, not just plain data — Proxy is JavaScript's main tool for it.
📖 Explanation ▾

A Proxy wraps a target object and lets you supply traps — functions that run instead of the default behavior for a fundamental operation on that object. The two that matter most: a get trap fires whenever a property is read, and a set trap fires whenever one is written. Everywhere else in the app, code just uses the proxy like a normal object — it has no idea anything is being intercepted.

Reflect is the companion tool: it exposes the same fundamental operations (Reflect.get, Reflect.set, …) as plain functions, so a trap can run its own logic first and then call Reflect to actually carry out the normal read or write. A set trap can also reject a write outright — e.g. throwing if a value doesn't match the expected type — which is how Proxy gets used for validation.

The practical payoff worth remembering is reactivity: a UI framework can put an app's state behind a Proxy and use its set trap to detect the exact moment a piece of state changes, then schedule a re-render — without the app code ever calling something like setState() itself. This is, in general shape, how Vue 3's reactivity system works under the hood. Writing code that intercepts or modifies the behavior of other code like this — rather than just operating on plain data — is called metaprogramming, and Proxy is JavaScript's main built-in tool for it.

💻 See the code ▾
JavaScript 
const user = { age: 30 };

const proxy = new Proxy(user, {
  get(target, prop) {
    return Reflect.get(target, prop); // ✅ read forwarded as normal
  },
  set(target, prop, value) {
    if (prop === "age" && typeof value !== "number") {
      throw new TypeError("age must be a number"); // ❌ rejected before it's stored
    }
    return Reflect.set(target, prop, value); // ✅ actually writes the value
  }
});

proxy.age = "old"; // throws — never reaches `user`

The set trap decides whether the write even reaches user — Reflect.set is what makes it actually happen.

JavaScript 
function reactive(target, onChange) {
  return new Proxy(target, {
    set(obj, key, value) {
      const changed = obj[key] !== value;
      const ok = Reflect.set(obj, key, value); // real write still happens
      if (changed) onChange(key, value); // 🔔 the reactivity hook
      return ok;
    }
  });
}

const state = reactive({ count: 0 }, () => rerender());
state.count++; // rerender() fires automatically — no manual "update" call anywhere

This is the general shape of the trick, not a real framework's actual implementation — the interesting part is that a plain state.count++ is enough to trigger rerender() on its own.

🌍 Real-world example ▾

A UI framework needs to know the instant state.user.name changes, without the app calling something like setState() itself. Wrapping the state object in a Proxy and reacting inside its set trap is exactly how that gets solved — every plain assignment the app already writes becomes the framework's signal to schedule a re-render.
