Managed vs. self-hosted serving — who's holding the pager when a GPU runs out of memory?

Once you've picked an open-weight model, do you call a managed endpoint or run it yourself with something like vLLM or Ollama — and what are you actually signing up for either way?

Why it matters ▾
  • This is a different decision than "Model Families" (closed API vs. open-weight model choice) — this page is what happens after you've already decided to run a model yourself: how it actually gets served.
  • Comes up any time a team has open-weight model access and now has to decide who owns the GPUs, the inference server, and uptime.
  • A common way senior/architect interviews probe real infrastructure judgment: "you have the weights — now what?"
🔥 Easy interview recall

Managed / API → provider owns everything below the call

Self-hosted → you own the GPUs, the server, the uptime

Think: managed trades control for zero operational effort. self-hosted trades operational effort for control and better cost at scale.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

vLLM/TGI and Ollama are not interchangeable. vLLM and TGI are production-grade inference servers built for high-throughput serving (continuous batching); Ollama is a much lighter tool for local development and small-scale self-hosting, not typically the choice for real production traffic.

🔄 Likely Follow-up

"Why not just always self-host to save money?" Because self-hosting only pays off once you have the GPU scale and the operational expertise to run it cheaper than pay-per-token — below that scale, a managed endpoint is usually both cheaper and far simpler.

🎯 Say this in the interview — the exact lines to land

"Once I've chosen an open-weight model, the next decision is who serves it — a managed endpoint means the provider owns the GPUs, the scaling, and the inference server software; self-hosting with something like vLLM or TGI means I own all of that myself, in exchange for more control and better cost at real scale."

  • Managed → use when you want zero operational effort and never need to touch GPU sizing or the inference server.
  • Self-hosted (vLLM/TGI) → use when you need production throughput, control, and cost at scale, and can own scaling and uptime yourself.
  • Ollama → good for local development and small-scale experimentation, not the usual pick for high-throughput production.
  • Quantization (GGUF, AWQ) → the GPU-memory tradeoffs you own once you self-host — a managed API hides all of that.
  • Continuous batching → the technique vLLM/TGI use to serve many requests' generation steps together, instead of one request at a time.
📖 Explanation ▾

Managed/API serving means a provider runs the model for you — whether that's a fully closed model's own API, or a managed endpoint sitting in front of an open-weight model. Either way, you never touch GPUs, scaling, or the inference server software; it's the least operational effort, at the cost of ongoing dependency on that provider's availability and pricing. Self-hosted serving means you run an open-weight model yourself, on your own (or rented) GPUs — full control over data residency, customization, and cost structure at scale, but you own the operational burden: sizing GPUs, running the inference server, scaling it, and keeping it up. Note this is a different axis than the earlier Model Families page — that page was about which model to use (closed vs. open-weight); this one is about who runs it once an open-weight model is already chosen.

vLLM and TGI (Text Generation Inference) are production-grade inference server software built specifically to serve LLMs efficiently — the kind of software a team runs itself when self-hosting at real scale. A key technique behind that efficiency is continuous batching: serving multiple requests' generation steps together efficiently, rather than handling one request fully before starting the next. Ollama is a much simpler, lighter-weight way to run open-weight models locally or on a single machine — good for development and experimentation, not typically the choice for high-throughput production serving.

Self-hosting is also exactly where quantization formats like GGUF and AWQ matter — they shrink a model's memory footprint so it fits on the GPUs you actually have. A managed API abstracts all of that away entirely; you never see it. The real decision axis is how much operational effort you're willing to own, weighed against cost at scale, data residency needs, and customization needs — the same tradeoff shape as Model Families, just one layer down, at serving instead of model choice.

💻 See the code ▾
Pseudocode 
# managed: you never touch a GPU or a server process
response = client.chat.completions.create(
    model="some-managed-endpoint",
    messages=[{"role": "user", "content": prompt}]
)  # ✅ one HTTP call — that's the entire operational surface

Nothing here configures a GPU, a batching strategy, or an uptime target — that's the whole point of managed serving.

Pseudocode 
# self-hosted: you stand up the inference server yourself
$ vllm serve meta-llama/Llama-3-8B --port 8000   # production: continuous batching built in
$ ollama run llama3                              # local/dev: one command, one machine

vLLM/TGI are what a team runs for real production throughput; Ollama is the quick local path — not usually the production choice.

🌍 Real-world example ▾

Managed serving is like renting a fully-serviced apartment — someone else fixes the plumbing and you just pay rent. Self-hosting is owning a house — more control over what you do with it, but you're the one calling the plumber at 2 AM.

Scenario: your team already fine-tuned a small open-weight model on internal data, but a compliance requirement says that data can never leave your own network — that's a clean case for self-hosting; no managed endpoint clears that bar, no matter how good its pricing looks.
