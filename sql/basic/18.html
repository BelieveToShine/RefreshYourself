Constraints — the database says no, even when the app forgot to

"Which constraints exist beyond PK/FK, and PRIMARY KEY vs. UNIQUE?"

Why it matters ▾
🚫 NOT NULL
❗ ProblemA required column can end up empty.
✅ SolutionNOT NULL rejects a row that leaves it NULL.
RecallNOT NULL = a value must exist.
🔑 UNIQUE
❗ ProblemTwo rows can share a value that should be one of a kind, like an email.
✅ SolutionUNIQUE rejects the duplicate.
RecallUNIQUE = no two rows share it.
📏 CHECK
❗ ProblemNonsense values, like a negative age, slip in.
✅ SolutionCHECK rejects a row when its rule is false.
RecallCHECK = a rule every row must pass.
✏️ DEFAULT
❗ ProblemCallers forget optional columns and leave gaps.
✅ SolutionDEFAULT fills a value when the INSERT leaves the column out.
RecallDEFAULT = fills a blank, never rejects.
🔥 Easy interview recall

NOT NULL → a value is required

UNIQUE → no duplicates

CHECK → value must pass a rule

DEFAULT → fills a missing value

Think: PRIMARY KEY = UNIQUE + NOT NULL, once per table.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"CHECK (Age >= 18) guarantees every age is at least 18." A NULL age passes — CHECK only rejects a row when the rule is false, not when it is unknown — so pair it with NOT NULL.

🔄 Likely Follow-up

"PRIMARY KEY vs. UNIQUE — what is the difference?" A table has one primary key and it never allows NULL; it can have many UNIQUE constraints, and in SQL Server a unique column allows a single NULL. By default the primary key also gets the clustered index.

🎯 Say this in the interview — the exact lines to land

"Beyond primary and foreign keys, NOT NULL requires a value, UNIQUE blocks duplicates, CHECK enforces a rule, and DEFAULT fills in a missing value. A primary key is UNIQUE plus NOT NULL, once per table."

  • NOT NULL → the column must always have a value.
  • UNIQUE → many per table; SQL Server allows one NULL in the column.
  • CHECK → rejects a row only when the rule is false; NULL passes.
  • DEFAULT → used only when the column is left out of the INSERT.
  • PRIMARY KEY → UNIQUE plus NOT NULL; only one per table.
  • Last line of defence → application checks can be bypassed; constraints cannot.
📖 Explanation ▾

Each constraint guards one thing. NOT NULL forces a value, UNIQUE blocks repeats, CHECK tests a rule on each row, and DEFAULT supplies a value when the INSERT omits the column. Passing an explicit NULL to a nullable column with a default stores the NULL; the default is not used.

Where they sit matters. Application validation can be skipped by another service, a script or a hand-run query, but a constraint runs on every write. That is why the database is the last line of defence.

💻 See the code ▾
T-SQL 
CREATE TABLE Employees (
    Id     INT IDENTITY(1,1) PRIMARY KEY,                       -- UNIQUE + NOT NULL
    Email  NVARCHAR(100) NOT NULL UNIQUE,                       -- required, no repeats
    Age    INT NULL CONSTRAINT CK_Employees_Age CHECK (Age >= 18),  -- rule
    Status NVARCHAR(20) NOT NULL DEFAULT 'Active'               -- filled if omitted
);

One table using all four constraints plus the primary key.

T-SQL 
INSERT INTO Employees (Email, Age) VALUES ('a@x.com', 30);   -- ✅ Status becomes 'Active'
INSERT INTO Employees (Email, Age) VALUES ('a@x.com', 31);   -- ❌ UNIQUE: duplicate Email
INSERT INTO Employees (Email, Age) VALUES ('b@x.com', 15);   -- ❌ CHECK: Age >= 18 fails
INSERT INTO Employees (Email, Age) VALUES (NULL, 40);        -- ❌ NOT NULL: Email required

Each bad insert fails on a different constraint, and the good one gets its default.

🌍 Real-world example ▾

Think of a club door. The guard checks you showed ID (NOT NULL), you are not already inside (UNIQUE), you are over 18 (CHECK), and gives you a wristband if you did not bring one (DEFAULT).
