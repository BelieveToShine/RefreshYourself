Model Binding — the framework fills it in. Does it check it too?

What is model binding, and how does validation actually get triggered?

Why it matters ▾
  • Comes up the moment an action takes any input — every create/update endpoint depends on this working correctly.
  • The [ApiController] auto-400 behavior is a favorite follow-up — a lot of candidates don't realize it's the attribute doing that, not ASP.NET Core in general.
  • Sets up the deeper Advanced topic on binder source order and custom binders — this page is the practical foundation that one builds on.
🔥 Easy interview recall

Model binding = "the framework fills in your action's parameters for you."

Think: Route, Query, Body, Headers → the Model Binder fills the parameter Validation runs by itself — but ModelState.IsValid only helps if you actually check it

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Binding automatically rejects invalid data. It doesn't — the object still gets populated and its validation attributes still run either way; only checking ModelState.IsValid yourself (or letting [ApiController] do it for you) actually stops an invalid object from reaching your code.

🔄 Likely Follow-up

"If a query string, a route value, AND the request body all supply a value for the same parameter name, which one wins?" There's a defined default source-precedence order — see Model Binding Internals for the exact ordering, since that's where the full priority list belongs.

🎯 Say this in the interview — the exact lines to land

"Model binding automatically populates an action's parameters — a simple type or a whole class — from the route, the query string, the body, or headers. Data-annotation attributes like [Required] run automatically as part of that same step, but only checking ModelState.IsValid actually stops invalid data from reaching your code."

  • CreateOrder(OrderDto order) → the binder reads route, query, body, and headers and fills the object in for you.
  • [Required], [Range], etc. → checked automatically, with the result recorded in ModelState.
  • Forget to check it → invalid data still reaches your business logic in a classic controller.
  • [ApiController] → auto-returns 400 on invalid ModelState; plain controllers don't get that for free.
📖 Explanation ▾

Model binding is the step where a raw HTTP request turns into ordinary C# parameters. Before your action code runs, the framework reads the route values, the query string, the request body, and headers, matches them up by name against your action's parameters, and hands them over already assembled — that's why CreateOrder(OrderDto order) can just take a fully-formed OrderDto instead of anyone hand-parsing Request.Body.

Validation piggybacks on that same step. Any data-annotation attribute on the model — [Required], [StringLength], [Range] — gets checked the moment binding finishes, and the outcome is recorded in ModelState. ModelState.IsValid is just a yes/no summary of what was already recorded — it doesn't do any checking itself, it only reports what the checking already found.

What happens to an invalid object depends entirely on whether anyone reads that summary. A classic MVC controller never reads it for you — the object still reaches your action, valid or not, unless you check ModelState.IsValid yourself. [ApiController] changes that default: it reads ModelState before your action runs and returns a 400 automatically when it's invalid, which is why Web API controllers built with [ApiController] almost never need the manual check.

💻 See the code ▾
C# 
[HttpPost("orders")]
public IActionResult CreateOrder(OrderDto order)
{
    // order.Name, order.Total are already populated
    // from the JSON body — nobody parsed Request.Body
    _orders.Save(order);
    return Ok();
}

The binder already matched the JSON body to OrderDto's properties — no manual parsing anywhere.

C# 
public class OrderDto
{
    [Required]
    public string Name { get; set; }

    [Range(1, 100)]
    public int Quantity { get; set; }
}

public IActionResult CreateOrder(OrderDto order)
{
    _orders.Save(order);   // ❌ runs even if order.Name is null
    return Ok();
}

ModelState.IsValid was never checked — an invalid order still reached _orders.Save().

C# 
[ApiController]                 // ✅ auto-checks ModelState
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    [HttpPost]
    public IActionResult CreateOrder(OrderDto order)
    {
        _orders.Save(order);   // only runs if order was valid
        return Ok();
    }
}

[ApiController] returns 400 before this line ever runs — a plain Controller needs the if (!ModelState.IsValid) check written by hand.

🌍 Real-world example ▾

QA reports that empty order names are getting saved to the database, even though OrderDto.Name has [Required] on it. Nine times out of ten the controller is a plain Controller, not one marked [ApiController], and nobody ever added if (!ModelState.IsValid) return BadRequest(); — the validation attribute ran and recorded the failure, but no code ever asked ModelState what it found.
