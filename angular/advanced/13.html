🔥 Must Know

OnPush isn't broken — it's following its own rules, exactly

An OnPush component isn't updating — what's the actual, ordered checklist you go through?

Why it matters ▾
  • "The UI isn't updating" is one of the most common real bugs in an Angular codebase, and almost every case traces back to one of a very small number of causes.
  • Interviewers use this scenario to check whether you actually have a diagnostic process, not just definitions of OnPush and Signals memorized separately.
  • A near-guaranteed follow-up once you name the mutation-in-place cause — see the trap below.
🔥 Easy interview recall

Mutated in place → same reference, OnPush never sees it

Outside Zone.js → nothing told Angular, no trigger fired

Signal never read → not tracked, template missed it

Think: every "why isn't this updating" bug is one of three things — a reference that didn't really change, nothing that told Angular to look, or a Signal() that was never actually read.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Switching a broken OnPush component back to Default is not a fix. It papers over the real bug — almost always a mutation instead of a new reference — so the same mutation resurfaces the next time that same data feeds any other OnPush component.

🔄 Likely Follow-up

"If switching back to Default 'fixes' it, was OnPush actually the problem?" No — Default checks unconditionally on every run, so it happens to paper over the mutation bug by accident; the actual bug (data mutated in place instead of replaced) is still there and will resurface the next time that same data feeds an OnPush component.

🎯 Say this in the interview — the exact lines to land

"I'd check three things, in order: first, whether the bound @Input is getting a genuinely new reference or the same object mutated in place — that's the most common cause by far. Second, whether the update happened through something Zone.js wouldn't have noticed at all, like a raw third-party callback, with no markForCheck() and no Signal involved. Third, if the value is a Signal, whether the template is actually calling it — a Signal read wires up its own update path regardless of the component's change-detection strategy."

  • Mutation instead of a new reference → the #1 cause; this.items.push(x) keeps the same reference, OnPush never sees it.
  • Outside anything Angular watches → a raw callback with no markForCheck() and no Signal never triggers a check, under Default or OnPush.
  • Signal not actually read → the template has to call it (value()), not just hold a reference to the Signal object.
  • Diagnosing a too-frequent render → Angular DevTools Profiler shows exactly what's triggering each check.
  • An inline object literal passed as an @Input → recreated every parent render; stabilize its reference in the parent, not the child.
📖 Explanation ▾

Almost every "change detection isn't doing what I expect" bug reduces to one of three things: a reference that didn't actually change, an update that happened somewhere Angular was never told to watch, or a Signal that was never actually read in the right place. The checklist here is just "which of these three is it" — worked in a sensible order, most common cause first.

Check 1 — reference vs. mutation. OnPush compares the @Input's reference to its last-known one. Mutating the same array or object in place (.push(), .length = 0, setting a nested property) never changes that reference, so the component has no signal anything happened — even though the data itself is genuinely different now.

Check 2 — did anything actually tell Angular? If the update comes from a raw callback that isn't one of Zone.js's patched async APIs — a third-party library calling its own event handlers directly — neither Default nor OnPush would have any reason to run, because nothing scheduled a check at all. The fix is an explicit markForCheck() inside that callback, or converting the state to a Signal.

Check 3 — is the Signal actually read? A Signal's update should work regardless of the component's change-detection strategy, because reading it in a template wires up its own direct notification path. If it's still not updating, confirm the template is actually calling the Signal, not just holding a reference to the Signal object without calling it — and confirm it's the same Signal instance being updated, not a new one the template never switched to.

Diagnosing the opposite problem — a component checked far more often than expected — starts the same way: open the Angular DevTools Profiler and see exactly what's triggering each check. The usual causes are a Default-strategy ancestor sitting in the path of frequent async events, a markForCheck() called inside a tight loop or very frequent event, or an @Input-bound object recreated with a new reference on every parent render (an inline object literal passed as a prop) even though its content barely changes — the fix there is stabilizing that reference in the parent, not changing the child's own strategy.

💻 See the code ▾
TypeScript 
// @Input() items: Item[] — this component is OnPush
this.items.push(newItem);        // ❌ same reference — OnPush sees nothing
this.items = [...this.items, newItem];  // ✅ new reference — OnPush sees it

Check 1 in code — the array's reference is exactly what OnPush compares on an @Input; mutating in place never changes it.

TypeScript 
thirdPartyLib.onUpdate(() => {
  this.value = thirdPartyLib.getValue();
  this.cdr.markForCheck();  // ✅ tell Angular explicitly
});
// thirdPartyLib's own callback runs outside anything Zone.js patched

Check 2 in code — without this explicit call, nothing told Angular the callback even ran, under Default or OnPush.

🌍 Real-world example ▾

A product-list component is OnPush, receiving its products array through an @Input from a parent that fetches and periodically refreshes it. After a refresh, the network tab confirms fresh data arrived, but the list on screen never changes. Investigation shows the parent's refresh logic does this.products.length = 0; this.products.push(...newProducts); — mutating the exact same array reference every time. The fix: change the parent to this.products = newProducts;, a genuinely new reference, which the OnPush child picks up on its very next input-binding check, with nothing else in the codebase touched.
