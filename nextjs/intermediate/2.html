fetch()'s cache options — one function, three caching strategies

"How do fetch()'s cache and revalidate options map onto SSG/SSR/ISR?"

Why it matters ▾
💾 fetch() cache options
❗ ProblemThe Pages Router forced a whole-page, all-or-nothing choice between getStaticProps (built once) and getServerSideProps (built every request) — there was no way to mix freshness strategies within one page.
✅ SolutionA single fetch() call's options decide its own freshness: {cache:'force-cache'} behaves like SSG, {cache:'no-store'} behaves like SSR, and {next:{revalidate:N}} behaves like ISR — per call, not per page.
Recallcache option on the fetch = the freshness strategy for that one call.
🔥 Easy interview recall

force-cache → SSG-like, reused

revalidate: N → ISR-like, refreshed after N sec

no-store → SSR-like, always fresh

Think: Next.js 15 flipped the default — fetch() is now not cached unless you opt in.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A plain fetch() is not automatically cached. That was true in Next.js 14 and earlier — as of Next.js 15, fetch() is uncached by default, so you must opt in with cache: 'force-cache' or next: {revalidate: N} to get the old caching behavior.

🔄 Likely Follow-up

"What's the actual difference between no-store and revalidate: 0?" Both give fresh data on every request in practice, but no-store skips the Data Cache layer entirely, while revalidate: 0 is "cache with a zero-second revalidation window" — same result, different mechanism.

🎯 Say this in the interview — the exact lines to land

"fetch()'s cache and next.revalidate options pick the freshness strategy per call: force-cache behaves like SSG, no-store behaves like SSR, and revalidate: N behaves like ISR. As of Next.js 15, none of that caching happens unless you opt in explicitly."

  • cache: 'force-cache' → SSG-like, reused indefinitely.
  • next: {revalidate: N} → ISR-like, refreshes after N seconds.
  • cache: 'no-store' → SSR-like, always hits the network.
  • Next.js 15 reversed the default — opt-in caching, not opt-out.
📖 Explanation ▾

Every fetch() call inside a Server Component writes into (or reads from) Next.js's own Data Cache, and the cache/next.revalidate options control exactly how. {cache: 'force-cache'} stores the response and keeps reusing it — the same build-once, serve-many idea as static generation. {next: {revalidate: 60}} also stores it, but treats it as stale after 60 seconds and regenerates it in the background — the same idea as Incremental Static Regeneration.

{cache: 'no-store'} skips the Data Cache entirely — every call goes straight to the network, the same always-fresh guarantee Server-Side Rendering used to require a dedicated getServerSideProps function for.

The version detail matters here more than almost anywhere else on this site: in Next.js 14 and earlier, a plain fetch() with no options at all was cached by default. Starting in Next.js 15, that default flipped — a plain fetch() is uncached unless one of these options says otherwise.

💻 See the code ▾
Next.js 
// SSG-like: fetched once, reused on every request
const res = await fetch('https://api.example.com/products', {
  cache: 'force-cache'
});

Same cached response served to every visitor, until the next deploy.

Next.js 
// ISR-like: cached, but refreshed in the background every 60s
const res = await fetch('https://api.example.com/products', {
  next: { revalidate: 60 }
});

Fast cached responses, but never more than 60s stale.

Next.js 
// SSR-like: never cached, always hits the network
const res = await fetch('https://api.example.com/cart', {
  cache: 'no-store'
});   // ✅ fresh on every single request

Right choice for per-user, per-request data like a shopping cart.

🧭 Use Cases — recognize these when they happen to you ▾
1 Marketing/content pages that rarely change

A marketing page or docs page whose content only changes on deploy is the clearest fit for force-cache — every visitor gets the same cached response with no per-request cost.

RememberChanges only on deploy → force-cache.
2 A product catalog that updates periodically, not per-request

A product listing whose prices/stock change every few minutes doesn't need a fresh network call on every page load — revalidate: 300 keeps it fast while still bounding how stale it can ever get.

RememberPeriodic updates → revalidate: N bounds the staleness.
3 You assume a plain fetch() is cached "because Next.js does that"

This was true for Next.js 14 and earlier. In Next.js 15+, the same plain call hits the network every time unless you add cache: 'force-cache' or next.revalidate explicitly — a version-specific reversal, not a one-time fact.

RememberAlways name the version when stating a fetch() caching default.
🌍 Real-world example ▾

A news site's homepage needs to feel current without hammering the CMS on every pageview. next: {revalidate: 60} on the article-list fetch gives every visitor a fast cached response, while guaranteeing the list is never more than a minute old — no manual rebuild, no per-request database hit.
