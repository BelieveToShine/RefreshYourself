Migrations, Mechanically — what dotnet ef actually writes to disk

What does a migration actually produce mechanically — what files does dotnet ef migrations add generate, and what does applying one do?

Why it matters ▾
📝 migrations add
❗ ProblemAfter changing the model at dev time, there's no reviewable record of what changed — without one, nobody can check the change in a pull request before it goes anywhere near a real database.
✅ SolutionIt diffs the current model against ModelSnapshot.cs and writes the result to a new Up()/Down() file pair plus an updated snapshot — a reviewable artifact that never touches a real database.
Recallmigrations add = writes the plan to disk, dev time only, no database touched.
🚀 database update
❗ ProblemThat same reviewed change still has to run safely on dev, staging, and production without re-running something already applied or running blind against a schema someone edited by hand.
✅ SolutionIt (or Database.Migrate()) reads __EFMigrationsHistory in that specific database and runs only the migrations not yet recorded there, at deploy/startup time.
Recalldatabase update = runs only what's missing, checked against history, at deploy time.
🔥 Easy interview recall

migrations add → writes the change to a file

database update → runs it on a real database

Think: one command add writes the plan, the other update carries it out.

⚠️ Common Trap

A manual schema edit doesn't confuse EF Core — it's invisible to it. EF Core only trusts what's recorded in __EFMigrationsHistory, so a column added by hand outside a migration desyncs the real schema from what EF Core believes has run, and the next migration can fail outright or silently miss it.

🔄 Likely Follow-up

"Two developers each add their own migration on separate branches, then merge — what can go wrong?" Both migrations were generated against the same starting snapshot, so the merge can leave conflicting Up() steps or a snapshot file that matches neither branch — usually needs one migration manually resolved or regenerated, a genuinely common pain point on real EF Core teams.

🎯 Say this in the interview — the exact lines to land

"dotnet ef migrations add compares the current model to the last snapshot and writes a new <timestamp>_Name.cs file with Up()/Down() plus an updated snapshot — it never touches a database. dotnet ef database update (or context.Database.Migrate()) is the step that actually runs those changes, using the __EFMigrationsHistory table to skip anything already applied."

  • migrations add → generates files only, no database touched.
  • Produces two files → the <timestamp>_Name.cs pair (Up/Down) plus a .Designer.cs metadata file.
  • Also updates → the model snapshot, so the next diff starts from the new baseline.
  • database update → only runs what's missing from __EFMigrationsHistory.
  • A manual schema edit → is invisible to EF Core and desyncs history from reality.
📖 Explanation ▾

dotnet ef migrations add <Name> is a purely code-time step. It loads the current EF Core model and compares it against the last known model, which EF Core keeps as a serialized C# file — typically <Context>ModelSnapshot.cs. Whatever changed becomes a new migration file pair: <timestamp>_<Name>.cs, holding Up() and Down() methods full of MigrationBuilder calls that apply or reverse the change, plus a <timestamp>_<Name>.Designer.cs metadata file. The snapshot file itself then gets rewritten to match the new model, so the next migrations add diffs against this migration, not the one before it.

dotnet ef database update (or calling context.Database.Migrate() at startup) is the separate step that actually touches a real database. EF Core keeps a __EFMigrationsHistory table inside that database recording which migrations have already run there. Applying just reads that table, finds the migrations not yet listed, and runs their Up() methods in order — then records each one.

Splitting the two steps this way is deliberate: a generated Up()/Down() file can be reviewed, edited, or held back in a pull request before it ever touches a database, and the exact same migration file can be applied later to dev, staging, and production without being regenerated each time.

💻 See the code ▾
C# 
public partial class AddEmailIndex : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.CreateIndex(
            name: "IX_Users_Email",
            table: "Users",
            column: "Email");   // ✅ generated from the model diff
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropIndex(
            name: "IX_Users_Email",
            table: "Users");    // ✅ the exact reverse, also generated
    }
}

Nobody types this by hand — migrations add writes both directions for you.

C# 
using var context = new AppDbContext();
context.Database.Migrate();
// ✅ runs only migrations missing from __EFMigrationsHistory, in order

Safe to call on every startup — already-applied migrations are skipped, never re-run.

C# 
var pending = context.Database.GetPendingMigrations();
// ⚠️ only compares against __EFMigrationsHistory —
// a column added by hand outside EF Core won't show up here at all

GetPendingMigrations() trusts the history table completely — it has no way to see a manual schema change.

🧭 Use Cases — recognize these when they happen to you ▾
1 You just changed an entity's model and need EF Core to record it

The model changed but nothing has run against a database yet. migrations add just diffs the model against the stored snapshot and writes the change to a new file pair you can review before it goes anywhere. This is the #1 moment you'll actually hit day to day.

RememberModel changed → migrations add writes the file, nothing runs.
2 A reviewed migration needs to run on a real database at deploy time

database update (or Database.Migrate() at startup) reads __EFMigrationsHistory first and only runs what isn't recorded there yet — already-applied migrations are skipped, never re-run.

RememberDeploy time → database update runs only what's new.
3 Two teammates each generate their own migration, then merge branches

Both migrations were diffed against the same starting snapshot, so merging the branches can leave conflicting Up() steps or a snapshot file that matches neither branch — usually needs one migration manually resolved or regenerated.

RememberSame starting snapshot, two migrations → expect a manual merge fix.
🌍 Real-world example ▾

Think of it like a recipe card. The live model is the finished dish, the snapshot is the last recipe card on file, and migrations add just writes down what changed between the two — the kitchen itself (the database) doesn't change until someone actually follows that recipe by running database update.

Scenario: a teammate adds a MiddleName column directly through a database GUI to unblock a demo. Weeks later, someone runs a routine migrations add — EF Core has no record of that column at all, so the generated migration tries to add it again, and the deploy fails on every environment where the manual fix already exists.
