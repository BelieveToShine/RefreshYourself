this(), super(), and what actually runs first

"What's the actual order of initialization when a subclass object is constructed?"

Why it matters ▾
🔁 this(...)
❗ ProblemSeveral constructor overloads in the same class often need to run the exact same setup logic, and copy-pasting that logic into each one means a fix has to be repeated everywhere.
✅ Solutionthis(...) calls another constructor in the same class — it must be the very first statement, so one overload can delegate its setup to another.
Recallthis(...) = call a sibling constructor, same class.
⬆️ super(...)
❗ ProblemA subclass object isn't fully a valid object until its parent's own fields and setup have run too — skipping that would leave inherited state uninitialized.
✅ Solutionsuper(...) calls the parent's constructor — also required as the first statement if written, and inserted automatically (no-arg) if neither this(...) nor super(...) is written at all.
Recallsuper(...) = call the parent's constructor, implicit if omitted.
🔥 Easy interview recall

Static init → once, at class load

Superclass → fields + ctor body, fully

Subclass → fields + ctor body, after

Think: the parent's entire construction finishes — fields and constructor body — before the child's construction even starts.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling an overridable instance method from a constructor is dangerous. If a subclass overrides it, that override can run before the subclass's own field initializers have executed — operating on fields that are still at their default (often null/zero) values.

🔄 Likely Follow-up

"What happens if a constructor writes neither this(...) nor super(...)?" The compiler inserts an implicit, no-argument super() call as the very first statement — and it's a compile error if the parent has no no-arg constructor for it to call.

🎯 Say this in the interview — the exact lines to land

"The real order is: static initializers once at class load, then the superclass's field initializers and constructor body — completing fully — then the subclass's field initializers, then the subclass's own constructor body. this(...)/super(...) must be the first statement if written, and super() is inserted implicitly if neither is."

  • this(...) → same class, another constructor.
  • super(...) → parent class, implicit if omitted.
  • Superclass construction → fully completes before subclass construction begins.
📖 Explanation ▾

this(...) and super(...) both have to be the very first statement in a constructor if you write either one — Java won't let you run other code first and then chain. If you write neither, the compiler silently inserts a no-arg super() for you, which is why every constructor, even one that never mentions super, still calls its parent's constructor.

The real initialization order runs top-down through the whole hierarchy before any constructor body runs: static initializers once, the first time the class is loaded; then, for the object itself, the superclass's instance field initializers and instance initializer blocks (in source order), followed by the superclass's own constructor body — and only once all of that is finished does the subclass's instance field initialization begin, followed by the subclass's constructor body.

That "superclass fully finishes first" guarantee is exactly what makes the constructor trap dangerous: an overridable method called from the superclass constructor dispatches to the subclass's override (polymorphism doesn't care which constructor is running) — but that override runs while the subclass's own fields are still unset.

💻 See the code ▾
☕ Java 
class Pizza {
    Pizza() { this("plain"); }      // delegates to the other ctor
    Pizza(String topping) {   // ✅ this(...) is the first statement
        System.out.println("Topping: " + topping);
    }
}

The no-arg constructor never repeats setup logic — it just delegates to the one that already has it.

☕ Java 
class Animal {
    Animal() {
        makeSound();              // ❌ trap — calls the OVERRIDE, not Animal's version
    }
    void makeSound() { System.out.println("..."); }
}
class Dog extends Animal {
    String name = "Rex";
    @Override
    void makeSound() { System.out.println(name.length()); } // 💥 NPE — name isn't set yet
}

new Dog() runs Animal's constructor first — name is still null when the override fires.

🧭 Use Cases — recognize these when they happen to you ▾
1 You have 3 constructor overloads that all need the same validation logic

Every overload delegates its setup to one "real" constructor via this(...), so the validation logic exists exactly once. This is the #1 reason this(...) chaining actually gets used.

RememberMultiple overloads → this(...) chains to one real constructor.
2 A subclass needs to pass data up to a parent that requires it in its constructor

If Animal has no no-arg constructor, every subclass must write an explicit super(...) call that supplies what the parent needs — skipping it is a compile error, not a runtime surprise.

RememberParent has no no-arg ctor → subclass must call super(...) explicitly.
3 A superclass constructor calls a method the subclass overrides

The call dispatches to Dog's override because polymorphism doesn't know or care which constructor is currently running — but Dog's own fields haven't been set yet at that point.

RememberOverridable call in a constructor → may run on unset subclass fields.
🌍 Real-world example ▾

Building a house. The foundation and frame (superclass) have to be fully finished — not "mostly" finished — before anyone starts installing the second floor's wiring (subclass). Calling an inspector in to check the second floor while the foundation crew is still working is exactly the constructor-method trap: they'll inspect rooms that don't exist yet.
