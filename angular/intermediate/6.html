🔥 Must Know

signal() — a value that knows who's reading it, so nothing has to subscribe

"What is a Signal, and why did Angular introduce it when RxJS already existed?"

Why it matters ▾
  • Signals are the reactivity model every newer Angular feature builds on — including zoneless change detection, covered later in this track.
  • Interviewers use this to check you understand the actual problem Signals solve, not just the new syntax.
  • Mixing up computed() with a plain cached function is one of the most common wrong answers candidates give.
🔥 Easy interview recall

signal() → writable source of truth

computed() → derived, read-only, auto-updates

effect() → side effect, runs on change

Think: one signal() can feed a computed() and an effect() at the same time — nobody subscribes to anything, they just read it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

computed() is not just a cached function call. It's genuinely reactive — it automatically re-runs and updates its own value the moment any Signal it depends on changes, with nobody calling it again; a plain memoized function would just keep returning a stale result until something explicitly invalidated the cache.

🔄 Likely Follow-up

"Can you call .set() on the result of computed()?" No — a computed Signal is read-only by design; it has no .set() or .update() at all, because its value always comes from re-deriving from its source Signals. Trying to treat it like a writable Signal is a compile-time type error, not something you could do by accident at runtime.

🎯 Say this in the interview — the exact lines to land

"A Signal is a value that tracks who reads it and notifies those readers when it changes — you read it by calling it as a function, and you only ever write it through .set() or .update(), never by direct assignment."

  • signal() → writable source of truth — call .set() to replace it, .update() to derive from the current value.
  • computed() → read-only, derived value — recalculates automatically, no .set() exists on it.
  • effect() → runs a side effect automatically whenever a Signal it reads changes — logging, syncing to storage, not computing a value.
  • Still reach for RxJS when it's genuinely a stream over time — HTTP calls, debouncing input, combining multiple async sources.
  • Signals don't replace RxJS — Angular ships toSignal()/toObservable() specifically because both models are meant to coexist.
📖 Explanation ▾

A Signal is a wrapper around a value that automatically tracks who reads it. You read a Signal by calling it like a function (count()), and you write it only through its own setter methods — .set(newValue) replaces it outright, .update(current => ...) derives the new value from the current one. Plain component-instance properties can't do any of this — nothing about a normal field tracks who's reading it, which is exactly the gap Signals were built to close, and the reason Angular introduced them even though RxJS already existed: RxJS is built for streams of events over time, not for "this one value changed, re-render whatever shows it."

computed() and effect() both track their dependencies the same way: whichever Signals actually get read inside their callback, during that callback's last run, become the things they react to. There's no dependency array to declare by hand — it's based purely on what was actually accessed. Reading a Signal inside a component's template does the same thing: it registers that template as a consumer, so Angular knows precisely which bindings to re-check when the Signal changes — this fine-grained tracking is also the foundation zoneless change detection is built on.

Signals don't replace RxJS — they solve a narrower problem: synchronous, fine-grained state and values derived from it. Anything genuinely about a stream over time — an HTTP request, debouncing user input, combining multiple async sources, cancellation — is still RxJS's job; there's no direct Signal equivalent for most of that operator vocabulary. Angular ships toSignal() and toObservable() as interop, covered later in this track, specifically because both models are expected to coexist.

💻 See the code ▾
TypeScript 
const count = signal(0);                                   // writable — source of truth
const doubled = computed(() => count() * 2);          // derived — recalculates automatically
effect(() => console.log('count is now', count()));  // side effect — runs automatically

count.set(5);
// doubled is now 10 — nobody called computed() again, it just reran
// effect logs "count is now 5" automatically

One .set() call — the derived value and the side effect both update without being told to.

TypeScript 
count.update(c => c + 1);      // ✅ derives from the current value
count.set(count() + 1);        // also works, just more to type

.update() exists specifically for "new value depends on the old one" — .set() can do it too, it's just more verbose.

🌍 Real-world example ▾

A writable Signal is a shared whiteboard number everyone can see. A computed() is a second whiteboard that automatically rewrites itself — say, always showing double the first board's number — the instant the first one changes, with nobody manually updating it. An effect() is a person who takes an action, like sending an email, every time they notice either whiteboard change.
