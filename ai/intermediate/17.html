Search with the fake answer, not the real question

"Multi-query and HyDE both improve retrieval when a user's raw question isn't phrased like the source documents — how does each one actually work?"

Why it matters ▾
🔀 Multi-query
❗ ProblemA single phrasing of the question can miss documents that only match a different wording of the exact same request.
✅ SolutionGenerate several reformulations, retrieve for each one, then merge and dedupe the hits — one search per phrasing catches what a lone phrasing would have missed.
RecallMulti-query = ask it many ways, merge the hits.
🧬 HyDE
❗ ProblemEmbedding the raw question compares a question against an answer — two different kinds of writing — so the match can be weak even when the right document exists.
✅ SolutionHave the LLM write a hypothetical answer first — right or wrong doesn't matter — then embed and search with that, since it's usually worded closer to the real documents.
RecallHyDE = search with the fake answer, not the real question.
🪜 Step-back
❗ ProblemA narrow, specific question can retrieve documents too narrow to give the broader context actually needed to answer it well.
✅ SolutionAsk a more general version of the question first, retrieve broadly for that, then use the wider context to help answer the original specific question.
RecallStep-back = ask the general question first, then answer the specific one.
🚦 Routing
❗ ProblemNot every question belongs in the same index or source — searching the wrong one wastes a retrieval pass before the real answer is ever reached.
✅ SolutionDecide which index or source is even worth searching before retrieval starts — no new embedding, just dispatching to the right target.
RecallRouting = pick the right source before you search, not after.
🔥 Easy interview recall

Multi-query = "ask it many ways." HyDE = "search with a fake answer, not the real question."

Think: Multi-query → several rephrasings, one search each, merge the hits HyDE → LLM writes a made-up answer → embed that → search

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Multi-query and HyDE are not the same trick. Multi-query still searches with (several versions of) the actual question. HyDE never searches with any version of the question at all — it searches with a hypothetical answer instead, even one that's factually wrong.

🔄 Likely Follow-up

"Does the hypothetical answer in HyDE need to be factually correct?" No — it's never shown to the user or checked for accuracy. Its only job is to be phrased like a real answer, so its embedding lands closer to the actual matching documents.

🎯 Say this in the interview — the exact lines to land

"Multi-query generates several rephrasings of the question, retrieves for each one, and merges the results. HyDE goes further — it has the LLM write a hypothetical answer first, then embeds and searches with that answer instead of the question, because a plausible answer is usually phrased more like the real documents than the question is."

  • Multi-query → several reformulations, one retrieval each, then merge and dedupe the hits.
  • HyDE → embed the hypothetical answer, not the question — it doesn't need to be correct.
  • Step-back prompting → ask a more general question first, retrieve broadly, then answer the specific one.
  • Query routing → decide which index or source is even worth searching, before retrieval starts.
  • All four exist because a raw question is often phrased differently from the documents that answer it.
📖 Explanation ▾

A user's question and the document that actually answers it are rarely written in the same style. Someone types "why is my app slow," but the fix lives in a page titled "Diagnosing latency in connection pooling." Embedding the raw question and searching directly compares two different kinds of writing — a question and an answer — so the match can be weak even when the right document exists. Query transformation is the umbrella term for reshaping what actually gets embedded and searched, before retrieval runs, to close that gap.

HyDE's trick works specifically because embedding similarity measures how alike two pieces of text are worded, not whether one is a correct answer to the other. A plausible-sounding hypothetical answer — even a wrong one — is usually phrased closer to how the real source documents are written than the original question ever was, so its embedding lands nearer the documents that actually matter.

💻 See the code ▾
Python 
# multi-query — several rephrasings of the same question
variants = llm_generate_variants(user_query, n=4)

results = []
for v in variants:
    results += vector_search(embed(v))

merged = dedupe(results)   # combine hits from every phrasing

Every variant gets its own retrieval pass — merging catches documents that only matched one phrasing.

Python 
# HyDE — ask for a plausible answer FIRST
hypothetical_answer = llm_generate_answer(user_query)  # may be wrong, that's fine

# embed and search with THAT — not the raw question
hits = vector_search(embed(hypothetical_answer))

The fake answer never reaches the user — its only job is to be worded like a real document.

🧭 Use Cases — recognize these when they happen to you ▾
1 Retrieval quality is weak even though the rest of the RAG pipeline already works end to end

This is the natural deep-dive an interviewer asks after "walk me through your RAG pipeline" — the fix isn't reindexing, it's reshaping what actually gets embedded and searched, before retrieval runs. This is the #1 scenario you'll actually run into once the basic pipeline already works.

RememberWorking pipeline but weak recall → reach for query transformation, not more index tuning.
2 A question is too narrow to retrieve the wider context actually needed to answer it

Step-back asks a broader, more general version of the question first, retrieves for that, then uses the wider context to help answer the original specific question — the two-step order is what makes it different from just rephrasing the same question.

RememberNarrow question → ask the general one first, then answer the specific one.
3 You describe multi-query's several rephrasings as "basically HyDE"

Multi-query still searches with (several versions of) the actual question — it never stops asking a real question. HyDE never searches with any version of the question at all; it searches with a hypothetical answer instead, even one that's factually wrong.

RememberStill asking a version of the question = multi-query. Searching with a fake answer instead = HyDE.
🌍 Real-world example ▾

Asking a librarian "how do I fix a leaky faucet" gets a slower search than handing them a page that already reads like a repair manual. HyDE writes that fake manual page itself — right or wrong doesn't matter — then goes looking for the real one that's worded the same way.
