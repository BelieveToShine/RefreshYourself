Jest & Vitest — the async test that passes before it's actually done

"How do you write and isolate a unit test in JavaScript — and why can an async test pass even when the code under test is actually broken?"

Why it matters ▾
🌐 Mock fetch itself
❗ ProblemIf a test only fakes the wrapper's return value, the wrapper's own fetch-handling code — building the request, checking the response — never actually runs, so a bug living inside it stays hidden.
✅ SolutionReplace the global fetch and fake a whole Response-shaped object instead, so the wrapper's real logic executes against a controlled answer — the right call when the wrapper function itself is what's under test.
RecallMock fetch itself → fake a full Response, exercises the wrapper's own logic.
🎭 Mock the wrapper function
❗ ProblemTesting code that merely calls a wrapper doesn't need the wrapper's real network call running underneath it — faking a whole Response object is more setup than that test actually needs.
✅ Solutionjest.mock()/vi.mock() swaps in a fake wrapper that returns the resolved value directly, no Response object needed — best when testing code that calls the wrapper, though it hides real fetch-specific bugs like headers or status.
RecallMock the wrapper → return the value directly, but can hide real fetch-specific bugs.
🔥 Easy interview recall

describe/it → group and name the test, run nothing by itself

expect().toBe() → check the result against what you expect

jest.mock() → swap the real dependency for a fake one

Think: if a test never awaits its async assertion, it can report green before the real answer ever comes back.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A green checkmark doesn't mean the assertion actually ran. If an async assertion like expect(promise).rejects.toThrow() isn't returned or awaited, the test function finishes before the promise settles, so the runner marks it passed no matter what the real result turns out to be.

🔄 Likely Follow-up

"How is jest.mock() different from just writing a fake object yourself?" jest.mock()/vi.mock() replaces every import of that module in the test file automatically and tracks calls for you (toHaveBeenCalledWith); a manual fake is a plain object or function you pass in by hand — same isolation, less built-in call tracking.

🎯 Say this in the interview — the exact lines to land

"A unit test isolates one function or module and fakes its real dependencies — jest.mock()/vi.mock() swaps in a fake so the test never hits a real API or database. describe/it structure the tests, expect(...) matchers check the result, and any async assertion has to be awaited or returned, or the test can pass on a bug."

  • describe/it → groups and names tests; it doesn't check anything by itself.
  • toBe() → strict equality toEqual() → deep equality for objects/arrays
  • jest.mock()/vi.mock() → isolates the unit from a real API or database call.
  • Testing a fetch call → mock fetch itself, or mock the wrapper function that calls it.
  • Async test → must await or return the assertion, or it can pass while wrong.
📖 Explanation ▾

A test runner like Jest or Vitest does three plain things: it discovers every file matching a test pattern, runs each function registered with test(...) or it(...), and reports whether every expect(...) assertion inside it held true. describe is just a label that groups related tests together in the output — it doesn't run or check anything on its own. Matchers are the actual checks: .toBe() is strict equality (same primitive value, or the exact same object reference), while .toEqual() does a deep comparison, which is what you want for objects and arrays.

Mocking exists for the same reason isolating a function or module always has: a test shouldn't fail because a real database was down or a real API was slow. jest.mock() (or vi.mock() in Vitest) replaces every import of a module in that test file with a fake version — or you can skip the tooling and pass in a plain manual fake yourself. When the code under test calls fetch, there are two honest ways to isolate it:

Async tests carry one specific risk: expect(promise).resolves... and .rejects... both return a promise of their own, and if the test function doesn't await or return that promise, the runner considers the test finished the instant the (synchronous) function body ends — before that promise ever settles. The fix is always the same: await the assertion, or explicitly return the promise it produces.

💻 See the code ▾
JavaScript 
describe('sum()', () => {
  it('adds two numbers', () => {
    // Arrange / Act
    const result = sum(2, 3);

    // Assert — matchers do the actual checking
    expect(result).toBe(5);            // strict equality
    expect({ total: 5 }).toEqual({ total: 5 }); // deep equality
  });
});

describe only groups and labels — it is the actual test; expect(...) matchers decide pass or fail.

JavaScript 
// api.js is the real module — a real network call
import * as api from './api.js';
import { getUserName } from './orderService.js';

jest.mock('./api.js');   // ✅ every import of api.js is now a fake in this file

it('reads the user name from the API response', async () => {
  api.fetchUser.mockResolvedValue({ name: 'Sam' }); // canned fake result

  const name = await getUserName(42);
  expect(name).toBe('Sam');
});

The real api.js never runs — getUserName is tested against a canned, instant fake instead of a real network call.

JavaScript 
it('rejects a negative deposit', () => {
  // ❌ no return, no await — the test function returns immediately
  expect(depositAsync(-5)).rejects.toThrow();
});
// PASSES even if depositAsync(-5) never rejects at all —
// the promise settles after the test was already marked done

Green, but meaningless — the assertion's real outcome arrives after the runner already moved on.

JavaScript 
it('rejects a negative deposit', async () => {
  // ✅ awaited — the runner actually waits for the promise to settle
  await expect(depositAsync(-5)).rejects.toThrow();
});

Same assertion, now awaited — this one lives or dies on what depositAsync(-5) actually does.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're testing code that calls a wrapper like getUserName() — not the wrapper itself

The code under test just needs a wrapper that returns a predictable value — jest.mock('./api.js') swaps in exactly that, so getUserName() runs against a canned { name: 'Sam' } result instead of a real network call.

RememberTesting the caller → mock the wrapper's return value directly.
2 You're testing the wrapper function itself — the one that actually calls fetch

Here the wrapper's own request/response-handling logic is exactly what needs to run, so faking only its return value would skip right over the code you're trying to test — fetch itself gets mocked instead, with a fake Response-shaped object standing in for the real network answer.

RememberTesting the wrapper's own logic → mock fetch itself, not the wrapper.
3 An async assertion like expect(promise).rejects.toThrow() isn't awaited or returned

The test function finishes before the promise ever settles, so the runner marks it passed no matter what depositAsync(-5) actually does — a green checkmark that never actually checked anything. A common trap — an async assertion has to be awaited or returned, or the test can pass on a real bug.

RememberNo await/return on an async assertion → passes even when broken.
🌍 Real-world example ▾

A mock is a stunt double, not the real actor. The real API call is the actor doing the actual stunt — slow, sometimes unpredictable, expensive to run over and over. A mock is the double who performs the same result reliably every single take, so the test can focus on checking the scene — your code's logic — instead of the safety of the real dependency.
