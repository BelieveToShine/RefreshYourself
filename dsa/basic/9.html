Sorting — why not just always use quicksort?

"Why not just always use quicksort — isn't it always O(n log n)?"

Why it matters ▾
  • Almost every interview assumes you know the standard sorts cold — but the real test is judgment, not reciting Big-O tables.
  • Picking a sort without checking stability or worst-case behavior is a real source of production bugs, not just an interview trap.
  • A common opener before harder questions — how you reason about trade-offs here predicts how you'll reason about everything else.
🔥 Easy interview recall

Comparison sort → hard floor of O(n log n), never faster

Quicksort → fast average, but O(n²) worst case

Counting / Radix → skips comparisons, beats the floor

Think: merge sort plays it safe. quicksort plays the odds. counting sort doesn't even play the same game.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Quicksort is not always O(n log n). Its worst case is O(n²) — picking the first (or last) element as pivot on already-sorted or reverse-sorted input keeps splitting the array 1-vs-everything-else; real implementations dodge this by randomizing the pivot or using median-of-three, which doesn't change the theoretical worst case, just makes it very unlikely.

🔄 Likely Follow-up

"You have a huge array of integers, all between 0 and 100 — what's the fastest way to sort it?" Counting sort — O(n + k) with k = 101, beating any comparison sort's O(n log n) floor because the value range is small and already known.

🎯 Say this in the interview — the exact lines to land

"Comparison sorts can never beat O(n log n) in the worst case. Quicksort is usually fastest in practice but can degrade to O(n²), so I'd reach for merge sort when I need a guaranteed worst case or stability, and a non-comparison sort like counting sort when the value range is small and known."

  • Quicksort → everyday default for in-memory sorting — fastest average case, low memory overhead.
  • Merge sort → use for a guaranteed worst case or stability — linked lists, external sort, tie-sensitive data.
  • Heap sort → use when you need the O(n log n) guarantee in-place and don't need stability.
  • Counting / Radix sort → use when the value range is small and known — skips comparisons entirely.
📖 Explanation ▾

A comparison sort decides order only by asking "is this one bigger or smaller than that one?" — and it's a proven result that no comparison sort can do better than O(n log n) in the worst case, no matter how clever the algorithm is. Merge sort, quicksort, and heap sort all live at that bound, but they get there very differently.

Merge sort splits the array in half, sorts each half, then merges — always O(n log n), and stable, at the cost of O(n) extra space for the merge. Quicksort picks a pivot and partitions around it — average case O(n log n), in-place, but a poorly chosen pivot on the wrong input drags it to O(n²). Heap sort repeatedly pulls the max out of a heap — guaranteed O(n log n) with O(1) extra space, but not stable, and its scattered heap access tends to run slower in practice than quicksort's cache-friendly scan.

A non-comparison sort beats the O(n log n) floor by never comparing elements pairwise — it exploits known structure instead. Counting sort counts how many times each value occurs (O(n + k), k = the value range) and rebuilds the output from those counts. Radix sort sorts digit-by-digit using counting sort as a subroutine, in O(d·(n + k)). Bucket sort drops elements into ranged buckets and sorts each one — near-linear on average if the data is roughly evenly spread. All three only work when the values have exploitable structure — an unbounded, arbitrary range gets no benefit from any of them.

💻 See the code ▾
Python 
def partition(arr, low, high):
    pivot = arr[low]              # ❌ naive choice — first element
    i = low + 1
    for j in range(low + 1, high + 1):
        if arr[j] < pivot:
            arr[i], arr[j] = arr[j], arr[i]
            i += 1
    arr[low], arr[i - 1] = arr[i - 1], arr[low]
    return i - 1

On already-sorted or reverse-sorted input, this naive pivot keeps splitting 1-vs-everything-else — that's the O(n²) worst case in action.

Python 
def counting_sort(scores, max_score=100):
    counts = [0] * (max_score + 1)
    for s in scores:
        counts[s] += 1                 # no comparisons at all
    result = []
    for value, count in enumerate(counts):
        result.extend([value] * count)  # ✅ rebuilt straight from counts
    return result

O(n + k) with k = 101 — faster than any comparison sort's O(n log n) floor, because the range is small and already known.

🌍 Real-world example ▾

You're sorting a list of customer orders by date for a report. Several orders land on the same date, and you want those ties to stay in the order they were originally entered. That's a job for a stable sort — merge sort or counting sort — not a plain quicksort or heap sort, which can silently shuffle same-date orders out of their original order.
