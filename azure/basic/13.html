VNets & Subnets — carving one network into rooms with different locks

"What are the basics of networking on Azure — VNets and subnets?"

Why it matters ▾
☁️ VNet
❗ ProblemDeploying resources straight into Azure with no boundary of your own would leave you with no private address range and no outer edge controlling what can reach in.
✅ SolutionA VNet is your own private network inside Azure, with the address range you define acting as the outer boundary of the whole thing.
RecallVNet = your own private network + the outer address-range boundary.
🧩 Subnet
❗ ProblemA single flat VNet gives every resource inside it the same access — a web server and a database with no way to apply different security rules.
✅ SolutionA subnet is a non-overlapping sub-range carved out of the VNet's own range, and each subnet carries its own NSG and route table, scoped just to it.
RecallSubnet = a slice of the VNet, with security scoped per slice.
🔥 Easy interview recall

VNet → its own private address range

Subnet → a slice of that same range

Think: one VNet, cut into subnets — each subnet gets its own NSG, like its own locked room.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A subnet's IP range is not its own independent network. Every subnet's address range has to be a non-overlapping sub-range carved directly out of its VNet's own range — you can't assign a subnet a CIDR block that falls outside (or overlaps another subnet inside) that VNet.

🔄 Likely Follow-up

"Why put different resource types in different subnets?" To apply different NSG rules and route tables per tier — e.g. a web-tier subnet open to the internet, a data-tier subnet only reachable from the web subnet.

🎯 Say this in the interview — the exact lines to land

"A subnet is a sub-range carved out of its VNet's address space, each with its own NSG. Splitting resources into separate subnets lets you apply different security rules per tier, instead of one flat network with one set of rules for everything."

  • Subnet → a slice of the VNet's own address range, never a separate network.
  • NSG per subnet → each subnet can carry its own firewall rules and route table.
  • Ranges must nest → subnet CIDRs are non-overlapping pieces carved out of the VNet's block.
  • Tier by subnet → web, app, and data subnets each get only the access they actually need.
📖 Explanation ▾

A VNet (Virtual Network) is your own private, isolated network space inside Azure — you choose its address range (e.g. 10.0.0.0/16), and nothing outside it can reach in unless you allow it. A subnet then divides that range into smaller pieces, and every resource you deploy — a VM, an App Service with VNet integration, a database — lands inside exactly one subnet.

Each subnet can carry its own NSG (a basic firewall that filters traffic by IP, port, and protocol) and its own route table, so a web subnet can accept traffic from the internet on ports 80/443 while a database subnet only accepts traffic from the app subnet next to it. Resources inside the same VNet reach each other over Azure's private backbone — that traffic never has to go out onto the public internet just to cross from one subnet to another.

💻 See the code ▾
Azure CLI 
az network vnet create --name vnet1 \
  --address-prefix 10.0.0.0/16 \   -- the VNet's own range
  --subnet-name web \
  --subnet-prefix 10.0.1.0/24          -- carved out of 10.0.0.0/16

The subnet's 10.0.1.0/24 range sits nested inside the VNet's own 10.0.0.0/16 range — it is never a separate address space.

🧭 Use Cases — recognize these when they happen to you ▾
1 You spin up a brand-new VNet before deploying anything else

This is the first Azure networking step: you define an address range once, and nothing outside it can reach in until you allow it. Everything you deploy afterward lands inside a subnet carved from this same range.

RememberVNet first — the address range is defined before anything deploys.
2 You split a 3-tier app across web, app, and data subnets

Each subnet carries its own NSG, so the web subnet accepts traffic from the internet, the app subnet only accepts traffic from the web subnet, and the data subnet only accepts traffic from the app subnet. This is the most common scenario you'll actually run into.

RememberDifferent tiers → different subnets → different NSG rules.
3 You try to give a subnet a range that overlaps another subnet, or falls outside the VNet

Azure rejects this. Every subnet's range has to be a non-overlapping sub-range carved directly out of its VNet's own range — a subnet is never an independent network with a range of its own choosing. A common interview trap.

RememberSubnet ranges nest inside the VNet — never overlap, never outside.
🌍 Real-world example ▾

A 3-tier app splits itself across three subnets — one for web servers, one for app servers, one for the database. Each subnet's NSG only allows the adjacent tier to reach it: the web subnet accepts traffic from the internet, the app subnet only accepts traffic from the web subnet, and the database subnet only accepts traffic from the app subnet.
