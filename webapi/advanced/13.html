Changing a live API — additive, or does it break someone?

"You need to change an API that existing clients already depend on — how do you design the change so it doesn't break them?"

Why it matters ▾
🔄 Backward Compatibility
❗ ProblemClients you don't control, and often can't even see, are already calling the current contract — changing or removing a field or endpoint's existing meaning breaks them the moment the new version ships, with no warning.
✅ SolutionMake changes additive and opt-in — version the contract, add new fields as optional, never repurpose an existing one — and give old clients a real deprecation window before anything is actually removed.
RecallAdditive and opt-in is safe. Changing what already exists isn't.
🔥 Easy interview recall

Backward compatible = "add, don't change — and give old clients a way out."

Think: New field → optional, with a default New behavior → a new version, old one keeps working Never → repurpose an existing field's meaning

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Backward compatible" doesn't mean "never change anything." That's not sustainable — the real skill is making changes additive and opt-in with a real migration path for old clients, not freezing the API forever.

🔄 Likely Follow-up

"URL versioning vs. header versioning — which would you pick and why?" URL versioning (/v2/...) is simpler to discover, cache, and route; header versioning keeps URLs stable but is less discoverable and harder to test casually — URL versioning is the more common default for public APIs.

🎯 Say this in the interview — the exact lines to land

"Additive changes are safe — new optional fields, new endpoints. Changing or removing something a client already depends on isn't, so I'd version the API, usually by URL, so existing clients keep hitting the unchanged contract while new clients opt into the new one. New fields get sensible defaults instead of being required, I never repurpose an existing field's meaning, and I deprecate with a clear timeline before actually removing anything."

  • Additive is safe → new optional fields and new endpoints don't break existing callers.
  • Versioning → URL path is the common default — simple to discover, cache, and route.
  • Never repurpose a field → add a new one instead of changing what an old one means.
  • New required fields → make them optional with a default, not mandatory.
  • Deprecate with a plan → a clear timeline and signal before removal, not a surprise.
📖 Explanation ▾

Additive changes — a new optional field, a new endpoint — are safe because an existing client simply never asks for them and never notices they exist. Changing what an existing field means, removing a field, or changing a status code or response shape a client already parses is a breaking change, even if it looks small from the server's side. The fix isn't to avoid changing the API forever; it's to make the change additive and opt-in. Versioning — in the URL path, a header, or a query parameter — is the mechanism: old clients keep hitting the contract they were built against, new clients opt into the new one by using the new version explicitly.

A few concrete rules make this easy to apply consistently: give new fields sensible defaults instead of making them required, so an old request that doesn't know about the new field still works. Never repurpose an existing field's meaning — if a field's semantics genuinely need to change, add a new field and leave the old one alone (or deprecated) rather than changing what the same name means out from under existing callers. And when something really does need to go away, deprecate it with a timeline — a deprecation header, a changelog entry, a sunset date — so clients have a real window to migrate before it's removed, rather than finding out when it breaks.

💻 See the code ▾
C# 
[ApiController]
[Route("v1/orders")] // ✅ unchanged contract, still served
public class OrdersV1Controller : ControllerBase { /* same shape as before */ }

[ApiController]
[Route("v2/orders")] // ✅ new fields live here, opt-in by calling v2
public class OrdersV2Controller : ControllerBase { /* adds new optional fields */ }

Both controllers deploy together — an old client calling /v1/orders never sees the v2 shape, by design.

🌍 Real-world example ▾

A partner integration has been calling /v1/orders for two years. The team needs to change what the status field means to support a new workflow. Instead of changing status in place and breaking the partner overnight, they ship /v2/orders with the new meaning, keep /v1 serving the old one unchanged, and give the partner a six-month deprecation notice with a clear migration guide before /v1 is ever turned off.
