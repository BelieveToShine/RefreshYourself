Options API vs. Composition API — organized by type, or organized by feature?

"What's the real difference between the Options API and the Composition API?"

Why it matters ▾
📋 Options API
❗ ProblemA component with several real features (search, pagination, selection) ends up with each feature's logic scattered across separate data(), methods, and computed sections instead of living together.
✅ SolutionThe Options API organizes a component by option TYPE — simple and predictable for a small component, where there's barely enough code to scatter in the first place.
RecallOptions API = organized by option type (data/methods/computed).
🧩 Composition API
❗ ProblemAs a component grows, finding everything related to one feature means jumping between the data(), methods, and computed sections instead of reading it in one place.
✅ SolutionThe Composition API organizes a component by FEATURE — state, computed values, and functions for one concern sit together, and can be extracted into a reusable composable.
RecallComposition API = organized by feature, reusable via composables.
🔥 Easy interview recall

Options API → grouped by option type

Composition API → grouped by feature

Think: Same logic, two filing systems — by drawer type, or by project.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Treating the Composition API as "the new mandatory way." The Options API is fully supported and often clearer for a small, simple component — the real differentiator is code organization and reuse at scale, not deprecation.

🔄 Likely Follow-up

"Can you mix both in the same component?" Yes — a component can have a setup() alongside Options API options, though mixing styles in one component hurts readability more than it helps; most real code picks one per component.

🎯 Say this in the interview — the exact lines to land

"The Options API organizes a component by option type — data, methods, computed — so related logic for one feature ends up scattered across sections. The Composition API organizes by feature instead — all the state, computed values, and functions for one concern sit together, and can be extracted into a reusable composable."

  • Options API → organized by option type, simple for a small component.
  • Composition API → organized by feature, scales better and enables composables.
  • Neither is deprecated — Options API is still fully supported, not a legacy-only path.
  • Mixing both in one component works but hurts readability — most components pick one.
📖 Explanation ▾

The Options API is Vue's original component shape — you fill in predefined options like data(), methods, and computed, and Vue wires them together. For a small component this reads cleanly: there's barely enough code in each section to get lost in.

The Composition API (setup(), or <script setup>) drops the fixed sections. You write plain variables and functions, and group them however makes sense — usually by feature, so everything related to one concern (its state, its computed values, its functions) lives next to each other. That same grouped logic can be lifted into its own function — a composable — and reused across components, which the Options API has no equivalent for.

Neither API is "more correct." A tiny component with one piece of state reads fine either way; the Composition API's real advantage only shows up once a component has several distinct features, or once logic needs to be shared across components.

💻 See the code ▾
Vue 
// Options API
export default {
  data() { return { count: 0 }; },
  methods: { increment() { this.count++; } },
  computed: { doubled() { return this.count * 2; } }
};

One counter's state, behavior, and derived value — three separate sections.

Vue 
// Composition API — <script setup>
const count = ref(0);
function increment() { count.value++; }
const doubled = computed(() => count.value * 2);   // ✅ all one place

Same logic, grouped together — and this whole block could move into a reusable composable unchanged.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're writing a small, single-purpose component

A component with one piece of state and one method is clear either way — there's nothing to get lost scattering, so the choice comes down to team convention. This is the #1 scenario you'll actually run into.

RememberTiny component → both APIs read equally well.
2 Several components need the same stateful logic (e.g. a debounced search)

A useSearch() composable can be called from any component that needs the same debounced-search behavior, with no mixin-style property-naming collisions to worry about.

RememberShared stateful logic → a composable, not a mixin.
3 You assume the Options API is deprecated and must be rewritten

There's no forced migration — Vue 3 fully supports the Options API, and plenty of real, current codebases use it. Rewriting working components just to "modernize" them isn't something the framework asks for.

RememberOptions API code → not legacy, no forced rewrite.
🌍 Real-world example ▾

Think of organizing a toolbox. Options API is sorting every tool by type — all screwdrivers together, all wrenches together. Composition API is sorting by project instead — everything needed for "fix the bike" in one bag. Both get the job done; the second scales better once you're juggling several projects at once.
