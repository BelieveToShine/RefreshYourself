⭐ AI · Intermediate · Should Know

One shared vector index, many tenants — how do you stop Tenant B's data from reaching Tenant A's answer?

"You're building a RAG system that serves many customers over their own private documents. How do you make sure one customer's data never leaks into another customer's answer?"

Why it matters ▾
  • Tests whether you know isolation has to happen at the retrieval/vector-store layer itself, not by trusting the prompt to behave.
  • A real, dangerous mistake in production multi-tenant SaaS-style RAG systems — a leak here is a security incident, not just a quality bug.
  • A natural follow-up right after any RAG-pipeline or vector-DB question, the moment the system involves more than one customer.
🔥 Easy interview recall

Multi-tenant RAG = "filter by tenant BEFORE the search runs — never after."

Think: Every stored chunk carries a tenant_id tag as metadata Every query applies that filter inside the vector-store search itself — not as cleanup afterward

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Telling the model "only answer about Tenant A's data" in the prompt is not isolation. If the retrieved context already contains Tenant B's chunks, the model is reading them regardless of what the prompt instructs — the leak already happened at retrieval, before the prompt ever ran.

🔄 Likely Follow-up

"Why not just filter the results after retrieval, instead of during the search?" Filtering after the fact still runs the similarity search across every tenant's vectors, so it can hand back a smaller or wrong result set — and depending on the implementation, another tenant's chunks may briefly sit in application code that then has to remember to discard them. The filter has to be part of the vector-store query itself.

🎯 Say this in the interview — the exact lines to land

"In a multi-tenant RAG system, every stored chunk gets a tenant ID as metadata, and every retrieval query filters on that tenant ID inside the vector-store search itself — never as a step applied after the fact, and never left to the prompt to enforce."

  • Tenant ID → stored as metadata on every chunk, at ingest time.
  • Filter at search time → the actual security boundary — apply it inside the vector-store query itself.
  • Filtering after retrieval → too late — the wrong tenant's data may already be in front of application code.
  • Prompt instructions → not a security boundary — they don't stop already-retrieved data from being read.
📖 Explanation ▾

A multi-tenant RAG system is one application serving many separate customers, each over their own private documents, through a single shared deployment. The chunks from every tenant usually end up in the same underlying vector store — that's normal and efficient. The isolation problem is making sure a similarity search run on behalf of Tenant A's question can never return a chunk that belongs to Tenant B, no matter how semantically close that chunk happens to be to the query.

The fix is metadata filtering: every chunk is stored with a tenant identifier attached as metadata alongside its vector, and every retrieval query applies a filter on that identifier as part of the vector-store search itself — not as a separate step run afterward on the results. Filtering during the search means the wrong tenant's vectors are never compared against, scored, or returned in the first place.

This is exactly why metadata filtering alongside vector search matters as a vector-database capability, not a nice-to-have. In a multi-tenant system, it's the actual security mechanism the whole design depends on — not a convenience feature for narrowing search results.

💻 See the code ▾
Python 
# ingest — every chunk stores its tenant alongside the vector
index.upsert(
    vector=embed(chunk_text),
    metadata={"tenant_id": "tenant_a", "doc_id": doc_id}
)

The tenant ID travels with the chunk from the moment it's stored — there's nothing to add later.

Python 
# retrieval — the filter is part of the search call itself
results = index.query(
    vector=embed(user_query),
    filter={"tenant_id": "tenant_a"},  # ✅ applied during the search
    top_k=5
)

Tenant B's vectors are never compared against or scored — the filter runs inside the search, not after it.

🌍 Real-world example ▾

Think of a shared storage warehouse with lockers belonging to many different companies. Metadata filtering is the security guard checking each locker's tag before anyone opens it. Relying on the prompt instead is like handing someone the whole warehouse floor plan and just asking them nicely to only open Company A's lockers — they might comply, but nothing actually stopped them from opening Company B's.
