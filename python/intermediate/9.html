Type hints are a lint-time contract, not a runtime guarantee — Python still runs untyped underneath

"Why use type hints in a dynamically-typed language, and what's the actual difference between static and runtime checking?"

Why it matters ▾
  • Checks whether you understand that hints are tooling metadata, not enforcement — a very common misunderstanding in real codebases.
  • Comes up any time the conversation turns to code quality, CI setup, or "how do you catch bugs before production" in Python.
  • A natural opener before a deeper question about mypy/pyright configuration or Pydantic-style runtime validation.
🔥 Easy interview recall

mypy / pyright → checks hints before the code runs

Python interpreter → ignores hints completely at runtime

Think: def f(x: int) is a note to a tool, not a lock Python enforces.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Type hints don't stop a bad value from reaching a function. They're a static-analysis and documentation tool only — nothing stops an untyped caller, or a skipped/misconfigured type checker, from passing the wrong type at runtime, which is exactly why Pydantic-style runtime validation exists as a separate, complementary tool.

🔄 Likely Follow-up

"When is Protocol preferable to inheriting from an ABC?" When you just want to type-check "does this object have the right shape" without forcing every implementer to formally subclass anything — useful for third-party objects you don't control, or to avoid an unnecessary inheritance hierarchy.

🎯 Say this in the interview — the exact lines to land

"Type hints are checked by a separate static tool — mypy or pyright — never by the Python interpreter itself at runtime."

  • Static checking → mypy/pyright analyze the code ahead of time, catching mismatches before anything runs.
  • Runtime → Python itself ignores hints completely; nothing stops a bad value from reaching the function.
  • Protocol → type-checked duck typing — checks an object's shape without requiring it to inherit anything.
  • TypeVar → same type in, same type out — keeps a function generic instead of writing it once per type.
  • Pydantic → actually validates data at runtime — the complementary tool for values a static checker can never see, like malformed JSON.
📖 Explanation ▾

The typing module gives hints a vocabulary: Optional[X] means X | None; Union[A, B] means either type; modern generic syntax like list[str] or dict[str, int] (3.9+) means a list of strings or a dict from str to int; Any opts a spot out of type checking entirely. A TypeVar is a placeholder type that ties a function's return type to its input type, so one function stays generic instead of being rewritten per type. A Protocol declares a shape — the attributes/methods an object must have — without requiring formal inheritance, so a checker can validate duck typing structurally.

Static checking and runtime validation catch two different kinds of problems. mypy or pyright read the source ahead of time and flag a type mismatch across the whole codebase before a single line executes. A runtime validator like Pydantic instead checks the actual values while the program is running, so it can catch bad data — malformed JSON from a request, a missing field, a string where a number was expected — that a static checker, which only ever looks at code, can never see.

💻 See the code ▾
Python 
T = TypeVar("T")

def first(items: list[T]) -> T:
    return items[0]  # ✅ return type == input's item type

TypeVar ties the return type to whatever type went in — a checker knows first([1, 2, 3]) returns an int, not just "something".

Python 
class HasName(Protocol):
    name: str

def greet(thing: HasName) -> str:
    return f"Hi {thing.name}"

greet(some_user)  # ✅ checks — no inheritance from HasName needed

Protocol checks the shape only — some_user never has to inherit from HasName, it just needs a .name attribute.

🌍 Real-world example ▾

A function typed as def charge(amount: int) -> None: got called with a raw str straight from an unvalidated request body. The static checker existed in the repo, but nobody had wired it into CI, so it never actually ran against that code path — nothing caught the mismatch until it failed in production. Adding Pydantic validation right at the request boundary would have rejected the bad value the moment it arrived, instead of letting it travel deep into the codebase first.
