Filters, CORS, HTTPS & Logging — four pipeline names you can't afford to fumble

"What do filters, CORS, HTTPS redirection, and logging each actually do in the ASP.NET Core pipeline?"

Why it matters ▾
  • Four separate core-knowledge terms interviewers ask about individually — mixing one up costs you an easy point.
  • CORS is one of the most misunderstood security terms in web interviews; knowing exactly what it protects is a real differentiator.
  • Where HTTPS redirection sits, and how logging plugs into DI, are both quick "order of the pipeline" questions.
🔥 Easy interview recall

Filters → hooks around an action, before/after

CORS → opts in which origins can read the response

HTTPS → redirects to HTTPS early, before anything else

Logging → ILogger<T> writes, a provider decides where

Think: CORS protects the browser, not the server — a curl request ignores it entirely.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming CORS protects the server. It protects the USER'S BROWSER SESSION on other sites — it decides who's allowed to read the response in a browser, not whether the request happens; a non-browser client like curl or a backend service ignores it entirely.

🔄 Likely Follow-up

"Does a backend service calling this API need to worry about CORS?" No — CORS is enforced by the browser, not the server, so a server-to-server call never triggers a CORS check at all.

🎯 Say this in the interview — the exact lines to land

"Filters are attribute-driven hooks that run before or after an action. CORS is a browser-enforced rule that opts specific origins into reading my API's response. HTTPS redirection sits early in the pipeline so nothing downstream ever handles unencrypted traffic. Logging is injected as ILogger<T> and routed to whichever provider is configured, without the app code knowing where it ends up."

  • Filters → hooks before/after an action — action, exception, and authorization filters all live under this umbrella.
  • CORS → protects the browser, not the server — it decides who can read the response, not who can send the request.
  • HTTPS redirection → enforced early in the pipeline — before routing or auth ever run.
  • Logging → injected as ILogger<T> — the app code never knows which provider is actually recording it.
📖 Explanation ▾

Filters are the general umbrella term for a hook that runs at a specific point around action execution — before it, after it, or around an exception. Action filters, exception filters, and authorization filters are all specific filter types that live under this same idea; the MVC-specific types go deeper on their own page, this one just needs the umbrella name.

CORS (Cross-Origin Resource Sharing) exists because a browser's same-origin policy would otherwise block a script on siteA.com from reading a response from api.siteB.com — which is exactly what stops a malicious page from silently calling another site and reading back the victim's logged-in data. Enabling CORS on the server explicitly opts specific origins into being allowed to do that from a browser; it never affects a request that isn't coming from a browser page.

HTTPS redirection — app.UseHttpsRedirection() — is middleware placed early in the pipeline. Any request that arrives over plain HTTP is redirected to HTTPS before anything else gets a chance to process it, so no later middleware, filter, or action ever has to handle unencrypted traffic.

Logging works through the same dependency injection every other service uses: an ILogger<T> is injected into a class, and app code just calls _logger.LogInformation(...). ASP.NET Core's logging pipeline routes that call to whichever "providers" are configured — console, a file, Application Insights — without the calling code knowing or caring which one.

💻 See the code ▾
C# 
public class LogActionFilter : IActionFilter
{
    public void OnActionExecuting(ActionExecutingContext ctx)
        // runs BEFORE the action
        => Console.WriteLine("before");

    public void OnActionExecuted(ActionExecutedContext ctx)
        // runs AFTER the action
        => Console.WriteLine("after");
}

IActionFilter is one filter type among several — action, exception, and authorization filters all share this same before/after shape.

C# 
app.UseCors(policy => policy
    .WithOrigins("https://trusted-site.com")   // ✅ explicitly allowed origin
    .AllowAnyMethod());

Only a browser script running on trusted-site.com can read this response — every other origin is blocked by the browser, not by this line.

C# 
var app = builder.Build();
app.UseHttpsRedirection();   // ✅ runs early — before routing, auth, anything else
app.UseRouting();

Placed early on purpose — nothing downstream ever gets a chance to handle the unencrypted request.

C# 
public class OrderService
{
    private readonly ILogger<OrderService> _logger;  // injected like any other service

    public OrderService(ILogger<OrderService> logger) => _logger = logger;

    public void Ship() => _logger.LogInformation("Order shipped");
}

OrderService never knows or cares whether this line ends up in the console, a file, or Application Insights.

🌍 Real-world example ▾

Four guard rails on the same road. Filters are checkpoints along the route, CORS is the border guard deciding who's allowed to read what comes back, HTTPS is the toll gate you pass through before you're even on the road, and logging is the dashcam quietly recording everything, whichever lane you're in.
