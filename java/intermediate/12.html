throw vs. throws — raising one now, or declaring the possibility

"What's the difference between throw and throws?"

Why it matters ▾
🎯 throw
❗ ProblemCode sometimes reaches a state where continuing would be wrong — invalid input, a broken invariant — and needs a way to immediately stop normal execution and hand control to whatever is prepared to deal with it.
✅ Solutionthrow raises one specific exception instance, right there, at that exact line — execution of that method stops immediately and control jumps to a matching catch or propagates up the call stack.
Recallthrow = actually doing it, right now.
📋 throws
❗ ProblemA method that might propagate a checked exception needs a way to tell its callers "this can fail this way" — without that signal, a caller has no idea which checked exceptions it needs to handle, and the compiler couldn't enforce anything.
✅ Solutionthrows lists the checked exceptions a method might propagate, directly on its signature — pure documentation for the compiler, it never raises anything itself.
Recallthrows = just a label on the signature.
🔥 Easy interview recall

throw → raises it, right now

throws → declares it, signature only

Think: throw is a verb — do it. throws is a label — might happen.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

throws doesn't catch or handle anything. A method declaring throws IOException still crashes the program with an uncaught exception if nothing up the call chain actually catches it — declaring it only satisfies the compiler.

🔄 Likely Follow-up

"Can a method have throws without ever using throw itself?" Yes — throws just means "this might propagate that exception," often because it calls another method that declares it; the method itself never needs its own throw statement.

🎯 Say this in the interview — the exact lines to land

"throw is a statement that actually raises an exception instance, right now, at that line. throws is a declaration on a method signature, listing which checked exceptions it might propagate — it doesn't raise anything itself."

  • throw → an action, raises an exception instance immediately.
  • throws → a declaration, lives only on the method signature.
  • throws never handles anything → still crashes if uncaught.
  • A method can have throws → without its own throw, if it calls something that declares it.
📖 Explanation ▾

throw is a statement, exactly like return — it does something, at a specific line, the moment execution reaches it. Writing throw new IllegalStateException("...") creates that exception object and immediately hands control to the nearest matching catch, skipping the rest of the current method entirely.

throws is not a statement at all — it's part of a method's signature, the same category as the return type or parameter list. It tells the compiler (and every caller) "this method might propagate one of these checked exceptions," so the compiler can enforce that callers deal with it. A method can declare throws and never contain a single throw of its own, if the exception actually comes from something it calls.

Only checked exceptions ever strictly need a throws declaration — an unchecked exception can be thrown from anywhere without the compiler requiring it to be listed, though declaring it anyway is sometimes used purely for documentation.

💻 See the code ▾
Java 
void withdraw(double amt) throws InsufficientFundsException {
    if (amt > balance)
        throw new InsufficientFundsException();  // ✅ the action
    balance -= amt;
}

throws is the label, throw is the thing that actually happens.

Java 
void loadConfig(String path) throws IOException {
    Files.readAllLines(Path.of(path));  // this call may throw it
}

No throw statement here at all — throws just propagates a call's own exception.

Java 
void setAge(int age) {   // no throws — unchecked doesn't need it
    if (age < 0) throw new IllegalArgumentException();  // ✅ compiles fine
}

An unchecked throw never needs a matching throws — only checked exceptions do.

🧭 Use Cases — recognize these when they happen to you ▾
1 Validating input and stopping execution immediately

This is the #1 scenario you'll actually run into. The moment input is known to be invalid, throw stops execution right there instead of letting bad data flow further into the method.

RememberStop right now → throw.
2 Calling a checked-exception-throwing API and re-declaring it

A method that intentionally doesn't want to handle a checked exception itself just re-declares it with throws, pushing the decision one level up the call chain instead.

RememberDon't want to handle it here → declare it, don't catch it.
3 You assume throws Exception on a signature somehow "handles" the error

Adding throws Exception to satisfy the compiler does nothing at runtime — if nothing up the call chain actually catches it, the program still terminates with an uncaught exception exactly as if nothing was declared.

RememberDeclaring it ≠ handling it.
🌍 Real-world example ▾

A code reviewer asks why a method signature lists throws SQLException even though the method body has no throw statement anywhere. It's because the method calls a JDBC method that declares SQLException itself — that declaration has to propagate up the call chain, by this method's own throws, until something finally catches it.
