GroupBy vs. ToLookup — deferred regrouping, or a built structure?

"Both group elements by a key — what's the real difference between GroupBy and ToLookup?"

Why it matters ▾
🔗 Grouping twice
❗ ProblemLooking up a group by key repeatedly, or enumerating the same grouped query more than once, either re-runs the entire grouping pass each time (if it's still a lazy GroupBy) or risks an exception on a missing key (if it's mistaken for a Dictionary).
✅ SolutionToLookup builds the whole grouped structure once, immediately, and behaves like a read-only, multi-value dictionary you can index into directly (lookup[key]) — indexing a missing key never throws, it just returns an empty sequence, which is exactly the safety GroupBy doesn't give you on repeated access.
RecallGroupBy = re-groups every time. ToLookup = built once, indexed safely forever after.
🔥 Easy interview recall

GroupBy → deferred, re-groups every enumeration

ToLookup → immediate, built once, indexed like a dictionary

Think: lookup[missingKey] never throws — it just hands back an empty sequence.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A Lookup is not a Dictionary. Indexing a missing key on a Lookup never throws — it just hands back an empty sequence; a Dictionary would throw KeyNotFoundException for the same missing key.

🔄 Likely Follow-up

"So is ToLookup always the safer choice?" Not automatically — it forces an immediate, full pass over the entire source up front, even if you only ever need one key's group, where a lazy GroupBy enumerated once would do the same amount of real work with none of the upfront cost if it's never enumerated twice.

🎯 Say this in the interview — the exact lines to land

"GroupBy is deferred — it re-runs the grouping pass every time the result is enumerated, same as any other LINQ operator. ToLookup is immediate — it builds the whole grouped structure once, right away, and behaves like a read-only, multi-value dictionary: indexing it with a missing key never throws, it just returns an empty sequence."

  • GroupBy → deferred, re-groups on every enumeration.
  • ToLookup → immediate, grouped once up front.
  • lookup[key] → indexable directly, like a dictionary.
  • Missing key → empty sequence, never an exception.
📖 Explanation ▾

GroupBy behaves like every other sequence-producing LINQ operator: calling it builds a plan, not a result. Enumerating that plan — a foreach, a ToList(), a second enumeration of the same variable — runs the entire grouping pass over the source again, from scratch, every single time.

ToLookup is a materializing operator, like ToList() or ToDictionary() — it forces an immediate, one-time pass over the entire source and returns a concrete ILookup<TKey,TElement>. From that point on, lookup[someKey] is a direct index into an already-built structure — no re-grouping, no re-reading the source.

The key behavioral difference beyond timing is what a missing key does. A Lookup is purpose-built for the "zero or more values per key" case — indexing a key with no matches just returns an empty sequence, the same way GroupBy simply wouldn't produce a group for a key with no matches. Neither one throws for "key not found" — that behavior is specific to a true Dictionary<TKey,TValue>.

💻 See the code ▾
C# 
var grouped = orders.GroupBy(o => o.CustomerId);   // still deferred

foreach (var g in grouped) { }   // ❌ runs the grouping pass — once
foreach (var g in grouped) { }   // ❌ runs it AGAIN — twice total

Same as any lazy query — two enumerations, two full grouping passes.

C# 
var lookup = orders.ToLookup(o => o.CustomerId);   // ✅ grouped once, right now

var mine = lookup[42];       // ✅ real key — the matching orders
var none = lookup[-1];       // ✅ missing key — empty sequence, no exception

lookup[-1] is safe by design — a Lookup never throws for a key with no matches.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to look up several different groups by key, repeatedly, across a request

Building the lookup once pays for the grouping pass a single time; every key access after that is a direct index, with no risk of re-grouping cost multiplying with each lookup.

RememberMany repeated key lookups → build a ToLookup once.
2 You enumerate every group once, in a single pass, and never look anything up by key again

A single foreach over a GroupBy result, with no second enumeration, does the same amount of work as ToLookup would — plain GroupBy is the simpler, equally correct choice here.

RememberEnumerated exactly once → plain GroupBy is enough.
3 You treat a Lookup's missing-key behavior like a Dictionary's

Wrapping a Lookup indexer in a try/catch for a missing key is dead code — it will never throw. Checking .Any() on the returned sequence (or just iterating it, since it's empty either way) is the correct pattern instead.

RememberLookup ≠ Dictionary — a missing key is empty, not an exception.
🌍 Real-world example ▾

A report page needs each customer's orders, looked up by customer ID, dozens of times while rendering the page. Building a ToLookup once at the top of the request and indexing into it for every customer avoids re-grouping the whole order list on every single render call.
