Microsoft.Extensions.AI vs. Semantic Kernel — know which layer you're coding against

"What's the difference between Microsoft.Extensions.AI and Semantic Kernel, and why would a .NET application use both?"

Why it matters ▾
  • This is the site's own .NET differentiator: it's the idiomatic, first-party way to build GenAI features in a .NET codebase, not a Python-first mental model bolted on.
  • Comes up any time an interviewer asks "how would you add an LLM call to an existing ASP.NET Core service" — the expected answer routes through a registered IChatClient, not a hardcoded provider SDK.
  • A natural follow-up once tool-calling and the agent loop have already come up — this is what that pattern looks like on the .NET side.
🔥 Easy interview recall

Microsoft.Extensions.AI → the wire — one interface (IChatClient), any provider

Semantic Kernel → the app — plugins, planner, memory on top

Think: IChatClient is the generic HTTP client. Semantic Kernel is the web framework built on top of it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

They're not two competing SDKs to pick between. Semantic Kernel is built to sit on top of IChatClient (or another client) — choosing Semantic Kernel doesn't mean giving up the provider-agnostic abstraction underneath, it means adding an orchestration layer on top of it.

🔄 Likely Follow-up

"So do you always need Semantic Kernel?" No — for a single chat call, IChatClient alone is enough. Reach for Semantic Kernel once you need plugins the model can call, a planner to sequence them, or memory across a conversation.

🎯 Say this in the interview — the exact lines to land

"Microsoft.Extensions.AI gives .NET a single IChatClient abstraction, so application code depends on one interface instead of a specific provider's SDK — that's what makes swapping providers or faking the client in a test easy. Semantic Kernel is the higher-level orchestration framework built on top of that same idea, adding plugins, planners, and memory. Together they're the idiomatic, first-party way to build GenAI features in .NET instead of reaching for a Python-first framework."

  • Semantic Kernel → adds orchestration — plugins (tool-calling), planners, memory.
  • Layering → Semantic Kernel sits on IChatClient, it doesn't replace it.
  • Your edge → first-party, idiomatic .NET GenAI — no need to borrow a Python-first framework's mental model.
📖 Explanation ▾

Microsoft.Extensions.AI is a set of unified abstractions — most notably IChatClient — for talking to different LLM providers from .NET code through one consistent interface. Application code depends on IChatClient, not on any one provider's specific SDK type, so swapping providers later or substituting a fake implementation in a test doesn't touch the calling code at all.

Semantic Kernel is a higher-level .NET framework built for orchestrating GenAI applications on top of that same idea. It adds plugins — reusable functions the model can call, the .NET equivalent of tool-calling — planners, which break a goal into a sequence of plugin calls, and memory, for storing and retrieving context across a conversation or session. None of that requires giving up the provider-agnostic client underneath; Semantic Kernel can be built on IChatClient (or another client) rather than instead of it.

💻 See the code ▾
C# 
public class TicketSummarizer
{
    private readonly IChatClient _chat;   // ✅ depends on the abstraction

    public TicketSummarizer(IChatClient chat) => _chat = chat;

    public async Task<string> SummarizeAsync(string ticketText)
    {
        var response = await _chat.GetResponseAsync(ticketText);
        return response.Text;
    }
}

The constructor asks for IChatClient, not an OpenAI-specific (or any other provider-specific) client type — the concrete provider is registered elsewhere, the same way any other dependency is.

C# 
var builder = Kernel.CreateBuilder();
builder.Plugins.AddFromType<TicketPlugin>();   // ✅ registers a plugin the model can call
Kernel kernel = builder.Build();

public class TicketPlugin
{
    [KernelFunction, Description("Looks up a ticket by its ID")]
    public Ticket GetTicket(int ticketId) => _repo.Find(ticketId);
}

A [KernelFunction] is the .NET shape of a callable tool — Semantic Kernel decides when to call it, the same pattern as tool-calling, just wired through the kernel instead of a raw provider API.

🌍 Real-world example ▾

A generic HTTP client vs. a full web framework built on top of it. IChatClient is like a generic HTTP client — one consistent way to make a call, regardless of which server answers it. Semantic Kernel is like a full application framework built on top of that same client — routing, conventions, and reusable pieces (plugins, planners, memory) layered on, not a replacement for the client doing the actual talking.
