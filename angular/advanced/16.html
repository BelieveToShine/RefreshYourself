One page, two renders — what happens when they stop agreeing

Users started seeing hydration errors right after SSR was introduced — what's the actual, ordered way to investigate?

Why it matters ▾
  • Hydration-mismatch warnings spiking right after an SSR rollout is one of the most common real production alerts on an Angular app — not a rare edge case.
  • Interviewers use this to hear an actual ordered investigation, not just the definition of hydration.
  • A common trap: blaming SSR itself for a slowness problem that was already there before SSR ever existed, just less visible.
🔥 Easy interview recall

⏰ Time/random → computed twice, can disagree

🌐 Browser-only API → behaves differently on the server

🔀 Different data → a race, not a bug in the render itself

Think: every real hydration bug is the server and the client computing the same thing, twice, differently — the fix is always doing it once and sharing the result.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Fast on the server, slow right after hydration" does not mean SSR is broken. SSR already did its job — a real first paint — a heavy hydration is a separate bundle-size/initialization-cost problem that existed before SSR too, just invisible until there was a fast-looking page to notice the gap against.

🔄 Likely Follow-up

"If a hydration mismatch is found, is disabling SSR for that page ever the right long-term fix?" It's a reasonable short-term mitigation to stop user-visible errors immediately, but the root cause — a non-deterministic value, unguarded browser-only code, or a data race — is still there; disabling SSR permanently just gives up that page's fast-first-paint and SEO benefits to avoid diagnosing a usually well-understood class of bug.

🎯 Say this in the interview — the exact lines to land

"Every real hydration bug comes down to the server and the client computing the same thing differently. I'd check, in order: a non-deterministic value read directly during render, browser-only code behaving differently in each environment, or genuinely different data between the server's render and the client's hydration — then fix it by computing that value once and sharing it, not by disabling SSR."

  • Non-deterministic value → check first — a clock, random value, or timezone computed independently on each side.
  • Browser-only API → guard with a platform check before ever touching window/document/localStorage.
  • Different data → a race condition in data loading, not a rendering mistake.
  • Fast-then-slow → not an SSR bug — it's a pre-existing bundle/initialization cost, now visible.
  • The real fix → compute once, pass through as resolved data — never recompute independently in two environments that can disagree.
📖 Explanation ▾

Start every hydration investigation the same way: compare the actual server-rendered HTML — view page source, or the raw SSR response — against what the client would independently render for the same state. The gap between those two is almost always one of three things, checked in this order because they're roughly this common in real codebases: a non-deterministic value read directly during rendering (current time, a random value, anything timezone-dependent), browser-only code that behaves differently — or throws — during SSR, or genuinely different data because of a race between when the server rendered and when the client's own data became available.

A separate symptom — the page looks ready immediately but doesn't feel interactive for a moment after — isn't a hydration mismatch at all. SSR solved the first-paint problem; it never touched the underlying bundle-size or component-initialization cost. That cost is now just easier to notice, because there's a fast-looking page sitting there while hydration and JS initialization finish. Investigate it exactly like any other performance issue — bundle size, unnecessary eager work, whether incremental hydration or @defer could shrink how much has to hydrate before the page feels ready — not as something wrong with SSR itself.

For browser-only code specifically, the fix is a guard, not a removal: find every place that unconditionally touches window/document/localStorage/navigator or a browser-assuming library at construction or render time, and check a platform indicator before running it — deferring the logic to a point that's confirmed safe, rather than disabling SSR for that whole section.

Same idea as the relative-time label below — anything read from the clock during rendering is computed twice, once per environment.

if (isPlatformBrowser(this.platformId)) {
  // ✅ only reached in the browser — safe to touch localStorage here
  const theme = localStorage.getItem('theme');
}

Guard the specific unsafe line, not the whole component's SSR — that keeps the fast first paint for everything around it.

🌍 Real-world scenario ▾

Shortly after enabling SSR, error logs show a spike in hydration-mismatch warnings on a specific product page. Comparing the raw server-rendered HTML against the client's own render for the same product finds a "time since this review was posted" label (e.g. "2 hours ago") computed with Date arithmetic directly inside the template's render logic — the server computes it at request time, the client recomputes it independently a moment later during hydration, and the two can disagree by enough to cross a rounding boundary ("2 hours ago" vs. "3 hours ago").

The direct fix: compute the relative-time string once, on the server, and pass it through as already-resolved data the client hydrates against — eliminating the mismatch at its actual source instead of working around the symptom.
