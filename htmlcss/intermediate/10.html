@container — when the same component needs two different looks at one screen width

"What's the actual difference between a media query and a container query, and when would you reach for a container query instead of a media query?"

Why it matters ▾
🖥️ @media
❗ ProblemA page still needs to adapt at the whole-page level, but @media only ever has one thing to read: the browser's own viewport width or height.
✅ SolutionThat's exactly what it's built for — page-level layout, no setup needed, always active, checking the screen itself rather than any one element's own space.
Recall@media = viewport decides, best for whole-page layout.
📦 @container
❗ ProblemA single reusable component — a card used in both a narrow sidebar and a wide main column — needs two different layouts at the exact same viewport width, which @media can't tell apart since it only ever asks the screen.
✅ SolutionAn ancestor gets container-type first, then @container reads that ancestor's own width — so the identical component renders compact in one spot and expanded in another, correctly, at the same time.
Recall@container = the container decides, best for one reusable component used in multiple spots.
🔥 Easy interview recall

@media → viewport decides

@container → container decides

Think: @media only ever asks the screen. @container asks the box around the element instead.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A container query is not just "a smaller media query." It only works on an ancestor you've actually turned into a size container with container-type — with no container declared above it, an @container rule simply never matches, and nothing happens.

🔄 Likely Follow-up

"Are there container-relative units too, like viewport units?" Yes — cqw/cqh/cqi/cqb (plus cqmin/cqmax) size things relative to the query container instead of the viewport, so font-size or spacing can scale with the container the same way vw/vh scale with the screen.

🎯 Say this in the interview — the exact lines to land

"A media query only ever reads the browser viewport, so it can't tell two differently-sized placements of the same component apart. A container query fixes that: I mark an ancestor with container-type to turn it into a size container, then an @container rule reads that ancestor's own width, so the exact same component can render differently depending on how much space it actually has, no matter where it sits on the page."

  • container-type: inline-size on the ancestor → turns it into something that can be queried by width.
  • @container → reads like @media, but checks the container's width, never the screen's.
  • Best fit → a reusable component that needs to look right wherever it's dropped — sidebar, main column, modal.
  • cqw/cqh/cqi/cqb → container-relative sizing units, the same idea as vw/vh for the viewport.
  • Not a replacement → page-level layout still uses media queries; container queries win at the component level.
📖 Explanation ▾

A media query only ever reads one thing: the browser's viewport width or height — see Responsive Design for the full media-query rundown. That's fine for page-level layout, but it means a media query has no way to know how much space one specific element actually has — only how big the whole screen is. A container query answers a different question: instead of the viewport, it reads the width (or height) of the element's own nearest ancestor container, wherever that container happens to sit on the page.

Turning an element into something query-able is a two-step deal. First, an ancestor gets container-type: inline-size, which tells the browser "let elements inside this one query my width." Second, an @container rule — written just like @media — targets that nearest ancestor container instead of the screen. container-type: size exists too, for querying height as well as width, but it's used far less often since it usually needs the container's own height fixed some other way first.

The case container queries actually solve, that media queries can't, is a single reusable component rendered in more than one spot — a card that's genuinely narrow in a sidebar and genuinely wide in the main column, at the exact same viewport width. A media query can only ever give both placements the same answer, because it only ever asks the screen. A container query gives each placement its own correct answer, because it asks each placement's own box.

🧠 Visual Mental Model — how container-type and @container connect
💻 See the code ▾
CSS 
/* turn the ancestor into a size container */
.card-slot {
  container-type: inline-size;   // query by width
  container-name: card-slot;     // optional — clearer once containers nest
}

/* the card reacts to ITS OWN container's width, not the screen's */
@container card-slot (min-width: 400px) {
  .card { display: grid; grid-template-columns: 120px 1fr; }
}

container-name is optional — an unnamed @container just queries the nearest ancestor that has a container-type set; naming it matters once containers are nested inside containers.

CSS 
/* only ever sees the viewport, not this card's own space */
@media (min-width: 900px) {
  .card { grid-template-columns: 120px 1fr; }  // fires the same everywhere on a wide screen
}

/* reacts to the space THIS card actually has */
@container (min-width: 400px) {
  .card { grid-template-columns: 120px 1fr; }  // only fires where the card's own box is wide enough
}

Same card, same breakpoint number — but the @media version fires (or doesn't) based on the whole screen, while the @container version fires based on the card's own container, so a narrow sidebar and a wide main area can get different, correct results at the exact same viewport width.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your card component gets dropped into both a narrow sidebar and a wide main column

This is the #1 scenario you'll actually run into — the exact one the main diagram above shows: same viewport, two different-sized placements of the same component. @container lets each placement's own ancestor width decide the layout, so the sidebar renders compact and the main column renders expanded, correctly, at the same time.

RememberSame component, different container width → let @container decide, not @media.
2 You want font-size or spacing to scale with the container's own width, not the screen's

Container-relative units — cqw/cqh/cqi/cqb, plus cqmin/cqmax — work the same way vw/vh do for the viewport, but measured against the query container instead. Spacing or type size can then scale smoothly as that one container grows or shrinks, independent of the screen.

Remembercqw/cqh/cqi/cqb → same idea as vw/vh, just measured against the container.
3 An @container rule is written, but nothing happens

A container query only works on an ancestor that's actually been turned into a size container with container-type — with none declared above it, the @container rule simply never matches. It's easy to mistake this for a typo in the query itself rather than a missing container-type declaration up the tree. A common trap — candidates often assume the rule alone is enough.

RememberNo container-type on an ancestor → @container never matches, silently.
🌍 Real-world example ▾

A photo frame that reads its own wall space, not the house. Picture a frame that automatically switches between a portrait and a landscape layout based on the size of the wall it's actually mounted on, not the size of the whole house. A media query only knows the house's total footprint — the viewport. A container query lets the frame check its own wall space directly, so two identical frames in two different rooms of the same house can pick different, correct layouts.
