🔥 Python · Basic · Must Know

Python doesn't pass by value or by reference — it passes object references, and mutability is what actually matters

"Are function arguments passed by value or by reference in Python? What are *args and **kwargs?"

Why it matters ▾
  • Almost every Python interview opens a functions question this way — it's the fastest way to check whether someone actually understands the object model, not just the syntax.
  • Explains a real bug pattern: passing a list or dict into a function and being surprised the caller's own copy changed too.
  • Usually followed immediately by "what are *args and **kwargs?" — worth having both answers ready together.
🔥 Easy interview recall

Mutate → shared object changes, caller sees it

Rebind → local name points elsewhere, caller never knows

Think: Python passes an object reference — same object in, so mutation shows through. Reassigning the parameter just relabels the local name, never the caller's variable.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Python is not "pass by reference." If it were, reassigning the parameter inside the function would rebind the caller's variable too — it doesn't; only mutating a shared, mutable object through the parameter is visible outside the function.

🔄 Likely Follow-up

"What's the difference between mutating and rebinding a parameter inside a function?" Mutating (lst.append(x), lst[0] = x) changes the shared object, so the caller sees it; rebinding (lst = [...]) just points the local name at a new object, which the caller never sees.

🎯 Say this in the interview — the exact lines to land

"It's pass-by-object-reference: mutation is visible to the caller, rebinding is not — 'pass by value' or 'pass by reference' is the wrong frame entirely."

  • An object reference is passed in — the caller's variable and the parameter name point at the same object.
  • Mutating that shared object (.append(), lst[0] = x) is visible to the caller.
  • Rebinding the parameter (lst = [...]) only repoints the local name — invisible to the caller.
  • *args collects extra positionals into a tuple; **kwargs collects extra keywords into a dict.
  • Positional-only (/) and keyword-only (*) parameters are an API-design tool, not just syntax trivia — they control what a caller can rely on.
📖 Explanation ▾

Functions are first-class objects in Python — assign one to a variable, pass it into another function, return it from a function, or store it in a list or dict, exactly like any other value.

Python's real argument-passing model is pass-by-object-reference (also called pass-by-assignment) — neither classic "by value" (which would copy the object) nor classic "by reference" (which would let the callee rebind the caller's own variable) describes it exactly. A parameter starts out pointing at the exact same object the caller's variable points at, so mutating that object through the parameter is visible to the caller. Rebinding the parameter name to a different object only changes what the local name points at — it never touches the caller's variable.

*args collects any extra positional arguments into a tuple; **kwargs collects extra keyword arguments into a dict. A signature like def f(a, b, /, c, *, d): adds two more controls: everything before / is positional-only (callers can't name it, so it isn't part of the public API and can be renamed later without breaking anyone), and everything after * is keyword-only (callers must name it, which forces clarity at the call site).

💻 See the code ▾
Python 
def append_one(lst):
    lst.append(1)

my_list = [0]
append_one(my_list)
print(my_list)

What does this print, and why? [0, 1] — the function receives a reference to the SAME list object; .append() mutates that shared object, so the caller sees the change.

Python 
def rebind(lst):
    lst = [99]  # rebinds the LOCAL name only

my_list = [0]
rebind(my_list)
print(my_list)

Still [0] — rebind() pointed its own local lst at a brand-new list; my_list in the caller never changed.

🌍 Real-world example ▾

Handing someone the key to your actual apartment is mutation — anything they do inside changes the same place you live in. Handing them keys to a completely different apartment (rebinding) never touches your place at all, no matter what they do with those new keys.

This exact mechanism — a shared mutable object surviving between calls — is also what causes the classic mutable-default-argument trap, covered on the Mutable vs. Immutable page (Intermediate).
