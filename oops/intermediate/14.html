Law of Demeter — talk to friends, not strangers

What is the Law of Demeter, and what's wrong with a.GetB().GetC().DoIt()?

Why it matters ▾
🚂 Law of Demeter
❗ ProblemCode like order.GetCustomer().GetAddress().City makes the caller know how Order, Customer, and Address are linked. Change any link and every such caller breaks.
✅ SolutionAsk Order for what you need (order.GetShippingCity()). Only Order knows how it gets there, so the inside can change freely.
RecallDemeter = don't reach through objects; ask the one you know.
🔥 Easy interview recall

a.GetB().GetC().Do() → train wreck

a.DoIt() → tell, don't ask

Think: Law of Demeter says: ask the waiter, don't walk into the kitchen to open the fridge.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The rule means never use more than one dot." It is about reaching through an object's internal structure, not counting dots. A fluent chain that keeps returning the same kind of object, like LINQ or a builder, is usually fine.

🔄 Likely Follow-up

"What does 'tell, don't ask' mean?" Tell an object to do the work instead of pulling its data out and deciding yourself. The logic then lives next to the data it uses.

🎯 Say this in the interview — the exact lines to land

"The Law of Demeter says a method should only talk to its direct collaborators, not reach through them. Long chains like a.GetB().GetC().DoIt() tie the caller to the whole structure, so I add a method on the nearest object that does the job — tell, don't ask."

  • Rule → talk only to your immediate collaborators.
  • Smell → a chain that reaches through objects (a train wreck).
  • Fix → add a method on the nearest object that does the job.
  • Careful → fluent same-type chains aren't the problem, structure leaks are.
📖 Explanation ▾

A train wreck is a chain that walks through several objects: order.GetCustomer().GetAddress().City. The caller now depends on Order, Customer, and Address, plus how they connect. If Address moves inside Customer, this caller breaks even though it never cared.

The fix is tell, don't ask. Give Order a method like GetShippingCity() that does the digging inside. The caller depends on one object. This is encapsulation applied across objects — the same idea, one level up.

Do not count dots mechanically. Chaining on a value that stays the same kind (a LINQ query, a builder) does not expose anyone's internals. The smell is reaching into the structure of other objects.

💻 See the code ▾
C# 
// ❌ caller knows Order → Customer → Address
var city = order.GetCustomer().GetAddress().City;

Three objects and their links are now baked into the caller.

C# 
public class Order
{
    private readonly Customer _customer;

    public string GetShippingCity() => _customer.GetShippingCity();   // ✅ Order talks to its own field
}

var city = order.GetShippingCity();   // ✅ caller knows only Order

The caller asks one friend; the digging stays inside.

🌍 Real-world example ▾

Billing code needs the customer's city, and the address model is about to move into its own type. If many callers chain through Order, all of them break. If they call order.GetShippingCity(), you change one method.
