🔥 Python · Intermediate · Must Know

A default argument is evaluated ONCE, at function-definition time — not on every call

Python 
def add_item(item, items=[]):
    items.append(item)
    return items

"What happens across repeated calls to add_item(1) then add_item(2), and why?"

Why it matters ▾
  • Tests whether you actually know a default argument is built once, at def-time, not rebuilt on every call.
  • Explains a real class of "why does my function remember state from a completely unrelated call" bugs.
  • One of the most commonly cited Python interview gotchas — expect it live, as a predict-the-output question, not a plain definition ask.
🔥 Easy interview recall

Default args = "built once, at def-time — never rebuilt per call."

Think: add_item(1) → [1] add_item(2) → [1, 2] — not [2] — same list, reused

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

add_item(2) does not return [2]. Both calls share the exact same default list object created once at def-time, so it returns [1, 2] — state silently persists across calls that look completely unrelated.

🔄 Likely Follow-up

"Why does a tuple containing a mutable list still count as immutable?" Immutability is about the container's own structure — a tuple can never be resized or have its slots reassigned. Mutating what's inside one of those slots is a completely different operation, and it's still allowed.

🎯 Say this in the interview — the exact lines to land

"Default arguments are evaluated once, at def-time, not on every call — so a mutable default like a list or dict gets shared and accumulates state across every call that doesn't pass its own. Never use a mutable default."

  • items=None sentinel → the standard fix — check for None inside the function and build a fresh list per call.
  • Immutable → int, float, bool, str, tuple, frozenset, None Mutable → list, dict, set, bytearray
  • A tuple holding a list → still immutable — only its own slots can't be reassigned, not what's inside them.
📖 Explanation ▾

Python evaluates a function's default argument values exactly once — when the def statement itself runs, not each time the function is later called. That same default object is then reused as-is on every call that doesn't supply its own value for that parameter. For an immutable default (a number, a string, None) this is invisible, because nothing can change that object in place — the only way to get a different value is to rebind the name to a brand-new object. A mutable default behaves differently: append(), update(), and other in-place operations mutate the one shared object directly, so state from one call leaks straight into the next.

The standard fix is the None-sentinel pattern: default the parameter to None, then build a fresh mutable object inside the function body only when one wasn't supplied.

Immutable built-insMutable built-ins
int, float, complex, bool, str, tuple, frozenset, Nonelist, dict, set, bytearray

A tuple containing a list is still an immutable tuple — you can never reassign what one of its slots points to, and it can never grow or shrink. But the list sitting inside that slot can still be mutated in place, because that's a change to the list, not to the tuple. Immutability describes a container's own structure and references, not everything it happens to hold.

💻 See the code ▾
Python 
def add_item(item, items=None):
    items = items if items is not None else []  # ✅ fresh list per call
    items.append(item)
    return items

Every call that skips items now gets its own fresh list — nothing carries over from a previous call.

🌍 Real-world example ▾

This exact bug causes real "why does my function remember state from a previous, unrelated call" production issues. It shows up most often in test suites: a helper function with a mutable default quietly accumulates data across every test that calls it without passing its own list or dict, so tests start passing or failing depending on run order — often the first clue something's wrong.
