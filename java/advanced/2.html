Why your own java.lang.String never gets a chance — parent-first delegation

"How does the classloader delegation hierarchy prevent a user-defined java.lang.String from shadowing the real one?"

Why it matters ▾
🏛️ Delegation Hierarchy
❗ ProblemIf a classloader tried loading a class itself before asking its parent, a stray classpath entry named java.lang.String could load in place of the JDK's real, security-critical core type.
✅ SolutionEvery classloader asks its parent first — Bootstrap → Platform → Application/System — so the trusted ancestor always gets the first chance, and a user-defined core class never even gets considered.
RecallParent-first = ask up the chain before ever trying yourself.
⏳ Lazy Initialization
❗ ProblemAssuming a class's static code already ran just because it's referenced in an import or type declaration leads to wrong expectations about exactly when its side effects fire.
✅ SolutionA class initializes lazily, only on first "active use" — the first instantiation, a static method/field access, or a subclass being initialized — never from simply appearing in source.
RecallReferenced in code ≠ initialized. Only active use triggers it.
🔥 Easy interview recall

Bootstrap → core JDK classes, asked first

Platform → JDK modules, asked second

Application/System → your classpath, asked last

Think: every loader asks its parent first — your own java.lang.String never gets a turn, because Bootstrap already answered.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Defining your own java.lang.String on the classpath does not shadow the real one. Parent-first delegation means the Application loader asks Bootstrap before trying anything itself — Bootstrap already has the real class, so your copy is simply never reached (and attempting it directly throws a security exception for classes in the java.* package).

🔄 Likely Follow-up

"So when exactly does a class get initialized, if not when it's imported?" On first active use — instantiating it, calling a static method, reading a non-constant static field, or initializing a subclass — never from an import or a type reference alone.

🎯 Say this in the interview — the exact lines to land

"Classloaders form a parent-first delegation chain — Bootstrap, then Platform, then Application/System — where each one asks its parent before trying to load a class itself. That's what stops a user-defined java.lang.String from ever shadowing the JDK's real one: Bootstrap already has it, so nothing below it gets the chance. Separately, a class is only initialized lazily, on first active use."

  • Bootstrap asked first, every time — no loader skips ahead of its parent.
  • Platform and Application never load their own copy of a class the parent already resolved.
  • Core java.* classes can't be shadowed — delegation plus a runtime package-sealing check both block it.
  • Initialization is lazy, triggered by first active use — not by an import or a type declaration.
📖 Explanation ▾

Each classloader's loadClass() is written to check with its parent before attempting anything itself. The Bootstrap loader (implemented in native code, with no parent of its own) holds the core JDK classes. The Platform loader (introduced with the Java module system) holds JDK platform modules. The Application/System loader is the one that actually reads your own classpath or module path. Because the chain always asks upward first, a request for java.lang.String issued by your own code still resolves at Bootstrap, long before the Application loader would ever get a turn to look at your classpath.

This isn't the only guard, either — the JVM also enforces that classes in sealed java.* packages can't be defined by anything other than the Bootstrap loader, so even deliberately trying to force one through a custom loader fails with a security error. Delegation order is the everyday mechanism; package sealing is the backstop.

Separately from loading, initialization happens lazily. The JVM specification defines a small set of triggers — "active use" — and a class sits loaded and linked, untouched, until one of them actually happens at runtime.

💻 See the code ▾
Java 
System.out.println(String.class.getClassLoader());
// prints null — Bootstrap is native, Java code can't name it directly

System.out.println(MyOwnApp.class.getClassLoader());
// prints something like jdk.internal.loader.ClassLoaders$AppClassLoader@...

A core JDK type's loader is Bootstrap (reported as null, since it has no Java-side object) — your own classes load through the Application loader.

Java 
package java.lang;
public class String { /* your own copy */ }
// java.lang.SecurityException: Prohibited package name: java.lang
// the JVM refuses to even define this class from anything but Bootstrap

Even trying to force a class into a sealed java.* package from your own code is rejected outright — delegation stops it first, package sealing is the backstop.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two libraries on your classpath bundle different versions of the same class

The Application loader resolves a class name once and caches it — whichever version it finds first on the classpath is the one every part of the app gets, which is exactly why "dependency version conflict" bugs happen.

RememberSame class name twice → one loader, one winner, silently.
2 A plugin system needs to isolate each plugin's classes from the others

Frameworks like app servers and IDE plugin systems give each plugin its own classloader — a custom loader can still delegate to the standard parents for JDK classes, while keeping each plugin's own classes (even same-named ones) fully separate from each other.

RememberCustom loaders isolate app code, but still delegate up for JDK classes.
3 You expect a static block's log line to appear at startup, but it never runs

A candidate often assumes referencing a class — an import, a field declared with that type, an unreached branch — is enough to run its static block. It isn't. Without a genuine active use, that class can stay loaded but uninitialized indefinitely.

RememberReferenced, not actively used → static block simply never fires.
🌍 Real-world example ▾

An application server hosting several independent web apps gives each one its own classloader, so two apps can each bundle a different version of the same library without colliding — every one of those custom loaders still delegates up to the shared Bootstrap and Platform loaders first for anything that's a core JDK class, which is exactly why none of them can ever accidentally override java.lang.String on their own.
