Greedy Algorithms — can you prove it, or does it just look right?

"How do you know a greedy approach is guaranteed to give the optimal answer here — and can you show me a case where greedy would fail?"

Why it matters ▾
  • Greedy is the fastest, simplest-sounding answer to almost any "optimize this" question — interviewers ask about it to test whether you can justify correctness, not just propose something plausible.
  • Comes up constantly in scheduling/interval questions and coin-change/knapsack-style questions — some of those are genuinely solved by greedy, some aren't, and mixing them up is a very common mistake.
  • A near-guaranteed follow-up after any greedy answer: "prove it," or "break it."
🔥 Easy interview recall

Greedy = "pick the best option right now, and never look back."

Think: Only correct when today's best pick is provably part of some optimal solution — if you can build one small counter-example where it locks out a better answer, greedy is the wrong tool.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Greedy is not "correct whenever it feels intuitive." Making change for 6 with coins {1, 3, 4} proves it isn't — greedy grabs 4, then 1, then 1 (3 coins), while 3 + 3 (2 coins) is actually optimal.

🔄 Likely Follow-up

"Can you construct a small counter-example where your greedy approach fails?" Yes — that's exactly the check to run: find the smallest input where the greedy choice provably blocks a better global answer, the way {1, 3, 4} making 6 blocks the 3+3 solution.

🎯 Say this in the interview — the exact lines to land

"Greedy makes the locally best choice at each step and never reconsiders it — that only gives the correct global answer when the problem has the greedy-choice property, meaning today's best local pick is provably part of some optimal solution. Interval scheduling and canonical coin systems have that property; arbitrary coin systems and 0/1 knapsack don't, and those need dynamic programming instead."

  • Interval/activity scheduling → sort by end time, greedy is provably optimal.
  • Canonical coins like {1, 5, 10, 25} → greedy is optimal, because of that specific coin system's structure.
  • Arbitrary coins like {1, 3, 4}, or 0/1 knapsack → greedy fails, needs dynamic programming.
  • Fractional knapsack (items can be split) → greedy by value-per-weight ratio is optimal, unlike its 0/1 version.
  • Before reaching for greedy → ask "could a different choice ever beat this one later?" — one real counter-example means greedy is the wrong tool.
📖 Explanation ▾

A greedy algorithm builds a solution one step at a time, always taking whatever looks best right now, and it never goes back to reconsider an earlier choice. That's exactly why greedy algorithms are usually fast and simple — often just a single sort plus one linear pass, commonly O(n log n) or O(n) — but speed isn't the same as correctness. Greedy only reaches the true global optimum on problems with the greedy-choice property: today's locally best pick is provably part of some globally optimal solution.

Interval scheduling is the textbook case where that property genuinely holds: sorting a set of meetings by end time and greedily keeping the earliest-ending one that doesn't conflict with what's already picked is a well-established, provably optimal way to fit the maximum number of non-overlapping meetings. Coin change works the same way, but only for a canonical coin system like {1, 5, 10, 25} — always grabbing the biggest coin that still fits happens to be optimal for that specific set of denominations, purely because of how those numbers relate to each other.

Swap in an arbitrary coin system, and the same rule stops being optimal — the diagram above is the proof, not a guess. The same failure shape shows up in 0/1 knapsack: greedily taking items by best value-per-weight ratio can waste capacity on a locally attractive item and leave no room for a better combination afterward. Its close cousin, fractional knapsack (where an item can be split), is one of the classic cases where that same value-per-weight greedy rule is provably optimal — the difference is entirely in whether items can be divided. Both arbitrary coin change and 0/1 knapsack need dynamic programming instead, which the next page covers.

💻 See the code ▾
Python 
def greedy_make_change(coins, amount):
    coins = sorted(coins, reverse=True)
    count = 0
    for coin in coins:
        while amount >= coin:
            amount -= coin
            count += 1
    return count

greedy_make_change([25, 10, 5, 1], 6)   # ✅ 2 (5 + 1) — matches the true optimal

For {1, 5, 10, 25}, the local pick never blocks a better combination — this coin system has the greedy-choice property.

Python 
# same function, arbitrary coin system
greedy_make_change([4, 3, 1], 6)   # ❌ 3 (4 + 1 + 1) — optimal is really 2 (3 + 3)

For {1, 3, 4}, grabbing the biggest coin first (4) uses up value a smarter combination needed — greedy can't recover from that later.

🌍 Real-world example ▾

Booking a single meeting room for the day is real interval scheduling. Sort every requested meeting by end time, and greedily keep any meeting that starts after the last one you kept ends — that greedy rule is the actual algorithm behind many real scheduling tools, because interval scheduling is one of the genuine cases where greedy is provably optimal, not just convenient.
