var — inferred once, at compile time, never dynamic

"Is var in Java dynamically typed, like JavaScript's var or Python?"

Why it matters ▾
🧩 var Type Inference
❗ ProblemSpelling out a long generic type like Map<String, List<Order>> on every local variable adds noise without adding safety, and can tempt someone into assuming Java now supports loose, dynamic typing.
✅ Solutionvar (Java 10+) lets the compiler infer a local variable's type from its initializer — the inferred type is fixed and checked at compile time, identical in effect to spelling the type out by hand.
Recallvar = the compiler fills in the type for you, once.
🔥 Easy interview recall

var = "the compiler writes the type for you — once, at compile time."

Think: var behaves exactly like the explicit type it replaced — only the keystrokes changed, never the type-safety.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

var does not mean "can change type later" or "untyped." The compiler locks in one concrete type at the declaration — reassigning to an incompatible type is a compile error, exactly like it would be with an explicit type.

🔄 Likely Follow-up

"Can you use var for a field, a method parameter, or a return type?" No — it only works for local variables that have an initializer to infer from; fields, parameters, and return types all still need an explicit type.

🎯 Say this in the interview — the exact lines to land

"var lets the compiler infer a local variable's type from its initializer — it's not dynamic typing, the inferred type is fixed and checked at compile time exactly like spelling the type out. It only works for local variables with an initializer, never fields, parameters, or return types."

  • var → type fixed at compile time, not flexible at runtime.
  • Reassigning an incompatible type → compile error, same as an explicit type.
  • Only local variables with an initializer → no fields, parameters, or return types.
📖 Explanation ▾

var (finalized in Java 10) tells the compiler "figure out this local variable's type from whatever is on the right-hand side." It isn't a type itself — var x = 5; compiles to exactly the same bytecode as int x = 5;; the keyword only saves keystrokes, it never defers anything to runtime.

This is genuinely different from dynamic typing in languages like JavaScript or Python, where a variable can be reassigned a completely different type at any point and the check only happens when that line actually runs. In Java, var's type is settled once, during compilation, and never revisited.

💻 See the code ▾
☕ Java 
var list = new ArrayList<String>();  // inferred: ArrayList<String>
var total = 0;                     // inferred: int

Hover either one in an IDE and it shows the exact concrete type — nothing is left for runtime to decide.

☕ Java 
var x = 5;
x = "hello";   // ❌ compile error — x is int, not reassignable to String

Fails exactly like int x = 5; x = "hello"; would — var changed nothing about type-safety.

☕ Java 
public var getName() { ... }        // ❌ not allowed as a return type
public void greet(var name) { }   // ❌ not allowed as a parameter type

var needs an initializer to infer from — fields, parameters, and return types never have one.

🧭 Use Cases — recognize these when they happen to you ▾
1 You refactor a long generic declaration to var

The declared type disappears from the source line, but the compiled type is identical — every method call on m still resolves exactly as before. This is the #1 scenario you'll actually use var for.

RememberShorter source, zero change to the compiled type.
2 You assume var means the variable can hold different types later

Java's var has nothing in common with JavaScript's var here — the type was already locked in at the declaration, so this fails to compile, it doesn't quietly reassign.

RememberJava's var ≠ JS's var — the type never becomes flexible.
3 You try var on a field, a parameter, or a return type

Fields, parameters, and return types never have a right-hand-side value for the compiler to infer from at that point — var is local-variable-only.

RememberNo initializer → no inference → var isn't allowed there.
🌍 Real-world example ▾

Asking a colleague to print a label for you instead of writing it by hand. The label itself is just as permanent either way — var only changes who writes the word on it, not whether it can be peeled off and swapped later.
