IMemoryCache forgets everything on restart — Redis doesn't

"Your API caches data in-memory, but a restart wipes it and every request floods the database again — how do you fix this?"

Why it matters ▾
🗄️ Caching Across Restarts
❗ ProblemIMemoryCache lives inside the process's own RAM — a restart, a redeploy, or scaling out to multiple instances all wipe it or leave every instance with its own disconnected cache.
✅ SolutionMove to a distributed cache like Redis via IDistributedCache — it lives outside the process, survives restarts, and is shared by every instance behind the load balancer.
RecallIn-process cache dies with the process; a distributed cache outlives it.
🔥 Easy interview recall

IMemoryCache → process RAM, wiped on restart

IDistributedCache → outside the process (Redis), survives restart

Think: more than one instance running? IMemoryCache goes inconsistent, not just restart-unsafe.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Assuming "cache" always means IMemoryCache. The moment there's more than one instance, in-memory caching silently becomes inconsistent — instance A's cache doesn't know about instance B's writes — not just restart-unsafe.

🔄 Likely Follow-up

"Does moving to Redis fully solve the restart problem?" It solves data loss, but you still need a cache-warming or lazy-load strategy — Redis itself can be restarted or flushed too. The real fix is treating the cache as disposable and rebuildable, never as the source of truth.

🎯 Say this in the interview — the exact lines to land

"IMemoryCache lives inside the process's own RAM, so a restart, a redeploy, or scaling out to multiple instances wipes it or splits it into separate, inconsistent caches. I'd move it to a distributed cache like Redis through IDistributedCache, which lives outside the process and is shared by every instance — and I'd still treat the cache as disposable and rebuildable, never as the source of truth."

  • IMemoryCache → process RAM, wiped by restart or redeploy.
  • Multiple instances → each gets its own separate cache — inconsistent, not just restart-unsafe.
  • Fix → IDistributedCache (Redis) outside the process, shared by every instance.
  • Still disposable → Redis can restart or flush too — rebuild it, never rely on it as the source of truth.
  • Pattern → cache-aside: read cache, miss → read DB → write cache.
📖 Explanation ▾

IMemoryCache stores everything in the process's own RAM. That's fast — no network hop — but it means the cache's lifetime is tied exactly to the process's lifetime. A restart, a new deployment, or an autoscaler spinning up a second instance all either wipe it or give that instance a brand-new, empty cache of its own.

IDistributedCache is an abstraction over a cache that lives outside every instance — in practice, almost always Redis in .NET. Every instance talks to the same Redis, so a write from instance A is immediately visible to instance B, and a restart of any one instance doesn't touch the cached data at all.

Redis can still restart or be flushed, so the cache is never the source of truth — the usual pattern is cache-aside: read the cache, and on a miss read the real database and write the result back into the cache before returning it. That way a cold or flushed cache self-heals instead of causing an error.

💻 See the code ▾
C# 
// ❌ IMemoryCache — gone the moment this process restarts
public class PriceService(IMemoryCache cache)
{
    public async Task<decimal> GetPriceAsync(int id)
        => await cache.GetOrCreateAsync($"price:{id}", _ => _db.GetPriceAsync(id));
}

Fine with one instance that never restarts — but that's rarely how a real deployment behaves.

C# 
// ✅ IDistributedCache (Redis) — outside the process, shared by every instance
builder.Services.AddStackExchangeRedisCache(o =>
    o.Configuration = builder.Configuration["Redis:ConnectionString"]);

public class PriceService(IDistributedCache cache)
{
    public async Task<decimal> GetPriceAsync(int id)
    {
        var cached = await cache.GetStringAsync($"price:{id}");
        if (cached is not null) return decimal.Parse(cached);

        var price = await _db.GetPriceAsync(id);          // cache-aside: miss → read DB
        await cache.SetStringAsync($"price:{id}", price.ToString());
        return price;
    }
}

A restart doesn't touch Redis, and every instance reads the same cached value.

🧭 Use Cases — recognize these when they happen to you ▾
1 A single instance that rarely restarts, caching cheap-to-rebuild data

With exactly one instance, there's no consistency problem — a restart just means the next request rebuilds the cache. IMemoryCache is a reasonable choice here.

RememberOne instance + cheap-to-rebuild data → IMemoryCache is fine.
2 The app gets scaled to 3 instances behind a load balancer

Each instance now has its own IMemoryCache. Users can see different, stale answers depending on which instance the load balancer sends them to.

RememberScaling out turns IMemoryCache inconsistent, not just restart-unsafe.
3 Rate-limit counters or session data need to be seen by every instance

A rate limit or session has to be correct no matter which instance handles the request. Only a shared store like Redis gives every instance the same number.

RememberNeeds to be correct across instances → it belongs in Redis, not IMemoryCache.
🌍 Real-world example ▾

A pricing API caches product prices in IMemoryCache and runs fine with one instance. Ops then scales it to four instances behind a load balancer, and support starts getting reports of different prices for the same product. Switching to IDistributedCache backed by Redis, with a cache-aside read on a miss, fixes it immediately — one price, one cache, visible to every instance.
