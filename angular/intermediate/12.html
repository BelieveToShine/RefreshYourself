Subject — an Observable AND an Observer, at the same time

What's the difference between a Subject, a BehaviorSubject, and a ReplaySubject?

Why it matters ▾
📡 Subject
❗ ProblemSeveral unrelated components need to react to the same one-off event the moment it happens — like a logout click — but a plain Observable only replays its own predefined values, it can't be pushed into from outside.
✅ SolutionA Subject is both an Observable and an Observer at once — any code can call .next() on it, and every subscriber listening right then receives that value live.
RecallSubject = a live push-and-subscribe event bus; a late joiner gets nothing from before.
💾 BehaviorSubject
❗ ProblemA component that mounts after some state already changed still needs "what's the current value right now," synchronously, not just whatever updates happen to arrive after it subscribes.
✅ SolutionBehaviorSubject requires a starting value at construction and always hands a brand-new subscriber the current value immediately, readable synchronously via .value.
RecallBehaviorSubject = always has a "current value" a late joiner gets right away.
🔁 ReplaySubject
❗ ProblemA single current value isn't enough when a late joiner actually needs the recent history that led up to now — not just where things stand this instant.
✅ SolutionReplaySubject buffers a configurable number of past values (or a time window) and replays exactly those to a new subscriber before continuing live.
RecallReplaySubject = replays the last N values to whoever joins late.
🏁 AsyncSubject
❗ ProblemSometimes every intermediate value would just be noise — only the final outcome of an operation actually matters, and delivering each step along the way adds clutter no one needs.
✅ SolutionAsyncSubject withholds everything until .complete() is called, then emits exactly one value — the last one pushed.
RecallAsyncSubject = withholds everything until complete(), then emits just the final value.
🔥 Easy interview recall

Subject → late subscriber gets nothing

BehaviorSubject → late subscriber gets the current value now

ReplaySubject → late subscriber gets the last N values

Think: Subject → a live radio broadcast, tune in late and you missed it BehaviorSubject → a whiteboard showing today's status right now ReplaySubject → a voicemail box replaying the last few messages

⚠️ Common Trap

A plain Subject is not a place to store "the current value." A late subscriber gets nothing from before they joined — if code needs "give me whatever the value is right now, even if I just joined," that's specifically what a BehaviorSubject is for, not a plain Subject.

🔄 Likely Follow-up

"Why is EventEmitter technically a Subject under the hood, and does that mean you should call .subscribe() on an @Output?" It really is built on Subject, but Angular's binding syntax — (myEvent)="handler($event)" — is the intended way to consume it; manually subscribing works mechanically but bypasses the template binding Angular's own tooling and change detection expect, and isn't the conventional pattern.

🎯 Say this in the interview — the exact lines to land

"A Subject is both an Observable and an Observer — you subscribe to it, and you also call .next() on it to push values out to whoever's currently subscribed. A plain Subject gives a late subscriber nothing from before; a BehaviorSubject always hands a new subscriber the current value immediately; a ReplaySubject replays the last N values; an AsyncSubject only emits once, after complete(), with just the final value."

  • Subject → use as a simple event bus for something happening in your own app code, not for HTTP or another true async source.
  • BehaviorSubject → use when you need "the current value" readable synchronously via .value, plus live updates after.
  • ReplaySubject → use when a late joiner needs recent history, not just the single latest value.
  • Widely-shared Subjects erode a single source of truth — any code holding a reference can call .next(), with no enforced direction of data flow.
📖 Explanation ▾

A Subject is a multicasting bridge: it's an Observable (other code can .subscribe() to it) and an Observer (you call .next(value) on it yourself) rolled into one object. A plain Observable defines how to produce values and typically re-runs that definition per subscriber; a Subject has no such definition — it just relays whatever's pushed into it to whoever happens to be subscribed right then, which is why it's inherently hot and multicast rather than cold.

The four variants differ only in what a subscriber who joins late receives. A plain Subject has no initial value and no memory — nothing before "now." A BehaviorSubject requires a starting value at construction and always hands any new subscriber the current value right away, and it's also readable synchronously any time through .value/.getValue(). A ReplaySubject keeps a configurable number of past values (or a time window) and replays exactly those to a new subscriber, then continues live. An AsyncSubject is the odd one out — it holds everything back and emits only once, the single last value, and only once .complete() is called.

EventEmitter (Angular's own @Output type) is actually a thin subclass of Subject, scoped specifically to the parent-child @Output case — a plain Subject is the general-purpose version, usable anywhere. A BehaviorSubject also overlaps conceptually with what a Signal now does more simply for "give me the current value" — which is exactly the tension the next page, Signals + RxJS, works out.

💻 See the code ▾
TypeScript 
const subj = new Subject<number>();  // no initial value
subj.next(1);                          // pushed before anyone's subscribed
subj.subscribe(v => console.log(v));  // ❌ nothing logs — missed it

A plain Subject never replays what happened before you subscribed.

TypeScript 
const beh = new BehaviorSubject<number>(0);  // requires a start value
beh.next(1);                          // pushed before anyone's subscribed
beh.subscribe(v => console.log(v));  // ✅ logs 1 immediately

Same exact scenario — BehaviorSubject always hands a new subscriber the current value.

TypeScript 
// inside a component
@Output() saved = new EventEmitter<void>();

save() {
  this.saved.emit();  // ✅ normal @Output usage
}

EventEmitter is a Subject subclass under the hood — but .emit()/template binding, not manual .subscribe(), is the idiomatic way to use it.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app has an action several unrelated components need to react to right when it happens — a logout click, a toolbar action

Any code holding a reference can call .next() to broadcast that moment to whoever's subscribed right then — a plain Subject is built exactly for this simple event-bus role, not for storing state. This is the #1 reason most apps reach for a Subject at all.

RememberSimple one-off app event → reach for a plain Subject.
2 A component mounts after the state already changed, and you assumed a plain Subject would still hand it "the current value"

A plain Subject has no memory — a subscriber that joins after .next() already ran gets nothing from before that moment. Candidates often assume it still exposes "whatever the last value was," but that's specifically what a BehaviorSubject is for.

RememberNeed "the current value" on a late joiner → BehaviorSubject, not Subject.
3 A dropdown or toast list needs to show the last few things that happened, not just the single latest one

A ReplaySubject configured with a small buffer (e.g. the last 3) hands a newly-mounted component exactly that recent history immediately, then keeps it live for anything after — a single BehaviorSubject can't do this, since it only ever remembers one value.

RememberNeed recent history, not just the latest value → ReplaySubject.
🌍 Real-world example ▾

Radio, whiteboard, voicemail. A plain Subject is a live radio broadcast — tune in late and you missed everything before that moment. A BehaviorSubject is a whiteboard showing today's current status — whoever walks up now sees whatever's written, even if they missed everything that led up to it. A ReplaySubject is a voicemail box that replays the last few messages to anyone who checks it, not just the very latest one.
