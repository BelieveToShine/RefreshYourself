The page looks broken — which mechanic actually broke it?

"Something in this page is visually broken — not centered, overlapping, or shifting on load. Walk me through how you'd actually diagnose it."

Why it matters ▾
  • This is the "senior CSS" interview question — not "what does z-index do," but "given a real broken screen, which of the mechanics you already know is actually responsible."
  • Every scenario below routes back to a page already on this track — the skill being tested is diagnosis, not one more definition.
  • A near-guaranteed follow-up to "tell me about a tricky CSS bug you fixed" in any mid-to-senior front-end interview.
🔥 Easy interview recall

Not centered → wrong axis, not a broken property

z-index ignored → a stacking context problem

Page jumps on load → no reserved space for the image

Think: every symptom here already has a fix somewhere earlier on this track — this page is the index of "which page do I reach for," not a new set of tricks to learn.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

z-index not working is not a specificity problem. Raising the number or adding !important won't fix it if the element is trapped inside a parent's own stacking context — z-index only ever competes against siblings inside the same stacking context, never across one.

🔄 Likely Follow-up

"It fixed one page and broke five others — how do you find out why?" Find the exact selector that changed and its specificity, check what other selectors of similar or lower specificity were quietly relying on the old behavior across those five pages, and look for an overly broad selector (a bare tag or a shared utility class) that should have been scoped narrower in the first place.

🎯 Say this in the interview — the exact lines to land

"Almost every 'CSS is broken' report is really a diagnosis question: a centering bug is usually the wrong axis, a z-index bug is almost always a stacking-context problem, horizontal overflow is usually a fixed-width child or unaccounted padding under content-box, and a layout jump on image load means the space was never reserved. 'Works locally, breaks in production' is almost never a CSS bug at all — it's a build/cache/path/browser-support difference between environments."

  • Not centered → check the axis — Flexbox/Grid alignment properties are per-axis, and margin: auto only centers a block that already has a definite width (Flexbox).
  • z-index ignored → find the stacking context it's trapped in, not the specificity (Overflow & Stacking).
  • Horizontal overflow → a fixed-width child, unaccounted padding/border under content-box, or unwrapped text (Box Model).
  • Layout jumps on image load → no reserved space — add width/height or aspect-ratio (Modern CSS Layout). Works locally, not in production → check minification, CDN cache, asset paths, and browser support before touching the CSS itself.
  • Same change fixed one page, broke five → trace the selector's specificity and who else relied on the old rule (Cascade & Specificity).
  • No-JS accessible component → reach for the native element (details/summary, dialog, real button/a) before hand-rolling ARIA.
📖 Explanation ▾

"Why isn't my element centered?" is almost always a wrong-axis assumption, not a broken property. Flexbox and Grid have separate alignment properties for the main axis (justify-content) and the cross axis (align-items) — setting the one for the wrong axis leaves the element centered on one direction and stuck on the other. Text-align only ever centers inline content, never a block-level box itself; that's what margin: 0 auto is for, and it only works once the box has a definite width. See Flexbox for the full mechanics.

"Why isn't z-index working?" is a stacking context problem, not a specificity problem — a higher z-index only wins against siblings that share the same stacking context. Certain properties (position plus a value other than static, opacity less than 1, transform, and others) create a brand-new stacking context on their parent, and once an element is boxed inside one, no z-index value can make it appear above something outside that context — the two elements are never even being compared. See Overflow & Stacking for how stacking contexts form.

"Why does the page overflow horizontally?" usually comes down to one of three things: a fixed-width element (a hardcoded pixel width, or a wide image with no max-width: 100%) that's simply wider than its container; padding or border adding on top of a set width under the default content-box model; or a child with long unbroken text (white-space: nowrap, or a long word/URL with no word-break/overflow-wrap) spilling past its box. See Box Model for exactly what width does and doesn't include.

"Why does layout jump when an image loads?" — until an image finishes downloading, the browser doesn't know its real size unless it was told in advance. With no width/height attributes and no aspect-ratio, the browser reserves little or no space for it, so everything below renders in the wrong spot and gets pushed down the instant the real image arrives. Setting aspect-ratio (or explicit width/height) tells the browser the shape up front, so the space is already correct before the image loads. See Modern CSS Layout for aspect-ratio.

"Why does CSS work locally but not in production?" is rarely a CSS-language question — it's an environment-difference question. The usual suspects: a build/minification step that changed selector order or merged rules in a way that shifted a specificity tie; a CDN or browser cache still serving an older stylesheet; an absolute asset path that's correct locally but wrong once deployed under a different base path; or a newer feature/vendor-prefix gap that only shows up on whichever browser version actually gets tested in production. "Why does the page look different across browsers?" is a related but separate question — see Cross-Browser Compatibility (coming soon) for the deeper rendering-engine differences; the short version here is: check feature support and vendor prefixes before assuming your CSS is wrong.

"How would you build a responsive dashboard?" — Grid or Flexbox for the overall page skeleton, container queries or media queries so individual widgets adapt to their own available space rather than the whole viewport, and clamp() for fluid typography and spacing so text and gaps scale smoothly between a floor and a ceiling instead of jumping at fixed breakpoints. Reuse the same building blocks already covered — Flexbox and Modern CSS Layout — rather than inventing new layout tricks for a dashboard specifically.

"How would you make a component accessible without JavaScript?" — reach for the native HTML element that already has the accessible behavior built in before building a custom widget: <details>/ <summary> for a collapsible panel, <dialog> for a modal, and a real <button> or <a> instead of a clickable <div>. Each of those gets keyboard support, focus handling, and correct semantics for free — a hand-rolled equivalent needs JavaScript just to catch up to what the native element already does. See Semantic HTML and HTML5 Elements & Browser APIs.

"A CSS change fixed one page but broke five others — how do you diagnose the cascade?" — first identify the exact selector that changed and compute its specificity, then check what other selectors of similar or lower specificity across those five pages were quietly relying on the old rule winning or losing. Very often the real cause is an overly broad selector — a bare element selector or a shared utility class — that should have been scoped to the one page it was meant for. See CSS Fundamentals & Cascade and Specificity.

💻 See the code ▾
CSS 
/* Centered on the WRONG axis — main axis only, cross axis untouched */
.row {
  display: flex;
  justify-content: center;   // ✅ centers on the main axis (horizontal here)
}
/* Item still sticks to the top — align-items was never set */
// fix: add align-items: center; for the cross axis too

justify-content and align-items control different axes — setting only one leaves the other axis exactly where it started.

CSS 
/* z-index: 999 here does NOTHING against .toast — different stacking context */
.modal {
  position: relative;
  z-index: 999;      // ❌ only competes within ITS OWN context
}
.modal-backdrop {
  position: fixed;
  opacity: 0.98;   // opacity < 1 creates a NEW stacking context here
  z-index: 1;
}
/* .modal is a child of .modal-backdrop's stacking context — */
/* raising .modal's own z-index can never escape it */

The fix is removing (or not creating) the extra stacking context on the parent — not raising the child's number further.

CSS 
/* Prevents the layout jump — space is reserved before the image loads */
img.hero {
  width: 100%;
  aspect-ratio: 16 / 9;   // ✅ height is now known immediately
  object-fit: cover;
}

The browser now knows the box's shape on the first layout pass — nothing below it has to move once the real image arrives.

🌍 Real-world example ▾

An interviewer says "our marketing page looks perfect in staging, but in production the hero banner is missing its rounded corners and a badge in the corner is hidden behind the nav bar — where do you start?" Two separate scenarios in one report: the missing rounded corners is a "works locally, not in production" question — check whether the build step minified/reordered the CSS in a way that changed a specificity tie, or whether production is serving a stale cached stylesheet; the hidden badge is very likely a stacking-context problem — the nav bar (or something wrapping it) probably creates its own stacking context that the badge's z-index can never reach into. The signal being graded is naming both causes correctly and pointing at the specific mechanic for each, rather than one vague "let me check the CSS" answer.
