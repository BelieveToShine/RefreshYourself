Most objects die young — why the heap is split, and which collector to reach for

"Why does the JVM split the heap into generations, and how would you choose between G1, ZGC, and Parallel GC?"

Why it matters ▾
🌱 Generational Heap
❗ ProblemScanning the entire heap on every collection to find garbage is wasteful when most objects (request-scoped data, temporary buffers) die within milliseconds of being created.
✅ SolutionSplit the heap into a small, frequently-collected young generation for new objects and a larger, rarely-collected old generation for objects that survive — "the generational hypothesis": most objects die young.
RecallMost objects die young — collect the young generation often, the old generation rarely.
⚖️ Choosing a Collector
❗ Problem"Always use the newest collector" ignores that throughput and pause time are a real trade-off — a collector tuned for one costs something in the other.
✅ SolutionG1 balances both for most general workloads; ZGC/Shenandoah target very low pause times for latency-sensitive apps at some throughput/memory cost; Parallel GC favors raw throughput over pause time.
RecallPick by what you're optimizing for — pause time and throughput trade off against each other.
🔥 Easy interview recall

Young gen → small, collected often

Old gen → large, collected rarely

Survives enough cycles → promoted/tenured to old gen

Think: G1 = balanced default. ZGC/Shenandoah = lowest pause time. Parallel = highest throughput.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Always use the newest collector" is not real advice. ZGC's very low pause times come at a real cost in throughput and memory overhead — a batch-processing workload with no latency requirement is often better served by Parallel GC's higher throughput, not whichever collector is newest.

🔄 Likely Follow-up

"What happens during a major/full GC that doesn't happen during a minor GC?" A minor GC only scans the young generation; a major/full GC also examines the old generation (and sometimes the whole heap), which is why it takes much longer and happens far less often.

🎯 Say this in the interview — the exact lines to land

"The JVM splits the heap into a young generation, collected often and cheaply because most objects die quickly, and an old generation for objects that survive enough young-gen cycles to get promoted. G1 is the default and balances throughput with pause time for most workloads; ZGC and Shenandoah trade some throughput for very low, sub-millisecond-class pause times; Parallel GC favors raw throughput. Which one to use is a real trade-off, not a 'pick the newest' question."

  • Young gen collected often, cheap — most objects die here.
  • Old gen collected rarely, holds long-lived survivors.
  • G1 → balanced default for general-purpose workloads.
  • ZGC/Shenandoah → lowest pause times, for latency-sensitive services.
  • Parallel GC → highest throughput, for batch/offline jobs that can tolerate longer pauses.
📖 Explanation ▾

The generational hypothesis — most objects become garbage shortly after allocation — is what justifies splitting the heap at all. A minor GC only has to scan the young generation, which stays small, so it's fast and frequent. An object that survives several minor collections gets promoted (also called tenured) into the old generation, which is scanned far less often because it holds the objects expected to live a long time anyway.

Which collector to reach for is a genuine trade-off, not a ranking. G1 (the default in modern JDKs) divides the heap into regions and collects incrementally, aiming for a configurable pause-time target while still keeping reasonable throughput — the right starting point for most services. ZGC and Shenandoah do most of their work concurrently with the application threads to push pause times into the sub-millisecond class, which matters for strict latency SLAs, at some cost in CPU/memory overhead and slightly lower raw throughput. Parallel GC stops the application during collection but uses multiple threads to do it fast, maximizing total throughput for workloads (batch jobs, offline processing) where occasional longer pauses are acceptable.

💻 See the code ▾
Shell 
# Balanced default — usually no flag needed, G1 is already the default
java -XX:+UseG1GC -jar app.jar

# Latency-sensitive service — very low pause times
java -XX:+UseZGC -jar app.jar

# Batch job — maximize throughput, pauses are acceptable
java -XX:+UseParallelGC -jar app.jar

The collector is a startup flag, not something your code calls directly — the choice is an operational/deployment decision tied to the workload's actual latency and throughput needs.

🧭 Use Cases — recognize these when they happen to you ▾
1 A typical web service with no extreme latency SLA

Most everyday services don't have an extreme pause-time budget — G1's balance of throughput and pause time is already the right fit, and it's the default, so there's usually nothing to configure.

RememberNo special latency need → G1's default balance is correct.
2 A trading or real-time system with a strict p99 latency budget

When any multi-millisecond pause would blow a latency SLA, ZGC or Shenandoah's near-concurrent collection is worth the extra CPU/memory overhead — this is the scenario those collectors exist for.

RememberStrict latency SLA → pay for ZGC/Shenandoah's low pauses.
3 A nightly batch job processing millions of records with no user waiting

A job with no interactive user waiting on any single response cares about total completion time, not individual pause length — Parallel GC's higher throughput finishes the overall job sooner, even with occasional longer stop-the-world pauses.

RememberNobody's waiting on a single pause → optimize for throughput instead.
🌍 Real-world example ▾

A checkout service suddenly shows 2-second response-time spikes under load. Before touching any application code, check the GC logs for a long major/full GC pause — if the old generation is filling up and triggering expensive full collections, the fix might be as simple as increasing heap size to give promoted objects more room, or switching to a collector with a lower pause-time target, rather than assuming it's a code-level bug.
