Migrations & SaveChanges() — nothing touches the database until you say so

What is a migration, and what does SaveChanges() actually do?

Why it matters ▾
  • The #1 place candidates trip up in EF Core interviews: knowing exactly when code actually reaches the database, not just how to write it.
  • Migrations are how EF Core evolves a real database safely, without anyone hand-writing DDL.
  • A very common opener: "Walk me through what happens when you call SaveChanges()."
🔥 Easy interview recall

Migration → schema change, versioned & applied

SaveChanges() → data change, sent right now

Think: Migrations move the shape. SaveChanges() moves the rows. Neither happens until you explicitly trigger it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling Add() or Remove() sends something to the database. It only updates the in-memory Change Tracker — nothing reaches the database until SaveChanges() (or SaveChangesAsync()) actually runs.

🔄 Likely Follow-up

"If context.Orders.Add(order) runs, but the method returns before SaveChanges() is ever called, what state is the database in?" Completely unchanged — the Change Tracker held the new row in memory, but nothing was ever sent.

🎯 Say this in the interview — the exact lines to land

"A migration is a versioned description of a schema change, generated by comparing the current model against the last snapshot of it — applying it runs the SQL that brings the database's schema in line. SaveChanges() looks at everything the Change Tracker knows about — entities marked Added, Modified, or Deleted — generates the matching INSERT, UPDATE, and DELETE statements, and sends them, normally inside one implicit transaction."

  • Migration → schema change, compared against the last snapshot, applied as SQL DDL.
  • Add() / Remove() / property edits → Change Tracker only — nothing sent yet.
  • SaveChanges() → the one call that actually reaches the database.
  • By default, all of it runs inside one implicit transaction.
📖 Explanation ▾

A migration exists because your C# model and the real database schema drift apart the moment you add a property or a new entity. EF Core compares your current model against the last snapshot it kept of that model, works out the difference, and writes that difference down as a migration. Applying it just runs the resulting SQL — CREATE TABLE, ALTER TABLE, and so on — against the actual database.

SaveChanges() works the same idea, one level down: instead of comparing models, it looks at what the Change Tracker already knows — every entity marked Added, Modified, or Deleted since the context started tracking it — and turns that into the matching INSERT, UPDATE, and DELETE statements. By default, all of it runs inside one implicit transaction, so a failure partway through rolls the whole batch back instead of leaving the database half-updated.

💻 See the code ▾
C# 
using var context = new AppDbContext();
context.Orders.Add(new Order { CustomerId = 42 });
// ✅ still just the Change Tracker — nothing sent to the database yet

Add() only updates the Change Tracker in memory — the database hasn't changed.

C# 
int rowsWritten = context.SaveChanges();
// ✅ the INSERT is generated and executed right here
Console.WriteLine($"{rowsWritten} row(s) written");

SaveChanges() is the one call that diffs the tracker and actually sends SQL.

🌍 Real-world example ▾

SaveChanges() is like hitting "save" on a shared document. You can edit as many cells as you want locally — nothing changes for anyone else until you actually save. A migration is more like publishing a new version of the spreadsheet's own template: it changes the shape everyone's copy is built on, as its own separate, deliberate step.
