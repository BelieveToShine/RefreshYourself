Hydration — attaching React's brain to HTML that already exists

"What is hydration, and what causes a hydration mismatch?"

Why it matters ▾
  • Almost every senior React interview asks how server rendering actually makes a page interactive, not just "SSR is faster."
  • A hydration mismatch is a real production bug — it shows up as a console warning, a content flash, or broken interactivity right after page load.
  • Streaming SSR is where the conversation goes next once hydration itself is understood — a common follow-up in any full-stack React framework discussion.
🔥 Easy interview recall

Hydration = "attaching React's event listeners and state to markup that already exists, instead of building the DOM from scratch."

Think: the server sends a page that already looks right. Hydration is React quietly waking it up underneath.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The markup just needs to LOOK the same, not match exactly. React expects the server-rendered HTML and the client's first render to match structurally — using Date.now(), Math.random(), or checking typeof window during that first render produces genuinely different output on each side, which is a real hydration mismatch, not a cosmetic non-issue.

🔄 Likely Follow-up

"What's streaming SSR, and what does it solve that traditional SSR can't?" Traditional SSR buffers the ENTIRE page server-side before sending anything, blocking the whole response on the single slowest piece of data; streaming SSR sends the page's shell immediately and streams in slower sections as they individually become ready, so the user sees meaningful content much sooner instead of waiting on everything at once.

🎯 Say this in the interview — the exact lines to land

"Hydration is React attaching its event listeners and internal state to HTML the server already sent, instead of rebuilding the DOM from scratch — a mismatch happens when the server's first render and the client's first render produce genuinely different markup, usually from something environment-dependent like Date.now() or typeof window."

  • CSR → ships an empty shell, renders everything client-side.
  • SSR → renders real HTML first, then hydrates it for interactivity.
  • Hydration mismatch → server and client output differ structurally, not just visually.
  • SSG → pre-renders HTML once at build time, not per request like SSR.
  • Streaming SSR → sends the shell first, streams in slower sections instead of blocking on all of them.
📖 Explanation ▾

Client-side rendering (CSR) ships a mostly-empty HTML shell plus a JavaScript bundle, and the browser builds the entire page from nothing once that bundle runs. Server-side rendering (SSR) renders the initial HTML on the server instead, so the browser has real content the moment the page arrives — React then hydrates that markup: it attaches event listeners and internal state to the DOM nodes that already exist, rather than re-building them. Hydration is what lets a page get both the fast first paint of server-rendered HTML and the full interactivity of a normal React app afterward.

A hydration mismatch happens when the server's render output and the client's first render output don't line up structurally. The usual cause is something environment-dependent evaluated during that first render — Date.now(), Math.random(), or a typeof window check — which produces one result on the server and a different one in the browser.

Static site generation (SSG) pre-renders HTML at build time, once, ahead of any request — the trade-off is always-fresh-but-slower (SSR, computed per request) against fast-but-only-as-fresh-as-the-last-build (SSG). SSR generally helps SEO, since crawlers see real content immediately, at the cost of added server infrastructure and caching considerations. Streaming SSR sends the page's shell right away and streams in slower sections as they individually finish, instead of buffering the entire page and blocking the whole response on its single slowest piece of data.

💻 See the code ▾
JSX 
function Greeting() {
  // ❌ Date.now() differs between the server's render and the client's
  return <p>Rendered at {Date.now()}</p>; // hydration mismatch
}

Conceptual, not a specific framework's exact API — the point is any environment-dependent value read during that first render, not this one call in particular.

🌍 Real-world example ▾

Traditional SSR is a restaurant that won't seat you until every dish for your whole table is fully plated and ready to serve all at once. Streaming SSR is the same restaurant bringing out each dish as soon as it's ready — you're eating the appetizer while the entrée is still finishing.
