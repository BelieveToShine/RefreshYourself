⭐ Next.js · Intermediate · Should Know

(groupName) — organize folders without touching the URL

"What does a folder named (groupName) actually do to the URL?"

Why it matters ▾
📁 Route Groups
❗ ProblemA marketing section and a dashboard section of the same app often need completely different layouts — but nesting one inside the other to share folder structure would force an unwanted segment (like marketing) into every URL under it.
✅ SolutionWrapping a folder name in parentheses — (marketing) — groups its routes and lets them share a layout, without that folder name ever appearing in the actual URL.
Recall(parens) = organize on disk, invisible in the URL.
🔥 Easy interview recall

(groupName) = "a folder for organization and shared layout — the URL never sees it."

Think: app/(marketing)/about/page.js is still just /about.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A route group doesn't isolate routes from each other. Its only job is grouping for organization and shared-layout purposes — it doesn't create any actual routing or data isolation between what's inside it and what's outside.

🔄 Likely Follow-up

"Can you have multiple root layouts using route groups?" Yes — this is the standard technique for giving a marketing section and a dashboard section of one app completely different root-level layouts, by putting a layout.js inside each separate route group.

🎯 Say this in the interview — the exact lines to land

"A folder named (groupName) organizes routes and lets them share a layout, without adding that name to the URL — app/(marketing)/about/page.js is still just /about."

  • (parens) → invisible in the URL, purely organizational.
  • Shared layout per group — each group can have its own layout.js.
  • No routing/data isolation — grouping only, nothing is sandboxed.
  • Multiple root layouts → the standard way to give two app sections entirely different shells.
📖 Explanation ▾

Wrapping a folder's name in parentheses — (marketing) — tells Next.js to treat that folder as organizational only: it still participates in the file-based routing structure (so a layout.js inside it applies to everything nested beneath it), but the folder's own name is stripped out when building the actual URL for any page.js inside it.

This is what makes it possible for two different sections of one app — (marketing) and (shop), say — to each have their own distinct root-level layout, header, and styling, while both still live under the same top-level app/ folder and neither section's URLs carry any trace of the grouping.

Because the only thing a route group changes is where files live on disk and which layout wraps them, it's purely an organization tool — it has no effect on data fetching, caching, or any kind of isolation between the routes inside it and routes outside it.

💻 See the code ▾
Next.js 
// folder structure
app/
  (marketing)/
    layout.js          // its own marketing nav/footer
    about/page.js      // → /about (no "marketing" segment)
    pricing/page.js     // → /pricing
  (shop)/
    layout.js           // a completely different shell
    products/page.js    // → /products

Two sibling groups, two different layouts — neither group name appears in either URL.

🧭 Use Cases — recognize these when they happen to you ▾
1 A marketing site and an app dashboard sharing one codebase

Each group gets its own root layout.js — a public, SEO-friendly shell for marketing pages and a completely different authenticated shell for the dashboard — all from one app.

RememberDifferent root layouts in one app → separate route groups.
2 Organizing a large route tree without a pointless URL segment

A handful of related pages (profile, billing, security) can be grouped into one folder for tidiness, with none of them forced to carry an extra "account-settings" segment in their real URLs.

RememberGroup for tidiness, not because the URL needs the extra segment.
3 Expecting a route group to sandbox data or auth between sections

Putting admin pages inside a (admin) group doesn't add any access control on its own — it's still just a folder name. Protecting those routes still needs real auth logic (e.g. in Middleware or the layout itself).

RememberA group name is not a security boundary — write the actual auth check.
🌍 Real-world example ▾

A SaaS product has a public marketing site and a logged-in dashboard, deployed from one Next.js app. Route groups (marketing) and (dashboard) give each its own root layout and styling, while the marketing team never has to think about the word "marketing" showing up in a URL a visitor sees.
