Written top-to-bottom, executed in a completely different order

"What is the logical order a SQL query actually executes in, and why does that explain why you can't reference a SELECT alias in WHERE?"

Why it matters ▾
🔢 Logical execution order
❗ ProblemYou type SELECT first, so it's easy to assume it also runs first — which is exactly why filtering on an aggregate in WHERE, or referencing a SELECT alias in WHERE, both look like they should work and both fail.
✅ SolutionSQL is logically processed in a fixed order that's different from the order you write it — FROM/JOIN, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY — so once you know that order, both failures explain themselves.
RecallWritten order ≠ executed order — knowing the real one is what separates memorized syntax from real understanding.
🔥 Easy interview recall

Execution order = "FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY — not the order you typed it in."

Think: SELECT runs 5th, not 1st — that's exactly why a SELECT alias doesn't exist yet when WHERE runs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

SQL runs in the order you typed it. It doesn't — FROM/JOIN runs first and SELECT runs almost last, which is exactly why a column alias defined in SELECT is invisible to WHERE, GROUP BY, and HAVING, but works fine in ORDER BY.

🔄 Likely Follow-up

"Why can you use a SELECT alias in ORDER BY but not in WHERE?" ORDER BY is logically processed after SELECT, so the alias already exists by then — WHERE runs before SELECT, so it doesn't.

🎯 Say this in the interview — the exact lines to land

"SQL is logically processed as FROM/JOIN, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY — with LIMIT/OFFSET/TOP applied last of all. That's not the order you write it in, and it's exactly why WHERE can't filter on an aggregate or see a SELECT alias, while HAVING and ORDER BY can."

  • Written vs. executed → you type SELECT first, but FROM/JOIN runs first and SELECT runs fifth.
  • WHERE can't see aggregates → aggregates aren't computed until GROUP BY, which runs after WHERE — that's exactly why HAVING exists.
  • Alias blind spot → a SELECT alias doesn't exist yet when WHERE, GROUP BY, or HAVING run, so referencing it there fails.
  • ORDER BY sees it → ORDER BY runs after SELECT, so the alias is already defined and safe to use.
  • LIMIT/OFFSET last → row-count trimming happens after everything else, on the final sorted set.
📖 Explanation ▾

A SQL query is logically processed in a fixed order that has nothing to do with the order you type the clauses in: FROM/JOIN, then WHERE, then GROUP BY, then HAVING, then SELECT, then DISTINCT, then ORDER BY — with LIMIT, OFFSET, or TOP applied after all of that, on the final sorted set. "Logically" matters here: a real database engine's query optimizer is free to reorder or combine steps internally for speed, as long as the result it hands back is identical to running the steps in this exact logical order.

This is exactly why WHERE can't filter on an aggregate like COUNT(*) — aggregates aren't computed until the GROUP BY step, which runs after WHERE is already done. That's the direct reason HAVING exists: it's the filter that runs after grouping. See WHERE vs. HAVING for that comparison in full.

The same ordering fact explains the alias behavior. A column alias is only assigned once the SELECT step runs — step 5. Since WHERE, GROUP BY, and HAVING are all steps 2-4, they run before the alias exists, so referencing it there fails. ORDER BY is step 6, running after SELECT, so the alias is already available by the time it runs.

💻 See the code ▾
SQL 
SELECT salary, salary * 1.1 AS new_salary
FROM employees
ORDER BY new_salary;   -- ✅ Works: ORDER BY runs AFTER SELECT, alias already exists

By the time ORDER BY runs (step 6), SELECT (step 5) has already created new_salary.

SQL 
SELECT salary, salary * 1.1 AS new_salary
FROM employees
WHERE new_salary > 50000;   -- ❌ Error: invalid column name "new_salary"

WHERE is step 2 — it runs before SELECT (step 5) ever creates new_salary, so the alias doesn't exist yet.

🧭 Use Cases — recognize these when they happen to you ▾
1 You reference a SELECT alias inside WHERE

The alias is only created when SELECT (step 5) runs. WHERE (step 2) runs three steps earlier, so the alias doesn't exist yet — the reference fails.

RememberWHERE runs before SELECT → the alias isn't there yet.
2 You try to filter on an aggregate like COUNT(*) directly in WHERE

COUNT(*) isn't computed until the GROUP BY step (step 3), which runs after WHERE (step 2) is already done — that's the direct reason HAVING exists, as the filter that runs after grouping.

RememberFiltering on an aggregate → use HAVING, not WHERE.
3 You reference that same SELECT alias inside ORDER BY instead

ORDER BY is step 6, running right after SELECT (step 5) has already created the alias — so by the time ORDER BY runs, the alias is already defined and safe to use. This is the one place the alias reliably works.

RememberORDER BY runs after SELECT → the alias already exists.
🌍 Real-world example ▾

A SQL query reads like a recipe but runs like a factory line. Raw materials (rows from FROM/JOIN) get filtered and grouped long before anything gets its final label (SELECT), and the boxes only get trimmed to a smaller batch (LIMIT) once every earlier station on the line is finished.
