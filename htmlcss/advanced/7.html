⭐ HTML & CSS · Advanced · Should Know

It renders perfectly in your browser — what makes sure it survives everyone else's?

How do you make sure something that works in your own browser doesn't quietly break for someone using a different one — and what's the actual difference between checking for a feature and checking for a browser name?

Why it matters ▾
  • The real bug this explains: a feature ships fine in whatever browser you happened to build it in, then silently breaks for a slice of real users on an older browser or a different rendering engine — nobody notices until a support ticket shows up.
  • A near-universal front-end interview opener — "how do you handle browser compatibility?" — because it separates people who've actually shipped to real, mixed traffic from people who've only ever tested in one browser.
  • It sets up the senior-level answer (build a working baseline, then layer enhancements on top) instead of the junior answer ("test in Chrome and hope").
🔥 Easy interview recall

Cross-browser compatibility = "ask the browser what it can actually do, don't guess from its name — and always leave a working floor underneath."

Think: @supports checks the feature first → the base rule always still works → the enhanced rule only layers on top where it's actually supported.

🧠 Visual Mental Model — one base rule, one enhancement layered on top
⚠️ Common Trap

Checking the browser's name is not feature detection. A user-agent/browser-name check breaks the moment that guess is wrong — a new version, an unfamiliar browser, a spoofed string — while @supports and equivalent JavaScript checks ask the browser directly whether it actually supports the feature.

🔄 Likely Follow-up

"Is @supports the only place feature detection happens?" No — it's the CSS-native version. JavaScript has its own feature checks (e.g. testing whether an API exists on window) for anything CSS itself can't test, but it's the same idea either way: check the actual capability, never the browser's name or version.

🎯 Say this in the interview — the exact lines to land

"Cross-browser compatibility means writing a baseline that works everywhere, then using feature detection — like CSS's @supports — to layer on enhancements only where a browser actually supports them, so anything unsupported degrades gracefully instead of breaking."

  • @supports → CSS-native feature detection — ask the browser directly, don't guess from its name.
  • Progressive enhancement → build the working floor first, then layer extras on top for browsers that support them.
  • Graceful degradation → the same idea from the other side — an enhanced experience that still functions, just less polished, if a feature is missing.
  • Vendor prefixes → a historical bridge, far less necessary today now that most stable CSS features ship unprefixed.
  • Compatibility testing → real target browsers and versions, never just whatever's open on your own machine.
📖 Explanation ▾

Different browsers use different rendering engines, and even two versions of the same engine can render valid CSS or HTML differently — especially for a newer feature, an edge case, or plain default styling nobody thought to reset. That's why feature detection exists: checking, at runtime, whether the browser actually supports something before relying on it, instead of guessing from its name or version string, which is unreliable — names and version numbers change and don't map cleanly onto what any specific build actually supports.

Progressive enhancement starts from a baseline that works everywhere, then layers extra behavior on top only for browsers that can handle it. @supports is the CSS-native way to do exactly that: it's an at-rule that only applies the block inside it when the browser actually supports the feature or property value being tested. Graceful degradation is the same idea read from the other direction — an enhanced experience that still functions, maybe a little less polished, instead of breaking outright when a feature isn't there.

Progressive EnhancementGraceful Degradation
Starting pointA baseline that works everywhereThe full, enhanced experience
DirectionBuilds up from the floorHandles the gap below the ceiling
Older browser seesThe plain baseline, on purposeA reduced but still working version

Vendor prefixes (-webkit-, -moz-, -ms-, -o-) were the same idea at the property level, years ago: a browser maker shipped an experimental feature under its own prefix before it became a finished standard, so a page sometimes needed three or four prefixed versions of one rule. That's far less true today — most mainstream CSS features ship unprefixed once they're stable — so reaching for a prefix by default isn't the safe assumption it used to be. None of this replaces actually testing on the real browsers and versions people use — assuming from whatever's open on your own machine is exactly the gap this whole page exists to close.

💻 See the code ▾
CSS 
.cards {
  display: flex;
  margin: 0 -8px;          /* fallback: works everywhere */
}
.cards > * { margin: 0 8px; }

/* only runs where the browser understands gap on flex */
@supports (gap: 16px) {
  .cards {
    gap: 16px;             /* enhanced: no margin trick needed */
    margin: 0;
  }
  .cards > * { margin: 0; }
}

The margin rule always applies first. @supports only layers the gap-based version on top where the browser actually understands it — nothing breaks either way.

JS 
if ('IntersectionObserver' in window) {
  // enhanced: lazy-load images as they scroll into view
} else {
  // fallback: images just load normally, nothing breaks
}

Same idea as @supports, just in JavaScript — check for the actual feature on the object it would live on, never the browser's name or version string.

🌍 Real-world example ▾

Think of the base CSS rule like a building's plain staircase — it always works, no matter what. @supports is like checking "does this building also have an elevator?" before offering it: if yes, that becomes a nicer option on top; if not, everyone still reaches the same floor by the stairs, just without the extra convenience.
