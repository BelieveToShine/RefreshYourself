ToDictionary vs. ToLookup — one key, one value or many?

"Same key selector, different contract — what happens when two elements share a key?"

Why it matters ▾
🗂️ ToDictionary
❗ ProblemMaterializing results keyed by something assumed unique — an Id — but that turns out to have a duplicate crashes the whole operation with an ArgumentException the moment it happens, not a graceful fallback.
✅ SolutionToDictionary enforces a strict unique-key contract by design — it throws exactly when a collision happens, surfacing a bad uniqueness assumption immediately instead of silently overwriting one value with another.
RecallToDictionary = unique key, or it throws.
📚 ToLookup
❗ ProblemNeeding "all orders for this customer" grouped by key has no safe home in a Dictionary<TKey,TValue> — a single value slot can't hold multiple matches, and ToDictionary would throw the instant two orders share a customer id.
✅ SolutionToLookup is built for one-to-many from the start — every key maps to a list of values, and indexing a missing key returns an empty sequence instead of throwing.
RecallToLookup = one key, many values, never throws.
🔥 Easy interview recall

ToDictionary → unique key, throws on collision

ToLookup → many values per key, never throws

Think: Two orders, same customer id — ToDictionary crashes, ToLookup just groups them.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ToDictionary is not the "safe default" over ToLookup. It's the strict one — the moment the key selector isn't actually unique, it throws at runtime instead of degrading gracefully like a collection would.

🔄 Likely Follow-up

"What happens if you index a ToLookup result with a key that was never in the source?" It returns an empty sequence — never throws. That's different from a real Dictionary's indexer, which throws KeyNotFoundException for a missing key.

🎯 Say this in the interview — the exact lines to land

"ToDictionary demands a unique key and throws ArgumentException the moment the key selector produces a duplicate. ToLookup is built for one-to-many from the start — each key maps to a list of matches, and indexing a missing key just returns empty instead of throwing."

  • ToDictionary → use when the key is genuinely unique, IDs, enum values.
  • ToLookup → use when one key legitimately maps to many, grouping by a non-unique field.
  • Missing key → Dictionary throws, ToLookup returns empty, no exception either way for ToLookup.
  • Both are immediate, not deferred — built once, at the call.
📖 Explanation ▾

ToDictionary walks the source once and inserts each element under the key your selector returns. The contract is strict: if a second element produces a key already in the dictionary, it throws immediately — there's no "overwrite" fallback, the whole materialization fails right there.

ToLookup was built for exactly the case ToDictionary can't handle: many elements legitimately sharing one key. It behaves like a read-only, multi-value dictionary — lookup[key] returns every matching element as a sequence, and a key that was never in the source just returns an empty sequence instead of throwing.

Both are immediate — the whole structure is built the moment you call them, not re-built on each enumeration the way a deferred query would be. The decision between them isn't about performance; it's entirely about whether the key selector is actually unique for your data.

💻 See the code ▾
C# 
var byId = customers.ToDictionary(c => c.Id);
Console.WriteLine(byId[42].Name);   // ✅ fine — Id is genuinely unique

Works cleanly only because the key is actually unique per element.

C# 
var byCustomer = orders.ToDictionary(o => o.CustomerId);
// ❌ ArgumentException — two orders share a CustomerId

The exact same call style crashes the moment a key repeats.

C# 
var byCustomer = orders.ToLookup(o => o.CustomerId);
foreach (var order in byCustomer[42])   // ✅ every order for customer 42
    Console.WriteLine(order.Total);

foreach (var order in byCustomer[999])  // ✅ empty sequence, no exception
    Console.WriteLine(order.Total);

The same duplicate key that crashed ToDictionary is exactly what ToLookup is for.

🧭 Use Cases — recognize these when they happen to you ▾
1 Keying a price list by SKU for O(1) lookups

A pricing service keying products by SKU is the textbook ToDictionary case — SKU is supposed to be unique, and if a bad feed ever sends a duplicate, throwing immediately catches a real data bug instead of silently overwriting one price with another.

RememberGenuinely unique key → ToDictionary, and let it throw on a real collision.
2 Grouping orders where one customer can have many

Showing "all orders for this customer" on an account page is exactly the one-to-many shape ToLookup exists for — building it once and indexing by customer id repeatedly is far cheaper than re-filtering the whole order list each time.

RememberOne key, many legitimate matches → ToLookup, not ToDictionary.
3 Reaching for ToDictionary "just in case" duplicates exist

Treating ToDictionary as the generic "keyed materializer" is exactly backwards — it's the strict option. The moment real data has even one duplicate key, the entire materialization throws, instead of degrading the way a collection would.

RememberNot sure the key is unique? That uncertainty is the reason to use ToLookup instead.
🌍 Real-world example ▾

A pricing service materializes a price list keyed by SKU for fast O(1) lookups. ToDictionary is correct there because SKU truly is unique — but the moment an upstream feed sends a duplicate SKU by mistake, ToDictionary throws immediately instead of silently overwriting one price with another, which is actually the behavior you want: it surfaces a real data integrity bug instead of hiding it.
