Middleware says no at the door — who checks again once you're inside?

"Where should auth checks actually live in a Next.js app — Middleware, or inside the page itself?"

Why it matters ▾
🛡️ Middleware check
❗ ProblemEvery protected route needs a session check before it renders — repeating that logic inside every single page is easy to forget on a new route.
✅ SolutionMiddleware runs on the Edge before the route renders, checking a session cookie on every matching request and redirecting unauthenticated ones away immediately.
RecallMiddleware = the fast gate, checked before anything renders.
🧩 Server Component re-check
❗ ProblemMiddleware's redirect can be bypassed in edge cases (a misconfigured matcher, a direct API call) and runs on a different runtime, so it's not always the right place for a heavier check.
✅ SolutionA Server Component independently re-verifies the session, server-side, right before rendering genuinely sensitive data — a second, real checkpoint, not blind trust in the first.
RecallServer Component = the second gate, right before the sensitive data renders.
🔥 Easy interview recall

Middleware → checks fast, before render

Server Component → re-checks, before sensitive data

Think: Middleware is the bouncer at the door. Server Component checks ID again before handing over anything valuable.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Trusting Middleware's redirect as the only auth check. Middleware can be bypassed in edge cases — a misconfigured matcher, a direct API call — so a protected Server Component or Route Handler still needs its own server-side check.

🔄 Likely Follow-up

"Where does a Server Action fit into this?" A Server Action must independently verify the caller's session at the top of its own function body — it's a real callable endpoint under the hood, not automatically protected just because the UI calling it happens to sit behind an authenticated page.

🎯 Say this in the interview — the exact lines to land

"Middleware checks the session cookie on every matching request and redirects before the route renders, which is cheap and runs on the Edge. The Server Component (or Route Handler) still re-verifies the session itself before touching sensitive data — Middleware alone isn't treated as the only line of defense."

  • Middleware → fast, Edge-level, first gate, based on the cookie alone.
  • Server Component → heavier, server-side re-check right before sensitive data.
  • Defense in depth → never rely on one checkpoint for anything genuinely sensitive.
  • A Server Action → verifies its own caller, independent of the page around it.
📖 Explanation ▾

Next.js Middleware runs on every request that matches its config.matcher, before the route it's protecting even starts rendering. Reading a cookie and redirecting is cheap, so it's a good fit for a fast, blanket "is anyone logged in at all" check across many routes at once.

What Middleware is not is a full authorization system. It runs on a constrained Edge runtime, so a heavier check — looking up a user's role in a database, checking a permission table — is often better placed in the Server Component itself, which already has normal server-side access to whatever data store the check needs.

Treating these as two independent layers, rather than one handing off blind trust to the other, is the actual point: a request that somehow reaches the Server Component without passing through Middleware (a typo in the matcher, a route added later) still gets stopped, because the Server Component never assumed Middleware already did the work.

💻 See the code ▾
JS 
// middleware.js
export function middleware(request) {
  const session = request.cookies.get('session');
  if (!session) {
    return NextResponse.redirect(new URL('/login', request.url)); // ❌ no cookie — redirect before render
  }
  return NextResponse.next();  // ✅ cookie present — let it through
}

export const config = { matcher: ['/dashboard/:path*'] };

Cheap and fast — only checks that a cookie exists, not what role it belongs to.

JSX 
// app/dashboard/page.jsx
export default async function DashboardPage() {
  const session = await getSession();  // 🔁 re-verify, don't just trust Middleware
  if (!session) redirect('/login');        // ✅ defense in depth

  const data = await getSensitiveData(session.userId);
  return <Dashboard data={data} />;
}

The page never assumes Middleware already did the work — it checks again, server-side.

🧭 Use Cases — recognize these when they happen to you ▾
1 A logged-out visitor types /dashboard straight into the address bar

Middleware sees there's no valid session cookie and redirects before the dashboard route ever starts rendering — the page's own code never even runs. This is the #1 scenario Middleware exists for.

RememberNo cookie at all → Middleware alone already handles it.
2 An admin-only page needs more than "is this user logged in"

Middleware's cheap check only confirms a session exists — it typically doesn't do a full database lookup. Checking the user's actual role or permission belongs in the Server Component, which already has normal server-side access to that data.

RememberRole/permission checks beyond "logged in?" → Server Component, not Middleware.
3 A new protected route is added, but the Middleware matcher is never updated

If the new route isn't covered by config.matcher, Middleware never runs for it at all — the request reaches the Server Component directly. Only that component's own re-check stops an unauthenticated request from seeing real data.

RememberMatcher gaps happen — the Server Component's own check is what actually saves you.
🌍 Real-world example ▾

Your app's Middleware only checks /dashboard/*, but a teammate adds a new /billing page under the same account area and forgets to update the matcher. Because the Server Component for /billing still re-verifies the session itself, a logged-out request is stopped there anyway — if that check didn't exist, the missed matcher entry would have quietly exposed billing data to anyone with the URL.
