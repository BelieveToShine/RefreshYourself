List vs. Set vs. Map vs. Queue — four root shapes, one real choice

"What's the difference between the four root collection shapes — List, Set, Map, and Queue?"

Why it matters ▾
📋 List
❗ ProblemYou need items in a specific order, reachable by position, and the same value might legitimately show up twice (a shopping cart, a sentence of words).
✅ SolutionA List keeps insertion order and lets you fetch by index — duplicates are allowed because position, not uniqueness, is the point.
RecallList = ordered + indexed, duplicates fine.
🧺 Set
❗ ProblemA collection of tags or IDs breaks the moment the same value sneaks in twice — now you're double-counting or double-processing it.
✅ SolutionA Set refuses a duplicate on add() per its equality contract — order isn't promised unless you pick LinkedHashSet or TreeSet.
RecallSet = no duplicates, order not promised.
🗂️ Map
❗ ProblemLooking up a value by a meaningful name — a user ID, a config key — by scanning a List every time is slow and awkward.
✅ SolutionA Map stores key→value pairs with unique keys, so a lookup is a direct key access instead of a linear scan.
RecallMap = key → value, keys unique.
🚦 Queue
❗ ProblemA set of tasks has to be processed in the order they arrived, not in whatever order you happen to pull them.
✅ SolutionA Queue models that processing order — typically first-in-first-out, with Deque adding both-ends access and PriorityQueue ordering by priority instead.
RecallQueue = ordered for processing, FIFO by default.
🔥 Easy interview recall

List → ordered + indexed, duplicates OK

Set → no duplicates, order not promised

Map → key → value, keys unique

Queue → ordered for processing (FIFO default)

Think: need position → List need "no repeats" → Set need a lookup by name → Map need arrival order → Queue

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A Queue is not guaranteed to be FIFO. Plain FIFO is just the default behavior of implementations like LinkedList used as a Queue — PriorityQueue orders by priority instead of arrival, and it's still fully a Queue.

🔄 Likely Follow-up

"What happens if I add the same element to a List vs. a Set twice?" The List stores it twice and keeps both. The Set's add() returns false the second time and the collection stays the same size — equals()/hashCode() is what it checks against the elements already there.

🎯 Say this in the interview — the exact lines to land

"List keeps order and lets you index into it, and allows duplicates. Set enforces uniqueness through its equality contract, usually without a guaranteed order. Map pairs unique keys to values for direct lookup. Queue models processing order, typically first-in-first-out."

  • List → order + duplicates OK, pick it when position matters.
  • Set → uniqueness enforced, pick it when "do I already have this" matters.
  • Map → key → value lookup, pick it when you look things up by name.
  • Queue → FIFO processing by default, Deque/PriorityQueue change that.
📖 Explanation ▾

A List and a Set are both "a bunch of elements," but they disagree on two things: order and duplicates. A List remembers the exact position you put things in and happily holds the same value twice — think a numbered coat-check row. A Set checks every new element against what it already holds and rejects an exact duplicate outright — think a guest list where nobody's name appears twice.

A Map is a different shape entirely — it doesn't store bare elements, it stores key→value pairs, and only the key has to be unique. That's what makes a lookup "give me the user with ID 42" a direct jump to the right bucket instead of a scan through every element.

A Queue is about processing order, not storage order for its own sake. The default mental model is a single line at a checkout counter — first one in line is the first one served — but Deque lets you add/remove from both ends, and PriorityQueue throws arrival order out entirely in favor of whichever element currently has the highest priority.

💻 See the code ▾
☕ Java 
List<String> names = new ArrayList<>();
names.add("Amy");
names.add("Amy");           // ✅ stored twice — List allows it

Set<String> unique = new HashSet<>();
unique.add("Amy");
boolean added = unique.add("Amy"); // ❌ false — duplicate rejected

Set.add() returns false on a duplicate — the size never grows for a repeat.

☕ Java 
Queue<Integer> fifo = new LinkedList<>();
fifo.offer(3); fifo.offer(1); fifo.offer(2);
fifo.poll();                     // ✅ 3 — arrival order

Queue<Integer> byPriority = new PriorityQueue<>();
byPriority.offer(3); byPriority.offer(1); byPriority.offer(2);
byPriority.poll();               // ❌ 1 — smallest value wins, not arrival

Same Queue interface, two different orderings — never assume FIFO without checking the implementation.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're de-duplicating a list of signup emails before sending one newsletter

Dumping the raw list into a Set drops every exact repeat automatically — no manual loop checking "have I seen this one already." A List would keep every duplicate, so the same person gets emailed twice.

RememberNeed "no repeats" → reach for Set, not List.
2 You need an O(1) lookup from a user ID to that user's profile

A Map<String, User> turns "find the user with this ID" into one direct key access instead of scanning a List element by element until a match is found.

RememberLookup by name/ID → reach for Map, not a scanned List.
3 You assume the Queue you're using always processes in arrival order

Code written against the Queue interface alone can't tell you the ordering — a LinkedList-backed queue polls in arrival order, but a PriorityQueue polls by priority, which can silently change behavior if someone swaps the implementation.

RememberQueue ≠ guaranteed FIFO — the implementation decides the order.
🌍 Real-world example ▾

A List is a numbered coat-check row. A Set is a guest list where no name repeats. A Map is a phone book — name in, number out. A Queue is the single line at a checkout counter.
