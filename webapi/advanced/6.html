Intermittent 500s in prod, clean on your machine — where do you actually look?

"Your API starts throwing intermittent 500 errors in production that you can't reproduce locally. Walk me through your diagnostic approach."

Why it matters ▾
🚨 500 Errors in Production
❗ ProblemA 500 in production with no obvious reproduction steps is one of the most common on-call situations — guessing at a fix wastes time while it keeps happening.
✅ SolutionCorrelate the failing requests first (timing, deploys, load, specific users/endpoints) to find the real pattern before trying to reproduce it deliberately.
RecallProd 500s = correlate with data before you touch a single line of code.
🔥 Easy interview recall

Prod 500s = "correlate with data before you touch a single line of code."

Think: Correlate → narrow → reproduce on purpose → fix — skip a step and you're guessing, not diagnosing.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Add a try/catch and swallow it" is not a fix. It — and "just add more logging and ship it" — suppresses the symptom without ever confirming the real cause, so the intermittent failure keeps happening, just more quietly, which is worse than a visible 500.

🔄 Likely Follow-up

"Suppose the logs show the errors cluster tightly right after every deploy, then taper off within a few minutes — what does that suggest?" That points at a deploy-time issue, not a load issue — new instances still warming up or cold-starting, a rolling deploy briefly running old and new code side by side against a shared resource, or a cache/connection-pool warming back up — a different diagnostic path than one driven by traffic volume.

🎯 Say this in the interview — the exact lines to land

"I'd start with data, not a guess — pull the failed requests' logs by correlation ID to see the full stack trace and context, then check whether the 500s correlate with a specific endpoint, client, load level, time of day, or deploy window. 'Intermittent' and 'can't reproduce locally' are themselves clues, often pointing at concurrency or an environment difference. Once I have a real hypothesis, I reproduce it deliberately under production-like conditions before shipping any fix."

  • Correlation/trace IDs → tie one failed request to its full stack trace and context in the logs.
  • "Intermittent" + "won't repro locally" → often points at concurrency, shared state, or an environment difference, not just bad luck.
  • Narrow before touching code → correlate against deploys, downstream status, and infra events first.
  • Reproduce deliberately → simulate prod-like load and concurrency, not one request in an IDE.
  • A real fix → confirms the cause before shipping, never just suppresses the symptom.
📖 Explanation ▾

The first move is data, not a guess. Pull the failing requests from logs or an error tracker and follow each one's correlation/trace ID — the same id threaded through every log line written while that request ran — back to its full stack trace and request context. See Global Exception Handling for the middleware that actually captures an unhandled exception's details in the first place. Once there are several failures to look at, check whether they correlate with anything: a specific endpoint, a specific client, a time of day, a load level, or a deployment window.

"Intermittent" and "can't reproduce locally" are themselves information, not just an annoyance. A bug that only shows up in production under real concurrency or scale is exactly the class of problem covered on Distributed Systems Considerations — a race condition, a shared-state assumption that holds on one dev machine but breaks across multiple instances, a connection pool or a downstream rate limit that only exhausts under real traffic — or it's an environment difference: a config value, a certificate, an environment variable that's only set (or wrong) in production.

Correlate the failure timestamps against deploys, downstream dependency status, and infrastructure events — autoscaling, restarts — before changing a single line; a blind change made on a guess can mask the real cause or introduce a new one. Once there's a real hypothesis, reproduce it on purpose. That usually means simulating production-like conditions — concurrent requests, multiple instances — since a single local request already failed to show the bug once.

If the 500s correlate with…That points toward…

💻 See the code ▾
C# 
app.Use(async (context, next) =>
{
    // every log line written during this request now carries the same id
    using (_logger.BeginScope(new Dictionary<string, object>
    {
        ["CorrelationId"] = context.TraceIdentifier
    }))
    {
        await next(context); // ✅ this is what a failed request's ID gets grepped for
    }
});

Without a correlation id tying every log line for one request together, "check the logs" means scrolling through everyone else's requests too.

🧭 Use Cases — recognize these when they happen to you ▾
1 500s spike right after a deploy, then taper off within minutes

Spiking right after a deploy and fading within minutes points at the deploy itself, not the code — new instances still cold-starting, a rolling deploy briefly running old and new code side by side against a shared resource, or a cache/connection pool still warming back up.

RememberSpikes right after deploy, then fade → a deploy-time issue, not a code bug.
2 500s only appear under concurrent or high load, never on a single request

500s that only appear once real concurrent traffic hits, and never on a single request, usually mean a race condition, a shared-state assumption that held on one machine but breaks across instances, or a connection pool/rate limit that only exhausts under real volume.

RememberOnly under load → race condition or exhausted shared resource.
3 500s cluster tightly on one specific endpoint or one specific client, nowhere else

500s that cluster on one specific endpoint or one specific client — and nowhere else — point at a code path or a downstream dependency tied to that particular request shape, not a problem with the API as a whole.

RememberSame endpoint/client every time → check that path's own dependency.
4 500s show no pattern across traffic, deploys, or time of day

500s with no correlation to traffic, deploys, or time of day are the case where the cause usually isn't the request at all — a config value, certificate, or environment variable that's only set, or only wrong, in production.

RememberNo pattern anywhere → suspect an environment difference, not randomness.
🌍 Real-world example ▾

Monitoring shows 500s spiking sporadically — roughly 1 in 500 requests, no obvious pattern in the alert, and every attempt to hit the same endpoint locally succeeds. Pull the failing requests' logs by correlation id first — is it always the same endpoint, the same client, or the same downstream call? Check whether the spikes line up with a deploy, a time of day, or a load spike. Only once a real hypothesis exists — a connection pool exhausting under concurrent load, say — try to reproduce it deliberately, with real concurrency, not a single request from an IDE.
