reactive() — what's actually watching when your data changes?

"How does Vue 3's reactivity system actually work under the hood?"

Why it matters ▾
🪤 Proxy-based reactivity
❗ ProblemA plain JavaScript object has no way to tell anything when one of its properties is read or changed — without something intercepting those reads and writes, Vue has no way to know which parts of the UI depend on which piece of data, or when to update them.
✅ Solutionreactive() wraps the object in a JavaScript Proxy. Its get trap records which effect is currently reading a property; its set trap re-runs every effect that read it. Vue 2 used Object.defineProperty instead — a different mechanism that only works on properties that already existed when it ran, which is why it couldn't see new/deleted keys or array index writes.
Recallreactive() = a Proxy that watches every get and set.
🔥 Easy interview recall

Proxy reactivity = "get tracks, set triggers."

Think: get('count') → tracks the current effect set('count', 1) → triggers every tracked effect

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Vue 3 reactivity is not built on Object.defineProperty. That was Vue 2's mechanism — Vue 3 uses a Proxy around the whole object instead, which is also why it can detect new/deleted keys and array index writes that Vue 2 structurally couldn't.

🔄 Likely Follow-up

"Why can't a plain destructured primitive be reactive, given all this?" A Proxy traps operations on the object itself — once you copy a primitive value out via destructuring, you have a plain JS value with no Proxy wrapping it anymore, so there's nothing left to intercept.

🎯 Say this in the interview — the exact lines to land

"reactive() wraps an object in a JavaScript Proxy. Its get trap records which effect is currently running, so it gets tracked as a dependency; its set trap looks up every tracked effect for that property and re-runs them. Vue 2 used Object.defineProperty instead, which only intercepted properties that already existed — that's why Vue 3 can detect new keys and array index writes that Vue 2 structurally couldn't."

  • get trap → tracks the currently running effect as a dependency.
  • set trap → triggers every effect that depends on that property.
  • Vue 2's Object.defineProperty → only worked on pre-existing properties, missing new keys and array indices.
  • Destructured primitive → no longer reactive — the Proxy wraps the object, not a value copied out of it.
📖 Explanation ▾

An "effect" is just any reactive function Vue runs that depends on data — a component's render function, a computed getter, or a watch callback. When an effect runs and reads a reactive property, the get trap notices and adds that effect to a dependency list kept for that specific property. When code later writes to that property, the set trap looks up the same list and re-runs every effect in it.

This is why Vue 3 can see things Vue 2 couldn't. Object.defineProperty has to be called on a property that already exists — Vue 2 walked an object's existing keys at setup time and converted each one individually. Adding a brand-new key, deleting one, or writing to an array index by position all happened outside that setup step, so Vue 2 had no hook in place to notice them. A Proxy wraps the whole object once; its traps fire for any property access, including ones that didn't exist yet.

💻 See the code ▾
JavaScript 
import { reactive, effect } from 'vue'

const state = reactive({ count: 0 })

effect(() => {
  console.log(state.count)   // 'get' trap tracks THIS effect
})

state.count++                // ✅ 'set' trap re-runs the effect above

Reading state.count inside effect() is what ties them together — the get trap only tracks whatever effect is running at that moment.

JavaScript 
const { count } = state   // ❌ count is now a plain number
count++                        // does nothing to state.count — no Proxy here

Destructuring copies the value out — the Proxy only wraps state itself, so a copied-out primitive has no traps left on it.

🧭 Use Cases — recognize these when they happen to you ▾
1 A computed getter reads a reactive property

The get trap fires and adds the computed getter's own effect to count's dependency list — the exact mechanism that lets computed re-evaluate automatically later.

RememberReading inside a computed → tracked, same as any other effect.
2 You write to a reactive array by index

Because the Proxy traps any property access, writing arr[2] = 'X' fires set like any other property — Vue 2's Object.defineProperty approach couldn't see this at all, so it needed its own special-cased array methods.

RememberArray index write → just another set trap, no special-casing needed.
3 You destructure a value out of reactive state, expecting it to stay reactive

A candidate might assume the destructured count is still "the same reactive thing." It isn't — it's a plain primitive now, and nothing intercepts reading or writing it anymore. (This is exactly what toRefs() exists to fix.)

RememberDestructured value → plain primitive, no Proxy left to trap it.
🌍 Real-world example ▾

Think of the Proxy as a receptionist standing in front of a filing cabinet. No one touches a file directly — every read or write goes through the receptionist first, who writes down who asked to see which file, and later tells all of them when that file changes. The cabinet itself never changed; the receptionist is the whole reason anyone gets notified.
