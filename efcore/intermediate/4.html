Eager vs. Explicit vs. Lazy Loading — who decides when the query fires?

Eager loading vs. explicit loading vs. lazy loading — what triggers each, and when does the actual query run for each?

Why it matters ▾
📥 Eager Loading
❗ ProblemRelated data loaded separately later needs its own round trip.
✅ SolutionInclude() folds it into one query, upfront.
RecallEager → asks upfront, one query.
🎯 Explicit Loading
❗ ProblemEager loading everything upfront wastes a query when it's rarely needed.
✅ Solution.Load() fetches an already-tracked entity's data only when your code decides.
RecallExplicit → asks on demand, later.
💤 Lazy Loading
❗ ProblemManually remembering Include() or .Load() everywhere is easy to forget.
✅ SolutionProxies fire the query automatically, the instant a property is touched.
RecallLazy → asks automatically, without telling you.
🔥 Easy interview recall

Eager → asks upfront, one query

Explicit → asks on demand, later

Lazy → asks automatically, without telling you

Think: Eager → you decide before the query runs Explicit → you decide after, on your own call Lazy → nobody decides — touching the property decides for you

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Lazy loading isn't free convenience. Turning it on project-wide makes every navigation-property read a potential hidden query — exactly what makes the N+1 problem so easy to miss in code review, since the offending line just looks like an ordinary property access.

🔄 Likely Follow-up

"Why would a team deliberately disable lazy loading entirely, project-wide, even though it's more convenient?" It forces every data load to be explicit or eager, so it's visible right there in the code — making N+1 and other unexpected queries far easier to catch during code review.

🎯 Say this in the interview — the exact lines to land

"Eager loading, with Include()/ThenInclude(), pulls related data into the original query so it runs once, at query time. Explicit loading calls .Load() on an already-tracked entity's navigation property whenever the code decides to. Lazy loading, with proxies enabled, fires a query automatically the instant you touch a navigation property — which is exactly what causes the N+1 problem inside a loop."

  • Include()/ThenInclude() → one query, at query time — a JOIN, or a couple of controlled queries with AsSplitQuery().
  • Explicit → .Load() on demand, called later in the code, on an entity that's already tracked.
  • Lazy → transparent, on touch — needs UseLazyLoadingProxies(), and it's the exact mechanism behind N+1.
  • Many teams disable lazy loading project-wide on purpose, so every load stays visible in the code.
📖 Explanation ▾

Eager loading folds the related data into the query you already wrote — Include() names the navigation property to bring along, and ThenInclude() reaches one level deeper. By default EF Core builds one SQL query with a JOIN; call AsSplitQuery() and it switches to a couple of separate, still-controlled queries instead (the Advanced tier's Query Splitting topic covers when that trade-off is worth it).

Explicit loading waits. The entity is already tracked by the context, and later — inside an if, after a check, wherever the code actually needs the data — you call context.Entry(order).Collection(o => o.Lines).Load(). Same navigation property as eager, just a separate trip triggered on purpose.

Lazy loading needs UseLazyLoadingProxies() enabled and runtime proxy classes around your entities. From then on, simply reading order.Lines — no method call, nothing that looks like a database operation — is enough to fire a query the moment it happens. Read that same property once per iteration inside a loop, and it fires one query per iteration — the N+1 problem.

💻 See the code ▾
C# 
var orders = context.Orders
    .Include(o => o.Customer)      // one level
    .ThenInclude(c => c.Address)    // one level deeper
    .ToList();                      // ✅ one query, runs now

Include()/ThenInclude() load everything as part of the same query — no extra round trip.

C# 
var order = context.Orders.First();   // Lines not loaded yet

if (needsLineDetails)
{
    context.Entry(order)
        .Collection(o => o.Lines)
        .Load();                        // ✅ separate query, triggered here
}

You decide the moment — the query only runs if this branch actually executes.

C# 
// UseLazyLoadingProxies() enabled at startup
var orders = context.Orders.ToList();   // Lines not loaded yet

foreach (var order in orders)
{
    Console.WriteLine(order.Lines.Count);   // ❌ one query per order — N+1
}

Every order.Lines read looks like a normal property access — that's exactly what makes N+1 invisible in review.

🧭 Use Cases — recognize these when they happen to you ▾
1 You already know you'll need an order's Customer and Address, every time

Every order display needs Customer and Address, so eager loading pulls both into the same query — no extra round trip once the page renders.

RememberAlways needed → Include(), upfront.
2 An order's Lines are only needed inside one specific if-branch

The order is already tracked; calling .Load() only inside the branch that needs Lines means the extra query only runs when that branch actually executes.

RememberOnly-sometimes needed → explicit .Load(), on demand.
3 A navigation property gets read inside a foreach loop, with lazy loading on

Each order.Lines read looks like an ordinary property access, but with lazy loading it silently fires one query per iteration — the N+1 problem hiding in plain sight during code review.

RememberProperty read in a loop + lazy → N+1.
🌍 Real-world example ▾

Your order-summary endpoint feels slow, and the database logs show a burst of near-identical queries for a single request. Check whether lazy loading is enabled and whether a navigation property is being read inside a loop — switching that one access to an eager Include() (or an explicit .Load() before the loop starts) collapses that burst into a single query.
