for x in obj works because Python calls __iter__ under the hood — dunders are how your object plugs into built-in syntax

__str__ vs. __repr__? How do dunder methods integrate a custom object with Python's own syntax?

Why it matters ▾
  • Printing a custom object and seeing <Point object at 0x7f...> instead of something readable is the everyday bug this explains — no __str__ or __repr__ was defined.
  • Every custom collection, wrapper, or ORM-style class relies on dunders to behave like a built-in — a class with __getitem__ and __len__ can be indexed, sliced, and looped over exactly like a list.
  • __str__ vs. __repr__ is one of the most common Python OOP interview openers — it's a quick way to check real understanding vs. memorized syntax.
🔥 Easy interview recall

__len__ → len(obj)

__getitem__ → obj[key]

__iter__ → for x in obj

__call__ → obj()

Think: every dunder is a plug — implement it, and Python's own built-in syntax just works on your object, the same way it works on a list or a string.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Defining __eq__ alone is enough. It isn't — once a class defines __eq__ without __hash__, Python automatically sets __hash__ to None, silently making every instance unhashable (it can't go in a set or be used as a dict key) until you define __hash__ too.

🔄 Likely Follow-up

"Why does defining __getitem__ alone still make an object iterable in a for loop?" Python has an older fallback protocol — without __iter__, for falls back to calling __getitem__(0), __getitem__(1), … until an IndexError, so a sequence-like object is still iterable even without the modern iterator protocol.

🎯 Say this in the interview — the exact lines to land

"Dunder methods are literally how your object plugs into Python's built-in syntax — __iter__ backs the for loop, __call__ makes an instance callable, __getitem__ backs obj[key], and so on. Implement the right one and the built-in syntax just works."

  • __str__ → human-readable, used by str()/print(). __repr__ → developer-facing, used by the REPL/debugger, and the fallback str() uses if __str__ is missing.
  • __eq__ without __hash__ → Python sets __hash__ to None, making the type unhashable — it silently breaks sets and dict keys.
  • __len__, __getitem__, __call__, __iter__ → each backs one specific built-in operation — len(), obj[key], obj(), and the for loop.
  • __getitem__ alone → still makes an object iterable through the old fallback protocol — __getitem__(0), (1), … until IndexError.
  • __enter__/__exit__ → back the with statement — covered in depth on the Context Managers page.
📖 Explanation ▾

Python's built-in functions and operators don't special-case every type — they call one fixed dunder method on whatever object you give them and let your class decide what happens. str() and __repr__ both produce text, but they're not interchangeable:

__str____repr__
Called bystr(obj) / print(obj)repr(obj), the REPL, the debugger
Goalreadable for a personunambiguous — ideally valid Python that could recreate the object
If missingstr() falls back to __repr__Python's own default, e.g. <Point object at 0x...>

__eq__ defines what == means for your type — once you customize it, Python no longer auto-derives a consistent hash, so __hash__ needs defining alongside it (or set explicitly to None to mark the type unhashable on purpose). Two objects that compare equal must return the same hash, or a set/dict built on them breaks in subtle ways.

__len__, __getitem__, and __call__ follow the same pattern as __iter__ — each one is the single hook a piece of built-in syntax calls. __enter__/__exit__ back the with statement the same way; the Context Managers page (Intermediate) covers that pair in depth.

💻 See the code ▾
Python 
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):
        return f"Point({self.x!r}, {self.y!r})"   # looks like code that rebuilds it

>>> Point(1, 2)
Point(1, 2)

__repr__ is what the REPL and debugger show — write it so it looks like the code that made the object.

Python 
class Point:
    def __eq__(self, other):
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)

    def __hash__(self):
        return hash((self.x, self.y))   # equal objects, equal hash

Define both together — __eq__ alone silently makes the type unhashable (see the Trap above).

Python 
class Point:
    def __getitem__(self, i):
        return (self.x, self.y)[i]

>>> p = Point(3, 4)
>>> p[0]
3

__getitem__ backs obj[key] — and with no __iter__ defined, it's also what a for loop falls back to.

🌍 Real-world example ▾

A small Vector class implements __add__, __eq__, and __repr__ so it behaves like int or str in everyday code: Vector(1, 2) + Vector(3, 4) returns a new Vector(4, 6), two vectors with the same coordinates compare equal, and printing one in the debugger shows Vector(4, 6) instead of a meaningless memory address. None of that is special magic — it's the same dunder-to-syntax plug this whole page is about.
