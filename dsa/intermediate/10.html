Overlapping intervals — sort once, sweep once, never compare every pair.

"How would you merge overlapping intervals, check if someone can attend every meeting, or find the minimum number of meeting rooms needed — without comparing every interval against every other one?"

Why it matters ▾
  • "Merge intervals," "meeting rooms," and "insert interval" are three of the most frequently asked interview questions in this entire category — genuinely common, not a rare corner case.
  • The naive fix — checking every pair of intervals for overlap — is O(n²), and it's the exact thing interviewers are listening for you to avoid.
  • One idea (sort, then one linear sweep) answers all three question shapes: merging, yes/no overlap checks, and counting simultaneous overlaps.
🔥 Easy interview recall

Merge → sort by start, extend the end

Can attend all? → sort by start, check for any overlap

Min rooms needed? → +1/-1 events, sweep, track the peak

Think: Every version starts the same way — sort first, then one sweep left to right. Never pair-by-pair.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Checking every pair of intervals for overlap is not the efficient way to do this. That's an O(n²) scan — sort the intervals once (by start time for most versions of this problem) and then sweep through them in a single O(n log n) pass instead.

🔄 Likely Follow-up

"How would you find the maximum number of overlapping intervals at any single point in time?" Split every interval into a +1 event at its start and a -1 event at its end, sort all the events by time, sweep through incrementing/decrementing a running counter, and track its peak value — that peak is the answer, and it's exactly the "minimum meeting rooms needed" answer too.

🎯 Say this in the interview — the exact lines to land

"Almost every interval problem starts the same way: sort first, usually by start time — that turns an O(n²) pairwise comparison into a single O(n log n) sort-and-sweep. For merge intervals, I extend the current interval's end whenever the next one starts before it ends. For 'can I attend all meetings,' I just check whether any interval starts before the previous one ends. For 'minimum rooms needed,' I split every interval into a +1 start event and a -1 end event, sort all the events by time, and track the running counter's peak value."

  • Merge intervals → sort by start, extend the end when the next one overlaps.
  • Can attend all meetings? → sort by start, any overlap at all means no.
  • Minimum rooms needed? → +1/-1 events, sweep, track the peak count.
  • Sweep line turns O(n²) pairwise checks into one sort plus a single linear pass.
📖 Explanation ▾

Almost every interval problem has the same first move: sort the intervals — usually by start time, sometimes by end time depending on the exact question. Once they're sorted, you can walk through them once, left to right, instead of comparing every interval against every other one.

Merge intervals walks the sorted list and keeps a "current" merged interval: if the next interval's start is at or before the current one's end, they overlap, so the end gets extended to whichever end is later; otherwise the current interval is finished and a new one starts. Meeting rooms splits into two genuinely different questions: "can one person attend every meeting" just needs any single overlap to say no, but "what's the minimum number of rooms" needs to know how many meetings are active at the same time — which is where the sweep line technique earns its keep. Splitting every interval into a +1 event at its start and a -1 event at its end, sorting all of those events together by time, and sweeping through with a running counter turns "how many overlap at once" into a single linear pass — the counter's highest value during that sweep is both the answer to "maximum simultaneous overlap" and "minimum rooms needed."

Interval scheduling — picking the largest possible set of non-overlapping intervals — is a related but separate question, already covered from the greedy angle on the Greedy Algorithms page (sort by end time, always take the earliest-ending interval that doesn't conflict). This page's own contribution is the sweep line: the technique for counting overlaps over time, not just picking a non-overlapping set.

One genuine edge case worth knowing: when a start event and an end event land on the exact same time value, whether you process the end first or the start first can change the answer — it depends on whether the problem counts a meeting ending at 2:00 and another starting at 2:00 as overlapping. There's no universal tie-breaking rule; it follows from that specific problem's own definition of "overlapping."

💻 See the code ▾
C# 
intervals.Sort((a, b) => a.Start.CompareTo(b.Start));   // sort by start, once

var merged = new List<(int Start, int End)> { intervals[0] };
for (int i = 1; i < intervals.Count; i++)
{
    var last = merged[^1];
    if (intervals[i].Start <= last.End)                    // ✅ overlaps — extend
        merged[^1] = (last.Start, Math.Max(last.End, intervals[i].End));
    else
        merged.Add(intervals[i]);                          // ❌ no overlap — new interval
}

Sort once, then one linear pass — extend the current interval, or start a new one.

C# 
var events = new List<(int Time, int Delta)>();
foreach (var m in meetings)
{
    events.Add((m.Start, +1));                        // start → +1
    events.Add((m.End, -1));                          // end → -1
}
events.Sort((a, b) => a.Time.CompareTo(b.Time));       // starts & ends, mixed, by time

int active = 0, peak = 0;
foreach (var e in events)
{
    active += e.Delta;
    peak = Math.Max(peak, active);                     // 🔺 track the peak
}
// peak == minimum meeting rooms needed

The counter's peak value across the whole sweep is the minimum rooms needed.

🌍 Real-world example ▾

Your team's calendar app needs to show "3 meetings are happening right now," or book the fewest possible conference rooms for a packed day's schedule. Both are the same sweep-line problem: convert every meeting into a start/end event, sort the events by time, sweep through once, and the running counter's peak value is the answer — no meeting ever needs to be compared directly against every other meeting.
