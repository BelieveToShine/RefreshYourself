/user/:id — same route, same component, different data

"How do dynamic route segments work?"

Why it matters ▾
🔑 Dynamic segments
❗ ProblemWriting a separate route and component for every single user/product/order id would mean hand-writing thousands of near-identical routes — completely unworkable.
✅ SolutionA dynamic segment like :id in /user/:id matches any value in that position and hands it to the component as a param, so one route and one component serve every id.
Recall:id = a placeholder the router fills in and passes to the component.
🔥 Easy interview recall

:id = "a wildcard slot the router captures into route.params."

Think: /user/:id matches /user/42 → params.id === '42'.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The component does not automatically remount when only the param changes on the same route. Navigating from /user/1 to /user/2 reuses the existing component instance for efficiency — a plain mounted/onMounted hook won't re-run, so you need a watcher on route.params to react to the change.

🔄 Likely Follow-up

"How would you force a remount on param change instead?" Bind a :key to the route param on <router-view> (or the component) — changing the key tells Vue it's a different instance, forcing a fresh mount.

🎯 Say this in the interview — the exact lines to land

"A route like /user/:id captures whatever's in that segment as a param. The component reads it with useRoute().params.id — but because the SAME route matches both /user/1 and /user/2, Vue Router reuses the component instance instead of remounting it, so I need a watcher on the param to react to the change."

  • :id in the path → captured into route.params, read with useRoute().
  • Same route, different param → component instance is reused, not remounted.
  • Need to react to the param itself → watch(() => route.params.id, …).
  • Need a guaranteed fresh instance → :key="route.params.id" on the view.
📖 Explanation ▾

A dynamic segment is any path piece written with a leading colon, like :id in /user/:id. The router treats it as a wildcard for that position — whatever string shows up there in the real URL gets captured, not just matched.

Inside the component, useRoute() (Composition API) or this.$route (Options API) gives you a reactive route object, and route.params.id holds the captured value as a string — even if it looks like a number, it always arrives as text.

Vue Router's efficiency optimization — reusing the component instance across a same-route param change — is exactly why a watch on the param is the standard fix: the component is still "the user page," it just needs telling that the id underneath it moved.

💻 See the code ▾
Vue 
// router/index.js
{ path: '/user/:id', component: UserPage }

// UserPage.vue — <script setup>
import { useRoute } from 'vue-router'
const route = useRoute()
console.log(route.params.id)   // ✅ '42' when URL is /user/42

The param always arrives as a string, even for a numeric-looking id.

Vue 
import { watch } from 'vue'

watch(() => route.params.id, (newId) => {
  fetchUser(newId)            // ✅ re-fetch, instance reused
})

Without this watcher, navigating /user/1 → /user/2 would show stale data.

🧭 Use Cases — recognize these when they happen to you ▾
1 A product detail page shared across every product id

Thousands of products, one route and one ProductPage component. The id in the URL is the only thing that changes — everything else about the page's shape stays the same.

RememberMany items, same layout → one dynamic route, not one per item.
2 Clicking "next product" shows the OLD product's data for a moment

No watcher on route.params.id means onMounted's one-time fetch never re-runs — the reused component keeps showing whatever it fetched the first time it mounted.

RememberStale data on param change → missing watch(() => route.params…).
🌍 Real-world example ▾

A blog with one route, /post/:slug, serving every article. One PostPage component fetches whichever post matches the current slug — adding a new article never needs a new route or a new component, only a new row in the database.
