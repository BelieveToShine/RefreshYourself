Properties vs. Fields — a gate in front of your data

"What's the difference between a property and a field, and why not just make fields public?"

Why it matters ▾
🚪 Property
❗ ProblemA public field lets any code store any value — a negative age, a null name — and once other code depends on it directly, you can't add a check or change how it is stored without risking those callers.
✅ SolutionA property looks like a field to the caller but runs get/set code, so you can validate, compute, or restrict access, and change the storage later.
RecallProperty = get/set methods that guard a private field.
🔥 Easy interview recall

Field → the data itself

Property → the door to the data

Think: Field is the room. Property is the door with a lock.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An auto-property is not just a public field with extra typing. { get; set; } compiles to accessor methods over a hidden backing field, so you can add logic later without changing how callers write it.

🔄 Likely Follow-up

"What do private set and init do?" private set lets only the class itself change the value; init allows setting it only while the object is being created — see init / required.

🎯 Say this in the interview — the exact lines to land

"A field is raw storage; a property is a pair of accessor methods, usually over a private backing field. I keep fields private and expose properties, so I can validate, make a setter private or init-only, and change how the data is stored later without changing the callers' code."

  • A property is get/set methods written with field-like syntax — usually over a private backing field.
  • It can validate on set or compute on get; a public field can do neither.
  • { get; set; } is an auto-property — the compiler writes the hidden backing field for you.
  • Each accessor can have its own access (private set) or be init-only.
  • Interfaces can declare properties but not fields, and frameworks like data binding and serializers typically work with properties.
📖 Explanation ▾

A field is a variable stored inside an object. A property looks the same to the caller (p.Age), but it is really two small methods, get and set, usually wrapping a private field.

Public fields work at first, but every caller then touches the raw data. You can't reject a bad value, and if you later want to compute the value or store it differently, switching a field to a property can break code that was already compiled against it.

Writing { get; set; } gives you the property now and a hidden field behind it; you only add a body when you need logic. This is encapsulation in practice — see Encapsulation vs. Abstraction and Access Modifiers, and for "set once, then read-only" see init / required and immutable objects.

💻 See the code ▾
C# 
public class Person
{
    private int _age;                 // the field: private data

    public int Age                    // the property: the gate
    {
        get => _age;
        set
        {
            if (value < 0) throw new ArgumentOutOfRangeException(nameof(value));
            _age = value;
        }
    }

    public string Name { get; init; } = "";   // auto-property, set only at creation
}

The setter can say no — a public field never could.

C# 
var p = new Person { Name = "Ada" };
p.Age = 30;    // runs the set accessor
p.Age = -1;    // throws ArgumentOutOfRangeException

Callers write the same p.Age = ... they would for a field.

🌍 Real-world example ▾

A bank account. Balance has a public getter but a private setter, so everyone can read it and only Deposit and Withdraw can change it.
