generateStaticParams() — pre-rendering a dynamic route at build time

"How do you statically generate a dynamic route like [slug] at build time?"

Why it matters ▾
🏗️ generateStaticParams()
❗ ProblemA dynamic route like /blog/[slug] looks like it must be rendered per-request — there's no fixed list of URLs the way a static page has, so it seems to need a live render every time.
✅ SolutiongenerateStaticParams() returns the actual list of param values (every blog post's slug) up front, so Next.js can pre-render a separate static HTML file for each one at build time — same speed as a fully static page.
RecallgenerateStaticParams = the list of param values to pre-build, one file per value.
🔥 Easy interview recall

generateStaticParams() = "here's every slug value — build one page per value, up front."

Think: return 3 slugs → get 3 pre-built HTML files, same speed as fully static.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Forgetting generateStaticParams() doesn't make the route error — it makes it dynamic. Without it, Next.js has no list of params to pre-render, so a route you intended to be static silently falls back to rendering on every request instead.

🔄 Likely Follow-up

"What happens to a param value NOT returned by generateStaticParams()?" By default it's rendered on demand at request time and then cached — unless dynamicParams is explicitly set to false, in which case an unlisted param 404s instead.

🎯 Say this in the interview — the exact lines to land

"generateStaticParams() returns the list of param values to pre-render for a dynamic route at build time — Next.js generates a separate static HTML file for each one, so the dynamic-looking route performs exactly like a static page."

  • Returns an array of param objects → one file built per value.
  • Missing it → no build-time list, route renders per-request instead.
  • Unlisted param → rendered on demand and cached, unless dynamicParams: false 404s it.
📖 Explanation ▾

A dynamic segment like app/blog/[slug]/page.js doesn't have a fixed set of URLs on its own — slug could be anything. generateStaticParams() is how you tell Next.js the actual, concrete list of values that segment should take: it returns an array of objects (e.g. [{ slug: 'post-1' }, { slug: 'post-2' }]), and Next.js pre-renders one static HTML file per entry at build time.

The result reads as a dynamic route but behaves like a static one — every value returned by generateStaticParams() gets the exact same build-once, serve-many performance profile as a page with no dynamic segments at all.

What happens to a slug that wasn't in that list is a separate, configurable decision. By default (dynamicParams: true), Next.js renders it on the fly the first time it's requested and caches the result afterward. Setting dynamicParams = false changes that to a hard 404 for anything not explicitly listed.

💻 See the code ▾
Next.js 
// app/blog/[slug]/page.js
export async function generateStaticParams() {
  const posts = await getAllPostSlugs();   // e.g. ['post-1','post-2','post-3']
  return posts.map(slug => ({ slug }));   // ✅ one static file per slug
}

export default async function BlogPost({ params }) {
  const post = await getPost(params.slug);
  return <article>{post.title}</article>;
}

Every returned { slug } becomes its own pre-built HTML file.

🧭 Use Cases — recognize these when they happen to you ▾
1 A blog or docs site with a known, finite set of pages

Every post slug is known ahead of time from the CMS or file system — returning the full list from generateStaticParams() pre-builds every post page, so visitors never wait on a render.

RememberFinite, known set → return the whole list, pre-build everything.
2 Thousands of product pages — too many to all pre-build

Returning only the most-visited product slugs keeps build time short — anything not in that list still works, rendered the first time it's visited and cached from then on (since dynamicParams defaults to true).

RememberToo many to pre-build → return the important subset, let the rest render on demand.
3 You forgot generateStaticParams() on a route meant to be static

No error is thrown — the route just quietly falls back to rendering on-demand for every request, which can go unnoticed until someone checks build output or server load and wonders why this "static" page isn't actually pre-built.

RememberNo generateStaticParams() → no error, just no pre-rendering.
🌍 Real-world example ▾

A documentation site with a few hundred pages, each at /docs/[slug]. generateStaticParams() returns every doc's slug once at build time, so the entire site ships as pre-rendered static HTML — fast for every visitor, with no live render cost per request despite the dynamic-looking route.
