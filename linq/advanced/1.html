Func<T> vs. Expression<Func<T>> — compiled code, or data describing code?

"Both Func<T,bool> and Expression<Func<T,bool>> can represent x => x.Age > 30 — what's the real difference?"

Why it matters ▾
🧩 Func<T>
❗ ProblemYou need to run a predicate as code, right now, against data already sitting in memory — nothing else is ever going to read or rewrite that logic first.
✅ SolutionFunc<T,bool> compiles to a regular delegate — an in-memory pointer to already-generated IL — so calling it just runs the code immediately, with no way for anything else to inspect its structure first.
RecallFunc<T> = compiled code, already runnable.
🌳 Expression<Func<T>>
❗ ProblemA provider like EF Core needs to turn x => x.Age > 30 into something else entirely — a SQL WHERE clause — before anything runs, but a compiled delegate is a black box it can't look inside.
✅ SolutionExpression<Func<T,bool>> compiles the same lambda into a data structure instead — a tree the provider can walk, read, and rewrite into SQL (or anything else) before ever executing it as C#.
RecallExpression<Func<T>> = data describing the code, not the code itself.
🔥 Easy interview recall

Func<T> → compiled, callable right now

Expression<Func<T>> → data tree, inspected first

Think: Func<T> runs. Expression<Func<T>> describes what to run.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An Expression<Func<T>> isn't directly callable. It has no Invoke — you can only run it as code after calling .Compile(), which turns the tree back into a delegate at a real runtime cost.

🔄 Likely Follow-up

"So can I just call .Compile() on every Expression<Func<T>> and get a working Func<T> back?" Yes, technically — but doing that against an IQueryable means you've opted out of translation entirely: the compiled delegate can only run in-memory, so nothing in it reaches the database as SQL anymore.

🎯 Say this in the interview — the exact lines to land

"Func<T,bool> is already-compiled, callable code — calling it just runs the lambda. Expression<Func<T,bool>> is a data structure describing that same lambda's logic, which a provider like EF Core walks and translates into something else, like SQL, instead of ever running it as C#."

  • Func<T> → compiled delegate, runs now.
  • Expression<Func<T>> → expression tree, inspected and translated first.
  • IQueryable<T>'s operators take Expression<Func<T>> → so a provider can see the logic before anything runs.
  • .Compile() → turns a tree back into a delegate, but only for in-memory use.
  • Same lambda syntax → the compiler picks which one to build from the target type it's assigned to.
📖 Explanation ▾

The compiler decides which of these it builds based on the target type, not the lambda's own syntax. Assign x => x.Age > 30 to a Func<Person,bool> and the compiler emits ordinary IL for a delegate — exactly like compiling any other method body. Assign the identical lambda to an Expression<Func<Person,bool>> and the compiler instead emits code that builds an object graph — a tree of BinaryExpression, MemberExpression, and similar nodes describing "compare this property with this constant," rather than compiling the comparison itself.

This is the actual mechanism behind IQueryable<T>. Its standard query operators (Where, Select, OrderBy...) are defined to accept Expression<Func<T,...>> parameters specifically — IEnumerable<T>'s versions of the same-named methods take plain Func<T,...> instead. That signature difference is what forces the compiler to hand a provider like EF Core a tree it can read, rather than a delegate it can't look inside.

.Compile() exists to cross back over: it walks the tree and emits a real delegate at runtime, which does real work and isn't free. Calling it on a tree that was about to be translated to SQL throws away that translation path entirely — everything after it just runs as LINQ-to-Objects, in memory.

💻 See the code ▾
C# 
Func<Person, bool> predicate = p => p.Age > 30;
bool isAdult = predicate(person);   // ✅ runs immediately — real compiled code

A Func<T> is just a method reference — calling it runs it.

C# 
Expression<Func<Person, bool>> predicateExpr = p => p.Age > 30;
// predicateExpr(person);     ❌ won't compile — it's data, not a callable method
var compiled = predicateExpr.Compile();   // turns the tree back into a delegate
bool isAdult = compiled(person);           // ✅ now callable — but only in memory

The tree itself can't be invoked — only a delegate produced by .Compile() can.

C# 
// IEnumerable<T>'s Where — takes a Func, runs it directly
public static IEnumerable<T> Where<T>(this IEnumerable<T> src, Func<T, bool> predicate);

// IQueryable<T>'s Where — takes an Expression, hands it to the provider
public static IQueryable<T> Where<T>(this IQueryable<T> src, Expression<Func<T, bool>> predicate);

Same method name, different parameter type — that signature difference is the mechanism.

🧭 Use Cases — recognize these when they happen to you ▾
1 Writing a reusable filter for an in-memory List<T>

Nothing is ever going to read or rewrite this lambda, so a plain Func<T,bool> is exactly right — it compiles once and is called directly, every time.

RememberIn-memory, never inspected → Func<T> is the right tool.
2 Writing a filter for a DbSet<T> that must become SQL

EF Core must be able to see the logic's structure before it runs anything — which is exactly why IQueryable<T>'s Where demands an Expression<Func<T,bool>>, not a Func.

RememberNeeds translation → must stay an Expression, not a Func.
3 Calling .Compile() on a query you meant to run on the database

Calling .Compile() turns the tree into a delegate that can only run against data already in memory — any part of the query that was still meant to reach the database loses its path there the moment this happens.

Remember.Compile() too early → opts out of SQL translation entirely.
🌍 Real-world example ▾

Think of Func<T> as a sealed envelope you can only open by running it — you hand it an input and get an output, with no way to see what's inside first. Expression<Func<T>> is the same instructions written on a piece of paper instead — someone else (the provider) can read those instructions, cross things out, and rewrite them into a completely different language before anyone actually follows them.
