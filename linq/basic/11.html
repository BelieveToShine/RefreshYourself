ToList vs. ToArray vs. ToDictionary — same immediate execution, not the same safety

"All three force immediate execution — what's the actual difference between them, and when does ToDictionary throw at materialization time that the other two don't?"

Why it matters ▾
📋 ToList
❗ ProblemA deferred query isn't something you can Add to or Remove from — you need a real, editable collection to keep working with after the query runs.
✅ SolutionToList() runs the query right now and copies the results into a resizable List<T> you can freely edit afterward.
RecallToList = immediate run into a resizable list.
📦 ToArray
❗ ProblemSome APIs expect a plain T[], and you already know the item count is fixed once the query finishes — a resizable list is more than you need.
✅ SolutionToArray() runs the query right now and copies the results into a fixed-size, compact T[].
RecallToArray = immediate run into a fixed-size array.
🗄️ ToDictionary
❗ ProblemScanning a list every time you need one item by its key is slow — you want direct, O(1)-style lookup instead.
✅ SolutionToDictionary(keySelector) runs the query right now and builds a Dictionary<TKey,TValue> — but it demands every key be unique, and throws immediately if two elements produce the same one.
RecallToDictionary = immediate run into a keyed lookup — unique keys only.
🔥 Easy interview recall

ToList() → List<T>, resizable

ToArray() → T[], fixed-size

ToDictionary() → Dictionary<K,V>, keyed

Think: ToList/ToArray never care whether the data is unique. ToDictionary does — a duplicate key crashes it the instant the query runs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ToDictionary fails the same way ToList or ToArray would. It doesn't — ToDictionary throws ArgumentException the instant it finds a duplicate key, a failure mode the other two can never hit because neither one cares about uniqueness at all.

🔄 Likely Follow-up

"What if two elements genuinely need to share that key?" Then ToDictionary is the wrong tool entirely — reach for ToLookup instead, which is built from the start for a many-values-per-key relationship and never throws on a repeated key.

🎯 Say this in the interview — the exact lines to land

"All three force immediate execution, but into different shapes — ToList gives a resizable List<T>, ToArray gives a fixed-size T[], and ToDictionary gives a keyed lookup that throws ArgumentException right away if the key selector produces a duplicate."

  • ToList → use when you'll keep editing the results afterward.
  • ToArray → use for a fixed-size result, or when an API specifically expects T[].
  • ToDictionary → only safe when the key is genuinely unique per element — otherwise it crashes on materialization, not later.
📖 Explanation ▾

All three methods share one job: they stop the query from being a lazy, re-runnable plan and force it to run right now, copying every result into a real in-memory collection. Where they differ is only the shape of that collection — and, for ToDictionary, a correctness requirement the other two never carry.

ToList and ToArray never look at the values themselves to decide whether materialization can succeed — every element just gets copied in, one after another, position by position. ToDictionary is different: it has to run the key selector on every element and check the result is unique along the way, because a dictionary simply can't have two entries with the same key. The moment it finds a second element producing a key it's already seen, it throws — during the ToDictionary() call itself, not on some later lookup.

💻 See the code ▾
C# 
List<string> names = people.Select(p => p.Name).ToList();
names.Add("Extra Person");   // ✅ works — List<T> is resizable

ToList hands you something you can keep editing after the query runs.

C# 
int[] ids = people.Select(p => p.Id).ToArray();
// ids.Length is fixed the instant this line finishes

ToArray gives a fixed-size array — no Add/Remove afterward.

C# 
Dictionary<string, Person> byEmail =
    people.ToDictionary(p => p.Email);
// ❌ throws ArgumentException the moment two people share an email

The crash happens right here, on this line — not later, when someone reads byEmail.

🧭 Use Cases — recognize these when they happen to you ▾
1 You'll keep adding or removing items after the query runs

Building up a results list that a user will keep filtering, sorting, or editing in memory afterward? ToList() is the right shape — a plain List<T> you can mutate freely once it's built. This is the #1 scenario you'll actually run into.

RememberNeed to keep editing it → ToList.
2 You're handing the result to an API that expects T[]

Some method signatures are written to take T[] specifically, and you already know the count won't change once the query is done. ToArray() gives exactly that shape, with no resizing overhead you don't need.

RememberFixed-size result, API wants T[] → ToArray.
3 Your key selector isn't actually unique across the sequence

Keying by something that genuinely repeats — two employees in the same department, two orders for the same customer — crashes ToDictionary the instant it hits the second one. There's no silent "last one wins" fallback; reach for ToLookup or GroupBy instead when the key can repeat.

RememberKey can repeat → ToDictionary is the wrong tool entirely.
🌍 Real-world example ▾

Think of a filing cabinet drawer labelled by name. ToList is a shopping list you can keep adding items to after you leave the store. ToArray is a sealed, pre-counted box sized for exactly the shelf it's going on. ToDictionary is that labelled drawer — but the cabinet refuses the second file the instant two files try to use the same label.
