Envelope encryption — the data key locks the data, KMS locks the data key

"How does envelope encryption work, and how do KMS key policies differ from IAM policies?"

Why it matters ▾
✉️ Envelope encryption
❗ ProblemSending a big file to KMS to be encrypted is slow, and KMS can only encrypt small payloads directly (a few KB — check current docs).
✅ SolutionEncrypt the data locally with a data key, then ask KMS to encrypt just that small key. Store the locked key right beside the data.
RecallData key locks the data. KMS key locks the data key.
📜 Key policy vs. IAM
❗ ProblemMost AWS resources are controlled by IAM alone — a KMS key is not. An IAM Allow can still be refused because the key itself has not agreed.
✅ SolutionEvery KMS key has a key policy (a resource policy on the key). IAM policies only count if the key policy lets them — usually through one default statement that trusts the account.
RecallKey policy is the main gate; IAM works only if the key policy allows it.
🔑 AWS-managed vs. customer-managed
❗ ProblemThe default keys just work, but you can't change their policy, share them with another account or switch them off.
✅ SolutionA customer-managed key gives you the key policy, optional rotation, and the ability to disable it. An AWS-managed key is the zero-effort default.
RecallNeed control or cross-account? Customer-managed.
🔥 Easy interview recall

Envelope → data key locks data, KMS key locks the data key

Key policy → the key's own rulebook — required

IAM policy → only works if the key policy allows it

Rotation → same key ID, old material kept — nothing re-encrypted

Think: Two locks, nested: a small data key locks your data, and KMS locks that small key. Throw away the plaintext key and the data is safe to store.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"If my IAM policy says Allow on the key, I can use it." Not necessarily — a KMS key also needs its key policy to allow it (directly, or through the default statement that trusts the account's IAM). Across accounts, the key policy and the other account's IAM must both allow it.

🔄 Likely Follow-up

"What happens to old data when a key rotates?" Nothing is re-encrypted. Rotation adds new key material under the same key ID and keeps the old, so existing ciphertext still decrypts and new data uses the new material.

🎯 Say this in the interview — the exact lines to land

"Envelope encryption means a data key encrypts the data, and a KMS key encrypts the data key — so big data never goes to KMS, and I store the encrypted data key beside the data. For access, the key policy is the main gate; IAM policies only work if the key policy allows them."

  • Data key → encrypts the data locally; keep only the encrypted copy.
  • KMS key → encrypts the data key and never leaves KMS.
  • Key policy → the main gate — IAM counts only if the key policy allows it.
  • Customer-managed → you control the policy, rotation and disabling; AWS-managed is the hands-off default.
  • Rotation → same key ID, old material kept — nothing is re-encrypted.
  • Grant → temporary, programmatic permission on a key — AWS services use these for you.
📖 Explanation ▾

Envelope encryption is two keys, nested. Your app asks KMS for a data key; KMS returns it twice — once as plaintext, once encrypted under a KMS key. The app encrypts the data locally with the plaintext key, throws that key away, and stores the encrypted copy beside the data. To read it back, the app sends the encrypted key to KMS, gets the plaintext key back, and decrypts locally. The KMS key never leaves KMS, and big data never travels to it. S3's SSE-KMS uses this pattern for you.

A key policy is a resource policy attached to the KMS key itself, and every key has one. An IAM policy is attached to an identity. For most services either one can grant access; for KMS, the key policy has the final say — IAM policies work only when the key policy allows it. The default key policy does this with one statement that trusts the account's root, which hands control to IAM. A grant is a lighter tool: a temporary, programmatic permission on a key, which AWS services use on your behalf.

AWS-managed keys are created for you by services; you can't edit their policy or disable them. Customer-managed keys cost extra but you control the policy, can disable them, and can turn on automatic rotation — a new key version under the same key ID, with older versions kept so old data still decrypts. Check current docs for rotation periods and pricing.

💻 See the code ▾
CLI 
aws kms generate-data-key \
  --key-id alias/my-app-key \
  --key-spec AES_256

Returns two things: a plaintext data key (use it to encrypt locally, then discard it) and a CiphertextBlob — the same key, encrypted by KMS — which you store next to the data.

JSON 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnableIAMPolicies",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": "kms:*",
      "Resource": "*"
    }
  ]
}

The default key-policy statement (account ID is an example). It is what lets IAM policies in that account control the key — remove it and IAM alone can no longer grant access.

🌍 Real-world example ▾

An app backs up a large file: it asks KMS for a data key, encrypts the file locally, and uploads it with the encrypted data key beside it. To restore, it sends that key to KMS, gets the plaintext key back, and decrypts — the file itself never went to KMS.
