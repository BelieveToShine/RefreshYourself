A slow ASP.NET Core app — where do you actually start?

"What performance improvements would you make to a slow ASP.NET Core application?"

Why it matters ▾
💾 Caching
❗ ProblemA request that re-fetches data nobody changed since the last call still pays the same database or network round trip every single time, even though the answer was already known.
✅ SolutionIMemoryCache caches it per instance, a distributed cache like Redis keeps every instance seeing the same value once there's more than one, and response/output caching middleware can cache a whole safe-to-cache HTTP response.
RecallThe fastest request is the one that never reaches your code.
⏳ Async I/O
❗ ProblemCalling .Result or .Wait() on an async call blocks the calling thread until it finishes — a thread-pool thread sits idle instead of serving another request.
✅ SolutionAwait I/O-bound work (database, network calls) all the way up the call stack so the thread is freed while the wait happens — that's what lets a small thread pool serve many concurrent requests.
RecallBlock a thread → one less thread free for every other request.
🔌 Connection Reuse
❗ ProblemA new HttpClient() created per outgoing call can exhaust available sockets under load instead of reusing them.
✅ SolutionIHttpClientFactory manages pooled, reused HttpClient instances for outgoing HTTP calls — database connections are already pooled under the hood by ADO.NET/EF Core, so you don't manage that by hand.
RecallDon't new HttpClient() per call — let the factory reuse connections.
📦 Reduce Allocations
❗ ProblemA hot path that allocates a new object on every call puts constant pressure on the garbage collector, which steals CPU time away from actual request work.
✅ SolutionSpan<T>/Memory<T> work with a slice of existing memory without copying it, and ArrayPool<T> reuses buffers instead of allocating a new array every time.
RecallFewer allocations on a hot path → less GC pressure → smoother latency.
🗜️ Response Compression
❗ ProblemA large JSON or text response sent uncompressed spends more time travelling over the network than it needs to, especially on a slower connection.
✅ Solutiongzip/brotli compression middleware trades a little CPU for a smaller payload — most worth it for larger JSON/text responses, not content that's already compressed, like images.
RecallCompress text responses; skip what's already compressed.
🗄️ Database Access Patterns
❗ ProblemFetching a list, then looping over it to fetch each row's related data separately, turns one logical request into dozens or hundreds of round trips to the database.
✅ SolutionEager-load the related data up front with a single query instead of letting the loop issue its own query per item — this is one of the biggest real-world performance wins in a typical app.
RecallOne well-written query beats N+1 round trips, every time.
🔥 Easy interview recall

💾 Caching → skip the work entirely

⏳ Async I/O → never block the thread pool

🔌 Connections → reuse, don't re-create

📦 Allocations → fewer objects, less GC

Think: profile first — whichever lever is actually causing the slowdown is the one worth fixing; compression, N+1 queries, and GC/AOT settings round out the list below.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Scaling out before checking for a blocking call. Adding more server instances without first checking for code blocking the thread pool (.Result, .Wait()) just multiplies the same mistake across more machines — it doesn't fix it.

🔄 Likely Follow-up

"Where do you even start if you don't know what's actually slow?" Profile it — dotnet-trace, dotnet-counters, or a BenchmarkDotNet micro-benchmark on a specific suspect method — so the fix targets whatever the measurement actually shows, not a guess.

🎯 Say this in the interview — the exact lines to land

"I'd start by profiling it — dotnet-trace or dotnet-counters — then work through caching, making sure I/O is actually async all the way down, reusing connections with IHttpClientFactory and connection pooling, cutting allocations on hot paths, and checking for N+1 database queries."

  • Caching → IMemoryCache per instance, Redis once there's more than one, or response caching for whole responses.
  • Async I/O → blocking with .Result/.Wait() starves the thread pool; await all the way up the call stack instead.
  • Connections → IHttpClientFactory reuses HttpClient instances; DB connections are already pooled.
  • Allocations → Span<T>/Memory<T>/ArrayPool<T> cut GC pressure on a hot path.
  • Database access → avoid N+1 queries — eager-load instead, one of the biggest real-world wins.
  • Profile first → dotnet-trace, dotnet-counters, BenchmarkDotNet before you guess.
📖 Explanation ▾

There's no single fix for "the app is slow" — the honest first move is to profile it (dotnet-trace, dotnet-counters, or a BenchmarkDotNet micro-benchmark on one suspect method) so the rest of this list targets whatever the measurement actually shows, not a guess.

Caching and async I/O are the two levers worth checking first in practice. A cache (IMemoryCache per instance, Redis once there's more than one instance, or response caching for a whole safe-to-cache response) removes work entirely instead of making it faster. Blocking a thread with .Result or .Wait() on an async call ties up a thread-pool thread that could otherwise be serving another request — await the call instead, all the way up the call stack, so the thread is free while the I/O happens.

Reusing connections (IHttpClientFactory for outgoing HTTP calls, pooled database connections under the hood) avoids exhausting sockets under load, and cutting allocations on a hot path (Span<T>/Memory<T>, ArrayPool<T>) reduces how often the garbage collector has to run — see C#'s own Performance Checklist for the GC-pressure angle specifically. Response compression trades a little CPU for less time on the wire, and avoiding N+1 database queries — eager-loading related data instead of fetching it one row at a time inside a loop — is one of the most common real wins in a typical app; see EF Core's Beyond N+1 page for exactly how that happens and how to fix it. Server GC is usually the right default for a high-throughput service, and AOT/trimming mainly help startup time rather than steady-state throughput, so they're worth knowing about without needing to be the first thing you reach for.

💻 See the code ▾
C# 
// ❌ blocks a thread-pool thread until the call completes
var data = _repository.GetDataAsync().Result;

// ✅ frees the thread while the I/O happens
var data = await _repository.GetDataAsync();

Under load, the blocking version runs out of free thread-pool threads long before the async version does.

C# 
// ❌ a new HttpClient() per call can exhaust sockets under load
var client = new HttpClient();
var response = await client.GetAsync(url);

// ✅ injected, factory-managed — connections are pooled and reused
public class OrdersClient
{
    private readonly HttpClient _client;
    public OrdersClient(HttpClient client) => _client = client;
}
builder.Services.AddHttpClient<OrdersClient>();

IHttpClientFactory handles the pooling so you don't manage HttpClient lifetimes by hand.

C# 
byte[] buffer = ArrayPool<byte>.Shared.Rent(4096);
try
{
    // use buffer here
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);  // ✅ reused, not garbage
}

Renting and returning a buffer avoids a fresh heap allocation every time this runs.

C# 
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;
});
var app = builder.Build();
app.UseResponseCompression();  // ✅ gzip/brotli for eligible responses

Worth it for larger JSON/text responses — skip it for content that's already compressed, like images.

🧭 Use Cases — recognize these when they happen to you ▾
1 An endpoint's p99 latency is fine at low traffic but falls over under load

Check for a blocking call (.Result, .Wait()) starving the thread pool before reaching for "add more servers" — scaling out just multiplies a blocking call across more machines, it doesn't remove it.

Rememberp99 collapsing under load → check for blocking calls before scaling out.
2 The same data is fetched from the database on almost every request

Data that's read far more often than it changes is exactly what a cache is for — IMemoryCache for one instance, Redis once there's more than one, so the database stops seeing a request it's already answered.

RememberSame data, every request → that's what caching is for.
3 A list page got much slower right after it started showing a related field

A loop that fetches each row's related data with its own query turns one page load into one-plus-N round trips. Eager-load the related data in the original query instead of fetching it one row at a time.

RememberA loop issuing its own query per item is N+1 — eager-load instead.
🌍 Real-world example ▾

A checkout API's p99 latency is fine in staging but spikes badly once real traffic hits it. A dotnet-trace capture shows most requests spending their time waiting on thread-pool availability, not on the database or network itself — dotnet-counters confirms the thread pool is growing slowly under the burst because a payment-provider call further down the stack is calling .Result on an async method. Switching that one call to await removes the block; adding a short-lived cache in front of the catalog lookup that every checkout request also makes removes a second, unrelated source of load on the same endpoint.
