Cookie or Bearer token — who's actually carrying your login?

What's the difference between cookie-based and token-based (JWT) authentication, and what does [Authorize] actually check?

Why it matters ▾
  • Every ASP.NET Core app has to pick — or combine — an authentication scheme; this is the layer underneath every [Authorize] check that actually knows who's calling.
  • Comes up the moment you're wiring a browser-rendered app next to a public API, or debugging why a mobile client can't "stay logged in" the way a browser session does.
  • A very common interview opener right before the interviewer drills into policies and claims.
🔥 Easy interview recall

Cookie → server remembers you

JWT → you carry the proof

Think: Cookie is stateful — the browser resends it for you. JWT is stateless — the client has to attach it itself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An app doesn't have to pick exactly one scheme. ASP.NET Core can register cookies and JWT bearer at the same time — cookies for a browser-rendered admin UI, bearer tokens for the public API — with [Authorize(AuthenticationSchemes = "Bearer")] picking which one each endpoint trusts.

🔄 Likely Follow-up

"If a JWT is stolen, what can you actually do about it before it expires?" Short expiry plus a refresh-token rotation pattern is the standard mitigation — a stolen short-lived token limits the exposure window; true instant revocation typically needs a server-side denylist, which reintroduces some of the statefulness JWT was meant to avoid.

🎯 Say this in the interview — the exact lines to land

"Cookie auth has the server create an encrypted cookie holding the user's identity on login, and the browser resends it automatically on every request. Token-based (JWT) auth has the server issue a signed token that the client stores and attaches itself as a Bearer header, with no server-side session lookup. [Authorize] just checks whether HttpContext.User — populated by the authentication middleware — is an authenticated identity, and that check happens in the authorization stage, right after authentication already ran."

  • Cookie → server-managed session, the browser resends it for you.
  • JWT → client-managed, self-contained, no server lookup needed.
  • Multiple schemes can run together → cookies + bearer, side by side, chosen per endpoint.
  • [Authorize] checks HttpContext.User, after authentication middleware already ran.
  • Revocation → a JWT is hard to kill early; short expiry plus refresh rotation is the standard fix.
📖 Explanation ▾

Cookie-based auth has the server create an encrypted authentication cookie containing the user's claims on a successful login, and send it to the browser. The browser automatically re-sends that cookie on every later request, and the server decrypts it each time to know who's calling — a server-managed session. That's an easy fit for a traditional browser-rendered app, but cookies don't travel naturally to non-browser clients — a mobile app, or a SPA calling an API on a different origin — without extra work.

Token-based (JWT) auth has the server issue a signed JSON Web Token containing claims on login, but the client is responsible for storing it and attaching it (Authorization: Bearer <token>) to every later request. The server only verifies the signature — no server-side session lookup is needed, because the token is self-contained. That statelessness is exactly why JWT fits APIs, mobile apps, SPAs, and service-to-service calls so well, at the cost of harder revocation: a JWT stays valid until it expires, with no simple "log this session out right now" the way killing a server-side cookie session provides, unless extra infrastructure is built for it.

[Authorize] checks whether HttpContext.User — populated by whichever authentication middleware actually ran, cookie or JWT bearer or both — represents an authenticated identity meeting the attribute's requirements: a bare [Authorize] just requires "any authenticated user," while [Authorize(Roles = "Admin")] or a named policy narrows further. This page is about what that check inspects and the two mechanisms behind it; exactly where in the pipeline that check runs relative to authentication is covered on Authentication vs. Authorization — short version, authorization always runs after authentication has already populated User.

💻 See the code ▾
C# 
builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.LoginPath = "/Account/Login";   // where an unauthenticated user gets sent
    });

The cookie scheme's name becomes the default — what [Authorize] checks against unless told otherwise.

C# 
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new()
        {
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = signingKey,
            ValidateLifetime = true   // rejects an expired token
        };
    });

No session store here — checking the signature is enough to prove the token wasn't tampered with.

C# 
builder.Services.AddAuthentication()
    .AddCookie("Cookies")
    .AddJwtBearer("Bearer");   // ✅ both schemes registered on the same app

[Authorize(AuthenticationSchemes = "Bearer")]
[HttpGet("api/orders")]
public IActionResult GetOrders() { ... }

Same app, two schemes — the attribute is what tells this one endpoint which one to trust.

🌍 Real-world example ▾

A cookie is a coat-check ticket; a JWT is a stamped wristband. Hand the coat-check ticket back and the venue (the server) looks up what's yours — it's the one keeping the record. A stamped wristband you carry yourself — anyone can check the stamp is genuine without ever calling the venue.

Scenario: your team ships a browser-rendered admin dashboard and a public mobile app against the same ASP.NET Core backend. The dashboard uses the cookie scheme because the browser handles it automatically; the mobile app has no cookie jar, so it authenticates against the JWT bearer scheme instead and attaches the token itself. Both schemes are registered on the same AddAuthentication() call, and each controller states which one it trusts.
