Abstract class vs. interface — a shared "is-a" hierarchy, or just a shared capability?

"When would you reach for an abstract class instead of an interface, or vice versa?"

Why it matters ▾
🏛️ Abstract Class
❗ ProblemSeveral related subclasses share real state and behavior (a field, a constructor, a helper method) — repeating that in every subclass duplicates code and risks the copies drifting apart.
✅ SolutionAn abstract class holds that shared state, constructors, and a mix of concrete + abstract methods once, in one place, while still forcing each subclass to supply the parts that genuinely differ.
RecallAbstract class = shared state + behavior, single inheritance only.
📜 Interface
❗ ProblemUnrelated classes with no shared hierarchy at all (a Car and a Duck) can still both need to opt into the same capability, like being Comparable or Flyable.
✅ SolutionAn interface describes a pure contract — method signatures any unrelated class can implement — and modern Java (8+) lets it also carry default/static methods with real bodies, while still allowing a class to implement many interfaces at once.
RecallInterface = a contract, implementable by many unrelated classes.
🔥 Easy interview recall

Abstract class → is-a hierarchy, shared state, one parent

Interface → can-do contract, no shared state, many parents

Think: Abstract class answers "what are you, deep down?" Interface answers "what can you do?"

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"An interface with default methods is now basically an abstract class." It still can't hold instance fields (state) or constructors, and a class can implement unlimited interfaces but extend only one abstract class — the state and single-inheritance limit are what still separate them, not just syntax.

🔄 Likely Follow-up

"Can an abstract class implement an interface too?" Yes — and it doesn't have to provide every method; it can leave some of the interface's methods abstract itself, pushing the obligation down to its own concrete subclasses.

🎯 Say this in the interview — the exact lines to land

"An abstract class can hold state, constructors, and a mix of abstract and concrete methods, but a class can extend only one. An interface is a pure contract — traditionally just method signatures, now also default and static methods with bodies — and a class can implement as many as it needs."

  • Abstract class → use when subclasses share real state in a genuine "is-a" hierarchy.
  • Interface → use for a capability unrelated classes can opt into, no shared state needed.
  • Inheritance limit → one abstract class, but many interfaces at once.
📖 Explanation ▾

An abstract class is still a class — it can declare instance fields, give them a constructor to initialize, and mix fully-implemented concrete methods alongside abstract methods that force subclasses to fill them in. The trade-off is Java's single-inheritance rule: a class can extend only one (abstract or otherwise) parent.

An interface traditionally held nothing but abstract method signatures (and constants) — a pure "here's what you must be able to do" contract, with zero shared state. Since Java 8, an interface can also provide default methods (a body implementing classes inherit unless they override it) and static helper methods — but it still cannot declare an instance field. A class can implement as many interfaces as it needs.

💻 See the code ▾
Java 
abstract class Vehicle {
    int fuelLevel;             // ✅ real state, shared by every subclass
    Vehicle(int fuel) { fuelLevel = fuel; }  // a real constructor
    abstract void move();      // each subclass must supply this
}
class Car extends Vehicle { ... }   // ❌ can't also extend Bike

Shared state and a constructor live once in Vehicle — but Car only gets one parent.

Java 
interface Flyable { void fly(); }
interface Swimmable { void swim(); }

class Duck implements Flyable, Swimmable {  // ✅ both at once — no state shared between them
    public void fly() { ... }
    public void swim() { ... }
}

Duck opts into two unrelated capabilities — neither interface carries any state.

🧭 Use Cases — recognize these when they happen to you ▾
1 A real family of related types sharing fields and a constructor

Every animal genuinely shares a name, an age, and a constructor that sets them — that's real shared state in a real hierarchy. This is the #1 reason to reach for an abstract class.

RememberReal shared state, real "is-a" → abstract class.
2 Unrelated classes that all need to sort, compare, or be closed

A file and a network socket share no hierarchy and no state at all — but both can promise "I can be closed," which is exactly the kind of cross-cutting contract an interface is built for.

RememberNo shared state, just a shared capability → interface.
3 You try to give an interface an instance field "just this once"

A field declared inside an interface is implicitly public static final — a shared constant, not a per-instance field. Reaching for actual mutable instance state is exactly the signal you need an abstract class instead.

RememberNeed real instance state → interface is the wrong tool.
🌍 Real-world example ▾

An abstract class is a family tree; an interface is a license. Every member of a family genuinely shares blood and a shared history (one family, one tree) — that's the abstract class. A driving license, a passport, a gym membership can all be held by people who share nothing else about them — that's an interface: an unrelated holder opting into one specific capability.
