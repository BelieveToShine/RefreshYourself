Closures — why the inner function still remembers, even after the outer one is gone

"What is a closure, and why does the inner function still have access to the outer function's variables after that outer function has already returned?"

Why it matters ▾
  • Almost every "harder" JS question is secretly a closures question underneath — private state, factory functions, memoization, and the classic loop/setTimeout bug all reduce to this one mechanic.
  • It's the difference between reciting "a closure is a function that remembers its scope" and actually being able to say where that memory lives and why it isn't cleaned up.
  • Forgotten closures are a real, common source of memory leaks in long-running apps — worth knowing that connection exists, even briefly.
🔥 Easy interview recall

Closure = "a function that keeps a live link to the variables from where it was created, even after that place is gone."

Think: counter() returns a tiny function that still has its own private count — nowhere else, just inside that one closure.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A closure is not a copy of the outer variables. It's a live reference to the same variable — if something else in the closure's scope can still change it, the function sees the updated value, not a snapshot taken at creation time.

🔄 Likely Follow-up

"Can closures cause memory leaks?" Yes — a closure keeps everything it captured alive for as long as the closure itself is reachable, so a forgotten callback or timer holding a closure over a large object keeps that object from ever being collected.

🎯 Say this in the interview — the exact lines to land

"A closure is a function bundled with a live reference to the lexical scope it was created in. Because JavaScript scope is lexical — decided by where a function is written, not where it's called — the inner function keeps that reference even after the outer function returns, and the JavaScript engine keeps that scope alive instead of collecting it, for as long as the closure itself is still reachable."

  • Lexical scope — where a function is written decides what it can see, not where it's called from.
  • Not garbage collected — a captured scope survives exactly as long as something still references the closure.
  • counter() factory → each call makes a brand-new, independent closure — never a shared one.
  • Private state, memoization, and callbacks all lean on the same mechanic — a variable no outside code can reach directly.
  • var vs. let in a loop is the same closure rule — one shared binding vs. one fresh binding per iteration.
📖 Explanation ▾

JavaScript scope is lexical — a function's access to variables is fixed by where it's physically written in the code, not by where or when it gets called later. When a function is defined inside another function, it's written inside that outer function's scope, so it keeps a reference to it forever, baked in at creation. That reference is what a closure actually is: the inner function plus the scope it was born into, travelling together as one unit.

Normally, a function's local variables live only for the duration of that call — once it returns, nothing needs that scope anymore, so the engine reclaims the memory. A closure changes that: if the returned inner function is still reachable (assigned to a variable, passed as a callback, stored in an array), it still holds its reference to the outer scope, so that scope can't be reclaimed either. This is also exactly why a closure kept around too long — a forgotten event listener, an old timer — is a common source of memory leaks: the captured variables stay alive for as long as the closure does, whether or not anyone still needs them.

This same mechanic is why a var loop and a let loop behave differently with setTimeout: var is function-scoped, so every callback's closure captures the exact same single variable, which has already finished looping by the time any callback runs. let is block-scoped, so the loop creates a fresh binding each pass, and each callback's closure captures its own separate one. It isn't two unrelated facts about var and let — it's one closures rule producing two different outcomes depending on how many bindings existed to capture.

🧠 Visual Mental Model — the factory example, made concrete
💻 See the code ▾
JavaScript 
function counter() {
    let count = 0;                    // lives inside counter()'s scope
    return () => ++count;             // inner fn closes over count
}

const inc = counter();               // counter() has already returned here
console.log(inc());                 // 1 — count still exists, just for inc
console.log(inc());                 // 2
console.log(inc());                 // 3

const inc2 = counter();              // a brand-new, independent closure
console.log(inc2());                // 1 — not 4, it never saw inc's count

count is never a global variable anywhere — it only exists inside the closure inc holds. inc2 starts back at 1 because it's a completely separate call, with its own count.

JavaScript 
for (var i = 1; i <= 3; i++) {
    setTimeout(() => console.log(i), 100);  // closes over the SAME i
}
// logs: 4, 4, 4 — var is function-scoped, one shared binding

for (let j = 1; j <= 3; j++) {
    setTimeout(() => console.log(j), 100);  // closes over its OWN j
}
// logs: 1, 2, 3 — let is block-scoped, a fresh binding per pass

This is the same setTimeout-in-a-loop example from the var vs. let vs. const page — and it's the exact same closures mechanic explained above, not a separate rule. var gives every callback's closure one shared i to capture; let gives each iteration its own binding, so each callback's closure captures a different one.

JavaScript 
function memoize(fn) {
    const cache = new Map();           // private — only this closure can reach it
    return (arg) => {
        if (cache.has(arg)) return cache.get(arg);  // ✅ cache hit, skip the work
        const result = fn(arg);
        cache.set(arg, result);
        return result;
    };
}

const fastSquare = memoize((n) => { console.log("computing…"); return n * n; });
fastSquare(5);  // logs "computing…", returns 25
fastSquare(5);  // no log — returns the cached 25

cache never leaves memoize() by name — the returned function is the only way to reach it. That's private state through a closure, not a language feature bolted on separately.

🌍 Real-world example ▾

A locker that only one key opens. The variable inside a closure is like cash left in a locker — no one can reach it directly, only through the one function (the "key") that was handed the reference when the locker was set up. Two lockers set up separately, even with identical contents at the start, are still two different lockers.
