AWS Fundamentals — where does AWS's responsibility actually end?

"What is AWS, and what does the shared responsibility model actually split between you and AWS?"

Why it matters ▾
💻 IaaS
❗ ProblemA team needs full control over the OS and runtime — exact versions, custom configuration — but doesn't want to buy or rack physical hardware.
✅ SolutionIaaS (like EC2) rents raw infrastructure and hands the team the guest OS, runtime, app, and data to manage themselves; AWS owns only the hardware, hypervisor, and network underneath.
RecallIaaS = you manage OS + runtime + app + data — AWS manages hardware, hypervisor, network only.
🗄️ PaaS
❗ ProblemPatching and maintaining the guest OS on every instance is repetitive ops work a team may not want to own for a workload like a database.
✅ SolutionPaaS (like RDS or Elastic Beanstalk) takes the OS and runtime patching off the team's plate too, leaving them to manage just the app and data on top of an already-managed platform.
RecallPaaS = AWS also manages OS + runtime patching — you're left with just app + data.
☁️ SaaS
❗ ProblemEven a managed platform still needs someone to deploy, configure, and operate the application itself — some teams want to skip owning that too.
✅ SolutionSaaS hands over a finished application: AWS or the vendor manages everything underneath it, and the team is only responsible for its own usage and configuration.
RecallSaaS = AWS/vendor manages everything underneath — you just use the product.
🔥 Easy interview recall

AWS → secures "of the cloud"

You → secure "in the cloud"

Think: the more managed a service is, the more of that line AWS takes over.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

AWS patches your EC2 instance's guest OS. It doesn't — that's squarely the customer's job under the shared responsibility model; AWS is only responsible for the underlying host and hypervisor, never the guest OS running on top of it.

🔄 Likely Follow-up

"How does the split change for a fully managed service like Lambda?" AWS takes on more — it manages the OS and runtime entirely, so the customer's responsibility narrows down to just their code and IAM permissions.

🎯 Say this in the interview — the exact lines to land

"AWS follows a shared responsibility model: AWS secures everything 'of the cloud' — the physical data centers, the hypervisor, and the network — while I'm responsible for everything 'in the cloud,' like my guest OS, my application, and my data. Exactly where that line sits moves depending on how managed the service is — I own more on EC2, AWS owns more on a fully managed service like Lambda."

  • IaaS → you own OS, runtime, app (e.g. EC2).
  • PaaS → AWS owns OS + platform patching too (e.g. RDS, Elastic Beanstalk).
  • SaaS → AWS/vendor owns everything underneath — you just use the product.
  • EC2 vs. Lambda → EC2 leaves you the OS to patch; Lambda leaves you only code + IAM permissions.
📖 Explanation ▾

AWS is a cloud platform: compute, storage, network, and database capacity rented on demand instead of bought as physical hardware, billed for only what actually gets used. How much of the stack you're handed to manage yourself depends on which delivery model a service uses — IaaS, PaaS, or SaaS.

IaaSPaaSSaaS
What you getraw infrastructure you configurea managed platform you deploy ontoa finished application you just use
ExampleEC2Elastic Beanstalk, RDSa hosted product (e.g. a managed email or CRM service)
You manageguest OS, runtime, app, datajust the app + dataonly your own usage/config
AWS manageshardware, hypervisor, network+ OS + runtime patchingeverything underneath

The Shared Responsibility Model states the same idea as a rule: AWS is always responsible for "of the cloud" — the physical data centers, the hypervisor, the global network — no matter which service is picked. Everything above that line is "in the cloud," and it's the customer's job, whether that's a full guest OS on EC2 or just application code on a serverless service.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your EC2 fleet's guest OS needs a security patch this month

EC2 is IaaS — AWS only manages the hardware and hypervisor underneath, so patching the guest OS lands squarely on the team's own schedule, never AWS's. This is the #1 scenario you'll actually run into.

RememberEC2 (IaaS) → you patch the guest OS, every time.
2 That same workload's database moves onto RDS instead of a self-managed EC2 instance

Moving to a PaaS service shifts OS and database-engine patching onto AWS — the team's job narrows down to just app configuration and the data itself, with no OS-patch task ever landing on their calendar.

RememberRDS (PaaS) → AWS also takes OS + engine patching off your plate.
3 The team rewrites that logic as a Lambda function instead of running a server at all

Lambda is fully managed — AWS owns the OS, runtime, and servers entirely, so the team's responsibility narrows to just their own code and its IAM permissions.

RememberLambda → AWS owns OS + runtime + servers; you own just code + IAM.
🌍 Real-world example ▾

A team running a fleet of EC2 instances has to patch the guest OS on a schedule — that's squarely on their side of the line. The same team's RDS database never gets a similar OS-patching task on the calendar at all, because AWS already owns that layer for a managed database.
