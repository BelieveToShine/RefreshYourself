Designing an immutable class — the recipe, not just the definition

"What's the actual recipe for designing a truly immutable class in Java?"

Why it matters ▾
🔒 Immutability
❗ ProblemA shared mutable object can be changed out from under you by any code holding a reference to it — including code you didn't write, at a time you didn't expect, causing bugs that only show up intermittently.
✅ SolutionAn immutable object's state can never change after construction — once it's built, it's safe to share across threads, cache, or hand to untrusted code with zero defensive synchronization.
RecallImmutable = built once, safe forever, no locks needed.
🔥 Easy interview recall

Immutable = "state that can never change once the object is built."

Think: final class, private final fields, no setters, defensive copy — miss any one step and the guarantee can leak.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A record with a mutable component isn't automatically truly immutable. record syntax gives you the constructor and accessors for free, but a List or array field still needs its own defensive copy — see the Records page for the full pitfall.

🔄 Likely Follow-up

"Isn't a final field alone enough to make a class immutable?" No — final only stops the reference itself from being reassigned; if that reference points to a mutable object like a List, its contents can still change underneath you unless you also defensively copy it.

🎯 Say this in the interview — the exact lines to land

"Make the class final, every field private final, give it no setters, and defensively copy any mutable field on the way in and the way out — skip that copy step and the whole guarantee collapses even if everything else is done perfectly."

  • final class → no subclass can reintroduce mutation.
  • private final fields, no setters → state is fixed the moment the constructor returns.
  • Defensive copy in/out → the one step people actually skip.
📖 Explanation ▾

Immutable means the object's observable state is fixed forever after the constructor finishes. The first three steps of the recipe — final class, private final fields, no setters — stop the class itself from ever changing a field after construction.

The step people actually skip is the defensive copy. If a constructor just stores the List or Date it was handed, the caller who passed it in still has their own reference and can mutate it later. The same problem runs the other way: a getter that returns the internal object directly hands the caller a live reference to your "immutable" state. The fix both times is the same — copy the mutable object on the way in, and copy it again on the way out.

💻 See the code ▾
☕ Java 
public final class Team {
    private final List<String> members;

    public Team(List<String> members) {
        this.members = new ArrayList<>(members);  // ✅ copy IN
    }

    public List<String> members() {
        return new ArrayList<>(members);          // ✅ copy OUT
    }
}

Both copies matter — skip either one and a caller can still mutate members after the fact.

☕ Java 
public List<String> members() {
    return members;             // ❌ hands out the real internal list
}

List<String> leaked = team.members();
leaked.add("Mallory");          // 🐛 Team's "immutable" state just changed

No exception, no warning — the object just quietly stopped being immutable.

🧭 Use Cases — recognize these when they happen to you ▾
1 You design a value object (Money) shared across threads

No shared mutable state means no race condition to guard — every thread sees the exact same, never-changing value. This is the #1 reason immutability matters in practice.

RememberNothing can change → nothing needs a lock.
2 Your constructor stores the caller's List reference directly

The caller who built the list still holds their own reference to it — if you didn't copy it, their later edit changes your "immutable" object's state retroactively.

RememberNo copy on the way in → the caller still owns your state.
3 A getter returns the internal mutable field directly

Handing back the real field gives any caller a live handle on your internal state — they can mutate your object through that reference without ever calling a setter that doesn't exist.

RememberNo copy on the way out → the getter is a secret setter.
🌍 Real-world example ▾

A sealed envelope vs. a whiteboard. Once an envelope is sealed (immutable), its contents can't change no matter who's holding it. A whiteboard (mutable) can be erased and rewritten by whoever has the marker — even if you didn't expect anyone else to touch it.
