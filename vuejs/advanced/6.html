h() — the function every template secretly compiles down to

"What is h(), and when would you actually use it instead of a template?"

Why it matters ▾
⚙️ h() — the render function templates compile to
❗ ProblemA component's output sometimes depends on complex runtime logic — a dynamic tag name, a variable shape of children — that template syntax expresses awkwardly, or not at all.
✅ Solutionh(tag, props, children) is the exact function templates compile down to. Calling it directly lets you build a component's VNode output programmatically, with full JavaScript logic, for the rare case a template genuinely can't express the variability cleanly.
Recallh() = what templates already compile to — call it directly only when a template can't.
🔥 Easy interview recall

h() = "the function templates secretly call for you."

Think: Template → compiler → h() calls → VNode tree Hand-written h() → same VNode tree, no compiler optimizations

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for a hand-written render function "for performance" is backwards. Templates already compile to this same optimized VNode-producing code via the compiler's static analysis — hand-written h() calls usually lose those optimizations (static hoisting, patch flags) unless you replicate them yourself.

🔄 Likely Follow-up

"What's a legitimate real case for h()?" A highly generic, structurally-dynamic wrapper component — one that decides its own tag name and children shape from a prop, render-prop style — where template syntax can't express the variability cleanly.

🎯 Say this in the interview — the exact lines to land

"h(tag, props, children) is the function templates compile down to. Calling it directly lets you build a component's output programmatically — useful when a component's markup shape genuinely depends on complex runtime logic a template would express awkwardly. It's not a performance shortcut: templates already compile to this same optimized call via static analysis, and hand-written h() calls usually lose automatic optimizations like static hoisting and patch flags unless you replicate them yourself."

  • h(tag, props, children) → the function templates already compile to.
  • Reaching for it "for performance" → usually loses hoisting & patch flags instead of gaining speed.
  • Legitimate use → structurally-dynamic wrapper components templates can't express cleanly.
  • Same VNode tree either way → no inherent performance difference between the two paths.
📖 Explanation ▾

h() is exported from vue and takes a tag (a string, a component, or a resolved component object), a props object, and children — and returns a VNode. You call it from a render option, or from a function returned out of setup(), instead of writing a <template> block at all.

Templates almost always win on more than just readability: the compiler's static analysis (static hoisting, patch flags — see the previous topic) only runs on template syntax it can parse ahead of time. Write the equivalent output by hand with h(), and none of that analysis happens unless you re-implement it yourself — which almost nobody does, because it isn't worth it outside genuinely unusual cases.

💻 See the code ▾
Vue 
<template>
  <component :is="tag">{{ label }}</component>
</template>

Vue's own <component :is> already covers most dynamic-tag needs without ever reaching for h() directly.

JavaScript 
function render() {
  return h(tag, null, label)  // ✅ same VNode, written by hand
}

Identical result — reach for this shape only once the component's tag or children shape is too dynamic for even <component :is> to express.

🧭 Use Cases — recognize these when they happen to you ▾
1 A design-system wrapper component picks its own root tag from a prop

A component whose rendered root element genuinely changes shape — not just the tag name, but which props and listeners are even valid — can assemble its own VNode with h() more cleanly than fighting template syntax for it.

RememberStructurally-variable root → h() can express what a template can't.
2 You rewrite a plain template in h() hoping for a speed boost

For an ordinary component, this trades away free compiler optimizations for hand-maintained code — the opposite of the intended effect.

RememberPlain component → template wins, every time.
3 You want to see exactly what a template "really" produces, for debugging

Vue's official template explorer compiles a pasted template to its actual h() calls — a genuinely useful way to see patch flags and hoisting in practice, without writing any h() by hand yourself.

RememberReading generated h() output → great for learning, not for writing.
🌍 Real-world example ▾

Writing h() by hand is like hand-assembling furniture instead of using a pre-cut flat-pack kit. Sometimes you genuinely need a custom shape the kit can't make — but for the standard cases, the kit (the compiler) already cuts every piece optimally, and redoing that by hand just means more work for the same result.
