🔥 SQL · Advanced · Must Know

It used to take 200ms — now it takes 8 seconds. Where do you look first?

This query used to be fast and now it's slow — how would you investigate? (Same question as: what would you check on a large table with degrading performance?)

Why it matters ▾
🐢 Performance Degraded Over Time
❗ ProblemWithout a real investigation process, "it used to be fast and now it isn't" tempts people to guess randomly or just suggest restarting the server — and to treat "this one query slowed down" and "this whole table's queries are degrading" as if they were two different problems needing different answers.
✅ SolutionOne repeatable checklist — current execution plan first, then data growth, then stale statistics, then blocking — turns a vague "it got slower" into an actual diagnosis, and recognizing both phrasings as the same investigation is itself part of answering it.
RecallSame query, slower now = something changed — not that the database got tired.
🔥 Easy interview recall

Same query, slower now = "something changed — not that the database got tired."

Think: check the plan first, then data growth, then stats, then blocking.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"If it was fast before, the query itself can't be the problem — something else outside the query must have changed." The query text staying exactly the same does not mean the right execution plan stays the same — data growth, stale statistics, or a dropped/changed index can all silently produce a worse plan for the identical SQL text, without anyone touching the query itself.

🔄 Likely Follow-up

"What's the very first thing you'd pull up to start investigating?" The current execution plan for that exact query, compared against what you'd expect — or against an older captured plan if you have one — because that tells you immediately whether it's still using the index/plan it used to, before checking anything else.

🎯 Say this in the interview — the exact lines to land

"A query getting slower over time — whether it's framed as one specific query regressing or a whole table's queries generally degrading — means something changed: the data grew, the execution plan changed, the statistics went stale, an index it relied on was dropped or changed, or something new is blocking it. I'd start by pulling up the current execution plan and comparing it to what I'd expect, then check for data growth, then stale statistics, then blocking."

  • Execution plan first → pull up the current plan and compare it to what you'd expect before checking anything else.
  • Data grows → more rows now than when it was fast can change which plan is actually the cheapest one.
  • Statistics go stale → after heavy inserts, updates, or deletes, the optimizer's row-count estimates can be wrong, so it picks a bad plan.
  • Blocking is separate → other concurrent activity can slow this exact query down with the query's own plan completely unchanged.
  • Same SQL, different plan → a dropped or changed index, or a stats update, can silently produce a worse plan for identical query text.
📖 Explanation ▾

A query that used to be fast and now isn't didn't just get unlucky — something concrete changed, and the job is to find which one. Most databases cache and reuse a query's execution plan rather than recomputing it every single run, so a plan that was cheap when the table was small can keep getting reused well after the table has grown — it doesn't automatically get thrown out just because the data underneath it shifted. That's why the plan is the first thing to check: it tells you directly whether the optimizer is still doing what it used to, before you spend time on anything else.

Whether the question is framed as "this large table has degrading performance" or "this one query used to be fast," it's the same investigation. A whole table degrading over time is usually just several queries against it all hitting the same underlying causes at once — the table grew, its statistics went stale, an index got dropped — not a separate category of problem. The checklist doesn't change: current plan vs. expected, data growth, statistics, blocking, and any index the query used to rely on.

💻 See the code ▾
SQL 
-- Run the exact same query again to capture its current plan
SELECT o.OrderId, o.Status, c.Name
FROM Orders o
JOIN Customers c ON c.CustomerId = o.CustomerId
WHERE o.CreatedAt > @since;
-- Compare this plan against what it used to be (or against expectation)

The query itself doesn't need to change for this step — you're capturing what plan it gets right now, to compare against before.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your table has quietly grown from thousands of rows to millions since it was fast

The query text and index are unchanged, but there's simply far more data to scan or join now — even a good plan gets slower as row counts climb, and past a tipping point the optimizer may switch to a worse plan entirely.

RememberMore rows now than before → check data growth.
2 You just ran a big bulk insert, update, or delete, and now this same query is slow

Statistics are the optimizer's row-count estimates — after a large data change they can go stale fast, so the optimizer picks a plan based on numbers that no longer match reality. This is a classic trigger to recognize right away.

RememberBig data change right before it got slow → check for stale statistics.
3 The query is only slow sometimes, depending on what else is running

This points to blocking, not a bad plan — other concurrent activity is holding locks on the same rows or tables, so the query's own execution plan can be completely unchanged and it's still forced to wait.

RememberSlow only sometimes → suspect blocking, not the plan.
🌍 Real-world example ▾

A dashboard query that used to run in 200ms now takes 8 seconds, and nothing about the query text changed. Check the current execution plan against what it used to be. Check whether the table has grown significantly since it was last fast. Check whether statistics are stale. Check for blocking from other concurrent activity — roughly in that order. Any one of those, on its own, is enough to turn a 200ms query into an 8-second one without a single character of the SQL itself being touched.
