IEquatable<T> — the typed Equals() that skips the cast

"What does IEquatable<T> solve that overriding Equals(object) alone doesn't?"

Why it matters ▾
⚡ IEquatable<T>
❗ ProblemEvery Equals(object) call on a struct boxes the argument onto the heap and casts it back before it can even look at the fields — in a hot path like a HashSet lookup, that's a fresh allocation on every single check.
✅ SolutionIEquatable<T> adds a typed Equals(T) the compiler already knows at compile time, so there's nothing to box and nothing to cast — List<T>, Dictionary, and HashSet<T> all pick it up automatically, with no change at the call site.
RecallIEquatable<T> = typed Equals(T) → no boxing, no cast, used automatically by collections.
🔥 Easy interview recall

Equals(object) → box + cast to compare

IEquatable<T>.Equals(T) → direct, no boxing

Think: Same comparison, IEquatable<T> just skips the round trip through object.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Implementing IEquatable<T> and thinking that replaces the Equals(object) override. Anything that only holds an object reference — old collections, reflection, a mixed-type list — still calls the object overload, so it must still exist, usually just forwarding to Equals(T).

🔄 Likely Follow-up

"So do you still need to override GetHashCode() too?" Yes — IEquatable<T> only changes how Equals is called, not the hashing contract; Dictionary/HashSet still need a matching GetHashCode() or lookups silently fail.

🎯 Say this in the interview — the exact lines to land

"IEquatable<T> adds a strongly-typed Equals(T), so a struct never gets boxed and a class never needs a downcast just to compare. It also turns a wrong-type comparison into a compile error instead of a silent false. You still keep the Equals(object) override — IEquatable<T> is an addition, not a replacement."

  • Equals(object) → requires a box + cast before struct fields can be compared.
  • IEquatable<T>.Equals(T) → compares directly, no boxing, no cast.
  • Wrong-type argument → compile error with IEquatable<T>, a silent false with the object overload.
  • Biggest win is on structs — that's where the boxing allocation actually happens.
📖 Explanation ▾

Equals(object) has to accept anything — so on a struct, passing itself through that parameter boxes it onto the heap first, then the method casts the boxed reference back down to the real type before it can even look at the fields.

Equals(T) from IEquatable<T> already knows the exact type at compile time, so there's nothing to box and nothing to cast — the parameter arrives ready to compare. That's the whole trade: one extra interface, one typed method, and the boxing round trip disappears.

The compiler also uses this to your advantage: collections like List<T>, Dictionary<TKey,TValue>, and HashSet<T> automatically prefer the typed Equals(T) when a type implements it, without any code change at the call site.

💻 See the code ▾
C# 
public struct Point : IEquatable<Point>
{
    public int X, Y;

    public bool Equals(Point other)          // typed — no boxing
        => X == other.X && Y == other.Y;

    public override bool Equals(object? obj)  // still needed for object callers
        => obj is Point p && Equals(p);      // forwards to the typed version

    public override int GetHashCode() => HashCode.Combine(X, Y);
}

The object override still exists — it just forwards to the typed Equals(Point) instead of duplicating the comparison.

C# 
object boxed = new Point { X = 1, Y = 2 };  // ❌ boxes the struct onto the heap
bool same = boxed.Equals(new Point { X = 1, Y = 2 });
// runs Equals(object) — casts obj back to Point before comparing

Storing the struct in an object forces a box before Equals even runs.

C# 
var a = new Point { X = 1, Y = 2 };
var b = new Point { X = 1, Y = 2 };
bool same = a.Equals(b);   // ✅ compiler picks Equals(Point) — no boxing, no cast

Same fields, same answer — just reached without ever touching the heap.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your struct is used as a Dictionary key or lives inside a HashSet in a hot loop

The collection calls Equals(T) directly the moment the type implements IEquatable<T> — no boxing, no cast, no change at the call site. This is the #1 scenario the interface exists for.

RememberStruct + collection lookup → IEquatable<T> removes the allocation.
2 You accidentally try to compare against the wrong type

The typed Equals(T) overload only accepts the exact type, so passing the wrong one is a compile error. The old Equals(object) overload would have quietly accepted it and returned false instead.

RememberWrong type + IEquatable<T> → compile error, not a silent false.
3 Your struct gets stored or passed around as a plain object reference — an old collection, reflection, a mixed-type list

Anything that only holds an object reference still calls the object overload, so IEquatable<T> alone doesn't save you here — it only pays off because that overload is written to forward to the typed Equals(T).

RememberHeld as object → still Equals(object) → still needs the override.
🌍 Real-world example ▾

A HashSet<Point> tracking visited grid cells in a pathfinding or game-simulation loop. Every membership check calls Equals — without IEquatable<Point>, that's a fresh heap allocation per check, and enough of those show up as extra GC pressure in a profiler. Implementing it removes the allocation entirely; List<T>.Contains, Dictionary, and HashSet<T> all pick it up automatically, with no change at the call site.
