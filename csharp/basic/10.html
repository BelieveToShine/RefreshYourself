int? — what happens when an int can be nothing

Why it matters ▾
🔢 int
❗ ProblemA plain int always holds some real number — modelling something genuinely optional, like a middle-name initial left blank, leaves no legal way to say "not provided" without faking it with a number that means something else.
✅ SolutionReach for plain int exactly when a value is guaranteed to exist — because it can never be empty, it's always safe to just read it, no check needed.
Recallint = always a real number, no null, no check needed.
❓ int?
❗ ProblemReading .Value on a null int? doesn't return 0 — it throws an InvalidOperationException, exactly the mistake this topic exists to catch.
✅ Solutionint? adds null as a legal extra state — check .HasValue (or use ??) before trusting .Value, the same way reference types were already allowed to be null.
Recallint? = Nullable<int> — check .HasValue or use ?? before reading .Value.
🔥 Easy interview recall

int? = "an int, plus one more legal state: null."

Think: age ?? 0 → the real value, or 0 if it's null

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reading .Value on a null int? doesn't return 0 — it throws. Always check .HasValue (or use ??) first.

🎯 Say this in the interview — the exact lines to land

"int? is Nullable<int> — it adds null as a legal state on top of every normal int value. Check .HasValue, or use ?? for a fallback, before trusting .Value."

  • null means "not set," not the same as zero.
  • Reference types were already nullable — this brings the same idea to value types.
📖 Explanation ▾

A plain value type like int can never be "empty" — it always holds some number, even if that number is just 0. int? (shorthand for Nullable<int>) adds one more legal state on top: null, meaning "genuinely no value," not "zero."

Check .HasValue (or compare to null) before trusting .Value — reading .Value on a null nullable throws. The ?? operator sidesteps that: age ?? 0 reads as "give me the value, or 0 if there isn't one."

Reference types (string, classes) could already be null — nullable value types just extend that same idea to int, bool, DateTime, and every other value type.

💻 See the code ▾
C# 
int? age = null;   // legal — int? allows "nothing"
Console.WriteLine(age.Value);   // ❌ throws InvalidOperationException

There's no value to give you — reading .Value without checking first is the exact mistake this topic exists to catch.

C# 
if (age.HasValue)              // check before reading .Value
    Console.WriteLine(age.Value);   // ✅ safe

int safeAge = age ?? 0;   // ✅ 0 if null, else the real value

Two safe patterns — check first, or fall back with ??.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're modelling a field or column that's genuinely optional, like a middle-name initial left blank.

A plain int has to hold some number, so there's no way to say "not provided." int? adds null as that extra legal state — exactly the way the blank box on a form really means "not provided," not zero.

RememberOptional data → int?, not a made-up 0.
2 You need a plain int back out of a nullable one, with a sensible fallback if it's null.

The ?? operator skips the .HasValue check entirely — age ?? 0 always returns a value either way, so there's no branch to write yourself.

Rememberage ?? 0 → the real value, or 0 if it's null.
3 You read .Value on an int? without checking .HasValue first — a common interview trap.

Reading .Value on a null int? doesn't return 0 — it throws an InvalidOperationException, because there's no value to give you.

RememberNo .HasValue check before .Value → InvalidOperationException.
🌍 Real-world example ▾

A form field left blank. A required "age" field always has a number in it. An optional "middle name initial" field can be blank — blank isn't the same as "the letter zero," it means "not provided." int? is how C# represents that blank box.
