One method, three hidden dependencies — name the principle at each step

"You're handed a service that directly instantiates its own database connection, its own logger, and calls a static email-sender method — how would you refactor it?"

Why it matters ▾
🔌 Hard-Coded Dependencies
❗ ProblemA class that builds its own database connection, its own logger, and calls a static email method can't be unit-tested — none of the three can be substituted for a fake.
✅ SolutionInject an abstraction for each dependency through the constructor instead, so a test can hand in three fakes and substitute every one of them.
RecallOwn the dependency = untestable. Inject the abstraction = swappable in a test.
🔥 Easy interview recall

new SqlConnection → inject IOrderRepository

new FileLogger → inject ILogger

EmailSender.SendStatic() → inject IEmailSender

Think: every new and every static call inside a class is a hidden dependency — the fix is always the same shape: depend on an interface, and have it handed in.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Injecting a concrete type isn't Dependency Inversion. NotificationService(SqlOrderRepository repo) just moves the new call to whoever constructs this class — real DIP means depending on IOrderRepository, the abstraction itself, not merely avoiding new inside the class.

🔄 Likely Follow-up

"If you could only make ONE of these three changes before your interview time runs out, which do you do first?" The database connection — it's normally the single biggest blocker to writing any unit test for this class at all, so fixing it first unlocks testing the rest of the refactor incrementally.

🎯 Say this in the interview — the exact lines to land

"Each extraction is the same move: stop constructing the dependency yourself, and take it through the constructor as an interface instead. That's Dependency Inversion — the database connection, the logger, and the email sender all become IOrderRepository, ILogger, and IEmailSender. Once that's done, I'd step back and check the class still has one job — Single Responsibility — before calling it finished."

  • new SqlConnection → inject IOrderRepository through the constructor, not a concrete repository.
  • new FileLogger → inject ILogger, so the class never decides how or where logging happens.
  • EmailSender.SendStatic() → a static call can't be substituted in a test; wrap it behind IEmailSender and inject that instead.
  • Concrete type injected instead of an interface → still coupled, just to a different constructor — not real DIP.
  • After all three extractions → re-check Single Responsibility; retries, templating, or scheduling creeping in means splitting further.
📖 Explanation ▾

All three extractions are the same underlying move applied to a different collaborator: the class stops deciding which concrete thing it talks to, and instead takes an abstraction through its constructor. That's Dependency Inversion — the service now depends on IOrderRepository, ILogger, and IEmailSender, none of which know or care whether the real implementation is SQL Server, a file, or an SMTP call. Each swap also happens to fix the coupling problem on its own terms: the class no longer hard-depends on ADO.NET specifically, or on writing to a file specifically.

The static EmailSender.SendStatic() call deserves its own attention — it's a coupling dead-end in a way new isn't quite as bad. A test can at least construct a real FileLogger pointed at a throwaway path; it cannot substitute a static method call without extra tooling (a static-mocking library, or wrapping the call in an interface anyway). Wrapping it behind IEmailSender removes a hidden global dependency, not just an inconvenient one.

Extracting all three doesn't automatically mean the refactor is finished. Once NotificationService only orchestrates a repository, a logger, and an email sender it's handed, ask whether that's still its one job. If it's also grown retry logic, message templating, or scheduling along the way, that's a separate signal — Single Responsibility, not Dependency Inversion — to split it further.

💻 See the code ▾
C# 
public class NotificationService
{
    public void SendOrderConfirmation(Order order)
    {
        var connection = new SqlConnection("Server=prod-db;..."); // ❌ owns its own DB connection
        var logger = new FileLogger(@"C:\logs\app.log");       // ❌ owns its own logger
        EmailSender.SendStatic(order.CustomerEmail, "Confirmed"); // ❌ static call, can't substitute
        // ...uses connection and logger directly...
    }
}

Three hidden dependencies in one method — none of them can be swapped for a test double, so this class cannot be unit-tested as written.

C# 
public class NotificationService
{
    private readonly IOrderRepository _repo;
    private readonly ILogger _logger;
    private readonly IEmailSender _emailSender;

    public NotificationService(IOrderRepository repo, ILogger logger, IEmailSender emailSender)
    {
        _repo = repo;               // ✅ injected abstraction, not new SqlConnection
        _logger = logger;           // ✅ injected abstraction, not new FileLogger
        _emailSender = emailSender; // ✅ injected abstraction, not a static call
    }

    public void SendOrderConfirmation(Order order)
    {
        _logger.Log($"Confirming order {order.Id}");
        _emailSender.Send(order.CustomerEmail, "Confirmed");
    }
}

Every collaborator arrives through the constructor as an interface — a test can hand in three fakes and never touch a real database, file, or mail server.

C# 
// ❌ Still not Dependency Inversion — repo's type is concrete, not an interface
public NotificationService(SqlOrderRepository repo)
{
    _repo = repo; // the "new" call just moved to whoever constructs this
}

This compiles and looks injected, but NotificationService still hard-depends on SqlOrderRepository specifically — swap in IOrderRepository to actually invert the dependency.
