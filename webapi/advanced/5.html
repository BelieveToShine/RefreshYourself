Your API just went 10x — do you diagnose or scale first?

"Your API suddenly gets 10x its normal traffic. Walk me through how you'd diagnose and respond."

Why it matters ▾
📈 Real growth
❗ ProblemDemand genuinely went up and it's sticking around — treat it like a fluke and real users start hitting rate limits or errors during a spike you should be capturing, not blocking.
✅ SolutionScale out (or autoscale) and invest in caching and capacity planning — this is the one cause where adding capacity is actually the right fix.
RecallReal growth → scale for it, it's not going away.
🔁 Retry storm
❗ ProblemA downstream dependency has a bad patch, callers with no backoff retry the same failed call over and over, and the retries alone multiply into a spike that looks identical to real growth.
✅ SolutionThrottle at the edge to survive the moment, then fix backoff and circuit breaking on the caller — scaling out only gives the storm more to retry against.
RecallRetry storm → fix the caller's backoff, don't just add servers.
🚨 Attack
❗ ProblemMalicious or abusive traffic floods the API on purpose — scaling out just hands the attacker more capacity to hit, and nothing about the actual problem improves.
✅ SolutionRate-limit and block at the edge — WAF rules and abuse detection stop bad traffic before it ever reaches the backend.
RecallAttack → block at the edge, scaling doesn't help.
🔥 Easy interview recall

Triage → look at metrics before touching anything

Mitigate → scale or throttle to stop the bleeding

Diagnose → why it happened, once it's stable

Think: Look before you touch. Fix the symptom fast, find the cause after.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just add more servers" is not the whole answer. Scaling out doesn't help if the real bottleneck is a saturated database connection pool or a downstream dependency that's already maxed out — you'd only be sending more failed requests faster, and you'd still never find out why it happened.

🔄 Likely Follow-up

"What's the very first thing you'd look at, before touching any infrastructure?" The metrics and dashboards — request rate, error rate, latency, and resource saturation — so you know where the failure actually is before changing anything. Changing things blind on an already-unstable system risks making it worse.

🎯 Say this in the interview — the exact lines to land

"First I'd look at metrics, not guess — request rate, error rate, latency, CPU/memory per instance, and DB connection pool saturation — to find where it's actually failing. Then I'd apply the fastest safe fix: scale out if the service is stateless, or throttle at the edge to protect the backend. Once it's stable, I'd find out why it happened — growth, a client retry storm, or an attack — and fix that specifically, plus put in caching, autoscaling, and load testing so the next spike isn't a surprise."

  • Triage → check metrics before touching anything — request rate, error rate, latency, CPU/memory, DB pool saturation.
  • Mitigate → scale out if stateless, or throttle at the edge to protect the backend from total collapse.
  • Communicate → signal degraded mode if that capability exists, rather than fail silently for everyone.
  • Diagnose the cause → growth, a retry storm, or an attack each need a genuinely different fix.
  • Architect for next time → caching, autoscaling tied to the right metrics, and load testing before the next spike, not during it.
📖 Explanation ▾

Triage comes first, always. Before changing anything, look at request rate, error rate, latency, CPU/memory per instance, and database connection pool saturation to find where the system is actually failing — the API tier, the database, or a downstream dependency. Only once you know that does a mitigation make sense: scale out horizontally if the service holds no in-memory state (scaling a stateful instance just spreads the same problem across more boxes), or throttle/rate-limit at the edge (see Rate Limiting) so the backend degrades for some requests instead of collapsing for all of them.

Once the immediate fire is out, the real interview signal is asking why it happened — the fix is different for each cause. See Retry vs. Resilience for why a downstream outage without backoff turns into a retry storm that looks identical to real growth on a traffic graph.

💻 See the code ▾
C# 
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("perClient", opt =>
    {
        opt.PermitLimit = 100;              // requests
        opt.Window = TimeSpan.FromSeconds(10);
        opt.QueueLimit = 0;                 // ✅ reject fast, don't queue up more load
    });
    options.RejectionStatusCode = 429; // Too Many Requests
});

Throttling at the edge is the fast, safe mitigation while you diagnose — it protects the backend from total collapse instead of letting every request fail.

🧭 Use Cases — recognize these when they happen to you ▾
1 Traffic is up, but it's coming from many different users and IPs, hitting the normal mix of endpoints

Look at unique client counts, not just total requests — when the extra volume is spread across a broad, varied set of callers and lands on the same mix of endpoints your API normally serves, that spread is the signature of real growth, not a malfunction. This is the #1 scenario you'll actually run into.

RememberMany distinct IPs, normal spread → real growth.
2 Traffic is up, but it's the same handful of endpoints getting hit with duplicate-looking calls, right around a recent partial outage

Check your own logs and incident history first — if the spike lines up right after a downstream dependency was returning errors, and the extra volume is concentrated on the same few endpoints as duplicate retries of the same failed calls rather than spread across your normal traffic, that combination is a retry storm, not new demand.

RememberDuplicate calls + recent outage timing → retry storm.
3 Traffic is up with patterns that don't look like real usage — one endpoint way out of proportion, a narrow set of IPs, or oddly-shaped requests

Look for traffic that doesn't behave like a real client would — near-total concentration on a single endpoint, a small number of source IPs generating a huge share of volume, or requests with malformed or scripted-looking payloads and headers. That combination is the signal to rate-limit and block at the edge, not to provision more capacity for it.

RememberConcentrated + narrow IPs + malformed requests → attack, not demand.
🌍 Real-world example ▾

A downstream payment provider starts returning 500s for ninety seconds. Every client library retries each failed call three times with no backoff — real user traffic hasn't changed at all, but request volume at your API jumps 10x in minutes, purely from retries. Scaling out here just gives the retry storm more capacity to retry against; the actual fix is backoff and circuit breaking on the caller, not more servers.
