🔥 Web API · Advanced · Must Know

One of three calls just failed — does the whole response go down with it?

"Your API calls three other services to build one response, and one of them is failing — what do you do?"

Why it matters ▾
🧩 Partial Downstream Failure
❗ ProblemLetting one failing dependency's exception propagate takes down the entire response, even when the other calls succeeded and the failing one wasn't essential to answering the request.
✅ SolutionDecide essential vs. supplementary up front — fail fast for essential calls, degrade gracefully for supplementary ones — and wrap every call in a timeout and a circuit breaker either way.
RecallEssential → fail fast. Supplementary → degrade, don't fail the whole request.
🔥 Easy interview recall

Essential call fails → fail fast, clear error

Supplementary call fails → degrade, return the rest

Think: One bad call shouldn't sink a response the other two calls already earned — unless it genuinely had to be there.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Letting one failing call take down the whole response is an all-or-nothing mistake. If the other two downstream calls succeeded and the failing one wasn't essential, a partial response was the better answer, not a 500.

🔄 Likely Follow-up

"What does a circuit breaker add beyond a timeout?" A timeout limits how long you wait on one call; a circuit breaker remembers a dependency has been failing and stops calling it for a cooldown window entirely — protecting both your own app from wasted waiting and the struggling downstream service from a retry pile-up making its recovery harder.

🎯 Say this in the interview — the exact lines to land

"It depends on whether that call is essential or supplementary. If I can't produce a meaningful response without it, I fail fast with a clear error. If it's a nice-to-have enrichment, I degrade gracefully — return the response with that piece missing or defaulted. Either way, I wrap the call in a timeout so one slow dependency can't hang the whole request, and a circuit breaker so repeated failures stop retrying a service that's clearly down."

  • Essential call fails → fail fast with a clear error, don't hang.
  • Supplementary call fails → degrade gracefully — return the rest, omit or default that field.
  • Every downstream call → gets its own timeout, so one slow call can't hang everything.
  • Circuit breaker → stops retrying a dependency that's clearly down, protects both sides.
  • Never → let one failure silently sink two successful calls.
📖 Explanation ▾

The right response to a failing downstream call depends entirely on what that call was for. An essential dependency is one the response genuinely can't be correct without — pricing data for a checkout, inventory for an order. For that, fail fast: return a clear error immediately rather than letting the request hang or returning something silently wrong. A supplementary dependency is an enrichment the response is still meaningful without — a "recommended for you" panel, a non-critical metadata field. For that, degrade gracefully: catch that specific failure, omit or default the affected field, and return the rest of the response that the other calls already built successfully.

Independent of that decision, every downstream call should carry its own timeout (so a slow dependency doesn't hang the whole request indefinitely) and ideally a circuit breaker (via a library like Polly — see Resilience in .NET) so that once a dependency has clearly started failing, calls stop being sent to it for a cooldown window instead of piling up retries against an already-struggling service. The combination — essential/supplementary judgment, timeout, circuit breaker — is what turns "one dependency is down" from a full outage into a contained, partial degradation.

💻 See the code ▾
C# 
var pricing = await _pricing.GetPriceAsync(id, ct); // essential — no try/catch, let it fail fast

Recommendation[] recs = [];
try
{
    recs = await _recommendations.GetForAsync(id, ct); // ✅ supplementary — caught on its own
}
catch (Exception ex)
{
    _logger.LogWarning(ex, "Recommendations unavailable, degrading");
}

return Ok(new { pricing, recommendations = recs }); // recs can be empty, pricing can't

The essential call has nothing catching it — a failure there should surface. The supplementary call is caught and defaulted so it can never take the response down with it.

🌍 Real-world example ▾

A product page calls pricing, inventory, and a "customers also viewed" service. The recommendations service times out. Pricing and inventory both succeeded. Treating the recommendations failure as supplementary — logging it and returning the page without that panel — keeps the page usable; treating it the same as a pricing failure and returning a 500 would take down a perfectly sellable page over a feature nobody would have missed.
