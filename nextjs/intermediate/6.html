Dynamic rendering is inferred, not a mode you switch on

"How does a route become 'dynamic' (SSR-like) in the App Router without an explicit getServerSideProps?"

Why it matters ▾
⚡ Dynamic rendering, auto-detected
❗ ProblemThe Pages Router needed an explicit getServerSideProps export before a page would render per-request — without a clear equivalent switch, it's not obvious how the App Router decides a route needs per-request rendering at all.
✅ SolutionNext.js automatically detects when a route uses request-specific data — cookies(), headers(), searchParams, or an uncached fetch — and opts that route out of static rendering on its own, no manual declaration required.
RecallTouch request data → Next.js makes the route dynamic automatically.
🔥 Easy interview recall

Dynamic rendering = "whatever the route does decides it, not a flag you set."

Think: use cookies() or no-store → route becomes per-request automatically, no declaration needed.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

There's no separate "SSR mode" setting to flip in the App Router. Dynamic rendering is usually inferred automatically from what the route actually does — reading cookies(), headers(), or using no-store — not a manual switch you configure elsewhere.

🔄 Likely Follow-up

"Can you force a route to be dynamic even if nothing inside it strictly requires it?" Yes — export const dynamic = 'force-dynamic' at the route's top level forces per-request rendering regardless of what the code inside does.

🎯 Say this in the interview — the exact lines to land

"A route becomes dynamically rendered when it uses request-specific data — cookies(), headers(), searchParams, or cache: 'no-store' — and Next.js detects that automatically, without needing an explicit 'this is SSR' declaration the way the Pages Router required getServerSideProps."

  • cookies() / headers() → auto-triggers dynamic rendering.
  • No manual switch → inferred from what the code does, not declared.
  • Need it forced anyway? → export const dynamic = 'force-dynamic'.
📖 Explanation ▾

The App Router doesn't ask you to declare a page as static or dynamic up front — it looks at what the route actually does. Calling cookies() or headers() (both only meaningful per-request), reading searchParams, or making a fetch() with cache: 'no-store' are each a signal that this render can't be reused across requests, so Next.js opts the route into dynamic rendering automatically.

This is the opposite direction from the Pages Router, where getServerSideProps was the explicit, named thing you added to get per-request behavior. In the App Router, dynamic behavior falls out of what the component already needed to do — nothing extra to declare.

You can still override the inference either direction: export const dynamic = 'force-dynamic' forces per-request rendering even if nothing inside strictly needs it, and export const dynamic = 'force-static' forces static rendering (dropping any request-specific reads would otherwise trigger).

💻 See the code ▾
Next.js 
// app/dashboard/page.js — becomes dynamic automatically
import { cookies } from 'next/headers';

export default async function Dashboard() {
  const session = cookies().get('session');   // ✅ request-specific → dynamic
  const user = await getUser(session?.value);
  return <p>Welcome, {user.name}</p>;
}

No dynamic export anywhere — reading cookies() alone is enough.

Next.js 
// forcing it explicitly instead of relying on inference
export const dynamic = 'force-dynamic';   // ✅ always per-request, no exceptions

export default async function Page() { return <div>...</div>; }

Useful when the inference wouldn't otherwise trigger but you still want per-request behavior.

🧭 Use Cases — recognize these when they happen to you ▾
1 A page shows content specific to the logged-in user

Reading the session cookie to show a personalized dashboard is exactly the kind of request-specific read that makes the route dynamic on its own — no extra configuration needed.

RememberPer-user content → cookies() read makes it dynamic automatically.
2 A search results page driven by a query string

Using searchParams to render results means every distinct query string needs its own render — this alone pushes the route into dynamic rendering, the same automatic inference as reading cookies.

RememberReading searchParams → dynamic, same automatic rule.
3 You go looking for a config file flag to "turn on SSR"

There's no site-wide "enable SSR" setting to find — the decision is made per-route, inferred from what that route's code actually reads, or set explicitly per route with the dynamic export.

RememberNo global SSR switch — it's always a per-route decision.
🌍 Real-world example ▾

A dashboard that reads a session cookie to greet the logged-in user by name. The moment the component calls cookies(), Next.js renders that route per-request — no page config, no exported function, just the natural consequence of needing request-specific data to render the page at all.
