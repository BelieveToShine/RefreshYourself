Events vs. Delegates — a delegate with a safety lock

"What's the difference between an event and a delegate — why not just expose a public delegate field?"

Why it matters ▾
🔔 event
❗ ProblemA public delegate field lets any outside code call it as if it were its own, or overwrite it with = and silently remove every other subscriber.
✅ SolutionThe event keyword gives outsiders only += and -=; only the owning class can raise it.
Recallevent = delegate + lock: outsiders can subscribe, not fire.
🔥 Easy interview recall

public Action → anyone can call or wipe it

event → outsiders only subscribe / unsubscribe

Think: with an event, the owner shouts and everyone else only listens.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

An event is not a separate thing from a delegate. It is a delegate with restricted access — the event keyword changes who can call it, not what it holds.

🔄 Likely Follow-up

"How can events cause a memory leak?" The publisher keeps a reference to each subscriber's method (and its object), so a subscriber that never does -= can't be collected while the publisher lives — unsubscribe, often in Dispose() (see IDisposable).

🎯 Say this in the interview — the exact lines to land

"A delegate holds methods; an event is a member built on a delegate that outsiders can only add handlers to with += or remove with -=. Only the declaring class can raise it. I follow the EventHandler<T> convention, and I unsubscribe so long-lived publishers don't keep subscribers alive."

  • event → outsiders get += and -= only; they can't invoke it or assign with =.
  • Only the owning class raises it — usually Changed?.Invoke(this, args).
  • Convention: EventHandler<TEventArgs> — the handler gets (sender, args).
  • The publisher references its subscribers, so a forgotten -= is a classic leak.
  • It is the publish/subscribe idea — the publisher doesn't know who is listening.
📖 Explanation ▾

An event is built on a delegate. Declaring public event EventHandler Changed; gives outside code only two moves: += to subscribe and -= to unsubscribe. This builds on delegates.

Raising the event is only allowed inside the declaring class. With a public delegate field, any outside code could invoke it, or replace it with = and drop every other subscriber. The event keyword is the lock that prevents both.

The standard shape is EventHandler<T> with a sender and an args object, raised with ?.Invoke(...) so having no subscribers is safe. Because the publisher keeps references to its subscribers, unsubscribe when you are done.

💻 See the code ▾
C# 
public record ChangedArgs(int Value) : EventArgs;

public class Counter
{
    public event EventHandler<ChangedArgs>? Changed;
    private int _n;

    public void Increment()
    {
        _n++;
        Changed?.Invoke(this, new ChangedArgs(_n));   // only Counter can raise it
    }
}

The event is declared once; only the class itself calls it.

C# 
var c = new Counter();
EventHandler<ChangedArgs> h = (s, e) => Console.WriteLine(e.Value);

c.Changed += h;    // subscribe
c.Increment();     // prints 1
c.Changed -= h;    // unsubscribe — avoids keeping the handler alive

// c.Changed(c, new ChangedArgs(0));   // compile error outside Counter
// c.Changed = null;                   // compile error — only += and -=

Outsiders can subscribe and unsubscribe, nothing more.

🌍 Real-world example ▾

A button's Click. The button raises it; any number of handlers subscribe with +=; none of them can fire a click on the button's behalf.
