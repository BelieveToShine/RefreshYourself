Pages Router → App Router — migrate one route, not one big bang

"What's the recommended strategy for migrating a large production app from the Pages Router to the App Router?"

Why it matters ▾
🚦 Incremental migration
❗ ProblemMigrating an entire app directory and every data-fetching call in one pass is a large, high-risk batch of changes with no incremental verification point — it blocks all other work until it's fully done.
✅ Solutionapp/ and pages/ can coexist in the same project — the officially recommended path is moving one route at a time, verifying it, and shipping in between.
Recallpages/ and app/ coexist — migrate route by route, not all at once.
🔥 Easy interview recall

Migration strategy = "one route at a time, both directories coexist the whole way."

Think: replacing one tile at a time in a floor you're still walking on — never ripping the whole floor out at once.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Migrating the entire app/ directory and every data-fetching call in one pass before shipping anything is not the recommended approach. It's a large, high-risk batch with no incremental verification point — exactly what the official incremental guidance exists to avoid.

🔄 Likely Follow-up

"What's usually the hardest part of a real migration, in practice?" Converting getServerSideProps/getStaticProps-based data fetching (and any code that assumed a fully client-rendered component tree) into the Server/Client Component split — more of a mental-model shift than a mechanical find-and-replace.

🎯 Say this in the interview — the exact lines to land

"The officially recommended path is incremental, route by route — app/ and pages/ can coexist in the same project during migration, so I'd move one route at a time, verify it, and keep shipping in between, rather than one big-bang rewrite."

  • Recommended strategy → incremental, one route at a time.
  • app/ and pages/ → coexist throughout the migration.
  • Avoid → migrating everything in one unverified pass.
  • Hardest part in practice → the data-fetching → Server/Client Component mental shift.
📖 Explanation ▾

Next.js lets app/ and pages/ coexist in the same project — a route defined in one doesn't conflict with a route defined in the other, as long as they don't claim the same path. That's what makes an incremental migration possible at all: move one route, deploy, confirm it behaves correctly in production, then move the next.

The alternative — migrating the whole app/ structure and every data-fetching call before shipping anything — removes every incremental checkpoint. Any regression has to be found somewhere inside one giant diff, after a long stretch with nothing shippable in between.

In practice, the mechanical part (moving a file, renaming getStaticProps's call site) is rarely what's hard. The real work is deciding which parts of a page are Server Components and which need to be Client Components — a genuine architectural decision, not a search-and-replace.

💻 See the code ▾
JSX 
// pages/about.js — still untouched, still serving /about
export default function About() {
  return <h1>About</h1>;
}

// app/dashboard/page.jsx — migrated, serving /dashboard, in the SAME build
export default function Dashboard() {
  return <h1>Dashboard</h1>;
}

Both routes ship together — /about hasn't moved yet, and that's fine.

🌍 Real-world example ▾

A large e-commerce app needs the App Router's streaming for its product pages, but can't risk its checkout flow during the switch. Migrate the product pages first, ship, watch them in production — leave checkout on the Pages Router until the rest of the migration has already proven itself elsewhere.
