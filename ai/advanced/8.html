N tenants shouldn't mean N hand-written prompts — layer them instead

How would you design a prompt system that gives every tenant or use case shared baseline behavior plus its own overrides, without maintaining a fully separate prompt per tenant — and how would you let it improve automatically from real usage?

Why it matters ▾
🧩 Prompt Layering
❗ ProblemHand-writing N complete prompts for N tenants means every shared-behavior fix has to be copy-pasted into every one of them by hand, and the copies quietly drift apart from each other over time.
✅ SolutionKeep one shared base prompt plus a thin per-tenant override layer, resolved into a single prompt at runtime — a shared fix changes in one place, the base, instead of N separate copies.
RecallPrompt layering = 1 base + N thin overrides, merged at runtime — never N full, hand-written prompts.
🔥 Easy interview recall

Base + override → merged at runtime into one resolved prompt

Auto-tuned proposal → must clear a validation gate before it's live

Think: maintain 1 base + N thin overrides — never N full, separately hand-written prompts.

🧠 Visual Mental Model — understand it in 5 seconds
🔁 The Feedback Loop — auto-tuning, behind a gate
⚠️ Common Trap

Assuming an "auto-tuned" prompt is safe to activate the moment the job produces it. Without a validation gate between the proposal and activation, one bad automatic tune — from noisy, gamed, or unrepresentative feedback — ships straight into production for every user under that tenant.

🔄 Likely Follow-up

"How is this different from just A/B testing prompts?" A/B testing compares versions a person deliberately chose to test; auto-tuning is the system itself proposing a new candidate layer from feedback. In practice they combine — A/B testing in production is often exactly how an auto-tuned candidate earns its way past the gate, not a separate concern from it.

🎯 Say this in the interview — the exact lines to land

"A shared base prompt plus a per-tenant override layer are resolved at runtime into the one prompt actually sent — never N fully separate, hand-written prompts. Both layers are versioned, can be A/B tested, and a tenant's own layer can even be auto-tuned from real feedback — but never activated without passing a validation gate first."

  • Base + override → resolved at runtime into the final prompt — one shared source of truth, not N.
  • Per-tenant override → versioned and swappable independently of the base.
  • A/B testing → compare prompt/layer versions in production before fully rolling one out.
  • Auto-tuning → a scheduled job grows a tenant's layer from win/loss, click, or correction signals.
  • Validation gate → an auto-tuned change is checked before activation — it never ships unchecked.
📖 Explanation ▾

Prompt layering means keeping one shared base prompt — the instructions every tenant or use case gets — and a thin per-tenant override layer on top of it. The two are resolved at runtime into the single prompt that's actually sent to the model, instead of maintaining N completely separate, hand-written prompts for N tenants. A shared-behavior fix changes in one place, the base, instead of being copy-pasted into every tenant's own copy.

Each layer is its own versioned, production artifact — the same discipline as any production prompt: it lives outside the application code and can be updated or rolled back without a redeploy. Because a layer is just versioned data, two versions of it can be run side by side in production and A/B tested against each other to compare real outcome quality before one fully replaces the other.

A real pattern this enables: a scheduled job that grows a tenant's own override layer automatically, using real signals from actual usage — wins and losses, clicks, or human corrections. The proposed change is still just a candidate. It has to pass a validation gate before it's activated as the tenant's current layer; a proposal that fails the gate is rejected, not silently shipped. That gate is the whole point — it's what keeps an automatic tune from becoming an automatic outage.

💻 See the code ▾
Python 
def resolve_prompt(tenant_id: str) -> str:
    base = prompt_store.get("base", version="current")          # shared
    override = prompt_store.get(f"override:{tenant_id}", version="current")
    return base + "\n\n" + override  # ✅ merged once, per request

The app never hand-writes one full prompt per tenant — it merges the shared base with that tenant's own override layer at request time.

Python 
proposal = auto_tune_job.propose_layer(tenant_id, signals=recent_feedback(tenant_id))

if validation_gate.passes(proposal):        # ✅ checked before it ships
    prompt_store.activate(tenant_id, proposal)
else:
    prompt_store.reject(proposal)              # 🐛 caught, never goes live

A proposal only replaces the tenant's current layer after it clears the gate — a bad automatic tune is rejected, never silently activated.

🧭 Use Cases — recognize these when they happen to you ▾
1 A new tenant needs its own tone, disclaimer, or house rules

The instinct is to hand-write that tenant a complete prompt of its own. Give it the shared base prompt plus a thin override layer instead — the same base + override split this page's main diagram shows — so a later shared-behavior fix only has to change the base once, not be copy-pasted into every tenant's own copy.

RememberNew tenant → thin override on the shared base, never a full new prompt.
2 You want to try a change to a tenant's layer without risking it on every request

Because each layer is just versioned data, two versions of a tenant's override can run side by side and be A/B tested against each other to compare real outcome quality — before one version fully replaces the other, rather than a risky one-shot swap.

RememberComparing layer changes → A/B test the versions, don't just swap and hope.
3 An auto-tune job just proposed a change to a tenant's override layer

Candidates often assume a freshly auto-tuned proposal is safe to activate the moment the job produces it. It's still just a candidate — it must clear the validation gate first; a proposal from noisy, gamed, or unrepresentative feedback gets rejected there, not shipped to every user under that tenant.

RememberAuto-tuned proposal → gated before activation, never activated on arrival.
🌍 Real-world example ▾

Scenario: 200 enterprise tenants share one core assistant, but each wants its own tone, disclaimer, or house rules. Hand-writing 200 full prompts means a shared bug fix has to be copy-pasted 200 times and inevitably drifts. The fix: one base prompt everyone shares plus a thin, versioned override layer per tenant, resolved into the final prompt at request time — a shared fix changes once, and a bad per-tenant tweak (or a rejected auto-tune) only ever touches that one tenant's own layer.
