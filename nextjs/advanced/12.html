Bundle Analysis — the one dependency secretly bloating every page

"How would you find and fix an unexpectedly large client bundle?"

Why it matters ▾
📦 Bundle size
❗ ProblemA heavy client-side library imported at the top of a widely-shared file ends up bundled into every page that transitively imports that file — not just the one page that actually needs it.
✅ Solution@next/bundle-analyzer visualizes what's really inside each shipped chunk; dynamic import() and Next.js's automatic per-route splitting then let only the page that needs a heavy dependency pay for it.
RecallThe analyzer finds the oversized box — code-splitting is what shrinks it.
🔥 Easy interview recall

Bundle analyzer = "a treemap of what's actually inside the JS you ship."

Think: one oversized rectangle in an otherwise normal page bundle is exactly the finding it exists to surface.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Importing a heavy client library at the top of a broadly-shared file is not harmless just because only one page uses it. That dependency gets bundled into every page that transitively imports that file, not only the one that needs it.

🔄 Likely Follow-up

"Does a Server Component's own dependencies count toward the client bundle at all?" No — a Server Component's imports, even heavy backend libraries, never reach the client bundle, since the component itself never ships its own JS to the browser. This is one of the Server Component model's real bundle-size benefits.

🎯 Say this in the interview — the exact lines to land

"I'd run @next/bundle-analyzer to see what's actually inside each chunk, find the disproportionately large dependency, and either dynamic-import() it so it only loads on the page that needs it, or confirm it can move into a Server Component instead so it never ships to the client at all."

  • @next/bundle-analyzer → visualizes what's really inside each shipped chunk.
  • A heavy import in a shared file → bundled into every page that imports that file.
  • Fix → dynamic import() the heavy dependency on the page that actually needs it.
  • Server Component dependencies → never reach the client bundle at all.
📖 Explanation ▾

@next/bundle-analyzer renders each shipped JS chunk as a treemap — box size roughly proportional to byte size — so an accidentally-large dependency stands out visually instead of hiding inside a build log full of file names.

Next.js already code-splits automatically per route, so one page's code doesn't ship inside another page's bundle by default. The gap that still needs manual attention is a dependency imported at module scope inside a file that many routes share — that import rides along into every one of them. A dynamic import() for a heavy client-only library, or deferring a below-the-fold interactive widget, keeps that cost scoped to the page that actually needs it.

Server Component imports never reach the client bundle at all — the component's code runs only on the server and never ships its own JS, so even a large backend-only dependency it uses costs nothing client-side.

💻 See the code ▾
JSX 
// ❌ top-level import in a widely shared file
import ChartLib from "heavy-chart-lib"; // ~180kb, used by one page

Every page that imports this file now ships heavy-chart-lib, whether it renders a chart or not.

JSX 
// ✅ dynamic import — only loads on the page that renders it
import dynamic from "next/dynamic";

const Chart = dynamic(() => import("heavy-chart-lib"));

The cost of heavy-chart-lib now lands only on the page that actually calls <Chart />.

🌍 Real-world example ▾

Lighthouse flags a surprisingly large JS payload on a page that doesn't look JS-heavy. Running the bundle analyzer on that page's chunk is usually how you find the real cause — often a library pulled in indirectly through a shared utility or layout file, not anything the page itself obviously imports.
