FromSql vs. FromSqlRaw — same-looking code, very different safety

How do you run raw SQL or a stored procedure in EF Core, and is it safe?

Why it matters ▾
💉 SQL injection
❗ ProblemLINQ can't express everything, and the moment you build a raw SQL string from user input, that input can rewrite the query.
✅ SolutionFromSql with an interpolated string turns every {value} into a database parameter, so input stays data — and FromSqlRaw is safe only when you pass parameters, never when you concatenate.
RecallInterpolated into FromSql = parameter. Concatenated into FromSqlRaw = injection.
🔥 Easy interview recall

FromSql($"… {x}") → parameterized ✅

FromSqlRaw("… {0}", x) → parameterized ✅

FromSqlRaw("…" + x) → pasted into SQL ❌

Think: FromSql sees the placeholders, so it makes parameters.FromSqlRaw only gets a finished string — it can't tell data from SQL.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

FromSql($"…{x}") and FromSqlRaw($"…{x}") look the same but are not. FromSql receives the interpolated string as a template and parameterizes each value; FromSqlRaw receives an already-built string, so the value is pasted straight into the SQL.

🔄 Likely Follow-up

"Can you add .Where() or .Include() after a stored-procedure call?" No — on SQL Server a stored procedure can't be wrapped as a subquery. Run it, call AsEnumerable() right after, and finish in memory. A plain SELECT can be composed with LINQ.

🎯 Say this in the interview — the exact lines to land

"I use FromSql with an interpolated string — EF Core turns each placeholder into a database parameter, so user input stays data and can't inject SQL. I never concatenate input into FromSqlRaw. For commands that return no rows I use ExecuteSql, and a stored procedure runs through the same calls."

  • FromSql($"…{x}") → each {x} becomes a parameter.
  • FromSqlRaw → only with {0} placeholders or DbParameters, never concatenation.
  • ExecuteSql → non-query commands, returns rows affected.
  • Stored procedure → can't be composed — add AsEnumerable() and filter in memory.
  • Raw SQL is the last resort — reach for it when LINQ can't express the query.
📖 Explanation ▾

FromSql (EF Core 7+) runs your SQL and maps the rows to entities. Pass the SQL as an interpolated string and EF Core turns every {value} into a database parameter — the value travels separately from the SQL text, so it can never change what the SQL means.

FromSqlRaw takes a plain string, so it can't tell where your values came from. It is safe only with {0}-style placeholders plus separate arguments, or DbParameter objects. Build the string yourself — with + or $"…" — and the input is pasted into the SQL: SQL injection.

ExecuteSql is the same idea for commands that return no rows (UPDATE, DELETE, a stored procedure) and gives back the rows affected. Raw queries must return every column the entity needs. A plain SELECT can still be composed with LINQ (EF Core wraps it in a subquery); a stored-procedure call cannot (SQL Server doesn't allow composing over it). Database.SqlQuery<T> covers results that aren't entities (arbitrary types from EF Core 8). See also Stored Procedures and Bulk Operations.

💻 See the code ▾
C# 
string name = input;
var users = db.Users
    .FromSql($"SELECT * FROM Users WHERE Name = {name}")   // ✅ {name} becomes a parameter
    .ToList();

The interpolated string is a template to FromSql — the value never becomes part of the SQL text.

C# 
var users = db.Users
    .FromSqlRaw("SELECT * FROM Users WHERE Name = '" + name + "'")   // ❌ input pasted into SQL
    .ToList();

var safe = db.Users
    .FromSqlRaw("SELECT * FROM Users WHERE Name = {0}", name)        // ✅ parameterized
    .ToList();

Same method, two outcomes — what matters is whether you concatenated.

C# 
int rows = db.Database.ExecuteSql($"UPDATE Users SET Active = 0 WHERE Id = {id}");   // ✅ command

var top = db.Orders
    .FromSql($"EXEC dbo.GetTopOrders {count}")   // stored procedure
    .AsEnumerable()                              // ✅ stop composing in SQL
    .Where(o => o.Total > 100)                   // filtered in memory
    .ToList();

ExecuteSql for commands; after a stored procedure, AsEnumerable() keeps EF Core from composing over it.

🌍 Real-world example ▾

A search box on an admin page was wired to FromSqlRaw with the text concatenated in. Typing ' OR '1'='1 returned every customer. Switching to FromSql with an interpolated string fixed it — no other change.
