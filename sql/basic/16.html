🔥 SQL · Basic · Must Know

DELETE removes some rows, TRUNCATE empties the table, DROP erases it

"What's the difference between TRUNCATE, DELETE and DROP?"

Why it matters ▾
✂️ DELETE
❗ ProblemRemoving only some rows (cancelled orders, old logs) needs a way to pick them.
✅ SolutionDELETE takes a WHERE, removes the matching rows, logs each row removed, and fires any delete triggers.
RecallDELETE = pick the rows, remove them.
🧹 TRUNCATE
❗ ProblemEmptying a big table row by row is slow and fills the log.
✅ SolutionTRUNCATE frees all the data pages at once and resets the identity counter.
RecallTRUNCATE = empty it fast, keep the table.
💥 DROP
❗ ProblemA table nobody needs still clutters the database after its rows are gone.
✅ SolutionDROP TABLE removes the data and the table definition itself.
RecallDROP = the table no longer exists.
🔥 Easy interview recall

DELETE → removes chosen rows, one by one

TRUNCATE → empties every row, fast

DROP → removes the table itself

Think: DELETE → rows, with WHERE TRUNCATE → all rows, identity restarts DROP → table gone

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"TRUNCATE can't be rolled back." In SQL Server it can — inside an explicit transaction, ROLLBACK brings the rows back, because TRUNCATE is logged (as page deallocations) rather than skipped.

🔄 Likely Follow-up

"Why does TRUNCATE fail on a table that another table references with a foreign key?" SQL Server refuses to truncate a table referenced by a foreign key, even when the child table is empty — use DELETE instead, or drop the foreign key first.

🎯 Say this in the interview — the exact lines to land

"DELETE removes rows one at a time and can filter with WHERE. TRUNCATE empties the whole table quickly and resets the identity counter. DROP removes the table itself — data, structure and indexes."

  • DELETE → use for some rows — takes WHERE, fires delete triggers, every row logged.
  • TRUNCATE → use to empty a table fast — no WHERE, no delete triggers, identity reset.
  • DROP → use when the table is no longer needed — structure goes too.
  • Rollback → in SQL Server, DELETE and TRUNCATE can both be rolled back inside a transaction.
  • Foreign key → blocks TRUNCATE on a referenced table; DELETE still works.
📖 Explanation ▾

DELETE is the careful one. It removes rows you pick with WHERE, writes a log record for every row, and fires any DELETE triggers. Without a WHERE it still removes every row, but one by one — slow on a big table. The identity counter keeps going from where it was.

TRUNCATE is the fast reset. It frees whole data pages instead of touching rows, so it is quick even on millions of rows. There is no WHERE, no delete triggers, and the identity counter restarts at its seed. It needs ALTER permission on the table, not just DELETE. DROP goes further and removes the table definition, its data and its indexes.

💻 See the code ▾
T-SQL 
DELETE FROM Orders WHERE Status = 'Cancelled';   -- ✅ only the matching rows
DELETE FROM Orders;                          -- all rows, logged one by one

DELETE chooses rows with WHERE; with no WHERE it still works row by row.

T-SQL 
BEGIN TRANSACTION;
TRUNCATE TABLE Orders;   -- all rows gone, identity reset
ROLLBACK;                -- ✅ rows are back (SQL Server)

In SQL Server a TRUNCATE inside an explicit transaction can be undone. Some other databases commit it implicitly.

T-SQL 
DROP TABLE Orders;   -- ❌ table, rows and indexes are all gone

DROP TABLE leaves nothing to query afterwards, so the next SELECT fails with an invalid object name.

🌍 Real-world example ▾

DELETE is taking chosen books off a shelf one by one. TRUNCATE is sweeping the whole shelf clean in one move and leaving the shelf. DROP is carrying the shelf out of the room.
