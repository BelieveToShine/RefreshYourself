Promises — once it settles, it never changes its mind

"What are the states of a Promise, and what happens to the rest of a .then() chain if one step throws?"

Why it matters ▾
  • Every async API you'll use — fetch, file I/O, timers wrapped for async/await — is built on this exact state machine, so a shaky answer here makes every later async answer shaky too.
  • "What happens if one .then() throws?" is one of the most common ways interviewers separate someone who's memorized the syntax from someone who can actually trace execution.
  • A real "why didn't my .catch() fire" or "why is my data an actual Promise object" bug almost always traces back to error propagation or resolution/adoption — exactly the two ideas this page exists to make click.
🔥 Easy interview recall

Promise = "a placeholder for a value that isn't ready yet, which settles into fulfilled or rejected exactly once."

Think: pending → fulfilled or rejected — whichever happens first wins, and it's final.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Calling resolve() or reject() more than once does nothing after the first call. A Promise's state is decided by whichever settle call fires first — every later resolve/reject call, even from the same executor, is silently ignored.

🔄 Likely Follow-up

"Does .finally() get the resolved value or the rejection reason?" No — its callback receives no arguments at all. It just runs for its side effect (closing a spinner, releasing a lock) and the original value or error passes through unchanged, unless .finally() itself throws.

🎯 Say this in the interview — the exact lines to land

"A Promise represents a value that will exist later. It starts pending and settles exactly once, into fulfilled or rejected, and never changes again. .then() handles the fulfilled path, .catch() handles rejection, and .finally() always runs. Because a rejection skips every remaining .then() until the next .catch(), and resolving with another Promise adopts that Promise's own eventual state, chaining reads as one flat, readable sequence instead of nested callbacks."

  • pending → fulfilled/rejected settles exactly once, never again.
  • A throw or rejection anywhere in the chain skips every remaining .then() until the next .catch().
  • Resolving with another Promise adopts that Promise's eventual state — you never end up with a Promise wrapping a Promise.
  • A Promise is a first-class value you can pass around and compose — a callback is just a function argument with no shared shape.
  • Chaining flattens nested callbacks into one readable, top-to-bottom sequence — that's the actual fix for deeply nested callbacks.
  • .finally() always runs, gets no value or reason, and passes the original result through.
📖 Explanation ▾

A Promise wraps a value that doesn't exist yet — the result of an async operation like a network call. It's created pending, and the function passed to new Promise((resolve, reject) => …) calls resolve(value) to move it to fulfilled or reject(reason) to move it to rejected. Once either happens, the Promise is settled — no later call to resolve/reject has any effect at all.

.then(onFulfilled, onRejected) registers callbacks for the two outcomes and always returns a new Promise. .catch(onRejected) is really just .then(undefined, onRejected) — a handler for the rejected path only. .finally(onFinally) runs no matter which way the Promise settled, receives no argument, and lets the original value or error pass straight through unless it throws its own error.

Because every .then() returns a new Promise, they chain — and the chain has one rule worth knowing cold: if a step throws, or returns a rejected Promise, every .then() after it is skipped, and control jumps straight to the nearest .catch() below it. Nothing between the throw and that .catch() ever runs.

A related, easy-to-miss rule is resolution (adoption): if resolve() is handed another Promise instead of a plain value, the outer Promise doesn't settle right away — it waits and adopts the inner Promise's own eventual state, fulfilling with its value or rejecting with its reason. You never end up holding a Promise whose value is itself a Promise.

💻 See the code ▾
JavaScript 
fetchUser(id)
  .then(user => {
    console.log("step 1: got user");        // ✅ runs
    return user.profile.avatarUrl;             // 🐛 throws — profile is undefined
  })
  .then(url => {
    console.log("step 2: got avatar url");  // ⏭ skipped — never reached
    return resizeImage(url);
  })
  .then(img => {
    console.log("step 3: got resized image"); // ⏭ skipped — never reached
    return img;
  })
  .catch(err => {
    console.log("caught:", err.message);    // ✅ runs — the throw lands here
  })
  .finally(() => {
    console.log("done");                    // ✅ always runs, no matter what
  });

Step 1 throws, so steps 2 and 3 are skipped completely — execution jumps straight to .catch(), and .finally() still runs last either way.

JavaScript 
getUser(id, (err, user) => {
  if (err) return handleError(err);     // error check, level 1
  getPosts(user.id, (err, posts) => {
    if (err) return handleError(err);   // error check, level 2
    getComments(posts[0].id, (err, comments) => {
      if (err) return handleError(err); // error check, level 3
      console.log(comments);
    });
  });
});

Nested callbacks ("callback hell") — the exact same three steps, but nesting one level deeper each time, with the same error check repeated at every level.

JavaScript 
getUserAsync(id)
  .then(user => getPostsAsync(user.id))
  .then(posts => getCommentsAsync(posts[0].id))
  .then(comments => console.log(comments))
  .catch(handleError);                          // ✅ one handler covers every step above

The same three steps, flat and top-to-bottom — one .catch() covers every step's errors, instead of one if (err) per nesting level.

JavaScript 
new Promise((resolve, reject) => {
  resolve(fetchUser(id));    // resolve() handed a Promise, not a plain value
}).then(user => {
  console.log(user);         // ✅ the actual user object, not a Promise
});

Resolution (adoption) — the outer Promise doesn't settle right away; it waits and adopts fetchUser(id)'s own eventual state instead of resolving to the Promise object itself.

🌍 Real-world example ▾

A checkout flow: charge the card, then send a receipt email, then update the order status. Written as nested callbacks, that's three levels deep with the same error check copy-pasted at every level. Written as a Promise chain, it's four flat lines — and if the card charge fails, every step after it is skipped automatically, landing in one .catch() at the end instead of three scattered ones.
