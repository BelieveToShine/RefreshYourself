Liskov Substitution Principle — substitutable, or just compiles?

What does the Liskov Substitution Principle actually require of a subclass?

Why it matters ▾
🤝 LSP
❗ ProblemA subtype like Square or ReadOnlyRepository compiles fine against its base type, but silently breaks a promise callers already rely on — Square changes Height behind Width's back, ReadOnlyRepository throws where Save() always worked — and nothing catches it until that code path actually runs.
✅ SolutionLSP requires every subtype to keep the base type's exact guarantees — preconditions that never get stricter, postconditions that never get weaker — so it's genuinely safe to substitute anywhere the base type is expected, not just wherever it happens to compile.
RecallLSP = a subtype can't break a promise the base type made.
🔥 Easy interview recall

LSP = "a subtype can't break a promise the base type made."

Think: if callers trust IRepository.Save() to work, a subtype that throws instead is not really substitutable — it just compiles like one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

LSP is not just the square/rectangle puzzle. The real violation is any subtype that compiles fine but throws or weakens behavior for a method the base type promised — like ReadOnlyRepository throwing on Save().

🔄 Likely Follow-up

"How would you actually fix the ReadOnlyRepository case?" Don't make it implement IRepository at all — split off a smaller IReadableRepository that only promises read operations; the fix is really the Interface Segregation Principle catching an LSP violation upstream.

🎯 Say this in the interview — the exact lines to land

"LSP says a subtype must be usable anywhere the base type is expected without surprising the caller — it can't demand stricter inputs than the base type accepted, and it can't deliver weaker guarantees, like throwing where the base type never would."

  • Substitutable means the subtype keeps every guarantee the base type made — not just that it compiles in the base type's place.
  • Preconditions → can't get stricter Postconditions → can't get weaker
  • Square : Rectangle breaks LSP because forcing Width and Height to stay equal changes behavior callers already relied on.
  • ReadOnlyRepository throwing on Save() is the same violation, just without the geometry.
  • Real fix → split into a smaller interface (e.g. IReadableRepository) instead of inheriting a contract you can't fully honor.
📖 Explanation ▾

Named after Barbara Liskov, the Liskov Substitution Principle says a subtype must be usable anywhere the base type is expected, without the caller noticing a difference. That's a stronger claim than "it compiles" — it means preconditions can't get stricter (the subtype can't refuse inputs the base type accepted), postconditions can't get weaker (the subtype can't deliver less than promised), and it can't throw for a case the base type handled fine.

Rectangle exposes independent Width and Height setters, so any caller can reasonably write rect.Width = 5; rect.Height = 10; and expect Area to become 50. Square overrides both setters to force them to stay equal — so setting Width silently changes Height too. The code still compiles; the behavior a caller was entitled to rely on is gone.

The same rule applies with no geometry at all: a ReadOnlyRepository that implements IRepository but throws NotSupportedException on Save() is exactly the same shape of violation. Code written against IRepository reasonably assumes Save() works — the "substitutable" subtype breaks that assumption at runtime instead of compile time, which is what makes LSP violations easy to ship and expensive to discover.

💻 See the code ▾
C# 
class Rectangle
{
    public virtual double Width { get; set; }
    public virtual double Height { get; set; }
    public double Area => Width * Height;
}

Rectangle r = new Rectangle();
r.Width = 5;
r.Height = 10;
Console.WriteLine(r.Area);   // ✅ 50 — matches what the caller expects

Any code written against Rectangle can set Width and Height independently and trust Area to follow.

C# 
class Square : Rectangle
{
    public override double Width
    {
        get => base.Width;
        set { base.Width = value; base.Height = value; }   // forces both equal
    }
    // Height overridden the same way
}

Rectangle sq = new Square();
sq.Width = 5;
sq.Height = 10;
Console.WriteLine(sq.Area);   // ❌ 100, not 50 — Height silently changed Width too

Square compiles as a Rectangle but silently breaks the caller's assumption — that's the LSP violation.

C# 
class ReadOnlyRepository : IRepository
{
    public Entity Get(int id) => _store[id];

    public void Save(Entity entity)
        => throw new NotSupportedException();   // ⚠️ breaks the promise
}

Same violation, no geometry — code written against IRepository reasonably assumes Save() works.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're implementing an interface that already has other implementations

Repositories, payment methods, file systems — any time code is written once against a base type and more than one class implements it, one implementation can quietly fail to honor part of the contract. A ReadOnlyRepository that throws on Save() is this exact situation. This is the real-code scenario you'll actually run into, far more often than a geometry puzzle.

RememberOne implementation can't fully honor the interface → LSP violation, no geometry required.
2 A subtype overrides a setter to keep two properties in sync

The classic interview opener: Rectangle lets Width and Height move independently, so a caller can set them separately and trust Area to match. Square overrides both setters to force them equal — the code still compiles, but that caller's Area no longer matches the values they set.

RememberSquare forcing Width == Height is the textbook LSP violation — it compiles, it just lies about Area.
3 A subtype override adds a stricter precondition, without throwing anything new

Candidates often assume an LSP violation always means something throws or breaks outright. A subtype whose override demands stricter input than the base type ever required is a violation too, even though nothing looks broken in a code review — a caller who wrote code against the base type's original, looser rules can start failing validation the base type never enforced.

RememberStricter preconditions break LSP just as much as weaker postconditions do.
🌍 Real-world example ▾

Scenario: a reporting job accepts any IRepository and calls Save() after transforming records — someone wires up a ReadOnlyRepository to reuse the same interface for a read-only data source.

What happens: it compiles and deploys fine, then throws NotSupportedException the first time that code path actually runs in production — nothing at compile time caught that this "repository" can't do half of what IRepository promises.
