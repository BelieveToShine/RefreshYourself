🧠 Deep Dive

A large Angular app isn't organized by what a file IS — it's organized by what a feature DOES

"How would you structure a large Angular application, and what actually causes a 'god component'?"

Why it matters ▾
  • A codebase where "checkout" logic is scattered across components/, services/, and models/ costs real time to navigate as it grows — this is what separates "knows Angular syntax" from "can actually run a large Angular codebase."
  • Comes up directly in senior/lead/architect interviews as "how would you structure a large app" or "what causes a god component."
  • Matters the moment more than one person — or more than one team — touches the same codebase, not only at huge scale.
🔥 Easy interview recall

Layer-based → group by file TYPE

Feature-based → group by what it DOES

Think: components/, services/, models/ → scattered checkout/, users/, dashboard/ → together

🗂️ Layer-based & 📁 Feature-based
⚠️ Common Trap

A god component isn't caused by one bad decision. It's built one small, individually-reasonable addition at a time — nobody stops to split logic into a service or break the UI apart as the feature keeps growing.

🔄 Likely Follow-up

"If feature-based is generally better, is layer-based (components/, services/) always wrong?" No — a small app, or a genuinely small shared/core layer at the top level for truly generic code, can still use it fine. The real mistake is applying it to feature-specific code as the app keeps growing.

🎯 Say this in the interview — the exact lines to land

"I'd organize by feature — folders named for what a feature does, like checkout/ or users/, each holding its own components, services, and models — plus a deliberately small shared/core layer for truly generic code. Components stay focused on presentation and orchestration; business logic, API calls, and validation rules live in services. A god component is almost always slow, incremental buildup, not one bad decision — the fix is splitting things out as the feature grows, not a one-time rewrite."

  • Feature-based → group folders by what a feature does, not by file type.
  • Components → presentation and orchestration only; business logic and validation rules belong in services.
  • Shared/core layer → deliberately small and truly generic, never feature-specific logic.
  • Dependency direction → features never import directly from each other; shared code goes through core.
  • God component → caused by slow, incremental buildup, not one bad decision — fix by splitting as you go.
  • Cross-cutting concerns (auth, logging, errors) → centralize via an interceptor and a global ErrorHandler, not per-feature reimplementation.
📖 Explanation ▾

Layer-based folders group by superficial similarity — every service sits together in services/ whether or not those services have anything to do with each other. Feature-based folders keep everything one piece of work needs physically close together instead, so most current large-scale Angular guidance favors it — it scales better with app size and team count, because it's easier to find, reason about, and eventually remove a whole feature.

Inside a feature, a component should stay focused on what's on screen and wiring user interaction to method calls — the actual business logic (calculations, complex rules, data transformation) belongs in a service instead. API calls follow the same rule: they live in a dedicated service per resource, never directly inside a component, so the component never needs to know HTTP specifics and the same API logic can be reused and tested on its own. Validation follows it too — the actual rules about what makes data valid belong in a shared service or a reactive-forms validator function, not reimplemented inside every component that happens to need the same check.

A genuinely reusable component (a button, a modal, a data table) belongs in a clearly designated shared location every feature can depend on — but only what's truly generic, never something that just looks reusable today. That discipline also sets the dependency direction for the whole codebase: shared/core code never depends on feature code, and features generally shouldn't import directly from each other — if two features need the same thing, it gets extracted into shared instead. Cross-cutting concerns (auth, logging, error handling) get centralized the same way, at a small number of integration points — an HTTP interceptor, a global ErrorHandler — rather than every feature reimplementing its own version.

Everything checkout owns sits in one folder — easy to find, easy to remove as a whole feature.

TS 
// components/checkout.component.ts
// services/checkout.service.ts   ← scattered across unrelated services
// models/checkout.model.ts       ← scattered across unrelated models

Same three files — now three unrelated folders to open just to see one feature's whole picture, and it only gets worse as more features pile in.

🌍 Real-world example ▾

Feature-based is organizing a kitchen by MEAL. Everything for tonight's pasta dish — sauce, noodles, the recipe card — sits together in one basket. Layer-based is organizing by INGREDIENT TYPE across the whole pantry instead: all sauces together regardless of which of 50 different dishes they belong to, all noodles together the same way. The second feels tidy in the abstract, but gathering everything for one dish now means walking to five different shelves every single time.
