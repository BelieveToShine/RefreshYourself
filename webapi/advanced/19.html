⭐ Web API · Advanced · Should Know

An API is slow — which lever do you pull first?

"What would you do to improve the performance of a REST API?"

Why it matters ▾
🗂️ HTTP Caching
❗ ProblemA client re-fetching the same rarely-changing resource makes a full round trip to your server every single time, even when nothing actually changed.
✅ SolutionETag/Cache-Control/Last-Modified headers let the client, or a CDN/reverse proxy in front of your server, skip re-fetching unchanged data entirely — the request may never even reach you.
RecallThe cheapest request is the one that never reaches your server.
🗜️ Response Compression
❗ ProblemA large JSON or text payload sent uncompressed spends extra time just moving bytes over the wire, on both slow and fast connections.
✅ Solutiongzip/brotli compression middleware shrinks the payload before it leaves the server — most valuable for larger response bodies, less so for tiny ones.
RecallCompression shrinks the bytes, caching skips the trip entirely.
📄 Pagination & Field Selection
❗ ProblemAn endpoint that returns an unbounded result set, or the full entity graph when a client only needed three fields, moves far more data than anyone actually asked for.
✅ SolutionAlways page a large result set, and return only the fields a client actually needs instead of the full entity.
RecallNever return more rows, or more fields, than were asked for.
📦 Avoid Chattiness
❗ ProblemMany small round trips to render one screen cost more in cumulative network latency than one combined call would, even if each individual call is itself fast.
✅ SolutionA batch/bulk endpoint turns N requests into one, where the client's actual access pattern allows it.
Recall20 small round trips can cost more than 1 combined one.
🚦 Rate Limiting
❗ ProblemWithout a limit, one noisy or misbehaving client can consume a disproportionate share of capacity and degrade the API for every other client.
✅ SolutionA rate limit caps what any single client can consume, so performance stays predictable for everyone else — see Rate Limiting.
RecallRate limiting protects everyone else's performance, not just yours.
🔌 Reuse Outgoing Connections
❗ ProblemWhen this API itself calls other services, creating a new HttpClient per call can exhaust available sockets under load instead of reusing them.
✅ SolutionIHttpClientFactory manages and reuses the underlying connections for you — see IHttpClientFactory.
RecallA new HttpClient per call risks exhausting sockets.
🔁 Avoid N+1 at the Data Layer
❗ ProblemThe API layer inherits whatever inefficiency sits underneath it — one query to fetch a list, then one more query per row to fetch each row's related data.
✅ SolutionLoad related data in the same query (eager loading, a join, a projection) instead of once per row — see Beyond N+1.
RecallNo amount of caching fixes an N+1 query underneath it.
⏳ Async I/O for Downstream Calls
❗ ProblemA request thread blocked waiting on a slow downstream dependency can't do anything else while it waits, which limits how many requests the API can serve at once.
✅ Solutionasync/await on the downstream call frees that thread to serve other requests while the wait is in progress.
RecallAsync I/O frees the thread, it doesn't make the downstream call faster.
🔥 Easy interview recall

🗂️ Caching → the request never reaches your server at all

🗜️ Compression → shrink the bytes that do have to travel

📄 Pagination / fields → never return more than was asked for

📦 Avoid chattiness → one batch call beats twenty small ones

Also on the list: 🚦 rate limiting → protects everyone else's performance 🔌 IHttpClientFactory → reuse outgoing connections 🔁 avoid N+1 → fix it at the data layer, not with more cache ⏳ async I/O → free the thread while a downstream call waits

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Caching a slow endpoint doesn't fix the slow query underneath it. It just hides the cost until the cache misses or gets invalidated — the real fix is making the thing being cached fast in the first place.

🔄 Likely Follow-up

"Of all of these, which would you actually reach for first?" HTTP caching almost always, because a cache hit means the request never even reaches your server — compression and pagination/field selection come right after, since both are cheap, broadly applicable wins.

🎯 Say this in the interview — the exact lines to land

"I'd start with HTTP caching — ETag/Cache-Control — since a cache hit never even reaches my server, then compression and pagination with field selection to cut payload size. Next I'd reduce chattiness with a batch endpoint where the access pattern allows it, add rate limiting so one client can't degrade everyone else, reuse outgoing connections with IHttpClientFactory, fix any N+1 queries at the data layer, and use async I/O so a slow downstream call doesn't hold a request thread hostage."

  • Caching → the cheapest win, the request may never reach the server.
  • Compression → shrinks the bytes still worth sending.
  • Pagination & field selection → never return more than was asked for.
  • Avoid chattiness → a batch endpoint turns N round trips into one.
  • Rate limiting → protects performance for every other client, not just yours.
  • N+1 & async I/O → fix the data layer, free the thread while it waits.
📖 Explanation ▾

The highest-leverage fixes are the ones that avoid work entirely rather than doing the same work faster. HTTP caching is the cheapest because a correctly cached response can be served by the client's own cache, or by a CDN/reverse proxy sitting in front of the API, without the request ever reaching application code. Compression and pagination/field selection are the next cheapest — both cut down how much data has to move, whether or not a cache is involved.

Chattiness is a design-level fix: a client making twenty small calls to render one screen pays twenty round trips' worth of network latency, even if the server answers each one instantly — a single combined or batch endpoint removes that overhead where the access pattern allows it. Rate limiting is less about speeding up a single request and more about protecting everyone else's requests from one noisy client. The remaining items — reusing outgoing connections, fixing N+1 queries, and using async I/O for downstream calls — matter most once the API itself is calling other services or a database, which is why they're covered in depth on their own dedicated pages rather than repeated here.

HTTP/2 (which multiplexes many requests over one connection) or gRPC can reduce overhead for internal service-to-service calls compared to repeated HTTP/1.1 connections, but for most public-facing REST APIs this is a smaller lever than the ones above — worth mentioning, not worth leading with.

💻 See the code ▾
C# 
app.MapGet("/catalog/{id}", (int id, HttpContext ctx) =>
{
    var item = Catalog.Get(id);
    ctx.Response.GetTypedHeaders().ETag =
        new($"\"{item.Version}\"");               // ✅ client can send If-None-Match next time
    ctx.Response.GetTypedHeaders().CacheControl =
        new() { Public = true, MaxAge = TimeSpan.FromMinutes(5) };
    return Results.Ok(item);
});

A matching If-None-Match on the next request turns this into a 304 Not Modified — no body sent at all.

C# 
builder.Services.AddResponseCompression(opts =>
{
    opts.EnableForHttps = true;                     // ✅ brotli/gzip over HTTPS too
    opts.Providers.Add<BrotliCompressionProvider>();
});
// ...
app.UseResponseCompression();                       // ✅ must run before writing the response

Most valuable on larger JSON/text bodies — skip it for small, already-tiny responses where it's not worth the CPU.

C# 
// ❌ Twenty separate calls — one network round trip each
foreach (var id in ids)
    results.Add(await client.GetAsync($"/items/{id}"));

// ✅ One batch call — one round trip for all of them
var batch = await client.PostAsJsonAsync("/items/batch", ids);

A batch endpoint only helps where the client's own access pattern actually needs many related items at once — don't add one nobody will call.

🧭 Use Cases — recognize these when they happen to you ▾
1 A mobile client re-fetches the same rarely-changing catalog endpoint every time a screen opens

Most of those re-fetches become cheap 304 Not Modified responses once the endpoint sets ETag/Cache-Control — the data hasn't changed, so neither client nor server does the full work again.

RememberA re-fetch of unchanged data should cost almost nothing.
2 A dashboard makes 20 small API calls to render one screen

Each of those 20 calls might be individually fast, but the cumulative network latency of 20 round trips adds up — a combined/batch endpoint that matches how the dashboard actually consumes the data replaces all 20 with one.

RememberLatency from many small calls adds up even when each call is fast.
3 Someone proposes adding a cache in front of an endpoint that's slow because of an N+1 query

A cache in front of a slow query only hides the cost until it misses or gets invalidated — the query is still just as slow underneath. Fix the N+1 at the data layer first; add caching on top of that if it's still needed.

RememberCaching a slow query doesn't make the query fast.
🌍 Real-world example ▾

A product-listing endpoint gets slower as traffic grows. The fastest wins come first: add ETag/Cache-Control so repeat requests for the same catalog page cost almost nothing, enable compression on the JSON response, and make sure the endpoint is paginated with only the fields the list view needs — not the full product entity. Only after those are in place is it worth looking at whether the data access behind the endpoint itself has an N+1 query to fix.
