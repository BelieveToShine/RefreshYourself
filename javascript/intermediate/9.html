Event Delegation — one listener instead of a thousand

"A list has 10,000 rows and every row needs a click handler — do you attach 10,000 listeners, or something smarter?"

Why it matters ▾
🔁 One listener per item
❗ ProblemA list with thousands of rows needs every row's click to trigger the same handler.
✅ SolutionLoop over every row and call addEventListener directly on each one — it works, but that's one listener per row sitting in memory, and any row added after the loop runs gets no handler at all.
RecallOne listener per item = simple to write, doesn't scale, misses rows added later.
🔀 Event delegation
❗ ProblemAttaching a separate listener to every row is a real memory/setup cost that shows up in code review, and it silently misses any row appended after that loop already ran.
✅ SolutionPut one listener on the stable parent and let bubbling carry the click up to it, then check event.target (usually with closest()) to find which row was actually clicked — covering every row that exists now or gets added later.
RecallEvent delegation = one listener on the parent, event.target tells you which child.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

event.target is not the same element the listener is attached to. Inside a delegated handler, event.target is whichever child (or grandchild) actually got clicked, while event.currentTarget is always the parent the listener sits on — checking the wrong one is why closest() shows up in almost every delegation example.

🔄 Likely Follow-up

"Does delegation work for every event type?" No — a few events, like focus and blur, don't bubble at all; use their bubbling equivalents, focusin and focusout, to delegate those instead.

🎯 Say this in the interview — the exact lines to land

"I attach one click listener to the parent, and inside it check event.target — usually with closest() — to figure out which child was actually clicked. That covers every existing row plus any added later, with a single handler instead of one per item."

  • One listener on the parent → covers every child, present and future.
  • Bubbling → the click travels up from the child to the parent on its own.
  • event.target → the child actually clicked event.currentTarget → the parent holding the listener
  • Dynamically added children → no re-binding needed, the parent was already listening.
  • Performance win → one handler instead of thousands, real memory/setup savings.
  • Watch for non-bubbling events → focus/blur need focusin/focusout instead.
📖 Explanation ▾

Delegation exists for one reason: attaching a handler to every child doesn't scale. A list with 10,000 rows would mean 10,000 separate listeners sitting in memory, and every one of them has to be set up individually. Instead, you attach a single listener to the stable parent that contains all of them, and let bubbling — the same mechanic from the DOM events page — carry the click up to that one listener automatically.

Inside that one handler, event.target tells you exactly which child (or grandchild) was actually clicked, so the parent's listener can react as if it were sitting on that specific row — usually by calling event.target.closest('.list-item') to walk up from whatever was clicked (an icon, a span, plain text) until it finds the row itself. This is also what makes dynamically-added elements a genuine practical win, not just a performance trick: a row appended to the list an hour after the page loaded was never individually wired up, but it's still inside the parent, so the exact same listener already covers it — nothing to remember to re-bind.

Delegation isn't free of sharp edges. Mixing up event.target and event.currentTarget is the most common one. A handful of events — focus, blur — never bubble at all, so they can't be delegated the normal way; the fix is to listen for their bubbling equivalents, focusin/focusout, instead. And on a deeply nested UI, the target-matching logic itself (walking up through several unrelated layers to find the right ancestor) can get genuinely complex enough that it's worth asking whether delegation is still the simplest option for that particular piece of markup.

💻 See the code ▾
JavaScript 
const items = document.querySelectorAll('.list-item'); // 10,000 of them

// ❌ one handler per row — 10,000 listeners created and held in memory
items.forEach(item => {
  item.addEventListener('click', () => handleClick(item));
});
// any row added after this loop runs has NO handler at all

10,000 closures, 10,000 listeners — and a row added later is silently missed unless this whole loop runs again.

JavaScript 
const list = document.querySelector('.list-container');

// ✅ ONE listener, no matter how many rows exist now or get added later
list.addEventListener('click', (event) => {
  const item = event.target.closest('.list-item');
  if (!item) return;              // click landed outside any row
  handleClick(item);
});

closest() walks up from whatever was actually clicked until it finds the row itself — event.target alone might be a child of the row, not the row.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your list, table, or menu renders thousands of items

This is the #1 scenario you'll actually run into: infinite scroll, live search results, a todo list — wiring up a handler per item would mean thousands of listeners sitting in memory. Put one listener on the parent instead and let bubbling carry each click up to it.

RememberMany dynamic rows → delegate, don't loop and bind.
2 A row gets appended to the list after the page already loaded

A row appended after the page loaded was never individually wired up, but it's still inside the parent — the same delegated listener already catches its clicks, with nothing extra to bind.

RememberAdded later → still caught, nothing to re-bind.
3 Inside the handler, you reach for the wrong one — the child clicked, or the parent holding the listener

event.target is whichever child (or grandchild) actually got clicked, while event.currentTarget is always the parent the listener sits on — checking the wrong one is why closest() shows up in almost every delegation example. A common trap — candidates often assume they're the same element.

🌍 Real-world example ▾

Your app has an infinite-scroll comment feed, and new comments get appended to the DOM every time the user scrolls further down. If each comment's reply/delete buttons were wired up individually as it rendered, every newly-loaded batch would silently need the same setup repeated. One delegated listener on the feed container already covers every comment that exists now or gets added later, with nothing extra to remember.
