🔥 Must Know

RxJS in production — the same handful of mistakes, over and over

"A subscription keeps running after the user navigates away — how do you actually find and fix the leak?"

Why it matters ▾
🎯 Match the Symptom, Not the Habit
❗ ProblemThe most common wrong turn is reaching for switchMap as the default fix for any "stale or duplicate results" symptom, without checking which actual relationship is happening — the wrong operator can drop a result that should have run, or run duplicates that should have been ignored.
✅ SolutionEach higher-order operator fixes one specific relationship: switchMap cancels an older race, concatMap waits its turn for a sequential dependency, exhaustMap ignores extra clicks mid-flight, and forkJoin waits for a fixed, known batch — naming the real relationship first is what points to the right one.
RecallName the relationship first (race / sequence / duplicate click / fixed batch) — the operator follows automatically.
🔥 Easy interview recall

Stale / out-of-order results → switchMap

Sequential dependency → concatMap

Prevent duplicate submits → exhaustMap

Fixed parallel batch → forkJoin

Think: Subscription still running after navigation → missing takeUntilDestroyed() Stream goes dead after one error → catchError on the wrong (outer) level

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

switchMap is not the universal fix for "prevent duplicate or stale results." It's right when a newer request should cancel an older one of the same kind — search, live status polling — but wrong for a duplicate submit click, where cancelling the in-flight submission to start a new one is worse than just ignoring the click; that's exactly what exhaustMap is for.

🔄 Likely Follow-up

"If takeUntilDestroyed() is the modern default for subscription cleanup, is there ever still a reason to use the async pipe instead?" Yes — the async pipe means the component never even needs a manual .subscribe() call in the first place, so there's nothing to clean up at all. takeUntilDestroyed() matters specifically for a manual subscription that has to exist because the component needs to DO something in response to each emission, not just display a value.

🎯 Say this in the interview — the exact lines to land

"Real RxJS production bugs are almost always one of three things: the wrong higher-order operator for how two requests actually relate, a catchError sitting around the outer stream instead of the inner call that can fail, or a subscription with no completion or cleanup mechanism — matching the symptom to the cause is the actual skill."

  • switchMap → a newer request should cancel an older one of the same kind — search, live status, any race.
  • concatMap → strict order, one at a time — the next call waits for the current one to finish.
  • exhaustMap → ignore extra clicks while one is in flight — never cancel or duplicate a submission.
  • forkJoin vs. mergeMap → a fixed, known batch vs. an ongoing stream of parallel work.
  • Leaked subscription → takeUntilDestroyed(), or the async pipe if it's just a displayed value.
  • Stream goes dead after one error → catchError was on the outer stream, not the inner call.
📖 Explanation ▾

Real production RxJS bugs almost never need a new concept — they trace back to one of three familiar causes: the wrong higher-order operator for how two requests relate, a misplaced catchError, or a subscription with no completion or cleanup mechanism. A search box debounced with debounceTime and then piped through switchMap fixes two different problems at once — debounce cuts down how often a search fires at all, and switchMap guarantees that if a couple still fire close together, only the newest one's result ever wins. That's the same relationship behind any "old request vs. new request" race, not just search boxes. concatMap is the fix instead when calls are sequential and order-dependent — the next one doesn't start until the current one completes. exhaustMap solves a different shape entirely: dropping extra clicks while a submission is still in flight, rather than cancelling it (switchMap) or running duplicates in parallel (mergeMap). For a fixed, known batch that all need to finish and combine, forkJoin is the tool — mergeMap is for an ongoing stream still mapping new values into parallel work.

A stream that goes silent after one error almost always has catchError in the wrong spot — wrapped around the whole outer, long-lived stream instead of the one inner request that can actually fail. Moving it inside, around just the inner Observable, means one bad attempt gets swallowed and the outer subscription keeps living for the next value.

A subscription that keeps running after its component is gone is missing one of three protections: it isn't a one-shot call that already completes on its own, it isn't piped through takeUntilDestroyed() (or the older takeUntil(destroy$) pattern), and it isn't consumed through the async pipe instead of a manual subscribe. Any manual .subscribe() on a long-lived Observable with none of the three is the leak — checking each subscription against that short list is the actual diagnostic move.

💻 See the code ▾
TypeScript 
this.searchTerm$.pipe(
  debounceTime(300),                          // wait for typing to pause
  distinctUntilChanged(),                     // skip if the value didn't actually change
  switchMap(term => this.api.search(term))    // ✅ cancels the previous in-flight search
).subscribe(results => this.results = results);

debounceTime cuts down how often a search fires at all; switchMap guarantees only the latest one's result ever wins if a couple still fire close together.

TypeScript 
this.data$.pipe(
  takeUntilDestroyed()   // ✅ auto-completes on component destroy
).subscribe(data => this.process(data));

The unguarded version — the same line with no takeUntilDestroyed(), no takeUntil(destroy$), and no async pipe — keeps running silently after the component is gone; this line is the fix, not an optional extra.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two search calls fire close together and the screen ends up showing the older result

This is the #1 scenario you'll actually run into: without switchMap, nothing tells the stream which request should win, so an older call that happens to resolve after a newer one silently overwrites the fresh result on screen. Naming this as a race between two calls of the same kind is what points straight at switchMap.

RememberNo switchMap on a race → whichever response lands last wins, even the older one.
2 One inner API call fails and the whole stream goes permanently silent afterward

catchError wrapped around the whole outer, long-lived stream instead of just the inner request means one failed attempt terminates the entire subscription — no more values ever come through, even though nothing else was wrong. Moving catchError inside, around just the inner Observable, lets one bad attempt get swallowed while the outer subscription keeps living.

RemembercatchError on the outer stream kills everything after one failure — move it to the inner call.
3 A component keeps polling in the background long after the user has navigated away

A manual .subscribe() with no takeUntilDestroyed() (or the older takeUntil(destroy$)), and no async pipe instead, keeps running after its component is gone. It shows up later as unexplained extra API load that scales with how much people navigate around, not with how many people are actually looking at the page.

RememberManual subscribe with no takeUntilDestroyed()/async pipe outlives its component silently.
🌍 Operational scenario ▾

A component polls order status every 5 seconds inside ngOnInit, subscribing manually with no cleanup. Users navigate away from the order page and back several times over a session, and each visit starts a brand-new polling subscription that never stops — every one of them still hitting the API independently in the background. In production this shows up as unexplained extra API load that scales with how much people navigate around the app, not with how many people are actually looking at the order page right now.

The direct fix: pipe the polling Observable through takeUntilDestroyed() so each subscription is guaranteed to stop the moment its component is destroyed — then confirm in the network tab that request volume tracks active viewers again, not navigation history.
