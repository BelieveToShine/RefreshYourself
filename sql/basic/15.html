BEGIN is the only thing standing between you and autocommit.

What do BEGIN TRANSACTION, COMMIT, ROLLBACK, and a SAVEPOINT actually do, mechanically?

Why it matters ▾
  • Comes up any time reliability of a multi-step write is discussed — a very common, very practical SQL question.
  • Explains a real production bug pattern: a multi-step update that "half-applied" because nothing was ever wrapped in an explicit transaction.
  • A near-guaranteed follow-up the moment ACID or "atomicity" comes up in an interview.
🔥 Easy interview recall

BEGIN → starts the transaction

COMMIT → locks in every change

ROLLBACK → undoes everything since BEGIN

SAVEPOINT → marks a point to roll back to

Think: no BEGIN? Every statement is already its own transaction — committed the instant it succeeds.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"I'm doing a transaction, so it's safe until I say COMMIT." Without an explicit BEGIN TRANSACTION, autocommit is on and each statement is already its own separate transaction — committed the instant it succeeds, with no way to roll an earlier one back once a later statement fails.

🔄 Likely Follow-up

"You run three INSERT statements back to back without ever calling BEGIN TRANSACTION, and the third one fails. What's the state of the first two?" Already committed, permanently — under autocommit each one was its own independent transaction; only wrapping all three in one explicit BEGIN…COMMIT/ROLLBACK would have made them atomic together.

🎯 Say this in the interview — the exact lines to land

"BEGIN TRANSACTION turns off autocommit and starts grouping statements together. COMMIT makes every change since then permanent, ROLLBACK undoes all of them, and a SAVEPOINT lets me roll back to just one point inside that transaction instead of losing the whole thing."

  • Autocommit → the default — every statement is its own transaction unless BEGIN says otherwise.
  • COMMIT → makes every change since BEGIN permanent and visible to other sessions.
  • ROLLBACK → undoes everything back to BEGIN — or back to a named SAVEPOINT instead.
  • SAVEPOINT → an intermediate marker — lets one later step get undone without losing earlier work.
📖 Explanation ▾

Most database engines start in autocommit mode: every individual statement is its own implicit transaction, committed the instant it succeeds. BEGIN TRANSACTION (or BEGIN TRAN) turns that off — everything that runs afterward becomes part of one larger unit, until an explicit COMMIT or ROLLBACK ends it.

COMMIT makes every change made since BEGIN permanent and visible to other sessions — exactly when another session can see it depends on the isolation level in play, covered on its own page (see Isolation Levels). ROLLBACK does the opposite: it undoes everything since BEGIN, as if none of it had ever run.

A SAVEPOINT doesn't commit or undo anything by itself — it just names a point inside the still-open transaction. Naming that point in a ROLLBACK TO SAVEPOINT undoes only the work done after it; everything before the savepoint, inside that same transaction, is left standing.

💻 See the code ▾
SQL 
BEGIN TRANSACTION;

UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;   -- Statement 1

SAVEPOINT AfterDebit;   -- marks this point

UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 999;   -- ❌ Id 999 doesn't exist

ROLLBACK TO SAVEPOINT AfterDebit;   -- undoes only the failed credit

COMMIT;   -- the debit from Statement 1 is now permanent

Rolling back to the savepoint discards only the failed credit — the earlier debit inside the same transaction survives and gets committed.

SQL 
INSERT INTO Orders (Id) VALUES (1);   -- ✅ commits immediately, its own transaction
INSERT INTO Orders (Id) VALUES (2);   -- ✅ commits immediately, its own transaction
INSERT INTO Orders (Id) VALUES (2);   -- ❌ duplicate key, this one fails
-- No BEGIN TRANSACTION was ever called.
-- Rows 1 and 2 are already permanent — there is nothing left to roll back.

With no explicit BEGIN TRANSACTION, autocommit was on the whole time — the first two inserts were never part of anything the third one could pull down with it.

🌍 Real-world example ▾

A transaction is a rough draft you can still throw away entirely — nothing in it is final until COMMIT. A SAVEPOINT is a checkpoint in a video game: dying sends you back to the last checkpoint, not all the way back to the start of the level.
