⭐ Web API · Advanced · Should Know

One API, three very different clients — who gets what shape?

"How would you design an API that needs to serve web, mobile, and partner-integration clients well?"

Why it matters ▾
🖥️ Web SPA
❗ ProblemNarrowed onto mobile's sparse fieldset or partner's frozen contract, a web SPA loses the full, richer shape its screens actually render.
✅ SolutionIt requests the full shape straight off the shared core contract — many small, chatty calls are fine since it isn't bandwidth or battery constrained.
RecallWeb SPA = full shape, chatty is fine.
📱 Mobile App
❗ ProblemGiven the same full response as the web SPA, a mobile app pays in bandwidth and battery for fields its screens never render.
✅ SolutionSparse fieldsets (?fields=id,total), or a BFF once needs diverge further, let it request a narrower shape and make fewer, larger calls off the same endpoint.
RecallMobile = sparse fields, fewer/bigger calls.
🤝 Partner Integration
❗ ProblemHeld to the same shape your team can redeploy anytime, a partner integration breaks silently on your next release — it can't redeploy alongside you.
✅ SolutionA versioned, documented contract (a frozen v1 route) stays stable behind a deprecation window, so their code keeps working on their own schedule.
RecallPartner = stable, versioned contract.
🔥 Easy interview recall

Web → full shape, chatty is fine

Mobile → sparse fields, fewer/bigger calls

Partner → stable, versioned contract

Think: Web asks for everything. Mobile asks for less. Partner asks for a promise that won't move under them.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Just return everything, it's safer" is backwards. A maximal one-size-fits-all response bloats mobile's payload and still doesn't give a partner the compatibility guarantee they actually need — ask what THIS consumer needs, not what every consumer might ever want.

🔄 Likely Follow-up

"If a BFF layer exists for the mobile app, doesn't that mean maintaining two APIs instead of one?" Yes, genuinely — that's a real cost, which is why a BFF is a deliberate trade-off for cases where client needs diverge enough to justify it, not a default pattern to reach for on every project; sparse fieldsets and good API design on one shared contract are often enough without a separate BFF at all.

🎯 Say this in the interview — the exact lines to land

"I'd design one core API contract, let sparse fieldsets handle payload size for mobile, put a BFF in front only if a client's shape genuinely diverges, and hold partner integrations to strict versioning and deprecation discipline since they can't redeploy alongside us."

  • Web → requests the full shape, chatty requests are fine for it.
  • Mobile → sparse fieldsets (?fields=id,name,total) keep its payload small.
  • Partner integrations → strict versioning and deprecation discipline matter most here — they can't redeploy alongside you.
  • BFF (Backend-for-Frontend) → a deliberate trade-off, maintaining two APIs, only when a client's needs genuinely diverge.
  • The real discipline → ask what THIS consumer needs, never expose a maximal shape "to be safe."
📖 Explanation ▾

A single API contract often has to serve genuinely different-shaped consumers. A web SPA is rich and can make many small requests — it's tolerant of chattiness. A mobile app is constrained on bandwidth and battery, so it wants fewer, larger requests and cares about payload size. A partner integration needs a stable, well-documented, versioned contract it can build against independently — it's often less latency-sensitive, but far more compatibility-sensitive, since it can't just redeploy alongside your own teams.

Field selection (?fields=id,name,total) is the cheapest fix: it lets a mobile client request only what it needs while a web client still requests the full shape, off the exact same endpoint. A BFF goes further — a thin, client-specific aggregation layer shapes or combines calls the way one specific client needs, without forcing the shared core domain API to know about every consumer's UI. It's a real second thing to build and maintain, so it earns its place only when a client's needs have genuinely diverged, not as a default layer added up front.

Versioning discipline matters most for the partner column specifically: your own web and mobile teams can redeploy the moment the API changes, but a partner's code keeps running against whatever shape you shipped last, on their own schedule — see Backward Compatibility for how that deprecation window actually works.

💻 See the code ▾
C# 
public class OrdersController : ControllerBase
{
    [HttpGet("orders/{id}")]
    public IActionResult GetOrder(int id, string? fields)
    {
        var order = _repo.GetOrder(id);
        if (string.IsNullOrEmpty(fields))
            return Ok(order);              // ✅ web: the full shape

        var shape = FieldSelector.Apply(order, fields); // mobile: ?fields=id,total
        return Ok(shape);
    }
}

Same endpoint, two payload sizes — the fields query string is how a mobile client opts into the smaller shape without a second endpoint.

C# 
public class MobileOrdersBffController : ControllerBase
{
    private readonly IOrdersApi _orders;      // calls the shared core API
    private readonly IShippingApi _shipping;

    [HttpGet("mobile/orders/{id}")]
    public async Task<IActionResult> Get(int id)
    {
        var order = await _orders.GetAsync(id);
        var eta = await _shipping.GetEtaAsync(id);
        return Ok(new { order.Id, order.Total, eta }); // ✅ shaped just for this screen
    }
}

The BFF calls the shared core API on the mobile app's behalf — the core domain API never has to know a mobile client exists at all.

C# 
[ApiController]
[Route("api/v1/orders")]        // ✅ partner builds against this, frozen
public class OrdersV1Controller : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult Get(int id) => Ok(_repo.GetOrderV1(id));
}

[Route("api/v2/orders")]        // new shape lives alongside v1
public class OrdersV2Controller : ControllerBase { /* ... */ }

v1 keeps running unchanged while v2 ships — a partner is never forced onto a new shape on your release schedule.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your mobile app is fetching orders over a slow, metered connection

The full order object carries fields the mobile screen never renders — every extra byte costs real battery and data over a slow connection. Sparse fieldsets fix that off the exact same endpoint mobile already calls, no second API needed. This is the #1 scenario you'll actually run into.

RememberSlow connection + unused fields → sparse fieldsets, not the full shape.
2 A partner is building their own integration against your API, on their own schedule

Your own web and mobile clients redeploy the moment the API changes — a partner's code doesn't. Freezing api/v1/orders and shipping any new shape as a separate api/v2/orders keeps the partner's integration running unchanged until they choose to move, inside a real deprecation window.

RememberPartner can't redeploy with you → freeze the version, don't move it under them.
3 Your web dashboard's screen needs a richer, more deeply-nested response than mobile or the partner ever ask for

The dashboard renders nested detail mobile's screen has no room for and a partner's integration has no use for — it just asks the same endpoint for the full shape, and many small, chatty calls are fine since it isn't fighting bandwidth or battery limits the way mobile is.

RememberRicher UI, no bandwidth constraint → request the full shape, chattiness is fine.
🌍 Real-world example ▾

Your product ships one API behind a web dashboard, and now wants a native mobile app alongside it, plus a partner who wants raw API access to build their own integration. Keep one core contract as the source of truth. Add sparse fieldsets for mobile first — it's cheap and usually enough. Only reach for a BFF if mobile's shape keeps diverging further than fieldsets can comfortably cover. Freeze a versioned contract for the partner from day one, because they can't experiment against a moving target the way your own teams can.
