Global infrastructure — surviving one AZ isn't the same bet as surviving one Region

"How would you design an application to survive an Availability Zone failure, and when would you go further and design for a Region failure?"

Why it matters ▾
  • Comes up in almost any AWS resilience or system-design question, even at a basic level.
  • Tests whether a candidate confuses "highly available" with "disaster-recovery-ready" — two very different investments.
  • Sets up every later AWS resilience topic (RDS Multi-AZ, ALB + Auto Scaling) that already assumes this distinction.
🔥 Easy interview recall

Region → a geographic area of isolated AZs

AZ → its own power, cooling, network

Edge Location → closer to users, no general compute

Think: multi-AZ is close to a default. multi-region is a deliberate, costly step.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Multi-AZ and multi-region are not the same level of resilience investment. Multi-AZ is close to a default best practice; multi-region is a deliberate, costly architectural decision that needs a real business justification.

🔄 Likely Follow-up

"What actually happens if one AZ disappears entirely?" Traffic and Auto Scaling shift to the healthy AZs automatically if you've architected for it (ALB + ASG spanning multiple AZs, RDS Multi-AZ) — but only if resources were deployed across AZs in the first place.

🎯 Say this in the interview — the exact lines to land

"Multi-AZ is close to a default best practice — deploying across AZs protects against a single-AZ failure like a power, cooling, or hardware outage. Multi-region is a much bigger, deliberate step — it adds data replication and real cost and complexity — so I'd only reach for it when there's a real business requirement like compliance, latency, or disaster recovery."

  • Multi-AZ → near-default — protects against a single-AZ power/cooling/hardware failure.
  • Multi-region → deliberate and costly — data replication, added complexity, needs real justification.
  • Edge Location → exists for latency (CloudFront/Route 53), not a place to run general compute.
  • AZ failure → traffic and Auto Scaling shift to healthy AZs automatically, but only if you deployed across AZs to begin with.
📖 Explanation ▾

A Region is a geographic area that contains multiple, isolated data centers. Each of those is an Availability Zone (AZ) — one or more discrete data centers with their own independent power, cooling, and networking, connected to the other AZs in that same Region by low-latency links. An Edge Location is different again: a CloudFront/Route 53 point of presence placed closer to end users for speed — it is not a full Region and doesn't run general-purpose compute.

Deploying an application across multiple AZs protects against a single-AZ failure — a power, cooling, or hardware problem in one data center. Going multi-Region is a much bigger step: it means real data replication, added cost, and added complexity, and it's only worth it when a genuine business requirement — compliance, latency, or disaster recovery — actually demands it.

🌍 Real-world example ▾

A web app spans 3 AZs within one Region for day-to-day resilience, and only adds a second Region once a compliance requirement demands data residency in a specific geography.
