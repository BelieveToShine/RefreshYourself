🔥 Must Know

Modernizing a 5-year-old Angular app — gradual migration, never a big-bang rewrite

You inherit a 5-year-old NgModule-based Angular app — how would you actually modernize it, without a rewrite?

Why it matters ▾
  • "Just rewrite it" is the single most common wrong answer to this question — interviewers are listening for whether you know Angular's old and new APIs were deliberately built to interoperate.
  • Comes up any time a candidate has real experience on a codebase old enough to predate standalone components or Signals — which by now is most production Angular apps.
  • Ties together three separate advanced topics — standalone components, state management, and large-app structure — into one coherent plan, which is exactly what a senior/architect interview is probing for.
🔥 Easy interview recall

Modernize → incrementally, feature by feature

Rewrite → not the plan — throws away working code

Why it works → old and new APIs interoperate

Think: renovate the house room by room while everyone still lives in it — not knock it down and rebuild from an empty lot.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Modernize" is not license to rewrite from scratch. A rewrite throws away years of already-working, already-tested business logic and typically takes far longer and carries far more risk than an incremental migration that leans on Angular's own deliberate interop between old and new APIs.

🔄 Likely Follow-up

"If standalone and NgModules can coexist indefinitely, is there ever real pressure to actually finish the migration?" Some — while both can coexist, staying on NgModules for new code misses out on the standalone ecosystem's simpler mental model and forgoes tooling/community energy that's increasingly standalone-first; the pressure is more about staying aligned with where the ecosystem and hiring pool are headed than about NgModules becoming literally unsupported.

🎯 Say this in the interview — the exact lines to land

"I'd modernize incrementally, feature by feature, never as one big rewrite that blocks shipping for months — new features are built standalone and with Signals from day one, existing components are converted with the official schematic starting with the highest-maintenance-cost modules, and existing RxJS-based state gets bridged with toSignal() rather than rewritten. This works because Angular's old and new APIs are explicitly designed to interoperate, which turns a terrifying rewrite into a series of individually low-risk, shippable steps."

  • Standalone + NgModules interoperate directly — a standalone component drops into an NgModule's imports, and vice versa.
  • New code standalone and Signals from day one — no reason to build new code the old way.
  • Existing components converted with the official schematic, incrementally, never all at once.
  • Existing RxJS state bridged via toSignal() — the old service stays untouched.
  • Team-structure pain fixed with feature folders first — reach for micro frontends only if that alone doesn't solve a real, felt release-blocking problem.
📖 Explanation ▾

Every one of these individual migrations works for the same underlying reason: the old and new approaches are explicitly designed to interoperate. NgModules and standalone components coexist — a standalone component can be imported straight into an NgModule's imports array, and an NgModule-based component is still reachable from standalone code through the module it belongs to. That interop is exactly what makes an incremental migration possible: modernize one feature or component at a time, never as one large, risky rewrite that blocks shipping anything else for months.

The same pattern repeats for state. New state and new features use Signals from the start; existing RxJS-based state doesn't need to be rewritten to benefit — toSignal() and toObservable() bridge the two models at the boundary where it actually matters, because Signals and RxJS are explicitly designed to coexist, not compete. And for teams that are actually blocked on each other, the fix is usually the same internal structure already covered on the Large Application Architecture page — feature-based folders, clear per-team ownership, and a deliberately narrow shared surface — introduced now, as part of the modernization, rather than reaching straight for micro frontends.

Lack of that structure is often part of what made the legacy app hard to work in to begin with — introducing it is itself a real piece of the modernization, not a separate concern. Micro frontends only earn their operational cost once multiple teams are genuinely, currently blocked on each other's release schedules — for most legacy modernization efforts, improving internal structure inside the existing app gets most of the real benefit without that cost.

💻 See the code ▾
TypeScript 
@NgModule({
  imports: [NewStandaloneWidgetComponent],  // ✅ standalone component, works fine here
  declarations: [OldLegacyComponent]        // old code, untouched
})
export class FeatureModule {}

This interop is why the migration can happen gradually — a new standalone component ships inside an old module without either side needing to change.

TypeScript 
readonly currentUser = toSignal(
  this.legacyAuthService.user$,  // existing RxJS service, untouched
  { initialValue: null }
);                                    // ✅ new code reads a Signal, old service untouched

The old AuthService keeps its RxJS internals exactly as they were — only the new component's boundary changes.

🌍 Real-world example ▾

A 5-year-old e-commerce app has 200+ NgModule-based components and heavy RxJS use throughout, with a small team that can't afford months of a parallel rewrite. The plan: a redesigned checkout flow — the one new feature — is built standalone from day one. The migration schematic runs against the three most-frequently-touched existing feature modules first, since those carry the highest ongoing maintenance cost and the biggest win from modernizing. Signals are introduced only in the new checkout flow initially, bridged to the existing RxJS-based cart service via toSignal() rather than rewriting that service. Six months in, roughly a third of the app is standalone, the team has shipped several unrelated features the whole time, and nothing was ever "down" for a rewrite.
