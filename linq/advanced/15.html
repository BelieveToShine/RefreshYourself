Streaming vs. Buffering Large Results — constant memory, or the whole set at once

"What's the real difference between streaming a large result set and buffering it?"

Why it matters ▾
🌊 Streaming vs. Buffering
❗ ProblemPulling a result set that could be millions of rows into one List<T> with ToListAsync() holds the entire thing in memory before a single row can even be processed — fine at thousands of rows, a real crash risk at millions.
✅ SolutionStream it instead — await foreach over an IAsyncEnumerable<T>, or a plain foreach over a still-deferred IEnumerable<T> — so each row is read, processed, and released one at a time, at roughly constant memory no matter how many rows there are.
RecallStreaming = one row at a time, constant memory. Buffering = the whole set, all at once.
🔥 Easy interview recall

Streaming → constant memory, one row at a time

Buffering → everything loaded before processing starts

Think: ToListAsync() waits for the whole table. await foreach starts working on row one immediately.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ToListAsync() is not "just a formality" before iterating. It's the exact point where the whole result set — however large — gets pulled into memory at once, before your code has looked at a single row.

🔄 Likely Follow-up

"If streaming is roughly constant memory, why doesn't everything just stream?" Buffering is simpler to work with — you can index into it, re-enumerate it, sort it in memory — and for a result set you know is small, that convenience costs nothing real. Streaming earns its keep specifically when the row count is large or unbounded.

🎯 Say this in the interview — the exact lines to land

"Streaming processes one row at a time with roughly constant memory — await foreach over IAsyncEnumerable<T>, or a foreach over a still-deferred IEnumerable<T>. Buffering — ToListAsync() or ToList() — holds the entire result set in memory before anything can process it, which is fine at thousands of rows and a real problem at millions."

  • Streaming → constant memory, starts on row one immediately.
  • Buffering → the whole set loaded before any processing begins.
  • Small, bounded result set → buffering is simpler, and the cost is real but trivial.
  • Large or unbounded result set → stream it, or risk exhausting memory.
📖 Explanation ▾

Streaming means the sequence is never fully materialized — each element is produced, consumed, and released before the next one is even read. await foreach over IAsyncEnumerable<T> (what EF Core's AsAsyncEnumerable() returns) does this across an actual I/O boundary, awaiting between rows as they arrive from the database; a plain foreach over a still-IEnumerable<T>/IQueryable<T> query does the equivalent thing synchronously, one row per iteration.

Buffering — calling ToListAsync() or ToList() — is a terminal operator: it forces the provider to run the entire query and copy every single row into a new, fully in-memory list before that call even returns. Nothing downstream can start working until that copy is complete, and the list's memory stays held for as long as the list itself is referenced, not released row by row.

Neither one is universally "correct." A result set you know is small and needs to be indexed, sorted again, or re-enumerated is genuinely easier to work with as a materialized list. The decision point is scale: once a result set is large or its size isn't bounded in advance, streaming is what keeps memory usage flat instead of tracking the row count.

💻 See the code ▾
C# 
// Streaming — processes one row at a time, memory stays flat
await foreach (var order in db.Orders.AsAsyncEnumerable())
{
    Process(order); // ✅ this row is released before the next one arrives
}

Each order is read, processed, and eligible for garbage collection before the next one is fetched — the list of all orders never exists at once.

C# 
// Buffering — forces the ENTIRE result into memory first
var orders = await db.Orders.ToListAsync(); // ❌ every row, loaded before any processing
foreach (var order in orders)
{
    Process(order); // this loop can't even start until the line above finishes
}

Identical end result on a small table — but at millions of rows, the ToListAsync() line alone can exhaust available memory before a single Process() call happens.

🧭 Use Cases — recognize these when they happen to you ▾
1 Exporting millions of rows to a report or file

This is the scenario streaming exists for. An IAsyncEnumerable<T> over a multi-million-row export reads, writes, and discards one row at a time — memory never tracks how many rows are left.

RememberUnbounded or huge result set → stream it.
2 Populating a dropdown from a few hundred lookup rows

A known-small, bounded set is exactly where buffering is the right call — it's simpler code, and the memory cost is real but trivial. Streaming here would just add complexity for no benefit.

RememberSmall and bounded → buffering is the simpler, correct choice.
3 A "load more later" query with no Take(), run against a table that's since grown huge

A query written years ago when the table was small, still calling ToListAsync() with no Take(), is the classic way this becomes an incident: the table grew, the call site didn't change, and now one line tries to hold the entire thing in memory at once. A common interview trap: assuming a working query stays safe forever just because it worked at launch.

RememberAn unbounded buffering call is a time bomb as the table grows.
🌍 Real-world example ▾

A nightly export job that used to finish in seconds starts crashing with an out-of-memory exception. The table it reads from has grown from thousands of rows to tens of millions, and the job still calls ToListAsync() on the whole thing. Switching to AsAsyncEnumerable() with await foreach fixes it without changing what the job actually does — it just stops holding every row in memory at once.
