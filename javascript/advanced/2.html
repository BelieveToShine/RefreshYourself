🔥 JavaScript · Advanced · Must Know

Firing 100 requests at once is easy — staying in control of them is the real skill.

"You need to fetch 100 URLs, but only 5 requests are allowed to run at the same time — how would you implement that, and what do you do when one of them fails?"

Why it matters ▾
🎯 Concurrency Pool
❗ ProblemReal APIs and databases have connection and rate limits, so mapping 100 URLs straight into fetches floods them and often makes the whole batch slower, not faster — and Promise.all doesn't fix that, since it only waits for promises that are already running, it never limits how many start.
✅ SolutionA concurrency pool starts exactly K worker loops that each claim the next unclaimed task the instant one finishes, so no more than K requests are ever in flight and no slot ever sits idle.
RecallConcurrency pool = K workers, always pulling the next task the moment one frees up.
🔥 Easy interview recall

Concurrency control = "run many things at once, but only let K run at the same time."

Think: Promise.all waits for every one. Promise.race takes whichever finishes first. A pool caps how many are ever running together.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Promise.all does not limit concurrency. It only waits for promises that are already running — if you map 100 URLs straight into 100 fetches and pass that array to Promise.all, all 100 already fired before Promise.all was ever involved.

🔄 Likely Follow-up

"So what happens when one of those 100 requests fails — do you retry it right away?" Not immediately — retrying instantly usually hits the same failure again, or makes it worse if the server is already struggling. Retry with a capped number of attempts and a delay that grows each time (exponential backoff), so a failing call backs off instead of hammering the server.

🎯 Say this in the interview — the exact lines to land

"I'd cap concurrency with a small pool — keep exactly K promises running, and the instant one settles, pull the next task off a queue and start it in its place. I'd wrap each task in a retry with exponential backoff and a max-attempt cap, and use an AbortController if any individual call needs to be cancelled."

  • Promise.all → all succeed, or the whole thing rejects on the first failure.
  • Promise.allSettled → always resolves, giving back every result and every error individually.
  • Promise.race / Promise.any → first to settle wins — race takes the first result or error, any takes the first success only.
  • A concurrency pool keeps exactly K tasks running — never fire everything at once just because the syntax lets you.
  • Retry with backoff, not immediately — cap the attempts and grow the delay after each failure.
📖 Explanation ▾

Running things one after another versus all at once is the first decision — async/await already covers the mechanics of that choice. This page is about the layer above it: once several things are running at once, how many is too many, what happens when one of them fails, and what do you actually do about it?

The four combinator functions — Promise.all, Promise.allSettled, Promise.race, and Promise.any — each answer that "what happens on failure" question with a different rule: all gives up the instant one fails, allSettled never gives up early and hands back every result, race and any only care about whoever finishes first. The full side-by-side comparison lives on the next topic, Promise Combinators — this page is about the technique of running them well, not memorizing the differences between them.

Real systems don't run promises alone, though — they run a pool of them with a hard cap, so a database or third-party API never sees more concurrent requests than it can handle. Pair that pool with a retry that backs off (waits longer each time it fails) and a cancellation path via AbortController for anything that's taking too long — together, those three are what actually ships to production, not just whichever combinator someone happens to pick.

💻 See the code ▾
JS 
async function runWithLimit(urls, limit, task) {
  const results = new Array(urls.length);
  let next = 0;              // index of the next URL to start

  async function worker() {
    while (next < urls.length) {
      const i = next++;    // claim the next task, then move on
      results[i] = await task(urls[i]);
    }
  }

  // start exactly `limit` workers — each pulls tasks until the queue is empty
  const workers = Array.from({ length: limit }, worker);
  await Promise.all(workers);
  return results;
}

const responses = await runWithLimit(urls, 5, (url) => fetch(url));

Only 5 worker loops ever exist — each one grabs the next unclaimed URL the instant it's free, so exactly 5 requests are in flight at any moment, never more.

JS 
async function retryWithBackoff(task, maxAttempts = 4) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await task();
    } catch (err) {
      if (attempt === maxAttempts) throw err;  // out of attempts — give up
      const delay = 300 * 2 ** (attempt - 1); // 300ms, 600ms, 1200ms…
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
}

Each failed attempt waits twice as long as the last one before retrying — that's the "exponential" part. The attempt cap is what stops it retrying forever.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to fetch 100 URLs but only let 5 run at the same time

This is the #1 scenario you'll actually run into. Start exactly 5 worker loops — each one grabs the next unclaimed URL the moment it's free, so exactly 5 requests are in flight at any moment, never more and never idle.

RememberK workers, each pulling the next task the instant one frees up.
2 You map 100 URLs straight into fetches and pass the array to Promise.all, assuming that caps concurrency

By the time Promise.all gets involved, all 100 fetches already fired — it only waits for promises that are already running, it never limits how many started in the first place.

RememberPromise.all waits — it does not throttle.
3 One of the 100 requests fails while the pool is running

Retrying instantly usually hits the same failure again, or makes it worse if the server is already struggling. Retry with a capped number of attempts and a delay that doubles each time (exponential backoff), so a failing call backs off instead of hammering the server.

RememberRetry with backoff and a cap — never retry immediately.
🌍 Real-world example ▾

It's a car wash with 5 bays and a line of cars waiting. Cars don't all wash at once, but the moment a bay opens up, the next car in line pulls in immediately — no bay ever sits idle while cars wait, and no more than 5 ever wash at the same time. A concurrency pool does the same thing with async tasks instead of cars.
