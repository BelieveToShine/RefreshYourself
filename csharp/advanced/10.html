Reflection — reading your own code's metadata at runtime

"What is reflection, and what can it do that normal code can't?"

Why it matters ▾
  • It's the actual mechanism behind serializers, DI containers, and ORMs — none of those libraries could hand-write code for every type you'll ever define.
  • Comes up as "how does a JSON serializer know about my class without me telling it anything?" — reflection is the real answer.
  • Knowing it's too slow for a hot path is what separates "used it once" from actually understanding the cost.
🔥 Easy interview recall

Reflection = "code that looks at its own types at runtime and can call into them, without knowing those types at compile time."

Think: obj.GetType() → walks its metadata → finds DoWork() → MethodInfo.Invoke() calls it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Reflection is basically free, so I'll use it anywhere I'd use a normal method call." Reflected member access is dramatically slower than a direct call — fine for one-time setup (building a DI container at startup), risky the moment it sits inside a loop that runs on every request.

🔄 Likely Follow-up

"How would you avoid paying that cost on every call?" Cache the MethodInfo/PropertyInfo you looked up once, or compile it into a delegate the first time — reflect once, invoke fast after that.

🎯 Say this in the interview — the exact lines to land

"Reflection lets code inspect and invoke types, members, and metadata that aren't known until runtime — it's the basis for serializers, DI containers, and ORMs. The cost is speed: reflected access is much slower than a direct call, so it belongs in one-time setup, not a hot path."

  • typeof(Foo) / obj.GetType() → the entry point into a type's own metadata.
  • Reflection can read properties, methods, and attributes the calling code never referenced at compile time.
  • MethodInfo.Invoke() → calls a method found at runtime, no compile-time reference needed.
  • In a hot path → cache the lookup or compile a delegate — don't reflect on every call.
📖 Explanation ▾

Reflection is the runtime handing your own code a mirror. Every compiled type carries its metadata — its properties, methods, constructors, attributes — inside the assembly alongside the IL. typeof(Foo) (compile-time) or obj.GetType() (runtime) hands back a Type object that can walk that metadata: list members, read attributes, find a specific method by name — all without the calling code ever writing Foo in a type position.

Finding a member is only half the story — reflection can also invoke it. MethodInfo.Invoke() calls a method it found by name, on an object it only knows as object. This is exactly how a JSON serializer sets a property it has never heard of, or a dependency-injection container calls a constructor it discovered by scanning an assembly for a matching type.

None of this is free. Every reflected call goes through extra lookup and validation the JIT can't optimize away the way it can a direct call. That's fine for a one-time setup step — building a container at startup — and risky inside code that runs on every request.

💻 See the code ▾
C# 
object plugin = LoadPlugin();
Type t = plugin.GetType();   // ✅ runtime — no compile-time reference to Foo
Console.WriteLine(t.Name);      // "Foo"

GetType() reads the object's actual runtime type — the caller never wrote Foo anywhere.

C# 
MethodInfo? method = t.GetMethod("DoWork");  // 🔍 found by name, not by reference
if (method != null)
    Console.WriteLine(method.Name);                // "DoWork"

GetMethod/GetProperties walk the type's own metadata — the same data the compiler used, exposed as objects you can query.

C# 
method.Invoke(plugin, null);  // ✅ calls Foo.DoWork() — plugin is still just "object" here

Invoke() calls the method it found — the calling code never had to know it was a Foo.

🌍 Real-world example ▾

Every JSON serializer you've used runs on this. It was written long before your class existed, yet it can read and set every property on it — because at runtime it asks your type for its own property list instead of the author hard-coding every possible class up front.

Scenario: a dependency-injection container needs to construct hundreds of classes it has never seen source code for. It scans loaded assemblies, reflects on each type's constructor to find what it needs, and builds the object graph — all metadata lookups, no hard-coded list of types.
