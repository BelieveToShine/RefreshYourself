One rate limit for every endpoint — fair, or just lazy?

"You need different rate limits for different endpoints on the same API — where and how do you implement that?"

Why it matters ▾
🚦 Per-Endpoint Rate Limiting
❗ ProblemOne global rate limit either starves a cheap, frequently-called endpoint or lets an expensive endpoint (a report generator, a bulk export) get hammered just as hard as the cheap one.
✅ SolutionGive each endpoint its own policy — cheap endpoints get a high limit, expensive ones get a low one — enforced either in app-layer middleware for fine-grained control, or at a gateway for a centralized, pre-request layer.
RecallDifferent endpoints cost different amounts — the limit should match the cost, not be one-size-fits-all.
🔥 Easy interview recall

App middleware → fine-grained, per-endpoint, sees auth context

API gateway → centralized, protects before the app even sees it

Think: Cheap endpoint → high limit. Expensive endpoint → low limit. Same API, different cost.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

One global rate limit for the whole API is not "simpler, so it's fine." It either starves a cheap, frequently-called endpoint or lets an expensive one get hammered just as hard as the cheap one.

🔄 Likely Follow-up

"How would you rate-limit per-user instead of per-IP?" Key the rate-limit counter on the authenticated user/API-key identity instead of the client's IP — IP limiting breaks down for users behind a shared NAT/corporate proxy, and doesn't stop one authenticated user from spreading requests across multiple IPs.

🎯 Say this in the interview — the exact lines to land

"I'd give each endpoint its own policy instead of one global limit — a cheap read endpoint gets a high limit, an expensive report-generation endpoint gets a low one. That can live in the application layer, using ASP.NET Core's rate-limiting middleware configured per route, which gives fine-grained control and access to the authenticated user for per-user limits. Or it can live at the infrastructure layer — an API gateway like Azure API Management — which centralizes the policy and protects the app before a request even arrives, at the cost of being coarser-grained and another moving piece."

  • Per-endpoint policy → match the limit to that endpoint's actual cost, not one global number.
  • App-layer middleware → fine-grained, sees auth context for per-user limits.
  • API gateway → centralized, protects the app before the request even arrives.
  • Per-user vs. per-IP → key on identity, not IP, once users are authenticated.
  • Never → one uniform limit across endpoints with very different costs.
📖 Explanation ▾

Per-endpoint rate limiting can be implemented at two different layers, and the choice is about where the policy should live, not which one is "correct." Application-layer middleware — ASP.NET Core's built-in rate limiter, configuring a different policy per route or endpoint group — runs inside the app itself, so it has full access to request context: the authenticated user, their role, their API key. That makes it the natural place for per-user limits, not just per-IP ones. Infrastructure-layer enforcement — an API gateway or load balancer in front of the app, like Azure API Management — centralizes the policy outside any one app's code and can reject excess traffic before it ever reaches the backend, which is valuable when the goal is protecting the app's own capacity, not just fairness between callers. The tradeoff is that a gateway is coarser-grained and one more moving piece to configure and keep in sync with the app's actual routes.

Whichever layer enforces it, the policy itself should be sized to each endpoint's real cost — a cheap, frequently-polled read endpoint can sustain a high limit; an expensive report-generation or bulk-export endpoint needs a much lower one, because a handful of concurrent calls to it can do as much damage as thousands of calls to a cheap one. And whatever the limit is keyed on, keying by authenticated identity rather than IP address handles two real cases IP-based limiting misses: many legitimate users sharing one IP behind a NAT/corporate proxy (who shouldn't be throttled together), and one abusive user spreading requests across multiple IPs (who should still be caught).

💻 See the code ▾
C# 
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("reports", o => { o.PermitLimit = 5; o.Window = TimeSpan.FromMinutes(1); }); // expensive
    options.AddFixedWindowLimiter("reads", o => { o.PermitLimit = 1000; o.Window = TimeSpan.FromMinutes(1); }); // ✅ cheap
});

app.MapPost("/reports", GenerateReport).RequireRateLimiting("reports");
app.MapGet("/items", GetItems).RequireRateLimiting("reads"); // ✅ each route gets its own policy

Each endpoint opts into the policy sized for its own cost — nothing forces every route to share the same number.

🌍 Real-world example ▾

A dashboard polls GET /items every few seconds for thousands of users, while a handful of admins occasionally trigger POST /reports, which runs an expensive aggregation query. A single global limit sized for the report endpoint would make the dashboard feel broken; sized for the dashboard, five concurrent report requests could tie up the database. Giving each endpoint its own policy lets the dashboard poll freely while the report endpoint stays protected.
