HashMap vs. Hashtable vs. ConcurrentHashMap — the real choice is only ever two of three

"What's the real choice between HashMap, Hashtable, and ConcurrentHashMap?"

Why it matters ▾
🗂️ HashMap
❗ ProblemA single-threaded piece of code just needs a fast key→value store — paying for any kind of locking would only slow it down for no benefit.
✅ SolutionHashMap has no synchronization at all — it's the fast, modern default, and it even allows one null key and multiple null values.
RecallHashMap = fast, not thread-safe, the default.
🏛️ Hashtable
❗ ProblemBefore the Collections framework existed, there was no concurrent map option at all besides locking the entire structure on every call.
✅ SolutionHashtable made every method synchronized on the whole table — it works, but only one thread can touch it at a time, for any key, and it rejects null entirely.
RecallHashtable = legacy, one lock for everything.
⚡ ConcurrentHashMap
❗ ProblemMany threads sharing a cache or counter need real concurrent throughput — Hashtable's single whole-table lock turns every one of them into a queue.
✅ SolutionConcurrentHashMap locks at a much finer grain (per bin, since Java 8), so threads touching different parts of the map rarely block each other at all.
RecallConcurrentHashMap = thread-safe, fine-grained, fast.
🔥 Easy interview recall

HashMap → not thread-safe, the default

Hashtable → legacy, one lock for the whole table

ConcurrentHashMap → per-bin locking, real concurrency

Think: Hashtable isn't really in the running anymore — the live choice is HashMap alone, or ConcurrentHashMap under real contention.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ConcurrentHashMap does not lock the whole map like Hashtable, just "more modern." Since Java 8 it locks at the level of an individual bin during a write, so threads touching different buckets rarely block each other — that per-bin design is exactly what gives it real concurrent throughput Hashtable never had.

🔄 Likely Follow-up

"How does ConcurrentHashMap actually avoid locking the whole table?" Since Java 8, a write locks only the bin (bucket) it's modifying, so threads writing to different bins never block each other — most reads don't need a lock at all.

🎯 Say this in the interview — the exact lines to land

"HashMap is the modern single-threaded default and allows null. Hashtable is legacy and synchronizes every method on the whole table. ConcurrentHashMap is the real concurrent choice — thread-safe with fine-grained, per-bin locking since Java 8, and it doesn't allow null keys or values."

  • HashMap → single-threaded default, one null key allowed.
  • Hashtable → legacy, whole-table lock — don't reach for it in new code.
  • ConcurrentHashMap → per-bin locking, genuine concurrent throughput.
  • Need thread safety → ConcurrentHashMap, never Hashtable.
📖 Explanation ▾

HashMap has no synchronization whatsoever — every get/put runs with zero locking overhead, which is exactly right when only one thread touches the map, or when you've already wrapped access in your own synchronization.

Hashtable predates the Collections framework and solved thread safety the simplest possible way: mark every method synchronized, so only one thread can be inside the object at all, for any key. It works, but it means a thread reading key "A" blocks a thread writing key "Z" for no real reason.

ConcurrentHashMap is the actual modern answer to "I need a thread-safe map." Since Java 8 it locks at the level of an individual bin during a write instead of the whole table, so unrelated writes to different bins proceed in parallel, and most reads need no lock at all.

💻 See the code ▾
☕ Java 
Map<String, String> m1 = new HashMap<>();
m1.put(null, "ok");         // ✅ one null key is fine

Map<String, String> m2 = new Hashtable<>();
m2.put(null, "ok");         // ❌ throws NullPointerException

Hashtable and ConcurrentHashMap both reject null outright — only HashMap tolerates it.

☕ Java 
Map<String, Integer> hits = new ConcurrentHashMap<>();
hits.merge("/home", 1, Integer::sum); // ✅ thread-safe, no explicit lock
// a thread updating "/about" never blocks this one — different bin

Two threads hitting different keys proceed without contending for the same lock.

🧭 Use Cases — recognize these when they happen to you ▾
1 A single request-handling thread builds a short-lived lookup map

No locking overhead is paid for a map that's built, used, and discarded inside one request on one thread — HashMap is the correct, fastest choice here, with nothing to synchronize.

RememberNo sharing across threads → reach for HashMap.
2 A shared cache is read and written by many request-handling threads at once

Many threads hitting different cache keys at the same time want to proceed in parallel, not queue up behind one lock — ConcurrentHashMap's per-bin locking is built for exactly this.

RememberShared across threads → reach for ConcurrentHashMap.
3 You inherit old code using Hashtable and assume "thread-safe" means "fine as-is"

"Thread-safe" doesn't mean "performs well under load" — Hashtable's single whole-table lock becomes a real bottleneck the moment traffic grows, even though it was never actually broken. Migrating to ConcurrentHashMap fixes throughput without changing the thread-safety guarantee.

RememberOld Hashtable under load → migrate to ConcurrentHashMap.
🌍 Real-world example ▾

A Hashtable is a store with a single checkout register — every customer waits behind it, even ones shopping in completely different aisles. ConcurrentHashMap is a store with a register per aisle — customers in different aisles never block each other.
