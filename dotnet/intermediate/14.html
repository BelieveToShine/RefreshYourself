Roles vs. Policies — one flat label, or a rule that can check anything?

"What's the difference between role-based and policy-based (claims-based) authorization?"

Why it matters ▾
🎭 Role-based
❗ ProblemA permission gate like "only Admins can hit this endpoint" needs a check defined right on the action — sprinkling hand-written "does this user have role X" checks through every method instead is easy to forget on a new endpoint.
✅ Solution[Authorize(Roles="Admin")] checks one role claim, declared inline in the attribute — simple, but coarse: best for a flat, non-conditional permission.
RecallRole check = one claim, checked inline, coarse but simple.
🧩 Policy-based
❗ ProblemA rule like "department Sales AND subscription tier Premium" can't be expressed as one role — roles multiply awkwardly, and a role check has no way to combine conditions at all.
✅ SolutionA policy is named once via AddPolicy and can combine any claims (claims are just the inputs it reads — role included) plus custom logic, then gets reused everywhere with [Authorize(Policy="...")].
RecallPolicy = named once, checks any claim(s) + logic, reused.
🔥 Easy interview recall

Roles → checks one claim: the role

Policy → checks any claim(s), plus logic

Think: both read the same claims — a role check just asks one narrow question of them.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Roles and policies are not two competing systems. Even [Authorize(Roles = "Admin")] is implemented as a built-in policy that checks for a role claim under the hood — a role check is just one narrow shape of a policy, not a separate mechanism you choose instead of one.

🔄 Likely Follow-up

"How would you authorize 'a user can edit their OWN order, but not someone else's'?" That's resource-based authorization — a policy alone can't compare the user to one specific order, since it never sees the resource. Call IAuthorizationService.AuthorizeAsync(user, order, "policy"), which passes the actual resource in so a requirement handler can check ownership.

🎯 Say this in the interview — the exact lines to land

"[Authorize(Roles = "Admin")] checks whether the user has one specific role claim — simple, but coarse. A policy is a named rule I define once with AddPolicy that can check any claim or combination of claims, and even run custom logic. Roles aren't a separate system — they're just one built-in kind of policy."

  • Claims → any key-value fact about the user, role is just one of them.
  • Roles → use for a simple, coarse permission check — one flat label.
  • Policy → use when the rule is conditional or combines claims — department, tier, and more.
  • Resource ownership → needs AuthorizeAsync(user, resource, policy), not a policy alone.
📖 Explanation ▾

A claim is any key-value fact attached to the authenticated identity — role: Admin, department: Sales, subscription_tier: Premium. A role is not a separate mechanism from a claim; it's just one conventional kind of claim, stored and read the same way as any other.

Role-based authorization — [Authorize(Roles = "Admin,Manager")] — checks whether the current identity carries one of the listed role claims. It's simple, but coarse: a role is one flat label, and roles multiply awkwardly once you need a finer distinction, like "Manager, but only for their own department."

Policy-based authorization solves that by naming a policy once — options.AddPolicy("SalesOnly", p => p.RequireClaim("department", "Sales")) — and applying it with [Authorize(Policy = "SalesOnly")]. A policy can combine multiple claim checks or run custom requirement-handler logic, which is strictly more than a role check can express. Even the built-in role check is implemented internally as a policy — knowing that is the actual skill being tested, not memorizing two separate attribute forms.

💻 See the code ▾
C# 
[Authorize(Roles = "Admin,Manager")]   // one flat claim
[HttpDelete("{id}")]
public IActionResult Delete(int id)
{
    // ✅ passes only if the user has an "Admin" OR "Manager" role claim
    ...
}

Coarse and simple — it can only ever ask one question: does a role claim match?

C# 
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("SalesOnly", policy =>
        policy.RequireClaim("department", "Sales")
              .RequireClaim("subscription_tier", "Premium"));
});

[Authorize(Policy = "SalesOnly")]   // ✅ two claims, one named rule
public IActionResult SalesDashboard() { ... }

A policy can combine multiple claims — something a plain role check has no way to express.

C# 
var result = await _authService.AuthorizeAsync(
    User, order, "OwnerOnly");   // the resource itself is passed in

if (!result.Succeeded) return Forbid();   // 🐛 not their order

Neither a role nor a plain claims policy can see which order — only this overload can.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to gate an action to one flat group, nothing conditional

One flat label is all this needs, so [Authorize(Roles="Admin")] checking that single role claim inline is simpler than reaching for a named policy for a rule this coarse. This is the most common case you'll actually write.

RememberOne flat label, no conditions → role check is enough.
2 The rule combines two facts about the user, not one

No single role expresses "Sales department AND Premium tier" — a named policy built with two RequireClaim calls handles it in one place, and every action that needs the same rule just references the policy's name.

RememberCombined conditions → name a policy, don't stack roles.
3 The rule depends on WHICH record, not just who's asking

A role check and a claims policy both only ever look at the user — neither one ever sees which specific order is being requested, so "edit YOUR OWN order" can't be expressed by either. A great interview trap — candidates often assume a policy alone can cover this. It needs AuthorizeAsync(user, order, "OwnerOnly"), which passes the actual resource in.

RememberDepends on the specific record → neither role nor policy alone, need AuthorizeAsync(user, resource, policy).
🌍 Real-world example ▾

Your API needs "a user can edit their own order, but not someone else's." A role check can't express that at all, and a claims policy still can't — both only ever look at the user, never at the specific order being requested. The fix is resource-based authorization: call AuthorizeAsync(user, order, "OwnerOnly") so a requirement handler can compare order.OwnerId against the current user's id before allowing the edit.
