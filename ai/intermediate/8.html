RAG vs. fine-tuning vs. prompt engineering — what's actually missing?

"When would you use RAG vs. fine-tuning vs. prompt engineering — and how do you decide?"

Why it matters ▾
  • Tests whether you know these three solve different problems, not that one is simply "better" than the others.
  • Comes up whenever a system needs a new capability — interviewers want to see you don't default to fine-tuning (or RAG) for everything.
  • A common system-design-style question in AI interviews, not just a definitions check.
🔥 Easy interview recall

Decision order = "prompt first, RAG for missing facts, fine-tune for missing behavior."

Think: Missing facts → RAG Missing style / format / behavior → fine-tune Neither → prompt engineering alone is usually enough

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Fine-tuning is not how you teach a model new facts. A fine-tuned model can still hallucinate specifics it wasn't reliably given during training — retrieval (RAG) is what actually guarantees the right facts reach the model; fine-tuning doesn't.

🔄 Likely Follow-up

"Could you fine-tune the model on our product catalog instead of building RAG?" Not reliably — fine-tuning shapes style, format, and task behavior, not memorized facts, so the model could still get catalog details wrong. RAG is what actually guarantees the right facts reach the model at answer time.

🎯 Say this in the interview — the exact lines to land

"I start with prompt engineering — it's the cheapest option and needs no training step. I reach for RAG when the model needs fresh, private, or frequently-changing facts it wasn't trained on. I reach for fine-tuning only when the need is about style, format, or task behavior — not knowledge, because fine-tuning doesn't reliably teach new facts."

  • Prompt engineering → try this first — cheapest, fastest, no training step.
  • RAG → use when facts are missing — fresh, private, or constantly-changing knowledge.
  • Fine-tuning → use for style, format, or task behavior — not for teaching facts.
  • Fine-tuning a model on your wiki → still won't guarantee facts — that's what RAG solves, not fine-tuning.
📖 Explanation ▾

Prompt engineering adjusts the instructions and examples inside the prompt itself — cheapest, fastest to try, and no infrastructure or training step needed. It's limited by what actually fits in a prompt and by the model's existing knowledge and behavior, so it can't fix a fact the model was never trained on.

RAG retrieves relevant, up-to-date, or private information at query time and feeds it into the prompt as grounding context. That solves the "model doesn't know this specific fact" problem without retraining, and the underlying data can be updated any time — the model itself never has to change.

Fine-tuning further trains the model's weights on examples of the desired style, format, or task. It's good for a consistent output shape, a specific tone, or a narrow specialized task — it is not a reliable way to teach new facts, because a fine-tuned model can still hallucinate facts it wasn't reliably given during training. That gap is exactly what RAG exists to close.

💻 See the code ▾
Python 
# Prompt engineering — the fix lives entirely in the instruction
prompt = f"""Summarize the article in 3 bullet points, formal tone.
Article: {article_text}"""
answer = call_model(prompt)  # ✅ no training step, works immediately

Nothing about the model changes — only the words we send it.

Python 
# RAG — the missing facts are supplied at query time
query_vector = embed(user_question)
context_chunks = wiki_index.search(query_vector, k=5)  # fresh, private data
prompt = build_prompt(user_question, context_chunks)
answer = call_model(prompt)  # ✅ grounded, not memorized

The model itself is never retrained — the fact it was missing is handed to it instead.

Python 
# Fine-tuning — reshapes HOW it answers, not WHAT it knows
examples = load_examples(brand_tone_and_json_shape)
tuned_model = fine_tune(base_model, examples)  # retrains the weights
answer = call_model(tuned_model, prompt)  # ⚠️ still not guaranteed to be factually correct

Consistent tone and shape — but it can still get facts wrong, because facts weren't the thing being taught.

🌍 Real-world example ▾

A support-bot team gets three requests in the same sprint: summaries feel too long — a prompt-engineering fix, tightening the instructions. Users ask about a wiki that changes every week — a RAG fix, retrieving the current page at query time. Leadership wants every reply in one exact JSON shape and brand voice — a fine-tuning fix, training on examples of that format. Same model, three different missing pieces, three different tools.
