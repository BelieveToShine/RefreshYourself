Custom Hooks — sharing behavior, not sharing state

"What is a custom Hook, and does using the same one in two components share their state?"

Why it matters ▾
🔁 Custom Hook
❗ ProblemCopying the same fetch-and-loading (or any other repeated stateful) logic into every component that needs it means a bug fix has to be repeated in every copy — and it's easy to assume that pulling that logic into one shared function also shares its state across every component that calls it.
✅ SolutionA custom Hook — just a function named use... that itself calls other Hooks like useState/useEffect — lets every component call the exact same logic from one place, while React still gives each call its own independent state, so the behavior is reused but the data never is.
RecallCustom Hook = one shared function, one fresh state per call — never one shared state.
🔥 Easy interview recall

Custom Hook = "shares LOGIC, never STATE."

Think: useFetch() called twice = two separate loading/data states, same reusable behavior.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Two components using the same custom Hook do not share the same underlying state. Each call to a custom Hook creates its own, completely independent state instance — a custom Hook shares the LOGIC/behavior between the components that call it, never the actual state itself.

🔄 Likely Follow-up

"What's the actual difference between a custom Hook and a plain utility function?" A custom Hook can call other Hooks (useState, useEffect, etc.) internally, tying it into React's state and lifecycle; a plain function can't — if the reusable logic doesn't need to call any Hook itself, it doesn't need to be a Hook, a regular function is simpler and just as reusable.

🎯 Say this in the interview — the exact lines to land

"A custom Hook is just a function whose name starts with use and that itself calls other Hooks — that's what ties it into React's state and lifecycle. It shares the LOGIC between components, never the actual state: each component that calls it gets its own independent copy."

  • Name starts with use → calls other Hooks internally, that's the real rule, not just a naming convention.
  • Shares behavior, never state — every call creates its own independent instance.
  • Custom Hook vs. plain function → only a Hook can call other Hooks like useState/useEffect.
  • Keep it focused on one job — a Hook doing too many unrelated things gets hard to reuse and predict.
📖 Explanation ▾

A custom Hook is nothing more than a function whose name starts with use, that itself calls other Hooks (useState, useEffect, and so on) inside its body. That internal call is what actually matters — it's what lets the custom Hook tie into React's state and lifecycle at all, not the naming convention by itself.

What gets reused across components is the behavior — the pattern of "how to fetch a URL and track loading/error state," for example — never the state instance itself. Each component that calls the custom Hook gets React's own fresh useState call for that render tree position, so two independent copies of the state exist side by side, even though both came from calling the exact same function.

A custom Hook earns its keep when it stays focused on one clear job. Once it starts doing several unrelated things at once, or its internal effects/side effects become hard to predict from the outside, it stops being something a teammate can safely reuse without reading its insides first — at that point it's worth splitting back into smaller, single-purpose Hooks.

💻 See the code ▾
JSX 
function useFetch(url) {
  const [data, setData] = useState(null);   // its own state

  useEffect(() => {
    fetch(url).then(r => r.json()).then(setData);
  }, [url]);

  return data;
}

This is the whole custom Hook — a function, starting with use, that calls other Hooks inside it.

JSX 
function UserProfile() {
  const data = useFetch("/api/user");   // own independent data
  return <div>{data?.name}</div>;
}

function ProductList() {
  const data = useFetch("/api/products"); // own independent data
  return <ul>{data?.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

Same useFetch, two components — each gets its own data state, completely unrelated to the other's.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're copying the same fetch-and-loading logic into two or more components

This is the #1 reason to reach for a custom Hook: instead of writing the same useState/useEffect pattern in every component, pull it into one function like useFetchData(url) and call it from each place that needs it.

RememberDuplicated stateful logic across components → pull it into a custom Hook.
2 You assume two components using the same custom Hook share its state

Each call to useFetchData runs its own useState/useEffect, so React gives every call site a completely independent state instance — nothing links them, even though they're running identical code.

RememberSame custom Hook, different call sites → separate state every time.
3 You're deciding whether new reusable logic should become a custom Hook or stay a plain function

The deciding factor is whether the logic itself needs to call another Hook (useState, useEffect, etc.) internally. If it does, it has to be a Hook — and its name must start with use; if it's just a calculation or formatting step with no Hook calls inside, a plain function is simpler and equally reusable.

RememberCalls a Hook inside → must be a Hook. No Hook calls inside → a plain function is enough.
🌍 Real-world example ▾

A custom Hook is a recipe, not a shared dish. Any kitchen can follow the same recipe — but two kitchens following it at the same time each end up with their own separate dish, not one shared plate magically appearing in both places. The recipe (the logic) is shared; the actual food (the state) never is.
