The client hung up — does your API keep working or stop?

"What happens to a request when the client disconnects, and how do you stop wasted work?"

Why it matters ▾
🚦 CancellationToken
❗ ProblemWhen a client disconnects, your code does not stop by itself — a slow query or downstream call keeps using the database and connections for an answer nobody will read.
✅ SolutionASP.NET Core signals the disconnect through RequestAborted; take a CancellationToken and pass it to every async call so that work stops too.
RecallThe token is only a signal — it helps only where you pass it.
🔥 Easy interview recall

RequestAborted → fires when the client leaves

CancellationToken ct → the action parameter bound to it

Pass ct → to every EF and HttpClient call

OperationCanceledException → expected, not a server fault

Think: The client left. The token is the only way your code finds out — and only if you pass it down.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Adding CancellationToken ct to the action cancels nothing by itself. It is only a signal — until you pass it into every awaited call, the work still runs to the end.

🔄 Likely Follow-up

"The client's own HttpClient times out — does your server stop?" Only if you pass the token. When the connection closes, RequestAborted fires, but nothing stops on its own; the client timeout and your server code are two separate things.

🎯 Say this in the interview — the exact lines to land

"When a client disconnects, ASP.NET Core cancels HttpContext.RequestAborted. I take a CancellationToken parameter in the action, pass it to every EF Core and HttpClient call, and treat the resulting OperationCanceledException as normal, not as an error."

  • RequestAborted → fires when the client disconnects.
  • Action parameter CancellationToken → bound to that same token.
  • Pass it down → to every EF and HttpClient call, or the work continues.
  • OperationCanceledException → expected, not a 500, so don't alert on it.
  • Server timeouts → request timeouts middleware (.NET 8) cancels the same token.
  • Writes → decide deliberately whether a half-done change should be cancelled.
📖 Explanation ▾

When a client closes the connection, the server does not kill your code. ASP.NET Core only cancels a token: HttpContext.RequestAborted. A CancellationToken parameter on a controller action or minimal API handler is bound to it. If you pass that token to ToListAsync(ct) or HttpClient.GetAsync(url, ct), those calls stop and throw OperationCanceledException. If you don't, they run on and the database keeps working for nobody.

Client timeouts and server timeouts are different things. A client timeout (for example HttpClient.Timeout) only makes the caller stop waiting. On the server, ASP.NET Core has a request timeouts middleware (.NET 8 and later) that cancels that same RequestAborted token after a limit you choose — a default policy for all endpoints, or [RequestTimeout] / WithRequestTimeout per endpoint. It does nothing until you configure a limit, and if your code doesn't handle the cancellation and write a response, the default status is 504. Either way, your code stops only where the token is used. Retry vs. Resilience covers the caller's side of timeouts; the host shutdown token is on The Generic Host.

Two cautions. A cancelled call is not an error — don't log it as one or return a 500 for it. And for writes, think before wiring the token through: cancelling a multi-step change halfway is a design decision, not a default. For a per-call limit of your own, link a CancellationTokenSource to the request token and call CancelAfter.

💻 See the code ▾
C# 
[HttpGet("reports/{id}")]
public async Task<IActionResult> GetReport(int id, CancellationToken ct) // = RequestAborted
{
    var rows = await _db.Sales
        .Where(s => s.ReportId == id)
        .ToListAsync(ct);                                  // ✅ the DB call can be cancelled

    var rate = await _http.GetStringAsync("https://rates.example/usd", ct); // ✅ so can this
    return Ok(Build(rows, rate));
}

Take the token in the signature, then hand it to every awaited call. Leave ct out of ToListAsync() and the query runs to the end even after the client is gone.

C# 
builder.Services.AddRequestTimeouts(o =>
    o.DefaultPolicy = new RequestTimeoutPolicy
    {
        Timeout = TimeSpan.FromSeconds(10)       // ✅ server-side limit per request
    });

var app = builder.Build();
app.UseRequestTimeouts();                       // cancels the request's token on timeout

A server-side limit (.NET 8+) — it cancels the same token, so code that ignores the token still isn't stopped. It does not fire while a debugger is attached, and with an explicit UseRouting it must come after it.

🌍 Real-world example ▾

A user opens a heavy report, gets impatient, and hits refresh five times. Without the token, five expensive queries all run to the end for pages nobody sees. With it passed down, the four abandoned requests are cancelled the moment their connections close, and the database only does the work that someone is still waiting for.
