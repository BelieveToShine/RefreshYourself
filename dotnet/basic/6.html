"Unit" vs. "integration" test — the dependency is the tell

"What makes a test a unit test rather than an integration test, and what does the AAA pattern mean?"

Why it matters ▾
  • Almost every .NET interview asks at least one testing question — it's treated as a baseline skill, not a specialty.
  • Mislabeling a test that hits a real database as a "unit test" is one of the most common small mistakes candidates make out loud.
  • This is the foundation the next page — mocking and testing ASP.NET Core components — builds directly on.
🔥 Easy interview recall

Unit test → one class, isolated — every dependency is faked

Integration test → real collaborators — the actual DB/API/file system runs

AAA → Arrange, Act, Assert — same shape in every framework

Think: if it talks to something real, it's not a unit test anymore — it's an integration test.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Living in the "unit test" project doesn't make it a unit test. If it talks to a real database, a real API, or the real file system, it's an integration test — whatever folder it lives in.

🔄 Likely Follow-up

"So why does dependency injection actually help here?" Constructor injection means a class declares what it needs in its signature — a test can pass in a fake without needing a real DI container or a running database at all.

🎯 Say this in the interview — the exact lines to land

"Unit tests isolate one method or class and fake every dependency, so they're fast and deterministic. Integration tests wire real components together — a real database, a real HTTP call — so they're slower but closer to production behavior. AAA — Arrange, Act, Assert — is the same shape either way, whatever framework runs it."

  • Unit test → fakes every dependency — runs in memory, no real infrastructure.
  • Integration test → real collaborators — closer to production, slower to run.
  • AAA pattern → Arrange, Act, Assert — the same structure in xUnit, NUnit, or MSTest.
  • Constructor injection → makes isolation possible — swap in a fake without a real container.
📖 Explanation ▾

Every unit test follows the same three-part shape, called AAA: Arrange sets up the object and its fakes, Act calls the one thing being tested, Assert checks the result. This shape doesn't change between frameworks — only the attribute names and assertion syntax do.

xUnit, NUnit, and MSTest are the three mainstream .NET test frameworks. They test the same way underneath — a method the runner discovers and executes — but disagree on naming:

xUnitNUnitMSTest
Test method[Fact][Test][TestMethod]
Parameterized test[Theory][TestCase][DataRow]
Assert styleAssert.Equal(a, b)Assert.That(b, Is.EqualTo(a))Assert.AreEqual(a, b)

What actually makes a test a unit test is isolation, not which folder or attribute it uses: every dependency the class under test needs is faked, so the test is fast, deterministic, and never fails because a database happened to be down.

💻 See the code ▾
C# 
[Fact]
public void Add_ReturnsSum()
{
    // Arrange
    var calculator = new Calculator();

    // Act
    var result = calculator.Add(2, 3);

    // Assert
    Assert.Equal(5, result);
}

Three clearly separated steps — this exact shape is what "AAA" means, in any framework.

C# 
public void Ship_MarksOrderShipped()
{
    var repo = new SqlOrderRepository(realConnectionString);
    // ❌ hits a real database — this is an integration test, not a unit test
    var service = new OrderService(repo);
    service.Ship(42);
}

Swap SqlOrderRepository for a fake and it becomes a genuine unit test — same class, same method, isolated instead of real.

🌍 Real-world example ▾

Testing one gear off the machine, versus running the whole assembly line. A unit test pulls a single gear out and checks it turns correctly on its own. An integration test bolts it back in and runs the whole machine to see if the finished product actually comes out right.
