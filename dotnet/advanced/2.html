Model binding internals — who wins the source race, and when you need your own binder

"How does model binding actually decide where to pull a value from — and when do you need a custom binder?"

Why it matters ▾
🏁 Source priority
❗ ProblemThe same name can show up in a form, the body, the route, and the query string — without a clear order you can't tell which value your action really got.
✅ SolutionThe default binder checks sources in a fixed order and the first match wins. Headers and services bind only when you ask for them by attribute.
RecallForm, body, route, query — first match wins.
🧩 Custom binder
❗ ProblemThe default binder maps one value to one property by name — it can't split ?ids=1,2,3 into a list or parse a value object.
✅ SolutionWrite an IModelBinder and attach it to the parameter, so only that parameter uses your parsing.
RecallCustom binder = your own parsing for one parameter.
🔥 Easy interview recall

Form fields → 1st, posted fields on a POST form

Request body → 2nd, a non-form request body

Route values → 3rd, straight from the URL path

Query string → 4th, after the ?

Think: [FromHeader] / [FromServices] → only when you name them IModelBinder → your own parsing, one parameter

⚠️ Common Trap

The sources don't merge — the first match wins. If the route has id=5 and the query string has ?id=7, the action gets 5. The query value isn't consulted for that parameter at all, so a "missing" query value can silently be ignored.

🔄 Likely Follow-up

"Do you have to put [ModelBinder] on every parameter to use a custom binder?" No. For something reusable, register an IModelBinderProvider in the MVC options (for example by inserting it into ModelBinderProviders) and the framework picks your binder for that type everywhere, instead of one parameter at a time.

🎯 Say this in the interview — the exact lines to land

"The default binder checks form fields first, then the request body, then route values, then the query string — headers and services are bound explicitly with [FromHeader] and [FromServices] instead of joining that priority chain. When the default can't parse what I need, like a comma-separated list, I write a custom IModelBinder and attach it to just that parameter."

  • Binder priority → form fields win first, then request body, then route values, then query string.
  • First match wins → sources don't merge; a later source isn't checked for that value.
  • Headers and services → bound by attribute, with [FromHeader] and [FromServices].
  • Custom binder → needed for app-specific parsing, e.g. a comma-separated ?ids=1,2,3 into a List<int>.
  • Reuse → an IModelBinderProvider applies a binder to a type everywhere.
📖 Explanation ▾

Form fields are checked first — values posted from a traditional form submission win on a name match before anything else is even looked at. The request body is checked next, then route values captured by the route template (like {id}), and finally the query string. [FromHeader] and [FromServices] sit outside this chase entirely — they bind explicitly by attribute, never by search order. For a complex or nested type, the binder repeats this same source search recursively, property by property. (Model Binding & Validation covers how triggering and validation actually work — this page picks up from there, on where the bound value comes from.)

The default binder only knows how to match one value to one property by name — it can't apply logic on top of that. A query string like ?ids=1,2,3 won't bind to a List<int> on its own, and a value object like Money or EmailAddress can't be parsed from a single string with its own validation baked in. That's what IModelBinder is for: implement it, then register it with [ModelBinder(BinderType = ...)] on the parameter (or a binder provider for something reusable), and the framework calls it instead of the default just for that one parameter.

MVC, Web API, and Razor Pages all use this same binding. Picking between them is a separate question, covered on MVC vs. Web API vs. Razor Pages. Finding why an MVC app is slow is covered on Slow MVC App Under Load — Triage.

💻 See the code ▾
C# 
public class IntListBinder : IModelBinder
{
    public Task BindModelAsync(ModelBindingContext ctx)
    {
        var raw = ctx.ValueProvider
            .GetValue(ctx.ModelName).FirstValue; // "1,2,3"
        if (raw is null) return Task.CompletedTask;

        // ✅ the default binder can't split one value into a list
        var ids = raw.Split(',').Select(int.Parse).ToList();
        ctx.Result = ModelBindingResult.Success(ids);
        return Task.CompletedTask;
    }
}

The default binder expects one value per key — ?ids=1,2,3 would otherwise bind an empty List<int>.

C# 
[HttpGet("products")]
public IActionResult GetByIds(
    [ModelBinder(BinderType = typeof(IntListBinder))] List<int> ids)
{
    // GET /products?ids=1,2,3 → ids = [1, 2, 3]
    return Ok(_products.Where(p => ids.Contains(p.Id)));
}

[ModelBinder(BinderType = ...)] overrides the default binder for just this one parameter — every other parameter still binds normally.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your action gets the same value from both the route and the query string

The binder checks route values before the query string — route wins on a name match before query is even considered.

RememberRoute beats query when both share a name.
2 You need to bind a comma-separated list like ?ids=1,2,3

The default binder can't split one string into a list — a custom IModelBinder is what makes a comma-separated value bind at all.

RememberComma-separated values need a custom binder.
3 Your action needs the caller's X-Api-Key header

The default search never looks at headers. Add [FromHeader] on the parameter and the binder reads that header, outside the usual source order.

RememberHeaders bind only when you say so.
🌍 Real-world example ▾

A product search page sends ?ids=1,2,3, and the action receives an empty list. The default binder expects one value per key, so it can't turn that single string into a List<int>. A small custom binder that splits on commas, attached to that one parameter with [ModelBinder], fixes it without touching any other action.
