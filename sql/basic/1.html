Primary Key vs. Foreign Key — who's actually being protected?

"What's the actual difference between a primary key and a foreign key?"

Why it matters ▾
  • Comes up the moment table design or table relationships are discussed — a foundational SQL question.
  • Explains a real, everyday bug: an insert or delete failing with a constraint violation traces straight back to this rule.
  • Almost always the opening SQL fundamentals question before joins, indexing, or normalization come up.
🔥 Easy interview recall

PK → uniquely IDs this row

FK → points to a PK in another table

Think: a table has only one PK (possibly composite) but can have many FKs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A foreign key means the two tables are "linked" automatically. An FK is only a constraint that blocks invalid references — it stops an insert pointing at a customer that doesn't exist and stops a still-referenced customer from being deleted without cascading — it doesn't create any automatic data-syncing or lookup beyond that check.

🔄 Likely Follow-up

"Can a table have more than one foreign key?" Yes — a table can have many FKs, one per relationship it participates in, but only one primary key, which can itself be composite (made of multiple columns).

🎯 Say this in the interview — the exact lines to land

"A primary key uniquely identifies each row in its own table — no duplicates, no nulls. A foreign key is a column that must match an existing value in another table's primary key, so the database enforces the relationship itself instead of trusting the application to get it right."

  • Primary key → unique, not null, one per table (can be composite).
  • Foreign key → must match a real value in another table's key — many allowed per table.
  • Enforces, doesn't sync → blocks bad inserts and deletes, never auto-updates related data.
  • Real trigger → an insert or delete failing with a constraint violation is this rule at work.
📖 Explanation ▾

A primary key is the column (or set of columns) that uniquely identifies every row in its own table — the database enforces no duplicates and no NULLs on it, usually backed by a unique index. A foreign key is a column in one table whose value must already exist as a primary key (or a unique key) value in another table. It's a promise the database checks, not a suggestion.

That check is the whole point: it stops an Orders row from ever pointing at a Customer that doesn't exist, and stops a still-referenced Customer from being deleted unless the relationship allows it (cascade, restrict, or set null). Nothing about an FK keeps the two rows "in sync" beyond that — updating a customer's name doesn't ripple anywhere automatically; the FK only guards the reference itself.

Primary KeyForeign Key
What it identifiesa unique row in its own tablea row it depends on, in another table
Duplicates / NULLsnever allowedduplicates allowed; NULL allowed unless the column itself is NOT NULL
How many per tableexactly one (can be composite)zero, one, or many
What breaks the rulea duplicate or NULL inserta value with no matching row in the referenced table
💻 See the code ▾
SQL 
CREATE TABLE Customers (
    Id INT PRIMARY KEY,             // uniquely IDs each customer
    Name VARCHAR(100) NOT NULL
);

CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    CustomerId INT NOT NULL,
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(Id)   // must match Customers.Id
);

Orders.CustomerId can only hold a value that already exists as Customers.Id — naming the constraint makes the error message point straight at it.

SQL 
INSERT INTO Orders (OrderId, CustomerId) VALUES (1, 99);
// ❌ Error: The INSERT statement conflicted with the FOREIGN KEY constraint
// "FK_Orders_Customers". No Customer with Id = 99 exists.

The insert is rejected before the row is ever written, because CustomerId = 99 has no matching row in Customers.

🌍 Real-world example ▾

A primary key is like your library card number — unique to you, nothing else in the system shares it. A book's checkout slip references that card number as a foreign key: the slip only gets accepted if that card number actually exists. Hand over a made-up number and the checkout is rejected on the spot.
