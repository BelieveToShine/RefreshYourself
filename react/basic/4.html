State — memory you can read, but never touch directly

"What is state, and why does React force you to use a setter instead of mutating it directly?"

Why it matters ▾
🔁 State
❗ ProblemA plain local variable resets to its initial value on every render, so a component has no way to remember something — like a click count — from one render to the next.
✅ SolutionState is a value React keeps alive between renders for that component — you only ever change it by calling the setter useState gives you, because React relies on that exact call to know something changed and schedule a re-render.
RecallState = memory between renders — change it only through the setter, never by mutating it directly.
🔥 Easy interview recall

State = "memory a component keeps between renders." You never touch it directly — you always call the setter.

Think: setCount(n+1) schedules a change; mutating count++ directly does nothing React notices.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Mutating state directly, then calling the setter with that same object, still updates the UI correctly." React compares by reference for many of its optimizations — passing back the exact same object/array reference can make React think nothing actually changed, silently skipping the re-render you expected.

🔄 Likely Follow-up

"Why do state updates feel asynchronous?" React batches multiple setState calls together and applies them before the next render for performance — reading the state variable immediately after calling its setter, in that same function, still shows the old value, because that read happens in the current render's closure, before the batched update is actually applied.

🎯 Say this in the interview — the exact lines to land

"State is the memory a component keeps between renders. I never mutate it directly — I always call the setter, because React relies on that call to know something changed and to schedule a re-render."

  • Never mutate directly — a mutated object keeps the same reference, so React can't see the change.
  • Updates are batched — multiple setState calls in one event apply together before the next render.
  • Functional updates — setCount(c => c + 1) reads the latest pending value, not a stale closure.
  • Derived state isn't state — if it can be computed from existing state or props, compute it during render instead.
📖 Explanation ▾

A plain local variable resets every time a component renders — state is different because React keeps that value alive between renders for that component. You never change it directly, though: you always call the setter useState gives you, because React relies on that call to know a change happened. Mutating state in place also defeats React.memo: if that same mutated reference gets passed down as a prop, the prop reference looks unchanged, and the memoized child skips re-rendering even though the data underneath it changed.

State updates can feel asynchronous because React batches multiple setState calls together and applies them before the next render, for performance. Reading the state variable right after calling its setter, in the same function, still shows the old value — that read happens in the current render's closure, before the batched update lands. A functional update (setCount(c => c + 1)) avoids this by always working off the latest pending value instead of the one captured in the closure.

A value you can calculate from state or props you already have generally shouldn't be its own state — compute it during render instead. Storing a derived value separately just gives it a chance to go out of sync with the state it came from.

💻 See the code ▾
JSX 
const [state, setState] = useState({ items: [] });

state.items.push(newItem);   // same reference
setState(state);             // ❌ React may not detect a change

Same object reference in, same object reference out — React has nothing new to compare against.

JSX 
setState(prev => ({           // ✅ builds a genuinely new object
  ...prev,
  items: [...prev.items, newItem]
}));

Spreading into a new object/array gives React a different reference to compare — the change is now visible.

🧭 Use Cases — recognize these when they happen to you ▾
1 You call the setter, then read that same state variable right after, in the very same function

This is the #1 scenario you'll actually run into: state updates are batched, so React groups every setter call inside the same event and applies them together before the next render. Reading the state variable right after calling its setter, in that same function, still shows the old value — that read happens in the current render's closure, before the batched update lands.

RememberReading state right after its own setter still shows the old value — the update hasn't rendered yet.
2 You mutate the state object or array directly, then call the setter back with that exact same reference

This still feels like it should work, but React compares by reference for many of its optimizations — handing back the exact same object or array reference the setter already had can make React conclude nothing actually changed, and silently skip the re-render you were expecting.

RememberSame reference in, same reference out — React has nothing new to compare against.
3 You need to call the setter more than once in a row, each update based on the newest value

Calling setCount(count + 1) twice in the same event both read the same stale count captured in that render's closure, so the two calls don't actually add up to two. A functional update — setCount(c => c + 1) — reads the latest pending value instead of that stale closure, so each call correctly builds on the one before it.

RememberFunctional updates read the latest pending value, not a stale closure.
🌍 Real-world example ▾

State is a whiteboard a component keeps between meetings (renders). You don't scribble directly on last meeting's board and hope everyone just notices — you formally submit a new version through the proper channel, the setter, which is what actually gets people (React) to update.
