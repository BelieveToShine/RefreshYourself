The Dispose pattern — deterministic cleanup vs. the GC's last resort

"The Dispose pattern vs. a finalizer — why have both, and when does the finalizer even run?"

Why it matters ▾
  • A service leaking database connections under load almost always traces back to one code path — often an exception path — that never reaches Dispose().
  • Interviewers use this to check whether you actually understand the GC's non-determinism, not just whether using exists.
  • A common trap for anyone who assumes "C# has garbage collection" means cleanup is automatic and timing doesn't matter.
🔥 Easy interview recall

Dispose() → deterministic, runs now

Finalizer → non-deterministic, GC's last resort

SuppressFinalize → skips the wasted finalizer call

Think: Dispose() is you cleaning up before you leave. A finalizer is the landlord cleaning up months later — only if you never did.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The finalizer is not a safety guarantee. It runs eventually, in an unpredictable order, only if the object is still unreachable when a GC happens to check that generation — and it may never run at all before the process exits.

🔄 Likely Follow-up

"Does calling GC.SuppressFinalize() release the resource itself?" No — it only tells the GC to skip queuing this object's finalizer. The actual release still has to happen inside Dispose(); skip that call and SuppressFinalize has nothing to suppress a cleanup for.

🎯 Say this in the interview — the exact lines to land

"Dispose() is deterministic cleanup — called explicitly or through using — and it should call GC.SuppressFinalize(this) once it's run, so the object skips the finalizer queue entirely. A finalizer is the GC's last-resort safety net: it only runs if Dispose() was never called, and its timing is never guaranteed."

  • Dispose() → deterministic, immediate cleanup, on the thread that calls it.
  • Finalizer → non-deterministic, last resort, runs on the GC's own schedule.
  • GC.SuppressFinalize(this) → skips the finalization queue once Dispose() already ran.
  • Leaking resources under load → check every path reaches Dispose(), including exception paths.
  • Injected dependency ownership → the container owns disposal, tied to its own scope, not the class that consumes it.
📖 Explanation ▾

Dispose() is a normal method — nothing stops calling code from simply not calling it, which is exactly the gap a finalizer exists to patch. The full pattern splits cleanup into Dispose(bool disposing) so it can release both managed and unmanaged resources when called from Dispose() itself, but only the unmanaged half when called from the finalizer — by then, any managed objects it references may already have been finalized themselves, in an order the GC decides.

The finalizer costs more than people expect: a finalizable object survives at least one extra GC generation, sitting on the finalization queue instead of being reclaimed outright, and its cleanup runs later on a dedicated finalizer thread — at a time the GC picks, not the code. GC.SuppressFinalize(this) inside Dispose() is what avoids that cost once cleanup has already happened deterministically.

Ownership matters as much as mechanics. A class that receives a disposable dependency from outside — through a constructor, from a DI container — rarely knows that dependency's real lifetime, so it usually shouldn't call Dispose() on it at all: whoever created the dependency, and controls its scope, is the one who should close it.

💻 See the code ▾
C# 
public class ResourceHolder : IDisposable
{
    private SafeHandle _handle;
    private bool _disposed;

    public void Dispose()
    {
        Dispose(true);           // caller-driven cleanup
        GC.SuppressFinalize(this); // ✅ skip the finalizer — already clean
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing)
            _handle?.Dispose();      // safe here — other managed objects still alive
        _disposed = true;
    }

    ~ResourceHolder() => Dispose(false); // last resort only
}

The finalizer calls the same Dispose(bool), but with disposing: false — it must not touch other managed objects, since the GC may already have finalized them.

C# 
var r = new ResourceHolder();
// r.Dispose() never called
r = null;                 // object is now unreachable
// ...sometime later, GC finalizes it — timing not guaranteed, maybe never before exit

Same end state as calling Dispose() — the resource is eventually released — but with no control over when, or whether it happens in time.

C# 
public class ReportService
{
    private readonly IReportRepository _repo; // disposable, injected

    public ReportService(IReportRepository repo) => _repo = repo;

    // ❌ don't call _repo.Dispose() here — this class doesn't own its lifetime
}

The DI container disposes _repo when its own scope ends — not when this service happens to be done with it.

🌍 Real-world example ▾

Your app is wired up with a DI container, and a service takes a disposable dependency through its constructor. Should that service call Dispose() on it? Almost always no — the container itself should own disposal, tied to whichever scope created the dependency (a single web request, for example). Calling Dispose() directly on an injected dependency risks releasing something another consumer in that same scope still needs.
