Server Components — code that never ships to the browser

"What are React Server Components, and why can't every component simply be one?"

Why it matters ▾
  • Almost every "modern React architecture" interview eventually asks this, and a shaky answer signals stale React knowledge.
  • Get the boundary wrong in a real app and you'll misplace a secret or a database call inside code that's about to ship straight to the browser.
  • A common opener before an interviewer digs into Actions, streaming, or any full-stack React framework.
🔥 Easy interview recall

Server Component → ships zero times to the client

SSR → ships twice — renders, then re-runs to hydrate

Think: SSR runs the SAME code on the server, then ships it again to run on the client. Server Components never ship that code to the client at all.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Server Components are not just Server-Side Rendering with a new name. SSR renders the same component code on the server once and then ships that code to run again on the client; a Server Component's code runs only on the server and never ships to the client's JS bundle at all — a genuinely different mechanism, not a rename of the same thing.

🔄 Likely Follow-up

"What does "use client" actually mean?" It marks the boundary where a module — and everything it imports — becomes a Client Component, opting back into browser APIs, state, effects, and event handlers; everything above that boundary in the tree can still be a Server Component. It's a directive marking where the client-side world begins, not a whole-app setting.

🎯 Say this in the interview — the exact lines to land

"A Server Component's code runs only on the server and never ships to the client's JavaScript bundle — that's the real difference from Server-Side Rendering, where the same code runs on the server once and then ships again to hydrate on the client."

  • Zero client-bundle cost for anything server-only — that code never reaches the browser.
  • Direct access to databases, file systems, and secrets — no API layer needed in between.
  • No state, effects, or event handlers — none of that makes sense for code that only ever runs once, server-side.
  • Anything interactive → must be a Client Component, marked with "use client".
  • Only serializable data can cross into a Client Component as props — never a function or a class instance.
📖 Explanation ▾

Every component is a Server Component by default — no directive needed. Its code only ever executes on the server; once it finishes rendering, only the resulting output reaches the browser, never the component's own JavaScript. That's the mechanical difference from SSR: SSR takes the exact same module and runs it twice — once on the server to produce the first HTML, once again on the client to attach event listeners (hydration). Server Components exist so that second run, for that specific code, never has to happen at all.

That's also why a Server Component can't hold state, run an effect, or attach an event handler — there's no live browser session left for any of that to attach to by the time it has already finished running. Anything that genuinely needs to react to a click, a keystroke, or a later re-render has to live in a module marked "use client" instead, which opts that module — and everything it imports — back into the normal React runtime that ships and re-runs in the browser.

The trade-off is a real new boundary to reason about. Server-only code never adds a byte to the client bundle and can reach a database or a secret directly, with no API layer in between — but data can only cross from a Server Component into a Client Component if it's serializable: a plain object, string, or number crosses fine; a function or a class instance does not.

💻 See the code ▾
JSX 
// no "use client" — this file is a Server Component by default
async function ProductList() {
  const products = await db.product.findMany(); // direct DB access

  return (
    <ul>
      {products.map(p => <li key={p.id}>{p.name}</li>)}
    </ul>
  ); // this function's own code never reaches the browser
}

Only the rendered HTML for ProductList ships to the browser — its code, and the database call inside it, never do.

JSX 
"use client"; // marks this module as a Client Component

import { useState } from "react";

function LikeButton() {
  const [liked, setLiked] = useState(false); // needs a live browser session

  return (
    <button onClick={() => setLiked(!liked)}> // event handlers only work here
      {liked ? "❤️ Liked" : "🤍 Like"}
    </button>
  );
}

This is where interactivity has to live — useState and onClick only work once the code is actually running in the browser.

🌍 Real-world example ▾

A Server Component is a kitchen (the server) handing over a fully-cooked dish — the customer never needs the recipe or any tools, they just receive the finished plate. A Client Component is a build-your-own-taco bar — the customer genuinely needs real tools and ingredients in front of them, because assembling it themselves is the whole point.
