Webhooks — your API calls the client back, so prove it's really you

"How would you design an API that calls the client back? How do you secure and retry webhooks?"

Why it matters ▾
🔔 Webhook
❗ ProblemA callback URL is open to anyone, so a fake event can trigger real actions, and a delivery that fails while the receiver is down is simply lost.
✅ SolutionSign every payload (HMAC), retry with backoff until a 2xx, and make the receiver idempotent so a repeated delivery does no harm.
RecallWebhook = signed POST, retried until 2xx, safe to receive twice.
🔥 Easy interview recall

Signature → HMAC of the body + timestamp

Replay → reject old timestamps

Retry → backoff + jitter, then dead-letter

Receiver → 2xx fast, dedupe by event ID

Think: Signature proves who sent it. Timestamp proves it is new. Event ID proves you haven't done it already.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A valid signature doesn't mean the request is new. The signature only proves who sent it — an attacker who captured a real request can send it again, so also check the timestamp and skip event IDs you have already handled.

🔄 Likely Follow-up

"The provider may deliver the same event twice — what does your receiver do?" It stores each event ID, skips one it has already seen, and still returns a 2xx so the provider stops retrying. That is the same idempotency idea, applied to a callback.

🎯 Say this in the interview — the exact lines to land

"I'd sign each webhook body with an HMAC and a timestamp, retry with exponential backoff and jitter until the receiver returns a 2xx, move it to a dead-letter queue after a limit, and make the receiver verify, dedupe by event ID, and acknowledge fast."

  • Signature → HMAC over the raw body, compared in constant time.
  • Replay → reject old timestamps and event IDs already seen.
  • Retries → backoff plus jitter, then a dead-letter queue.
  • Receiver → return 2xx fast, do the work off the request.
  • Delivery is at least once → the receiver must be idempotent.
📖 Explanation ▾

A webhook flips polling around: the client registers a URL, and your API POSTs to it when something happens. It is the callback option from Async APIs in depth. Two problems follow straight away: the URL is public, so who is calling? And the receiver can be down, so what happens to the event?

For trust, the provider signs the raw body (plus a timestamp) with a secret both sides share, using HMAC-SHA256, and sends the result in a header. The receiver recomputes it and compares in constant time. Putting the timestamp inside the signed data stops replay: an old captured request fails the age check. For failure, the provider retries with exponential backoff and jitter, and parks the event in a dead-letter queue after a limit so a human can look. The same retry rules from Retry vs. Resilience apply.

Retries mean at-least-once delivery, and order is not guaranteed. So the receiver checks the signature, checks the timestamp, dedupes by event ID, puts the work on a queue, and returns a 2xx quickly — a slow receiver looks like a failed one and gets retried. See HTTP Verbs for why repeat-safety matters.

💻 See the code ▾
C# 
static bool IsValid(byte[] secret, string timestamp, string body, string sent)
{
    var signed = Encoding.UTF8.GetBytes($"{timestamp}.{body}"); // time + raw body
    var expected = Convert.ToHexString(HMACSHA256.HashData(secret, signed));
    return CryptographicOperations.FixedTimeEquals(       // ✅ constant-time compare
        Encoding.UTF8.GetBytes(expected), Encoding.UTF8.GetBytes(sent));
}

The receiver recomputes the signature itself — a plain == on strings is the wrong tool for comparing secrets. The header names and signing format here are an example; each provider documents its own.

C# 
[HttpPost("webhooks/orders")]
public async Task<IActionResult> Receive()
{
    var body = await new StreamReader(Request.Body).ReadToEndAsync(); // raw body
    var ts = Request.Headers["X-Timestamp"].ToString();

    if (!IsValid(_secret, ts, body, Request.Headers["X-Signature"].ToString()))
        return Unauthorized();                  // ❌ not from the provider

    if (!long.TryParse(ts, out var sec) ||
        Math.Abs(DateTimeOffset.UtcNow.ToUnixTimeSeconds() - sec) > 300)
        return BadRequest();                    // ❌ too old: replay

    var evt = JsonSerializer.Deserialize<WebhookEvent>(body)!;
    if (!await _seen.TryAddAsync(evt.Id))   // event ID already stored?
        return Ok();                            // ✅ duplicate: ack, do nothing

    await _queue.EnqueueAsync(evt);            // the real work happens later
    return Ok();                                // ✅ fast 2xx
}

Verify, check age, dedupe, enqueue, answer — the receiver does almost nothing before the 2xx. _seen and _queue stand in for your own store and queue.

🌍 Real-world example ▾

A payment provider tells your shop "order paid" through a webhook, and your site is mid-deploy when the first attempt arrives. It fails, the provider tries again a little later, and this time it lands. If the provider happens to send the same event twice, your stored event ID makes the second one a harmless no-op — the order ships once.
