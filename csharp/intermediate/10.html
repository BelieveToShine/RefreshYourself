Nullable reference types — a warning, not a guarantee

"What problem do nullable reference types solve, and what do they not solve?"

Why it matters ▾
🧩 Nullable Reference Types
❗ ProblemBefore C# 8, nothing in a reference type's own signature said whether it could be null — a NullReferenceException could show up from any dereference with zero warning until it actually crashed at runtime.
✅ Solutionstring? lets you mark the "might be null" case, and the compiler tracks that promise through your code, flagging a risky dereference like name.Length with a warning (CS8602) before you ever run it — but it stays advisory, so the build still succeeds and nothing changes at runtime.
Recallstring? = a compiler-only note that flags risk before runtime — it never adds a runtime check.
🔥 Easy interview recall

Solves → compile-time warning on a risky null use

Doesn't solve → nothing stops it at runtime

Think: string? is a note left for you, not a null-check the runtime performs.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The compiler warned me, so it must have stopped the null reference." A nullable-reference warning like CS8602 doesn't block the build and adds no check — ignore it, and the exact same NullReferenceException is still waiting for you at runtime.

🔄 Likely Follow-up

"So does turning on nullable reference types change runtime behavior at all?" No — it's a compile-time-only analysis you opt into with <Nullable>enable</Nullable> or #nullable enable. It adds zero IL and zero runtime checks; you can even silence a warning with the ! null-forgiving operator and nothing about how the program runs will change.

🎯 Say this in the interview — the exact lines to land

"Nullable reference types are a compile-time-only annotation — string? tells the compiler and other developers 'this can be null, check before you use it,' and the compiler emits a warning such as CS8602 if you don't. They add zero runtime enforcement: ignoring the warning still lets a NullReferenceException happen exactly as before. That makes it a completely different mechanism from int?, even though the syntax looks the same."

  • string? → documents intent, doesn't enforce it.
  • Warning (CS8602) → compiles anyway — it's advisory, not a build error.
  • int? → real runtime struct (Nullable<T>) — a different mechanism entirely, same ?.
  • <Nullable>enable</Nullable> → opt-in, incremental rollout for an existing codebase.
📖 Explanation ▾

Before C# 8, every reference type could always be null — there was no way to say otherwise in the type itself. Nullable reference types let you write string? for "might be null" and plain string for "I'm telling the compiler this is never null," and the compiler starts tracking that promise through your code, flagging the moment you dereference a string? without first narrowing it.

The part that catches people out is that this tracking is advisory only. The compiler has no way to verify most real-world null sources (a database read, a JSON deserializer, a dictionary lookup) actually match the annotation, so it can't turn the warning into a hard guarantee without breaking huge amounts of working code. The result: CS8602 is a warning, the build still succeeds, and a wrong annotation or an ignored warning fails exactly the same way it always did — a NullReferenceException at the dereference.

This is why it's worth contrasting directly with int?. int? compiles down to a real struct, Nullable<int>, that exists at runtime and is checked via .HasValue. A nullable reference type compiles down to nothing extra at all — the ? is erased after compilation and lives only in the compiler's analysis.

💻 See the code ▾
C# 
string? name = GetName();       // GetName() may return null
Console.WriteLine(name.Length);   // ⚠ CS8602 — compiles anyway

The warning is advisory — the build still succeeds, and nothing extra runs at the dereference.

C# 
string? name = null;
Console.WriteLine(name.Length);   // ❌ NullReferenceException — warning ignored

The annotation didn't prevent this — it's the same crash you'd get without ? at all.

C# 
if (name != null)
    Console.WriteLine(name.Length);   // ✅ warning gone, safe

Narrowing with a null check is what actually removes the risk — the ? only asked you to do this.

🧭 Use Cases — recognize these when they happen to you ▾
1 You dereference a string? without narrowing it first

This is the #1 scenario you'll actually run into. The compiler flags CS8602, the build succeeds anyway, and if GetName() really did return null, the exact same NullReferenceException throws at runtime that would've happened before C# 8.

RememberWarning ≠ fix — the crash still happens if you ignore it.
2 Your team turns on nullable reference types on an existing codebase

Hundreds of new warnings appear the moment it's switched on, because years of existing code never had to prove its null-safety before. The fix isn't fixing every warning in one pass or globally suppressing them — enable it per-project or per-file and clean up the highest-risk dereferences first.

RememberRoll it out incrementally — don't fix-all or suppress-all.
3 You reach for the ! null-forgiving operator just to make a warning go away

Candidates often assume ! is a safe fix because the squiggly disappears. It isn't — ! only tells the compiler to stop warning you, it adds zero runtime safety. If the value actually is null, the same NullReferenceException still throws, just later and without the warning that could've caught it earlier.

Remember! silences the messenger — it doesn't fix the risk.
🌍 Real-world example ▾

Your team enables nullable reference types on a five-year-old codebase and wakes up to eight hundred new warnings. You don't fix them all in one pass, and you don't globally suppress them either — both wreck the point of turning it on. Enable it per-project or even per-file, fix the highest-risk dereferences first (the ones near user input or external data), and reach for the null-forgiving operator (!) sparingly and only where you can actually justify "this is never null here" — it silences the warning without adding any safety at all, so an unjustified ! just hides the same risk this feature exists to surface.
