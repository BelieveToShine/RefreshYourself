Latency and exceptions in prod — guess, or read the evidence first?

"Your API is live and users report latency and random exceptions — how do you actually track this down?"

Why it matters ▾
🩺 Triage Order
❗ ProblemJumping straight to a fix — restarting the app, adding more servers — before reading a single exception or metric destroys the evidence that would have shown the real cause, and the same failure just comes back later.
✅ SolutionWork a fixed triage order: read the actual logs/APM traces first, correlate with load, check for resource exhaustion, then check downstream dependencies — each step narrows it down before anything gets changed.
RecallRead the evidence before you touch anything — restarting treats the symptom, not the cause.
🔥 Easy interview recall

Diagnosing prod latency = "logs first, then load, then resources, then downstream."

Think: Logs/APM → real stack traces + timing Load → only under traffic, or constant? Resources → thread pool, DB pool, GC pauses Downstream → a slow dependency cascading

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Restarting the app or adding servers is not a diagnosis. It can make symptoms disappear for a while, but it also destroys the exact evidence — in-flight stack traces, thread pool state — that would have shown the actual cause.

🔄 Likely Follow-up

"What's a common root cause of 'latency under load but fine when idle'?" Thread pool starvation from sync-over-async code (.Result/.Wait() on a Task) — fine at low concurrency, catastrophic once enough requests pile up waiting for the same limited thread pool.

🎯 Say this in the interview — the exact lines to land

"I'd work a fixed order, not a guess: pull the actual exception stack traces and timing from logs/APM first, check whether it's correlated with load or happening constantly, then look for resource exhaustion — thread pool starvation from sync-over-async code, a maxed-out DB connection pool, or GC pressure from memory — and finally check whether a slow downstream dependency is cascading into my own latency. Each step narrows it down before I change anything."

  • First move → read logs/APM for the real stack traces and timing, never guess.
  • Load correlation → only under traffic, or constant? — changes where you look next.
  • Resource exhaustion → thread pool starvation, DB pool exhaustion, GC pauses.
  • Downstream deps → a slow call to another service cascades into your own latency.
  • Sync-over-async → .Result/.Wait() starves the thread pool under load, fine when idle.
📖 Explanation ▾

The first move is always reading the actual evidence — an APM tool (Application Insights, or equivalent) or structured logs, pulled for the failing requests specifically. The exception's real stack trace and the request's timing breakdown tell you more in thirty seconds than ten minutes of guessing. Only after that does it make sense to correlate with load: does latency track the traffic graph (a capacity problem), or is it happening even when the system is quiet (a code-level or dependency problem that load just makes more visible)?

If it's load-shaped, the next place to look is resource exhaustion. Sync-over-async code — calling .Result or .Wait() on a Task instead of await-ing it — blocks a thread pool thread for the whole call instead of releasing it, and the thread pool is a shared, limited resource across the whole process. At low concurrency there are enough threads to go around; once enough requests pile up waiting on the same limited pool, new requests queue for a thread before they even start, and latency climbs sharply with concurrency instead of linearly. The same shape shows up with a maxed-out database connection pool (requests queue for a connection) or memory pressure forcing longer/more frequent GC pauses. If none of that explains it, the last stop is a downstream dependency — a slow database query or a third-party API call that your own request is waiting on, which makes the slowness look like it's yours.

💻 See the code ▾
C# 
// ❌ sync-over-async — blocks a thread pool thread for the whole call
public Customer GetCustomer(int id)
{
    return _db.Customers.FindAsync(id).Result; // thread waits, can't serve anything else
}

// ✅ fully async — the thread is freed while the call is in flight
public async Task<Customer> GetCustomerAsync(int id)
{
    return await _db.Customers.FindAsync(id); // ✅ thread returns to the pool while waiting
}

At low traffic both versions feel the same; under load, the first one starves the thread pool while the second scales because threads aren't held hostage waiting.

🌍 Real-world example ▾

Users report the API getting slow and occasionally erroring, but only during the afternoon rush. The APM trace shows request latency climbing sharply, not linearly, past a certain concurrency — a clear sign of a shared, limited resource queuing up requests, not a genuinely slow operation. Grepping the codebase for .Result turns up a controller action that blocks on a downstream call instead of awaiting it — exactly the pattern that's fine at low concurrency and collapses once enough requests pile up waiting for the same thread pool.
