Concurrent rendering — interruptible work, not multiple threads

"Does concurrent React mean it uses multiple threads?"

Why it matters ▾
  • Answering "concurrent = multi-threaded" is a common first mistake that immediately signals shallow understanding to a senior interviewer.
  • It's what actually explains why a search box can stay instantly responsive while a huge list is re-filtering behind it — a real UX problem, not just trivia.
  • A near-guaranteed Deep Dive follow-up the moment React 18+, startTransition, or useDeferredValue comes up.
🔥 Easy interview recall

Concurrent ≠ "multi-threaded." It means render work is interruptible and prioritizable — an urgent update can cut in line ahead of a big, non-urgent one.

Think: JS is still single-threaded — "concurrent" describes scheduling, not parallelism.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Concurrent rendering does not mean React runs render work on multiple threads. JavaScript stays single-threaded — "concurrent" means render work built on Fiber can be interrupted and reprioritized, which solves an urgent update getting stuck behind a big non-urgent render, not doing two things at the exact same instant.

🔄 Likely Follow-up

"What's the actual difference between useTransition and useDeferredValue?" useTransition marks a state update you're making as non-urgent, and gives you an isPending flag you control; useDeferredValue takes a value you already have and gives you a lagging, lower-priority copy of it — same underlying priority mechanism, shaped for different situations.

🎯 Say this in the interview — the exact lines to land

"React stays single-threaded — 'concurrent' means Fiber makes render work interruptible and prioritizable, so an urgent update like typing can cut ahead of a big, non-urgent render like re-filtering a large list. startTransition and useTransition mark a state update as non-urgent; useDeferredValue does the same thing for a value I already have."

  • startTransition → marks a state update as non-urgent, interruptible by anything more urgent.
  • useTransition → same as startTransition, plus an isPending flag your UI can show.
  • useDeferredValue → lags a value you already have, for when you can't wrap the update itself.
  • Concurrent rendering → still single-threaded, just reordered work, not literal parallelism.
  • Misusing transitions → marking urgent work as non-urgent makes the UI feel delayed when it should feel instant.
📖 Explanation ▾

JavaScript is still single-threaded — React never runs two pieces of render work at the exact same instant. What Fiber changed is that render work is broken into small, interruptible units, so React can pause a big render partway through, throw it away, or let a higher-priority update go first. "Concurrent" is the name for that scheduling capability, not a claim about parallel execution.

startTransition marks a state update as non-urgent, so React is free to interrupt it the moment something more urgent — a keystroke, a click — comes in. useTransition gives that same capability plus an isPending flag so the UI can show that something is still catching up. useDeferredValue solves a narrower problem: sometimes you don't own the update itself — the value comes from a parent component, a router, a library you don't control — so instead of wrapping an update, you take the current value and get a deliberately lagging, lower-priority copy of it to render the expensive part from.

Marking the wrong thing as non-urgent is a real cost, not just a theoretical one — if a transition delays something the user actually expected instantly, the UI reads as sluggish even though nothing "broke." Reach for a transition for the expensive-but-not- urgent half of an update, never for the part the user is directly interacting with.

💻 See the code ▾
JSX 
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  const input = e.target.value;
  setInputValue(input);          // ✅ urgent — updates instantly

  startTransition(() => {
    setFilterText(input);        // marks this update non-urgent
  });
}

setInputValue stays urgent so the box feels instant — only the expensive re-filter is marked non-urgent.

JSX 
const [query, setQuery] = useState('');
const deferredQuery = useDeferredValue(query);

// input reads `query` directly — always instant
<input value={query} onChange={e => setQuery(e.target.value)} />

// the expensive list renders off the lagging copy
<BigFilteredList query={deferredQuery} />

The input never waits on the big list — it renders from the always-current query, while the list catches up on the deferred copy.

🌍 Real-world example ▾

A barista working alone. Someone walks up mid-order and says "just a coffee, I'm in a rush" — the barista pauses the complicated custom drink they were already building, makes the quick coffee, then goes back and finishes the complicated one. Still one barista, one pair of hands — just reordering the work by urgency, exactly like one JS thread reordering render work.
