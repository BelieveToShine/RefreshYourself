🔥 AI · Basic · Must Know

system / user / assistant — one ordered list, not one flat block of text

"How is a chat prompt to an LLM actually structured under the hood — is it just one big string?"

Why it matters ▾
🖥️ system
❗ ProblemFolding the app's own rules into the user message instead of a dedicated role weakens how strongly the model follows them, and a conflicting user request can override them entirely.
✅ SolutionA separate system message, set once by the developer at the start, is generally given the strongest steering weight — so it keeps shaping behavior even against a conflicting request.
Recallsystem = sets behavior once, top priority.
👤 user
❗ ProblemIf every message in the array carried equal weight, the model would have no reliable way to tell the human's actual request apart from background instructions or its own prior replies.
✅ Solutionuser is the role reserved for whatever the human actually typed, sent fresh every turn — the model always knows which entry is the real question to answer.
Recalluser = the human's real input, every turn.
🤖 assistant
❗ ProblemMost chat completion APIs are stateless between calls — without something marking the model's own past replies, it has no way of knowing an earlier exchange ever happened.
✅ Solutionassistant holds the model's own earlier replies, re-sent as history in the array on every request, so multi-turn context actually works.
Recallassistant = the model's own past replies, kept as history.
🔥 Easy interview recall

system → sets behavior, once, top priority

user → the human's real input

assistant → the model's own past replies, kept as history

Think: it's a labeled conversation array, not one flat string — the model reads every past turn, in order, every single time.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"The system prompt is just extra context glued onto the user's message." It isn't concatenated text — it's a separate, distinctly-tagged message that's generally given the strongest steering weight, which is exactly why a clear system instruction usually wins out over something conflicting the user asks for.

🔄 Likely Follow-up

"Why send the whole conversation back every single time instead of just the newest message?" Most chat completion APIs are stateless between calls — the model has no memory of its own, so every earlier user/assistant turn has to be re-sent in the array or the model has no way of knowing it happened.

🎯 Say this in the interview — the exact lines to land

"A chat prompt isn't one string — it's an ordered array of role-tagged messages: system sets behavior once with the strongest priority, user is the human's actual input, and assistant holds the model's own prior replies so multi-turn context actually works."

  • system → sets behavior once, strongest priority over how the model responds.
  • user → the human's actual input for that turn.
  • assistant → the model's own past replies, re-sent so it has real history.
  • Prompt templating → build the messages from a reusable template, injecting the real question at request time.
📖 Explanation ▾

Chat-format LLM APIs don't take one flat string as input — they take an ordered array of messages, each one tagged with a role. system is set once, usually right at the start, to define the model's persona, behavior, and constraints; most providers treat it as the strongest instruction in the conversation, generally winning out when it conflicts with something the user asks.

user messages hold whatever the human actually typed. assistant messages hold the model's own earlier replies — most chat completion APIs are stateless between calls, so an app has to resend every earlier turn in the array on every request, or the model has no way of knowing a previous exchange ever happened.

Real applications rarely hand-write a fresh prompt string for every request. Instead they build these role-tagged messages from a reusable template with placeholders, and substitute the actual user question (or retrieved data, or prior turns) into that template at request time — the instruction wrapper stays the same; only the variable part changes.

💻 See the code ▾
JSON 
[
  { "role": "system", "content": "Be a concise support bot." },
  { "role": "user", "content": "My order hasn't arrived." },
  { "role": "assistant", "content": "What's your order number?" },
  { "role": "user", "content": "12345" }
]

This exact four-message array gets sent again on every single call — nothing is remembered between requests.

Python 
template = "You are a {persona}. Answer only about {topic}."
system_msg = template.format(persona="support bot", topic="order status")  # ✅ same wrapper, new variables

One template, many requests — only the placeholders change, never the instruction wrapper itself.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your app needs the model to remember earlier turns in a conversation

The API is stateless between calls, so your app has to resend the entire messages array — every earlier user/assistant turn — on each new request, or the model has no idea a previous turn ever happened. This is the #1 scenario you'll actually run into once a "chat" feature needs more than one back-and-forth.

RememberNo memory between calls → the whole array gets resent, every single time.
2 You're building one system prompt that gets reused across many requests

Instead of hand-writing a fresh prompt string per request, the system message gets built from one reusable template with placeholders, and the actual persona/topic is substituted in at request time — the instruction wrapper stays identical; only the variables change.

RememberOne template, filled in per request — not a new prompt hand-written every time.
3 You fold an instruction into the user's message instead of giving it its own system message

That instruction now competes at the same weight as the user's actual request instead of getting the strongest steering priority a dedicated system message carries — so the model follows it less reliably, especially if the user's own wording conflicts with it.

RememberWrong role weakens an instruction — give steering rules their own system message, not the user's.
🌍 Real-world example ▾

Think of the system message like a stage direction handed to an actor before a play starts. The audience — the user — never sees that direction, but it shapes every line the actor (the assistant) delivers back for the rest of the scene.
