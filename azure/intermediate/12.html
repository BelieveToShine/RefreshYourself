Durable Functions — giving a stateless Function some memory

"What problem do orchestrator/activity/entity patterns solve that a plain stateless Function can't?"

Why it matters ▾
🧭 Orchestrator
❗ ProblemA plain, stateless Function starts fresh every call — it can't natively hold the sequence of a multi-step workflow, wait on an event, or run several steps in parallel and combine the results.
✅ SolutionThe orchestrator function defines that workflow — sequence, waiting, fan-out/fan-in — with its state checkpointed and replayed to rebuild it, which is exactly why its own code has to stay deterministic.
RecallOrchestrator = the workflow itself, replayed to rebuild state.
⚙️ Activity
❗ ProblemThe real work — calling a database, hitting an external API, touching the filesystem — is exactly the non-deterministic code an orchestrator can't safely contain, since replaying it would replay those side effects too.
✅ SolutionActivity functions hold that work instead: ordinary, retryable steps, and the safe place for the clock, randomness, or direct I/O.
RecallActivity = the actual work, safely retryable, never replayed.
🗄️ Entity
❗ ProblemSomething many callers read and update over time — a running counter, a per-customer total — isn't a sequence of steps at all, so forcing it into a workflow shape doesn't fit.
✅ SolutionEntity functions add a different shape: a small, addressable stateful object that responds to operations directly, closer to a lightweight actor than a workflow step.
RecallEntity = a small stateful object, updated over time, not stepped through.
🔥 Easy interview recall

Orchestrator → defines the workflow, must be deterministic

Activity → does the real work, safely retryable

Entity → a small, addressable stateful object

Think: Orchestrator is the recipe. Activity is the cook. Entity is a fridge that remembers things.

🧠 Don't mix these three — which piece does which job, and which one must stay deterministic
⚠️ Common Trap

Putting DateTime.Now, a random value, or direct I/O right inside the orchestrator. Don't — the framework replays orchestrator code to rebuild its state, so it must be deterministic; that kind of work belongs in an activity function instead.

🔄 Likely Follow-up

"What's the fan-out/fan-in pattern used for?" Running many activity functions in parallel (fan-out), then waiting for all of them to finish before continuing (fan-in) — e.g. processing 100 files concurrently and then aggregating the results.

🎯 Say this in the interview — the exact lines to land

"The orchestrator defines the workflow and must be deterministic; activities do the real work and can be retried."

  • Orchestrator → defines the workflow — sequence, waiting, fan-out/fan-in — and gets replayed to rebuild its state.
  • Activity → does the actual work and is the safe place for the clock, randomness, or direct I/O.
  • Entity → a small, addressable stateful object, closer to a lightweight actor than a workflow step.
  • Fan-out/fan-in → run activities in parallel, then wait for all of them before moving to the next step.
📖 Explanation ▾

A plain Azure Function is stateless and short-lived — every call starts fresh with no memory of the last one, and it can't natively pause for hours, coordinate several steps, or wait on an external event. Durable Functions adds three building blocks on top of the regular Functions runtime that give it exactly that kind of memory: orchestrator functions, activity functions, and entity functions.

The orchestrator function defines the workflow itself — the sequence of steps, any waiting, any fan-out/fan-in. Because the framework replays an orchestrator's code from the top whenever it needs to rebuild state (after a checkpoint, a restart, or resuming after a wait), that code has to be deterministic — same inputs, same path, every replay. The real work — calling a database, hitting an external API, touching the filesystem — happens in activity functions instead: ordinary, retryable units of work, and exactly where non-deterministic code belongs.

Entity functions add a different shape again: a small, addressable object that holds its own state and responds to operations, closer to a lightweight actor than a workflow step — useful for something like a running counter or a per-customer total that many callers read and update over time.

💻 See the code ▾
C# 
foreach (var file in files)
{
    // ✅ deterministic — no DateTime.Now, no random, no direct I/O here
    var result = await context.CallActivityAsync<string>("ProcessFile", file);
    results.Add(result);
}

One activity call per loop turn, awaited before the next — a plain sequential workflow.

C# 
var tasks = files.Select(file =>
    context.CallActivityAsync<string>("ProcessFile", file)).ToList();

// fan-out: every activity started together, fan-in: wait for all of them
var allResults = await Task.WhenAll(tasks);

Same activity, called for every file up front — the orchestrator waits once, for all of them together.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to call three APIs one after another, and it might take minutes to finish

The orchestrator awaits one activity call at a time, exactly the sequential shape in the diagram above. This is the #1 scenario you'll actually run into.

RememberOne activity call awaited at a time → the plain orchestrator pattern.
2 You need to process 100 files at once, then combine the results before moving on

This is fan-out/fan-in: the orchestrator starts every activity together, then waits for all of them (Task.WhenAll) before continuing — the same pattern as the second code sample above.

RememberStart many activities together, wait for all → fan-out/fan-in.
3 You need a running counter or a per-customer total that lots of different callers read and update over time

Neither an orchestrator nor an activity fits this shape — what actually fits is an entity function: a small, addressable stateful object that holds its own state and responds to operations directly.

RememberMany callers reading/updating shared state over time → entity function, not a workflow.
🌍 Real-world example ▾

A document-approval workflow. The orchestrator calls an activity to submit the document, then waits — potentially for days — for a human's approval signal before calling the next activity to notify everyone and archive it. Because its state is checkpointed the whole time, the orchestrator survives app restarts, deployments, or scale-ins without losing its place in the workflow.
