SQL injection — keep input as data, never let it become code

What is SQL injection, and how do you prevent it?

Why it matters ▾
💉 SQL injection
❗ ProblemWhen a query is built by gluing user input into a string, input such as ' OR 1=1 -- becomes part of the command, so an attacker can read or change data the page never meant to expose.
✅ SolutionPass values as parameters (sp_executesql) so they are never parsed as SQL; use an allow-list with QUOTENAME for names, and least privilege as a backstop.
RecallInjection = input that gets executed as code.
🔥 Easy interview recall

Injection = "user input that gets executed as code."

Think: Concatenate → input becomes code ❌ Parameter → input stays data ✅

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Escaping or stripping quotes makes concatenated SQL safe." Hand-made sanitizing misses cases; the dependable fix is to keep values out of the code string altogether by using parameters.

🔄 Likely Follow-up

"Parameters cannot be used for table or column names — what then?" Check the name against an allow-list (for example a fixed list or the names in sys.tables) and wrap it in QUOTENAME; never concatenate a raw name from the user.

🎯 Say this in the interview — the exact lines to land

"SQL injection happens when user input is concatenated into a SQL string, so it can change the query itself. I prevent it by passing values as parameters — for dynamic SQL, sp_executesql with a parameter list — validating identifiers against an allow-list with QUOTENAME, and giving the application login only the permissions it needs."

  • Concatenated input becomes code — that is the whole vulnerability.
  • Parameterize values: sp_executesql with a parameter list, or any parameterized API.
  • Parameters cover values, not table or column names → allow-list plus QUOTENAME.
  • Least privilege → the app login gets only what it needs, which limits the damage.
  • Do not rely on sanitizing — escaping quotes or blocking words is easy to bypass.
  • A stored procedure is not automatically safe if it builds dynamic SQL by concatenation inside.
📖 Explanation ▾

Dynamic SQL means building SQL text at run time and executing it — legitimate for optional search filters or a table name chosen at run time. The danger is how you build it. If the text is assembled by concatenating user input, the database cannot tell your code from their input.

Classic example: WHERE Name = ' + input + '. If the input is ' OR 1=1 --, the quote closes your string, OR 1=1 makes the filter always true, and -- comments out the leftover quote — every row comes back. The same trick can be used to read other tables or change data, depending on permissions. It is input crossing from the data lane into the code lane.

The fix is to never let it cross. Parameterize: with sp_executesql, the query text and the values travel separately, so the value is only ever a value. For names, which cannot be parameters, allow-list them and wrap with QUOTENAME. Add least privilege so a mistake does less damage. Context: Stored Procedures; the same rule applies to raw SQL issued from an ORM.

💻 See the code ▾
T-SQL 
-- ❌ vulnerable: input is glued into the code
DECLARE @sql NVARCHAR(MAX) =
    N'SELECT * FROM dbo.Users WHERE Name = ''' + @Name + N'''';
EXEC (@sql);
-- 🐛 @Name = ' OR 1=1 --   →   WHERE Name = '' OR 1=1 --'   (every row)

The quote in the input closes the string early, so the rest of the input is read as SQL.

T-SQL 
EXEC sp_executesql
    N'SELECT * FROM dbo.Users WHERE Name = @Name',   -- code, fixed text
    N'@Name NVARCHAR(100)',                         -- parameter definition
    @Name = @Name;                                       -- ✅ value stays data

-- names can't be parameters: allow-list, then QUOTENAME
SET @sql = N'SELECT * FROM dbo.' + QUOTENAME(@TableName);

Same input as before — now it is searched for as an odd name, not run. For identifiers, check the name against an allow-list first, then quote it.

🌍 Real-world example ▾

Scenario: a search box builds its query by concatenation, so typing ' OR 1=1 -- returns every user; the same box rewritten with sp_executesql just searches for that odd text and finds nothing.
