async / await — does await actually block the whole engine?

"What does an async function actually return, and does await block the JavaScript engine while it's waiting?"

Why it matters ▾
  • The natural next question after Promises — the honest answer is that async/await isn't a new concurrency model, it's syntax written on top of the same Promise.
  • Believing await freezes the whole page leads to a real bug: writing two independent calls as two back-to-back awaits and quietly doubling the wait time.
  • A near-guaranteed follow-up to any Promises question, and often the question that separates "knows the keyword" from "understands the event loop."
🔥 Easy interview recall

async function → always returns a Promise, even for a plain value

await → pauses this function only, hands control back to the event loop

try/catch → catches a rejected await like a thrown exception

Think: async/await is Promises with better handwriting — same states, same event loop, just read top-to-bottom instead of chained.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

await does not pause the whole JavaScript engine. It only pauses the async function it's inside — every other queued piece of work (event handlers, timers, other async functions) keeps running on that same single thread while that one function waits.

🔄 Likely Follow-up

"If getB() doesn't depend on getA(), why write them as two sequential awaits at all?" Usually just habit from reading top-to-bottom — reach for Promise.all the moment two awaited calls have no dependency on each other; sequential still works, it's just slower.

🎯 Say this in the interview — the exact lines to land

"An async function always returns a Promise — even a plain returned value gets wrapped in one. await doesn't block the JavaScript engine; it pauses only that function and lets the event loop run other code until the awaited Promise settles, then resumes. A rejected await throws inside the function, so an ordinary try/catch handles it. And two independent awaits in a row make their latencies add up — Promise.all starts them together so the total is only as long as the slower call."

  • async function always returns a Promise — plain values get auto-wrapped.
  • await pauses the function, not the engine — other code keeps running.
  • A rejected await throws inside the function — catchable with a normal try/catch.
  • Steps that depend on each other → keep them sequential, no way around it.
  • Independent steps → start together with Promise.all — total ≈ the slower one, not the sum.
📖 Explanation ▾

async/await is not a different way of doing async work — it's syntax written directly on top of Promises (the previous page). Marking a function async guarantees it always returns a Promise: if the function returns a plain value, JavaScript wraps that value in an already-resolved Promise for you; if it returns a Promise, that Promise is passed through as-is. await is the reverse operation — it unwraps a Promise's resolved value, or throws its rejection, right at that line.

await does not block the JavaScript engine. Hitting an await pauses only the async function it's inside — its own execution is suspended and control is handed back to the event loop immediately, so any other code already queued (other event handlers, timers, other async functions) keeps running on the same single thread. Once the awaited Promise settles, the paused function's remaining code is scheduled to resume — it doesn't just sit there frozen, and it doesn't freeze anything else either.

Because a rejected await throws at that exact line, an ordinary try/catch around it catches it exactly like a synchronous exception — no separate .catch() chain needed. That's the real ergonomic win over raw Promises: error handling reads like normal control flow instead of a parallel chain of callbacks.

💻 See the code ▾
JavaScript 
async function loadUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);   // may reject (network down)
    if (!res.ok) throw new Error("Bad response"); // a rejected await throws HERE
    return await res.json();
  } catch (err) {
    console.error("Failed to load user:", err); // ✅ caught — a normal try/catch
    return null;
  }
}

A rejected await throws right at that line — the surrounding try/catch catches it exactly like a synchronous exception.

JavaScript 
async function loadUserUnsafe(id) {
  const res = await fetch(`/api/users/${id}`); // ❌ no try/catch anywhere
  return await res.json();                  // a rejection here has nowhere to go
}
loadUserUnsafe(42);   // 🐛 unhandled promise rejection — caller never even finds out

With no try/catch (and no .catch() on the call), a rejected await just makes the function's own returned Promise reject — silently, unless something is watching for it.

JavaScript 
// Sequential — getB() doesn't start until getA() has fully settled
const a = await getA();    // wait ~120ms
const b = await getB();    // THEN wait ~200ms — total ≈ 320ms

// Concurrent — both start at the same instant
const [a2, b2] = await Promise.all([getA(), getB()]); // total ≈ 200ms — the slower one

Only correct when getB() doesn't need a's result — if it does, sequential is the only option, no matter how tempting Promise.all looks.

🌍 Real-world example ▾

A profile page loads a user's details and their notifications in two awaited calls, one after another, and it feels slower than it should. Check whether the two calls actually depend on each other — here they don't, so switching to Promise.all fires both requests immediately and the page loads in roughly the time of the slower one, not both added together.
