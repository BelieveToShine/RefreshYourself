GET / PUT / DELETE / POST — which ones can you safely call twice?

"What is idempotency, and which HTTP verbs are supposed to guarantee it?"

Why it matters ▾
  • A network retry after a timeout is a daily reality — knowing which calls are safe to blindly repeat is what keeps a retry from becoming a duplicate.
  • A very common opener before an interviewer moves into deeper REST-verb questions.
  • Mixing up "idempotent" with "has no side effects" is an easy way to sound unsure of a term you actually understand.
🔥 Easy interview recall

GET / PUT / DELETE → same end state, every time

POST → new thing created, every time

PATCH → depends on what it changes

Think: call it 1 time or 100 times — does the end state change past the first call?

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Idempotent doesn't mean "safe" or "no side effects." DELETE clearly changes something the first time — the resource is gone — it's still idempotent because repeating it never changes the outcome any further.

🔄 Likely Follow-up

"If POST isn't idempotent, how do you make a 'create' operation safe to retry over a flaky network?" Idempotency keys — the client sends a unique key per logical operation, and the server checks whether it already processed that key before creating anything new, returning the original result instead of a duplicate. This is exactly how payment APIs like Stripe make retry-safe charge creation possible.

🎯 Say this in the interview — the exact lines to land

"An operation is idempotent if making the same request multiple times leaves the system in the same end state as making it once. GET, PUT, and DELETE are specified to be idempotent. POST is not, because its job is to create a new thing every time. PATCH depends on whether the patch sets an absolute value or something like an increment."

  • GET / PUT / DELETE → repeat it, the end state doesn't change further.
  • POST → repeat it, you likely get duplicates.
  • PATCH → idempotent only if it sets an absolute value, not if it increments.
  • Retry-safe POST → use an idempotency key, not the verb itself.
📖 Explanation ▾

An operation is idempotent when calling it once and calling it many times, back to back, with the exact same input, ends with the system in the same state. It's a promise about the end state the server lands in — not a promise that nothing happens, and not a promise that the call is risk-free.

PUT replaces the whole resource with whatever body you send, so sending the same replacement twice leaves the same object in place the second time. POST's job is different by design: it means "create a new thing," so the spec doesn't — and can't — promise idempotency; two identical POST calls are two separate creates on purpose. PATCH sits in between: it's idempotent only when the patch itself is (setting a field to a fixed value), not when it isn't (incrementing a counter).

This is exactly why retry logic differs by verb. A client or load balancer can safely retry a GET, PUT, or DELETE after a timeout without knowing whether the first attempt actually landed. Retrying a POST the same blind way is what creates duplicate orders, duplicate charges, duplicate emails.

💻 See the code ▾
C# 
[HttpPut("orders/{id}")]
public IActionResult UpdateOrder(int id, OrderDto body)
{
    var order = _db.Orders.Find(id);
    order.Quantity = body.Quantity;   // ✅ always sets the same absolute value
    _db.SaveChanges();
    return Ok(order);
}

Call this twice with the same body and Quantity ends at the same value both times — idempotent by how PUT is written, not by luck.

C# 
[HttpPost("orders")]
public IActionResult CreateOrder(OrderDto body)
{
    var order = new Order(body);      // ❌ a brand-new row, every call
    _db.Orders.Add(order);
    _db.SaveChanges();
    return Created($"/orders/{order.Id}", order);
}

Two identical calls make two different order rows with two different Ids — not idempotent, exactly as the spec expects from POST.

C# 
[HttpPost("orders")]
public IActionResult CreateOrder(OrderDto body, [FromHeader] string idempotencyKey)
{
    var existing = _db.Orders.FirstOrDefault(o => o.IdempotencyKey == idempotencyKey);
    if (existing != null)
        return Ok(existing);            // ✅ same key → return the original, don't duplicate

    var order = new Order(body) { IdempotencyKey = idempotencyKey };
    _db.Orders.Add(order);
    _db.SaveChanges();
    return Created($"/orders/{order.Id}", order);
}

The verb is still POST — the endpoint itself becomes idempotent because it checks the key before creating anything.

🌍 Real-world example ▾

A mobile client's PUT request times out after the server already processed it. The app's retry logic fires automatically. Because PUT is idempotent, that blind retry is safe — worst case, the same order gets updated to the same values twice. If that had been a plain POST with no idempotency key, the exact same automatic retry could double-order or double-charge the customer.
