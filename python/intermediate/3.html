🔥 Python · Intermediate · Must Know

A shallow copy copies the outer container — the nested objects inside are still shared

"A shallow copy of a list-of-lists is mutated through the copy's nested list — what happens to the original, and why?"

Why it matters ▾
  • Checks whether you understand that Python's copy operations differ in exactly how much of the object graph gets duplicated — just the outer container, or everything inside it too.
  • Comes up constantly in real bugs: a list, dict, or config object is "copied" for safety, but a nested mutable object underneath is still the exact same shared object.
  • A natural follow-up into mutable-default-argument bugs and general aliasing questions.
🔥 Easy interview recall

b = a → same object, zero copies

copy.copy() → new outer, shared inner

copy.deepcopy() → new outer, new inner too

Think: copy.copy() copies the box. copy.deepcopy() copies the box AND everything inside it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"copy.copy() makes something fully independent." It doesn't — it only decouples the outer container; any nested mutable object (a list, dict, or custom object) inside it is still the exact same shared object until you deep-copy it.

🔄 Likely Follow-up

"When should you avoid deep copying?" When the object graph is huge or has cycles — deepcopy handles cycles correctly, but at real cost — or when it contains non-copyable resources like open file handles, sockets, or locks; a targeted shallow copy plus manually copying just the specific mutable pieces you need is often the better trade-off.

🎯 Say this in the interview — the exact lines to land

"Shallow copy only decouples the outer container — nested mutable objects are still shared until you deepcopy. If I need the copy to be fully independent, all the way down, I reach for copy.deepcopy() instead."

  • b = a → no copy at all — same object, two names.
  • copy.copy() → new outer, shared inner — nested lists/dicts are still the same objects.
  • copy.deepcopy() → fully independent — recursively copies everything inside.
  • Skip deepcopy for huge/cyclic graphs or non-copyable resources — file handles, sockets, and locks can make it slow or fail outright.
📖 Explanation ▾

Assignment (b = a) doesn't copy anything — a and b are just two names for the exact same object. copy.copy() creates a genuinely new outer container, but every reference inside it is copied as-is — so if an item inside is itself a mutable object (a list, dict, or custom instance), the copy and the original still point at that same one object. copy.deepcopy() walks the whole structure recursively and copies every object it finds along the way, so the result shares nothing mutable with the original.

This only really matters for mutable contents. A shallow copy of a list of numbers or strings behaves like a full copy in practice, because numbers and strings can't be mutated in place anyway — there's nothing shared that could ever change out from under you. The risk shows up specifically with nested lists, dicts, sets, or objects.

💻 See the code ▾
Python 
import copy

original = [[1, 2], [3, 4]]
shallow = copy.copy(original)
shallow[0].append(99)
print(original)

Predict the output: What does this print, and why?

Prints [[1, 2, 99], [3, 4]]. The outer list is new and independent, but shallow[0] is literally the same inner-list object as original[0] — appending through shallow mutates that shared object, so original shows the change too.

🌍 Real-world example ▾

A caching layer shallow-copied a nested configuration dictionary "to be safe" before handing it to each caller. The copy's nested sub-dict was still the exact same object as the original's, so when one caller mutated its own copy's settings, the change silently leaked into the cached config for every other caller reading it afterward.
