Command — the request itself becomes an object

"What is the Command pattern, and how does it support undo and queuing requests?"

Why it matters ▾
🎬 Command
❗ ProblemCalling a method directly means the caller has to know exactly what to run and when — there's no way to queue the request for later, log it, hand it to a different trigger, or undo it once it's done.
✅ SolutionCommand wraps a request as a standalone object with an Execute() (and optional Undo()) method, so an Invoker can run, queue, log, or reverse it without ever knowing what it actually does.
RecallCommand = the request itself is an object, not just a method call.
🔥 Easy interview recall

Command = "turn a request into an object you can queue, log, or undo."

Think: Invoker → holds/triggers the command, never the logic Receiver → does the real work ConcreteCommand → binds Receiver + action together

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Command is not just "Strategy with a different name." Both wrap behavior behind an interface, but Strategy swaps which algorithm runs right now; Command makes the request itself a first-class object so it can be queued, logged, triggered from multiple places, or undone.

🔄 Likely Follow-up

"How is this different from Strategy?" Strategy picks which algorithm executes right now; Command is about the request as an object — the same ICommand can be queued, stored in a history stack for Undo, or triggered by a button and a menu item alike.

🎯 Say this in the interview — the exact lines to land

"Command wraps a request as an object with an Execute() method, so an Invoker can run, queue, log, or undo it without knowing what it actually does. A ConcreteCommand binds a Receiver to the specific action; undo works by pushing executed commands onto a history stack and reversing them."

  • ICommand → one Execute() (plus optional Undo()), the request as an object.
  • Receiver → does the real work; the command just calls it.
  • Invoker → triggers commands without knowing their concrete type.
  • Undo → push executed commands on a stack, pop and reverse.
  • Command vs Strategy → Command makes the request an object; Strategy swaps the algorithm.
📖 Explanation ▾

Command turns "do this thing" into an object instead of a direct method call. An ICommand interface exposes Execute() (and often Undo()); a ConcreteCommand binds together a specific Receiver (the object that actually does the work) and the exact action to run on it. The Invoker holds the command and triggers it — a remote-control button, a menu item, a queue worker — without ever knowing what the command actually does or who the receiver is.

Because the request is now an object, it can be stored. An Invoker with a history stack can push every executed command and pop + Undo() them in reverse order to build undo/redo. The same object can be logged, serialized, or queued for later — none of that is possible when "doing the thing" is just a direct method call on the spot.

💻 See the code ▾
C# 
interface ICommand
{
    void Execute();   // the request, as a method
    void Undo();      // the reverse of that request
}

class AddTextCommand : ICommand
{
    private readonly Document _doc;
    private readonly string _text;

    public void Execute() => _doc.Append(_text);               // ✅ binds Receiver + action
    public void Undo() => _doc.RemoveLast(_text.Length);       // ✅ exact reverse
}

ConcreteCommand — binds a specific Receiver (Document) and action together behind one small interface.

C# 
class Invoker
{
    private readonly Stack<ICommand> _history = new();

    public void Run(ICommand c)
    {
        c.Execute();           // doesn't know it's AddTextCommand
        _history.Push(c);      // ✅ stored for undo later
    }

    public void UndoLast() => _history.Pop().Undo();

Invoker — only ever talks to ICommand. The history stack is what makes undo possible: it's storing objects, not a log of method calls.

🌍 Real-world example ▾

A restaurant order ticket. The waiter (Invoker) doesn't cook — they just carry the ticket (Command) to the kitchen (Receiver). The same pattern shows up in a remote-control button mapped to an action, and a GUI menu item that triggers the exact same underlying action from a completely different entry point.
