A load balancer changes your code, not just your infrastructure

"What actually changes once your API has more than one instance behind a load balancer?"

Why it matters ▾
  • Intermittent, hard-to-reproduce bugs that only show up under real load are very often exactly one of these assumptions quietly breaking — never seen in QA on a single box.
  • Interviewers use this to see whether you treat scaling out as a code review trigger, not only an ops checkbox.
  • A common opener right before the interviewer pushes into idempotency, retries, or a "describe an intermittent bug you debugged" scenario.
🔥 Easy interview recall

Shared state → move it out of memory, into a store every instance can read

Ordering → not guaranteed across two instances

Clocks → drift — don't compare wall-clock time across instances

Retries → need an idempotency key, not just a resend

Think: one box became many boxes — anything that quietly assumed "the same process handles every request" now needs a second look.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"We just added a load balancer" is not a purely infrastructure change. Shared state, ordering, clocks, and idempotent retries are all code-level assumptions — skipping that review is exactly how teams end up chasing intermittent, load-correlated bugs in production.

🔄 Likely Follow-up

"How would you even detect one of these bugs — they sound intermittent by nature?" Look for failures that correlate with load, or with the same client firing concurrent requests, rather than with a specific input — that correlation is the signature. See the 500-errors-in-production scenario for how that investigation actually goes.

🎯 Say this in the interview — the exact lines to land

"Going from one instance to many means no code can assume it owns the only copy of state, that requests arrive in order, that clocks agree, or that a retry is safe without an idempotency key — scaling out is a code review trigger, not just an infrastructure change."

  • Shared state → move it to a shared store, or use sticky sessions if you must keep affinity.
  • Request ordering → not guaranteed across instances — don't assume "create always beats update."
  • Clock drift → use a logical clock or sequence number, never a raw wall-clock comparison.
  • Retry after a timeout → may hit a different instance — always carry an idempotency key.
  • Sticky sessions → a real trade-off, not a free fix — it defeats even load distribution.
📖 Explanation ▾

On a single instance, in-memory state is the whole world — a Singleton service holding a dictionary in memory (see Service Lifetimes) sees every request, because there's only one process to see them. The moment a second instance joins behind a load balancer, that Singleton's memory is only that one instance's view — a second request can land on the other instance with no knowledge of the first. Session state, in-memory caches, and rate-limit counters all need to move to a store both instances can read, or the load balancer needs to pin a client to one instance every time ("session affinity" / sticky sessions) — itself a trade-off, since it defeats even load distribution and complicates scaling further.

Ordering and timing stop being free assumptions too. Two requests from the same client can be handled by two different instances at the same time, in either order, if the client fires them without waiting for the first to finish — logic that assumes "the create always happens before the update" can break under real concurrent load. Different instances' clocks can also drift slightly from each other; anything comparing wall-clock time across instances needs a logical clock or a sequence number instead, wherever the ordering actually matters.

Retries matter more, not less. A client or load balancer retry after a timeout can land on a different instance than the original request. If that original request actually succeeded but the response was lost in transit, a naive retry with no idempotency key can create a duplicate — see Idempotency for the single-instance version of this check; distributed, the key has to live somewhere every instance can see it.

💻 See the code ▾
C# 
public class RateLimiterService // registered as Singleton
{
    private readonly Dictionary<string, int> _hits = new(); // ❌ lives in THIS instance's memory only

    public bool Allow(string clientId)
    {
        _hits.TryGetValue(clientId, out var count);
        if (count >= 100) return false; // ❌ only counts requests THIS instance saw
        _hits[clientId] = count + 1;
        return true;
    }
}

A client bouncing between two instances gets up to 200 requests through, not 100 — each instance's dictionary only ever sees its own half of the traffic.

C# 
public class RateLimiterService
{
    private readonly IDistributedCache _cache; // ✅ Redis, SQL — anything shared

    public async Task<bool> AllowAsync(string clientId)
    {
        var count = await _cache.GetIntAsync(clientId) ?? 0; // seen by EVERY instance
        if (count >= 100) return false;
        await _cache.SetIntAsync(clientId, count + 1);
        return true;
    }
}

Same 100-request limit, but now every instance reads and writes the same counter — the limit holds no matter which instance a request lands on.

C# 
[HttpPost("orders")]
public async Task<IActionResult> CreateOrder(OrderDto body, [FromHeader] string idempotencyKey)
{
    // ✅ checked against a shared table — a retry that lands on a
    // DIFFERENT instance still sees the same key
    var existing = await _db.Orders.FirstOrDefaultAsync(o => o.IdempotencyKey == idempotencyKey);
    if (existing != null) return Ok(existing); // same result, no duplicate

    var order = new Order(body) { IdempotencyKey = idempotencyKey };
    _db.Orders.Add(order);
    await _db.SaveChangesAsync();
    return Ok(order);
}

This only works because the idempotency key lives in the database every instance shares — the same check kept in a static in-memory set would miss a retry the load balancer routes to a different instance.

🌍 Real-world example ▾

Your API scales from one instance to three behind a load balancer, and support starts reporting a bug that only reproduces "sometimes" — never in QA on a single box. Check whether the failure correlates with load, or with a client firing two requests close together, rather than with any specific input. That correlation is the tell: it points straight at shared state, ordering, clock drift, or a missing idempotency key — not at the business logic everyone starts by re-reading.
