Typography — why the words on screen keep moving while the page is still loading

"Why does text cause layout shift while the page loads?"

Why it matters ▾
🔤 Web Font Loading & Layout Shift
❗ ProblemA custom web font takes real time to download, so the browser has to render the text with something before that file arrives — and whatever it shows first rarely takes up the exact same space as the font that shows up later.
✅ Solutionfont-family, font-size, font-weight, line-height, and letter-spacing together decide how much room text takes up in each state, so once the real font swaps in, a mismatch in those values reflows the page — a real, measurable layout shift Core Web Vitals-style metrics are built to catch, not a cosmetic flicker.
RecallThe swap isn't the bug — a fallback and a real font with different metrics is.
🔥 Easy interview recall

Font layout shift = "the browser shows a stand-in font first, swaps in the real one later, and the page reflows if they're not the same size."

Think: Fallback font renders now. The @font-face font renders later — different letters, different width, different height.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It's just a visual flicker, nothing measurable." A font swap that changes line count or line height is a real, measurable layout shift — exactly what Core Web Vitals-style metrics like Cumulative Layout Shift are built to score, not just an appearance change.

🔄 Likely Follow-up

"So how would you actually reduce it?" Pick a fallback font with a similar average character width and line-height to the real one, or lean on font-display deliberately (e.g. swap vs. optional) so the trade-off between a brief invisible-text flash and a later reflow is a choice you made, not an accident.

Once the file arrives, the browser swaps it in; if the fallback and the real font take up different amounts of space per character, the text reflows to a different width or height, and that's a real, measurable layout shift, not just a cosmetic flicker."

📖 Explanation ▾

Five properties decide how text looks and how much room it takes: font-family (which font, tried as an ordered list), font-size, font-weight (how bold the strokes are), line-height (vertical space per line), and letter-spacing (horizontal gap between characters).

PropertyWhat it controls
font-familyWhich font to use — a list of names tried in order, ending in a generic fallback like sans-serif
font-sizeHow large each character renders
font-weightHow thick the strokes are (e.g. 400 normal, 700 bold)
line-heightThe vertical space each line of text takes up
letter-spacingExtra horizontal gap added between characters

A web font is a font file the browser downloads instead of one already installed on the device, loaded with @font-face and then referenced from font-family like any other name. Downloading takes real time — the browser can't render text in that font until the file actually arrives. In the meantime it either shows the next name in the font-family list (a real, already-available fallback font) or, depending on the font-display setting, keeps the text invisible for a short window. Either way, once the real file lands, the browser swaps it in.

That swap is where layout shift comes from: a fallback font and a custom web font almost never have the exact same average character width or line-height, so the same text can wrap onto a different number of lines or take up a different height before and after the swap. Anything positioned below that text — a paragraph, a card, a whole section — physically moves when that happens. It's a genuine reflow the browser has to recompute, which is exactly why it counts as a real layout-shift metric, not just something that looks different.

💻 See the code ▾
CSS 
h1 {
  font-family: "Poppins", "Helvetica Neue", Arial, sans-serif;  /* tried in order */
  font-size: 28px;
  font-weight: 700;
  line-height: 1.3;       /* space per line, not just text height */
  letter-spacing: 0.2px;
}

The font-family list is tried left to right — sans-serif at the end always works because it's a built-in generic family, not a specific font file that has to load.

CSS 
@font-face {
  font-family: "Poppins";
  src: url("/fonts/poppins-700.woff2") format("woff2");
  font-weight: 700;
  font-display: swap;   /* show the fallback now, swap Poppins in once it's downloaded */
}

font-display decides what shows while the file is still downloading — swap shows the fallback immediately and reflows later; other values (like block or optional) trade that flash-vs-reflow decision differently.

CSS 
.title {
  white-space: nowrap;      /* keep it on one line */
  overflow: hidden;         /* hide whatever doesn't fit */
  text-overflow: ellipsis;  /* does nothing without the two lines above */
}

Drop either white-space: nowrap or overflow: hidden and text-overflow: ellipsis quietly does nothing — all three are required together.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your custom web font is still downloading when the heading first renders

This is the #1 scenario you'll actually run into. The browser shows the next name in the font-family list — or keeps text invisible, depending on font-display — while the real file downloads, then swaps the web font in once it arrives. If the fallback and the web font don't share the same average character width or line-height, the text reflows to a different width or height and everything below it visibly jumps.

RememberFallback shows now, real font swaps in later — mismatched metrics push the page.
2 You dismiss the jump as "just a flicker," not a real bug

A font swap that changes line count or line height is a real, measurable layout shift — exactly what Core Web Vitals-style metrics like Cumulative Layout Shift are built to score, not just an appearance change. Calling it "just a flicker" in an interview is the exact trap this topic is testing for.

RememberVisual flicker ≠ harmless — a reflow is a real CLS hit.
3 You add the ellipsis truncation rule and the text still doesn't truncate

text-overflow: ellipsis only truncates visibly once overflow: hidden and white-space: nowrap are also set on the same element — drop either one and the ellipsis rule quietly does nothing, with no error to warn you.

RememberEllipsis needs all three: nowrap + hidden + ellipsis.
