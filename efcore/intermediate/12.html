Find vs. FirstOrDefault — one may skip the database entirely

What's the difference between Find and FirstOrDefault?

Why it matters ▾
🔎 Looking up one row
❗ ProblemFour ways to fetch a single row look interchangeable, but they differ on whether they hit the database, what they search by, and what happens with duplicates.
✅ SolutionFind looks up by primary key and checks the change tracker first; First* and Single* always query and differ on how they treat a second match.
RecallFind = key, tracker first. First = any match. Single = exactly one.
🔥 Easy interview recall

Find(key) → tracker first, key only

First* → always queries, takes the first match

Single* → always queries, throws on a duplicate

Think: Find may skip the database. First takes any. Single insists on one.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Find is not just a shorter FirstOrDefault(x => x.Id == id). If that entity is already tracked, Find returns it without sending any SQL at all; FirstOrDefault always queries.

🔄 Likely Follow-up

"When would you pick SingleOrDefault over FirstOrDefault?" When at most one match is a business rule (a unique email) — it throws if there are two, so a data bug shows up instead of being hidden. Use First with an OrderBy when you just want one of several.

🎯 Say this in the interview — the exact lines to land

"Find looks in the change tracker first and only queries the database if the entity isn't already tracked — and it works on the primary key only. FirstOrDefault and SingleOrDefault always send a query: First takes the first match, while Single insists there is at most one and throws if there are more."

  • Find → tracker first, primary key only; no SQL if already tracked.
  • FirstOrDefault → always queries, null if none — add an OrderBy.
  • SingleOrDefault → throws if more than one; use it for unique rules.
  • Need Include or AsNoTracking → Find can't; use First or Single.
📖 Explanation ▾

Find does one thing: look up by primary key. It checks the change tracker first; if an entity with that key is already tracked, it is returned with no SQL. Otherwise it queries the database by key. Nothing found → null.

First* and Single* take any condition and always send a query. FirstOrDefault returns the first match (add an OrderBy, or "first" isn't defined) or null. SingleOrDefault insists on at most one: with two matches it throws InvalidOperationException — EF Core fetches two rows precisely so it can spot the duplicate.

Because Find is a DbSet method, you can't chain Include or AsNoTracking onto it — use FirstOrDefault or SingleOrDefault for that. Background: Tracking vs. AsNoTracking() and The Change Tracker & SaveChanges().

💻 See the code ▾
C# 
var a = await db.Customers.FindAsync(5);   // not tracked yet → SELECT
var b = await db.Customers.FindAsync(5);   // ✅ already tracked → no SQL

The second Find is answered by the change tracker — zero queries.

C# 
var c = await db.Customers.FirstOrDefaultAsync(x => x.Id == 5);         // ❌ always sends SQL
var d = await db.Customers.SingleOrDefaultAsync(x => x.Email == email);   // throws if 2 rows match

First* / Single* go to the database every time; Single also guards uniqueness.

C# 
var e = await db.Customers
    .Include(x => x.Orders)                  // Find has no Include
    .AsNoTracking()
    .FirstOrDefaultAsync(x => x.Id == 5);

Need related data or no tracking? Switch to a query — Find can't be chained.

🌍 Real-world example ▾

A request handler loads the same customer in three helper methods. With Find, only the first call costs a query. Looking the customer up by email instead? That needs SingleOrDefault — Find only knows the key.
