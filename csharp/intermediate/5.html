Exception filters — catching only the exception you actually meant

"What is an exception filter, and why not just catch then check with an if?"

Why it matters ▾
  • Lets you catch by exception type and a runtime condition in one clause — no separate catch-then-rethrow logic to maintain.
  • The natural tool for retry logic: catch a network failure only when it's the transient status you can actually recover from, and let everything else propagate.
  • A frequent follow-up after try/catch/finally — interviewers use it to check you understand propagation, not just syntax.
🔥 Easy interview recall

Exception filter = "catch this type, but only keep it if the condition is also true."

Think: a failed when lets the exception keep walking to the next catch — an if inside the block has already caught it, too late to hand it on.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

A when filter that evaluates false does not swallow the exception. It's as if that catch clause were never tried — checking the same condition with a plain if inside the catch body already caught it, so it can no longer reach a later, more specific catch.

🔄 Likely Follow-up

"So what's the difference between throw ex; and throw; when you rethrow inside a catch?" throw; preserves the original stack trace; throw ex; resets it to the rethrow point, hiding where the exception actually started — always prefer throw;.

🎯 Say this in the interview — the exact lines to land

"An exception filter — catch (Ex e) when (condition) — only enters the catch block if the type matches and the condition is true. If the condition is false, the exception keeps propagating to the next matching catch or the caller, exactly as if this catch didn't exist — catching first and checking with an if would swallow it either way, which changes behavior."

  • catch (Ex e) when (cond) → type match AND condition both required to enter the block.
  • Filter evaluates false → exception keeps propagating, this catch's body never runs.
  • Custom exception type → earns its place only when a caller needs to catch this specific failure distinctly, not just for a nicer message.
  • Rethrowing? → throw; keeps the original stack trace; throw ex; resets it.
📖 Explanation ▾

catch (Ex e) when (condition) is evaluated before the runtime decides this catch block gets the exception at all. If condition is false, it's as if this catch clause doesn't exist for this particular exception — the runtime moves on to the next catch, or out to the caller.

A plain if inside a catch can't do that. Once catch (Ex e) matches, the exception is already caught — a following if can only decide what code runs next, not hand the exception to a different, more specific catch further down.

A custom exception type earns its place the same way — only when a caller genuinely needs to catch this failure separately from every other error. Wrapping a built-in exception just to give it a friendlier message doesn't need a new type; a filter or a clearer message is enough.

💻 See the code ▾
C# 
try
{
    CallExternalService();
}
catch (HttpRequestException e) when (e.StatusCode == HttpStatusCode.ServiceUnavailable)
{
    Retry();  // ✅ only runs for 503 — anything else keeps propagating
}

The when clause only claims a 503 — a 404 or 500 skips this catch entirely and keeps propagating.

C# 
catch (HttpRequestException e)
{
    if (e.StatusCode == HttpStatusCode.ServiceUnavailable)
        Retry();
    else
        throw;  // have to remember to do this manually
}

Without a filter, every HttpRequestException is already caught — you must manually throw; the ones you didn't actually want.

C# 
catch (Exception e)
{
    throw;        // ✅ preserves the original stack trace
    // throw e;  ❌ resets it to this line — hides where it started
}

throw; keeps pointing at the real origin; throw ex; makes it look like the exception started in this catch block.

🌍 Real-world example ▾

Your service calls a flaky external API and should retry automatically — but only for a 503, never a 404. An exception filter on the HttpRequestException catch does exactly this in one clause: the retry runs when the status matches, and every other failure keeps propagating to whatever error handling already exists further up the call stack.
