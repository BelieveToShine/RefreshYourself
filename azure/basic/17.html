API Management — one front door for many backends

"What is Azure API Management, and what problem does it solve for exposing APIs?"

Why it matters ▾
🚪 API Management
❗ ProblemWithout a shared gateway, every backend team has to build and maintain its own auth, rate limiting, and versioning — the same plumbing rebuilt again for each new API consumer.
✅ SolutionAPIM sits in front of the backends as one gateway, applying auth, throttling, and versioning as configured policies — so that logic is written once, not per service.
RecallAPIM = one front door for many backend APIs.
🔥 Easy interview recall

APIM = "one front door for many backend APIs."

Think: the front door checks the badge (auth), counts entries (rate limit), and hands out a map (dev portal) — the backend behind it never sees any of that work.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

APIM does not replace the backend's own auth. It's a front door that can enforce policies — like validating a JWT — before a request even reaches the backend, but the backend can still keep its own checks too; it's an added layer, not a full replacement.

🔄 Likely Follow-up

"What's a 'policy' in APIM?" An XML-based rule (inbound, outbound, or backend) that runs on each request/response — like a rate limit, a header rewrite, or a JWT check — configured without touching the backend's own code.

🎯 Say this in the interview — the exact lines to land

"APIM is a gateway layer in front of your backends — it handles auth, rate limiting, and versioning without touching the backend code."

  • Policies are configuration, not code — XML rules applied to requests/responses, no backend redeploy needed.
  • Not a backend replacement — APIM is an added layer; the backend can still enforce its own checks too.
  • Developer portal → gives API consumers docs, keys, and a place to try calls, all in one place.
  • Versioning & throttling → expose multiple API versions and cap calls per client without touching backend code.
📖 Explanation ▾

Azure API Management sits in front of one or more backend APIs as a gateway. Every request passes through it first, where it can handle authentication, rate limiting/throttling, request and response transformation, and versioning — all before the request ever reaches the backend. It also gives API consumers a developer portal: documentation, subscription keys, and a place to try calls out.

None of this requires changing the backend's own code. A policy is configured on the gateway itself, so a team can add a rate limit or rewrite a header today without a backend deployment. The backend can still run its own checks in parallel — APIM is an added layer in the request path, not a substitute for whatever the backend already does.

💻 See the code ▾
XML 
<policies>
  <inbound>
    <!-- caps each caller at 5 calls per 60 seconds -->
    <rate-limit calls="5" renewal-period="60" />
    <validate-jwt header-name="Authorization" />
  </inbound>
</policies>

This is configuration on the gateway, not backend code — the request is rejected here if it's over the limit or the token doesn't check out, before the backend ever sees it.

🧭 Use Cases — recognize these when they happen to you ▾
1 External partners need one consistent API surface across several internal microservices

The partner only ever sees one versioned, rate-limited API — APIM routes the request to whichever of the 5 backend microservices actually owns it, and each one keeps its own internal shape.

RememberMany backends in, one consistent surface out.
2 One API consumer is calling far more often than the rate the backend can take

The gateway's own rate-limit policy rejects the extra call with a 429 before it ever reaches the backend — the backend code never has to know a limit was even applied.

RememberRate limiting lives on the gateway, not in backend code.
3 APIM validates the JWT, so the team assumes the backend itself is now fully secured

APIM's JWT check only gates what reaches it through the gateway — it doesn't secure the backend itself. If the backend is reachable another way, or needs its own authorization rules per operation, it still has to enforce them.

RememberA gateway check is not a backend security replacement.
🌍 Real-world example ▾

A company has 5 internal microservices — orders, inventory, payments, and two more — none of them meant to be called directly by outside partners. It puts a single APIM instance in front of all of them, so partners see one consistent, versioned, rate-limited public API surface, while each microservice behind it keeps its own internal shape and never has to know APIM is even there.
