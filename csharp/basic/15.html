is / as / explicit cast — safe conversion, or an exception waiting to happen?

"What's the difference between is, as, and an explicit cast?"

Why it matters ▾
  • One of the three throws on a bad conversion — the other two just tell you "no."
  • Shows up the moment you're filtering a mixed-type collection.
  • An easy way to look sloppy: casting where a pattern match would be safer and shorter.
🔥 Easy interview recall

is → test only, returns bool

as → try, gives null on failure

(T)obj → throws on failure

Think: is pattern (is Cat c) tests and binds in one step — no separate cast needed.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Reaching for an explicit cast when as (or an is pattern) would avoid the exception entirely. If you're not already certain the conversion will succeed, a cast is the risky choice, not the default one.

🔄 Likely Follow-up

"Does as work for value types too?" Only nullable ones — as has to be able to return null on failure, so the target type must be a reference type or a Nullable<T>; a plain non-nullable value type won't compile with as.

🎯 Say this in the interview — the exact lines to land

"is only tests and returns a bool — or with pattern matching, tests and binds in one step. as tries the conversion and gives you null on failure. An explicit cast throws InvalidCastException if it fails — it's the only one of the three that can crash."

  • is pattern (is Cat c) → test and bind in one line, no separate cast.
  • Explicit cast → use only when you're already certain the conversion succeeds.
📖 Explanation ▾

is just answers a yes/no question — "is this object actually a Cat?" — without producing a usable Cat reference on its own (unless you use the pattern-matching form, is Cat c, which tests and hands you c already typed as Cat).

as attempts the same conversion but hands back the result directly — a working Cat reference on success, or null on failure. It never throws, which is exactly why it can't be used for non-nullable value types: there's no "null" for it to fall back to.

An explicit cast — (Cat)o — is the one with no safety net. It's the right tool only when failure genuinely isn't expected; using it "just in case" is what turns a normal type mismatch into an unhandled exception.

💻 See the code ▾
C# 
object o = new Dog();
if (o is Cat c)
    c.Meow();                 // never runs — o isn't a Cat
else
    Console.WriteLine("not a cat");  // ✅ runs, no exception

is with a pattern tests and binds in one line — no separate cast statement needed.

C# 
Cat? maybeCat = o as Cat;
if (maybeCat != null)
    maybeCat.Meow();          // ✅ safe — skipped if o wasn't a Cat

as never throws — a failed conversion is just null, checked like any other reference.

C# 
Cat c = (Cat)o;   // ❌ throws InvalidCastException — o is a Dog

The explicit cast assumes success — when that assumption is wrong, it's the only one of the three that crashes.

🌍 Real-world example ▾

You're filtering a mixed box of shapes for circles. You wouldn't grab every item and force it to be a circle (that's the explicit cast, and it breaks on the first square). You'd check each one first (is), or try to treat it as a circle and set it aside if it doesn't fit (as).
