On-Demand vs. Reserved vs. Spot — what's the actual decision?

"On-Demand vs. Reserved vs. Spot — what's the actual decision, and what happens to an EBS volume when the instance terminates?"

Why it matters ▾
🔓 On-Demand
❗ ProblemCommitting to a 1-3 year Reserved rate before you actually know a workload's usage pattern risks locking into years of payments for capacity you might not need.
✅ SolutionOn-Demand bills per second with zero commitment — you pay full price, but billing stops the instant you stop the instance, with no risk.
RecallOn-Demand = no strings attached, full price, stop any time.
📅 Reserved
❗ ProblemA steady, predictable workload paying full On-Demand price hour after hour is an expensive default for usage that was never actually a gamble.
✅ SolutionReserved Instances / Savings Plans trade a 1-3 year commitment for a significant discount — but that flat committed rate is billed every period whether the instance runs or not.
RecallReserved = commit 1-3 yrs, save money, billed flat regardless of use.
⚡ Spot
❗ ProblemFault-tolerant, interruptible work like batch jobs still gets billed at full On-Demand rates by default, even though it doesn't actually need guaranteed availability.
✅ SolutionSpot sells AWS's spare capacity at the deepest discount, with the trade that AWS can reclaim it with only a 2-minute interruption notice — safe only for jobs that checkpoint and resume.
RecallSpot = cheapest, but AWS can reclaim it with 2 minutes' notice.
🔥 Easy interview recall

On-Demand → no strings attached, pay full price

Reserved → commit 1-3 yrs, save money

Spot → cheapest, but can vanish

Think: On-Demand is flexible. Reserved is a steady bet. Spot is a cheap seat you might get bumped from.

⚠️ Common Trap

Spot is just "cheaper On-Demand." It isn't — Spot capacity can be reclaimed with only a 2-minute warning, so it's only safe for fault-tolerant, interruptible work (batch jobs, stateless web tiers behind an Auto Scaling group), never for a stateful workload that can't checkpoint and resume.

🔄 Likely Follow-up

"What happens to an EBS volume when the instance terminates?" By default the root EBS volume is deleted on termination unless "Delete on Termination" is explicitly disabled — a common source of "why did my data disappear" surprise.

🎯 Say this in the interview — the exact lines to land

"On-Demand for flexibility, Reserved for steady predictable load, Spot for interruptible workloads — that's the whole decision. And separately, EBS's root volume is deleted by default when the instance terminates, unless Delete on Termination is turned off."

  • On-Demand → default choice for unpredictable or short-lived needs, no commitment.
  • Reserved / Savings Plans → commit 1-3 years for a steady, predictable workload's discount.
  • Spot → deepest discount, but only for fault-tolerant work that can survive a 2-minute reclaim notice.
  • EBS default → the root volume's "Delete on Termination" is on by default; extra attached volumes default the other way and persist.
📖 Explanation ▾

On-Demand bills by the hour or second with no upfront commitment — it's the most flexible option and the most expensive per hour of compute. Reserved Instances and Savings Plans trade a 1- or 3-year commitment for a meaningfully lower rate, which only pays off if the workload is actually running steadily enough to use that commitment. Spot Instances sell AWS's spare EC2 capacity at a steep discount, with the catch that AWS can take that capacity back — the instance gets a 2-minute interruption notice before it's reclaimed.

Storage is a separate decision from pricing model. An EBS volume is persistent, network-attached block storage — it survives an instance stop, and by default the root volume is also removed automatically when the instance terminates (its "Delete on Termination" attribute defaults to on); any additional EBS volumes attached to the instance default the other way and are kept after termination. Instance store volumes are physically attached to the underlying host and are always ephemeral — their data is wiped on stop or terminate, with no "keep it" option.

💻 See the code ▾
AWS CLI 
aws ec2 run-instances \
  --image-id ami-0abcd1234efgh5678 \
  --instance-type m5.large \
  --instance-market-options '{"MarketType":"spot"}' -- ❗ asks for Spot capacity
  --count 1

Drop --instance-market-options entirely and the exact same call is a normal On-Demand request — the flag is the whole difference.

🧭 Use Cases — recognize these when they happen to you ▾
1 You just launched a new service and have no idea yet what its traffic pattern will look like

This is the #1 scenario you'll actually run into — until you have months of steady usage data, committing to Reserved pricing is a bet you can't back yet. On-Demand costs more per hour, but nothing is locked in and billing stops the instant you stop the instance.

RememberNew or unpredictable load → stay On-Demand until the pattern is proven.
2 You've watched a service run at steady, predictable load for months and it isn't going away

That's exactly the profile Reserved Instances or Savings Plans are built for — a 1-3 year commitment turns proven steady usage into a real discount. Commit before the usage is actually proven, though, and you're paying that flat committed rate anyway on the months it barely runs.

RememberSteady, proven load → commit to Reserved for the discount.
3 You've got a nightly batch job that checkpoints its progress and can resume right where it left off

That's the one workload shape that can safely absorb Spot's 2-minute interruption notice — an occasional reclaim just delays that one job a few minutes, and in exchange you get Spot's deepest discount. Try this on a stateful job that can't checkpoint, and a reclaim mid-job loses real work instead of just resuming.

RememberCheckpointable, interruptible work → Spot for the deepest discount.
🌍 Real-world example ▾

A company runs its steady-state web tier on Reserved Instances or a Savings Plan, since that traffic is predictable enough to justify the commitment. Its nightly batch-processing fleet runs on Spot instead — the jobs checkpoint their progress and resume cleanly, so an occasional interruption just delays that one job a few minutes instead of losing anything.
