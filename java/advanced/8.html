🔥 Java · Advanced · Must Know

Same write, same program — why might another thread never see it?

"Why isn't a visible-looking write in one thread guaranteed to be seen by another thread?"

Why it matters ▾
🧠 Happens-Before
❗ ProblemWithout an explicit ordering guarantee between threads, a compiler or CPU is free to reorder, cache, or delay a write — so a plain field write in one thread can look like it never happened to a thread reading the same field, with no exception and no crash, just a value that's wrong only sometimes.
✅ SolutionThe Java Memory Model (JMM) defines exactly which actions are guaranteed to be visible across threads through a happens-before relationship — established by synchronized, volatile, a thread's start()/join(), and the concurrency utilities. Without one, there's no promise of visibility at all — not even a stale-but-eventually-correct read.
RecallNo happens-before edge → no visibility guarantee, not just a delay.
🔥 Easy interview recall

Happens-before = "the only thing that guarantees thread B ever sees thread A's write."

Think: synchronized, volatile, Thread.start()/join(), and the concurrency utilities all create one. Everything else is just luck.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"It worked in my testing" is not evidence of thread-safety. The JMM explicitly permits a compiler or CPU to reorder or cache memory operations in ways that only surface as a bug under specific timing, hardware, or JIT-optimization conditions — a race can pass thousands of test runs and still be wrong.

🔄 Likely Follow-up

"What specifically creates a happens-before edge in Java?" A synchronized block's exit happens-before the next thread's entry on the same lock, a volatile write happens-before a later volatile read of that same field, and Thread.start() happens-before anything the started thread does — plus the higher-level concurrency utilities (e.g. a CompletableFuture completing happens-before .get() returning).

🎯 Say this in the interview — the exact lines to land

"The JMM only guarantees thread B sees thread A's write if there's a happens-before edge between them — through synchronized, volatile, thread start/join, or a concurrency utility. Without one, visibility isn't guaranteed at all, not just delayed."

  • No happens-before edge → no visibility guarantee, not a guaranteed-but-late value.
  • synchronized → lock release happens-before the next acquire on the same monitor.
  • volatile → a write happens-before a later read of that same field.
  • Thread.start()/join() → the parent's prior actions happen-before the child starts, and the child's actions happen-before join() returns.
  • "Worked in testing" → not evidence of thread-safety — reordering bugs are timing- and hardware-dependent.
📖 Explanation ▾

The Java Memory Model exists because a modern CPU and a JIT compiler both do real work to go fast — caching a value in a core's own cache line, reordering independent instructions, keeping a variable in a register instead of writing it back to main memory right away. All of that is invisible and harmless for a single thread. Across threads, with no coordination, it means a write in Thread A has no promise of ever becoming visible to Thread B at all.

A happens-before relationship is the JMM's own name for the coordination that closes that gap. It's established a small number of specific ways: a synchronized block's unlock happens-before the next thread's lock on the same monitor; a volatile write happens-before a later volatile read of that field (and, critically, happens-before pulls along every plain write that occurred earlier in the same thread too); Thread.start() happens-before the started thread's first action, and the started thread's last action happens-before a join() on it returns; and the higher-level concurrency utilities (java.util.concurrent) establish their own happens-before edges internally.

Without one of those, the JMM makes no promise — not "probably fine," not "eventually consistent," just undefined. That's what makes these bugs so unpleasant: the exact same code can pass every test on one machine and silently misbehave on another, or under load, because nothing about the language ever guaranteed visibility in the first place.

💻 See the code ▾
Java 
class Flag {
    private boolean ready = false; // not volatile
    private int value;

    void writer() {
        value = 42;
        ready = true;      // writer thread sets it
    }

    void reader() {
        while (!ready) {}  // ❌ no happens-before edge to writer()
        System.out.println(value);
    }
}

With no happens-before edge between writer() and reader(), the JVM is free to never make ready's new value visible to the reader thread — a documented, real possibility, not a hypothetical.

Java 
class Flag {
    private volatile boolean ready = false; // ✅ establishes happens-before
    private int value;

    void writer() {
        value = 42;       // a plain write
        ready = true;       // volatile write — the happens-before edge
    }

    void reader() {
        while (!ready) {}   // volatile read observes the write
        System.out.println(value); // ✅ also guaranteed visible
    }
}

Marking just ready volatile is enough — the JMM guarantees every plain write that happened earlier in the writer thread (like value = 42) is visible too, once the reader observes ready == true.

🧭 Use Cases — recognize these when they happen to you ▾
1 You read a flag set by another thread, with no synchronized or volatile

A worker thread looping on a plain (non-volatile) field it never synchronizes on has no guarantee it ever observes the write — it can spin past the shutdown signal indefinitely. A common interview trap: assuming it'll "catch up eventually" even without an edge.

RememberNo edge → may never see it, not just see it late.
2 You publish an object safely through a thread-safe mechanism

A thread-safe collection like BlockingQueue establishes its own happens-before edge internally between put() and take() — the consuming thread is guaranteed to see the fully-constructed object, no manual synchronized/volatile needed on your part.

RememberConcurrency utilities carry their own happens-before edge.
3 Two threads both guard the same field with the same lock

Guarding both the write and the read with synchronized blocks on the same lock object gives a guaranteed happens-before edge — the unlock from the writer's block happens-before the lock acquire in the reader's block.

RememberSame lock on both sides → visibility is guaranteed.
🌍 Real-world example ▾

A background worker thread never notices a shutdown flag the main thread sets, even though a debugger confirms the flag really did flip to true. Because the flag isn't volatile and nothing synchronizes on it, there's no happens-before edge between the main thread's write and the worker's read — the worker may keep spinning on a stale cached value indefinitely. Marking the field volatile establishes the edge it needs to actually observe the write.
