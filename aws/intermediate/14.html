ECS, EKS, Lambda — how much orchestration do you actually need?

"ECS vs. EKS vs. Lambda for microservices — how do you actually decide?"

Why it matters ▾
📦 ECS
❗ ProblemA team running a dozen AWS-only microservices doesn't want to take on Kubernetes' learning curve and operational overhead just to keep containers running.
✅ SolutionECS is AWS's own container orchestrator — a task definition describes the container, an ECS service keeps the right number of tasks running, and Fargate removes instance management entirely.
RecallECS = AWS's own orchestrator, simplest ops.
☸️ EKS
❗ ProblemA team already has Kubernetes-specific tooling — Helm charts, a custom operator — or genuinely needs multi-cloud portability, and ECS's own API doesn't give them that.
✅ SolutionEKS is managed Kubernetes — AWS runs the control plane, but you get the real K8s API and its ecosystem: Helm charts, operators, K8s-native tooling.
RecallEKS = managed Kubernetes, more power/complexity.
⚡ Lambda
❗ ProblemA workload only needs to run in response to an event and then stop — keeping an ECS or EKS task alive around the clock for that would mean paying for containers that sit idle.
✅ SolutionLambda runs your function on trigger and stops — no containers, no orchestrator, no instances to choose at all.
RecallLambda = event-driven, no persistent service.
🔥 Easy interview recall

ECS → AWS's own orchestrator, simplest ops

EKS → managed Kubernetes, more power/complexity

Lambda → event-driven, no persistent service

Think: Fargate → no servers to manage, for either ECS or EKS EC2 launch type → you manage the instances, cheaper at steady scale

⚠️ Common Trap

"We should use EKS because Kubernetes is the industry standard." For most AWS-only microservice workloads, ECS (especially on Fargate) gives simpler operations without Kubernetes' learning curve and operational overhead — EKS earns its complexity when you genuinely need Kubernetes-specific tooling or portability, not by default.

🔄 Likely Follow-up

"Fargate vs. EC2 launch type — the real tradeoff?" Fargate trades some cost efficiency and low-level control for zero instance management; the EC2 launch type is cheaper at steady, predictable scale and gives you control over instance types/placement, at the cost of managing the underlying fleet yourself.

🎯 Say this in the interview — the exact lines to land

"I'd reach for ECS for simpler AWS-native container operations, EKS when the team genuinely needs Kubernetes itself, and Fargate removes instance management from either one. Lambda fits when the workload is event-driven rather than a persistent service."

  • ECS → AWS's own orchestrator, simplest operational model, tightly integrated with other AWS services.
  • EKS → managed Kubernetes — reach for it when you need the real K8s API, Helm charts, or portability.
  • Fargate → serverless compute mode for both ECS and EKS — no EC2 instances to manage, just CPU/memory per task.
  • EC2 launch type → you manage the fleet — more control and cost-efficiency at scale, more operational burden.
  • The real signal for EKS: a genuine need for Kubernetes-specific tooling already built elsewhere — not "Kubernetes is popular."
📖 Explanation ▾

ECS (Elastic Container Service) is AWS's own container orchestrator. An ECS task is one running instance of a task definition (the blueprint describing the container image, CPU/memory, and networking); an ECS service keeps a specified number of tasks running — similar in spirit to an Auto Scaling Group, but for containers instead of EC2 instances. EKS (Elastic Kubernetes Service) is managed Kubernetes — AWS runs the control plane, but you're working with the real Kubernetes API and its ecosystem (Helm charts, K8s-native operators/tooling, and the portability of standard Kubernetes manifests).

Both ECS and EKS need somewhere to actually run their containers. Fargate is a serverless compute mode available to both — you specify the container's CPU and memory, and AWS handles the underlying instances entirely. The EC2 launch type is the alternative for either service: you manage the EC2 instances the containers run on yourself, which gives more control over instance types and placement and can be more cost-efficient at steady, predictable scale, at the cost of the operational work of managing that fleet.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're running a dozen AWS-only microservices and just want them to stay up, simply

The task definition is the blueprint; the ECS service keeps the right number of tasks running for you automatically. Add Fargate and there's no server fleet to patch either. This is the #1 scenario you'll actually run into.

RememberAWS-only microservices, simple ops → ECS (+ Fargate).
2 Your team already has Kubernetes tooling built elsewhere — Helm charts, a custom operator — or genuinely needs multi-cloud portability

EKS gives you the actual Kubernetes API and scheduler, so Helm charts, operators, and standard K8s manifests all just work — that genuine need for K8s-specific tooling or portability is the real reason to take on the extra complexity, not because Kubernetes is the industry standard.

RememberGenuine need for K8s tooling/portability → EKS, not "K8s is standard."
3 Your workload only fires on an event — a file upload, a queue message — and sits idle the rest of the time

Lambda runs the function only when triggered and stops right after — there's no persistent service, no containers, and no instance choice to make at all, unlike every ECS/EKS option above.

RememberEvent-driven, not a persistent service → Lambda, skip containers entirely.
🌍 Real-world example ▾

A startup runs its dozen microservices on ECS with Fargate and only migrates to EKS once an acquired team brings along a Kubernetes-specific operator they'd already built — a concrete, genuine need for the Kubernetes API, not a switch made just because Kubernetes is the industry standard.
