MCP — one client, any number of standardized servers

"What is MCP, and what problem does it solve that plain function/tool calling doesn't?"

Why it matters ▾
🔌 Custom Integration
❗ ProblemConnecting an AI app to a tool or data source needs some way to make the call, and with no shared protocol to lean on there's no standard way to do it.
✅ SolutionWrite bespoke glue code that wires this one app directly to this one tool — it works, but only for that exact pairing, so every new app-tool combination needs its own one-off integration (an "N apps × M tools" problem).
RecallCustom integration = one app, one tool, hand-wired — doesn't scale past a few pairings.
🧩 MCP
❗ ProblemCustom integration's glue code can't be reused — a second app that wants the same tool has to write its own one-off integration all over again, and that cost multiplies as apps and tools grow.
✅ SolutionMCP standardizes how a server exposes its Tools, Resources, and Prompts — write the server once, and any MCP-compliant client can discover and use it, turning N×M bespoke integrations into N clients + M servers.
RecallMCP = one server, written once, reusable by any compliant client — no per-tool glue code.
🔥 Easy interview recall

Custom integration → one app wired to one tool, by hand

MCP → any client talks to any compliant server

Server exposes → Tools, Resources, Prompts

Think: MCP is a common plug shape, not a new kind of socket.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

MCP isn't a replacement for function/tool calling — it's the standardized layer on top of it. The model still calls tools the same way it always did (see Function/Tool Calling); MCP standardizes how those tools and data sources get exposed and discovered across different apps, so the same server can be reused by any MCP-compliant client instead of every app wiring its own bespoke integration.

🔄 Likely Follow-up

"How is this different from just giving the model a list of function definitions, like in the agent loop?" The agent loop's tool-calling mechanic (see the Agent Loop) is still how the model decides to call something — MCP is about where those tools/resources come from: a standard server any client can connect to, instead of that same list being hand-defined and wired separately inside every single application.

🎯 Say this in the interview — the exact lines to land

"MCP is an open, standardized protocol for connecting an AI application to external tools and data sources. An MCP server exposes Tools, Resources, and Prompts over a standard interface, and any MCP-compliant client can discover and use them — so instead of every app writing its own one-off integration for every tool, you write the server once and any compliant client can use it."

  • MCP server → exposes capabilities — Tools, Resources, Prompts — over a standard interface.
  • MCP client → the agent/app host — connects to one or more servers and discovers what they offer.
  • Core value → N clients + M servers, not N×M bespoke integrations, one per app-tool pairing.
  • Not a new tool-calling mechanic → standardizes exposure/discovery of the tools, not how the model decides to call one.
📖 Explanation ▾

MCP (Model Context Protocol) is an open, standardized protocol for connecting AI applications — specifically LLM-based apps and agents — to external tools, data sources, and systems. It defines a client-server architecture: an MCP server exposes a set of capabilities — Tools (functions the model can call), Resources (data the model can read, like files, database rows, or documents), and Prompts (reusable prompt templates) — over a standard interface. An MCP client is the AI application or agent host; it connects to one or more of these servers and can discover and use whatever capabilities each one exposes.

The point isn't a new way for a model to decide to call something — that mechanic is the same function/tool calling covered on the Function/Tool Calling page, wired into the same kind of loop covered on the Agent Loop page. The point is standardizing how tools and data get exposed and discovered across systems. Without a shared protocol, every application that wants to use a given tool writes its own one-off integration for it — an "N apps × M tools" problem. Write an MCP server once for a tool or data source, and any MCP-compliant client can use it, turning that into "N clients + M servers," each side implementing the protocol once instead of every pairing needing its own bespoke glue code.

💻 See the code ▾
Pseudocode 
# One MCP server exposes its capabilities once
server = McpServer("files-server")
server.add_tool("search_files", handler=search_files)      # callable function
server.add_resource("docs/readme.md")                    # readable data
server.add_prompt("summarize_doc", template=summarize_tmpl) # reusable template

This server is written once — its Tools, Resources, and Prompts are now discoverable by any compliant client.

Pseudocode 
# Any MCP client can connect to multiple servers, no per-tool glue code
client = McpClient(agent=my_agent)
client.connect("files-server")     # ✅ same protocol
client.connect("search-server")    # ✅ different server, same protocol
tools = client.discover_tools()   # pulled from every connected server

The client discovers each server's capabilities the same way regardless of which server it is — no server-specific integration code.

🧭 Use Cases — recognize these when they happen to you ▾
1 You've got exactly one app hardwired to call exactly one tool

For a single app-tool pairing, custom integration is the simplest option — you write the glue code once, direct, no protocol to learn. This is the case custom integration was never a problem for.

RememberOne app, one tool → hand-wired custom integration is fine.
2 A second app now needs the exact same tool or data source your first app already uses

Without MCP, the new app has to write its own one-off integration for that same tool all over again — the N apps × M tools problem. Write one MCP server for that tool instead, and the new app can connect and discover it the same way the first app did, with no new integration work on either side.

RememberSecond app, same tool → reuse the MCP server, don't rewrite the glue code.
3 You assume adopting MCP changes how the model decides to call a tool

MCP doesn't change how the model decides to call a tool — that's still the same function/tool-calling mechanic used inside the agent loop. What MCP standardizes is where those tools and data sources come from and how a client discovers them. A common trap — candidates sometimes describe MCP as a new tool-calling mechanic instead of the standardized layer on top of the existing one.

RememberMCP standardizes exposure/discovery, not how tools get called.
🌍 Real-world example ▾

A team builds one MCP server for their internal ticketing system and one for their document store. Their chat agent connects to both as an MCP client and can use whichever a request needs. Later, a second internal tool — an entirely different AI app — connects to the same two servers and gets the same capabilities immediately, with no new integration work on either side.
