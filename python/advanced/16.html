WSGI is a synchronous, one-request-at-a-time contract — ASGI exists specifically to add async to that contract

WSGI vs. ASGI? Flask vs. FastAPI vs. Django? What's actually different about async endpoints?

Why it matters ▾
  • Framework-choice questions come up constantly once a role touches web APIs — knowing why you'd pick FastAPI over Flask matters more than reciting feature lists.
  • "Just make it async def" is a very common wrong instinct — this is the exact spot the asyncio page's blocking-the-event-loop trap shows back up in a web framework's own request handling.
  • A frequent interview opener once concurrency comes up at all: "what's actually different between WSGI and ASGI?"
🔥 Easy interview recall

WSGI → synchronous, one request per worker at a time

ASGI → WSGI's async-native successor

async def → only helps if every I/O call inside is also async

Think: ASGI didn't replace WSGI's contract — it added async on top of it.

🧠 Visual Mental Model — the same request pipeline, two different endings
⚠️ Common Trap

Marking a Flask/Django endpoint async def doesn't automatically make it faster or non-blocking. If the ORM, database driver, or HTTP client it calls inside isn't ALSO async-native, that call still blocks — you've only added async syntax around the exact same blocking work, and risk the asyncio page's own event-loop-freezing trap in the process.

🔄 Likely Follow-up

"When would you pick FastAPI over Flask for a new Python API?" When you want type-hint-driven request validation/serialization and automatic OpenAPI docs with less manual wiring, and especially when the workload genuinely benefits from native async I/O throughout the stack — Flask stays reasonable for simpler, sync-first services or when you want more direct control.

🎯 Say this in the interview — the exact lines to land

"Switching to async def only helps if every I/O call inside it is also genuinely async — otherwise you've just added syntax around the same blocking calls. ASGI is WSGI's async-native successor, not a totally separate standard."

  • Flask → minimal and unopinionated — you assemble the pieces yourself, sync-first on WSGI.
  • FastAPI → ASGI-native, type-hint-driven — automatic request validation/serialization and OpenAPI docs.
  • Django → batteries-included (ORM, admin, auth, templating) — historically WSGI/sync-first, now with growing async support.
  • async def only pays off when every I/O call inside it is also async — one blocking call reintroduces the freeze.
📖 Explanation ▾

WSGI (Web Server Gateway Interface) is the original standard interface between a Python web app and a web server — fundamentally synchronous: one worker handles one request at a time, start to finish. Flask and classic Django are built on it. ASGI (Asynchronous Server Gateway Interface) is the newer standard that adds native support for async/await, WebSockets, and long-lived connections, while staying backward-compatible with sync-style handling too — FastAPI is ASGI-native, and Django has grown ASGI support over time.

A request's lifecycle is the same shape either way: it arrives, routing matches it to a handler, middleware runs before and after that handler, the handler itself runs (often just calling into business logic — see the Production Python Architecture page), and a response is serialized and returned. FastAPI's own idiom for wiring dependencies into a handler — a database session, a config object — is dependency injection: declaring them as ordinary function parameters that the framework resolves and injects automatically.

An async def handler can genuinely await I/O without blocking the worker from handling other concurrent requests in the meantime — but that's only true if every I/O call inside it is also properly async; one blocking call still freezes the whole worker for its duration. Two supporting patterns worth knowing by name: connection pooling (reusing a fixed set of already-open database/HTTP connections instead of opening a new one per request) and handing off work that shouldn't block the request/response cycle to a background task queue instead of running it inline.

💻 See the code ▾
Python 
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    # ✅ an async-native driver — the worker is free during this wait
    user = await db.fetch_one("SELECT * FROM users WHERE id = :id", id=user_id)
    return user

While this await is waiting on the database, the same worker can pick up and serve other requests.

Python 
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    # ❌ a SYNC driver call inside an async def — still blocks the worker
    user = sync_db.fetch_one("SELECT * FROM users WHERE id = :id", id=user_id)
    return user  # async syntax, zero actual concurrency benefit

Same async def, same route — but this call blocks the whole worker exactly like a sync framework would, because nothing inside it ever actually yields control back to the event loop.

🌍 Real-world example ▾

A team migrated a high-concurrency API from Flask to FastAPI expecting an automatic throughput win, and saw none — because their ORM and database driver were still the same synchronous ones from the Flask app. Every async def handler still called a blocking driver underneath, so each request still held the worker for its full duration. Throughput only improved once they also swapped in an async-native database driver, so the await calls were genuinely non-blocking end to end.
