Template Method — the skeleton stays fixed, only the steps change

"What is the Template Method pattern, and what is the Hollywood Principle it relies on?"

Why it matters ▾
🧩 Template Method
❗ ProblemSeveral subclasses need the same overall algorithm (fetch, format, write) but a few individual steps genuinely differ per subclass — copying the whole method into each subclass duplicates the fixed parts and risks the steps running in the wrong order.
✅ SolutionTemplate Method puts the fixed sequence in one base-class method and defers only the differing steps to abstract or virtual methods the subclasses override — the order never changes, only what each step does.
RecallTemplate Method = fixed skeleton in the base class, swappable steps in the subclass.
🔥 Easy interview recall

Template Method = "fixed steps, in a fixed order, some filled in by the subclass."

Think: AbstractClass → owns the template method and its fixed order ConcreteClass → overrides only the steps it needs to Hollywood Principle → "don't call us, we'll call you" — base calls into the subclass

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Template Method is not Strategy. Template Method varies individual steps by inheritance — overriding a protected method in a subclass ("white-box reuse"); Strategy varies the whole algorithm by composition — injecting a different interface implementation ("black-box reuse").

🔄 Likely Follow-up

"Isn't this the same as a subclass just calling a shared helper method?" No — the direction is reversed. The base class's template method calls the subclass's overridden step (the Hollywood Principle); the subclass never calls back up into the base to run the sequence itself.

🎯 Say this in the interview — the exact lines to land

"Template Method defines the algorithm's fixed sequence in a base-class method, and defers specific steps to abstract or virtual methods subclasses override. It follows the Hollywood Principle — don't call us, we'll call you — the base class calls the subclass's step, not the reverse. That's different from Strategy, which swaps the whole algorithm via composition instead of inheritance."

  • Template method → fixed call order, defined once in the base class.
  • Steps → abstract (must override) or virtual (optional default).
  • Hollywood Principle → base class calls the subclass's step, never the reverse.
  • vs Strategy → inheritance + override steps, not composition + swap algorithm.
  • Reuse style → white-box (subclass sees the base's structure), not black-box.
📖 Explanation ▾

AbstractClass defines the template method — one public method that calls a fixed sequence of "primitive" step methods. Some steps are abstract (a subclass must supply them), others are virtual with a sensible default a subclass can optionally override. The order those steps run in is decided once, in the base class, and never changes.

The name for the direction of control is the Hollywood Principle — "don't call us, we'll call you." A ConcreteClass never calls the sequence itself; the base class's template method calls into the subclass's overridden step at the right moment. That inversion — base calling down into the subclass, not the subclass calling up into a shared helper — is the actual hallmark of this pattern, not just "a subclass overrides something."

💻 See the code ▾
C# 
abstract class DataExporter
{
    public void Export()                              // ✅ the template method — fixed order
    {
        var data = FetchData();
        var formatted = FormatData(data);
        WriteOutput(formatted);
    }

    protected abstract IEnumerable<Row> FetchData();          // must override
    protected virtual string FormatData(IEnumerable<Row> rows)
        => DefaultFormat(rows);                                          // optional override
    protected abstract void WriteOutput(string content);         // must override
}

AbstractClass — Export() never changes. Only the steps marked abstract/virtual get filled in differently per subclass.

C# 
class CsvExporter : DataExporter
{
    protected override IEnumerable<Row> FetchData()
        => _repository.GetAllRows();                 // ✅ Export() calls THIS, not the other way around

    protected override void WriteOutput(string content)
        => File.WriteAllText("report.csv", content);

ConcreteClass — supplies only the two steps it needs to; Export() itself is inherited untouched, and FormatData() keeps the base's default.

🌍 Real-world example ▾

A standardized exam procedure. Check in, take the exam, submit — the sequence never changes, but the actual content of "take the exam" differs per subject. A recipe works the same way: prep, cook, plate are fixed steps, while the specific technique in each step varies by dish.
