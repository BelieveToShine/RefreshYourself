Strategy — swap the whole algorithm, not one more branch

"What is the Strategy pattern, and how is it different from a long if/else or switch?"

🧩 Also see the OOP-angle page: Strategy Pattern vs. Conditional Logic
☕ Also see the Java-angle page: Comparable vs. Comparator
Why it matters ▾
🧭 Strategy
❗ ProblemA checkout or shipping flow built as one big if/else or switch over every possible algorithm grows unwieldy fast, and adding one more option means editing that same method again.
✅ SolutionStrategy puts each algorithm behind a common interface and lets the Context hold a reference to whichever one it's given, so a new algorithm is a new class, not a new branch in an existing method.
RecallStrategy = interchangeable algorithms behind one interface, picked by the caller.
🔥 Easy interview recall

Strategy = "pick the algorithm, call it the same way regardless."

Think: Context → holds an IStrategy field swap it → in the constructor, or a setter, at runtime who decides → the caller, not the object itself

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Strategy is not Template Method. Strategy swaps the whole algorithm via composition — inject a different object; Template Method varies one step of a fixed algorithm via inheritance — override a method in a subclass.

🔄 Likely Follow-up

"How is Strategy different from State?" Structurally they look alike — both hold an interface reference and delegate to it — but the intent differs: Strategy is usually picked once by the caller, for reasons external to the object (the user chose express shipping); State transitions are driven by the object's own internal lifecycle, often decided by the current state itself.

🎯 Say this in the interview — the exact lines to land

"Strategy defines a family of interchangeable algorithms behind one interface, and the Context holds a reference to whichever one it's given so the algorithm can vary independently of the code that uses it. It's different from a growing if/else because each algorithm is its own class, and different from Template Method because it swaps the whole algorithm through composition instead of overriding one step through inheritance."

  • IStrategy → one shared method every concrete strategy implements.
  • Context → holds a Strategy reference and delegates, never branches on type.
  • Who decides → the caller, once, for reasons outside the object — unlike State.
  • vs. Template Method → whole algorithm via composition, not one step via inheritance.
  • Real use → routing mode in a maps app, payment method at checkout.
📖 Explanation ▾

Strategy has three parts: the Strategy interface declares one method every algorithm must provide; each ConcreteStrategy (A, B, C…) implements that method its own way; and the Context holds a reference to whichever Strategy it was given and calls it through the interface. The Strategy can be swapped at runtime — usually by passing a different one into the Context's constructor or a setter — without touching the Context's own code at all.

Strategy is easy to mix up with two other patterns that also "vary behavior," but the mechanism differs in each case:

StrategyStateTemplate Method
What variesthe whole algorithmbehavior over the object's lifecycleone or more steps of one fixed algorithm
How it's swappedcomposition — inject a different objectcomposition — the state reassigns itselfinheritance — override a method in a subclass
Who decidesthe caller, externallythe object, via its own transitionsthe base class skeleton, subclass fills gaps
💻 See the code ▾
C# 
public interface IShippingStrategy
{
    decimal CalculateCost(Order order);
}

public class StandardShipping : IShippingStrategy
{
    public decimal CalculateCost(Order order) => order.Weight * 1.0m; // flat rate
}

public class ExpressShipping : IShippingStrategy
{
    public decimal CalculateCost(Order order) => order.Weight * 2.5m; // same shape, different rate
}

Each strategy implements the same interface — the Context never needs to know which concrete one it's holding.

C# 
public class Order
{
    private readonly IShippingStrategy _strategy;

    public Order(IShippingStrategy strategy) => _strategy = strategy; // ✅ caller picks it

    public decimal GetShippingCost() => _strategy.CalculateCost(this); // same call either way
}

var order = new Order(new ExpressShipping()); // the caller decides, not Order itself
order.GetShippingCost();

Order delegates to whatever strategy it was given — swapping the strategy never touches Order's own code.

🌍 Real-world example ▾

Choosing a route in a maps app. "Get directions" is the same call every time, but picking fastest, shortest, or avoid-tolls swaps which strategy object actually computes the route underneath — the app's own code calling it never changes. Choosing a payment method at checkout (card, PayPal, wallet) works the same way.
