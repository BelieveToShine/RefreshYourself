Keeping the same class name from colliding

Why it matters ▾
  • Explains the "the type X exists in both..." compiler error.
  • Every C# file you'll ever read starts with a block of these — worth knowing what they do.
  • A small, easy win to show basic fluency early in an interview.
📖 Explanation ▾

A namespace groups related types under one folder-like name, and gives each type a full, unique address — MyApp.Billing.Invoice is a different type from MyApp.Reports.Invoice, even though both are just called Invoice up close. That's exactly what namespaces are for: letting the same short name exist safely in more than one place.

A using directive imports a namespace into a file so you can use its types by their short name instead of typing the full address every time. If two imported namespaces both have an Invoice, you're back to spelling out the full name to say which one you mean.

💻 See the code ▾ 
namespace MyApp.Billing
{
    public class Invoice { }        // full address: MyApp.Billing.Invoice
}

using MyApp.Billing;                 // import — drop the prefix below

var inv = new Invoice();             // short name works now
var inv2 = new MyApp.Billing.Invoice(); // same thing, spelled in full
🌍 Real-world example ▾

A street address vs. a first name. Two "Sam"s can live in the same city without confusion as long as you know their full address. A namespace is that full address; using someone's first name (the short class name) only works once you've made clear which Sam (which namespace) you're talking about.

🎯 Say this in the interview — the exact lines to land

  • A namespace gives a type a full, unique address — not just a short name.
  • using imports a namespace so you can drop the prefix.
  • Two same-named types from different namespaces need the full name to disambiguate.
  • This is purely an organization tool — it has no effect on runtime behavior.
