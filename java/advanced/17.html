A stage throws — what happens to the rest of the CompletableFuture chain?

"If a stage in a CompletableFuture chain throws, what happens to the rest of the chain?"

Why it matters ▾
🛟 exceptionally()
❗ ProblemAn exception mid-chain skips every remaining thenApply/thenCompose stage — without a recovery step, the caller just gets a failed future.
✅ Solutionexceptionally(fn) catches the failure and recovers with a fallback value, letting the rest of the chain resume normally.
Recallexceptionally = catch, but only for the failure path.
🔀 handle()
❗ ProblemSometimes you need to react no matter how the stage ended — success or failure — without writing two separate callbacks.
✅ Solutionhandle(fn) always runs, and its function receives either the result or the exception (one of the two is always null).
Recallhandle = runs either way, sees both possible outcomes.
👁️ whenComplete()
❗ ProblemLogging or metrics code needs to observe the outcome of a stage without changing what the rest of the chain actually sees.
✅ SolutionwhenComplete(fn) is a side-effect observer — it sees the result/exception but doesn't change the outcome, and re-throws whatever exception came in.
RecallwhenComplete = watch, never change, never swallow.
🔥 Easy interview recall

exceptionally → recover with a fallback value

handle → always runs, sees result or exception

whenComplete → observes only, re-throws

Think: an exception short-circuits every normal stage after it, until one of these three finally catches it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

whenComplete() does not stop the exception. It observes the result or the exception for side effects (logging, metrics) and then re-throws whatever exception it saw — only exceptionally() or handle() actually recover the chain with a new value.

🔄 Likely Follow-up

"What does handle() receive if the stage actually succeeded?" Its function gets (result, null) — the exception argument is null on success, and the result argument is null on failure; exactly one of the two is always populated.

🎯 Say this in the interview — the exact lines to land

"An exception thrown inside any stage short-circuits the normal thenApply/thenCompose chain — those stages are skipped entirely until a stage that handles failure: exceptionally recovers with a fallback value, handle runs regardless and sees either outcome, and whenComplete only observes before re-throwing."

  • Exception mid-chain → every later thenApply/thenCompose is skipped.
  • exceptionally(fn) → recovers with a fallback value, only on failure.
  • handle(fn) → always runs, sees result or exception.
  • whenComplete(fn) → observes only, re-throws whatever it saw.
  • Want to react to both outcomes and change the result? → handle(), not whenComplete().
📖 Explanation ▾

A CompletableFuture chain is built from stages, and each stage either completes normally or completes exceptionally. Once a stage fails, every subsequent thenApply/thenAccept/thenCompose stage simply propagates that same failure forward without running its own function — the callback you wrote for those stages never executes at all.

The three recovery methods differ in what they're allowed to do with that failure. exceptionally only fires on failure and must produce a replacement value. handle fires on both outcomes and can also produce a replacement value either way. whenComplete fires on both outcomes too, but purely for observation — whatever it returns is ignored, and the original outcome (success or the same exception) continues unchanged afterward.

💻 See the code ▾
Java 
CompletableFuture.supplyAsync(() -> riskyLookup())
    .thenApply(v -> v * 2)              // ❌ skipped if riskyLookup() throws
    .exceptionally(ex -> 0);           // ✅ fallback value on failure only

If riskyLookup() throws, thenApply never runs — the chain lands straight on exceptionally with a safe fallback.

Java 
future.handle((result, ex) -> {
    if (ex != null) return fallback(); // result is null here
    return result;                         // ex is null here
});

Exactly one of result/ex is non-null — never both, never neither.

Java 
future.whenComplete((result, ex) -> {
    if (ex != null) log.warn("lookup failed", ex);
    else metrics.record(result);
}); // ❌ does NOT stop ex from propagating further

Purely observational — the returned future still carries the original exception onward if one was present.

🧭 Use Cases — recognize these when they happen to you ▾
1 A downstream call might fail, and a safe default is good enough

A recommendation service that can fall back to a cached or generic result if the live call fails is a textbook exceptionally case — simple, one fallback value, done.

RememberGood-enough fallback → exceptionally().
2 The caller needs uniform handling whether the call succeeded or failed

Building an HTTP response object that looks the same shape whether the underlying call succeeded or failed (just with different fields populated) is a natural fit for handle, since it sees both outcomes in one place.

RememberNeed one unified outcome → handle().
3 Logging inside whenComplete(), expecting it to stop the failure

Logging the failure inside whenComplete feels like "handling" it, but the exception still propagates to whatever's next in the chain. A common interview trap: assuming any callback that "sees" the exception also clears it.

RememberwhenComplete observes → it never clears the exception.
🌍 Real-world example ▾

A price-lookup call occasionally times out, and the UI should show a cached price instead of an error screen. Wrapping the async call with exceptionally(ex -> cache.getLastKnownPrice()) gives the rest of the chain a usable value either way, while a separate whenComplete alongside it can still log the timeout for monitoring, without affecting what the UI actually receives.
