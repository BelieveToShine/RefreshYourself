class — is this a new inheritance model, or the same prototype chain underneath?

"Did ES6 classes replace JavaScript's prototype-based inheritance with something new?"

Why it matters ▾
  • Checks whether you understand class sits on top of the same object model from Prototypes & Prototype Chain — a common way interviewers separate "knows the keyword" from "understands the engine."
  • Comes up any time someone debugs why a private field (#x) behaves differently from an underscore-prefixed "private-by-convention" field, or why extends makes instanceof work across two classes.
  • A near-guaranteed follow-up once prototypes have already come up in the same interview.
🔥 Easy interview recall

class → just syntax over prototypes

extends → wires up the same [[Prototype]] chain

Think: a class's methods still live on ClassName.prototype — nothing new was invented under the hood, it's a cleaner way to write what prototypes always did.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Classes are a new inheritance model, separate from prototypes." They're not — class is syntax layered over JavaScript's existing prototype-based object model: a class's methods still live on ClassName.prototype, extends still sets up a normal prototype chain, and instanceof still works by walking that same chain.

🔄 Likely Follow-up

"If classes are just prototypes, why does a derived class's constructor have to call super() before touching this?" Because this isn't created until the base class's constructor runs — a derived constructor has no this to work with until super() finishes, so touching it earlier throws a ReferenceError.

🎯 Say this in the interview — the exact lines to land

"class is syntax over JavaScript's existing prototype system — it didn't replace it. A class's methods still live on ClassName.prototype, extends still links the two prototype objects together, and instanceof still walks that same chain to decide the answer."

  • class → syntax over prototypes, not a new object model.
  • Methods in a class body → non-enumerable properties on ClassName.prototype, same place a manually-assigned prototype method would go.
  • extends → wires up the [[Prototype]] link between the two prototype objects.
  • Private fields (#field) → truly inaccessible from outside the class, unlike an underscore-prefixed field that's only private by convention.
  • static members → live on the constructor function itself, not on instances.
📖 Explanation ▾

Before class existed, building an inheritance chain meant wiring it by hand: Child.prototype = Object.create(Parent.prototype), then calling Parent.call(this, ...) inside the child's own function. class doesn't change what happens underneath — it's the same prototype-based model, wrapped in syntax that reads like inheritance in a classical OOP language. constructor is just the function that runs on new; every other method written in the class body gets attached to ClassName.prototype, not copied onto each instance.

extends sets up two prototype links at once: the derived class's .prototype points to the base class's .prototype (so instances look up methods through both), and the derived class's constructor is itself linked to the base constructor (so static members inherit too). super(...) calls the base class's constructor — mandatory before a derived constructor can touch this, because this doesn't exist until the base constructor builds it. super.methodName() inside an overriding method calls the base class's version instead of the overridden one.

Getters and setters (get/set) let a property read and write like a plain field while running code behind the scenes — validation on write, a computed value on read. static methods and fields live on the class itself, not on instances, which is why they're used for factories and shared counters. Private fields (#name) are enforced by the engine, not just a naming habit — code outside the class can't read, write, or even detect that a #field exists, unlike an _underscore field, which is still a perfectly normal, accessible property that only "looks" private.

💻 See the code ▾
JavaScript 
class Animal {
  constructor(name) {
    this.name = name;                 // set on the instance
  }
  speak() {                             // lives on Animal.prototype
    return `${this.name} makes a sound`;
  }
}

class Dog extends Animal {    // extends → links the prototype chain
  speak() {
    return `${super.speak()} — specifically, a bark`; // super calls Animal's version
  }
}

new Dog("Rex").speak(); // "Rex makes a sound — specifically, a bark"

Dog's speak() doesn't replace Animal's — super.speak() calls it directly, the same as manually calling Animal.prototype.speak.call(this) would.

JavaScript 
class BankAccount {
  #balance = 0;                // private — invisible outside the class

  static accountsOpened = 0;   // lives on the class itself, not instances

  constructor() {
    BankAccount.accountsOpened++;
  }

  get balance() {              // read like a plain property
    return this.#balance;
  }
  set balance(amount) {        // runs validation on write
    if (amount < 0) throw new Error("Balance can't go negative");
    this.#balance = amount;
  }
}

const acc = new BankAccount();
acc.balance = 100;   // ✅ goes through the setter
acc.#balance;        // ❌ SyntaxError — #balance isn't reachable from outside

#balance is enforced privacy, not a naming habit — code outside the class can't read it, unlike an _balance field, which is just an ordinary accessible property.

JavaScript 
typeof Dog.prototype.speak;                                   // "function" — speak() lives on the prototype
Object.getPrototypeOf(Dog.prototype) === Animal.prototype;  // true — extends wired this up
new Dog("Rex") instanceof Animal;                            // true — walks that exact chain

None of this is class-specific machinery — it's the same [[Prototype]] chain from Prototypes & Prototype Chain, just wired up automatically by extends.

🌍 Real-world example ▾

A REST API defines ValidationError and NotFoundError, both extending a shared AppError base class. A single top-level error handler can check err instanceof AppError to decide "did my own code throw this, or did something unexpected blow up" — and that check only works because extends put every custom error class on the same prototype chain as AppError.
