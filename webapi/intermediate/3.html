/orders/{id} vs. ?status= — which one changes WHAT you're asking for?

When does a value belong in a route parameter versus a query parameter?

Why it matters ▾
🔑 Route parameter
❗ ProblemCram WHICH resource into a query string instead (/orders?id=42) and every order looks like a variation of the same URL — harder to cache, bookmark, or reason about, and it breaks REST convention.
✅ SolutionPut the value that identifies WHICH resource in the path — /orders/{id} — so each resource gets its own stable, cache-friendly URL.
RecallRoute param = identity lives in the path.
🔎 Query parameter
❗ ProblemCram a filter into the path instead (/orders/status/shipped) and you end up inventing endless path combinations for what's really one endpoint with options.
✅ SolutionPut filtering, sorting, or paging values in the query string — /orders?status=shipped — so the base resource stays one endpoint, and removing the value just widens the result.
RecallQuery param = narrows or defaults, never changes WHAT you're asking for.
🔥 Easy interview recall

Route param → which resource you mean

Query param → how to narrow or shape it

Think: Remove it and the URL points at something different → route. Remove it and the URL just gets wider → query.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

/orders?id=42 is not a substitute for /orders/42. It runs fine, but it hides the resource's identity inside a filter — breaking the convention that WHICH resource you mean lives in the path, and making the URL less cache- and bookmark-friendly.

🔄 Likely Follow-up

"Where does a value that's partly identifying but optional go — like an API version, or an 'include related data' flag?" Almost always a query parameter (or a header) — /orders/42 is already a complete, meaningful request on its own, even before you decide whether to also add ?expand=customer.

🎯 Say this in the interview — the exact lines to land

"A route parameter identifies WHICH resource you're asking for — the resource doesn't make sense without it. A query parameter refines a request that's already valid on its own, like filtering, sorting, or paging a collection."

  • Route parameter → part of the resource's identity, remove it and the URL means something else, or nothing.
  • Query parameter → narrows or defaults, remove it and you just get the wider, unfiltered result.
  • /orders?id=42 → technically works, breaks convention — identity belongs in the path.
  • Optional/partial fields like version or expand flags → usually query params or headers, since the base resource still stands without them.
📖 Explanation ▾

A route parameter is part of the URL's path — it identifies which resource you mean. /orders/{id} without a value for id isn't "orders, but general" — there's no meaningful single-order request left at all; the resource genuinely doesn't exist without it.

A query parameter refines a request that's already complete on its own. /orders alone is a perfectly valid request — "give me all orders" — and ?status=shipped just narrows that result set down. Removing it changes how much comes back, never what you're fundamentally asking for.

The same distinction is also why route-based identity plays nicer with caching and tooling: two different resources get two different URLs. Cramming an id into a query string (/orders?id=42) makes every resource look like a variation of one URL, and cramming a filter into the path (/orders/status/shipped) does the opposite mistake — inventing endless path combinations for what's really one endpoint with options.

💻 See the code ▾
C# 
[HttpGet("orders/{id}")]
public IActionResult GetOrder(int id) // id says WHICH order
{
    var order = _repo.Find(id);
    return order is null ? NotFound() : Ok(order);   // ✅ no id, no request
}

{id} lives in the route — remove it and there's no single-order endpoint left.

C# 
[HttpGet("orders")]
public IActionResult GetOrders(
    [FromQuery] string? status,
    [FromQuery] int page = 1)
{
    var query = _repo.AllOrders();
    if (status is not null)
        query = query.Where(o => o.Status == status);   // ✅ narrows, doesn't change WHAT
    return Ok(query.Skip((page - 1) * 20).Take(20));
}

status and page are optional — /orders alone is still a completely valid request.

C# 
[HttpGet("orders")]   // ❌ id crammed into a query string
public IActionResult GetOrderWrong([FromQuery] int id)
{
    return Ok(_repo.Find(id));   // ❌ compiles and runs — still the wrong shape
}

/orders?id=42 works, but hides identity behind a filter — /orders/42 is the correct shape.

🧭 Use Cases — recognize these when they happen to you ▾
1 You need to point at one exact resource, like order #42

The id says WHICH order — there's no meaningful "one order" request left without it. That identity belongs in the path, never in a query flag. This is the most common shape you'll actually write.

RememberOne resource, one URL → id lives in the path.
2 You need to narrow or sort a collection, like orders that already shipped

/orders alone is already a complete, valid request — "give me all orders." The query string just narrows or reorders that same result set; it never changes which endpoint you're calling.

RememberNarrowing a list → query string, not a new path.
3 You want an optional extra that isn't really part of the resource's identity, like expand=items

/orders/42 is already complete and meaningful on its own — the order still exists and still means the same thing whether or not you also ask to expand it. Because expand doesn't change WHICH order this is, it stays a query parameter (or a header), never squeezed into the path.

RememberOptional and identity-unrelated → query param, not the path.
🌍 Real-world example ▾

/orders/42 is a street address — it tells you which house. ?status=shipped is more like telling the carrier "only show me the packages that already shipped" — same neighborhood, just a narrower list.

A teammate proposes POST /orders/cancel?orderId=42 to cancel one order. That buries which order inside a query flag on an action route. The fix: POST /orders/42/cancel — the order id stays in the path, where a resource identifier belongs.
