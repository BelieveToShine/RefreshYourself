package vs. import — one is baked into the class's real identity, the other never runs at all

"What does a package actually do, and does import affect runtime performance?"

Why it matters ▾
📦 package
❗ ProblemWithout any namespacing, two unrelated classes both named Order in different parts of a large codebase would collide, and nothing could be hidden from outside code either.
✅ SolutionA package is a namespace, backed by a real folder structure, that groups related classes under a unique dotted name — and any member declared with no access modifier is only visible to classes inside that same package.
Recallpackage = a namespace + a real visibility boundary.
📥 import
❗ ProblemWriting every type's full dotted name (java.util.List) everywhere it's used would bury the actual code in boilerplate.
✅ Solutionimport tells the compiler "this short name means this fully-qualified type, here" — a compile-time shortcut that produces nothing in the compiled bytecode.
Recallimport = a compiler shorthand, erased after the build.
🔥 Easy interview recall

package → namespace + visibility boundary

import → compiler shorthand, erased after build

Think: import never executes — delete an unused one and only the source file gets shorter, nothing about runtime changes.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

More imports (or a wildcard import com.foo.*) does not slow a program down. Import is a compile-time name lookup only — it has zero cost at runtime, no matter how many names it resolves.

🔄 Likely Follow-up

"So does package have any runtime effect at all?" Yes, unlike import — a class's package is baked into its fully-qualified (binary) name, which is exactly what the JVM's classloader uses to find and load it.

🎯 Say this in the interview — the exact lines to land

"A package is a real namespace — it groups classes under a unique name, controls default package-private visibility, and is part of the class's identity at the bytecode level. import is purely a compile-time convenience that lets you write a short name instead of the fully-qualified one — it has no effect on runtime behavior or performance."

  • package → namespace + visibility boundary, matters to the classloader.
  • import → erased after compilation, never executes, never costs anything.
📖 Explanation ▾

A package is both a naming convention and a folder-structure convention — com.app.model maps to a real com/app/model/ directory. It groups related classes together and draws a default visibility line: any class, field, or method declared with no access modifier is package-private — reachable only from other classes in that same package.

import just tells the compiler which fully-qualified type a short name refers to in this one file. It never loads a class, never runs any code, and leaves no trace in the compiled .class file — the bytecode only ever contains fully-qualified names, whether you typed import or not.

💻 See the code ▾
☕ Java 
package com.app.model;

class Order {              // no modifier → package-private
    int amount;             // visible only inside com.app.model
}

No access modifier at all means package-private — visible only to other classes in com.app.model.

☕ Java 
package com.app.service;

import com.app.model.Order;   // compile-time only

Order o = new Order();    // ✅ same thing as writing com.app.model.Order o = ...

Delete the import and spell out com.app.model.Order instead — the compiled program behaves identically.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two unrelated classes in your codebase are both named Order

No collision — their fully-qualified names (com.app.billing.Order, com.app.shipping.Order) are genuinely different. import just picks which one the short name Order means in a given file.

RememberSame short name, different package → no collision at all.
2 You delete an unused import line during cleanup

The compiled bytecode is byte-for-byte unaffected — only the source file gets one line shorter. There was never anything running to "stop" in the first place.

RememberRemoving an unused import changes source only, never behavior.
3 You assume import com.foo.*; "loads" every class in that package

A wildcard import is still just a compile-time name-lookup convenience — it doesn't preload or instantiate anything. Classes are loaded lazily by the JVM the first time they're actually used, regardless of how they were imported.

RememberWildcard import ≠ eager loading — the JVM still loads classes lazily, on first use.
🌍 Real-world example ▾

A package is like a company department. "Engineering" and "Sales" are real, named groups — they're on the org chart and control who can walk into which meeting. import is just asking a colleague by their first name instead of saying "the person in the third cubicle in Engineering" every time — same person either way, just less typing.
