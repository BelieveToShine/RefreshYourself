5,000 rows is a scale problem, not a rendering bug

"A page renders 5,000 rows and is slow — what do you actually do about it?"

Why it matters ▾
📊 Scaling a Large List
❗ ProblemWrapping the row component in React.memo feels like the fix for a slow 5,000-row table, but the very first render still has to mount every one of those 5,000 real DOM nodes — memo only skips re-renders on later updates, it never touches that up-front mount cost.
✅ SolutionVirtualization changes the actual number of DOM nodes that exist at any moment: it tracks scroll position and renders only the slice of rows currently inside the viewport (plus a small buffer), so mounting stays cheap no matter how many rows are in the underlying data.
RecallReact.memo skips re-rendering unchanged rows — it does NOT reduce how many DOM nodes exist. Virtualization is the actual fix for a genuinely large list.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Wrapping the row component in React.memo is enough to fix a slow 5,000-row table. Memo helps avoid re-rendering rows that didn't change between updates, but it does nothing about the up-front cost of mounting 5,000 real DOM nodes in the first place — the actual fix for a genuinely large list is virtualization (rendering only the currently-visible rows), which memo alone can never provide, since the two solve entirely different problems.

🔄 Likely Follow-up

"A search box fires an API call on every keystroke — how would you improve it?" Debounce the input — wait for a short pause in typing before actually firing the request, so a user typing "react" fires roughly one request instead of five — and cancel or ignore any in-flight request that's no longer for the current input value once it resolves.

📖 Explanation ▾

Mounting 5,000 real DOM nodes is expensive no matter what happens afterward. React.memo only skips re-rendering a row on a later update if its props haven't changed — it has no effect on the very first render, since every row still has to mount once regardless. Virtualization changes the actual number of DOM nodes that exist at any moment: it tracks scroll position, works out which slice of the data currently falls inside the viewport (plus a small buffer), and renders only that slice — everything above and below is empty spacer space, not real elements.

A search box firing on every keystroke has a different problem entirely: too many requests, not too many DOM nodes. Debouncing delays firing the request until typing pauses for a short window, collapsing what would otherwise be one request per keystroke into roughly one request per pause. Because a slower, earlier request can still resolve after a newer one, whichever response no longer matches the current input value should be cancelled or ignored — otherwise a stale result can overwrite a fresher one on screen.

💻 See the code ▾
JSX 
function VirtualizedList({ items, rowHeight, viewportHeight, scrollTop }) {
  const startIndex = Math.floor(scrollTop / rowHeight);      // first visible row
  const visibleCount = Math.ceil(viewportHeight / rowHeight);
  const endIndex = startIndex + visibleCount;

  const visibleItems = items.slice(startIndex, endIndex);    // ✅ only these actually mount

  return (
    <div style={{ height: items.length * rowHeight }}>         {/* keeps real scroll height */}
      <div style={{ transform: `translateY(${startIndex * rowHeight}px)` }}>
        {visibleItems.map(item => <Row key={item.id} item={item} />)}
      </div>
    </div>
  );
}

Only visibleItems ever renders — the rest of the 5,000 rows are represented by the spacer height, not by mounted <Row> elements.

JSX 
function SearchBox() {
  const [query, setQuery] = useState('');

  useEffect(() => {
    const timer = setTimeout(() => search(query), 300); // wait for a pause
    return () => clearTimeout(timer);                          // ✅ cancels the previous timer
  }, [query]);

  return <input value={query} onChange={e => setQuery(e.target.value)} />;
}

Typing "react" resets the timer on every keystroke — only the last one, after a 300ms pause, actually fires search().

🧭 Use Cases — recognize these when they happen to you ▾
1 Your table renders thousands of rows and feels slow to mount or scroll

This is the #1 scenario you'll actually run into: mounting thousands of real DOM nodes at once is expensive no matter what happens afterward. Virtualization tracks scroll position and renders only the slice of rows currently inside the viewport (plus a small buffer), so the real DOM node count stays tiny regardless of how many rows are in the underlying data.

RememberVirtualization renders only the visible slice — the fix for a genuinely large list.
2 You already wrapped the row component in React.memo, but the table is still slow to load

Candidates often assume React.memo alone should fix this once they've applied it — but memo only skips re-rendering a row on a later update if its props haven't changed. It has no effect on the very first render, since every row still has to mount once regardless — the 5,000-node mount cost is untouched.

RememberReact.memo helps updates, not the first mount — it can't reduce how many nodes get created.
3 Your search input fires an API call on every single keystroke

This is a different problem entirely — too many requests, not too many DOM nodes. Debouncing delays firing the request until typing pauses for a short window, collapsing what would otherwise be one request per keystroke into roughly one request per pause, and any response that's no longer for the current input value should be cancelled or ignored.

RememberDebounce waits for a pause in typing, then cancels or ignores stale responses.
