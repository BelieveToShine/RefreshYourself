🔥 Angular · Intermediate · Must Know

switchMap, mergeMap, concatMap, exhaustMap — one of the strongest practical Angular interview differentiators: four operators, four different answers to what happens to the previous inner request.

"switchMap, mergeMap, concatMap, exhaustMap — what's the actual difference, and how do you pick the right one?"

Why it matters ▾
🔄 switchMap
❗ ProblemLetting an older, slower inner request finish after a newer one could let a stale result overwrite the newest one — e.g. an outdated search response landing last.
✅ SolutionIt cancels whatever inner request is still in flight the instant a new value arrives, so only the latest one ever survives.
RecallswitchMap = cancel the old, keep only the newest.
🔀 mergeMap
❗ ProblemSome inner requests are genuinely independent of each other, and cancelling or delaying any of them would lose or hold up work that has nothing to do with the others.
✅ SolutionIt never cancels or queues — every inner request runs concurrently, and results land in whatever order they actually finish.
RecallmergeMap = run everything in parallel, nothing waits.
📥 concatMap
❗ ProblemOrder-dependent requests would come back out of sequence, or overlap, if every one of them were allowed to start right away.
✅ SolutionIt queues each new inner request strictly behind the current one — the next one doesn't even start until the previous one completes.
RecallconcatMap = queue one at a time, in order.
🚫 exhaustMap
❗ ProblemA fast double-click on something like a submit button could start a second, competing request before the first one is even done.
✅ SolutionIt drops any new value that arrives while an inner request is still running — a new one only starts once the current request finishes.
RecallexhaustMap = ignore new arrivals until the current one's done.
🔥 Easy interview recall

switchMap → cancels the old one

mergeMap → runs all in parallel

concatMap → queues, one at a time

exhaustMap → ignores new while busy

Think: Search box → switchMap (only the latest keystroke's answer matters) Submit button → exhaustMap (never let a second click start a second request)

⚠️ Common Trap

switchMap is not "the one you always use for HTTP calls." It's the right choice specifically when a newer request should invalidate an older one (search-as-you-type) — it's the wrong choice for a form submission (cancelling the first submission could lose it) or for anything that needs every request to actually finish, like parallel or sequential work.

🔄 Likely Follow-up

"Why is exhaustMap specifically right for submit-button de-duplication, instead of switchMap?" switchMap would cancel the first, already-in-flight submission on every extra click — a fast double-click could mean the form never actually finishes submitting at all. exhaustMap instead lets that first submission finish undisturbed and simply drops the extra clicks that arrive while it's still running.

🎯 Say this in the interview — the exact lines to land

"All four map each outer value into a new inner Observable — the only difference is what happens to the previous inner Observable when a new outer value shows up. switchMap cancels it, mergeMap runs everything concurrently, concatMap queues it strictly in order, and exhaustMap ignores the new value until the current one finishes."

  • switchMap → search-as-you-type: cancel the stale request, only the latest query's result matters.
  • mergeMap → independent parallel requests: nothing waits, nothing gets cancelled.
  • concatMap → order-dependent requests: the next one doesn't start until the current one completes.
  • exhaustMap → submit-button de-duplication: drop extra clicks, never queue or cancel the one in flight.
  • Cancelling an inner HTTP request isn't just ignoring its response — HttpClient wires the unsubscribe through to actually abort the request at the network level.
📖 Explanation ▾

All four operators start the same way: take a value from an outer Observable and map it into a brand-new inner Observable — usually an HTTP call. Where they genuinely differ is what happens if a new outer value shows up while the previous inner Observable is still running.

switchMap cancels whatever inner Observable is in flight and switches straight to the new one — only the latest result is ever kept. mergeMap (also called flatMap) never cancels anything — every inner Observable runs concurrently, and results land in whatever order they actually finish. concatMap queues them instead: the next inner Observable doesn't even start until the current one completes, so order is guaranteed. exhaustMap takes the opposite approach from switchMap — while an inner Observable is running, any new outer value is simply dropped, not queued and not run; a new inner Observable only starts once the current one finishes.

For an HTTP-backed inner Observable specifically, "switchMap cancels it" is a concrete technical fact, not a figure of speech: Angular's HttpClient wires the RxJS unsubscription through to actually abort the underlying network request — the same mechanism used when unsubscribing from an HTTP call manually.

One more distinction worth knowing: for a fixed, known batch of parallel requests that all need to run to completion, forkJoin is the more common tool — mergeMap is for an ongoing stream that keeps mapping new values into parallel inner requests as they arrive.

💻 See the code ▾
TypeScript 
// search box — only the LATEST query's results should ever win
this.searchInput$.pipe(
  debounceTime(300),                          // wait for typing to settle
  switchMap(q => this.api.search(q))         // cancels the previous search request
).subscribe(results => this.results = results);

Every new keystroke's request cancels whatever search request was still in flight — no stale response can overwrite a newer one.

TypeScript 
// submit button — never let a second click start a second request
this.submitClicks$.pipe(
  exhaustMap(() => this.api.submit(this.form.value)) // ignores clicks while one is in flight
).subscribe();

switchMap here would have cancelled the first, real submission on every extra click — exhaustMap instead lets it finish and just drops the extra clicks.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your search box fires off a new API call on every keystroke

Every keystroke maps to a new inner search request. If an older request outraced a newer one, its response could arrive last and overwrite the more relevant result. switchMap cancels whatever search request is still in flight the moment a newer keystroke arrives, so only the latest query's response is ever kept.

RememberSearch-as-you-type → cancel the old, keep only the latest.
2 A submit button gets clicked twice before the first request finishes

A fast double-click could start a second, competing submit request before the first one is even done. Reaching for switchMap here is the common trap: it would cancel the first, real submission on the second click, risking the form never actually finishing. exhaustMap instead lets that first submission finish undisturbed and simply drops the extra click that arrived while it was still running.

RememberSubmit button → exhaustMap, never switchMap — don't cancel a real in-flight submission.
3 You need to fire off several API calls, and every one of them actually has to complete

If those calls are genuinely independent of each other, mergeMap runs every inner request concurrently and lets each one land whenever it actually finishes — nothing is ever cancelled or delayed. If instead the calls are order-dependent and must happen in a specific sequence, concatMap queues them strictly instead — the next one doesn't start until the current one completes.

RememberIndependent, all must finish → mergeMap. Order matters → concatMap.
🌍 Real-world example ▾

Four ways to handle a new customer walking in while you're serving someone else. switchMap drops the current customer to help the new one — only the latest one matters. mergeMap calls in more staff so both get helped at once. concatMap makes the new customer wait in line until the current one is done. exhaustMap tells the new customer "sorry, come back later" and keeps serving the current one — no line, no callback, just gone.
