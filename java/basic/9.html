final vs. finally vs. finalize — three words that share a root and nothing else

"What's the difference between final, finally, and finalize?"

Why it matters ▾
🔒 final
❗ ProblemA value, a method's behavior, or a class's hierarchy sometimes needs to be locked down so nothing later in the codebase can quietly reassign, override, or extend it.
✅ Solutionfinal is a modifier enforced by the compiler: a final variable can't be reassigned, a final method can't be overridden, a final class can't be extended.
Recallfinal = locked, checked at compile time.
🔁 finally
❗ ProblemCleanup code (closing a file, releasing a lock) has to run whether a try block succeeds, fails, or throws — skipping it on the exception path leaks the resource.
✅ Solutionfinally is a block that always runs after try/catch, exception or not, guaranteeing the cleanup executes either way.
Recallfinally = always runs, success or exception.
🗑️ finalize()
❗ ProblemOld code relied on a hook the garbage collector would call right before reclaiming an object, to run last-chance cleanup.
✅ Solutionfinalize() was that hook — but it's deprecated since Java 9 and on the path to removal. try-with-resources and Cleaner are the real modern answer.
Recallfinalize() = deprecated, don't rely on it.
🔥 Easy interview recall

final → modifier, locks a variable/method/class

finally → block, always runs after try/catch

finalize() → deprecated GC hook, don't use it

Think: final locks. finally always runs. finalize() is retired.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"finalize() is a normal, recommended way to clean up resources." It isn't — it's deprecated since Java 9, never guaranteed to run promptly (or at all), and the real modern answer is try-with-resources or java.lang.ref.Cleaner.

🔄 Likely Follow-up

"Does finally always run, no matter what?" Almost always — it's skipped only if the JVM exits (System.exit()) or the process crashes/is killed before reaching it; a thrown exception, a return inside try/catch, or normal completion all still trigger it.

🎯 Say this in the interview — the exact lines to land

"final, finally, and finalize only share a root word. final is a modifier that locks a variable, method, or class. finally is a block that always runs after try/catch. finalize() was a deprecated Object method the garbage collector used to call before reclaiming an object — it's on the path to removal, not a recommended cleanup mechanism."

  • final → compile-time lock on a variable, method, or class.
  • finally → guaranteed cleanup, runs whether or not an exception was thrown.
  • finalize() → deprecated, don't rely on it — use try-with-resources or Cleaner instead.
📖 Explanation ▾

final is checked at compile time: a final variable's value can only be assigned once, a final method's body can never be overridden by a subclass, and a final class can never be extended at all.

finally is a block attached to try/catch that the JVM guarantees to run on the way out, whether the try block finished normally, threw an exception, or even hit a return statement — the one place cleanup code belongs when it absolutely must execute.

finalize() was Object's hook for the garbage collector to call, once, sometime before reclaiming an unreachable object's memory — "sometime" being the actual problem: the JVM never guaranteed when, or even if, it would run before deprecating it in Java 9. try-with-resources (deterministic, immediate) and Cleaner (a safer GC-driven hook) replaced it for real cleanup needs.

💻 See the code ▾
Java 
final int MAX = 10;
MAX = 20;   // ❌ compile error — final variable can't be reassigned

final is enforced by the compiler, not at runtime.

Java 
try {
    return risky();
} catch (Exception e) {
    return fallback();
} finally {
    System.out.println("cleanup");  // ✅ runs before either return completes
}

finally runs even when try/catch both hit a return.

Java 
// ❌ old, deprecated way
protected void finalize() { resource.release(); }

// ✅ modern way — deterministic, no GC guessing
try (Resource r = new Resource()) {
    r.use();
}

try-with-resources closes the resource immediately — it never waits on the garbage collector.

🧭 Use Cases — recognize these when they happen to you ▾
1 A constant that must never change after it's set

A retry limit, a conversion rate, a fixed configuration value — mark it final so the compiler itself guarantees nothing later reassigns it by mistake. This is the #1 everyday use of final.

RememberValue must never change → final.
2 A file, socket, or database connection you must close

Whether the read throws or not, the file handle has to close — that's exactly what a finally block (or, better, try-with-resources) is for.

RememberMust-run cleanup, exception or not → finally.
3 You're tempted to override finalize() for cleanup

A resource that depends on finalize() to close can leak for a long time, or forever — the GC decides when (or if) to call it, not your code. Use try-with-resources or Cleaner instead.

RememberRelying on finalize() for cleanup → the classic trap.
🌍 Real-world example ▾

final is a locked door, finally is the light switch you always flip on the way out, finalize() is a janitor who might show up next week — or never. Only one of the three is something you can actually depend on for cleanup.
