Attach vs. Update — which columns get written?

"A detached entity comes in from an API — how do you save it?"

Why it matters ▾
📥 Disconnected Entities
❗ ProblemAn API hands you an entity that no DbContext is tracking. Save it the wrong way and you quietly overwrite columns the client never sent.
✅ SolutionChoose on purpose: Update() writes every column, Attach() plus marking a property writes just that one, and load-then-patch writes only what really changed.
RecallDetached save → Update = all columns; Attach = only what you mark; load-then-patch = only real changes.
🔥 Easy interview recall

Detached save = "decide which columns get written."

Think: Update() → every column Attach() + IsModified → only the column you mark Load, then patch → one SELECT, only real changes

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Update() just saves my changes." It marks every column as modified — any field the client left out is written back as null or default, silently erasing data that was already stored.

🔄 Likely Follow-up

"So why not call Update() every time?" It saves a SELECT, but it writes every column from whatever the client sent — missing fields get overwritten, and a client could set fields it should never touch. Load-then-patch costs one read, writes only real changes, and lets you return a 404 if the row is gone.

🎯 Say this in the interview — the exact lines to land

"A detached entity isn't tracked, so I choose how to start tracking it. Update() is quick but marks every column as modified. Attach() and marking only the changed properties writes just those. For an API, I usually load the row and copy over the allowed fields, so only real changes are written."

  • Update() → every column is written — quickest, riskiest.
  • Attach() + IsModified → only the marked column is written.
  • Load, then patch → one SELECT, only real changes — my API default.
  • Row doesn't exist → UPDATE hits 0 rows and SaveChanges() throws DbUpdateConcurrencyException.
📖 Explanation ▾

A detached entity is one no DbContext is tracking — typically an object built from an API request body. To save it, EF Core must first start tracking it, and how you start decides the SQL that comes out.

Update() starts tracking the entity as Modified with every property marked modified, so the UPDATE sets every non-key column. On an object graph it walks the related entities too. Attach() starts tracking as Unchanged (when the key is set), so nothing is written until you mark properties modified. Setting Entry(e).State = EntityState.Modified on one entity behaves like Update() on it.

Load-then-patch reads the row, copies the new values in, and lets change detection find the real differences. It costs one SELECT, but it is also the natural place to check the row exists and to copy only the fields you allow — which blocks overposting.

💻 See the code ▾
C# 
db.Products.Update(product);          // key set → Modified, every column
await db.SaveChangesAsync();           // ❌ UPDATE sets Name, Price, Description…

Update() writes every column — including ones the client never sent.

C# 
db.Attach(product);                                       // starts as Unchanged
db.Entry(product).Property(p => p.Price).IsModified = true; // ✅ only Price
await db.SaveChangesAsync();                               // UPDATE sets Price only

Attach() plus IsModified narrows the UPDATE to the property you marked.

C# 
var p = await db.Products.FindAsync(id);
if (p is null) return NotFound();             // ✅ row check for free
db.Entry(p).CurrentValues.SetValues(dto);     // copy matching properties
await db.SaveChangesAsync();                  // only changed columns written

Load first, copy values in, and only the differences reach the database.

🌍 Real-world example ▾

A PUT /products/5 endpoint receives only name and price, but the row also has a Description. Update() writes the missing description as null; load-then-patch keeps the stored one.
