Health checks — alive is not the same as ready

"How do you expose liveness and readiness for an ASP.NET Core app?"

Why it matters ▾
💚 Liveness
❗ ProblemA process can be stuck while still "running", and nothing outside the app notices.
✅ SolutionA liveness endpoint answers "is the app itself OK?" so an orchestrator can restart it when it isn't.
RecallLiveness = should I restart it?
🚦 Readiness
❗ ProblemA new instance may be up but still warming up, or its database may be down — traffic sent to it just fails.
✅ SolutionA readiness endpoint also checks dependencies, so traffic is routed only to instances that can serve it.
RecallReadiness = should I send traffic?
🔥 Easy interview recall

Two questions: "alive?" and "ready?"

Think: /health/live → the app itself only, no dependencies /health/ready → also the database, cache, other dependencies

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Putting the database check on the liveness endpoint. When the database goes down, every instance fails liveness and the orchestrator may restart all of them — and restarting the app doesn't fix the database. Dependency checks belong on readiness.

🔄 Likely Follow-up

"What HTTP status does an unhealthy check return?" 503 by default. Healthy and Degraded both return 200, and you can change that mapping with ResultStatusCodes on HealthCheckOptions.

🎯 Say this in the interview — the exact lines to land

"I register checks with AddHealthChecks, tag them, and expose them with MapHealthChecks — a liveness endpoint that checks only the app itself, and a readiness endpoint that also runs dependency checks like the database. Liveness tells the orchestrator when to restart; readiness tells it when to send traffic."

  • AddHealthChecks() + MapHealthChecks() → register checks once, expose them per endpoint.
  • Tags + Predicate → choose which checks each endpoint runs.
  • Liveness → the app only, no dependencies — a restart signal.
  • Readiness → dependencies included — a traffic signal.
  • Unhealthy → 503 by default; healthy and degraded return 200.
📖 Explanation ▾

AddHealthChecks() returns a builder you add checks to — a quick lambda with AddCheck, or a class that implements IHealthCheck. Each check reports Healthy, Degraded or Unhealthy. MapHealthChecks("/path") turns the registered checks into an endpoint; the default response is just the status word.

Give each check tags, then give each endpoint a Predicate that picks checks by tag. That is how one app serves a cheap liveness endpoint and a fuller readiness endpoint. Orchestrators such as Kubernetes call HTTP probe paths you configure: a failing liveness probe can trigger a restart, a failing readiness probe takes the instance out of traffic. Load balancers use similar health probes — set the probe path in their settings.

Related: the host's own lifecycle is on The Generic Host & Application Lifetime; for health in distributed systems see the Web API track's Distributed Systems Considerations and 500-Errors-in-Production Scenario.

💻 See the code ▾
C# 
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: new[] { "live" })
    .AddCheck<DbCheck>("db", tags: new[] { "ready" });

var app = builder.Build();
app.MapHealthChecks("/health/live",  new HealthCheckOptions { Predicate = c => c.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new HealthCheckOptions { Predicate = c => c.Tags.Contains("ready") });

Tags decide which checks run on which endpoint — the DB check is only on readiness.

C# 
public class DbCheck : IHealthCheck
{
    private readonly AppDbContext _db;
    public DbCheck(AppDbContext db) => _db = db;

    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken ct = default)
    {
        return await _db.Database.CanConnectAsync(ct)
            ? HealthCheckResult.Healthy()                     // ✅ 200
            : HealthCheckResult.Unhealthy("Database down");   // ❌ 503
    }
}

A custom check returns a result object — the endpoint turns it into a status code.

🌍 Real-world example ▾

A rolling deploy. A new instance starts but is still warming up. Readiness keeps failing, so the load balancer holds traffic back; liveness stays green, so nobody restarts it for being slow. Once readiness passes, traffic flows.
