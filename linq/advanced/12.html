Offset Pagination vs. Keyset Pagination — Skip/Take vs. seeking by the last key

"Skip(n).Take(pageSize) vs. keyset ("seek") pagination — what's the actual difference, expressed in LINQ?"

Why it matters ▾
📄 Offset pagination
❗ ProblemSkip(n).Take(m) re-scans and discards the first n rows on every single page request — page 50 of a long list does nearly as much work as scanning the whole table, over and over.
✅ SolutionIt's the simplest to write, and fine for small tables or shallow pages — the trade-off only really bites on deep pagination over a large, growing table.
RecallOffset = re-scan from the start, every page.
🔑 Keyset pagination
❗ ProblemA user paging deep into a long list with Skip/Take notices each page getting slower, and rows inserted or deleted mid-scroll can shift the page boundaries entirely.
✅ SolutionWhere(x => x.Id > lastSeenId).OrderBy(x => x.Id).Take(m) seeks straight to the right spot using an indexed column — roughly constant cost, no matter how deep the page is.
RecallKeyset = seek directly to the last key you saw.
🔥 Easy interview recall

Skip/Take → re-scans from the start, every page

Where(Id > last) → seeks straight to the last key

Think: Skip counts rows to throw away. Where jumps straight there.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Offset pagination's page contents can shift between requests. Insert or delete a row while a user is paging and they can see a row twice or miss one entirely — keyset pagination, anchored to a real column value instead of a row count, doesn't have this problem.

🔄 Likely Follow-up

"Can keyset pagination jump straight to an arbitrary page, like 'go to page 50'?" Not directly — it only knows how to seek forward from the last key it saw. Arbitrary random-access page numbers are offset pagination's real strength, and keyset's real limitation.

🎯 Say this in the interview — the exact lines to land

"Skip(n).Take(m) re-scans and discards the first n rows on every page request — cheap for shallow pages, expensive for deep ones. Where(x => x.Id > lastSeenId).OrderBy(x => x.Id).Take(m) seeks straight to the right spot instead, at roughly constant cost no matter how deep the page is."

  • Skip/Take → re-scans from row zero, every single page.
  • Where(Id > last) → seeks directly, using an indexed column.
  • Rows inserted/deleted mid-paging → offset can skip or duplicate a row; keyset can't.
  • Jumping to an arbitrary page number → offset's real strength, keyset's real limitation.
📖 Explanation ▾

Offset pagination is expressed as OrderBy(...).Skip(n).Take(m) — straightforward, and the database still has to walk past (or otherwise account for) the first n rows before it can hand back the page, every single time that page is requested. The cost grows with n, so the deeper a user pages, the more work each request does, even though the page size never changed.

Keyset pagination replaces "skip this many rows" with "start after this specific value": Where(x => x.Id > lastSeenId).OrderBy(x => x.Id).Take(m). Given an index on the ordering column, the database can seek directly to that value instead of counting rows to get there — the cost per page stays roughly flat regardless of how many pages came before.

The trade-off is real, not one-sided: keyset needs the client to carry the last key forward between requests, and it can't answer "show me page 50" out of context the way offset can — it only knows how to continue from where it left off.

💻 See the code ▾
C# 
List<Post> page = context.Posts
    .OrderBy(p => p.Id)
    .Skip(pageNumber * pageSize)   // ❌ re-scans every earlier page
    .Take(pageSize)
    .ToList();

Page 50 re-scans (or accounts for) the first 49 pages' worth of rows before it can return anything.

C# 
List<Post> page = context.Posts
    .Where(p => p.Id > lastSeenId)  // ✅ seeks straight past what we've shown
    .OrderBy(p => p.Id)
    .Take(pageSize)
    .ToList();

Same cost on page 2 and page 500 — the database seeks to lastSeenId using the index, nothing earlier gets touched.

🧭 Use Cases — recognize these when they happen to you ▾
1 A small admin table that only ever has a handful of pages

With only a few pages, the "re-scan from the start" cost never gets large enough to matter — offset's simplicity wins here, and keyset would be solving a problem that doesn't exist yet.

RememberShallow pages, small table → Skip/Take is fine.
2 An infinite-scroll feed over a large, constantly growing table

This is exactly the case keyset pagination was built for — a feed users scroll through indefinitely, where offset's cost would keep climbing the deeper they go.

RememberDeep, growing feed → keyset, not Skip/Take.
3 A UI with numbered page links, like "jump to page 50"

Keyset pagination only knows how to continue from the last key it saw — it has no concept of "page 50" in isolation, so a UI that needs arbitrary jump-to-page links has to use offset, cost trade-off accepted.

RememberNeed arbitrary page jumps → offset is the only option.
🌍 Real-world example ▾

A public API returns an activity feed, paged with Skip/Take. Each page gets noticeably slower the further back a client scrolls, and clients occasionally see a duplicate or missing item when new activity gets inserted mid-scroll. Switching to Where(x => x.Id < lastSeenId).OrderByDescending(x => x.Id).Take(m) fixes both problems at once — constant per-page cost, and no shifting between requests because it's anchored to a real Id value instead of a row count.
