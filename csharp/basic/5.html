const, readonly, static — locked when? Shared how many times?

Why it matters ▾
🔒 const
❗ ProblemA value needs to be identical for every single caller and locked before the program even runs — a plain field can still be reassigned later, and different callers could end up disagreeing on it.
✅ Solutionconst bakes the literal value straight into every caller's own compiled code at compile time, so it's always shared and can never be reassigned.
Recallconst = compile-time literal, baked in, always shared, never per-object.
🖊️ readonly
❗ ProblemA value still needs to stay locked once set, but different objects legitimately need different values — like two Config objects each getting their own Id — which const can't do since it's always identical for everyone.
✅ Solutionreadonly can be assigned inside the constructor, so it's locked forever after that — just locked to whatever value that one object's constructor received.
Recallreadonly = locked once per object, at construction — can differ instance to instance.
🔗 static
❗ ProblemSome data isn't about locking at all — like an InstanceCount every Config object needs to read and update together, not a separate copy each.
✅ Solutionstatic gives every instance one shared copy instead of one each — a completely different axis from const/readonly, which is why static readonly can combine both.
Recallstatic = one shared copy for every instance — a sharing rule, not a locking rule.
🔥 Easy interview recall

const → locked before it runs

readonly → locked once, per object

static → one shared copy

Think: static readonly → computed once, shared forever

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Changing a const doesn't update old callers. The value is baked into their compiled code at compile time — they stay stale until they're rebuilt.

🎯 Say this in the interview — the exact lines to land

"const is fixed at compile time and always shared. readonly is fixed once per object, at construction. static is a sharing rule, not a locking rule — one copy for every instance."

  • static readonly combines both: computed once, shared forever.
  • readonly can differ per object — const never can.
📖 Explanation ▾

const is baked into the compiled code itself — the value has to be known at compile time (a literal, or another const), and it's always implicitly shared, never per-object.

readonly is more flexible: it can be assigned in the constructor, so different objects can end up with different, still-unchangeable values — useful when the "constant" depends on something only known at runtime.

static is a completely different axis — it's not about whether a value can change, it's about whether there's one copy shared by every instance, or one copy per instance. You can combine it with readonly (static readonly) for a value computed once at startup and shared forever.

💻 See the code ▾
C# 
public const int MaxRetries = 3;   // compile-time, shared
MaxRetries = 5;   // ❌ compile error — const can never be reassigned

const is locked before the program even runs — there's no legal way to change it, ever.

C# 
public readonly string Id;
public Config(string id) => Id = id;   // ✅ allowed — inside the constructor
Id = "new";   // ❌ compile error — outside the constructor

Two different Config objects can end up with two different Id values — each locked after its own constructor runs.

C# 
public static int InstanceCount;
// every Config instance reads and writes the SAME InstanceCount

static isn't about locking at all — it's one copy shared by every instance.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're defining a fixed rule or limit that should be identical for every caller, forever — like a max retry count

This is exactly what const is for — the compiler bakes the literal into every caller's own compiled code, so there's no way to change it later without recompiling everyone who uses it.

RememberFixed forever, identical everywhere → const.
2 Each object needs its own locked-in value that isn't known until the object is constructed — like a Config's Id

readonly lets the constructor set the value once, per object — two Config objects end up with two different, still-unchangeable Id values.

RememberKnown only at construction, can differ per object → readonly.
3 Multiple instances need to share and update one counter or piece of state together — like tracking how many objects exist

static isn't about locking — it's one shared copy that every instance reads and writes, exactly like an InstanceCount tracking how many Config objects exist in total.

RememberOne shared copy across every instance → static.
🌍 Real-world example ▾

A printed rulebook vs. a signed contract vs. a shared office clock. const is the rulebook — printed once, identical for everyone, never reprinted. readonly is a signed contract — fixed once signed, but each person's contract can say something different. static is the office wall clock — there's exactly one, and everyone in the room reads the same time off it.
