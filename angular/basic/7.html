Services & Dependency Injection — who hands you your dependencies, and who decides how long they live?

What is Angular's dependency injection, and what does providedIn: 'root' actually mean?

Why it matters ▾
🏗️ useClass
❗ ProblemTests (or a different feature) need a different implementation behind the same dependency token.
✅ SolutionuseClass tells the injector to construct a different class for that token instead.
RecalluseClass = same token, a different class gets constructed.
📦 useValue
❗ ProblemA constant, like an API URL, has nothing to construct — building it via a class would be pointless.
✅ SolutionuseValue hands the injector an already-built value directly, no construction step.
RecalluseValue = no construction, just hand over the ready-made value.
⚙️ useFactory
❗ ProblemSome values can only be produced at runtime, depending on another injected service.
✅ SolutionuseFactory calls a function you provide at resolve time, and its return value is handed back.
RecalluseFactory = a function call at resolve-time, not a fixed class or value.
🔥 Easy interview recall

Dependency injection = "you declare what you need; an injector builds it and hands it to you."

Think: providedIn: 'root' → one shared instance, everywhere provided in a component → a fresh instance, just for that subtree

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

@Injectable() does not automatically make a service an app-wide singleton. It's only a shared singleton if it's provided at the root level — the exact same service provided again inside a component's own providers array gets a brand-new instance scoped to that subtree instead.

🔄 Likely Follow-up

"If two components both provide the same service in their own providers array, do they share an instance?" No — each component gets its own instance from its own injector; sharing only happens when the same injector level (like root) is the one providing it, which is what hierarchical DI is about.

🎯 Say this in the interview — the exact lines to land

"Angular's dependency injection means a class declares what it needs — like private http = inject(HttpClient) — and an injector hands over an already-built instance instead of the class constructing it itself. providedIn: 'root' registers a service with the app's root injector, so one shared instance is created and reused everywhere it's injected."

  • useClass → swap in a different implementation — a mock in tests, for example.
  • useValue → hand over an already-built value, no construction at all — constants, config.
  • useFactory → call a function at runtime when the value depends on something only known then.
  • inject() → the only option inside functional guards, interceptors, and factories — there's no constructor to hook into.
  • Component-level providers → a fresh instance for that subtree, not the shared root singleton.
  • No provider found → NullInjectorError, thrown right when the injector tries to build it.
📖 Explanation ▾

Dependency injection flips how a class gets what it needs. Instead of writing new HttpService() itself, a class just declares the dependency it wants, and an external injector hands over an already-built instance — inversion of control applied to object construction. Any class marked @Injectable() is one Angular's DI system knows how to construct.

providedIn: 'root' registers a service with the app's root injector — the first time anyone injects it, one instance gets built, and every later injection anywhere in the app receives that same instance. It's also tree-shakable: a service nobody ever injects never even ships in the build. That shorthand is really a provider — the recipe telling the injector how to produce a value for a token — and a provider can build a value three different ways:

useClassuseValueuseFactory
What it doesConstructs an instance of a classHands over an already-built valueCalls a function to produce the value
Any construction?✅ yes — Angular builds the class❌ no — nothing to construct✅ yes — inside your own function
Best used forSwapping in a mock/alternate implementationConstants, config objectsA value depending on another injected service

Angular fills in a constructor parameter automatically (constructor injection) by reading its type — the classic pattern. inject() does the same job as a field initializer, and it's the only option inside functional code with no constructor at all (guards, interceptors, provideXyz() factories). Both only work inside an injection context — calling inject() from inside a setTimeout callback throws. If nothing can supply what's asked for, Angular throws a NullInjectorError ("No provider for X") right at construction.

💻 See the code ▾
TypeScript 
class UserComponent {
  constructor(private http: HttpClient) {}
}

Constructor injection is the classic pattern — Angular reads the parameter's type and supplies it automatically.

TypeScript 
class UserComponent {
  private http = inject(HttpClient);
}

inject() works as a field initializer too — and it's the only option inside functional guards, interceptors, or provideXyz() factories, none of which have a constructor to hook into.

TypeScript 
export const API_URL = new InjectionToken<string>('API_URL');

providers: [
  { provide: API_URL, useValue: 'https://api.example.com' }
]

InjectionToken gives a plain value a unique, typed identity to inject by — a TypeScript interface or primitive type doesn't exist at runtime, so it can't be a DI key on its own.

🧭 Use Cases — recognize these when they happen to you ▾
1 Your unit test needs a fake AuthService instead of the real one

The test's own providers array sets { provide: AuthService, useClass: MockAuthService } — the injector constructs the mock class instead, and every consumer still asking for the AuthService token gets it automatically.

RememberuseClass → same token, a different class gets constructed.
2 Your app needs a constant, like an API base URL, injected everywhere

There's nothing to construct — useValue hands the injector the already-built string (or config object) directly, and every injection of that token receives that exact value as-is.

RememberuseValue → no construction, just hand over the ready-made value.
3 A provider's value can only be produced at runtime, from another injected service

useFactory calls the function you provide at the moment the token is resolved — inside it you can ask the injector for whatever other service that value depends on, then return the built result.

RememberuseFactory → a function call at resolve-time, can depend on other services.
🌍 Real-world example ▾

DI is like a hotel handing you a room key at check-in instead of you building your own lock and key. providedIn: 'root' is the master key that opens the same room for everyone — one shared instance. A component-level provider is like getting your own private room instead — nothing shared with anyone else staying at the same hotel.
