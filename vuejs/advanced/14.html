Micro-frontends — independent teams, one shared cost

"What's a micro-frontend architecture, and what does it actually cost you?"

Why it matters ▾
🧩 Micro-frontends
❗ ProblemA single large Vue app shared by several teams means every team ships through the same build, the same deploy, and the same release schedule — one team's broken change can block everyone else's release.
✅ SolutionA micro-frontend architecture splits the app into independently deployable pieces, each potentially its own Vue app, composed together at runtime — letting separate teams ship on their own schedule without touching each other's bundle.
RecallIndependent teams, independent deploys — at the cost of real added complexity.
🔥 Easy interview recall

Micro-frontends = "one product, several independently-deployed apps."

Think: each team ships its own app on its own schedule — the shell just composes them, it doesn't own their code.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Micro-frontends are not a default architecture for a normal-sized app. The added complexity — shared dependency versioning, cross-app communication, duplicated framework runtime cost — only pays off at genuine multi-team, independently-deployed scale.

🔄 Likely Follow-up

"How do independently-built Vue micro-frontends typically communicate?" Custom events on a shared event bus, a shared minimal state layer, or URL/query-param state — never a direct import of one app's internal store into another's bundle, which would defeat the independence the architecture is for.

🎯 Say this in the interview — the exact lines to land

"A micro-frontend architecture splits a large app into independently deployable pieces, each potentially its own Vue app, composed together at runtime — through Module Federation, a web component wrapping a Vue app, or an iframe. It lets separate teams ship independently versioned pieces of one product, at the cost of real added complexity that only pays off at genuine multi-team scale."

  • Micro-frontend → independently deployable piece of one larger product.
  • Composition at runtime → Module Federation, web components, or iframes.
  • Cross-app talk → events/shared state/URL — never a direct import.
  • Default-reaching for this → the trap — it's a cost that needs real scale to justify.
📖 Explanation ▾

The point of a micro-frontend is organizational, not technical — it exists so separate teams can own, build, test, and deploy their own slice of a product without coordinating a single shared release. The "shell" app's only job is to compose the pieces together on the page; it shouldn't own their internal code or state.

Three common ways to compose them at runtime: Module Federation (webpack/Vite plugin that lets one app load another's bundle at runtime, sharing a dependency like Vue itself if versions align), a web component wrapping a whole Vue app so it can be dropped into any page regardless of framework, or an iframe (the simplest isolation, at the cost of a heavier and more constrained integration).

None of this is free. The real costs: each micro-app may ship its own copy of shared dependencies (bundle size), cross-app communication has to be built deliberately instead of just importing a shared store, and debugging spans multiple independently-deployed codebases instead of one.

💻 See the code ▾
Vue 
// micro-app A — publishes an event, doesn't know who's listening
window.dispatchEvent(
  new CustomEvent('cart:updated', { detail: { count: 3 } })
)

// micro-app B — listens, no import of A's code at all
window.addEventListener('cart:updated', (e) => {
  cartCount.value = e.detail.count   // ✅ decoupled — A could be rewritten entirely
})

Neither app imports the other's module — they only agree on an event name and its payload shape.

🧭 Use Cases — recognize these when they happen to you ▾
1 A large org with several independent teams owning one product

This is the scale where the added complexity genuinely pays off — each team ships on its own schedule, and a broken change in one micro-app doesn't block the others' releases.

RememberReal multi-team, independently-deployed scale → the architecture earns its cost.
2 A single small team reaching for this on a normal-sized app

With one team and no independent deploy need, every added layer (shared dependency versioning, cross-app events) is pure overhead. A common interview trap: treating micro-frontends as a sign of technical maturity rather than a scale-specific tradeoff.

RememberNo multi-team need → a normal single Vue app is the right call.
3 Two micro-apps need to react to the same cart state

A custom event on window (or a small shared pub/sub layer) is the standard way two independently-built micro-apps stay in sync — without either one importing the other's internal store.

RememberCross-app state sync → events/URL state, never a direct store import.
🌍 Real-world example ▾

A large retail platform with separate teams owning search, product pages, and checkout. Each is its own deployed Vue app, composed into one shell at runtime; search can ship ten times a day without ever touching checkout's release — the exact coordination cost a single shared app would otherwise impose on every team.
