pages/ vs. app/ — which router is your project actually using?

"What's the difference between the Pages Router and the App Router?"

Why it matters ▾
📄 Pages Router
❗ ProblemBefore Server Components existed, Next.js still needed a way to turn a file into a route and fetch its data — with no built-in concept of layouts that persist across navigation.
✅ SolutionThe Pages Router (pages/ directory) is Next.js's original system — each file in pages/ is a route, and data fetching happens through getStaticProps/getServerSideProps.
RecallPages Router = pages/ folder, getStaticProps / getServerSideProps.
🧩 App Router
❗ ProblemTeams wanted nested layouts that don't re-render on every navigation, and a way to fetch data straight inside a component — the Pages Router had no built-in way to do either.
✅ SolutionThe App Router (app/ directory, stable since Next.js 13.4) is built on React Server Components — folder-based routing with special files (page.js, layout.js), fetching data directly inside components with fetch().
RecallApp Router = app/ folder, Server Components, fetch() right in the component.
🔥 Easy interview recall

Pages Router → pages/, getStaticProps

App Router → app/, Server Components

Think: pages/ is the original. app/ is the current default — both still work.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

The Pages Router is not deprecated or removed. It's still fully supported for existing/maintenance apps — the App Router is the recommended default for NEW projects, not a mandatory forced migration.

🔄 Likely Follow-up

"Can both routers coexist in one project?" Yes — Next.js supports having both app/ and pages/ directories at the same time, which is exactly how an incremental, route-by-route migration works.

🎯 Say this in the interview — the exact lines to land

"Next.js has two routers. The Pages Router — pages/, data via getStaticProps/getServerSideProps — is the original system and is still fully supported. The App Router — app/, stable since Next.js 13.4 — is the current recommended default, built on Server Components with fetch() directly inside them."

  • pages/ → original router, file = route.
  • app/ → current default, Server Components, direct fetch().
  • Both → can coexist in the same project for incremental migration.
📖 Explanation ▾

The Pages Router is file-based in the flattest sense — put a file in pages/, it becomes a route. Fetching data for that page means exporting a separate function (getStaticProps for build time, getServerSideProps for every request) alongside the component.

The App Router is folder-based instead of file-based — the folder is the URL segment, and a page.js inside it makes that folder a real route. It's built on React Server Components, so a component can call fetch() directly inside itself, with no separate data-fetching function required.

Directorypages/app/

💻 See the code ▾
JavaScript 
// pages/blog/[slug].js — Pages Router
export async function getStaticProps({ params }) {
  const post = await getPost(params.slug);  // separate data function
  return { props: { post } };
}
export default function BlogPost({ post }) {
  return <article>{post.title}</article>;
}

Data fetching lives in its own exported function, separate from the component.

JavaScript 
// app/blog/[slug]/page.js — App Router
export default async function BlogPost({ params }) {
  const post = await getPost(params.slug);  // ✅ fetch right in the component
  return <article>{post.title}</article>;
}

No separate data function — the Server Component fetches its own data directly.

🧭 Use Cases — recognize these when they happen to you ▾
1 You're maintaining an existing Next.js app that still uses pages/

There's no requirement to migrate a working app. pages/ is still fully supported — getStaticProps/getServerSideProps keep working exactly as before.

RememberExisting pages/ app → no forced migration, it just keeps working.
2 You're starting a brand-new Next.js project today

create-next-app scaffolds the App Router by default today. This is the #1 scenario you'll actually run into for any new project.

RememberNew project → create-next-app gives you app/ by default.
3 You're migrating an older app one route at a time

Both directories can exist in the same project at once — move one route into app/, leave the rest in pages/, and migrate at your own pace.

RememberIncremental migration → pages/ and app/ coexist, route by route.
🌍 Real-world example ▾

An older office wing and a newly built one, in the same building. People still work in the old wing (pages/) every day — it hasn't been shut down. New hires just get desks in the new wing (app/) by default, and the building can renovate one floor at a time without closing either wing.
