⭐ C# · Intermediate · Should Know

IEnumerable → ICollection → IList — each one promises more

"What does each collection interface actually add over the last?"

Why it matters ▾
  • Comes up any time you're deciding what type to put in a method signature — the interface you pick is a promise to every caller.
  • A quick check for whether you actually understand these three or just recognize the names.
  • Mixing them up (expecting an indexer on the wrong one) is a real, easy mistake in day-to-day code.
🔥 Easy interview recall

IEnumerable<T> → iterate only

ICollection<T> → + Count / Add / Remove

IList<T> → + index access this[int]

Think: IEnumerable just walks. ICollection also counts and edits. IList can also grab any item by position.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

ICollection<T> is not "IEnumerable<T> plus an indexer." It adds Count, Add/Remove, and Contains — this[int] only shows up once you're holding an IList<T>.

🔄 Likely Follow-up

"If the method actually builds a List<T> internally, why declare the return type as IEnumerable<T>?" Because the return type is a promise to the caller — IEnumerable<T> promises only "you can iterate this," so the implementation stays free to change later without breaking anyone who called it.

🎯 Say this in the interview — the exact lines to land

"IEnumerable<T> only supports forward iteration. ICollection<T> adds Count, Add/Remove, and membership checks. IList<T> adds index-based access with this[int] — each one is a superset of the last."

  • IEnumerable<T> → return this when the caller only needs to loop over the results.
  • ICollection<T> → use when the caller needs to know the count or add/remove items.
  • IList<T> → use when the caller needs direct access by position (this[int]).
  • Pick the narrowest interface that still does the job — it's what keeps an implementation free to change later.
📖 Explanation ▾

IEnumerable<T> is the base contract — it only promises you can walk through the items once, forward, with foreach. It says nothing about how many items there are, or whether you're even allowed to change them.

ICollection<T> extends that with size and mutation: Count, Add, Remove, Contains. It still has no concept of position — there's no "first item" or "third item," just a set of members you can check and change.

IList<T> extends ICollection<T> one step further with position: this[int] lets you read or write any element by index, plus Insert/RemoveAt. It's the one to reach for when order and position actually matter.

💻 See the code ▾
C# 
IEnumerable<int> numbers = GetNumbers();
foreach (var n in numbers)
    Console.WriteLine(n);      // ✅ the only thing IEnumerable<T> promises
// numbers[0];              // ❌ won't compile — no indexer here

IEnumerable<T> gives you a walk through the items — nothing about count or position.

C# 
ICollection<int> bag = new List<int> { 1, 2, 3 };
bag.Add(4);                    // ✅ Add/Remove/Contains all exist
Console.WriteLine(bag.Count);  // ✅ Count exists
// bag[0];                    // ❌ still won't compile — no indexer on ICollection<T>

ICollection<T> adds size and mutation — still no this[int].

C# 
IList<int> ordered = new List<int> { 1, 2, 3 };
ordered[0] = 99;                // ✅ this[int] — read/write by position
ordered.Insert(1, 50);          // ✅ position-aware insert

IList<T> is the only one of the three where "give me item 7" compiles.

🌍 Real-world example ▾

A conveyor belt only lets you watch items go by — that's IEnumerable<T>. A storage bin lets you also count what's inside and add or remove items — that's ICollection<T>. A row of numbered lockers lets you do both of those, plus walk straight to locker #7 — that's IList<T>, the only one where "give me item 7" is fair game.
