Endpoint routing — decided before your code ever runs

"What is endpoint routing, and how does it differ from the older MVC-only routing model?"

Why it matters ▾
  • Checks whether you understand the modern request pipeline, not just controller/action mechanics.
  • Explains why middleware like authorization can see which endpoint will run before that endpoint's code executes.
  • A common opener before the interviewer drills into conventional vs. attribute routing specifics.
🔥 Easy interview recall

Endpoint routing = "matches the URL to a handler before anything else runs."

Think: Routing became a middleware step — MVC, Razor Pages, minimal APIs, and gRPC all feed the same lookup table.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Conventional routing isn't "the MVC way" and attribute routing isn't "the API way." Modern ASP.NET Core mixes both freely — most real MVC apps lean heavily on attribute routing for view-returning controllers too, not just REST endpoints.

🔄 Likely Follow-up

"If a request could match two different routes, which one wins?" Endpoint routing scores each candidate by specificity — a more specific template or an explicit HTTP-verb constraint beats a looser, more general pattern; if two routes are equally specific, registration order breaks the tie.

🎯 Say this in the interview — the exact lines to land

"Endpoint routing is a middleware step — UseRouting()/UseEndpoints(), or app.MapGet(...) directly in minimal APIs — that matches a request to an endpoint before most other middleware runs, including authorization. That means middleware can inspect the matched endpoint's metadata, like an [Authorize] attribute, before the endpoint's own code ever executes. Conventional routing feeds that lookup with one shared template inferring controller and action by convention; attribute routing feeds it explicit [Route]/[HttpGet] declarations per action."

  • Endpoint routing → a first-class middleware concern, not something buried inside MVC.
  • Matching happens → before other middleware executes, so authorization can see the endpoint first.
  • Conventional routing → one shared template, controller/action inferred by convention.
  • Attribute routing → explicit per-action routes, unambiguous, needed for REST-shaped URLs.
  • Any framework plugs in → MVC, Razor Pages, minimal APIs, gRPC all share one routing system.
📖 Explanation ▾

Endpoint routing made routing a first-class piece of the middleware pipeline instead of something buried inside MVC. UseRouting() matches an incoming request to a specific endpoint and records that match on the HttpContext; UseEndpoints() (or, in a minimal API, calling app.MapGet(...) directly) is what actually invokes it. MVC, Razor Pages, minimal APIs, and gRPC all register their handlers as endpoints into that same lookup — there's no separate "MVC routing" anymore, just one shared table every framework plugs into.

That split matters because matching happens before most other middleware runs. Once UseRouting() has picked an endpoint, any middleware registered after it — including UseAuthorization() — can read that endpoint's metadata (its [Authorize] attribute, its allowed HTTP verbs) and decide whether to let the request continue, before the endpoint's own code runs at all. In the older, MVC-only model, routing and dispatch were one step inside the framework, so this "check first, run later" separation wasn't possible.

Conventional and attribute routing are two different ways of registering entries into that same table — see how they differ below. (For the MVC-specific depth on when to pick one over the other inside a controller, see Razor & Routing.)

💻 See the code ▾
C# 
app.UseRouting();          // 1. match request → endpoint
app.UseAuthorization();      // 2. can inspect [Authorize] on the match
app.UseEndpoints(endpoints =>
{
    endpoints.MapControllers();
});                          // 3. only now does the endpoint's code run

Authorization sits between the match and the endpoint's own code — that ordering is the whole point of endpoint routing.

C# 
endpoints.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");
// one template, controller/action inferred by convention

Conventional routing — rename the action method and the URL changes with it, silently.

C# 
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult Get(int id) => Ok(id);   // ✅ explicit, unambiguous URL
}

Attribute routing — the URL is spelled out on the action itself, so a rename can't silently change it.

🌍 Real-world example ▾

Analogy: endpoint routing is a building directory a receptionist checks before letting anyone go upstairs — the receptionist (authorization) already knows which floor and office (endpoint) you're headed to, and can turn you away at the desk before you ever reach the door.

You add [Authorize] to an endpoint and a load balancer's health-check probe suddenly starts getting 401s instead of hitting the handler. That's endpoint routing and authorization working exactly as designed — the middleware saw the matched endpoint's metadata and rejected the request before the endpoint's code ever ran. The fix is routing the health check to a separate, unauthenticated endpoint, not disabling authorization.
