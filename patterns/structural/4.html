Proxy — a stand-in that controls access, not a bigger version of the real thing

What is the Proxy pattern, and what are its main variants — virtual, protection, and remote?

☕ Also see the Java-angle page: Reflection Costs, Dynamic Proxies and Annotations
Why it matters ▾
🛡️ Proxy
❗ ProblemSome real objects are expensive to create, live in another process, or need a permission check before use — but callers shouldn't have to deal with any of that in their own code.
✅ SolutionA Proxy implements the same interface as the real object and controls access to it — creating it lazily, checking permissions, or forwarding to a remote service — while callers keep calling the exact same interface.
RecallProxy = same interface as the real object, controls access instead of adding behavior.
🔥 Easy interview recall

Proxy = "a stand-in behind the same interface that controls access to the real object."

Think: Virtual Proxy → lazy-loads the expensive real object Protection Proxy → checks permission before forwarding Remote Proxy → stands in for an object in another process

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Proxy and Decorator are structurally the same, so they're the same pattern." They're not — a Decorator adds new responsibility on top of the call; a Proxy controls access to it (lazy-load, permission check, remote forwarding) and keeps the operation's meaning unchanged.

🔄 Likely Follow-up

"Is this a real thing in .NET, or just a textbook idea?" It's real — EF Core generates lazy-loading proxy subclasses of your entity types when lazy loading is enabled. That's a genuine Virtual Proxy running in production code.

🎯 Say this in the interview — the exact lines to land

"Proxy implements the same interface as a real subject and controls access to it instead of adding behavior to it. A Virtual Proxy lazy-loads an expensive object, a Protection Proxy checks permissions before forwarding, and a Remote Proxy represents an object living in another process. EF Core's lazy-loading entity proxies are a real Virtual Proxy running in production code."

  • Proxy → same interface, controls access to the real object.
  • Virtual → lazy-loads an expensive object on first real use.
  • Protection → permission check before forwarding.
  • Remote → stands in for an object in another process.
  • Versus Decorator → controls access, doesn't add new responsibility.
📖 Explanation ▾

A Subject is the shared interface both the real object and the proxy implement. The RealSubject is the real, possibly expensive, remote, or sensitive object. The Proxy implements Subject, holds a reference to the RealSubject, and controls access to it — it may create the RealSubject lazily, check permissions before forwarding, log the call, or forward it across a process boundary.

Three named variants cover almost every real use: a Virtual Proxy delays creating an expensive object until it's actually needed. A Protection Proxy checks permissions or access rules before forwarding the call. A Remote Proxy represents an object that lives in a different process or machine — a generated gRPC client stub is a Remote Proxy you've probably already used.

Proxy and Decorator look almost identical structurally — both wrap an object behind the same interface. What separates them is intent: a Decorator adds responsibility to the call; a Proxy controls whether or how the call reaches the real object, without changing what the operation means.

💻 See the code ▾
C# 
public interface IImage   // Subject
{
    void Display();
}

public class HighResImage : IImage   // RealSubject — expensive to create
{
    public HighResImage(string path) { /* loads a big file from disk */ }
    public void Display() { /* ... */ }
}

The real object does the actual work, but its constructor is the expensive part.

C# 
public class ExpensiveImageProxy : IImage   // Virtual Proxy
{
    private readonly string _path;
    private HighResImage? _real;
    public ExpensiveImageProxy(string path) => _path = path;   // ✅ no real object yet

    public void Display()
    {
        _real ??= new HighResImage(_path);   // ✅ created lazily, on first real use
        _real.Display();
    }
}

Callers hold an IImage the whole time — the expensive object isn't created until Display() actually runs.

🧭 Use Cases — recognize these when they happen to you ▾
1 You hold something heavy that might never be used

The proxy is cheap to create, so your code holds an IImage straight away. The expensive HighResImage is only built the first time Display() really runs. If nobody ever displays it, the big file is never loaded. This is the #1 scenario you'll actually run into.

RememberVirtual proxy → pay the cost only when used.
2 Only some users are allowed to call the real object

The proxy looks at who is calling before it forwards anything. Allowed callers reach the real object. Others are stopped at the proxy. The operation means the same thing either way, it is only gated, and callers keep using the same interface.

RememberProtection proxy → permission check, then forward.
3 The real object lives in another process or machine

Your code calls a normal-looking local object. The proxy forwards the call across the process or machine boundary to the real one. A generated gRPC client stub is a Remote Proxy you have probably already used.

RememberRemote proxy → local stand-in for a far-away object.
🌍 Real-world example ▾

A credit card is a proxy for a bank account. It controls and limits access to the money — a spending limit, a merchant check — without being the account itself. EF Core's lazy-loading entity proxies work the same way for your data: the real query only runs the moment the navigation property is actually touched.
