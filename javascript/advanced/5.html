Your SPA's memory keeps climbing after every page change — what's actually holding on?

"What causes memory leaks in JavaScript, and how would you investigate an SPA whose memory usage keeps growing after navigating between pages?"

Why it matters ▾
  • A real diagnostic question senior engineers get asked directly — "the memory graph keeps climbing" — not a request to recite "JavaScript has garbage collection."
  • Tests whether you understand reachability, the actual rule the engine uses, instead of treating garbage collection as a black box that "just handles it."
  • Detached DOM nodes, forgotten listeners/timers, and long-lived closures are three of the most common real memory leak causes in front-end code, not rare edge cases.
🔥 Easy interview recall

Roots = global object + running call stack → everything reachable from them survives

No path back to any root → eligible for collection

Removed from the DOM, still referenced in JS → detached node — never collected

Think: a leak is never "the garbage collector being broken" — it's something you forgot still points at it.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"JavaScript has garbage collection, so it can't leak memory." The GC only frees objects with no path back to a root — a forgotten listener, timer, or long-lived closure still counts as a path, so the object stays alive even though nothing actually needs it anymore.

🔄 Likely Follow-up

"If I remove a DOM element from the page, why doesn't its memory get freed right away?" Removing it from the document only detaches it visually — if a variable, array, or closure still references that element, it's still reachable, so it stays on the heap as a detached node until every last reference to it is gone too.

🎯 Say this in the interview — the exact lines to land

"The garbage collector only frees objects that are unreachable from a root — the global object or the currently-executing call stack — using mark-and-sweep: mark everything reachable, sweep the rest. Real leaks come from something still holding a reference on purpose or by accident — a detached DOM node, a long-lived closure, or a listener/timer that was never removed."

  • Roots = global object + running call stack — everything else is judged reachable starting from there.
  • Mark-and-sweep → mark what's reachable, sweep what's left unmarked.
  • Detached DOM node → removed from the page but still referenced in JS = never collected.
  • Closures keep their whole captured scope alive as long as the closure itself is reachable — a forgotten long-lived one can pin down large objects.
  • Forgotten listeners/timers → the callback, and everything it closes over, stays alive indefinitely.
  • Investigate growth with heap snapshots taken over time, never a single snapshot on its own.
📖 Explanation ▾

All JavaScript values live on the heap — the memory space the engine manages for you. There's no manual free(); instead the engine periodically decides what's still needed using reachability: starting from a set of roots — the global object and whatever's currently on the call stack — it walks every reference it can follow and marks everything it reaches. Anything left unmarked has no path back to a root, so it's swept: its memory is freed. That's the whole conceptual idea behind mark-and-sweep — reachable survives, unreachable gets freed.

A "memory leak" in JavaScript really means an object that's technically still reachable, so the GC correctly leaves it alone, even though the app no longer needs it. Three common causes: a detached DOM node — an element removed from the page but still held in a variable, array, or closure never gets collected, because JS is still pointing at it. A closure keeps its entire captured scope alive for as long as the closure itself is reachable — a closure that was only meant to run once can end up pinning down large objects it never needed to keep. And a forgotten event listener or timer that's never removed keeps its callback alive indefinitely — and everything that callback closes over goes with it.

Senior scenario: an SPA's memory keeps growing after navigating between pages — walk it through as an investigation, not a definition. Take heap snapshots before and after several navigations, and compare them for object counts that keep climbing instead of settling back down. Look specifically for detached DOM nodes left behind by components that unmounted but left a listener or interval still running. Check for closures capturing something large — a full dataset, a big DOM subtree — that never needed to survive past the page that created it. And check whether the route-change cleanup genuinely removes every listener and subscription it added, rather than assuming it does just because the component "went away."

💻 See the code ▾
JavaScript 
// ❌ Removed from the page, but a variable still points to it
let row = document.getElementById("row-42");
table.removeChild(row);        // gone from the DOM...
// ...but `row` still references it — a detached node, still on the heap

// ✅ Drop the reference once you're done with it
row = null;                // nothing points to it now — eligible for GC

removeChild() only detaches the element from the page's visible tree — the node itself stays on the heap until every JS reference to it (a variable, an array, a closure) is gone too.

JavaScript 
function setup() {
    const bigDataset = loadHugeArray();   // large — meant for one-time use
    const handler = () => log(bigDataset.length);
    // ❌ handler is kept forever, so bigDataset never gets collected
    window.addEventListener("resize", handler);
    // no matching removeEventListener anywhere
}

The listener's closure keeps bigDataset alive for as long as the listener stays registered — forever, in this case, since nothing ever removes it.

JavaScript 
// ✅ Remove the listener (and its closure) when it's no longer needed
function setup() {
    const handler = () => log("resized");
    window.addEventListener("resize", handler);
    return () => window.removeEventListener("resize", handler);  // call on cleanup/unmount
}

Calling removeEventListener drops the engine's own reference to handler — once nothing else points to it either, the handler and everything it closed over can finally be collected.

🌍 Real-world example ▾

A contact you never deleted for someone who moved away. The person (the DOM node, the big object) is gone from where they used to live, but the entry in your phone (a variable, a closure, a listener) still points at them — so it stays in your contacts, taking up space, until you actually delete that entry. Nothing was wrong with your phone's storage; it just correctly kept something you told it, indirectly, to keep.
