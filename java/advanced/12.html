Wrong answer, no answer, or never your turn — three ways concurrency breaks

"What's the difference between a race condition, a deadlock, and starvation?"

Why it matters ▾
🎲 Race Condition
❗ ProblemTwo threads reading and writing the same shared state without coordination can interleave in an order neither of them controls — the result silently depends on timing, not logic.
✅ SolutionA race condition is exactly that: correctness depends on unpredictable thread interleaving. Guard the shared state (synchronized, Lock, Atomic classes) so the outcome stops depending on timing.
RecallRace condition = the answer depends on who got there first.
🔗 Deadlock
❗ ProblemTwo threads can each grab one of two locks and then wait for the other lock, which the other thread is holding — neither can ever proceed.
✅ SolutionA deadlock is that exact circular wait. The classic fix: always acquire multiple locks in the same, consistent order across every thread.
RecallDeadlock = two threads, two locks, each other's missing piece.
🐢 Starvation
❗ ProblemA thread can be technically runnable and never actually blocked, yet keep losing out to other threads for a resource — it's running, just never making real progress.
✅ SolutionThat's starvation: perpetual denial of access, often from priority imbalance or an unfair scheduling/locking policy. A fairness policy (e.g. a fair Lock) is the usual fix.
RecallStarvation = always ready, never picked.
🔥 Easy interview recall

Race condition → wrong result from timing

Deadlock → stuck forever, circular wait

Starvation → never gets a turn

Think: a race gives you the wrong answer. A deadlock gives you no answer. Starvation keeps you waiting for an answer.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

Starvation is not the same as a deadlock. A starved thread is still running and eligible, simply never winning the resource; a deadlocked thread is actually blocked forever, unable to proceed at all.

🔄 Likely Follow-up

"What's the classic fix for a deadlock caused by lock ordering?" Always acquire multiple locks in the same, consistent order across every thread and code path — if thread A always locks X before Y, make sure thread B never locks Y before X. tryLock() with a timeout is a fallback when a consistent order isn't practical.

🎯 Say this in the interview — the exact lines to land

"A race condition means the result depends on unpredictable thread timing. A deadlock means two or more threads are each waiting on a lock the other holds, and neither can proceed. Starvation means a thread is technically running but keeps losing out to others and never makes real progress."

  • Race condition → wrong result, caused by unguarded shared state.
  • Deadlock → stuck forever, classic cause is inconsistent lock-acquisition order.
  • Starvation → never progresses, despite technically being runnable.
  • Fix for a race → guard the shared state — synchronized, Lock, or an Atomic class.
  • Fix for a deadlock → consistent lock order, or tryLock() with a timeout.
📖 Explanation ▾

A race condition happens when correctness depends on which thread's instructions get interleaved in which order — nothing is blocked, nothing hangs, the program just produces a different (and often wrong) answer depending on timing that isn't controlled anywhere in the code. A deadlock is a completely different failure shape: two or more threads are each blocked, waiting on a resource (almost always a lock) that another one of them is holding, and none of them can ever make progress because the wait is circular.

Starvation sits apart from both — a starved thread isn't blocked at all, it's perfectly eligible to run, but something about the scheduling or locking policy keeps picking other threads over it. A classic cause is thread-priority imbalance, or an unfair lock implementation that happens to keep favoring recently-arrived threads over one that's been waiting the longest.

💻 See the code ▾
Java 
int balance = 100;

// two threads both run this concurrently, unguarded
void withdraw(int amount) {
    if (balance >= amount) {       // ❌ check and update aren't one step
        balance -= amount;          // another thread may have changed balance between the two
    }
}

Both threads can pass the check with the same stale balance, then both subtract — the account can go negative despite the guard.

Java 
// Thread 1
synchronized (lockA) {
    synchronized (lockB) { transfer(); }  // ❌ A then B
}

// Thread 2 — same two locks, opposite order
synchronized (lockB) {
    synchronized (lockA) { transfer(); }  // ❌ B then A — classic deadlock
}

If Thread 1 grabs lockA and Thread 2 grabs lockB at nearly the same moment, each then waits forever for the lock the other is holding.

🧭 Use Cases — recognize these when they happen to you ▾
1 Two threads both do check-then-update on a shared account, unguarded

Both threads can read the same balance before either writes back — a withdrawal can silently succeed twice, or the account can go negative despite a guard that looked correct.

RememberCheck-then-act unguarded → classic race condition.
2 Two transfer methods lock the same two accounts in opposite order

A transfer from account A to B locks A then B; a transfer from B to A locks B then A. Run concurrently, each thread can grab its first lock and then wait forever for the other's. A common interview trap: assuming "it'll usually be fine" because it only fails under the right timing.

RememberSame two locks, opposite order → deadlock.
3 A low-priority background thread keeps losing a lock to a flood of requests

A background cleanup thread competing for the same lock as a constant stream of request-handling threads can be technically runnable forever while never actually winning the lock — it's not blocked, it's just never picked.

RememberAlways ready, never picked → starvation, not a deadlock.
🌍 Real-world example ▾

Two transfer operations between the same two accounts occasionally hang completely, with thread dumps showing both threads BLOCKED on each other's lock. That's a classic deadlock from acquiring the two account locks in opposite order. The fix is a single consistent lock order (e.g. always lock the account with the smaller ID first), or tryLock() with a timeout as a fallback.
