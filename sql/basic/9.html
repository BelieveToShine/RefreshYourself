DISTINCT — free to write, not free to run

"What does DISTINCT do, and what's its cost on a large result set?"

Why it matters ▾
🔁 DISTINCT
❗ ProblemA result full of duplicate rows looks like a simple fix — just add DISTINCT — but treating it as a free keyword hides that finding those duplicates is real work, and bolting it onto an already-slow query can make it slower instead of fixing it.
✅ SolutionDISTINCT removes duplicates by comparing the whole selected row, which means the engine has to sort or hash the entire result set first — genuine work whose cost scales with how many rows and columns are involved.
RecallDISTINCT fixes duplicates correctly, but the sort/hash behind it isn't free.
🔥 Easy interview recall

DISTINCT = "dedupe the whole row — but finding duplicates costs a sort/hash over everything."

Think: on a big result set, DISTINCT can be one of the pricier parts of the query, not a free filter keyword.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

DISTINCT is basically free — it's just a keyword. It requires the engine to actually sort or hash the whole result set to detect duplicates, work that scales with the size of that result set — on a large table it can meaningfully add to query cost, not just filter silently for free.

🔄 Likely Follow-up

"Does DISTINCT consider all selected columns, or just one?" All of them — the whole row (every column in the SELECT list) is the unit of comparison; two rows are duplicates only when every selected column matches exactly.

🎯 Say this in the interview — the exact lines to land

"DISTINCT removes duplicate rows by comparing the whole row — every selected column together — and to find those duplicates the engine typically has to sort or hash the entire result set first. That's real work that scales with the size of the result, so on a large query DISTINCT isn't a free filter, it's genuine extra cost."

  • Compares the whole row → every selected column has to match for two rows to count as duplicates.
  • Needs a sort or hash → that's how the engine actually finds the duplicates.
  • Cost scales with size → more rows and columns means more sorting/hashing work.
  • Not a free keyword → on a large result set it can meaningfully add to query cost.
📖 Explanation ▾

DISTINCT removes duplicate rows from whatever the SELECT list returns — but "duplicate" means the whole row, not any single column. Two rows only get removed as duplicates if every column in the SELECT list matches on both of them; add one more column to that list and rows that used to look identical can become unique again.

Finding those duplicates isn't a simple lookup — the engine typically has to sort or hash the entire result set first, so matching rows end up next to each other (or in the same hash bucket) where they can actually be compared. That's real, non-trivial work, and like any sort/hash operation its cost grows with how many rows it's applied to — invisible on a small lookup table, but on a large result set it can become one of the more expensive steps in the whole query.

💻 See the code ▾
SQL 
SELECT DISTINCT City                -- one column: dedupe on City alone
FROM Customers

Simplest case — two rows are duplicates here only if their City values match.

SQL 
SELECT DISTINCT City, Country       -- whole row now = (City, Country) together
FROM Customers

Now a row is only a duplicate if both City and Country match another row — the whole selected row is the unit of comparison, not just City on its own.

🧭 Use Cases — recognize these when they happen to you ▾
1 You just want the unique values from one column

Selecting just City with DISTINCT is the simplest and most common way DISTINCT actually gets used — two rows are duplicates here only if their City values match, so repeated city names collapse down to one row each.

RememberOne column selected → dedupe on that column alone.
2 You add a second column to the SELECT list

Add Country next to City and the whole selected row — (City, Country) together — becomes the unit of comparison. Paris, France and Paris, USA now count as two different rows, even though City alone would have looked identical.

RememberMore selected columns → the whole row has to match to count as a duplicate.
3 You bolt DISTINCT onto an already-slow query to "fix" duplicates

DISTINCT is a correct fix for duplicate rows, but it isn't free — the engine still has to sort or hash the entire result set to find them. Adding it to a query that's already slow on a large result set can make it slower, not faster — a common trap for candidates who treat it as a free filter keyword.

RememberLarge result set → DISTINCT adds real sort/hash cost, not a free filter.
🌍 Real-world example ▾

Sorting a big box of photos to pull out only the unique ones. You can't tell which photos are duplicates by glancing at the box — you have to lay them all out and actually compare them before you can say which are copies. DISTINCT can't skip that same comparison work either; it has to look at every row before it can tell you which ones survive.
