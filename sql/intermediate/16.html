Triggers — code that runs automatically, hidden from the call site

What is a trigger, and why are they often discouraged even though they're a real, working tool?

Why it matters ▾
  • Comes up any time auditing, denormalized data, or "why did this update do more than I expected" gets discussed.
  • Explains a real production surprise: a plain-looking UPDATE silently doing extra work somewhere else entirely.
  • A common opener before a follow-up on when a trigger is actually the right tool versus application code.
🔥 Easy interview recall

Trigger = "code the database runs automatically on INSERT/UPDATE/DELETE — hidden from whoever wrote the statement."

Think: a plain UPDATE can silently insert an audit row, update another table, or fire another trigger — none of it visible in the statement itself.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Triggers should never be used." The real guidance is narrower — don't hide business logic that would be clearer in application code; for something like an audit trail that must hold no matter what touches the table, a trigger is a legitimate, sometimes the only reliable, choice.

🔄 Likely Follow-up

"When would a trigger genuinely be the right tool instead of putting the same logic in application code?" When the behavior has to be enforced no matter what modifies the data — even a DBA's ad-hoc script or a completely different application touching the same table — a true audit trail that can't be bypassed is the classic case.

🎯 Say this in the interview — the exact lines to land

"A trigger is code that runs automatically when a table gets an INSERT, UPDATE, or DELETE — used to enforce rules or side effects a plain constraint can't express. They're often discouraged because that logic is invisible at the call site: a simple UPDATE can silently do far more than it looks like. That doesn't mean never use them — for something like an audit trail that has to hold no matter what touches the table, a trigger is the right, sometimes only, tool."

  • Runs automatically on INSERT/UPDATE/DELETE — nobody calls it directly.
  • Invisible at the call site → a plain UPDATE can hide an audit insert, another table's update, even another trigger.
  • Real risk → cascading triggers can chain into each other, or even loop.
  • Right tool when the rule must hold no matter what touches the table — a true audit trail is the classic case.
  • Wrong tool when it's just hiding logic that would be clearer sitting in application code.
📖 Explanation ▾

A trigger is code attached to a table that the database engine runs automatically whenever a matching INSERT, UPDATE, or DELETE happens — nobody calls it, it just fires. That makes it possible to enforce business rules or side effects a plain constraint can't express: auditing every change to a row, keeping a denormalized summary column in sync, or checking a rule that spans more than one table.

The reason triggers are often discouraged is that same automatic firing. A developer reading UPDATE Orders SET Status = 'Shipped' has no way to tell, from that line alone, that it might also insert an audit row, update a second table, or fire another trigger that fires yet another. That hidden control flow makes a system harder to reason about and to performance-tune — a "simple" update can end up doing far more work than it looks like — and it's easy to accidentally wire two triggers into an infinite cascade between related tables.

None of that makes triggers universally wrong. For something like immutable audit logging, where the rule genuinely has to hold no matter what touches the table — a DBA's ad-hoc script included — a trigger is a legitimate, sometimes the only reliable, choice. The real guidance is narrower than "never use triggers": don't use one to hide logic that would be better off visible in application code.

💻 See the code ▾
SQL 
CREATE TRIGGER trg_Orders_AuditStatus
ON Orders
AFTER UPDATE
AS
BEGIN
    INSERT INTO OrderAudit (OrderId, OldStatus, NewStatus, ChangedAt)
    SELECT d.OrderId, d.Status, i.Status, GETDATE()
    FROM inserted i
    JOIN deleted d ON d.OrderId = i.OrderId;
END;

This never runs on its own — it fires automatically the moment any UPDATE touches Orders, reading the before/after values from the built-in inserted/deleted tables.

SQL 
UPDATE Orders SET Status = 'Shipped' WHERE OrderId = 42;
-- ✅ looks like one simple statement...
-- 🐛 ...but trg_Orders_AuditStatus just fired too — invisible right here

Nothing in this statement hints that an audit row was just written — that's the exact hidden control flow the trap is about.

🌍 Real-world example ▾

Scenario: a team spends an hour debugging why a plain UPDATE Orders SET Status = 'Shipped' is far slower than it should be — profiling shows writes hitting tables the query never even mentions. Check for triggers on Orders first: an AFTER UPDATE trigger doing an audit insert or a cascading update explains extra writes that never show up in the statement itself, and is a far likelier cause than app-level code once that's ruled out.
