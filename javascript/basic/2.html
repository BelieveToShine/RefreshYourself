var vs. let vs. const — the loop bug every interviewer asks about

"What's the difference between var, let, and const — and why does a var loop with setTimeout print the wrong numbers?"

Why it matters ▾
  • Almost every JavaScript interview opens here — it's the fastest way to check whether you actually understand scope, not just syntax.
  • var's function-scope leak is a real source of bugs in loops, callbacks, and conditionals in production code, not just a trivia question.
  • Getting the classic "predict the output" loop question wrong is one of the most common early red flags interviewers watch for.
🔥 Easy interview recall

var → whole function can see it

let → only its block can see it, can change

const → only its block can see it, can't reassign

Think: var leaks out of { }. let and const stay locked inside it.

⚠️ Common Trap

const does not make an object immutable. It only locks the binding — the variable can never point at a different object — but the object's own properties can still be changed freely.

🔄 Likely Follow-up

"If const objects can still be mutated, how do you actually make one immutable?" Call Object.freeze(obj) — it stops property changes (silently in non-strict mode, throws in strict mode), though it's still only shallow: nested objects inside it stay mutable unless you freeze those too.

🎯 Say this in the interview — the exact lines to land

"var is function-scoped and hoisted with an initial value of undefined, so it's accessible (but empty) before its line runs. let and const are block-scoped and hoisted into a Temporal Dead Zone — they exist but throw a ReferenceError if you touch them before their own declaration line. const additionally locks the binding, not the value — you can't reassign it, but if it holds an object you can still mutate that object's properties."

  • var → function scope, redeclarable, usable before declared
  • let → block scope, reassignable, not redeclarable in the same scope
  • const → block scope, binding can't be reassigned or redeclared
  • Hoisting differs by keyword → var hoists as undefined; let/const hoist into the Temporal Dead Zone.
  • const obj = {} → binding is locked, the object's own properties are still mutable.
  • A var loop shares one variable across every iteration — a let loop creates a fresh one each time.
📖 Explanation ▾

var belongs to the nearest function (or the global scope, if there's no function) — an if, for, or any bare { } block does nothing to contain it. let and const belong to the nearest block — the pair of curly braces they're declared inside, whatever that block happens to be.

Redeclaration and reassignment are two separate rules, easy to mix up. var can be redeclared with var again in the same scope with no error. let cannot be redeclared in the same scope, but its value can be reassigned freely. const can't be redeclared or reassigned — the name is permanently bound to the value it was given.

All three are hoisted — moved to the top of their scope during compilation, before any code runs — but they're initialized differently. var is hoisted and immediately set to undefined, so reading it early gives undefined instead of an error. let/const are hoisted but left uninitialized, sitting in the Temporal Dead Zone (TDZ) — the span between the top of the scope and the actual declaration line. Touching them anywhere in that span throws a ReferenceError, not undefined.

const is the one people get backwards: it freezes the name → value link, not the value itself. const user = { name: "Sam" }; user.name = "Alex"; is completely legal — only user = someOtherObject would fail.

💻 See the code ▾
JavaScript 
for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 0);
}
// prints: 3, 3, 3

var i is one function-scoped variable. All 3 callbacks close over the same i — by the time any of them runs, the loop has already finished and i is 3.

JavaScript 
for (let i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 0);
}
// prints: 0, 1, 2

let creates a new block-scoped i for every iteration. Each callback closes over its own copy, frozen at the value it had that round.

JavaScript 
const user = { name: "Sam" };
user.name = "Alex";        // ✅ mutating a property — allowed
user = { name: "Jo" };     // ❌ TypeError: reassigning the binding

const locks the variable, not the object — properties on the object it points to can still change freely.

🌍 Real-world example ▾

A dashboard wires up click handlers for a row of buttons inside a for (var i = ...) loop, expecting each button to log its own index. Every button logs the same last index instead — the classic bug the loop diagram above exists to explain. Switching the loop to let fixes it with a one-character change, because each iteration now gets its own i for the handler to close over.
