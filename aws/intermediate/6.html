S3 vs. EFS — most "shared storage" needs are actually S3 in disguise

"S3 vs. EFS — when does a workload actually need shared, networked file storage instead of object storage?"

Why it matters ▾
  • Tests whether you reach for the familiar-sounding managed service or actually reason about what the workload needs.
  • Comes up any time a design mentions "multiple instances need access to the same files."
  • A common follow-up once someone proposes shared storage in an architecture review — the interviewer wants to hear you justify EFS specifically, not default to it.
🔥 Easy interview recall

S3 → object API, no mount

EFS → real filesystem, mounted by many at once

Think: S3 is a bucket you call. EFS is a drive you mount.

🧠 Visual Mental Model — understand it in 5 seconds
⚠️ Common Trap

"Multiple instances need access, so it must be EFS." Most of those workloads can be redesigned around S3's object API instead — cheaper and more scalable; EFS earns its place only when the app genuinely needs POSIX filesystem semantics (directories, file locking), not just multi-instance access.

🔄 Likely Follow-up

"How would you design S3 for compliance?" Combine Object Lock (WORM) with versioning, cross-region replication, and access logging — so retained records can't be altered or deleted, even by an account admin, until the retention period ends.

🎯 Say this in the interview — the exact lines to land

"S3 is object storage accessed through an API — it's not a mountable filesystem. EFS is a real shared filesystem that multiple EC2 instances or containers mount at the same time, with POSIX semantics like directories and file locking. Most workloads that seem to need shared storage are actually a better fit for S3; I'd only reach for EFS when the application genuinely expects that filesystem behavior."

  • S3 → object storage via an API, not mountable — virtually unlimited scale, pay per GB stored + requests.
  • EFS → a real shared filesystem — mounted by multiple EC2 instances/containers at once, with POSIX semantics.
  • CRR / SRR → automatic S3 replication across or within Regions, for compliance, DR, or latency.
  • Object Lock → WORM retention — even an account admin can't alter or delete a locked object early.
📖 Explanation ▾

S3 is object storage: files ("objects") are addressed by key and read/written through API calls (GET, PUT, and so on), not through a traditional filesystem mount. It scales to effectively unlimited storage and is priced by GB stored plus requests made — no server capacity to plan for.

EFS is a fully-managed NFS filesystem that multiple EC2 instances or containers can mount at the same time, giving real POSIX filesystem semantics — directories, file paths, file locking — that S3 simply doesn't have. That's the only reason to reach for it: an application that genuinely expects to open, lock, and write files through normal filesystem calls, not one that merely happens to run on more than one instance.

For compliance and durability, S3 adds two more pieces on top of the object model: Cross- Region Replication (CRR) and Same-Region Replication (SRR) automatically copy objects to another bucket for disaster recovery, latency, or regulatory reasons, and Object Lock enforces write-once-read-many (WORM) retention — its stricter Compliance mode locks objects so even the account's root user cannot delete or overwrite them until the retention period passes.

🌍 Real-world example ▾

A legacy content-management app expects a real shared filesystem — every web-tier instance needs to read and write the same files through normal file paths. Rewriting it to call S3's object API would be a large change, so it gets migrated onto EFS instead, mounted by every web-tier instance, and keeps working exactly like it did on-premises.
